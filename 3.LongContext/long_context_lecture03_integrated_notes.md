## 开始前：先有一个具体任务，再认识几个基本词

假设你让 Agent 阅读一份长报告，核对基金 A 的半年收益。它需要先读报告，再查表格，发现口径不一致后回看定义，最后写出带来源的结论。整个过程可能调用模型很多次。

这时会遇到四个很实际的问题：**材料放不放得下？每次读这么多要等多久？材料在里面能不能用对？任务做到一半，怎样保存进度继续做？** 全文就是沿着这些问题展开。

另一个贯穿全文的例子是修复代码：用户要求保留 CUDA 12.4，Agent 排查日志、修改参数、运行测试。CUDA 是相关 GPU 计算软件环境，这里只需理解“12.4 是不能随意改变的版本要求”。Agent 必须区分“猜到原因”“改完代码”和“测试确实通过”。这些状态在压缩后仍要分得清。报告中的数字和代码任务的运行编号均按各节说明使用假设值。

| 先认识的词 | 在本文中怎样理解 |
|---|---|
| token | 模型处理文字时使用的小单位，可能是一个字、词的一部分或符号；具体切法由 tokenizer（分词器）决定，不能固定换算成字数 |
| 上下文（Context） | 本次调用实际交给模型的内容，包括指令、消息和工具结果；本轮没有提供的历史，不能假设模型仍然直接看得到 |
| 上下文窗口 | 一次调用可以容纳内容的容量上限；输入和输出怎样共同占用它，取决于具体模型与接口 |
| 向量、维度 | 向量是一组数字，如 `[2, 1]` 有两个数，称为二维；模型用许多数字共同表示特征，单个数通常没有人能直接命名的业务含义 |
| 矩阵、张量 | 矩阵可先理解成一张数字表；张量是更一般的多维数字数组。缓存里的“张量”是计算数据，不是一份可直接阅读的中文摘要 |
| 参数（权重）与训练 | 训练根据数据调整大量参数，学习怎样把输入变成输出；推理是使用已学参数处理当前输入，通常不修改这些长期参数 |
| 层与注意力头 | 层是一轮表示加工，多层依次加工；一个注意力层里可以有多组匹配与读取计算，称为多个“头”。头的作用由训练学出，不预设一头专门认数字、一头专门认姓名 |
| Agent | 在这里指会反复调用模型和工具、根据新结果决定下一步的程序；文件、历史保存和工具执行通常由外围程序配合完成 |

这些是起步所需的概念。Softmax、位置编码、门控等会在用到时解释，不需要现在记住所有缩写。需要回查时可用[附录 A.4 的术语索引](#glossary)。

**遇到数字和符号时**：K、M、B、T 通常分别表示千、百万、十亿、万亿；出现在模型名称中常指参数量，跟在训练量后常指 token 数。长度中的 K 有时按 1024 计，精确算例会明确写出取值。公式里的下标 $t$ 表示第几步，$t-1$ 表示上一步，$\sum$ 表示把多项加起来；同一个字母在不同公式中也可能表示不同量，以就近定义为准。

**两种阅读深度**：正文先回答“为什么需要、怎样工作、有什么代价”；进阶内容再回答“公式怎样推出来、论文具体如何实现”。对于主要关心应用的读者，先连读第 1—3、10—16 章也可以；完整阅读则按现有章节顺序前进。

## 先看懂材料之间的关系

先用四句话认识全图：模型内部可以改变保存和读取历史的方式；训练要让模型学会利用远处信息；服务程序可以复用已经算过的结果；Agent 还需要保存任务进度并按需找回原件。下面的论文名是这些思路的路标，初读时只看每行的中文意思即可。

```text
完整注意力：保留历史位置，让远处信息可以被直接访问
  ├─ Longformer → DSA：保留位置，但减少每次读取的连接
  │                    └─ CSA/HCA：进一步沿序列维度合并历史条目
  ├─ Linear Transformer → Fast Weights → DeltaNet → Gated DeltaNet → KDA
  │                      把历史汇入有限状态，再改进更新与遗忘
  └─ GQA / MLA：每个历史位置用更少的 KV 表示

模型允许更长输入
  → 位置表示是否适应？
  → 训练是否真正要求远距离依赖？
  → 评测能否验证有效上下文？

单次模型调用
  → DistServe：区分 Prefill 与 Decode 的资源需求
  → Prompt Cache：按 schema 预计算模块，检查位置与跨模块依赖
  → SGLang：利用多次调用之间的共享前缀
  → Cache-Aware Routing：把请求送到有用缓存所在的服务节点

上下文依然有限
  → LongLLMLingua：已知当前问题时，选择最有用的内容
  → MemGPT：保留外部原件，需要时重新读取
  → Compaction：保存目标、约束、状态和恢复路径，继续完成任务
  → ReSum 与搜索策略实验：比较摘要续作、裁剪、重置及其训练适配
```

这里的箭头表示本文的理解顺序或问题之间的衔接，不意味着每一项工作都直接继承另一项工作的全部实现。

讲义第 5 页把问题分为 **Capacity** 和 **Efficiency**：前者问“模型能否利用所需证据”，后者问“系统能否承担服务成本”。这两条线最后在 Compaction 汇合：输入缩短以后，后续行为还能否正确？[L03，p.5、pp.47–53](#ref-l03)

## 1. Context 的四个层次：保存过，不代表本轮看得到

**本章先解决一个疑问**：Agent 昨天明明读过报告，今天为什么还会答错？先查“报告是否保存”“本轮是否提供”“模型是否理解正确”，才能知道错在哪一环。

### 1.1 不要把聊天记录、上下文、KV Cache 和外部记忆混成一个东西

沿用核对报告的任务：原始 PDF 在磁盘里，上次读取结果在聊天记录里，本轮请求只带了几个段落，而服务器可能还保存着这些段落先前算出的中间结果。它们互相有关，却各有用途：

| 层次 | 实际保存的对象 | 它能解决什么 | 它不能自动保证什么 |
|---|---|---|---|
| 完整历史 | 用户消息、工具请求与响应、修改和决策记录 | 追溯、重建、复盘 | 历史仍在本轮输入里 |
| 当前上下文 | 本轮实际提供给模型的指令、任务状态与证据 | 当前这一步的直接推理依据 | 模型一定利用正确 |
| KV Cache | 模型对前缀算出的中间张量 | 避免重复计算，供后续位置使用 | 业务事实正确、输入更短 |
| 外部记忆与证据 | 文件、数据库、日志、检索索引 | 扩大可保存和可恢复的信息范围 | 模型知道何时、去哪里重新读取 |

这一区分由讲义的推理、缓存与压缩部分共同构成；MemGPT 则明确规定：外部内容必须显式移入主上下文，才能参与本次模型推理。[L03，pp.7–9、38、48](#ref-l03) [R13，§2.1，pp.2–3](#ref-r13)

“Agent 以前读过这个文件，所以应该知道里面的数据”不是可靠的工程前提。过去的工具结果可能已被截断、压缩或移出工作集；即使仍在输入中，也可能被模型误读。

**更好的心智模型：完整历史是档案室，当前上下文是工作台，KV Cache 是工作台内容已经计算过的中间结果，外部检索是从档案室取回材料的方式**。这个类比用于帮助分层，不意味着这些系统与操作系统具有相同的可靠性保证。

### 1.2 从保留证据到正确行动，需要哪些环节？

作为工程分析，可以把一条证据到正确结论的链路拆成：

```text
证据被系统保留
→ 当前步骤能找到并读取它
→ 相关内容实际进入本轮模型输入
→ 模型正确理解它属于哪个对象、哪个期间
→ 输出或动作经过必要核验
```

后文的“工作集”指当前处理所需、实际带进来的材料；“事实绑定”指把数值和正确的对象、期间、单位等对应起来。例如，记住 8.2% 却把它当作一年收益，数字还在，关系已经错了。这条链用于定位错误，并非概率公式：丢失、未取回、未选入本轮输入、误理解、缺少校验，需要分别检查。

### 1.3 长任务和长输入不是同一个问题

一次阅读 100K token 后回答一个问题，是长输入。一个 Agent 连续执行几十步、每一步都产生新观察，则是长任务。

后者除了检索与理解，还涉及状态更新：哪个结论被撤销、哪个测试已经通过、哪条限制始终有效、哪个工具调用尚未完成。讲义最终采用“压缩之后继续任务”的评测方式，正是因为单次阅读测试不能覆盖这些要求。[L03，pp.46–51](#ref-l03)

**读完自检**：系统保留了整份报告，本轮只发送摘要，模型能直接引用报告第 80 页吗？

## 2. 上下文为什么越来越贵：三种增长与两种推理阶段

**本章的问题**：一次对话看着不长，为什么多聊几轮就越来越慢？要分别看重复带了多少历史、处理这些内容需要多少计算，以及中间结果占多少显存。显存就是 GPU 用来存放权重和计算数据的内存，三种成本不能只用一个 token 数概括。

### 2.1 历史线性增长，累计输入可能平方增长

讲义第 3 页展示五次调用：输入分别为 6K、11K、16K、21K、26K。最后一轮只有 26K，五轮累计却输入了 80K。[L03，p.3](#ref-l03)

原因可以直接从数字看出来：第一轮的 6K 内容，如果后面每次都完整携带，就在五次请求中出现了五次；第二轮新增的内容也会在后续请求中反复出现。“目前有多少历史”和“到目前一共发送过多少输入”自然不同。这里 K 表示约一千个 token。

**推导**：设初始前缀为 $P$，每轮新增 $\Delta$ 个 token，第 $t$ 次调用输入为：

$$
n_t=P+(t-1)\Delta
$$

执行 $T$ 次，累计逻辑输入量为：

$$
\sum_{t=1}^{T}n_t=TP+\frac{\Delta T(T-1)}2
$$

这里计算的是每次请求携带的 token 总量，不是实际重算的 GPU 工作量，也不直接等于服务商账单。缓存会改变实际计算和计费方式，但不一定改变逻辑输入长度。

### 2.2 Prefill 与 Decode：读完已知输入，和生成未知输出，是不同的工作

先想一次普通对话：你把报告发进去，等一会儿看到第一个输出，后面的文字再陆续出现。服务器的主要模型计算可以分成两段。

**Prefill（处理输入）**：报告和问题已经全部给出，模型处理这些已知位置，建立供后续使用的 K/V 中间表示，并得到第一个输出 token 的预测。这些输入位置已知，可以组织并行计算。对于这里讨论的因果生成模型，每个位置的计算只能利用当前位置及之前的信息；这就是“因果约束”，并行计算也不会取消它。

**Decode（逐步生成）**：得到一个输出 token 后，再把它纳入计算，预测下一个。普通自回归生成就是这样使用先前输出继续预测，因此不能把尚未确定的后续 token 当成已知输入一次算完。[R01，§2.1，pp.1–3](#ref-r01)

K/V 的具体含义在第 3 章展开，现在先把 KV Cache 理解为“为后续读取而保存的历史计算结果”。

因此，要分开看两个指标：

| 指标 | 定义 | 常见排查方向 |
|---|---|---|
| TTFT | 请求到达至收到首 token 的时间 | 排队、未缓存 Prefill、调度、传输 |
| TPOT | 首 token 之后，输出 token 的平均生成间隔 | Decode、权重与 KV 访问、批量和并发 |
| 任务总时延 | 完成整个任务的端到端时间 | 所有模型调用、工具、压缩、恢复和重试 |

TTFT 是 Time To First Token，关注“等多久才开始输出”；TPOT 是 Time Per Output Token，这里关注“开始后平均隔多久输出下一个 token”。例如首 token 等了 2 秒，随后每个间隔为 0.05 秒，共输出 101 个 token，则最后一个约在 $2+100\times0.05=7$ 秒时到达。这是解释指标的假设算例。

当输出 $m$ 个 token，且 TPOT 按首 token 后的平均间隔定义时：

$$
T_{\text{request}}=\mathrm{TTFT}+(m-1)\mathrm{TPOT}
$$

TTFT 包括等待等开销，不能只统计 Prefill 的 kernel（执行具体计算的底层程序）运行了多久。DistServe 明确区分执行时间与包含排队的时延，并分别约束两个阶段的服务目标。[R01，§1、§2.2–3.1，pp.2–5](#ref-r01)

### 2.3 “Prefill 计算密集、Decode 带宽密集”有适用条件

计算密集指大量工作花在算术运算上；带宽密集指数据搬运速度容易成为限制。可以把它理解为“算得不够快”和“数据送得不够快”两类瓶颈。这里的批量（batch）是一次一起处理的请求或序列数量；批量增大可能提高设备利用率，但也会占用更多资源。

Prefill 同时处理很多已知位置，容易形成大矩阵运算；低批量 Decode 每步新增的位置很少，却仍然需要访问模型权重和历史状态。DistServe 用具体模型与硬件实验展示了这种差异。[R01，§2.1、§3，pp.3–6](#ref-r01)

但这不是所有长度与批量下的绝对标签。短 Prefill 可能无法充分利用 GPU；Decode 批量足够大后，也会逐渐提高计算利用率。部署时应该测真实工作区间，不能只依据这两个词推断瓶颈。

### 2.4 Attention 的平方复杂度，是另一种增长

**先数比较次数**：100 个位置两两比较，完整方阵有 $100\times100=10000$ 个格子；200 个位置则有 40000 个。长度翻倍，格子数变成四倍。因果注意力只看当前及之前的位置，使用约半张方阵，增长趋势仍然是平方级。

但生成时如果旧位置的 K/V 已经保存，新来一个位置只需要新增一行对历史的比较。历史从 100 增至 200，这一行的比较数大致翻倍。**整张表增长与新增一行增长，要分开看。** 大写 $O$ 描述规模增大时的主要增长趋势，不是精确运行秒数；$d$ 表示相关向量宽度，宽度越大，每次比较也越费计算。

常规稠密注意力在长度为 $n$ 的 Prefill 上，需要大约 $O(n^2d)$ 的成对计算。已有 KV Cache 时，单步 Decode 新增一个 Query，对历史做比较，注意力部分约为 $O(nd)$，不是每一步都重算全部 $n\times n$。[L03，pp.10、19](#ref-l03) [R03，§3.2、§4](#ref-r03)

**不要混淆**：多轮重复携带历史导致的累计输入增长、单次 Prefill 的成对计算增长，以及单步 Decode 的历史读取增长。

<details>
<summary>进阶：多轮注意力计算量怎样累积</summary>

**进一步推导**：固定初始长度 $P$、每轮新增量 $\Delta>0$ 和向量宽度 $d$，只考察轮数 $T$ 很大时的主要增长项。若每次完整重算稠密 Prefill，有：

$$
\sum_{t=1}^{T}O(n_t^2d)=O(\Delta^2T^3d)
$$

如果前缀完全可复用，只计算新增 $\Delta$ 个位置与历史的交互，相关累计注意力工作可以降到 $O(\Delta^2T^2d)$ 的量级。这些写法省略了依赖初始长度 $P$ 的低阶项；当初始材料很大、轮数较少时，不能只看这个最高阶项判断实际成本。这里讨论的是特定假设下的注意力工作，不是完整模型的通用运行时间、网络开销或 API 费用。

</details>

这些增长方式解释了为什么 Agent 系统特别需要复用：**缓存可以避免一次次从头重算，但历史的存储和读取仍有成本**。

### 2.5 显存还有一条独立的线：KV 随历史增长

可以先按“每个位置要保存多少数字 × 位置数量”算空间。模型有多层，每层可能有多组 K/V，每组又有多个数，所以还要乘层数、KV 头数和每头维度。这里的“头”是第 3 章将解释的一组注意力计算，不需要先理解所有结构细节才能读这个乘法。

对层配置相同的常规 MHA/GQA，逻辑 KV 存储量按张量形状计算为：

$$
M_{\mathrm{KV}}=2L\,n\,H_{\mathrm{KV}}\,d_h\,b
$$

$L$ 为层数，$H_{\mathrm{KV}}$ 为 KV 头数，$d_h$ 为头维度，$b$ 为每元素字节数，2 表示 K 和 V。GQA 的出发点正是减少 KV 存储和读取带宽。[R10，§1–2，pp.1–2](#ref-r10)

**假设配置算例**：32 层、8 个 KV 头、每头 128 维、每元素 2 字节，长度取 $128K=131072$：

$$
M_{\mathrm{KV}}=16\ \mathrm{GiB}
$$

这里 $128K$ 明确按 $128\times1024$ 取值；GiB 是 $1024^3$ 字节。上述结果仅是一个请求、全模型合计的逻辑 KV，不包含模型权重、工作空间与分配开销。八个独立且完整驻留、没有共享的请求，对应 128 GiB 的逻辑 KV。把缓存分到多张设备、共享重复部分、用更少字节表示每个数，或采用不同层结构，都会改变实际物理占用。

**“单请求能跑 128K”和“能以合适并发服务 128K”是不同能力**。

**读完自检**：前缀缓存已经命中，是否意味着后续生成不再付出读取历史的成本？

<details>
<summary>参考答案</summary>

不是。缓存减少重复计算，但历史 K/V 仍占空间，新位置仍可能读取历史。累计输入量、计算量和显存占用要分别看。

</details>

## 3. 回到 Transformer：完整注意力用什么代价，换来了什么？

**接着上一章**：我们已经知道历史越长，读取越贵。现在先理解模型究竟怎样读历史，后面才看得懂各类省钱方法。注意力可以先理解为：当前位置对可见历史做匹配，把匹配结果变成权重，再汇合对应的信息。

这一章主要讨论从左到右生成的模型：“完整”或“稠密”注意力指没有进一步删减允许的读取连接，仍然遵守不能看未来位置的规则。第 4 章的 Longformer 文档编码例子允许双向阅读，那里会另作区分。

### 3.1 最初的价值：缩短信息传播路径

传统循环模型按顺序读取，每读一步就更新内部记录。第 1 步的信息若要影响第 1000 步，就需要经受中间许多次更新。公式中的 $x_t$ 是第 $t$ 步输入，$h_{t-1}$ 是此前记录，$f$ 是更新规则：

$$
h_t=f(h_{t-1},x_t)
$$

早期信息要影响很晚的输出，需要经过多次更新。Transformer 则让当前位置与远处位置建立直接注意力连接。原论文第 6 页表 1 不只比较运算复杂度，还比较顺序操作数量和最大信息路径长度；缩短长距离依赖的传播路径，是其重要动机。[R03，§4，pp.6–7](#ref-r03)

以代码为例：第 2000 行调用第 20 行定义的函数。系统可以要求中间处理不断转交定义，也可以保留早期位置，需要时直接读取。完整注意力提供的是后一种访问机会。

**完整注意力保留了一种机会：当前位置可以直接参与对远处位置的读取计算。** “历史位置的直接可寻址性”说的就是这件事。读取的是那个位置的内部表示，能否据此还原准确事实仍取决于模型。这是本文对原论文设计取舍的概括。

### 3.2 Q、K、V 是学习出来的访问机制

用报告问答来理解：当前正在生成“半年收益”的回答，需要找到与这个问题有关的历史信息。注意力的基本过程可以拆成三步：

1. **形成匹配表示**。当前位置生成 Query（Q）；每个可见位置提供 Key（K）。Q 和 K 都是向量，用来计算匹配分数。
2. **把分数变成权重**。Softmax 对每个分数取指数，再除以这些指数的总和，得到非负且总和为 1 的一组权重。分数更高，通常得到更大的权重。
3. **按权重汇合信息**。每个历史位置还提供 Value（V）向量，把这些向量按相应权重相加，就得到这组注意力的输出。

“Q 想找什么、K 怎样被找到、V 读出什么”是帮助记忆的说法。它们都由模型从表示中计算出来，既不是人工填写的检索词，也不是原文字符串。[R03，§3.2，pp.3–5](#ref-r03)

**跟着算一次（假设数字）**：先从指数转换后的正数开始，假设它们为 $[2,1,1]$。除以总和 4，权重就是 $[0.5,0.25,0.25]$。取指数的计算暂时不用手算；这里先看清“转换成正数 → 除以总和 → 按比例汇合”的过程。如果为了演示，将三个 Value 简化为一维数值 $[10,20,40]$，输出就是：

$$
0.5\times10+0.25\times20+0.25\times40=20
$$

这个 20 是一次加权计算的结果；实际 Value 通常是多维内部表示，注意力输出还会经过后续层，不能把它直接当作报告收益的算术平均。这个例子只说明**匹配如何影响各位置的信息贡献**。

还要区分两个同名词：这里的“注意力权重”是模型针对当前输入算出的比例；开头说的“模型权重”是训练学到的参数。一次回答中注意力比例改变，不代表模型重新训练了长期参数。

**再读公式**：$X$ 是输入表示组成的矩阵，$W_Q,W_K,W_V$ 是训练学到的变换参数。同一份输入分别经过三种变换，得到 Q、K、V：

$$
Q=XW_Q,\qquad K=XW_K,\qquad V=XW_V
$$

$$
O=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}+M\right)V
$$

从左到右看，$QK^\top$ 收集各位置之间的匹配分数，$\sqrt{d_k}$ 用于缩放分数，$M$ 排除不允许读取的位置，Softmax 对每个 Query 对应的那一行分别产生权重，最后乘 $V$ 完成加权汇合。每一行的权重和为 1，不能把整张分数表混在一起归一化。$\top$ 表示转置，也就是把矩阵的行列交换。两个向量的内积则是对应数字相乘后求和，例如 $[1,2]$ 与 $[3,4]$ 的内积为 $1\times3+2\times4=11$；这里用它计算匹配。

“掩码”就是把不允许读取的位置挡住。公式中，对当前位置及之前的位置加 0；对未来位置加 $-\infty$，经 Softmax 后相应权重为 0。Q/K/V 是学习到的数值表示，并不保证精确检索或理解。[R03，§3.2，pp.3–5](#ref-r03)

完整注意力保留了读取远处位置的通道，却没有保证 Query 一定找到正确证据，更没有保证模型把数字、对象、期间和版本正确绑定。

**多头和 KV Cache 接在哪里？** 一个注意力层可以并行做多组这样的计算，各组称为一个头，再把输出组合起来。普通因果生成中，旧位置不能看到新生成的未来位置；在前缀及计算条件不变时，它们已经算出的 K/V 可以保存并复用。新位置生成新的 Q，读取这些历史 K/V。旧 Q 不承担未来位置查询历史的职责，因此这里缓存的是 K/V。第 7 章讨论多个头怎样共享或压缩这些表示，第 10 章再讨论跨请求复用条件。

### 3.3 长度扩展改变了原始计算取舍

原论文讨论自注意力相对循环层的计算优势时，提到当时常见的 $n<d$ 区间；同时提出可以为很长序列使用受限邻域，代价是信息路径变长。[R03，p.7](#ref-r03)

这说明后续研究不是简单地把“错误设计”修好，而是在新的长度与硬件区间，重新分配成本。

下表是第 4—7 章的导航。先看每行“保留什么、改变什么”，方法名称随后逐个解释，不需要现在记住全部缩写。

| 路线 | 保留什么 | 改变什么 | 新风险 |
|---|---|---|---|
| 完整注意力 | 显式历史位置 | 每次对可见历史做稠密读取 | 存储与读取昂贵，仍可能利用错误 |
| 滑动窗口 | 局部可直接访问的位置 | 限制连接范围 | 远处信息需要间接传递或额外全局层 |
| 内容相关稀疏注意力 | 历史位置及其状态 | 按 Query 选择读取集合 | 选择器漏掉证据 |
| CSA/HCA 序列压缩 | 随长度增长的压缩条目与近期窗口 | 合并多个位置，再稀疏或稠密读取 | 压缩丢失细节、块级可见性限制 |
| 线性/循环状态 | 有限大小的累计表示 | 写入时合并历史 | 容量、干扰与不可直接回读原位置 |

## 4. Longformer → DSA → CSA/HCA：减少连接，也可以合并历史条目

**本章的问题**：每个位置都和所有可见历史比较，成本太高，能否少读一点？这里有三种做法：预先规定只读附近与少量全局位置；临时挑出更相关的位置；先把多个位置合成较少条目再读。下文依次说明它们省在哪里，又可能漏掉什么。

**讲义连接**：第 14、18、24 页。Longformer 解释固定的局部与全局连接；DSA 进一步讨论如何让选择随 Query 改变；DeepSeek-V4 附件补充沿序列维度压缩的路线。

### 4.1 Longformer 不只是“只看附近”

假设有 1000 个位置，每个位置原本要考虑很大范围的内容。现在规定多数位置只与附近 32 个位置交互，连接数就更接近“1000 × 32”，而不是“1000 × 1000”。这就是滑动窗口的基本直觉；具体方向和边界取决于模型是双向阅读还是因果生成。

局部窗口令每个位置只读取附近 $w$ 个位置，相关计算从 $O(n^2)$ 变成 $O(nw)$。多层堆叠会扩大感受野；膨胀窗口则在连接中留出间隔，用相近的连接数量覆盖更远的位置。[R04，§3.1，pp.3–4](#ref-r04)

“感受野”指一个位置经过这些计算后，可能受到多远范围的信息影响。如果一层只读邻居，下一层可以通过邻居间接接收到更远的信息。“膨胀窗口”则类似隔几个位置读一次，覆盖得更远，但中间留有空档。

但 Longformer 没有停在局部窗口。其文档编码任务加入少量全局位置：分类时使用 `[CLS]` 这个负责汇总分类信息的特殊位置，问答时让问题 token 获得全局注意力。全局位置可以读取全文，其他位置也可以读取它；全局与局部注意力还使用不同的投影参数，也就是用不同的变换生成相应表示。[R04，§3.1，p.4](#ref-r04)

因此，更完整的理解是：**大量位置负责局部内容加工，少量与任务相关的位置负责全文信息交互**。

这里存在任务形态边界。Longformer 的上述全局连接是对称的，适用于其编码器式文档任务；讲义第 18 页展示的却是因果窗口。不能把双向连接不加修改地搬进自回归生成模型。

### 4.2 感受野扩大，不等于直接读取原始位置

多层局部网络可以逐步传递远处信息，但“远处信息经过多个中间表示传到了这里”，与“当前 Query 可以直接读取那个位置的表示”不同。

**理解**：如果报告开头定义“所有收益均为累计收益”，而后面才出现数字，纯局部网络需要依靠中间位置传递这条定义；全局注意力则提供更直接的访问路径。两个系统都可能完成任务，但它们对信息传递、表示容量与学习的要求不同。

### 4.3 消融实验：省下连接以后，全局通道的重要性更清楚了

消融实验就是改变或去掉某个组件，再看结果怎样变化。这里要检验：效果来自“能放更长文本”，还是也依赖全局信息通道？表中的准确率越高越好，先看最后两行的变化，再读各行具体改变了哪些条件。

Longformer 第 9 页的 WikiHop 开发集消融如下。除表中特别指定的因素外，相关设置使用相同的五轮微调条件。

| 配置 | 准确率 |
|---|---:|
| Longformer，序列长度 4096 | 73.8 |
| 序列长度缩短到 2048 | 73.1 |
| 去掉全局注意力的独立投影 | 72.2 |
| 同时去掉独立投影与全局注意力 | 65.5 |

来源：[R04，§6.5，p.9，表 10](#ref-r04)。

最后一行同时改变两个因素，不能把全部下降归因于“只去掉全局注意力”。不过结合前一行，可以看到全局信息通道与独立投影的作用。实验说明，增加窗口并不是全部；网络是否有适合任务的信息交换路径，也很重要。

### 4.4 更少 FLOPs 不自动意味着更快

FLOPs 是浮点运算次数，用来描述算术工作量。GPU 擅长成批处理规则的大块计算；如果省掉一些运算，却增加很多零碎读取和调度，实际耗时仍可能更长。就像搬货次数少了，但每次都要绕路找货，总时间未必减少。

Longformer 比较了循环版、分块向量化版和自定义 CUDA 版。循环版节省内存，但速度很慢，主要用于测试；分块版只支持非膨胀窗口；CUDA 实现支持更完整的模式。[R04，§3.2，p.4](#ref-r04)

**工程启示**：把一个大矩阵乘法改成许多零碎读取和小操作，理论运算量可能减少，但 GPU 利用率也可能下降。研究架构时要同时看数学复杂度、访存模式、矩阵运算规模和实际 kernel，而不能只看 $O(n)$。

### 4.5 DSA：把预先规定的连接，变成 Query 相关的选择

固定窗口按预先规定的相对范围读取，例如“当前位置之前的 32 个位置”。窗口会随当前位置移动，但不会因为问题需要就自动跳到很远的证据处。DSA（DeepSeek Sparse Attention）增加一个较轻的筛选步骤：先估计哪些历史位置更值得读，再把主要计算用在它们身上。Indexer 是这个打分器；Top-K 指按分数保留前 K 个，K 在这里是数量，不是 Key 矩阵。

附件 `009_DeepSeek_Sparse_Attention.pdf` 的实际内容是 DeepSeek-V3.2 技术报告。其 DSA 由 lightning indexer 与细粒度 token 选择组成：先给历史位置打分，再选择 Top-K KV 条目执行主注意力。[R09，§2.1，pp.3–4](#ref-r09)

```text
当前隐藏表示
→ 轻量 indexer 计算历史位置的匹配分数
→ Top-K 选择
→ 在选中位置上进行主注意力，并重新归一化
```

Longformer 的固定模式成本可预测，但不能为每个 Query 灵活改变连接；DSA 的选择更灵活，却增加了选择错误。当前层没有选中的位置，主注意力就无法在这一层直接读取。这个结论对应讲义第 24 页的对比。[L03，p.24](#ref-l03)

### 4.6 DSA 为什么需要继续训练？

筛选器必须学会选，主模型也要适应“只能读到选中位置”的环境。继续训练指从已经训练好的模型出发，再用数据调整参数；冻结主模型则表示这个阶段不更新它的参数，只训练指定组件。损失是训练时衡量预测与目标差距的量，训练尝试降低这种差距。

报告首先保留稠密注意力、冻结主模型，只训练 indexer，使其输出分布接近主注意力分布；之后启用稀疏选择，再让主模型适应稀疏模式。主模型使用语言建模损失，indexer 使用单独的分布匹配损失。[R09，§2.1.1，p.4](#ref-r09)

其配置中，warm-up 约 2.1B token；稀疏训练为每个 Query 选择 2048 个 KV token，并使用约 943.7B token 的继续训练。这里引用数字是为了说明适配工作的量级，不是给出可迁移到任意模型的训练配方。

因此，不能把论文方案理解成“给现成模型换一个 Top-K kernel”。选择器、主模型适配与高效实现，都属于方案的一部分。

### 4.7 DSA 没有让所有平方项消失

报告明确写道，主注意力从 $O(n^2)$ 降到 $O(nK)$，但 lightning indexer 仍有 $O(n^2)$ 复杂度，只是计算常数更小。短序列 Prefill 还使用专门实现，以适应该区间的效率特征。[R09，§2.3，p.5](#ref-r09)

**准确的结论：DSA 减少了昂贵的稠密主注意力工作，不等于整个模型已经严格线性**。

### 4.8 与应用层 RAG 的关系

RAG（检索增强生成）先从外部资料里找相关片段，再把找到的内容交给模型回答问题。例如先检索基金 A 的收益表，再让模型依据该表组织回答。

**类比，而非机制等价**：DSA 和 RAG 都可以被描述为“先筛选，再精读”。筛选没有提供关键证据，后续处理就缺乏直接依据。

但 RAG 在应用层选择文档或片段；DSA 在模型内部、针对隐藏表示进行 token 选择。它们的训练方式、选择粒度与可审计性不同。不要用“模型内部已有稀疏检索”推导“应用不需要检索和证据管理”。

### 4.9 CSA 与 HCA：还可以先合并历史，再决定怎么读

**先数条目，再看公式名**：假设 1000 个历史位置按每 10 个汇成一个条目，远处历史就约有 100 个条目可读。然后还可以选择“只读其中一部分”，或“把这 100 个全读一遍”。CSA 与 HCA 分别体现这些组合思路；近期细节另用局部窗口保留。这个数字例子只说明条目数变化，真实方案的压缩权重、重叠与因果边界见下文。

DeepSeek-V4 附件增加了一条不能仅用“每条 KV 存得更窄”解释的路线：**沿序列维度减少历史条目数**。其两种分支分别为：[R29，§2.3，pp.9–13](#ref-r29)

| 分支 | 历史怎样保存 | 当前 Query 怎样读取 |
|---|---|---|
| CSA：Compressed Sparse Attention | 压缩后的条目数约为原来的 $1/m$；论文使用相邻块重叠的加权压缩 | indexer 从压缩条目中选 Top-K，再执行主注意力 |
| HCA：Heavily Compressed Attention | 使用更大的压缩因子 $m'$，采用非重叠块压缩 | 对可见的压缩条目执行稠密注意力 |
| 两者的局部窗口分支 | 保留近期未压缩的 KV | 与压缩条目共同参与注意力，补充局部细节 |

CSA 的一个条目可汇集相邻两个块的信息，但相邻条目的覆盖有重叠，因此条目总数的压缩率仍是约 $m$，不是 $2m$。压缩权重由模型学习，不是把业务文本生成自然语言摘要。

压缩还带来因果性问题：当前 token 不能读取包含未来 token 的完整压缩块。因此，论文只让 Query 访问此前已经完成的压缩块，并用滑动窗口补充当前块内和近期信息。这个窗口同时承担局部建模与弥补块级可见性缺口的作用。[R29，§2.3.3，p.13](#ref-r29)

**机制上的区别**：MLA 缩小每个位置的表示，DSA 选择读取位置，CSA/HCA 合并多个位置，KDA 将历史写入固定大小的状态。CSA/HCA 的压缩条目仍随长度增长，不能据此称为固定状态模型；对于固定压缩因子，HCA 的稠密读取和 CSA 的全候选索引仍可能保留平方级 Prefill 工作。这是由其条目数和连接方式得到的复杂度判断，不是“整个模型已经线性”的结论。

**读完自检**：只选历史中的 100 个位置，与把 1000 个位置合成 100 个条目，有什么区别？

<details>
<summary>参考答案</summary>

前者主要改变读哪些位置，后者先改变历史怎样表示。合并可能丢掉条目内部细节；筛选可能漏掉关键位置，两种操作还可以组合。

</details>

## 5. 线性注意力 → Fast Weights → DeltaNet：从历史列表到可更新的关联状态

**换一种保存思路**：上一章保留逐位置的历史，或者把多个位置汇成较少的条目；即使做了块压缩，条目数通常仍随历史增长。本章考虑每读到新内容就更新一张大小固定的数字表，以后从这张表读取信息。好处是表不会随历史一直变大；困难是越来越多的信息写进同一个空间，可能混在一起，也可能难以正确替换旧信息。

理解顺序是：5.1—5.3 看怎样汇总，5.4—5.5 看为什么混淆，5.6 看怎样修正，5.7—5.9 再深入更新的边界与数学解释。这张表是模型内部的数值状态，和第 13 章由程序保存的中文任务摘要不同。

**讲义连接**：第 19–21 页。这条链解释：固定状态为什么高效、为什么会干扰，以及怎样改进更新。

### 5.1 线性注意力改变了保存历史的方式

这份固定大小的记录包含两部分：$S$ 是关联表，用于汇总信息；$z$ 用于归一化，让最后的读取按匹配程度形成加权结果。这里先假设 Q 和 K 已经转换成用于匹配的特征，具体转换方式放在下面的进阶公式中。

**两条历史的算例**：两条记录的 Key 特征分别是 $[1,0]$、$[0,1]$，为简化计算，Value 分别只有一个数：10、20。按以下步骤保存和读取：

1. **写入关联表**：第一条贡献 $[1\times10,0\times10]=[10,0]$，第二条贡献 $[0\times20,1\times20]=[0,20]$。加起来，表里的两个数是 10 和 20，即 $S=[10,20]^\top$。
2. **记录归一化所需信息**：把两条 Key 特征相加，得到 $z=[1,1]^\top$。这一步没有乘 Value。
3. **只匹配第一个方向**：查询特征为 $[1,0]$，从 $S$ 计算分子 $1\times10+0\times20=10$，从 $z$ 计算分母 $1\times1+0\times1=1$，读出 $10/1=10$。
4. **同时匹配两个方向**：查询为 $[1,1]$，分子为 $10+20=30$，分母为 $1+1=2$，读出 $30/2=15$。

第二次查询同时匹配两条关联，因此得到混合结果。后续再来新记录，继续更新同样大小的 $S$ 和 $z$ 即可。但真实模型不能预设特征总能像此例一样清楚地区分对象；混淆的问题会在 5.4 节接着讨论。

<details>
<summary>进阶：从逐条加权到累计状态的公式</summary>

先把第 3 章的读取过程写成一句话：对每条历史算匹配程度，把它的 Value 乘上这个程度，再把贡献汇总。下面分子的含义就是这个加权汇总，分母则用匹配程度的总和做归一化。$i\le t$ 表示只使用截至当前第 $t$ 步可见的位置，$\operatorname{sim}$ 表示匹配程度：

$$
o_t=\frac{\sum_{i\le t}\operatorname{sim}(q_t,k_i)v_i}
{\sum_{i\le t}\operatorname{sim}(q_t,k_i)}
$$

如果每次都逐条处理历史，历史越长，单次读取就越贵。《Transformers are RNNs》换用一种可以拆开的相似度。先用 $\phi$ 把 Q 和 K 转换成另一组特征，再求内积；$\phi$ 读作 phi，称为特征映射。它让历史一侧的计算可以提前汇总：

$$
\operatorname{sim}(q,k)=\phi(q)^\top\phi(k)
$$

于是，保存两份累计结果：$S_t$ 汇总 Key 与 Value 的关联，$z_t$ 汇总 Key 特征，供之后计算归一化分母。$\sum$ 就是把各位置的项加起来：

$$
S_t=\sum_{i\le t}\phi(k_i)v_i^\top,\qquad
z_t=\sum_{i\le t}\phi(k_i)
$$

再读取：

$$
o_t=\frac{S_t^\top\phi(q_t)}{z_t^\top\phi(q_t)}
$$

递推更新为：

$$
S_t=S_{t-1}+\phi(k_t)v_t^\top,\qquad
z_t=z_{t-1}+\phi(k_t)
$$

若特征维度为 $m$，主要矩阵状态大小为 $m\times d_v$，不再随序列长度增长。可以把 $S_t$ 想成一张行列数固定、格子里的数持续更新的表。它汇总了很多位置的贡献，却没有为每个位置保留一个独立格子。论文通过相似度分解、结合律与因果前缀累积得到这个形式。[R05，§3.2–3.3，pp.3–4](#ref-r05)

</details>

### 5.2 这里不是把原始 Softmax 无损地重新排列

上一节省掉逐条回看，靠的是换用了能够提前汇总的相似度。结合律只允许在条件成立的矩阵乘法中改变分组：先算 Q 与所有 K 的关系，或者先汇总 K 与 V。原始 Softmax 夹在中间，不能直接越过它改变顺序。

<details>
<summary>进阶：为什么不能越过 Softmax 直接重排乘法</summary>

结合律允许：

$$
(QK^\top)V=Q(K^\top V)
$$

但不能据此把带 Softmax 的表达式任意重排。论文明确指出，精确指数核一般对应无限维特征映射；实际采用有限维特征映射，改变了注意力机制。其一个实验选择为 $\phi(x)=\operatorname{ELU}(x)+1$。[R05，§3.2.1，pp.3–4](#ref-r05)

讲义第 20 页为了突出结构，使用了更简化的无归一化双线性形式。它是教学用简化，不是原始论文全部细节。理解讲义后，再读论文中的 $\phi$ 和归一化项，才能把两者接起来。[L03，p.20](#ref-l03)

</details>

### 5.3 “线性”主要是对长度而言

每一步仍需更新和读取一个矩阵，成本与状态维度有关。它的优势是这些操作不必随着已读历史持续变大，而不是所有维度和所有层的计算都非常小。

训练时还要保留或重算供参数更新使用的中间结果，这些中间表示常称为激活；反向传播计算误差对参数的影响，优化器再据此更新参数。因此，推理时用于汇总历史的状态大小固定，不代表训练的全部内存也固定。论文专门推导累计求和式的反向传播，减少朴素实现保存所有中间状态的开销，但完整输入输出和其他激活仍需计入。[R05，§3.3.1，p.4](#ref-r05)

### 5.4 Fast Weights：固定状态实际上是一种关联记忆

“关联记忆”指根据一组特征读出与之关联的信息。它面临的问题可以沿用 5.1 节算例：如果两条不同记录的 Key 都是 $[1,0]$，它们的贡献就写向同一方向。单凭相同的查询，基本存储机制无法再判断你要的是哪一条。Key 即使不完全相同，只要有重叠，也可能把别的 Value 混进来，这叫串扰。

**从这里起换一个简化形式**：5.1 节的读出含有归一化分母；下面为单独观察关联的写入与更新，省略该分母和特征映射，只看累计状态本身。两种形式的具体数值不能混用。例如取一维 Key 和查询均为 1，先后写入 10 和 12，归一化累加会读出平均值 11，无归一化累加则会读出 22；两者都没有直接表达“最新值应为 12”。下面采用后一种形式：

$$
S=\sum_i k_iv_i^\top
$$

对 Query $q$ 读取：

$$
S^\top q=\sum_i v_i(k_i^\top q)
$$

只要某个非目标 Key 与 $q$ 也有相似度，其 Value 就会混入结果。《Linear Transformers Are Secretly Fast Weight Programmers》从这个角度指出：有限维空间中不可能容纳无限多个相互正交的 Key，持续叠加关联会遇到容量与串扰问题。[R06，§4.1，pp.3–4](#ref-r06)

这不是“一个深层模型最多记住 $m$ 个 token”的定理，而是对该基本关联存储方式的容量分析。层、多头、学习到的表示和任务结构，都会影响完整模型的表现。

**两篇论文的衔接：前一篇展示如何用固定状态降低成本；后一篇追问固定状态里如何存、如何读、何时会互相干扰**。

### 5.5 “存不下”与“不会更新”必须分开测

Fast Weights 论文设计了两类合成实验。第一类增加不同 Key 的数量，检验容量；第二类允许同一个 Key 被重新赋值，要求返回最近的 Value，检验更新能力。第二类的一个设置使用 20 个不同 Key、40 个位置；查询在序列末尾出现，模型此前不知道最终会问什么。[R06，§6.1，pp.6–7](#ref-r06)

这比单纯增加长度更有诊断价值。对于 Agent，“记住旧配置”和“知道旧配置已失效”不是同一个任务。

### 5.6 Delta Rule：先读当前关联，再写入需要纠正的差额

**先走一个简化例子**：沿用 5.4 节不带归一化分母的状态，取一维 Key 为 1，当前读出 10，新输入希望它对应 12。继续把 12 累加进去会得到 22；更合适的更新是先求差额 $12-10=2$，再按差额修正。完整修正后是 12；只修正一半则是 11。这里的 Key 长度为 1，满足后面精确混合公式的条件；真实模型的向量关联还可能互相影响。

Delta 就是差额。公式把这件事分成三步。先用当前 Key 从旧状态读取，看看现在记成了什么；$\hat v_t$ 上面的帽子表示读出的预测值：

$$
\hat v_t=S_{t-1}^\top k_t
$$

再用目标值减去读出值，得到误差 $e_t$：

$$
e_t=v_t-\hat v_t
$$

最后沿当前 Key 对应的方向写入差额；$\beta_t$ 是可学习的更新强度，控制这次修正多少：

$$
S_t=S_{t-1}+\beta_tk_te_t^\top
$$

直白地说：**不是持续累加新内容，而是检查目前记成了什么，再按差额修正**。Fast Weights 将这描述为读取旧关联、移除对应旧内容、写入可学习的新旧混合。[R06，§4.2，pp.4–5](#ref-r06)

<details>
<summary>进阶：Delta 精确替换所需的条件</summary>

**推导**：如果 $\lVert k_t\rVert_2=1$，则沿当前 Key 读取的新结果为：

$$
S_t^\top k_t=(1-\beta_t)S_{t-1}^\top k_t+\beta_tv_t
$$

当 $\beta_t=1$ 时，当前 Key 的读取被修正为新值。没有单位范数等条件时，不能直接照搬这个精确替换解释。

这里的“单位范数”就是向量长度为 1。加上这个条件，公式才给出上述精确的新旧混合；实际大模型也不是直接把业务数字 10 和 12 填进这张状态表。

</details>

### 5.7 定向更新不是完全隔离更新

给一条关联纠错，也可能改变其他查询读出的结果，因为它们可能使用重叠的特征。两个方向“正交”指内积为 0，在这个简化更新规则下，正交能保证本次更新不改变另一查询的读出。这个几何条件不能直接翻译成“两个业务对象不同，所以一定互不影响”。

<details>
<summary>进阶：其他查询会受到多大影响</summary>

**推导**：对另一个 Query $q$，这次更新造成：

$$
\Delta o=\beta_t(k_t^\top q)e_t
$$

当更新强度和误差都非零时，与 $k_t$ 正交的查询读出保持不变，非正交查询则会受影响；若误差为零或更新强度为零，本来就没有有效更新。因此，讲义中“无关记忆保留”应结合这些条件理解，不能当作数据库事务级别的独立记录更新。[L03，p.21](#ref-l03)

</details>

### 5.8 为什么叫“快权重”：上下文处理与在线学习的连接

“慢”和“快”描述更新发生的时间尺度：生成 Q/K/V 的参数主要在训练中学习，处理当前序列时通常保持不变；关联状态则每读一个输入就能变化，所以称为快权重。这里的在线学习指边接收当前序列边调整这个快速状态。下面用梯度下降——沿降低误差的方向更新——说明两者的数学联系。

<details>
<summary>进阶：将状态更新写成一步梯度下降</summary>

Delta 更新可以写成对重建损失的一步梯度下降：

$$
\ell_t(S)=\frac12\lVert S^\top k_t-v_t\rVert_2^2
$$

$$
S_t=S_{t-1}-\beta_t\nabla_S\ell_t(S_{t-1})
$$

慢权重学习怎样生成 Query、Key、Value 与更新强度；快速状态 $S_t$ 随当前输入变化。Gated DeltaNet 与 Kimi Linear 都进一步采用在线回归的角度解释这种状态更新。[R07，§3.1，p.5](#ref-r07) [R08，§2.2，p.3](#ref-r08)

这提供了一个重要认识：**模型推理可以包含当前序列的快速状态学习，而不只是读取固定权重**。但变化的是快速状态，不等于每一步微调整个大模型，也不自动形成跨会话永久知识。

</details>

### 5.9 状态容量还取决于特征映射，而不只取决于更新规则

还可以给特征更多表达空间。用较少的数描述对象，容易出现难以区分的关联；展开到更多特征后，可能更好地区分它们，但保存关联的表也会变大。这一节讨论“用什么特征表示 Key”，与前面“已有记录怎样更新”是两个问题。

<details>
<summary>进阶：DPFP 特征展开与状态容量</summary>

Fast Weights 论文还提出 DPFP（Deterministic Parameter-Free Projection）：通过确定性的特征展开增大内积空间，避免依赖随机特征采样。按论文记号，展开维度可为 $2d_{\mathrm{key}}\nu$，其中 $\nu$ 控制容量与计算、存储成本。[R06，§5，pp.5–6](#ref-r06)

这补充了前面的容量讨论：ELU+1 不改变输入特征维度；更大的特征空间可能容纳更多易区分的关联，但状态也更大。**特征映射决定怎样区分 Key，Delta Rule 决定怎样修改已有映射，两者是不同的设计轴**。增大特征维度不意味着消除有限容量，也不能把这项早期实验直接当作现代 KDA 模型的扩容配方。

</details>

**读完自检**：固定状态的大小不再增长，是否表示可以无限精确地记住更多关联？

<details>
<summary>参考答案</summary>

不能。有限特征空间会有容量和串扰问题。Delta 更新改善已有关联的修正方式，没有让有限状态变成无限、独立的数据库记录。

</details>

## 6. Gated DeltaNet → KDA → 混合架构：能修改，还必须会清理

**接着上一章的问题**：会修正一条关联，还不足以处理大量过时信息。本章加入“旧状态保留多少”的控制，再讨论怎样让不同特征有不同保留速度。最后会看到：有限状态有成本优势，某些任务仍需要直接访问历史，因此可以把两类层放进同一个模型。

先读 6.1—6.3 和 6.6，抓住遗忘与混合的思路；6.4—6.5、6.9 的进阶内容解释怎样让这些数学操作在硬件上高效运行。

**讲义连接**：第 22–23 页，并回接第 15 页的混合架构。

### 6.1 DeltaNet 还缺什么？

Delta Rule 能修正当前 Key 的关联，但上下文切换后，可能有一大批旧信息已经无用。逐条纠正未必来得及，旧信息还会继续干扰读取。Gated DeltaNet（简称 GDN）先减弱旧状态，再修正当前关联，把整体遗忘与定向修改结合起来。[R07，§1，p.2](#ref-r07)

“门控”就是由模型计算一个控制量，决定信息通过或保留多少。保留系数 $\alpha_t$ 为 1 时旧状态保持原强度，为 0.9 时先乘 0.9、保留九成。若某项贡献连续三步都只经历 0.9 的衰减，没有其他更新影响，它会剩下 $0.9^3=0.729$ 倍。下面的 $\beta_t$ 则控制当前关联修正多少，两种控制各有职责。

按讲义的状态方向：

$$
\widetilde S_{t-1}=\alpha_tS_{t-1}
$$

$$
S_t=\widetilde S_{t-1}+\beta_tk_t
\left(v_t-\widetilde S_{t-1}^\top k_t\right)^\top
$$

其中，$\alpha_t$ 控制一个头内旧状态保留多少，$\beta_t$ 控制当前关联修正多少。令 $\alpha_t=1$，就回到 DeltaNet。[L03，p.22](#ref-l03) [R07，§3.1，pp.4–5](#ref-r07)

### 6.2 遗忘有收益，也有代价

先认识这里的测验：NIAH（Needle in a Haystack，大海捞针）把目标信息插进很多背景文字，再要求模型找回来。UUID 是形如一长串随机字符的标识符，难以仅靠语义猜中，因此能检验精确读取。下表三列各是一种检索任务，数值越高表示该项表现越好；先在同一列比较模型，不要把不同列直接相减。

为了清掉噪声而衰减状态，也可能抹掉很久以前仍然重要的信息。Gated DeltaNet 第 5 页表 2 的 1.3B 模型实验很好地揭示了这个矛盾。

| 模型 | 重复背景中的口令，8K | 真实文章中的数字，4K | 真实文章中的 UUID，4K |
|---|---:|---:|---:|
| DeltaNet | 98.8 | 18.6 | 22.4 |
| Mamba2 | 30.4 | 56.2 | 4.6 |
| Gated DeltaNet | 91.8 | 92.2 | 27.6 |

来源：[R07，§3.2，p.5，表 2](#ref-r07)。三列的任务和长度不同，不能把它们当作同一条件下的总体分数。

简单重复背景中，需要记的东西很少，长期保留最重要，DeltaNet 表现很好。真实文章中，潜在相关信息多，缺少清理会造成更强的状态干扰，门控的价值上升。UUID 又提出更强的精确绑定要求；27.6 的结果也提醒我们，改进不等于问题彻底解决。[R07，§3.2，pp.5–6](#ref-r07)

由此，NIAH 不应该被当作一种统一能力：背景是否真实、目标是否随机、干扰是否相似，都影响它测量的是保留、过滤还是精确关联。

### 6.3 KDA：不同特征方向，可以有不同的遗忘速度

上一节一个头用一个数决定整体保留程度，这个单独的数称为标量。KDA（Kimi Delta Attention）改为一组保留系数，也就是向量。假设两个特征方向的系数分别为 0.9 和 0.2，就可以让一个方向减弱得慢，另一个减弱得快。

这里的“通道”可以先理解为内部表示中的一个特征分量。它不天然对应“用户约束”或“日志”。公式中的 $\operatorname{Diag}$ 把这组系数放到矩阵对角线上，其余位置为 0；这样左乘状态矩阵，就能分别缩放对应的行：

$$
D_t=\operatorname{Diag}(\boldsymbol\alpha_t)
$$

$$
S_t=(I-\beta_tk_tk_t^\top)D_tS_{t-1}+\beta_tk_tv_t^\top
$$

它先按通道衰减旧状态，再做定向修正。不同 Key 空间特征可以有不同的记忆寿命。[R08，§3，p.4](#ref-r08)

阅读这条式子时先按操作顺序看：$D_tS_{t-1}$ 分别衰减旧状态，$I-\beta_tk_tk_t^\top$ 调整当前 Key 方向上的旧关联，最后一项写入新的关联。$I$ 是单位矩阵，可理解为矩阵乘法中的“1”；$kk^\top$ 是向量与自身的外积，得到一张描述该方向影响的表。

不能进一步断言“某个通道专门记用户约束、另一个专门记日志”。业务语义并非人为指定；通道级遗忘描述的是可学习机制，而不是预设分类。

### 6.4 为什么递归形式仍能高效训练？

“递归状态”或这里的递推，是上一状态参与下一状态的计算。这些方法的状态更新具有可利用的代数结构，加上训练时整段输入已知，才允许按块组织等价计算：块间传递记录，块内把很多小操作合成适合 GPU 的矩阵运算。仅仅“输入已知”并不能让任意递推都自动变成高效并行算法。

<details>
<summary>进阶：块内并行的简化推导</summary>

数学上的 $S_t$ 依赖 $S_{t-1}$，不意味着训练实现必须用逐 token 的低效循环。Gated DeltaNet 与 KDA 的重要贡献是 chunkwise 算法：块之间传递状态，块内部尽量转成适合 GPU 的矩阵操作。[R07，§2–3，pp.3–6](#ref-r07) [R08，§3.1，pp.4–5](#ref-r08)

**以最简单的加法状态为例的推导**：对于一个长度为 $C$ 的块，输入状态为 $S_{\text{in}}$，则：

$$
S_{\text{out}}=S_{\text{in}}+K^\top V
$$

$$
O=QS_{\text{in}}+(QK^\top\odot M_{\text{causal}})V
$$

这里 $Q,K,V$ 按行放置块内各位置的向量；$\odot$ 表示逐个格子相乘。$M_{\text{causal}}$ 是二值掩码：允许的位置为 1，未来位置为 0。它与第 3.2 节加在分数上的 $0/-\infty$ 掩码用法不同，不能互换。本例沿用无归一化的加法状态，不含 Softmax。

第一项读取块之前的历史状态，第二项处理块内部的因果交互。虽然块内出现 $C\times C$ 矩阵，但若 $C$ 固定，块数随总长度增长，仍可形成对长度线性的算法。这是理解更复杂 WY/UT 变换的入口，而不是 GDN/KDA 完整 kernel 的替代公式。

</details>

### 6.5 KDA 的结构约束，是硬件效率的一部分

这节的主旨是：允许任意复杂的状态变换，计算会很贵；限制变换形式，可以保留有用的更新能力，同时更容易并行。“对角加低秩”就是一种结构：先分别缩放各特征，再加上由少数向量组合产生的修正。低秩表示修正受较少独立方向约束；本节的 DPLR 是 Diagonal Plus Low Rank 的缩写。

<details>
<summary>进阶：对角加低秩结构与硬件实现</summary>

**由 KDA 递推直接改写**：

$$
(I-\beta kk^\top)D=D-(\beta k)(k\odot\alpha)^\top
$$

这是受约束的对角加低秩结构。一般 DPLR 可以更灵活，但计算和并行化更困难；KDA 绑定部分变量，保留细粒度遗忘，并减少部分计算。论文同时讨论细粒度衰减导致的数值精度问题及其 kernel 处理方式。[R08，§3.2、§6.2，pp.5、14–16](#ref-r08)

**工程理解**：一个结构限制可能降低自由度，却使表达能力、数值稳定性和 GPU 运算方式形成更好的折中。读架构论文时，要同时问“多表达了什么”和“多表达的东西能否高效算出来”。

</details>

### 6.6 Kimi Linear 为什么还保留完整注意力？

可以让多数层使用较便宜的状态更新，再用少数层保留逐位置读取历史的能力。下面会出现 MLA，它是第 7 章要讲的 KV 表示压缩方法：在此处保留全局访问，同时减少每个历史位置的存储。先知道这两个职责，就能理解混合的理由。

论文明确指出，纯线性注意力的长上下文检索仍是主要瓶颈，因此采用三层 KDA 加一层 MLA 的交替结构。逐层混合也考虑了基础设施简单性和训练稳定性。[R08，§4，p.6](#ref-r08)

**这是深度上的层配置，不是每生成三个 token 才查看一次全局历史**。每个位置都经过这些层：多数层做便宜的状态更新，少数层提供显式的全局访问机会。

论文通过改变两类层的比例，观察预测质量与成本的取舍。PPL 是困惑度（perplexity），衡量模型对真实后续 token 的预测表现；在可比数据和设置下通常越低越好。它不是问答准确率，5.65 也不表示错误率为 5.65%。论文的混合比例消融如下：

| KDA : MLA | 训练 PPL | 验证 PPL |
|---|---:|---:|
| 0 : 1 | 9.45 | 5.77 |
| 1 : 1 | 9.29 | 5.66 |
| 3 : 1 | 9.23 | 5.65 |
| 7 : 1 | 9.23 | 5.70 |
| 15 : 1 | 9.34 | 5.82 |

来源：[R08，§5.2，p.8，表 1](#ref-r08)。这是特定规模和计算预算下的结果，不是证明 3∶1 对所有模型和任务最优。1∶1 的质量接近，但全局计算更多；进一步增大线性层比例，也可能损害泛化。

只要保留固定比例的稠密全局层，相关平方级 Prefill 工作与随历史增长的 KV 仍存在。混合架构减少的是系数和部分成本，不等于消灭所有平方项。

### 6.7 不要把单请求加速与固定显存吞吐混在一起

这里有两种不同的“快”：一个人来问问题，他多久得到回答，叫单请求时延；很多人同时来问，一段时间能完成多少工作，叫吞吐。节省显存后，系统可能一次接待更多请求，使吞吐增加，却没有让每个请求都按相同倍数加速。

Kimi Linear 第 13 页图 7 使用 batch size=1：1M 长度下，Prefill 标注约 2.9 倍，Decode 标注约 2.2 倍。第 16 页相关文字又使用约 2.3 倍的表述。本文保留这一细小不一致，不把不同标注强行合成一个精确值。[R08，p.13 图 7、p.16 效率讨论](#ref-r08)

论文更大的约 6 倍收益还与节省 KV 后允许更大批量有关，不能解释成同一固定 batch=1 条件下单请求快六倍。[R08，p.1 图 1、p.16](#ref-r08)

读性能数字，至少分清：**单请求时延、固定批量吞吐、固定显存条件下允许改变批量的吞吐**。

### 6.8 混合架构有多种路线，层数比例也不是全部

这一节作为实例查阅即可：不同模型可以组合局部窗口、有限状态、稀疏或全局读取。除了“各有多少层”，还要看“这些层放在哪里”和“改动后训练了多少”。RULER 是长上下文任务基准，表中某个长度上的分数描述对应任务表现，不代表模型所有能力。

<details>
<summary>进阶：不同混合模型和层布局实验</summary>

### 6.9 Kimi K3 的有界衰减：数值范围会反过来影响模型设计

计算机表示数字有范围和精度限制。很多小于 1 的数连续相乘，会得到很小的结果；再取倒数，可能大到无法表示。BF16 是一种浮点数格式，Tensor Core 是 GPU 上加速矩阵运算的硬件单元。本节说明：限制遗忘系数的范围，有时能让更快的硬件计算方式变得可用。

<details>
<summary>进阶：有界衰减的数值范围</summary>

KDA 的块并行计算涉及累计保留系数及其倒数。连续相乘后系数过小，倒数就可能溢出。Kimi K3 将每步 log-decay 限制在 $(g_{\min},0)$，其中 $g_{\min}=-5$；于是 16-token 子块的累计 log-decay 位于 $(-80,0)$，倒数小于 $e^{80}$，处于 BF16 的指数范围内。[R26，§2.1.1，pp.4–5](#ref-r26)

论文用这一约束让对角子块也能采用 Tensor Core 矩阵运算，替换部分逐位置对计算。这里的论点是“限制动态范围使高效计算路径可行”，不意味着 BF16 的舍入误差或所有训练稳定性问题都被解决。这也是第 6.5 节“结构、数值与硬件共同设计”的具体例子。

</details>

**读完自检**：把旧状态衰减得更快，是否一定更容易找回很早出现的随机口令？

<details>
<summary>参考答案</summary>

不一定。衰减有助于清理干扰，也可能减弱仍然重要的旧信息。保留与过滤要按任务测试，不能只追求更强遗忘。

</details>

<a id="s07"></a>
## 7. GQA 与 MLA：不是减少历史条数，而是降低每条历史的表示成本

**本章换一个省空间的角度**：假设必须保留每个历史位置，能否减少每个位置需要保存的数字？GQA 让多组读取计算共享 K/V，MLA 用较短的内部表示承载内容 K/V。二者仍保留随历史增长的位置记录。

**讲义连接**：第 25 页，并连接第 7–9 页的 KV 与服务瓶颈。

### 7.1 从 MHA 到 MQA，再到 GQA

第 3 章介绍了多头：同一层并行进行多组匹配和读取。这里保留各头不同的 Query，改变它们是否共用 K/V。例如有四个 Query 头：

```text
MHA（Multi-Head Attention，多头注意力）：
Q1 → KV1；Q2 → KV2；Q3 → KV3；Q4 → KV4

MQA（Multi-Query Attention，多查询注意力）：
Q1、Q2、Q3、Q4 → 共享一组 KV

GQA（Grouped-Query Attention，分组查询注意力）：
Q1、Q2 → 共享 KV1；Q3、Q4 → 共享 KV2
```

共享减少了要存储的 K/V 组数，但每个 Query 仍可以计算自己的匹配权重。这是表示共享与表达能力之间的取舍。[R10，§2，pp.1–2](#ref-r10)

如果 Query 有 32 个头，KV 有 8 组，在头维度相同的条件下，相比 32 组 KV，逻辑 KV 存储降到四分之一。但 Query 仍有 32 个头，不能顺便声称所有注意力运算也减少四倍。

GQA 保留历史位置，只减少每个位置的头级表示开销；这与固定状态的线性注意力不同。

### 7.2 GQA 的贡献也包含如何改造已有模型

已经训练好的模型原本习惯使用各自的 K/V；合并后，需要适应共用表示。Checkpoint 在这里指保存下来的模型参数版本，与后面描述任务进度的检查点含义不同。

论文先对组内 KV 投影做均值合并，再继续预训练，使模型适应新结构。其主要方案使用约 5% 原始预训练计算量。[R10，摘要、§2.1](#ref-r10)

这意味着它不是一个任意现有 checkpoint 都能无损切换的纯推理配置。论文主要评估 T5 这类将输入编码与输出生成分开的模型，也承认 ROUGE（比较生成文本与参考文本重合情况的指标）不足以完整反映长文本生成质量，未充分比较所有从头训练的替代方案。[R10，§3.1、Limitations，pp.2、5](#ref-r10)

### 7.3 MLA：每个位置缓存较小的 latent

MLA（Multi-head Latent Attention，多头潜在注意力）进一步考虑：多个头需要的 K/V 能否由一份较短的共享表示产生？这份表示叫 latent，即潜在表示，是一组学习到的数。假设一个位置原本需要保存很多组展开后的数字，现在只缓存较短的 $c_t$，再利用学到的变换参与读取；具体能省多少取决于维度和实现。

这里的“压缩”指用较少的数承载表示，模型需要训练来适应它，不能理解成对任意现成 K/V 做无损文件压缩。讲义给出的简化结构为：

$$
c_t=W_Dx_t,\qquad k_t^{(h)}=W_K^{(h)}c_t,\qquad v_t^{(h)}=W_V^{(h)}c_t
$$

缓存的是较小 latent，而不是所有头展开后的 K/V。[L03，p.25](#ref-l03)

$W_D$ 把当前位置表示 $x_t$ 变成较短的 $c_t$；各头的 $W_K^{(h)}$、$W_V^{(h)}$ 则从它产生本头需要的表示，$h$ 表示头编号。不过每次都还原全部历史 K/V，可能吃掉节省的收益。下一步的“投影吸收”是在允许的条件下重新安排乘法，把部分变换移到当前 Query 或最终输出一侧。

<details>
<summary>进阶：MLA 怎样重新安排投影计算</summary>

**由简化公式得到的代数理解**：不含额外位置分支时：

$$
q^\top W_Kc=(W_K^\top q)^\top c
$$

$$
\sum_i a_iW_Vc_i=W_V\sum_i a_ic_i
$$

因此，数学上不一定要先为所有历史位置显式重建完整 K/V，再计算注意力；可以把部分投影吸收到 Query 或输出计算中。DeepSeek-V2 的 MLA 正是利用这一点减少推理时的历史表示与重建开销。[R20，§2.1.2、附录 C，pp.7、31](#ref-r20)

</details>

#### 7.3.1 为什么直接加入 RoPE 会妨碍投影吸收？

**这里先补一个前置概念**：RoPE（旋转位置编码）根据位置编号旋转 Q/K 向量，让匹配分数包含相对位置关系，第 8.3 节会用二维例子解释。此处只需抓住一个困难：如果每条历史的变换都依赖它自己的位置，就难以把这些变换统一搬到当前 Query 一侧、只做一次。

<details>
<summary>进阶：位置旋转为什么妨碍统一吸收投影</summary>

设内容 Query、Key 分别为 $W_Qh_t$、$W_Kc_i$。如果将整个向量旋转，注意力分数中会出现：

$$
h_t^\top W_Q^\top R(i-t)W_Kc_i
$$

中间的旋转矩阵随历史位置 $i$ 改变，矩阵乘法也不能任意交换顺序。因此，不能再像无位置分支时那样，将 $W_K$ 一次吸收到一个对所有历史位置通用的 Query 投影中。这是投影吸收的障碍，不是 RoPE 与所有低秩表示在数学上都不相容。[R20，§2.1.3，p.8](#ref-r20)

</details>

#### 7.3.2 解耦 RoPE：让内容压缩和位置关系各走一个分支

“解耦”在这里是拆开职责：内容部分继续用较短表示并做投影吸收，位置部分单独保留并参与匹配。因此计算缓存量时，既要算内容 latent，也要算位置 Key。进阶公式中的方括号和分号表示把两部分向量接在一起。

<details>
<summary>进阶：解耦位置分支与 MLA 缓存量公式</summary>

MLA 将每个头的 Query 与 Key 分为内容部分和位置部分：

$$
q_t^{(h)}=[q_{t,C}^{(h)};q_{t,R}^{(h)}],\qquad
k_i^{(h)}=[W_K^{(h)}c_i;k_{i,R}]
$$

位置 Key $k_{i,R}$ 在各头间共享，位置分支使用 RoPE；内容分支保留前面的投影吸收。注意力分数由两个内积相加得到，原论文再按内容与位置维度之和开平方进行缩放。[R20，§2.1.3，p.8，式 14–19](#ref-r20)

因此，DeepSeek-V2 推理时每层、每位置需要缓存 **$c_i$ 和 $k_{i,R}$**。在层配置相同、元素均为 $b$ 字节的条件下，全模型逻辑缓存为：

$$
M_{\mathrm{MLA}}=Ln(d_c+d_h^R)b
$$

$d_c$ 为联合 KV latent 维度，$d_h^R$ 为共享位置 Key 维度。这里没有再乘 2，因为同一 latent 同时承载内容 K/V；也不能漏掉位置 Key。低秩 Query 投影主要减少训练激活，不进一步减少历史 KV。[R20，§2.1.2–2.1.4，pp.7–9](#ref-r20)

这个公式描述 DeepSeek-V2 式 MLA 的逻辑张量，不包括分配、量化元数据或临时工作区。后续采用 NoPE 的 MLA 变体不应机械照搬其位置分支。

</details>

### 7.4 几种方法为什么可以组合？

| 方法 | 直白解释 |
|---|---|
| MLA/GQA | 每个历史位置存得更省 |
| DSA | 每个 Query 只读取选中的一部分位置 |
| CSA/HCA | 沿序列维度将多个历史位置汇成较少条目 |
| KDA 混合 | 多数层不保存无限增长的位置列表，少数层保留全局访问 |

它们优化的轴不同，但实际组合仍需专门训练、位置处理和 kernel 适配，不能当作任意可叠加的开关。理解这个区别以后，就不会把“压缩 KV”“稀疏读取”“压缩文本上下文”误当成同一件事。

### 7.5 KV 节省会变成服务收益，但不一定以同样比例变成时延收益

DistServe 指出，Decode 的批量受活跃请求 KV 显存限制；GQA、分页管理或模型并行有助于增大可服务批量。[R01，§3.2，p.6](#ref-r01)

**工程推论**：内存节省可能首先表现为能容纳更多请求，而不是一个请求快同样倍数。实际收益取决于瓶颈原本在 KV 带宽、模型权重、计算、排队还是网络。要把架构改变放进真实服务负载中评测。

**读完自检**：GQA 把 KV 组数减到四分之一，能否推出所有注意力计算都快四倍？

<details>
<summary>参考答案</summary>

不能。Query 头数可能不变，其他计算和实际瓶颈也仍存在。它直接减少的是相应 KV 的存储与读取需求，端到端速度需测量。

</details>

## 8. 位置编码与训练：架构允许长输入，不等于模型已经会用

**本章的问题**：即使显存够大，怎样让模型理解一个词在哪里、两个词隔多远？“A 替换了 B”和“B 替换了 A”使用相同的词，却表达不同结果。模型需要顺序信息；当输入比训练时长很多，原先学到的位置使用方式也可能失效。

先理解位置表示、位置插值和训练适配的分工，再读旋转矩阵与频率。位置公式能计算很大的编号，只说明能产生这个表示，实际任务还要验证。

**讲义连接**：第 26–36 页。用 Longformer 的适配实验解释“为什么不能只改窗口”，再用 Kimi Linear 连接 NoPE 与循环状态。

### 8.1 Longformer 的位置适配实验，比一句“需要长文本训练”更有说服力

先看实验想回答什么：原模型只熟悉较短的位置范围，增加新位置时，随机给它们一套表示是否就够了？MLM（掩码语言建模）通过遮住部分内容，让模型预测被遮住的内容。下表的 MLM BPC 是相应的每字符比特数指标，可以先理解为预测误差的一种度量，越低越好。阅读重点是新增位置怎样初始化、继续训练后又怎样变化。

Longformer 从 RoBERTa 继续训练时，需要把位置范围从 512 扩到 4096。第 6 页表 5 的 base 模型结果如下：

| 设置 | MLM BPC，越低越好 |
|---|---:|
| RoBERTa，512 长度 | 1.846 |
| Longformer，4096，新增位置随机初始化 | 10.299 |
| 复制已有位置嵌入进行初始化 | 1.957 |
| 再训练 2000 步 | 1.753 |
| 再训练至 65000 步 | 1.705 |

来源：[R04，§5，pp.6–7，表 5](#ref-r04)。这是语言建模损失相关指标，不是长文本问答准确率；不同长度的基线也不能被当作完全相同输入条件下的对照。

这个实验说明，网络结构容纳更多位置以后，还需要尽量保留已有权重学到的行为，再通过训练适应新范围。复制位置嵌入有助于保留局部结构；继续训练则帮助模型利用新连接和长上下文。

同一篇论文还有一个反例：膨胀窗口在字符级实验中有收益，但加入从 RoBERTa 继续训练的设置后反而伤害性能，作者认为可能与预训练权重不兼容。[R04，p.6，脚注 6](#ref-r04)

**架构技巧不是可以不经适配、随意叠加的开关**。

### 8.2 绝对位置编码：在输入处给位置一个表示

一种直接做法是给每个位置一组数字：第 1 个位置一组，第 2 个位置另一组，再把它和该位置的 token 表示相加。下式中的 $E[x_t]$ 是 token 的内容表示，$p_t$ 是位置表示，$z_t$ 是两者相加后的结果：[L03，p.28](#ref-l03)

$$
z_t=E[x_t]+p_t
$$

位置向量在形成 Q/K/V 之前进入输入表示。有两种常见来源：一是训练一张“位置编号 → 一组数字”的表，也叫位置嵌入表；二是用正弦等公式计算这组数字。前者通常受表的范围限制，后者可以算出更远的位置，但“公式能算”不代表模型在更远位置仍表现可靠。[L03，p.28](#ref-l03) [R03，§3.5，p.6](#ref-r03)

### 8.3 RoPE：通过旋转 Q/K 引入相对位置关系

可以先在纸上想象一根二维箭头。RoPE 按位置编号把它转一个角度：位置不同，旋转角度不同；旋转保持箭头长度，却改变方向。Q 和 K 都这样处理后，它们的内积会带上相对位置的信息。

**二维示意**：假设某一对通道每前进一个位置多转 10°。位置 3 的 Q 转 30°，位置 5 的 K 转 50°，两者比较时出现的额外相对转角就是 20°。如果一起移到位置 8 和 10，相对转角仍然是 20°。这是解释相对位置性质的假设角度；实际 RoPE 在多对通道中使用不同旋转速度，内容向量也参与分数计算。

公式里的 $R(i)$ 就是“按位置 $i$ 做旋转”的矩阵，波浪线表示旋转后的向量：

$$
\tilde q_i=R(i)q_i,\qquad \tilde k_j=R(j)k_j
$$

$$
\tilde q_i^\top\tilde k_j=q_i^\top R(j-i)k_j
$$

显式位置作用与相对位移有关；这里的标准 Q/K RoPE 不旋转 Value。注意，分数并不是只由位置决定，内容向量也参与计算。[L03，p.29](#ref-l03)

<details>
<summary>进阶：从旋转矩阵推导相对位移</summary>

把每对通道看成二维平面，其旋转块为：

$$
R_\ell(t)=\begin{bmatrix}
\cos(t\theta_\ell)&-\sin(t\theta_\ell)\\
\sin(t\theta_\ell)&\cos(t\theta_\ell)
\end{bmatrix}
$$

各二维块组成 $R(t)$。由于旋转正交，$R(i)^\top R(j)=R(j-i)$ 且 $\|R(i)q\|_2=\|q\|_2$，所以得到上面的相对位移公式。**位置改变向量方向，而不单独改变其范数**。RoFormer 还分析了与距离相关的衰减界，但这不保证任意内容向量的注意力分数都随距离单调下降。[R21，§3.2–3.4，pp.4–8](#ref-r21)

</details>

**理解**：能够计算任意角度，不等于训练过的网络已经适应所有角度组合与远距离依赖。数学可计算性和模型泛化能力，是不同层面。

### 8.4 Position Interpolation：把更长的位置映射回熟悉范围

假设原来训练到约 4096 个位置，现在希望处理约 16384 个，长度放大了 4 倍。位置插值（PI）把位置坐标除以 4：原来会走到 12000 的位置，现在按 3000 的坐标计算旋转。这样避免直接跑到很远的陌生范围，但相邻位置也从相差 1 变成相差 0.25，局部区分方式会改变，所以还需要适配。

“插值”可理解为在熟悉的范围内使用中间坐标；“外推”则把已经学到的方式直接延伸到范围之外。这里压缩的是用于位置计算的坐标，输入仍然包含原来的全部 token。

原始范围为 $L$，目标范围为 $L'=sL$，位置插值使用：

$$
R(t)\longrightarrow R(t/s)
$$

也可以理解为把各对通道随位置旋转的速度统一放慢。这样远处位置对应的旋转角度落回更熟悉的范围，但相邻位置之间的角度差也会变小。[L03，p.31](#ref-l03)

<details>
<summary>进阶：位置插值的分析与适配实验</summary>

**为什么不能直接外推？**PI 论文把 RoPE 分数看作一组正弦、余弦基函数的线性组合：在训练过的位置范围内表现有界，不保证范围外仍然稳定。远处位置的异常分数可能干扰归一化，所以失败不只是“读不到远处”，还可能连近处证据也利用不好。其插值误差界说明了相邻已知位置之间更容易控制的条件，不是所有模型任务准确率的保证。[R23，§2.2–2.3，pp.3–5](#ref-r23)

论文对 LLaMA 7B 扩展到 16K 的 PG19 实验中，采用 PI 但尚未微调时 PPL 为 112.13；200 步后为 7.05，1000 步后为 6.83。数字来自同一训练步数消融，而不是不同模型的排行榜。[R23，p.8，表 3](#ref-r23)

论文还分别测试语言建模、口令检索、长文摘要及原始窗口内的任务。**位置映射、长距离检索、真实任务和短上下文保持，应分别验证**。口令检索成功不等于任意多跳问题的有效窗口都达到同样长度；部分短窗口指标略有退化，也说明扩窗存在取舍。[R23，§3](#ref-r23)

</details>

### 8.5 YaRN：不能为了远距离，完全牺牲局部区别

上一节把所有位置变化统一放慢，但 RoPE 的各对通道本来就有不同的旋转速度。转得快的分量对相邻位置更敏感，转得慢的分量有更长的变化周期。YaRN 按频率分别处理，试图兼顾较远范围和局部区别。

这里频率就是旋转变化的快慢，波长是转完一圈所需的位置跨度，相位是转到了哪个角度。另一个参数“温度”会调整 Softmax 权重的集中程度：其他条件相同时，温度降低通常使高分位置获得更集中的权重。先理解这些作用，再看下方具体公式与实验条件。

若缩放规则还随当前长度改变，旧 Key 的旋转方式也可能需要调整。复用缓存时必须使用一致的位置规则，否则新旧表示可能对不上。具体动态缩放方案和训练配置放在进阶内容中。

<details>
<summary>进阶：YaRN 的频率、温度、动态缓存和训练配置</summary>

讲义中的 YaRN 使用频率选择性插值：长波长维度更充分插值，短波长维度保留更多局部相位，中间平滑过渡。概念式为：

$$
\theta'_\ell=(1-\gamma_\ell)\frac{\theta_\ell}{s}+\gamma_\ell\theta_\ell
$$

它还调整注意力温度。讲义特别提醒，温度的具体经验公式基于特定模型拟合，不是普适常数。[L03，p.32](#ref-l03)

论文用波长 $\lambda_\ell=2\pi/\theta_\ell$ 和比值 $r_\ell=L/\lambda_\ell$ 解释分段：在训练窗口内已旋转很多圈的高频维度，保留更多局部相位；尚未覆盖完整周期的低频维度，优先插值。中间用线性 ramp 混合。其在 LLaMA 系列上的示例阈值为 1 和 32，不是所有模型的固定配置。[R24，§3.1–3.2，pp.4–5](#ref-r24)

按注意力温度 $\tau$ 表示，分数为 $q^\top k/(\tau\sqrt{d_k})$。论文还给出将 Q、K 同时乘以 $\sqrt{1/\tau}$ 的等价实现，拟合式为 $\sqrt{1/\tau}=0.1\ln s+1$。这项额外缩放会改变范数，应与第 8.3 节的纯旋转分开理解。[R24，§3.3，pp.5–6](#ref-r24)

**动态缩放与缓存必须一起设计**。Dynamic Scaling 随当前长度调整 $s$；尺度变了，过去 token 应使用的旋转也变了。如果直接复用按旧尺度旋转后的 Key，就可能混合两套位置表示。论文建议缓存旋转前的表示，再使用一致的当前尺度；具体实现仍需权衡重算与缓存布局。[R24，§3.4，p.6](#ref-r24)

训练长度也不必等于评测长度：论文的 Llama 2 128K 配置从 64K 配置继续训练，新增训练仍使用 64K 数据，再评测到 128K。因此，“在 128K 做过评测”不能被改写成“在 128K 完成全部训练”。[R24，§4.1–4.2，p.7](#ref-r24)

因此，修改 `max_position_embeddings` 或加一个 RoPE scaling 配置，不应当直接被描述为“获得了可靠的长上下文能力”。位置范围、训练分布与任务评测仍需一起检查。

</details>

### 8.6 NoPE：没有显式位置编码，不等于没有顺序

NoPE 是 No Positional Encoding，即不显式加入位置编码。即使不给每个位置贴编号，第一个位置和第十个位置能看到的历史范围仍不同；按顺序更新的状态也会随输入次序变化。这些结构可以提供顺序线索，但模型能否学会利用，仍需要证据。

讲义第 30 页指出，顺序可以通过因果计算或循环动态体现；移除显式位置编码的外推问题，并不会移除训练长距离行为的需求。[L03，p.30](#ref-l03)

原始 NoPE 论文研究的是 decoder-only Transformer。不同位置能看到的因果前缀不同，因此移除位置向量后，模型也不等同于一个对输入顺序完全不敏感的集合模型。论文在带起始 token 的构造中证明，存在参数使第一层恢复绝对位置信息；若后续层保留该信息，还存在实现相对位置分数的参数。[R22，§5.1，pp.5–6](#ref-r22)

这里的关键词是“存在参数”：它说明模型结构能够表达这种计算，不保证实际训练就会学到，更不证明对任意长度可靠外推。作者另外观察到，训练后的 NoPE 注意力分布更接近 T5 的相对位置偏置——后者按位置距离给匹配分数加上额外调整。这是经验支持，不能把“分布相近”升级为内部算法完全相同。[R22，§5.2，pp.6–7](#ref-r22)

Kimi Linear 的做法更具体：全局 MLA 层使用 NoPE，把顺序信息和偏向近期内容的倾向（近因偏置）主要交给 KDA 层。状态按顺序更新，不同信息经历不同的衰减和修正，所以整个模型并非无序。[R08，§4，pp.6–7](#ref-r08)

**论文之间的连接：KDA 不只是节省 KV，也成为位置与时间顺序建模的一部分**。

### 8.7 用实验限制 NoPE 的结论范围

这一组实验关注“换位置处理方式以后，长上下文任务表现怎样”。RULER 和 LongBench V2 是不同的任务基准，表中分数越高越好；先在同一列比较。平均分更高，不能代替检查每一类任务是否退化。

Kimi Linear 的长上下文对比使用相同 1.4T 训练 token 的对照模型。下面只摘录表 5 的部分任务列；“表中总体平均”沿用原论文对更多任务的汇总，**不是这里展示的 RULER 与 LongBench V2 两列的算术平均**：

| 模型 | RULER | LongBench V2 | 表中总体平均 |
|---|---:|---:|---:|
| MLA 基线 | 81.3 | 36.1 | 52.2 |
| Kimi Linear，RoPE 版本 | 78.8 | 35.4 | 51.8 |
| Kimi Linear，全局层 NoPE | 84.3 | 35.0 | 54.5 |

来源：[R08，§5.5，p.12，表 5](#ref-r08)，论文描述此组长上下文评测在 128K 条件下进行。

NoPE 版本总体平均更高，但 LongBench V2 没有最好。因此不能得出“去掉 RoPE，所有任务都会更强”。作者关于不同层位置偏置分配的解释是机制假说，不能当作所有架构上的定理。[R08，§5.2，pp.8–9](#ref-r08)

还要区分这组 1.4T 控制实验与最终 5.7T 发布 checkpoint。不能把更长训练、更大窗口的发布模型结果混进同一架构消融，宣称差异全部来自一个组件。[R08，§5.4.1，p.10](#ref-r08)

NoPE 原论文提供另一组独立证据：约 107M 参数模型在复制、反转、加法、排序等 10 项任务上分别从头训练，每个任务与位置编码组合使用 3 个随机种子；它比较的是已见与未见的问题长度，不是现代大模型的百万 token 文档理解。[R22，§3–4，pp.3–5](#ref-r22)

论文还有两个有助于评测设计的限制：第一，scratchpad（让模型写出中间解题步骤）的收益依赖任务与格式，在其所测数学和推理任务中，并未普遍改善对更长输入的适应能力；第二，额外的约 1B 规模语言建模实验中，另一种位置方法 ALiBi 在更长区间的 PPL 可以比 NoPE 更稳定。ALiBi 的基本做法是按距离给注意力分数加上线性偏置。因此，**PPL、算法任务正确率和长文 Agent 成功率应分别报告**，不能用一个指标替代全部能力。[R22，§6–7，pp.7–9](#ref-r22)

### 8.8 真正有效的长上下文训练：让目标必须依赖远处信息

设想两道训练题：第一道的答案就在最后一句，前面再放一百页也不影响作答；第二道必须把第一页的定义和最后一页的数字结合。两道题都很长，只有后者明确要求利用远处信息。训练数据既要足够长，也要让正确答案真正依赖那些远处内容。

讲义列出四类数据：连贯长文档、打包样本、Agent 轨迹和受控合成任务。[L03，pp.27、34–35](#ref-l03)

| 数据形式 | 能提供的训练信号 | 需要留意的问题 |
|---|---|---|
| 连贯长文档 | 自然结构、跨段落依赖 | 文本长，不代表每个目标都依赖远处 |
| Packed examples | 提高 token 利用率 | 边界、位置处理与不应发生的信息泄漏 |
| Agent 轨迹 | 动作—观察、状态变化、失败恢复 | 错误轨迹与已验证结果如何区分 |
| 合成依赖任务 | 控制证据位置、跳数与干扰 | 简单任务分数不能替代真实任务表现 |

**训练设计建议**：除了延长序列，还应让目标依赖早期约束、分散证据、重新赋值、被撤销结论与失败后的正确恢复。表中的 Packed examples 就是把多个样本装进一个长序列，提高一次训练的空间利用率；需要正确处理样本边界，避免出现任务不允许的信息互相读取。独立短样本拼起来，并不会自动产生需要跨文档推理的任务。

Kimi 的反向复制要求把内容倒序返回；MQAR 要求回答多个键值关联查询；多栈 PUSH/POP 则要求跟踪几组“后放入、先取出”的记录。它们分别检查精确读取、多关联与状态跟踪。相关合成实验采用小模型配置，有助于拆开测能力，但不直接证明大型 Agent 的任务成功率。[R08，§5.1，pp.7–8](#ref-r08)

## 9. Kernel、并行、分页与 DistServe：别把四种系统优化混成一种

**本章转到运行模型的服务器**：一次请求先排队，再处理输入，接着逐步生成输出。这些过程中，GPU 要计算、搬运数据、分配缓存空间，也可能与其他 GPU 通信。Kernel 是执行具体计算的底层程序；并行是让多个设备分担工作；分页是按块管理存储；DistServe 则把处理输入和生成输出分给不同实例。

**讲义连接**：第 7–9、36、41 页。它们分别处理执行形态、单设备压力与 KV 分配。

### 9.1 FlashAttention：优化计算与数据搬运，不是删掉上下文

可以把成对计算的结果想成一张很大的表。普通直觉是先把整张表算出来、存下来，再做后续处理；FlashAttention 的关键思路之一是分块处理并及时汇总，减少大块中间数据在存储之间来回搬运。“物化”就是实际把这张中间表存出来；不存完整大表，仍可以完成对应的注意力计算。

GQA 论文的相关工作指出，FlashAttention 通过避免显式物化平方规模的注意力分数矩阵，降低内存开销并加速计算。[R10，§4，p.4](#ref-r10)

与稀疏注意力的区别是：标准稠密 FlashAttention 优化的是完整注意力的执行与访存方式，并不靠只选 Top-K 历史位置来省计算。浮点运算顺序可以带来数值差异，但它不属于按语义删减上下文的方法。

**计算层面的解释：不把 $n\times n$ 分数矩阵完整存入显存，不等于不做这些位置之间的成对计算**。内存复杂度改善和算术复杂度改善，要分别描述。

### 9.2 Context Parallelism：让多张设备共同处理一条长序列

讲义第 36 页用 Ring Attention 说明：将序列相关数据分布到多个设备，交换 K/V 块，并尝试让通信与分块计算重叠。讲义给出的每设备相关存储量随设备数下降，而总稠密注意力工作仍为 $O(n^2d_k)$。[L03，p.36](#ref-l03)

这里的内存估算针对序列相关状态，不应当被扩展成“所有模型内存都严格除以设备数”。

**稀疏注意力是少做一些连接；Context Parallelism 是让更多设备分担这些连接**。通信是否能有效隐藏、负载是否均衡，仍会影响实际效果。

#### 9.2.1 为什么分块后仍能得到完整注意力？

每块算完以后，需要把它们合成一个整体加权结果。可以用两组学生的平均分作类比：10 人平均 90 分、30 人平均 60 分，整体平均为 $(10\times90+30\times60)/40=67.5$，不能简单把两个平均分再平均成 75。注意力合并各块时也要带上相应的权重信息，不过使用的是匹配分数形成的归一化量，不是块内人数或 token 数。下方公式处理它的具体合并方式。

<details>
<summary>进阶：怎样合并各块的 Softmax 结果</summary>

每个设备保留自己的 Query 块，依次处理环上传来的 K/V 块。不能把每块单独 Softmax 后的输出直接相加：各块的归一化分母不同。需要合并最大分数、指数和与加权 Value 和，得到针对所有可见 Key 的统一归一化。[R30，§3，pp.3–5](#ref-r30)

**合并公式**：对同一个 Query，将一块统计记为最大值 $m_a$、稳定指数和 $\ell_a$、未归一化加权和 $u_a$；另一块记为 $m_b,\ell_b,u_b$。则：

“稳定”指先将该块每个分数减去块内最大值，再取指数；$\ell_a$ 累加这些指数，$u_a$ 则用同样的指数加权 Value。这样指数不会因原始分数太大而溢出。合并时再把两块调整到共同的最大值基准：

$$
m=\max(m_a,m_b),\quad
\ell=e^{m_a-m}\ell_a+e^{m_b-m}\ell_b,\quad
u=e^{m_a-m}u_a+e^{m_b-m}u_b,\quad o=u/\ell
$$

这是 Softmax 分块合并的代数解释，实际还要正确处理因果掩码与全遮蔽块。在实数运算意义上不删减注意力连接；浮点实现可能因累加顺序不同而产生误差。

</details>

#### 9.2.2 “通信可隐藏”需要足够计算量

“隐藏通信”指 GPU 算当前一块时，下一块数据恰好在传输，传输时间与计算重叠。若数据到得太慢，GPU 仍然要等；若计算足够久，传输可能在当前计算结束前完成。它描述时间重叠，不代表数据没有传输或带宽没有被占用。

<details>
<summary>进阶：计算时间能否覆盖传输时间</summary>

Ring Attention 用块长 $c$、宽度 $d$、算力 $F$ 和链路带宽 $B_{\mathrm{net}}$ 分析重叠。在其 BF16 与计算量简化假设下，块计算约为 $4dc^2$ FLOPs，K/V 传输约为 $4dc$ 字节，需要满足：

$$
\frac{4dc^2}{F}\ge\frac{4dc}{B_{\mathrm{net}}}
$$

这说明更大的块有利于覆盖传输，但也增加内存需求。实际有效算力、带宽、启动开销与因果负载分布都会改变交叉点，不能把“环形通信”直接等同“零通信开销”。[R30，§3，pp.4–5](#ref-r30)

</details>

#### 9.2.3 Megatron CP 与 SP 的边界

在 Megatron 这套模型训练框架里，CP（Context Parallelism，上下文并行）与 SP（Sequence Parallelism，序列并行）虽然都按序列分配数据，涉及的运算范围却不同。初读只需记住：看到“序列并行”这个名字，还要问究竟分配了哪些层的工作。

<details>
<summary>进阶：Megatron 的具体切分范围</summary>

本地 Megatron 文档区分：其 SP 主要切分 Dropout、LayerNorm 的序列激活；CP 则沿序列维度切分输入和各层激活。逐 token 的 Linear、LayerNorm 可在本地处理，注意力需要交换 K/V；反向传播还需汇合对应梯度。文档描述以环形点对点操作实现相关通信，并强调因果负载均衡、FlashAttention kernel 以及 GQA/MQA 对通信量的降低。[R31，Context Parallelism Overview](#ref-r31)

这里的 SP 指 Megatron 文档中的特定术语，不代表所有论文中名为 sequence parallelism 的方法都只做同样的切分。

</details>

### 9.3 Paged KV：降低分配浪费，不是压缩业务事实

假设给每个请求预留 100 格缓存，实际只用到 20 格，剩余 80 格就暂时浪费了。改成每块 4 格、用完再申请下一块，就能更贴近实际需求；块表记录逻辑上的第几块放在物理上的哪里。实际系统以 token 对应的 KV 块管理，这里用格子解释分配方式。

讲义第 41 页展示逻辑 KV 块到物理块的映射。一个请求逻辑上连续的 KV 可以分散在不同物理块中，而不必预留一大段连续显存。[L03，p.41](#ref-l03)

分页管理关心的是“这些张量放在哪里、怎样增长和共享”。它不会把 100K token 的语义内容自动缩成 10K，也不等同于跨请求前缀缓存。

尤其要区分两种淘汰：淘汰可重算的 KV，通常意味着以后重新计算；从逻辑上下文中删除唯一证据，则可能改变模型能看到的内容。前者是计算缓存管理，后者是信息保留策略。

**浪费从哪里来？**预先按最大输出长度预留空间，会保留大量尚未使用的位置；分配块内部可能有空余，不同分配之间也可能留下难以利用的空洞。PagedAttention 支持 kernel 按块表读取非连续 KV，运行时再按需分配固定大小的物理块。在论文的基本单序列布局下，未填满空间限制在最后一个块内，但块越大，潜在尾部浪费也越大。[R35，§2、§4.1–4.3，pp.2–6](#ref-r35)

**共享后怎样安全地分叉？**多个候选输出可以把公共前缀映射到同一批物理块，由引用计数跟踪使用者。当某个分支需要写入仍被共享的末尾块时，先复制该块，再继续写；完整公共块仍可共享。这就是块级 copy-on-write。它既支持并行采样，也支持 beam search 中不断变化的共享关系。[R35，§4.4，pp.6–8](#ref-r35)

**显存不足后怎样恢复？**论文比较两条路径：把 KV 换到 CPU 后再读回，或保留 token 序列、恢复时重新 Prefill。重算已生成的 token 不必逐 token 重走 Decode，因为它们现在已是已知输入，可以并行 Prefill。两者的取舍依赖传输带宽与计算能力，论文中的调度策略不能直接视为当前 vLLM 的全部默认行为。[R35，§4.5，pp.8–9](#ref-r35)

分页、共享和恢复共同把有限显存转成更大的可服务批量；它们既不提供业务事实校验，也不允许把不同前缀下的相同文本 KV 任意混用。

### 9.4 DistServe：分别服务 Prefill 与 Decode

想象系统一边为已有用户持续输出，一边收到一个很长的新报告。处理新报告需要大量计算，可能让正在输出的用户突然停顿。DistServe 尝试把“处理大段已知输入”和“持续生成”交给不同实例，分别安排资源，再把前一阶段产生的 KV 交给后一阶段。

DistServe 的出发点是，同一批次中的长 Prefill 会拖慢正在输出的 Decode；优先服务某一阶段，又可能伤害另一阶段的时延。混部还耦合了资源配置与模型并行方式。[R01，§1–2，pp.2–4](#ref-r01)

其方案为 Prefill 与 Decode 分配不同实例，使两个阶段独立配置资源，再传输主要由 KV 构成的中间状态。不同实例维护各自的模型权重副本，所以这不是没有额外代价的拆分。[R01，§2.3，p.4](#ref-r01)

### 9.5 Goodput：不能只问每秒生成多少 token

先设服务目标，例如“多数请求在规定时间内开始输出，后续输出间隔也不过长”。这样的目标称为 SLO（服务等级目标）。Goodput 在这篇论文里关心：满足这些要求时，每张 GPU 最多能承接多大的请求率。尾部时延则关注那些等待特别久的请求，例如第 95 或第 99 百分位，而不仅是平均用户。

DistServe 优化的是：在 TTFT、TPOT 和达标比例约束下，每张 GPU 能承接的最大请求率。[R01，§1，p.2](#ref-r01)

例如，系统 A 的 token/s 更高，但大多数用户等很久才出首字；系统 B 的总 token/s 略低，却能稳定满足交互时延。服务目标不同，后者可能更有价值。

**工程建议**：把平均值与尾部时延、吞吐与达标吞吐分开。批处理报告与交互式问答可以采用不同服务目标，不必强迫所有请求共享一个“越快越好”的指标。

### 9.6 排队会放大小小的执行差异

如果设备平均每秒只能完成一个请求，而请求几乎每秒都来一个，一次小延误就可能积累成队列；忙得越接近极限，等待越敏感。下面的简化排队模型用于解释这种趋势，实际系统还需测请求长度和调度行为。

<details>
<summary>进阶：简化排队模型及适用条件</summary>

DistServe 在固定执行时间 $D$、泊松到达率 $\lambda$、单请求已使设备饱和等简化条件下，使用 M/D/1 模型：

$$
E[T]=D+\frac{\lambda D^2}{2(1-\lambda D)},\qquad \lambda D<1
$$

第一项是执行，第二项是排队。[R01，§3.1，p.5](#ref-r01)

**从公式观察**：当负载接近服务极限，排队会急剧增大。因此，稍微缩短执行时间，有时能显著降低排队；只在空闲服务器测单请求，可能看不出线上收益。真实请求长度不均匀时，上述简化假设不再完全成立，论文也讨论了其局限。[R01，§3.3，p.6](#ref-r01)

</details>

### 9.7 分离是否划算，取决于负载和通信

KV 从 Prefill 实例送往 Decode 实例会消耗网络带宽。DistServe 因此同时考虑请求分布、GPU 放置、通信条件和并行配置，而不是给出“所有系统都应该拆分”的结论。[R01，§3.3–4，pp.6–7](#ref-r01)

**落地顺序建议**：先测请求长度分布、并发、缓存命中和两个阶段时延；再判断是否有必要增加分布式复杂度。小规模内网服务中，减少巨大工具输出、避免前缀无谓变化、设置合理批量，可能比先做分离更直接。

**读完自检**：把完整注意力分给多张 GPU，是否就消除了它的平方级总计算？

<details>
<summary>参考答案</summary>

没有。设备共同分担工作，可能降低单设备压力；总成对计算仍在，还增加通信与协调。

</details>

## 10. 前缀缓存、模块复用与缓存感知路由：复用的不只是一次请求

**本章的问题**：读同一份报告回答十个问题，能否复用报告已经计算过的结果？可以寻找共享的开头部分，也就是“前缀”。但复用要满足计算条件；谁保存了缓存、缓存是否过期、把请求送到哪里，都会影响收益。

**讲义连接**：第 37–44 页。这一部分把模型调用看成程序的一部分，而不是互不相关的独立请求。

### 10.1 为什么要强调“前缀相同”？

“前缀相同”是从开头起有一段相同，而非中间恰好出现同一段文字。以下为假设例子，并假设模型、位置与其他计算条件兼容：

```text
公共前缀 P = 稳定指令 + 报告全文
请求 A：P + 问题：半年收益是多少？
请求 B：P + 问题：一年收益是多少？
        P 是这里保证相同的部分，两个问题仍需分别处理。

请求 C：新的分析规则 + 报告全文 + 问题：一年收益是多少？
        前面改了，后面的报告不能仅因文字相同就复用原 KV。
```

一个位置的隐藏表示依赖它前面的输入。相同文本段落，如果前面有不同的指令或历史，通常不能直接假设其 KV 相同。SGLang 的前缀复用建立在相同 prompt prefix 上。[R11，§3，p.4](#ref-r11)

工程上还必须确保模型及影响前缀计算的配置兼容。文本“语义相近”不等于相同计算状态，缓存键不能只靠模糊语义匹配。

兼容性也包含位置处理。例如第 8.5 节的动态 RoPE 缩放若改变过去位置的表示，就需要相应的缓存更新。**相同 token 前缀是重要条件，但还要保持产生这些张量的计算条件一致**。

### 10.2 多次工具调用如何扩展可复用前缀？

沿用代码任务：第一次模型决定读日志；工具返回日志后，第二次请求在原历史后追加日志。若旧前缀缓存仍可用，就能复用已处理的部分，重点计算新增输入。第二次生成的新输出和后续工具结果，又成为下一轮历史的一部分。

讲义第 38 页展示：第一次请求建立 KV 并生成输出；工具结果返回后成为新输入；新结果完成 Prefill 后，又加入下一轮可以复用的前缀。[L03，p.38](#ref-l03)

```text
调用 1：稳定前缀 + 用户请求 → 模型输出
调用 2：已有前缀与输出 + 工具结果 → 新输出
调用 3：继续复用前缀 + 新观察 → 下一步
```

缓存并没有缩短模型的可见历史。新增位置仍可能需要读取已有历史。它主要减少重复计算，不是事实准确性机制。[L03，p.53](#ref-l03)

#### 10.2.1 Prompt Cache：模块复用比相同前缀复用多了什么条件？

前缀复用要求共同的开头；这篇名为 *Prompt Cache* 的论文进一步研究把预先算好的模块组合起来。这里的 schema 是模块组织与位置的约定，PML 是描述这种约定的标记形式。难点在于：模块单独计算时没有看过另一个模块，拼在一起以后也不会自动补上那次交互。

Prompt Cache 论文将可复用片段显式写成 PML schema 中的模块，为模块分配固定位置 ID，并预计算各自的 KV。请求选择模块、提供参数，再计算未缓存的部分。参数槽位、互斥模块和嵌套结构允许同一 schema 表达不同请求。[R32，§3.1–3.4，pp.3–6](#ref-r32)

例如，同一旅行应用有“公共说明”“东京资料”“巴黎资料”三个模块。schema 预先确定各模块的位置，用户请求选择其中一些模块；未选择模块留下的位置间隔并不要求重新编号。系统因此需要支持不连续位置 ID，而不是简单把缓存张量按新文本顺序拼起来。

**最重要的边界是跨模块依赖**。独立编码巴黎资料时，它没有读取另一个模块中的临时约束；即使后来把两者的 KV 放到一起，巴黎资料的旧隐藏表示也不会自动变成“已经读过该约束”的状态。因此，模块化复用不保证等同于把完整文本重新做一次稠密 Prefill。[R32，§3.3，p.6，Attention masking effect](#ref-r32)

论文要求模块尽量自包含、语义独立，并提出 scaffolding：对需要一起编码的模块集合额外保存联合状态，用更多存储换取保留这些模块之间的注意力。它并不提供任意模块、任意位置、任意前文下的无损组合。

| 复用方式 | 复用前提 | 应怎样看待质量 |
|---|---|---|
| 相同因果前缀 | token、模型、位置和相关配置一致 | 不改变原有依赖关系；数值实现仍需检查 |
| 独立模块 KV 组合 | schema 与位置安排兼容，模块尽量独立 | 改变模块间编码依赖，需要任务质量评测 |
| scaffold 联合模块 | 预计算了所选模块集合的联合状态 | 保留集合内交互，但增加缓存容量与组合管理成本 |

论文的主要时延收益发生在首 token 之前，后续 Decode 仍读取组合后的历史。应同时记录 TTFT、缓存存储/搬运和任务质量，不能把 Prefill 加速当作每个输出 token 都同倍数加速。[R32，§3.4、§5，pp.6–10](#ref-r32)

### 10.3 SGLang：利用多调用程序的结构

同一份材料可以分叉执行正确性、性能、安全性分析，然后合并结果。共同前缀不必在每个分支里重新计算。SGLang 通过生成、选择、分叉与合并等程序结构，让运行时利用这些复用机会。[R11，§1–3，pp.1–4](#ref-r11)

```text
稳定指令 + 代码 + 任务
        ├─ 正确性分析
        ├─ 性能分析
        └─ 安全性分析
              ↓
           合并判断
```

这说明工作流组织也会影响推理效率。但分支之间交换的结论仍需证据与冲突处理，缓存共享不能自动保证各分支正确。

### 10.4 RadixAttention 为什么使用基数树？

可以把它想成按共同开头组织请求的树：“指令＋报告”共用一段主干，半年问题和一年问题在后面分叉。基数树将连续的公共片段合并保存，便于找出最长公共前缀。LRU 是“最近最少使用”淘汰策略；引用计数记录还有多少使用者，避免回收正在用的内容。

基数树可以保存共享前缀和分叉结构：共同部分只存一份，出现差异的位置分叉。论文使用叶子优先的 LRU 回收，让公共祖先尽量保留；正在被运行请求使用的节点由引用计数保护。缓存与活跃请求共享内存池，内存压力高时可以为运行批量让出空间。[R11，§3，pp.4–5](#ref-r11)

这些设计分别处理：查找公共前缀、共享分支、保护活跃请求，以及缓存与并发争夺显存的问题。它不是简单地加一个 `dict[prompt] = kv`。

### 10.5 调度顺序也影响缓存收益

假设一批请求分别询问报告 A、B、C。如果先连续处理同一报告的问题，就有机会反复用到已经驻留的缓存，减少在不同材料间切换。但在线服务不能让新来的陌生问题一直被插队；这种长期得不到服务的情况叫“请求饥饿”。

SGLang 论文在离线批处理、缓存至少能容纳最长请求等条件下，证明按请求前缀树的深度优先顺序访问可以达到最优缓存命中率。最长共享前缀优先与此相联系。[R11，§3，pp.5–6，定理 3.1](#ref-r11)

在线请求不断到来，离线条件不再完整成立。论文还提醒贪心缓存调度可能导致请求饥饿。[R11，p.6](#ref-r11)

因此，“命中率更高”不必然意味着“每个用户更快”。需要把排队、公平性和任务时延一起看。

### 10.6 Cache-Aware Routing：缓存在哪个 Worker，也很重要

Worker 是承接计算的服务节点。假设节点 A 已经有报告缓存，节点 B 没有，把请求送给 A 可能省计算；但如果 A 排了很长的队，B 反而可能更快。因此路由需要同时考虑能复用多少和要等多久。下表检验特定负载下路由变化带来的吞吐与命中变化；命中率说明复用情况，不能单独代替用户时延和任务质量。

SGLang v0.4 的附件材料讨论了路由器维护 Worker 缓存的近似前缀树，在可复用缓存与负载均衡之间选择节点。[R12，Cache-Aware Load Balancer](#ref-r12)

其示例实验为：

| 指标 | 对照设置 | 缓存感知设置 |
|---|---:|---:|
| 吞吐，token/s | 82,665 | 158,596 |
| 缓存命中率 | 20% | 75% |

材料明确说明，该工作负载包含多个长前缀组，且各组完全均衡。这个结果说明特定复用模式下的潜力，不是所有线上服务的保证。[R12，同节实验表与说明](#ref-r12)

**连接 DistServe 的工程推论**：应该选择的不是缓存最多的节点，而是综合排队、未缓存计算和数据传输后，最可能满足时延目标的节点。

### 10.7 Prompt 布局既是语义设计，也是性能设计

讲义建议稳定前缀、追加变化状态、避免时间戳和无意义重排，并测量实际缓存 token、TTFT 与淘汰情况。[L03，p.44](#ref-l03)

一个可测试的布局是：

```text
稳定指令与工具定义
→ 稳定任务背景或阶段性资料
→ 当前检查点
→ 最近消息与工具结果
→ 本轮具体要求
```

这不是固定模板。检查点更新可能使后续前缀失效；多份材料重排可能改善阅读却降低缓存。应当比较质量与总成本，而不是为了缓存强行保留无效信息。

### 10.8 实际计算成本与 API 定价不是一个量

讲义第 39–40 页区分了物理计算成本和服务商 token 价格。缓存读取、缓存创建、普通输入与输出可能有不同计价方式，且价格表带有时间点。[L03，pp.39–40](#ref-l03)

对自部署系统，即使没有逐 token API 账单，仍有 GPU 时间、显存与可服务并发的成本。对 API 服务，也不能把 token 折扣直接当作底层 GPU 运算减少的比例。

本文不复刻讲义的时点价格表。这里需要保留的是：**账单、逻辑输入量、实际重算工作和用户时延，应当分别测量**。

#### 10.8.1 可复用多少次，以及缓存放在哪里？

先用一个假设账本理解：每次从头处理成本为 10；另一方案先单独花 10 建缓存，之后每个消费请求付 2 复用成本。只消费一次，后者总共花 12；消费五次，从头算要花 50，缓存方案花 $10+5\times2=20$。但若每次复用还要付 9 的传输成本，重复使用再多次也无法按这个账本省钱。这里假设提前单独建缓存；若首个请求一边计算一边建缓存，应按实际过程另算，不能多计一次复用。下面的公式使用前一种口径；这些数字没有现实货币单位，不是产品报价。

《Can I Buy Your KV Cache?》研究最简单的共享前缀情形：固定模型与精度，保存某一文档前缀的 KV，之后在正确位置、正确 attention mask 下追加问题。它没有解决任意独立文档缓存的融合。[R33，§4，pp.3–4](#ref-r33)

<details>
<summary>进阶：缓存计算、存储和传输的成本公式</summary>

按论文的简化成本模型，令 $N$ 为共享该前缀的消费请求数，$C_{\mathrm{prefill}}$ 为一次前缀计算成本，$C_{\mathrm{reuse}}$ 为每次复用成本，则：

$$
C_{\mathrm{fresh}}=NC_{\mathrm{prefill}},\qquad
C_{\mathrm{cached}}=C_{\mathrm{prefill}}+NC_{\mathrm{reuse}}
$$

若 $C_{\mathrm{reuse}}<C_{\mathrm{prefill}}$，复用划算的条件为：

$$
N>\frac{C_{\mathrm{prefill}}}{C_{\mathrm{prefill}}-C_{\mathrm{reuse}}}
$$

这里省略了两种方案共有的工作。论文的存储扩展模型进一步加入缓存体积 $S$、保存时长 $T$、单位体积单位时间的存储成本 $\sigma$，以及每次加载时单位体积的传输成本 $\beta_{\mathrm{net}}$；各项须换算为同一成本单位：

$$
C_{\mathrm{cached}}=C_{\mathrm{prefill}}+\sigma ST
+N(C_{\mathrm{reuse}}+\beta_{\mathrm{net}}S)
$$

</details>

**存储成本可以被更多请求摊薄，每次都要支付的传输成本却不会因请求数增加而消失**。缓存驻留在服务端与把完整张量逐次发送给远端消费者，是两种不同成本结构。[R33，§5，p.5](#ref-r33)

这份论文的加速实验比较了完整前缀计算和“缓存已经在设备上时的一步续算”，没有计入完整的加载与服务过程。因此，它能说明这两个计算环节的差别，不能直接代表用户请求从头到尾会快多少。

<details>
<summary>进阶：驻留缓存实验测了什么</summary>

论文的 8.6–49.7 倍是 Qwen3-4B、FP16、Apple M1 Pro/MPS、255–3774 token、每点 5 次运行中位数下，完整前缀 Prefill 与**驻留 KV 上的一步续算**的计算时间比，排除了磁盘 I/O。24/24 个贪心 token 一致的检查也只是一个有限样例，且 logits 存在小数值差异。这里 FP16 是数值格式，MPS 是相关设备计算后端，I/O 指数据读写，贪心选择是每步取最高分 token，logits 是转成概率前的预测分数。该实验既不是完整服务链路加速比，也不能直接换算成生产 GPU 的费用或服务商利润。[R33，§6–8，pp.5–7](#ref-r33)

</details>

**工程推导**：追加问题含多个 token 时，它们仍要与已缓存前缀交互；其开销不是与前缀长度无关的常数。决定缓存收益时，应实际计入后缀 Prefill、反序列化、传输、缓存管理和后续 Decode。

#### 10.8.2 API 缓存需要可观测的生命周期

缓存有“建立、保留、命中、过期或被淘汰”的过程。TTL 是存活时长；断点是接口允许标记的缓存边界。下面的参数和字段来自本地文档快照，阅读重点是怎样确认真的命中，而不是记住一组永久有效的配置。

Anthropic 本地文档快照给出一个具体例子：缓存的是按 `tools → system → messages` 组织的完整前缀，可使用自动缓存或显式断点；是否命中还受最小长度、TTL、断点查找范围和配置变化影响。相同文本反复出现，不保证已经满足这些条件。[R34，How prompt caching works、Cache limitations、What invalidates the cache](#ref-r34)

快照中讨论了 5 分钟与 1 小时 TTL，并说明过短输入可能不建立缓存；具体阈值、支持平台与价格需按部署时文档确认，本文不把快照参数当作永久 API 契约。

其 usage 字段将输入拆成：

$$
N_{\mathrm{input,total}}=
N_{\mathrm{cache,read}}+N_{\mathrm{cache,create}}+N_{\mathrm{uncached}}
$$

对应 `cache_read_input_tokens`、`cache_creation_input_tokens`、`input_tokens`。因此，只查看 `input_tokens` 会漏掉缓存部分的逻辑输入长度。这是该接口的字段语义，其他服务商必须分别核对。[R34，Tracking cache performance](#ref-r34)

**排查顺序建议**：先确认输入达到缓存条件，再查是否真正创建过条目、是否仍在生命周期内、匹配位置是否可找到，以及前缀或配置是否变化。将读取、创建与普通输入分别计量，才知道高命中是否真正降低全任务成本。

### 10.9 混合模型还需要恢复不同类型的历史状态

可以想象一份分块处理的历史：较早的完整块已被合并保存，最近尚未凑满一块的内容仍单独保留。恢复这两部分可能需要不同办法，所以“命中了多少前缀”未必能概括全部恢复工作。

第 4.9 节的 CSA/HCA 与滑动窗口组合，也改变了缓存管理。DeepSeek-V4 报告将已经形成的压缩条目与固定大小的近期状态分开管理；后者包含窗口 KV 和尚未凑成压缩块的尾部状态。不同层的压缩率、条目大小与淘汰方式并不相同。[R29，§3.5.1，pp.21–23](#ref-r29)

其磁盘缓存复用到最后一个完整压缩块；不完整尾部还要重新计算。对窗口 KV，报告比较全量保存、周期性检查点、完全不保存而重算三种方案。这里的“检查点”保存的是模型计算状态，**不是第 13 章描述的自然语言任务检查点**。[R29，§3.5.2，p.23](#ref-r29)

这说明“前缀命中多少 token”未必充分描述混合架构的恢复成本。工程测量还应区分压缩块命中、窗口状态加载与尾部重算；不能直接假设所有层都具有相同的逐 token KV 布局。

**读完自检**：报告文字没有变，但最前面的分析指令变了，原报告 KV 一定还能复用吗？

<details>
<summary>参考答案</summary>

不能仅凭报告文字相同判断。历史表示依赖前文和位置，还要检查模型及计算配置；相同片段不等于相同前缀。

</details>

<a id="s11"></a>
## 11. LongLLMLingua：减少模型看到的内容，但按问题保留信息

**本章的问题**：如果这次只问“半年收益是多少”，有必要把报告里的所有市场回顾都发进去吗？问题相关压缩会优先保留回答当前问题所需的内容。它会改变模型看到的文字，因此需要检查关键定义、数字和名称有没有被一起删掉。

**讲义连接**：第 48 页。与前缀缓存不同，Prompt Compression 真正改变了输入内容。

### 11.1 普通摘要与问题相关压缩的目标不同

普通摘要倾向于概括一份材料“主要讲了什么”；LongLLMLingua 关心“哪些内容对这个问题有帮助”。其框架由问题感知的粗到细压缩、文档重排、动态预算与子序列恢复组成。[R14，§4，pp.3–5，图 2](#ref-r14)

论文将压缩理解为：在减少输入长度的同时，尽量控制完整输入与压缩输入导致的输出差异。这和讲义后面的行为保真思想相关，但论文主要针对已知问题的回答。[R14，§2，p.2](#ref-r14)

### 11.2 粗粒度：怎样判断文档与问题的关系？

先从整篇或整段材料中选，再考虑删哪些 token，这叫从粗到细。$p(q\mid d)$ 可以读成“已经给了文档 $d$，问题 $q$ 在模型看来有多容易预测”。选择文档时固定同一个问题，例如“半年收益是多少”，分别提供收益说明和无关介绍，比较哪份材料更有助于模型预测这个问题。论文借助这类信号估计相关性，并不是直接得到了“文档能正确回答问题”的概率。

论文讨论了两个方向：给定问题预测文档 $p(d\mid q)$，与给定文档预测问题 $p(q\mid d)$。前者容易被文档中大量与问题无关的内容影响，论文因此使用后者对应的条件概率/困惑度信息进行关联判断。[R14，§4.1，p.3](#ref-r14)

这里不把正文中的分数符号直接转成未经核对的排序代码。实现时需核对具体损失定义、排序方向和源码，不能凭“分数越大越相关”的直觉照搬。

### 11.3 细粒度：语言上意外，不等于任务上重要

例如当前要核对收益，“基金 A 半年收益为 8.2%”中的期间和数值很重要，某个罕见但无关的人名则未必有用。词少见、难预测，和它对当前任务有帮助，是两回事。这一节通过比较“有没有提供当前问题时的预测表现”，寻找与问题相关的信号。

困惑度 PPL 衡量模型对文本的预测表现，可比条件下越低通常越容易预测；第 6.6 节介绍过它。仅按 token 本身的困惑度决定去留，会把“是不是容易预测”与“是否对问题有用”混在一起。论文采用 contrastive perplexity（对比困惑度）：

$$
s_i=\operatorname{PPL}(x_i\mid x_{<i})-
\operatorname{PPL}(x_i\mid q,x_{<i})
$$

它观察加入问题条件以后，token 的可预测性如何变化，从而识别问题相关信息。[R14，§4.1，p.4](#ref-r14)

本文保留论文的公式命名，不把一般意义上的 PPL 差值直接当作对数概率比使用。需要进一步推导信息论解释时，应核对论文对 “perplexity” 的具体定义与附录，而不是省略这些条件。

### 11.4 同样压短，结果可能完全不同

读这个实验时，先比较两种压缩方法：它们都把输入压到七八百 token，长度很接近，因此可以观察选择内容的方式有多重要。准确率越高越好，token 数越少表示输入越短；这两个指标不能彼此替代。

NaturalQuestions 的 20 文档实验中，将正确文档放在第 10 个位置，选取未使用重排的对应列：

| 输入方式 | 输入 token 数 | GPT-3.5-Turbo 准确率 |
|---|---:|---:|
| 原始 Prompt | 2946 | 54.1 |
| LLMLingua，约 4 倍压缩 | 775 | 23.5 |
| LongLLMLingua，约 4 倍压缩 | 748 | 71.2 |

来源：[R14，p.7，表 1](#ref-r14)。这是论文中固定历史模型与任务条件下的结果，不是当前模型上的保证。

两种压缩都把输入减到了七八百 token，一种明显变差，另一种变好。决定结果的不是“短”这个属性，而是保留了什么、删掉了什么。

两倍压缩的消融也支持这一点：第 10 个位置上，去掉问题感知的粗粒度选择，准确率从 70.8 降到 39.7。[R14，p.8，表 3](#ref-r14)

### 11.5 重要内容多留一点：动态预算和重排

LongLLMLingua 不对所有文档机械使用同一个压缩比例，而是将粗粒度的重要性判断用于细粒度预算分配；同时调整文档顺序，以改善模型在不同位置利用信息的差异。[R14，§4.2–4.3，pp.4–5](#ref-r14)

**工程启示**：背景说明、关键定义、实体名、唯一标识符和当前问题，未必适合相同压缩力度。按文本类型和任务重要性分配预算，比统一砍掉一半更值得测试。

### 11.6 理解大意和精确复述，是两件事

论文专门讨论实体名被 token 级压缩破坏的问题：模型可能大致理解所指对象，却复制残缺名称。因此，它根据原文、压缩文本和模型输出的子序列关系，恢复对应的原始字符串。[R14，§4.4，p.5](#ref-r14)

这与 Fast Weights 的关联问题形成呼应：**语义大致保留、对象—数值绑定正确、原始字符串精确，是三个不同标准**。

子序列恢复也不是通用的无损解压。被删除的任意语义并不会自动全部恢复。对文件路径、版本号、命令参数、代码标识符和精确数字，工程上应优先保留原样或用可靠 ID 绑定原件。

### 11.7 压缩器自己的开销必须计入

论文的端到端时延包括压缩时间与模型请求时间；部分方法虽减少输入，却因自身调用或顺序计算开销导致更慢。[R14，p.8，Latency evaluation](#ref-r14)

**工程决策**：不要只问“少了多少 token”，还要问压缩耗时、后续复用次数、是否破坏缓存，以及错误后是否需要额外恢复。压缩比例不是最终目标。

**读完自检**：压缩后 token 少了一半，就能判断方案更好吗？

<details>
<summary>参考答案</summary>

还要检查答案质量、精确名称与事实是否保留，并计入压缩耗时、缓存变化和额外恢复成本。

</details>

## 12. MemGPT：外部记忆的价值不只是能存，还在于能正确取回

**上一章留下的问题**：当前只问半年收益，下一步却可能追问去年同期。现在用不到的内容，未必永远用不到。MemGPT 的基本思路是把原始资料放在外部，需要时通过工具取回；本章重点看“发现缺口、查找、继续读取”的过程。

**讲义连接**：第 48 页的 Evidence Store，并为第 49–51 页的恢复与继续执行提供基础。

### 12.1 为什么问题相关压缩还不够？

LongLLMLingua 通常已经知道当前问题。长任务的下一步却可能变化：先找错误原因，再查引入错误的提交，再决定回滚方式。当前看似不相关的信息，未来可能重新重要。

MemGPT 选择建立主上下文与外部存储的层级，而不是要求一段固定摘要永远覆盖所有需求。[R13，§1–2，pp.1–3](#ref-r13)

### 12.2 MemGPT 的几个部分分别负责什么？

先按“本轮桌面”和“桌外保存”来分：Working context 与近期消息参与当前输入，Recall storage 保存可回查的历史交互，Archival storage 保存其他持久资料。FIFO 是先进先出的队列，较早进入的消息先到移出边界。下表的管理器和执行器负责把这种安排变成实际运行过程。

| 组件 | 作用 |
|---|---|
| System instructions | 只读控制规则，说明记忆层级与工具使用 |
| Working context | 有限、可编辑的工作区，保存当前重要信息 |
| FIFO queue | 近期消息、工具交互和系统事件 |
| Recall storage | 历史消息存储，可再次检索 |
| Archival storage | 更大的资料与持久化内容存储 |
| Queue manager / Function executor | 管理消息、溢出、工具执行和反馈 |

来源：[R13，§2，pp.2–3，图 3](#ref-r13)。外部存储不在模型当前输入中，必须通过工具换入才能使用。

论文示例会在接近窗口限制时发出 memory pressure 提示，给模型保存重要信息的机会；移出队列的消息仍留在 Recall storage。70%、100%、50% 等数值是论文示例，不是生产系统通用阈值。[R13，§2.2，p.3](#ref-r13)

### 12.3 控制流为什么与记忆同样重要？

控制流就是“程序下一步执行什么”。Heartbeat 在这里是让工具结束后继续触发模型执行的机制；一次查询只得到线索时，Agent 才有机会顺着线索继续查，而非立刻停止。

一次检索可能只提供下一次检索的线索。MemGPT 使用函数调用与 heartbeat 机制，让工具完成后立即继续模型执行，而不是马上等待下一条用户消息。[R13，§2.4，pp.3–4](#ref-r13)

```text
读取 A → 返回 B
判断 B 是否仍需展开
读取 B → 返回 C
检查终止条件
输出最终结果
```

这不只是多存了一些文本，而是把“何时查询、查什么、何时停止”纳入执行循环。

### 12.4 Nested KV：不一定要很长，也可能很难

这里的 KV 指实验数据里的键值对，和第 2—10 章的模型 KV Cache 是不同对象。例如记录写着 `A → B`、`B → C`，问题要求从 A 出发找最终值；只查一次得到 B 还没有完成。Nested 指这种嵌套关联，跳数就是顺着关系读取的次数。

MemGPT 的嵌套 KV 实验使用 140 个 UUID 键值对，约 8K token，通过增加关联跳数和改变位置来测试多跳读取。它并不只是靠超长输入制造难度。[R13，§3.2.2，pp.7–8](#ref-r13)

这与 NIAH 的 UUID-chain 可以联读：前者展示外部工具如何把部分读取步骤显式化；后者可以测试模型在输入内发现和串联关系的能力。[R02，Built-in tasks](#ref-r02)

多步工具读取在部分基础模型上改善了结果，但论文也观察到提前停止翻页、没有完成足够跳数等失败。基础模型的工具调用与控制能力，影响整个记忆系统表现。[R13，§3.2，pp.7–8](#ref-r13)

**外部存储扩大了可恢复范围，没有保证模型一定意识到自己缺少了什么**。

### 12.5 为什么“更多文档更好”和“删掉文档更好”可以同时成立？

MemGPT 文档 QA 中，正确文档可能不在最前面的检索结果，扩大读取范围可以提高证据覆盖。[R13，§3.2.1，pp.6–7](#ref-r13)

LongLLMLingua 则说明，当重要证据已经存在时，移除噪声并提高信息密度可能改善结果。[R14，§5，pp.6–8](#ref-r14)

两者对应不同情况：**关键材料还没找齐，就扩大查找与读取范围；材料已经有了却夹杂很多噪声，就改善筛选和组织。** 前一种“把相关材料尽可能找回来”常称为提高召回。

### 12.6 操作系统类比的边界

**进一步理解**：操作系统通常可以根据明确地址确定性地调入页面；Agent 却需要先判断知识缺口，再构造查询、选择结果。语义检索和自我判断并不具有同样的确定性。

因此，恢复设计不应只有向量检索。精确 ID、文件版本、页码、单元格、运行编号和原始命令，都可以降低恢复歧义。对于已知对象，优先精确读取通常比重新做模糊搜索更可控。这是工程建议，不是 MemGPT 论文已经给出的业务系统标准。

**读完自检**：检索得到 A→B，问题要求沿关联找到最终值，能否直接结束？

<details>
<summary>参考答案</summary>

要先检查 B 是否还指向其他内容。外部存储提供材料，执行控制决定是否继续查、何时停止；提前停止仍会失败。

</details>

## 13. Compaction：不是概括聊天，而是保存能够继续行动的状态

**本章的问题**：Agent 已经排查了几十步，窗口快满了，怎样让它接着做？可以把工作过程交接成一份较短的记录：任务是什么、限制有哪些、目前确认了什么、还没做什么、证据在哪里。Compaction 在这里指整理并缩短后续调用使用的历史视图；是否成功，要看交接后能否采取正确的下一步。

**讲义连接**：第 45–51 页。这是模型架构、外部记忆与 Agent 工程最终汇合的位置。

### 13.1 “摘要像不像”，不是最终标准

先把目标说直白：拿到交接记录的人，应该知道接下来怎样做，尽量接近他看过完整过程时的选择。文字写得流畅却漏掉“还没测试”，就可能让后续行动出错。下面的公式只是把“长度要受控、后续行为要尽量保持”写成数学形式。

<details>
<summary>进阶：用预算和后续行为描述压缩目标</summary>

讲义第 47 页把 Compaction 写成：

$$
\hat s_t=\mathcal C(H_t;B),\qquad |\hat s_t|\le B
$$

并希望：

$$
p(A_{\mathrm{future}}\mid H_t)\approx p(A_{\mathrm{future}}\mid\hat s_t)
$$

$H_t$ 是完整历史，$\hat s_t$ 是预算 $B$ 内的工作状态。目标是：只拿压缩后的状态继续工作，尽量接近拿完整历史继续工作。[L03，p.47](#ref-l03)

它与 LongLLMLingua 的输出保真目标相关，但更难：未来动作可能尚未确定，后续还会产生新的观察。本文将它理解为“面向后续决策的近似状态”，不把它当作已经证明的充分统计量。

</details>

### 13.2 一个思想实验：只差一个状态词，下一步就不同

两段历史几乎相同，唯一差别是：

```text
历史 A：代码修改完成，测试已运行并通过。
历史 B：代码修改完成，测试尚未运行。
```

如果都压成“修改已完成，可以继续提交”，文本概括看起来相近，却会导致错误行动。

保留关键差异后的交接可以是：

```text
A 的检查点：代码已改，当前改动的测试已通过；下一步检查 diff 和提交条件。
B 的检查点：代码已改，测试尚未运行；下一步运行测试，记录结果后再决定后续动作。
```

这里 diff 指修改前后的内容差异。真正系统里，A 还应关联测试运行记录，B 则不能提前填写“通过”。检查点只要保留这个状态差异，就能帮助两种历史走向不同的正确下一步。

**推论：只要两个历史要求不同的下一步，压缩器就不能轻易把它们合并成同一个状态**。这比“摘要覆盖了多少主题”更贴近 Agent 的目标。

### 13.3 讲义的 CI 示例：哪些信息真正服务于继续工作？

CI（持续集成）在这里可以理解为自动执行检查和测试的流程；`--workers=1` 是将相关工作进程数设为 1 的参数。先看下面哪种记录能让接手者继续操作。

原始过程包含 CI 超时、大量日志、端口冲突、把参数改为 `--workers=1`、测试通过，以及日志路径。讲义保留的是目标、原因、已验证设置、证据与下一步，而不是把每次尝试平均概括一遍。[L03，p.46](#ref-l03)

“我们调查并修复了测试问题”是一句流畅摘要，但接手的 Agent 不知道改哪个参数，也不知道哪次验证可信。

“原因是端口冲突；`--workers=1` 已通过测试；证据见指定运行日志；下一步检查并提交改动”，才包含足够的执行状态。

### 13.4 哪些要原样保留，哪些可以概括？

讲义第 48 页将内容区分为 Anchors、Checkpoint、Recent tail、Evidence store 与可丢弃内容。[L03，p.48](#ref-l03) “锚点”是仍然有效、需要准确保留的目标和限制；“最近尾部”就是最后一段尚在处理的消息与工具往来；“证据存储”保存可回查的原件。用户明确更新约束时，应记录新约束和替代关系，不能把“精确保留”理解为旧要求永远不能变化。

| 类型 | 例子 | 建议处理方式 |
|---|---|---|
| 精确锚点 | 目标、不可更改的约束、参数、版本 | 原样复制并校验，不反复自由改写 |
| 检查点 | 已完成步骤、决策、状态、待办、ID | 结构化更新，保留依据与未决事项 |
| 最近尾部 | 当前尝试、刚完成的工具调用及响应 | 在合法边界内保留足够完整的内容 |
| 外部证据 | 原始日志、表格、全文、版本快照 | 外置保存，留下可靠定位与恢复接口 |
| 冗余过程 | 重复搜索、过期草稿、被替代的输出 | 可从本轮视图中移除，不必删除原始审计记录 |

最后一列是工程展开。尤其应保留“尚未验证”“已证伪”“已被新版本替代”的状态，避免压缩以后猜测变成事实、旧结论重新生效。

### 13.5 重复压缩为什么会漂移？

讲义的例子是：

```text
CUDA 12.4
→ CUDA 12.x
→ 较新的 CUDA
→ 约束消失
```

每次似乎只省掉一点细节，累计起来却丢掉了精确约束。[L03，p.50](#ref-l03)

这种损失也可能发生在关系上，而不是单个词上。例如数字还在，但不再明确绑定对象、期间和单位。于是检查“数字有没有留下”仍可能漏掉错误。

**工程建议**：精确字段尽量由程序复制、按源记录重建，而不是依赖“摘要的摘要”。必要时从原始事件重新生成检查点，并校验关键锚点。保留最近尾部能减少活动步骤被过早概括，但不能代替长期约束与原始证据。

### 13.6 触发、切分、替换、恢复，是四个不同决策

讲义第 49 页给出 Trigger → Select → Replace → Recover。[L03，p.49](#ref-l03)

**触发**：何时压缩？可以由 token 预算、服务端溢出、手动请求或任务阶段决定。不要只等到完全越界后才处理；还要给输出、压缩操作本身及后续工具结果留下空间。

**选择**：压缩哪段？保护任务锚点和正在执行的工作。切点要遵守消息与工具协议。例如原记录是一条“读取日志”的工具请求，加上一条对应的日志返回，删掉前者却留下孤立的工具返回，可能使下一次输入不符合接口要求；不能随意把一组交互从中间切断，也不能把未完成步骤概括成已经完成。

**替换**：用什么表示？可以是可读摘要、结构化检查点或服务商定义的不透明条目。不透明条目指调用方不应自行解释或改写的专用数据。序列化则是把记录按接口要求组织成可传输、可保存的格式；不同表示的要求不同，不能随意把它们都拼成一段字符串。

**恢复**：失败怎么办？保留原始历史，候选结果不通过验证则不提交。后续动作需要精确依据时，回读原始证据，而不是继续猜。

### 13.7 一个可实现的事务式流程

“事务式”在这里强调先生成候选记录、验证通过后再整体切换。假设压缩开始时测试还没完成，生成摘要期间测试已经失败，如果直接用旧快照覆盖当前状态，就会漏掉新结果。会话版本检查用于发现这种变化；原子提交表示检查点和本轮视图作为一致的更新生效，避免只换了一半。

下面是设计流程，不是某个框架的现成 API：

```text
读取当前会话版本与任务锚点
→ 计算真实输入预算
→ 在合法边界选择待压缩区间
→ 生成候选检查点
→ 验证锚点、状态、证据 ID、工具关系与预算
→ 校验会话版本没有被并发修改
→ 原子提交新检查点与模型视图
→ 记录压缩事件、前后 token 数、成本和验证结果
→ 继续执行；涉及精确事实时按策略重新读取
```

在生成候选结果期间，不先删除原始历史；失败时记录失败事件并保留恢复依据。并发修改、取消和重试也需要明确语义，否则压缩器可能覆盖新产生的任务状态。

### 13.8 预算应面向下一段执行，而不是一个孤立百分比

假设总窗口是 100 个单位，本轮要给输出留 10，还希望后续有空间接收约 20 的工具结果，再留 5 的安全余量，那么压缩后的工作输入可以先以不超过 65 为目标。这是规划下一段执行的假设算例；真实系统要用 token 计数和具体接口限制来计算，不能机械套用这个比例。

**预算设计建议**：可以把输入预算理解为总窗口减去输出余量、计划内观察结果余量和安全余量。这里的“后续观察”是为接下来的执行留空间，不是说当前 API 必须把尚未产生的工具结果计入本次输入。

输入长度应按实际 tokenizer、消息模板与工具 Schema 估算或计数。不同模型、消息协议与多模态输入，不应统一用字符数代替硬边界。

70% 或 80% 可以作为实验起点，但不是正确性保证。更好的阈值取决于下一步需要多大的工具结果、还要工作多少轮，以及压缩本身的成本和风险。

### 13.9 压缩不能改变信任层级

**安全设计建议**：工具返回的网页、日志或文档是证据，不因为被写入检查点就自动变成高优先级指令。系统约束、用户目标与外部内容需要保留来源和角色边界。

同样，权限限制与需要人工确认的操作，不应只存在于一段容易被压缩掉的自然语言历史里。运行时权限控制与模型上下文管理，应互相配合，而不是互相替代。

### 13.10 ReSum：把摘要变成下一段执行的起点

可以把一次很长的搜索切成几段：第一段拿原问题搜索，快到窗口上限时整理已知信息；第二段拿“原问题＋摘要”继续搜索。ReSum 研究的就是这种接续方式。下文的 ReAct 指模型交替进行推理、工具行动和观察的执行方式；策略 $\pi$ 表示模型按当前信息产生输出或动作的规则。

ReSum 将普通 ReAct 历史 $H_t$ 在接近窗口限制时交给外部摘要工具，生成 $s_t$，再把工作历史重置为原始问题 $q$ 与摘要的组合：

$$
s_t\sim\pi_{\mathrm{sum}}(\cdot\mid H_t),\qquad
H_t\leftarrow(q,s_t)
$$

Agent 从这个状态继续调用搜索、浏览工具，直到回答或耗尽预算。论文实际采用规则触发，并未证明 Agent 总能自主决定最佳压缩时机。“可持续扩展探索”指单次窗口不再直接限制累计轨迹长度，不意味着没有调用预算、信息损失或失败风险。[R36，§3.1，p.3；附录 B，p.13](#ref-r36)

需要区分三件事：

| 层次 | ReSum 做了什么 | 不能混淆的结论 |
|---|---|---|
| 执行范式 | 触发摘要，以原问题和摘要启动下一段探索 | 可直接接入现有 Agent，不代表所有组件都未训练 |
| 摘要工具 | 可调用现成模型；作者另用 9000 余组 Conversation–Summary 数据训练 ReSumTool-30B | “training-free ReSum”主要指执行 Agent 无需为接入该范式另行训练 |
| 执行 Agent 训练 | ReSum-GRPO 让策略学习从摘要状态继续行动 | 是摘要续作适配，不是增大模型本身的上下文窗口 |

来源：[R36，§3.2–3.3，pp.4–5](#ref-r36)。

**原文模板与本文工程方案不同**。论文附录 C 的摘要提示要求整理明确、有助回答问题的信息，并刻意不强制输出信息缺口和行动计划，以免引入反复自我核验。本文第 13.4 节建议保留约束、未决状态和证据 ID，是面向更一般工程任务的设计，不能声称就是 ReSum 的原始模板。[R36，附录 C，p.14](#ref-r36)

在其主要免训练实验中，WebSailor 的窗口为 32K，各策略最多调用工具 60 次。以 WebSailor-30B 的 Pass@1（%）为例：

### 13.11 ReSum-GRPO：压缩了历史，还要训练策略会使用它

读完整历史和读交接摘要，输入形态不同，模型可能需要学习如何从摘要继续工作。这里的 rollout 是一次从任务开始到结束的执行轨迹；奖励表示最终表现好坏；优势表示某条轨迹相对同组其他轨迹表现怎样。GRPO 是利用这种组内比较来训练策略的方法，本章只解释它怎样用于摘要续作。

发生 $K$ 次摘要的轨迹可以分成 $K+1$ 段；首段从原问题开始，后续段从原问题和最近摘要开始。论文从整条轨迹的最终答案得到奖励，在同一问题的多条 rollout 间归一化成优势，再将**同一个轨迹级优势用于该轨迹的每一段训练**，这就是这里的“优势广播”。例如一次轨迹有三段，这三段都接收整条轨迹得出的同一个相对表现信号，而非各自获得独立评分。环境返回的工具观察不参与策略损失。[R36，§3.3，pp.4–5](#ref-r36)

这让早期探索和后续摘要条件下的动作都收到最终成功与否的学习信号，但不能据此判断每个动作究竟贡献了多少。“信用分配”讨论的就是把最终结果的好坏归到哪些动作上；这里的做法没有解决精确的逐动作因果归因，也不是 GRPO 的完整训练实现。

论文表 2 中，WebSailor-7B 的 BrowseComp Pass@1 为：标准 GRPO 模型用 ReAct 执行为 5.8，用 ReSum 执行为 8.5；ReSum-GRPO 模型用 ReSum 执行为 12.3。前两个结果有助于观察执行范式变化，后一个加入了范式相关训练。[R36，p.7，表 2](#ref-r36)

**比较边界必须一起看**。虽然训练数据为同一批 1K 样本、若干超参数相同，附录 D.2 明确给出：标准 GRPO 训练最多 40 次工具调用，ReSum-GRPO 为 60 次，输入/响应预算分配也不同；附录分析还报告后者约 1.5 倍训练时间。因此，不能把分数差全部归因于 advantage broadcasting，也不能称为严格等训练算力的单因素消融。[R36，p.8；附录 D.2，p.15](#ref-r36)

### 13.12 摘要、裁剪和重置：保留得更多不一定在所有搜索任务中更好

DeepSeek-V3.2 在上下文使用超过窗口 80% 时比较 Summary、丢弃前 75% 工具调用历史、丢弃全部工具调用历史，并加入多条独立轨迹的并行搜索基线。其 BrowseComp 实验中，Summary 在平均约 364 步的配置得到 60.2；Discard-all 在图示配置达到 67.6，并表现出不同的成本—质量曲线。[R09，§4.4，pp.16–17，图 6](#ref-r09)

这些点不是严格相同步数下的配对结果，不能直接把差值当作“删除历史比摘要提高多少”。它们仍提供一个有用的反例：**摘要不是无需比较就应采用的默认最优策略**。清理历史可以减少噪声与继续扩展探索，但也可能丢掉约束和必须保留的证据。

GLM-5 提供了更细的清理对象区分：Keep-recent-k 只把较早的工具观察替换成省略标记，保留轨迹中的其他部分，并非只留下最近几轮的所有消息。报告使用 $k=5$，其相应 BrowseComp 配置从 55.3 提升到 62.0；再与超过阈值时丢弃工具调用历史的重置结合，构成分层管理，阈值通过搜索取为 32K。[R25，§4.2.4，p.19](#ref-r25)

| 策略 | 主要操作 | 必须单独检查的风险 |
|---|---|---|
| 清理旧工具观察 | 减少大段、过时或可重新读取的结果 | 后续理由是否还引用已不可见的证据 |
| 保留最近尾部 | 裁去旧消息，留下近期工作 | 早期约束和已排除路线丢失 |
| 目标相关摘要 | 以概括状态继续执行 | 改写错误、关系丢失、重复摘要漂移 |
| 重置后重新探索 | 清空特定历史，保留题目重新推进 | 重复工作、丢失不可重建状态 |
| 检查点加证据恢复 | 保留关键状态并按需回读原件 | 未识别缺口、读取失败或证据版本错误 |

最后一行是本文工程方案，不是上述报告共同验证过的最优方法。搜索问答可重新检索的环境，也不同于已经修改文件、提交外部操作或受精确约束的执行任务；不能把 Discard-all 的实验结论直接迁移为“可以丢弃用户约束”。清理模型视图与删除持久化历史仍应分开。

## 14. 五个 Agent 项目：从论文思想到真实运行时

### 14.1 OpenCode：自动压缩、旧工具结果清理、预留空间要分开

附件 README 介绍 Agent 与文档入口，未包含完整压缩算法。[R16，Agents、Documentation](#ref-r16)

**官方资料补充**：初稿记录的配置页把 `compaction.auto`、`compaction.prune` 和 `compaction.reserved` 分别用于自动压缩、旧工具输出清理与压缩余量。[E01，Compaction](#ref-e01)

**工程启示**：不要把一切省 token 的动作都做成自由摘要。清理已经结束步骤的巨大输出，与概括跨步骤决策，是风险和成本不同的操作；前者也应保留证据定位。

### 14.2 Pi：追加压缩记录，再重建模型视图

“追加记录”是把压缩事件另存下来；“重建视图”是从完整会话里选出下一次真正发给模型的内容。下面的条目 ID 用于定位保留边界，类似明确交接从哪条记录接起。

附件将运行时状态管理、durable conversation 与 CLI 等职责分开列出。[R17，All Packages](#ref-r17)

**官方资料补充**：初稿记录的 Compaction 文档描述：追加 `CompactionEntry`，记录 `firstKeptEntryId`，以摘要和保留消息重建下一次输入；切点不应落在工具结果上。一次性摘要请求还会使用新的路由会话标识，并在支持时禁用 Prompt Cache 写入。[E02，Overview、How It Works、Cut Point Rules](#ref-e02)

**工程启示**：“当前不再发给模型”与“从会话存储删除”可以分开；压缩器也需要缓存策略，不必让一次性请求污染长期前缀缓存。

### 14.3 Codex：回合前与回合中压缩，可能有不同恢复布局

可以把“回合”理解为处理用户这一次请求的过程。开始处理前整理历史，与工具已经执行到一半时整理历史，可能需要保留和重新放入不同的信息；接续位置会影响下一次调用看到的消息顺序。

附件 Codex README 主要提供产品与文档入口，并没有展开这些实现。[R15，Docs](#ref-r15)

**官方源码补充**：初稿记录的 `compact.rs` 区分回合前/手动压缩与回合中压缩的初始上下文注入方式；注释说明其与摘要在历史中的位置有关。源码还维护压缩元数据与条目 ID，以保持运行中历史和持久化历史一致。[E03，`InitialContextInjection`、`CompactedHistoryMetadata`](#ref-e03)

**工程启示**：Compaction 不只是生成一段文本，也会改变协议布局。恢复顺序、角色和条目身份都应受测试覆盖，不能假设摘要插在哪里都一样。

### 14.4 OpenHands：Condenser 可插拔，但事件数不是 token 数

Condenser 是整理、压缩会话事件的组件；可插拔表示可以替换它的实现。事件可能是一条消息，也可能是一次工具调用或返回，因此“一条事件”并没有固定的文本长度。

附件明确区分 Agent Canvas、software-agent-sdk 与 automation 仓库，Agent、工具、会话和事件的核心职责位于 SDK。[R19，Repository boundaries](#ref-r19)

**官方资料补充**：初稿记录的 SDK 文档给出 `LLMSummarizingCondenser`，以摘要替换部分旧事件；示例配置 `max_size` 与 `keep_first`，并用事件数量说明触发与保留范围。[E04，Setting Up Condensing](#ref-e04)

**工程启示**：十条短消息与一条几十万字符的日志不能只按条数管理。事件层 Condenser 之外，还应有工具输出大小与真实 token 预算控制。文档示例不是整个生产预算策略。

### 14.5 Hermes：当前任务状态与跨会话记忆有不同生命周期

Hermes 附件描述了 Agent 整理的记忆、保存提示，以及基于全文搜索（这里使用 FTS5）和摘要的跨会话回忆，并列出压缩与用量查看入口。[R18，功能介绍、CLI vs Messaging Quick Reference](#ref-r18)

**工程启示**：本次 CI 临时分支属于当前任务；某类故障的诊断步骤可能成为长期经验。并不是当前上下文中的所有东西都值得永久保存，也不是被压缩的内容都可以失去恢复路径。

### 14.6 读这些项目时应追踪的一条调用链

```text
真实输入如何序列化与计数
→ 何时检查阈值
→ 怎样选择切点
→ 哪些内容受到保护
→ 谁生成摘要/检查点
→ 怎样验证和持久化
→ 压缩失败或取消后怎么办
→ 下一次调用如何重建
```

这条阅读路径比只搜索 `summarize` 更完整。观察是否记录原始事件、压缩版本、来源 ID 和最终实际 Prompt，才能判断系统在长任务中是否可复现、可恢复。

**读完自检**：某项目 README 说支持记忆，是否足以判断其压缩失败后能正确恢复？

<details>
<summary>参考答案</summary>

不够。还要追踪触发、切点、持久化、失败处理和下一轮输入重建；不同来源能证明的范围不同。

</details>

## 15. 工程落地：两个案例与一套最小可用 Context 架构

**把前面的知识串成一次实际工作**：模型每次开始前，需要知道任务进度，并拿到这一步所需证据。本章用修复代码和核对收益两个例子，说明完整历史、任务检查点和证据记录如何配合。代码块是方便程序读取的记录格式，先看每个字段表达什么即可。

本节都是根据前述材料提出的**工程设计示例**，不是已经跑完的实验，也不是对某个具体模型错误原因的诊断。

### 15.1 不先做复杂记忆平台，先把三份数据分开

```text
完整事件历史：发生过什么，用于追溯与重建
任务检查点：当前做到哪里，哪些限制与决定仍有效
证据存储：精确事实、原始材料、版本与定位
```

当前模型视图由这三者按需要构造：

```text
稳定指令与工具
+ 精确任务锚点
+ 当前检查点
+ 最近活动工作
+ 本步所需证据
```

它组合了 MemGPT 的层级思想、讲义的工作状态划分和多调用缓存的稳定前缀思路，但不是要求必须采用某个特定框架。

### 15.2 案例 A：修复 CI 超时

下方 YAML 是用缩进表示层次的文本格式。可以先当成交接单阅读：`constraints` 写限制，`verified_state` 写已确认状态，`pending` 写待办，`evidence_refs` 写证据位置。字段怎样命名可按系统约定，关键是这些职责不能丢。

沿用讲义的端口冲突案例，再加入一条假设约束“CUDA 版本必须保持 12.4”。一个可接续的检查点可以是：

```yaml
schema_version: 1
checkpoint_version: 3
task_id: ci-timeout-example

goal: 修复 CI 超时
constraints:
  cuda_version: "12.4"
  public_api_change_allowed: false

verified_state:
  cause: 端口冲突
  tested_setting: "--workers=1"
  test_status: passed
  test_run_id: ci-run-1842
  tested_code_snapshot: ci-code-v3

rejected_hypotheses:
  - hypothesis: 依赖安装超时
    status: refuted
    evidence_id: ci-log-1842
    evidence_section: 安装阶段

evidence_refs:
  - artifact_id: ci-log-1842
    artifact_version: "1"
    location: "/artifacts/ci-run-1842.log"

pending:
  - 检查实际 diff 是否只包含预期修改
  - 完成提交前检查

next_action: 读取 diff，完成检查后再决定是否提交
```

这段 YAML 是结构示例，里面的运行 ID、代码快照与路径均为假设。`evidence_id` 对应下方 `evidence_refs` 中的日志，安装阶段还应能由真实日志的行号或事件定位展开；`tested_code_snapshot` 指向测试实际运行的代码版本。实际系统必须保存这些对象并验证它们存在、对应正确，不能把“有一个路径或 ID 字符串”当作完成了可恢复性设计。

为什么要记录已证伪假说？因为压缩后容易重走旧路。为什么测试结果绑定运行 ID 和代码快照？因为“以前某次通过”不代表“当前改动已通过”；测试后若又改了代码，就要重新判断结果是否仍然适用。为什么 `pending` 不能省略？因为“主要问题解决”不等于“所有后续动作都已完成”。

### 15.3 案例 B：长报告中的数字与期间混淆

下面 JSON 用字段名和值保存一条事实。阅读时先找对象、期间、数值和来源，再看其他字段如何消除歧义；不需要先学习编写 JSON。

假设一份表中，基金 A 的半年累计收益率为 8.2%，一年累计收益率为 13.5%。这些是虚构数据，只用于说明绑定问题。

为便于后文引用，假设系统把半年记录编号为 `F-017`，一年记录编号为 `F-018`；下面只展示半年记录。编号负责指向事实，不代替事实内容的核验。

错误不一定是模型忘掉数字，也可能是只记住“8.2 和 13.5 都是基金 A 的收益”，却丢掉半年/一年关系。

因此，一条精确事实至少应是：

$$
\text{事实}=\text{对象}+\text{指标}+\text{期间}+\text{口径}+\text{单位}+\text{值}+\text{来源版本}
$$

一个示例记录：

```json
{
  "fact_id": "F-017",
  "entity": "基金A",
  "share_class": "A",
  "metric": "累计收益率",
  "period_start": "2025-01-01",
  "period_end": "2025-06-30",
  "value": "0.082",
  "unit": "ratio",
  "display_value": "8.2%",
  "source": {
    "artifact_id": "returns-v3",
    "artifact_version": "3",
    "sheet": "收益表",
    "cell": "G12"
  },
  "status": "verified"
}
```

`verified` 必须由实际校验流程赋予，不能只是模型随手生成的标签。上游抽取错了，结构化存储不会自动变正确。

### 15.4 让模型组织文字，让程序检查可确定的绑定

一个可实现的报告流程：

```text
确定当前章节需要哪些事实
→ 按精确条件读取事实记录与必要原文
→ 生成内部带 fact_id 的草稿
→ 检查对象、期间、口径、单位、值与来源是否一致
→ 对派生数字检查计算公式和输入版本
→ 通过后渲染正式文本
```

例如，草稿写“基金 A 半年收益为 13.5%”。13.5 本身可能是表中的真实数字，但校验器应发现它绑定一年期事实，而不是半年期事实。

这要求草稿同时提供可核对的结构化声明，例如“对象=基金 A、期间=半年、数值=13.5%、引用=F-018”。程序可以检查这些字段是否与事实记录一致，再用通过检查的字段渲染文字。只在一段自由文本旁贴上 `fact_id`，不能保证程序已经理解句子的意思；自由表述仍需要额外的语义检查。

这比只让另一个模型泛泛评价“文章准确吗”更有针对性。模型仍可辅助检查表达和复杂语义，但确定性的字段与计算应尽量使用程序核验。

### 15.5 压缩后重新取事实，而不是继续引用摘要里的数字

检查点可以保留“半年收益已验证，引用 F-017；一年收益引用 F-018”，而不要求摘要模型每次重新口述数值。

当前章节真正需要输出数字时，再取事实记录或原始单元格。这样，进度可以概括，精确事实依然受原始绑定约束。

**关键区别：工作状态负责告诉 Agent 下一步去哪；证据记录负责告诉它可以据什么说**。

### 15.6 工具结果应有恢复入口，不只是大段文本

建议工具响应分开提供：

| 内容 | 用途 |
|---|---|
| 本次操作状态与覆盖范围 | 知道操作是否成功、检查了多少 |
| 命中证据或结构化结果 | 支持当前步骤判断 |
| 原件 ID、版本和定位 | 支持精确回查 |
| 分页或继续读取入口 | 结果过多时按需展开 |
| 截断/省略标记 | 防止部分结果被误认为完整结果 |

日志工具可以返回错误分组、相关上下文、运行编号与完整日志；检索工具可以返回命中段落、文档版本、页码和展开入口；表格工具可以返回所需行列与明确的指标口径。

不要把“返回前 1000 字”当作普遍压缩策略。它减少长度，但没有保证证据与任务相关，也没有保证保留了否定条件或上下文。

### 15.7 缺失类判断还需要覆盖信息

以营销材料审核的工程任务为例：“检索结果里没有风险提示”与“整份材料没有风险提示”不同。前者只反映检索输出，后者需要充分的检查范围支持。

因此，检查点还应保存 `reviewed_pages`、未检查区域与解析失败情况。不得把 Top-K 检索未命中直接变成全文缺失结论。这是证据覆盖的逻辑要求，不是对某条法规的解释。

### 15.8 缓存与 Compaction 的联合取舍

可以沿用做报告的过程：还要继续读写很多轮时，花一次成本整理历史可能值得；若只剩最后一句，压缩和重建反而可能增加耗时。下面的不等式用于比较“现在额外付出的成本”与“后面预计省下的成本”，并不替代质量检查。

重写早期历史可能破坏前缀缓存；为了命中而一直携带大量旧内容，又可能增加读取开销和干扰。这是 SGLang 与 Compaction 两部分共同带来的问题。

**成本分析框架**：

$$
C_{\text{compact}}+C_{\text{rebuild}}
<\sum_{r=1}^{R}\left(C_{\text{old},r}-C_{\text{new},r}\right)
$$

左边是压缩与必要重建成本，右边是预期后续 $R$ 轮节省的成本。它只是决策框架，不是可脱离测量直接使用的精确模型；还必须满足质量和恢复约束。

一种值得实验的策略是：阶段内尽量追加并保持稳定；阶段结束时生成经过验证的检查点，按需重建视图。还剩两步与还剩五十步的任务，可能不适合相同压缩策略。

### 15.9 最小实施顺序

**先做可观察**：记录实际输入长度、工具返回长度、缓存命中、压缩事件、模型与材料版本，并能重建失败请求。

**再做可恢复**：保留完整事件和原始材料，增加检查点与精确证据 ID，明确压缩失败行为和回读规则。

**最后做优化**：在同一评测集上比较工具结果选择、不同压缩策略、前缀组织与服务配置，保留真正改善端到端任务结果的组合。

这三步比先搭很多记忆 Agent 更容易定位收益与风险，也更适合小团队逐步实现。

**读完自检**：报告中的 13.5% 确实存在，写成“半年收益为 13.5%”就可靠吗？

<details>
<summary>参考答案</summary>

不可靠。例子中 13.5% 属于一年，半年是 8.2%。要同时核对对象、指标、期间、单位、值及来源版本。

</details>

## 16. 评测：从“找得到针”升级为“压缩以后仍能做对”

**本章的问题**：改了缓存或压缩方法，怎样知道真的更好？先固定同一任务，再有意改变上下文条件，观察正确率、耗时与恢复过程。评测就是设计可比较的检验；基准是约定好的一组任务；基线是用来对照的原有或简单方法。

**讲义连接**：第 11 页与第 51 页。前者测有效上下文，后者测持续执行，两者不可替代。

### 16.1 NIAH 是起点，不是长上下文总分

NIAH 是“大海捞针”：把一条目标信息放进长文本，再问模型能否找出来。“插入深度”就是它位于全文开头、中间还是末尾；UUID 测试要求精确找回一串标识符，UUID-chain 还要沿多条关联继续查。第 6.2 节已经用它比较过保留与遗忘，这里关注怎样组织完整评测。

附件 NIAH 沿“长度 × 插入深度”扫描，并支持单事实、多事实、UUID 与 UUID-chain。[R02，Built-in tasks、Result rows & reconstruction](#ref-r02)

这些任务逐步增加事实数量、精确字符串要求和组合难度。讲义引用的早期 GPT-4 热力图来自 2023 年，只能作为历史实验说明，不能描述当前模型能力。[L03，p.11](#ref-l03) [R02，Original story & historical results](#ref-r02)

更合理的认识是：

$$
\text{任务可靠性}=f(\text{长度、位置、干扰、绑定难度、推理要求、恢复机制})
$$

这是能力维度的描述，不是已经拟合的定量函数。“支持 128K”无法替代这些维度的结果。

同样不能只看语言建模 PPL。大量目标可能主要依赖近处信息，PPL 在更长输入上稳定，仍不足以证明模型完成了远距离精确检索、状态更新或多跳推理。NoPE 论文对 PPL 与下游任务的分歧提供了具体例子。[R22，§7，p.9](#ref-r22)

### 16.2 用四组条件隔离故障位置

沿用半年收益任务，先只给正确表格和定义，再加入很长的历史，随后分别测试压缩且不回查、压缩且能回查。这样每一步都有明确对照，才能判断问题更可能发生在理解、长文利用、压缩还是恢复环节。

| 条件 | 所提供的上下文 | 主要诊断目标 |
|---|---|---|
| A：最小完整证据 | 完成当前任务所需证据，没有无关长历史 | 基础理解与推理能力 |
| B：完整长历史 | 原始材料与长交互，不做压缩 | 长度、位置、噪声和状态冲突 |
| C：压缩后不回查 | 仅检查点与保留尾部 | 压缩本身的保真度 |
| D：压缩后允许恢复 | 使用生产检索与读取流程 | 完整系统能否补救信息不足 |

这是建议的实验设计，未声称已经在任何模型上跑出结果。

A 就出错，不应只怪上下文长。B 正确而 C 错误，更支持压缩损失。C 错误而 D 恢复，说明取回原始证据有价值。D 仍错误，还需区分未发现缺口、查询错误、证据未召回和理解错误。

### 16.3 不只测试静态事实，还测试更新、撤销与未完成状态

Fast Weights 的重新赋值实验提醒我们，更新能力不同于容量；MemGPT 提醒我们，多跳读取需要正确终止条件；讲义提醒我们，摘要以后要继续做任务。[R06，§6.1.2](#ref-r06) [R13，§3.2.2](#ref-r13) [L03，p.51](#ref-l03)

建议植入以下类型的信息：

| 类型 | 示例 | 后续验证 |
|---|---|---|
| 精确限制 | CUDA 必须为 12.4 | 是否被改成宽泛版本 |
| 最新状态 | A 配置已被 B 替换 | 是否仍使用旧值 |
| 未完成工作 | 修改完成，测试未运行 | 是否直接宣称通过 |
| 已证伪路线 | 网络故障已排除 | 是否重复同一失败调查 |
| 分散证据 | A→B、B→C 分布不同位置 | 是否完成必要跳数 |
| 数值绑定 | 同对象、不同期间、相似数字 | 是否串期间或口径 |
| 覆盖信息 | 只检查了部分页面 | 是否输出全文缺失判断 |

### 16.4 Compaction 应使用 continuation-based evaluation

这个英文术语就是“让它继续做，再评价结果”。随机种子是控制随机过程的一项设置，多次重复用于观察结果是否稳定，不能用一次成功代替整体表现。

讲义第 51 页的流程是：植入状态 → 执行真实压缩策略 → 继续任务 → 测后续决策。[L03，p.51](#ref-l03)

不要只问摘要里有没有“CUDA 12.4”几个字。应该让 Agent 继续修改环境、运行测试或生成报告，观察它是否真的遵守约束并使用正确证据。

建议比较 0、1、3、5 次压缩，在多个长度、证据位置与随机种子下重复。压缩次数与长度应尽量分开控制，否则很难判断误差来自累计改写还是单纯历史更长。

### 16.5 指标要同时覆盖正确性、恢复和效率

| 指标 | 建议定义或测量方式 |
|---|---|
| 任务成功率 | 完成预定义验收条件的任务占比 |
| 精确约束违背率 | 触犯预先植入约束的任务占比 |
| 事实绑定准确率 | 对象、指标、期间、单位、值及版本全部正确的声明比例 |
| 证据支持率 | 关键结论有可访问且真正支持结论的证据比例 |
| 恢复成功率 | 明确需要回读证据的样本中，完成正确读取并继续执行的比例 |
| 重复失败率 | 再次执行已经明确证伪路线的任务比例 |
| 请求 TTFT / TPOT | 同时报告分布或分位数，不只平均值 |
| 全任务成本 | 输入、输出、工具、压缩、恢复与重试的总和 |
| 峰值资源与 Goodput | 指定服务目标下的显存、并发与达标请求率 |

这些指标是工程评测建议，不同业务需要定义清楚分母、验收条件与人工标注规则。不能只把模型自己的“已完成”文本当作成功标签。

计算全任务成本时，要先统一单位，例如全部折算为费用或设备时间；不同单价的 token、工具调用次数和秒数不能直接相加。各类 token 数、调用数和耗时仍应分别保留，便于解释成本变化。

### 16.6 三组最值得实际运行的实验

**实验一：能力与 Context 管理分离**：使用同一批长报告任务，比较最小证据、完整历史、自由摘要、结构化检查点与证据回读。重点看错误类型，不只看一个平均分。

还应加入只保留尾部、只清理旧工具观察以及重置的简单基线，分别对应不同信息损失方式。对有副作用的执行任务，所有条件都必须保护权限和不可丢弃的用户约束，不能为了基线而允许错误操作。本文提出的结构化方案也必须经过比较，不能预设其胜出。

**实验二：缓存到底省了什么**：同一长前缀下，比较冷缓存、完全相同前缀、仅追加内容、修改最前面的字段。记录实际 cached tokens、TTFT、TPOT 和总时延，区分复用 Prefill 与读取历史的成本。

对 API 分开记录 cache read、cache create 与普通输入，并测试生命周期和断点条件；对自部署分开计量驻留命中、磁盘加载、网络传输和重算。若测试 Prompt Cache 式模块复用，还需加入跨模块依赖问题，验证省下 Prefill 后是否损害质量。

**实验三：反复压缩后的真实行动**：在任务早期埋入约束，中间加入失败尝试和状态更新，压缩多次后继续执行。比较自由摘要与“精确锚点 + 检查点 + 最近尾部 + 原始证据回读”。

**共同控制条件**：使用相同任务、基础模型、工具环境、采样配置与重复次数；固定是否允许访问原件，并明确被删除的到底是观察文本、调用记录还是全部消息。基础的等工具调用上限实验之外，还应报告实际调用数、摘要与恢复模型成本，并绘制或列出质量随总 token、费用或时延预算变化的结果。不同策略很难同时严格等步数、等 token 和等时间，应说明控制哪一项，而不是笼统称为“同预算”。

论文复用也要遵守同样原则：ReSum 的免训练评测有统一调用上限，但其 RL 训练预算存在差异；DeepSeek-V3.2 图 6 是不同计算预算下的曲线；GLM-5 的策略和评测设置又不同。它们能帮助选基线，不能将各自分数排成一张统一策略排行榜。[R36，附录 D](#ref-r36) [R09，§4.4](#ref-r09) [R25，§4.2.4](#ref-r25)

### 16.7 失败必须能够复现

NIAH 附件保存实际插入位置、最终 token 数、随机种子、期望答案与响应，并提供重建实际输入的机制。[R02，Result rows & reconstruction](#ref-r02)

工程上建议记录的最小复现信息为：模型及运行配置、Prompt/工具 Schema 版本、材料版本、实际输入或可重建配方、工具响应、检查点版本、压缩前后边界、采样参数和最终验收结果。包含敏感内容时还要有访问控制，不应为了调试无边界复制数据。

### 16.8 一张排障表

| 现象 | 优先怀疑的层次 | 先收集什么 | 可比较的改动 |
|---|---|---|---|
| 长材料迟迟不出首字 | 排队、冷 Prefill | TTFT 分解、输入量、缓存量 | 前缀稳定、服务调度、输入选择 |
| 输出阶段很慢 | Decode、KV、批量 | TPOT、活跃 KV、并发 | GQA/MLA 模型差异、批量配置 |
| 输入内有事实却答错 | 信息利用或绑定 | 证据位置、相似干扰、最小证据对照 | 结构化证据、重排、任务分解 |
| 摘要后突然用旧结论 | 状态压缩 | 原历史、候选检查点、更新记录 | 保留有效性、撤销与版本字段 |
| 外部资料在但没有查询 | 恢复控制流 | 是否触发缺口判断、工具轨迹 | 精确读取规则、分步验证 |

## 17. 汇合后的五个洞见

**读到这里，把方法放回同一项任务**：报告原件在哪里，本次拿到哪些内容，模型内部怎样读，计算能否复用，任务进度怎样接续？本章用这几个问题把前面的方法联系起来，不再增加需要背诵的新架构。

以下是基于正文所分析材料的综合理解，而不是任何单篇论文的定理。

### 17.1 最根本的区别，是“什么时候决定什么重要”

线性状态在写入时已经合并历史，此时未来 Query 未必已知。DSA 等当前 Query 出现后再选择位置；CSA 则先压缩历史块，再做 Query 相关选择。LongLLMLingua 利用已知问题筛选内容。MemGPT 允许任务推进以后再查回原件。Compaction 则必须在当前预算与未来未知需求之间折中。

**重要性判断越早、丢弃越不可逆，对未来任务变化就越敏感**。这解释了为什么长任务系统需要恢复通道，而不能只追求更聪明的摘要。

### 17.2 “现在没读”与“以后也读不到”，是不同风险

某层稀疏注意力没选中一个位置，不等于应用原文永久消失。缓存被淘汰，可能只是以后重新计算。原始事件被唯一摘要覆盖，则可能再也无法恢复细节。

因此，应显式记录每个操作到底是跳过、移出工作集、淘汰可重算缓存，还是不可逆压缩。它们不应该共用一个模糊的“删除历史”概念。

### 17.3 减少 token，不是独立优化目标

LongLLMLingua 说明选择标准可以同时影响质量与长度；SGLang 说明前缀顺序决定复用；MemGPT 说明少带材料可能换来更多读取调用；DistServe 说明排队与服务目标决定实际价值。

所以，压缩率、缓存命中率、吞吐各自达到局部最优，并不能保证完整任务最优。最终应优化在质量与约束内完成任务的总成本。

ReSum、DeepSeek-V3.2 与 GLM-5 的策略实验还说明，摘要、裁剪和重置的收益取决于模型、可恢复性及探索预算。保留信息更多有助于接续，但保留噪声更多也有成本；应通过同任务对照确定取舍。

### 17.4 模型内记忆与应用外记忆，面对相似矛盾，但不是替代关系

DeltaNet 纠正关联，GDN/KDA 管理遗忘，检查点保存任务状态，证据库保留可回查的原始材料。它们都要处理写入、更新、读取与遗忘，但可控制程度和对象不同。

神经状态不能替代业务事实库的版本与定位；外部数据库也不能替代模型理解、多跳控制与正确选择。可靠系统需要明确分工，而不是要求单一机制包办。

### 17.5 有效 Context 是一个系统能力，不是一个窗口数字

窗口决定本轮允许放多少内容；架构决定怎样表示和访问；训练决定能否利用；服务决定成本与时延；工具和检查点决定哪些事实进入工作集；恢复机制决定离开工作集后是否还能找回。

最终可以用一句话概括这节课：

> **用架构控制历史访问成本，用缓存避免重复计算，用检查点保存可继续的任务状态，用原始证据守住精确事实，再用真实后续行动评测整个系统**。

对于长报告：进度可以概括，数字必须绑定。对于 Coding Agent：过程可以压缩，约束、当前状态和验证结果不能含糊。对于所有长任务：压缩以后要能继续做对，而不只是继续生成文字。

**读完自检**：“没被本层选中”“缓存被淘汰”“原件被唯一摘要覆盖”是否意味着同一种丢失？

<details>
<summary>参考答案</summary>

不是。分别涉及当前读取选择、可重算的计算状态，以及可能不可逆的原始信息损失。要先分清操作对象和恢复路径，再选择改进方法。

</details>

## 附录 A：公式与机制速查

### A.1 统一记号

**公式约定**：单个位置的向量写成列向量；把整段位置放进 $X,Q,K,V$ 时，按行堆叠相应向量的转置，所以批量公式写成 $Q=XW_Q$。矩阵投影符号按所在公式定义，不把批量右乘矩阵与单向量左乘矩阵视为无需转置的同一个对象。循环状态采用讲义的 $S_t\in\mathbb R^{d_k\times d_v}$，读取为 $S_t^\top q_t$；第 5.1 节使用特征映射后，行数相应变为特征维度 $m$。部分论文采用转置的状态定义，因此公式左右乘位置看起来不同。$\mathbb R^{a\times b}$ 表示有 $a$ 行、$b$ 列实数的矩阵，$\top$ 表示转置。

| 符号 | 含义 |
|---|---|
| $n$ | 当前序列长度 |
| $L$ | 层数；位置插值小节单独用 $L$ 表示原始长度 |
| $d_k,d_v$ | Key 与 Value 的每头维度 |
| $H_{\mathrm{KV}}$ | KV 头数 |
| $d_c,d_h^R$ | MLA 的联合 KV latent 维度与共享位置 Key 维度 |
| $b$ | 每个缓存元素占用的字节数 |
| $w$ | 局部窗口大小 |
| $K$ | 稀疏注意力选中的位置数；与 Key 矩阵 $K$ 按上下文区分 |
| $S_t$ | 按讲义约定的 $d_k\times d_v$ 快速状态 |
| $\alpha_t$ | 标量保留系数；KDA 使用向量形式 |
| $\beta_t$ | 当前关联的更新强度 |
| $B$ | Compaction 的 token 预算 |

### A.2 核心公式

| 机制 | 核心形式 | 必须记住的条件 |
|---|---|---|
| 稠密注意力 | $\operatorname{softmax}(QK^\top/\sqrt{d_k}+M)V$ | 因果掩码与数值实现另行处理 |
| 线性状态简式 | $S_t=S_{t-1}+k_tv_t^\top$ | 简式省略特征映射与归一化 |
| DeltaNet | $S_t=S_{t-1}+\beta_tk_t(v_t-S_{t-1}^\top k_t)^\top$ | 关联仍可能串扰，不是数据库隔离更新 |
| Gated DeltaNet | $S_t=\alpha_t(I-\beta_tk_tk_t^\top)S_{t-1}+\beta_tk_tv_t^\top$ | 先衰减，再针对衰减后状态修正 |
| KDA | $S_t=(I-\beta_tk_tk_t^\top)D_tS_{t-1}+\beta_tk_tv_t^\top$ | $D_t=\operatorname{Diag}(\boldsymbol\alpha_t)$；顺序不能任意交换 |
| 常规逻辑 KV | $2LnH_{\mathrm{KV}}d_hb$ | 同构层配置，不包含所有服务内存 |
| MLA 逻辑缓存 | $Ln(d_c+d_h^R)b$ | latent 联合承载内容 K/V，另存共享位置 Key；实际配置按层求和 |
| 请求时延 | $\mathrm{TTFT}+(m-1)\mathrm{TPOT}$ | TPOT 定义为首 token 后的平均间隔 |
| 多轮累计输入 | $TP+\Delta T(T-1)/2$ | 每轮固定增量；非实际 GPU 重算量 |

## 附录 B：最容易混淆的结论与实验边界

| 容易产生的误解 | 更准确的说法 |
|---|---|
| 能输入 128K，就能稳定利用其中任意信息 | 有效能力依赖任务、位置、干扰和训练 |
| 有 KV Cache，长历史就没有成本 | 重复计算减少，但读取、存储和新增位置交互仍有成本 |
| 单步 Decode 也是每步 $n^2$ | 有常规 KV 复用时，单步注意力部分随历史约线性增长 |
| FlashAttention 把稠密注意力变成线性 | 主要优化访存与中间矩阵物化，不消除所有成对计算 |
| PagedAttention 就是 Prefix Cache | 一个管理分配，一个管理计算复用，可以协作但概念不同 |
| 线性注意力是精确 Softmax 的有限维无损重排 | 实际有限维映射改变了机制，精确指数核有不同要求 |
| 固定状态意味着无限精确记忆 | 固定状态存在容量与干扰问题 |
| Delta Rule 只影响当前业务事实 | 有效更新可能影响相关方向；正交能保证不受本次更新影响，但业务对象不同不代表特征正交 |
| 加强遗忘总会提升长上下文 | 清理有收益，但可能伤害长期保留 |
| 混合 3∶1 是每三个 token 看一次历史 | 指层的组织；不是生成步频率 |
| NoPE 意味着不需要顺序 | 顺序可以由因果结构和循环状态体现 |
| NoPE 的构造性证明保证训练后任意长度外推 | 表达能力、优化是否学到与实际长度泛化是不同问题 |
| 改 RoPE 尺度后，旧 Key 缓存一定可直接复用 | 动态尺度可能改变历史旋转，需要一致的位置与缓存策略 |
| MLA 缓存只需保存一个内容 latent | DeepSeek-V2 还保存共享位置 Key；不能漏算这一部分 |
| 固定压缩率的 CSA/HCA 使全部计算变成线性 | 压缩条目仍随序列增长，相关 Prefill 仍可包含平方项 |
| DSA 所有计算都为 $O(nK)$ | 报告中的 indexer 仍有较小常数的平方项 |
| Kimi 的约六倍收益就是 batch=1 快六倍 | 必须区分固定批量时延与节省显存后增大批量的收益 |
| Longformer 的 8.3 点下降只来自删除全局注意力 | 对应消融同时改变全局注意力与独立投影 |
| LongLLMLingua 的收益来自单纯缩短输入 | 问题感知选择、预算、重排与恢复共同影响结果 |
| MemGPT 有外部存储，所以总能取回正确证据 | 是否发现缺口、是否正确查询和继续翻页仍可能失败 |
| Compaction 只要摘要覆盖率高就成功 | 必须检验压缩后的实际续作与约束遵守 |
| Prompt Cache 的独立模块组合等于完整稠密 Prefill | 独立编码缺少跨模块依赖；scaffolding 需额外预计算组合 |
| ReSum 的免训练方案意味着整套系统没有训练 | 执行 Agent 可直接使用，但摘要工具可以已经过专门训练 |
| 重置历史在搜索实验中有效，所以所有 Agent 都应清空历史 | 可重新检索的网页与不可重复的外部操作有不同恢复条件 |
| 模型缓存检查点等于自然语言任务检查点 | 前者恢复计算状态，后者保存任务语义，不能互相替代 |
| 检索没有命中，就证明全文不存在 | 缺失判断需要足够覆盖范围和解析质量 |
| README 提及记忆，就证明完整压缩实现已核实 | 需区分 README、官方文档、源码与特定发布版本 |

**对资料的使用边界**：本文已依据本地原文补充 Prompt Cache、ReSum、位置编码与插值、Ring Attention、PagedAttention 等机制和相应实验条件，但没有复现实验或验证它们的完整实现。FlashAttention 仍按讲义与配套材料提供的范围讨论。模型报告只选取与长上下文有关的内容，不展开全部预训练、RL、榜单和硬件细节；价格网页只作为历史资料入口，不将快照价格写成当前报价。部分网页快照缺少可核验正文，具体取舍见附录 D。这里区分“已收录材料”“已分析原文”和“已验证实现”。
