# Knowledge Agents 演讲：延伸一手资料核查

核查日期：2026-10-03。已先查阅本目录 `SOURCES.md`，并通读下列四篇网页正文。本文用于支持金融投研场景的工程延伸；**不能把这些文章的观点、实验数字和实现细节写成 Benjamin Clavié 演讲中的直接论述**。Mixedbread 文章虽有 Benjamin 署名，也不等于演讲逐字内容。

## 1. 多智能体研究系统：收益、委派和成本边界

来源：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)，Anthropic，2025-06-13；重点定位 Benefits、Prompt engineering 第 2 项、Appendix。

原文要点：开放研究会随发现改道；并行独立探索可分担上下文。委派应明确目标、产出格式、工具与来源、任务边界。强依赖、共享上下文需求高的任务较不适合。子任务成果可独立保存，再返回引用，避免多次转述。其数据中，单 agent 和多 agent 分别约用普通聊天 4 倍、15 倍 token；内部评测的多 agent 比单 agent 提升 90.2%，并非准确率。这些均为该系统的观察，不能外推为普遍成本或性能定律。

特别核查：这里的 **90.2%** 与演讲 BrowseComp-Plus 数值毫无同一实验关系；**15 倍的分母是普通聊天，不是单 agent**。内部评测比较还改变了执行组织和使用模型组合，不应写成等预算的架构因果结论。

## 2. 工具设计：按任务设计接口，再测实际使用

来源：[Writing effective tools for AI agents—using AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)，Anthropic，2025-09-11；重点定位 Principles for writing effective tools。

原文要点：不要机械地把现有 API 全部包装成工具；少量职责清楚、适合任务的工具可降低选择和上下文负担。返回高信号内容，支持过滤、分页和不同详细度；错误应给出可操作的修正方向。说明应显式解释默认术语、资源关系和输入输出。用真实任务与保留测试集验证，记录正确性、耗时、调用数、token 和工具错误。命名、格式的最佳选择依模型和任务而异。

易误读：文章允许一个工具合并常见的多步操作，不能据此规定“一项底层 API 就必须对应一个独立工具”；也没有支持“JSON 永远优于 Markdown”。

## 3. 上下文工程：按需取证，保留状态，谨慎压缩

来源：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，Anthropic，2025-09-29；重点定位 Context retrieval、Context engineering for long-horizon tasks。

原文要点：上下文工程管理整个推理输入，包括指令、工具、历史和外部数据。按需取回策略保存轻量引用，运行时加载原文；代价是探索可能更慢。可以结合预先检索与自主探索。长任务可使用压缩、外部结构化笔记、子 agent 独立上下文；过度压缩会丢失后来才显出重要性的细节。子 agent 的浓缩交付减少主上下文负担，但大窗口仍不能自动消除信息污染。

易误读：“有限注意力预算”是工程解释，不是每加入一个 token 都造成同等损失的定量定律；文中对法律、金融适用混合策略的表述是可能性判断，不能把整个金融信息环境概括为静态。事实数据库与证据追溯方案是我们的延伸。

## 4. Mixedbread 研究愿景：研究必须能服务真实工作

来源：[Our Research Vision, Part 1](https://www.mixedbread.com/blog/research-vision)，Benjamin Clavié、Aamir Shakir，2025-09-24；重点定位 Why we do what we do、Pillar 2: Real-World Usability。

原文要点：持续变化的外部知识不能仅靠模型记忆，搜索是智能体的重要基础工具；研究既需要明确收益，也必须考虑可部署性。离线高分不足以说明方案可用，服务成本、延迟、索引和压缩同样重要。文章提出研究与产品反馈的循环，并说明开放与封闭成果并存的路线。

易误读：这是作者的研究取向和公司愿景，不能作为多智能体提升投研收益、或某检索器必然优于 BM25 的实验依据。

## 金融投研的独立推导：如何把延伸内容讲清楚

以下均是基于以上资料和投研任务特征提出的设计建议，不是四篇文章已经验证的金融方案。

1. **给研究任务一张清楚的委派单。** 除目标和产出外，写明实体、期间、资料截止时间、指标口径、允许来源、排除范围、预算与停止条件。比如“核实利润增长来自主营还是一次性因素”，要明确不能直接把收入增长当成经营利润改善。
2. **先找可独立解决的问题，再决定是否并行。** 公司之间的事实核验通常比较容易拆开；同一公司利润归因与估值重算可能存在数据口径依赖，应先校准共同输入。不得把多 agent 本身设为验收目标。
3. **备忘录和事实记录各负其责。** 备忘录记录回答、证据引用、反证、未解问题；事实记录保存数值、单位、期间、口径和原始页码。写作时由事实记录重新取数，不依赖几轮之前的自然语言摘要。
4. **统一比较质量和总代价。** 同预算比较结果质量，再比较达到相同质量所需的机器成本和研究员复核时间。减少工具调用不是自动同比例减少费用；并行提速也不是自动减少 token。
5. **工具的粒度由失败案例决定。** 如果 agent 总把表格单位遗漏，可让读取工具一起返回表头、单位、脚注与邻页入口；如果总进行大量名单扫描，应提供实体与期间过滤，而不是仅加一句“认真检查”。
6. **评测应包含缺失和冲突。** 明确区分不存在、尚未找到、服务失败、来源冲突四类状态；评估系统是否停止无效搜索，以及是否避免把“未检索到风险”写成“没有风险”。

这组延伸资料最适合用于解释：为何主研究 agent 应管理问题和证据缺口；为何子 agent 需要清楚交付物；为何工具与上下文必须一起设计。它们不能替代对演讲原视频、演示幻灯片及 MADQA、BrowseComp-Plus 原论文的核查。
