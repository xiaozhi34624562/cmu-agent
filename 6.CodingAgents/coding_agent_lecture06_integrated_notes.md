## 1. 整体认识：从“生成什么”到“下一步做什么”，再到“是否应该交付”

### 1.1 三个对象，三个不同的评价问题

讲义第 2 页把能力分为写代码、修改仓库、参与整个软件开发生命周期。这三个层次不能只用同一种代码生成指标评价。[L06，p.2](#ref-l06)

| 对象 | 主要负责什么 | 应该怎样评价 |
|---|---|---|
| 代码模型 | 根据输入生成代码、解释或修改内容 | 语言知识、推理、补全、填空、局部编辑能力 |
| Coding Agent | 根据需求与环境反馈决定下一步行动 | 定位、工具使用、反馈利用、修复成功与停止判断 |
| 软件交付系统 | 确定变更能否被接受、发布与持续维护 | 回归、审查、权限、监控、恢复与后续变更成本 |

用户把相关代码和完整需求交给模型时，主要是在问“生成什么”。用户只提供一个行为异常时，Agent 还必须决定“去哪里找、先看什么、怎样确认”。当补丁准备合并或发布时，问题进一步变成“这些证据是否足以支持交付”。

讲义第 32 页给出的最终产物是 **Patch + evidence：补丁和证据**；第 61 页则明确区分测试通过与发布决定。[L06，pp.32、61](#ref-l06)

**工程推论：**失败不能统一归因于“模型不够聪明”。不知道怎样实现、没有找到正确文件、补丁应用错了位置、运行了错误测试、加载了旧版本代码，以及需求本身不清楚，分别需要不同的改进。

### 1.2 贯穿案例：零次重试为什么变成三次？

讲义使用下面的默认值逻辑：

```python
def retry_count(config):
    return config.get("retries") or 3
```

其约定是：缺失配置或值为 `None` 时返回 `3`；显式配置为 `0` 或正数时保留原值。原程序把零也当作假值，因而返回默认值。[L06，pp.34–36](#ref-l06)

| 输入 | 期望结果 | 原实现结果 |
|---|---:|---:|
| `{}` | 3 | 3 |
| `{"retries": None}` | 3 | 3 |
| `{"retries": 0}` | 0 | 3 |
| `{"retries": 2}` | 2 | 2 |

局部修复是：

```python
def retry_count(config):
    value = config.get("retries")
    return 3 if value is None else value
```

修改一行并不难。真实难点是：在陌生仓库中找到这段逻辑，确认零确实在这里被覆盖，知道调用者怎样使用它，最后验证问题消失且旧行为没有被破坏。

这里还要尊重需求边界。上述契约没有完整定义字符串、负数、布尔值等输入的处理方式。不能因为模型“想增强健壮性”，就顺便新增一套可能破坏兼容性的校验规则。

### 1.3 代码既是文本，也是可执行对象

CodeExecutor 论文区分代码的两个信息通道：变量名、注释等自然通道帮助理解意图；编译器和解释器处理的形式化通道决定精确执行语义。[R12，§1，p.1](#ref-r12)

```python
def disable_retries(config):
    return config.get("retries") or 3
```

函数名表达了“禁用重试”的暗示，却不会改变零被覆盖的实际行为。名字、注释与解释可以提供线索，但不能覆盖执行语义。

这解释了参考材料的分工：基础模型学习文本与代码分布；语法模型约束结构；DrRepair 使用诊断；CodeRL 使用测试结果；CodeExecutor 学习状态变化。**它们在缩小不同类型的错误空间。**

### 1.4 需求通常对应多个正确实现

“满足契约”并不意味着必须复现某一个参考字符串。条件表达式、普通分支以及其他等价结构，都可能完成任务。AlphaCode 将这类问题描述为 one-of-many：同一道问题存在许多不同算法和实现。[R17，§4.3，p.12](#ref-r17)

因此，参考答案的文本概率、与参考实现的相似程度、候选能否通过有限测试，以及真实需求是否满足，是相关但不同的问题。后面的训练、评估与搜索方法，都必须在这个区别下理解。

## 2. 基础能力：数据、Tokenizer、专业化与长上下文

**对应讲义：pp.7–13。主要材料：R01–R06。**

### 2.1 OLMo：不仅研究模型能力，也研究如何知道能力来自哪里

OLMo 的重要贡献是开放从数据、训练代码、评估代码到中间检查点和训练日志的完整研究条件。它区分训练中的 in-loop evaluation 与训练后的模型评估，并结合下游任务和困惑度等指标。[R01，§1、§2.4，pp.1–4](#ref-r01)

Dolma 数据流水线包括语言过滤、质量过滤、内容过滤、去重、多源混合与 tokenization，并保留来源之间的区分。[R01，§2.2，p.3](#ref-r01)

这里最适合迁移到 Agent 工程的不是某个超参数，而是**可控实验与可诊断性**。如果一次同时更换模型、提示词、工具接口、预算和测试集，即使成功率提高，也无法判断主要原因。

> **工程推论：**Agent 系统也需要版本化任务、固定环境、可重放过程和分阶段指标。否则“优化”很容易只是一次偶然成功。

OLMo 本身不是仓库修复 Agent 的直接实验证据。它在本课中提供的是基础训练和实验方法，不能被包装成完整开发能力已经得到证明。

### 2.2 StarCoder：代码数据应保留开发活动的结构

StarCoderBase 使用源代码、issue、提交记录和 Notebook 等数据。StarCoderBase 与后续专门增加 Python 训练的 StarCoder 也不是同一个训练阶段。[R02，§1，pp.1–3；§5，pp.14–16](#ref-r02)

论文第 15 页给出几种值得关注的结构：

```text
代码：仓库 / 文件元信息 + 源代码
Issue：标题 + 按参与者区分的评论序列
Notebook：解释文本 → 代码 → 输出 → 下一段解释
Commit：修改前代码 + 提交说明 + 修改后代码
```

对提交记录，论文会使用完整文件或变更附近的上下文窗口；对 issue 和 Notebook，则使用分隔标记保留不同内容的角色。[R02，§5.1，p.15](#ref-r02)

源代码说明“最终实现是什么”；提交记录补充“为什么以及怎样修改”；Notebook 的输出又增加“运行后发生什么”。这些不是完全可互换的数据。

但必须保留一条边界：**预训练时读过 commit，不等于模型已经稳定学会按用户指令做修改。**OctoPack 正是在进一步研究这个差距。

### 2.3 清洗规则并非越强越好，关键是它会删除什么

StarCoder 对不同语言做人工检查与差异化过滤。某些适合普通源码的字母比例过滤，会误伤 Assembly 等语言；因此，论文没有把同一个阈值机械用于所有文件。[R02，§3.1，p.5](#ref-r02)

Qwen2.5-Coder 则使用多阶段清洗处理文本—代码混合数据。报告第 5 页的图显示，数据保留量从约 582B token 降到 118B，而其 1.5B 模型在 HumanEval 与 MBPP 上的平均分从 41.6% 提升到 46.8%。这属于该清洗实验的结果，不是“任意删数据都能提高能力”。[R06，§3.1.1，p.5，图1](#ref-r06)

**工程推论：**企业训练数据不能只分成“代码”和“垃圾”。配置、测试、SQL、文档、生成代码、依赖清单与业务实现，对不同任务有不同价值。你保留什么，实际上是在选择模型将来更容易理解什么。

对于去重与污染，也不能只删除完全相同的字符串。讲义强调仓库 fork、复制库、相似文件、题目家族和评测泄漏等问题。训练集与评测集的划分单位，应与实际可能发生的重复关系相匹配。[L06，p.8](#ref-l06)

### 2.4 Tokenizer 不等于编译器的词法分析器

语言模型的 token 可能切开一个标识符，也可能把换行与多个空格组合起来。讲义第 9 页甚至给出了 StarCoder2 对缩进代码的实际切分，而不是按“关键字—变量—缩进”整齐分组。[L06，p.9](#ref-l06)

你提供的 `003_Whitespace-run_tokens.pdf` 是完整的 2021 年 Codex 论文。它在原有 tokenizer 上增加不同长度的空白串 token，使同样代码大约使用少 30% 的 token 表示。这个比例属于当时的具体设置，不能套用到全部模型。[R03，§3.2，p.4](#ref-r03)

你提供的 StarCoder2 tokenizer 配置则可以直接核对到：

```text
<fim_prefix>  → 1
<fim_middle>  → 2
<fim_suffix>  → 3
<repo_name>   → 5
<file_sep>    → 6
```

它采用数字预切分、ByteLevel 预处理与 BPE；这些事实来自真实 JSON 字段，不是从模型名称推断出来的。[R04，added_tokens、pre_tokenizer、model 字段](#ref-r04)

这对部署至少有两个影响。第一，实际可容纳的代码量同时受窗口长度与表示效率影响。第二，模型权重、tokenizer、输入模板和停止标记需要一起匹配。StarCoder2 的 `<fim_prefix>` 与 Qwen2.5-Coder 的 `<|fim_prefix|>` 不能只因为名字类似就互换。[R04，added_tokens](#ref-r04) [R06，§2，p.4，表2](#ref-r06)

不要把“减少 token”理解成随意删除代码空白。空白可能承担语法功能，也可能属于字符串字面量。也不要根据词表中出现 PR、review 或 issue 标记，就推断模型已经具备可靠的软件审查能力。

### 2.5 Code Llama：专业化不是只增加代码占比

Code Llama 从 Llama 2 初始化，再通过代码训练、长上下文训练与指令训练逐步专业化。7B、13B、34B 的初始追加代码训练为 500B token；上传报告中的 70B 变体有不同训练规模，不能统一概括为全部 500B。[R05，§2.1，p.3](#ref-r05)

在论文所列 500B 配方中，采样比例为 85% 代码、8% 与代码相关的自然语言、7% 一般自然语言。[R05，§2.2，pp.3–5，表1](#ref-r05)

为什么保留自然语言？报告希望保留理解能力，并观察到适量自然语言数据对部分代码任务有帮助。对 Coding Agent 而言，需求解释、错误理解、变更说明和下一步决策，也都不是纯代码续写。[R05，§2.2，p.3](#ref-r05)

另一个值得学习的实验细节是初始化。Codex 在其设置下没有观察到通用模型初始化带来最终性能优势，但收敛更快；Code Llama 的对照发现，从 Llama 2 初始化优于在相同追加数据上从零训练。[R03，§3.2，p.4](#ref-r03) [R05，§3.4.1，p.13](#ref-r05)

这不是可以用一句话消除的矛盾。实验的模型、数据与预算不同，Code Llama 还继承了基座预训练投入。**“相同追加代码训练预算”不等于“从零开始的总计算量相同”。**

### 2.6 Qwen 的混合实验：能力平衡，不是所有指标单调提高

`006_Qwen2.pdf` 的实际题名是 *Qwen2.5-Coder Technical Report*。它比较代码、文本与数学的组合，最终采用 70% 代码、20% 文本、10% 数学的混合。[R06，§3.1.2，p.6](#ref-r06)

| 代码 / 文本 / 数学比例 | Common coding | MATH | GSM8K | MMLU |
|---|---:|---:|---:|---:|
| 100 / 0 / 0 | 49.8 | 10.3 | 23.8 | 42.8 |
| 70 / 20 / 10 | 48.3 | 33.2 | 64.5 | 62.9 |

以上对应原论文表 3 的两行与选定列。可以看到，混合后综合能力更均衡，但 Common coding 并未提高。[R06，p.6，表3](#ref-r06)

> **来源差异：**讲义第 12 页把纯代码组 MMLU 写成了 23.8；原论文表 3 中，23.8 对应 GSM8K，MMLU 是 42.8。上表按原论文列名展示，不把讲义与论文的不同数字静默合并。原论文另外一行的比例表述也存在不一致，本文不使用该行推导结论。[L06，p.12](#ref-l06) [R06，p.6，表3](#ref-r06)

### 2.7 长上下文能力：长度、数据组织与任务训练缺一不可

讲义用 `types.py → worker.py → caller.py` 说明跨文件约束：一个类型允许 `None`，经过中间模块传递后，调用者需要补上空值处理。多个文件只是放在同一个窗口里还不够，它们之间需要有可以学习的关系。[L06，p.13](#ref-l06)

Qwen2.5-Coder 先做 8,192 token 的文件级训练，再使用约 300B 长上下文代码数据做仓库级训练，将训练长度扩展到 32,768，并通过 YaRN 支持更长输入。仓库级格式显式保留仓库名、文件路径与分隔符。[R06，§3.2，pp.6–7](#ref-r06)

Code Llama 同样区分长上下文训练长度与外推长度：长上下文微调使用 16,384 token 序列，论文另外评估更长输入上的行为。[R05，§2.4，p.4](#ref-r05)

**工程推论：**“装得下整个仓库”“找得到相关文件”“理解跨文件依赖”“修改后不破坏调用者”是四件事。长窗口可以减少一部分容量限制，但不自动完成定位与验证。

## 3. FIM：为什么会续写，不等于会编辑？

**对应讲义：pp.14–17。主要材料：InCoder、FIM scaling study；连接 Code Llama 与 Qwen。**

### 3.1 编辑改变了模型应该利用的条件信息

普通从左到右生成近似建模：

$$
P(\text{后续代码}\mid\text{前缀})
$$

而一个填空式编辑任务需要：

$$
P(\text{缺失片段}\mid\text{前缀},\text{后缀})
$$

例如讲义中的返回类型：

```python
def is_positive(x: int) -> ____:
    return x > 0
```

函数体位于空洞右边，它给出了返回 `bool` 的证据。对重试示例，右侧的 `else value` 同样会限制空洞内应该是什么结构。[L06，p.14](#ref-l06)

InCoder 的出发点正是：代码通常经过多轮编辑，而不是一次从左到右写完。[R07，§1，p.1](#ref-r07)

### 3.2 InCoder：改变数据顺序，而不是让模型读取“未来”

原程序可以分为 `Left + Span + Right`。InCoder 把它重排为：

```text
Left + <Mask:0> + Right + <Mask:0> + Span + <EOM>
```

第一次出现的 mask 标记空洞位置，第二次标记被移动片段的开始。生成 `Span` 时，左右两侧都已经出现在自回归序列的历史中。多个空洞用不同标记对应不同位置。[R07，§2，pp.2–3](#ref-r07)

模型依旧从左到右计算条件概率，架构不需要因此变成双向生成器。这里的技巧是**重新组织“什么信息先出现”**。

训练目标也需要区分清楚。InCoder 对重排后的序列进行训练，并排除 mask sentinel 的损失；FIM scaling study 保留前缀、后缀、中间三部分的语言建模信号，并强调训练结束标记。不能统一写成“FIM 只计算被挖空部分的损失”。[R07，§2.1，p.3](#ref-r07) [R08，§3，pp.6–7](#ref-r08)

### 3.3 InCoder 的同模型实验：生成前使用约束，比生成后补救更直接

为了隔离右侧上下文的作用，InCoder 使用同一个 6.7B 模型比较三种推理方式：只看左侧生成一个候选；只看左侧生成十个，再利用右侧重排；直接利用左右上下文生成。[R07，§4，p.4](#ref-r07)

| 推理方式 | 右侧上下文的用途 | 单行填空通过率 | 多行填空通过率 |
|---|---|---:|---:|
| 左到右，单候选 | 不使用 | 48.2% | 24.9% |
| 左到右，十候选重排 | 只用于选择 | 54.9% | 28.2% |
| Causal-masked infilling | 直接参与生成 | 69.0% | 38.6% |

这些是 HumanEval 衍生填空任务的结果，不是完整仓库任务成功率。[R07，p.5，表1](#ref-r07)

它说明，“先告诉模型约束，再生成”与“缺少约束时多猜几次，最后再挑选”并不等价。后者无法从全都偏离正确方向的候选中创造正确答案。

**工程推论：**编辑前补充必要的调用约定、类型与测试，可能比反复盲改更有效。不过这不是“上下文越多越好”的证明，相关性与结构仍然重要。

### 3.4 FIM scaling study：真实编辑边界会切开 token

FIM scaling study 不仅讨论能否填空，还研究怎样使训练与真实编辑场景匹配。它比较按行、BPE token、字符选择缺失片段。[R08，§4.5，p.12](#ref-r08)

| 训练时的挖空边界 | 单行填空 | 多行填空 | 任意字符片段填空 |
|---|---:|---:|---:|
| 按行选择 | 58.6% | 26.9% | 1.5% |
| 按 token 选择 | 54.8% | 24.2% | 10.2% |
| 按字符选择 | 55.7% | 25.0% | 32.1% |

表中为论文特定中等规模模型的通过率，原表使用小数，这里统一换算为百分比。[R08，p.12，表2](#ref-r08)

按行训练在按行评估中略好，但对任意编辑位置很弱。原因是光标可能停在一个变量名甚至一个 BPE token 中间，而训练中只见过完整行或完整 token 边界。

这是一种非常具体的部署失配：**模型不一定缺少程序知识，而可能不熟悉编辑接口产生的输入形态。**

### 3.5 数据打包顺序会破坏训练样本的约束关系

如果先把一个长文件重排为 FIM，再切成窗口，前缀或后缀可能在切分中丢失。论文比较 document-level 与 context-level FIM，后者在分块后处理，以减少这种碎片化。[R08，§3.2，p.7；§4.4，p.12](#ref-r08)

有趣的是，某些改动只造成极小的测试 loss 差异，却对应显著的实际生成差异。因此，训练流水线不能只以“张量形状正确、loss 正常下降”为验收条件，还需要检查模型实际收到的任务结构与生成表现。[R08，§4.4，p.12](#ref-r08)

这与 OLMo 的实验方法形成呼应：**损失用于观察学习过程，任务评估用于检验你真正关心的能力。**

### 3.6 PSM 与 SPM：任务格式也影响 KV cache

PSM 的内容顺序是 Prefix–Suffix–Middle；SPM 是 Suffix–Prefix–Middle。具体 sentinel 的放置与编码有细节，不能把下面的概念顺序当成任何模型都可直接接受的模板。

SPM 的动机之一是缓存复用：用户持续在光标处输入时，前缀更频繁变化，把相对稳定的后缀放在前面，有利于保留这部分计算。但若后缀变化，也会影响后面前缀的缓存。论文明确指出优势依赖应用场景。[R08，§3.1，p.7](#ref-r08)

因此，训练数据序列化、编辑体验与推理成本存在联系。它们不是完全独立的模块。

### 3.7 FIM-for-free 的准确含义

论文发现，在研究覆盖的模型与预算下，混合 FIM 训练可以增加填空能力，而不明显损害原有的从左到右能力。所谓 free 指这种能力权衡，不是没有训练成本，也不是任意训练目标都可无代价叠加。[R08，§1、§8，pp.3–5、17](#ref-r08)

反过来，先做纯自回归训练，再通过追加训练获得相近填空能力，在该论文实验中可能需要相当多计算量。其 100B token 普通预训练后的对照，只有较激进的 50B 追加训练、90% FIM 比例和相应学习率设置追上对照水平。[R08，§5，p.13，图9](#ref-r08)

Code Llama 将这类思想纳入代码训练；Qwen 则进一步做仓库级 FIM，并在后训练中混入部分 FIM 指令样本，以保留对应能力。[R05，§2.3，p.4](#ref-r05) [R06，§3.2.2、§4.2，pp.7、9](#ref-r06)

### 3.8 FIM 的能力边界，正是 Agent 的起点

FIM 解决“空洞位置已知、上下文已知时，生成什么”。它没有自动解决“应该改哪个文件、用户的意图是什么、修改是否引入回归”。

所以，从 FIM 到 Coding Agent，不只是把填空做得更长，而是增加任务理解、信息获取、修改选择与验证。

## 4. 从填空到修改：OctoPack 与 DrRepair 提供了什么？

**对应讲义：p.18，并连接 pp.33–35。主要材料：R09、R10。**

### 4.1 FIM 学“补什么”，提交记录还提供“为什么改”

FIM 的监督通常是被挖空代码到缺失片段；OctoPack 利用 Git commit 中的自然配对结构，把修改前代码、提交说明与修改后代码组织起来。[R09，摘要、§2，pp.1–4](#ref-r09)

下面是按其结构构造的教学样例，不是论文原始样本：

```text
修改前代码：
return config.get("retries") or 3

修改指令：
Preserve an explicit zero retry count.

修改后代码：
value = config.get("retries")
return 3 if value is None else value
```

这类数据提供的是“意图—行为变化”的联系。模型需要根据要求改变部分内容，同时保留其余内容，而不是恢复被随机删除的原文。

**工程推论：**训练编辑模型时，只收集最终正确代码，会丢掉修改方向的信息。保存问题说明、原代码、变更与验证结果，才能为后续编辑或 Agent 训练提供更完整的基础。

### 4.2 原始数据规模、过滤数据规模与训练样本规模必须分清

OctoPack 的 COMMITPACK 接近 4TB，覆盖 350 种编程语言；进一步过滤得到约 2GB 的 COMMITPACKFT。主要指令实验从中选取约 5,000 条、来自六种评测语言的样本，并与其他指令数据组合。[R09，§2，pp.3–4，表1](#ref-r09)

尤其值得注意的是，构建时过滤了涉及多个文件的提交，以减少指令歧义和复杂性。因此，它是对代码指令学习、局部修改能力的有力研究，不是多文件仓库开发的直接证明。[R09，§2，p.3](#ref-r09)

这也提醒我们：一篇论文宣布拥有很大的数据集合，不代表所有实验都使用了整个集合。阅读时要分别追踪原始库、清洗后库、实际训练子集和评测集。

### 4.3 指令训练不只增加知识，还塑造输出行为

OctoPack 的消融发现，提交记录对修复能力很重要；要让模型解释代码，训练数据中还需要自然语言作为目标输出。只训练“问题→代码”，模型可能在用户要求解释时仍继续生成代码。[R09，§4.1，pp.5–6，图4](#ref-r09)

这是 Coding Agent 的一个重要基础。一次开发任务中，模型可能先说明假设，再调用工具，再生成补丁，再汇总证据。这些行为之间的切换，不能完全由“模型会写代码”推出。

论文也观察到，小而有针对性的修改并不总比从头生成容易。模型可能原样重写错误函数、引入新错误，或者不擅长删除多余逻辑。[R09，§4.2，p.8](#ref-r09)

因此，代码生成分数高，不意味着局部修复、解释和修改范围控制同样强。

### 4.4 HumanEvalPack：用多任务评估避免只看“从零生成”

OctoPack 将 HumanEval 扩展为代码修复、代码解释和代码合成三类任务，并覆盖六种语言。[R09，§3，pp.4–5](#ref-r09)

其中 HumanEvalExplain 的设计很巧妙：先让模型把代码解释成自然语言，再由同一个模型根据解释重建代码，最后运行测试。为防止直接抄源码，它限制解释长度并移除较长的代码重合片段。[R09，§3，p.5](#ref-r09)

这个过程检验解释是否保留了足以重建行为的信息，但结果也受到第二次生成能力的影响。它不是纯粹的解释质量指标，更不是内部推理忠实性的证明。

**工程推论：**评价模型是否理解代码，不必只听它讲得是否流畅。可以要求它预测边界输入、生成能够区分版本的测试，或重建等价行为，再用外部执行检验。

### 4.5 DrRepair：诊断信息是推理证据，不只是一个失败标签

上传的 DrRepair 文件是 PMLR 摘要页，不是完整 PDF。摘要明确介绍了两点：用 program-feedback graph 连接源码与诊断信息中的相关符号，再用图神经网络建模；从无标签程序构造额外修复样本进行自监督预训练。[R10，Abstract](#ref-r10)

它所处理的核心困难是：**诊断中出现的符号与源码中的定义、使用位置需要关联起来，错误被发现的位置不一定是错误产生的位置。**

可以用一个教学示意理解：某处把变量声明成字符，后面却按字符串对象调用成员方法。诊断出现在方法调用处，但合理修复可能在更早的变量声明处。这个示意用于解释定位思想，不作为上传 HTML 已包含完整模型细节的证据。

把这件事放大到仓库级，用户看到“客户端仍在重试”，可能不是重试循环写错，而是上游配置把零覆盖了。**Localize 的目标不是定位一个报错字符串，而是定位足以解释异常的原因。**

### 4.6 OctoPack、DrRepair 与讲义循环的连接

OctoPack 提供“怎样根据修改意图改变代码”的监督；DrRepair 提供“怎样根据错误诊断寻找修复依据”的思路；讲义把二者放进一个多轮过程：定位原因、生成局部修改、执行验证，失败后修订假设。[L06，pp.18、33–36](#ref-l06)

这也解释了为什么高质量修复数据不能只有成功补丁。失败程序、诊断信息、当时的假设与验证结果，决定模型是否能学习从失败走向下一步。

## 5. 正确性评估：语法合法、相似、测试通过分别证明什么？

**对应讲义：pp.19–27。主要材料：R13、R14、R15、R03、R16。**

### 5.1 为什么文本相似度不足以衡量代码正确性？

讲义给出整数正数判断：

```python
return x > 0           # 参考行为
return x >= 0          # 在 x = 0 时改变了行为
return not (x <= 0)    # 对整数而言与第一种等价
```

第二种只改一个字符，却不满足要求；第三种写法不同，却可以满足相同语义。这里的“等价”限定在讲义给出的整数输入，不扩展到任意对象或浮点特殊值。[L06，p.20](#ref-l06)

因此，exact match 可能错罚不同正确实现，词重合指标也可能偏爱看起来很像、行为却错误的程序。

### 5.2 语法生成：先排除不合法的结构

Yin 与 Neubig 的语法生成模型不是直接自由输出所有源码 token，而是先构建 AST，再确定性地转换为代码。[R13，§1–2，pp.1–2](#ref-r13)

生成过程有两类动作：

```text
APPLYRULE：为当前 AST 节点选择适用的语法产生式。
GENTOKEN：在变量名、常量等终结符位置填入内容。
```

规则必须匹配当前待扩展节点；变量名还可以从输入描述中复制。论文也利用父节点信息反映递归结构。[R13，§3–4，pp.3–5](#ref-r13)

这种方法把一部分合法性先验交给确定性语法结构，减少模型从数据中重新学习所有语法规则的负担。但它不会单凭 AST 保证业务逻辑正确。一个合法的 `return 0`，仍然破坏默认值和正数重试行为。

**工程推论：**合法工具调用、合法 JSON、可应用补丁和合法 AST，都可以作为早期门槛；它们不能直接升级为最终验收。

### 5.3 CodeBLEU：把词、语法树与数据流结合起来

CodeBLEU 由四部分加权组合：

$$
\mathrm{CodeBLEU}
=\alpha\,\mathrm{BLEU}
+\beta\,\mathrm{BLEU}_{\mathrm{weight}}
+\gamma\,\mathrm{Match}_{\mathrm{AST}}
+\delta\,\mathrm{Match}_{\mathrm{DF}}.
$$

普通 BLEU 比较 n-gram；加权部分提高关键字的重要性；AST 匹配比较语法结构；数据流匹配比较变量值的依赖关系。[R14，§3，p.2](#ref-r14)

论文的均值计算例子很有说明力：总和变量与均值变量都已正确计算，最后返回哪个变量，只差很少文本，但意义完全不同。数据流可以补充词重合和 AST 结构难以区分的信息。为减小命名差异影响，论文还归一化数据流中的变量名。[R14，§3.2–3.3，p.3](#ref-r14)

不过，“数据流匹配”仍是一个评估代理，不是对功能正确性的形式证明。不同正确算法可能拥有不同 AST 和不同数据流；CodeBERTScore 论文也以此解释 CodeBLEU 的局限。[R15，§1，p.1](#ref-r15)

### 5.4 CodeBERTScore：比较带上下文的代码表示

CodeBERTScore 分别编码：

```text
需求或注释 + 参考代码
需求或注释 + 候选代码
```

然后对代码 token 的表示计算两两余弦相似度，用最佳匹配构造 precision 与 recall。需求参与编码，却不直接参与最终匹配计分；大部分非字母数字符号也被排除，论文保留了算术操作符等例外。[R15，§2.3，pp.3–4](#ref-r15)

设参考代码向量为 $r_i$，候选代码向量为 $c_j$，忽略可选权重后的直观形式为：

$$
P=\frac{1}{|C|}\sum_j\max_i\cos(r_i,c_j),
\qquad
R=\frac{1}{|R_f|}\sum_i\max_j\cos(r_i,c_j).
$$

其中 $|R_f|$ 表示参考代码参与计分的 token 数，避免与 recall 的符号混淆。论文报告 F1，也计算更强调 recall 的 F3：

$$
F_1=\frac{2PR}{P+R},
\qquad
F_3=\frac{10PR}{9P+R}.
$$

它能够比较词面不同而角色相近的代码，但仍有两条重要限制：需要参考实现；分数不是经过校准的“通过测试概率”。[R15，§2，pp.3–4](#ref-r15)

所以，CodeBERTScore 与 CodeRL 的 critic 不是同一个对象。前者比较参考与候选的表示，后者直接学习测试结果类别。名称中都有 Code，也都使用神经网络，并不意味着职责相同。

### 5.5 执行测试更接近行为，但证据范围仍然有限

HumanEval 使用签名、docstring 和测试来评价生成函数。它接受与参考答案不同但满足检查的实现，避免只盯住文本。[R03，§2，pp.2–4](#ref-r03)

然而，有限测试只观察有限条件。讲义同时强调测试的收益与依赖：需要可信检查、稳定依赖、隔离环境，以及时间和资源预算。[L06，pp.23–24](#ref-l06)

对贯穿案例，只测试零值会接受下面这个错误补丁：

```python
def retry_count(config):
    return 0
```

只测试配置缺失与正数，又会放过原始 `or 3`。真正关键的是测试是否区分了默认值与显式零，而不是测试文件里有多少断言。

### 5.6 EvalPlus：评价模型之前，还要评价测试是否充分

EvalPlus 通过 LLM 生成有意义的种子输入，再进行类型感知变异，用差分测试比较候选与参考实现的行为。[R16，§1–2.1，pp.2–4](#ref-r16)

```text
已有需求、参考程序、示例输入
        ↓
LLM 提供边界、复杂或困难输入
        ↓
程序按类型做数值、容器、字符串等变异
        ↓
输入契约检查
        ↓
候选与参考实现实际执行并比较输出
```

数值可以增减，列表可以删除、重复、插入元素，复合类型可以递归变异。模型提供语义上有价值的起点，程序低成本扩展输入空间。[R16，§2.1，p.4，表1](#ref-r16)

这里还存在一个不能忽略的 oracle 问题：差分测试假定参考实现可信。EvalPlus 也报告检查并修订了原有基准中的错误参考实现。因此，“有参考答案”不等于参考答案已经被证明正确。[R16，§3，p.6](#ref-r16)

### 5.7 输入契约：不要用未定义行为误判模型

如果需求只允许正整数，生成负数输入得到不同结果，未必构成有效缺陷。EvalPlus 用前置条件断言明确输入域，并过滤违反契约的样本。[R16，§2.3，p.5](#ref-r16)

迁移到工程中，修复重试配置时必须先明确“零是什么、缺失是什么、`None` 是什么”。不能测试写一套语义、实现猜另一套语义，最后把分歧都记成模型错误。

**测试正确性依赖需求正确性；执行精确，不代表需求已经无歧义。**

### 5.8 测试集可以很小，但应保留鉴别力

EvalPlus 不只增加测试，也研究如何减少成本。它把测试约简建模为集合覆盖：选择较小子集，尽量保留原有分支覆盖、变异缺陷检出能力与错误模型样本检出能力。[R16，§2.2，p.5](#ref-r16)

这里要区分代码覆盖率与缺陷检出率。某一行被执行过，不代表其所有错误实现都能被识别。变异测试通过主动修改比较符、操作符等，检查测试能否抓住这些人为错误。

测试约简保留的是选定要求下的能力，不是对未来所有未知缺陷的保证。用其他模型的错误样本选择测试时，论文还采用相应的留一模型设置，避免直接用待评模型结果为自身选择测试。[R16，§2.2，p.5](#ref-r16)

### 5.9 非功能需求需要相应证据

“输出正确”之外，还可能有性能、资源、安全和可维护性要求。讲义第 27 页展示运行计时、参考编辑比较和静态检查等不同评估手段。[L06，p.27](#ref-l06)

例如，课件要求对最大 $10^{12}$ 的 $n$ 计算 $1+\cdots+n$，逐项求和与公式在小输入上都正确，但其计算成本完全不同。[L06，p.29](#ref-l06)

```python
sum(range(n + 1))
n * (n + 1) // 2
```

**工程推论：**性能优化需要代表性负载与计时；安全修复需要针对威胁与受保护行为的检查；可维护性还需要审查。不能用“补丁像参考修改”替代全部验收。

## 6. 候选搜索：Codex、AlphaCode 与推理计算量

**对应讲义：pp.25–26、50。主要材料：R03、R17，并连接 CodeRL。**

### 6.1 pass@k 衡量候选集合，不直接衡量最终交付

对一项任务生成 $n$ 个候选，其中 $c$ 个通过测试。Codex 论文使用的 pass@k 估计为：

$$
\widehat{\mathrm{pass@k}}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad n\ge k.
$$

含义是“一减去抽出的 $k$ 个全都失败的概率”，再对任务求平均。论文采用这种估计以降低直接采样估计的方差，也指出把经验 pass@1 代入 $1-(1-\hat p)^k$ 不是同一个无偏估计。[R03，§2.1，p.3](#ref-r03)

但用户可能只接受一个补丁。十个候选中有一个正确，却最终提交另一个错误候选，仍然是交付失败。

因此，需要分别观察候选集合覆盖、选择器质量和最终选定补丁的成功率。

### 6.2 早期 Codex 实验揭示了“生成能力—选择能力”的差距

在 2021 年论文的 Codex-S 设置中，单样本解决 37.7% 的 HumanEval 问题；生成 100 个候选后按最高平均 log-probability 选择，解决 44.5%；知道测试答案的 oracle 选择达到 77.5%。这些数字属于历史研究模型与论文设定，不能混同于今天同名产品。[R03，p.2，图1](#ref-r03)

这个差距意味着：正确候选存在时，系统仍可能无法识别它。只提高生成次数而没有可信选择器，并不会自动得到 oracle 水平。

### 6.3 AlphaCode：大量采样之后，还有过滤和行为聚类

AlphaCode 的流程是：预训练与竞赛数据训练，针对新题生成大量候选，使用题目中的公开示例过滤，再根据程序行为聚类，从不同候选群体选择少量提交。[R17，§4.4–4.6，pp.12–13](#ref-r17)

论文讨论过百万级内部采样，但提交预算限制为每题最多十次。**内部生成量与对外提交量是两项不同预算。**

为什么不能直接从通过示例的候选里随便挑？因为许多代码虽然变量名与结构不同，却实现了同一种错误算法。如果它们全都在零值场景上错误，那么一千份表面不同的程序也没有提供一千种独立思路。

### 6.4 行为多样性比字面多样性更接近有效探索

AlphaCode 额外生成输入，运行剩余候选，把输出行为相同的程序分成一组，减少有限提交预算在同一类行为上的重复消耗。[R17，§4.6，p.13](#ref-r17)

一个重要细节是：**比较两个候选行为是否不同，不一定需要知道正确输出。**只要给它们相同输入，就可以观察是否产生不同结果。

但“相同行为”也不代表“正确行为”。多个候选可以共享同一个错误。论文按群组选择的经验结果，不是关于最大群组必然正确的定理。

### 6.5 AlphaCode 与 EvalPlus 都生成输入，但用途不同

EvalPlus 用参考输出判定正确性，必须避免无效输入造成误判；AlphaCode 的这一步用输入区分行为，原论文指出某些不完美输入仍可能帮助分组。[R16，§2.1、§2.3，pp.4–5](#ref-r16) [R17，§4.6，p.13](#ref-r17)

两者不能合并成“测试输入越多越好”这一句。**一个是用于验收，一个是用于搜索空间划分。**它们对输入质量的要求与产生的证据类型并不相同。

### 6.6 从图表看清推理扩展的前提

AlphaCode 第 20 页图 8 比较随机选十个、公开示例过滤、过滤加聚类，以及 oracle pass@k。内部采样量增加时，没有筛选机制的随机选择几乎不能利用新增候选；过滤和聚类则能把部分额外生成转化为解决率提升。[R17，p.20，图8](#ref-r17)

**工程推论：**增加推理预算前，先判断瓶颈在候选产生还是候选识别。若根因一直定位错误，应改善信息获取；若正确补丁经常出现却未被选中，应改善验证与排序；若所有候选都围绕同一错误思路，应改善行为层面的探索。

### 6.7 为什么 validation loss 有时不是解决率的好代理？

AlphaCode 报告，其一个早期 1B 训练实验中，验证语言建模 loss 在一定训练步数后上升，但目标解决率仍提高。作者推测，概率质量可能从一些不典型解法转向更典型的正确解法，使覆盖全部参考答案的似然变差，而找到可提交解法的机会变好。[R17，§6.5，pp.26–27，图13](#ref-r17)

这只是论文中的观察与解释，不意味着验证 loss 应该被忽略。它与 FIM 的实验共同提示：当最终任务是开放生成与候选选择时，**必须同时看任务级结果和训练代理指标**。

## 7. 执行反馈怎样进入训练：CodeRL、SFT、DPO 与推理重试

**对应讲义：p.18、pp.28–30。主要材料：R11；连接 R05、R06、R17。**

### 7.1 四种“用了执行反馈”的方法，机制并不一样

| 用法 | 是否改变模型权重 | 执行结果扮演什么角色 | 材料 |
|---|---|---|---|
| 推理时把错误回填，再生成 | 否 | 当前任务的观察与上下文 | DrRepair 思路、CodeRL 推理、讲义循环 |
| 筛选正确样本后做 SFT | 是 | 决定哪些监督样本进入训练 | Code Llama self-instruct |
| 根据反馈构造偏好后做 DPO | 是 | 构建候选之间的偏好关系 | Qwen2.5-Coder |
| 将测试结果转成奖励做 RL | 是 | 优化生成策略的任务回报 | CodeRL、讲义 DeepCoder 示例 |

“会反思”“会重试”不等于在线强化学习。判断标准是反馈是否进入参数更新，以及怎样进入。[L06，p.28](#ref-l06) [R05，§2.5，p.5](#ref-r05) [R06，§4.2，p.9](#ref-r06) [R11，§3，pp.5–10](#ref-r11)

### 7.2 为什么普通监督学习与程序正确性之间有距离？

设需求为 $d$，参考程序为 $y$。监督学习优化：

$$
\mathcal L_{\mathrm{SFT}}
=-\sum_t\log p_\theta(y_t\mid d,y_{<t}).
$$

训练时模型通常看到正确前缀，生成时则面对自己此前产生的 token。更关键的是，提高某个参考程序的似然，并不完全等同于提高“任意正确程序”的生成概率。CodeRL 把这些问题与测试反馈利用不足作为研究动机。[R11，§1、§3.1，pp.3、5](#ref-r11)

这不是说监督学习无用。CodeRL 自身就先做模仿学习 warm-start。它是在已有生成能力上，进一步利用程序执行结果。

### 7.3 执行奖励不可微，为什么仍然能训练？

CodeRL 将程序生成视为策略采样，以执行回报优化：

$$
J(\theta)=\mathbb E_{y\sim p_\theta(\cdot\mid d)}[R(y)].
$$

一种基础策略梯度形式为：

$$
\nabla_\theta J
=\mathbb E\left[
(R(y)-b)\sum_t\nabla_\theta\log p_\theta(y_t\mid d,y_{<t})
\right].
$$

这里的重点不是对编译器求导，而是根据一次采样的结果，提高或降低产生相应程序的概率。上式用于解释论文的基本出发点；CodeRL 随后加入了它特有的 critic 局部权重。[R11，§3.3，pp.6–8](#ref-r11)

### 7.4 四类结果与相对 baseline

CodeRL 的具体回报设计为：编译错误 `-1.0`，运行错误 `-0.6`，测试失败 `-0.3`，全部测试通过 `+1.0`。它使用贪心解码程序作为 baseline，利用采样程序与 baseline 的回报差。[R11，§3.3.1–3.3.2，p.7](#ref-r11)

假设 baseline 运行报错，而新程序能运行但未通过所有测试，相对回报仍可为正。这样可以利用尚不完美但较有希望的程序，而不是把所有失败一视同仁。

不过，这组数值不是通用软件风险排序。**工程推论：**在真实业务中，静默地产生错误数据可能比显式异常更危险，因此生产场景不能不加分析地复制竞赛程序生成的奖励设计。

### 7.5 Critic 的局部反馈不等于因果归因

CodeRL 训练一个 critic，输入需求与程序，预测编译错误、运行错误、测试失败或通过。再从 token 的上下文化表示中提取对应类别的分数，构造局部权重。[R11，§3.3.3，p.8](#ref-r11)

其 actor 更新思路可概括为：

$$
-\left(R(y)-R(y^{\mathrm{greedy}})\right)
\sum_t \hat q_\phi(y_t)
\nabla_\theta\log p_\theta(y_t\mid d,y_{<t}).
$$

训练阶段的局部权重取自对应实际结果类别的预测分数，不能一概称为“每个 token 的通过概率”。也不能把这些分数解释为通过逐 token 干预得到的真实因果贡献。它们是缓解反馈过于粗糙的一种学习近似，而不是精确指出错误源的证明。[R11，§3.3.3，p.8，式10](#ref-r11)

### 7.6 训练流程：先有可用策略，再利用反馈改进

论文先以交叉熵进行 warm-start，再固定 actor 收集生成样本训练 critic，随后结合交叉熵与 RL 目标继续训练 actor。[R11，§3.4，p.10](#ref-r11)

消融实验显示，在论文的 CodeT5-770M 设置下，已经 warm-start 后继续只做交叉熵或只做 RL 都可能退步；组合目标更稳定。相应表格还比较有无 baseline、critic 与简单位置权重。这里的部分 pass@k 消融采用 beam search，不能与所有随机采样结果不加区别地横比。[R11，§4.4，pp.12–13，表2–3](#ref-r11)

因此，从 CodeRL 得出的合理结论是“执行反馈值得进入训练，但必须处理基础能力、奖励、信用分配与稳定性”，而不是“代码可以执行，所以直接从零 RL 即可”。

### 7.7 Critic Sampling：从成功候选继续优化，从失败候选继续修复

CodeRL 的推理流程首先生成候选，并用题目中的公开示例测试检查。

当有候选通过示例时，critic 帮助选择有希望的程序前缀，以此作为种子继续生成和优化；当没有候选通过时，则选取失败程序，连同错误类别和信息交给修复模型。[R11，§3.3.4，pp.8–10，图4](#ref-r11)

```text
生成候选 → 运行公开示例
                  ├─ 有通过候选：选择前缀 → 部分再生成
                  └─ 全部失败：选择失败程序 + 诊断 → 修复
                                   ↓
                         再次检查与最终评估
```

这里必须区分公开示例与隐藏验收测试。前者可以用于推理反馈，后者用于最终评估；不能在不断读取隐藏答案的情况下声称模型具备同等泛化能力。

通过示例也不意味着通过全部隐藏测试。CodeRL 正是基于这一点保留了对已通过候选继续 refine 的分支。[R11，§3.3.4，p.8](#ref-r11)

### 7.8 把 CodeRL、DrRepair 与 AlphaCode 放在同一条搜索链上

AlphaCode 重点展示大量候选与行为筛选；DrRepair 重点利用诊断修复；CodeRL 同时研究如何用执行结果更新模型，以及推理时怎样修复和再生成。[R10，Abstract](#ref-r10) [R11，§3](#ref-r11) [R17，§4](#ref-r17)

它们并非互斥选项。在一个工程系统中，候选产生、诊断修复、筛选与模型训练，可以处在不同环节。真正需要防止的是把不同环节的成本和收益混为一个“模型更强”的结论。

### 7.9 Code Llama 与 Qwen 的执行反馈路径

Code Llama 的 self-instruct 会生成问题、测试和多个解答，保留通过测试的解答进入指令训练。这是执行筛选后的监督数据构造。它还保留少量代码与自然语言数据进行 rehearsal，避免能力回退。[R05，§2.5，p.5](#ref-r05)

Qwen2.5-Coder 在 SFT 后做离线 DPO：对算法式、自包含代码使用执行反馈；对其他复杂代码使用 LLM-as-a-judge。报告还描述多语言静态检查与沙箱，但不能因此声称所有复杂仓库样本都经过完整运行验证。[R06，§4.1–4.2，pp.8–9](#ref-r06)

这也给出一个监督质量上的区别：执行测试、模型偏好评分与人工验收可能都被称为“反馈”，但它们的可信边界、误差来源与适用场景并不相同。

### 7.10 DeepCoder 图中的 16K、32K、64K 不要读错

讲义第 30 页的 16K→32K 表示 RL 期间的**响应 token 上限**；星号对应的 64K 是评估时增加推理预算，没有进一步 RL。它不是输入上下文从 16K 扩展到 64K 的证据。[L06，p.30](#ref-l06)

读训练结果时，应分别检查：权重是否变化、训练数据是否增加、单次响应预算是否变大、是否生成更多候选，以及选择器是否变化。

## 8. 仓库级 Agent：定位—编辑—验证的闭环

**对应讲义：pp.31–37、44–45。前面所有论文在这里进入同一个工作流程。**

### 8.1 从程序生成升级为序贯决策

多数函数生成、填空和评分任务，都默认相关问题与代码已经整理好。真实开发任务却可能只有一句“我设置了零次重试，但系统仍然重试”。Agent 要自己决定获取哪些信息。[L06，pp.32–34](#ref-l06)

可以用下面的形式化视角理解这一点。记当前历史为：

$$
h_t=(\text{需求},\text{已观察代码},\text{此前动作},\text{工具结果}),
$$

策略选择下一步：

$$
a_t\sim\pi_\theta(a\mid h_t).
$$

这个视角用于解释讲义循环，不表示讲义给出了某个完整最优决策算法。关键是：模型并不直接拥有全部相关信息，需要通过动作逐渐获取。

有的动作改变仓库，如应用补丁；有的动作改变知识，如读取调用者；有的动作两者兼有，如运行程序得到日志与副作用。一个优秀的下一步可能没有生成任何代码，却排除了一个错误假设。

### 8.2 Localize：定位原因，而不只是命中关键词

对于零值问题，可以提出三种假设：

```text
假设 A：命令行参数解析没有保留整数 0。
假设 B：配置合并把 0 当作缺失值。
假设 C：客户端收到 0，但执行循环仍然重试。
```

这时，直接重写循环不是唯一选择。检查解析后的值，可以排除 A；观察客户端接收到的配置，可以区分 B 与 C。这些是教学推演，用于说明“能区分假设的动作”为什么有价值。

讲义第 44–45 页要求沿值的流动追踪：零在哪里被读入，在哪里变成三；依赖图帮助定位调用者、实现、使用者与相关测试，再通过执行确认。[L06，pp.44–45](#ref-l06)

这与 DrRepair 的联系非常直接：错误出现的位置、诊断中的符号与根因位置，需要建立关系。仓库级定位是在更大范围内做这件事。

### 8.3 代码检索：语义相似只是相关性的一种

在仓库里，最相关的文件可能与 issue 的词面差异很大。类型定义可能只说明某个字段可为 `None`；调用者可能使用缩写；默认值合并可能位于公共工具模块。

**工程推论：**定位可以按下面顺序逐步扩展，而不是一开始把全部仓库塞进上下文：

```text
仓库结构与项目配置
→ 错误、配置键、API、符号名搜索
→ 定义与引用
→ 调用者、被调用者、类型与数据流邻域
→ 相关测试与最小复现
→ 执行检查当前假设
```

这与讲义“检索相关邻域，再执行检查”的思想一致，但不意味着每个项目都需要先建设复杂图数据库。简单搜索可以是有效起点，关键在搜索策略与反馈利用。[L06，pp.39、44–45](#ref-l06)

### 8.4 Edit：写清语义变化，而不只描述文本变化

从：

```python
return config.get("retries") or 3
```

改成：

```python
value = config.get("retries")
return 3 if value is None else value
```

“把 `or` 改成条件表达式”只描述了文本；“把默认值触发条件从所有假值收窄到 `None`”才描述了语义。[L06，p.35](#ref-l06)

后者能直接连接需求、测试和审查。它同时说明哪些行为被改变，哪些行为应该保持。

**工程推论：**优先做能够解释需求的最小语义变更，不等于追求最少字符。真正目标是减少无关行为变化与审查范围。若确实需要跨模块修改，也应通过依赖关系和契约说明其必要性，而不是人为限制成一行补丁。

### 8.5 Verify：局部正确、调用链正确、回归正确要分别看

讲义中的四类输入构成局部语义验证：缺失、`None`、零、正数。[L06，p.36](#ref-l06)

真实仓库还要检查：配置是否经过另一层合并再次被覆盖；客户端是否确实使用这份配置；测试是否加载当前工作区代码；修复是否破坏原有默认值和正数行为。

可以把验证拆成三层：

| 验证层 | 要回答的问题 | 重试案例 |
|---|---|---|
| 局部契约 | 目标函数是否符合要求？ | 四类输入得到正确返回值 |
| 调用链 | 用户入口到最终行为是否贯通？ | 解析与合并后，客户端真正收到零 |
| 回归 | 相关原有行为是否保留？ | 默认和正数重试仍符合旧契约 |

这里的分层是工程设计。它将讲义 Fail→Pass 与 Pass→Pass 的思想落实成可检查的范围。[L06，pp.36、47](#ref-l06)

### 8.6 失败以后，应修订假设，而不是机械重复动作

如果零仍然变成三，可能还有另一个默认值覆盖点；如果缺失配置不再工作，可能修改条件破坏了原有契约；如果测试没启动，则首先是环境问题。

讲义第 33 页明确把失败指向“修订假设”。闭环不是“同样的提示词多跑几次”，而是让观察改变下一步。[L06，p.33](#ref-l06)

> **工程推论：**连续两次没有新证据、没有新假设、没有状态变化的重试，应视为停滞信号。系统应要求重读关键上下文、重新归因，或记录阻塞点，而不是无限循环。

### 8.7 Agentless：固定流程也是一种有效系统设计

讲义第 37 页用 Agentless 展示固定流程的对照：层次化定位文件、类或函数与编辑位置，再生成补丁，结合复现与回归检查进行验证和排序。[L06，p.37，原始流程图](#ref-l06)

它与开放式 Agent 的主要区别是控制流程由谁决定，不是是否使用 LLM。

**工程取舍：**对边界清楚、重复性高的任务，可以固定阶段与验收条件，在阶段内允许模型自主搜索。对未知环境或问题，增加自适应探索空间。无需先假定“越自主越先进”，也不能从单个实验得出固定流程永远更好。

## 9. 工具接口、上下文与状态一致性

**对应讲义：pp.38–45。连接 FIM 的格式敏感性、语法模型的动作约束与 DrRepair 的反馈利用。**

### 9.1 工具数量少，不代表行动空间小

讲义展示 shell-only 的工具集：同一个终端接口可以完成搜索、读取、文件编辑、构建和测试，并返回输出、退出状态与超时信息。[L06，p.39](#ref-l06)

因此，不能用“工具只有一个”判断 Agent 简单，也不能用“工具很多”判断能力强。一个 shell 背后已经包含很大的动作空间。

**工程取舍：**通用 shell 灵活，但模型需要正确组织命令；专用读取、补丁和测试工具更容易提供明确约束与结构化结果。选择取决于任务与模型适配，不只是接口数量。

### 9.2 编辑格式会改变实际成功率

讲义比较四类主要形式：

| 编辑方式 | 优点 | 典型风险 |
|---|---|---|
| 整文件重写 | 应用简单，适合创建小文件 | 重复大量未变代码，容易误删或顺手重构 |
| Search/Replace | 表达紧凑 | 旧内容不唯一或已变化时匹配失败 |
| Unified diff | 清楚表达局部增删 | 上下文、行号与补丁语法可能出错 |
| 文件操作补丁 | 显式表达新增、更新、删除 | 需要匹配具体工具解析协议 |

这些差异来自讲义对不同编辑接口的比较。[L06，pp.41–42](#ref-l06)

讲义第 43 页引用 Aider 的历史重构实验：89 个 Python 任务、特定 GPT-4 Turbo 版本下，Search/Replace 成功率为 20%，简化 unified diff 为 61%。这是特定模型、任务与工具实现的结果，不是“diff 永远优于 replace”的结论。[L06，p.43](#ref-l06)

它与 FIM 形成同一条原则：**模型的能力通过一个具体表示与接口发挥出来，接口不是完全中性的包装。**

### 9.3 补丁合理，不代表此刻能够安全应用

以下属于工程设计建议，而不是原论文中的统一接口标准。

补丁工具应检查目标路径、匹配是否唯一、文件是否已变化、变更是否在允许范围内。应用失败时返回明确原因，不应猜测模型“可能想改哪个位置”。

尤其在并发编辑中，要区分两个问题：

```text
这个补丁表达的意图是否正确？
这个补丁是否仍适用于当前版本的文件？
```

第二个问题是状态一致性，不是多写一句“请谨慎修改”就能解决。可考虑让补丁携带读取时的文件哈希或版本前提，失配后重新读取、重新生成。

局部编辑失败时，也不应自动升级为整文件重写，从而扩大未经确认的变化范围。

### 9.4 工具结果应保留下一步决策需要的信息

若测试只返回：

```text
Tests failed
```

Agent 无法区分逻辑错误、依赖缺失、超时和执行目录错误。

一个示意性的工具结果可以包括：

```json
{
  "status": "failed",
  "exit_code": 1,
  "timed_out": false,
  "working_directory": "/workspace/project",
  "command": "project-defined test command",
  "failed_tests": ["test_zero_retry"],
  "error_type": "AssertionError",
  "message": "expected 0, got 3",
  "code_state_id": "snapshot-17",
  "full_log": "artifacts/test-run-004.log"
}
```

这只是工程字段示例，不是某个现有工具的 schema。它落实了 DrRepair“诊断也是输入”和讲义“根据观察继续行动”的思想。[R10，Abstract](#ref-r10) [L06，pp.33、39](#ref-l06)

对长日志，可以返回关键摘要与原始日志定位，但不要丢弃最有鉴别力的错误信息。把全部失败压缩成同一种标签，相当于主动削弱 Agent 的决策条件。

### 9.5 上下文应组织成约束和证据，而不只是很多代码块

FIM 的右侧上下文、Qwen 的仓库结构、DrRepair 的符号关联，分别说明约束位置、文件关系和诊断关系的重要性。[R07，§4.1](#ref-r07) [R06，§3.2.2](#ref-r06) [R10，Abstract](#ref-r10)

**工程推论：**一个编辑上下文可以按“任务契约→目标实现→必要类型与调用者→相关测试→当前诊断”组织。并为片段保留来源路径、范围与版本，避免模型把不同版本的信息拼在一起。

这不意味着必须固定为同一种长提示词。上下文应由当前动作需要什么决定。定位阶段与精确编辑阶段所需的信息，可能不同。

### 9.6 长任务中，事实、假设与验证状态必须分开

建议持久化：已确认事实、未证实假设、已应用变更、已执行检查、未验证范围与下一步。示例：

```text
事实：参数解析后 retries 是整数 0。
事实：默认值函数把 0 变成 3。
假设：修复该函数即可解决客户端问题，调用链尚未检查。
变更：只在 value is None 时使用默认值。
已验证：四类局部输入。
未验证：客户端实际请求次数。
```

它比“已经看过配置模块，问题基本解决”更可恢复。这里是基于课程的工程推演，不是说讲义证明了某一种记忆格式最优。

还要区分上下文缓存与事实有效性。缓存复用节省计算；证据是否仍然对应当前代码，是另一件事。缓存命中不能证明信息没有过期。

### 9.7 验证结果应绑定代码与环境状态

“测试昨天通过”不是“这份补丁已通过”。只记录 Git commit 也不一定足够，因为工作区可能存在未提交修改。

建议绑定当前代码状态、依赖或环境标识、测试命令与实际结果。文件修改、依赖改变或测试入口变化后，需要重新判断旧证据是否仍然适用。

一个容易忽略的例子是 Python 导入路径：测试可能加载已安装的旧包，而不是当前工作区。此时测试结果本身可以真实，但它验证的是错误对象。**证据真实与证据相关，同样重要。**

## 10. Coding Agent 的评估、训练与 Harness

**对应讲义：pp.46–54。把函数级监督、执行奖励与完整开发任务连接起来。**

### 10.1 仓库修复的两条基本标准

讲义第 47 页区分：**Fail→Pass**，原来失败的目标行为恢复；**Pass→Pass**，原来正常的行为被保留。[L06，p.47](#ref-l06)

相比补丁文本匹配，这更接近开发需求。但结论依然受测试范围约束，不能把它理解为形式化证明。

工程评估还应分别记录环境启动失败、补丁应用失败、预算耗尽、任务逻辑失败与人工拒绝等状态。否则同一个“成功率”无法告诉你应该修模型、工具还是运行环境。

### 10.2 一条可执行任务，不是只有 issue 和 patch

讲义的 runnable task 包含起始文件、依赖、测试命令、任务说明、复现和行为检查。它要求先验证环境，再收集训练轨迹。[L06，p.48](#ref-l06)

一个任务资产更接近：

```text
代码快照
+ 可恢复执行环境
+ 用户可见需求
+ 允许的工具与权限
+ 复现和验收检查
+ Agent 交互过程
```

其中，“模型在任务开始时允许看见什么”也需要明确。目标补丁、隐藏测试或未来状态不能无意进入策略输入。

这与 OctoPack 的单文件编辑样本存在本质区别。后者提供修改意图与答案，前者还要教模型怎样在不完整信息中获取证据并行动。[R09，§2，pp.3–4](#ref-r09)

### 10.3 Agent SFT 的学习对象是行为轨迹，不是把所有文本都照抄

讲义第 49 页把 Assistant actions 标为训练目标，而文件发现、补丁应用结果、测试输出作为上下文。[L06，p.49](#ref-l06)

可以用一个示意损失表示：

$$
\mathcal L_{\mathrm{agent\text{-}SFT}}
=-\sum_{t\in\mathcal A}\log \pi_\theta(a_t\mid h_t),
$$

其中 $\mathcal A$ 表示被训练的 Assistant 行为位置。这是对讲义图示的形式化解释，具体实现还会涉及消息与 token 级别的掩码。

不要把工具输出的文件内容、错误堆栈、退出码都当成模型应该主动生成的动作。它们对下一步很重要，但监督角色不同。

### 10.4 多步骤 RL 的难点是延迟奖励与信用分配

Agent 轨迹可能包含搜索、读取、编辑、测试和结束。终局回报为“是否修复”，可写作：

$$
J(\theta)=\mathbb E_{\tau\sim\pi_\theta}[R(\tau)].
$$

讲义强调，最后失败不会自动指出哪一个早期决定错了。[L06，p.49](#ref-l06)

CodeRL 的 token 级反馈已经面对这个问题；仓库级任务还多了一层动作选择：错误定位、错误命令、不合适的测试顺序和环境失效都可能影响结局。

**工程推论：**即使训练以终局奖励为主，日志仍应保留中间行为与失败类别，用于诊断和任务质量检查。不能把环境无法启动一律记成“模型不会修复”。

### 10.5 SWE-smith：从可执行基线注入缺陷

讲义第 51–52 页展示的流程是：准备通过测试的基线，修改程序而不是测试，保留造成新测试失败的变异，再确认恢复正确实现后行为恢复。[L06，pp.51–52](#ref-l06)

```text
正确基线：4 个测试通过
    ↓ 将 is None 改成 not value
变异版本：3 个通过，零值测试失败
    ↓ 恢复正确条件
恢复版本：4 个测试通过
```

它比“让模型编一个 bug 和一个答案”多了执行约束。但合成缺陷可能过于局部、规律化，不能直接代表所有真实开发问题。这是对合成任务适用范围的工程提醒。

### 10.6 不同论文中的“变异”，并不是同一种监督

| 材料 | 主要变异对象 | 变异后要得到什么 |
|---|---|---|
| DrRepair | 正常程序 | 可用于学习诊断与修复的错误程序 |
| CodeExecutor | 可执行程序 | 更丰富的执行路径与状态轨迹，不必定义为待修复 bug |
| EvalPlus | 测试输入；并以程序变异评价测试能力 | 更多有效输入，以及测试能检出的缺陷集合 |
| 讲义中的 SWE-smith | 可运行仓库的程序实现 | 被测试验证成立的修复任务 |

[R10，Abstract](#ref-r10) [R12，§3，pp.3–4](#ref-r12) [R16，§2，pp.4–5](#ref-r16) [L06，pp.51–52](#ref-l06)

**程序被修改过不等于它就是 bug；执行没报错不等于它符合需求。**标签必须对应明确任务。

### 10.7 训练规模、推理规模与系统变化应分别计量

讲义第 50 页同时展示更多训练轨迹与更多推理 rollout、learned-verifier 选择的效果。[L06，p.50](#ref-l06)

读这种图时要分开：训练数据是否增加，权重是否改变，单个任务运行是否更久，是否生成更多候选，最终由什么选择器挑选。

对照实验最好固定一个维度再改另一个。否则系统效果提高，并不能直接归结为某种训练方法有效。

### 10.8 Multi-harness 不等于 Multi-agent

讲义定义：

```text
Harness = prompts + tools + agent loop + context management
```

多 harness 训练，是让同一个模型面对不同的提示、工具接口、循环与上下文组织方式；不是让多个 Agent 同时聊天。[L06，p.54](#ref-l06)

这与 FIM、编辑格式实验形成一条一致认识：模型与任务接口存在适配关系。更换模型后，原有编辑格式、日志摘要、上下文压缩和停止条件，都值得重新评测。

讲义列出若干框架与训练工作的例子。本文保留这一概念，不把这些名称当作当前可用性、功能或排行榜的重新核验结论。

### 10.9 多语言任务首先需要尊重项目本身

讲义第 53 页用 Python、TypeScript、Rust 对照说明，Agent 应先读项目配置，再选择构建与测试命令。[L06，p.53](#ref-l06)

看到 Python 就默认执行某一条 pytest 命令，看到 JavaScript 就默认执行某一个脚本，都可能绕过项目真正的验证入口。

**工程推论：**模型的跨语言生成能力与环境适配能力应分别测试。能写某种语言的代码，不代表它知道这个仓库如何安装、构建和运行。

## 11. 前端 Coding Agent：行为正确与视觉正确是两条验证链

**对应讲义：pp.55–59。连接代码执行评估与多模态观察。**

### 11.1 一个前端修复，不只是改对一个条件

讲义的表单例子原先检查 `value.length`，因此全空格名字也能保存；修改为 `value.trim().length` 后，空白输入应被拒绝。[L06，p.58](#ref-l06)

但交付证据不应停留在这行代码。要同时检查：没有产生错误记录；合法名字仍能保存；用户看到明确且可读的错误提示。

| 证据链 | 检查什么 | 单独不能证明什么 |
|---|---|---|
| 行为验证 | 输入、点击、状态变化、保存结果 | 错误提示是否被遮挡或难以阅读 |
| 视觉验证 | 布局、提示、可见性与呈现 | 数据库没有新增记录、后端状态正确 |

这是讲义从后端代码检查走向前端任务时增加的重要维度。[L06，pp.56–59](#ref-l06)

### 11.2 浏览器 Agent 与自动化脚本不承担相同职责

讲义区分：浏览器 Agent 每一步根据观察决定动作；自动化脚本把已知操作与断言写成可重复检查。[L06，p.57](#ref-l06)

前者适合探索不熟悉的界面，后者适合稳定复现和回归。截图可以用于视觉理解或与已批准基线比较，但不是所有前端任务都应该按截图相似度打分。

**工程推论：**先允许 Agent 探索操作路径，再把重要路径固化成可重复检查，能够把一次性探索结果转化为长期验证资产。不要每次都重新依赖模型临场判断相同按钮和状态。

### 11.3 Issue 带图片，不意味着评估规则是图片相似度

讲义第 59 页明确提醒，输入包含图像，不代表正确性由图像相似度决定。[L06，p.59](#ref-l06)

对 LLM 应用也是如此。页面显示“已完成”，不代表后台任务已完成；页面显示“结果已保存”，不代表保存的数据符合需求。这是教学迁移，不是讲义针对特定业务系统的测试结论。

因此，前端 Agent 要把视觉观察与真实状态对应起来，而不是用一张看起来正常的截图证明全部行为正确。

## 12. 从修复一个 Issue 到软件开发全生命周期

**对应讲义：pp.60–72。重点是任务类型、时间跨度与验收方式的变化。**

### 12.1 不同任务交付不同对象，也需要不同的完成证明

讲义第 63–69 页将开发任务展开为定位、应用创建、库实现、测试生成、CI 修复与持续维护。[L06，pp.63–69](#ref-l06)

| 任务 | 交付对象 | 主要验收问题 |
|---|---|---|
| 定位 | 文件、模块、函数等位置 | 是否找到与问题相关的修改位置？ |
| Issue 修复 | 补丁 | 目标行为是否恢复，旧行为是否保留？ |
| 库实现 | 一组协同工作的函数和模块 | 包级接口和集成测试是否成立？ |
| 应用创建与扩展 | 可运行应用 | 功能流程能否按测试计划完成？ |
| 测试生成 | 新测试 | 能否区分错误版与修复版？ |
| CI 修复 | 代码或构建配置 | 必需安装、构建与测试是否真正恢复？ |
| 持续维护 | 累积变更后的系统 | 依赖任务、回归与长期一致性是否保持？ |

如果把这些任务都用“生成代码是否像答案”来评分，就会丢掉真正目标。

### 12.2 定位任务与修复任务不相同

讲义用 CodeScout 说明可以单独评价文件、模块和函数层面的定位，并对照 gold patch 的位置；gold patch 不是策略输入。[L06，p.64](#ref-l06)

这有助于区分“找不到”与“找到了但不会修”。但定位 F1 不等于最终修复成功率：同一位置可以产生很多错误修改，正确修改也需要执行验证。

这里按上传讲义说明任务形式，不把讲义中的年份与名称当作当前外部研究状态的更新核验。

### 12.3 Commit0 与 ProgramBench：实现同一功能，信息来源可以不同

讲义第 66 页对照两种设定。Commit0 提供库骨架、文档与测试，要求一起实现多个函数；ProgramBench 提供参考可执行程序，通过输入—输出观察重建实现。[L06，p.66](#ref-l06)

前者更接近“根据明确接口补齐系统”，后者更接近“根据可观察行为重建功能”。不同内部设计可能都成立，因此更不能要求文本逐字匹配参考源码。

这与 AlphaCode 的 one-of-many 和 EvalPlus 的行为验证共同说明：**实现形式可以多样，但交付必须落在可检查的契约上。**

### 12.4 应用创建：从零构建、修改参考应用、修改自己的旧代码不同

讲义用 ViBench 区分 Zero-to-One、Vibe-on-Ref 与 Vibe-on-Vibe：从零创建，在参考 MVP 上扩展，以及在 Agent 自己之前创建的应用上继续修改；结果使用人为编写的浏览器测试计划检查。[L06，p.65](#ref-l06)

第三种任务尤其值得关注，因为模型必须承受此前设计选择的后果。一次性“能运行”的实现，未必能支持后续扩展。

**工程推论：**长期评估应包括多轮有依赖变更，而不只是把一组互不相关的任务分别从干净仓库启动。

### 12.5 测试生成：测试本身也要被验证

讲义第 68 页的 SWT-Bench 图示给出清楚判据：目标测试应在有 bug 的版本失败，在修复版通过。[L06，p.68，图示](#ref-l06)

```text
错误版失败，修复版通过：识别了目标差异。
错误版通过，修复版通过：没有捕获目标 bug。
错误版失败，修复版失败：测试可能不符合正确契约。
```

这与 EvalPlus 的测试鉴别力思想一致。因此，“新增了很多测试”不是可靠成果指标；应进一步问它们捕获了什么错误、保护了哪些行为。

### 12.6 CI 修复：恢复检查，而不是绕过检查

讲义的例子中，运行时版本不符合包要求，Agent 应检查项目支持的运行时，并重新运行安装、构建和测试。[L06，p.69](#ref-l06)

其中 Node 16、18、20 的数字属于课堂示例，不作为当前版本选型建议。真正要学习的是因果修复：使环境与项目要求一致，而不是删除失败步骤、忽略退出码或关闭必需检查。

这也可以看作验证系统的一条边界：**修改被检查的实现，与修改“怎样判定成功”不是同一件事。**后者需要单独授权和审查。

### 12.7 持续维护：系统必须承受自己的历史

讲义第 67 页的持续任务图示，把任务依赖与持续演化的代码库放在同一过程中，而不是每次回到独立初始快照。[L06，p.67，SWE-Milestone 图示](#ref-l06)

一个局部成功的补丁，可能增加重复逻辑、接口不一致或后续回归风险。这些问题在单次修复中不一定显现，却会在长期维护中积累。

**工程推论：**除了单次成功率，还应检查多轮变更后的旧测试、接口稳定性、人工审查成本，以及下一项需求需要多少返工。不要仅用一次完成的代码行数判断系统贡献。

### 12.8 中间技能训练与跨任务迁移

讲义第 70–72 页讨论代码定位、依赖搜索、函数实现和 bug 测试等技能，如何通过 SFT 或 RL 支持新仓库任务，并强调比较时的推理预算。[L06，pp.70–72](#ref-l06)

第 71 页的 SWE-Playground 流程图包含项目与任务提案、仓库搭建、测试与实现等步骤，用于生成开发练习；第 72 页展示 Hybrid-Gym 在修复、测试生成与库构建任务上的选定结果。[L06，pp.71–72，图示](#ref-l06)

本文只按讲义介绍这一研究方向，不把未附上的原论文视为已经完整复现或独立核验。应保留两个边界：不同任务的 success 定义不一定相同；中间技能改善还需要回到最终任务中验证。

### 12.9 不要把整个开发过程缩成写代码时间

讲义第 62 页引用一项 2019 年研究：在 5,928 个微软员工自报工作日中，读写代码和测试归入 coding，约占 15%。这是特定时期、样本与分类口径，不能推广成所有团队的固定比例。[L06，p.62](#ref-l06)

它在本课中的意义是：软件开发还有需求、沟通、调试、运行测试、审查、发布与维护。若生成更快却引入更多回归和审查负担，整体交付未必更快。

讲义第 61 页因而强调：**测试通过是开发中的一步，不是发布决定本身。**[L06，p.61](#ref-l06)

## 13. CodeExecutor 与世界模型：预测执行不能冒充真实执行

**对应讲义：pp.73–79。主要材料：R12。**

### 13.1 静态代码关系与具体执行轨迹不同

CodeBLEU 的数据流表示变量依赖；CodeExecutor 则研究在具体输入下哪些语句真正执行、变量状态怎样改变。静态结构有价值，但不足以直接给出全部动态行为。[R12，§1，p.1](#ref-r12)

例如：

```python
items = [1]
alias = items
alias.append(2)
result = len(items)
```

讲义中的真实结果是 `result == 2`。如果模型误把别名赋值当成复制，就会预测错误。[L06，p.75](#ref-l06)

这种错误不是少认识一个关键字，而是没有正确跟踪状态、引用与操作语义。

### 13.2 CodeExecutor 如何构造监督？

它使用可执行 Python 程序及其变异，训练模型预测执行行序列和中间变量状态。任务从单行状态变换、教程程序，逐渐扩展到 CodeNet 程序及其变异。[R12，§3–4，pp.3–5](#ref-r12)

```text
程序与输入
→ 第一步执行行及状态
→ 第二步执行行及状态
→ 循环、分支与函数调用
→ 最终输出
```

这里的数据变异不必被定义为待修复 bug。目的可以是生成更多可执行行为，以提供更丰富的动态语义监督。

论文也解释了为什么不能简单抓取任意 GitHub 程序：很多代码依赖外部模块、文件和资源，无法直接批量运行。[R12，§3.1，p.3](#ref-r12)

这再次连接到仓库级训练：**可执行环境决定了你能得到什么监督。**

### 13.3 课程学习带来改善，但不代表精确解释器

在 CodeNetMut 评估中，CodeExecutor 的输出准确率为 48.06%，完整轨迹准确率为 33.38%；去掉课程学习后分别为 45.93% 和 30.98%。这些是论文特定数据与模型的结果。[R12，§6.1，p.7](#ref-r12)

最终输出正确与完整轨迹正确不同。复杂数据结构操作、多分支、长循环和生成长度限制，仍会造成不忠实预测。论文也把 Python 范围与轨迹窗口长度列为限制。[R12，§6.2、Limitations，pp.8–9](#ref-r12)

因此，不应该把“模型学会预测执行”概括成“它已经是一个可替代解释器的执行器”。

### 13.4 预测执行怎样用于候选筛选？

CodeExecutor 论文先让 Codex 对每道 HumanEval 题生成 200 个候选，再预测候选对示例输入的输出，根据与预期输出的相似度排序，最终评估保留的前 50 个。[R12，§6.3，p.8](#ref-r12)

这里得到的是一个候选筛选机制，而不是只调用模型一次就输出最终正确程序。因此，读到表中的 pass@1 时，必须连同前面的 200→50 筛选流程一起理解。

它与 AlphaCode 的关联在于都改进候选选择；区别在于这里依赖学习到的执行预测，不能把预测输出当成真实运行结果。

### 13.5 Policy、World Model 与 Environment 的职责

讲义第 74 页区分：

$$
\pi(a\mid h)\quad\text{决定下一步做什么},
$$

$$
p(o'\mid h,a)\quad\text{预测行动后会观察到什么}.
$$

真实环境通过实际执行产生观察。[L06，p.74](#ref-l06)

| 对象 | 重试案例中的问题 |
|---|---|
| 策略 | 先检查配置入口，还是先运行零值测试？ |
| 世界模型 | 运行这项测试后，大概会得到什么结果？ |
| 真实环境 | 这份代码在这个环境里实际产生了什么结果？ |

三者可以协作，但不能相互替代。一个模型既可以生成动作，也可以被训练预测结果；这不意味着它预测的结果已经获得真实执行证据。

### 13.6 两种 Code World Model 路线不要混淆

讲义第 77 页的 CWM 延续从程序执行相关数据学习行为预测的方向；第 78 页的 Code World Models / GIF-MCTS 则展示另一条路线：生成一个由代码实现的环境模拟器，通过真实轨迹校验和修订，再用于规划。[L06，pp.77–78，图示](#ref-l06)

```text
路线 A：神经模型直接预测代码或行动的结果。
路线 B：模型生成可执行模拟器，由模拟器计算环境变化。
```

这里按讲义图示区分机制，不补充未提供原文中的额外训练指标。前者的风险是预测不忠实，后者的风险是合成模拟器与真实环境不一致。

### 13.7 世界模型要用最终决策效果评价

讲义第 76 页展示一个反例：正确补丁被预测为失败，错误补丁被预测为成功，选择器因此留下错误补丁。[L06，p.76](#ref-l06)

平均预测准确率不错，也可能在最关键的候选上犯错。需要同时看任务成功率、错误丢弃正确候选的情况，以及总延迟、token 与环境调用是否真正下降。第 79 页还要求关注新程序、依赖和环境下的泛化与真实执行回退条件。[L06，p.79](#ref-l06)

**工程推论：**预测更适合用于安排检查顺序、筛查明显无效动作或辅助规划。对便宜且确定性的关键测试，真实执行往往更容易形成可审计证据。关键交付结论不应仅由未验证预测支持。

## 14. 工程实践：把课程能力组织成一个可靠系统

> **本章为工程推论。**它将讲义与参考论文中的机制转换为设计建议，不声称这些具体架构、字段或流程已经由某篇论文整体验证。

### 14.1 最小系统不必有很多 Agent，但应有清晰职责

一个可行的起点是一个主 Agent 加确定性工具与验证器，分清四项职责：

| 职责 | 负责的事情 | 对应课程思想 |
|---|---|---|
| 任务与契约 | 改变什么、保留什么、输入边界、完成条件 | EvalPlus 的契约与任务歧义 |
| 行动控制 | 定位、读取、编辑、测试、失败后的调整 | Localize–Edit–Verify、诊断反馈 |
| 执行与状态 | 工作区、补丁应用、资源限制、日志、恢复点 | 代码执行、环境可复现性 |
| 独立验证 | 目标行为、回归与未验证范围 | Fail→Pass、Pass→Pass、测试鉴别力 |

这些职责可以由同一模型与不同程序模块承担，不意味着必须拆成四个聊天角色。职责边界比 Agent 数量更重要。

### 14.2 把“请修好”改成可验证契约

一个好的任务说明至少描述目标变化、保持不变的行为与验证要求。例如：

```text
目标：显式 retries=0 时不进行额外重试。
保留：缺失或 None 使用默认值 3；正数配置保持原语义。
范围：优先局部修复，不做无关重构或未经要求的输入规则修改。
过程：先定位和复现，再修改；根据反馈修订假设。
验证：局部四类输入、真实调用链、相关回归。
交付：根因、语义变化、修改文件、实际命令、结果与未验证项。
```

这不是通过更强硬措辞提高智能，而是减少任务歧义，让生成、检查和审查共享同一标准。

### 14.3 把 Agent 的自述与系统的任务状态分开

模型可以提出“我认为修复完成”，但任务状态应由证据驱动。建议至少区分：待定位、已复现、已修改、验证通过、验证失败、环境阻塞、预算耗尽与待人工审查。

同样地，模型说“测试通过”不是工具返回码；工具返回码为零，也不一定证明运行了正确范围的测试。需要把命令、工作目录、代码版本与结果结合起来。

### 14.4 安全边界由运行时执行，不只写在提示词中

早期 Codex 的评估已经明确提出对不可信代码进行隔离，防止修改宿主、持久化、访问敏感资源和数据外传。[R03，§2.3，p.4](#ref-r03)

在具体工程设计中，应把独立工作区与安全沙箱区分开。工作区隔离有利于管理变更，不自动构成网络、文件系统和凭证的安全边界。

可写路径、网络访问、资源上限、凭证注入与发布权限，应通过实际工具和运行环境限制。提示词用于表达工作规则，不能替代权限控制。

测试与构建本身也会执行代码。不能只把模型新生成的文件视为风险，而默认仓库脚本完全可信。

### 14.5 验收标准不能被被验收者随意修改

可以允许 Agent 新增针对性测试，但应防止通过删除、跳过或放宽正确断言来“修复”失败。确实需要调整错误测试或需求变更时，应作为单独变更说明理由并接受审查。

这不是禁止模型编辑测试，而是把“修程序”“修测试”“改需求”三个动作分开。否则模型可能优化检查机制，而不是修复目标行为。

### 14.6 把失败分成可行动的类别

| 失败类别 | 典型信号 | 下一步应优先检查 |
|---|---|---|
| 定位失败 | 找不到合理因果路径 | 搜索范围、调用关系、类型与配置来源 |
| 补丁应用失败 | 匹配不唯一、文件版本变化 | 重新读取目标、核对版本与编辑协议 |
| 环境失败 | 缺依赖、构建入口错误 | 环境恢复与项目配置 |
| 行为失败 | 断言不满足契约 | 当前假设与实现逻辑 |
| 回归失败 | 旧行为被破坏 | 修改范围与接口兼容性 |
| 超时或资源失败 | 运行超限 | 算法复杂度、死循环、环境和预算 |
| 验证不足 | 没有覆盖目标差异 | 更有鉴别力的输入与调用链检查 |
| 工作停滞 | 重复动作却没有新证据 | 假设重组、恢复点或人工接管 |

这张表是诊断设计，不是一套已经训练验证的奖励函数。尤其不要把基础设施失败统一作为程序逻辑负样本。

### 14.7 给自主性设置预算，也给失败设置出口

建议为一次任务限定总时间、模型调用、执行次数、修改范围或成本，并设置恢复点。超出预算后应返回当前证据、阻塞原因与未验证状态，而不是默认宣布失败或继续无限循环。

多候选探索也应受预算管理：候选数、每个候选允许的验证深度和选择器成本，会共同影响最终收益。并不是候选越多越好。

当恢复代码时，应明确恢复边界，避免覆盖用户或其他任务已经产生的变化。回滚能力需要与工作区版本、补丁前提一起设计。

### 14.8 用配对实验，而不是感觉，选择改进方向

固定模型、任务快照、环境与总预算，逐项改变系统条件：

| 待检验假设 | 对照实验 | 主要指标 |
|---|---|---|
| 缺少定位证据 | 关键词结果 vs 加入调用与类型邻域 | 定位准确性、最终修复与成本 |
| 编辑格式不适配 | 两种补丁格式 | 应用失败、无关修改、回归 |
| 测试不够严格 | 原测试 vs 加入边界与变异检查 | 错误补丁漏过率与检查耗时 |
| 选择器不足 | 单候选 vs 等预算候选筛选 | 实际选定补丁成功率，而非仅 pass@k |
| 历史压缩丢失约束 | 自由摘要 vs 结构化状态 | 重复操作、事实混淆、恢复后成功率 |

这些是假设和建议实验，不是已跑出的系统结果。应避免把候选数量、更多推理 token 与模型训练改进混在一起。

### 14.9 度量整个交付，而不只度量生成

可以同时报告任务总成功率、在可启动环境中的成功率、环境失败占比、回归率、补丁应用率、人工接管率与总成本。分母应清楚，不能通过排除困难任务让指标看起来更好。

若定义“每个成功任务的平均成本”为总成本除以成功任务数，应保留失败任务消耗；成功数为零时，该指标不可计算，不能填零。这是指标设计上的基本约束。

对实际团队，人工审查时间和后续返工也应进入观察。生成速度更快、代码更多，并不自动等于交付更高效。

### 14.10 交付报告应当回答四个问题

**为什么错：**根因与证据是什么，而不只是哪里报错。  
**改变了什么：**语义变化是什么，为什么修改范围必要。  
**怎样验证：**哪些命令在什么状态下真正运行，目标与回归是否覆盖。  
**还不知道什么：**未验证范围、环境限制与剩余风险。

这就是把讲义的 Patch + evidence 转换成可审查的工程交付，而不是让模型写一段更自信的总结。[L06，pp.32、61](#ref-l06)

## 15. 可执行教学实验与工作模板

### 15.1 实验范围与假设

下面的完整脚本把四件事放在一起：复现默认值错误、比较候选修复、检查局部契约、检查调用者的实际行为。

它基于讲义的四类输入，但调用者、模拟操作与附加测试是本文的教学构造，不是某个真实生产仓库，也不是 SWE-bench 的复现。[L06，pp.34–36](#ref-l06)

为了消除“重试次数”和“总尝试次数”的歧义，本实验明确约定：**`retries` 表示首次调用之外允许的额外重试次数。**所以 `retries=0` 应调用一次；`retries=3` 最多调用四次。它不包含网络、等待、退避或生产异常分类。

### 15.2 四个候选分别错在哪里？

| 候选 | 缺失 | `None` | 零 | 正数 2 | 问题 |
|---|---:|---:|---:|---:|---|
| 原始 `get(...) or 3` | 3 | 3 | 3 | 2 | 零被覆盖 |
| `get("retries", 3)` | 3 | None | 0 | 2 | 显式 `None` 不再使用默认值 |
| 恒定返回零 | 0 | 0 | 0 | 0 | 只迎合零值用例，破坏其余语义 |
| 仅在 `is None` 时默认 | 3 | 3 | 0 | 2 | 满足本例所定义的四类输入 |

这张表来自下方脚本实际执行。它没有计算 CodeBLEU 或 CodeBERTScore，也没有检验所有可能输入。它用于展示“测试是否有鉴别力”，而不是提供一个完整生产级重试组件。

### 15.3 完整脚本

保存为 `retry_contract_demo.py`，使用 Python 3.10 或更高版本运行。仅使用标准库：

```bash
python retry_contract_demo.py
```

```python
"""教学实验：默认值修复、候选鉴别与调用链验证；仅依赖 Python 标准库。"""
from __future__ import annotations

import sys
import unittest
from collections.abc import Callable, Mapping

Config = Mapping[str, int | None]


def original(config: Config) -> int:
    return config.get("retries") or 3


def default_only(config: Config) -> int | None:
    return config.get("retries", 3)


def always_zero(config: Config) -> int:
    return 0


def fixed(config: Config) -> int:
    value = config.get("retries")
    return 3 if value is None else value


CASES: tuple[tuple[str, dict[str, int | None], int], ...] = (
    ("missing", {}, 3),
    ("None", {"retries": None}, 3),
    ("zero", {"retries": 0}, 0),
    ("positive", {"retries": 2}, 2),
)
CANDIDATES: dict[str, Callable[[Config], int | None]] = {
    "original": original,
    "default_only": default_only,
    "always_zero": always_zero,
    "fixed": fixed,
}


class TransientError(Exception):
    """本实验约定可以重试的错误。"""


class FakeOperation:
    def __init__(self, failures: int) -> None:
        self.failures = failures
        self.calls = 0

    def __call__(self) -> str:
        self.calls += 1
        if self.calls <= self.failures:
            raise TransientError("simulated failure")
        return "ok"


def run_with_retry(
    operation: Callable[[], str],
    config: Config,
    resolver: Callable[[Config], int] = fixed,
) -> str:
    # 教学约定：retries 是首次调用之外的额外重试次数。
    # 本示例不包含等待、网络请求或生产环境的退避策略。
    retries = resolver(config)
    for attempt in range(retries + 1):
        try:
            return operation()
        except TransientError:
            if attempt == retries:
                raise
    raise AssertionError("Unreachable for the demonstrated nonnegative inputs")


class RetryContractTests(unittest.TestCase):
    def test_missing_uses_default(self) -> None:
        self.assertEqual(fixed({}), 3)

    def test_none_uses_default(self) -> None:
        self.assertEqual(fixed({"retries": None}), 3)

    def test_zero_is_preserved(self) -> None:
        self.assertEqual(fixed({"retries": 0}), 0)

    def test_positive_values_are_preserved(self) -> None:
        for value in (1, 2, 7):
            with self.subTest(value=value):
                self.assertEqual(fixed({"retries": value}), value)

    def test_zero_makes_one_attempt_on_failure(self) -> None:
        operation = FakeOperation(failures=10)
        with self.assertRaises(TransientError):
            run_with_retry(operation, {"retries": 0})
        self.assertEqual(operation.calls, 1)

    def test_default_allows_three_extra_attempts(self) -> None:
        operation = FakeOperation(failures=3)
        self.assertEqual(run_with_retry(operation, {}), "ok")
        self.assertEqual(operation.calls, 4)

    def test_positive_allows_configured_extra_attempts(self) -> None:
        operation = FakeOperation(failures=2)
        self.assertEqual(run_with_retry(operation, {"retries": 2}), "ok")
        self.assertEqual(operation.calls, 3)

    def test_successful_first_attempt_is_not_repeated(self) -> None:
        operation = FakeOperation(failures=0)
        self.assertEqual(run_with_retry(operation, {"retries": 0}), "ok")
        self.assertEqual(operation.calls, 1)

    def test_original_bug_is_visible_in_caller(self) -> None:
        operation = FakeOperation(failures=10)
        with self.assertRaises(TransientError):
            run_with_retry(operation, {"retries": 0}, resolver=original)
        self.assertEqual(operation.calls, 4)

    def test_checks_distinguish_wrong_candidates(self) -> None:
        failures = {
            name: sum(candidate(config) != expected
                      for _, config, expected in CASES)
            for name, candidate in CANDIDATES.items()
        }
        self.assertEqual(failures, {
            "original": 1, "default_only": 1, "always_zero": 3, "fixed": 0
        })


if __name__ == "__main__":
    print("Python:", sys.version.split()[0], flush=True)
    print("candidate       missing  None  zero  positive", flush=True)
    for name, candidate in CANDIDATES.items():
        values = [str(candidate(config)) for _, config, _ in CASES]
        print(f"{name:<15} {values[0]:>7} {values[1]:>5} "
              f"{values[2]:>5} {values[3]:>9}", flush=True)
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(RetryContractTests)
    result = unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
    sys.exit(0 if result.wasSuccessful() else 1)
```

## 16. 把全部材料收束成一个统一认识

### 16.1 每组论文补齐的是不同的能力缺口

| 能力缺口 | 主要材料 | 仍然不能由此推出什么 |
|---|---|---|
| 不熟悉代码与开发语言 | OLMo、StarCoder、Codex、Code Llama、Qwen | 不自动获得仓库定位、工具控制和交付能力 |
| 不熟悉代码的表示与边界 | Tokenizer、FIM scaling study | 特殊 token 存在不证明相应任务已经可靠 |
| 只会续写，不会利用右侧约束 | InCoder、FIM | 不自动知道哪里应该修改 |
| 不会按意图做局部变更 | OctoPack | 单文件编辑数据不等于跨仓库交互轨迹 |
| 不会利用失败信息 | DrRepair、CodeRL | 诊断或 critic 分数不等于精确因果解释 |
| 不知道候选是否可靠 | 语法生成、CodeBLEU、CodeBERTScore、EvalPlus | 合法、相似与有限测试通过都不是完整证明 |
| 正确候选存在但不会选 | Codex、AlphaCode、CodeRL | 候选集合 pass@k 不等于最终交付成功率 |
| 无法准确预测执行过程 | CodeExecutor、讲义世界模型 | 学习预测不能冒充真实执行 |
| 无法完成完整开发任务 | 讲义后半部分 | 一次修复成功不等于长期维护和发布已可靠 |

以上关系是对材料的综合整理，各项具体机制与证据范围见前文相应章节。[L06，pp.18、81](#ref-l06)

### 16.2 三条最重要的跨论文联系

**第一条：表示与接口会改变能力。**Tokenizer 决定基本表示；FIM 决定约束信息的顺序和边界；语法模型决定可选动作；Agent 编辑工具决定修改能否被准确应用。它们共同说明，模型不是脱离接口发挥能力的。

**第二条：评价标准会反过来塑造训练与搜索。**如果只看参考文本，系统倾向模仿某种形式；如果测试遗漏边界，训练和候选筛选可能奖励错误实现；如果只看 pass@k，可能忽略最终选择。CodeRL 与 AlphaCode 的有效性，都依赖反馈与选择机制的质量。

**第三条：可执行环境是学习与交付的共同基础。**它既产生训练信号，也产生测试证据；环境不一致，会同时污染训练标签和工程判断。因而，环境、日志、版本和验收不是模型之外可有可无的配套设施。

这三条是基于材料的综合推论，不表示任一论文已单独证明整个系统最优。

### 16.3 对 LLM 开发工程师，最重要的是正确归因

一次任务失败时，应能判断：缺少领域或程序知识，缺少必要上下文，定位策略不合适，工具接口不匹配，状态已过期，环境不可运行，测试缺乏鉴别力，还是最终选择与交付条件不清楚。

如果每一种问题都只通过更长提示词或更多 Agent 处理，系统复杂度会增加，但失败原因可能一直存在。

> **Coding Agent 的核心交付物不是代码量，而是受需求约束的软件变更与可信证据。模型负责提出和选择行动，系统负责让行动可控、结果可查、失败可恢复。**

从 lecture-06 的视角看，真正的进步不是从十行代码变成一千行代码，而是从一次性回答，走向能够获取证据、修订假设、完成验证，并承担后续变更影响的开发过程。[L06，pp.2、32–36、61、81](#ref-l06)

### C.2 不可混用的实验口径

| 容易混淆的概念 | 应保持的区别 |
|---|---|
| 训练长度与支持长度 | Code Llama、Qwen 的长输入能力不等于在最大支持长度上完成全部训练 |
| 输入上下文与输出预算 | DeepCoder 图的 16K / 32K 是 RL 响应 token 上限，64K 是评估时增加预算 |
| Codex 与 Codex-S | 28.8 / 70.2 与 37.7 / 77.5 等数字属于不同模型或设置，不交叉组合 |
| 历史 Codex 与当前同名产品 | 2021 年研究结果不等于当前产品表现 |
| pass@k 与最终交付 | 候选集合含正确程序，不保证系统选中了它 |
| CodeExecutor 的 pass@1 | 需要连同 200→50 候选筛选流程解释，不是一次端到端调用 |
| CodeRL 消融与随机采样 | 部分消融采用 beam search，不能不加条件横比 |
| 基座初始化的计算优势 | 相同追加训练预算不代表包含基座预训练的总预算相同 |
| 不同任务的 success | 修复、测试生成、库构建的定义不同，不能只比较百分比大小 |
| HumanEval 测试数量 | 不同论文和版本的计数口径不同，不能把所有平均数当作同一事实 |

### C.3 五个必须保留的能力边界

**合法不等于正确。**合法 AST、JSON 或补丁只保证某一层结构条件。  
**相似不等于等价。**CodeBLEU 与 CodeBERTScore 是有用代理，但不能承担全部验收。  
**测试通过不等于完整证明。**结论受测试、契约、参考实现和环境约束。  
**预测不等于执行。**CodeExecutor 或世界模型的结果必须标明是预测。  
**单次修复不等于长期交付能力。**持续维护、审查、发布和恢复需要额外证据。

### C.4 本文教学实验的验证边界

完整 Python 脚本在本次整理环境实际运行，10 项检查通过。只验证了本教学示例、所列契约和明确说明的重试次数定义。

本文没有声称重新训练任何论文模型、复现论文基准成绩、搭建真实企业代码库 Agent，或验证上传讲义中所有框架的当前实现。短代码片段、JSON、YAML、提示模板和工程架构用于说明与复用，不能自动视为生产验收结果。
