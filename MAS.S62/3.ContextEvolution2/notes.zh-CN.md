## 1. 从 Prompt 优化走向候选方案优化

### 1.1 什么在变，必须先说清楚

讲义 pp.3–11 回顾 Context：它包含模型生成下一个 token 前能够看到的全部信息；Prompt 是用来引导行为的输入组织方式。优化过程中可以保持底座参数不变，同时改变说明、范例、失败反馈、工具结果与历史方案。[L3, pp.3–11]

可以用三个对象分别记录：

| 对象 | 内容 | 更新后影响什么 |
|---|---|---|
| 模型参数 $\theta$ | 预训练和后训练形成的权重 | 模型在各种输入上的条件分布 |
| 当前上下文 $c_t$ | 当前任务、提示、候选、成绩和反馈 | 这一次生成的条件分布 |
| 外部档案 $A_t$ | 历史程序、实验、评分、失败和血缘 | 哪些经历能够被选入下一次上下文 |

于是下一次候选可以写成：

$$
z_{t+1}\sim p_{\theta}(\cdot\mid x,\operatorname{BuildContext}(A_t)).
$$

这里 $z$ 可以是 Prompt、程序、图表、实验方案或构造某种数学对象的函数。模型权重没有更新，**搜索系统已经拥有可累积的状态**。这能解释本课称为 Context evolution 的含义，也能避免把任何多轮修正都描述成模型训练。

工程上需要分别保存模型版本、上下文构造版本和档案版本。只记录“用了同一个模型”不足以复现实验：提示模板、历史选择、采样温度和评价样本变化，都可能改变最终结果。

### 1.2 改进为什么可能发生

第一次生成时，模型只看到任务；第二次可能看到可执行错误、若干高分解、某类约束被违反的原因。输入条件发生变化，生成分布也会变化。模型不必在权重里记住本次问题的所有经验，就能在下一轮利用经验。

不过，有反馈只说明系统获得了新信息。它不保证模型正确解释反馈，也不保证反馈本身正确。必须检查：反馈是否指向可修复的原因、是否足以区分方案、下一轮是否真的应用了它，以及新方案是否通过同一个可信评价过程。

以一个教学例子说明：候选程序对 90 个输入正确、对 10 个边界输入错误。反馈只写“90%”时，模型需要猜测失败原因；反馈若包含“全部失败来自空列表”，候选空间会显著缩小。若反馈把测试器超时误记为算法错误，优化器反而可能删掉正确逻辑。有效反馈取决于信息质量和归因，而不只是文本长度。

### 1.3 三种“变好”是不同目标

1. **单个答案更好**：针对当前实例，找到一个正确解或更低延迟实现。
2. **可复用程序更好**：找到能处理多个未见输入的策略或算法。
3. **搜索策略更好**：在相同计算预算下，更容易找到高质量候选。

FunSearch 主要搜索可生成解的程序；发现一个具体大 Cap Set 与发现能构造多个规模 Cap Set 的程序，输出形式和验证范围不同。OPRO 中一个 Prompt 在开发样本上的高分，也不能直接证明它使未来所有任务都更好。[FS, §1–2；OPRO, §2–4]

设计实验前先选定目标。若目标是找到单个工程内核，可关注给定预算下的最好合格实现；若要部署一个通用规则，则需要独立任务、输入分布和运行时约束。两种评测都合理，但不能互换。

## 2. TextGrad 续讲：文本反馈究竟怎样流过计算图

讲义 p.12 把 TextGrad 留作继续讨论的入口，具体方法应回到原论文，而不是从“自动微分”这个名字推断实现。[L3, p.12；TG, §2]

### 2.1 从最终错误返回中间可修改变量

设系统先用 Prompt $p$ 回答问题，再由评价模块检查答案：

$$
y=F(p,x),\qquad e=E(y,x,a^*).
$$

普通数值自动微分要求节点可微，能够沿计算图计算局部导数。TextGrad 使用 LLM 产生自然语言批评，并把反馈传播到较早的文本变量；这些“梯度”是修改建议，未必是某个实值目标的精确导数。论文把文本变量、可组合计算图、反向反馈和文本优化器组织在一起，使多个环节可以共同被优化。[TG, §2, Fig.1]

例如，最终答案少了单位，可能有三个原因：任务 Prompt 未规定单位、检索阶段遗漏单位、计算阶段进行了错误换算。若只修改最终措辞，会掩盖计算错误；若把所有错误都归给 Prompt，可能把它越写越长。计算图的价值是表达依赖关系，再让反馈定位到相关变量。它提供更好的组织方式，不提供自动正确的因果判断。

### 2.2 反馈、更新和验证应分开

一个合理的教学流程是：

```text
原 Prompt → 答案 → 评价
                     ↓
             哪些要求未满足、为什么
                     ↓
        沿依赖关系归给可修改的文本变量
                     ↓
          文本优化器提出候选 Prompt
                     ↓
            独立样本验证并决定是否接受
```

自然语言反馈可以告诉优化器“应该检查范围边界”，但只有重新执行才能知道修复是否有效。更新器应接收修改范围，例如允许修改说明与示例、禁止修改评价规则。验证器应处于候选代码或候选 Prompt 的修改边界之外。

### 2.3 什么时候值得引入 TextGrad 式结构

若系统只有一个 Prompt 和一个可重复评价任务，简单候选搜索可能已经够用。若系统有检索、规划、计算、生成等多个文本节点，错误会跨节点传播，显式依赖图更有价值。代价是需要额外评价调用、反馈传播调用、图的维护以及验证预算。

工程设计应先测三个问题：反馈能否定位真实错误，节点级修改是否优于只改最终 Prompt，是否在相同总调用预算下仍有改善。不能把“生成了一段具体批评”直接当作优化成功，也不能因为框架叫梯度就承诺下降方向或收敛。[TG, §2–3；本节选择标准为工程推导]

## 3. 一个通用闭环：Propose、Evaluate、Select、Remember

讲义 pp.13–22 展示从自我修改到写作、Harness、可视化、图像、视频的例子。它们的共同结构可以抽象成：先提出候选，取得反馈，再选择哪些经验进入下一轮。[L3, pp.13–22]

### 3.1 Self-Refine 与外部评分提供了不同的信息

Self-Refine 使用同一个 LLM 扮演生成、反馈、修改等角色，在多轮过程中改善输出。它的优势是容易接入自然语言任务，不要求先设计可微损失；局限是批评者与生成者可能共享同样的盲点。论文在若干任务上报告效果，不能据此认为模型总能自行发现事实错误。[SR, §2–4]

外部评分可以是单元测试、目标函数、图像相似度、人工评分或另一模型的判断。它并不天然可靠。数学程序的合法性检查与模型对文章质量打分，有完全不同的保证。工程系统应给评分器记录来源、版本、输入、判定及可能的误差。

一个实用的反馈对象可以是：

```python
feedback = {
    "candidate_id": "candidate-008",
    "valid": False,
    "failure_kind": "constraint_violation",
    "evidence": {"input_id": "case-17", "violated": "capacity <= 10"},
    "objective": None,
    "evaluator_version": "packing-v1",
}
```

这是教学接口，字段并非论文 API。把合法性与目标值分开，可以避免把“不合法但看起来节省很多箱子”的候选当成优秀结果。

### 3.2 OPRO 怎样让模型利用优化轨迹

OPRO 的输入是 meta-prompt：任务描述、约束、历史候选与对应分数。模型根据历史提出新候选，评价器给出分数，再把新结果追加到历史中。原论文研究了小规模数学优化与 Prompt 优化，后者可将训练样本正确率作为目标。[OPRO, §2–4, Fig.2]

与只改上一个候选相比，优化轨迹同时提供多个观察点。假设历史包含三个启发式及其在不同规模实例上的分数，模型可以尝试寻找共同特征。但它看到的是有限样本，不是真实目标函数的完整形状。把候选按分数排序、限制上下文、保持输出结构，都属于优化器设计的一部分。

用教学符号表示：

$$
A_t=\{(z_i,v_i,\text{feedback}_i)\}_{i=1}^{t},\qquad
z_{t+1}\sim p_\theta(\cdot\mid \mathcal{T},\operatorname{Select}(A_t)).
$$

其中 $\mathcal{T}$ 是目标和约束，$v_i$ 是观测分数。Select 如果只保留最高总分，可能删掉某些在困难子分布表现更好的方案。保留整体分数之外的指标向量，可以给后续更准确的选择提供依据。

OPRO 的 Prompt 实验还区分 **optimizer LLM** 与 **scorer LLM**：前者写指令，后者带着候选指令回答有标签任务，评价器以正确率给候选评分。这里的 scorer 不是仅凭语言感觉给 Prompt 打分。例如论文 Table 1 固定预训练 PaLM 2-L 为 scorer，人工的 “Let's think step by step.” 得到 GSM8K 测试准确率 71.8%，PaLM 2-L-IT 优化出的指令为 80.2%，相差 8.4 个百分点。这是模型、指令位置、训练样本选择和测试协议共同限定的结果；论文没有证明那句指令对所有模型有效。[OPRO, §4–5, Table 1, PDF p.1]

### 3.3 探索与利用不是调高一次温度就完成

利用是围绕当前高分区域细改；探索是保留不同算法结构、不同假设和不同父程序。采样温度影响候选多样性，但多样性还取决于父程序选择、Prompt 中的示例、修改范围和档案淘汰规则。[OPRO, §2.3；FS, §1]

若十个候选只有变量名不同，高温度没有带来有效探索。可按抽象语法树、行为指纹、运行复杂度或子任务得分观察差异。行为指纹更接近“做法是否不同”，但它也依赖用于比较的测试集合；在小样本上行为相同的程序，可能在未见输入上分歧。

### 3.4 通用闭环不代表统一评价标准

写作系统可能优化连贯性和覆盖度；图表系统可能同时检查数据一致性、图形结构和视觉效果；视频系统还要检查时间连续性。不能直接把单一数学评分器换成一个“质量 Judge”，就假定系统保留了同等可靠性。[L3, pp.18–22]

教学上可统一“提出—执行—评价—保留”的控制结构。工程上必须重新定义每个领域的有效候选、错误证据和发布标准。尤其当 Judge 看不到原始数据，只看成品时，漂亮输出可能掩盖数值错误。

## 4. FunSearch：为什么搜索程序能够帮助发现新解

### 4.1 搜索空间的设计决定了问题难度

讲义 p.28 强调 FunSearch 搜索具有固定输入输出约定的 Python 函数。它常保留一个人为给定的程序骨架，让模型改动关键优先级函数，而不是每次重新生成整个系统。[L3, pp.27–29；FS, §1, Fig.2]

以在线装箱为例：物品依次到达，箱子容量固定，必须立即决定放入哪里。骨架负责读取物品、筛选能够容纳物品的箱子、调用启发式评分函数、选出箱子并更新状态。模型只负责输出每个可行箱子的优先级。

这样做分开了两种责任：

- **固定语义**：不能超容量，每件物品恰好放一次，不能窥看未来物品。
- **可搜索策略**：在当前可行箱子之间怎样选择。

缩小修改空间通常能提高有效候选比例，并让错误更容易归因。代价是骨架可能排除某些更好的算法。若所有候选都陷入同一瓶颈，应检查瓶颈来自优先级函数，还是固定骨架本身已经限制了能力。

### 4.2 Cap Set 中，合法性与大小是两个检查

讲义 pp.24–26 用 Cap Set 说明科学发现。我们在 $\mathbb{F}_3^n$ 中选择向量集合，要求不存在三个不同向量满足

$$
a+b+c=0\pmod 3.
$$

搜索器希望集合尽可能大，但合法性是硬约束。给出一个大集合后，可以用确定性计算检查是否有违规三元组。模型还可以输出一个生成集合的优先级程序，使人类查看程序、扩展构造或分析其中对称性。[FS, §2.1]

**找到更大的合法集合提供的是构造性下界。** 它不自动给出最大可能规模的证明。讲义提到八维构造从 496 增至 512，应按该问题与结果口径理解；不能把它扩大成“已经解决整个 Cap Set 问题”。[L3, p.24；FS, §2.1]

这也是“容易验证、难以寻找”的有用例子：一个合格候选的检查成本可以显著低于从巨大组合空间找出它的成本。自动验证使搜索可以依赖机器反馈继续运行。

### 4.3 程序既是候选，也是压缩后的假设

直接保存一个向量列表只说明当前实例上选了什么。保存构造函数还描述“为什么按这种顺序选择”，并可能用于其他规模。程序的可解释性并非自动成立，但它给专家提供可检查的结构，比一组不可复用输出更便于分析。[FS, §1–2]

不过，短程序不必然有更好的泛化。如果程序通过输入规模、样本编号或特殊常数识别训练实例，它仍然可能过拟合。应分别测试输入规模变化、随机种子变化和任务分布变化，并审查候选能访问哪些信息。

### 4.4 Best-shot prompting 怎样利用历史程序

FunSearch 从程序库中取若干程序，按表现组织成带版本后缀的函数，再请 LLM续写更高版本。它提供给模型的不是一份抽象“继续改进”的要求，而是具体代码、评价和版本之间的变化。论文的默认选择是两个程序，超过两个的额外收益在其消融中有限；这是该论文的设置，不是所有程序搜索系统都应固定使用两个父程序。[FS, §1]

从工程角度，需要区分三个 ID：父程序 ID、Prompt 中的临时函数名、生成后归一化的函数名。若字符串替换错误，把新函数仍然调用旧版本的辅助函数，会导致评价对象与实际记录不一致。候选应在执行前解析并记录最终可执行内容的哈希。

## 5. 种群、岛屿与执行评价

### 5.1 为什么不能始终只保留冠军

如果每一轮只围绕当前最高分方案修改，早期偶然领先的结构会持续占据上下文。不同结构的低分候选可能包含组合后有效的子思路，却被过早淘汰。FunSearch 使用 islands：多个相对独立的种群各自演化，再周期性重置表现较差的岛屿，让优秀程序传播而保留分开的探索路径。[L3, pp.30–33；FS, §1, Methods]

讲义 p.30 的通用进化算法选择示意可以用 softmax 表达：

$$
P(i)=\frac{\exp(f_i/T)}{\sum_j\exp(f_j/T)}.
$$

这里 $T$ 控制对分数差异的敏感度；接近零时更倾向高分候选，较大时更分散。该公式是讲义的教学表示，FunSearch 的具体采样还涉及分组、短程序偏好和温度调度，应以论文 Methods 为准，不能用一行 softmax 当作完整复现。

讲义 p.33 与原论文 Methods 给出了可以实际实现的两级选择。程序先在多个输入上执行，形成 **signature（评分签名）**，即逐输入分数组成的元组；同一岛内，签名相同的程序归为一个 cluster。构造 Prompt 时，先均匀抽一座岛，再按聚合分数偏向高分 cluster，最后在 cluster 内偏向短程序；默认取两个父程序。合格子程序回到父程序所属岛，按新签名加入已有或新建 cluster。[L3, p.33；FS, Methods, PDF pp.17–18]

例如两个装箱策略在三个实例上的箱数分别为 $(10,12,14)$ 和 $(11,11,14)$，总数同为 36，但逐例签名不同，应保留为不同组。相同签名只表示这些测试输入上的分数相同，不表示代码等价。先按签名分组，也能避免大量改名副本因数量多就垄断父代抽样；短程序偏好则发生在同签名组内，不是无条件用更短代码替代高分程序。

### 5.2 “删除差岛屿”之后还需要重新播种

讲义 p.32 给出初始化、岛内增长与淘汰的流程。原论文补充了重要步骤：周期性清空较差的一半岛屿，并从幸存岛屿中选择优秀程序重新初始化它们。归档论文默认使用 10 座岛，每 4 小时重置；比较的是各岛最佳程序的分数，每座待重置岛均匀选择一座幸存岛，复制其最佳程序，而非把所有新岛都变成全局冠军的副本。重新播种既传播已有进展，也重新打开后续独立探索。[L3, p.33；FS, Methods, PDF p.17；Supplementary Table E.2, PDF p.50]

工程上至少要记录岛屿创建时间、重置原因、种子程序、代数以及评分版本。若评价器更换后旧分数仍与新分数混用，岛屿淘汰会失去语义。同一候选在不同数据集上的分数应保留不同命名空间。

### 5.3 评估必须执行最终程序

候选要经过：语法和接口检查、受限执行、输出合法性检查、目标计算。FunSearch 会丢弃不执行、资源超限或输出无效的程序；高分必须来自实际执行产生的有效输出。[FS, §1]

以下是工程分层，而非论文 API：

```text
生成文本
  → 解析出指定函数
  → 组合到不可修改的程序骨架
  → 对最终代码计算哈希
  → 在受限进程执行
  → 检查输出合法性
  → 计算目标值及成本
  → 保存候选、证据和父子关系
```

静态解析只能检查结构，不能保证代码安全或终止。超时、内存限制、网络和文件权限应由执行环境承担；不要在主同步进程中对生成内容直接调用 `exec`。这些边界保护的是评价过程的可信性，也是复现候选时的基本条件。

### 5.4 异步执行带来吞吐，也带来一致性问题

FunSearch 把程序数据库、采样器和评估器分开，允许生成与执行并行。原论文的某些实验达到百万量级候选，使用多个采样器和 CPU 评估器；这些规模解释了搜索所消耗的资源，不能简化为“几个 Prompt 找到数学发现”。[FS, §1]

异步系统中，候选是在某一历史档案下生成的，到评价完成时档案可能已经更新。需要保留快照 ID；重试同一候选应复用候选 ID；同一结果的重复消息不能被重复计入种群。对于随机评价，应记录重复次数与随机种子，避免一次幸运结果永久占据冠军位置。

### 5.5 实验证据：发现一次好解与稳定提升是两种结果

八维 Cap Set 的 512 点构造是可独立检查的发现，但直接搜索的成功频率并不高：原文报告 140 次实验中仅 4 次找到 512。它说明大预算搜索能产生新构造，不能被讲成每次运行都稳定刷新纪录。论文另有经 admissible sets 间接改善渐近下界的路线：研究者从程序中识别对称性，再收窄后续搜索空间；其中人的分析仍是发现链的一部分。[FS, §2.1、Methods, PDF pp.9–10、18]

装箱的证据口径不同。论文从 best-fit 启发式出发，在生成的、规模与 OR1 相同的实例上演化，再测试 OR1–OR4；另为 Weibull 分布演化启发式。Table 1 报告的是相对离线最优解 **L2 下界** 的超额箱子比例，越小越好：OR4 上 best-fit 为 4.94%，FunSearch 为 2.47%；Weibull 100k 上分别为 3.79% 与 0.03%。这些不是“任务准确率”，下界也不一定能被在线算法达到。不同分布分别演化的结果，不能合并成同一启发式对任意物品分布都有效的保证。[FS, §2.2, Table 1, PDF p.11]

## 6. AlphaEvolve、Autoresearch 与搜索对象的扩展

### 6.1 从单个函数到复杂程序

讲义 p.34 把 AlphaEvolve 概括为程序范围扩大、使用 SEARCH/REPLACE、提供更丰富上下文和多指标。原论文进一步说明，用户提供初始可运行程序、可修改代码块和固定评价函数，系统选择父程序、构造 Prompt、生成修改、应用修改、执行评价，再写回数据库。[AE, §2, Figs.1–3]

它扩展了可搜索的抽象层次：可以进化一个对象构造器，一个特定预算下的搜索算法，或程序内多个相互依赖组件。可修改部分越多，潜在收益越广，接口不一致和无效候选也越多。

工程上可先让模型优化一个热点函数，证明评价可信，再逐步扩大修改范围。若直接允许改评价脚本、输入数据和被评价算法，就无法区分真实改进和改变评分方式。

### 6.2 Diff 降低输出量，也引入匹配语义

SEARCH/REPLACE 需要明确原始片段、替换片段和父版本。若多个位置匹配，或父程序已被并发更新，修改可能作用到错误位置。完整程序哈希、匹配次数检查及失败时拒绝应用，是可审查的实现方式。不能把“模型生成了 diff”当作“代码已经按意图改变”。[AE, §2.3；验证规则为工程推导]

候选记录最好同时保存 diff 与应用后的完整代码。diff 便于理解修改，完整快照用于复现。只有 diff 而没有确切父版本，会导致后续无法还原实际评价对象。

### 6.3 多指标不能用一句“综合评分”带过

AlphaEvolve 的评价函数可返回多个标量，并支持先低成本过滤、再更昂贵评价的级联过程。[AE, §2.1, §2.4]

例如优化一个排序内核：

| 指标 | 性质 | 合理处理 |
|---|---|---|
| 输出是否正确 | 硬约束 | 不通过则拒绝候选 |
| 数值误差是否在允许范围 | 硬约束或分段约束 | 按预先确定的容差检查 |
| 延迟 | 优化目标 | 固定硬件与输入形状，重复测量 |
| 峰值内存 | 约束或目标 | 明确上限，并记录测量方法 |
| 编译或预处理开销 | 摊销成本 | 根据调用频次决定是否值得 |

若把正确性也当成可补偿的加权分数，一个错误但极快的算法可能胜出。应先定义有效集合，再在有效集合中做性能比较。不同业务权重形成不同最优解，不能把某个权重下冠军称为普遍最优。

### 6.4 Autoresearch 的关键是实验契约

讲义 p.35 以 Autoresearch 说明：在固定单次实验预算下，让 Agent 提出修改、编辑代码、运行训练并比较结果。讲义给出的分钟和夜间实验次数是示例性设置，具体运行取决于硬件、实现和任务。[L3, pp.35–38]

可靠的自动研究循环需要把三种产物关联起来：候选代码、不可更改的实验配置、运行生成的结果。文本实验日志只能解释结果，不能替代机器可读的度量文件。模型输出“验证指标更好”，必须能追溯到这一次运行的代码哈希、数据切分和真实日志。

讲义 pp.36–37 随后把“还能 autoresearch 什么”引向 EdgeBench：图中同时出现科学/机器学习、系统与软件、组合优化、知识工作、形式数学、交互游戏。这一步是在扩展任务类型，不是在说明一个统一评分器能够衡量所有任务。前面的短训练实验可以反馈一个验证损失，长时工程任务则可能需要测试、交付物审查或交互环境反馈；迁移闭环时必须重新定义反馈与完成条件。[L3, pp.36–37，按讲义图解读，本文未复核 EdgeBench 原始基准]

Week 3 的 HW1 入口位于讲义 p.38，是 OpenEvolve 实践入口；[本地 Notebook](../assignment/assignment-1/OpenEvolve_assignment.ipynb) 保留原始下载文件名。学习时应先复现固定 seed 的已知基线，再把候选生成器接入；这能先确认评价链路，降低把基础脚本错误归因给搜索方法的风险。教程和作业是否依赖模型 API、GPU 或额外数据，需要按其原始说明准备，本文没有执行付费模型实验。

## 7. 当发现无法被一个数充分评价

### 7.1 候选可评分，不代表研究价值可评分

讲义 p.39 列举难以获得直接数值评分的发现。这里的关键是评价函数与研究目标之间可能存在较大的距离。一个程序可以在固定测试集上更快；一个研究想法的长期价值、理论新颖性与可实现性，通常需要不同证据。[L3, pp.39–42]

模型评价能够帮助初筛，但若模型同时负责提出想法、判断新颖性、设计实验和打分，多个环节可能共享偏差。增加角色数量并不自动产生独立证据。独立证据可以来自外部文献检查、实际实验、不同评审者、盲评或领域专家的质疑。

### 7.2 人类研究论文测量了什么

*Can LLMs Generate Novel Research Ideas?* 招募了写想法和评审想法的 NLP 研究者，总计 104 位参与者；研究比较专家想法、AI 想法和 AI 加人工重排。匿名评审包含新颖性等维度，并采用不同统计分析处理条件和评审差异。[NI, §4–5]

具体是 49 位想法作者、79 位评审者，其中 24 人参加两项工作；三个条件各有 49 个想法。讲义 p.40 展示的新颖性均分为人类 4.84、AI 5.64、AI 加人工重排 5.81，对应论文把每份 review 当作观察值的 Test 1。由于同一想法被多次评审，论文另按想法聚合，并按评审者处理偏差；AI 新颖性优势在这些分析中仍成立。可行性等维度并未一致显示显著优势，因此不能把新颖性结果改写成“整体研究质量全面超过专家”。[NI, §4、§5.1–5.3, Tables 7–9, PDF pp.7–12]

它提供的证据是特定研究任务下的**想法评价**。它不是这些想法都被实现、在新实验上成功或产生长期科学贡献的证据。自动生成大量想法还暴露重复性问题：生成数量远大于有效独特想法数量，去重与筛选是系统的一部分。[NI, §3.2, §7]

把它迁移到工程选题，可以分别考察：研究问题是否已有答案、建议是否具体、关键假设能否被检验、实验成本是否现实，以及失败后能否得到信息。只评价“听起来新颖”容易鼓励陌生术语与复杂包装。

### 7.3 AI Scientist 的贡献在于连接完整过程

2024 年的 *The AI Scientist* 从代码模板出发，连接想法生成、新颖性检查、实验执行、绘图、写作与自动评审。代码执行失败会返回给编辑 Agent 修复；实验完成后保留日志与图表供写作阶段使用。[AS24, §3–4]

2026 年的 *Towards End-to-End Automation of AI Research* 讨论模板式与更开放的树搜索式实验流程，并报告与组织者合作进行的 workshop 评审实验。应分别引用两个版本，不能把新论文结果直接归给 2024 系统。[AS26, §2–4]

这些工作说明研究流程中的多个环节可以自动衔接，也提醒我们衔接处容易丢失事实：图表来自哪个运行，失败实验有没有保留，候选是否未经验证就进入论文，引用是否真正支持结论。自动写出完整报告是产物完整性，研究是否成立需要证据完整性。

### 7.4 通过评审是特定事件，不能作为通用科学裁判

2026 论文报告向 ICLR 2025 的 ICBINB workshop 提交三篇生成稿件，其中一篇平均评审分 6.33，达到该场景下的接受门槛；按事先约定，稿件随后撤回，没有成为实际发表论文。该 workshop 接受率约为 70%。研究团队在各阶段人工筛选输出，提交条件包括主题匹配、代码正确实现想法并可运行、稿件格式正确；不是从任意三次生成中随机抽取。这表明系统在该实验场景下完成了有意义的流程；它不支持“AI 已经全面替代研究者”的结论，也不证明自动 Reviewer 可以无条件代替人类评审。[AS26, §4–5, PDF pp.4–6]

自动 Reviewer 与历史接受决定的一致性，还受到会议、年份、样本分布和训练数据污染的影响。论文自身区分了知识截止前后的数据。工程应用中，审核器应依据需要验证的具体事实来设计，而非直接把“像被接受的论文”作为唯一奖励。

## 8. 形式验证：把“能说服人”推进为“能被检查器接受”

讲义 pp.43–46 引入数学推理与形式化验证。需要分开三步：自然语言问题是否被正确形式化，候选证明是否符合形式系统，形式系统中的命题是否对应我们真正想证明的陈述。[L3, pp.43–46]

讲义 pp.43–44 的具体例子是 **DeepSeek-Prover-V2 的子目标分解**：先让 DeepSeek-V3 写出证明思路和带待补子目标的 Lean 骨架，再用 7B prover 尝试补齐子目标，最后组合成完整证明。带 `sorry` 的骨架只表达待完成工作，不能作为定理已证的证据；最终验收应要求完整证明由检查器通过，并核对是否仍有占位或新增不当公理。该图还把组合出的证明与原始推理配对，用于冷启动训练数据，因此要区分“本次找到证明”的搜索循环和“后续更新模型”的训练循环。[L3, pp.43–44；ProverV2, §2.1–2.2, Fig.2, PDF pp.3–5]

如果把一个强命题误写成弱命题，证明检查器可以完全正确地接受后者，工程目标仍未达成。因此，“通过 Lean”可以证明在给定公理、形式化陈述与检查器下候选证明有效；它不能自动保证建模正确，也不能涵盖未被形式化的实现行为。

对应程序优化，也有类似层次：

| 证据 | 能支持什么 | 尚未支持什么 |
|---|---|---|
| 少量样例通过 | 这些输入上未观察到错误 | 任意输入正确 |
| 随机或属性测试通过 | 给定采样与性质检查下的可靠性 | 全部状态覆盖 |
| 与可信实现逐项一致 | 给定比较域与容差中的等价表现 | 比较器本身无误 |
| 形式证明通过 | 指定形式化规范下的性质 | 规范一定符合真实需求 |

本课可迁移的工程思想是：让创造者尽可能多提出候选，让验证器承担清晰的、可执行的判定责任，再保留人对规范的审查。验证器与生成器可以协作，但其权限和评价目标要能区分。

## 9. 一个完整工程案例：在线装箱启发式搜索

以下案例由本文构造，目的是把搜索空间、状态、反馈、泛化和评价连起来。它不是 FunSearch 原论文的复现。

### 9.1 先定义任务契约

输入是容量 $C$ 与正整数物品序列 $w_1,\dots,w_m$，每个物品不超过容量。算法按到达顺序放置，不能改变顺序或读取未来物品。输出是每个物品的箱子编号。固定评价器验证三件事：编号合法、没有漏放或重复放、每个箱子的总容量不超过 $C$。目标是在有效放置中最小化使用箱子数。

物品 $[6,5,3,2,2,2]$、容量 10 的例子很有启发：离线可以构造 $[6,2,2]$ 与 $[5,3,2]$ 两箱。某个在线贪心策略可能先把 3 放到 6 后面，最终用了三箱。拿离线最优当作性能参考可以帮助理解差距，但不能给在线算法泄漏未来序列。

### 9.2 模型只输出评分函数

固定骨架先筛出可行箱子，再对每个箱子调用一次标量评分函数，传入当前物品大小和该箱子的剩余容量。候选函数返回一个分数，骨架选择分数最高的箱子：

```python
def score(item, remaining):
    # 示例：倾向放置后空余最小的箱子
    return -(remaining - item)
```

分数的绝对大小无意义，排序影响动作。评分器不应能够修改箱子状态或评价数据。若函数返回非数值、NaN 或无限值，应判为接口失败，不能任由隐式排序产生不可预测结果。

### 9.3 候选档案要保存足够的复现信息

```text
candidate_id, parent_id, source_hash
generator_model, sampling_config, prompt_hash
train_distribution, evaluator_version, seed
validity, bins_used_by_case, runtime
failure_kind, failure_evidence, archive_generation
```

父子关系使人能追溯某条思路是如何形成的；按案例保存箱子数使人能发现某个总体高分策略只在大物品上有效；完整源代码使人能复现，而非依赖模型写出的说明。

### 9.4 运行一个无模型依赖的教学实验

本课附有 [bin_packing_lab.py](examples/bin_packing_lab.py)。它比较预先写定的启发式，在开发集合上选择候选，再到未参与选择的集合与移位分布测试，并检查每个箱子的容量和物品守恒。运行方式：

```bash
python3 MAS.S62/3.ContextEvolution2/examples/bin_packing_lab.py
```

这个实验没有调用 LLM，没有执行动态生成代码，也没有实现 FunSearch 的岛屿搜索。它验证的是固定骨架、可行性与目标分离、开发选择和独立评价这几个概念。具体输出由脚本的固定种子决定，见 [运行记录](examples/RESULTS.md)。不能把这些结果用于证明某个模型或论文方法更好。

### 9.5 接入 LLM 后，怎样分阶段验证

第一阶段只让模型生成可解析的候选，统计语法、接口和执行有效率。第二阶段冻结模型和评价器，比较随机修改、无历史采样、单一最佳父程序、档案多样性四种策略。第三阶段扩大输入规模与分布，检查是否泛化。每阶段保持可审查的预算约束，失败候选也计入成本。

若有效率低，应先缩小候选接口并改善解析反馈；若有效率高但分数不升，应分析搜索空间、奖励信号和多样性；若开发分数升而独立分数下降，应检查过拟合与评价泄漏。不同现象对应不同修改，不能统一归结为“模型不够强”。

## 10. 实验设计：怎样证明改善来自搜索方法

### 10.1 对照组要分开生成能力与记忆能力

至少可以比较：固定人工基线；同模型多次独立采样后选择；根据最后一次反馈修改；根据完整或选择后的历史修改；加入种群或岛屿机制。每组使用相同任务、模型版本和预算口径。

“没有演化”的对照也应获得公平的采样预算。如果演化组调用模型一千次，而基线只调用一次，观察到的差距混合了搜索策略与额外计算。可以同时报告固定生成次数和固定总成本下的结果，因为不同方法每个候选的上下文与执行成本并不相同。

### 10.2 开发集、选择集和最终测试集

优化器反复看到的开发样本实际上已经参与训练过程，即使底座权重从未改变。选择最终候选的集合也会产生选择偏差。最终测试集合应在候选锁定后使用，若把其错误再反馈给优化器，就需要明确改变了实验设置。

对程序任务，可按实例族而不仅按随机样本拆分。装箱中应区分不同大小分布、序列长度和容量；图优化中可按图结构与节点规模拆分。这样才能判断候选学到了可迁移策略，还是适应了一个狭窄分布。

### 10.3 指标应覆盖目标、过程和计算

| 层次 | 建议记录 | 用途 |
|---|---|---|
| 目标 | 最好合法分数、均值、分位数、相对基线差值 | 判断产物质量和长尾退化 |
| 过程 | 有效候选比例、独特行为数量、父代多样性、停滞轮数 | 判断搜索是否在有效探索 |
| 预算 | 输入/输出 token、评价次数、CPU/GPU 时间、失败重试 | 判断代价是否可接受 |
| 可靠性 | 超时、违规输出、非确定性、验证器分歧 | 判断分数是否可信 |
| 泛化 | 独立实例、移位分布、规模变化 | 判断收益的适用范围 |

至少保留多个随机种子与候选轨迹。单次搜索的最高点可以作为发现证据，但它不能完整代表算法稳定性。报告最好结果时，还应给出试验次数、总预算及其余运行的分布。

### 10.4 科学发现与通用部署需要不同的归因

对找到一个新数学构造，最终可独立验证的对象具有重要价值；对一个每天处理大量请求的通用 Agent，还必须衡量长期平均收益、错误风险及维护成本。不能因为两者都使用搜索，就要求同一种单一指标，也不能用前者的发现案例替代后者的系统评估。

## 11. 成本、架构选择与故障诊断

### 11.1 总成本由多个环节组成

一个简化教学分解是：

$$
C_{\mathrm{search}}=\sum_{i=1}^{N}
(C_{\mathrm{prompt},i}+C_{\mathrm{generate},i}+C_{\mathrm{execute},i}
+C_{\mathrm{verify},i}+C_{\mathrm{retry},i}).
$$

候选数相同不代表成本相同。档案越来越长会增加输入 token；昂贵验证器会使执行成本超过生成；失败重试和资源闲置会降低实际吞吐。原始 FunSearch 与 AlphaEvolve 在模型能力、候选规模和评价成本上的设置不同，不能仅按论文候选数比较效率。[FS, §1；AE, §2, Table 1]

如果搜索得到的实现将被调用 $K$ 次，每次节省成本 $\Delta c$，粗略摊销条件是 $K\Delta c>C_{\mathrm{search}}+C_{\mathrm{integration}}$。这是工程估算，尚未计入失败风险、维护和硬件变化。低频任务可能更适合使用现成稳健算法；高频热点函数更有机会摊销搜索成本。

### 11.2 选择架构时先问哪些前提成立

| 条件 | 可优先考虑 | 需要特别验证 |
|---|---|---|
| 搜索空间小、目标便宜 | 枚举、随机搜索、传统优化器 | LLM 是否真的提供额外价值 |
| 有清晰程序骨架、可靠执行评分 | FunSearch 式函数搜索 | 骨架偏置、过拟合、多样性 |
| 复杂代码与多指标、评价昂贵 | AlphaEvolve 式修改与级联评价 | diff 正确性、调度、预算和评价隔离 |
| 文本质量可人工评价但难自动评分 | 辅助提出与筛选，保留人工审核 | Judge 偏差、事实验证、评价一致性 |
| 需要一个新构造且能独立验证 | 大预算搜索与最终证据验证 | 发现范围、独立检查、搜索成本披露 |

这张表是依据本课方法构造的工程决策框架，不是课程作者给出的选型排行榜。

### 11.3 从现象定位失败环节

| 现象 | 可能原因 | 优先做的验证 |
|---|---|---|
| 候选很多但大部分无法执行 | 搜索接口过宽、依赖未固定、生成格式不稳 | 分别统计解析、类型、依赖和运行错误 |
| 所有候选结构高度相似 | 父代单一、历史缺少反例、采样不足 | 固定模型比较不同档案选择与父代策略 |
| 开发分数上升、测试下降 | 选择过拟合、样本泄漏、硬编码 | 锁定候选后更换独立实例族 |
| 性能突然大幅提升 | 真实突破或跳过工作、读取答案、计时错误 | 独立验证实现语义、运行日志和计时边界 |
| 分数相近但运行时间翻倍 | 上下文增长、评价堵塞、重试增加 | 分阶段分解时间与资源利用 |
| 同一候选重复运行分数差异很大 | 随机性、硬件噪声、未固定环境 | 记录种子，多次重测与可信基线交错运行 |
| 档案扩大后反而变差 | 错误历史、上下文噪声、低质经验挤占 | 固定候选集，单独消融记忆选择策略 |

应先取得能区分原因的证据，再决定升级模型、修改 Prompt、改验证器还是换搜索空间。直接让 Agent“更仔细一点”通常无法解释上述不同故障。

## 12. 本课总结、开放问题与自测

讲义 p.47 提出长上下文分布漂移、不可自动验证的真正发现，以及更快适应三个开放方向。它们也可以转成系统研究问题：历史越积越长时反馈是否仍被正确利用，评价指标是否覆盖真正价值，能否从更少实验中提取更有用的设计原则。[L3, p.47]

本课的三项核心认识是：**候选表示决定可搜索范围，验证器决定何种进展可信，档案与选择决定经验怎样影响后续生成。** 模型能力很重要，但它只是闭环的一部分。下一课把可修改对象从当前 Prompt 或候选程序扩展到 Harness 中的记忆、工具和控制流。[L3, p.48]

### 自测题

1. 参数从未更新，为什么系统仍然可能随实验改善？
2. 一个候选使在线装箱少用了两个箱子，为什么还不能直接收进冠军档案？
3. 为什么 FunSearch 固定程序骨架既可能帮助搜索，也可能限制搜索？
4. 把十次独立采样基线与一千轮演化比较，会混入什么因素？
5. 一篇 AI 生成论文通过 workshop 评审，支持与不支持哪些结论？
6. 已经使用独立测试集，什么时候测试集仍然可能成为开发集？
7. “通过证明检查器”和“真实工程需求已经满足”之间还缺哪一步？

### 参考答案

1. 当前上下文和外部档案发生变化，新的条件输入改变提议分布。改善发生在有状态系统层面，是否稳定有效仍须独立评估。
2. 先检查物品守恒、容量、在线访问约束、评价版本和执行证据，再与相同条件下基线比较。目标值不能补偿无效输出。
3. 它将模型预算集中在关键策略、提高可执行率；同时排除了骨架之外的算法，需要在停滞时检查固定部分是否成为瓶颈。
4. 混入额外推理、执行和选择预算，不能只归因于演化机制。应提供预算匹配的独立采样和消融。
5. 支持该系统在指定条件下完成研究流程并达到该场景的评审门槛；不证明普遍研究能力、所有结论正确或替代全部研究人员。
6. 当测试错误、分数或评审反馈被用来继续选择与修改候选时。此后必须明确适应协议或重新保留未参与决策的评价集合。
7. 检查形式化规范是否准确表达需求，以及实现、输入和环境假设是否与被证明对象一致。
