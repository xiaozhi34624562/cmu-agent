你可以带着服务开发中的三个问题来读：这次调用用了什么配置？调用结束后，什么状态会留下？下一版配置凭什么替换当前版本？它们分别接到本课的推理、持久学习和更新评估。本文默认你理解接口、日志、版本和测试，但会解释概率与训练术语。学完后，应能画出一个系统的执行与更新两条调用链，指出哪一项状态发生了变化，并设计一个能区分“当前任务修好了”和“新任务也会受益”的对照。

## 1. 先把“会做任务”和“会持续改善”分开

讲义第 4 页把测试时扩展、Agent、多 Agent、用户反馈、持续学习、工具与长期记忆、强化学习和环境设计放在一起。这些方向有联系，但它们改变系统的方式不同。[L1，pp.4—5]

设想一个修复代码的 Agent。它第一次看到任务：`retries=0` 应该保留为 0，但代码用 `value or 3` 把它改成了默认值 3。Agent 读文件、改代码、运行测试并提交修复。这说明它完成了一次任务；还没有说明下一次任务会受益。

再看三种后续变化：

1. 它在同一任务内多运行几次测试，修好了当前错误。
2. 它把“用真值判断实现缺省值可能破坏合法的 0”保存为有适用条件的经验，在下一任务使用。
3. 它改写了自己的调试流程，今后遇到类似问题都会先检查缺失、`None`、0 和空字符串的语义。

第一种主要增加当前任务的搜索与验证；第二种改变跨任务的记忆状态；第三种改变运行框架。是否变好，仍要通过新任务和回归任务检验，不能从“写入经验”或“修改流程”直接推出。

**教学定义**：本文把自演化系统看作一个包含经验采集、候选更新、独立检验和持久化采纳的循环。这个定义用于工程分析，不声称所有论文都采用同样的术语。

### 1.1 六个问题比一个标签更有用

阅读任何 self-evolving 系统，先填写：

| 问题 | 代码 Agent 的例子 |
|---|---|
| 什么被更新？ | 记忆条目、系统提示、工具代码或底座权重 |
| 谁提出更新？ | 固定反思提示调用的模型，或当前 Agent 自己 |
| 反馈来自哪里？ | 失败断言、隐藏测试、人工审查、模型评价 |
| 更新怎样保留？ | 版本化文件、技能库、权重 checkpoint |
| 怎样证明收益？ | 未参与生成候选的任务和预先规定的指标 |
| 适用于哪里？ | 某仓库、某类配置语义，还是跨仓库的通用错误类型 |

如果一篇工作只回答前四项，它可能实现了更新机制；其改进效力、迁移范围和长期稳定性仍需要额外证据。

### 1.2 本课真正要求的先验能力

讲义第 7—8 页强调编程、实验能力、对现有 AI 局限的理解，以及外部领域知识。原因是改进信号往往来自模型之外：程序测试、物理模拟、科学实验或真实用户目标。只知道怎样调用模型，不能判断模型提出的目标是否正确、实验是否有效。[L1，pp.7—8、17]

例如，金融计算中“数值相近”不等于口径正确，代码修复中“样例通过”不等于没有回归。领域知识帮助我们构造验证器和失败分类，也帮助我们识别一个看似漂亮、实际上绕开任务的更新。

## 2. LLM 基础：输入条件和权重分别改变什么

### 2.1 自回归模型为什么能通过上下文改变行为

将语言模型写成条件分布：

$$
p_\theta(y\mid c)=\prod_{t=1}^{|y|}p_\theta(y_t\mid c,y_{<t}).
$$

这里 $\theta$ 是权重，$c$ 是当前输入，$y$ 是输出序列。改变 $c$，即使 $\theta$ 不变，也可能显著改变输出。Prompt、示例、检索证据、工具返回、历史反思，都可能通过条件分布影响行为。

把公式展开看：$y_t$ 是第 $t$ 个 token，$y_{<t}$ 是它之前已经生成的 token；竖线 $\mid$ 表示“在这些信息已给定的条件下”，$\prod$ 表示把每一步的条件概率相乘。假设一个教学输出恰好含两个 token，第一个的概率为 0.6，接着生成第二个的条件概率为 0.5，那么这条指定序列的概率是 $0.6\times0.5=0.3$。第二步依赖第一步，不能当成两次相互独立的抽签；这个 0.3 也不是答案正确率。它描述模型倾向于生成什么，正确与否仍要由任务检验。

GPT-3 的 few-shot 设置正是在没有梯度更新的情况下，把任务和示例放入输入；其论文 §2 开头和图 2.1（PDF pp.6—7）区分 zero-shot、one-shot、few-shot 与 fine-tuning，§2.4 再说明具体评测设置。[L1，pp.26—27；R1，§2、图 2.1、§2.4]

这里要分开两种“学习”：

- **行为适应**：在给定上下文下表现改变，不要求修改权重。
- **参数学习**：通过训练过程改变模型参数，能力以 checkpoint 等形式保留。

上下文中的教训如果没有被后续调用加载，就不会自动成为模型的长期能力。反过来，权重没有变化，也不妨碍整个系统积累可复用状态。

### 2.2 为什么预训练能力与遵循指令不是一回事

讲义用 GPT-3 与 InstructGPT 对同一提示的响应说明：擅长续写不等于擅长按用户意图完成任务。[L1，pp.28—29]

InstructGPT 的训练过程包括示范数据上的监督微调、输出偏好排序、奖励模型，以及基于反馈的强化学习。其结果说明目标和数据能改变模型行为；不能把它简化成“模型更大，所以更听话”。论文摘要中小模型获得更高偏好的结论，限定在其提示分布和人类评价设置下。[R2，§3、§4]

这条训练链可以按输入输出理解。**监督微调（SFT）**拿到“请求 → 示范回答”，调整权重，让示范中正确的后续 token 更容易生成。**奖励模型（RM）**拿到同一请求下回答 A 优于 B 的比较，学会给回答打分；它近似的是这批偏好判断，并不是事实真伪的通用判定器。**强化学习（RL）**让当前模型自己生成回答，再根据评分调整生成策略。与 SFT 直接模仿示范相比，RL 用结果好坏来引导尝试；这三步都是训练工作，普通业务请求中的一次模型调用不会自动执行它们。[R2，图 2、§3.1、§3.5]

对自演化系统，这引出一个关键区分：**用户满意度、事实正确性和任务成功率是不同信号**。如果系统只优化“用户点赞”，它可能学会更顺从、更肯定地回答，却没有提高可靠性。训练或搜索之前，必须先确定希望改变的行为及可观测指标。

### 2.3 思维过程是计算资源，也可能是噪声

Chain-of-Thought 将中间推理显式放入序列；讲义还给出 zero-shot reasoning 的例子。[L1，pp.30—31]

显式推理可以分解多步问题，但“解释写得更长”没有自动提供新事实。若缺少外部观察，模型可能在错误假设上继续推演。工程上应分辨：

- 推理是否发现了约束、生成了可执行检查？
- 是否通过工具取得新证据？
- 还是重复重述同一个未经验证的假设？

这也是后续课程把 Context、Harness、反馈和环境放在一起的原因。单纯延长文本计算与设计更好的信息采集流程，解决的瓶颈不同。

## 3. 从 Reasoning 到 Acting：外部反馈进入闭环

### 3.1 ReAct 改变的是信息流

讲义第 32—33 页展示推理与行动交替。ReAct 论文 §2 将 Agent 放在观察、动作和历史组成的交互过程中：当前推理可以指导下一次检索，检索结果又可以改变计划。[R3，§2、图 1]

```text
任务和当前上下文
→ 提出下一步动作
→ 运行工具
→ 得到观察或错误
→ 更新对任务的认识
→ 继续行动或结束
```

对代码任务，动作是打开文件、修改代码、运行测试；测试日志是观察。把工具错误回传给模型，比单纯让它“再仔细想一遍”增加了可检验的信息。

但是，动作由谁执行、工具参数是否有效、错误如何编码、何时终止，都需要程序控制。模型产生一段看似工具调用的文字，不能等同于环境已经完成动作。

### 3.2 执行轨迹与评估轨迹要分别保存

**工程推导**：同一任务应记录两类轨迹。

| 轨迹 | 例子 | 用途 |
|---|---|---|
| 执行轨迹 | 模型输入输出、工具参数、文件差异、工具返回 | 分析系统做了什么 |
| 评估轨迹 | 哪个断言失败、测试环境、判分规则、人工复核 | 分析为什么获得这个分数 |

仅保存最终 `reward=0`，会丢掉“读错了文件”“错误处理了 None”“测试根本没有启动”等不同原因。反思模块只能根据输入形成归因；原始诊断信号丢失后，增加反思调用未必能恢复它。

### 3.3 从单次成功走向跨次改进，还差一个更新过程

ReAct 主要定义任务内的交互方式。要跨任务改善，需要额外构造：从轨迹中选择值得学习的经验，表示成可用状态，并在下一次执行时调用。[L1，pp.32—33、69—70]

在本例中，错误日志是 `assert retry_count({"retries": 0}) == 0` 失败。一个有价值的候选经验应包含：

- 适用范围：需求区分“缺省值”和“显式提供的假值”。
- 观察依据：0 被错误替换，哪段代码造成问题。
- 可操作策略：分别测试键缺失、None、0、普通值。
- 例外：空字符串、False 是否有效，要回到具体需求。

“以后要更仔细”无法告诉下一任务应检查什么；“所有 falsey 值都要保留”又把一个任务的需求错误推广成通用规则。

## 4. 强化学习、测试时计算与 Harness 的作用边界

### 4.1 RL 使行为改变发生在模型参数中

讲义第 34—38 页从推理模型延伸到多轮检索 Agent。训练目标通常围绕轨迹收益，示意为：

$$
J(\theta)=\mathbb E_{x\sim D,\tau\sim p_\theta(\cdot\mid x)}[R(\tau)].
$$

这里 $x\sim D$ 表示按任务分布抽一个任务，$\tau$ 表示从开始到结束的一条执行轨迹，$R(\tau)$ 是这次执行的奖励，$\mathbb E$ 是对可能任务和执行结果取平均。$p_\theta$ 简写当前模型在给定环境中产生轨迹的分布，完整轨迹还受工具和环境响应影响。若奖励只取成功 1、失败 0，按同一评测协议抽取的 4 次执行有 3 次成功，则样本平均奖励为 0.75；它估计总体表现，不是模型对某一句话的自信程度。任务分布、轨迹生成方式、奖励定义任一改变，都会改变实验含义。

DeepSeekMath 的 GRPO 在同一问题上采样一组输出，利用组内奖励比较估计优势，从而避免额外训练与策略同规模的 critic。讲义第 35 页概括的是这一比较思路；论文 §4.1 还包括旧策略比率、裁剪和参考策略 KL 等训练设计。[R4，§4.1、图 4，PDF p.13]

先理解“优势”：它衡量一次尝试比比较基线好多少。教学上先看减去组均值这一步：同题 4 个输出奖励为 $[1,1,0,0]$，均值 0.5，差值为 $[0.5,0.5,-0.5,-0.5]$；GRPO 的结果监督版本还除以组内标准差，本例标准差取总体定义时为 0.5，归一化后为 $[1,1,-1,-1]$。训练据此倾向于增加较好输出、减少较差输出的生成概率，而不是把这四条文字存进记忆库。这里的 **critic/value model** 是学习预测未来回报的模型，用来提供比较基线；GRPO 用同题多次尝试的分数代替这一额外模型。若一组全同分，就缺少这种组内区分信号，零标准差也要在实现中处理。[R4，§4.1.2，PDF p.14]

其余三个词先按职责识别：新旧策略的**概率比率**比较同一个已采样 token 在更新前后有多大生成概率；**裁剪**限制过大的概率变化继续带来优化收益，并不是保证所有参数变化都有硬上限；**KL 约束**惩罚当前输出分布偏离参考模型过远，参考模型通常用于保留原有行为。它们让“按分数改模型”成为可控制的训练过程。本课先理解这条因果链，完整目标与梯度计算留到模型演化课程。[R4，PDF pp.11、13—14]

“无需 critic”不等于“没有比较基线或正则化”；“奖励正确”也不等于训练必然改善所有任务。对奖励数据、采样预算、长度及输出约束的依赖，需要到模型演化课程继续展开。

### 4.2 测试时多算一次，并不一定留下跨任务收益

Best-of-N、迭代修订、树搜索都可能提高单题结果。要判断是不是发生持续改善，可以做一个简单检查：**删除当前轨迹，重启系统，面对新题时还保留什么？**

- 仅保留最终答案：主要是当前产物改善。
- 保留可检索策略：可能有跨任务的上下文或记忆改善。
- 保留新的工具或工作流：可能有 Harness 改善。
- 保留新权重：属于参数改善。

这些机制可以组合，但报告中需要分别统计直接收益和未来收益。为一道题采样五条轨迹，不能把其中最好的一条当成单次生成能力。

### 4.3 Harness 能力不应从模型分数中推断

SWE-agent 的核心贡献之一是 Agent-Computer Interface：围绕搜索、查看、编辑与环境反馈设计适合模型使用的接口。[L1，pp.39—42；R5，§2—3]

工具返回太长，重要行可能被淹没；编辑接口缺少语法反馈，错误会延迟暴露；同一信息要经过很多轮才能取到，会浪费预算。改进这些接口可以提高整个系统表现，而没有训练底座。

因此，“模型 A 在 Harness X 上得分高于模型 B 在 Harness Y 上”无法单独证明模型 A 更强。至少要固定任务、工具、预算、终止条件和环境，再讨论模型因素。反过来，Harness 改得更复杂，也可能因为额外约束不适合某个模型而退步。

### 4.4 宣传性案例应该怎样读

讲义第 2、41—45 页引入 AI 协调、企业内部开发和研究加速的例子，提供研究动机。这里有三类证据需要分开：

1. 组织或作者对内部实践的陈述。
2. 可重复的受控实验。
3. 对广泛未来能力的推测。

企业报告的代码占比或协调 Agent 数量，不直接给出工作质量、任务选择、人工审核成本和反事实基线。工程师可以据此提出值得研究的问题，但不宜把它们当成本地项目的预期提升值。[L1，pp.2、41—45]

## 5. 历史主线：从可证明的自修改到经验性的搜索

### 5.1 Intelligence Explosion 是递归假设

讲义第 47—48 页概括 Good 的设想：能设计机器的机器设计出更好的后继，而后继也更擅长机器设计，进一步加速改进。

这条推理包含需要独立检验的环节：解决任务更强，是否意味着设计后继更强？搜索是否仍能找到改进？算力、数据、评估和现实实验的瓶颈是否允许加速？当前某个任务收益增加，不能证明递归过程会无限持续。

### 5.2 Gödel Machine 与 DGM 的证据标准不同

讲义第 49—50 页介绍形式化的 Gödel Machine：系统在能证明自修改有益时才修改。形式证明依赖目标、环境及证明系统的假设；在复杂开放环境中，证明一个实际 AI 代码变更全局有益通常不可操作。

DGM 采取经验路线：由 Agent 修改自己的代码，在编码基准上评估，并保留一个不断扩展的 Agent 档案。后续版本可以来自不同祖先，而不只来自当前最高分个体。[L1，p.55；R6，§2—3]

这两个名字相近，但验证含义不能混用。DGM 的基准改善是特定任务、预算和环境下的经验结果，不是形式上的全局最优证明。一个测试通过的修改，仍可能在未测任务上退化。

还要分清哪些代码实际可改：本地 DGM 论文使用冻结的预训练底座，允许 Agent 修改自己的工具和工作流；档案维护与父代选择等外层探索过程仍是固定的。论文没有展示底座再训练，也没有让整套演化算法任意改写自身。称其具有结构上的自指性有依据，称其已经验证所有层级的递归加速则超出了实验。[R6，§3，PDF pp.4—5]

### 5.3 为什么保留次优候选可能有价值

**教学例子**：版本 A 善于短文件修复，版本 B 在长日志定位上更好，但平均分稍低。如果只让平均最高的 A 继续演化，可能丢掉 B 的长任务能力；保留多样祖先，可能为后续组合或探索提供起点。

这里的价值来自潜在搜索路径，不意味着所有次优候选都应该无限保留。档案维护、重复版本去重、环境依赖和评估成本都是实际约束。DGM 的开放探索解释为什么需要多样性；工程系统还应决定档案容量和淘汰策略。

### 5.4 AlphaGo Zero 与 FunSearch 为什么重要

AlphaGo Zero 的例子说明，在规则明确、胜负可判定的环境中，可以通过自博弈生成训练经验；FunSearch 将模型生成的程序放进可执行评估与演化循环。[L1，pp.51—54]

这里需要留意讲义的过渡：p.51 在“AlphaGo Zero”标题下回顾的是原版 **AlphaGo** 先模仿人类棋谱、再强化学习的路线；p.53 才说明 **AlphaGo Zero** 不使用人类棋谱、从自博弈循环改善。不能把前者的模仿预热写成 Zero 的训练前提。“没有人类棋谱”也不等于没有人设计的棋规、搜索和训练系统。[L1，pp.51—53]

共同点是：模型提出的内容有外部环境检验。不同点是被优化的对象、反馈形式和成本。棋局有明确终局；科学程序可能有可计算目标；真实科研或个性化助理的目标更开放，评价延迟更长、反馈也更有歧义。

导论中不需要立即复现所有系统，但应该学会问：**这个领域是否提供了像胜负或程序测试一样可靠的约束？如果没有，用什么替代，误差如何进入后续更新？**

## 6. 第一张地图：到底什么在演化

讲义第 58—65 页逐步添加四类对象。它们是可组合的分析维度，不是互斥的产品类别。

| 演化对象 | 保存的产物 | 典型更新 | 对应讲义例子 | 主要验证问题 |
|---|---|---|---|---|
| Contexts & artifacts | 提示、答案、程序、档案 | 改写提示，生成更优程序 | FunSearch、DSPy | 新产物在独立输入上是否有效？ |
| Memory & harness | 记忆、技能、工具、运行代码 | 添加策略、修改调度或工具 | Voyager、DGM、Meta-Harness | 哪个组件导致收益，是否能安全撤回？ |
| Model weights | 权重、adapter | 梯度训练、蒸馏或自训练 | STaR、DeepSeek-R1、Absolute Zero | 新能力是否泛化，旧能力是否遗忘？ |
| Environment & tasks | 任务、课程、模拟器、验证器 | 生成新挑战、调整难度 | Absolute Zero 等 | 新任务是否可解、有效且有学习价值？ |

### 6.1 Context 与 artifact 的关系

生成一个更好的程序时，优化对象可能是最终程序，而不是求解器本身。程序如果被再次放进模型输入，就又成为上下文的一部分。分类依据应是这次实验究竟更新和部署什么，而不只是文件格式。

例如，为每个用户请求都从头搜索一次提示，可能没有跨请求积累；把验证后的提示纳入公共版本，才使后续请求使用更新后的系统。这也是为什么要记录状态生命周期。

### 6.2 Memory 与 Harness 的关系

记忆包含数据；Harness 定义这些数据怎样被写入、检索、加载和使用。增加数据库记录与修改检索策略，是不同的处理。

遇到失败时，如果根因是“正确记忆没有被取到”，继续向库中写同类记忆可能增加噪声。若根因是“错误经验被当作约束”，增大召回反而可能加重问题。只有明确读写与控制流，才能知道该改内容、路由还是模型。

### 6.3 参数更新与外部经验的权衡

提示和记忆便于检查、局部更新与撤回，但会增加输入、检索及管理成本。参数更新可以使行为更紧凑，却需要训练基础设施和更大范围的回归验证。不能仅根据“迭代速度快”或“推理 token 少”做决定。[L1，p.82]

**工程建议**：先定位瓶颈。如果知识变化频繁、需要精确来源或按用户隔离，可先尝试外部化；如果一种稳定行为在大量调用中反复出现，且有可靠训练信号，再评估是否值得内化。这个顺序是可讨论的实施策略，不是课程证明的普遍最优路径。

### 6.4 任务与模型可以联合演化

Absolute Zero 的同一模型既提出代码推理任务又解决任务，用代码执行器验证任务与答案，从而让课程和求解能力共同变化。[L1，pp.63—65；R7，§2—3]

“Zero data”在论文语境中指避免外部人工整理的训练任务与标签；模型预训练、代码语言、执行器、奖励和初始任务结构仍然提供先验与约束。把它读成“没有知识、没有环境设计、没有计算投入”会误解贡献。

联合演化还带来评价问题：如果任务变简单，分数可能上涨；如果任务变难，分数下降也未必表示求解器退步。因此，应该同时保留固定的外部锚点和动态课程指标。

## 7. 第二张地图：怎样发生演化

### 7.1 模型视角：哪些 token 是自己的计算，哪些来自环境

讲义第 66 页画出“任务 → think/action → observation → think/action”的序列，并区分模型生成的 token 与来自工具、检索、环境的新信息。

用 $h_t$ 表示可访问历史，模型基于 $h_t$ 决定动作；环境返回观察，系统构造 $h_{t+1}$。并不是所有上下文 token 都是模型选择的动作。在后续训练中，工具日志不能未经区分地当作策略生成 token 计算损失。

讲义把上下文视作决策状态的表示。严格来说，完整环境状态通常不可见，有限上下文、检索记忆和压缩摘要也未必满足 Markov 性。这里的 MDP 图帮助组织状态—动作—奖励关系；工程实现仍需处理部分可观测、信息丢失和状态过期。

**Markov 性**要求：给定当前状态和动作后，预测下一步不再需要更早的历史。**MDP（马尔可夫决策过程）**就是用状态、动作、状态转移和奖励描述这类决策。例如，服务只保存“提交超时”，却没有保存请求 ID 和服务端是否落库，单靠这个摘要无法判断重试是否重复写入。Agent 同样可能只看到一部分日志；把摘要命名为 `state`，不会自动使它包含决策所需的全部信息。

p.66 的 $V(\text{context})$ 是从当前上下文出发的期望最终回报，不是文本质量分数。图中的上升曲线表达希望增加有效计算或信息的目标；无关日志、错误观察和过度压缩都可能让决策变差，因此“继续加 token”并不保证 $V$ 单调上升。[L1，p.66；本段为图示的教学解释]

### 7.2 三种 Agent 更新机制

第 67—73 页对比三个机制：

1. **由外部改进**：外部数据和固定更新规则将 Agent v1 变成 v2。
2. **从自身经验改进**：数据来自自身交互，更新规则仍由人预先固定。
3. **自指式改进**：Agent 利用经验改写自己的部分结构或更新过程。

三个机制的差别在经验来源与更新规则的可变性。例如，固定的“失败后反思”提示能生成新记忆，但不代表反思算法本身也在演化。

### 7.3 写成两个时间尺度，更容易检查实验

**教学推导**：设执行配置为 $S_k=(\theta_k,P_k,M_k,H_k)$，经验为 $E_k$，更新算子为 $U_k$。

$k$ 数的是系统版本，而第 7.1 节的 $t$ 数的是一次任务里的行动步骤。$\theta_k$ 是权重，$P_k$ 是提示配置，$M_k$ 是持久记忆，$H_k$ 是运行框架；$D_k$ 是这一轮用来获取经验的任务分布，$B_k$ 是调用、时间或计算预算。可以把 $S_k$ 看成一次服务发布的配置清单，把 $U_k$ 看成根据运行记录构造下一版的更新程序。

$$
E_k=\operatorname{Run}(S_k,D_k,B_k),\qquad
S_{k+1}=U_k(S_k,E_k).
$$

这已经描述了一个经验驱动的改进循环。如果还允许更新规则变化，则再引入：

$$
U_{k+1}=\operatorname{MetaUpdate}(U_k,E_k,\operatorname{EvalHistory}_k).
$$

这里 $\operatorname{MetaUpdate}$ 是构造新版更新程序的过程，$\operatorname{EvalHistory}_k$ 是截至当前版本的评估历史。例如，$U_k$ 原来把每次失败反思直接写入记忆，更新后增加了“检查反例再采纳”的步骤。只有真的修改了这段更新逻辑，才对应第二个式子；一次新增记忆条目只改变 $M_k$，仍属于第一个式子。

第二个式子提出更高层的学习问题，但不能单靠符号证明系统具有递归改进能力。需要看到更新规则实际改变，并检验这种改变对后续改进效率的贡献。

例如，一次更新使修复任务更好，只说明执行者改善；它能否提出更有价值的下一次更新，还需要独立任务。否则“更强求解器”与“更强改进器”会被错误合并。

### 7.4 自身经验不等于封闭世界

Agent 可以从自身尝试中学习，但反馈仍可能来自人工、测试程序和外部环境。反过来，自己写答案、自己判正确、自己存为经验，会产生强相关的错误。闭环有没有接触可靠外部信号，比“所有模块是否自动化”更重要。

## 8. 第三张地图：Discovery、Continual Learning 与 RSI

讲义第 74—77 页将 AI for Discovery、AI for AI Research、Continual Learning 和 Recursive Self-Improvement 放在不同关系中。

- **AI for Discovery** 关心发现目标：科学规律、程序或工程设计可以是对象。
- **AI for AI Research** 将发现目标收缩到 AI 自身的算法和系统。
- **Continual Learning** 关心经历一串任务后知识如何保留、迁移和避免遗忘。
- **Recursive Self-Improvement** 进一步关心改进能力是否也因自身更新而增强。

第 74 页的框图还表达了三种具体关系：AI for AI Research 被画在 AI for Discovery 内，因为发现对象换成了 AI；它只有在“被改进的 AI 又承担下一轮研究”时，才为 RSI 提供反馈路径；Continual Learning 指向 RSI 的“required”，强调收益必须留在改进器里，下一轮才可能利用它。这是课程的概念组织，不是说任何一次 AI 研究或记忆积累都已实现递归改进。[L1，p.74]

一个替研究员整理文献的 Agent 参与了研究流程，但如果没有独立检验发现和更新自身，它不自动构成 RSI。一个持续学习的客服系统可能积累用户偏好，却不修改自己的学习算法。一个搜索程序的科学发现系统，也可能在每次实验后完全重置。

**阅读技巧**：将论文的广义动机、实际实现对象和实验支持范围分别写成一句话。很多概念混淆来自把第一句话当成第三句话。

## 9. 把地图落成最小工程闭环

以下是基于课程框架的教学设计，并非某一篇论文的完整复现。

### 9.1 从一个窄任务族开始

选定任务族：Python 配置读取与缺省值处理。系统只允许修改指定函数，环境提供可执行测试。先完成静态基线，再加入一种演化对象，例如经验记忆；不要同时更换模型、修改工具、加搜索和训练。

```text
固定任务与环境
→ 基线执行并保存轨迹
→ 用失败轨迹提出候选经验
→ 校验适用范围和来源
→ 用开发任务比较候选与基线
→ 版本化采纳
→ 在隔离的审计任务上检查最终系统
```

这条流程把“生成更好的解释”与“部署更好的执行配置”分开。解释可以作为候选，但采纳需要证据。

### 9.2 需要保存哪些对象

| 对象 | 必要字段 | 为什么重要 |
|---|---|---|
| TaskSpec | 任务 ID、需求、允许修改范围、环境版本 | 防止候选改变任务定义 |
| RunRecord | 配置哈希、输入、工具事件、产物、终止原因、成本 | 可以重放和定位变化 |
| Feedback | 评分器版本、观察、断言、噪声与异常标记 | 使归因能回到实际证据 |
| CandidateUpdate | 父版本、修改对象、差异、依据、适用范围 | 知道系统究竟学到了什么 |
| EvaluationRecord | 任务划分、每题结果、预算、指标与时间 | 防止只留平均分 |
| ReleaseManifest | 被采纳产物、依赖、回滚目标 | 能恢复历史系统 |

可将候选写成如下结构。字段设计是教学示例：

```json
{
  "candidate_id": "memory-defaults-v2",
  "parent_id": "memory-defaults-v1",
  "changed_object": "memory",
  "claim": "区分缺失值与需求允许的显式假值",
  "scope": ["python-config-defaults"],
  "evidence_run_ids": ["run-017"],
  "applicability": "需求明确允许 0 时，检查真值回退是否错误",
  "counterexample": "空字符串是否有效需由任务约定决定",
  "status": "candidate"
}
```

这条记忆保留的是策略和证据定位，不应把真实凭据、用户私密数据或特定测试答案混入可共享经验。这里的隔离直接服务于经验能否正确迁移，而不只是文件管理。

### 9.3 为什么需要父版本

不同任务可能从同一基线并行提出候选。若每个候选都直接覆盖“当前记忆”，就不知道它基于哪个状态生成，也无法发现冲突。

一个最小处理方式是：候选携带 `parent_id`；合并前确认基线仍匹配；如果已经变化，重新评估或显式合并。两个候选分别在旧基线上有效，不证明合并后仍有效，因为它们可能增加相互冲突的指令或共同超过上下文预算。

### 9.4 提议、评估与采纳分别是谁的责任

提出更新的模型可以访问开发轨迹；评估程序执行既定协议；采纳器检查预算、分布覆盖与约束，再选择版本。三者可以自动运行，但职责应可分辨。

如果让候选同时修改测试断言和被测函数，就改变了任务。若课程研究对象本身包含验证器演化，需要额外固定外部审计集来判断新验证器是否仍与真实目标一致。

## 10. 怎样设计能回答问题的实验

### 10.1 明确研究假设

一个可检验的假设是：

> 在底座模型、工具、每任务预算和任务族相同的条件下，保存带适用条件的失败经验，能改善未参与经验生成的新任务成功率。

这比“让 Agent 更聪明”具体，因为它确定了处理因素、比较条件、评测对象和预期变化。

### 10.2 至少区分三组任务

- **经验构建集**：允许优化器读取轨迹和反馈。
- **开发选择集**：用于选候选和调参；被反复查看后已经参与选择。
- **隔离审计集**：最终比较，不能将答案或轨迹回流给改进器，再仍称为未见测试。

任务高度相似时，应按仓库、模板、时间或问题族分组划分。随机拆分会把同一模式的变体同时放入经验与审计，夸大迁移能力。

### 10.3 区分四个可能的收益来源

| 对照 | 回答的问题 |
|---|---|
| 无记忆基线 vs 真实记忆 | 添加这一机制总体是否有益？ |
| 等 token 的无关记忆 vs 真实记忆 | 收益是否只来自更多上下文或额外提醒？ |
| 原始轨迹 vs 提炼经验 | 表示和提炼本身有没有贡献？ |
| 真实经验 vs 同预算更多重试 | 改善是否值得额外学习成本？ |

这些对照不是每课都强制执行的固定表格。应根据该方法声称的贡献选择最能排除替代解释的实验。

### 10.4 同题重试与新题迁移必须分别报告

同题第二次尝试时，Agent 已经拥有该题错误反馈；首次处理新任务时没有。前者衡量任务内适应，后者更接近经验迁移。

如果报告“最终在 N 次内通过”，应同时报告 N、选择器获得了什么反馈、总预算和首试结果。否则一个高成本多次搜索系统可能被误认为单次能力提升。

### 10.5 在线持续改善需要遵守时间顺序

对于任务流 $q_1,\dots,q_T$，一个基本协议是：先用 $M_{t-1}$ 预测 $q_t$，记录结果，再用当时允许的反馈构建 $M_t$。不能先读当前任务的真实答案改写记忆，再把改写后的答案算作该任务预测。

还应记录任务顺序、初始记忆、何时重置、环境是否延续。较早任务留下的状态会影响较晚任务，因此流式分数与独立重置分数回答不同问题。

### 10.6 以每题差异解释平均分

可将候选与基线逐题配对，记录：共同成功、共同失败、候选新增成功、候选新增失败。新增失败集中在哪些类型，往往比一个平均提升更能指导下一次修复。

应报告样本数量、重复运行配置、结果波动和未完成任务。对小样本，不要将一两道题的变化包装成稳定规律。所有这类协议建议是本课的工程展开；它们并非由导论中的单个案例直接验证。

## 11. 目标、奖励与验证器也会出错

### 11.1 Reward hacking 可以在很普通的任务中发生

若评分器只检查输出是否包含“测试通过”，Agent 可以直接写这几个字。若只检查一个可见样例，它可以硬编码答案。若以代码长度为成本，它可能删除必要检查。

因此，应先明确任务完成的可观测后果，再设计评分信号。测试通过是一种有用证据，其可信度取决于覆盖范围、环境与被测对象是否隔离；模型评价更需要检查是否偏好文风、长度或自信表达。[L1，p.83]

### 11.2 反思是归因假设，不是因果证明

看到测试失败后，模型可能给出一段合理的故事，但故事是否对应真实根因，需要通过替换组件、重跑关键步骤或构造反例验证。

例如，Agent 反思“提示过短”，而实际失败来自超时。延长提示可能偶然在下一次运行成功，却没有修复超时机制。诊断中至少保留环境错误与任务错误的区分，避免把服务波动转化为长期错误规则。

### 11.3 任务演化不能把真实目标一起改掉

模型不断生成它容易解决的任务，会让自评成绩提高；不断生成无法判定的任务，又会让反馈失去意义。任务生成器需要有效性、可解性、难度和多样性约束，外部锚点用于检查真实能力是否变化。

验证器同样可能演化。此时应同时评估它的判别能力：对已知正确、已知错误及对抗性产物是否给出恰当结果。评价一个验证器不能只看它是否让求解器获得更高奖励。

## 12. 成本、延迟与长期收益

### 12.1 一轮演化不只有生成候选的费用

**教学成本模型**：

$$
C_{\text{update}}=C_{\text{rollout}}+C_{\text{feedback}}+C_{\text{proposal}}+C_{\text{validation}}+C_{\text{storage}}.
$$

部署后的每次调用还可能增加检索、输入 token、工具和验证成本。延迟要分离串行关键路径与可并行工作：并行十个候选可以缩短等待，但并不消除总调用成本。

### 12.2 何时值得保留一个更新

假设候选一次构建成本为 $C_u$，在未来 $N$ 次调用中，每次质量改善的价值为 $\Delta V$，新增运行成本为 $\Delta C$，则一个简化的收益条件是：

$$
N(\Delta V-\Delta C)>C_u.
$$

这个式子是决策框架，不是论文实验结论。真实系统还应考虑错误成本差异、未来任务分布和更新失效时间。

**教学数值例子**：若一次构建费用 20 个单位，每次预计净收益 0.05 个单位，则约需超过 400 次后续调用才覆盖构建费用。这里不使用真实 API 价格，也不假设净收益已经得到验证。低频、快速变化的任务可能更适合临时搜索；高频且稳定的流程才更容易摊销学习成本。

### 12.3 记忆更长，未必账单更高，也不保证更便宜

更长输入通常增加处理负担，但缓存复用、检索选择和推理轮数减少，可能改变总成本。不能只看 token 总量，也不能只看供应商账单；还应记录缓存命中、工具时间、总延迟、失败重试和质量。

在本课导论中只建立测量习惯；Week 2 的 ACE 嘉宾材料会给出一个具体的缓存与上下文长度案例。跨系统比较时必须带上实际缓存条件。

## 13. 故障诊断：把“没有变好”拆成可定位的问题

| 现象 | 候选原因 | 有区分力的检查 | 可能的下一步 |
|---|---|---|---|
| 更新文件很多，成功率不变 | 写入内容未被读取，或条目无作用 | 记录检索、加载与使用链；冻结其他因素做消融 | 修读取策略或停止无效写入 |
| 开发集提升，审计集下降 | 选择过拟合、模板泄漏、规则过窄 | 按任务族重划分；检查条目中的题目特征 | 缩小适用范围，减少搜索自由度 |
| 首批任务变好，长期退步 | 错误积累、冲突或上下文过长 | 按时间绘制表现；回放记忆版本 | 撤回污染条目，加入去重与失效规则 |
| 更多重试却更慢且无增益 | 反馈无新信息，或选择器不可靠 | 比较候选多样性和选择正确率 | 改进观察与验证，减少重复计算 |
| 固定测试提高，真实任务失败 | 验证器覆盖不足 | 加入真实错误类型和外部审计 | 修评估目标后再继续优化 |
| 自修改后无法重放 | 环境、依赖或代码版本没有固定 | 用 release manifest 重建运行 | 先补可追溯性再做能力结论 |

排错顺序建议是：先确认实验能被重放，再确认评分有效，然后确认更新实际进入执行，最后分析方法本身。顺序的理由是避免把基础设施异常误判为学习算法问题。

## 14. 一次端到端教学推演

下面把前面几节连成一个完整实验，而不提供虚构的实测分数。

**任务**：修复 Python 配置处理函数。缺省和 None 使用 3，显式 0 使用 0。基线错误实现如下：

```python
def retry_count(config):
    return config.get("retries") or 3
```

**第 1 次执行**：Agent 看到 `0` 的失败用例，改为 `config.get("retries", 3)`。显式 None 仍然失败。执行记录保留这两个不同现象。

**反馈与候选**：反思模块提出策略：“先枚举缺省、None、合法假值，再选择判断条件。”候选包含需求引用和失败用例的类型，不保存隐藏测试答案。

**正确产物示例**：

```python
def retry_count(config):
    value = config.get("retries")
    return 3 if value is None else value
```

**本地验证范围**：已用 Python 检查缺失键、None、0、2 四个输入；错误版本在 0 上失败，正确版本四项均符合上述约定。这只验证两段函数与教学规格的关系，没有调用 LLM，也没有执行自演化实验。

这段代码只满足本教学任务的语义。若另一个系统要求键存在且值为 None 时抛错，它就不是正确实现。

**开发比较**：使用不同字段和函数名的开发任务，比较无记忆、原始轨迹、提炼策略；固定模型与总预算。观察成功和失败是否集中在同类语义。

**独立审计**：加入合法 False、空容器、字符串 `"0"` 等需求不同的任务，检验候选是否会无条件推广。如果新增经验导致把所有假值都保留，应拒绝这一过宽版本。

**采纳或撤回**：通过事先规定的条件后，才将候选状态从 `candidate` 改为 `active`，并保留父版本。部署中出现新反例，先限制适用范围或回滚，再决定是否继续学习。

本例展示的知识进展是：从“修对一个函数”，走向“提炼出有边界的策略”，再走向“验证这条策略在新任务上有用”。它没有证明某个 LLM 可以稳定自动完成所有环节。

## 15. 怎样把研究方向收缩成一个项目

讲义第 79—86 页列出了创新判断、自动研究、经验沉淀、权重与 Harness 选择、监督、科学工程、个性化和具身学习等方向。

| 讲义方向 | 一个可操作的问题 | 最小评价证据 |
|---|---|---|
| p.79：新颖研究想法与 taste | 优化器能否提出不重复、可证伪的候选？ | 新颖性与可行性分开评判，保留评价者信息 |
| p.80：自动化工程和 AI 研究 | Agent 能否用固定预算改进一个明确算子？ | 独立验证器、资源约束与复现日志 |
| p.81：经验转成持久知识 | 失败经验是否改善新任务，而非只帮助重试？ | 同题与跨题实验、错误记忆分析 |
| p.82：权重还是 Harness | 稳定策略外部化与内化的收益成本如何？ | 相同任务与预算，分别统计构建和运行成本 |
| p.83：监督自主系统 | 评价器是否能识别高分但违反目标的产物？ | 真实反例、错误接受和错误拒绝 |
| p.84：科学工程 | 模型提出的设计能否通过真实约束？ | 模拟与真实结果差异、重复实验 |
| p.85：个性化 | 记忆能否适应用户偏好变化？ | 按时间划分、撤销偏好、用户隔离 |
| p.86：多模态与具身 | 经验能否迁移到观测与动作变化的环境？ | 感知错误、环境漂移和行为成功分开测量 |

提案应写清楚：问题、基线、改变的变量、数据和反馈、独立评价、预算、失败时能获得什么知识。一次严谨的负结果也可以说明某种更新在何种条件下无效；项目价值不依赖每轮分数单调上涨。

讲义第 17—18 页把项目组织成文献、基线、错误分析、方法迭代与评估。对自学者，可以把它当作学习顺序：先让静态系统能执行和测量，再决定值得演化什么。

## 16. 自测与参考答案

### 问题

1. Agent 第一次失败、第二次成功，是否证明跨任务学习？
2. 同一底座换了新工具后分数提高，改进属于哪个层次？
3. 为什么 DGM 的实证结果不能当成 Gödel Machine 的形式保证？
4. 给 Agent 更长上下文，为什么不能自动获得长期记忆？
5. 固定评分器是不是一定可靠？
6. 如果新版本平均分提高，但一个重要任务族明显退步，应怎样报告？
7. 同一模型提出任务、解题和评价，最需要保留什么独立约束？
8. 怎样区分“更新后的 Agent 更强”与“它更擅长改进自己”？
9. 一个服务把失败经验写入数据库，但下次请求未检索它；另一个服务读取了经验但没有训练模型。两者分别改变了什么？
10. 同题四次尝试奖励为 $[1,1,0,0]$。组内比较能提供什么训练信号？它与把成功回答放进下一次提示有什么不同？

### 参考答案

1. 不足以证明。第二次拥有同题反馈；需要用未参与经验构建的新任务验证迁移，并与等预算重试比较。
2. 主要是 Harness 或动作接口的变化；应固定其他因素，再定位具体工具设计的贡献。
3. 前者在有限基准和预算下观察收益，后者要求在形式假设中证明修改有益。两者证据范围不同。
4. 长上下文仅扩大一次可读取空间；持久化、检索、加载和更新机制仍需实现，信息可能过期或丢失。
5. 不是。固定测试也可能覆盖不全、目标错误或易被利用；需要检查它与真实任务完成的对应关系。
6. 同时报告总体和分组的新增成功与新增失败，按预先规定的重要约束决定是否采纳，不能用平均数掩盖退化。
7. 有效任务与答案的外部验证、固定审计锚点和资源约束；自我一致并不等于真实正确。
8. 前者测最终任务表现；后者还需用相同改进预算比较后续候选质量、搜索效率与持续收益，且避免重复使用选择集。
9. 前者改变了存储状态，但经验没有进入后续决策，不能据此认定行为改善。后者改变了调用上下文，权重可以保持不变；应进一步检验经验是否改善新任务。两种情况都不能仅凭“写入”或“读取”断言效果。
10. 减去均值后差值为 $[0.5,0.5,-0.5,-0.5]$；按总体标准差归一化后为 $[1,1,-1,-1]$。它提供相对好坏方向，配合完整训练目标更新权重。把成功回答放进提示改变的是输入条件，既不等于参数训练，也不保证成功方法能迁移到新任务。
