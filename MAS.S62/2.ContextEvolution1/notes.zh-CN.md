## 1. Context 是模型实际读取的东西

### 1.1 Context 与 Harness 的边界

讲义给出两个定义：[L2，pp.4—6]

- **Context**：模型生成下一个 token 之前读取的全部输入。
- **Harness**：管理模型上下文与执行流程、帮助模型完成任务的外围代码。

对一个 Agent，可以先写出：

$$
c_t=\operatorname{BuildContext}(P,M_t,h_t,o_t,x),\qquad
a_t\sim p_\theta(\cdot\mid c_t).
$$

这是教学表达：$P$ 是提示，$M_t$ 是可访问记忆，$h_t$ 是部分历史，$o_t$ 是当前观察，$x$ 是任务。构建上下文的函数属于 Harness；真正送进模型的内容才是 Context。

因此，一篇论文放在磁盘上，不等于模型已读；向量库命中了一条记录，不等于它被加入本次输入；一条经验被加载，不等于它对当前动作有帮助。实现和评测应分别记录这几步。

### 1.2 固定权重，也能改变条件行为

讲义第 7—8 页从条件分布解释上下文。模型对下一项的预测依赖前缀；示例可以使任务解释从多个可能方向收缩到某个方向。[L2，pp.7—9]

$$
p_\theta(y\mid c)=\prod_t p_\theta(y_t\mid c,y_{<t}).
$$

Context evolution 改变 $c$ 的构建、内容或持久状态；它不要求在本轮修改 $\theta$。这里的“学习”发生在系统行为和外部状态中。要获得未来收益，新的提示、示例或经验还必须在之后被保留、找到并正确应用。

### 1.3 把上下文拆开，才能决定怎样优化

| 上下文内容 | 例子 | 合理的改变方式 | 主要风险 |
|---|---|---|---|
| 任务规范 | 返回 JSON，区分金额与币种 | 澄清、结构化、固定接口 | 优化器删除必要约束 |
| Few-shot 示例 | 问题与符合要求的输出 | 选择、排序、替换、压缩 | 标签泄漏或模板过拟合 |
| 外部证据 | 检索到的文档和工具结果 | 检索、过滤、定位、截取 | 过期或不可信内容被当作指令 |
| 过程状态 | 已完成动作、待验证项 | 增量记录、摘要、恢复 | 摘要把“尝试”写成“完成” |
| 经验策略 | 某类失败的处理办法 | 提炼、加适用条件、修订 | 一次偶然现象被推广 |
| 多模态输入 | 图像、音频、视频或其描述 | 对齐、编码、分段、工具化 | 丢掉时序、关系或置信度 |

这个拆分是工程分析工具，不是新提出的课程分类。它帮助避免把所有问题都归结为“system prompt 不够好”。

## 2. 上下文不只有文本：多模态与交互

### 2.1 多模态信息怎样进入语言模型

主讲义第 12—17 页给出三类路径：通过编码器与 adapter 将其他模态映射到模型可用表示；通过对齐和指令训练学习图文交互；或者先用专门模型把感知结果转换成语言，再组织后续推理。[L2，pp.12—17]

以图像问答为例：

```text
图像 → 视觉编码器 → 视觉表示/投影 → 与文本上下文共同输入模型
```

另一种组合方式是：

```text
图像 → 图像描述工具 → 文本描述 → 语言模型计划 → 环境动作
```

后者接口更容易组合，但图像描述可能丢失细节；前者保留的表示更丰富，却依赖模型架构和训练。不能用一句“模型看到了图片”忽略实际信息路径。

### 2.2 为什么这也属于上下文工程

多模态系统同样要选择提供哪些帧、哪些时间片、哪些观测置信度。若视频摘要丢掉先后顺序，后续语言推理可能很完整，但结论仍然错误。

**教学例子**：系统要判断“物体是否在警报之后被移动”。只传递“出现警报，物体被移动”两个事实，缺少时间关系。改写推理提示不一定补得回来；应先保留带时间戳的观测。

所以，对上下文的优化不只是措辞搜索，还包括表示、选择和信息保存。优化器能否改变这些变量，要在实验开始前说明。

### 2.3 CoT、Tree of Thoughts 和 ReAct 分别增加什么

讲义第 10—11 页讨论推理与搜索，第 18 页回到推理与行动交替。[L2，pp.10—11、18]

- CoT 增加显式中间推理。
- Tree of Thoughts 引入多个候选状态及搜索、评价和选择。
- ReAct 通过动作获得外部观察，形成后续推理依据。

它们可能改变同一问题的求解质量，但成本和信息来源不同。多写思维步骤不等于取得新证据；搜索多条路径也依赖选择器质量；工具交互还依赖执行器是否正确。后续 Prompt 优化应针对实际瓶颈，而不是统一要求“想得更长”。

## 3. 提示优化的形式：搜索变量、评分器和预算

### 3.1 为什么手工改提示难以扩展

讲义第 19—20 页展示措辞、格式等非任务语义特征可能影响表现，以及用户难以知道怎样提供合适指令。[L2，pp.19—20]

但“模型对提示敏感”是需要绑定模型和任务的观察，不代表所有微小变化在所有模型上都同样重要。工程上要先测自己的基线，避免花大量预算优化一个并非主要瓶颈的变量。

第 21 页进一步区分：人写提示、模型辅助人写提示、通过执行与评估组成自动优化循环。只调用一次模型生成更好的提示，还没有执行效果检验。

### 3.2 一个统一优化目标

**教学推导**：设候选上下文参数为 $z$，系统为 $F_\theta(x;z)$，评分器为 $m$，预算为 $B$：

$$
z^*=\arg\max_{z\in\mathcal Z}\mathbb E_{(x,y)\sim D}[m(F_\theta(x;z),y)]\quad\text{s.t.}\quad C_{\rm search}(z)\le B.
$$

$z$ 可以是单段提示、多个模块的提示集合、示例选择，或者一组记忆条目。这里的分布期望只能通过有限数据估计；开发集上最好的候选，不保证在真实分布上最好。

开始优化前，应明确：

1. 哪些文本可以修改，哪些规范必须固定？
2. 评价的是最终答案、执行后果，还是模型的主观评价？
3. 优化器能读取哪些标签和轨迹？
4. 搜索、验证与最终推理分别消耗多少预算？
5. 什么结果会被保留并进入下一次运行？

### 3.3 离散、高维与模块化

第 22—23 页指出，文本 token 是离散对象，可能的长字符串空间巨大。即使拿到 embedding 上的数值梯度，也不能直接保证得到有用、合法的文本修改。[L2，pp.22—23]

本课讨论三种实际路径：候选搜索、文本反馈引导的局部修改、通过模块化缩小每次优化的范围。它们都利用了语言模型的先验，但仍需要外部或独立评价来选择更新。

## 4. APE：把提示当作自然语言程序搜索

### 4.1 从输入输出示例反推指令

APE 将 instruction 看作程序，使用模型提出候选，再执行和评分。输入可以是一些输入输出示例；候选生成器试图推断产生这些映射的指令。[L2，p.24；R1，§3、图 1—2]

以词语反义任务为例，模型看到 `on→off`、`direct→indirect`，可能提出“给出反义词”，也可能误解成某种字符串编辑。候选之间的区别需要在新输入上执行，不能只判断哪一句更自然。

### 4.2 完整流程与两个评分视角

```text
少量任务示例
→ 生成多条候选指令
→ 在目标模型上运行候选
→ 根据任务指标评分
→ 淘汰低分候选
→ 可选：围绕高分候选重新采样
→ 输出评分集上表现最好的指令
```

原论文算法 1 用 `D_train` 的子集逐轮筛选，最终仍按 `D_train` 分数选指令；独立 `D_test` 用于报告效果。上图中的“评分集”是候选选择所使用的数据，不能因为名称中出现 evaluation 就把它当作未参与选择的测试集。工程上可以另设开发集选择，但应明确这是自己的数据协议。[R1，pp.3—5、算法 1]

APE 讨论 execution accuracy 和答案对数似然等评分。二者回答不同问题：前者直接看输出任务完成情况；后者衡量模型对期望答案的倾向。较高答案似然不必然产生同样的实际解码结果，且并非所有 API 都提供必要分数。[R1，§3.2]

### 4.3 论文结果说明什么

论文在 Instruction Induction 与部分 BIG-Bench 任务中比较自动与人工指令，支持“模型生成并筛选提示可以在这些设置中接近或超过人工提示”的判断。[R1，§4]

它不意味着模型已经理解任何产品目标，也不意味着自动生成的所有提示都有效。APE 的效果依赖候选生成模型、目标模型、示例代表性、评价函数和搜索预算。一个任务上找到的提示迁移到另一模型，还需要重新验证。

### 4.4 工程上什么时候先用 APE 风格搜索

适合：输出可自动评分，提示变量较小，希望建立一个便宜清晰的基线。实现上可以先生成少量有语义差异的候选，保存每题结果，再决定是否需要更复杂的反馈算法。

如果错误主要来自检索不到证据、工具接口或环境失效，纯提示搜索可能只是在错误信息上找更会表达的答案。此时应先修复信息链路，而非扩大搜索。

## 5. TextGrad：沿计算图传播可操作的文本批评

### 5.1 “梯度”在这里是类比

主讲义第 25 页使用 gradient descent 的语言介绍 TextGrad；论文明确说明，文本梯度是由 LLM 产生的自然语言反馈，借用自动微分的图结构和接口来分配修改建议。[L2，pp.25—29；R2，§2]

它没有保留数值梯度的全部性质：没有保证满足链式法则对应的导数运算，没有通用下降保证，也没有可直接解释为局部线性变化率的向量。不能用 `backward()` 这个 API 名字推断它是对底座权重求导。

### 5.2 用五个步骤拆开最小例子

设 $p$ 为可修改提示，$q$ 为问题，$a^*$ 为训练时可用答案：

$$
y=F(p,q),\quad e=E(q,y,a^*),\quad g_y=B_E(y,e),\quad g_p=B_F(p,q,y,g_y),\quad p'=U(p,g_p).
$$

| 步骤 | 实际发生什么 | 最容易误解的地方 |
|---|---|---|
| Forward | 任务模型用提示回答问题 | 答案可以错误，仍要保留上下文 |
| Evaluate | 评价器定位答案错误或给出任务反馈 | 文本 loss 未必是数值标量 |
| Backward 到答案 | 解释答案应怎样改变 | 不是直接修改最终答案就完成训练 |
| Backward 到提示 | 根据调用关系把错误归因到上游提示 | 归因是模型推断，可能错误 |
| Update | 模型结合当前提示与反馈生成新提示 | 新提示仍是待验证候选 |

R2 第 4—5 页给出从 Prompt 到 Prediction、Evaluation 的示例，以及 TGD 的更新形式。反馈不仅需要“错了”，还需要变量的角色、所在调用和下游要求；否则优化器可能把应该修答案的问题误归到提示。

### 5.3 教程中的百分比问题

T2 使用“先增加 50%，再减少 50%”作为演示。原始任务模型回答“等于原数”，评价指出：

$$
x\times1.5\times0.5=0.75x.
$$

原始提示为“简洁回答数学问题”。反馈认为过度强调简洁可能省略必要计算，更新器提出包含验证、解释和误区检查的可复用提示。教程约束还要求不把本题数字和答案写进提示。[T2，前半部分 Core Method]

应分开两个观察：一个是 Notebook 已保存输出呈现了这条改进路径；另一个是这个提示在新问题上是否有收益。单题演示没有回答第二个问题。

### 5.4 `requires_grad`、`role_description` 与反馈缓存

在课程 Notebook 中，Prompt 的 `requires_grad=True`，Question 为 False。它们都是文本变量，但只有前者是要更新的对象。`role_description` 会进入反馈和更新请求，用来说明这个变量是“可复用系统提示”，而不是当前题目的答案。

`optimizer.zero_grad()` 清除旧反馈；`backward()` 收集并传播批评；`optimizer.step()` 才替换提示。多个样本通过 `tg.sum(losses)` 汇集反馈，不应把它理解成文本 loss 的数值加法或数学梯度平均。[T2，单题循环、Prompt Optimization on a Dataset；R2，§2]

### 5.5 强反馈模型带来了什么额外因素

教程用 `gpt-3.5-turbo` 或其快照做任务模型，用 `gpt-4o` 提供评价和更新。强模型可能把自己的知识和推理策略传给弱模型。因此，收益不能完全归因于“图式反馈结构”。若要分离这种因素，可对照直接由强模型写提示、等预算自我修订、同模型反馈等设置。

这些模型名和接口来自课程快照，不代表当前服务可用性保证。重跑需要确认依赖版本、模型访问条件与预算；原 Notebook 的 `%pip install textgrad` 没有锁定版本，保存输出也不能证明任意版本都产生同一结果。

### 5.6 多任务优化、验证回退和测试集的角色

教程后半部分使用 BBH Object Counting，保存的数据划分为 train 50、validation 100、test 100，batch size 为 3。它以验证集分数决定是否撤销提示更新，代码中 `run_validation_revert` 负责恢复先前提示。[T2，Dataset 部分]

这比只在单题上看改进更接近可复用提示优化，但还需要注意：

- 验证集参与候选选择，反复使用后不是独立测试。
- 教程每一步都计算 test 分数，代码宣称只报告进度；如果人据此选轮次、调约束或停止，test 就实际参与了选择。
- 随机种子固定了本地抽样，不能保证远程模型和服务调度完全确定。
- 一个保存输出中出现 0.93、0.94 等验证准确率，是那次运行记录；本文没有重跑，不把它写成本地复现结果。
- 新提示是否改变最终答案格式，要与解析器共同检查。教程保存候选曾从 `Answer:` 改向 `Total:`，格式变化本身可能影响评分。

### 5.7 梯度式反馈什么时候失效

反馈模型可能把随机采样错误归因于提示，也可能反复加入“仔细”“准确”等泛化指令，使提示膨胀。若错误在检索阶段，批评最终答案可能找不到真正根因。

处理思路是保留模块输入输出与评估轨迹，明确允许修改的变量，对不同失败类型分组，使用独立开发集验证候选。对关键格式和不可变规则，应使用程序检查，而非只把它们写成更新器的自然语言 constraints。

### 5.8 不只有 Prompt：图中的变量也可以是代码或科学候选

L2 p.30 同时展示代码、分子和放疗计划优化。它们共享的是“候选 → 外部执行/计算 → 反馈 → 修改候选”的接口，而不是所有评分器都由 LLM 主观判分：代码可运行测试，分子候选可交给性质预测与对接评分，计划参数可交给数值求解器与剂量指标。[R2，p.3、§3.1、§3.4—3.5]

因此，应先说清可修改变量和前向计算，再谈文本反向反馈。例如修改程序时变量是代码；评价来自执行结果；反馈解释失败原因；更新器产出下一版代码。把同一框架用于分子或计划，不会自动使这些候选满足领域约束，也不能把代理评分改善当成真实实验或临床效果。图中 Prompt 的 77.8%→91.9% 属于论文实验，不是 T2 保存的 50/100/100 划分运行记录，二者不能拼接。

## 6. DSPy：用模块化程序组织可优化变量

### 6.1 为什么一整段提示难以维护

主讲义第 31—34 页把问题从自由字符串转向可组合模块。一个 RAG 系统可能有 query 生成、检索、证据整理和回答；如果它们全部塞进一个巨大的提示，难以知道哪个局部改变导致效果变化。[L2，pp.31—34]

DSPy 的签名描述输入输出角色，例如 `question, context -> answer`；模块选择怎样实现这个变换；程序控制流决定模块怎样协作；编译器根据数据和指标优化模块参数。[R3，§3—4]

### 6.2 Signature 是接口，不是完整业务规范

签名提供字段、描述及可能的指令。它有助于格式化、解析和追踪，但只写 `question -> answer` 不会自动定义证据正确性、权限或失败策略。

**教学例子**：财务数字抽取可使用 `document, field_spec -> value, unit, period, evidence`。签名明确了要交付什么；验证器仍需判断数值是否对应正确期间、单位和原文位置。

如果只优化 `answer_exact_match`，系统可能在缺证据时凭参数知识答对。业务目标需要证据充分时，应把这一要求纳入评分，不能假设使用 RAG 后自然获得可追溯性。[R3，p.6 的 answer-and-context metric 示例]

### 6.3 编译器到底优化什么

主讲义总结三类操作：[L2，p.34；R3，§4]

1. 为各个 Predict 模块生成候选说明、字段描述和 demonstrations。
2. 通过搜索选择候选参数。
3. 对程序做更高层组合，例如多个副本的集成。

BootstrapFewShot 的重要思路是：只要求最终输出的评价，也可以从成功执行中收集中间模块的示例；不必人工为每一步标注。但最终正确的轨迹可能包含不理想中间步骤，收集示例仍应注意过滤标准。

DSPy 论文还覆盖通过编译进行微调。因而“DSPy 一定不改权重”是不准确的；本课上下文主线主要讨论提示和示例层面的优化，具体 optimizer 决定实际改变对象。

### 6.4 为什么整体指标不足以定位局部失败

假设检索遗漏了一篇关键文档，回答模块仍因参数知识给出正确答案，整体 EM 评分会认为这次执行成功。若把 query 和回答都收成示例，可能把偶然成功固化。

**工程建议**：保留端到端目标，同时增加有诊断作用的中间指标，如证据召回、引用支持、结构合法性。中间指标用于定位原因，不宜任意加权成一个看似精确、却与任务目标脱节的分数。

## 7. GEPA、PromptQuine 与 Reflexion：三种不同更新路径

这三篇阅读扩展了第 22 页的搜索问题。它们可以放在同一张地图上理解，但优化对象与经验范围不同。

### 7.1 GEPA：用执行反馈做模块级反思和候选演化

GEPA 将多模块系统的提示集合视为优化对象，底座权重固定。每次从候选池选择一个系统版本，选择要改的模块，运行一批任务，收集分数及文本反馈，然后提出局部提示修改。[R6，§2—3、算法 1]

候选先在小批次与父版本比较；满足条件后，再进入更大范围的候选选择。执行器产出的错误日志、编译信息和规则违反，可以在压缩成一个奖励数值之前提供更具体的学习信号。

论文另有 **GEPA+Merge**，在反思修改之外组合互补模块。它要求两个候选具有共同祖先、修改了不相交的提示模块、都在候选前沿且都优于祖先，再从各自谱系取出对应模块构成新系统。这种 system-aware crossover 需要记录祖先和每个模块的演化，不能直接把两段提示拼接。[R6，p.23，附录 D.1]

Merge 也不是免费增强：论文在 GPT-4.1 Mini 上得到额外收益，而相同超参数在 Qwen3-8B 上出现退化，作者将其与预算分配、调用时机和谱系多样性联系起来。实现时应把基础 GEPA 与 GEPA+Merge 分别标记，并在合并后重新评估。[R6，§4，Observation 5]

### 7.2 GEPA 的 Pareto 到底指什么

这里的重要设计是保留在不同任务实例上表现互补的候选。候选 A 在若干题上最好，候选 B 在另一组题上最好；平均分略低的 B 仍可能提供有价值的探索方向。[R6，§3.1、算法 2]

它不是默认在“价格—延迟—准确率”三目标上建立业务 Pareto 前沿。论文的 instance-wise selection 需要读取各任务分数矩阵，不能只保存每个候选一个平均值。

GEPA 的训练数据又划分为反馈集和用于候选选择的 Pareto 集。两者都参与优化，最终测试仍需要隔离。反复在 Pareto 集挑选胜者，也会产生选择偏差。

### 7.3 如何理解“优于 RL、需要更少 rollouts”

R6 比较了特定模型、任务和预算下的 GEPA、GRPO 及其他提示优化器，支持“自然语言反馈能在这些条件下高效学习”的结论。它不证明任何提示优化都优于任何参数训练。

Rollout 数量也不是完整成本：反馈调用、反思模型、输入长度、验证和目标模型推理都要计入。较长优化提示可能提高部署时输入成本；权重训练则有不同的前期和运行成本结构。选择时应看总预算及未来调用规模。

### 7.4 PromptQuine：子序列搜索挑战可读性直觉

R5 的 PromptQuine 搜索固定顺序的提示子序列，通过删减 token 和演化选择寻找有效提示。论文展示某些看起来不连贯的提示可能胜过更自然的文本，研究对象包括 ICL demonstrations 的剪枝。[R5，§2.3—3]

这里的关键启发是：人类可读性不是模型任务表现的充分代理。它不是“随机删掉生产提示就会更好”的建议。不可变的权限约束、输出契约和审计信息，应与可搜索示例分开；即使分数提高，也需要检查模型版本迁移、异常输入和可维护性。

PromptQuine 的 held-out selection 与独立 test 是重要的实验设计。搜索可能利用验证集的偶然结构，尤其在候选很多、数据很少时。每次减少 token 带来的性能变化也可能非单调，不能用“越短越好”替代实验。

### 7.5 Reflexion：把一次尝试的反馈写进下一次上下文

Reflexion 包含 Actor、Evaluator、Self-Reflection 和经验记忆。Evaluator 提供二值、启发式或模型评价；反思模块基于轨迹与反馈生成教训，下一轮 Actor 读取这些内容。[R4，§3、图 2]

反思保存在文本记忆中，不是对底座权重进行策略梯度更新。“Verbal reinforcement”是论文机制和命名，应与参数 RL 区分。

最需要注意的是：同题后续尝试可以拥有之前的失败反馈。HumanEval 一类最终分数必须按论文的尝试预算、自生成测试与隐藏评测设置理解，不能无条件当成原始单次生成能力。

### 7.6 按瓶颈选择更新路径

| 当前瓶颈 | 优先尝试的思路 | 仍需验证什么 |
|---|---|---|
| 不知道初始指令怎样写 | APE 风格候选搜索 | 评分是否可靠、候选是否跨样本有效 |
| 错误可通过图结构追到上游文本 | TextGrad | 反馈归因是否正确、是否只是强模型传知识 |
| 多模块组合与示例管理困难 | DSPy | 接口、指标和中间轨迹是否正确 |
| 任务间存在不同强项，贪心更新丢失多样性 | GEPA | 选择集过拟合、候选预算与部署成本 |
| 示例冗长，想研究表示与剪枝 | PromptQuine | 不可变约束保护、跨模型稳定性 |
| 同题多轮试错存在可靠反馈 | Reflexion | 与等预算重试比较、反思是否准确 |

这是一张工程起点表。最终选择取决于实测瓶颈，不是方法名字或论文摘要中的最高分。

## 8. 从任务内反思到跨任务记忆：ReasoningBank

### 8.1 保存轨迹与保存策略不是一回事

原始轨迹信息全，但可能很长，包含页面 ID、偶然状态和无用步骤；工作流擅长保留操作路径，却可能难以表达“何时要改变策略”。ReasoningBank 提炼的是带标题、描述和正文的 reasoning strategy。[R7，§3.2、图 2]

例如，从购物网站查“最早订单”的经历中，可以提炼“当前页面常展示最近记录，先确认排序与完整历史范围”。它比固定点击某个旧按钮更容易迁移，但仍应确认网站结构和任务语义。

### 8.2 读取—提取—整合的具体链路

论文实现使用 embedding 相似度检索相关条目，将它们加入系统指令。任务完成后，用 LLM-as-a-judge 根据任务和轨迹判断成功或失败，再分别提取经验。整合部分有意保持简单，主要采用添加条目，而非复杂冲突解决。[R7，pp.4—5、附录 A]

这点很重要：不能只看到“consolidation”就推断系统已经解决删除、矛盾、时效和来源审计。工程实现可能需要这些功能，但它们超出论文原型的具体机制。

### 8.3 无真实标签不等于没有误差

在论文的流式测试学习设置中，系统不能读取未来任务和真实答案，依赖自身轨迹与代理评价。这样更接近一些真实场景，但错误判断可能被写成经验，再影响未来任务。[R7，§3.1—3.2]

因此，学习记忆时最好保留依据、适用条件和验证状态。一次“自评成功”可作为候选线索，不应自动转化成永久事实。评估需要同时看成功率与错误记忆传播。

### 8.4 MaTTS 怎样让更多计算变成更好的经验

MaTTS 将额外轨迹用于对比：并行生成多个尝试，从相同任务的成功和失败中提炼策略；或在单轨迹中迭代修订，利用中间纠正过程形成经验。[R7，§3.3、图 3]

额外计算的两个收益应分开：本题通过概率提高，以及未来任务获得更好记忆。论文也分别讨论随机选取一条轨迹的 Pass@1 与 Best-of-N。最佳候选选择依赖什么可用信号，必须记录；不能将知道真实结果后的最佳值等同于部署选择器能达到的值。

### 8.5 实验数字要读对粒度

R7 Table 3 在 Mind2Web 上分别报告 element accuracy、action F1、step success rate 和完整任务 success rate。这些数值可能相差很大：步骤更准不等于整条任务已经可靠完成。[R7，p.8]

其方法在多个环境与模型上改善指标，支持策略记忆具有经验价值；但网页任务序列、模型、检索和任务划分不同，不能把它与 ACE 的 AppWorld 平均分直接排成统一排行榜。

## 9. 长上下文：容量、计算与有效使用是三个问题

### 9.1 先读懂 Attention 的计算

主讲义第 36—37 页回顾注意力。以单头形式表示：

$$
Q=XW_Q,\quad K=XW_K,\quad V=XW_V,\qquad
\operatorname{Attn}(X)=\operatorname{softmax}(QK^\top/\sqrt{d_k})V.
$$

若 $X$ 有 $T$ 个位置，注意力分数矩阵有 $T\times T$ 个元素。这帮助解释为什么全注意力的长序列计算和存储会变昂贵。这里是标准形式的教学整理，不能把文本抽取出来的公式排版残缺直接当成新的模型定义。

更大窗口说明模型接受更长输入，不保证它能稳定找到、整合和应用所有证据。一次检索命中、跨文档推理和长时间保持状态，也不是同一个能力。

### 9.2 讲义的三条路线

[L2，p.39]

| 路线 | 改变什么 | 优点 | 代价与边界 |
|---|---|---|---|
| 新架构 | 注意力连接和计算方式 | 降低特定成本 | 需要架构、训练和算子配合 |
| 长上下文训练 | 训练分布、长度与位置表示 | 扩展可用长度 | 需要数据、计算及长任务评价 |
| 上下文管理 | 检索、摘要、记忆与信息流 | 可在既有模型外迭代 | 依赖选择和压缩质量 |

滑动窗口减少全局可见范围；全局加局部或动态稀疏改变信息路径。哪些位置可交流、是否需要跨层传播、核实现是否高效，都影响实际表现。理论连接数减少不等于端到端速度按比例提升。[L2，pp.40—42]

### 9.3 长训练数据要包含可用结构

讲义第 43 页列出自然长文档、Agent 轨迹和控制证据位置的合成任务。它们培养的能力不同：长文本可以训练局部语言结构；轨迹包含动作与反馈；合成任务能控制位置和干扰，但可能过于规则。[L2，pp.43—45]

第 44 页的 uniform position interpolation 给出一个具体办法：原训练长度为 $L$、目标长度为 $sL$ 时，把目标位置 $t$ 映射为 $t/s$，即在熟悉的位置范围内使用旋转相位；图上写成 $R(t)\to R(t/s)$，等价于相应频率缩放。这是位置映射，不是替模型补上长距离推理训练；把更多位置挤进原范围还会改变位置分辨率。[L2，p.44]

位置编码扩展也不是简单“把最大长度改大”。位置分布、训练课程、远距离关系和短任务保留都需验证。讲义列举的模型架构表是课程快照，不作为当下产品能力或选型排名。

### 9.4 Needle-in-a-Haystack 为什么不够

在长文本里找一个明确事实，是有价值的受控测试；但业务还可能要求多证据整合、拒绝无依据回答、保持引用、总结、排序和多步动作。第 46 页使用 HELMET 的多任务评测分类，强调不同能力要分别检查。[L2，pp.38、46]

对工程系统，至少区分：证据是否被取到、是否被正确使用、最终答案是否正确、引用是否支持结论、任务状态是否保持。一个“针找到了”的分数不能覆盖这些问题。

## 10. ACE：把上下文从反复改写的字符串变成可维护状态

### 10.1 从 access token 失败看过程性知识

嘉宾讲义用 AppWorld 的工具调用说明：Agent 知道 API，却没有按正确流程取得 access token。把“先登录获取 token”的过程提示放进上下文，能改变后续行为。[G2，pp.2—7]

缺失的是程序性或情境知识，不只是百科事实。这里的实验案例说明上下文可以补充操作规范；并不证明任何认证错误都能通过提示解决。真实工具仍应验证参数与访问权限，模型写出 token 字段不代表它有有效凭据。

### 10.2 Brevity bias 与 Context collapse

ACE 提出两个风险：[G2，pp.9—10；X1，§2.2]

- **Brevity bias**：为了生成简洁、通用的提示，丢掉领域细节和失败模式。
- **Context collapse**：每轮全量重写不断压缩过去经验，使已积累信息突然消失。

X1 第 3 页提供一个 AppWorld 案例：上下文从 18,282 tokens 缩到 122 tokens，相关准确率从 66.7 降至 57.1，低于该案例的无适应基线 63.7。它是定位一种失效模式的具体观察，不意味着所有摘要都会崩溃，也不意味着越长越好。

### 10.3 三种角色分别承担什么责任

[G2，pp.12—21；X1，§3、图 4]

```text
Query + 当前 Playbook
→ Generator 执行任务并产生轨迹
→ Reflector 从结果和轨迹提取可操作经验
→ Curator 组织成局部增量
→ 程序确定性合并到 Playbook
→ 下一个任务读取更新后的状态
```

Generator 负责做任务；Reflector 负责归因和经验提取；Curator 负责组织与更新。它们可以使用同一个模型。职责分离帮助提供不同上下文和输出约束，不自动保证模型之间独立，也不要求部署成三个永久运行的服务。

### 10.4 Playbook 由条目和元数据组成

ACE 条目具有标识、内容，以及 helpful/harmful 等反馈计数。更新只作用于相关条目，保留原有内容，并进行周期性或惰性的去重与整理。[X1，§3.1—3.2]

相较于“请把下面所有经验重新总结一遍”，增量更新减少了无关重写，也方便定位哪条知识造成变化。它仍然需要处理错误条目、冗余、冲突和容量。计数多不等于因果效果大：经常被使用的条目可能只是更常被检索。

**教学数据结构**：

```json
{
  "id": "auth-017",
  "section": "tool-protocol",
  "content": "在需要用户身份的读取前，确认有效会话已建立",
  "scope": ["appworld-like-authenticated-api"],
  "source_runs": ["run-42"],
  "helpful": 3,
  "harmful": 0,
  "version": 2,
  "status": "candidate"
}
```

`scope`、来源轨迹和候选状态是本文为工程可追溯性增加的字段，不声称是 ACE 原始 schema 的完整复刻。

### 10.5 确定性合并保证什么

程序合并可以保证输出结构合法、操作类型受限、旧状态可追溯，避免让 LLM 随意重写所有历史。它不能保证条目内容正确或彼此一致。

假设两个并发增量都修改 `auth-017`，需要携带基线版本，检测冲突并重新评估。若一个条目说“总是重新登录”，另一个说“复用有效会话”，应根据适用条件决定，而非简单以最后写入为准。

合并后的上下文也必须重新运行评估；两个分别有益的增量组合后，可能因为重复提示、指令冲突或长度增加而变坏。

## 11. ACE 的实验：把增益与条件一起读

### 11.1 主模型与对照设置

X1 使用相同的 DeepSeek-V3.1 非 thinking 模式承担 Generator、Reflector、Curator，以减少由更强反馈模型向弱执行模型传知识的混杂。其主要实验包括 AppWorld 及金融等领域任务，区分离线与在线、是否提供真实标签。[X1，§4.1—4.3]

对 AppWorld，指标包括 Task Goal Completion 和 Scenario Goal Completion，分别在 test-normal 与 test-challenge 上报告。表中的 Average 是指定指标的汇总，不能简单称作所有真实业务的任务成功率。

### 11.2 一组可直接回到原表的结果

X1 Table 1（本地 PDF p.7）给出：

| 设置 | GT labels（原表标记） | Average |
|---|---:|---:|
| ReAct 基线 | — | 42.4 |
| 离线 ReAct + ICL | 有 | 46.0 |
| 离线 ReAct + GEPA | 有 | 46.4 |
| 离线 ReAct + ACE | 有 | 59.4 |
| 离线 ReAct + ACE | 无 | 57.2 |
| 在线 ReAct + DC | 无 | 51.9 |
| 在线 ReAct + ACE（含离线 warmup） | 无 | 59.5 |

这些结果支持该实现和设置下 ACE 的有效性。离线与在线的反馈时间和可访问状态不同，不能把它们当成完全相同训练条件的算法排名。

**在线初始化不能省略**：Table 3（p.9）将不含 offline warmup 的在线 ACE 报为 56.1，加入 warmup 后才是 Table 1 的 59.5。因此不能把 59.5 解读为从空白上下文开始、完全只靠当前测试流得到的结果。原表把带 warmup 的在线行也标为 GT Labels ✗，Table 1 的表注将该列解释为适应时 Reflector 能否访问真实标签；但本地 §4.6 只说明先离线适应来初始化上下文，没有单独交代 warmup 的标签权限、使用哪份初始 Playbook。本文保留原表标记，不据此进一步声称“全流程从未用过标签”，也不代作者断言 warmup 用了标签。复现需要补清初始 Playbook 的来源、标签权限与构建成本。[X1，pp.7、9，§4.6、Table 3]

其中基线 42.4 到离线有标签 59.4，是 **17.0 个百分点** 的该项平均分变化；不能把它写成“相对提高 17%”。摘要的跨基线汇总数字也不等于每个任务、每个指标都有同幅度收益。

### 11.3 必须保留的负结果

X1 Table 2（p.8）里，FiNER 无适应为 70.7，在线无 GT labels 的 ACE 为 67.3，即下降 3.4 个百分点；同一行 Formula 仍有提高。论文将此与缺少可靠反馈时的上下文污染联系起来。

这说明“无需标签也能学习”需要任务条件：程序执行反馈可能提供可靠约束，某些领域判断则可能缺少这样的信号。不能因为 Agent 环境中有效，就自动推广到无可执行验证的金融或医疗判断。

### 11.4 嘉宾汇总图必须还原到实验行

G2 p.31 展示 ACE 的 FiNER 78.3、Formula 76.5；在本地论文 Table 2 中，它们分别与“离线、有标签”的 FiNER 和“在线、有标签”的 Formula 数值一致，而离线有标签 Formula 是 85.5。因此不能把汇总图中的两根柱子直接当成同一适应设置下的一组结果，也不能仅凭与某一行不一致就推断论文改了版本。具体比较须回到原表逐行注明离线/在线和标签条件。[X1，Table 2，p.8]

同样，嘉宾展示的生产案例提供实践动机；本文没有独立审计企业实现，不能据此声称在本地业务上已复现收益。[G2，pp.32—34]

### 11.5 长上下文与缓存成本

G2 p.30 报告 91.8% 的输入 token 由缓存提供、输入账单成本减少 82.6%。X1 §4.7（p.10）进一步说明：这是 **OpenAI API、GPT-5.1、evaluation 阶段**的 prompt-caching 研究，降低幅度相对于“把全部原始输入 token 按非缓存价格计费”。它不是主实验 DeepSeek-V3.1 的缓存测量，也不是相对于 GEPA 的端到端总费用降幅。

**计费条件的算术解释**：若缓存输入单价是普通输入的 10%，缓存比例 $h=0.918$ 时，归一化输入费用为 $(1-h)+0.1h=0.1738$，对应约 82.6% 节省。这里的 10% 是与论文这两个舍入数字一致的价格假设，用来解释账单计算；该本地段落没有列价表版本，不能视为当前所有服务的折扣保证。缓存比例本身也不等于相同比例的总算力、显存或延迟节省。

缓存收益依赖前缀稳定性、服务实现、失效规则及价格。输入更长仍会增加某些资源和首轮延迟；频繁修改前缀也可能降低缓存复用。应同时记录原始输入、缓存输入、输出、rollout、适应延迟和最终质量，而不是仅比较总 token 数。[G2，pp.29—31；X1，§4.7]

## 12. 一个贯穿案例：让文档计算 Agent 学会正确处理单位和期间

以下是基于本课机制的教学设计，不是 ACE 或 TextGrad 的实测案例。

### 12.1 定义任务和正确结果

Agent 从两份报告中提取本年度营收，计算同比变化，并提供对应证据。报告可能分别使用元、万元，页面中也可能并列列出本期与上期。

系统模块：

```text
问题解析 → 证据检索 → 字段抽取 → 单位/期间校验 → 计算 → 带引用回答
```

错误不一定来自算术。把上期数当本期、把万元当元、引用不同公司或合并口径，都可能得到一个算术正确但业务错误的答案。

### 12.2 先定位错误，再决定修改什么

假设最终答案错误：

| 证据 | 推测根因 | 候选改进 |
|---|---|---|
| 正确页面从未取回 | 检索查询没有包括期间 | 修改 query 模块，不先改最终回答提示 |
| 页面正确，抽取丢单位 | schema 与提示缺少单位字段 | 修改模块接口并加单位校验 |
| 字段正确，计算错 | 计算步骤或工具使用错误 | 固定计算器路径或局部求解策略 |
| 数字正确，引用错误 | 证据与答案对应关系丢失 | 保留来源 ID 与字段绑定 |
| 一次偶然成功被存经验 | 评价器误判 | 修经验提取条件，撤回条目 |

这种模块归因与 TextGrad/DSPy 的主线相连；用多条轨迹反思和候选池探索，可连接 GEPA；持续保存适用策略，可连接 ReasoningBank/ACE。

### 12.3 将反馈变成有范围的条目

一个过宽的经验是：“所有营收数字都乘一万。”正确的策略应更接近：

> 抽取数值时同时读取对应表格标题与单位；只在来源明确为万元时转换，保存转换前数值、单位和来源位置；计算前确认两个期间与统计口径可比。

这个条目还需要带任务依据、适用范围和验证状态。若来源换成“百万元”，不能继续使用固定倍数。

### 12.4 不可变约束与可学习内容分开

不可变部分可以包括：输出 schema、必须返回证据位置、禁止把未知值默认为零。可优化部分可以是查询策略、抽取示例、失败检查清单及经验条目。

TextGrad 或 GEPA 可以改写某些提示；ACE 可以新增经验；程序验证器检查 schema、单位和期间组合。将所有责任都塞进可改写提示，会使优化器有机会为提高单一分数而删除必要规范。

### 12.5 一个可讨论的最小更新流程

```python
# 教学伪代码：展示职责，不代表某个库的当前 API。
trace = run_agent(task, frozen_system, active_playbook)
feedback = evaluate(trace, evaluator_version)
insights = reflect(trace, feedback, allowed_scope)
delta = curate(insights, base_version=active_playbook.version)
validate_schema_and_invariants(delta)
candidate = merge_into_copy(active_playbook, delta)
result = compare_on_development_tasks(frozen_system, candidate)
if acceptance_rule(result):
    publish_version(candidate)
else:
    keep_as_rejected_candidate(delta, result)
```

这里的 `acceptance_rule` 不能由模型在看到结果后临时改写。最终审计任务的答案和轨迹也不能在这段开发循环里被使用。

## 13. 实验设计：怎样证明系统学会了，而不是多花了钱

### 13.1 先冻结比较条件

记录底座模型与快照、执行模型和反馈模型、工具定义、数据版本、提示起点、每任务预算、缓存设置、失败重试、检索参数、终止规则及评分器版本。

只说“同一个模型”不够：是否使用更强 reflector、是否增加工具调用轮数、是否使用真实标签，都会改变实验含义。

### 13.2 三类问题对应三类实验

| 要验证的命题 | 合适的比较 | 应保留的结果 |
|---|---|---|
| 某段提示更适合任务 | 固定上下文来源，比较旧/新提示 | 每题正确性、格式、长度与成本 |
| 某种经验表示更可迁移 | 等预算比较原始轨迹、反思、结构化条目 | 新任务、跨模板和反例的表现 |
| 在线更新能长期积累 | 相同顺序的任务流，先预测后更新 | 随时间的成功率、记忆变化和错误传播 |

离线测试应冻结最终上下文；在线测试允许按规定更新，但必须描述可使用的反馈、初始状态和任务顺序。两者都需要防止使用未来信息。

### 13.3 针对本课贡献的关键消融

可按研究问题选择：

- 同预算直接强模型重写提示 vs TextGrad 的图式反馈。
- 整体提示重写 vs 只更新相关模块。
- 全量上下文重写 vs 增量条目合并。
- 真实经验 vs 相同长度的无关内容。
- 有真实标签 vs 仅执行反馈 vs 仅模型自评。
- 新经验立即生效 vs 验证后生效。
- 无记忆 vs 等预算增加重试。

目的在于排除替代解释。不是消融项目越多越好，而是每个对照都应对应一个明确声称的收益来源。

### 13.4 指标必须覆盖结果与过程

对文档计算案例，可以记录最终数值正确率、单位和期间正确率、引用支持率、任务完整成功率、工具轮数、输入/输出/缓存 token、适应成本、p50/p95 延迟及人工复核量。

如果只优化最终数值，可能出现“答对但证据错”；如果只优化引用，可能出现“引用正确但没有完成计算”。完整成功应由需求定义，而不是把容易测的指标当作全部目标。

### 13.5 开发分数不会自动代表泛化

不断选择提示、改 rubric、加约束后，开发集已经成为系统设计的一部分。最终独立测试应保留至版本冻结；多次比较还应记录搜索次数与结果波动。

任务同源时，应按文档、实体、时间或模板分组，防止几乎相同的样例同时进入训练与测试。新增成功和新增失败最好逐题配对检查，特别关注高代价错误。

## 14. 成本、故障与工程决策

### 14.1 一轮优化的完整成本

**教学成本模型**：

$$
C_{\rm total}=C_{\rm data}+C_{\rm rollouts}+C_{\rm feedback}+C_{\rm mutation}+C_{\rm validation}+N\cdot C_{\rm deploy}.
$$

APE 可能增加候选执行，TextGrad 增加评价与反向反馈，GEPA 增加候选池及选择验证，ACE 增加反思和条目维护。它们可能减少未来错误和重试，但这个收益需要用实际任务测量。

对低频任务，复杂提示优化可能无法摊销；对重复高频任务，较高的一次性构建成本可能值得。预算不足时，先修复确定性错误和评价器，再增加搜索复杂度。

### 14.2 什么时候改变上下文，什么时候考虑权重

如果模型已经能在充分说明和证据下完成任务，上下文优化可能快速释放已有能力。若它始终无法完成关键推理，反复改提示可能接近上限；需要更强底座、训练、任务分解或工具支持。

若某种稳定长提示在大量调用中反复出现，可在之后研究蒸馏到权重的收益。但这会引入参数训练、泛化、遗忘和新回归问题，不能从本课上下文实验直接推出有效性。[G2，p.35]

### 14.3 故障定位表

| 现象 | 可能原因 | 检查方式 | 对应改进 |
|---|---|---|---|
| 提示越来越长，效果不变 | 反馈泛化、重复添加 | 按条目消融，检查真实使用 | 合并重复，限制无证据更新 |
| 重写后突然退步 | context collapse、约束丢失 | 比较版本差异和条目存留 | 增量更新、必要约束程序化 |
| 格式分数下降 | 输出要求被优化器改写 | 验证 parser 与 prompt 契约 | 固定格式，另测内容质量 |
| 训练集提高，跨文档下降 | 模板或答案泄漏 | 按来源分组测试 | 改数据划分、加适用条件 |
| 无标签在线学习越跑越差 | 自评噪声累积 | 抽查条目来源、回放早期版本 | 降低自动采纳，接入可靠反馈 |
| 长输入账单降低但延迟升高 | 缓存掩盖了部分费用 | 记录缓存命中与关键路径 | 分离费用和延迟目标 |
| 反思指出错误却一直重犯 | 未检索、未加载或规则冲突 | 跟踪条目从命中到动作的链路 | 修读取、位置与控制流 |
| 各候选单独有效，合并后失败 | 指令冲突或预算超限 | 合并后整体评估 | 版本冲突检测、重新选择 |

### 14.4 最低可用落地顺序

先做静态基线和可信评价；再增加少量明确的候选提示；只有在轨迹显示可归因错误时引入文本反馈；多模块项目再建立模块级追踪；出现跨任务重复错误后建立策略记忆；长期信息积累才需要更复杂的增量维护。

这个顺序用于降低诊断难度，不是宣称任何方法天然更高级。实现的复杂度应由已观察到的瓶颈支持。

## 15. 自测、练习与参考答案

### 问题

1. 将一条经验写入数据库，是否说明完成 Context evolution？
2. TextGrad 的 `backward()` 为什么不能当作数值梯度下降？
3. APE 的高似然提示与最高实际任务准确率提示为什么可能不同？
4. DSPy 的签名能否替代业务验证器？
5. GEPA 为什么保存各题表现，而不只保存候选平均分？
6. ReasoningBank 的 consolidation 是否已经解决所有冲突和记忆过期？
7. ACE 使用增量更新后，是否保证新条目正确？
8. “无需 GT labels”为什么在 AppWorld 和 FiNER 中可能产生不同结果？
9. 在线先读取答案更新上下文，再预测当前样本，有什么问题？
10. 每轮看 test 曲线、最后挑最好的轮次，test 还是独立评测吗？

### 参考答案

1. 还需后续正确加载、应用并验证收益；存储状态改变和模型实际输入改变是不同事件。
2. 反馈是自然语言归因，更新由模型产生，没有数值导数及通用下降保证；底座权重通常固定。
3. 分数代理与实际解码不同，有限样本和解码策略也会影响两者关系。
4. 不能。签名描述接口，证据、事实、权限和任务完成还需定义与检验。
5. 互补候选可能分别在不同任务最好，平均分会掩盖有价值的搜索方向。
6. 没有。论文原型主要采用简单追加，复杂冲突、删除与时效属于需要额外处理的工程问题。
7. 不保证。确定性合并保证结构和状态操作可控，语义正确性仍需证据和评估。
8. 前者可用执行反馈，后者某些领域判断缺少同样可靠的约束，错误自评会污染未来上下文。
9. 使用了预测时不可得的信息，混淆学习与测试；应先预测，再使用协议允许的反馈更新。
10. 不是。test 已参与选择；应另留最终隔离审计，或明确报告这种开发用途。

### 两个可实践的研究练习

**练习 A：反馈是否真的比更多尝试有效？** 选一个可自动判分的小任务族，固定总模型调用预算，比较重复采样、APE 风格候选和带文本反馈更新。预先规定 train/dev/test，保存每题结果与调用成本。结果可以为负；重点是判断差异来自反馈、预算还是候选选择。

**练习 B：增量更新能否防止知识丢失？** 构造一个包含逐步增加规则、随后修正旧规则的任务流，对比全量重写和条目增量。除最终正确率外，记录必要旧规则保留、冲突条目、上下文长度与新规则生效时间。此练习无需使用真实隐私数据；所有规则和答案可以人工构造。

- **G2**：Qizheng Zhang，*Agentic Context Engineering*，[本地](slides/context_guest.pdf)，36 页；[原地址](https://mit-mi.github.io/how2ai-course/fall2026/schedule/context_guest.pdf)。机制图与展示实验；汇总图按论文对应实验行还原条件，分别标注。
- **T2**：课程公开 [Textgrad_tutorial.ipynb](tutorials/Textgrad_tutorial.ipynb)；[Colab 原入口](https://colab.research.google.com/drive/1rL24Ydm9yQKRUPoGXHr2-zJumFbBRfvJ)。本文阅读代码与保存输出，未执行远程 API。
- **R1**：Zhou et al.，*Large Language Models Are Human-Level Prompt Engineers*，arXiv:2211.01910v2，[本地](../readings/papers/Large_Language_Models_Are_Human-Level_Prompt_Engineers.pdf)，[原文](https://arxiv.org/abs/2211.01910)。主要使用 §3 的搜索、评分及 §4 评价设置。
- **R2**：Yuksekgonul et al.，*TextGrad: Automatic “Differentiation” via Text*，本地为 arXiv:2406.07496v1，[本地](../readings/papers/TextGrad_Automatic_Differentiation_via_Text.pdf)，[原文](https://arxiv.org/abs/2406.07496)。主要使用 §2、pp.3—6 的计算图、反馈和 TGD，以及 §3 的应用范围。
- **R3**：Khattab et al.，*DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines*，本地为 arXiv:2310.03714v1，[本地](../readings/papers/DSPy_Compiling_Declarative_Language_Model_Calls_into_Self-Improving_Pipelines.pdf)，[原文](https://arxiv.org/abs/2310.03714)。使用 §3—4 的签名、模块、编译和示例选择；API 按论文快照解释。
- **R4**：Shinn et al.，*Reflexion: Language Agents with Verbal Reinforcement Learning*，[本地](../readings/papers/Reflexion_Language_Agents_with_Verbal_Reinforcement_Learning.pdf)，[原文](https://arxiv.org/abs/2303.11366)。使用 §3、图 2 的 Actor—Evaluator—Reflection—Memory，以及 §4 的尝试预算与评价边界。
- **R5**：Wang et al.，*Evolving Prompts In-Context: An Open-ended, Self-replicating Perspective*，arXiv:2506.17930v1，[本地](../readings/papers/Evolving_Prompts_In-Context_An_Open-ended_Self-replicating_Perspective.pdf)，[原文](https://arxiv.org/abs/2506.17930)。使用 §2.3、§3 固定顺序子序列空间和演化搜索；不把可读性结论当成部署建议。
- **R6**：Agrawal et al.，*GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning*，arXiv:2507.19457v2，[本地](../readings/papers/GEPA_Reflective_Prompt_Evolution_Can_Outperform_Reinforcement_Learning.pdf)，[原文](https://arxiv.org/abs/2507.19457)。重点 §2—3、算法 1—2、pp.4—7，区分固定权重、模块更新和 instance-wise Pareto 选择。
- **R7**：Ouyang et al.，*ReasoningBank: Scaling Agent Self-Evolving with Reasoning Memory*，arXiv:2509.25140v2，[本地](../readings/papers/ReasoningBank_Scaling_Agent_Self-Evolving_with_Reasoning_Memory.pdf)，[原文](https://arxiv.org/abs/2509.25140)。重点 §3、§4、图 2—5 和附录 A，区分简单整合、代理评价和 MaTTS。
- **X1**：Zhang et al.，*Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models*，arXiv:2510.04618v3，[本地](references/Agentic_Context_Engineering_Evolving_Contexts_for_Self-Improving_Language_Models.pdf)，[原文](https://arxiv.org/abs/2510.04618)。重点 §2—4；AppWorld Table 1、金融 Table 2、消融与成本分别按原始条件解释。

**最终认识**：Context evolution 的工程价值来自可追溯的反馈、明确的可变对象、可靠的状态更新和独立验证。把一段提示改得更漂亮，只完成了候选生成；让正确经验在合适任务中被使用，并验证它确实改善结果，才完成了学习闭环。
