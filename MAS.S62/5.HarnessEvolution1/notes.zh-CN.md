## 1. 先把 Agent 拆成模型、状态与控制程序

### 1.1 为什么一个更强的模型仍需要 Harness

语言模型在一次调用中接收上下文并生成内容。任务系统还需要决定：读取哪些文件、何时调用工具、把工具输出放在哪里、遇到错误如何恢复、何时完成、哪些经验留到以后。这些决定构成 Harness 的职责。讲义第 6 页把它分成 Context、Control、Action、Evaluation、Evolution 五类。[L4，p.6](slides/lec4%20-%20harness.pdf#page=6)

用一个代码修复任务观察它们：

```text
任务：修复金额解析函数，支持括号表示负数
  Context：需求、代码、测试结果、项目约定
  Control：先复现，再修改，再验证；必要时重新读取依赖
  Action：读取文件、执行测试、修改代码
  Evaluation：测试、静态检查、差异审查
  Evolution：把这次发现的可复用解析边界写入经验或技能
```

这五个方面不是五个必须独立部署的服务。同一段代码可以同时管理上下文与控制流；分解的价值在于让我们知道一次改动改变了哪类行为。以上代码修复场景是教学示例。

### 1.2 两个循环，两个不同的输出

把单次任务执行称为内循环，把修改未来行为的过程称为外循环：

$$
\tau_t, y_t=\operatorname{Solve}(M,H_t,x_t),\qquad
H_{t+1}=\operatorname{Update}(H_t,\tau_t,y_t,f_t).
$$

这里 `M` 是底座模型，`H_t` 是 Harness 及其可持久化状态，`x_t` 是任务，`f_t` 是反馈。内循环产出任务结果，外循环产出未来使用的 Harness 版本。这是便于贯穿本课的教学记号；与 Meta-Harness 的优化目标及 Harness-Evolution 的 solve–evolve 协议相呼应。[MH，§3，pp.4–5](../readings/papers/2603.28052.pdf#page=4)；[HB，§3，pp.3–4](../readings/papers/2605.30621.pdf#page=3)

一次任务失败后直接重试，未必发生持久化学习。只有变化被保留下来，并在后续任务中可被读取或执行，才形成这里讨论的能力积累。反过来，持久化也不能自动证明能力提升：它可能只是保存了一条错误结论。

### 1.3 “模型没变”仍需要记录哪些版本

工程建议至少记录：模型标识、系统提示版本、工具描述与实现版本、技能集合、检索/压缩策略、预算配置、评测器版本。固定模型但同时升级了工具和测试，不能把结果差异全部归给记忆策略。把 `H` 看成一个可追溯的运行版本，会比把它理解为“一段 prompt”更便于归因。

此外要区分**程序版本**与**运行状态**。相同的 Harness 代码可以加载不同记忆库；相同记忆库也可以由不同检索策略读取。因此应同时保存 `harness_revision` 和 `memory_snapshot`，避免只记 Git 提交而遗漏导致行为变化的数据。

## 2. 记忆管理的第一步是区分保存对象

### 2.1 七类内容不能全部写成“经验”

讲义第 7 页列出轨迹、反馈、事实、工具、技能、产物和计划，并提醒 experience 常被含糊地使用。[L4，p.7](slides/lec4%20-%20harness.pdf#page=7)

| 内容 | 示例 | 未来怎样使用 | 主要风险 |
|---|---|---|---|
| 轨迹 | 哪段代码被读过，哪次测试失败 | 回放、归因、技能诱导 | 太长，包含偶然步骤或敏感输出 |
| 反馈 | 某测试失败；人工指出币种错误 | 定位缺陷、选择候选 | 评测器误判、反馈范围过窄 |
| 事实 | 当前仓库使用 Decimal | 检索后作为任务依据 | 版本变化后失效 |
| 工具 | `run_tests(target)` | 执行动作 | 接口变化、副作用越界 |
| 技能 | 如何定位并验证金额解析问题 | 指导或组合多步操作 | 过度专用、隐藏环境依赖 |
| 产物 | 修复补丁、测试报告 | 提交、复用、比较 | 把候选当最终正确结果 |
| 计划 | 先定位解析入口，再检查调用方 | 管理未完成工作 | 状态变化后仍执行旧计划 |

教学上可以使用一个共同的元数据外壳，但不同内容需要不同验证：事实需要来源与时效；程序技能需要接口与执行证据；计划需要完成状态；反馈需要评测器出处。用同一个向量库保存它们并不消除这些差别。

### 2.2 三条分类轴与一条使用链

讲义第 9 页分别问：存什么、怎样表示、存在哪里，并列出 retrieve、adapt、compose、transfer 等复用方式。[L4，p.9](slides/lec4%20-%20harness.pdf#page=9)

- **保存内容**可以是事实、过程、反馈或轨迹。
- **表示**可以是自然语言、结构化记录、可执行程序或参数。
- **位置**可以是当前上下文、外部存储或模型权重。
- **使用方式**决定它怎样影响动作：直接提示、检索、适配、组合，还是训练后隐式调用。

“程序形式的技能”与“长期记忆”可以同时成立；它在外部库存储，检索后作为可执行模块使用。不要用“这是 Memory 还是 Skill”代替更具体的设计问题。

### 2.3 保存成功与使用成功之间有四道关

建议把链路分成：

```text
信息被保存 → 被发现 → 被加载 → 被正确遵循或调用 → 任务收益
```

每个箭头都可能断。相似度高但不适用的技能可能被加载；有效技能可能因描述不清而从未被选中；加载后底座模型也可能遗漏关键步骤。HB 的实验正是把更新能力与从更新中受益的能力分开，并在较弱模型中观察到激活和长程遵循方面的失败。[HB，§4.3，pp.6–8](../readings/papers/2605.30621.pdf#page=6)

因此，“生成了 200 条经验”只能衡量存储活动，不能替代检索质量、实际遵循和任务效果。

## 3. 外部记忆：从可查档案到可执行调度

### 3.1 MemGPT 为什么不等于加一个检索器

讲义先用 MemGPT 说明：模型可以通过函数调用访问不同记忆层级。原论文把工作上下文、消息队列与外部存储结合，并让记忆压力事件和函数执行参与控制流。[L4，pp.10–11](slides/lec4%20-%20harness.pdf#page=10)；[MG，§2，pp.2–4](references/003_MemGPT.pdf#page=2)

区别可以从下面的过程看出：

```text
一次性检索：任务 → 检索若干片段 → 生成答案
可调度记忆：任务 → 查项目 → 发现版本缺失 → 查发布记录
             → 保存当前关键事实 → 继续任务 → 必要时再次检索
```

后者需要知道查询结果能否回答当前问题、是否继续查询、是否将状态写回，不能只用 Top-k 召回率评价。外部存储扩大的是可访问的信息空间；模型一次实际处理的上下文仍然有限。

**工程建议：**将永久历史和当前输入分开保存。摘要中保留来源指针、版本、未决问题和禁止误用的条件；原始材料仍应可回查。否则摘要丢失信息后，系统没有恢复路径。

### 3.2 Mem0：写入之前先比较，而非不断追加

讲义用 Mem0 展示事实提取、关系表示以及 add/update/delete/noop 等操作。[L4，pp.12–13](slides/lec4%20-%20harness.pdf#page=12)；[M0，§2–3](references/001_Mem0.pdf#page=3)

这里要区分论文的两个版本：基础 **Mem0** 先提取候选事实、检索语义相似旧记忆，再让 LLM 选择 ADD/UPDATE/DELETE/NOOP；**Mem0g** 才把实体与关系存为有向标记图。L4 p.12 展示的是图扩展，p.13 展示基础更新链，不能把“采用 Mem0”一概等同于“已用图数据库”。[M0，§2.1–2.2，pp.3–5]

教学案例：昨天保存“项目 A 使用库 v1”；今天出现“迁移计划改用 v2”。若直接覆盖为“项目 A 使用 v2”，会把计划误当已经完成的事实。应先抽取事件性质、主体、有效时间与证据，再决定新增计划、更新事实或保持不变。

一个实用的写入判断顺序是：

1. 新内容在说同一实体、同一属性、同一版本吗？
2. 它是观测、要求、预测还是候选方案？
3. 与旧记录冲突时，是否有更可靠或更晚的生效依据？
4. 更新后能否解释旧记录为什么被替代？

这套顺序是工程建议，不是把论文的提取器改写为确定性事实裁判。关系图能表示实体关联，但错误实体合并同样会扩大污染范围。

### 3.3 用外部记忆时最值得测的三件事

- **召回与定位：**应该读取的证据有没有进入模型当前输入？
- **语义保真：**进入输入后，实体、时间、版本、否定和不确定性是否保持？
- **行为贡献：**读到这些内容后，Agent 是否采用了正确动作？

只做问答准确率会把检索问题和推理问题混在一起。可以加入“直接提供正确证据”的对照：若提供证据仍失败，继续扩充记忆库通常不能解决当前瓶颈。

## 4. MEM1：把压缩和推理放进同一个内部状态

### 4.1 需要解决的不是单次摘要，而是长任务中的状态更新

常规 Agent 不断追加思考、动作和工具返回；长任务中历史增长，成本提高，而且大量旧信息未必仍有用。MEM1 在每一轮生成新的内部状态，并让下一轮只保留当前问题、最新状态及必要的新信息。讲义用多目标问答演示状态如何分项保存、更新和承认无法回答。[L4，pp.14–21](slides/lec4%20-%20harness.pdf#page=14)；[M1，§3，pp.4–6](../readings/papers/2506.15841.pdf#page=4)

教学记号：

$$
s_{t+1},a_t\sim\pi_\theta(\cdot\mid q,s_t,o_t).
$$

`q` 是目标，`s_t` 是内部状态，`o_t` 是新观察。下一轮不再依赖把所有旧观察重新拼接。这里的状态是显式文本/生成内容，不应和模型不可见的神经隐藏状态混为一谈。

金额解析案例可以把状态写成：

```text
目标：括号代表负数；保留原有币种处理
已证实：parse_amount 是入口；现有测试覆盖普通负号
未证实：调用方是否允许字符串里的空格
已失败：只删除括号会把负数变成正数
下一步：加入括号样例，检查 Decimal 的输入归一化
```

状态保留的是下一步决策需要的信息，不是对前面聊天的均匀摘要。

### 4.2 “近似固定状态”不等于任意任务无损压缩

原论文通过状态生成方式和任务训练研究记忆管理；它不证明所有长任务都存在固定大小的充分统计量。[M1，§3–4](../readings/papers/2506.15841.pdf#page=4)

若任务要比较 1000 条互不相关的原始金额，直接丢掉原始输入就可能不可恢复。工程上可以让状态保存一个文件位置或索引，而把原始记录外置；但此时系统已结合了外部存储，不能把全部效率归给内部文本压缩。

还要检查状态究竟省了什么：单步可见上下文较短，不代表总轮数、生成状态的开销、外部读取或总体延迟都下降。若模型每轮重写大量状态，节省历史输入可能被额外输出抵消。

### 4.3 训练时必须让模型看到与 rollout 一致的历史

MEM1 的论文方法不只是一条“请总结”指令。它在策略训练中处理动态可见状态：计算动作概率时，需要屏蔽模型在当时推理中本来不可访问的旧内容；环境输出也不能当作模型生成动作去计算策略损失。论文图 3 与 §3.2 讨论了注意力和信息掩码。[M1，pp.5–6](../readings/papers/2506.15841.pdf#page=5)

若 rollout 丢掉旧历史，但训练概率计算却能看到它，优化的就是另一条条件分布。模型可能在训练时借助“额外记忆”获得虚假的低损失，部署时无法复现。读这类论文时，要同时检查执行状态、训练输入和 loss mask，而不仅是外层算法名称。

### 4.4 哪些反馈能教会模型记住正确内容

MEM1 使用可验证任务结果训练，论文说明并非直接给每段摘要一个“压缩质量奖励”。模型通过任务结果间接学习保留有用信息。[M1，§3–4，pp.4–7](../readings/papers/2506.15841.pdf#page=4)

这意味着奖励覆盖很关键：如果评测只问最终金额，模型可以丢掉币种和来源而不受罚；到了审计任务就会失败。工程建议在代表性任务中加入对实体、来源、版本和未决状态的检查，并把“答案正确但证据链错误”单独统计。奖励可验证也不等于奖励完整。

### 4.5 从讲义的趋势图回到训练与指标条件

L4 p.17 区分直接提示与用奖励训练；论文的主要 MEM1 结果则来自 **Qwen2.5-7B Base 经 PPO 训练**，QA 用 Exact Match 结果奖励，WebShop 用环境奖励，不能归为冻结模型只增加一句摘要提示的收益。论文也用同尺寸 instruct 模型套相同 truncation prompt/rollout 作对照，以区分状态协议与训练效果。[M1，§4—4.2，pp.6–8]

第 18 页图右轴是 **Exact Match Count**，可以超过 1；它反映答对的子问题数量，不是取值在 0—1 的“全部子问题同时答对率”。横轴目标数从 1 增到 16 时，正确数上升也不自动代表单个子问题的正确率上升。训练使用 2-objective 组合，测试扩展到 16-objective，证据支持这种任务组合下的长度迁移；不证明任意任务都可无损压成固定大小状态。工程比较还应保留每子问题准确率、整题完整成功、预算与上下文峰值，避免把不同粒度的“准确率”混在一起。[M1，图 4、Table 1，p.8；附录 A.4.1，p.18]

## 5. Reflexion 与 ExpeL：把反馈变成下一次可用的经验

### 5.1 Reflexion 的改进发生在什么位置

Reflexion 让任务执行者获得环境或评估反馈，再生成自然语言反思，并在后续尝试中读取。它以语言形式保留教训，不能因为名称中有 reinforcement learning 就直接等同于参数梯度更新。[L4，pp.22–23](slides/lec4%20-%20harness.pdf#page=22)；[REF，§3，pp.3–5](../readings/papers/2303.11366.pdf#page=3)

教学示例：

```text
原始反馈：test_parentheses_negative 失败
低质量反思：下次更仔细处理金额
较可用经验：删除括号之前记录负号语义；加入“(12.30) → -12.30”的边界测试
适用范围：本仓库金额字符串解析；不自动用于会计格式之外的括号表达式
```

第二种表达包含动作和触发条件，比自我评价更容易被后续执行采用。但它仍是候选经验，需由实际测试确认；如果原始失败来自测试环境，反思可能把环境问题误写成业务规则。

### 5.2 一次尝试内修正与跨任务复用要分开评价

允许同一道题多次试错，测的是迭代解决能力；把教训带到新题，测的是迁移。若后续尝试已经见过同题测试反馈，就不能把它与一次性作答直接作为同预算泛化比较。

工程上建议报告：首次尝试、允许重试后的成功、总调用成本、后续新任务的收益。对于有副作用的操作，重试也不一定免费；执行记录要说明环境是否重置。

### 5.3 ExpeL 在经验库中增加跨任务抽取

讲义接着用 ExpeL 说明轨迹、经验与反馈可以共同为未来提供上下文。ExpeL 从训练任务的尝试中提取自然语言洞见，并检索成功经历作为示例；它比只保存某一道题的失败反思更强调跨任务积累。[L4，p.24](slides/lec4%20-%20harness.pdf#page=24)；[EXP，§4.1–4.3](references/003_ExpeL.pdf#page=4)

它具体使用两种抽取材料：同一训练任务的失败/成功轨迹对，以及不同任务的成功轨迹组。洞见集可执行 ADD、EDIT、UPVOTE、DOWNVOTE；新洞见计数从 2 开始，编辑/赞同增加、反对减少，降到 0 则移除。评测时把洞见集与按任务相似度检索的成功轨迹一起交给 Agent，在未见任务上单次尝试；训练时的 Reflexion 重试与部署评测应分开计费。这些计数提供整理启发式，并不证明每条洞见的因果贡献。[EXP，§4.1–4.3，p.4、算法 1–3，p.6]

可复用经验应在具体性与泛化之间取舍。“改第 18 行”无法迁移；“任何解析都先删除特殊符号”则可能错误泛化。更稳妥的对象应包含：触发条件、推荐操作、必要前提、例外、验证办法和来源轨迹。

这里有一个容易忽略的工程决定：同一经验的更新方式。若不断追加互相矛盾的规则，模型要在运行时临时裁决。更可控的做法是保存版本、撤销关系和适用范围，把冲突识别前移到知识整理过程。

## 6. CLM：上下文成为模型可以修改的文件

### 6.1 与“在 prompt 里放一个摘要”的差别

CLM 把活动上下文暴露为文件，让模型使用代码或命令编辑；运行机制再把编辑结果同步为模型后续可见上下文。多个 Agent 可以拥有各自的上下文文件。讲义第 27 页展示了进度板、局部删除、上下文角色和压缩函数等行为。[L4，pp.25–27](slides/lec4%20-%20harness.pdf#page=25)；[CLM，§4.1，pp.4–5](../readings/papers/2609.37725.pdf#page=4)

普通摘要机制通常由 Harness 预设何时压缩、压缩哪部分；CLM 扩大了模型可操作的上下文空间。但“模型能编辑”仍需运行程序定义同步时点、格式、不可修改区域和错误恢复。权限边界不会因编辑动作是语言模型提出的就自动消失。

### 6.2 三种学习层次不要混在一起

1. **零样本使用**：已有模型直接用上下文编辑接口完成任务，权重不变。
2. **上下文策略优化**：用自然语言指导或技能优化改变何时压缩、怎样备份，仍可以保持权重不变。
3. **参数学习**：训练模型更有效地使用上下文编辑动作，权重发生变化。

讲义依次展示这三类实验；论文还提出与服务系统相关的缓存复用方案。零样本接口有效，不代表训练增益也来自接口本身；训练比较需与相同训练预算的其他 Harness 对照。[L4，pp.28–30](slides/lec4%20-%20harness.pdf#page=28)；[CLM，§4.2、§5](../readings/papers/2609.37725.pdf#page=6)

参数学习的具体信号也值得拆开：CLM 用 stepwise GRPO，把整条轨迹的任务结果优势分给各次模型调用，并加入 **success-gated efficiency advantage**。只有同组至少两条成功轨迹时，才在成功轨迹内部按 prefix-reuse FLOPs 比较效率；失败轨迹的效率优势为零。这不是按删掉多少 token 或编辑多少次直接奖励，因为那会鼓励删掉重要信息、破坏缓存等投机行为。失败仍由任务结果项约束。[CLM，§4.2、公式 6，p.6]

### 6.3 为什么删了 token，计算反而可能上升

常规前缀缓存依赖相同前缀。若模型修改上下文中间较早的位置，后续部分可能需要重新 prefill。CLM 论文用 prefix-reuse FLOPs 讨论解码、预填充和重新预填充，并研究 Suffix Cache Reuse；这说明应用层 token 统计不能替代服务端计算分析。[CLM，§4.1、§4.3](../readings/papers/2609.37725.pdf#page=5)

教学例子：

- 策略 A 每轮追加 300 个 token，前面大部分保持不变；
- 策略 B 每轮把 8000 个 token 重写成 5000 个，输入更短，但早期前缀变化大。

哪一个便宜，取决于缓存命中、重写的输出、服务端实现和 API 计费。不能只比较最终上下文长度。应记录可见输入、实际计费输入、缓存输入、输出和端到端耗时；能获取服务端算力指标时再报告 FLOPs。

**Suffix Cache Reuse 还改变了计算语义**：若上下文 `A+B+C` 中的 `B` 改成 `B′`，标准前缀复用重算 `B′+C`；SCR 保留存活的 `C` 的旧缓存，只重算新插入/追加的部分。`C` 的缓存仍编码原来的 `B`，论文明确称其为 stale cache states；它不等价于对新文本 `A+B′+C` 完整重算，甚至可能保留已从文本删除的信息。因此不能把 SCR 当成任意 API 都有的无损加速，也不能用文本删除证明缓存中的相关信息已消除。论文主体先按标准 prefix-reuse FLOPs 报告，SCR 的额外节省在 §5.3 单独报告。[CLM，§4.3、图 4，p.6]

### 6.4 讲义图表怎样阅读

第 28 页左侧图使用特定模型、上下文限制和轮数上限比较准确率与计算成本；右侧是数学优化任务的 best-of-run 结果，不同指标有向上或向下的优化方向。它们没有共同的统一“总分”。第 29 页展示指令如何影响压缩时机和备份行为，说明行为可被引导，不能单独当作任务泛化收益证明。[L4，pp.28–29](slides/lec4%20-%20harness.pdf#page=28)

因此，读图先确定横轴计量、模型、任务、预算和结果聚合方式，再判断方法在这些设置下的取舍。某个点位于更优的质量/成本区域，也不保证在你的任务上保持同一关系。

## 7. 工具与技能：行动空间本身也可以积累

### 7.1 工具是动作接口，技能是可复用过程

讲义第 32 页将工具概括为任务中的原子外部动作，技能概括为可复用过程。真实系统中的“原子”取决于接口粒度：一个 `search_products()` 可能内部调用多个 HTTP 接口；它对 Agent 仍可以是一次工具动作。[L4，pp.32–34](slides/lec4%20-%20harness.pdf#page=32)

设计时可分别问：模型需要决定哪些分支？哪些重复操作可以固定？哪些环境条件必须每次重新观察？技能越大，调用次数可能越少，但预条件和异常状态也越多。

### 7.2 CodeAct 为什么能改变调用成本

可执行代码能够组合控制流和数据流：循环处理一批对象、保存中间变量、组合工具、对执行错误进行修正。CodeAct 比较了代码、文本和 JSON 等行动表达；效果与其模型和工具任务设置绑定。[L4，pp.35–36](slides/lec4%20-%20harness.pdf#page=35)；[CA，§2，pp.2–5](references/002_CodeAct.pdf#page=2)

工程推导：若 100 条记录需要相同的确定性归一化，模型生成一次程序后执行，通常比让模型逐条提出动作更易保留一致逻辑。但若程序静默吞掉错误，批量化也会把一个错误同时扩散到 100 条记录。应让输出包含处理数量、拒绝数量、错误样本和结果文件，而不只是返回“完成”。

### 7.3 Toolformer 和 ToolLLM 修改的是哪一层

讲义用这两项研究说明工具使用能力可以通过数据构造和模型训练获得。Toolformer 筛选那些帮助后续文本预测的 API 调用，再进行语言模型训练；ToolLLM 包含 API 检索、指令和多步调用路径数据，并训练 ToolLLaMA。[L4，pp.37–38](slides/lec4%20-%20harness.pdf#page=37)；[TF，§2，pp.3–4](../readings/papers/2302.04761.pdf#page=3)；[TL，§2–3，pp.3–7](../readings/papers/2307.16789.pdf#page=3)

这与给冻结模型新增一个 API 描述是不同干预。一个工具可被服务器发现，不等于模型已学会适时调用；一个模型会输出合法参数，也不代表当前服务器能执行。下周将把模型能力、接口设计和运行时职责放回同一执行链。

### 7.4 AWM、ASI 与 PolySkill 对应三个不同问题

| 方法 | 主要处理的问题 | 对工程师有用的观察 |
|---|---|---|
| AWM | 从经历中抽取可复用工作流，并提供给后续任务 | 存在工作流与成功检索之间还有选择过程 |
| ASI | 诱导并验证程序形式的技能，再纳入动作空间 | 技能的真实调用和执行证据是关键 |
| PolySkill | 把技能的抽象目标与网站/环境具体实现分开 | 可复用接口不应隐藏环境适配条件 |

讲义第 40–43 页连接这三种方向。它们不构成跨论文同环境的排行榜；训练数据、任务、模型和验证过程各不相同。[L4，pp.40–43](slides/lec4%20-%20harness.pdf#page=40)；[AWM，§2–3](references/004_Agent_Workflow_Memory_AWM.pdf#page=3)；[ASI，§2–3](references/005_Agent_Skill_Induction_ASI.pdf#page=3)；[PS，§3](references/013_PolySkill.pdf#page=4)

三者的操作链也不同。AWM 将轨迹中的固定实例值抽象为变量，诱导自然语言工作流，后续由 Agent 读工作流再选择底层动作；它提供过程提示，并不会自动把这些文字变成一次可执行调用。ASI 则把被判为成功的轨迹清理后诱导为 Python 函数，重写原轨迹以强制使用新技能，并截掉最后一次技能调用之后的旧原始动作，让 Agent 重新完成结尾，避免照搬旧答案导致伪成功。入库检查同时要求任务被判成功、至少调用新技能、调用确实改变环境。[AWM，§2，pp.3–4；ASI，§2.2–2.3，pp.3–4]

L4 p.42 把成功和失败轨迹一起概括为来源，但 AWM 原论文的在线算法只对 **LLM 评价为成功** 的经历做诱导（图 2、§2.3）；不能据此声称它已经显式从失败轨迹提炼纠错规则。这里也只是代理评价成功，仍可能误收错误工作流。若工程实现要利用失败，应另定可复用片段筛选与验证规则，而不要把整条失败动作序列直接入库。[AWM，pp.3–4]

PolySkill 在这个验证链上增加领域抽象父类与网站子类：跨网站保留的是共同方法签名和组合逻辑，点击与表单定位仍由当前网站实现。文本工作流容易临场适配，但每一步还需模型决策；程序技能减少重复决策，却可能因页面变化而失效；多态把适配边界显式放到实现层。三者的取舍应围绕真实调用成功、前置条件和环境变化测试。[PS，§3.2–3.3，pp.5–6；L4，pp.40–43]

教学例子：金额解析技能可以定义 `parse_amount(text, convention)`，但它应明确支持的格式、币种处理和小数规则。遇到新网站时重新实现抓取适配器，不能仅因函数名相同就假设数据含义相同。

### 7.5 Voyager 把技能库与主动探索连接起来

Voyager 将自动课程、可执行技能库和交互式程序修正组合在 Minecraft 环境中。新任务推动技能生成，执行反馈和验证帮助修改程序，已验证程序以描述为检索入口加入技能库，未来任务可组合复用。[L4，pp.44–45](slides/lec4%20-%20harness.pdf#page=44)；[V，§2，pp.3–5](../readings/papers/2305.16291.pdf#page=3)

它提示我们：当现有任务无法产生新能力的练习机会时，可以主动选择任务来积累技能。但课程生成器也会引入分布选择偏差。若 Agent 只选择容易成功的任务，技能数量增长并不意味着解决真实业务任务的能力增长。应同时报告课程探索覆盖和预先定义目标任务的迁移表现。

## 8. RLM 与嘉宾视角：把长问题重组为局部可解的问题

### 8.1 输入在外部环境中，而不是全塞入一次调用

RLM 将长输入存为外部环境中的变量，让模型用程序检查、切片、构造子问题，并在程序中发起递归模型调用。它的关键差异包括：原始长输入不必全进入模型窗口、子调用可由程序批量构造、中间结果和最终输出可以保存在符号状态中。[RLM，§2、算法 1–2，pp.3–4](../readings/papers/2512.24601.pdf#page=3)

教学例子：分析大型代码库时，根调用只看到任务和索引；程序按模块读取实现，用子调用分析特定接口，把发现存成结构化记录，再汇总交叉依赖。这个过程改变了计算组织方式，没有让单次 Transformer 注意力无损扩展到无限长度。

RLM 也不能简单等同于“加一个 subagent 工具”。若根模型需要逐条用自然语言发出子调用，调用规模和输出长度仍受它自己的窗口限制。论文算法对照正是在强调程序化递归和外部符号状态的差别。

### 8.2 “局部分布内”应怎样理解

嘉宾第 15–17 页从组合泛化角度展示：把整体很长、训练时未见的序列拆成局部较熟悉的模型输入，可能降低单次调用承担的泛化压力。[G，pp.15–17](slides/harness_guest.pdf#page=15)

这是一个有用的研究视角。它不意味着每个局部答案正确时，整体结果必然正确。工程上至少还有三种组合故障：

- 子任务定义丢掉全局约束；
- 各子答案使用不同的单位、版本或实体；
- 汇总阶段把不确定结论当作确定事实。

所以分解接口要明确输入范围、输出格式、证据位置、未决问题，以及与其他子任务的依赖。局部调用被简化的同时，全局一致性的责任转移到了分解和整合机制。

### 8.3 不把嘉宾的研究问题当成确定性结论

第 20–23 页讨论 Harness 如何影响规模化、模型形状与输入输出表示，并提出模型和 Harness 协同设计的问题。第 19 页是不同项目和生态实践的展示拼图；不能根据这些截图推导统一性能增益。[G，pp.19–23](slides/harness_guest.pdf#page=19)

“长上下文应由架构还是程序解决”并非一个只有二选一答案的问题。工程上应比较：直接长上下文、检索、压缩、外部文件、递归调用、适当的模型训练。最优组合依赖任务的证据密度、相互依赖、预算和验证能力。

## 9. 从修改模块到修改整个 Harness

### 9.1 Meta-Harness：诊断材料也是搜索空间的一部分

Meta-Harness 让 proposer 读取保存于文件系统中的候选代码、执行轨迹和评分，再提出新 Harness。候选通过接口检查后执行评估，全部结果继续进入历史文件系统。它保留大量可选择访问的反馈，外循环可修改提示、检索、记忆和完整程序结构。[L4，pp.46–50](slides/lec4%20-%20harness.pdf#page=46)；[MH，§3，pp.4–5](../readings/papers/2603.28052.pdf#page=4)

第 46 页的“约 10M token 反馈”应理解为某次评估所生成的诊断材料规模，不是要求每次把 10M token 全放进 proposer 输入。文件系统的作用是保留可追溯历史并支持选择性读取。工程上仍需记录 proposer 实际读了多少、花了多少，以及这些成本是否抵得上候选收益。

论文在在线文本分类、数学推理和 Coding Agent 等设置中报告结果；各设置的任务、底座模型、搜索预算和指标不同。跨任务结果说明搜索机制具有适用范围，但不能当作一个统一“Meta-Harness 提升率”。[MH，§4，pp.6–9](../readings/papers/2603.28052.pdf#page=6)

### 9.2 DGM：保留多样候选，允许跨过暂时无益的中间状态

DGM 维护不断增长的 Agent 档案，从档案选择父代，让它修改自己的代码，再用任务表现作经验检验。保留多样中间产物有助于探索不同改进路线；这与每次只接受当前最优版本的贪心更新不同。[DGM，§3，pp.4–6](../readings/papers/2505.22954.pdf#page=4)

档案也有准入门槛：新 Agent 必须能编译并保留修改代码库的基本能力，才能继续作为父代；论文还使用分阶段任务评测控制搜索成本。它不是把所有损坏候选都加入库。外部的档案维护与父代选择循环在本工作中固定，不属于 Agent 可改写的自身代码；因此“自修改”并非所有层级都无限开放。[DGM，§3、§4.2，pp.4–6]

它把“证明修改一定有益”放宽为实验检验，不能据此得到任意未来任务都改善的保证。多次在相同开发集上筛选候选会产生选择偏差；档案越大，越需要独立评测和搜索预算透明度。

工程建议将档案中的**搜索候选**和真正对用户生效的**发布版本**分开。一个对探索有价值的父代，可以保留在档案中而不立即替换生产版本；这不妨碍它成为未来组合改进的起点。

### 9.3 Continual Harness：环境不重置时，怎样在线演化

Continual Harness 在持续执行过程中周期性读取近期轨迹，更新系统提示、子 Agent、技能和记忆。其基本适配循环可以冻结模型；扩展的共同学习流程再对模型进行训练。论文图 2 和 §3 明确区分了两层更新。[CH，§2–3，pp.3–5](../readings/papers/2605.09998.pdf#page=3)

不重置环境更接近真实长任务，但评估变难：后半程进步可能来自环境推进、已解决的前置任务或状态更容易，而不全是新 Harness 的贡献。应保留检查点，在可恢复的相同环境状态比较版本；无法恢复时，至少使用多个运行、里程碑和更新前后轨迹诊断，并承认归因范围。

### 9.4 Harness 更新能力与 Harness 受益能力是两件事

HB 交叉变化 task-solving agent 与 evolver，并定义更新者对锚定 Agent 集合的平均增益，以及执行者从锚定更新者集合中获得的最大增益。论文中的模式是：更新质量不随基础解题能力简单单调增长，受益程度也依赖执行者的激活和遵循能力。[HB，§3–4，pp.3–8](../readings/papers/2605.30621.pdf#page=3)

这里的交叉配对不等于把一份固定技能无条件移植给所有模型：最终 Harness 记为 $H_T^{(f,e)}$，由执行者 $f$ 的轨迹和更新者 $e$ 共同产生。论文实测采用 **in-situ** 协议：先用当前 Harness 解当前批次并评分，再用其证据更新，最后汇总任务流分数。这与另留独立任务、冻结最终 Harness 后再测的工程泛化实验不同；后者仍需另做，不能把其收益直接归给论文已验证。[HB，§3.3、§4.1，pp.4–5]

这项研究直接改变工程排障顺序：

```text
没有收益
  ├── 更新内容本身无效？换执行者也没帮助
  ├── 有效但没被发现/加载？强制提供后改善
  └── 已加载但不会稳定使用？轨迹中出现遵循衰减
```

不要根据“更大的模型一定更会写技能”或“更强执行者一定增益最大”安排全部预算。该论文的具体发现仍以其模型、三类基准和演化预算为边界。

## 10. 怎样选择改进路径

下面是从本课机制出发的工程判断表，不是论文验证过的通用决策器。

| 观察到的瓶颈 | 先尝试的改进 | 必须检查的条件 | 暂不应直接推断 |
|---|---|---|---|
| 重要历史不可见 | 外部记忆与准确检索 | 原文可回查、实体/版本一致 | 需要训练更大模型 |
| 历史过长且重复 | 状态整理、压缩或 CLM | 保真、缓存、总调用开销 | 上下文更短必然更便宜 |
| 同类错误反复出现 | 结构化反馈与反思经验 | 错误归因可靠、后续确实加载 | 多写几条规则就会解决 |
| 多步程序重复 | 可验证的程序技能 | 前置条件、接口、失败退出 | 技能数越多越强 |
| 局部任务可分解但整体太长 | RLM 式外置与递归 | 子问题可验证、结果可组合 | 多个调用自动保持全局一致 |
| 多模块共同造成失败 | Meta-Harness 式程序搜索 | 轨迹、受控评估、可回滚 | 一次大改可以清晰归因 |
| 环境不能免费重置 | 在线演化 | 状态检查点、持续成本、归因设计 | 时间越久说明学习越好 |

一个适合小团队的顺序是：先建立强而简单的基线与完整轨迹，再修复可定位的上下文或接口问题，之后增加可验证的技能/记忆更新，最后再开放更大的程序搜索空间。这个顺序的依据是缩小诊断范围和减少混杂，不是限制研究探索。

## 11. 用统一目标连接质量、成本与迁移

### 11.1 Harness 优化目标不应只有开发集成功率

Meta-Harness 论文明确讨论期望奖励和多目标 Pareto 前沿。工程中可以把候选目标写成约束优化：[MH，§3，p.4](../readings/papers/2603.28052.pdf#page=4)

$$
\max_H\ \mathbb E_{x\sim D_{\rm target}}[Q(M,H,x)]
\quad\text{s.t.}\quad
\mathbb E[C]\le B,\quad P(\text{严重回归})\le\epsilon.
$$

这是教学形式。`Q`、成本和回归阈值必须由任务定义，不应给出脱离业务的默认权重。若使用加权和，应说明质量损失能否真的由省下的成本补偿；很多场景更适合硬约束和前沿比较。

### 11.2 更新成本何时能被摊销

假设一次演化搜索花费 `C_update`，未来每任务平均节省 `Δc`。只考虑费用且 `Δc>0` 时，简单盈亏平衡点是：

$$
N_{\rm break-even}=\frac{C_{\rm update}}{\Delta c}.
$$

若搜索花 120 个预算单位、每任务省 0.03，则要约 4000 个后续任务摊销；这是算术教学例子。若任务频繁变更、模型升级使技能过时或更新增加维护成本，这个估算会过于乐观。

质量改善不能随意换算为钱。应分别给出质量、费用和延迟，再由使用场景决定可接受的取舍。

### 11.3 迁移至少有三种含义

- **同分布新实例：**没有见过的新金额、文档或代码问题。
- **结构变化：**新仓库、新 API、新任务长度或不同错误组合。
- **执行者变化：**同一技能换到另一模型或 Harness。

这三类迁移应分别测。一个经验在原仓库中有效，并不说明它能跨网站工作；跨模型可加载，也不证明跨模型同等受益。HB 和 PolySkill 从不同方面展示了为何“可保存、可移植、可有效复用”必须分开判断。[HB，§4](../readings/papers/2605.30621.pdf#page=5)；[PS，§3–4](references/013_PolySkill.pdf#page=4)

## 12. 最小实现：把记忆更新当成可审查的状态变更

本节是教学设计，不声称实现了 MEM1、CLM 或 Meta-Harness 的完整系统。目标是展示：论文中的“写回状态”在工程里需要哪些边界。

### 12.1 经验对象应能回答为什么存在、何时适用

```json
{
  "id": "amount-parentheses-v1",
  "kind": "procedure",
  "scope": "repo-A@revision-17",
  "trigger": "修改金额字符串解析函数",
  "preconditions": ["输入采用会计括号负数格式"],
  "procedure": ["先识别符号语义", "再归一化字符", "使用Decimal解析"],
  "exceptions": ["普通表达式括号不能直接当作负数"],
  "evidence": ["run-42/test_parentheses_negative"],
  "status": "candidate",
  "supersedes": null,
  "created_by": "evolver-model-and-prompt-revision"
}
```

字段不应只是为了数据库整齐。`scope` 约束复用范围，`evidence` 支持回查，`status` 防止候选立刻获得权威，`supersedes` 保留撤回链路。文本描述“我认为这次成功了”不能代替可定位的执行证据。

### 12.2 读、写、发布应是三个操作

- **读取**返回内容、来源、范围和状态；过期记录可以返回警告或被过滤。
- **写入候选**产生一个待评估差异，不直接改写全局当前版本。
- **发布**要求接口校验、代表性任务评估和回归检查，并产生新的不可混淆版本。

对可执行技能还要记录输入输出契约、依赖、超时、允许的资源、已验证环境和已知失败。对纯事实，则更关注主体、时效和证据。把所有条目都用同一套字符串追加操作发布，会让后续诊断非常困难。

### 12.3 用版本比较避免覆盖别人的新状态

假设两个更新者都从记忆版本 5 开始：A 修复币种规则并产生版本 6；B 随后把自己的版本 5 全量写回，就会覆盖 A 的修复。最小保护是乐观版本校验：写入时声明 `base_revision`，若当前版本已变化，重新读取和合并。

```python
candidate = propose(snapshot_revision=5, evidence=trace)
validate_interface(candidate)
if store.revision != candidate.base_revision:
    reject_and_rebase(candidate)
else:
    evaluate_then_commit(candidate)
```

这段伪代码没有处理分布式一致性、长事务或跨存储原子性。它只说明：模型提出的更新也必须服从状态管理规则。若系统把“Agent 自主”理解成允许无条件覆盖共享文件，多 Agent 或在线演化会进一步放大丢失更新的问题。

### 12.4 可运行样例验证了什么

本目录提供 [versioned_memory.py](examples/versioned_memory.py)，只依赖 Python 标准库。它演示限定 scope 的事实写入、旧版本提案拒绝、未观测声明拒绝和回滚。整理时已运行：

```bash
python3 MAS.S62/5.HarnessEvolution1/examples/versioned_memory.py
```

输出为 `PASS: observed scoped write, stale/scope/unobserved rejection, rollback`。它验证的是本地状态规则；`evidence` 字段在样例中仍是字符串引用，程序不判断证据真假，更不验证大模型能否生成高质量经验。

真实系统必须另外验证证据是否存在、是否与任务和字段相关、是否由可信评测产生。这个例子的价值是把“状态规则正确”和“学习内容正确”分开。

## 13. 贯穿案例：一个金额解析 Agent 怎样改进

以下全部为教学案例；没有对应真实业务运行结果。

### 13.1 基线与第一次失败

任务是修复 `parse_amount("(12.30)")`，同时保持币种、普通负号和空值的既有语义。基线模型第一次只删括号，输出 `12.30`；可见测试指出符号错误。保存的轨迹应包括任务、读过的函数、补丁、测试命令、退出码和失败断言。

如果日志只写“修复失败”，外循环无法区分：没有找到入口、不了解括号规则、修改范围过大、测试根本没运行。诊断质量受观测材料限制，不能靠更长的反思提示弥补缺失的执行证据。

### 13.2 从失败中形成可检验的候选

更新者提出：增加格式识别步骤和边界测试，暂不改全局解析算法。这个候选的内容应可审查：

```text
变化：修改金额解析技能的预处理顺序
依据：括号负数断言；现有Decimal处理代码
预期作用：避免删除格式符号时丢失负号语义
潜在退化：把普通括号表达式或带注释文本误识别为金额
验证：新增括号、负号、空值、币种、非法输入组合
```

这里把“修改什么”与“为什么可能有用”同时记录。若更新者顺便换模型、换工具和重写全部 prompt，就失去一个容易解释的实验单位。

### 13.3 先证明确实被使用，再讨论任务收益

下一次执行可以记录以下事件：候选技能是否被检索、哪个版本被加载、是否执行了先识别符号的步骤、是否补充了对应测试。若任务仍失败，要先看失败发生在加载前还是执行后。

一个很有诊断价值的对照是直接把技能放进上下文。若强制提供有效而自动检索无效，瓶颈很可能在触发/选择；若两者都无效，则可能是内容不适用、表达不可执行、底座能力不足或评测错误。

这与 HB 区分更新者和受益者的做法相呼应，但上述具体诊断流程是工程设计。[HB，§4.3，pp.6–8](../readings/papers/2605.30621.pdf#page=6)

### 13.4 用新实例判断经验是否泛化

开发集的 `(12.30)` 成功只是必要检查。独立任务可包含空格、不同币种前缀、零、负零、空字符串、非金额括号，以及仓库中允许的其他语法。测试必须从真实需求得到，不能为证明更新有用而改变标准。

同时检查未涉及的正常输入。新技能若提高括号任务成功率却破坏大量原有任务，不能只报告目标子集。记录新旧版本逐任务结果，才能看见收益与退化各来自哪里。

### 13.5 当环境变化时怎样处理旧经验

若新仓库把括号用于解释性注释，旧技能应因 scope 不匹配被排除，或先进入适配流程。保留旧技能可以帮助推理，但不能把它直接作为当前规则。

一条经验有三种合理结局：在原范围继续有效；被新版本替代；在更广分布上证据不足而退回候选。持续改进应允许淘汰，而不是只有追加。否则经验库会逐渐变成互相矛盾的指令集合。

## 14. 评测：从“演化发生了”到“独立任务改善了”

### 14.1 先建立数据和权限分工

建议将任务分为用于更新的经验集、用于候选选择的验证集和只用于最终报告的独立测试集。更新者能够看到哪些标签、轨迹和测试结果要明确记录。若候选选择反复读取了测试结果，原来的测试集就已参与开发。

外循环可以生成更多任务，但生成器和评估器不应共享到足以泄漏答案的材料。特别是技能库和检索库：它们可能把任务答案以“经验”的名义带入评测输入。检查应覆盖路径、常量、文件名、目标实例和可见测试细节。

### 14.2 最小有用的对照组

| 组别 | 保持不变 | 唯一主要变化 | 回答的问题 |
|---|---|---|---|
| A 固定 Harness | 模型、工具、预算、任务 | 无更新 | 原始基线是什么 |
| B 只增加重试 | 同 A | 更多内循环尝试 | 收益是否只是更多计算 |
| C 经验写回 | 同 A | 跨任务记忆/技能 | 持久化内容是否有贡献 |
| D 强制正确加载 | 同 C | 绕过自动选择 | 瓶颈是否在发现与激活 |
| E 完整更新 | 相同模型与评测标准 | 多组件更新 | 完整系统能取得什么结果 |

预算可以做两种对齐：同任务最大费用，或同墙钟时间。结果不必相同；应分别说明。在线模式还需要按任务顺序和环境检查点配对，不能只比较时间轴前后两个不同难度阶段。

### 14.3 哪些指标值得保留

**结果指标：**任务成功、关键约束满足、严重回归、拒绝或无法完成的比例。  
**过程指标：**技能发现/加载/遵循、记忆冲突、压缩丢失、无效工具调用、错误恢复。  
**成本指标：**更新搜索与任务执行分别计费，输入/缓存/输出 token、工具费用、总延迟、失败重试。  
**迁移指标：**新任务、新环境、任务长度、执行模型变化下的表现。

这些指标不应机械加成一个分数。过程指标帮助诊断，最终收益仍需要任务结果；一个系统可以高效加载错误技能，也可以偶然在没有技能的情况下成功。

### 14.4 结果波动与搜索选择偏差

模型采样、工具服务和任务顺序都可能造成波动。至少记录重复运行、样本量、随机种子或采样设置、未完成任务和重试规则。报告单个最好候选时还要说明总共尝试了多少候选、挑选依据是什么。

如果测试集中只有 5 个任务，成功从 4 个变成 5 个，很难据此宣称普遍可靠提升。下一步应扩大代表性任务、检查逐任务差异和新增失败模式，而不是先把涨幅套用到生产规模。

### 14.5 成本归因与 HarnessTax 的启发

课程指定 HarnessTax，教程也用它提示：相同模型在不同 Harness 中可能质量相近而费用不同。本文把它作为成本比较的动机，不根据单一案例推导某套 Harness 永远更贵。[课表阅读入口](https://arena.ai/blog/coding-agents-harness-tax)；[下周教程 p.4](../6.HarnessEvolution2/tutorials/harness%20engineering%20tutorial.pdf#page=4)

本地归档文章的具体设置是：7 个模型 × 3 个 Harness，共 21 组；每个基准抽取 30 个任务，每题运行 3 次，使用各 Harness 自己的 high-effort 配置与 100-turn 上限，按固定的 2026-09-01 直接 API 价表估算费用。文章也说明 turn 和 effort 的含义随 Harness 而异，因此这属于受控工作负载比较，不是严格相等的推理计算量，也不足以证明所有任务上的质量等价。读其成本结论时应保留任务样本、价格日期和配置条件。[HarnessTax，本地归档](readings/008_HarnessTax_How_Much_Does_the_Harness_Matter_for_Coding_Agents_arena_ai_blog_coding_agents_harness_tax_c2dd74e6.html)

工程实验至少拆分：新增输入、额外模型轮数、子 Agent、工具/测试执行、搜索候选评估、日志存储和在线适配。只有总费用，没有分项，就无法知道改进来自少走弯路还是转移了成本。

## 15. 故障诊断：更新无效时先找断点

| 现象 | 优先假设 | 要查的证据 | 下一步实验 |
|---|---|---|---|
| 经验库持续增长，成绩不变 | 内容低价值或根本没加载 | 检索与加载事件、独立任务 | 强制提供高质量经验对照 |
| 加载后成绩下降 | 过时/冲突/过度具体规则 | scope、来源、版本、适用任务 | 分离内容质量与触发策略 |
| 压缩后突然忘记目标 | 目标/约束/未决项丢失 | 压缩前后差异、后续错误 | 强制保留关键字段并回放 |
| 上下文更短但费用增加 | 缓存失效、状态输出或轮数增加 | cache hit、输入输出、调用树 | 固定任务比较追加与重写 |
| 同题重试很好，新题退化 | 记忆答案或评测过拟合 | 更新集与测试重合、技能常量 | 新任务/新实体评测 |
| 相同代码结果不同 | 隐藏状态、环境、模型版本差异 | 记忆快照、依赖和执行日志 | 从同一检查点重跑 |
| 强模型写的技能弱模型用不了 | 激活或执行能力不匹配 | 强制加载、逐步骤遵循 | 缩短程序、明确接口、换执行者 |
| 更新覆盖其他人的改进 | 缺乏版本比较和合并 | base_revision、提交顺序 | 乐观锁与冲突重放 |
| 候选修改了评测器 | 优化目标边界混淆 | 文件差异、可写路径 | 隔离评测器并重测 |

这张表中的诊断是假设，不是仅凭现象就作出的归因。完整流程是：提出机制解释，找能区分竞争假设的观测，再做最小干预。反思文本本身也要作为待验证假设，不能当作系统已经“理解了失败”的证据。

## 16. 自测与参考答案

### 问题

1. 一个 Agent 保存了全部原始轨迹，为何仍可能没有学习？
2. MEM1 为什么需要训练时的注意力/信息掩码，而不仅是 rollout 时删历史？
3. CLM 的上下文更短，为何可能增加服务器计算？
4. RLM 与“加一个子 Agent 工具”最重要的差别是什么？
5. 如果 evolver A 写出的技能对模型 B 有用，对模型 C 无用，应先检查什么？
6. DGM 为什么保留暂时不是最优的候选？这是否意味着应该立即发布它们？
7. 某更新把开发集成功率提高了 8 个百分点，独立任务未改善，该怎么解释？
8. 本文的可运行样例证明了哪些东西，没有证明哪些东西？

### 参考答案

1. 还需要从轨迹中发现有用信息，使之被未来任务检索、加载和正确使用；保存量不等于收益。
2. 训练时条件分布必须匹配执行时的可见信息；旧内容泄漏会让训练优化另一个问题，环境 token 也不是策略动作。
3. 中间编辑可能破坏前缀复用，且重写状态本身有输出和额外调用成本。
4. 长输入外置、程序化构造和递归调用、符号化中间结果是关键；仅多一个自然语言委托动作并不提供全部性质。
5. 先分开内容适用性、发现/激活、加载后遵循和执行能力，不能直接断言技能质量差或模型 C 一定更弱。
6. 多样中间状态可成为未来改进的起点；搜索档案与对用户生效版本承担不同角色。
7. 可能开发集过拟合、任务分布不同、样本不足或新增退化；需要逐任务证据和受控对照，不能宣称普遍进化。
8. 只验证版本、scope、候选状态和回滚规则；没有验证事实真实性、LLM经验生成、检索或业务收益。

## 17. 本课总结与跨课联系

本课提供了一条逐步扩大的可优化对象链：**内部状态 → 上下文 → 可复用技能 → 整个 Harness**。每扩大一步，表达能力和搜索空间都变大，诊断、验证和版本管理责任也随之增加。

下一周会把这些抽象落到 Agent Loop、工具契约、Skill/MCP/Hook 等机制，以及规划、协作和多 Agent 演化。接下来的模型演化则改变参数：那时需要进一步问，收益来自权重、外部状态还是两者的交互。

对工程师最有价值的判断是：先确定瓶颈发生在哪一层，保留足以定位原因的轨迹，再用受控干预证明候选改善了独立任务。持续写入与持续修改可以是学习过程的一部分，可靠改进需要额外的收益证据。

### 附录 B｜术语速查

| 术语 | 本文含义 | 不应混同 |
|---|---|---|
| Harness | 组织模型上下文、动作和运行流程的程序及相关配置 | 单一 system prompt |
| State | 当前决策所依赖的可持久化信息 | 任何一段历史聊天 |
| Memory | 跨当前上下文保存并可再次使用的信息 | 信息已存在即已被模型看到 |
| Skill | 可复用的程序或过程性知识 | 一次任务的具体答案 |
| Evolution | 根据执行证据修改未来行为的机制 | 文件数量或更新次数 |
| Proposer/Evolver | 诊断经验并提出候选变更的角色 | 一定比执行模型更大的模型 |
| Benefit | 执行者使用更新 Harness 后相对基线的任务收益；是否独立测试由协议决定 | 能产出更新的能力 |
| Pareto frontier | 在既定指标上不被其他候选同时支配的集合 | 通用最优架构 |
| Reset-free | 执行环境在适配过程中持续推进 | 无需环境状态和版本追溯 |
