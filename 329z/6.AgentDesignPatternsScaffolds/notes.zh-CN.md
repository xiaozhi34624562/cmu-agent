第4—5页提醒设计模式需要适配具体环境，而不是可以直接照搬的完整产品。阅读时应为每个模式写出它改变的变量、信息依赖、反馈条件和失败代价。

一个模型会调用工具，并不意味着它已经具备完整的任务控制。你仍需决定哪些步骤固定、哪些由模型选择、观察结果怎样影响下一步、失败后留下什么、上下文不足时保留什么。本课把这些设计拆开，再解释 ReAct、Reflexion、CodeAct 和上下文管理为何可以组合，却不能相互替代。

贯穿案例仍是公司的内部助手，但任务升级为：“从项目往来邮件中确认下周评审安排，核对日历冲突，整理待确认事项并准备邀请草稿。”它可能要追踪多封修改邮件、辨别旧安排和当前安排、查询多人日历，并在信息不足时停止。邮件文本不是执行命令，助手生成的计划也不是外部事实。

## 1. Workflow 和 Agent 的区别在谁决定下一步

Anthropic 的指定阅读区分两种架构：workflow 由预定义代码路径组织模型和工具，agent 由模型动态控制过程和工具使用。两者都可以使用 LLM，也都可以包含循环与工具；关键在于运行时的控制权。[R2，What are agents?]

如果业务总是“解析邮件 → 规范化时间 → 查冲突 → 生成草稿”，固定 workflow 很合适。若助手不知道要读多少封邮件、先核对哪条修改、是否需要额外搜索，模型驱动的局部循环更灵活。实际系统可以在固定外层流程中放一个探索型 agent，再用确定性检查把它的结果接回主流程。

因此，不要用“节点多不多”“有没有 while”来判断是不是 Agent。更有用的问题是：哪个判断交给模型，模型能改变哪些变量，何时必须返回给程序或用户，以及最终怎样确认完成。

**工程建议**：把权限、预算、服务端状态和业务硬约束留在确定性边界内；把开放的信息查找、候选生成与语言解释交给模型。允许模型自由决定推理路径，不等于允许它自由扩大操作范围。

## 2. 五种 workflow 模式分别解决不同的不确定性

指定阅读介绍 prompt chaining、routing、parallelization、orchestrator-workers 和 evaluator-optimizer。[R2，Workflows]

| 模式 | 控制结构与适用前提 | 邮件任务的例子 | 常见失败 |
|---|---|---|---|
| Prompt chaining | 固定分解，步骤间可加检查 | 提取字段后再解释冲突 | 上游丢失证据，下游只能加工错误 |
| Routing | 请求可分成有意义的类别 | 会议、报销、资料检索分别处理 | 分类错后进入错误工具和权限范围 |
| Parallelization | 子任务独立，或多次尝试能提供有效差异 | 分别核对三位参会者日历 | 任务实际有依赖；多模型犯相关错误 |
| Orchestrator-workers | 子任务随输入变化，由中心动态分解 | 按邮件线程分派核对工作 | 拆分重复、遗漏约束、汇总丢来源 |
| Evaluator-optimizer | 有清楚标准，反馈能指导改进 | 用证据完整性检查修改草稿 | 评分器自信但错误，改写越多越偏 |

模式本身不保证提高质量。并行投票若都是同一错误假设的改写，不会增加有效独立证据；评价器只检查文风，就可能把事实错误改得更流畅。每引入一种结构，都要指出它针对什么失败，并用相同任务与预算作对照。

### 2.1 Gate 是程序判定，不一定需要再调用模型

可以用普通程序检查字段是否完整、日期是否合法、授权版本是否匹配，以及引用是否能定位到原邮件。需要语义判断的地方再使用模型评价。把全部检查都变成“请另一个模型看看”，会增加延迟，也会让错误相关性更难控制。

### 2.2 动态分解也需要明确交付契约

worker 不能只返回“已核对，没有问题”。它应返回核对对象、来源版本、结论、缺口与可验证事实。主控还需要检查不同 worker 结论是否引用同一封旧邮件，或者分别使用了不同的时间范围。分工降低了单个上下文的负担，同时增加协调和汇总成本。

### 2.3 STORM与Archon：模式是组成单位，不是互斥产品分类

讲义第22—25页用STORM说明一套研究流程如何组合模式：先调研并确定不同视角，多条对话围绕问题查询、筛选和合成资料，最后形成并修订提纲。第24页把前后步骤标成prompt chaining，把不同视角标成parallelization，也把局部问答循环近似标成evaluator-optimizer。[L6，pp.22—25] “近似”很重要：专家问答反馈不完全等同于一个独立质量评分器，动态视角分配也不意味着每一步都由自由多Agent规划。

第26—29页的Archon进一步把生成、融合、批评、排序、验证和测试生成看成可组合的推理时组件。第27页表中每个组件有不同输入输出和调用成本。因此，架构搜索不只是“多采样几次”，也包括怎么路由候选、怎样筛选和组合；加入验证器仍会受到验证信号质量的约束。[L6，pp.26—29]

这两个例子在本文依据课堂图解说明结构，没有把图中的结果当作本轮复现数据。迁移到研究助理，可以先生成不同核查视角，再并行收集证据，最后按同一来源与时点标准汇总；生产实现还要验证是否真的增加新证据，而不是增加几个表达相近的角色。

## 3. ReAct：让思考、行动和观察互相更新

ReAct 的核心是把推理与环境交互交错进行。模型根据当前上下文决定行动，工具返回新观察，观察又影响后续判断。论文把语言思考视为扩展动作空间的一部分：思考改变上下文，但本身不改变外部环境。[R1，§2，PDF p.3]

这解释了一个重要区别：“我已经检查日历”如果只是模型生成的句子，不代表发生过查询；真实工具事件及其回执才是外部观察。系统应分别记录计划、动作请求和执行结果，不能让模型自述替代工具证据。

教学轨迹可以是：

```text
目标：确认当前评审安排。
判断：最新邮件可能覆盖旧时间，需要读取同一线程的修改邮件。
动作：读取邮件 thread-17 中按发送时间排序的相关消息。
观察：周一原定周五 10:00；周二修改为周五 14:00；周三回复仍缺一位确认。
判断：当前候选为14:00，但不能把未确认当作已确认。
动作：查询候选时段的日历冲突。
观察：一位必要参会者存在重叠事件。
结果：生成待确认事项和草稿，停止在发送之前。
```

这里的“判断”是便于教学的任务级说明，不要求系统暴露模型私有推理过程。生产 trace 可以保留简短决策摘要、所用证据和动作理由，重点是可验证信息。

### 3.1 为什么只给模型写一份长计划不够

预先计划能提供方向，但执行中可能遇到空结果、版本变化和权限限制。ReAct 的价值在于让后续行动基于实际观察修正，而不是无论查到什么都继续执行旧计划。一次正确的工具返回只有在被后续决策正确利用时，才会提高最终表现。

### 3.2 为什么不能写成“ReAct 一定优于 CoT”

ReAct 原论文表 1 的 PaLM-540B 设置中，HotpotQA 上 ReAct 的 exact match 是27.4%，CoT是29.4%；FEVER准确率上ReAct是60.9%，CoT是56.3%。论文同时研究两者与 self-consistency 的组合。[R1，PDF pp.5—6，表 1]

这些数值说明，外部观察改善事实依据，却也可能引入检索失败与流程限制。更强的系统通常需要根据任务选择信息获取与推理方式；不能因为一个方法更可解释，就推断它在所有任务上分数更高。

论文中的错误分析还发现重复思考与动作循环，以及不含有效信息的搜索结果。[R1，§3.3，PDF p.6] 工程上因此需要空结果策略、重复状态检测、预算和停止条件，而不是只增加最大循环次数。

### 3.3 轨迹格式与模型是否学会这种格式，是两件事

讲义第35页专门展示ReAct微调。原论文用最终答案正确的3,000条轨迹训练PaLM-8B/62B；在其HotpotQA实验中，小模型仅靠上下文示例不容易同时学会推理和行动，微调后的相对表现明显改善。[L6，p.35；R1，§§3.2—3.3，PDF pp.5—6] 因此，把循环写成 `thought → action → observation` 并不保证任意底座都能稳定执行；模型训练、动作格式和工具反馈需要匹配。

这也不能改写成“使用ReAct必须自己微调”。原文同时评估了提示方法；后来的底座可能已经接受工具轨迹训练，需用实际模型测试。对于邮件助手，先测能否正确解释空结果、区分旧安排和新提议、在信息不足时停止，再判断问题来自接口与上下文还是稳定的行为能力缺口。最终答案正确的轨迹也可能含错误中间步骤，是否把它作为训练示范仍要审查。

## 4. ReAct 的状态与停止条件应怎样落地

一个最小循环应显式维护任务目标、约束、已确认事实、待查问题、证据引用和预算。每次动作前验证权限与参数；每次观察后更新事实；准备结束时运行任务级检查。

下面是**控制流程伪代码**，不是供应商 SDK，也没有连接外部服务：

```text
while budget remains:
    if cancelled: return cancelled status with current evidence
    context = select_context(goal, state, relevant_evidence)
    proposal = bounded model call within remaining budget and deadline
    account for actual model usage
    if cancelled: return cancelled status with current evidence
    if proposal requests finish:
        verify required facts and final artifact
        return confirmed result or explicit unresolved status
    validate proposal against tool contract and granted scope
    if cannot reserve a bounded tool attempt: break
    persist action intent, stable operation ID, and budget reservation
    observation = execute permitted tool with deadline
    append result or outcome_unknown to event log
    reconcile unknown writes before permitting any retry
    update structured state from verified observation
    if repeated no-progress state or unrecoverable error:
        return blocked status with evidence
return budget_exhausted with verified partial result and unresolved items
```

停止不只有成功一种：`completed`、`needs_clarification`、`blocked`、`budget_exhausted` 和 `cancelled` 应能区分。预算耗尽时应交付当前已确认事实及缺口，而不是为了输出完整答案而补造信息。

在邮件案例中，证据不足时的正确结果可能是“14:00 是最新提议，尚未得到全部确认”。若评测强迫模型只能在“14:00 已确认”和“10:00 已确认”中选一个，会奖励错误的确定性。

## 5. Reflexion：把一次失败压缩成下一次尝试可用的经验

ReAct 处理一次轨迹内的行动与观察；Reflexion 在尝试之间增加评价、反思和记忆。其三个角色分别是 Actor、Evaluator 和 Self-Reflection 模型。Actor 执行任务，Evaluator 提供结果反馈，反思模型根据轨迹和反馈生成文字经验，后续 Actor 把经验放入上下文。[R3，§3，PDF pp.3—5]

用教学符号表示：

$$
\tau_k=\operatorname{Run}(x,m_k),\quad
r_k=\operatorname{Eval}(\tau_k),\quad
e_k=\operatorname{Reflect}(\tau_k,r_k,m_k),\quad
m_{k+1}=\operatorname{Update}(m_k,e_k).
$$

$\tau_k$ 是第 $k$ 次尝试轨迹，$r_k$ 是反馈，$e_k$ 是文字经验，$m_k$ 是已有记忆。原方法的主要更新对象是上下文记忆，不是通过梯度更新底座权重。论文使用“verbal reinforcement”描述这条反馈链，不能直接把它等同于 PPO 或 GRPO 训练。

在邮件任务中，一条有用经验可以是：“同一会议线程里，最新提议不等于所有参会者已确认；需要分别保留候选时间和确认状态。”它包含失败条件与下一步检查。只写“以后要更认真”没有可执行价值；只写“以后都用周五14:00”又把一次具体事件错误推广到未来。

### 5.1 谁告诉反思模块失败在哪里

反馈可以来自环境完成信号、测试、启发式规则或模型判断。反馈越弱，反思越可能错误归因。例如日历 API 不可用导致任务未完成，模型却总结成“以后不要查询日历”，这会把临时基础设施故障写成错误流程规则。

因此，记忆更新需要保留触发条件、错误证据、建议动作和适用范围；高风险经验还应经过独立检查，再被未来任务选择。Reflexion 提供了文字反馈闭环，长期记忆的权限、版本、过期与冲突处理仍需额外设计。

### 5.2 反思确实可能让系统变差

Reflexion 论文在 MBPP Python 上没有超过其 GPT-4 基线，并分析了自生成测试的误判：错误实现可能通过不充分测试而提前停止，正确实现也可能被错误测试否定。[R3，§4.3，PDF pp.7—8]

这一反例比只记住 HumanEval 的高分更有工程价值。反思不能创造独立证据，它会把反馈放大；反馈错时，也可能把错误方向放大。改进评测应同时比较重试预算、反馈质量、记忆有无和记忆内容，而不是把“尝试次数更多”全部归因于反思机制。

### 5.3 为什么讲义紧接着讲CRITIC

第41页引用历史自我纠错实验，提醒“让同一模型再评一次自己”可能降低表现；第42页以CRITIC说明把外部工具接入验证器的价值。[L6，pp.41—42] 课程要建立的因果链是：先有可检查的外部反馈，再让模型根据反馈修正；单纯增加一段自信的自我批评，不能增加独立事实。

这个历史实验也不应被推成“所有现代模型都不能自我纠错”。讲义自身指出相关研究早于后来的推理模型；不同模型、任务、反馈与预算会改变结果。本讲没有逐篇复现CRITIC原论文，保留的是明确且可测试的工程假设：在邮件时间判断上，真实邮件、日历查询和格式验证应比无来源的再评价提供更可靠的约束。

## 6. CodeAct：让代码承担控制流和数据流

CodeAct 使用可执行 Python 代码作为 Agent 与环境交互的一种统一动作表示。模型可以在代码中组合函数调用、循环和条件，并利用解释器结果或异常作为观察，在后续轮次修复。[R4，§2.1，PDF p.3]

设需要检查 30 封邮件中的会议候选，逐次生成 30 次相同 JSON 调用可能重复消耗模型轮次。代码可以让同一段循环处理列表，把大对象保留在解释器变量中，最后只向模型返回紧凑结果。优势来自控制与数据流表达，以及对现有软件库的复用；并不是 Python 字符串天然比 JSON 安全。

CodeAct 论文区分简单原子工具调用与复杂多工具任务。后者的 M3ToolEval 包含 82 个任务，允许至多 10 轮交互，报告成功率和平均轮数；在这些条件下，代码动作对多个模型有优势，但并非所有模型都获益。[R4，§2.2—2.3，PDF pp.4—5]

这些结果不能直接推广为“让任意模型自由执行代码都更好”。能力较弱的模型可能不能正确编程；跨语言或复杂依赖环境也可能增加失败。原论文的任务、工具集合和评分方式应与动作表示一起理解。

### 6.1 代码执行能力扩大了什么边界

一个受限的 `get_calendar` 工具只能读取日历，而自由 Python 可能访问文件、网络、进程和凭据。因此，代码解释器需要独立的权限、资源限制、文件范围和网络策略。模型生成的代码不能通过“这是工具调用”自动获得宿主机全部能力。

对于外部写入，代码循环也会放大副作用：第 21 次失败后重跑整个循环，可能重复前 20 次操作。应使用业务幂等、每项状态与恢复边界，或者把写入收窄成经过验证的服务接口。

### 6.2 解释器状态并不等于长期可靠状态

把邮件列表保存在 Python 变量里可以减少 token，但进程退出后变量可能消失。若任务需要恢复，应持久化必要数据或可重建引用。模型上下文、解释器内存、文件状态和远端业务状态是四个不同存储位置，恢复设计必须逐个解释。

### 6.3 ReWOO与LLMCompiler：先规划，不是执行时永远不能看观察

讲义第47—49页提出另一种控制安排：先由Planner生成带依赖的计划，再由Worker执行工具，最后由Solver结合计划与证据回答。ReWOO的图中，后续动作可以引用`#E1`、`#E2`等先前结果；规划时不需要逐步接收每个工具返回，但执行器会用真实返回替换依赖变量。[L6，pp.47—49] 因而“Without Observation”不能理解为整个系统不使用工具观察，差别主要在规划与外部执行的耦合方式。

例如，先查三位参会者日历，随后汇总共同空闲时段，再生成邀请草稿。三份日历查询相互独立，可以并行；共同空闲计算依赖三份结果，不能提前执行。把这类依赖关系表示为有向无环图，能让执行器识别哪些任务已经具备输入，减少模型每执行一步都重新读全部历史的成本。

第50—52页把LLMCompiler的特点概括为并行执行和动态重规划，图中包括函数调用Planner、依赖管理/任务调度以及Executor。[L6，pp.50—52] 计划结构相对稳定、工具依赖可以描述时，这类安排有价值；若查询结果可能彻底改变目标或揭示新的必要操作，则需要重规划或退回局部ReAct循环。提前规划减少一些反复推理，也可能让错误计划影响更大范围。

本文对这两种方法的说明来自讲义图解，没有取得并完整核查其原论文，因而不复述具体加速倍数、准确率增益或实现API。工程上仍应分别测试计划正确率、依赖调度、取消、工具失败和重规划成本，不能把“可以并行”直接等同于端到端更快。

## 7. 对照这些方法：它们分别改变哪一部分

| 方法 | 主要改变 | 反馈在哪里进入 | 持久状态 | 主要风险 |
|---|---|---|---|---|
| ReAct | 一条轨迹中的决策与行动组织 | 每次工具观察后 | 当前轨迹与工作状态 | 检索空转、重复行动、错误使用观察 |
| Reflexion | 多次尝试间的文字经验 | 评价后反思，再给后续尝试 | 经验缓冲 / 外部记忆 | 错误归因、坏经验累积、反馈不可信 |
| CodeAct | 动作表示与组合能力 | 代码输出、异常和环境返回 | 解释器变量及按需持久化 | 代码错误、越权、批量副作用 |
| ReWOO / 依赖计划执行 | 规划和工具执行的安排 | 工具结果填入计划依赖，必要时重规划 | 计划、依赖结果与任务状态 | 错误计划扩散、动态变化未覆盖 |
| 固定 workflow | 可预期的步骤与分支 | 预定义 gate 或指定检查点 | 显式流程状态 | 对未覆盖情况不够灵活 |

ReAct 可以把 CodeAct 作为动作表达，Reflexion 又可以在失败后为下一次 ReAct 尝试提供经验。因此三者是可组合维度，不能仅按名称选择一个“最强算法”。比较时要固定模型、工具、任务和预算，明确究竟改变了哪一个维度。

## 8. 上下文工程：运行日志和模型视野要分开

LangChain 的指定阅读把上下文管理归为 write、select、compress、isolate。write 把信息存到窗口之外，select 把当前需要的信息取进来，compress 减少保留的 token，isolate 把不同任务或大对象隔离在不同空间。[R5，Context Engineering]

最关键的工程区分是：**完整事实可以保存在外部，模型每次只看到任务所需的视图**。如果为了减少 token 直接删除唯一的工具原始结果，后面既不能重新检查，也不能解释摘要从何而来。压缩模型上下文，不应自动等同于销毁可审计来源。

邮件案例可以保存三类内容：原始邮件及版本作为事实库，结构化的“当前候选时间与确认状态”作为运行状态，每次模型调用的精简材料作为上下文。它们之间用稳定 ID 和来源位置关联。一个模型看到的摘要只是视图，不应成为唯一权威记录。

## 9. Event log：记录发生了什么，再选择让模型看什么

事件日志可以按顺序保存用户要求、动作提议、实际工具执行、返回、授权、状态更新和终止。append-only 的设计让后续能追溯旧状态，而不是每次更新都覆盖上一事实。这是工程建议；它不要求把所有事件无差别塞回模型。

事件最小字段可以包括 `run_id`、`event_id`、父动作 ID、类型、时间、数据引用、来源版本和执行状态。对于邮件和日历，敏感正文可以留在受控存储，日志使用授权范围内的引用。trace 需要够用，但不应复制出新的无边界数据泄露面。

当一个旧会议被改期时，日志应保留“曾提议10:00”和“随后改提14:00”两个事件，而当前状态指向最新候选。若压缩只留下“会议时间14:00”，就可能丢失“仍未全部确认”的限制条件。把事件和当前状态分开，是避免长期助手记忆混乱的重要办法。

### 9.1 Memory offloading：写出去之后还要能找回来

讲义第64页用MemGPT说明，把事实、阶段结果或任务笔记移到外部记忆/文件，可以为模型窗口释放空间。[L6，p.64] 但offload只完成了一半：需要稳定标识、适用范围、版本和检索入口，后续调用才能按需恢复。把一条重要约束写到文件但不再加载，对当前Agent行为没有帮助。

邮件场景中，可以卸载全文邮件和中间搜索表，只在工作状态保留“当前安排、确认情况、来源ID和缺口”。如果下一步需要核对原话，再读取相关片段。这样区别于把完整线程一直放在prompt里，也区别于只保留不可追溯的摘要。后续记忆架构课会专门讨论跨任务更新与遗忘，本课先解决一条任务怎样继续执行。

## 10. Compaction：摘要应保存约束、证据与未完成动作

摘要压缩不是把对话改写得更短，而是保留继续执行所需的信息。一个可恢复摘要应至少包含：目标与用户约束、已经验证的事实、证据引用、关键决策、未解决缺口、已执行副作用、待确认内容和下一步。

摘要容易出现的三种错误是：把模型猜测写成事实，把临时观察写成永久规则，把未完成动作写成已经完成。后续模型通常看不到被丢弃上下文，因而更难自行纠正。这就是为什么需要来源 ID、状态字段和可重新读取的原始资料。

可以把“准备发送的草稿版本v3”和“发送成功消息ID m17”作为不同字段保存。若压缩只写“已经处理邀请”，就无法知道任务停在哪里。对恢复来说，状态的精度比文字是否流畅更重要。

**工程建议**：用压缩前后的同一任务快照做对照，检查事实是否保留、未完成动作是否一致、恢复后是否重复写入。摘要评测应关注后续任务能力，而不是只看摘要本身的可读性。

## 11. Observation masking：减少旧工具返回，但保留可追溯指针

很多 token 来自长工具输出，例如整封邮件、终端日志和搜索结果。对较早、已被利用的返回，可以在当前模型视图中用短标记或证据摘要替换，而把原文保留在外部。与通用摘要相比，这类策略可以更确定地针对 token 大户。

风险是丢掉后续仍需要的信息，或破坏动作与结果的配对关系。工具协议若要求调用与结果匹配，裁剪时必须维持合法消息序列；原始事件也应保留完整关联。不能只删一半消息，再期待模型或 SDK 自动补齐。

在贯穿案例中，旧邮件全文可以被替换成“邮件e12，原提议10:00，已被e18修改；原文可重读”。但若旧邮件中的参会者仍是当前唯一来源，就不能把它全部遮蔽而不给替代结构化字段。裁剪规则应与当前任务的事实依赖相匹配。

### 11.1 为什么长轨迹的累计成本容易迅速增加

设每轮都携带固定指令 $b$ token，每份新增工具观察约 $r$ token，一共执行 $n$ 轮，并约定第 $j$ 轮已经携带 $j$ 份观察，每次都把全部历史发回模型。输入 token 的教学近似为：

$$
\sum_{j=1}^{n}(b+jr)=nb+\frac{rn(n+1)}{2}.
$$

这说明累计输入规模可能按 $n^2$ 增长。它不是实际价格模型：缓存计费、输出 token、不同大小返回和服务实现都会改变成本，墙钟延迟也不一定与 token 数成严格比例。公式的作用是解释为什么仅减少某一次返回，还不够；应观察整条轨迹每轮重复携带的信息。

第66—68页把观察遮蔽、LLM摘要与原始Agent放在成本—解题率图中，三种方法在不同模型上并不形成一个完全统一的质量顺序。[L6，pp.66—68] 图支持的是“需要一起看成本与质量，并做任务相关选择”，不能读成遮蔽在所有模型上都严格更准确。本讲未独立核查该图引用论文的全部实验设置，所以不从图中估读小数或转述无条件收益。

## 12. Context isolation：隔离注意力，不自动隔离权限

指定阅读介绍通过子 Agent、解释器环境和结构化 state 隔离上下文。[R5，Isolating Context] 一个 worker 只看一条邮件线程，可以减少无关材料；解释器保留整个表格，只把统计结果返回模型，可以减少大对象占用。

但独立上下文不意味着独立文件、凭据或事务。同一目录中的两个 worker 仍可能同时修改同一个草稿；同一共享日历上的两条任务仍可能互相冲突。因此要分别设计“谁看什么”“谁能改什么”“谁拥有某个产物”“如何合并与处理冲突”。

交接应返回紧凑而可验证的包：任务范围、事实、证据引用、未知项、产物路径与版本、执行状态。只返回结论会把上下文隔离变成证据丢失；把全部轨迹再交回主控，又可能抵消隔离节省的 token。

### 12.1 Progressive disclosure与连续性：不是一开始加载全部说明

第70页通过skills说明按需披露：初始只提供任务路由需要的能力索引，真正进入某类任务时再加载对应说明、资源或工具。这样减少无关schema与背景干扰，但索引必须足够清楚，否则该调用的能力也可能永远不被发现。[L6，p.70]

讲义第59页同时要求聚焦当前任务与保留连续性，提到KV cache。模型语义上需要保留目标、约束与进度；系统性能上，希望尽量复用稳定前缀，减少无谓重写。两者相关却不同：把全部历史保留有利于前缀稳定，也可能形成上下文膨胀；大幅重排和压缩可能减少token，却影响缓存复用。是否获益应以所用模型服务的实际缓存命中、计费和质量测量判断，不能由讲义一句话推断具体引擎的缓存协议。[L6，pp.59、71—75]

## 13. 怎样判断 scaffold 是帮助还是负担

scaffold 可以提供计划、工具、记忆、检查点和恢复策略，但每个附加步骤都带来成本及新故障模式。一个反思环可能改善复杂任务，也可能在简单任务上制造多余改写；一个多 Agent 分工可能降低上下文干扰，也可能增加协调错误。

应先从失败提出假设。例如，“助手把旧邮件当新安排”对应来源时序与状态建模；“知道约束却忘了检查”对应显式 gate；“搜索多轮后空转”对应进度检测与停止条件；“跨尝试重复同样错误”才可能需要反思记忆。不要把所有失败都解释为需要再加一个 Agent。

一个有用的对照矩阵可以固定模型与任务，分别比较：基础循环；基础循环加结构化状态；再加观察裁剪；再加反思。每组用相同预算，并报告最终正确率、证据完整性、工具次数、输入输出 token、延迟、重复副作用和人工接管。这样才可能看出收益来自哪一层。

### 13.1 Pi案例：少工具可以配合复杂的状态管理

讲义最后用Pi把前面的维度合在一起：默认read、bash、edit、write四种工具；ReAct式循环；历史组织成可分支的树；由事件记录构造模型输入，结合skill渐进披露与compaction。[L6，pp.77—81] “工具少”不表示没有上下文管理，也不表示必须把整个世界都一次放入prompt。

树形历史让用户可以回到旧节点再展开另一条路径。但对外部世界而言，已经执行过的操作并不会随对话分支自动撤销。回到“发邀请之前”的消息，不代表真实日历事件已经不存在。一个成熟系统要分别处理模型看到的分支、文件或工具环境的状态、以及外部业务副作用；课程图解本身不提供事务回滚。[L6，p.80；工程推导]

第78、82—83页强调课堂所述Pi没有默认权限弹窗、plan mode或内置subagent等保护/功能，进程权限决定可操作范围。它说明功能可以通过外部环境或扩展组合，但不能用“没有弹窗”推断操作天然安全。企业部署需要在外层限定文件、网络、凭据和业务写入范围。[L6，pp.78—83] 这些是对课程快照的分析；本文没有检出Pi当前源码，不声称所有后续版本及社区扩展都保持完全相同功能集合。

## 14. 贯穿案例的完整设计

先用确定性入口解析用户授权范围，明确“准备草稿”不包括发送。检索相关邮件线程，按真实时间和来源版本组织；模型提取候选安排及依据；程序核验日期格式、时区和必需字段；必要时查询日历并记录冲突；模型整理待确认事项；最后检查草稿中每一项事实都有对应证据。

如果存在冲突或参会者未确认，系统交付部分结果和缺口。若用户补充信息，则更新状态而保留旧事件。若用户授权发送，绑定具体草稿版本，执行器使用幂等标识，并把外部回执保存为事实。执行中断后，根据状态恢复，不凭聊天摘要重新猜测有没有发送。

对于复杂邮件查找，可以使用 ReAct 局部探索；对于批量统计，可使用受限 CodeAct；对于反复出现且有可信反馈的失败，可提取条件化经验。但最外层的授权、预算、状态和终态校验保持明确，避免探索性推理扩张到不可控的外部操作。

## 15. 自测与答案

1. 固定 workflow 里使用 LLM，为什么仍可能不是模型驱动 Agent？
2. ReAct 的思考和环境动作在状态上有什么区别？
3. 为什么 ReAct 原文不能支持“在所有 QA 上优于 CoT”？
4. Reflexion 更新什么，为什么它不等于权重强化学习？
5. 自生成测试存在假阳性时，反思环可能发生什么？
6. CodeAct 减少模型轮数，为什么不一定减少业务风险？
7. 模型窗口之外的事件日志和 Python 变量有什么不同？
8. 好的压缩摘要至少应保存哪些执行信息？
9. 两个 worker 上下文独立，是否就不会修改冲突？
10. 怎样证明新增 scaffold 的收益来自机制，而不是增加预算？

**答案**：

1. 是否由模型决定下一步才是关键；固定代码仍可调用模型完成某个子任务。
2. 思考主要改变当前上下文，真实动作通过执行器影响或读取环境，并产生可验证观察。
3. 在其 PaLM-540B、HotpotQA 设置下 ReAct EM 低于 CoT，而 FEVER 更高，结论依任务与设置而变。
4. 更新文字经验及后续上下文；主要方法不通过梯度改变底座权重。
5. 错误实现被认为成功后可能提前停止；错误反馈也可能导致不必要修改，需独立校验和对照。
6. 一次代码动作可以执行很多有副作用操作，权限、资源和幂等仍需独立控制。
7. 日志用于持久追溯，解释器变量可能随进程退出消失；两者都不会自动成为模型可见上下文。
8. 目标约束、已验证事实及来源、关键决策、未知项、已执行副作用、待确认版本、下一步和停止条件。
9. 不能保证不冲突。共享文件、远端状态和凭据仍可能冲突，需要产物所有权、隔离或合并规则。
10. 固定模型、工具、任务与预算，做模块消融；共同改变多个因素时只报告整套方案效果。
