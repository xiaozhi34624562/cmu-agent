一个助手昨天已经知道“公司 A 的资本开支计划发生调整”，今天却重新询问；另一个助手永远记住昨天的数值，最新公告出来后仍用旧数值计算。前者没有把经验带到下一次任务，后者没有维护经验的有效性。讲义 pp.9–10 正是从 procedure、knowledge、progress 三种丢失，推到个性化、经验复用和跨会话连续性。**记忆工程同时解决留下什么、什么时候取回、什么时候修订和什么时候不应使用。**

本文沿课程的“记忆类型 → 架构模式 → 维护 → 评测与开放问题”展开，把 MemGPT 的分层管理、Generative Agents 的检索与反思、CoALA 的认知架构放进一个企业研究助手案例。论文结果限定于各自版本和任务；教学示例均为构造，未调用模型、训练权重或复现论文基准。文中 PDF 页码统一从 1 开始。

## 1. 先确定需要跨越哪一种边界

“记住了”至少可能指四件事：同一次推理中还能看到上一段信息；同一个任务继续执行时保留计划和工具结果；新会话能检索旧会话；整个系统通过新经验改变今后的行为。它们分别涉及上下文、任务状态、持久记忆与学习更新。调用一次 `save` 只证明某些字节落盘，还不能证明后来的调用检索了它，更不能证明用了它会改善结果。

把一次模型调用写为：

$$
y_t\sim p_\theta(y\mid q_t,c_t),\qquad c_t=\operatorname{Assemble}(h_t,\operatorname{Retrieve}(M_t,q_t)).
$$

$q_t$ 是当前请求，$h_t$ 是任务历史，$M_t$ 是持久记忆，$c_t$ 是实际送给模型的上下文。$\theta$ 是模型权重。普通记忆系统改变 $M_t$ 或上下文组装方式；权重可以完全不变。检索到数据库中的内容，只有被放进 $c_t$ 或被转化成影响动作的信号后，才可能改变这次输出。

**教学推导**：应沿“写入 → 索引可见 → 检索命中 → 装入上下文 → 正确使用 → 结果改善”检查记忆。每一箭头都可能失败。你的日志能证明写入成功，却不能替代最后两项的行为评测。MemGPT 对 main context 和 external context 的区分正好把这个边界讲清楚：外部内容必须显式移入主上下文，才会参与模型推理。[MemGPT，§2，PDF pp.2–3](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=2)

另一个重要边界是恢复与学习。Checkpoint 可以保存“本次任务已查过哪些文档、待处理工具调用、下一节点”等状态，支持继续运行。长期记忆可以保存“这种任务应该先核对财报口径”，支持以后处理新任务。两者可以共用数据库，但生命周期、读取时机和正确性标准不同。一个保存全部消息的 session，也不会自动变成整理好的事实库。

## 2. 四类记忆分别回答什么问题

下面是面向工程实现的解释；同一个系统可以同时具备多类记忆，一条自然语言文本也可能兼具多种用途。

| 类型 | 回答的问题 | 企业助手的例子 | 主要失效方式 |
|---|---|---|---|
| Working，工作记忆 | 现在正在处理什么？ | 本次比较的公司、期间、待解决证据缺口 | 上下文丢失、计划与已完成动作不一致 |
| Episodic，情景记忆 | 过去具体发生过什么？ | 某次查询、工具失败、研究员纠正及当时证据 | 时间或主体混淆，把一次经历当一般规则 |
| Semantic，语义记忆 | 目前认为哪些知识成立？ | 公司 A 的证券代码、指标定义、已确认业务事实 | 过时、冲突、来源不明、适用范围丢失 |
| Procedural，程序性记忆 | 类似事情应该怎样做？ | 财报更新核验流程、可复用工具操作、Skill | 错误流程被固化、条件不适配新任务 |

“用户偏好短报告”通常是可修订的语义性偏好；“用户在这次会议选择短报告”是事件；“生成晨报时先列异常再列背景”可以作为程序性策略。把三者都压成“用户永远只要短报告”，就跨越了原始证据允许的泛化范围。

**工程建议**：记忆对象至少记录主体、内容、类型、来源、产生时间、有效期间、适用范围和状态。研究资料还要记录报告期和公告发布时间，避免把“2025 年末的持仓”误当作当前持仓。“最近写入”与“最近生效”不是同一时间轴，补录旧事件时尤其如此。

可以用以下逻辑结构开始，无需一开始就引入图数据库：

```json
{
  "memory_id": "mem-017",
  "kind": "semantic",
  "subject": "company:A",
  "claim": "资本开支计划以公告v2为准",
  "source_ids": ["announcement:v2"],
  "observed_at": "2026-10-14T09:00:00+08:00",
  "valid_from": "2026-10-13",
  "supersedes": "mem-009",
  "scope": {"tenant": "research", "company": "A"},
  "status": "active"
}
```

这是教学设计，不是任何论文的原始 schema。`supersedes` 让修订关系可追溯；旧条目作为历史保留，但不再作为无时间限制的当前事实。权限范围参与检索前的过滤，不能依赖模型读到敏感内容后“自觉不回答”。

### 2.1 用 CoALA 把“记忆”放回决策循环

讲义 pp.15–21 借 CoALA 组织概念，原文图 4 则进一步区分内部动作与外部动作：检索把长期记忆读入工作区，推理在工作区内产生新信息，learning 把信息写入长期记忆，grounding 执行环境动作。这里的 learning 不专指梯度训练；写入一条可复用经验也属于该框架的学习动作。[CoALA，§4、图 4–5，PDF pp.8–11](readings/Cognitive_Architectures_for_Language_Agents.pdf#page=8)；[L7，pp.15–21](slides/lecture07.pdf#page=15)

还要修正一个常见缩写：讲义把 working memory 概括为当前 context window；CoALA 原文定义更广，它是跨模型调用保留的活动状态数据结构，每次只选其中一部分构造输入。程序中的任务变量、待执行调用和活动目标可以属于工作状态，即使未全部放入本轮 prompt。[CoALA，§4.1，PDF p.9](readings/Cognitive_Architectures_for_Language_Agents.pdf#page=9)

参数记忆与上下文记忆则是另一条分类轴。模型权重可以承载通用语义和操作倾向；外部检索可以把事实、轨迹或 Skill 放入上下文。同一种“程序知识”可能以两种形式存在，因此不能把“有 Skill 文件”和“模型已经训练掌握 Skill”画等号。讲义 p.21 的 episodic 参数项标为不适用，应按其工程分类理解，不能扩展成“模型训练绝不会记住个别事件”的绝对命题。

## 3. 从保存对话转向完整的记忆生命周期

一个可维护的系统需要六个动作。

1. **采集**：保留原始事件，包括用户消息、工具输入输出、时间和引用。原始日志的作用是可追溯，不能默认每个字都适合作为长期事实。
2. **提取**：从事件提出候选事实、偏好、教训或流程，并附上支持它的证据片段。
3. **验证与归类**：识别它是用户原话、工具观测、模型推断还是已确认结论；检查主体、期间、权限和重复项。
4. **合并或修订**：决定新增、补充来源、替代旧状态，还是保留冲突等待澄清。
5. **检索与组装**：根据当前任务、时间和权限选出条目，控制 token 预算，并保留来源与不确定性。
6. **维护与遗忘**：处理过期、删除、撤回、压缩和重建索引，让所有副本遵守同样的状态。

其中第 4 步最容易被“向量插入”替代。插入相似条目不等于更新实体事实：数据库可能同时有“计划 10 亿元”和“计划 8 亿元”，检索又更偏向旧报告。系统需要知道这是同一公司同一期间同一指标的修订，而不是两个可以平均的观测。

**教学案例**：研究员说“上次结果有误，表格单位是万元”。可以保存一次错误事件，并提出候选流程“数值抽取前核对表头单位”。但不能直接把此前所有表格的单位改成万元。事件负责说明发生了什么；程序性条目负责提出有条件的改进；已有事实的批量修订需要逐条回查证据。

提取过程也会犯错。若后台任务在会话结束后生成摘要，可能丢掉否定词和条件。应保存 `source_event_ids`、提取器版本、写入批次和审查状态，使“这条记忆来自哪里、谁生成、凭什么激活”都可回答。只有摘要而没有原始证据，会让后续纠错变成另一轮猜测。

### 3.1 存储选型回答 how，不能替代 what 与 when

讲义 pp.24–29 先问 what/when/how，再介绍文件、数据库和知识图谱。文件系统便于人读、版本化和目录导航；关系表便于按实体、时间、权限和状态精确过滤；向量或 BM25 用于内容候选检索；图适合表达关系与来源依赖，但需要维护节点身份和边的含义。[L7，pp.24–29](slides/lecture07.pdf#page=24)

| 存储方式 | 最小实现 | 适合优先解决的问题 | 维护代价 |
|---|---|---|---|
| 文件系统 | 每任务日志、实体文件、Skill 目录 | 少量可解释经验、人工检查与版本控制 | 并发覆盖、重复和全局检索 |
| 数据库加内容索引 | 记忆主表、来源表、文本/向量检索 | 多租户、时间状态、精确元数据过滤 | schema、索引一致性与删除传播 |
| 知识图谱 | 实体、事件、关系、证据边 | 多跳关系与依赖失效 | 实体消歧、边版本、推断错误传播 |

它们不是必须逐级升级的成熟度阶梯。文件也可以具备严格 schema，数据库也可以只保存毫无维护的长文本。先确认查询、更新与审计需求，再选择最小能支撑这些契约的介质。

## 4. 架构一：把稳定方法组织成可检索的 Skill

程序性记忆适合保存可重复操作，但一个 Skill 应包含触发条件、前置条件、步骤、输入输出契约、检查点和失败处理。单独保存“上次成功的回答”通常不足以在新数据上正确执行。

例如“财报更新核验”可以规定：确认公告主体与期间；抽取原始单位和会计口径；对照上期已公布数据；计算变化；回读异常字段；输出带来源的结论。触发条件是新财报或口径修订；不能在只有新闻标题时照搬完整流程。对于不可逆操作，还需要显式权限和幂等约束。

加载 Skill 的策略通常有两层：先用较短的名称、描述和触发条件选择候选，再按需加载细节或执行相关代码。这降低常驻上下文，但新增了路由错误风险。要分别评测“选没选对 Skill”和“选对后有没有执行正确”。如果所有失败都记在最终答案上，就看不到这两种不同原因。

**工程建议**：把 Skill 当成版本化的可执行知识。元数据包括适用工具版本、测试条件、已知限制、发布版本和回滚版本。成功轨迹可以作为生成候选 Skill 的材料；它本身不是已验证的通用策略。若一次成功依赖缓存、人工介入或特定日期的环境，迁移时就需要重新验证。

Skill 与工具也有边界。工具提供能力和运行接口，Skill 说明何时及怎样组合能力。相同工具可以被不同流程使用；流程不能绕过工具的权限检查。把一个 shell 脚本放入技能库，不会自动使其副作用适合所有任务。

### 4.1 讲义怎样连接 Voyager、AWM 与 Skill 文件

Voyager 的例子把成功行为保存成可调用代码技能，后续按任务复用；AWM 则从经历中归纳多步 workflow，把步骤模式作为后续任务的上下文。两者都超出了“保存完整旧聊天”：它们提取可重用方法，但方法的表达形式、触发和执行方式不同。[L7，pp.31–38](slides/lecture07.pdf#page=31)

讲义 p.33 的 diamond-tool 表中还有运行次数条件，不能只摘出醒目的“102 iterations”就解释为每次都能可靠完成。这里用它说明跨任务积累的可能性，不把该数字推广为企业流程的节省比例。pp.39–41 将 Skill 文件放回通用助手，并提醒动态环境会使已有程序失效：网站变更、接口升级或权限变化，都可能让旧流程需要更新。[L7，pp.33–41](slides/lecture07.pdf#page=33)

## 5. 架构二：MemGPT 如何在有限上下文中管理更多历史

MemGPT 的操作系统比喻解决的是“主上下文有限，外部存储可以更大”。它没有让 Transformer 同时注意无限 token，也没有让磁盘数据直接参与注意力计算。[MemGPT，§1–2，PDF pp.1–4](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=1)

其 main context 分为只读 system instructions、可读写 working context，以及 FIFO 消息队列。外部有 recall storage，保留消息历史；archival storage，保存可检索的任意文本。Queue manager 管理历史和容量；function executor 解释并执行模型提出的记忆函数调用。模型可以查询外部资料、修改工作记忆，再继续推理。[MemGPT，§2.1–2.3，图 3，PDF pp.2–3](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=3)

处理一条新消息，可以按运行顺序理解：

1. Queue manager 将输入加入队列，并记录到 recall storage。
2. 拼接系统指令、工作记忆和队列，调用模型。
3. 模型提出记忆操作或回答；参数先经过解析和检查。
4. 执行函数，将结果或运行错误放回上下文。
5. 若请求继续执行，立即进入下一次模型调用；否则交还控制。

论文用 `request_heartbeat=true` 支持函数链。它表示一次函数执行后继续安排推理，不等于训练更新，也不等于可靠任务调度器。生产系统仍要处理进程崩溃、重复执行、超时和预算。[MemGPT，§2.4，PDF p.4](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=4)

### 5.1 内存压力怎样触发“换入换出”

队列接近容量时插入 memory pressure 警告，给模型机会把重要信息移到工作区或归档；达到清理阈值后，移出一部分消息并更新递归摘要。原始消息仍在 recall storage，可通过检索重新取回。论文列出的 70%、100%、50% 是示例阈值，不是所有模型和应用的最佳配置。[MemGPT，§2.2，PDF p.3](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=3)

这里有两个独立保障：持久化避免字节丢失，检索机制避免关键历史在需要时不可见。压缩后的摘要即使错误，原始消息仍可能帮助恢复；但只有系统真的回查了原文，才完成纠错。保存全部历史并不保证模型知道该搜哪个关键词。

### 5.2 “像虚拟内存”有哪些不相同

传统内存访问有明确地址和页故障；自然语言任务通常没有一个可靠信号告诉系统“答案所需记忆不在当前上下文”。模型可能不知道自己忘了什么，也可能在未检索时直接编出答案。因此，记忆调用能力、查询质量、停止判断和索引质量都影响结果。

不能从“外部存储不受上下文上限约束”推出“任务可无限运行且准确率不下降”。随着历史变大，重复、冲突和隐私问题也会增加；检索增加推理次数和延迟。MemGPT 在较弱函数调用模型上的退化，正说明运行框架需要底座能力配合。[MemGPT，§3.2，PDF pp.6–8](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=6)

### 5.3 MemoryOS 为什么在分层图里出现

讲义 pp.48–49 展示短期、中期、长期 persona 三层，把近期互动、经过组织的片段和更稳定的人物知识分开。它与 MemGPT 共同回答容量和层次问题，但并非同一套队列/换页实现。对企业助手可以借鉴“原始短期活动 → 任务片段 → 稳定口径/偏好”的职责划分；具体迁移阈值、段落组织和检索算法仍要以相应原文为准，本文没有复现 MemoryOS。[L7，pp.48–49](slides/lecture07.pdf#page=48)

## 6. 架构三：从事件反思出可复用的高层知识

若每天都保存一份研究晨报，半年后已有上百份相似文本。用户问“这家公司投资逻辑如何变化”，单纯按语义相似度返回最新五份报告，未必能解释关键转折。系统需要在保留事件证据的同时，建立跨事件的主题、关系与趋势摘要。

反思性整理可以分三层：原始观测，例如公告内容；解释，例如这次调整与去年扩产预期相反；高层假设，例如管理层连续调整可能说明需求假设变化。层级越高，越需要来源与不确定性标记，不能让模型生成的推断和公司披露混为一谈。

**工程建议**：把“反思结果”写入候选区，并附支持事件 ID、适用期间、反例和后续验证条件。高层结论在检索时与来源一起返回。用户询问原因时，应能从摘要下钻到原始公告；来源被撤回时，也应知道哪些摘要需要失效。

反思会消耗模型调用，并可能放大原始错误。若五篇报告都复制了同一错误数字，反思模型可能把重复频率当作更强证据。需要先识别来源依赖：五个文档副本不等于五个独立观察。对高风险数字，应保留原始表格定位和计算链，而不是只保留“结论被多次提及”。

反思触发方式可以是定时、事件数量达到阈值、冲突出现、任务结束或反馈累积。选择应由业务收益决定。低频短任务没有必要每次生成层层摘要；高频助手则要控制后台队列、写入幂等和失败重试，避免每次恢复都重复生成同一结论。

### 6.1 Generative Agents：反思本身也成为带证据的记忆

讲义 pp.53–56 用 Smallville 展示 memory stream、retrieval、reflection 与 planning 的循环。原文把观测作为带创建和最近访问时间的条目；检索组合最近访问、重要性和当前相关性；反思再生成带支持条目指针的高层认识，并写回同一记忆流。[Generative Agents，§4.1–4.3，PDF pp.8–10](readings/Generative_Agents_Interactive_Simulacra_of_Human_Behavior.pdf#page=8)；[L7，pp.53–56](slides/lecture07.pdf#page=53)

反思过程先根据近期经历提出值得回答的高层问题，再检索相关记录，要求模型生成 insights 并指出证据编号。它可以基于更早的反思继续形成树状认识，因此来源依赖既是能力来源，也是错误放大的路径。原文的重要性阈值和一天反思次数属于其模拟环境配置，不是所有应用的建议值。[Generative Agents，§4.2，PDF p.10](readings/Generative_Agents_Interactive_Simulacra_of_Human_Behavior.pdf#page=10)

对研究助手，可把“多次下调资本开支”组织成事件链，并形成待验证的高层假设；不要把模型的因果猜测改写为公司披露。讲义 p.56 的消融是在行为可信度设置下比较架构，不能当作财务事实准确率，或者直接证明所有企业任务都需要同样的反思频率。

## 7. 架构四：记忆维护决定系统会不会越用越乱

新增记忆通常容易；可靠删除和修订更难。有效维护包括去重、冲突检测、时间管理、压缩、遗忘和权限传播。

讲义把 Memory Maintenance 单列一类：Sleep-time Compute 在当前请求之外提前处理上下文；A-Mem 将记忆构建、链接与演化交给专门机制；Mem0 展示提取与更新分离，并列出 ADD、UPDATE、DELETE、NOOP。它们共同说明维护是有成本的计算与状态转换，而不是索引建立后就结束。[L7，pp.57–64](slides/lecture07.pdf#page=57)

后台处理可以降低请求关键路径，但会产生任务积压、读取旧状态和重复提交。工程上要定义原始事件提交边界、后台批次 ID、可见版本和失败恢复；同一事件重复投递时不应反复添加同一条事实。主调用成功与后台记忆更新完成应分别观测。

### 7.1 冲突先分类，再决定合并

- **同义重复**：相同事实的不同表达，可以合并但保留来源。
- **时间变化**：去年计划与今年修订可以同时成立，应保留事件时间并更新当前状态。
- **口径不同**：集团与母公司、金额与比例、预测与已实现值不能直接合并。
- **真实矛盾**：相同期间、主体、口径却给出不同值，需要标记冲突并回查。
- **权限差异**：私有笔记与公开公告可能描述相同实体，但不能因此合并为所有人可见的条目。

一个简单的当前状态键可以是 `(tenant, entity, attribute, period, accounting_basis)`。这是工程上的起点，仍需按具体领域调整。没有实体规范化和口径字段，向量距离再精细也无法保证更新作用在正确对象上。

历史查询还需要两条时间轴：事实何时有效，以及系统何时得知它。10月14日收到一份追溯修订10月1日数据的公告，“现在回看10月1日的修正值”和“截至10月1日当时已知什么”应返回不同视图。只按 `valid_from` 过滤会把后来得到的知识泄漏进历史回测；应同时保存原始披露/取得时间、修订关系和查询的知识截止时点。[工程推导]

后台维护也不能靠最后写入获胜。若worker读到事实版本v2后开始生成摘要，而用户已把它纠正成v3，worker完成时应检查其依赖版本；不匹配就重新计算或保留为候选，不能覆盖v3。可以用条件更新、事务与稳定批次ID保护“读取依据—生成结果—激活条目”的关系。这样修正才不会被慢到达的旧摘要悄悄撤销。[工程建议]

### 7.2 遗忘不是只有 TTL

TTL 适合明确会过期的临时状态，例如本次网页操作的短期缓存。对历史事实，时间过去并不意味着应删除；它仍可能是解释演变的证据。可以降低默认检索优先级，同时允许按历史日期查询。

撤回和删除则需要覆盖原始记录、摘要、嵌入索引、缓存和副本。只把数据库主行设为 deleted，却保留已经组装进下一轮 prompt 的摘要，不算完成删除传播。生产系统可以使用墓碑记录、来源依赖图和索引重建任务，并在输出路径做最终状态过滤。

这项保证针对受管理的存储与后续使用：正在排队的旧上下文要失效，已启动的调用应按系统能力取消或阻止其结果再次进入记忆；已经交付给外部接收方的内容不能靠本地删除追回。外部记忆删除也不等于模型权重遗忘。验收时分别记录可检索副本、活跃上下文、外部处理和备份的处理状态，不能用一次向量删除宣称所有信息已消失。[工程边界]

### 7.3 新旧知识的竞争必须可观察

当用户明确纠正偏好，系统应记录纠正事件并更新当前偏好。若新陈述可能是玩笑、引用或临时要求，应该保留上下文而不是盲目覆写。对于“这次请详细一点”，合理动作是本次任务覆盖默认长度，不必自动修改长期偏好。

可记录 `activated_by`、`last_confirmed_at`、`confidence_basis` 和 `superseded_by`，但一个看似精确的 0.92 分值并不等于真实概率。未经校准的模型自评分更适合作为排序特征，而不是事实确认凭据。

## 8. 检索与上下文预算：相关不等于值得放入

记忆检索先限定访问范围与有效版本，再比较候选价值。Generative Agents 原文组合的是 **relevance、recency、importance**，分别归一化后加权；其中recency按距最近访问的时间衰减。它衡量近期活跃程度，并不判断业务事实是否过期。下面把这一机制改写为面向业务的教学评分，用有效时点相关的freshness替换recency；这是额外设计，不是原论文公式的原样复述。[Generative Agents，§4.1，PDF p.9](readings/Generative_Agents_Interactive_Simulacra_of_Human_Behavior.pdf#page=9)


$$
S(m,q)=w_r\,\operatorname{rel}(m,q)+w_t\,\operatorname{fresh}(m)+w_i\,\operatorname{importance}(m),
$$

访问范围与失效状态是过滤条件，不能因为相关性很高就在加权评分中抵消它们；最近访问、事件发生与生效时间也不能当成同一个时间戳。

其中 $m$ 是条目，$q$ 是请求，三个分量应先放在可比较的尺度上。权重不应凭公式外形就固定。对于历史追溯任务，freshness 还要相对于查询指定的历史时间计算；否则最新记录会压过正确的历史事实。

真正的组装是一个受限选择问题。设 $c_i$ 是第 $i$ 条记忆的 token 数，$B$ 是分给记忆的预算，$u_i$ 是对当前任务的预计收益，$z_i\in\{0,1\}$ 表示是否选入，则教学上可以写成：

$$
\max\sum_i z_i u_i\quad\text{subject to}\quad\sum_i z_i c_i\le B.
$$

它说明单位 token 的价值重要，但不是给出了一个已知最优检索算法。现实中条目有互补与重复：两个单独价值较低的事实可能组成关键证据链，两个高相似条目也可能完全重复。组装时还需要去重、保留时间与出处、确保原始问题和工具契约有足够预算。

**工程建议**：同时记录召回候选、过滤原因、最终装入条目、来源版本和 token 数。这样才能区分“检索没命中”与“命中了但组装时被截掉”。若有权限过滤，过滤结果应该在模型调用前完成；只在最终回答屏蔽敏感词会遗漏工具行为和侧信道。

## 9. 把企业研究助手完整跑一遍

设想用户连续三个会话：先要求跟踪公司 A 的资本开支；后来指出单位有误；再要求解释最新公告是否改变投资逻辑。一个可靠流程可以如下组织。

第一会话结束，保留原始查询、公告版本、抽取数值、计算过程和回答。提取候选“关注资本开支变化”，但不要把模型给出的投资判断直接标记为公司事实。工作记忆在会话结束后可以清空；有明确后续用途的事实、偏好与流程另行持久化。

第二会话出现纠正，先定位被纠正的数字与来源，写入修正事件；重新计算所有依赖它的派生指标；将旧状态标记被替代；提出候选程序性规则“读取表头单位再计算”。这时应评估规则是否适用于其他表格，而不是一次纠正后全局套用。

第三会话，先按公司、期间和权限过滤，再检索最新披露、旧计划和纠正记录。组装内容中同时保留“当时计划”“当前修订”和“差异依据”，使模型可以解释状态演变。若没有足够证据支撑因果解释，输出证据缺口，而不是从记忆中的旧假设推断管理层意图。

任务完成后，记录用了哪些记忆、忽略了哪些冲突、哪些结果获得确认。如果反馈只是“很好”，它可以作为用户体验信号，不能当作财务数字正确的标签。只有实际回查、业务确认或可执行校验才适合支持某些更强的质量更新。

这条流程不是要求每次都做完整知识图谱。可以先使用关系表保存事件与当前事实、对象存储保存原文、向量或混合检索找候选，再用明确键和版本规则完成更新。最小设计应能回答“哪次输入改变了什么，以后在哪些请求中会用到”。

## 10. 论文实验怎样读，才能判断对自己有没有用

MemGPT 的 DMR 任务基于 Multi-Session Chat。其构造了需要回忆历史会话的问答；基线看到历史的有损摘要，而 MemGPT 可分页查询完整历史。Table 2 报告 GPT-4 从 32.1% 到加 MemGPT 后的 92.5%，这里的条件包含特定历史模型、数据构造和评测器。不能解释成“任何企业助手加一层数据库就提高 60.4 个百分点”。[MemGPT，§3.1、Table 2，PDF pp.4–5](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=5)

该对照同时改变了历史访问方式和可保留信息量，因此它支持“这种系统组合在该任务上有效”，不足以单独归因于某一种替换策略。论文文档问答只抽取了 50 个问题，且部分评分使用 LLM judge；在对长尾、成本和现代更长上下文模型作判断时要保留这些限制。[MemGPT，§3.2，PDF pp.6–7](readings/MemGPT_Towards_LLMs_as_Operating_Systems.pdf#page=7)

你自己的最小对照可以包含：不保留跨会话状态、固定摘要、纯检索历史、分层工作记忆与检索、加入反思整理。保持模型、源数据权限、任务和预算一致；分别统计事实回忆、时间正确性、纠错能力、无关记忆引入率、隐私边界、延迟和费用。

任务至少包含以下类别：历史事实准确回忆；明确修订后使用新值；按声明的知识截止时点回答历史查询；同名实体区分；缺失证据时拒绝补造；删除后不再检索；用户临时要求不污染长期偏好。历史查询要区分“按当时已知信息”与“按现在核实的信息回看过去”，不能见到过去日期就一律返回旧值。只测“我叫什么名字”会遗漏最昂贵的生产故障。

### 10.1 本讲四个基准是在逐步改变“记忆成功”的定义

讲义 pp.68–94 用 realistic、long-context、challenging、verifiable 四个标准比较基准。关键进展不是单纯增加历史长度，而是从旧信息问答，逐渐走向必须利用历史才能完成的环境任务。[L7，pp.68–94](slides/lecture07.pdf#page=68)

| 基准 | 讲义中的信息源与验收形式 | 能观察到什么 | 仍需保留的归因限制 |
|---|---|---|---|
| LoCoMo，pp.70–74 | 长模拟会话，多类问题 | 跨事件、时间与多跳回忆 | 模拟用户会话与真实工具任务有距离；取回不等于正确使用 |
| PersonaMem，pp.75–80 | 偏好随互动演变，选择题 | 当前偏好、变化理由与近期信息 | 选择正确选项不等于能在实际操作中正确个性化 |
| LongMemEval-v2，pp.81–86 | Web Agent 轨迹，大量干扰轨迹与人工问题 | 工具经历中的细节回忆与规模压力 | pp.85 的文件/检索曲线还改变了底座模型，不能单独归因为存储方式 |
| MemoryArena，pp.87–92 | 多类可验证环境，逐步积累子任务约束 | 记忆参与真实任务执行的整体效果 | 失败可能来自规划、工具和执行，不能全部算作记忆失效 |

在 p.73 的表里，召回指标与回答 F1 分列，正好解释了本文开头的“检索命中”和“正确使用”两步。p.91 又明确提醒复杂任务的失败无法完全归因于记忆。反过来，某类 memory controller 在该任务较弱，也不足以证明所有自动记忆管理都无价值；应固定任务 Agent、记忆接口、模型与预算做消融。[L7，pp.73、85、91](slides/lecture07.pdf#page=73)

这些表格与结论在这里按讲义讲解，未把相关基准的全部原论文都当作本轮已精读复现。要选企业上线门槛，仍应加入自己的修订、历史查询、删除与跨权限任务。

## 11. 成本、收益与上线条件

记忆成本包含写入提取、嵌入与索引、反思整理、检索、上下文 token、额外模型轮次，以及修订与删除传播。只计算向量数据库费用会低估总成本。若每个会话都触发昂贵后台模型整理，而多数记忆以后从未使用，系统可能更贵也更慢。

一个教学收益模型是：

$$
\operatorname{NetValue}=N_{reuse}\,\Delta V-C_{write}-C_{maintain}-N_{read}\,C_{read}-C_{error}.
$$

$N_{reuse}$ 表示确实受益的复用次数，$\Delta V$ 是每次复用的业务价值；其余分别是写入、维护、读取和记忆错误造成的成本。它不是论文定律，只提醒我们：记忆的价值依赖未来复用，错误记忆还可能比没有记忆更危险。

适合优先保存的是稳定且经常使用的偏好、经过确认的口径和可复用操作经验。变化频繁、可以低成本实时查询的事实，可能更适合存来源与查询策略而非长期缓存结论。高敏感信息则需要更小的采集范围、明确保留目的和可验证的访问边界。

上线先允许记忆影响低风险建议；涉及交易、权限、外发或数据修改时，动作授权继续由明确的策略与工具接口执行。记忆中出现“用户以前同意过”不应成为无限期的通用授权。历史上下文与当前任务权限需要分别判断。

### 11.1 记忆污染和过度个性化也属于质量问题

讲义 pp.98–100 将程序性记忆投毒、隐私传播和过度使用旧偏好放在一起。外部网页、工具输出或历史模型回答可能包含指令；它们被提取为 Skill 后，影响会跨任务持续存在。记忆内容应作为带来源和可信等级的数据，不能因此取得比当前系统规则或工具权限更高的地位。[L7，pp.96–100](slides/lecture07.pdf#page=96)

过度个性化则可能发生在条目本身正确时。例如用户以前偏好激进假设，但当前任务明确要求保守压力测试。问题不是记忆真假，而是适用性错误。评测应包含“有相关历史但本次不应使用”的负例，并给用户可查看、纠正和删除的入口。

## 12. 诊断表：从症状找到需要检查的环节

| 症状 | 优先检查 | 有区别力的证据 |
|---|---|---|
| 反复忘记已经说过的事实 | 提取、索引可见性、检索与组装 | 原始事件、写入批次、候选列表、最终 prompt |
| 总是引用旧值 | 实体键、有效时间、替代关系 | 新旧来源版本和 active 状态 |
| 把两家公司混在一起 | 实体规范化、scope 过滤 | company ID、召回来源、跨租户命中 |
| 对新任务生搬旧经验 | 程序性条目的适用条件 | Skill 触发原因与前置条件检查 |
| 越聊越肯定错误结论 | 来源依赖、反思污染 | 高层条目的原始支持事件及模型推断标记 |
| 删除后仍出现内容 | 缓存、摘要和索引传播 | tombstone 版本、重建任务、上下文组装版本 |
| 费用上升但成功率不变 | 无效写入、低复用率、检索噪声 | 记忆使用率、消融、每成功任务总成本 |

调试应从最早出现错误的边界开始。最终回答错误不一定说明记忆检索差；也可能检索完全正确，但模型在比较期间或计算单位时误用了它。保留中间产物可以让下一轮修改针对真实失效点。

## 13. 自测与参考答案

**问题 1：把完整 session 写进数据库，是否已经实现长期记忆？**  
答案：实现了原始历史持久化。还需定义提取、检索、组装、修订和行为评测，才能说明它具有可用的长期记忆能力。

**问题 2：MemGPT 的“无限上下文”意味着模型能一次看见全部历史吗？**  
答案：不能。它通过有限主上下文与外部存储交换信息，检索返回后才进入推理。可存储容量、检索可达性和任务准确率是三件事。

**问题 3：用户说“这次要详细报告”，应覆写“偏好简短”吗？**  
答案：先作为当前任务要求。只有明确表达长期偏好变化，或持续反馈经确认后，才更新长期默认值；保存作用范围和来源。

**问题 4：旧值与新值冲突时，为什么不能简单按写入时间选最新？**  
答案：新写入可能是旧报告补录，或另一期间、口径、主体。先比较实体、指标、报告期、有效时间和来源修订关系。

**问题 5：向量检索命中正确条目，回答仍错，应看哪些记录？**  
答案：检查组装时是否保留、是否截断来源和限定条件、模型是否正确使用、工具计算是否采用正确单位；不能只看召回 top-k。

**问题 6：一个成功轨迹能直接变成全局 Skill 吗？**  
答案：只能作为候选经验。还需抽取条件和步骤、检查偶然依赖、在未参与生成的任务上验证，并保留版本与回滚。

**问题 7：为什么检索回忆正确率不能替代记忆系统的完整评测？**  
答案：它未覆盖新旧状态、删除、隐私、负迁移、过度个性化、成本和对最终任务的帮助；正确回忆也可能被用在错误场景。

**问题 8：怎样检验反思是否有用？**  
答案：在相同模型、历史和预算下，对比有无反思的系统，使用独立任务测正确性和证据追溯，再统计写入与读取成本。不能只展示一条看起来聪明的总结。

## 14. 本课实施清单与阅读顺序

先让系统能追溯原始事件，再分开事件、当前状态和操作经验；建立可查询的版本与 scope；实现最小检索和上下文记录；用修订、历史查询和删除任务建立评测；最后才决定是否需要复杂反思与自动技能生成。每多一层自动整理，就多一个需要独立观测和验证的状态转换。

阅读上先回到 MemGPT 图 3 和 §2，画出一条消息经历的存储与调用链；再用本案例区分工作区、原始历史和实体事实；最后用实验章节检查“对照究竟改了什么”。对今天的系统，原论文中的模型上下文长度、API 和性能数字是历史快照，不是当前平台能力说明。
