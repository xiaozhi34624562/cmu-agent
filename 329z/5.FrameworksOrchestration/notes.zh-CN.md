## 1. 先拆清楚：数据、系统和评测共同决定表现

讲义第10—12页把工程对象拆成Data、System/Model、Evaluation/Metric三个支柱。同一个模型，换一组示例、工具说明或工作流，就可能表现不同。DSPy 原论文把系统表达成由模块组成的文本变换图，并优化模块的提示或训练数据；HarnessTax 则在相同模型与不同 harness 的组合中同时测效果和成本。这两条证据共同提醒我们，系统表现不能只归因于底座参数。[L5，pp.10—18；R1，§3—5；R3，Experiment Setup]

为了便于工程分析，可以把输出写成一个教学函数：

$$
y=F(x;\theta,P,D,T,S,E).
$$

$x$ 是请求，$\theta$ 是模型权重，$P$ 是提示与示例，$D$ 是检索数据，$T$ 是工具，$S$ 是运行状态与控制流程，$E$ 是外部环境。它不是可直接求解的论文方程，而是一份归因清单。若版本变化时这些变量全部一起改，最终得分变化就很难解释。

一个可迭代系统还需要任务集、评分器、运行 trace 和版本记录。没有评测，所谓“更好的框架”容易变成体验印象；没有可追踪状态，失败时又无法判断是提示、工具还是恢复逻辑的问题。

## 2. 不同抽象分别管理什么

| 抽象 | 主要管理的对象 | 邮件与日历案例 | 不能自动提供的保证 |
|---|---|---|---|
| DSPy 式程序与优化器 | 模块行为及其可优化参数 | 从邮件提取结构化会议字段 | 时间真的存在、事件创建安全 |
| LangGraph 式状态图 | 步骤、状态和控制转移 | 提取、检查、确认、执行分支 | 图中的业务判断本身正确 |
| Agent harness | 模型与工具反复交互的运行环境 | 允许探索邮件、读取日历、修复参数 | 任意长任务都成功 |
| Durable workflow | 故障下的持续推进和恢复 | 用户明天确认后继续创建事件 | 外部写操作天然只执行一次 |
| Trace / eval 平台 | 记录、检查和比较运行 | 找出错时区、重复创建或遗漏确认 | 单靠日志就能证明因果 |

这张表是教学整理，不表示这些能力在某个产品中绝不重叠。一个框架可能覆盖多个层面，但选型时仍应指出这次依赖的是哪一项能力，以及它需要哪些配置和外部存储。

例如，只想改善会议时间抽取，不必先引入复杂的长任务编排；需要在人工确认后跨天恢复，就不能只保存最终聊天文本；需要查明会议重复创建的原因，也不能只看 LLM 调用耗时。

## 3. DSPy 的第一层：把输入输出任务声明为 signature

DSPy 原论文提出三个核心抽象：signature、module、teleprompter。signature 描述模块要完成的文本变换，例如输入邮件文本和当前日期，输出会议标题、开始时间与参与者；module 选择如何实现变换；teleprompter 通过数据与度量优化程序。[R1，§3]

signature 有点像服务接口，但原论文中的“自然语言类型”不是 Java 编译器意义上的静态类型。字段名、描述和可选说明帮助模型理解语义，实际输入输出仍需格式化、解析与验证。一个字段叫 `start_time`，不代表模型永远返回合法时区时间，也不代表它知道“下周五”以哪个地区日期为准。[R1，§3.1，PDF p.4]

教学上可以把任务声明为：

```text
输入：email_text, received_at, user_timezone
输出：intent, event_title, start_at, end_at, participants, evidence_spans
```

其中 `evidence_spans` 让时间和参与者能回到邮件原文。若原文只有“周五下午”，模型应该标记待确认信息，而不是编造 14:00。哪些字段可以缺失、哪些缺失必须停止，仍是业务程序要表达的条件。

## 4. DSPy 的第二层：module 是可组合行为，程序仍由代码表达

原论文的 `Predict` 接受 signature，维护模型配置与示例，负责格式化调用和解析返回；`ChainOfThought`、`ReAct` 等模块可以通过组合这些基本模块构造不同策略。开发者用普通控制流连接模块，而不是把全部逻辑塞进一个巨大的提示字符串。[R1，§3.2，PDF pp.4—5]

一个会议处理程序可以有“意图分类”“事件提取”“冲突解释”三个模型模块，也有时间规范化、权限判断和事件创建三个确定性步骤。优化某个模型模块的提示，不意味着要让优化器改写权限规则。

这种拆分有两个实用价值。第一，可以单独观察中间结果：会议是否提取正确、冲突是否解释清楚。第二，可以做局部替换：分类模块用便宜模型，困难时间表达用更强模型，而不改变外部日历工具的契约。

但模块多并不天然更好。相邻模块重复读同一封邮件，会增加 token 和延迟；过窄字段丢失背景，又会让后续步骤无法判断歧义。模块边界应该沿“可以独立验证的语义职责”设计，并保留必要证据，而不是沿每一句自然语言机械拆分。

## 5. DSPy 的第三层：用任务表现筛选有用的中间轨迹

DSPy 的编译不是把自然语言编译成一个可证明正确的程序。它根据数据、候选参数和度量搜索更好的程序配置。原论文主要关注自动构造、选择 few-shot demonstrations，也讨论微调与程序集成等优化方式。[R1，§4，PDF pp.6—7]

以 `BootstrapFewShot` 为例，先让教师程序或当前程序运行训练样本，收集各模块的输入输出轨迹；通过整体任务的 metric 筛选，把通过检查的中间模块行为收集为示例。若还要在多个示例组合间搜索和比较，原论文另给出 `BootstrapFewShotWithRandomSearch`、`BootstrapFewShotWithOptuna` 等实现；不能把候选生成与组合搜索都默认为基础 `BootstrapFewShot` 的同一个步骤。[R1，§4，PDF pp.6—7]

用教学符号表示：

$$
P^*=\arg\max_{P\in\mathcal P}\widehat Q_{\mathrm{dev}}(F_P),
$$

$\mathcal P$ 是候选程序配置集合，$P$ 可以包含示例选择、提示配置等，$\widehat Q_{\mathrm{dev}}$ 是开发集上的估计表现。式子不表示搜索一定得到全局最优，也不表示开发集最优就会泛化到生产。

在日历案例中，最终 metric 若只检查“事件创建成功”，就可能把时间错了却成功写入的轨迹当好示例。更合理的 metric 应同时检查时间与时区、参与者、是否有授权和是否重复创建；对有歧义输入，还要检查是否正确停在待确认状态。

### 5.1 成功轨迹不等于每个中间步骤都正确

最终回答正确，有时是后续步骤纠正了早期错误，有时是错误抵消，也可能是标签覆盖不完整。把整个成功轨迹全部当作金标准，会把坏的中间行为一起保存。工程上可以给关键模块增加局部约束，再和端到端 metric 结合；对来源与授权这类硬约束，不应用平均得分抵消违反行为。

### 5.2 优化数据和评测数据要分开

如果开发集反复被搜索使用，它已经参与优化。测试集应在选定配置后用于独立估计；对于重复邮件、同一事件的多封往来或近似模板，划分时应按事件或业务实体隔离，避免近重复泄漏。这里是工程推导，不是声称原论文解决了所有业务数据划分问题。

优化成本也要计入：候选生成调用、运行程序、评分器和重试都消耗预算。一个仅执行几十次的低频任务，可能没有足够请求摊薄大规模搜索成本；一个每天处理数万封邮件的稳定任务，则可能值得优化更便宜的模块。

## 6. 阅读 DSPy 实验时，系统和任务设定必须成套保留

本课复用的是 arXiv:2310.03714v1，而不是把后来的框架 API 自动当成原论文实现。原论文主要研究 GSM8K 数学文字题和 HotPotQA 多跳问答，比较不同程序、模型和编译策略。[R1，§5—7]

HotPotQA 的例子尤其有教学价值：单次 RAG 从原问题检索，可能缺少需要后续跳转的实体；多跳程序先生成查询、检索、累积上下文，再形成下一查询。表 2 因此把程序、编译器、模型、答案 exact match 和检索相关指标分别列出。[R1，§7，PDF pp.10—11]

这说明改进可以同时来自问题分解、检索方式和示例优化。不能把“多跳加编译优于单次 RAG”的分数差全部归给某一个提示优化器，也不能把 HotPotQA 的结果直接用作日历助手收益预测。本讲不复现论文分数，重点学习如何表达和比较可复现的“模型—程序—优化器—数据—metric”组合。

## 7. LangGraph：把任务状态和下一步控制显式化

官方概览把 LangGraph 定位为用于长时间、有状态 Agent 的低层编排框架，支持在同一图中混合确定性步骤与 LLM 驱动步骤，并强调持久化、人工介入、流式处理等能力。[R2，Overview、Core benefits]

概念上，state 是运行中需要传递和保留的数据，node 是读状态并执行工作的步骤，edge 决定后继步骤。图不要求每个节点都是 LLM：时间解析后的格式校验、冲突计算、权限检查都可以使用普通代码。

对会议任务，状态至少包含原邮件引用、结构化事件草稿、歧义项、冲突结果、用户确认版本、创建请求 ID 和外部事件 ID。把它们只压成一串聊天消息，会让恢复和重放都依赖模型重新解释旧对话；把关键事实独立成字段，可以明确判断当前已经完成什么。

一个合理分支是：发现歧义进入 `needs_clarification`，字段完整但未确认进入 `awaiting_approval`，确认对应当前版本且无冲突才进入 `create_event`。这里是业务状态图设计，不能期待框架自动猜出来。

### 7.1 持久化状态和长期记忆不是一件事

把某次任务运行状态写入 checkpoint，可以在同一任务中恢复；把“用户偏好上午开会”记录成长期信息，则需要跨会话选择、更新和访问控制。前者关注执行连续性，后者关注未来任务该加载什么信息。LangGraph 生态支持两类状态，但开发者仍要决定范围和生命周期。[R2；R4，Write context、Select context]

### 7.2 恢复不等于重新执行全部步骤

若用户已经确认事件版本 v3，进程中断后不应让模型重新生成 v4 并沿用旧确认。状态需要绑定内容版本与确认对象。若事件已经创建但回复发送前中断，恢复也应先读取外部事件 ID，避免创建第二份。框架的持久化能力必须和业务幂等一起设计。

### 7.3 同一个业务逻辑的第二种表达：课堂graph

notebook单元39用Pydantic的`EventDetails`表达结构化结果，单元40—44把`email`和`details`放在state中，`extract_node`读取邮件并返回部分更新，`START → extract → END`构成最小图。单元46—52加入emoji和status，`route`在事件名、日期与开始时间存在时进入后续节点，否则结束。[C5；L5，pp.53—75]

这里的条件edge是普通Python逻辑，模型负责字段抽取；二者的职责应分开。`TypedDict`帮助表达state结构，却不自动验证业务数据，Pydantic的格式检查也不证明日期来自正确邮件。图能画出来，只说明控制结构可见，不证明每个分支都满足需求。

单元54的`create_agent`实际上从`langchain.agents`导入，底层运行在LangGraph之上。讲义第76页把它概括为内置Agent工具，本讲按真实代码区分上层Agent构造器与底层图运行时，避免读者在错误模块寻找API。[C5，单元54；R2]

课堂构图调用`compile()`时没有传入持久化checkpointer，因此不能把这几行演示理解为已经实现跨进程恢复。LangGraph支持持久化是框架能力；本段示例实际启用了哪些能力，应由配置和运行验证判断，而不是从框架名称推断。

## 8. Durable orchestration：让业务流程跨故障继续推进

LLM 调用可能只持续几十秒，人工确认却可能等一天；长任务还可能遇到进程退出、机器重启、网络错误和远端限流。Durable workflow 的目标是把这些等待、结果和重试状态保存，使流程不依赖某个一直存活的 Python 调用栈。

教学上可以分成“控制逻辑”和“外部活动”：控制逻辑决定先提取、再确认、再创建；外部活动执行模型调用、访问日历或发送通知。恢复时哪些活动结果可以复用、哪些必须重试，以及外部副作用如何去重，需要由实现和业务契约共同保证。

对接任何 durable runtime 前，先回答四个问题：流程实例 ID 是什么；哪些数据持久化；中断后从哪个稳定边界恢复；重复调用某个活动会发生什么。只有说清这四点，“支持长任务”才有实际工程含义。

不应把持久化误解为无限重试。用户取消、权限撤销、事件已经过期或数据版本变化时，继续恢复旧计划可能更危险。正确的终止、补偿和重新确认也是流程设计的一部分。

### 8.1 Temporal演示的执行顺序与恢复依据

讲义第95—98页把activities、workflows、worker、task queue与服务端执行历史分开。课堂代码相应把LLM提取、emoji选择、日历写入定义成三类activity；`CalendarWorkflow`按顺序调用它们。workflow控制逻辑保持确定性，非确定的模型与外部I/O放到activity里，让已完成的结果可以从服务端历史重放。[L5，pp.95—106；C5，单元59—62]

`RetryPolicy`设置初始间隔1秒、最多5次尝试，每个activity有1分钟`start_to_close_timeout`。下一段的`flaky_select_emoji`人为在前两次尝试抛出503，第三次才执行模型选择emoji；server依据重试策略调度，而不是要求LLM重新猜测网络故障应该怎样处理。[C5，单元60、64—65；L5，pp.107—111] 这些是演示配置，不能据此给所有生产API设置同样的重试预算。

定时示例先启动子workflow创建事件，再`workflow.sleep(seconds)`。notebook先等待10秒后取消reminder worker，随后重新启动worker并等待结果；服务端记录的timer与已完成activity结果是恢复依据。[C5，单元67—69；L5，pp.112—117] 这里展示的是“worker停止、Temporal服务仍在”的恢复路径，不是完整服务端及持久存储同时丢失后的容灾证明。

还要区分**workflow重放不重复执行已记录activity**与**activity对外操作恰好一次**。tinycal服务每次创建事件使用新的随机ID，没有显式幂等键；若写入已成功但activity完成回执丢失，重试仍可能重复创建。课堂“恢复后只有一场会议”的展示不能证明所有故障点都不会重复。[C5，notebook单元59、69；`tinycal/server.py`的`_insert`创建逻辑] 生产需要自己的幂等与外部状态查询，这也是第4课工具执行边界的延伸。

讲义第92—93页引用METR的任务时间视角，并明确前一图是human-time。不能把“人类完成这类任务需要多长时间”的能力标尺直接换算为Agent真实运行时长；调度与预算应以实际trace测得的墙钟、token、工具等待和人工等待为准。

### 8.2 恢复契约要覆盖重试预算、取消和版本升级

示例的1分钟 `start_to_close_timeout` 限制一次activity尝试，不是整条workflow的1分钟截止时间。排队、退避、最多5次尝试和后续activity会继续增加总耗时；业务应另设整体截止时间与费用上限。取消也不等于回滚：若创建请求已经到达日历服务，停止worker或取消流程不能证明事件未创建，仍需查询与补偿。[C5，单元60、68；工程推导]

跨天流程还会遇到代码升级。恢复依赖已有历史，因此新控制逻辑需要能够解释旧执行记录，或让旧实例继续使用兼容版本；不能只更新依赖锁文件就假定所有存量流程可安全恢复。可将流程定义、模型配置、输入schema和已确认草稿版本一起记录，并在发布前用旧历史检查恢复路径。具体版本兼容机制依运行时而定，这里不提供未经运行验证的SDK配置。[承接 L5，pp.95—98、125、129 的工程建议]

对本课日历案例，最有辨别力的验收不是“重启后程序能跑”，而是分别中断在确认前、日历写入后但回执前、回执已记录后、提醒等待中，检查草稿版本、外部事件数和最终状态。它能区分状态保存、幂等和定时恢复是否分别成立；这些故障注入是建议的实验，本文未执行。

## 9. Agent harness：模型外围的执行系统会改变能力与成本

harness 管理模型调用、工具、上下文与任务推进。模型提供语言与决策能力，harness 决定它能看到哪些信息、以什么形式调用工具、何时停止、失败时如何恢复。它是系统行为的一部分，而不是完全中性的包装。[R3，Introduction]

比较两个 coding agent，如果一个拥有完整代码搜索、终端与测试反馈，另一个只得到单个文件，即使底座相同，也不等于比较同等条件。相反，给简单任务配很多冗长工具说明和默认指令，也可能增加成本而没有增加可测收益。

邮件日历助手同样如此。一个最小 harness 可以只有邮件搜索、邮件读取、日历查询、准备草稿和受控写入；业务类型逐渐扩展时，再依据失败数据增加工具。工具越多，选择和权限边界越难维护；工具越少，单个工具可能需要更强组合能力。选型应靠任务分布与评测决定。

### 9.1 从讲义的四个实例读出真正的权衡

讲义第82—85页列出mini-SWE-agent、OpenHands、Pi和OpenClaw的课堂快照。mini-SWE-agent以bash和线性历史为主，命令按独立subprocess执行；OpenHands强调事件记录、持久终端和停滞检测；Pi强调少工具、树形历史及精简控制；OpenClaw展示长驻入口、周期唤醒和文件化记忆。[L5，pp.82—85]

这些描述首先用于解释设计维度：独立shell中的`cd`或环境变量不会自动留给下一个命令，持久shell会保留状态却也可能携带污染；线性历史容易实现，树形历史便于分支却需要明确当前路径；周期触发改变了任务入口，还需要去重、预算与消息频率控制。不要把讲义中某个时刻的重复阈值、唤醒周期或夜间任务时间，当作所有版本和所有部署的固定协议。本轮没有逐一检出这些项目的源码验证，精确实现结论以其固定版本为准。

第87—88页进一步以Meta-Harness说明harness本身也可以成为优化对象。这里应和DSPy区分：被搜索的可能是工具、上下文或执行结构，而不只是一个模块的提示。讲义图提供研究方向，不构成本仓库已经运行自动harness搜索的证据。[L5，pp.87—89]

## 10. HarnessTax 给出的证据：别只盯成功率

HarnessTax 在两个基准上比较七个模型与三种 harness 的 21 个组合，每个基准抽取相同的 30 个任务，每个组合每题运行三次；使用官方评分器，并采用固定日期的直接 API 价格计算 token 成本。[R3，Experiment Setup]

作者观察到，在所测设置中，同一模型跨 harness 的成功率差异可能不大，费用却存在显著差异；较简洁的 Pi 也能达到有竞争力的效果与成本。这里应保留“在这些抽样任务和设置中”的边界，不能推导成复杂 harness 永远无用，或某个产品普遍更差。

实验还使用各 harness 的原生配置、高 effort 档和最多 100 agent turns，但 turn 与 effort 的具体含义遵循各自系统。这使实验更接近产品默认使用，却不等于严格统一了所有推理预算、上下文和动作语义。原文也提醒两个公开基准存在训练接触可能，真实交互开发或跨会话任务可能有不同结果。[R3，Experiment Setup、Ending Notes]

因此可以学习其比较方式：固定任务和价格口径，记录尝试间变异，同时报告质量与成本；不能把少量样本的均值排名当成生产必然排名，也不能拿不同定义的轮数直接解释因果。

### 10.1 为自己的助手画成本—质量边界

对同一封邮件任务，同时记录最终状态是否正确、生成与输入 token、工具次数、端到端延迟、人工接管率和外部副作用。若方案 B 成功率接近 A，但显著减少重复读取邮件和解释 token，就值得进一步做配对任务比较。

若平均成本更低，却把少数关键的权限错误或会议重复创建掩盖了，不能只看平均指标。可以把这些行为作为硬约束或单独报告的高优先级错误，再在满足约束的候选中比较费用与延迟。这是工程建议，并非原文采用的完整安全评测。

## 11. 观测与评测如何连成改进闭环

trace 描述一次运行发生了什么；eval 按预先定义的标准判断它好不好。LangGraph 概览把 LangSmith 作为调试、观测与评测的配套能力，但也明确 LangGraph 可以独立使用。[R2，Overview、LangGraph ecosystem]

一个最小可用 trace 应能重建以下事实：收到哪封邮件，使用哪个提示和模型，提取了哪些字段，哪条校验失败，日历查询返回什么，确认对应哪个草稿版本，外部写入是否确证。关键不在选择哪个品牌，而在于稳定的事件 ID、父子关系、数据版本和执行状态。

评测集可以从真实失败中构造：时区跨日、邮件引用旧会议、同一事件多封重复邮件、用户修改参会人、日历 API 超时但写入成功。每个失败至少需要一个可检查的预期终态，避免只有“应该更聪明”这种不可判定要求。

### 11.1 缓存、trace和工作流历史不要混为一谈

课堂`llm_cache.py`以prompt和模型配置字符串作为SQLite联合键，保存序列化后的模型响应；notebook单元6把它装入LangChain全局cache。[C5] 相同请求命中时可以重用响应，但这不是完整业务状态缓存，也不是Temporal执行历史。日历内容变化而模型prompt未变化时，缓存甚至可能重复旧判断，因此动态工具结果与数据版本需要被恰当地纳入上下文与评测设计。

cache命中时重复输出相同，不代表模型原生采样具有确定性，也不表示全部notebook重跑免费：未命中、配置变化、外部工具和服务仍有成本。讲义第8页与仓库README对演示费用的估算口径不同，不把任一估价作为当前运行承诺。本文没有运行付费notebook。[L5，p.8；C5，README]

MLflow、LangSmith与Langfuse在第119—121页作为观测示例出现；本讲不从一张产品图推断它们具有完全相同的存储、权限或采样语义。第125—129页更重要的工程要求是记录模型调用、工具调用、state变化、错误与预算，并构造自己的领域评测。除非研究一般coding能力，标准coding榜单不能替代公司内部助手的验收。[L5，pp.118—129]

然后一次只改变一个主要因素：先固定模型与数据检查提示优化，再固定提示检查编排与恢复，再比较 harness。多个因素必须同时改变时，应明确结果只能归因于整套方案，不能写成某个组件单独贡献。

## 12. 选型路线：从具体约束决定框架组合

如果目标明确、固定步骤和短任务足够，先用直接 API 加普通代码建立基线。遇到模型模块行为需要稳定优化时，考虑 DSPy 式模块与优化；遇到多分支、有状态或人工介入时，考虑状态图；遇到跨机器故障、长等待和活动重试时，考虑 durable runtime。观测与评测应从基线阶段就有，而不是等框架复杂后再补。

这条路线不要求把所有框架堆起来。每多一个运行时，就多一套状态、配置、版本和故障边界。若同时使用状态图与 durable workflow，要明确谁是业务流程的权威状态源、哪里记录外部活动结果、如何关联两个系统的运行 ID。否则“增强可靠性”可能变成两个系统都以为对方负责恢复。

**工程建议**：让外部副作用的权限和幂等检查保持在窄接口内；让模型优化器只调整允许优化的行为；让持久化存储持有可重建执行的事实；让 trace 保留足够版本信息。框架更换时，这些业务边界应能继续成立。

## 13. 自测与答案

1. signature 为什么不能替代服务端数据校验？
2. DSPy bootstrap 为什么可能保留错误的中间行为？
3. 开发集被优化器使用了很多轮，还能当最终独立测试吗？
4. “保存聊天记录”和“恢复日历创建流程”有什么差别？
5. 用户确认 v3 草稿后，模型生成了 v4，旧确认还有效吗？
6. 为什么 HarnessTax 的 turn 数不能直接当统一计算预算？
7. 一个方案更便宜、成功率相近，就能直接上线吗？
8. State graph 与 durable workflow 同时使用时，首先确定什么？

**答案**：

1. 自然语言字段只表达意图，实际格式、权限、时区和业务口径仍可能错误。
2. 整体成功不证明每一步正确，可能存在后续纠错或错误抵消；关键模块要额外检查。
3. 不能；它参与了选择，应用未用于优化的数据独立估计泛化，并控制近重复泄漏。
4. 恢复需要结构化阶段、外部回执、确认版本和副作用状态；聊天文本本身难以保证这些事实。
5. 通常不能，应绑定确认和具体内容版本，内容变化后按业务规则重新确认。
6. 各 harness 的轮次和 effort 定义不同，需结合 token、工具和真实耗时比较。
7. 还要验证任务覆盖、尾部延迟、关键风险、用户体验和恢复；均值可能掩盖严重失败。
8. 权威状态源、稳定流程 ID、活动结果和重试边界，避免双重恢复或重复执行。
