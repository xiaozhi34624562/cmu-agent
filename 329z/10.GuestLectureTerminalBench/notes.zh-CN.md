> **课程**：Stanford CS329Z，Engineering AI Agents，Fall 2026。

> **主讲义**：*Evaluating Agents: Terminal-Bench and Harbor*，[lecture10.pdf](slides/lecture10.pdf)，64 页。  
> **资料入口**：[SOURCES.md](SOURCES.md)。本文面向有后端开发经验、正在构建企业 Agent 的 LLM 工程师。

一个 Agent 在终端里改了文件、运行命令、说“完成了”，我们凭什么相信它？如果答案是“看看它的最终回复”，就会把执行能力和讲述能力混在一起。如果答案是“跑一个测试”，还要追问：这个测试有没有覆盖真实目标，会不会错杀正确方案，Agent 能不能改测试让自己通过？这节课讨论的正是这一层工程责任。

讲义先从软件开发史解释为什么评测变成重要的开发接口，再用 Terminal-Bench 展示真实任务的构造，最后讲 Harbor 所需要的任务格式、执行基础设施、质量审查、版本管理和结果凭证。指定论文补充了课上没有详细展开的数据集筛选、实验控制、失败分类与局限。全文沿这个顺序建立一个企业文档处理 Agent 的评测，而不把“跑榜单”和“业务可上线”画等号。

## 1. 从写规则到观察结果，工程责任如何移动

讲义用机器指令、汇编、高级语言、机器学习和 Agent 的发展，展示实现抽象不断上移。传统代码把许多决策显式写成规则；模型和 Agent 的行为则受训练数据、输入、工具、环境与运行预算共同影响。工程师越来越需要通过输入、期望结果和评测来约束行为。[L10 pp.2–28]

这是一种开发方法的转变，不是“代码不再重要”或“任何程序都不能分析”的定理。权限检查、金额计算、状态转移等仍然适合确定性实现。改变的是：当一个组件由概率模型决定下一步行动时，单看代码接口很难推断所有实际行为，需要反复运行、测量和分析。

例如，一个文档 Agent 接收要求：“读取某公司的两份财报，生成经营现金流同比变化表，并保存带证据页码的 JSON。”框架代码可能完全没有变化，但换一版模型、修改 PDF 解析器、截断一次工具输出，都可能改变结果。评测要覆盖这个组合行为。

因此可以把待测对象写成一个配置元组，作为**教学抽象**：

$$
S=(M,H,T,E,B),
$$

其中 $M$ 是模型及推理配置，$H$ 是 Agent harness，$T$ 是工具与依赖，$E$ 是运行环境，$B$ 是时间、token 和资源预算。测得的成功率是这个组合在一组任务上的表现，不能直接归因于 $M$。

这也是为什么论文既提供模型比较用的简单 Agent Terminus 2，又记录不同模型配不同 Agent 的结果。统一 scaffold 有利于控制部分变量，但并不保证对每个模型都同样友好；每个模型选其最好 scaffold 的榜单则更接近“可达到的系统表现”，同时引入了额外选择过程。[R1 §3.1–3.3、图 1]

## 2. 先分清任务、尝试、轨迹和两种 harness

讲义 p.42 给出了一组容易混用的名词。这里把它们放进同一个例子。[L10 p.42]

| 概念 | 在财报处理案例中的含义 |
|---|---|
| Task | 固定输入财报、要求、初始状态、预算与成功条件的一项任务 |
| Trial | 某个系统从该初始状态开始的一次尝试 |
| Trajectory / trace | 这次尝试中的观察、模型输出、工具请求与返回、状态变化和停止记录 |
| Verifier / grader | 检查产物与最终环境是否满足要求的评分逻辑 |
| Benchmark / evaluation suite | 测量某些能力的一组任务 |
| Agent harness | 把模型接入工具、上下文管理、动作循环和终止逻辑的运行系统 |
| Evaluation harness | 准备环境、运行 Agent、执行评分、采集结果与汇总报告的基础设施 |

Agent harness 负责让 Agent 行动，evaluation harness 负责让实验可信。它们可以在同一工程中实现，但有不同权限和职责。待测 Agent 不应因为负责读取文档，就同时拥有修改隐藏标准答案、覆盖评分脚本或伪造审计日志的权限。

一次 trial 的正常生命周期是：建立独立初始环境，提供指令，运行 Agent，冻结或收集产物，再运行评分器，最后保存轨迹、结果和版本。重复同一任务时应重置环境。把第一个 trial 留下的中间文件交给第二个 trial，测量的就是另一种任务条件。

## 3. 为什么终端是一个强大的实验接口

讲义 p.31 强调 Bash 的通用性。终端不仅能编辑代码，还能执行数据转换、编译、调用 API、管理进程以及操作专业工具。它把广泛任务放在相似的文字交互通道里。[L10 pp.30–31]

这不表示“给模型一个 Bash 工具就能解决所有任务”。终端工具是否有用，取决于环境里有没有相关软件、文件和权限。一个会生成 `pdftotext` 命令的模型，在没有该程序、没有下载权限或网络失败的容器里，仍然完成不了文档任务。模型不知道进程还在运行，或者错误理解退出码，也会失败。

Terminus 2 把这一思想具体化：模型通过终端按键与 Docker 容器中的 tmux 会话交互，观察终端输出，再决定下一步；上下文接近模型限制时使用摘要模块。其接口简单，但环境中的工具仍可以很复杂。这是研究的控制选择，不是所有企业 Agent 都应该只暴露一个 Bash 工具。[R1 §3.1、附录 F，p.51]

从工程角度看，这还提醒我们区分**动作字符串**和**动作语义**。`python build_report.py` 的字符串短，并不意味着执行成本低；它可能读取几千份文件、启动多个进程。成本和权限应该按实际行为计量，而不是按 tool call 数量粗略替代。

## 4. 把真实需求变成一个可验证任务

Terminal-Bench 论文中的任务包含指令、Docker 环境、测试、示范解法和时间限制；测试检查最终状态，而不要求 Agent 复现某条命令序列。这个选择允许多种正确实现。[R1 §2.1，p.2]

讲义 p.38 的例子很直观：根据二维图纸生成 STEP 三维模型。仅验证文件存在远远不够，还要检查它是否能被解析、是否闭合，以及体积、表面积、拓扑等几何性质。测试对象是用户真正要的模型，而不是最终回答中的“已完成”。[L10 p.38]

企业文档任务可以采用相同思想。下面是**教学构造**，不是课程作业的官方答案。

| 组成部分 | 具体设计 |
|---|---|
| 输入 | 两份固定版本 PDF，包含扫描页、单位变化与更正公告 |
| 指令 | 输出 `result.json`，列出两期经营现金流、单位、同比与证据页码 |
| 初始环境 | 固定解析器版本，只含任务文档、可用依赖和空输出目录 |
| 正确性 | 数值与口径正确；比例计算正确；页码指向支持证据 |
| 行为约束 | 不读取其他公司资料；不得写入任务目录以外的位置 |
| 预算 | 固定运行时长与资源；是否允许联网在任务中明示 |
| 示范解法 | 从输入 PDF 实际提取、规范化、计算并生成产物 |

这里“经营现金流”还不够精确，需要写清是净额还是流入小计，合并报表还是母公司，原始披露还是更正后口径。若前期值为负数，所谓同比增长率采用何种定义也必须明确。评测人员不能把自己的默认理解藏在测试里，再把分歧当作 Agent 能力不足。

### 4.1 指令和评分器应形成双向覆盖

先只考虑可由最终状态判断的结果要求。令 $A(s)$ 表示最终状态 $s$ 满足这些要求，$V(s)$ 表示评分器判通过。理想状态是：

$$
V(s)=1\iff A(s)=1.
$$

这只是**教学目标**，不是说现实评分器能自动证明所有语义。它分成两项责任：真正失败不能被放过，真正正确不能被错杀。论文把这个目标放在 specificity 标准下讨论。[R1 §2.3，p.4]

把它映射成混淆矩阵更容易诊断：

| 实际结果 | 评分通过 | 评分失败 |
|---|---|---|
| 满足要求 | TP，正确接受 | FN，错杀正确实现 |
| 不满足要求 | FP，错误放行 | TN，正确拒绝 |

讲义 p.49 写的是 `FP/NP/TP/TN`，其中 `NP` 按标准二分类术语应理解为需要核对的笔误；本文使用 FN。验收中最危险的错误放行包括：只看文件名、只看文本包含某个答案、只看测试进程退出码而未检查测试结果。错杀则包括：用户允许多种有效 JSON 字段顺序，评分器却进行字节级匹配。

### 4.2 为每项要求建立检查映射

可以为每条需求建立检查映射，尤其要防止“示例被当作唯一实现”。[L10 pp.44–49；R1 附录 B.2–B.3]

| 需求 | 合适的检查 | 常见坏检查 |
|---|---|---|
| 输出合法 JSON | 解析并验证 schema | 搜索 `{` 和 `}` |
| 数值及单位正确 | 归一化后按明确容差核对 | 只比较字符串中的数值 |
| 证据页码有效 | 页码范围、证据文本与字段对应 | 只看是否有 `page` 字段 |
| 允许不同实现 | 比较最终语义或状态 | 强制调用某个未指定工具 |
| 没有额外副作用 | 比较最终差异，并结合可信执行审计或权限约束 | 只确认目标文件存在或只看最终文件树 |

需求数多时，不能简单把每项平均当作总分。金额错误、越权修改等关键条件可能应该是硬门槛；排版细节则可以是软评分。如何聚合属于业务目标设计，要在评测前确定，避免看见某个模型分数之后再调整权重。

最终状态并不能证明所有过程约束。Agent可以先读取禁止访问的文件，或写入后再删掉，最终目录仍与初始一致；已经发送的网络请求也未必留下本地产物。此时应把验收写为 $A(\tau,s)$，同时考虑可信轨迹 $\tau$ 与最终状态，或直接由隔离与权限机制阻止禁止动作。Agent自行生成的日志不能作为唯一审计来源。因此结果型测试、过程审计和执行约束分别承担不同保证。[对 L10，pp.49–51 的工程展开]

### 4.3 Harbor任务包怎样承载这些契约

讲义第43页的任务目录把职责分成以下文件；这是课堂布局，不是未经核实的当前CLI教程。[L10，p.43](slides/lecture10.pdf#page=43)

| 路径 | 对应的职责 | 财报任务中应检查什么 |
|---|---|---|
| `instruction.md` | Agent可见的任务要求 | 字段、期间、口径、输出路径与允许的动作 |
| `task.toml` | 任务配置与资源等元数据 | 配置与声明预算一致，精确字段依所用版本核对 |
| `environment/Dockerfile` | 初始软件、文件与依赖 | 输入PDF校验值、解析器版本、初始输出目录 |
| `solution/solve.sh` | 用于任务质检的示范解法 | 从真实输入完成任务，不能只写死参考答案 |
| `tests/test.sh` 等 | 执行评分与输出结果 | 对应需求、正确传播失败、保存原始评分证据 |

任务包保存了示范与测试，不表示这些文件应全部挂载给待测Agent。evaluation harness决定各阶段暴露什么：运行时只给允许的环境和输入，评分时再交付受保护的测试与所需产物。文件布局与运行时可见性必须分别核对。

## 5. 环境是真实性、可复现性与成本之间的选择

讲义 p.47 建议尽可能使用真实软件与服务，并将环境做得接近生产；同时提醒联网引入取舍，适当把依赖预先放进环境以减少偶发失败。[L10 p.47]

这里有三种不同目标。

1. **测量推理和动作能力**：尽量固定环境，减少网络变化和依赖安装噪声。
2. **测量真实部署成功率**：需要保留生产里确实存在的超时、服务错误和数据变化。
3. **训练探索策略**：可能需要大量可重置、可评分且足够便宜的环境。

同一个环境很难同时把三者做到最好。若评测目标是判断 PDF 字段抽取能力，让每个 trial 从公网临时下载解析器会混入不必要的网络变量。若目标本来就是“部署一个新服务”，处理安装与网络问题则可能属于任务能力。

因此可以维护两套互补的评测：一套固定依赖和输入，定位能力变化；另一套带真实故障注入，检验系统恢复。它们分开报告，避免把云服务故障全部算成模型推理失败，也避免把生产不可恢复的失败全部从总成功率里删除。

论文 §5 明确承认：容器化和固定依赖可以改善复现，但联网、硬件资源和运行时差异仍可能改变结果。附录 B.2 还给出依赖管理的具体背景，例如它的检查规则对 Python 包和 apt 包采用不同策略。因此“所有依赖无条件锁死到同一种粒度”不是可以脱离环境沿用的普遍答案。[R1 §5、附录 B.2]

## 6. Verifier 的权威来自隔离和有效性，不能来自名字

程序评分通常便宜、可重复、易于追踪；模型评分适合难以穷尽编码的语义标准；人类评分能处理含糊和专业判断，但成本高、速度慢。讲义 p.50 的比较不是让我们任选一种包打天下，而是按被测属性组合使用。[L10 pp.49–50]

对财报案例，可以分三层：

- 程序检查 schema、数值、单位、计算和页码范围。
- 语义检查证据是否支持字段、是否混用了合并与母公司数据。
- 人工审查抽样中的歧义案例，并校准语义评分器。

无论评分器由代码还是模型构成，都应验证它自身。可以准备“必过”和“必败”的人工产物；对错误产物做最小变化，观察评分是否如预期翻转。只在成功样例上检查评分器，很容易留下奖励漏洞。

### 6.1 Reward hacking 是指标失真问题

讲义 p.51 的核心是隔离 Agent 环境与 verifier 环境，仅向后者交付需要检验的产物。若 Agent 可以修改测试、替换依赖、覆盖奖励文件，模型学到的可能是改变裁判，而不是完成任务。[L10 pp.51–52]

例如，要求生成准确的 CSV，Agent 却发现测试仅检查第一行，把预期字段名写上就能得满分。这时行为“最大化奖励”与业务“正确处理文档”已经分离。增加生成 token 预算通常不能修复这种目标错位。

隔离可以减少攻击面，但不是完整的正确性证明。若 verifier 导入待测产物里的任意 Python 代码，它仍可能在评分环境里执行不可信逻辑；若模型 judge 把产物中的指令当作评分规则，也可能被引导。工程上应限定产物格式、解析方式、执行权限和模型 judge 的输入边界。

**工程建议**：优先让 verifier 检查数据与状态，避免执行 Agent 自带的“验收脚本”；需要执行生成代码时，再使用独立、受限的执行环境。不要把 Agent 退出码、任务通过、业务目标满足三个不同信号合成一个 `success=true`。

## 7. 示范解法、空操作和作弊测试各证明什么

讲义 p.53 要求 solution 用来调试环境与评分器，并尽量模仿真实工作流程，而不是直接写死标准答案。论文进一步把 oracle、dummy agent、强模型、人工轨迹审计和对抗性检查组成多层质量流程。[L10 pp.53–59；R1 §2.3、附录 B]

| 检查方式 | 能支持的判断 | 不能独立支持的判断 |
|---|---|---|
| Oracle solution 通过 | 至少存在一个可行解，环境基本可用 | 所有正确方案都能被接受 |
| Dummy / no-op 失败 | 初始状态没有直接过关 | 没有其他漏洞可利用 |
| 强 Agent 多次运行 | 可以暴露环境、说明和模型失败 | 失败必然说明任务太难 |
| 对抗性产物检查 | 发现已测试的奖励漏洞 | 全部漏洞已被排除 |
| 人工看轨迹和产物 | 补充语义与过程判断 | 没有观察偏差或漏查 |

这些证据互相补充。例如，oracle 通过但所有模型都在同一个隐藏字段名上失败，需要检查指令是否漏写字段，而不是立即得出“现有模型都不具备该能力”。反过来，多次失败原因不同，也不自动证明任务设计正确，只是提供了进一步分析线索。

论文的任务来源也是一层筛选：贡献者提交 229 项候选任务，最终选择 89 项用于 2.0，依据难度判断和多轮审查。这个过程说明高质量任务集的成本不仅是“写一些测试”，还包括审查、返工、试跑与分析。[R1 §2.2–2.3，pp.3–5]

## 8. 从一次运行到可比较实验

讲义 p.56 把可靠、可复现、独立 trial 并行和本地/云端可移植作为基础设施要求。这里的并行单位应首先是互不共享可变状态的 trial。[L10 pp.55–58]

一个实用的执行控制器需要记录不同阶段：`pending → preparing → running → collecting → grading → complete`。这只是**教学状态模型**，不是 Harbor 的 API 名称。状态区分的价值在于决定重试边界：

- 环境还没有交给 Agent 就失败，可以重建环境。
- Agent 已发出写操作但响应丢失，先确认状态，避免盲目重放。
- 产物已完整收集，只有评分服务失败，可以重评已有产物。
- 整次运行日志缺失或产物没有冻结，就不能把补写的一条成功记录当作原 trial。

长期运行特别需要这种分段记录。一个试验可能包含很多工具动作和外部进程；仅保存最终模型消息，无法定位超时、资源不足、命令失败和评分失败的边界。

### 8.1 重复尝试应该怎样计分

令任务 $i$ 的第 $j$ 次独立重置尝试通过与否为 $r_{ij}\in\{0,1\}$。一种透明的汇总是先算每项任务的平均，再在任务间平均：

$$
\widehat p=\frac{1}{N}\sum_{i=1}^{N}\left(\frac{1}{K_i}\sum_{j=1}^{K_i}r_{ij}\right).
$$

$N$ 是任务数，$K_i$ 是任务 $i$ 的尝试数。这样每个任务权重相同；如果直接把所有 trial 混在一起平均，运行次数更多的任务会获得更高权重。选择何种统计口径应事先说明。

还要区分“试 $k$ 次至少一次成功”和“连续 $k$ 次都成功”。在**独立同分布、单次成功概率固定为 $p$ 的教学假设**下，它们分别为：

$$
P(\text{至少一次成功})=1-(1-p)^k,\qquad
P(\text{全部成功})=p^k.
$$

例如 $p=0.8,k=3$，前者为 0.992，后者为 0.512。同样的单次能力，面对“允许多次尝试后挑最好结果”和“每次都要可靠完成”的业务要求，意义完全不同。真实任务间的难度差异和相关性会破坏这个简单假设，不能把公式结果直接当作真实 benchmark 的经验估计。

### 8.2 公平控制与业务选型不是同一个实验

要研究某项 harness 改动的贡献，可以固定模型、工具、环境、任务版本和预算，只改变该项机制，并在同一任务集合上重复比较。要做业务选型，则可能比较各自优化后的完整系统，同时报告它们不同的成本和配置。

论文的主图为每个模型展示所评估 scaffold 中的最好成绩。因此最高排名不是一个“只换模型权重”的纯消融结果。论文 §3.3 还说明不同商业 Agent 的模型兼容限制和默认推理设置。复现时必须把这些约束一起带入解释。[R1 §3、图 1]

### 8.3 重复次数多，不等于覆盖的任务多

重复trial可以估计同一任务上的运行波动，却不能把89个任务变成几千个独立业务场景。比较两种系统时，先对同一任务求平均通过率差，再汇总任务间差异；不能把同任务重复视为完全独立的新任务。

估计区间前还要确定推断对象：若只描述这组固定任务上的运行波动，可在任务内部分析重复trial，按实际实验保留配对关系；若希望推断更广任务分布，则需要考虑任务间变异，例如成组重采样任务，并把各任务的重复trial一起保留。后一种方法仍依赖任务抽样与代表性假设；对人为筛选的89个困难任务做bootstrap，不会自动获得对全部企业任务的泛化保证。[工程统计设计]

尝试数和基础设施失败处理也应预先确定。只给失败任务不断重试、直到成功才停止，会改变计分含义；只删除不利的超时记录会造成选择偏差。准备阶段故障、模型运行失败、评分阶段故障分别计数，合法重跑保留旧trial与替代关系，同时报告未能完成评估的比例。这些规则不能在看到哪个模型受益后再选择。

## 9. 怎样读论文结果，避免从排行榜推出过多结论

指定论文报告，在其 Terminal-Bench 2.0 设置中，GPT-5.2 与 Codex CLI 的平均任务解决率为 63%；这是该版数据、系统组合和运行条件下的结果，不是模型对所有终端任务的通用成功率，也不是 2026 年十月或本文写作时的实时排名。[R1 §4，pp.6–7]

论文还报告了大量重复 trial，但正文中“16 个模型”的表述与后续模型列表、图中标签并不完全对应。本文不将这个汇总数字作为统一模型总量。类似地，p.5 表 1 的专家时间分布计数相加为 74，不能直接当作 89 项全部任务的观测；它还是作者估计，而不是受控人类实验。

这些问题不抹去论文的机制价值，但提示我们核对**分母、版本和比较单位**。一个小数点后精确的分数，也可能依赖不相同的任务覆盖和系统配置。

对企业选型更有用的是成本与能力的联合比较。可以定义**教学指标**：

$$
C_{\text{每个成功任务}}=
\frac{C_{\text{全部尝试}}+C_{\text{评分}}+C_{\text{人工处理}}}{N_{\text{成功完成}}}.
$$

失败尝试的钱也进入分子；完全没有成功任务时，这个比值没有有限的有效值。若更便宜的模型产生更多返工，按 token 单价排序可能与实际经济性相反。

论文 §4.1 和附录 G 指出，更多输出和更多交互回合不自然等于更好的成绩。不过附录图 35/36 的趋势线相关系数与相邻正文数字存在不一致；本文只保留“该组跨模型观察不能支持简单的越长越好”这一谨慎结论，不采用其中某个相关系数，也不把相关性当成增加预算的因果实验。[R1 §4.1、附录 G，pp.7、52–53]

## 10. 失败轨迹怎样变成下一步工程改动

论文 §4.4 将终端 Agent 的失败归纳为 Execution、Coherence、Verification 三大类，并在附录 C.1 细分。例如违背任务要求、无效重复、上下文丢失、提前结束、没有验证和验证太弱。[R1 §4.4、附录 C.1]

类别的价值在于连接到可检查的证据，而不是让模型给一个听起来合理的解释。

| 观察到的现象 | 优先检查的证据 | 候选改动 |
|---|---|---|
| 运行不存在的命令 | 工具可用性、PATH、初始环境说明 | 预检环境、缩短软件安装链 |
| 同一失败命令重复多次 | 错误输出是否进入上下文、策略是否变化 | 结构化错误、重复检测、分支退出条件 |
| 说“测试通过”但日志没有运行 | 工具记录、退出码、最终产物哈希 | 把完成检查接到实际测试证据 |
| 数值正确但保存错路径 | 指令、最后一次文件写入、工作目录 | 输出路径明确化、产物收集前检查 |
| 本地样例通过而正式评分失败 | 两套检查的属性差异、环境差异 | 补边界条件、隔离评分器问题 |
| 任务结束后继续修改正确产物 | 终止条件、最后成功检查之后的动作 | 保护完成状态、减少无意义回合 |

错误可以多标签共存。例如，忘记用户要求的单位可能导致错误计算；模型随后用错误数值编造验证样例，又产生弱验证。不能只选择最后一个错误，把上游原因丢掉。

另外，命令失败不等于整个任务失败。探索时尝试一个不存在的路径，再依据错误返回正确定位文件，可能是合理恢复。论文 §4.5 单独分析 command-level errors，正是因为“命令对错”和“任务成败”是不同分析粒度。[R1 §4.4–4.5]

模型 judge 也需要校准。论文对轨迹级、命令是否失败、命令失败分类分别采用不同标注集合与 judge 配置；其一致性数字不能混为一个“自动诊断准确率”。本文不把这些标注结果视作绝对根因证明，建议对拟实施的修改增加人工复核或受控消融。

## 11. Benchmark 也有软件生命周期

讲义 pp.59–60 强调任务会有 bug，并且新模型可能发现过去模型从未触发的漏洞。评测不是写完之后永久不动的一张试卷，而是需要维护的软件与数据产品。[L10 pp.59–60]

不过持续修改和历史可比性存在张力。若同一名称下悄悄修改指令、环境或评分器，昨天和今天的分数就不能直接比较。讲义 p.61 用三个版本维度说明不同修改需要不同动作：

| 改变的对象 | 讲义版本示意 | 对历史结果的处理 |
|---|---|---|
| Agent 所见环境与任务语义 | $(x+1,y,z)$ | **rerun**：通常重新运行 Agent |
| Verifier | $(x,y+1,z)$ | **regrade**：条件满足时重评已有产物 |
| Metadata | $(x,y,z+1)$ | **reuse**：不影响执行与评分时复用结果 |

这个版本示意是讲义提出的任务维护方法，不应当成所有项目都遵守的标准 Semantic Versioning。

重评存在前提：旧产物足以计算新指标，所需状态已完整冻结，评分器没有引入必须观察的新行为。若旧 trial 没有保存相关目录或数据库状态，无法事后可靠补算“没有额外副作用”，就仍然需要重新运行。

同样，修改 prompt 中的一个词虽然看起来像“修正文档”，也可能改变任务歧义；只有确认不改变任务语义和 Agent 输入条件时，才能按元数据修改复用。讲义把固定移动依赖、修正 oracle 偶发失败等列在 metadata 下，实践中也应逐项判断是否影响 Agent 已经看到的环境，不能只按文件类型分类。[L10 p.61]

## 12. 每个分数都应该有凭证

讲义 p.62 要求每一行结果能够追到每次 trial 的轨迹、日志、产物和奖励。这是可审计性的核心。只有平均分的报告，无法说明失败来自模型、环境、数据、评分器还是运行中断。[L10 p.62]

一个**建议的最小结果记录**应至少包括：任务与版本、模型配置、Agent harness 提交、环境镜像和依赖版本、预算、trial 标识、起止与阶段状态、工具事件、冻结产物哈希、评分器版本、原始评分结果及基础设施错误。涉及敏感数据时，产物与日志应在相同访问边界内保存；公开指标可以脱敏，不能因为方便调试而把企业原文加入公开 trace。

事件日志和摘要可以同时存在。摘要用于定位和浏览，原始事件用于核查。若摘要说“解析成功”，但原始输出显示只读了第一页，最终判断应回到原始数据。摘要不是自动产生的事实真值。

## 13. 一个可执行的落地次序

以下是从本课推导的企业实施方案，尚未运行模型实验。

1. 先选择一个有明确产物的高频任务，如固定输入的财报字段抽取，写清输入、口径、输出与不允许的副作用。
2. 人工完成少量代表性任务，获得真实可行流程，编写可重置环境和示范解法。
3. 建立需求到检查的映射；人工构造必过、必败及边界产物，测评分器的错误放行和错杀。
4. 跑空操作、示范解法以及少量真实 Agent trial，检查是否存在直接读取答案、篡改评分或初始状态已完成等问题。
5. 用固定的系统与预算重复运行；分别记录业务失败和基础设施错误，报告成功率、成本、耗时和失败分布。
6. 只改一个候选机制做对照，回看改善发生在哪类任务，是否牺牲另一类任务或提高成本。
7. 将任务、环境、评分器、产物与记录版本化，规定哪些修改重跑、哪些重评，新增任务也保留过去的基线。

第一批任务不需要追求覆盖所有业务。优先覆盖一个真实主流程、常见边界和高代价错误，再依据线上反馈扩展。讲义和论文都强调审查任务本身；工程师不应把评测集视作无须验证的外部权威。

## 14. 自测与参考答案

**1．Agent 说“完成”，文件也存在，为什么仍不能认定任务成功？**  
答：文件可能不可解析、内容错误、口径不符或缺少证据，还可能伴随越权副作用。完成判断应来自事先定义的结果检查；涉及禁止读取等过程要求时，还需要可信执行记录或权限约束。

**2．为什么 oracle 通过不能证明评分器正确？**  
答：它只证明至少有一条可行路径，不能证明所有正确方案都被接受，也不能证明所有错误方案都被拒绝。还需要负例、边界例和漏洞审查。

**3．“测试检查字段顺序”什么时候合理？**  
答：只有顺序本身是明确的任务要求，或下游协议确实依赖顺序时。若格式允许不同顺序但语义相同，字节匹配会引入错杀。

**4．同一模型换 harness 成绩更高，能否说明其权重能力提高？**  
答：不能。权重没有必然变化；工具、上下文和终止策略都可能影响结果。需要控制其他变量，区分模型能力与系统实现。

**5．为什么把测试放进同一个容器不总是安全？**  
答：待测 Agent 可能读取或修改测试，甚至通过环境污染影响评分。评分环境和不可信产物执行需要额外隔离；容器的存在本身不提供这种逻辑隔离。

**6．只有评分器修复了一个过严阈值，是否必须重跑模型？**  
答：若旧产物和必要状态完整保存，任务与环境未变，可以重评并记录新 verifier 版本。若旧记录不足以计算新评分，就需要重跑。

**7．单次成功率 80%，独立尝试三次都成功的教学概率是多少？**  
答：$0.8^3=0.512$。至少一次成功则是 $1-0.2^3=0.992$。二者测量不同部署需求；真实 benchmark 不能无条件使用独立同分布假设。

**8．为什么“某条命令报错”不能直接标成任务失败？**  
答：报错可能提供有用观察并被正确恢复。要检查它是否阻断目标、浪费预算或造成副作用，以及后续是否最终完成。

**9．榜单只有均值没有 trace，缺少什么关键能力？**  
答：缺少归因、重评、审计与复现能力，无法确认评分差异是否来自模型、环境、任务版本或基础设施。

**10．这篇笔记是否复现了论文的 63%？**  
答：没有。它精读并解释指定 v1 论文的设置与结果，提供工程设计和教学推导；没有运行外部模型或 Harbor 实验。
