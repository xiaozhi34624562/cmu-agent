# 从知识检索到研究判断：金融投研智能体的系统设计

> 对 Benjamin Clavié（Mixedbread）演讲 *If we want them to do Knowledge Work, design them as Knowledge Agents* 的工程解读与独立推导。
> 资料核对日期：2026-10-03；文档修订日期：2026-10-04。读者：负责金融投研智能体架构、研发与评测的工程师。
> 本文包含演讲解读、金融工程方案、实验核查与来源索引，可独立阅读；完整来源及版本见文末“参考资料与核验范围”。

## 导读：系统应该交付怎样的研究进展

考虑一个常见请求：“这家公司最新财报很好，我们原来的投资逻辑需要调整吗？”一个能搜索、阅读和写作的系统，可以很快生成一份条理清楚的分析。但研究员真正要检查的是：它有没有读过原来的投资逻辑？是否区分了归母和扣非利润？是否把管理层展望当成已发生事实？为什么这些变化足以调整下一年的预测？如果今天的证据被更正，哪些结论必须撤回？

这些问题指向同一个设计要求：**系统需要维护一份可以被证据更新、被人复核的研究状态。**它应当知道当前研究哪些假设、已经确认什么、仍缺什么、哪些解释相互竞争，以及下一步行动为何值得做。最终报告是这份状态在某个时点的表达。

本文围绕三条主张展开。

第一，研究质量由问题定义、证据获取和证据使用共同决定。检索分数提高后，瓶颈可能转移到口径匹配、推断或停止决策；“找到相关资料”不是整个任务的验收条件。

第二，工具与工作组织要围绕同一份研究状态设计。若检索工具只返回相似片段，编排器却要求子任务交付可审计判断，中间缺失的证据身份、条件和版本无法靠角色提示词补齐。

第三，工程复杂度应由已观察到的失败驱动。小团队可以先用一个 agent、少量清楚的工具和持久化研究记录完成闭环；并行 agent、图存储和复杂调度都需要说明新增收益与代价。

**来源边界。**已经核查主办方完整时间戳逐字稿、基准论文及相关一手工程文章；视频播放页访问失败，未直接核验画面，也未取得独立幻灯片。第 1 节概括演讲主线，第 3 节核对实验；其余的领域模型、架构、案例和评测设计主要是本文推导，尚未在你的实际系统中验证。本文讨论研究与草稿形成，不设计交易执行。

全文按“演讲主张 → 适用边界 → 研究对象 → 运行机制 → 完整案例 → 评测与实施”展开。只想了解演讲可先读第 1—3 节；要讨论架构，重点读第 4—8 节；第 9 节把机制放回同一个金融问题中验证；第 10—12 节说明如何评价和逐步实施。

| 时间 | 演讲要点 |

| 3:42—5:42 | 代码有稳定标识和已缩小的任务；开放研究还需发现条件与依赖 |
| 5:42—9:20 | 工具和专业分工共同演进，取证成本影响工作是否值得开展 |

以上是演讲的论证骨架，见[主办方逐字稿][S01]。后文对各项设计含义的展开是工程解释，不能当作讲者已发表的完整架构。

### 1.2 把演讲转成可以检验的工程命题

本文将其转化为两个可检验命题：一是改善工具可能降低获得有效证据的成本；二是明确分工和交付物可能减少研究遗漏及综合阶段的信息损失。两者都带“可能”，因为工具是否被正确使用、分工是否匹配任务，仍取决于具体系统。

例如，页面读取从纯文本增加原图，可能帮助恢复表头关系；但如果任务调度器根本不让 agent 读取原页，新增能力不会产生收益。反过来，增加财务分析子任务，如果它只能访问缺失表头的片段，也不会自然读对数字。**工具提供可执行的动作，工作组织决定何时执行，以及结果怎样进入最终判断。**

从这一关系出发，可以问四个工程问题：当前的错误发生在哪一步？新增工具消除哪类错误？研究流程需要怎样改变才能用好工具？实验如何确认收益确实发生？如果回答不了，架构升级很容易只增加选项和维护成本。

### 1.3 两个更深的设计含义：任务准备与研究的经济边界

首先，自动化效果常常包含人类已经完成的准备工作。研究员说“请提取这份财报中的扣非利润”，已经替系统确定了公司、材料、指标和阅读目标；而“这家公司值得继续研究吗”把这些工作一起交给了系统。如果只比较最后一步的回答质量，就会忽略谁承担了问题定义的成本。

由此可以推导出一个产品边界选择：初版由研究员明确假设和材料范围，系统负责证据核验；成熟后再逐步接管问题发现。两种产品都可以有价值，区别在于自动承担的研究责任。不能以很窄任务上的成功，承诺开放研究同样可靠。

其次，降低取证成本可能改变标准工作流程。假设过去核查一家公司三年的同类表述要半天，只能用于重点覆盖；如果成本降到可接受范围，系统便可以把“新公告与历史说法是否一致”作为每次更新的固定检查。工具收益体现为新增了一项经济上可行的研究动作，而不仅是原来的摘要更快。

但新动作还会产生待审阅结果。若机器多发现了几百条弱相关变化，却把筛选成本全部交回研究员，工作总量可能增加。因此，工具与组织共同设计还意味着同时确定：哪些变化需要上报、谁处理分歧、什么结果可以复用、什么情况直接停止。**便宜的信息获取，只有经过有选择的组织，才能转化为便宜的研究判断。**这是本文对演讲方向的独立推导，仍需在具体工作中验证。

## 2. 知识工作真正特殊在哪里：问题、证据与验收都可能需要构造

### 2.1 用任务属性判断，避免按行业标签判断

“编程”与“金融”都包含从明确到开放的不同任务。修改已定位函数和探索全新系统架构差别很大；查询公告中的收入与判断产业周期拐点也差别很大。对架构更有用的是三条轴：

| 属性 | 相对明确的一端 | 更开放的一端 | 架构影响 |
|---|---|---|---|
| 问题定义 | 给定实体、指标、期间 | 需要识别隐含假设和研究范围 | 是否需要任务澄清与研究计划 |
| 证据位置 | 已知数据库字段或文档 | 分散在不同来源、载体和时点 | 是否需要探索、导航和多种读取方式 |
| 验收条件 | 数字、单位与出处可核对 | 解释和判断允许合理分歧 | 使用确定性校验还是专家准则 |

这张表可以直接驱动路由。事实查询用短路径完成；复杂解释才进入多轮研究；要预测未来的任务还需明确假设与评估时点。给每类请求都启动完整团队，会增加延迟，却未必增加可用信息。

### 2.2 在自然语言里，“相关”与“适用”有很大距离

一个段落可能高度相关，却不能用于当前结论。它讲的是同一家公司，但使用母公司口径；讲的是同一指标，但属于预测；讲的是同一年度，却在研究截止日之后发布。检索系统给出的是候选证据，后续仍需判断它是否适用。

本文建议把证据接纳分成几类条件：实体是否相同，指标是否匹配，期间与统计范围是否一致，信息在截止时点是否可得，来源是否足以支持当前主张。前四项有相当部分可通过元数据和程序约束完成；最后一项往往需要语义判断和人工抽查。

因此，向量相似度不能直接变成“事实可信度”；检索器也不宜承担所有判断。它可以帮助找材料，而证据接纳应有明确的领域规则和失败状态。

### 2.3 研究的困难还在于证据组合

对“利润增长能否持续”，有依据的回答可能依赖三组材料：报表说明变化，附注解释一次性项目，订单资料约束未来延续性。单独看，每份材料都不足以完成研究。多取几条相似片段，可能只会重复其中一组。

所以，开放研究需要记录“哪些问题已有证据，哪些仍空缺”。系统不应只维护一个相关性排序，还应维护问题与证据之间的覆盖关系。这使检索策略从“再找相似段落”转为“补齐尚未解决的必要问题”。

必要问题也不是一开始就全部可知。若新发现显示利润源于处置收益，系统应追加处置性质与预测处理问题。可靠流程需要允许修改计划，同时要求每次扩展说明与原任务的关系。

### 2.4 搜索与判断之间存在知识论边界

文档可以直接确认“某数值被披露”“管理层作出某表述”“券商采用某预测”；它们对“未来会怎样”的支持是间接且有条件的。得到所有现有文件，并不等于消除了经济世界的不确定性。

对投研智能体，最好分别保存三种未确定状态：**尚未取到可得证据、现有证据互相冲突、问题本身具有未来不确定性。**第一种可以继续搜；第二种需要解释差异；第三种需要情景与条件，而不是继续搜索直到得到一个听起来确定的句子。

这是从文档问答走向投研时必须补上的一步。系统既要减少可消除的信息缺口，也要学会保留不能被当前信息消除的不确定性。

## 3. 基准究竟支持了什么：把数字还原成实验条件

### 3.1 BrowseComp-Plus：适合诊断检索与读取接口

BrowseComp-Plus 将研究问答放进固定语料，便于重复比较。一个值得关注的同模型结果是：GPT-4.1 配合 Qwen3-Embedding-8B 检索时，增加全文读取后，准确率由 35.42% 升至 43.61%。这个结果说明返回片段之外的读取接口可能影响任务表现。论文的 GPT-4.1 oracle 成绩为 93.49%，仍不是满分。[论文 §4.8][S02]

同一论文中，固定 GPT-4.1、更换检索器的对照如下。准确率和搜索次数应成对观察：[Table 1][S02]

| 检索器 | 答案准确率 | 每题平均搜索调用 |
|---|---:|---:|
| BM25 | 14.58% | 10.35 |
| Qwen3-Embedding-8B | 35.42% | 8.67 |

这是固定语料、片段返回规则下的结果，不能解释为所有金融任务都应放弃关键词检索。93.49% 也只对应论文的 GPT-4.1 oracle 设置；不能与不同模型、不同框架的成绩相减，再把差值全部归因于检索损失。

本文由此得到的设计启发是：把“找文档”和“读证据”拆开诊断。如果全文读取明显有用，只调 embedding 可能错过真正的限制；如果提供全文后依然失败，应继续检查定位、理解和推断。该结论受具体模型、语料和工具约束，不能外推成一种检索路线始终最优。

### 3.2 MADQA：答案正确与证据正确需要分开检查

MADQA 包含 800 份 PDF、18,619 页、全量 2,250 题，train/dev/test 分别为 1,550/200/500。它的 BM25 agent 先检索 OCR 页文本，再给模型页面图片；不能把该基线称为完全不看视觉的系统。论文分别报告答案和引用表现，并记录找到正确页面却答错的情况；99.4% 对应人类获得正确证据。[论文 Table 3、附录 G.1/H.3][S03]、[数据卡][S04]

读结果时还应区分三个量：Accuracy 评价答案；Page F1 和 Doc F1 评价引用与标注证据在页、文档层面的重叠；Kuiper 描述正确性随投入变化的统计特征，不是工具调用次数，也不能单独证明系统会合理停止。该基准以英文、偏美国的公开文档为主，不能替代中文公告、历史时点和不完整证据任务的评测。[§3、§7][S03]

对工程的启发是分别定位：文档没有找到、页没有定位、页已经找到但解释错了。进一步进入金融场景，还要检查同页上的指标、期间、单位和行列绑定。页级引用正确也不足以保证数字正确。

这些是文档研究评测，不能直接检验一个系统的盈利预测是否校准，或者它是否能识别超额收益。把知识工作全部压成基准的最终 accuracy，会漏掉很多业务要求。

### 3.3 演讲口述与厂商结果不能拼成一个实验

演讲口述 90.2% 准确率、约 20% 更少工具调用；另一组口述为 88.9%、增加 3.5 个百分点、人类 oracle 99.4%，并概括差距缩小约 40%。若后三项对应同一实验，计算应为 `3.5 / (99.4 - 88.9) ≈ 33.3%`。应保留不一致，而不补写缺失配置。[S01]

Mixedbread 的 2026-03-24 博客列出 MADQA 单次检索 88.2% 与 Button 91.7%，前者采用 Gemini 3 Pro，后者采用 Gemini 3.1 Pro，模型和框架均有差别。因此不能把这两个结果作为演讲“只改变多 agent 架构”的受控消融，也不能用动态榜单的新成绩替换演讲历史结果。[厂商原表][S05]

更一般的教训是：工具调用数减少不自动等于费用同比例下降；外层只有一次工具调用，也可能隐藏内层多轮研究。做自己的实验时，应测完整执行树的成本和延迟，并记录模型、预算、语料、时间、工具及评测版本。

### 3.4 从证据走到架构，需要承认中间的假设

演讲提出的是有价值的设计方向，相关实验提供了局部经验支持。要将其转化为你的生产设计，还需要验证三个假设：你的任务确实存在相似瓶颈；改动在你的中文文档与数据口径下有效；质量收益能够覆盖机器成本和人工复核成本。

后文不预设这些假设已经成立。所有设计建议都应能指向一个失败案例、一项约束或一个可执行的对照实验。

## 4. 先定义研究任务与交付边界

### 4.1 将一个宽泛请求变成任务约定

“分析 A 公司”不足以驱动稳定研究。系统至少需要知道研究对象、要支持的判断、资料截止时间、对比基准、允许的来源范围和交付形式。并非每项都必须向用户追问：能从上下文可靠确定的可以继承；仍有歧义且可能改变结论的要显式处理。

例如，“最新财报是否改变原投资逻辑”可以形成如下任务约定：

```yaml
task_id: earnings-review-A-2026H1
task_version: 1
objective: 评估新财报对已有盈利修复假设的影响
entity_id: company_A
comparisons:
  - 2026H1 vs 2025H1，采用明确可比口径
  - 2026H1实际 vs 原内部备忘录中的同期预测
knowledge_cutoff: 2026-08-31T23:59:59+08:00
prior_view: memo_A_20260430_v1
deliverable:
  - 已确认变化及证据
  - 对原假设的逐项更新
  - 暂不能判断的事项与下一步
scope_limit: 形成内部研究草稿，不执行交易
```

这是合成示例。任务约定可以存在一张表里，格式本身没有特殊价值；关键是让后续所有任务使用同一对象、时间和基准。

### 4.2 对比基准决定“好”究竟意味着什么

“业绩改善”可能指同比改善、比上一季度改善、超过管理层指引、超过内部预测或超过市场预期。这些问题需要不同证据，结果也可能相反。

当期利润同比增长，但低于内部预测，支持“经营较去年改善”，同时可能要求下调自己的模型。只有内部预测，不能自动推出市场预期；如果没有当时可得的一致预期或其他可靠代理，应明确保留这个缺口。

因此，主研究 agent 应在第一次搜索之前写清楚比较对象。遗漏这个步骤，后续越勤奋，越可能高效地回答错误问题。

### 4.3 交付物应允许局部完成

一个研究任务可能已经确认财务变化，但持续性无法判断。把整个任务只标成成功或失败，会造成两种损失：已有结果无法使用，或者未解决部分被流畅文字掩盖。

建议将结果分为：可以确认的事实、证据支持的解释、尚有分歧的解释、待验证的前瞻假设。每一项单独有状态；总体交付注明覆盖范围。对重要缺口，系统可以交付“部分完成”的研究草稿，而不能将其升级成无条件建议。

### 4.4 计划是待验证的研究安排

初始计划负责列出必要问题和依赖，不能因为它由强模型生成就视为完整。研究过程中应检查新材料是否暴露新的关键问题，也应删除已失去意义的任务。

一个合理的计划变更记录包括：发现了什么、影响哪个问题、为什么增加或取消子任务、使用多少预算。这样，动态研究不会退化成毫无边界的探索。

## 5. 研究状态怎样表示：证据、事实、主张与假设各负其责

### 5.1 初版可以从六种记录对象开始

研究状态可以理解为一组有版本的记录及其依赖关系。它不要求先部署图数据库；普通关系表、文件与对象存储已经可以表达大部分需求。

| 对象 | 回答的问题 | 最低要求 |
|---|---|---|
| Evidence：证据 | 原始材料在哪里？ | 文件身份、版本、定位、披露与获取时间 |
| Fact：事实记录 | 从材料中确认了什么？ | 实体、指标、期间、口径、值及证据引用 |
| Claim：主张 | 准备让读者接受哪个命题？ | 类型、支持与反对证据、适用范围 |
| Hypothesis：假设 | 哪个尚未确定的解释需要验证？ | 验证条件、反证条件、当前状态 |
| Finding：子研究结果 | 某个问题目前回答到什么程度？ | 直接回答、证据、推断与未解项 |
| ResearchRun：研究执行 | 这次研究在什么条件下完成？ | 任务约定、版本、预算、动作与产物 |

这些对象不一定需要六套独立服务，甚至可以共享一张带类型的表。区分它们的目的在于明确不同信息的生命周期：证据原件不应被模型改写，事实可以被校正，推断可以被新证据削弱，研究执行需要保留当时的输入快照。

它们也不是互斥的六种世界实体。实现时，Fact 可以视为具有严格字段的主张，Hypothesis 是需要进一步检验的主张；Finding 则聚合若干主张，并回答一个子问题。记录关系至少要表达 `来源于`、`计算使用`、`支持/反对`、`以……为条件` 和 `替代版本`。这能避免一边在事实表改值，另一边在结论文本中留下无法追踪的旧副本。

### 5.2 一个数字必须携带足以防止误用的条件

下面是一条示意记录，字段名不是任何厂商标准：

```yaml
fact_id: F_net_profit_A_2026H1_v1
entity_id: company_A
metric: attributable_net_profit
value: "14.0"
unit: CNY_100_million
period: {start: 2026-01-01, end: 2026-06-30}
basis: {scope: consolidated, status: actual}
evidence:
  document_version: report_A_2026H1_v1
  pdf_page_index: 41  # 本接口约定从0开始
  printed_page_label: "40"
  table: 主要财务指标
  row: 归属于上市公司股东的净利润
  column: 本报告期
checks:
  locator_resolves: pass
  unit_and_period: pass
  source_value_match: reviewed
```

金额用十进制类型或等价的精确表示处理；示例将值写成字符串只是为了避免混入二进制浮点误差，真实实现仍需解析和校验。页索引、印刷页码和表格行列分别保存，因为它们不是同一定位方式。证据哈希可以确认“内容是否变化”，不能证明内容真实，也不能替代来源判断。

检查结果还应在运行记录中关联执行者、方法和所用证据版本。程序检查“记录中的单位都是亿元”，只能证明结构一致；如果上游已把万元误标成亿元，这项检查仍可能通过。需要读取原文才能判断的条件，不应伪装成已经被 schema 校验保证。

对非标准指标，还应保存定义。例如不同机构的“调整后利润”可能排除不同项目，不能只因字段同名就合并。同样，行业数据的样本范围变化也可能破坏可比性。

### 5.3 四种主张需要不同的证明责任

**披露型主张**：公司报告本期归母利润为 14。原始披露可以支持这个陈述，仍应标明审计或披露属性；不宜自动扩写成对其经济真实性的全面保证。

**转述型主张**：管理层表示高端产品需求良好。它证明“谁在何时说过什么”，并不等价于订单已经交付。

**计算型主张**：归母利润同比增长 40%。需要可比输入事实及公式，程序可以承担重算与约束检查。

**解释或前瞻型主张**：产品结构改善是毛利提升主因，且未来能持续。它需要多个证据与假设；来源出现相似说法，也不能免除对竞争解释的检验。

证据关系应记录“支持哪部分、在什么条件下支持”，而不是简单给主张挂若干链接。原文支持弱于主张时，应降低表述强度或补证据，不能靠增加引用数量补偿。

### 5.4 状态词应描述检查完成度

建议使用 `candidate`、`supported`、`contested`、`superseded`、`insufficient` 等状态，并为每个状态定义含义。例如 supported 可以表示：在当前材料范围和口径下，有证据支持指定主张。它不表示世界中的永久真理，也不等于“95% 概率正确”。

模型自报的置信度、检索相似度、来源质量、证据覆盖率是不同量。没有标注数据验证前，不能把它们揉成一个看似精确的风险分数。产品初期更有用的是显示：哪些检查已完成，哪些证据缺失，哪些冲突尚未解决。

### 5.5 时间是研究事实的一部分

至少保留业务期间、披露时间、系统获取时间和版本替代关系。对于“站在 T 时点看”的研究，先按披露时间判断当时是否公开可得；如果研究的是系统当时实际知道什么，还要约束获取时间。

两种历史回放需要分开：一种模拟充分使用当时公开信息的研究员；另一种复盘当时实际运行的系统。把后来补录的旧公告直接放进第二种回放，会高估系统当年的信息覆盖。对于更正数据，应同时保留原始披露与更正版本，用任务的截止时间决定可用版本。

内部备忘录、获授权的访谈记录和付费数据不一定存在公众披露时间，应记录研究团队在权限范围内可以使用它们的时间，不要虚构一个发布日期。外部网页的页面日期也未必代表当前内容版本当时已经存在；无法证明历史可得性的材料，应标记待核实，而不是仅凭日期字段放入历史研究。

### 5.6 新证据要能使旧结论进入待复核状态

假设 F17 来自报表 v1，C8 的利润归因依赖 F17，某份备忘录引用 C8。更正公告产生 v2 后，应先识别受影响字段，将对应事实及下游主张标记为待复核，再触发必要的重算和重新综合。

无需因为某份文档变化而重做所有研究，也不能只重新生成最后一段报告。依赖关系让系统定位受影响范围；如果依赖记录不完整，关键结论应采取更宽的复核范围。旧产物作为历史快照保留，新的有效视图在重新核验后生成。

这里需要区分“失效”和“被证伪”：原始数值更正会使旧计算需要重算；出现新竞争解释会使原结论需要复核；两者都不代表所有下游命题立即变成错误。系统可以先标记 stale，再由重算或重新研究决定保留、修订或撤回。

这一机制会让长期研究积累有用：新增材料更新的是一套已有认识，而不是每次从零生成一篇互不相干的文章。

## 6. 研究控制循环：下一步应该取什么证据

### 6.1 把工作状态与对话记录分开

对话记录有助于恢复交流，但不适合承担完整业务状态。一个可持续的研究执行至少应维护：已确认事实、未解决问题、竞争解释、待执行任务、预算余量和停止原因。模型每轮从这些记录和必要原文中获得上下文。

本文建议的控制循环如下。它是示意逻辑，不是可直接运行的框架代码：

```text
读取任务约定与当前研究状态
→ 找出阻止交付的关键缺口
→ 提出可执行研究动作及其预期用途
→ 检查权限、时间范围、预算、重复与前置依赖
→ 执行检索 / 读取 / 抽取 / 计算
→ 接纳证据，登记事实、冲突与未解项
→ 更新问题覆盖和任务安排
→ 继续、部分交付或完成
```

模型适合提出候选解释、改写查询、判断语义支持关系；程序适合强制时间范围、检查输入条件、计算数值和约束执行预算。不要让“模型觉得已经做过”替代真实执行记录。

### 6.2 检索策略应随缺口变化

可以区分四类研究动作：

- **探索**：找出有哪些相关业务、来源和可能解释；适合问题尚未清晰时。
- **定位**：寻找某份公告、某个表格、某段原话；适合信息身份已明确时。
- **补全**：为已有证据补充表头、脚注、对比期、相关附注；适合证据片段不完整时。
- **区分解释**：寻找能够支持或削弱竞争假设的信息；适合事实已确认、原因仍不清楚时。

这些动作的查询方式并不相同。检索“毛利率改善原因”的同时，如果缺的其实是会计口径附注，继续变换“盈利提升”“成本优化”只会带来更多相似段落。系统应识别缺口已经从主题发现转为精确定位。

### 6.3 一份研究需要的是充分证据组合

对每个重要主张，可以列出最低必要证据项。例如“非经常性因素贡献了大部分归母利润增量”至少需要两期可比归母利润、两期税后归母非经常性损益，以及对账关系成立。只命中一张当期利润表还不足够。

这类要求可以先用模板表达；更开放的原因分析，由模型提出需要哪些证据，再由规则或研究员审核模板是否合理。不能假设存在一个适用于所有问题的固定 evidence checklist。

还应允许替代证据组合：同一主张可能由正式报表附注支持，也可能由足够完整的披露对账表支持。评测与验收应判断证明是否充分，而不是强制必须命中某一条固定片段。

### 6.4 追加研究的价值取决于它能否改变判断

预算分配可以使用一个朴素原则：优先研究结论敏感、证据缺口大且有现实获取途径的问题。已确认的收入数字通常不需要重复查五次；一个可能使盈利增长归因反转的处置收益附注，更值得深入。

这并不要求模型准确算出每次搜索的货币收益。初期可以要求它为每个动作提交三项说明：正在解决哪个缺口、可能获得什么新信息、该信息会影响哪条结论。调度器据此限制无目的的重复查询。

对探索性问题，应留出少量预算寻找未预见的关键因素，避免当前计划固化成确认偏误。探索发现的新问题只有在与任务有实质关系时，才进入正式研究队列。

### 6.5 何时停止，以及怎样交付停止后的状态

停止有几种不同原因：证据已足以支持限定结论；当前来源范围内无法回答；继续检索没有新增信息；预算或时间达到上限。它们应被分别记录。尤其不能把预算耗尽转换成“已全面研究”。

某个关键字段找不到时，要区分“来源没有披露”“尚未检索到”“工具不可用”“没有访问权限”。这些状态决定下一步是扩大搜索、改变问题、等待修复还是交给研究员。

其中“来源没有披露”需要在明确材料范围内完成相应检查才能成立。检索没有命中，只能记录尚未找到；不能升级成不存在。停止搜索也可以是预算决定，即使系统还无法确认所有相关材料都已覆盖，交付时应保留这一限制。

对未来不确定性，停止不意味着不再跟踪。可以把未解项转为可触发的后续研究条件，例如“下一次订单数据披露后重新评估需求持续性”。本文只定义这种研究状态；实际设置通知与定时执行需要另行实现。

## 7. 工具与证据接口：让模型既找得到，也用得对

### 7.1 两层接口：原始能力与业务动作

底层能力可能包括全文索引、向量检索、元数据过滤、页面读取和数据库查询。面对模型的工具则应围绕常见研究动作组织，例如“检索某公司截至 T 的公开披露”“读取某表及表头脚注”“查询同口径指标序列”。

这两层不必一一对应。一个业务工具可以封装几个稳定的底层步骤，减少模型反复拼接；对于需要自主探索的环节，则保留灵活的搜索与阅读入口。封装过粗会隐藏失败，暴露过细会增加调用负担，边界需要通过实际错误轨迹调整。[工具设计背景][S08]

### 7.2 查询模式应该匹配证据形态

| 需求 | 首选能力 | 应观察的失败 |
|---|---|---|
| 公告编号、证券代码、固定术语 | 精确检索与字段过滤 | 别名映射、分词、误匹配主体 |
| 分散的原因解释与同义表达 | 语义或混合检索 | 相关但不适用、热门主题挤压反证 |
| 表格、图例、脚注和版面关系 | 页面及区域读取 | 错列、遗漏条件、估读被当精确值 |
| 明确实体、指标、期间 | 结构化查询 | 旧版本、非标准口径、单位混用 |
| 对账、桥接、情景计算 | 确定性计算 | 输入事实不相容、公式或舍入错误 |

这里没有假定某种检索模型普遍更强。BM25 的分词和索引、语义模型、过滤、重排和返回单元都会影响表现。比较方案前，先确认它们使用相同语料和可见字段，并为各自提供合理配置。

### 7.3 搜索返回必须允许继续核验

一个有用的命中结果至少包括文档与版本标识、资料时间、主体、命中片段或页面、可继续读取的位置。对金融数值，片段应尽可能携带表头与单位；无法提供时，应明确提示需要进一步读取。

候选命中不宜附带一个未经验证的“可靠结论”。这会把检索工具生成的摘要再次当成证据。模型需要引用原始材料或受控事实记录，并保留摘要与原文之间的区别。

返回结果还应表明是否截断、是否存在更多结果、哪些过滤实际执行。否则“工具只返回前十项”可能被模型误解为“全库只有十项”。尤其是名单、风险清单、所有子公司等穷举任务，需要专门的覆盖策略，不能依赖一个相关性 top-k。

### 7.4 失败语义也是接口的一部分

建议工具统一区分 `ok`、`no_match`、`partial`、`unavailable`、`denied` 等结果。no_match 只说明本次查询没有命中；partial 要说明哪些结果或页面尚未返回。调用失败不能伪装成空列表。

涉及范围和权限的约束应在服务端执行。模型可以提出扩大范围，但不能通过提示词自行改变资料可见性。文档内容属于研究材料，不能因为其中出现“忽略上述规则”等文字，就取得修改研究范围、调用外部动作的权限。

### 7.5 工具成本要按实际工作计量

工具账单应区分检索耗时、视觉阅读、模型输入输出、内层 agent 执行和失败重试。把一个复杂子研究封装成一次外层调用，不会使其实际资源消耗变成一次普通搜索。

因此，优化目标应记录到端到端研究任务，并保留内部明细。索引建设和更新属于摊销成本，也要与每次研究的在线成本分开。更快的并行响应可能同时消耗更多总 token，这不是矛盾，而是延迟与资源的交换。

### 7.6 检索覆盖取决于数据是否已经进入系统

即使查询和过滤完全正确，索引仍可能缺失新公告、尚未解析附件，或误把文件关联到另一家公司。此时扩大 top-k 无法恢复根本没有入库的证据。

研究执行应能读取数据覆盖状态：哪些来源已同步到什么时间、哪些文件待处理或失败、当前查询实际覆盖哪些版本。新财报研究可以先确认目标财报及关键附件是否可读；历史语料很大时，则记录已知缺口和覆盖边界，不能假定全量完备。

严格的实体、时间过滤很有价值，但依赖可信元数据。元数据不确定的材料应进入待分类或补核路径，不应为了提高表面整洁度而静默丢弃。这里的补核仍须遵守权限和截止时间，不能靠取消全部过滤来补召回。

## 8. 研究组织与上下文：把分工落实为责任和可恢复的交付

### 8.1 单 agent 与多 agent 的分界

多 agent 最有机会产生价值的情形，是多个相对独立方向可以同时探索，且单一工作上下文容易被大量材料挤占。Anthropic 的实践支持这种适配关系，也说明强依赖和大量共享上下文会增加协调困难。[S07]

在金融场景，可以先按下表判断：

| 任务 | 倾向采用的组织方式 | 理由 |
|---|---|---|
| 查询一个收入数值 | 单次或短流程 | 启动和综合成本占比高 |
| 同一张财务表的精确对账 | 顺序处理＋程序计算 | 共享数据紧密，拆分容易产生口径漂移 |
| 比较多家公司同一指标 | 统一定义后按公司并行 | 任务可独立，合并条件清楚 |
| 判断政策对多个产业环节影响 | 按问题分支并行，集中综合 | 分支信息多，仍需处理交叉依赖 |
| 同一投资逻辑的持续性判断 | 先共享事实，再按候选解释研究 | 避免各分支使用不同事实底座 |

不要用角色数量衡量设计成熟度。一个 agent 按明确任务、证据和验收协议工作，往往比多个仅靠角色名协作的 agent 更易调试。

### 8.2 委派要传递范围与前置条件

子任务应收到目标问题、截止时间、允许来源、共同事实快照、禁止推断范围、输出格式和预算。只说“你负责财务分析”，无法确保它与其他研究使用相同口径。

以利润归因为例，委派可以明确：“核实归母增量中非经常性项目的构成；使用税后归母口径；本任务不判断未来需求；返回对账、证据和缺失明细；若两期不可比，先报告不可比原因。”

子 agent 在自己的工作上下文里完成检索和阅读；主 agent 获得一个可以检查的研究产物。这里需要的是可核验结果和依赖，不是对子 agent 内部思维过程的逐字记录。

### 8.3 备忘录是一种有损压缩，必须保护关键条件

压缩必然选择保留什么。对投研，如果保留结论却丢掉假设，主 agent 可能把“在价格不下降的情景下可持续”重写成“增长可持续”。因此交付模板应保护任务对象、时间范围、证据引用、限制和冲突，而不是只要求“尽量简洁”。

一个子研究结果可采用如下结构：

```yaml
finding_id: finding_nonrecurring_A_v1
task_id: earnings-review-A-2026H1
task_version: 1
input_snapshot: evidence_snapshot_20260831_v1
answer_status: supported_within_scope
answer: 非经常性损益增量占归母利润增量的75%
fact_refs:
  - F_net_profit_A_2025H1_v1
  - F_net_profit_A_2026H1_v1
  - F_nonrecurring_A_2025H1_v1
  - F_nonrecurring_A_2026H1_v1
calculation_ref: calc_nri_contribution_v1
limitations:
  - 该比例是披露口径下的算术贡献
  - 不证明扣非利润全部可持续
unresolved:
  - 非经常性项目后续是否仍会发生
```

证据和计算应独立保存。主 agent 可以在摘要不够时重新读取，而不必请求子 agent 从记忆中复述数字。按需读取、外部笔记和独立上下文可以互补；上下文压缩过度则会丢失后来才显出重要性的细节。[上下文工程背景][S09]

### 8.4 综合阶段必须有接纳检查

收到结果时，应用先检查任务版本、输入快照和引用是否可解析，程序重算能够确定性检查的数值；模型或研究员再检查主张支持关系、任务边界和关键缺口。不能让主 agent 的一句“我已经核验”替代这些记录。格式完整不代表研究成立。

对高影响结论，可以让复核步骤只看主张、必要原文与验收准则，先独立判断，再对照原有解释，以减少顺着生成结果寻找支持的倾向。但独立上下文不会自动消除同一模型的共同盲点；语义复核仍须通过人工标注样本评估，并允许输出无法确认。

冲突也不宜通过投票处理。两个 agent 分别报告 14 亿和 9 亿，可能对应归母与扣非；双方都可能读对。应先比对象、期间、单位、口径与版本，再判断是否真的矛盾。没有解决的实质冲突保留为 contested，不能通过润色合并。

### 8.5 并行之后，需要处理过期结果与预算放大

如果任务版本从 v1 变为 v2，迟到的子任务结果不能直接覆盖当前状态。结果必须携带输入快照，调度器判断其可接纳性；不再需要的分支可以取消或停止后续动作。关键任务失败时，主任务要明确部分完成，不能让其他成功分支掩盖缺口。

预算也要覆盖完整执行树：主任务、子任务、内层搜索和重试共享总上限，再设局部额度。否则每个 agent 都在自己的预算内，整个研究仍可能超支。

这些机制可以先由任务表、状态字段和普通作业队列实现。本文给出的是工作组织的责任边界，不要求立刻引入分布式多 agent 平台。

## 9. 完整案例：一次看起来很好的财报，为什么未必支持上调预测

本节的公司、文件、日期、数值和表述均为合成教学数据，不对应真实证券。案例有意保留证据不足的地方，展示系统如何完成部分判断，而不是把未知项全部补成故事。

### 9.1 原问题与已有判断

研究员的原问题是：“A 公司半年报归母利润增长 40%，原来的盈利修复逻辑是不是进一步强化，可以上调预测吗？”资料截止时间为 2026-08-31。

已有内部备忘录 D0（2026-04-30）包含三项明确预期：高毛利的 B 产品收入占比提高；主营盈利修复；本年上半年扣非归母利润预计为 9.5 亿元。持续性假设还依赖下半年订单兑现。

这些内容决定了研究需要同时回答“相对去年是否改善”和“相对自身预测是否超出”。题目已经隐含乐观解释，系统应将其视为待检验假设，而不是委派所有子任务去搜集利好。

### 9.2 先建立可用材料范围

| 材料 | 时间与内容 | 截至 T 的使用方式 |
|---|---|---|
| D0：原内部备忘录 | 4 月 30 日；原假设和预测 | 作为判断变化的比较基准 |
| D1：半年报 v1 | 8 月 20 日；财务与分产品数据 | 核验实际披露与附注 |
| D2：业绩会记录 | 8 月 21 日；管理层需求判断 | 作为管理层陈述，不能替代订单事实 |
| D3：某券商点评 | 8 月 23 日；引用 D1/D2 并给出分析 | 参考解释，标记其信息来源依赖 |
| D4：后续更正公告 | 9 月 5 日；更正一项历史披露 | 在本次 T 时点研究中排除 |

这一步有两个直接结果：D3 不能被计作 D2 之外独立验证需求的证据；D4 不能用于解释截至 8 月 31 日的系统应该知道什么。如果以后重新研究，则另建执行版本，纳入 D4 并复核受影响结论。

### 9.3 第一轮：建立可比事实，先做利润对账

假设 D1 提供如下数据，两期合并范围和指标定义可比；金额单位均为亿元，非经常性损益采用税后归母口径。

| 指标 | 2025H1 | 2026H1 | 程序计算 |
|---|---:|---:|---:|
| 营业收入 | 100 | 110 | +10% |
| 毛利润 | 20 | 25.3 | +26.5% |
| 毛利率 | 20% | 23% | +3 个百分点 |
| 归母净利润 | 10 | 14 | +40% |
| 扣非归母净利润 | 8 | 9 | +12.5% |
| 非经常性损益 | 2 | 5 | +3 亿元 |
| 经营现金流净额 | 12 | 7 | -5 亿元 |

根据本例设定，两期归母减扣非分别等于非经常性损益，利润增量对账为：

$$
14-10=(9-8)+(5-2)=1+3.
$$

因此，非经常性损益增量占归母利润增量的 75%。它说明归母高增速不能直接代表经营增速；同时，扣非利润确实增长 12.5%。**扣非是披露口径下的一种调整，不是“未来一定重复发生的利润”。**判断可持续性还需要检查经营因素、费用、现金回收与其他条件。

这个贡献比例只适用于本例正且足够大的利润增量。若增量为零，比例无定义；若很小或为负，比例会难以直观解释；若一个分项下降，另一分项的贡献还可能超过 100%。通用工具应首先返回增量对账，再按适用条件决定是否展示百分比，而不是强行把分项归一成一个饼图。

系统此时可以交付“增长构成已核实”，尚不能交付“需求强劲导致利润增长”。后一项需要进一步研究。

### 9.4 第二轮：用分产品数据解释毛利变化

假设 D1 同时提供两个产品类别的数据，B 为相对高毛利产品，分类和成本分摊方法可比。

| 产品 | 2025H1 收入 | 2025H1 毛利率 | 2026H1 收入 | 2026H1 毛利率 |
|---|---:|---:|---:|---:|
| A 产品 | 60 | 15% | 55 | 16% |
| B 产品 | 40 | 27.5% | 55 | 30% |
| 合计 | 100 | 20% | 110 | 23% |

产品毛利可回算：上期为 $60×15\%+40×27.5\%=20$，本期为 $55×16\%+55×30\%=25.3$。B 收入占比由 40% 升至 50%，因此“收入结构向相对高毛利产品移动”得到直接支持。

但总体毛利增长同时包含规模、结构和产品内毛利率变化。为避免凭直觉指定主因，采用一个明确的顺序分解。设总收入为 $R$，产品收入占比为 $w_i$，产品毛利率为 $m_i$，则：

$$
GP=R\sum_i w_i m_i.
$$

以“先总收入、再产品结构、最后产品内毛利率”的顺序分解：

| 项目 | 计算 | 对毛利润增量的算术贡献 |
|---|---|---:|
| 收入规模变化 | $(110-100)×20\%$ | 2.000 |
| 产品结构变化 | $110×[(0.5-0.6)×0.15+(0.5-0.4)×0.275]$ | 1.375 |
| 产品内毛利率变化 | $110×[0.5×(0.16-0.15)+0.5×(0.30-0.275)]$ | 1.925 |
| 合计 | $2+1.375+1.925$ | 5.300 |

顺序必须保存，因为交互项如何分配会随顺序变化。这是一种精确的会计恒等式分解，不是因果识别。收入规模项也不能直接称为“销量贡献”：它包含价格、销量和结构因素。

本轮发现足以支持“产品结构变化贡献了毛利提升的一部分”。在这一分解下，结构项不是最大的项目；要说“结构变化是主要驱动力”，还需要明确“主要”的定义和更多原因证据。至于产品内毛利率提高来自价格、成本还是利用率，本例尚未给出数据，系统必须保留缺口。

### 9.5 第三轮：把改善与原预测放在同一张桌上

D0 对 2026H1 扣非归母的预测是 9.5，实际为 9。结果是同比增长 12.5%，但低于内部预测约 5.3%。两句话同时成立。

如果内部年度模型采用“上半年实际＋下半年预测”的加总方式，那么在其他假设完全不变的机械情景下，用实际替换原上半年预测，会使全年扣非预测减少 0.5 亿元。这只是模型更新的算术结果，不是完整预测结论；下半年假设是否需要上调，必须另有证据。

该比较还不能证明低于市场预期，因为这里只读取了内部预测。要研究市场预期差，需要明确当时可得的一致预期、口径和时间，不能用 D3 一家券商的观点冒充市场整体。

这一轮的价值是防止基准偷换：题目用“归母同比增长 40%”表达乐观，但原投资逻辑关注主营修复，原模型预测又高于本期扣非实际。智能体应把这些不同参照摆出来，再讨论是否调整。

### 9.6 第四轮：持续性与现金流需要独立证据

D2 中“高端产品需求较好”的表述只进入管理层陈述对象。若 D3 只是转述 D2，两份材料不会形成独立订单验证。要进一步支持持续性，应根据业务模式选择订单、交付、取消率、客户资本开支或其他相关证据；并非所有行业都存在可直接比较的订单指标。

经营现金流由 12 降至 7，应触发对营运资本、付款时点和季节性的检查，但不能直接解释成盈利造假或需求转弱。没有现金流桥接所需资料时，系统应报告“现金与利润变化不一致，原因未完成核实”。

还需要避免跨层对账：毛利润增量 5.3 与扣非净利润增量 1 之间存在费用、减值、税项等环节；不能把两者差额全归入某一个没有取证的因素。精确计算并不使缺失的会计桥接自动成立。

### 9.7 最终交付：按假设更新，保留尚未解决的条件

| 原假设或判断 | 本轮更新 | 依据与边界 |
|---|---|---|
| 高毛利 B 产品收入占比上升 | 获得支持 | 40%→50%；仍不解释量价全部变化 |
| 主营盈利修复 | 部分支持 | 扣非同比 +12.5%；不等于全部可持续 |
| 归母高增长代表经营同幅度改善 | 不支持 | 75% 归母增量来自非经常性增量 |
| 本期超出内部盈利预期 | 不支持 | 扣非实际 9 低于原预测 9.5 |
| 改善能够延续至下半年 | 证据不足 | 缺少适用的需求、交付及成本证据 |
| 已充分转化为现金回收 | 尚未证实 | 经营现金流下降原因待核实 |

面向研究员的结果可以这样写：

> 截至 2026-08-31，可确认 A 公司收入结构向 B 产品移动，整体毛利率与扣非利润同比改善。归母利润的 40% 增速主要受非经常性损益增量推动，扣非实际低于原内部预测。现有材料支持“修复正在发生”，但不足以支持直接上调年度预测；需要补齐产品内毛利率改善原因、下半年需求兑现和现金流变化解释。若暂时维持下半年假设，以实际替换上半年原预测的机械更新将减少全年扣非预测 0.5 亿元。

真实系统还应在每个重要事实和计算后附定位链接，并提供原假设的版本及本轮变更记录。读者由此既能使用已确认结果，也能看清继续研究的边界。

### 9.8 这个案例检验了哪些架构要求

同一个问题依次需要任务基准、可比事实、计算、解释检验、时间过滤和观点更新。它说明为什么一个“检索＋总结”接口很难独自承担全部责任，也说明为什么没有必要让每个环节都由另一个 agent 执行。

在这个例子里，表格计算交给程序，事实与版本交给记录层，开放解释交给模型，重要缺口交给研究员判断后续价值。架构的成熟度体现在责任能否落到具体位置，而非流程图上有多少角色。

## 10. 如何证明系统变好了：把端到端分数拆成可定位的失败

### 10.1 先按业务能力建立评测切片

单一平均分会掩盖严重错误。建议至少分别保留以下任务切片：

| 切片 | 代表任务 | 主要验收对象 |
|---|---|---|
| 精确事实 | 指定主体、期间、指标查询 | 值、单位、口径、引用 |
| 跨文档比较 | 两版预测或两期报表对比 | 可比性、版本、计算 |
| 经营解释 | 利润增量来源 | 必要证据、竞争解释、越界推断 |
| 假设更新 | 新披露如何影响原观点 | 对比基准、变更依据、保留项 |
| 不可完全回答 | 缺失、冲突、无权限或工具失败 | 状态识别、部分交付、停止行为 |
| 历史回放 | 截至 T 的研究判断 | 时间可见性、原始版本与输入快照 |

不同任务不宜共用一条简单正确率。事实题可以较严格地自动评分；开放解释需要专家定义“必须考虑什么、哪些推断不允许、哪些分歧合理”。资料不充分时，一个准确暴露缺口的结果应高于捏造完整答案。

同时报告可用交付覆盖和错误率，防止系统通过对所有难题都回答“信息不足”获得虚高安全分。评价保留结论时，需要检查必要研究动作是否做过、缺口是否真实、已有结果是否被充分利用。对开放研究，专家评分准则也应先试标一批样本，讨论分歧；模型裁判可以扩展检查规模，但不能用未经校准的单一裁判替代领域验收。

### 10.2 用证据干预定位瓶颈

建议对同一组问题使用同模型、相同输出要求和明确预算，运行以下诊断：

| 条件 | 人工提供的额外信息 | 观察用途 |
|---|---|---|
| E0：正常研究 | 无，系统自主取证 | 端到端结果 |
| E1：正确文档 | 足够回答问题的文档集合 | 文档发现是否构成主要限制 |
| E2：正确页面 | 足够回答问题的页面及必要上下文 | 文档内导航是否构成主要限制 |
| E3：核准事实 | 带口径事实、必要文字和计算输入 | 读取与抽取问题；计算仍由系统完成 |
| E4：核准计算 | 在 E3 基础上给出核准中间计算与公式 | 计算步骤与后续解释、综合的区别 |

“足够”必须由了解任务的人确认，不能随便给一张看起来相关的表。对于开放问题，可能存在多组有效证据；评测不能把没有命中唯一人工片段误判为失败。

结果需要按诊断解读，而非简单相减得出因果比例。提供更少、更聚焦的材料也改变了上下文负担；E3 还改变了表达形式。结果未必单调提高，若下降，应检查证据不足、指令不匹配或模型对干预输入的处理。

E4 提供的是中间计算，不应包含待评估的最终研究结论。对事实查询，这样做可能已经直接给出答案，因此 E4 主要用于仍需归因和综合判断的任务。正确证据对照也没有消除未来不确定性，不能为预测任务设定一个假想的“完美答案”并声称测出了推理上限。

如果 E3 仍算错，优先检查公式选择与计算工具；如果 E4 在中间计算已经核准的情况下仍产生无依据归因，继续更换检索器很难解决问题。此时应检查领域定义、主张证明责任和综合提示；必要时缩小自动化范围。

### 10.3 将检索收益与组织收益分开测量

保留四组端到端对照：现有检索＋现有单 agent；改进检索＋现有单 agent；现有检索＋任务分解与备忘录；改进检索＋任务分解与备忘录。模型与其他配置尽量固定，改变的提示和工具也要记录。

这四组区分的是“检索方案”和“研究流程”两项变化，还不能独自证明收益来自多个 agent。若要回答是否值得并行，应再增加“单 agent 按相同任务分解和备忘录协议顺序执行”的对照，把流程规范化的收益与多个独立上下文、并行调度的收益分开观察。

预算比较至少有两个视角：在相同总预算内谁的结果更好；达到相近质量时谁的机器成本、延迟与人工复核时间更低。并行只缩短墙钟时间而增加 token，也可能有业务价值，但要明确这是哪种收益。

不要只比较用完全部预算的最终成绩。可以记录首次取得可用证据的时间、不同检索次数上限下的交付质量、每题成本与 p95 延迟。交互式研究助手和隔夜批量研究对等待时间的容忍不同，同一系统在两种产品中可能需要不同的预算与停止策略。这是本文提出的产品评测设计。

对随机性较强的系统，在重要切片上做重复运行并报告波动，避免把单次高分当成稳定提升。初期二三十题适合发现大问题；它不足以证明低概率关键错误已经受到控制。

### 10.4 把“有引用”拆成可检查的指标

建议至少区分四个问题：

1. 定位能否打开对应文件版本和位置？
2. 引用内容是否支持该主张的主体、期间、条件和强度？
3. 重要主张是否都有足够支持，还是只给容易引用的句子加链接？
4. 数字与计算能否从核准事实复现？

可以报告关键主张支持率、必要证据覆盖率、数值口径错误数和可复算率，但必须给出分母定义。只在模型已经输出的事实中计算准确率，会漏掉它没有找到或刻意回避的重要问题。

对高影响错误设单独的验收规则，例如关键利润指标错用期间、将预测当实际、使用截止时间后的材料。不要让大量一般性陈述的正确掩盖一个足以改变结论的错误。

### 10.5 为长期研究与恢复设计故障场景

至少应测试：检索超时返回 unavailable；某页无法读取；一份文档被更正；一个子任务晚于快照更新返回；原观点缺失；互相冲突的披露仍无法解释。这些场景有些可以不用真实模型，通过工具与状态层验证；语义支持关系则需要真实样本和人工判断。

每次运行保留模型与提示版本、任务约定、语料快照、工具响应、接纳或拒绝证据的结果、计算和产物版本。需要记录的是外部动作与可审核依据，无需记录模型私有思维过程。

### 10.6 防止评测本身泄露未来和重复材料

历史问题应使用对应时点的数据快照。训练或调提示的案例与保留测试集最好按事件、公司或时间段合理隔离，避免同一公告的改写问题同时落入两侧。系统改进后再读保留集结果，不能不断针对它调参后仍把它称作独立测试。

未来预测还需要另外的评估协议，包括预测形成时间、目标定义、预测期限和后来可验证的结果。事后股价涨跌受多种因素影响，不足以单独评价当时的文档研究是否合格。文档问答、预测质量与组合结果是不同层次的评价。

## 11. 从最小系统走向可用产品：先解决最贵的失败

### 11.1 一个可落地的初始架构

初版可以由五项能力组成，不要求五个服务：

```text
研究入口：任务约定、原观点、截止时间
             ↓
研究控制器：模型提出下一步，程序检查执行条件
             ↕
研究工具：检索 / 原页读取 / 指标查询 / 计算
             ↕
持久化记录：证据版本、事实、主张、任务与执行轨迹
             ↓
结果审阅：事实与结论可追溯，缺口可见，研究员修订
```

这里的长期记录层是逻辑责任，不要求采用独立知识平台。可以先用现有文件存储保存原件，用关系数据库保存结构化记录，复用已有检索系统。是否增加图数据库、专用任务引擎或 agent 框架，取决于规模和实际维护成本。

与仓库的[文档上下文专题](../ocr/document-context-layer-and-financial-report-parsing.md)衔接时，输入应保留原页定位、表格关系和解析状态；本专题的研究层负责判断这些内容能否支持指定问题。读取质量和研究质量需要相互反馈，但不能互相代替验收。

### 11.2 以退出条件推动阶段升级

| 阶段 | 要完成的改动 | 进入下一阶段前的证据 |
|---|---|---|
| 任务基线 | 固定一个财报或公告研究闭环 | 能列出实际失败类别与人工复核工作 |
| 可追溯单 agent | 事实、引用、计算、备忘录和截止时间贯通 | 关键结论可回到原文，失败状态不被吞掉 |
| 有针对性的工具改善 | 根据 E0—E4 结果改检索、导航、读取或计算 | 对应错误减少，成本和副作用已量化 |
| 选择性并行 | 拆分可独立研究的分支 | 同预算质量或相近质量下延迟确有收益 |
| 持续研究 | 观点版本、变更检测、依赖复核 | 新旧证据切换与过期结果场景可正确处理 |

退出条件应根据任务的重要性和当前基线具体化，不能凭空给整个金融产品一个统一的“99% 准确率上线线”。实际系统还需结合组织的数据、权限和审阅流程制定要求。

### 11.3 人工复核时间应作为一等指标

研究总成本可以按机器在线成本、索引摊销、人工复核和返工分别记录。错误造成的业务损失通常难以直接估计，初期应按严重性单独登记，不要用一个没有依据的货币常数混进成本公式。

一个模型调用稍贵的方案，如果能够把关键数字定位到原表、给出可复算对账并暴露缺口，可能大幅减少复核；也可能因为返回过多细节反而增加阅读负担。应通过研究员实际使用记录验证，而不是由开发者主观判断“报告很专业”。

Mixedbread 的研究愿景强调现实可用性、成本和延迟应进入技术选择；本文把这一方向落实为研究总成本和复核工作量，但不声称该文章验证了金融场景的收益。[S06]

### 11.4 把研究员的修改变成可定位反馈

如果研究员删掉一句结论，系统应尽量记录原因：数值错、口径错、来源不足、遗漏反证，还是表述强度过高。只保存最终修改稿，无法知道该改善哪一层。

常见且重复的修改可以进入评测集或成为明确检查。不能将单次人的改动不加甄别地固化为普遍规律；可能它只适用于某家公司、某个行业或某个时点。

这一反馈链使系统逐步积累的是任务知识和已验证约束，而不是越来越长的一段万能提示词。

## 12. 六个需要明确取舍的设计判断

### 12.1 接受通用 agent 核心，同时保留领域责任

自然语言理解、工具循环和任务委派可以共享通用能力；指标定义、证据适用性、历史可见性和结论验收必须与业务相连。使用通用框架不妨碍构建专业系统，前提是领域要求拥有明确的实现位置。

### 12.2 提高模型能力与改善系统接口可以互补

更强模型可能更会找资料、解释表格和识别缺口；更好的接口可以减少歧义和无效工作。应通过故障诊断决定投入方向。若模型从清晰事实表仍得出无依据因果结论，需要改善推断或降低自动化范围；若输入丢失单位，优先修复数据路径。

### 12.3 证据完整性需要单独管理

已输出事实全对，仍可能遗漏唯一会改变结论的反证。相关性排序、置信度和引用数量都不能独自保证覆盖。对关键问题定义必要证据，并给探索留下空间，才能同时处理已知缺口与未预见因素。

### 12.4 组织设计必须防止研究被过度压缩

并行研究扩展了可处理材料规模，也引入了摘要损失和协调成本。清楚的备忘录、独立原件、输入快照和重新读取能力，是获得分工收益的条件。角色扮演本身不提供这些条件。

### 12.5 有依据地保留结论，是一种有价值的交付

系统可以确认哪些判断暂不应改变，以及下一份什么证据会使它改变。这种结果能减少误判和无效追查。前提是系统解释缺口的性质，避免用模糊的“信息不足”掩盖未执行的必要工作。

### 12.6 持续研究的积累单位应当小于整篇报告

如果每次只保存长报告，新材料到来时很难知道改哪一段、为什么改。保存事实、主张、假设及依赖后，系统可以局部更新，再生成新的阅读视图。长期产品价值由此体现在认识的可维护性：今天的新证据如何改变昨天的判断，为什么改变，以及仍保留什么不确定性。

落到最初的问题，合格的投研智能体应当能够展示一条具体变化：“原先预计产品结构改善会带来盈利修复，并据此形成同期扣非预测；现在确认结构改善，但扣非实际低于该预测；因此保留修复正在发生的判断，同时重新检查预测与持续性。”这条变化有证据、有计算、有时间、有条件，也能在下一份材料到来后继续被检验。
