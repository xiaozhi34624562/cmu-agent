# 导论：先建立完整系统模型

## 0.1 为什么“知道很多功能”仍然做不好 Agent

设想一个文档研究助手。它能检索资料、提取数字、生成报告，你已经接入了工具调用、MCP、JSON 输出和长上下文。但下面的失败仍然可能发生：检索服务超时，被解释为没有资料；引用的段落真实存在，却把半年收入写成全年收入；报告已经写入系统，调用方没有收到回执，恢复后又写一次；子 Agent 在旧版资料上完成的结果，覆盖了新版任务状态。

这些问题不是同一种“幻觉”。第一个属于错误语义丢失，第二个属于事实绑定错误，第三个属于副作用结果不确定，第四个属于并发状态过期。**先把失败归到正确的层，才知道应该修工具、数据结构、事务还是上下文。**否则，每次都加一句“请认真核对”，只是改变输出分布，没有解决责任归属。

Anthropic 的官方实践把 Agent 看作模型与工具、环境、验证流程共同形成的系统，而不是一条更长的提示词。本书采用这个系统视角，但下述分层与实验结构是本文为教学设计的。[R02]、[R39]

## 0.2 一个够用的理论模型：模型提议，系统决定是否执行

可以把第 t 步写成：

```text
真实环境 x_t  --工具观察-->  当前信息 o_t
                              ↓
                  模型依据上下文 c_t 提出动作 a_t
                              ↓
                  应用检查参数、权限、前置条件
                              ↓
                  执行工具 → 得到新观察和可能的环境变化
```

这里最重要的不是公式，而是 **c_t 不等于 x_t**。模型看到的只是选择、检索、截断、压缩之后的信息；真实文件可能已修改，工具可能只完成一半，外部写入可能发生但回执尚未到达。因此，模型的“我认为可以执行”不能替代系统对当前真实状态的检查。

从决策角度，模型在回答“根据我掌握的信息，下一步做什么可能有帮助”；编排器在回答“这个动作是否允许、是否已经做过、预算是否足够”；工具在回答“实际发生了什么”；验收器在回答“这些实际结果是否满足原任务”。这四个问题必须分别有实现位置。

本书不是要把模型从流程中排除。检索措辞生成、任务探索、语义判断、候选方案提出，恰恰适合交给模型。需要隔离的是**概率性判断**与**必须成立的系统不变量**。不变量指的是不能因模型措辞变化而改变的条件，例如“未批准版本不发布”“同一业务动作重试不重复写入”“缺失字段不被当作已检查”。

## 0.3 四种状态：为什么只保存聊天记录不够

| 状态 | 例子 | 主要责任方 | 不能代替什么 |
|---|---|---|---|
| 协议状态 | 本轮模型要求执行 `tool_use_id=t1` | 模型接口适配层 | 不代表业务已经成功 |
| 工作流状态 | 已检查 7/10 份材料，等待人工确认两项 | 编排器与任务数据库 | 不代表文件内容仍是原版本 |
| 领域事实状态 | 某公司、某期间、某口径的收入得到指定原文支持 | 证据与事实登记层 | 不代表可以对外发布 |
| 外部副作用状态 | 报告版本 v3 已写入目标系统，回执为 p17 | 业务系统与回执记录 | 不会因清空会话或回滚提示词而消失 |

这四种状态没有一个天然包含另外三个。恢复模型会话，可能让模型记得“准备发布”；但发布到底是否成功，必须查业务记录。将代码文件恢复到检查点，也不会自动撤销已经发送的邮件或数据库写入。官方会话与工作机制文档明确区分了这些边界；本文进一步用独立账本来实现它们。[R14]、[R39]

## 0.4 三条贯穿全书的主线

**控制流主线**解决“谁决定、谁批准、谁执行、何时停止”。它从领域一的编排开始，在领域二的工具与权限落地，在领域三的 CI 和 Hooks 中形成交付约束。

**事实与状态主线**解决“知道什么、依据什么、版本是什么、还缺什么”。它连接领域二的来源读取、领域四的语义中间表示，以及领域五的压缩与恢复。

**验证反馈主线**解决“怎样知道这次真的完成、改动真的变好”。它不等到最后才出现，而贯穿工具选型、提示词迭代、代码修改和上线评估。

这三条线交汇时，系统的输出才不只是一段自然语言，而是一个可验收的对象：

```text
任务要求 + 完成范围 + 产物版本 + 证据关系 + 校验结果 + 副作用回执 + 未解决事项
```

## 0.5 贯穿项目：证据型文档研究助手

我们使用合成公司、合成报告和模拟审批规则，不涉及真实投资建议或法规结论。输入包含 A 公司半年报告、年度报告、B 公司相似数字，以及待核查摘要。系统的目标是核对指定指标，输出带证据的结构化事实，再生成内部草稿。批准之后，只在本地 SQLite 中模拟发布。

关键要求不是“写得专业”，而是：对象、指标、期间、统计口径、单位、数值必须绑定；证据缺失或冲突必须显式保留；原文版本变化会使旧核验失效；批准绑定精确产物与目标；中断后能区分已完成工作和未决工作；重复调用不能重复创建同一业务发布。

主干设计如下，初版不引入多 Agent：

```text
明确任务范围
    ↓
检索候选 → 读取原文 → 模型提出候选事实
                              ↓
                   结构 / 语义 / 来源 / 覆盖校验
                              ↓
                     已验证事实集与未决项
                              ↓
                      草稿 → 人工批准
                              ↓
                可信发布服务 → 持久化回执
```

后续增加子 Agent、Skills、缓存、批处理，都必须说明它改善了哪一种已观察到的失败，而不能仅以“技术更先进”为理由。

## 0.6 “简单方案优先”不是拒绝复杂度，而是要求收益证据

假设方案 A 单次调用成本为 20 个自定义成本单位，60% 任务通过；其余任务需要额外花 120 单位人工处理。则每个任务的期望成本为 `20 + 0.4 × 120 = 68`。方案 B 花 40 单位，若将失败降到 10%，期望成本变成 `40 + 0.1 × 120 = 52`。在这组**假设数字**下，较贵的模型流程反而更便宜。

反过来，如果增加三个 Agent 只改善很少的失败，却显著增加等待时间、人工排障与维护负担，就不值得。这里要比较的是**合格业务产物的总成本**，不是单次 Token 单价，也不是演示中最漂亮的一条回答。

因此，本书每一章都采用同一个判断标准：先定义失败与验收，再提出干预，最后检查它是否改善了目标指标，以及是否引入了新的失败面。


## 0.7 为什么单步表现不错，整条任务仍然容易失败

再看一个理论上更严格的区别。令 S_i 表示第 i 个必要步骤正确，则整条链正确的概率满足：

```text
P(所有必要步骤正确)
= P(S_1) × P(S_2 | S_1) × … × P(S_n | S_1, …, S_(n-1))
```

这是概率的链式分解，不需要假设各步骤独立。若在一个**假设流程**中，12 个必要步骤在前面都正确的条件下各有 98% 的成功率，那么全链成功约为 `0.98^12 = 78.5%`。注意：不能拿现实中各步骤的边际准确率直接这样相乘；共享资料、模型和环境会造成相关错误。

这个算例不是主张“步骤越少永远越好”。增加一个有效的证据校验步骤，可能显著减少未被发现的错误；增加三个重复表态的 Agent，则可能只增加成本与新的失败点。真正需要优化的是每一步的必要性、条件成功率和错误检测能力。

它也解释了为什么工程上要分层设关卡：尽早发现错误，避免带着错误事实继续写长文、进行计算或触发发布。验证不应只放在整条链的最后。

# 领域一：Agent 架构与编排

**Agentic Architecture & Orchestration**

本领域首先解决控制权。你需要能解释：模型可以自由决定什么，程序固定什么；一项任务如何拆分；发生失败以后，继续、重试、停止、恢复分别意味着什么。只有这个基础清楚，多 Agent 与 SDK 配置才不会变成“会调用，但不知道为什么”。

## 1.1 Agent 循环：一次模型调用结束，不是业务任务完成

### 先理解三个不同层次的“结束”

HTTP 返回成功，只能说明拿到了接口响应。`end_turn` 说明模型结束本轮输出。业务完成则要求输入范围全部处理、必要字段得到证据支持、必需产物通过验收。这是三道不同的门。

官方 Messages 工具协议要求，客户端工具请求以 `assistant` 中的 `tool_use` 块出现；应用执行后，通过后续 `user` 消息中的 `tool_result` 关联原调用 ID。一次响应可能包含文本与多个工具请求，不能只读取第一段文字或执行第一个工具。[R08]、[R09]

假设一次回复请求读取两份报告。工具 A 成功，工具 B 超时。正确的协议结果是分别返回两条关联结果，让后续推理看见成功与失败。错误的做法是只返回成功结果，然后把模型的“已经完成分析”作为全任务通过依据。协议丢失会进一步变成知识丢失：模型根本不知道 B 没有读到。

### 为什么要保存完整内容块

模型回复不一定只有文本。有些接口组合还包含工具请求、推理相关结构或其他带关联信息的块。只提取 `response.text` 再重建历史，可能破坏后续消息所需的结构。配套实验因此将整个 `content` 保存，而不是挑一段可读文字拼接。[R08]

```python
# 来自实验 runtime.py：历史保留完整内容，而不是只保留 text。
history.append({"role": "assistant", "content": deepcopy(content)})
requests = [b for b in content if b.get("type") == "tool_use"]
```

但“保存完整协议消息”不意味着“所有内容都永久进入普通日志”。协议正确性、上下文预算与敏感信息存储是三个不同要求；长期日志应采用适当脱敏和访问控制，见领域五。

### 停止原因应该怎样路由

| 模型返回 | 本次调用层含义 | 应用层下一步 |
|---|---|---|
| `tool_use` | 客户端有动作待处理 | 校验所有请求、执行允许的工具、逐一回传结果 |
| `end_turn` | 本轮输出自然结束 | 解析产物并执行业务验收 |
| `max_tokens` | 输出被截断 | 保留未完成状态，不用“补括号”冒充完整结果 |
| `pause_turn` | 服务端工具流程可能需要续接 | 按相应协议继续；不支持时显式暂停 |
| `refusal` | 没有得到普通任务结果 | 单独处理，不作为正常产物解析 |
| 未识别状态 | 适配器尚不能解释 | 保守停止并记录，不默认为成功 |

这些分支来自官方停止原因文档；配套实验仅实现客户端只读工具，遇到服务端续接会明确返回 `paused`，没有伪装成通用运行时。[R09]

### 为什么需要多种预算，而不是一个 max_tokens

`max_tokens` 限制单次输出，不能限制六十次短工具调用。轮数预算限制模型交互次数，不能限制一次回复提出的一百个请求。总时限限制用户等待，但不能撤销刚刚已经提交的外部写入。

本文建议分别管理模型轮数、工具次数、执行时限和允许的副作用数量。每到一个边界，先保存完成范围和未解决项，再返回可恢复的终态。在工具预算不足以处理本轮全部请求时，仍应给每个请求明确结果；未执行部分返回预算耗尽，不能让请求在历史中无声消失。

**实验对应。**`test_runtime.py` 检查多工具配对、截断、拒绝、未知状态、预算终止，以及 `end_turn` 后的业务失败。这里验证的是运行时对已知响应的处理，不是证明真实模型不会提出坏动作。

## 1.2 协调者与子 Agent：先设计信息流，再增加角色

### 多 Agent 真正提供了什么

它至少可能提供三种收益：不同子任务拥有各自工作上下文；独立资料读取可以并行；协调者可以根据途中发现的新问题动态创建任务。它也增加通信、重复检索、汇总失真和部分失败。

Anthropic 的研究系统采用协调者分派并汇总。公开复盘指出，模糊委派会导致不同执行者理解成不同范围，或者重复做相同搜索。因此，角色名称本身不足以形成有效任务接口。[R03]

**官方案例。**在半导体供给问题中，边界不清的任务曾让执行者分别研究不同时间背景，或重复搜索同一主题。这个案例说明，出问题的并非“没有专家角色”，而是任务对象、时间和范围没有被共同定义。[R03]

### 将一个任务分成三个对象

本文建议每项委派都有：**任务契约、输入快照、结果契约**。

任务契约包含要回答的问题、不得越过的范围和完成条件。输入快照包含材料 ID 与版本，而不是“使用最新文件”这种会随时变化的描述。结果契约包含已完成范围、候选结论、证据定位、失败与未决项。

```json
{
  "task_id": "check_A_H1",
  "input_revision": 7,
  "question": "核对合成公司 A 的 2025H1 合并营业收入",
  "source_ids": ["A:H1:2"],
  "allowed_actions": ["search", "read"],
  "completion": "返回证据或明确缺失，不推断全年数据",
  "output_fields": ["status", "claims", "evidence_ids", "unresolved"]
}
```

其中 `allowed_actions` 是任务说明，不自动构成执行权限。真正的工具集合和后端授权还要独立配置，见 2.3。

### 并行收益受依赖关系限制

设读取 A 需要 4 秒、读取 B 需要 6 秒、综合需要 3 秒。串行路径是 13 秒；理想并行路径是 `max(4,6)+3=9` 秒，而不是将全部工作时间除以执行者数量。若创建子 Agent、传递上下文、汇总增加了 5 秒，并行反而变成 14 秒。数字是本文假设，用于说明关键路径。

还要区分**并行工具调用**与**多 Agent**。若只需同时读取两个已知文件，一个 Agent 发出两个工具请求可能已足够；只有两个子问题需要独立搜索、推理或上下文时，才更有理由增加子 Agent。不要把简单 I/O 并发升级成不必要的智能体通信。

### 结果合并不是拼接摘要

协调者不能只把三段文字合在一起。它应先核对每项结果的任务版本、覆盖范围和状态，再合并事实。两个执行者返回同一事实时要去重；返回不同期间时不能当作冲突；使用相同上游错误来源时，意见一致也没有增加独立证据。

因此，拆分粒度可以遵循一个实用原则：**子任务之间尽量只交换稳定、可核验的产物，尽量不要共享频繁变动的中间推理状态。**需要不断协商同一文件每一行的任务，通常不适合粗暴并行。

## 1.3 子 Agent 的配置：可选调用、上下文和权限是三种机制

官方 SDK 的子 Agent 定义把描述、提示词、工具等配置分开。描述帮助主 Agent 判断何时委派；提示词告诉执行者如何完成任务；工具定义其可用能力。当前文档使用 `Agent` 作为委派工具名称，旧资料或轨迹可能出现 `Task`，应按实际版本核对。[R12]

### 为什么 description 不能保证必经检查

你可能创建一个“事实核验 Agent”，描述写成“每次报告输出前都调用”。这只是在影响模型选择。如果事实核验是不可跳过的业务要求，应由编排代码在产物提交前调用校验流程，而不能把必经步骤寄托在模型是否选择这个子 Agent。

这形成两种不同架构：**可选专家**用于模型认为有帮助时补充分析；**强制检查器**用于无论模型如何判断都必须经过的关卡。它们可以使用相同模型，但调用权不同。这个区别比专家提示词写得有多长更重要。

### 子 Agent 应拿到什么上下文

只传一句“请检查是否正确”，它缺少判定范围；传入父 Agent 全部历史，又可能让它继承错误结论和无关细节。本文建议传递任务目标、必要约束、待检产物、来源标识与不确定事项，而不是把主 Agent 的叙述当作事实。

例如，核验者应拿到“候选值 12.4、期间 2025FY、来源 A:H1:2”，然后独立读取来源。若只拿到父 Agent 已整理好的“全年收入 12.4，来源已确认”，核验就容易退化为复述。

官方文档区分独立与分叉上下文；无论使用哪一种，都应该明确任务所依赖的信息从哪里进入，而不是假设父子之间自动共享全部环境知识。[R12]、[R39]

### 如何避免主 Agent 汇总丢失重要细节

让子 Agent 返回“最终摘要”和“机器可读证据对象”两层产物。摘要用于阅读，证据对象用于校验与合并；主 Agent 可以重新组织文字，但不应任意改写事实对象的期间、单位与来源版本。

这是一种本文设计的**窄接口**：内部可以自由探索，外部交付保持稳定。将来替换子 Agent 的模型、提示词或检索方式，协调者仍只依赖结果契约，系统变化范围更小。

## 1.4 多步流程：从提示词约束走到业务不变量

### 一个完整的失败时间线

考虑这次发布操作：

```text
t1：应用检查报告 v3 已获批准。
t2：发布服务写入成功。
t3：返回回执之前，连接断开。
t4：调用方不知道 t2 是否发生，于是重试。
```

这里不是一般的“工具执行失败”，而是**结果不确定**。如果简单重发，可能重复发布；如果直接宣布失败，也可能与真实系统状态不一致。模型再推理一次，不能凭空知道 t2 是否提交。

官方工具与用户审批文档提供执行和批准的接口能力；下面的版本绑定、事务与去重是本文将这些接口用于业务流程时的工程设计，不是 SDK 自动替你完成的保障。[R08]、[R18]

### 必须分开的三个标识

`tool_use_id` 用于当前模型消息中的请求—结果配对。`operation_id` 标识一项业务动作，跨重试保持稳定。`artifact_hash` 标识动作处理的确切内容。三者不等价。

若每次重试重新生成 operation_id，下游会将它当成新业务动作；若只按报告名称去重，修改后的新报告又可能被误当旧报告。本文方案是在批准后的工作流中分配并持久化 operation_id，同时保存产物哈希、租户与目标。

### 本地可验证实现

配套实验将批准、发布记录与审计保存在 SQLite 中。发布方法开启事务，先查询业务动作是否已有回执；存在则核对内容和目标并返回旧回执；不存在才检查批准与验收，然后将发布记录和审计一并提交。

```text
BEGIN IMMEDIATE
    ↓
按 tenant + operation_id 查询既有发布
    ├─ 已存在、内容相同 → 返回历史回执，不再写入
    ├─ 已存在、内容不同 → 幂等键冲突，拒绝
    └─ 不存在
          ↓
      检查批准绑定的产物 / 目标 / 有效期
          ↓
      检查可信校验器结果
          ↓
      同一事务写入发布与审计
COMMIT
```

批准不能只保存 `approved=true`。报告获批后又改稿，原批准不应自动适用于新内容。批准也不应由模型通过一个 `approve` 工具自行授予。实验中的批准入口只有可信应用调用路径，没有暴露给模型。

**实测。**实验在事务提交后主动抛出“回执丢失”异常，再重新打开数据库、用原操作 ID 重试；最终仍只有一条发布记录和一条审计。16 个并发请求使用同一操作 ID，也得到同一回执。它验证的是这些明确条件下的本地数据库行为，不是所有崩溃场景。

### 为什么这不能直接推广成远程 exactly-once

假设把数据库内写入改成 HTTP 调用另一个发布系统，本地事务无法回滚对方已经完成的操作。即使本地使用 outbox——在业务事务内记录“需要发送的消息”，再由独立发送者递送——发送者也可能在远端成功后、本地标记之前崩溃。因此 outbox 解决的是可靠交接，不会凭空消除远端重复。

实际需要对方支持业务幂等键、可以查询操作状态，或建立对账与人工处理。不支持这些能力时，正确设计可能是将结果标为 `UNKNOWN_OUTCOME`，阻止盲目重试并核查。**承认未知状态，比用“重试三次”把不确定性放大更可靠。**

## 1.5 Hooks：放在什么时刻，决定能保护什么

官方 Hooks 区分工具执行前、成功后、失败后等时机。执行前检查可以阻止后续动作；执行后处理可以检查和调整模型看见的结果，但已经发生的外部副作用不会因此消失。[R15]、[R23]

### 前置检查也不一定足够

假设 PreToolUse 读到“报告 v3 已批准”，随后用户撤销批准，工具才开始执行。如果真正的发布后端不再次检查，就出现**检查与执行之间的竞态**。因此，Hook 适合集中应用策略和早期拒绝；与业务状态相关的授权，应尽量在实际提交点、同一事务或受版本约束的操作中完成。

这里不是说所有检查都要做两遍，而是检查应放在能够对其保护对象作出最终保证的位置。参数格式可以在入口检查；审批是否仍有效，要在业务提交时检查；网络与文件访问范围，依赖执行环境限制。

### 模型看不见，不代表日志里没有

当前 Hooks 文档允许通过 `updatedToolOutput` 改变提供给模型的工具结果，同时说明某些原始记录可能已在此前进入可观察性流程。因此，用后置 Hook 把账号替换成星号，不能直接宣称所有日志均已脱敏。[R23]

这是一条很实用的工程推论：需要保护的数据，最好在源工具结果、日志采集入口和存储权限上分别控制。后置展示转换只解决其中一条路径。也不要把返回文字改成“发布失败”，就认为真实写入被撤销。

### Hook 本身失败怎么办

关键写入的授权检查失败时，通常应该拒绝继续；耗时统计 Hook 失败时，则不一定值得阻断整条业务流程。本文建议按职责制定失效策略：**安全闸门偏向拒绝，观察功能偏向隔离故障，规范化转换失败则显式保留错误。**不是所有 Hook 共用一个“忽略异常”或“整个任务失败”的默认值。

异步 Hook 适合不参与当前决定的记录任务，不适合当作“结果出来之前不能执行”的闸门。要确定性执行的检查，使用明确代码和可预测输入；模型辅助判断可以提供建议，但不能被误当成确定性的权限规则。

## 1.6 任务分解：按信息依赖选择模式，不按术语选择

官方给出的串联、路由、并行、协调者—执行者、评估—优化等模式，是解决不同任务结构的方法，不是由低级到高级的排名。[R02]

### 从同一个问题比较三种方案

假设需要审查 100 份短报告。

**方案 A：固定流水线。**每份材料读取、抽取、校验，失败进入人工队列。若材料结构稳定、判定要求明确，这一方案容易追踪和批量对账；缺点是遇到新的证据缺口时不擅长自主探索。

**方案 B：单 Agent 自主补证据。**先执行同样的主干，在具体字段缺失时允许有限检索。它将不确定性集中在小范围探索中，同时保留可验收阶段。这通常比完全放开整个任务更容易定位问题。

**方案 C：协调者动态分派多 Agent。**当材料规模大、子问题类型差异大、检索路径未知时有价值；但若 100 个子 Agent 都需要同一基础资料和规则，重复上下文可能抵消并行收益。还需要处理迟到结果、范围重叠和汇总成本。

比较时，不应给 C 更多总调用预算，再把成功率提升全部归因于“多 Agent 架构”。至少记录总 Token、工具调用、时间和人工干预；最好比较相近预算下的结果。这个建议是本文的实验设计原则，不是引用一个固定官方性能保证。

### 分解过细与过粗都会失败

过粗的任务让一个执行者同时处理太多未知，容易遗漏；过细的任务让上下文不断在接口间丢失，协调成本高于实际工作。一个有用的检查是：**子任务能否凭自己的输入独立完成并被验收？**如果它必须不停问另一个执行者“你现在想到哪一步了”，说明边界切得不好。

还应区分确定性计算与语义判断。单位换算、字段唯一性、总数对账应优先由代码完成；判定原句是否对某结论提供支持，才可能需要模型或人工。不要让“每个框都是 Agent”的图掩盖本可更可靠完成的工作。

## 1.7 恢复、分叉、重放与补偿：四件容易混淆的事

**恢复**是在确认已持久化进度后继续未完成任务；**分叉**是从某个会话起点探索另一路径；**重放**是重新执行一段已有动作；**补偿**是对已发生且不能原子回滚的效果执行反向业务操作。它们需要不同的状态与权限。

官方会话机制支持恢复和分叉，但会话分叉不等于复制文件系统。代码试验的隔离需要工作树或独立环境，外部服务效果也不会随会话回滚而撤销。[R14]、[R39]

### 可靠恢复需要一个“恢复包”

本文建议保存任务目标与输入版本、已完成单元、已验证事实、未解决项、预算状态、待执行 operation_id 和已获回执。模型会话 ID 只是其中一个字段。

恢复时的第一步不是“继续上次分析”，而是检查：输入是否仍是旧版本？已验证产物是否存在？待发布操作是否已经有回执？当前任务状态是否被另一个执行者更新？只有完成这些检查，模型再接手剩余的语义工作。

### 为什么不能让迟到的执行者直接覆盖状态

执行者 A 在 revision=7 时开始核查。执行者 B 发现资料更新，将任务推进到 revision=8。A 最后返回旧结果，若直接写入，就可能把新的事实和进度覆盖掉。

实验使用版本条件更新：

```sql
UPDATE tasks
SET revision = revision + 1, payload = ?
WHERE tenant = ? AND task_id = ? AND revision = ?;
```

若影响行数为零，说明预期版本不再成立。应用应重新读取状态、判断结果还能否合并，而不是自动用新 revision 重试同一覆盖。这就是比较并交换（CAS）的用途：它不替你决定如何合并，但能阻止静默丢失更新。

### 官方长期任务案例怎样迁移到这里

Anthropic 的长期编码实践观察到，Agent 可能试图一次完成过大任务，留下难以接手的半成品；下一会话又可能因看到部分功能存在而过早宣告完成。其方案使用初始化环境、明确功能清单、进度记录和增量验证。[R06]

对文档助手，迁移的不是“照搬一个进度 Markdown”，而是对应的控制思想：任务拆成可验收单元，完成状态有证据，下一次运行先恢复环境和事实。进度文件解决可读交接；数据库版本和回执解决并发与真实动作。两者可以并存，不能互相替代。

**本领域的判断标准：**给出一条失败轨迹时，你能指出它停在哪种状态、哪些效果可能已发生、下一步需要查询什么，以及为什么不会把重试变成新的错误。

# 领域二：工具设计与 MCP 集成

**Tool Design & MCP Integration**

领域一规定“系统怎样向前走”，本领域规定“每一步怎样与真实世界交互”。工具接口不仅是一段函数签名，它决定模型能看见哪些动作、怎样表达意图、如何理解失败，以及能否拿到足够证据继续决策。

## 2.1 工具设计：优化的不是 API 数量，而是完成任务所需的决策负担

### 从传统 API 到模型使用的接口

传统后端接口可以假设调用者知道正确的表、ID、操作顺序和错误码。模型则需要在运行时根据描述选择工具，并构造参数。如果把所有内部 CRUD 接口原样暴露出来，你实际上把领域知识、依赖关系和合法组合全部交给模型临时猜测。

Anthropic 的工具设计文章强调围绕任务设计工具、返回有用信息，并通过真实任务轨迹评估接口，而不是机械地暴露所有后端能力。工具描述与输入 Schema 的具体结构由官方文档定义。[R04]、[R10]

这不是“工具越少越好”。一个 `do_everything(instruction)` 虽然只有一个入口，却让调用语义无法预测；一百个名称相似的低层工具，则使选择空间过大。合适的粒度是：**一个工具完成边界清晰、能解释成功与失败的业务动作，同时保留必要的选择权。**

### 两种接口为什么产生不同错误

```text
接口 A：query_data(query: string)
接口 B：search_report_sections(entity_id, reporting_period, query, limit)
```

A 让对象、时间和意图挤在一个字符串里。一次调用失败，你很难判断是实体匹配错、期间遗漏还是搜索措辞不佳。B 把这些维度显式化，使程序能验证对象范围，也能在评估中区分错误类型。

但 B 同样有前提：模型必须有途径找到正确 entity_id。若测试题直接给内部 ID，而真实用户只会说公司名称，你测到的是已经解决实体定位后的理想状态。官方工具文章特别提醒，评估任务应贴近真实用户问题，而不是把实际需要查找的信息提前送给 Agent。[R04]

### 搜索与读取为何常常值得分开

搜索工具返回候选标题、时间、片段、来源 ID；读取工具返回所选来源的完整必要内容和版本。这形成“宽召回 → 窄读取”的信息路径。它的收益不是少给资料，而是让模型先决定哪份资料值得展开，避免被整库结果淹没。

分开也有代价：更多调用与一次候选选择。如果业务中几乎总是按唯一键读取一个对象，直接 `get_report(entity, period)` 更简单；若一轮需要比较多个来源，搜索—读取更合适；若用户只需要确定性聚合，则应提供聚合工具，而不是让模型逐行心算。

因此，应按查询形态比较：确切查找、模糊探索、多来源比较、数值聚合。不要把一种检索接口强行覆盖全部任务。

### 描述应包含排除条件和失败语义

“搜索财务资料”不如“搜索上传报告中的正文段落；不提供实时行情；结果是候选证据，不能直接当作已经验证的事实；没有匹配返回空列表，服务不可用返回错误”。排除条件减少的是误用，不是装饰性文案。

Schema 同样应表达真正有意义的边界：必需字段、可空字段、枚举、允许的对象结构。服务端结构约束之外，应用还应校验范围、身份与当前业务状态。输入类型正确，不代表有权读取这个报告。[R10]、[R11]

**实验对应。**`ReadTools` 只有搜索和读取两个接口，返回的 `source_id` 可以继续读取，来源版本可用于后续校验；结构化真值字段不会作为“标准答案”直接送给脚本外的模型。

## 2.2 错误设计：告诉系统如何恢复，而不只是“发生异常”

### 三层错误不能混在一起

第一层是请求与协议：连接失败、认证失败、非法消息。第二层是工具执行：上游超时、对象不存在、参数不满足业务约束。第三层是任务质量：工具成功返回，但证据不足、数值冲突或不满足用户要求。

官方 API 错误文档与工具结果接口分别处理这些层。Messages 的工具结果使用 `is_error`；MCP 自定义工具结果使用 `isError`。拼写差异反映的是不同协议对象，不能原样混用。[R45]、[R08]、[R17]

### 空结果为什么是很重要的正常状态

成功搜索了指定范围但没有找到内容，是关于这个范围的一次有效观察。上游超时则没有完成观察。两者都返回 `[]`，模型就会把“没有得到证据”误写成“证据表明不存在”。

本文的工具错误对象保留状态、稳定错误码、是否可能恢复和追踪标识。详细堆栈留给受控日志，不把访问令牌和内部连接信息放进模型上下文。

```json
{
  "status": "error",
  "code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "operation_kind": "read",
  "trace_id": "read-1042",
  "message": "本次读取未在限定时间内返回，尚不能判断来源内容。"
}
```

这个 Schema 是本文设计，不是 MCP 强制的标准业务格式。

### retryable 不能独自决定是否重试

对只读查询，临时超时后有限重试通常不会产生新的业务副作用；对发布、转账或发邮件，超时可能发生在提交之后。后者必须先考虑结果是否可查询、是否有稳定幂等键，而不是看到 `retryable=true` 就重新执行。

| 情况 | 应改变什么 | 保留什么 | 停止条件 |
|---|---|---|---|
| 只读请求临时超时 | 延迟后有限重试或切换可用读取路径 | 原查询、来源范围、尝试号 | 预算耗尽或服务明确不可用 |
| 参数不合法 | 修正具体参数 | 原用户目标、业务对象 | 没有足够信息修正时澄清 |
| 权限不足 | 通过合法路径请求授权或升级 | 错误原因与所需资源 | 不尝试用别的工具绕过 |
| 搜索结果为空 | 调整查询策略或承认缺失 | 已搜索范围与条件 | 搜索收益不足、范围已覆盖 |
| 写入结果不确定 | 查回执、按稳定业务键重试或人工核查 | operation_id、产物哈希、目标 | 无法证明安全重试时暂停 |
| 原文相互冲突 | 比较口径、版本、修订关系 | 冲突双方原文 | 没有裁决依据时转人工 |

这一表的恢复策略是本文推导。它说明：**是否重试取决于动作语义，不只取决于 HTTP 状态。**

### 重试怎样放大成本和错误

假设一次失败实际来自“这个字段原文没有提供”。连续调用五次同样的模型，不会制造新证据，却增加一次碰巧输出猜测值的机会。真正有价值的重试必须改变可用信息或修正已定位的缺陷。

可采用“失败分类 → 明确修复动作 → 有限重试 → 再验收”的闭环。重试反馈不只是“请重做”，而应指出哪一项未通过、为何未通过、允许读取什么，以及不得改变哪些已验证字段。

## 2.3 工具可见性、批准、授权、沙箱：四层不能相互代替

### 四个问题，四种控制对象

**工具可见性**决定模型是否能够请求一个动作。**调用批准**决定这个请求在当前运行中是否需要询问。**后端授权**决定当前用户是否有权操作这项业务资源。**沙箱**限制进程对文件、网络等环境的访问。

一个子 Agent 看不见发布工具，不代表它使用的服务账户没有写权限；一个调用自动获批，不代表后端允许访问任何租户；一个 Bash 进程在沙箱里，也不代表其中的 HTTP 请求拥有正确业务权限。这些机制各自有价值，但保护对象不同。[R13]、[R28]、[R29]

### allowed_tools 最容易被误读在哪里

当前 Agent SDK 文档中，`allowed_tools` / `allowedTools` 用于加入自动批准规则，不能简单解释成“没有列入的工具都不存在”。子 Agent 的工具集合、禁止规则、权限模式和后端访问控制是另外的机制。某些已获批准的请求也不会再进入 `canUseTool` 交互审批回调。[R13]

因此，下述推理不成立：

```text
我设置 allowed_tools=["Read"]
    → 模型只能读取
    → 任何写入都不可能发生
```

你真正需要做的是枚举写入路径：内置文件写入、Shell 命令、写入型 MCP 工具、具有过大权限的远端 API。逐条检查模型能否请求、运行时如何处理、服务端凭据是否允许。对只读角色，应在实际资源访问层也限制写权限。

### 什么时候仍然需要人工批准

只读不一定低风险，例如读取未授权客户数据。写入也不一定每次都要人工点按钮，例如在隔离临时目录写测试产物。批准策略应由资源敏感性、操作影响与可逆性决定，而不是只看工具名称中有没有 `write`。

本文建议先建立能力矩阵，再定义自动批准项。不要反过来先开一个“少弹窗”的权限模式，再把便利性误认为完整的安全设计。

**实验边界。**实验中 `AuthContext` 是可信后端输入的模拟，没有身份认证网关。允许模型自己填写 `role="reviewer"` 再传给 Store，当然不安全。代码只证明可信上下文下的角色与租户检查，不声称解决身份真实性。

## 2.4 MCP 集成：协议连接只是链条的第一段

MCP 为工具、资源与提示模板提供统一的集成方式。Claude Code 和 Agent SDK 分别有配置入口；项目配置、个人配置以及认证方式影响实际加载行为。工具通常使用服务名称命名空间，但命名空间只是路由与配置标识，不是租户授权证明。[R16]、[R21]

### Host、客户端、服务端，以及三种能力

在本书的集成场景里，Claude Code 或你的应用是承载模型工作流的 Host；它通过 MCP 客户端连接服务端。服务端提供能力，Host 决定怎样把这些能力接到模型与用户的工作流中。模型本身不是那个持有连接、处理认证并执行全部请求的进程。[R16]、[R21]

Tools 表达可调用动作，Resources 提供可读取的数据或内容，Prompts 提供可复用提示模板。服务端有一个资源，不等于模型已经读取了它；服务端提供了模板，也不意味着模板天然拥有覆盖项目约束的权限。需要检查客户端支持什么、何时加载，以及内容最终以什么方式进入上下文。[R21]

这能解释一个常见集成误会：开发者确认服务端列出了文件资源，却期待模型像调用工具一样自动阅读。缺少的可能是 Host 侧的读取和上下文注入路径，而不是一句“请使用 MCP”的提示词。

### 一次请求经历了哪些环节

```text
配置文件被正确作用域加载
    → 本地进程启动或远程连接建立
    → 认证与协议初始化成功
    → 能力发现，客户端得到工具定义
    → 模型决定调用并生成参数
    → 运行时进行批准与权限处理
    → MCP 服务验证业务请求并执行
    → 结果被适配回模型可理解的工具结果
    → 应用校验最终任务产物
```

任何一层出错，都可能表现为用户眼中的“Agent 不会用工具”。不断改提示词只影响其中很少一部分。

### 一个分层排障例子

用户说“刚配置的报告工具不工作”。先确认当前项目是否加载对应配置；再检查进程或远端连接；再确认认证与工具发现；随后用明确参数测试一个只读工具；最后才检查模型是否选错工具或误解返回结果。

如果工具根本没有被发现，提示词再强调“必须调用报告工具”也无效。如果工具可调用但返回了 HTML 登录页，问题是认证或服务响应，不是模型不懂报告。如果结果正文正确但包装为不可读结构，应该修适配器，不是换一个更大的 Agent。

### 配置示例与信任边界

以下仅展示 Claude Code 项目配置形状，域名是占位符：

```json
{
  "mcpServers": {
    "research_docs": {
      "type": "http",
      "url": "https://mcp.example.org/research",
      "headers": {"Authorization": "Bearer ${RESEARCH_DOCS_TOKEN}"}
    }
  }
}
```

环境变量可以避免将字面令牌写入共享文件，但还需要管理变量注入、日志和运行环境。仓库中的配置也不天然可信：不应因有人提交一个新的本地服务启动命令，就无审查地以高权限运行。[R21]、[R30]

### MCP 没有替你完成什么

它没有自动完成业务幂等、权限模型、结果语义校验、事实核验和评测，也不会保证你暴露的工具粒度合理。把普通 HTTP 工具换成 MCP，主要改善接入一致性；原工具的错误语义若仍然含糊，换协议不会消除问题。

配套实验没有启动真实 MCP 服务，因此没有把消息结构测试描述成 MCP 互操作测试。真实接入至少应补做发现、认证、参数校验、错误包装、超时、权限拒绝和服务重连的契约测试。

## 2.5 内置工具与大结果处理：让模型做选择，让代码做确定性工作

### 官方案例：相对路径不是无害的小细节

Anthropic 在早期编码 Agent 复盘中提到，工具在切换工作目录后使用相对路径会出错；要求使用绝对路径改善了该问题。这个经验来自其具体编码任务，不意味着所有系统都必须采用同一种路径策略。[R02]

工程上的一般化解释是：相对路径依赖一个隐含环境变量——当前工作目录。模型可能不知道它已变化。解决方法是使这个依赖显式化，例如固定根目录、解析为明确路径，或每次工具调用携带工作目录。

但绝对路径只减少寻址歧义，不提供安全隔离。真正的路径访问控制仍需检查允许的根目录、符号链接以及执行环境权限。把 `/sandbox` 拼在路径前面，不等于构建了沙箱。[R29]

### 代码探索为何应先定位再展开

一个可复现的修改流程通常是：按文件名找到候选 → 按符号找到定义和使用处 → 读取上下文 → 小范围修改 → 执行针对性测试 → 检查差异和回归。`Glob`、`Grep`、`Read`、`Edit`、`Bash` 不是互相竞争的名字，而是分别承担定位、理解、变更和验证。[R39]、[R41]

先把整个仓库读进上下文，再“寻找可能有问题的地方”，会同时增加成本和错误定位难度。反过来，只凭搜索片段改代码，也可能遗漏调用前提。检索地图不能代替关键实现的实际读取。

### 大表格不应全部交给模型数

假设工具返回 10,000 行，每行约 120 个 Token，原始结果约 120 万 Token；而任务只需要某两个期间的 5 条汇总记录。这个**假设算例**说明，最优改进可能不是扩大上下文，而是在代码层筛选、聚合并返回结果、计算口径与来源定位。

Anthropic 关于 MCP 代码执行的文章讨论了按需加载工具，以及在执行环境中处理大量数据、减少进入模型上下文的内容。这里借鉴的是信息处理位置，不是声称执行代码永远更便宜或更安全。[R38]

过滤也有风险：如果代码丢掉单位、期间和来源，模型会拿到更短但不可验证的数字。正确目标是减少无关行，同时保留决定语义所必需的字段。让代码负责精确筛选与计算，让模型负责提出问题、解释结果与发现需要进一步核实的含义。

**本领域的判断标准：**当工具失败或选错时，你能区分接口设计、协议集成、权限、业务服务和模型决策中的哪一层需要改，而不是默认换模型或再写一段提示词。

# 领域三：Claude Code 配置与开发工作流

**Claude Code Configuration & Workflows**

这一领域不是命令速查。它研究如何把一个开发者临时使用 AI 的过程，变成团队可以重复执行、检查和回滚的工程工作流。核心区别是：项目知识、任务流程、执行权限和验收标准应当分别存放、分别生效。

## 3.1 CLAUDE.md：它是上下文，不是可强制执行的项目宪法

官方文档说明，`CLAUDE.md` 通过目录与导入机制进入模型上下文；它指导行为，但不是确定性的权限规则。还要区分这种内容加载与 `settings.json` 的实际配置优先级，两者不是同一种“覆盖”。[R19]、[R22]

### 三类内容为什么不应该混在同一个文件

**稳定知识**包括项目运行方式、模块边界、关键业务定义。**临时状态**包括这次已经处理到哪里、当前失败测试和下一步。**强制规则**包括是否允许命令执行、是否能写入某目录、是否需要批准。

稳定知识适合放项目说明；临时状态适合任务记录或状态存储；强制规则需要配置、执行环境或后端实现。如果把三者全部写成一个很长的 `CLAUDE.md`，会发生两个问题：模型每次都读大量过期信息；开发者误以为一句禁止性文字已经建立实际约束。

### 什么内容值得常驻

本文采用一个判断：**跨多数任务都重要，且模型不容易从当前文件直接推断出来的内容，才值得占用常驻上下文。**例如，“金额原始单位必须保留，禁止默认转成元”比“写优雅代码”更有用，因为前者揭示了项目特有风险，可以具体检验。

相反，几百行 API 说明可以保存位置，在相关任务中读取；上周某个修复的全过程不应该永久放进根指令。拆成多个文件也不自动省上下文：如果根文件导入全部内容，它们仍会被加载。[R19]

```markdown
# 项目约定

## 数据语义
数值必须与对象、指标、期间、统计口径、单位和来源版本一起保存。
缺失不等于零；冲突不等于取平均；没有依据不得补造字段。

## 验证
修改前读取相关实现与测试。
修改后运行针对性测试和受影响模块回归，并报告未执行的验证。
```

这份内容可以帮助模型正确行动，但“不得删除测试”仍要靠受保护测试和审查保障。应将项目指令视为提升合作效率的接口，而不是唯一防线。

## 3.2 Skills：封装的是可复用工作方法，而不是更多角色名称

官方将 Skills 定位为可按需调用的知识与流程扩展；子 Agent 提供独立执行上下文；MCP 提供外部工具连接；Hooks 在生命周期节点执行动作。这些机制有交集，但核心职责不同。[R20]、[R40]

### 用一个任务理解它们的区别

“核查报告证据”这个需求中，Skill 可以保存标准步骤与检查表；子 Agent 可以在独立上下文中执行核查；MCP 工具读取报告；Hook 可以在发布前检查状态。不是同一个需求必须把四种机制全部装上，而是每种机制解决其中一个独立问题。

若团队只是每次重复粘贴同一核查流程，一个 Skill 可能已经足够；若核查内容会干扰主任务上下文，再考虑子 Agent；若数据源尚未接入，再考虑 MCP；若步骤不可跳过，则增加编排关卡或执行检查。

### 一个 Skill 好不好，要看它减少了什么不确定性

差的 Skill 只是“你是资深专家，请严谨检查”。好的 Skill 告诉执行者：输入在哪里，检查顺序是什么，如何返回支持/缺失/冲突，证据定位采用什么格式，遇到问题何时停止，哪些动作不得进行。

但正文不应包含每份材料的事实真值，也不应把不断变化的规则硬编码到很多重复副本。可将稳定方法放 Skill，将规则和数据保存为有版本的外部资料，并在运行时引用。这样规则变化时不必逐一修改所有使用者的临时提示词。

配套包中的示例明确使用 Claude Code 项目目录：

```text
.claude/skills/evidence-review/SKILL.md
```

其 frontmatter 使用 `disable-model-invocation: true`，让用户显式启动。它不意味着建立了权限沙箱，也不保证所有其他工具自动消失。`allowed-tools` 相关设置要按当前 Claude Code 语义理解，不可与工具可见性和后端授权混为一谈。[R20]

### 触发质量也是一个评测问题

当 Skill 允许模型自动选择时，要同时测两类错误：应触发却没有触发，以及不应触发却占用上下文或执行错误流程。只测“显式输入 Skill 名称后能不能运行”覆盖不了自动选择问题。

可以准备相近请求进行对照，例如“核验候选摘要中的数字”“润色不涉及事实的标题”“寻找某份报告”。预先写下哪些应进入证据核验流程，再检查真实轨迹。若每次都触发，可能是描述太宽；若总不触发，可能是描述与用户表达不匹配。这个诊断比盲目增加 Skill 正文更直接。

## 3.3 按路径组织规则：让局部约束在需要时出现

官方支持在 `.claude/rules/` 中按主题组织说明，也可以通过 `paths` 约束适用范围。它帮助控制与当前文件相关的上下文，而不是让所有模块规则永久堆在一起。[R19]、[R27]

### 模块划分应对应不同风险

抽取模块的关键风险是期间、单位与来源；数据库模块的关键风险是事务、兼容和迁移；前端模块的关键风险是交互、可访问性和状态展示。把这些放成局部规则，能让模型在相关工作中获得准确约束，而不是每次收到一份全公司制度。

```markdown
---
paths:
  - "cca_lab/contracts.py"
  - "tests/test_contracts.py"
---

期间、统计口径、单位或来源版本发生变化，必须有对应负向测试。
不得让待评估模型同时生成候选答案和唯一的标准答案。
```

### 配置文件存在，不代表规则生效

常见失败包括路径模式没有匹配真实文件、规则放错目录、YAML 格式有误，以及根指令和局部规则相互矛盾。仅检查文件是否提交到仓库，不足以验证加载效果。

本文建议建立少量“配置冒烟任务”：分别读取目标模块、对应测试和无关文件，检查相关规则是否进入工作流程；再用一个故意违反规则的变更验证验收层能否发现。这区分了两件事：模型是否看见规则，以及系统是否能拦截违反规则的结果。

### 不要依赖模型自行解决制度冲突

如果根说明写“所有金额转换为元”，局部说明写“必须保留原始单位”，不应简单期待“更近的文件一定覆盖”。应明确数据模型，例如同时保存原始值、原始单位与规范化值，并消除说明中的语义矛盾。

上下文中的冲突会增加推理歧义。良好的规则工程不是写出更强硬的措辞，而是降低必须由模型临时裁决的矛盾数量。

## 3.4 规划：作用是减少未知，而不是增加一份长文档

Claude Code 官方最佳实践建议对复杂任务先探索和规划，并强调明确的验证标准。简单、已定位的小变更则不必强制经历冗长流程。[R26]、[R41]

### 用一次真实形态的迁移任务说明

假设系统原来只有 `value` 字段，默认单位是元；现在需要支持报告中的万元、亿元，同时不破坏旧报表。一个空洞计划是“分析代码、增加单位字段、运行测试”。它没有回答任何决定成败的未知。

一个有效计划需要沿数据链调查：输入哪里产生单位，原始值是否已被转换，下游如何解释历史 value，数据库是否允许空单位，旧接口是否仍有消费者，历史数据能否确定性回填。接着才确定迁移方案。

本文建议的演进路径是：先增加 `raw_value`、`raw_unit` 与显式规范化字段；保持旧消费者兼容；对无法确认历史单位的数据标记未知而非统一猜测；新旧计算并行对照；达到验收标准后切换读取路径。回退应回到旧消费逻辑，而不是删除新字段导致证据丢失。

这里的重点不是数据库技术选型，而是**计划必须包含需要验证的假设、变更依赖、兼容策略和回退条件**。

### 如何判断规划到什么程度就可以执行

当关键接口和不变量已清楚，剩余工作可以通过局部实验确认时，就可以开始小步实现。若计划仍依赖“应该没有其他地方使用这个字段”，应先检索调用者或检查运行数据，而不是把猜测写进方案然后继续。

规划的价值可以用“消除了多少高影响未知”衡量，不宜用字数衡量。计划也不是承诺永不改变；发现新的证据后，应明确调整原因，更新验收和回退路径。

### 规划模式不是安全环境本身

模式可以影响 Claude Code 的行动方式和批准流程，但不能替代文件系统、网络和后端权限限制。需要保护的生产数据不能仅靠“现在在规划模式”来保证不被访问或修改。[R13]、[R29]

## 3.5 迭代开发：先复现缺陷，再允许模型修复

### 为什么“继续改到测试绿”仍可能失败

如果模型能同时修改实现和验收标准，它可能让测试通过，却没有修复真实需求。即使没有恶意，模型也可能把困难样例当作过时测试删掉，或扩大变更范围引入未覆盖问题。

官方工作流强调提供可观察的验收信息、运行测试并验证结果。本文进一步将“实现可改、验收受保护”作为工程边界，避免成功标准随修改一起漂移。[R26]、[R41]

### 一个可执行的修复反馈包

```text
失败样例：source_id=A:H1:2
输入含义：2025 年上半年合并营业收入 12.4 亿元。
实际产物：period=2025FY。
预期：期间绑定检查拒绝该产物，报告 PERIOD_MISMATCH。
修改范围：contracts.py 的字段绑定逻辑。
不得改变：人工构造的来源事实与本条回归测试。
完成条件：定向测试通过，其他绑定测试不退步。
```

这个反馈包包含现象、证据、预期和范围。它比“你还是不够严谨”更容易促成正确修复，因为模型无需重新猜测问题定义。

### 为什么还要检查差异而不只看测试

测试只能检查覆盖到的行为。一次修复可能意外修改日志、默认配置或未覆盖分支。因此应检查实际 diff：是否修改了无关文件，是否放宽了校验，是否新增网络访问或依赖，是否把秘密写进代码。

每轮最好只改变一个主要因素，例如先修工具错误包装，再评估；不要同时换模型、改提示词、增加三个 Agent 和修改评测集。否则即使分数变好，也无法判断是哪项改动造成的，更难可靠回退。

### 变异测试为什么比“有测试文件”更有说服力

本文实验额外制作三个错误版本：去掉期间绑定、去掉批准的产物哈希绑定、忽略已有回执。对应测试全部捕获。它们说明这些测试对选定不变量有敏感性，而不是只走了一遍正常路径。

这仍不等于测试完整。没有被选择的错误模式可能逃过现有测试。变异测试的价值是主动质疑验收能力，不是换一个方式宣称“系统绝对可靠”。

## 3.6 CI/CD：让无人值守的 Agent 有明确权限和失败出口

### 首先分开两种 JSON

Claude Code 的程序化运行可以返回 JSON 格式的运行包装；`--json-schema` 则约束任务产物。当前文档将结构化产物放在 `structured_output` 等相应字段中，不能把“外层 JSON 能解析”当作审查成功。[R24]

```bash
claude -p "检查当前 diff 中有证据的缺陷；没有发现则返回空 findings" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"findings":{"type":"array","items":{"type":"string"}}},"required":["findings"],"additionalProperties":false}'
```

这只是接口示例，不是完整安全流水线。程序仍要检查退出状态、运行错误、结构化产物是否存在，以及发现能否定位到真实文件。空 findings 可能代表没有发现，也可能来自输入根本没加载；必须用运行证据区分。

### 代码仓库本身也可能是不可信输入

拉取请求中的代码、README、测试脚本和 MCP 配置，都可能影响 Agent 或执行环境。若同时给它们生产密钥和任意命令权限，提示词里一句“忽略恶意指令”不足以建立隔离。官方安全与 GitHub Actions 文档提供相关风险和配置依据。[R25]、[R30]

本文建议把流水线至少分成三种权限角色：

```text
不可信分支分析：只读资料、最小权限、不持有发布凭据
             ↓ 结构化审查产物
受保护验证：运行独立维护的验收与策略检查
             ↓ 已验收结果
可信发布：仅评论 / 创建工单 / 发布指定产物，不执行分支任意脚本
```

将模型审查与实际合并授权分开。即使审查建议被接受，合并仍应满足已有代码审查、测试和权限要求。不要把“模型没有指出问题”变成自动跳过现有控制的理由。

### 评审质量与告警负担要一起看

审查 Agent 如果经常报告没有证据的“潜在问题”，团队可能逐渐忽略所有评论。应统计有证据发现的比例、人工采纳情况、重复问题和修复收益；不确定的问题进入待确认列表，而不是把所有猜测作为阻断错误。

这些指标属于本文建议，应在自己团队数据中评估，不能引用某个模型的通用分数替代。开发 Agent 的价值不只是生成多少代码，还包括减少多少真实缺陷，以及没有制造多少额外审查工作。

**本领域的判断标准：**另一个工程师接手时，能否知道项目如何运行、哪些约定重要、怎样触发复用流程、哪些行为被强制限制，以及如何独立验证这次改动。

# 领域四：提示词工程、结构化输出与事实校验

**Prompt Engineering & Structured Output**

到这里，系统已经知道怎样执行任务、调用工具和控制权限。但仍有一个核心问题：模型输出究竟在表达什么，怎样证明它满足要求？本领域将提示词、示例、Schema 和验证器串成一条链，而不是把它们当作相互独立的技巧。

## 4.1 明确任务标准：先定义正确，再优化表达

官方提示词与评估资料强调清楚的指令、必要背景和可衡量的成功标准。不是所有效果问题都应该先通过改写提示词解决。[R31]、[R37]

### 为什么“专业地分析报告”无法直接验收

一个输出可能文字流畅，但遗漏关键期间；可能覆盖所有字段，但引用错来源；可能数字正确，却没有区分原文事实与模型推测。因此，专业、准确、完整这些形容词必须被拆成可以分别检查的条件。

对贯穿项目，本文把结果定义成三类对象：**从来源观察到的事实、基于事实计算得到的结果、需要判断的解释**。三者不能混在一个 `answer` 字符串里。

例如，“2025H1 收入为 12.4 亿元”是来源事实；“较上一可比期间增长 10%”可能是计算结果；“增长说明竞争优势增强”是解释。第一类要查原文，第二类要查输入与公式，第三类要查推论范围和替代解释。它们需要不同的验收器。

### 建立语义中间表示，而不是直接从资料写长文

可以借用编译过程的直觉：不要从杂乱原文一步生成最终报告，而是先形成一个含义明确、可检查的中间结构。本文称它为事实登记表，不是 Anthropic 的固定产品格式。

```json
{
  "entity": "SYNTHETIC_A",
  "metric": "revenue",
  "period": "2025H1",
  "basis": "consolidated",
  "unit": "亿元",
  "value": "12.4",
  "source_id": "A:H1:2",
  "source_version": "根据实际原文计算的内容哈希",
  "status": "supported"
}
```

其中 `basis` 表示统计口径，例如合并报表而非母公司口径。金额保存为十进制字符串，再由代码用 Decimal 处理；这避免演示中将浮点表示细节混入精确金额比较，但不意味着所有模型接口都必须用字符串表示数字。

这个中间结构的价值在于：报告可以改写语言，事实字段却有稳定身份。生成第二章时，应读取相关事实记录，不依赖模型记得第一章曾写过什么。

### 缺失、冲突、无问题与执行失败必须分开

“未发现不一致”意味着检查完成且没有发现问题；“缺少原文”意味着无法完成相关判断；“资料互相矛盾”意味着需要处理冲突；“工具不可用”意味着观察没有完成。把它们都写成“无异常”，会让质量指标产生严重误导。

同时，**诚实返回 missing 不一定代表模型做错了**。若资料本来没有字段，正确行为就是保留未知；但业务上要求完整核验后才能发布，则该产物应进入待补证据状态。模型行为正确性与业务可发布性是两种评价，不能混为一谈。

配套实验采用较严格的发布验收：指定事实必须全部受支持。它因此拒绝 missing/conflicted 发布，不意味着所有研究任务都必须拒绝输出带缺口的报告。

## 4.2 Few-shot：让示例教会边界，而不是让模型记住答案

官方建议示例与实际任务相关、具有差异性并覆盖边界。把相同格式的正例重复多次，不足以说明什么时候应该拒绝推断或承认缺失。[R31]

### 什么是最小对照样例

本文建议从一条基准材料出发，每次只改变一个关键因素：

| 原文或候选的变化 | 预期判断 | 要检验的边界 |
|---|---|---|
| 原文“2025 年上半年”，候选也是 2025H1 | supported | 正常绑定 |
| 只把候选期间改成 2025FY | 期间不匹配 | 数字相同不等于事实相同 |
| 只把对象换成合成公司 B | 对象不匹配 | 相同数值可能属于不同实体 |
| 删掉原文的期间且没有其他依据 | missing | 不允许用常识补齐关键口径 |
| 增加一份同期间、同口径但不同数值的材料 | conflicted 或按修订关系进一步核查 | 不静默选一个数字 |

这种对照减少了混杂因素。当模型在第三行出错，你能明确知道它没有正确绑定对象，而不是笼统地说模型不够聪明。

### 示例本身也会引入偏差

如果所有示例都包含错误，模型可能过度发现问题；如果所有例子都要求填满字段，它可能不愿意返回未知；如果只展示一种年份或单位，它可能学到不必要的格式依赖。应包含正常、缺失、冲突与不适用的案例。

示例数量不是越多越好。更多例子消耗上下文，也可能包含互相冲突的边界。首先修正不清晰的标准，再选择少量能解释主要决策差异的示例，最后通过保留样本检验迁移。

### 怎样避免评测泄漏

提示词中的例子是开发材料，不应再作为主要通过率证据。对文档任务，随机拆分相邻段落也可能泄漏：同一公司、同一报告、同一模板的相似句子分散在训练提示与测试中，会让评估过于容易。

本文建议按报告、模板或来源实体分组保留测试，并专门加入表达变化、期间歧义和新模板。这个数据划分方案是工程建议，不是官方规定的唯一做法。

如果从历史案例动态检索 few-shot，还要保存本次实际使用的示例 ID 与版本。否则一次成功无法重现，你也不知道是模型改进、检索变化还是恰好命中了极相似案例。

## 4.3 结构化输出：约束了合法表达，不等于证明了事实

官方提供工具输入的严格模式与最终 JSON 结构化输出。前者约束模型传给工具的参数，后者约束任务结果形状；当前原始请求使用 `output_config.format`，SDK 的便利方法可能有不同参数名。[R11]、[R32]

### 用集合区分形式与含义

设 `L_schema` 是满足 Schema 的所有输出集合。结构约束的目标，是让输出落在这个合法集合中。但我们真正需要的是：输出不仅属于 `L_schema`，还要满足业务规则 B，并得到证据 E 的支持。

```text
可以解析       ：output ∈ L_schema
业务语义一致   ：B(output) 成立
有原文支持     ：E 支持 output 中的具体事实
任务覆盖完整   ：必要检查项没有遗漏
```

这些条件是相交关系，不是前者自动推出后者。`{"period":"2025FY","value":"12.4"}` 完全可以是合法 JSON，同时引用了上半年数据。

### 为什么 Schema 应允许未知

如果原文没有期间，而 Schema 要求期间字段必须是非空字符串，模型就面临格式与证据之间的冲突。更合理的定义通常是字段必须出现，但允许为 null，并有清晰 status。这样系统能够区分“字段被遗漏”和“明确没有可确认的值”。

```json
{
  "type": "object",
  "properties": {
    "period": {"type": ["string", "null"]},
    "value": {"type": ["string", "null"]},
    "status": {"type": "string", "enum": ["supported", "missing", "conflicted"]}
  },
  "required": ["period", "value", "status"],
  "additionalProperties": false
}
```

这个示例只说明字段形状。应用仍需检查 supported 时是否有实际来源，missing 时是否留下了未经确认的值，以及 conflicted 时是否保存冲突双方。

### 不要把所有 JSON Schema 规则都假设为服务端保证

当前文档列出支持范围与限制；某些 SDK 辅助层可能将不支持的约束转换或留给本地校验。即使类定义中写了范围要求，也应确认服务端实际执行了什么、客户端又检查了什么。拒绝和截断等非普通完成状态也必须先处理。[R32]

对工程实现，更稳妥的思路是：服务端约束减少格式噪声，客户端保留完整业务验证器。这样更换模型或使用另一种结构化能力时，关键事实规则不会随之消失。

### 原生引用与自定义 source_id 不是同一功能

当前官方文档说明，原生 Citations 与 `output_config.format` 的 JSON 结构化输出不能直接在同一请求中组合。需要带证据 JSON 时，可以设计自己的 source_id 与定位字段，并在应用中验证；或者拆成两个保留映射的阶段。不能把自定义 ID 宣称为原生引用保证。[R32]、[R35]

这个限制也提醒我们：不能只列出一堆各自存在的功能，就假设它们可以无缝叠加。架构设计需要核对组合兼容性。

## 4.4 校验与修复：将“输出有错”拆成可定位的错误

### 五层验收，每层回答不同问题

| 层 | 问题 | 典型检查 | 失败后的适当动作 |
|---|---|---|---|
| 完成与协议 | 拿到完整、正常的结果了吗？ | HTTP、停止原因、工具配对 | 处理传输或续接，不解析半成品 |
| 结构 | 字段形状符合接口吗？ | 必需项、类型、枚举 | 定向结构修复或调整任务拆分 |
| 语义 | 字段间含义一致吗？ | 对象、期间、口径、单位、数值 | 读取相关来源，修正具体绑定 |
| 证据 | 来源和支持关系成立吗？ | 来源存在、版本、原文、定位 | 补证据、冲突处理或保留未知 |
| 覆盖 | 原任务需要的项都处理了吗？ | 预期项与已处理项对账 | 补做遗漏项，不以空列表通过 |

这五层是本文的工程拆解，结合官方结构化输出、减少幻觉和评估原则，但不是声称官网定义了同名的五层产品。[R32]、[R36]、[R37]

### “每一条都正确”仍可能不完整

假设用户要求检查十项字段，模型只返回一项，且这一项完全正确。若校验器只遍历已返回结果，它会报告 100% 通过。正确的覆盖检查应从预期任务集合出发，对未出现的九项给出缺失或未处理状态。

配套实验因此同时保存 `expected` 事实键集合和结果中的 `seen` 集合。空 claims 不能在有必检项时自动通过。这是许多演示里不显眼、却直接影响上线可靠性的遗漏类型。

### 事实键应该包含哪些维度

对当前案例，至少是对象、指标、期间、统计口径。单位和数值是事实值的一部分，来源版本决定这个核验对应哪一份材料。不同任务可能还需要币种、计量方法、复权方式或统计时点，但不要在没有需求时无限加字段。

一个经常被忽略的区别是：单位转换与期间转换不同。`12.4 亿元` 转成 `124000 万元` 可以依据明确规则计算；“半年收入”转成“全年收入”一般不能靠乘二。前者是等价表示变换，后者是新增事实或预测。

因此，校验器可以允许有记录的单位规范化，却不应把改变期间当作同一种修正。

### 目标修复，而不是整份报告重抽

假设 50 项事实中只有 F17 期间错误。让模型重新生成全部 50 项，会给已经正确的 49 项带来新的变化风险。更好的反馈是指定 F17、相关来源和失败条件，要求返回局部补丁，再对补丁与整个产物进行必要一致性检查。

但局部修复不是永久冻结其他字段。如果来源版本改变，多个字段可能共同失效，需要扩大重验范围。修复粒度应依据依赖关系，而不是固定“一次只改一个字段”。这也是事实登记表要保留来源谱系的原因。

### 校验器本身会不会错

会。原始文档可能被错误解析；单位映射可能写错；手工标签也可能有误。于是“模型与真值一致”只能证明相对于当前真值的正确性，不能证明真值本身正确。

配套实验明确使用人工构造的合成事实，原文匹配采取严格的固定文本比较。它不是通用的自然语言支持关系判断器，更不能证明真实 OCR 提取准确。真实上线需要对源文档、解析结果、标注样本和校验器分别进行抽检与评估。

## 4.5 批处理：两本账，防止请求成功掩盖业务失败

官方 Message Batches 面向可独立处理的异步请求；返回顺序可能与提交顺序不同，应通过 `custom_id` 关联。批次进入终态，也不意味着每个请求都成功，更不意味着每个产物都通过业务验收。[R33]

### 第一本账：请求处理结果

记录输入业务键、输入版本、请求关联 ID、批次 ID、尝试号和请求终态。请求可能成功、错误、取消或过期。不能按返回列表顺序对齐输入，也不能让重新提交后得到的结果覆盖另一版本材料。

### 第二本账：业务验收结果

请求成功之后，还要检查停止原因、结构、事实与覆盖。一个请求传输成功却输出被截断，属于拿到响应但没有合格产物；一个完整输出返回 missing，则可能是诚实的模型结果，但不满足当前发布要求。

本文采用如下对账结构：

```text
提交项 = 待处理 + 请求成功 + 请求错误 + 已取消 + 已过期
请求成功 = 业务通过 + 需修复 + 需人工确认
```

状态分类必须互斥，统计时点必须一致。不要将请求仍在处理中的快照与终态结果混在一起计算“丢失项”。

### 重投应以业务身份和输入版本为依据

可使用 `文档哈希 + 片段标识 + 任务版本` 作为业务关联信息，另保存每次请求的 `custom_id` 和 attempt。失败项单独重投，成功项保留。若任务规则发生变化，即使原文不变，也应该明确这是新任务版本，而不是静默覆盖历史结果。

`custom_id` 解决的是请求与结果关联，不是后续数据库写入的幂等保证。入库仍需唯一业务键、版本检查和事务控制，不能因为 ID 看起来唯一就省略这些步骤。

### 为什么批处理不能替代任意 Agent 循环

客户端工具调用仍然需要应用执行、回传并继续下一轮。提交一批模型请求，不会自动建立一个完整多步业务编排器。对于可独立的抽取任务，批处理很合适；对于需要按工具返回动态决定下一步的探索任务，需要另外的协调层。[R33]

## 4.6 多轮审查与长文生成：独立证据比更多赞同更重要

### 为什么多个模型可能一起错

若三个审查者都只看到同一份错误摘要，它们共享同一个错误输入。即使提示词分别写“严格”“专业”“谨慎”，也不代表获得了独立证据。让它们投票，可能只是把同一个错误重复计票。

官方工作流与评估文章提供多轮改进和不同评分方式的思路；下面对证据独立性的设计，是本文对研究助手的具体应用。[R02]、[R07]

有效的分工应按错误类型组织：结构检查交给代码；期间和单位绑定交给确定性规则与原文核查；自然语言解释是否过度推断交给有明确标准的模型或人工；发布权限交给业务系统。不是为每一种检查都创建一个自由讨论的 Agent。

### 长文为什么在后半段容易把数字混在一起

只让模型从一大段聊天历史连续写作，它需要同时记住任务结构、多个期间的数字、已经写过的内容和剩余计划。上下文压缩后，如果事实只以自然语言摘要存在，期间与数字的绑定可能被弱化。

本文建议将长文生成设计为一条可核对的“编译管线”：

```text
原始来源
    → 候选事实
    → 已验证事实登记表
    → 大纲：每节需要哪些 fact_id
    → 分节写作：重新读取该节事实
    → 句子级 claim—fact 映射
    → 全文一致性与遗漏检查
```

例如，第二节只使用 F_H1，第三节只使用 F_FY；模型在写每节前读取对应记录，而不是凭前几轮的记忆复述。最后将文中数字、期间与 fact_id 对齐，检测未经授权的新数值或替换。

### 句子级校验不是只查数字是否出现

原文包含 12.4 和 28.1，报告也包含这两个数，仍可能将期间互换。因此应验证“这句话中的对象—指标—期间—单位—数值”整体关系，而不是只做数字集合比较。

对计算结果，应保存输入 fact_id 与计算表达式，例如同比增长由两个可比期间事实计算得到。不要让模型重新心算、再把没有计算记录的结果当作新事实。对解释性句子，则检查它使用哪些事实、是否引入额外假设，以及有没有把相关性写成确定因果。

### 何时停止反复审查

停止条件应是明确标准通过、达到预算，或发现无法自动裁决的证据缺口。不能要求两个模型“讨论到一致”为止，因为一致可能来自反复改写而非新证据。

对于真实冲突，正确输出可以是一个清楚的人工问题包：两个来源、对应版本、口径差异、影响的结论、还需要什么依据。**不把未知伪装成结论，本身就是高质量交付的一部分。**

**本领域的判断标准：**你能构造一个格式完美但事实错误的输出，并说明它会在哪层被拒绝；也能区分模型诚实报告缺失与系统实际执行失败。

# 领域五：上下文管理、长期状态与可靠性

**Context Management & Reliability**

前四个领域构成一条能执行、能校验的任务链。本领域处理系统长期运行后的问题：资料越来越多、工作分多次完成、证据发生变化、执行者部分失败，以及人工如何高效接手。目标不是让模型永远记住所有内容，而是保证必要信息可以被重新获得，已发生的工作可以被正确识别。

## 5.1 上下文、状态、记忆与缓存：解决的是四种不同问题

官方上下文工程文章讨论按需获取信息、压缩、外部笔记与子 Agent；相关文档还提供压缩、上下文编辑和 Token 计数能力。它们提供管理输入的机制，不自动替代你的业务事实与任务状态设计。[R05]、[R42]、[R43]、[R44]

### 上下文窗口是工作台，不是唯一档案室

工作台上应放当前任务需要的目标、约束、相关证据和待处理问题。所有原始资料、已验证事实、历史产物和回执，应有独立保存位置。模型需要精确事实时再读取，而不是要求它一直携带整套资料。

这里有一个基本区别：**知道某份资料在哪里**，通常比**永久保存那份资料的整篇摘要**更易维护。摘要可以帮助定位，但需要输出精确数字、原文或代码接口时，应回到可验证记录。

这不意味着每一步都重新读全部原文。可以缓存已验证事实，但缓存键应包括来源版本和任务口径；源文件变化后，旧核验不能无条件复用。

### 一份有用的压缩记录应该保留什么

“已经完成数据分析，接下来写报告”不足以恢复精确工作。本文建议保留以下不变量：用户目标、对象与期间、已完成单元、事实 ID 与版本、未解决项、当前计划和待执行副作用标识。

```json
{
  "task_id": "review_A_2025",
  "revision": 8,
  "input_versions": {"A:H1:2": "来源哈希"},
  "verified_fact_ids": ["F_A_H1_REVENUE"],
  "pending_units": ["A:FY:5"],
  "unresolved": ["年度报告单位需确认"],
  "next_action": "读取 A:FY:5 后继续，不根据半年数据推断全年",
  "pending_operation_id": null
}
```

压缩质量应通过恢复任务来检验，而不是仅检查摘要是否短。可以故意在压缩前后询问同一事实，检查对象、期间、单位和来源版本是否仍一致；再改变源文件，检查系统会不会发现缓存失效。

### 删工具历史也有协议边界

不能只删除看起来很长的工具结果，却保留必须依赖它的调用结构，或随意重建带签名内容的历史。官方压缩与上下文编辑能力有各自协议，应该按文档使用。本文的语义状态快照是应用数据，不冒充这些原生机制的内部表示。[R08]、[R42]、[R44]

### 缓存为什么不是记忆

Prompt caching 复用匹配的提示前缀，主要处理重复计算开销；它不自动证明事实仍有效，也不意味着缓存部分不占上下文。把随机请求 ID 或频繁变化的内容放在前缀前面，可能破坏复用；更合理的排列是稳定的工具和规则在前、当前任务与变化资料在后，具体命中行为按官方文档确认。[R34]

下面给出**本文的成本推导**，不用某一型号的当前价格代替一般结论。设同一前缀普通输入成本为 1，首次写入缓存成本为 w，命中成本为 r，累计使用 n 次：

```text
不缓存成本：n
缓存成本  ：w + (n - 1)r
缓存更省的条件：n > (w - r) / (1 - r)，前提 r < 1
```

假设 w=1.25、r=0.1，则第二次有效复用就可能摊平首次额外成本。注意这是指定参数下的算例；真实模型价格、时效、命中条件和失效比例不同，不能将这个阈值当成所有型号的保证。[R34]

工程上应该同时观察命中率、缓存输入量、普通输入量、延迟与产物质量。为了提高命中率而保留大量无关内容，并不一定改善整个系统。

## 5.2 人工接管：先明确需要人决定什么

官方用户输入与审批接口区分运行中的询问与批准；减少幻觉资料也强调允许信息不足。落实到产品时，需要进一步区分澄清、授权、专业判断和故障处理。[R18]、[R36]

### 四种不同的人机交接

**需求澄清**处理用户目标中的关键歧义，例如“本期”到底指哪个区间。**操作批准**处理一个明确动作能否发生，例如是否发布已固定版本的报告。**证据裁决**处理来源冲突或专业判断。**运行接管**处理工具故障、预算耗尽或环境异常。

把它们都简化为“是否继续”，会让用户不知道同意什么，也让系统缺少可审计的决定对象。批准应指向具体产物和目标；澄清应给出真正改变结果的选项；故障交接应说明已完成范围与安全的下一步。

### 什么时候值得打断用户

不是所有模糊点都值得询问。若不同解释会影响关键字段、不可逆操作或最终结论，应先澄清；若只影响次要呈现方式，可以选择可逆、低影响的默认值并明确记录。不要把能够通过已有文件解决的问题重新问用户，也不要在缺乏证据时让用户“确认一个猜测数字”。

本文建议把交接包缩成可执行的决策单：问题是什么、已知证据是什么、尝试过什么、当前阻塞在哪、不同选择会发生什么。原始日志可以附后，但不能让用户必须读完几百轮轨迹才能做决定。

### 用成本思维理解自动处理边界

假设某类错误会造成损失 C_e，人工复核成本为 C_h，当前接受结果的错误概率估计为 q。一个非常简化的比较是：当 `q × C_e > C_h` 时，复核可能有经济意义。这是本文的假设模型，不是合规规则，也没有考虑人工错误、等待成本和尾部极端损失。

它的价值是让人看到：相同 95% 准确率，在草稿排序和正式对外披露中可能对应完全不同的处理策略。阈值不能脱离业务后果，更不能直接拿模型自报的 confidence 代入这个公式。

实际应使用经过评估的错误信号，结合确定性失败、证据缺失和操作风险分流。若必需授权不存在，就算模型很自信，也不能进入自动执行。

## 5.3 多 Agent 的部分失败：不要让汇总器“洗掉”未知

Anthropic 的多 Agent 实践强调明确委派和结果汇总。分布式工作还需要处理部分成功、范围重叠和失败传播；下面的结构是本文的具体工程设计。[R03]

### 一个文本摘要为何不足以合并

执行者返回“已完成 A 报告分析，发现三项结论”。协调者可能不知道它只读了前两页，也不知道第三页读取超时。若综合器只提取结论，部分失败就被转换成了完整成功。

本文建议返回状态、完成范围、未完成范围、证据版本、任务版本和错误。结论与状态必须一起传播：

```json
{
  "task_id": "worker_A",
  "input_revision": 7,
  "status": "partial",
  "completed_units": ["A:H1:2"],
  "missing_units": ["A:FY:5"],
  "claim_ids": ["F_A_H1_REVENUE"],
  "errors": [{"code": "UPSTREAM_TIMEOUT", "scope": "A:FY:5"}]
}
```

协调者可以补做缺失部分、换路径或交给人工，但不能因 claim_ids 非空就改成整项成功。

### 完成率必须以任务范围为分母

若十个任务中只有两个成功返回，而仪表盘只计算“返回内容中正确率”，会掩盖八个失败。至少分别报告已完成覆盖、已返回结果质量和未解决项数量。

同样，不同子任务大小不同，简单按“成功 Agent 数量”统计可能误导。一个执行者处理九十页，另一个处理一页，它们不一定应该被视为相同业务覆盖。分母应根据实际任务单位设计。

### 迟到、重复与陈旧结果分别处理

重复结果可按任务 ID、输入版本和尝试号识别。迟到结果不一定无用，但需要检查当前任务是否仍然需要它。陈旧结果意味着输入或任务条件已经改变，不能直接覆盖新状态。

实验中的 CAS 只阻止旧 revision 写入，它不解决语义合并。收到冲突后，正确流程是重读当前状态、检查来源版本，再决定局部复用、重做或丢弃。无脑循环“读取最新版本然后覆盖”，等于绕过了刚刚建立的并发保护。

### 部分输出能不能交付

这取决于业务契约。探索型研究可能允许发布清楚标注缺口的草稿；要求全量核验的正式产物则必须阻断。应把策略写在验收器和产品状态中，而不是让综合模型每次临时决定“尽量回答”。

## 5.4 大代码库与知识库：保存地图，按需验证地形

官方大型仓库与上下文资料强调范围控制、分层探索和相关信息按需读取。与小型 Demo 相比，大系统的难点通常不在某一文件太长，而在跨模块关系和资料版本不容易一次装进上下文。[R27]、[R05]

### 一份仓库地图应该是什么

它可以记录模块职责、关键入口、调用关系线索、测试命令和数据流。但地图是定位辅助，不是实现本身。代码改变后，旧地图可能继续指向存在的文件，却已不再准确描述行为。

因此可以为地图记录生成时的提交版本或范围哈希，并区分“已验证关系”和“待确认推测”。执行具体修改前，重新读取关键定义、调用者和测试，而不是只依据三个月前的自动摘要。

### 以字段链路探索代替泛泛浏览

比如要修半年/全年字段串位，应从入口参数追踪到解析器、标准化层、数据存储、报表消费和测试。每个环节记录文件与符号位置，直到可以解释一个具体样例如何变化。

这个过程得到的上下文小，却足够支持修改。相反，读遍所有 README 后仍不知道实际字段在哪变换，得到的是背景知识而不是修改证据。

### 子 Agent 怎样帮助探索

可以让不同执行者调查互不重叠的模块，各自返回相关接口、文件定位和未确认点。主 Agent 负责建立依赖关系并确定改动顺序。不要让每个子 Agent 都重新阅读整个仓库，再给出一份泛化总结，这会制造大量重复上下文。

合并之前还要检查版本：不同工作树、不同提交或同时发生的代码改动，可能让两份局部结论不能直接组合。代码仓库的版本边界与文档来源版本具有同样的工程意义。

## 5.5 评估与置信度：将“感觉更好”变成可检验的改善

官方 Agent 评估文章区分任务、试验运行、运行轨迹、最终结果和评分器，并讨论能力评估与回归评估。最终环境中任务是否完成，与模型声称完成是不同对象。[R07]、[R37]

### 先分开三个评估层

**运行时测试**检查给定响应是否被正确处理，例如 tool ID 配对、批准拒绝、回执恢复。**模型任务评估**检查真实模型面对代表性输入是否产生正确行动与产物。**端到端产品评估**检查真实数据、权限、用户工作流与环境中的最终效果。

本书的 74 项测试主要覆盖第一层和确定性业务校验，没有获得真实模型任务成功率。把它们统称为“Agent 准确率 100%”，是不成立的。

### pass@k 与稳定成功不是一回事

用一个**明确假设的算例**说明：某任务每次成功概率为 p，各次运行独立且条件不变。运行 k 次，至少成功一次的概率与每次都成功的概率分别为：

```text
至少一次成功：1 - (1-p)^k
k 次全成功 ：p^k
```

当 p=0.8、k=3，前者为 99.2%，后者为 51.2%。所以“尝试三次总能挑到一次好结果”和“用户每次运行都可靠”相差很大。

真实 Agent 的错误往往相关：共享同一错误来源、同一提示词漏洞、同一不可用工具。此时不能把上述独立假设公式当作实际保证。应该重复运行代表性任务，观察稳定性、失败聚集与不同输入分布，而不仅保留最佳一次演示。

### 高置信度如何被实际数据检验

模型输出 0.95，只是一个分数；除非经过校准评估，不能直接理解成 95% 正确概率。可以在单独的标注样本中分组比较分数与真实正确率，再选择人工分流阈值，最后在未参与调阈值的保留测试集上评估。

对高分样本也应抽检。只复核低分结果，会让“非常自信但持续错误”的模式长期不可见。更换模型、提示词、工具或输入模板后，也不能无条件沿用旧阈值。

这套校准流程是本文根据评估原则提出的方法，不是某个官方 CCA 固定公式。

### 同时报告覆盖率和自动接受错误率

```text
自动接受覆盖率 = 自动接受项数 / 全部待处理项数
自动接受错误率 = 自动接受但实际错误项数 / 自动接受项数
```

一个系统通过拒绝所有结果，可以让表面错误数量为零，却没有交付价值。因此必须同时看风险与覆盖。没有任何自动接受项时，第二个比率应标为不可计算，而不是写成 0%。

阈值选择还应考虑错误分布。若全部错误集中在新模板或某类长表格，应优先修该类输入路径，而不是只提高全局阈值、牺牲所有正常样本的自动化率。

### 二十次没错，为什么仍然不足以证明可靠

配套实验用 Wilson 近似区间演示样本不确定性。假设 20 个可比、独立样本观察到 0 次错误，在通常采用的 95% 双侧 Wilson 区间下，错误率上界仍约为 16.1%。这是统计算例，不是对 Claude 的测量，也不是所有抽样条件下的严格保证。

计算中的 `p̂=e/n` 是观察错误率，`z=1.96`；区间中心与半宽为：

```text
中心 = (p̂ + z²/(2n)) / (1 + z²/n)
半宽 = z × sqrt(p̂(1-p̂)/n + z²/(4n²)) / (1 + z²/n)
```

它提醒我们，不仅要报告点估计，还要考虑样本量与代表性。同一模板复制二十份，也不等于二十种独立失败机会。对真实数据，应按任务、文档或模板分组检查，并对高影响失败保留专门测试。

### 评分器也需要验收

代码评分适合确定性条件，模型评分适合部分语义与表达判断，人工评分适合复杂边界。模型评分需要明确标准、与人工对照，并避免只奖励文风；代码评分需要用已知错误检验是否能发现问题；人工评分需要统一口径并检查分歧。[R07]、[R37]

本文的变异测试正是在验证评分能力：故意删除关键约束后，测试应变红。如果错误实现仍然通过，优先修评测，不要因全绿而高兴。

## 5.6 来源、支持关系与不确定性：引用不是装饰

官方 Citations 提供将结果关联到文档位置的能力；减少幻觉资料强调基于证据与允许未知。工程系统还需要确认引用位置真实、版本有效，以及原文确实支持对应结论。[R35]、[R36]

### 从“有链接”走到“有证据链”

本文把一条结论的检查分为：来源存在、定位有效、语义支持、版本适用。四者分别可能失败。

一个链接能够打开，但页码错了，属于定位错误；引用了正确段落，却把半年写成全年，属于支持关系错误；原文曾经正确，但后来被修订，属于版本问题；原始来源本身不可信，则需要另一个来源质量判断，不能靠引用格式修复。

因此，事实记录至少应保留 source_id、来源内容哈希或版本、段落或页面定位、原始摘录、规范化字段和核验状态。对计算结果，还应保存输入事实 ID 与转换规则；对推论，则应明确它不是原文直接陈述。

### 两个不同数字不一定是真冲突

在宣布冲突前，先核对对象、期间、口径、单位和修订关系。一个是合并口径，一个是母公司口径，可能都正确；一个是原始公告，一个是明确修订的后续公告，可能存在可解释的版本替代。

只有可比维度已经对齐、数值仍不一致，才应进入真正的冲突裁决。不能机械取平均，也不能总选日期较新的来源：较新文件可能讨论的是另一个期间，或只是重复旧数据。

### OCR 与解析错误怎样进入下游

若原始页面是“12.4”，解析层读成“124”，后续模型和校验器都基于错误文本工作，它们可能达成一致。此时失败发生在证据进入系统之前，不能指望多 Agent 投票修复。

本文建议将证据链向上延伸到原文件、页码、表格单元格或区域定位，并保留解析版本。涉及高影响数值、合并单元格、表头层级或脚注口径时，允许回到页面检查。这个方案是对来源管理的工程延伸，不声称本实验实现了复杂版面识别，也不声称原生引用功能自动验证 OCR。

### 不确定性要绑定具体结论

一句“本文可能存在误差”放在报告末尾，对人工处理帮助很小。更有用的是：“F17 的期间缺失，影响第三节同比判断；已查 A 与 B 两份资料，仍需补充 C。”这样不确定性既有范围，也有下一步。

同样，不要把一处缺失扩大为整份报告一无所知，也不要因为多数结论可靠就隐藏剩余缺口。可信系统应能精确表达：已验证什么、未验证什么、为什么，以及什么新证据会改变当前判断。

**本领域的判断标准：**上下文被压缩、任务被中断、资料发生变化或部分执行者失败后，系统仍能恢复事实、识别边界，并把人真正需要处理的问题交清楚。

# 综合实验：从正常运行到故障恢复

这一部分不再增加概念，而是把五个领域放回同一个运行过程。项目代码随手册单独提供，默认只用 Python 标准库与合成数据。**它是可检查的教学实现，不是完整生产平台。**

这与“先把所有类定义读完”不同。你始终围绕同一个问题：这个字段或分支保护什么失败？删掉它会出现什么？

## P.2 一次正常运行：从候选事实到可发布产物

**第一步，明确预期覆盖。**本次只要求合成公司 A 的 2025H1 合并营业收入。`expected` 保存这项事实身份，避免模型仅返回一个无关但正确的事实也被算作完成。

**第二步，读取来源。**默认脚本模型请求 `read_source`，得到原文和版本。返回没有直接附上用来判分的结构化真值字段；真实 API 模式需要模型从原文形成候选字段。

**第三步，提出候选事实。**候选结果包含对象、指标、期间、口径、单位、值与来源信息。默认脚本返回预设结果，是为了让工具循环可以确定性测试，不是让模型自己参加考试再取得满分。

**第四步，执行业务验收。**校验器比较候选字段和合成真值，检查来源版本、原文引用与任务覆盖。运行时只有在正常结束且验收无错误后才返回 `validated`。

**第五步，走可信审批与发布路径。**演示脚本模拟一个已认证的人类审批入口，为产物哈希和目标创建批准。发布服务重新使用可信校验结果并执行事务。这个入口没有被注册为模型工具，也没有实现真实用户界面或身份认证。

这条链路刻意把“模型能做什么”与“系统要保证什么”分开。模型可提出候选结果，但不能自己生成一个 `approved=true` 就完成发布。

## P.3 故障实验一：数字没变，只改期间

将候选结果中的 `period` 从 `2025H1` 改成 `2025FY`，保持 12.4、单位和原文引用不变。Schema 仍然合法，但 `PERIOD_MISMATCH` 应出现，必要任务覆盖也会失败。

这个实验暴露了两类检查的区别：结构合法性只看字段形状；事实绑定检查确认同一个数字属于哪个对象和期间。若仅比较“答案中的数字是否在原文出现”，此错误会漏过。

**工程迁移。**对于真实报表，应将币种、口径、时间区间等关键维度与值一起保存。它们不是可有可无的注释，而是定义这个数值含义的组成部分。

## P.4 故障实验二：工具部分失败，但模型仍然结束

一次响应请求读取两份报告，其中一个工具返回超时。运行时必须把两个结果分别关联回请求 ID，不能只保留成功的一条。

是否能最终通过，不取决于“有一次工具失败”这个事实本身，而取决于失败是否影响必要任务。某份可选补充资料暂时不可用，可能不影响当前事实核验；必需来源未取得，则应保留未完成状态。这也是为什么验收器需要任务范围，而不是机械地将所有工具错误一律变成业务失败。

**工程迁移。**把必需依赖与可选增强依赖分开。这样降级才有明确语义：省略可选内容可以交付；缺少必要证据不能装成完成。

## P.5 故障实验三：写入成功，调用方没有收到回执

演示程序在数据库提交之后主动抛出异常。调用方只能知道本次交互失败，无法仅凭异常判断发布是否发生。

随后重新打开 SQLite 数据库，用相同 operation_id 再请求。系统找到已持久化的回执，并返回历史结果，最终发布记录与审计记录均为 1。另有测试通过一个新的 Python 子进程读取同一数据库并恢复回执，以证明结果不依赖原进程中的内存字典。

这是对“回执丢失窗口”的定向实验，不是磁盘断电或任意进程崩溃的全面测试。真实远端系统若没有幂等和状态查询能力，不能直接套用这个结论。

**工程迁移。**重试之前先问：动作可能已经发生吗？业务身份是否稳定？结果存在哪里？调用方重新启动后还能查到吗？只有这些问题有答案，重试才不只是重复执行。

## P.6 故障实验四：批准之后修改报告

先批准原产物，再修改 claims，然后尝试发布。由于批准绑定原产物哈希，发布应被拒绝。即使新产物在语义上看起来更好，也不能静默继承原版本的批准。

内容哈希在这里是指纹，不是数字签名，也不证明内容真实。它只帮助系统确认“正在操作的内容是否与批准对象一致”。批准来源的身份、事实的真实性，仍依赖其他独立控制。

**工程迁移。**涉及人工同意的工作流，要把“同意了什么”保存成可比较的对象。只保存一句“已确认”不足以处理后续改稿、目标切换或资料更新。

## P.7 故障实验五：旧执行者晚到

两个执行者读取同一任务 revision=0。第一个更新成功，任务进入 revision=1；第二个仍按 revision=0 提交，则必须得到 `STALE_TASK_REVISION`，不能覆盖新结果。

另有并发测试让八个执行者竞争同一个 revision，只有一个更新成功。这个测试验证版本控制，不验证复杂的语义合并，更没有实现一个完整分布式任务调度器。

**工程迁移。**当 Agent 可以并行执行、人工也可以修改任务时，状态更新需要表达“我依据的是哪个版本”。只记录“最后更新时间”但不参与写入条件，通常不能阻止丢失更新。

## P.8 实际执行结果与怎样复现

在项目目录运行：

```bash
python -m unittest discover -s tests -v
python demo.py
python run_mutations.py
```

本次交付实际结果为 **74 项测试通过，3 个选定的错误变体全部被捕获**。测试数量不是可靠性百分比；它只是这份实现已检查范围的具体记录。

| 测试部分 | 数量 | 主要覆盖 |
|---|---:|---|
| 事实契约 | 25 | 对象、期间、口径、单位、值、来源版本、引用、缺失、覆盖 |
| 工具运行时 | 20 | 完整消息、调用关联、多工具、预算、停止原因、业务验收 |
| 持久化与状态 | 21 | 批准、幂等、回执丢失、独立进程读取、并发、CAS、租户 |
| 评估计算 | 8 | 覆盖/错误率分母、重复成功假设、Wilson 区间边界 |

`demo.py` 的默认输出包含：

```text
agent outcome: validated
model calls: 2 ; tool calls: 1
injected fault: database committed, caller received no receipt
after recovery (publications, audit events): (1, 1)
late worker: rejected (stale revision)
hypothetical IID p=.8, k=3: at-least-one= 0.992 ; all= 0.512
0 errors in 20 synthetic trials: Wilson 95% upper bound= 0.1611
```

三个变异分别去掉期间绑定、批准哈希绑定与既有回执处理。变异是在临时副本中执行，原项目不会被破坏。日志中的 `FAILED` 表示错误变体被检测到；整个变异脚本成功退出，表示三个选定错误都未逃过测试。

特别看第三个变异：删除“返回既有回执”的处理后，数据库唯一约束仍然阻止第二条相同发布记录，但调用方得到异常，不能安全恢复原成功结果。因此，“没有重复写入”和“重试能得到同一业务结果”是两个要求。幂等设计不应只做到前者。

期间检查的变异测试也刻意隔离了错误来源：保持任务要求为 H1，引用真实 FY 来源并保留其余正确字段，只把候选期间标成 H1。这样任务覆盖检查不会替期间支持检查兜底，删除期间绑定就会错误通过。好的负向测试应针对一个明确不变量，而不是靠无关错误碰巧拒绝输入。

## P.9 接入真实模型后，还必须补什么

可选 `live.py` 使用真实 Messages API，请求中配置工具与结构化输出。需要用户在自己的环境显式设置 API Key 和可用型号，并会产生调用费用。本次没有发起线上请求，所以没有宣称账户可用性、模型抽取效果或 API 实际联调通过。

即使在线示例运行成功，还应补三类验证。

**真实模型评估。**准备未进入提示词的标注资料，运行同一组正常、缺失、冲突、长任务和错误输入。分别记录检索覆盖、事实正确性、工具误用、拒绝与人工分流，不能只看最终 JSON 能解析。

**真实集成测试。**启动真实 MCP 服务，验证连接、认证、工具发现、错误转换、服务重启和权限拒绝；检查原始 API 与 SDK 版本组合。离线脚本模型不覆盖这些兼容性。

**生产控制。**替换模拟身份上下文、固定时间和临时批准入口；建立真实身份鉴别、访问控制、批准有效期、受保护验收、运行日志和审计。这里的审计表只记录成功模拟发布，不是完整安全审计平台。任务 CAS 也只是并发更新原语，不等于所有状态迁移已被业务规则验证。

### 推荐的上线演进，而不是一次搭完大平台

先让系统只读并生成草稿，收集人工核查结果。随后在不改变人工流程的情况下进行影子运行，比较同一任务的证据与遗漏。达到明确标准后，才把部分低影响环节自动化；涉及正式发布仍由独立批准与业务系统控制。

扩大自动化范围时，应有对应回归集、故障处理和回退方式。上线开关不是“把 Agent 从测试环境移到生产环境”，而是逐步扩大它能影响的真实业务边界。


## P.10 生产排障与版本回退：让一次失败能够被解释

下面是本文提出的运行记录设计，不是声称配套实验已经实现完整可观察性平台。一条任务至少关联 `run_id`、任务版本、输入版本、模型与提示词版本、工具调用 ID、业务 operation_id 和最终验收状态。工具调用失败还应能关联相应上游请求，外部写入则关联回执。

这些标识解决不同的追踪问题：run_id 让你找到一次完整运行；tool_use_id 让你找模型交互中的调用；operation_id 让你识别跨重试的同一个业务动作；source_version 让你确认当时看到哪份材料。只保存一段“执行失败”的日志，无法回答这些问题。

排查一份错误报告时，可以沿下面的顺序推进：先确认是否加载了正确任务与资料版本；再看检索有没有取得必要来源；检查工具是否成功及结果是否截断；核对候选事实在哪个维度首次出错；检查校验器为什么未拦截；最后确认错误是否已经产生外部副作用。这个顺序从证据到行为，不要求先相信模型对自己失误原因的解释。

观察指标也应分层：请求失败率看服务稳定性，必检项完成率看任务覆盖，事实验收通过率看产物质量，人工接管比例看流程负担，单个合格产物的成本看经济性。低延迟和低错误率不能通过把困难任务全部静默丢弃获得；被拒绝和未完成的任务要保留在分母中。

版本发布时，应把模型选择、提示词、工具 Schema、校验规则与评测版本作为一组可追溯配置。单独回退其中一个组件，可能与其他组件不兼容。先在保留测试集和影子流量中验证，再扩大作用范围；出现退化时，回退的是后续处理路径，不是已经发生的历史效果。

例如，回退提示词不能撤销已经发布的报告。已经产生影响的错误，应通过更正、撤回或重新审批等明确业务流程处理，并保留原回执与修订关系。**代码回滚、状态恢复、业务补偿是不同动作。**

日志中也不应无差别保存全部原文和工具返回。可保存必要的结构化事件和受控来源定位；需要保存敏感原文时，应设置适当权限与保留策略。内容哈希和 ID 也不是自动匿名化工具，不能因此取消数据访问控制。

# 架构判断训练与学习验收

以下是本文自拟练习，不是官方真题。每题的目标不是选出一个术语，而是说明依据、替代方案和验证方式。

## A.1 一个工具返回 10,000 行，模型经常漏掉其中几条，应该换大窗口吗？

先确认任务需要逐行语义判断，还是可以确定性筛选与聚合。如果只需要几个期间的统计，优先将筛选和计算放到代码层，保留口径与来源，再提供少量结果。若每行都可能含重要语义，则按可独立单位处理并对账，不能直接过滤掉不理解的内容。

大窗口可能缓解容量限制，但不解决输出结构混乱、任务覆盖未定义和无关信息过多。比较方案时应使用相同任务集，测必要记录覆盖与最终正确性，而不只看输入是否装得下。

**对应：**2.1、2.5、4.5、5.1。

## A.2 核验 Agent 总是不被调用，应把 description 写得更强硬吗？

先判断核验是可选增强还是必经步骤。可选增强可以改善触发描述并评估误触发/漏触发；必经核验则应移到编排代码或提交关卡，不能依赖模型选择。两种需求的控制权不同，不能用同一种提示词手段解决。

验证方式是构造不调用核验者的候选轨迹：如果任务仍能进入发布，说明必经条件没有真正落实。

**对应：**1.3、1.4、3.2。

## A.3 报告中两个数字都能在原文找到，为何仍然不可信？

因为数值出现只证明字符存在，不能证明对象、期间、单位和口径对应。应构造数字相同但期间不同、对象不同的最小对照样例。若校验器只做文本包含判断，这些样例会暴露缺口。

正确修复是绑定语义维度和来源，而不是让模型再解释一次自己的信心。

**对应：**4.1、4.3、4.4、5.6。

## A.4 用户已经批准，为什么发布服务仍然检查产物？

批准回答“允许发布哪一个对象”，事实验收回答“对象是否满足要求”，两者相互独立。批准后改稿需要重新确认；批准本身也不能把假来源变成真实依据。有效流程应将批准绑定到精确产物，同时在提交路径验证必要条件。

如果人工明确决定接受带缺口产物，应通过受控业务例外记录处理，而不是让模型默默跳过校验。

**对应：**1.4、1.5、2.3、4.4。

## A.5 模型运行 3 次总能成功 1 次，能否宣称成功率接近 100%？

必须说明指标是“允许三次尝试后至少成功一次”，并包括失败重试成本。它不能直接代表单次稳定性。若最终由人工挑选最佳结果，人工选择成本和误选风险也属于系统成本。

评估应保留所有运行，区分单次成功、至少一次成功、连续稳定成功，并检查错误是否相关。不能只保存最好的轨迹。

**对应：**1.6、5.5。

## A.6 PostToolUse 已经脱敏，为什么审计系统仍可能看到原文？

因为后置转换只控制某一条输出路径，原始结果可能更早被工具、SDK 或日志采集器记录。需要画出数据经过的每个存储和显示位置，再分别确定脱敏与访问控制。模型可见内容被修改，不等于上游记录被删除。

应通过实际日志检查与测试验证，而不是只审阅 Hook 返回文本。

**对应：**1.5、2.3、3.6。

## A.7 Agent 恢复后用了旧资料，应扩大上下文还是保存更多摘要？

先检查事实与来源版本的关联。即使把旧摘要完整放回去，它仍然可能是过期信息。正确恢复需要读取当前任务版本和来源版本，确认已验证事实是否仍适用，再按需要重读原文。

上下文大小处理容量问题，版本与恢复协议处理时间一致性问题。它们可以共同改善系统，但不能互相替代。

**对应：**1.7、5.1、5.4、5.6。

## A.8 所有单元测试通过，为何不应立即上线？

先看测试层级。脚本模型测试证明运行时如何处理已知响应；它不证明真实模型面对新文档会选择正确动作。合成数据验证证明规则实现符合预设真值；它不证明真实解析与标注没有错。SQLite 测试也不证明远程发布接口的幂等与身份鉴别。

下一步不是简单增加更多同类单元测试，而是补齐真实模型任务集、集成契约、权限边界、故障注入和真实工作流验收。测试的价值取决于覆盖的失败面，而不是总数。

**对应：**3.5、3.6、5.5、综合实验。

## 学习完成的标准

你不需要记住全部参数，但应能够对每一种设计写出：它解决什么问题、依赖哪些假设、有哪些替代方案、失败怎样被发现、能否回退，以及哪些结论尚未得到验证。

建议保留三类学习产物：一份能解释选择理由的设计记录，一组能主动暴露失败的测试，一条可重现的完整运行轨迹。它们比“看完了几篇文章”更接近架构能力。

## 最容易混用的版本与产品边界

工具输入的 `strict: true` 与最终输出的 `output_config.format` 不是同一个配置；某些 SDK 便利方法又有不同参数名。CLI 的 JSON 运行包装不是任务结果本身。Messages 的 `is_error` 与 MCP 的 `isError` 属于不同层。`allowed_tools` 的批准语义不等于完整工具白名单。项目 `CLAUDE.md` 的内容加载不等于实际设置文件的确定性优先级。子 Agent 的当前委派名称与旧教程可能不同。原生引用与 JSON 结构化输出的组合应核对兼容性。[R08]、[R11]、[R12]、[R13]、[R17]、[R19]、[R22]、[R24]、[R32]、[R35]

遇到这些差异，应以安装版本的行为测试和当前官方文档共同核验，不能只根据变量名猜测。

## 本版仍然存在的明确限制

完整官方考试指南未成功读取，所以不把本书称为最新版所有知识/技能子项的官方逐条覆盖版。Partner Academy 认证入口在本次读取中不可访问；本书不据此前回答或第三方转录重申题量、费用、通过分数、权重和报名要求。

技术正文使用官方来源，不把社区题库或培训文章混作官方依据。细分学习编号沿用既有导航，目的是保持学习连续性；拿到完整官方指南后，应进一步核对细分要求及版本差异。

代码使用合成事实与受控故障，只验证已列明的不变量。没有完成真实 Claude 模型、MCP 服务、正式 CI、生产权限网关、真实复杂 PDF/OCR 或外部发布服务的端到端测试。线上适配器属于可供验证的实现起点，不是已验证部署。

## 结语：架构能力体现在哪里

当一个系统偶尔答对时，关键问题是怎样让它稳定工作；当一个系统经常出错时，关键问题是能否把失败定位到正确层。你最终应该能清楚区分：模型建议与执行许可、消息结束与任务完成、合法 JSON 与事实支持、上下文与持久状态、重复调用与重复业务动作、测试通过与生产验证。

掌握这些区分之后，具体工具可以更换，模型可以升级，框架可以重构；你仍然知道什么必须保持不变，以及怎样证明它没有被破坏。
