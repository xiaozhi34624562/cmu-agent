# 生产系统什么时候需要 CoT 与 reasoning：论文证据、API 语义和 RAG 评测方法

核查日期：2026-10-30（Asia/Shanghai）。这是独立工程专题，不是课程新增讲次。论文版本、核查位置、本地原文与 SHA-256 见 [SOURCES.md](SOURCES.md) 和 [REFERENCES.json](REFERENCES.json)。

本文回答一个具体决策：**对于 Agent / workflow 中的一次 LLM 调用，应不应该增加推理计算，应不应该写 `think step by step`，以及如何判断新增投入改善了整个业务流程。**论文结果、厂商建议与本文工程推导分别标注；没有调用付费模型、复现论文分数或测量用户生产服务。

## 1. 把问题拆开

原问题可以整理为五个相互关联、但需要分别验证的问题：

1. **提示干预**：在其他条件相同时，添加 `think step by step`、指定时间顺序或给出业务检查步骤，分别何时有效？
2. **计算控制**：API 的 reasoning / thinking / effort 控制什么？与提示式 CoT、最终答案长度有什么关系？
3. **证据使用**：RAG 已取回文档后，为什么进一步推理可能提高综合能力，也可能破坏对原文的忠实度？
4. **流程分工**：哪些节点值得多想，哪些节点应该去检索、调用计算工具或停止？
5. **验收与路由**：怎样用真实样例、配对实验和成本指标，决定默认配置与升级条件？

研究支持的回答是：**没有跨模型、跨任务通用的 CoT 开关规则。任务特征可以提供起始假设，生产选择要看同一节点的实测收益；推理模式、提示措辞、证据质量和工具反馈必须分别控制。**（[R01]，§3–6；[R04]，§2–5；[R05]，Table 1；[R06]，§5–6）

## 2. 四件经常被混在一起的事

| 层次 | 实际控制什么 | 不能据此推出什么 |
|---|---|---|
| 提示式 CoT | 请求模型先生成中间文字，例如逐步推导；它改变输入与输出行为 | 不保证启用某种厂商内部模式，也不保证实际更准确 |
| 推理模式与 effort | 服务端允许或调节推理计算；触发、预算与默认值依模型和接口而变 | 不等于固定生成多少 token；同名档位不保证跨厂商等价 |
| 最终答案和解释 | 用户看到的回答、引用、算式、检查结果与说明 | 长答案不代表高推理投入，短答案也不代表没有推理 |
| 工作流与工具反馈 | 程序安排多次调用，执行搜索、SQL、计算、测试并把结果送回模型 | 一次调用中写了完整计划，不等于这些动作已经执行 |

前两行的区分见 [OpenAI Reasoning models][D01]、[Claude Thinking][D03] 和 [DeepSeek Thinking Mode][D07]。最后一行见 Anthropic 对 workflow、agent 和环境反馈的区分。[D10]

对普通自回归模型，先生成中间文本可以增加串行计算，并让后续生成使用前面得到的中间结果。对经过推理训练的模型，服务端本来就可能进行这类计算；加一句提示不是把普通模型即时变成同等的推理模型。（[R01]，§2；[D01]，Advice on prompting）

关闭接口定义的 thinking 模式，也不等于模型完全失去逻辑推断能力；需要区分通常的生成计算与服务端专门提供的额外推理机制。

**可审核说明与内部 CoT 也要分开。**生产上可以要求“结论、支持它的原文、计算式、适用条件、缺失项”，不必要求模型公开全部内部思维。Anthropic 的干预实验表明，可读 CoT 不一定完整披露实际影响答案的因素；这不等于 CoT 没有计算作用。（[R10]，§2–5）

另一个容易混淆的词是 faithfulness：

- **内部过程忠实度**：显示的推导是否反映真正影响模型答案的因素。[R10]
- **上下文忠实度**：产物中的主张是否由给定证据直接支持，或经有效推导得到。（[R08]，§3）

企业 RAG 主要需要审核第二项；第一项研究不能直接变成企业文档幻觉率。

## 3. 近期论文究竟支持了什么

### 3.1 提示式 CoT 的收益具有任务差异

**To CoT or not to CoT?**（ICLR 2025；核对 v3，2025-05-07）汇总 100 多篇论文，并评测 14 个模型、20 个数据集。其主要发现是：提示式 CoT 对数学、逻辑和符号操作的收益较大，知识、常识等任务平均收益较小且不稳定；形式执行中，语言推导又常不如接入符号求解器。（[R01]，§3–5）

它适合反对“给所有节点统一加一句 step by step”。但研究主要是普通提示式 CoT，长时程规划覆盖有限；不能据此断言 GPT-6 等当前推理模型只对数学有价值。（[R01]，Appendix I.1）

### 3.2 2026 年的新证据修正了“简单事实题不需要推理”

**Thinking to Recall**（v1，2026-03-10）在 Gemini 2.5 Flash / Pro 与 Qwen3-32B 上比较 reasoning 开关，测试闭卷单跳事实问答。开启推理有时能召回原先难以答出的参数知识，特别是在多次采样的能力边界指标上。（[R04]，§2–4）

因此，“没有新外部事实”不能推导为“推理不会提高答案质量”。它可能帮助重组输入或激活模型已经学到的知识。论文也发现生成的中间错误事实会增加最终幻觉风险；这一闭卷结果不能证明企业 RAG 应允许模型用记忆补齐文档缺失。（[R04]，§5）

### 3.3 更多计算和更长轨迹都不是单调收益

**Scaling LLM Test-Time Compute Optimally…**（2024）在 MATH 和专门训练的修订器、验证器上发现，问题难度影响合适的计算分配：并行采样、顺序修改和搜索不是可以互换的投入方式。它研究的不是商业 API 的一个 effort 字段。（[R02]，§4–7）

**Don’t Overthink it…**（核对最新 v2，2026-02-03）在四个开放推理模型、数学竞赛题与 GPQA-Diamond 上，每题采样 20 条轨迹。同一道题中，较短轨迹常比冗长轨迹更有效；但难题平均仍需要更多思考。**采样后选出短轨迹，不等于强制截断推理会提高准确率。**（[R03]，§3–6）

**Inverse Scaling in Test-Time Compute**（TMLR 2025；v2，2025-12-15）构造带干扰、伪相关或约束跟踪问题，显示增加计算可能放大错误解题框架。不同模型使用的干预包含 API 档位、提示和预算，自然长度分析又属于另一种观察；部分模型在受控任务中仍正向受益。这些是有意寻找的逆缩放任务，不是生产任务的平均退化比例。（[R11]，§3–4、Appendix C/D）

工程含义是测试质量—预算曲线，同时评估另一种投入：把同等资源用于计算工具、重新检索或独立检查，是否更划算。这是基于上述研究的推导，不是论文已经替当前系统测出的最佳配置。

### 3.4 直接 RAG 开关实验：同一个模型也会出现相反方向

**LIR³AG**（AAAI 2026；v2，2026-01-19）提供了很贴近本问题的比较：固定 Qwen3 模型规模，在 Vanilla RAG 下比较 think / no-think。下表来自 **Table 1，实际 PDF p.6**，F1 为 0–1 标度：

| 模型与任务 | no-think | think | 观察 |
|---|---:|---:|---|
| Qwen3-14B，MultiHop-RAG | 0.637 | 0.615 | 下降 |
| Qwen3-32B，MultiHop-RAG | 0.668 | 0.654 | 下降 |
| Qwen3-32B，MuSiQue | 0.316 | 0.410 | 提高 |

这说明“都是多跳 RAG”仍不足以预测开关收益。作者提出上下文组织和冗余推导的解释，但没有单独证明下降的因果机制。其最终方法还同时改变重排和中间证据组织，不能把整个方案的收益归因为关闭 thinking。（[R05]，§3、§5）

### 3.5 最新 RAG 路由研究：检索和生成一起选，但保持证据权重

**One Size Does Not Fit All! Dynamic Retriever and Generator Selection for RAG**（DRAG，v1，2026-09-15，预印本）比较不同检索复杂度与生成配置。固定高检索时，GPT-OSS-20B 在 FRAMES 的 F1 随 low / medium / high 为 **28.6 / 28.8 / 26.3**，没有单调改善。（[R06]，Table 3，PDF p.7）

但其生成档位同时改变 `max_new_tokens`（512 / 2048 / 4096）。不能把结果视为单独隔离 effort 的实验；本地 vLLM / A100 / batch 12 的耗时也不能外推为 SaaS 延迟。该论文尚为预印本，主要用于补充“按查询联合分配检索与生成投入”的近期证据。（[R06]，§5.3、§5.5、§6）

### 3.6 先分清证据不足和证据使用失败

**Sufficient Context**（ICLR 2025；v3，2025-04-23）研究的关键是：相关片段不一定足以构成答案。模型可能在证据不足时继续回答，也可能在证据充分时答错。它不是 reasoning 开关比较，却提供了很有用的故障分类。（[R07]，§3–5）

**GRACE**（EMNLP 2026；v2，2026-08-22）评测上下文推导步骤的忠实度，说明最终答对仍可能伴随中间不受证据支持的步骤。其测试集刻意挑选 judge 有分歧的困难轨迹，不能把其中错误比例当作普通生产分布。（[R08]，§3–4）

对 Agent，**The Danger of Overthinking** 把问题进一步指向环境反馈：模型可能长时间在内部模拟，却不及时执行测试或读取工具结果。该研究中的 overthinking 不等同于 token 数多，而且低 effort 也未必更少出现这种行为。其若干计数、百分比存在内部不一致，本文只采用机制分类，不使用宣传式提升数字。（[R09]，§3–6）

## 4. 厂商官方建议：默认不需要再喊一句“逐步思考”

以下为 2026-10-30 实际访问的动态文档，访问日期不是发布日。厂商说明定义接口与提供实践建议，不能替代跨模型因果实验。

### 4.1 OpenAI

官方区分 reasoning tokens、可见输出和 `reasoning.effort`；Responses API 的字段为 `reasoning: {"effort": "low"}`，Chat Completions 为 `reasoning_effort`。effort 是计算投入调节项，支持值与默认值依模型而定。（[D01]，Reasoning effort）

官方最佳实践建议：任务、限制与输出格式写清楚；对本身会推理的模型，`think step by step` 通常无须添加，有时还会妨碍表现。它没有要求删除业务规则或可验证步骤。（[D02]，How to prompt reasoning models effectively）

当前模型也不一定允许完全关闭：例如 GPT-6 Astra 不支持 `none`，GPT-6.1 Sol 不支持 `none` / `minimal`。因此跨模型强行统一 off / low / high 可能产生请求错误。[D01]

### 4.2 Anthropic / Claude

当前 Claude 文档区分 thinking 与 `output_config.effort`；新模型主要使用 adaptive 机制，是否默认开启、能否关闭依模型而定。effort 还影响答案和工具调用投入，不只是思维 token 的硬上限。（[D03]；[D04]）

官方建议先调 effort，再在确有需要时用自然语言引导思考触发与深度，并在自身任务上评测。长文档任务可以先提取相关原文，帮助后续回答聚焦证据；这是可验证的工作产物，不要求公开完整内部推导。（[D05]；[D06]）

Claude 的可见 thinking 也可能是摘要或被省略；不能用“没有显示思维文本”判断没有进行推理或没有产生费用。[D03]

### 4.3 DeepSeek：必须纠正“传 reasoning 才算开启”

**这句话不是通用规则，对当前 DeepSeek 官方接口也不成立。**当前 `deepseek-flash` / `deepseek-v4-pro` 官方文档列明默认开启 thinking，默认 effort 为 high；旧版本、第三方部署或 SaaS 网关须另查。（[D07]；[D09]）

按当前文档，控制形式包括：

| 接口 | 控制形式 |
|---|---|
| Chat Completions 明确模式 | `thinking: {"type": "enabled"}` 或 `"disabled"`；OpenAI Python SDK 通过 `extra_body` 传入 |
| Chat Completions effort | `reasoning_effort`；API Reference 列 `none` / `low` / `high` / `max`，`none` 关闭 |
| Responses | `reasoning: {"effort": "none"}` 或相应开启档位 |

当前指南还列出映射：`medium` 和 `xhigh` 都映射到 high；所以某个 SaaS 的三个不同按钮，可能最终只对应一个实际档位。指南概览只列 low / high / max，API Reference 则补充了 none；实现时以具体协议参考为准，避免同时设置相互冲突的控制字段。（[D07]，Toggle and Effort Control；[D08]，reasoning_effort；[D11]，reasoning）

例如，使用当前官方 Chat Completions、通过 OpenAI Python SDK 显式关闭：

```python
# 文档核验示例；未发送付费请求。
# client 应事先指向 DeepSeek 官方 endpoint；第三方网关需单独确认兼容性。
response = client.chat.completions.create(
    model="deepseek-flash",
    messages=messages,
    extra_body={"thinking": {"type": "disabled"}},
)
```

还有一个实验陷阱：当前 DeepSeek thinking 模式下，`temperature`、`presence_penalty`、`frequency_penalty` 被忽略，`top_p` 又依模型和模式有不同规则。两组请求虽然写着相同采样值，服务端生效策略未必相同。此时比较的是完整模式的部署效果，不是纯粹只改了推理长度。（[D07]，Input and Output Parameters）

### 4.4 在第三方 SaaS 上，先确认实际执行的是什么

建议保存供应商、endpoint 类型、实际模型版本、SDK/适配器版本、转换后的请求字段、服务端 usage 和结束原因。不要保存凭据。区分：

1. 前端 reasoning 选项；
2. 网关实际转发或映射的字段；
3. 后端支持并执行的模式；
4. 返回给客户端的思维摘要或 token 用量。

它们不保证相同。没有 usage 字段时应记为“推理用量不可观测”，不能记成 0。此处是基于不同厂商接口差异的工程建议。（[D01]、[D03]、[D07]–[D11]）

## 5. RAG 中开启 reasoning 为什么可能更差、更慢

首先分开两种 RAG 合同：**严格文档问答**要求结论由指定资料支持；**允许外部背景的研究辅助**可以使用额外来源，但必须注明来源与推断边界。闭卷参数知识召回研究不能自动放宽第一种合同。（[R04]；[R07]；[R08]）

### 5.1 语义上可能发生的退化

以下是故障假设，需要逐例回放；不能看到答案变差就直接宣布根因是 overthinking。

- **引入文档外的前提**：模型用似乎合理的背景补足缺失信息，使推导与原始证据脱离。检查新增主张的支持来源。（[R04]、[R08]）
- **错误组合多个期间或口径**：把历史回顾与未来预测、母公司与合并口径拼成冲突或趋势。需要字段和原文核验，而不是更多修辞。
- **过早形成解释**：先假定某个原因，再围绕它选择证据。需要检查竞争解释与反证，而不是仅加“再认真想一遍”。
- **任务没有足够的推理收益**：直接字段抽取已经能完成，额外生成增加耗时，甚至引入改写错误。（[R01]、[R05]）

后两类中的具体业务机制属于工程诊断假设；论文的混合结果并未替当前系统证实它们。

### 5.2 运行层面看起来像“质量差”的问题

OpenAI 的 `max_output_tokens` 同时限制推理与可见输出，预算耗尽可能发生在最终答案生成之前；reasoning tokens 计入成本。Claude 和当前 DeepSeek Responses 也有思考与答案共享总输出上限的规则。（[D01]，Controlling costs；[D05]，Cost；[D11]，max_output_tokens）

因此应先排除：输出预算耗尽、请求超时、网关未透传模式、流式解析错误、把 `reasoning_content` 当最终 `content`、工具回合历史回传不符合供应商契约等问题。它们和“推理后的业务结论更差”是不同失败类别。（[D07]，Multi-round Conversation / Tool Calls；[D08]；[D11]）

### 5.3 一个贯穿例子：收入增长为什么不等于经营改善

假设检索到三条材料：

- E1：2025 年收入 120 亿元，2024 年收入 100 亿元；
- E2：2025 年包含新并表业务收入 25 亿元；
- E3：2026 年管理层预计恢复增长。

问“2025 年收入是多少”，抽取 E1 即可。问“同比多少”，用程序算出 20%，引用 E1。问“原有业务是否改善”，需要核对 E2 的口径、2024 年可比范围、并表时点等；**不能直接用 120−25 与 100 比较，就把结果写成同口径内生增长**。E3 又是未来展望，不能当作 2025 年已经改善的证据。

增加推理可能帮助发现这些约束，也可能把缺失条件补成看似完整的故事。可验收产物应是“已支持的事实、条件性推断、待补信息”；缺失项触发检索或保留不确定。该例为教学构造，不是论文或实际公司的实验。

## 6. 每个调用节点怎样选

下表是工程起始配置，**不是普适最优结论**。完全关闭不被支持时，从最低支持 effort 起测；不要为了构造 off 组而悄悄换模型。

| 节点及失败特征 | 起始方案 | 升级或改流程的条件 |
|---|---|---|
| 分类、字段抽取、格式转换 | 最低可用 effort；明确 schema、单位与缺失值规则 | 样例显示存在真实语义歧义，且更高 effort 能稳定修复 |
| 单文档直接问答 | off / low；证据优先，关键结论引用 | 需要跨段落组合、例外条款或复杂限定 |
| 多文档比较、时间与口径对齐 | low / medium 起测；保留证据身份和期间字段 | 证明 high 修复的实质性遗漏足以补偿延迟，且不增加无依据主张 |
| 数值计算、SQL 执行、代码测试 | LLM 识别任务与选择工具；程序执行并回传结果 | 失败在计划或条件理解时升级推理；执行错误优先查工具和输入 |
| query planning 与多跳检索 | 有限推理＋实际检索反馈 | 已识别必要证据缺口；升级取证路径，而非只延长最终生成 |
| 最终措辞、引用整理 | 尽量使用已核验事实；低投入起测 | 综合本身仍有未解决冲突时先返回证据分析节点 |
| 核验器 | 确定性校验＋必要的独立语义审查 | 有可检查准则或新反馈；重复相同主张不算独立验证 |

这些选择综合了任务差异、计算分配和反馈研究。（[R01]、[R02]、[R05]–[R09]） Anthropic 也建议增加复杂度应有可测收益，并让 agent 从工具结果获得环境反馈。[D10]

“按时间顺序推导”只有在时间关系本身决定答案时才是有理由的要求，例如区分事件发生日、发布日期、预测期和研究截止日。若任务是核对单位或比较定义，时间顺序未必是有效分解。**给模型必要的业务约束，比统一指定一种叙述顺序更有针对性。**这是工程推导，应作为待评测 prompt 版本。

## 7. 用什么 prompt 替代机械添加 step by step

建议保留任务原本必需的业务规则，用下面的方式表达证据合同。它是待验证模板，不保证优于当前 prompt。

```text
任务：根据给定材料回答问题。

证据规则：
- 结论必须由给定材料支持，或明确标记为基于材料的条件性推断。
- 核对实体、期间、实际/预测、指标口径和单位。
- 多条证据存在差异时，先判断它们是否真的可比。
- 缺少必要信息时指出缺什么；允许的工具可用于补齐，否则保留未确定状态。
- 数值运算交给指定计算工具；只有实际返回结果后才能引用。

返回：简洁结论、关键依据与来源ID、必要计算或条件、缺失信息。
```

如果使用工具，还需要单独说明允许的工具、参数、反馈处理和停止条件；在文本里写“已经检索/验证”不能替代真实执行记录。（[D01]，Advice on prompting；[D10]）

这里没有要求输出全部内部 CoT。对下游可复用、需要追责的结果，可以显式产出事实表、来源、关键计算式和未决事项。能校验这些对象，才有机会定位错误发生在取证、组合还是表达。

## 8. 如何做一次能指导上线选择的评测

本节是建议实验，**尚未执行**。不能根据论文分数直接替用户设置生产默认值。

### 8.1 先冻结问题和证据，分离两个实验

**实验 A：生成节点。**冻结问题、检索结果字节及排序、元数据、prompt、模型快照、工具返回和答案合同；只研究该步 generation。否则检索波动会被错误归因为 reasoning。

若该节点可以调用工具，应拦截新调用并返回预先冻结的对应结果；未被回放覆盖的调用参数记为工具策略差异，不能临时联网取得新材料后仍声称证据完全相同。也可以明确禁止执行，将工具请求作为待判分产物。

**实验 B：完整流程。**在同一问题集合比较不同路由，允许各策略实际检索和调用工具，衡量端到端成功、成本和时延。策略增加一次合理补充检索可能改善结果；应把收益记为整个策略的收益，不能再声称来自单次生成开关。

### 8.2 分阶段比较，不一次混改所有因素

| 组别 | Prompt | 推理设置 | 回答的问题 |
|---|---|---|---|
| A | 目标＋证据规则＋输出合同 | off 或最低支持档 | 基线 |
| B | 与 A 完全相同 | 中档 | 内部计算是否值得增加 |
| C | 与 A 完全相同 | 高档，仅在有理由时测 | 边际收益是否继续存在 |
| D | A 额外加 `think step by step` | 与 A 相同 | 这句提示是否单独有价值 |
| E | A 额外加具体业务检查步骤 | 与 A 相同 | 可执行约束是否修复某类错误 |

若 D/E 有收益，再在中档重复比较，检查 prompt 与模式的交互。对于 adaptive 模型，要记录实际触发与 token，而非假定所有请求用了同等思考量。若模式改变了不可控制的采样策略，明确结果属于完整模式比较。（[D01]、[D03]–[D05]、[D07]）

要测两个不同问题：一是提供足够输出预算，观察各模式能达到的质量；二是在相同成本或时延约束下比较可交付质量。只固定同一个很小的 token 上限，可能测到答案被挤占；只无限放宽预算，又不能回答在线系统是否值得采用。

### 8.3 样例必须分层

可先用 60–100 个真实问题做定位性试验，数量只是工程起点，不保证统计功效。至少包含：直接抽取、跨段落、多文档、时间/口径冲突、数值计算，以及资料不足或不可回答的问题。各类都要保留原始证据和允许的答案范围。

小规模重复调用用于观察稳定性，重要失败可重复 3–5 次；不能把同一问题的多次运行当成完全独立的新问题。prompt 调整用开发集，最终选择用保留集；模型或网关升级后保留同一回归集。

### 8.4 指标与判分

| 维度 | 应检查的内容 |
|---|---|
| 业务正确性 | 是否回答真正问题；实体、时间、口径、数字和因果判断是否正确 |
| 证据支持 | 关键主张是否被引用材料支持；引用存在与引用支持分开判 |
| 证据覆盖 | 有没有遗漏必要限制、反例、相关文档与问题子项 |
| 拒答与不确定性 | 缺证据时是否适当保留；资料充分时是否错误拒答 |
| 运行完整性 | 是否截断、空答案、超时、格式错误、工具失败或适配器丢字段 |
| 投入 | reasoning / final tokens、完整费用（含重试/核验）、P50/P95 时延、端到端用时 |

流式服务还应分开首个网络事件、首个可见答案和完成时间；先到达的 reasoning 数据不等于用户已经得到可用答案。

盲评时随机化组别和顺序，避免因回答更长而给高分；领域判断需人工抽查。可用按问题配对的 bootstrap 区间或适合二元结果的 McNemar 检验；重复运行按问题聚类，避免夸大样本量。评测模型可辅助检查，但不得把同一个模型的自评当作唯一真值。

### 8.5 如何决定上线

先设底线，例如关键事实、来源边界与错误拒答的允许变化，再比较满足底线的成本和时延。质量提升很小而成本翻倍时，只有在业务错误代价足够高且收益稳定时才有理由接受；阈值由业务设定，不从论文移植。

路由信号优先使用可观察特征：跨多少证据、是否存在实际冲突、是否需要计算、必要字段是否齐全、验证是否失败、步骤是否依赖新工具结果。模型自己的“我很确信/不确信”只能作为待校准信号。

建议有限升级：低投入结果未通过检查时，先定位失败；若证据充分但组合失败，可提高 effort；若缺资料，补检索；若缺表头或口径，读原页；若验证条件仍不满足，保留未确定状态。不能把所有失败都送进无限“再想一遍”循环。

## 9. 对原课程笔记的精确补充

原文“解释写得更长没有自动提供新事实”成立，但可以补成：

> 显式中间计算有时能改善多步组合、约束跟踪和已有知识的召回；它没有增加新的外部观察，不代表它没有能力收益。收益依赖模型、任务、证据和计算分配。对经过推理训练的模型，通常先用清楚的目标、约束与输出合同，不机械要求逐步展示全部推导；推理预算与提示式 CoT 应分开评测。证据不足时，推理可以发现缺口或规划检索，但不能凭推演把缺口变成已证实事实。（[R01]、[R04]–[R08]；[D01]–[D07]）
