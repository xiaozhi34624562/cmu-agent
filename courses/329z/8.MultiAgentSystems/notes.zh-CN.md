给一个助手增加“研究员、分析师、审阅者”三个角色，并不自动增加三份独立判断。三个角色可能共享同一错误证据，重复同一搜索，最后把错误共识写成更有说服力的报告。本课要解决的是：**哪些工作应该拆开，怎样交换足够的信息，怎样约束共享状态，以及最终由什么证据确认整体任务完成。**

## 1. 先判断是不是需要多个决策主体

一个模型连续调用十次工具，仍可以是一个 Agent：它沿同一状态和决策循环推进任务。让同一模型在新的上下文中承担独立子任务，并通过协议返回结果，则可以构成多个 Agent。模型参数相同并不妨碍它们作为不同运行实体；但同一调用被起了多个角色名，也不足以证明形成了有意义的协作。[Scaling Agent Systems，§3.1，PDF pp.6–8](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=6)

考虑“为公司 A 写财报更新报告”。任务可能拆成：读取公告并确认口径；比较主营业务变化；核验历史估值假设；整合报告。前三项在拿到同一份公告后有一定并行性，整合依赖它们的结果。若任务只有“读取公告总营收并换算单位”，分配三个研究 Agent 通常只增加沟通。

讲义 pp.10–15 同时区分 orchestration、communication 和 coordination：谁安排总体运行，怎样传递信息，怎样管理相互依赖的工作。它们可以由同一程序实现，但诊断时需要分开。判断标准应是信息和依赖，而不是报告章节数。两个章节若都依赖同一个尚未核实的数字，分开生成也不会消除共同瓶颈。反过来，一个章节需要从三个互不相关的数据源查证时，可能存在真正的并行价值。

**工程建议**：先建一个强单 Agent 基线，让它拥有相同工具、足够推理预算和完整验证流程。再考虑上下文隔离、并行取证、专业工具差异或独立复核能否带来额外价值。不能拿一个低预算单 Agent 和一个高预算团队比较后，把全部收益归因于协作。

## 2. 用任务依赖表达协作需求

把任务画成有向无环依赖图只是工程分析方法，不要求实际系统使用某一框架。节点表示有明确输入输出的工作，边表示必须等到某个结果才能开始。

设各子任务耗时为 $t_i$，单线程顺序执行近似耗时为 $\sum_i t_i$；理想并行情况下，完成时间至少受关键路径长度限制。真正的多 Agent 延迟还要加任务分发、通信、等待、复核、重试与结果汇总：

$$
T_{team}\gtrsim T_{critical\ path}+T_{dispatch}+T_{communication}+T_{verification}.
$$

这个加法假定所列额外开销位于关键路径且未相互重叠；实际系统可能隐藏或并行一部分开销，因此它是教学成本分解，不是某篇论文对所有系统的精确下界。它提醒我们，增加并发数只可能改善可并行部分；关键路径上的串行环境动作不能凭角色数缩短。如果子任务共享一个限流接口，并行还可能增加重试和总延迟。

分解时应逐个填写：要回答的问题、可使用的证据、允许动作、依赖、产物格式、成功条件、预算和遇到阻塞时的返回方式。一个好的子任务是“核对公司 A 在指定期间的营收口径并返回公告页码与计算”，不是“你是最强财务专家，请深度研究”。后者描述气质，没有定义可验收产物。

### 2.1 两类经常被混淆的并行

**独立求解**让多个 Agent 完整解决同一问题，然后聚合结果；收益主要来自搜索多样性和冗余验证。**任务分工**让不同 Agent 解决互补子问题，再合成一个答案；收益来自更大信息覆盖和上下文隔离。两者的实验对照不同：前者应与 best-of-N、多次采样或单 Agent 自检比较；后者应检查任务分解与交接质量。

所谓“审阅者”也可能只是读了作者的结论并附和。更有区分力的复核让审阅者直接拿到原始需求、证据和验收条件，必要时独立计算，而不是只评价文字是否流畅。不同模型、不同证据或不同验证方法可以降低某些共同错误，但都不能保证统计独立。

## 3. 拓扑决定信息怎样流动、谁能结束任务

| 结构 | 信息与控制 | 更适合的情况 | 主要成本和故障 |
|---|---|---|---|
| Independent | 各自求解，最后聚合 | 可独立验证的候选方案、并行搜索 | 重复劳动、相关错误、汇总丢信息 |
| Centralized | 协调者分配与汇总 | 需要统一任务状态、权限和验收 | 协调者瓶颈、上下文膨胀、错误分解 |
| Decentralized | Agent 直接交换和协商 | 需要持续互补发现的探索 | 沟通膨胀、共识锁定、责任不清 |
| Hybrid | 统一协调加受限横向交流 | 专项直接交互有收益的复杂任务 | 协议与状态复杂，难以归因 |

这四种命名按 Scaling Agent Systems 的受控比较理解；实际框架可能用 swarm、manager、handoff 等不同名称，需看控制流，不能只按产品标签归类。[Scaling Agent Systems，§3.1、Table 2，PDF pp.7–10](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=7)

中央协调者不一定每个步骤都亲自决策。它可以只负责分发、维护账本、接收完成事件和最终验收。子 Agent 内部仍然可以自主选择工具。关键是：谁可以修改任务目标、谁可以写共享状态、谁可以批准完成，应由显式规则定义。

若 $n$ 个 Agent 在一轮中都向其他每个 Agent 发送一条消息，定向消息数是 $n(n-1)$；星型结构中若每个工作者向协调者汇报一次，数量随工作者数线性增长。这是给定通信策略下的教学计数，不能直接替换论文里按具体实现测得的消息数，更不能把图上的一条边等同于一次廉价通信。每条消息还会进入接收者上下文，产生后续推理费用。

### 3.1 动态团队：DyLAN 改变的是活跃参与者

讲义 pp.25–28 再向前走一步：不把固定角色数视为任务的固有属性。其 DyLAN 示例先在若干问题上估计 Agent 贡献，再在新任务中按效用评分减少参与者，并按一致性条件提前结束。这里沿交互依赖分配 credit，不意味着对底座 LLM 权重进行了反向传播。[L8，pp.25–28](slides/lecture08.pdf#page=25)

动态删减可以减少无用轮次，但也可能过早剔除提出异议、暂时分数较低却掌握关键证据的 Agent；互相评分和一致性停止都需要校准。团队说法相同只说明一致，不保证已经达到外部验收。讲义 p.24 的成本次序应限定为其展示的架构与运行条件，不能推成所有任务上 swarm 总比单 Agent 更贵的定律。[L8，pp.23–28](slides/lecture08.pdf#page=23)

## 4. AutoGen：怎样把协作表达成可编程的对话

AutoGen 原论文把 Agent 设计为可接收消息、生成回复并发送消息的对象。其能力可以来自模型、工具、人类或组合；“Agent”不要求所有内部步骤都由 LLM 完成。论文的 AssistantAgent 和 UserProxyAgent 展示了生成方案、执行代码、接收环境错误、重新修正的交互。[AutoGen，§2.1，PDF pp.3–4](readings/AutoGen_Enabling_Next-Gen_LLM_Applications_via_Multi-Agent_Conversation.pdf#page=3)

一个运行片段可以按职责解释：助手提出 Python 代码；用户代理执行；执行器返回缺少依赖的错误；助手根据错误修改下一步；达到终止条件后结束。有效反馈来自真实执行环境，而不是另一个 Agent 说“这个代码看起来正确”。

论文将 conversation programming 分成两部分：**computation** 是个体如何基于消息行动并形成回复；**control flow** 是何时轮到谁、消息发往哪里、何时停止。自然语言提示可以影响两者，程序代码也可以规定终止、人工输入和执行逻辑。[AutoGen，§2.2，PDF pp.4–5](readings/AutoGen_Enabling_Next-Gen_LLM_Applications_via_Multi-Agent_Conversation.pdf#page=4)

这提供了一个工程上的分离：模型负责提出动作或判断，运行程序负责解析、检查、调度和执行。如果模型通过自然语言输出 `TERMINATE`，程序可以把它当作候选终止信号；但生产任务是否真的达到验收条件，仍需检查产物和环境状态。魔法字符串不能替代验证器。

**版本边界**：本课复用的原文为 arXiv:2308.08155v2，2023-10-03。文中的类名和接口用于解释当时架构，不在本文承诺为今天 AutoGen 的安装或 API 教程。读者实现当前系统时，应另外核对对应版本的一手文档。

原讲义 pp.33–35 将这种表达扩展到顺序、嵌套、群聊和层次会话。区别不只是消息数量：顺序模式规定交接次序，嵌套模式允许一个任务内部再启动子会话，群聊让多个成员共享部分交流，层次模式保留上级汇总。当前产品中的模式名称可能改变，设计时应还原实际路由、状态范围和停止规则。[L8，pp.32–35](slides/lecture08.pdf#page=32)

### 4.1 框架解决表达问题，不替你完成业务契约

一个统一的 `send/receive/generate_reply` 抽象，让多种会话模式容易编排；它不会自动知道“财务数字需要哪些单位”“哪种失败可以重试”“什么叫合规审核通过”。这些信息必须进入任务规范、工具契约、数据 schema 和验收器。

如果无法解释一条消息如何改变任务状态，就容易出现看起来一直在协作、实际上没有进度的系统。生产日志应把自然语言消息与结构化事件关联：发起任务、提交证据、请求澄清、报告阻塞、提交候选产物和通过验收，而不是只有一串 role/content。

## 5. 交接协议：让另一位 Agent 知道什么已经确定

讲义 pp.36–39 特别区分 handoff 与 agent-as-tool。两者都可能委托专业工作，控制权却不同：[L8，pp.36–39](slides/lecture08.pdf#page=36)

| 方式 | 控制权 | 返回与上下文 | 研究助手的例子 |
|---|---|---|---|
| Handoff | 接收方成为当前活动主体，继续后续交互 | 传递必要会话与任务背景；是否回切由具体流程决定 | 将当前对话转交合适专家，由其向用户澄清并负责下一步 |
| Agent-as-tool | 调用方保留总体控制 | 接收有界请求，返回结果或产物，调用方继续 | 协调者请求财务专家核对一项指标，再自行整合报告 |

下文的任务契约可用于这两种边界。不能因为子 Agent 使用了相同消息格式，就把所有“调用后返回”都当作 SDK 意义上的 handoff。

一次委派或交接不能只把上文压缩成“请接着做”，还应传递工作边界与可验证状态。下面先以调用后返回协调者的 **agent-as-tool** 为例给出教学契约；若改为handoff，还须在运行状态中明确新的活动主体及其交互权限，不能只更换消息接收人：

```json
{
  "task_id": "revenue-check-017",
  "parent_task_id": "report-A-2026Q3",
  "objective": "核对公司A指定期间的营收与单位",
  "input_refs": ["announcement:A:q3:v2"],
  "constraints": ["仅使用指定披露版本", "不得修改原始文件"],
  "acceptance": ["给出原始值与单位", "给出PDF页码", "说明同比口径"],
  "budget": {"max_tool_calls": 8},
  "state_version": 3,
  "return_to": "coordinator"
}
```

返回产物也应区别 `completed`、`blocked`、`failed` 和 `partial`。只返回“没问题”会丢掉最有价值的信息：查了哪些来源、哪些事实仍未确定、是否发生版本变化。建议返回结果、证据 ID、未解决问题、实际副作用和验证记录。失败的子任务可以提供部分已验证证据，不必把整条轨迹都丢掉。

### 5.1 摘要要保留约束和不确定性

压缩最容易留下结论、删掉限定条件。例如原文是“在合并口径、人民币万元、2026 年前三季度下同比下降”，交接只剩“营收下降”。后续 Agent 可能把它用于单季美元收入的比较。需要把实体、期间、单位和来源作为结构化字段，使摘要压缩不会悄悄删除它们。

交接也可能把提议误写成完成。“建议核对原表”与“已核对原表”是不同状态；“测试应该通过”与“执行日志显示通过”也不同。把 `proposed_action`、`executed_action`、`observed_result` 分开记录，能避免系统在语言层面不断推进、环境状态却没有变化。

## 6. 共享状态：通信成功并不意味着协作一致

多个 Agent 可能共享文件系统、数据库、浏览器、外部账户或工作队列。即使各自上下文隔离，外部副作用仍然会相互影响。两个 Agent 同时编辑一份报告，可能覆盖彼此段落；分别发送相同通知，可能造成重复外发；一个 Agent 更新数据口径，另一个仍按旧版计算。

**工程建议**：为共享对象分配明确写入者或使用受控合并。可拆的文件和模块按任务隔离；不可拆的全局配置由一个协调者提交变更。把读取版本与写入版本写进产物，避免新旧状态无声混用。

一个任务账本可以包含以下字段：

| 字段 | 作用 |
|---|---|
| task_id / parent_id | 建立任务和依赖关系 |
| status | pending、running、blocked、submitted、verified 等明确状态 |
| owner / lease_until | 谁正在负责，何时允许接管 |
| input_version | 产物基于哪个源数据和配置版本 |
| output_ref / evidence_refs | 结果与可核查证据 |
| attempt / idempotency_key | 重试次数与副作用去重 |
| verification | 谁在什么条件下验收，是否仍有缺口 |

租约解决工作者消失后任务长期占用的问题；幂等键解决同一外部动作因重试被执行两次的问题；版本解决结果基于旧状态却被当成最新的问题。它们解决不同故障，不能互相替代。一个工具调用 timeout 也不代表动作没有成功，恢复前应查询实际状态。

租约过期并不证明旧工作者已经停止。网络分区后，协调者可能把任务交给新工作者，而旧工作者仍在生成或写入。可给每次接管递增的执行代次，并在提交产物时由权威存储检查代次和输入版本；过期执行者的结果拒绝进入正式状态。若要拒绝旧工作者的远端写入，接收方也需要校验执行代次或提供等效的条件写入。业务幂等只合并同一逻辑操作的重复请求，不能阻止第一次到达的过期操作；两者不能互相代替。外部接口不支持这些约束时，应收窄为受控写入路径，并保留无法消除的在途请求与未知结果边界；仅在协调者账本上标记过期不能阻止远端操作。[工程建议，承接 L8，pp.52–56 的任务协调]

### 6.1 任务账本、共享经验与共享文件是三种状态

讲义 pp.53–56 用 Magentic-One 的 task ledger 和 Symphony 的任务分发说明当前工作怎样推进；pp.57–61 的 G-Memory 则讨论从过去整个团队的经历中检索经验。当前任务账本记录“现在谁在做什么”，跨任务记忆记录“过去遇到类似情况怎样处理”；工作区存放实际被编辑的产物，三者不能互相替代。[L8，pp.53–61](slides/lecture08.pdf#page=53)

G-Memory 的图分为 interaction graph、query graph 和 insight graph：原始 Agent 交互日志、与任务查询相关的组织索引、从经历中提炼的较一般认识。检索可以由类似任务进入相关交互，再利用有来源的洞见指导新协作。它不要求把全部旧消息原封不动发给每个成员；也不能从图存在就推断事实正确或权限自动隔离。[L8，pp.58–60](slides/lecture08.pdf#page=58)

工程上可以先用关系表与证据链接实现三层职责，未必一开始就部署图数据库。无论存储形式如何，一条高层协作经验都应能回到原始轨迹，并说明适用条件。未经验证的“上次成功做法”不宜成为所有团队默认策略。

### 6.2 Worktree 隔离到哪里为止

对 Coding Agent，不同 Git worktree 可以隔离工作目录，并通过分支与提交组织变更。它不会隔离共享远端数据库、同一个端口、全局依赖目录或外部服务。不同工作者修改同一公共接口时，仍需提前定义契约和集成顺序。

在学习资料库里也存在同样问题：一个 Agent 改了 PDF 文件名，另一个继续写旧链接；各自文档检查通过，合并后却有断链。因此应由统一来源索引确定路径，内容工作者只维护各自文档，集成阶段验证所有本地链接和最终哈希。这是工程集成建议，不是某篇论文的实验证明。

### 6.3 角色分工、资源分区和协商分别处理什么

讲义 pp.64–68 把三个协调模式并列。角色分工解决谁负责哪项交付；资源分区解决谁可以写哪组文件、使用哪个环境；协商解决两个有效方案发生依赖或冲突时如何收敛。前者写清职责仍可能争抢同一数据库；资源隔离后仍可能修改互不兼容的公共接口，因此三者需要组合。[L8，pp.64–68](slides/lecture08.pdf#page=64)

协商应提交约束、可行备选与证据，由明确仲裁规则决定无法共同满足的目标。让两个 Agent 各自“坚持完成自己任务”会奖励相互覆盖。决定公共接口后应把结论写回账本和版本化契约，让新加入的工作者看到相同承诺。

## 7. A2A、工具协议和共享黑板分别负责什么

协议可以统一任务描述、消息和状态交换，帮助不同系统互相发现和协作。它不能凭协议名称保证任务分解合理、证据可信或业务操作只执行一次。理解 A2A 等机制时，应问清楚：消息的 schema 是什么，状态由谁维护，取消和重试怎样表示，身份权限如何传递，以及完成状态是否经过业务验收。

工具协议主要连接 Agent 与能力接口；Agent 间协议主要交换任务和产物；共享黑板则提供大家可以读写的信息空间。这三层可能组合使用，但不能混为“用了某协议就实现了共享记忆”。共享内容是否一致、是否可见、是否过期，仍取决于具体存储和运行机制。

黑板适合集中保存任务状态、已确认事实和证据引用。其关键设计不是让所有 Agent 随意写长文本，而是决定哪些内容可以写、冲突怎样处理、订阅哪些变更、旧信息怎样失效。否则黑板会变成另一份不断膨胀、互相矛盾的共享上下文。

### 7.1 从黑板到 A2A 的具体消息链

讲义 pp.40–44 用 MetaGPT 等黑板式例子说明：产物可以成为协作媒介，不必所有信息都通过主会话逐字转述。发布订阅或按角色读取有助于控制信息量，但要定义产物格式、生产者、状态和版本；一个公开可读的 Agent 留言也不是受信任命令。[L8，pp.40–44](slides/lecture08.pdf#page=40)

pp.45–48 中的 A2A 链条是：客户端取得远端 agent card，了解能力、技能与输入输出；创建可追踪任务；交换进度与必要消息；接收任务产物。由此可以把发现、消息和 artifact sharing 统一成跨系统接口。它仍不提供业务事实正确性，或对底层副作用的“恰好一次”保证。[L8，pp.45–48](slides/lecture08.pdf#page=45)

对企业助手，agent card 类似可发现的服务能力说明；任务 ID 类似跨服务的关联 ID；最终 artifact 类似版本化业务产物。应用还需自己定义身份授权、取消后的副作用处理、失败重试和验收策略。这里解释的是课程消息模型，不指定今天某一 A2A 版本的完整字段。

## 8. 从 MAST 看失败：观察到什么，不能直接推断什么

MAST 基于多 Agent 执行轨迹建立 14 类失效模式，归为系统设计、Agent 间失配、任务验证三组。其 v3 数据集包含 1642 条轨迹；分类定义见附录 A，人工与模型标注过程见 §3。它提供可复用的观察语言，而不是自动证明所有失败的因果根源。[MAST，§3、附录 A，PDF pp.5–6、17–18](readings/Why_Do_Multi-Agent_LLM_Systems_Fail.pdf#page=17)

| 组别 | 模式 | 在企业研究助手里可能出现的行为 |
|---|---|---|
| 系统设计 | 1.1 违反任务规范 | 忽略指定期间或数据来源 |
| 系统设计 | 1.2 违反角色规范 | 取证 Agent 直接批准最终结论 |
| 系统设计 | 1.3 重复步骤 | 已取得原文后不断重复同一搜索 |
| 系统设计 | 1.4 丢失会话历史 | 忘记已经确认的单位修正 |
| 系统设计 | 1.5 不清楚终止条件 | 已达到目标仍无限讨论 |
| Agent 间失配 | 2.1 会话重置 | 交接后从头启动整项任务 |
| Agent 间失配 | 2.2 未请求澄清 | 对主体不明确的请求直接猜测 |
| Agent 间失配 | 2.3 偏离任务 | 由核对财报变成推荐投资标的 |
| Agent 间失配 | 2.4 未传递关键信息 | 知道表格单位，却未告诉计算 Agent |
| Agent 间失配 | 2.5 忽略他方输入 | 收到更正后仍沿用旧值 |
| Agent 间失配 | 2.6 推理与动作不一致 | 说要只读核查，却执行覆盖写入 |
| 任务验证 | 3.1 过早终止 | 某个子任务完成后就宣布全任务完成 |
| 任务验证 | 3.2 无验证或验证不完整 | 只检查格式，没有核对数字 |
| 任务验证 | 3.3 验证错误 | 用同一错误口径重新算一遍后认定正确 |

“Information withholding”在这里不一定意味着 Agent 主观隐瞒，更常见的是没有传递已经知道的关键条件。分类名称描述可观测行为，不能据此赋予系统心理动机。相同轨迹可以出现多个模式；成功轨迹也可能出现一些模式，只是没有在那一次导致最终失败。

### 8.1 如何从分类推进到根因

设汇总报告把单位用错了。可以先标记“信息未传递”或“忽略他方输入”，再查看：单位是否出现在子 Agent 工具结果中；是否进入其返回消息；协调者是否实际看到了；计算工具参数用的是什么；验收器有没有检查单位。这个逐步回查才能定位最早失效点。

如果修复是给交接 schema 增加单位字段，应在相同模型和任务上做回归，并确认失败率下降。只让模型把轨迹标成“信息未传递”，没有验证修改后的系统，仍停留在诊断假设。论文的 $\kappa$ 反映标注一致性，也不等于模型已找准所有因果根源；人工标注一致性与 LLM 标注一致性是不同实验。[MAST，§3.2–3.3、Table 2，PDF pp.5–6](readings/Why_Do_Multi-Agent_LLM_Systems_Fail.pdf#page=6)

### 8.2 CooperBench 与行为问题：会沟通不等于能兑现承诺

在 MAST 之后，讲义 pp.73–76 用同仓库协作编码的 CooperBench 对照提醒：两个工作者可能对彼此修改形成错误预期、作出未兑现承诺，或沟通后仍产生不兼容变更。单 Agent 完成两项耦合修改，有时优于两个 Agent 协作。这个例子强化的是依赖和共享状态问题，不是证明所有编码任务都应单线程。[L8，pp.73–76](slides/lecture08.pdf#page=73)

pp.77–82 再区分行为失效：相同或相似模型的团队可能从众、减少探索多样性；互不兼容的目标可能使工作者覆盖或破坏对方工作。应把这类观察视为设计压力测试的线索，而不是赋予 Agent 人类动机。一个可验证改进是让候选独立取证、保存分歧，并为冲突设置统一仲裁和权限边界。[L8，pp.77–82](slides/lecture08.pdf#page=77)

## 9. Scaling Agent Systems：为什么某种任务受益，另一种任务退化

本地采用 arXiv:2512.08296v3，2026-04-08。该版研究 260 个配置、六个基准、五种拓扑和三个模型家族，强调控制工具、提示与计算预算。不能把旧版的配置数量、基准数量或拟合优度混入本版说明。[Scaling Agent Systems，摘要、§4.1，PDF pp.1、10–12](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=10)

研究中 Finance Agent 的中央协调组合相对单 Agent 平均成绩提高约 80.8%，但 PlanCraft 的各多 Agent 组合都退化，独立组合相对下降约 70%。这些是相对变化，不是提高或下降同样数量的百分点；更不是在你的投研场景里的收益预测。[Scaling Agent Systems，§4.2，PDF pp.11–13](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=13)

作者给出的解释是：金融分析任务有互补信息和可分解推理机会；顺序规划任务依赖统一的环境状态，人工拆分会把预算花在协调与重复工作上。前者可能从并行研究中获益，后者会因多个工作者看到不同状态、动作彼此依赖而受损。即使都叫 Agent 任务，依赖结构也不同。

### 9.1 读实验时需要保留四个边界

第一，所测试的拓扑和调度实现只是架构空间的一部分，不能代表所有可能设计。其计算公平性具体通过匹配最大总迭代次数、给多Agent分配较少的每Agent轮数实现；这控制了一个预算代理，却不保证实际输入输出token、工具成本和验证费用完全相等。比较应同时看实际消耗，不能仅从摘要的“控制计算预算”推断严格同算力。[Scaling Agent Systems，§4.1，PDF p.12](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=12) 第二，部分重型基准使用较小子集，不能对细小差异过度下结论。第三，论文的回归模型用于描述和预测其分布中的关联，并不是可保证迁移的普适定律；本版交叉验证 $R^2$ 为 0.373，使用任务相关能力度量时为 0.413。[Scaling Agent Systems，模型说明，PDF p.4](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=4)

第四，论文区分任务级错误放大与轨迹级额外计算。前者比较失败率，后者估计协调失误增加的工作量。17.2× 与 4.4× 等轨迹指标不能被解释成“最终错误率增加 17 倍或 4 倍”。[Scaling Agent Systems，§3.1，PDF p.8](readings/Towards_a_Science_of_Scaling_Agent_Systems.pdf#page=8)

对测量方法也要保留判断。文本相似度低并不自动等于语义矛盾，输出重叠也未必意味着无效冗余。因此，可以借鉴该研究的实验控制思路，同时对你自己的任务重新定义可验证的冲突和重复指标。

## 10. 投票什么时候能改善，什么时候只是集体犯错

教学上，若三个求解者各自正确概率为 $p$，且相互独立、任务只有正确与错误两种结果、用多数票聚合，则团队正确概率为：

$$
P_{majority}=p^3+3p^2(1-p).
$$

当 $p=0.7$ 时得到 0.784。这是独立模型下的算术示例，不是对三个同模型 Agent 的效果预测。若它们都依据同一错误公告或同一检索遗漏，就有共同错误；多数票可能把共因错误变成更强的“共识”。

开放式报告也不能直接多数投票：不同答案可能都包含部分真相，错误还可能体现在缺失条件和不可追溯引用。更有效的聚合往往需要对事实、证据、口径和计算分别核验，把分歧转成待查证的问题，而不是只统计谁支持某结论。

中央验证者也会出错。如果它只看到经过压缩的一致结论，没有原始证据，就无法有效阻断共同错误。可以让某些验证走不同路径：数值交给确定性程序，引用回到原文，权限交给策略引擎，覆盖检查对照用户需求；模型审阅用于难以形式化的部分。

## 11. 从单 Agent 迭代到一个可评测团队

以研究助手为例，可以按以下顺序构建，逐步确认新增机制的价值。

**第一步：定义总体交付。** 报告需要哪些字段、数据日期、证据完整性和缺失说明？最终写报告的 Agent 不能自行把目标改成“给出投资建议”。

**第二步：建立单 Agent 基线。** 固定模型、工具、源数据快照、预算和验收器；记录成功率、延迟、费用和典型失败。

**第三步：只拆出一个明确瓶颈。** 例如同时查阅三家可比公司的披露，各自只读；不要一开始让所有角色自由讨论和修改共享文件。

**第四步：建立任务与返回契约。** 规定输入版本、证据字段、阻塞状态和预算；汇总者只使用已验证证据，缺失项保留缺失。

**第五步：加入独立验收。** 数字计算、引用定位和用户要求覆盖分别检查。子任务 `completed` 表示提交产物，整体 `verified` 才代表满足交付条件。

**第六步：公平对照与回归。** 与同预算单 Agent、多次采样、检索并行但不增加决策主体等基线比较。观察收益来自更多工具吞吐、更多推理、上下文隔离还是协作本身。

**第七步：故障恢复。** 杀死一个工作者、重复投递任务、制造工具 timeout、修订共享输入，检查是否重复外发、丢失任务或接纳过期结果。恢复能力需要真实故障注入；本文列的是拟议实验，没有在生产环境执行。

### 11.1 讲义的编译器 swarm 案例如何串起前面各层

pp.84–89 以构建 C 编译器的工程团队为案例：成员承担实现与调试、去重、文档、编译性能、生成代码效率、代码质量等互补工作；任务文件和 Git 保存认领、进度与经验；分离工作区后再集成。这里真正支撑长时间运行的，是可分解的失败、强测试与可搜索日志，而不是无限对话本身。[L8，pp.84–89](slides/lecture08.pdf#page=84)

讲义提炼六项做法：可靠正确性和回归测试；暴露可分离的子问题；明确任务认领与 Git 集成；保留跨会话知识和失败尝试；提供精简错误摘要与快速测试子集；分配互补目标。把它搬到研究助手，对应的是清晰的数据口径验证、独立证据源、有界取证任务、统一结果集成及可追溯缺口，不是照搬编译器的角色名称。

## 12. 成本与可观测性应按整个任务统计

团队成本不是最终协调者最后一次回复的 token 数。应包括子 Agent、协调消息、工具、验证、失败重试以及已经取消但仍消耗资源的工作。

在一批任务上，实际的每成功任务成本是 $\sum_i C_i/\sum_i s_i$，其中 $C_i$ 包含该任务全部成功或失败尝试的费用，$s_i\in\{0,1\}$ 表示最终是否通过验收。分母为0时不能报告一个有限成本。任务分布稳定且样本足够多时，可近似写成 $\mathbb E[C]/P(\mathrm{success})$；它不是任意单次费用除以成功率。涉及业务副作用或人工返工时，还需把这部分成本计入或单独报告，不能只比较 API 账单。

每条 trace 最少关联 `run_id`、`task_id`、`parent_task_id`、agent 标识、模型与提示版本、工具调用、输入输出来源、状态变化、资源消耗和验收。对于共享对象，再记录读写版本。不要要求保存模型供应商未提供的内部思维链；可观察的动作、工具参数、产物和环境结果已经是诊断的重要依据。

| 现象 | 能区分原因的观测 |
|---|---|
| 团队更慢 | 关键路径、队列等待、串行协调、共享限流 |
| 团队费用更高 | 重复取证、反复转述、大上下文、失败重试 |
| 子任务都成功但整体失败 | 子任务验收是否覆盖总体目标，汇总是否丢条件 |
| 结果偶发丢失 | 任务租约、返回消息确认、产物版本和幂等键 |
| 审阅总是赞同作者 | 审阅输入、独立证据、不同验证路径及否决记录 |
| 恢复后重复操作 | timeout 后状态核对、动作去重、提交确认机制 |

## 13. 自测与参考答案

**1．同一模型用三种提示运行，是不是多 Agent？**  
可以是多个独立运行实体，但角色数量本身不能证明有效协作。检查各自状态、职责、动作和消息协议；还要评测信息和错误是否足够多样。

**2．为什么不应该每个报告章节都分给一个 Agent？**  
章节划分不是依赖结构。多个章节可能共享尚未核实的瓶颈，拆开只会重复获取、放大口径不一致；应按可独立验收的工作分解。

**3．中央协调者能否避免所有状态冲突？**  
不能。它需要明确写入规则、版本和验收；子 Agent 的外部副作用还可能绕过协调者。中央架构只提供一种控制位置。

**4．Worktree 是否隔离数据库和外部通知？**  
不会。它隔离工作目录；共享数据库、端口、账户和服务仍需另外隔离或串行控制。

**5．MAST 标注“信息未传递”，是否已经找到根因？**  
还没有。需沿工具观测、子产物、交接、组装和最终动作定位最早失效点，再用干预与回归检验修复。

**6．论文中的相对提高 80.8% 是否是提高 80.8 个百分点？**  
不是。相对变化用与基线的差除以基线；该研究金融任务的结果也不能直接迁移到你的投研助手。

**7．如何公平验证多 Agent 的收益？**  
保持任务、模型、源数据、工具和总预算可比，加入足够强的单 Agent 与多采样基线，分别看准确性、可靠性、费用与延迟。

**8．为什么三个 Agent 达成一致仍可能是错的？**  
它们可能共享错误证据、相同检索遗漏和相似推理偏差。独立投票的数学前提不成立；要回查原始证据和不同验证路径。

**9．一个工作者超时后，能否直接重试写操作？**  
不一定。超时可能发生在动作完成而确认尚未返回之后，应先查实际状态或使用幂等协议，避免重复外发或修改。

**10．所有子任务状态都是 completed，为什么仍不能结束？**  
它只说明各自产物已提交。整体还需检查需求覆盖、输入版本、跨子任务一致性、来源和总体验收条件。

## 14. 回到三篇阅读的分工

AutoGen 提供“怎样表达交互”的构件；MAST 提供“怎样描述观察到的失效”的词汇；Scaling Agent Systems 提供“怎样在控制条件下比较架构”的实验思路。把三者串起来，才形成从设计、执行、诊断到验证的闭环。选择架构的依据应是任务依赖、信息互补、状态共享和实测收益，而不是团队看起来有多少角色。
