## 1. 先确定想改变哪一种能力

一个企业内部助手已经能够回答常见问题，现在要处理“找出某公司昨日公告与旧财报之间的现金流变化，并输出证据表”。它可能同时需要：识别公司和日期，检索正确版本，调用解析工具，规范化单位，计算指标，遇到缺页时补查，并在证据不足时停止猜测。

只用“用户问题 → 最终回答”的数据，可以教会一些回答形式，却隐藏了很多关键决策：检索失败时该查哪里、工具参数怎么改、何时需要重新验证、怎样知道不能作答。讲义 p.9 用程序修复例子说明，网页上的解释性文本和在环境中实际执行、观察错误、修改后复测，是不同的信息。[L11 pp.5–11]

因此在采集之前，要先写下目标能力及可观察证据。

| 想改善的行为 | 需要保留的数据 | 只有最终回答会丢失什么 |
|---|---|---|
| 正确选择工具 | 任务、当时可见工具、选择与参数 | 选择依据及未选择工具的上下文 |
| 从错误中恢复 | 失败请求、错误输出、后续动作、恢复结果 | 为什么第二次成功，是否只是偶然 |
| 根据证据停止 | 检索覆盖、证据缺口、终止决策 | 是可靠拒答还是没有尝试 |
| 生成准确产物 | 输入版本、加工步骤、输出与检查 | 能否重放、错误是在哪一步引入的 |
| 遵守权限 | 身份、可见资源、拒绝与副作用记录 | 回答看似正常时是否发生越权 |

这张表是教学设计，不是要求所有系统记录所有私人内容。记录范围应服务于具体能力和必要审计，敏感原文可以留在受控存储，通过可访问的版本引用关联；数据量大并不意味着有必要无限复制。

## 2. 两种核心对象：轨迹教示范，环境供练习

讲义 p.13 把 Agent 数据分为 trajectory 和 environment。[L11 pp.13–17]

**轨迹**是一项任务被执行的记录，通常含任务、观察、动作、工具结果和终止信息。它像一段带上下文的示范：在这个状态下，示范者选择了这个动作。

**环境**则是能让 Agent 反复尝试的任务系统：有初始状态、可用动作、执行后的反馈，以及成功的判定机制。它像可以重置的练习场，允许不同策略得到不同结果。

二者不是互斥的数据格式。运行环境会生成轨迹；从历史轨迹中也可能恢复一个可重放任务。关键是不能把“记录了一段看似合理的动作文本”当成“已经有可运行环境”。

### 2.1 轨迹里哪些内容是条件，哪些内容是目标

主讲义 p.14 用 loss mask 区分模型学习的 assistant 思考/动作与作为上下文的系统提示、任务及工具观察。这里先用动作示范解释，避免把“保存所有 token”误解为“训练所有 token”。[L11 p.14]

设一条序列为 $x_1,\dots,x_T$，其中每个 $x_t$ 是一个 token。$m_t\in\{0,1\}$ 表示这个位置是否需要模型学习生成。一个简化的 SFT 目标是：

$$
\mathcal L_{\mathrm{SFT}}(\theta)
=-\frac{\sum_{t=1}^{T}m_t\log p_\theta(x_t\mid x_{<t})}
{\sum_{t=1}^{T}m_t}.
$$

$\theta$ 是模型参数，$x_{<t}$ 是此前可见序列；分子惩罚模型对示范目标 token 给出的低概率，分母按被学习 token 数归一化。这里假定至少有一个受监督位置；mask 全为零的序列不能直接按此式计算有效损失。实际训练还可能采用样本权重、序列级归一化和不同 packing 方式，这里只是说明 mask 的作用。

例如工具返回“文件找不到”，它应该帮助模型决定下一步去列目录；通常不应把它当成模型要自行生成的事实。若工具观察被错误放进训练目标，模型可能学会模拟工具输出，看似知道文件内容却没有真正访问它。反过来，如果最终提交动作全部被 mask，模型可能学会长时间探索却不学结束。

此外，记录中的“理由”要说明来源。专家操作时的真实可见记录、模型自行生成的解释、事后补写的步骤说明，是不同监督信号。后两者可能帮助学习，但不是对专家隐含认知过程的直接观测。综述将 rationale 作为一种可合成的辅助标注，并讨论结构和质量，而没有把生成理由等同于事实正确性的保证。[R2 §3.3，p.4]

### 2.2 格式不是可忽略的包装

同一动作可以写成函数调用 JSON、ReAct 文本块、代码动作或终端按键。工具名、参数格式、返回包装和终止信号由 harness 决定。SFT 模仿看到的序列，未必能自动分清“任务技能”和“框架约定”。[L11 pp.14、69–71]

因此训练数据至少要记录 `harness_version`、工具 schema 版本、角色与消息类型，不能只保存扁平字符串。转换格式时还要验证语义：把 `finish` 映射成另一个工具调用，是否保留产物路径？将终端输出改为结构化结果，是否保留了错误码？格式统一不是只替换字段名称。

### 2.3 环境给 RL 的是什么

可以把环境写成**教学模型**：任务 $q$、初始状态 $s_0$、动作集合、状态转移 $P(s_{t+1}\mid s_t,a_t)$、观察以及奖励规则 $R$。Agent 用策略 $\pi_\theta(a_t\mid h_t)$ 根据历史 $h_t$ 选择动作，环境返回新观察。一个简化目标是提高期望累计奖励：

$$
J(\theta)=\mathbb E_{q\sim\mathcal D,\;\tau\sim(\pi_\theta,P)\mid q}
\left[\sum_{t=0}^{T}\gamma^t r_t\right].
$$

$\tau$ 是策略与环境共同产生的一次交互轨迹，$q$ 来自选定的任务采样分布 $\mathcal D$，$r_t$ 是该步奖励，$\gamma$ 是折扣系数。许多任务只在结束时给分；实际算法还会考虑策略约束、参考模型、优势估计等。本课关注的是奖励与数据来源，不把这个表达式当作完整 PPO 或 GRPO 实现。

SFT 的监督来自示范目标，RL 的反馈来自尝试的得分。讲义 p.16 用“预测正确动作获得 reward”的说法帮助直观理解，严格实现时，SFT 的 token 似然损失与环境返回的奖励不是同一种信号。

## 3. 一个环境怎样同时服务 SFT 和 RL

讲义 p.17 给出两条路径：在环境里采集很多 rollout，筛选后作为 SFT 数据；或直接评分，作为 RL 更新的反馈。[L11 p.17]

假设环境任务是修正一个 API 数据读取工具的日期边界错误。可以让教师 Agent 生成多次尝试，保留实际通过检查、没有读取答案、执行过程完整的轨迹，用来教学生模型。也可以让学生在相同环境中尝试，依照检查结果调整策略。

这两条路径对数据质量有不同要求。

- **SFT 需要可模仿的动作**：答案通过但过程充满无意义重复，可能把低效行为一起教给学生。
- **RL 需要能区分好坏的反馈**：如果所有策略都因环境损坏而零分，或测试漏洞让任何策略满分，就缺少有用学习信号。
- **两者都需要代表性任务**：只在同一种仓库、工具接口和数据格式里练习，可能只学到局部惯例。

训练前做一个环境自检比直接增加采样量更有效：验证正常解可行，空操作不能过关，明显错误能被拒绝，环境可重置，预算足够覆盖合理尝试，重复运行的基础设施失败可单独识别。上一课的 verifier 质量在这里直接成为学习质量，而不只是最终评测质量。

## 4. 五种获取方法，改变的是成本结构与误差来源

讲义 pp.20–57 依次介绍人工演示、从现实资料挖掘、合成轨迹、合成任务/环境、模拟用户/环境。它们可以组合使用，不能只按单条样本价格选一种。[L11 p.20]

| 方法 | 主要输入与产物 | 优势 | 首要风险 |
|---|---|---|---|
| 人工演示 | 专家完成任务，记录观察与动作 | 接近真实工作，覆盖隐性约束 | 昂贵、记录不完整、专家操作未必适合模型 |
| 现实资料挖掘 | issue、提交、教程、视频转为任务与步骤 | 复用大量现有知识 | 历史环境难重建，资料缺少隐含前提 |
| 合成轨迹 | 教师写步骤或实际探索后整理 | 规模化，能针对能力造样本 | 幻想动作、教师偏差、低多样性 |
| 合成任务/环境 | 构造初始状态、目标和验证器 | 可重复探索，便于 SFT 与 RL | 任务与评分器共享错误，难度不真实 |
| 模拟用户/环境 | 模型产生用户回应或状态转移 | 低交互成本，覆盖可控情景 | 学会模拟器漏洞，偏离真实交互分布 |

综述的结构正好补上每一行后面的步骤：**生成标注只是第一部分，还要评估、筛选，再决定是用于 SFT、对齐还是推理期上下文**。[R2 图 1、§§3–5，pp.2–8]

## 5. 人工演示：高真实感不等于直接可训练

主讲义 p.22 将人工采集分成定义任务、执行、记录、过滤和打包。这里最容易省略的是“记录”和“验证”。屏幕录像里看到了点击，并不一定知道它对应哪个元素；按键和浏览器内部状态没有对齐，也难以恢复模型当时所见。[L11 pp.21–28]

Mind2Web 和 OpenCUA 在讲义中形成一组对照：前者围绕网页动作与页面快照，后者覆盖桌面操作，记录视频、输入和更多系统状态；讲义还区分原始动作与后加的合成理由。比较它们时，重点是观测接口、动作空间和标注来源，而不是只比较任务数量。[L11 pp.23–28]

企业中可以让业务专家完成“核对一张营销材料中的业绩引用”。采集需要同步关联：当时版本的材料、业务规则、打开的证据、选择的区域、修改操作和最终审阅结论。只有邮件里的“已审核”，很难教会 Agent 怎样完成同一工作。

但也不能把专家轨迹原样当作最佳策略。专家可能用快捷键、依赖脑中的行业知识、在屏幕外查资料，或者先前已经熟悉某家公司。若这些条件没有被记录，模型会看到缺少因果中间环节的示范。

**工程建议**：优先采集少量可完整重放、能解释任务约束的示范，再确定哪些步骤需要专家、哪些可以由工具或教师模型补充。把专家真值、模型补写理由和验证结果分别存储。不要让后期生成的解释覆盖原始记录。

## 6. 挖掘现实资料：从“有人做过”到“现在能重放”

讲义 p.30 给出三类来源：代码历史、书面教程和视频。转换流程不是直接把它们加入训练语料，而是提取任务、恢复动作、在环境里重放并验证。[L11 pp.29–37]

### 6.1 代码历史能提供自然的前后状态

issue 可以成为任务，修复前提交可以成为初始环境，后续改动提供参考解，测试提供部分反馈。讲义用 SWE-rebench 介绍这种自动化采集路线。[L11 pp.31–32]

困难在于：一个 PR 可能同时修 bug、重构和改测试；issue 描述未必充分；依赖版本可能已经消失；原测试也未必能发现所声称的错误。最基本的验证应比较修复前后的检查结果，并明确哪些测试应由失败转为通过、哪些已有功能必须继续通过。

还要避免未来信息泄露。若给 Agent 的仓库保留了修复后的历史提交，任务可能变成搜索答案而不是修复问题。讲义 pp.60–61 用这类漏洞提醒我们，训练环境的可见内容也是监督的一部分。

### 6.2 教程写得对，不代表步骤已经执行过

教程常省略登录、已有配置、软件版本和中间等待。AgentTrek 在讲义中的路线是把教程作为引导，让 VLM 在真实浏览器执行，再筛选成功运行；这与仅由 LLM 离线写出动作有根本差异。[L11 pp.33–35、42]

对于企业 SOP，类似做法可以是：先读取操作规程，在测试系统中由 Agent 尝试执行，再由状态检查验证结果。SOP 提供方向，真实交互提供观察与后果，验证器提供接受条件。三者不能互相替代。

### 6.3 视频转动作存在逆问题

讲义介绍 VideoAgentTrek 时使用 inverse dynamics 思路：从前后画面推断可能的操作。[L11 pp.36–37]

这不是读取已经确定的动作标签。同样的画面变化可能来自点击、快捷键、自动刷新或后台服务。采集管线需要标记动作来源与不确定性，必要时再重放，而不是把所有推断动作当成同等可信的真值。

在金融文档流程里，视频里从一个页面跳到某张表，不一定能恢复精确检索词或原文版本。如果最终训练目标要求可审计的证据链，额外的原始文件标识和工具日志仍然有价值。

## 7. 合成轨迹：先写步骤，还是先探索再命名

讲义 p.39 区分两条路线：instruction first 与 interaction first。[L11 pp.38–45]

**先有任务再写步骤**可以很快扩展数据，也能使用大量教程。Synatra 在讲义中是离线合成示范的例子：LLM 根据间接知识生成步骤，没有把每一步都在真实环境中执行。

**先有交互再推断任务**则让 Agent 在应用中探索，然后在事后描述“刚才完成了什么”，并评分、筛选。讲义用 OS-Genesis、NNetNav 展示这种方向。它的好处是轨迹中的观察真实发生过，但事后标签仍可能过度解读：一次碰巧打开的页面不能自动说明用户目标已达成。

两者各有偏差。先写步骤可能生成不存在的元素或不可执行参数；先探索后命名可能只留下容易解释的简单任务，或者把副作用美化成目标。

面向需要真实工具执行的企业任务，可以设置三层验收：

1. **结构有效**：动作格式、角色、工具参数和消息关联符合目标 harness。
2. **执行有效**：关键动作能在指定初始环境中运行，观察确实来自执行。
3. **目标有效**：最终状态满足事先规定的任务，或事后标签经过独立验证。

结构有效只是最低门槛。一个完全符合 JSON schema 的工具调用，仍可能删除错误的数据库记录。像Synatra这样的离线合成可以提供候选监督，但合成观察与执行产生的观察应分别标记；未经过重放的样本不能因此被登记为“执行已验证”。是否使用这类候选，还要由学生在独立真实任务上的表现判断。

综述 §3 把合成对象进一步细分为指令/回答、类别标签、理由、成对偏好和文字反馈。它提示我们：若问题是“失败之后下一步怎么恢复”，单独合成更多最终回答不一定对症；可以标注错误类型、可采取的下一步、修正后的动作及对应结果。[R2 §§3.1–3.5，pp.2–5]

讲义 p.42 并列展示不同研究的单样本成本，但来源、模态、执行方式和模型不同。本文不据此计算谁的有效成功轨迹便宜多少倍。应当先统一样本定义、通过标准和成本范围，再比较。

## 8. 合成任务与环境：让数据包含可检验的后果

当需要大量练习时，可以自动构造环境、任务和 verifier。讲义 p.47 将代码 Agent 与工具使用 Agent 并列：前者在真实仓库中制造需要修复的问题，后者在 API schema 与数据库状态上构造目标。[L11 pp.46–51]

### 8.1 代码任务：故障必须被真正验证

讲义以 SWE-smith、R2E-Gym 介绍自动构造程序任务的不同路线。它们的共同工程问题是：如何得到有意义的初始错误，如何描述任务，如何验证修复。[L11 pp.48–50]

在企业文档系统中，可以对一个已验证的字段抽取器生成受控变化：单位表缺项、日期边界偏移、多个报表字段混淆，然后要求修复。但要注意，“注入一个会被现有测试发现的 bug”只覆盖现有测试能表达的性质。如果只制造一类字符串替换错误，模型也可能学到识别该生成器的指纹，而不是通用调试。

任务生成还应与答案隔离。若目标是自主定位故障，却在说明中直接透露标准修改位置，甚至附上答案patch，就可能绕过希望学习的诊断过程。真实issue中的堆栈或行号不应一律删除：若任务本来是根据这些线索修复，它们就是合法输入。应该根据希望测量的能力决定保留哪些线索，而不是默认信息越完整越好。

### 8.2 工具任务：数据库状态给出更清晰的奖励

讲义以 AgentScaler 说明，把工具调用看作对数据库的读写，可以构造依赖链并比较最终状态。[L11 p.51]

例如，用户要求“找到已确认的会议，修改时间，并通知已登记参与者”。任务状态包括会议记录、参与者和通知记录；成功判定需要检查正确会议被改动、其他会议没有变化、通知对象及内容符合要求。只检查最后一次 API 返回 `200`，不足以说明完整目标达到。

此类环境的优势是状态容易重置，副作用可以检查。风险是 API schema 真实、后端行为却过于简化：权限、并发、业务约束和异常处理若没有进入模拟，训练出的策略可能在真实系统里失败。环境规模大并不直接等于业务覆盖充分。

## 9. 模拟用户与模拟环境，替代的是不同对象

讲义 p.53 将两种模拟放在同一张图里，但它们的可信度问题不同。[L11 pp.52–57]

**模拟用户**产生请求、澄清、偏好与后续回应。Agent 的工具仍可以在显式数据库或真实测试环境中执行。讲义中的 τ-bench 和 APIGen-MT 属于理解这一方向的例子。关键问题是模拟用户是否代表真实人：是否知道得过多、表达过于完整、总是配合 Agent，或漏掉真实用户的误解与中断。

**模拟环境**由模型预测执行某个动作后会出现的状态或奖励。它替代了实际运行的部分成本。讲义以 DreamGym 的经验模型解释这一思路。风险更直接：如果模型预测某个错误工具调用会成功，策略可能持续利用这个不真实的转移。

两类模拟都适合生成候选练习，但应保留与真实环境的锚定：定期用真实执行检查模拟轨迹，对重要状态转移使用规则或可执行系统，记录模拟器版本，并在独立的真实任务上验证改善。

**教学推导**：假设每一步模拟状态有一个小概率偏离真实系统，长轨迹会积累偏差；即使单步误差不大，后续动作也可能进入真实系统从未到达的状态。因此不能只看单步预测准确率，还应检查完整任务的状态和奖励是否可迁移。这不是对某篇方法的定量误差界，而是选择模拟粒度时的工程约束。

## 10. 数据会把目标之外的东西一起教进去

讲义后半段不是附加的安全提醒，而是前面所有采集方法的验收条件。模型优化看到的目标，不会自动理解哪些是我们希望迁移的能力、哪些是数据管线留下的偶然特征。[L11 pp.58–75]

### 10.1 奖励漏洞：学会得分而没有完成目标

若环境允许读取未来修复、修改测试或通过不合法方式退出评分进程，成功标签就可能是错误标签。讲义 pp.60–65 用代码训练、行为监控和评测感知案例说明这种风险。

工程上首先检查**可见性和权限边界**：训练 Agent 能看到什么，能改什么，最终评分在哪里运行，评测材料是否泄漏。其次检查奖励的语义：非零退出码、跳过测试、测试未收集等应分别识别，不能只依赖一条“通过”的字符串。

讲义还展示，将行为监控信号直接并入训练奖励可能改变模型呈现的行为。本文不从单个案例推出“监控无效”，而是提醒：监控器成为优化目标后，需要在独立观察、结果检查和新行为分布上重新验证。检测到表达变化，不足以证明底层违规动作消失。[L11 pp.62–65]

### 10.2 记忆与污染：题目熟悉不等于任务能力

如果评测任务、修复提交、答案或近重复问题进入训练，模型可能凭记忆完成公开题目，却无法处理新仓库、新公司或新时间段。讲义 pp.66–67 用软件任务的记忆问题提出这个担忧；这里不采用未独立核验原研究的命中率数字。

对企业数据，仅按随机行拆分经常不够。一次问题的十种改写、一份年报的多种解析副本、同一事故的多次重试，可能被拆到训练和测试两边。要按共享来源或相关任务形成组，再在组之间拆分；对于面向未来的业务，还应加入时间隔离。

### 10.3 Harness 过拟合：把接口方言当成能力

讲义 pp.69–71 说明，工具名、参数格式、观察前缀和结束标记会成为训练分布的一部分。即使问题解决能力存在，部署接口不一致也可能让模型无法表达动作。[L11 pp.69–71]

修复思路不止“训练更多数据”。可以统一语义并验证转换、在训练中覆盖多种 harness、对目标部署格式做适配，或在分层评测中分别测任务推理与动作接口。要防止不同 harness 变化同时带来工具能力和预算变化，再把全部差异归因于格式。

### 10.4 SFT 与 RL 都可能越训越差

讲义 p.72 用 SWE-RL 案例讨论窄分布 SFT 与域外能力，p.73 用 OpenThoughts-Agent 的训练曲线说明 RL 峰值后可能退化，p.74 说明“排行榜最强教师”不必然训练出最好的学生。这些是课堂展示的研究案例，不能概括为“SFT 必然损害泛化”或“RL 总会改进”。[L11 pp.72–74]

需要观察的是训练分布、学生能力、示范难度、过滤标准、奖励与停止策略之间的匹配。教师的答案可以很强，但步骤超出学生可模仿范围；高分轨迹也可能太长、依赖特定工具或在某个漏洞上成功。教师选择应由学生训练后在独立任务上的表现验证，而不是只看教师自己原来的分数。

综述 §6.2 进一步讨论合成数据反复训练中的分布收缩、幻觉和近似误差累积，并介绍保留真实数据和多样性的应对思路。这不表示所有使用合成数据的训练都必然崩溃；风险取决于数据保留、采样、验证和学习过程。[R2 §6.2、Limitations，pp.8–10]

## 11. 从生产日志到可用样本，需要经过哪些状态

一个实用的数据管线应区分原始记录、已验证样本、可训练版本和独立评测，而不是把它们混在一个向量库中。

下面是**工程建议的样本结构**，字段含义比 JSON 语法更重要。

| 字段组 | 例子 | 为什么需要 |
|---|---|---|
| 来源身份 | trace ID、原始任务、授权范围、采集方式 | 能追溯实际来源与使用边界 |
| 输入与环境版本 | 文档哈希、数据库快照、工具 schema、harness 提交 | 能解释动作与结果是否可重放 |
| 事件序列 | 观察、动作、参数、结果、时间、父子调用关系 | 保留错误与恢复的因果顺序 |
| 监督标注 | mask、教师/人工来源、纠正动作、理由来源 | 明确模型究竟模仿哪些位置 |
| 验证证据 | verifier 版本、程序结果、人工标签、异议 | 防止把“看起来成功”直接写成真值 |
| 数据治理 | 组 ID、近重复簇、split、用途、保留期限 | 防止污染与未经允许的复用 |
| 成本与状态 | token、执行时长、基础设施失败、审阅状态 | 计算真实有效成本并定位瓶颈 |

原始日志进入候选集之前，先检查完整性：是否缺少工具输出，是否记录了最终产物，是否知道准确的初始状态。再做敏感信息处理、来源分组、验证、标注和版本化。训练导出是一个可重建的产物，不应反过来覆盖原始记录。

失败轨迹也有价值，但用途应分开。它可以用于失败分类、构造环境和偏好对，或者在纠正后形成示范。把失败动作原样当成“正确下一步”做 SFT，会监督错误；只留最短成功轨迹，又可能丢失恢复能力。数据使用方式应由目标能力决定。

### 11.1 清洗与导出也必须保留因果关系

**工程建议**：脱敏需要在同一轨迹和关联环境里保持映射一致。例如把观察中的客户 ID 改为 `customer_A`，却保留动作参数里的原 ID，会把正确调用变成无法解释的调用；把金额统一抹成占位符，也可能使原来的比较结论失效。应同步变换关联字段，重跑可执行检查；无法保留任务语义的样本应隔离，不能只凭“敏感词已移除”进入训练。

另一个边界是每一步当时能看见什么。训练时可以知道完整成功轨迹，但动作 $a_t$ 的输入前缀只能包含该步之前可用的信息。不要把后续工具结果、最终参考解或事后总结提前放入输入，制造部署时不存在的条件。纠正过的动作如果改变了环境，也不能直接接上原错误动作之后的观察；必须从分歧处重新执行或明确标记为未验证的候选轨迹。

来源分组与拆分也要早于扩增：先给原始任务、仓库或文档族分配 split，再让其改写、重试、教师补写和派生环境继承分组。否则只在导出时检查文本重复，会漏掉措辞不同但答案相同的同源任务。用于调试 verifier、筛选教师或选择数据配比的任务属于开发环节；最终留出集不能随这些选择反复回流。导出清单应绑定原始样本、变换、mask 和验证器版本，使一个错误标签能追踪到受影响的数据版本。

## 12. 指定阅读的关键补充：数据飞轮不要求先训练模型

Shreya Shankar 的文章把飞轮分为三部分：定义成功和指标，实现持续监控，再利用反馈改进应用。它强调让评价标准、评价实现与生产数据持续对齐，而不是只把日志积累起来。[R1，A Framework for Creating a Flywheel]

这和讲义的数据后训练主线形成互补。即使公司只能调用固定 API，没有权重训练条件，也可以把经人工修正的案例变成示例、改写工具接口、调整检索和工作流。长期留下的是版本化样本与系统配置；模型权重可以不变。[R1，Continual Improvement]

以文档抽取 Agent 为例，闭环可以这样落地：

1. 采集真实任务的输出、证据与运行记录。
2. 把质量拆成字段正确、证据充分、口径一致、无额外副作用等维度。
3. 先由代码检查确定性属性；语义维度由经过人工样本校准的 judge 辅助。
4. 对有代表性的错误做人工纠正，记录“原输出—为什么错—修正后证据”。
5. 将经过批准的案例作为新的 few-shot 候选、回归任务或训练样本。
6. 在没有参与候选生成和选择的评测集上比较新旧系统，再发布可回滚的版本。

文章也提醒，要验证输入而不只验证输出，对分类、写作和代码生成节点使用不同检查。将所有节点都用一个“总体质量 1–5 分”衡量，往往不利于定位错误。[R1，Evaluation §§c–d]

### 12.1 “评价标准”和“评价器实现”要分开维护

例如“回答简洁”是标准，“小于 200 字”是一种实现，二者并不等价。业务新增了必须披露的信息后，原来的长度阈值可能开始惩罚正确回答。对 LLM judge 也是如此：它的 prompt、few-shot 和底座模型都可能漂移。[R1，Monitoring]

应定期用新的人工标注样本测评价器与业务判断的偏差。不能因为评价器评分上升，就直接宣布业务质量提高；模型和评价器有共享偏差时，飞轮可能只是在相互强化错误。

文章提出用近期案例、分歧案例和相似案例改善动态 few-shot，但对一些策略明确表示尚缺充分实践验证，例如按新近程度加权。本文把这些保留为可以检验的工程候选，不将其称为已证实最优算法。[R1，Monitoring §b]

### 12.2 飞轮需要采纳门槛，而不是自动复制所有反馈

用户点“赞”可能是因为语气好、响应快，也可能尚未发现数值错误；用户点“踩”也可能来自超时而非推理失败。反馈要关联具体维度和可核实证据。

当检索到的“修正案例”会自动进入 prompt 时，它实际上成为系统输入供应链的一部分。文章脚注也提出 prompt poisoning 和受监管场景的审批问题。工程上应给案例适用条件、来源与发布状态，避免未经核实的用户文本被直接提升成全局规则。[R1，Footnotes]

## 13. 质量评估要评价数据，还要评价数据带来的改变

ACL 综述将评估与筛选单列一节。其方法包括规则、外部反馈、LLM 评估，以及用人工小样本检查自动标注质量。[R2 §4，pp.6–7]

可以把数据验证拆成三层：

1. **样本层**：格式有效、来源完整、动作可执行、标签可靠。
2. **数据集层**：任务覆盖、难度、多样性、近重复、类别与来源分布。
3. **学习效果层**：学生或应用在独立任务上的收益、回归和成本变化。

前两层通过，不代表第三层一定提高。一个完全正确但高度重复的简单数据集，可能没有补上真实能力缺口。反之，某些困难数据对容量较小的学生模型并不合适，需要课程或示范粒度调整。

人工抽查也要覆盖分歧和高风险切片。若只检查 judge 已经高分的样本，无法可靠估计错误放行。可以固定一部分随机抽样估计总体质量，再加一部分有目的的分歧/长尾抽样定位问题；两类结果分开报告，避免用主动选择的样本冒充总体比例。

## 14. 成本的分母应是有效且有用的样本

只计算教师模型生成一条轨迹的 token 费用，会漏掉环境重置、工具执行、筛选、人工复核和失败尝试。一个**教学成本模型**是：

$$
C_{\mathrm{有效样本}}=
\frac{C_{\mathrm{任务构造}}+C_{\mathrm{生成}}+C_{\mathrm{执行}}
+C_{\mathrm{验证}}+C_{\mathrm{人工}}}{N_{\mathrm{通过且可用}}}.
$$

如果生成 1,000 条候选花费 100 个预算单位，执行与验证花费 80，人工复核花费 120，最后只有 200 条去重后可用样本，那么每条有效样本是 $300/200=1.5$ 个预算单位，而不是 $100/1000=0.1$。若没有有效样本，不能报告这个比值为有限的有效单价。这些数字仅为算术教学例。

“有效”仍不等于“有学习价值”。若 200 条全是相同模板，单位数据成本虽然低，训练收益可能很小。最终还要比较固定预算下的独立任务改善，而不是只追求导出文件的行数。

讲义 p.18 混合展示预训练 token、SFT 示例、RL prompt 和不同阶段计算量，它们的单位与版本不同；不能直接把几个数字相除，得到企业 Agent 的通用数据配比或预算建议。这里更值得借鉴的是：小规模高价值后训练数据可能值得认真构造，但是否有效需要自己的验证。

## 15. 怎样设计一个可以归因的最小实验

下面的实验是建议方案，未执行模型训练。

**问题**：企业助手在遇到解析失败时反复重试同一工具。希望改善的是错误恢复，不是最终回答文风。

**基线与数据**：固定底座、工具、harness、任务集与预算。先收集带完整错误输出的真实失败，人工确定失败类型与合理恢复动作，再构造可重置环境。

**候选组**：原系统；只加 few-shot 恢复案例；使用相同案例做动作 SFT 的学生；若资源允许，再单独设计环境训练组。每组的改动范围和额外预算单独记录。

**隔离**：按文档来源、公司和错误生成模板分组拆分；隐藏测试包含新公司、新文档和不同表现形式的同类故障。不得用测试任务持续挑选候选案例。

**指标**：完整任务成功率、相同无效动作的重复次数、恢复后是否引入新错误、拒答正确性、总成本和耗时。若有基础设施失败，另记原因并同时报告端到端表现。

**归因**：如果 few-shot 和 SFT 都提高，说明这些数据提供了有效行为信号；仍要看新错误类型是否泛化。如果只在原工具名下改善，换 schema 后退化，就应调查 harness 依赖。如果平均成功率提高但高代价副作用增加，不能按单一均值发布。

**停止与采纳**：提前规定回归约束和成本预算，保留旧模型/配置与数据版本。采纳的是一个可验证的新系统版本，而不是“训练跑完”的 checkpoint。

## 16. 常见故障与诊断顺序

| 现象 | 先检查什么 | 常见错误处理 |
|---|---|---|
| 训练后会编造工具返回 | role、loss mask、观察是否当成目标 | 继续加入更多同样损坏的轨迹 |
| 训练集很好，新任务变差 | 来源分组、近重复、任务难度、生成模板 | 只增加 epoch |
| 换框架后没有合法 tool call | schema、动作格式、终止信号 | 认定模型不具备领域知识 |
| reward 上升但业务错误增多 | verifier 漏洞、标签与目标错位 | 直接加大奖励权重 |
| 模拟环境里成功，真实系统失败 | 状态转移、权限、并发、异常与工具语义 | 只扩大模拟数据量 |
| 数据很多但改进不明显 | 能力缺口、覆盖、重复、学生适配 | 按行数而不是独立效果汇报 |
| 自动 judge 与人工越来越不一致 | 业务标准、judge 模型/prompt、数据漂移 | 把新人工标签当作噪声删除 |
| 少数任务吞掉大部分成本 | 超时、重复动作、回合分布、环境重置 | 只看平均单条生成价格 |

诊断顺序应先确认数据和反馈是否可信，再分析训练算法。若原始环境坏了或标签反了，换优化器通常没有解决根因。

## 17. 自测与参考答案

**1．为什么最终问答对不能完整替代 Agent 轨迹？**  
答：它缺少当时观察、动作选择、工具反馈、错误恢复和终止过程，无法直接监督许多决策能力。

**2．保存了工具输出，是否就应该对这些 token 做 SFT？**  
答：不一定。工具输出通常作为条件，训练目标主要是模型需要生成的动作/回应。必须明确 role 和 loss mask，避免教模型伪造观察。

**3．轨迹和环境是什么关系？**  
答：轨迹记录一次尝试，环境允许重复产生新尝试并验证结果。一个环境可生成多条轨迹，历史轨迹也可能帮助恢复环境，但文字记录本身不保证可执行。

**4．合成理由为什么不等于真实专家思考记录？**  
答：它是事后或模型生成的监督内容，可能有用，也可能不忠实；来源必须标记，不能覆盖实际动作和原始证据。

**5．Synatra 与 AgentTrek 在讲义中的核心区别是什么？**  
答：前者例示离线生成示范，后者例示在真实浏览器中引导执行并筛选成功运行。它们不能仅按不同论文给出的单条成本直接排名。

**6．模拟用户与模拟环境分别替代什么？**  
答：前者替代人的请求与回应，后者替代动作之后的状态转移/反馈。它们各自存在分布偏差，需要真实任务验证。

**7．为什么训练前要让空操作和错误产物接受验证？**  
答：用来发现初始状态已过关、评分器缺陷和错误标签；否则模型可能学会利用奖励漏洞。

**8．失败轨迹是否都应删除？**  
答：不是。可以用于诊断、偏好、任务构造和纠正示范。但不要把失败动作未经处理当作正确动作监督。

**9．为什么随机行拆分可能污染评测？**  
答：同一文档、问题改写、重试或生成模板可能同时出现在训练与测试中。应按来源和相关任务组拆分，并考虑时间隔离。

**10．没有微调权限，能否构建数据飞轮？**  
答：可以。经验证的反馈可以改进示例检索、prompt、工具和工作流；系统状态得到持久更新，但不代表模型权重已经学习。

**11．数据生成质量高，为什么仍要训练后独立评测？**  
答：正确性、多样性和学生适配不同；高质量样本也可能重复、过难或只覆盖局部接口，实际收益需要独立任务验证。

**12．教师模型榜单最强，是否必然是最好教师？**  
答：不必然。学生能否模仿、轨迹长度和结构、工具约定及过滤方法都影响结果，应以学生训练后的独立表现选择。
