## 1．把研究对象从一次回答扩大到整个任务

设想基金公司的内部助手接到请求：“整理昨天持仓公司的重要公告，说明影响，并准备一份晨会材料。”模型直接生成一段流畅文字，只覆盖了工作的一小部分。完整任务还要确定“昨天”的时区和交易日口径、取得当日持仓、解析公司和证券代码、找到公告正文、检查发布时间、提取事实、计算暴露、保留证据，再生成材料。若还要向群里发布，就涉及一次有外部副作用的动作。

把整个任务缩减成 `prompt → answer`，会混淆至少四种能力：模型知道什么，系统取得什么，程序执行什么，人允许系统做什么。例子中的持仓来自受权限约束的业务数据；最新公告来自外部信息源；金额计算应交给确定性代码；是否发送材料取决于工作授权。模型参数中的“知识”不能代替这些对象。

BAIR 的指定阅读把多个模型调用、检索器和外部工具组成的系统称为 compound AI system。它强调，系统设计提供了更新信息、控制行为、调整成本与质量的空间；这是一篇研究观点文章及案例综述，并不是证明“任何复杂系统都优于单模型”的统一实验。[A，Why Use Compound AI Systems?、Developing Compound AI Systems]

由此，本课的最小分析单位应是**一次任务运行**：请求、执行环境、允许的动作、运行过程中得到的观察、最终产物和验证结果。后续的 RAG、工具、记忆、优化与评测，都可以放到这条任务链上理解。

## 2．三个相近概念，为什么需要分开

| 概念 | 谁决定主要执行顺序 | 内部助手例子 | 首要工程问题 |
|---|---|---|---|
| LLM 调用 | 调用方预先确定一次输入输出 | 把一则公告总结成三点 | 输入是否充分、输出是否正确 |
| Workflow | 程序预先组织控制流 | 持仓查询 → 公告检索 → 摘要 → 汇总 | 每步契约、失败处理、可恢复性 |
| Agent | 模型根据观察决定部分后续行动 | 发现公告缺少对比基期，再主动补查上期报告 | 行动边界、终止条件、观察质量 |

这些不是排他的产品分类。一个系统可以用固定工作流处理日常批次，在异常环节启动 Agent；Agent 内部也可以调用固定工作流。BAIR 阅读明确提出控制逻辑应该写在传统代码中，还是由模型驱动，是系统设计的选择。[A，Developing Compound AI Systems]

“Agent”本身没有所有研究者统一采用的二元定义。《AI Agents That Matter》§1.1 将自主程度看成连续谱，并从目标和环境复杂性、用户监督程度、系统控制流等方面讨论 agentic。我们在本文采用一个工程工作定义：**模型根据当前任务状态和环境观察，选择行动，系统执行行动并把结果交回模型，循环直到满足终止条件。**这是便于分析的教学定义，不替其他论文统一术语。[C，§1.1，PDF p.2]

判断一个功能是否值得用 Agent，可以问：“执行期间得到的新信息，会不会改变下一步应该做什么？”如果所有公告都固定经过同样四步处理，工作流常已足够。如果发现公司更名、公告补充、更正或缺失，需要临时制定补查路径，模型驱动的选择才可能提供价值。即便如此，权限校验、数据口径和提交规则仍适合由程序执行。

## 3．Agent 循环真正交换的是状态、动作和观察

用一个简化模型表达一次循环：

$$
c_t=C(g,h_t,m_t,\mathcal T),\qquad a_t\sim\pi_\theta(\cdot\mid c_t),
$$

$$
(o_{t+1},e_{t+1})=E(e_t,a_t),\qquad h_{t+1}=h_t\mathbin{\Vert}(a_t,o_{t+1}).
$$

这里 $g$ 是任务目标，$h_t$ 是已经发生的交互历史，$m_t$ 是可读取的外部记忆，$\mathcal T$ 是当前暴露的工具说明。$C$ 表示上下文构建过程；它选择哪些信息交给模型，并不意味着把整个数据库塞进去。$\pi_\theta$ 是参数为 $\theta$ 的模型产生行动的分布，$a_t$ 可以是工具请求或最终回答。$e_t$ 是环境真实状态，$o_{t+1}$ 是系统观察到的行动结果，$\Vert$ 表示把记录追加到历史。

这个公式是教学抽象，关键是把“模型认为发生了什么”和“环境实际发生了什么”分开。模型请求发送邮件，不等于邮件已经发出；工具返回超时，不等于邮件一定没发出。对于有副作用的动作，调用结果需要请求标识和事后查询机制，否则 Agent 的“再试一次”可能制造重复发送。[B，Agent System Overview、Component Three: Tool Use；上述状态表示和副作用分析为工程推导]

内部助手的一段可检查轨迹可以是：

| 步骤 | 系统事实 | 模型下一步可以据此决定什么 |
|---|---|---|
| 读取持仓快照 | 截止时点、公司代码、权重及版本 | 需要检索哪些公司 |
| 搜索公告 | 返回标题、发布日期、文档 ID | 哪些候选值得读取正文 |
| 读取正文 | 得到原文片段、页码、文件校验值 | 是否存在关键信息缺口 |
| 对比历史报告 | 收入基期或资本开支口径得到核实 | 能否作出比较性表述 |
| 验证材料 | 核心事实均有证据，计算通过 | 结束、修订或转人工 |

循环的价值来自观察改变决策。只是把模型多调用几遍，并不自动产生这种价值。

## 4．把 Agent 的组成部分放回它们的职责

讲义 pp.29–32 用 ReAct 轨迹把模型、推理、记忆、工具和环境逐一对应起来。Weng 的指定阅读以规划、记忆和工具使用组织 LLM Agent 的结构。它适合建立概念地图；其中一些实现与例子属于 2023 年的研究语境，不能直接当作当前框架的默认行为。[B，Agent System Overview]

**模型核心**负责在给定信息和约束下生成候选答案、计划或动作。它擅长处理模糊输入、语言匹配和不完全结构化问题；但生成了看似合理的数字、路径或工具名，并不证明对象存在。

**工具**把模型连接到外部能力。搜索工具取得证据；数据库工具读取业务状态；代码执行器完成确定性计算；写入工具改变环境。工具契约应解释输入、返回结构、错误及副作用。把几个功能高度重叠、名字近似的工具同时交给模型，会扩大决策歧义。

**上下文**是本轮真正可见的信息。模型不因某份报告已经下载，就自动知道其中内容；报告必须被读取、检索或以摘要形式加入当前输入。上下文也包含规则、工具说明和此前观察，因此数据量增长会同时带来成本与干扰。

**记忆**是运行框架在当前上下文外保留、以后可再加载的状态。数据库里的历史公告是资料库；任务进度表是工作状态；经过审核的检索策略是程序性经验。它们可以都被称为 memory，但生命周期和更新规则不同。向量库只是一种存储与检索方式，不能自动完成事实修订、权限隔离或经验适用性判断。[B，Component Two: Memory；生命周期划分为工程解释]

**环境**决定什么动作有效、什么结果可见。若数据库连接只提供只读权限，模型不能通过提示文字获得写权限；若工具只返回十条搜索结果，模型看不到其余结果。调试时要先检查环境暴露了什么，而不是先责怪模型“不够聪明”。

### 4.1 记忆内容、写入方式与存储介质要分开

讲义 pp.45–49 按内容区分 episodic、semantic 与 procedural memory。事件记忆保存“某天公司发布了什么”；语义记忆维护“公司当前产能和项目状态是什么”；程序性记忆保存“这种公告应怎样检索、核查与计算”。同一数据库可以存三种内容，同一种内容也可以存在文件或关系表中；这套分类不是三种数据库产品。

内部助手应保留历史事件，同时允许当前状态随更正公告修订；程序性经验则需要适用条件和回归验证。把“上次这个公司的公告在第 8 页”写成通用技能，会把偶然位置当成稳定规律。原始事件流、从事件推得的知识、经过验证的操作经验，应能彼此追溯。[L，pp.45–49；B，Component Two: Memory；具体更新契约为工程建议]

### 4.2 从 RAG 到工具调用，再到 MCP

讲义第 57 页把 RAG 概括为 retrieve、augment、generate；第 58 页把工具调用拆为选择、填参、校验、执行与结果回到上下文。检索是一种取得信息的动作，工具还可计算或改变外部状态；两者都需要把结果交回后续决策，而不是只在最终文字里声称执行过。

第 59 页的 MCP 图强调统一应用与数据、工具之间的连接方式。标准化接口可减少重复接入工作，但不能替代模型判断“现在该用什么工具”，也不能自动决定哪些业务操作被授权。具体协议能力应绑定版本：本页指向 2026-07-28 架构文档，课程第 4 课的指定阅读另列 2025-06-18 规范，不能把两个版本的条款混作同一份规范。[L，pp.57–59；本文在导论中只解释图示职责，不宣称逐条核查 MCP 新版协议]

### 4.3 工具能力怎样进入模型，为什么长任务更难训练

讲义第 51 页用 Toolformer 说明：工具使用可以成为训练目标，模型需要学会是否调用、调用哪个 API、填什么参数，以及如何利用返回结果；第 52 页以 Gorilla 引出大量 API 的接入问题。这与运行时把工具说明放入上下文是两条不同的干预路径。前者改变模型参数，后者改变模型本次可见的信息和动作空间。导论先建立这一区分，具体训练方法在工具与优化课再展开，不能仅因一个模型见过工具示例就认定它掌握了新增 API。[L，pp.51–52]

第 61 页列出 sparse reward、long horizon、expensive rollouts 三个训练困难。用晨报任务理解：最终“报告正确”只提供一个任务级结果，却不能直接指出错误来自公告召回、期间判断还是计算；几十步交互扩大信用分配范围；一次训练样本还可能需要真实检索、模型推理和沙箱执行，成本远高于读取一条静态问答。增加逐步反馈能帮助定位，但若只奖励格式正确或工具次数，就可能优化了代理指标而损害最终任务。[L，p.61；晨报对应关系为教学推导]

因此先把轨迹、输入版本、步骤结果和最终验收连接起来，再决定是改工具反馈、改提示与示例，还是训练权重。训练数据与运行系统不能分开设计：若训练时总能访问正确公告，而部署时检索经常缺失，训练出的行为不会自动修复这个环境差异。这个问题将由第 9 课的优化与第 11 课的数据设计继续展开。

## 5．为什么更大的模型不能直接替代系统设计

BAIR 阅读提出的几个动机，可以转化为企业内部助手的设计要求。[A，Why Use Compound AI Systems?]

第一，**知识更新**。昨天的公告尚未进入模型训练数据，必须从外部获取。检索将“最新事实从哪里来”变成系统能力，但仍需要检查抓取、发布日期和正文版本。

第二，**访问控制**。两个员工的资料可见范围可能不同。需要先根据身份限定检索空间，并在读取正文时再次校验。把敏感材料交给模型，再要求模型不要泄露，无法代替服务端授权。

第三，**可核查性**。有引用标记不等于论断得到支持。系统应能把“公司下调资本开支”定位到原文位置，并区分原句、计算结果和分析推断。如果只有一张摘要，没有原始文档标识，就很难追溯错误。

第四，**资源分配**。分类邮件、提取日期、判断投资逻辑变化，对模型能力与验证成本的要求不同。系统可以用便宜且稳定的确定性步骤处理明确对象，把预算留给复杂判断。是否采用小模型、路由或多次调用，应通过本地任务评测决定。

这些措施也有成本。增加检索会引入索引陈旧与权限过滤问题；加入验证器会增加延迟；多模型路由会增加配置和回归测试。系统工程提供的是更大的可控设计空间，而不是免费的性能提升。

## 6．规划与反馈：先做什么，何时改变主意

Weng 的阅读讨论任务分解、ReAct 和反思等思路。它们的共同点是给复杂任务增加中间结构，但作用不同：分解明确子问题，工具观察提供外部信息，反思试图根据失败改善后续尝试。[B，Component One: Planning]

讲义 pp.35–36 的 Apple Remote 示例展示关键差别：纯语言推理从一个错误前提继续扩展，ReAct 通过搜索纠正目标程序，又根据搜索失败调整实体名称。这里改善信息状态的是实际观察；“想得更详细”本身不保证前提正确。第 38 页的 self-consistency 对多条候选答案聚合，第 39–40 页的 Reflexion 把反馈压缩为后续可用的经验，第 41–43 页再引出辩论和编排。多数答案一致可能仍共享同一错误，多个 Agent 的协作也需要信息与任务分工，不能把人数直接当作独立证据。[L，pp.35–43]

对内部助手，一个合适的初始计划是“确定持仓范围 → 获取公告 → 筛选重大变化 → 回查证据 → 输出材料”。计划不应把尚未取得的事实当成前提。例如，在没有读取公告时写下“分析公司利润下滑原因”，已经把利润下滑预设为真。更稳妥的子目标是“判断利润同比变化，并核实可比口径”。

反馈也需要分级：

| 反馈 | 能证明什么 | 不能直接证明什么 |
|---|---|---|
| JSON 解析成功 | 输出满足某些结构条件 | 字段内容真实 |
| 工具执行成功 | 请求在该工具中执行完成 | 请求参数符合业务目标 |
| 计算断言通过 | 给定输入下算术关系成立 | 输入口径正确 |
| 证据审查通过 | 指定证据支持指定论断 | 整篇报告无遗漏 |
| 用户采纳 | 输出对该用户有帮助 | 无事实错误、可推广到其他用户 |

反思只有在失败信号可靠且能影响后续决策时才有意义。让模型阅读自己刚生成的文本，再问“是否正确”，可能重复原有假设。给它一个真实的失败断言、缺失证据位置或不一致字段，通常更容易定位问题。这是工程建议，不是声称所有反思论文都已证明同样效果。

## 7．停止条件是系统规格的一部分

“直到任务完成”过于含糊。内部助手需要可检查的完成条件，例如每个入选事件都包含公司代码、公告时点、事实摘录、来源位置和影响判断；影响判断中的数值变化可复算；无法查明的项目显式保留；外发步骤符合既定授权。

同时应有运行边界：最多工具调用次数、累计 token 或金额、整体超时、连续无进展次数，以及需要人工处理的情形。满足预算上限并不意味着任务成功；系统应返回部分成果与未解决事项，而不是把预算耗尽后的答案包装成完整结果。

交付结果可以分成三类：

1. **成功完成**：产物和验证满足事先定义的条件。
2. **可交接结束**：仍有缺口，但已记录缺口、证据和下一步。
3. **未形成可交付结果**：没有满足要求的成果，也没有足够可靠的部分成果可交接。

另外独立记录**停止原因**，例如满足验收、环境故障、权限不足、预算到顶或用户取消。预算耗尽时可以有可交接的部分成果，取消时也可能已有外部副作用；原因不能代替结果。持久化状态若只记录 `done=true`，以后无法知道报告是完成、被取消还是部分失败。对长流程，任务目标、已完成步骤、输入版本、外部副作用和剩余工作，比保存一大段聊天文本更能支持恢复。[工程建议；与 B 的记忆和规划结构相衔接]

## 8．从第一天就评测，避免把复杂度当作进步

讲义第 55 页把工程分为 System、Data、Evals 三个支柱：控制流设计、模型可见的数据与训练示范、衡量任务的指标需要同时考虑。第 61–63 页又区分多次运行的一致性、对合理扰动的稳健性和可理解、可恢复的失败方式；一次任务答对不能覆盖这些维度。《AI Agents That Matter》要求把成本和效果放在一起考察。其 HumanEval 分析比较了复杂 Agent 与重试、升温和模型升级等简单基线，指出某些复杂架构的增益不能与额外调用预算混为一谈。这个结论限定于论文中的任务、模型和实验设置；不能推广为“规划、反思和调试都无效”。论文自己也指出更困难的任务可能有不同结果。[C，§2，PDF pp.2–4]

对于内部助手，至少比较四个系统：单次模型回答；固定检索后生成；固定检索、生成与验证工作流；允许动态补查的 Agent。让它们使用同一资料快照、相同权限、相同任务集，并记录预算。这些比较能判断整个方案是否值得采用，但还不足以把差异归因于 Agent 控制，因为检索、验证与调用量也一起改变了。要隔离动态控制的作用，再在同一模型、工具、初始上下文和预算上限下，仅切换固定补查规则与模型选择；报告实际消耗、逐任务配对结果及重复运行的波动，并检查收益是否集中在确实需要改变路径的任务上。[工程实验设计]

建议先建立一个按真实错误分层的小评测集：日期边界、证券别名、公告更正、同名公司、表格负数、基期变化、缺少正文、数据源超时、权限不足和无重大事件。简单题和困难题要分开统计，否则大量简单摘要可能掩盖少数高风险失败。

常用指标需要明确分母：任务成功率按整个请求计算；事实支持率按可核查论断计算；事件召回率要求事先有参考事件集合；权限违规按尝试或实际泄露分别统计；延迟应报告分位数而不只均值。不要把这些指标无权重地平均成一个分数，掩盖不可接受的失败。

## 9．成本、延迟与可靠性怎样同时考虑

设一次任务用了 $N$ 次模型调用，教学成本模型为：

$$
C_{\mathrm{run}}=\sum_{i=1}^{N}(p_{\mathrm{in},i}n_{\mathrm{in},i}+p_{\mathrm{out},i}n_{\mathrm{out},i})+C_{\mathrm{tools}}+C_{\mathrm{infra}}.
$$

$n$ 是输入或输出 token 数，$p$ 是对应单价；实际账单还可能包含缓存、批处理和其他计费规则，不能把此式当作某个供应商的价格承诺。记录 token 与工具用量，便于在价格改变后重新计算。[C，§4，PDF pp.6–7；公式为教学展开]

若系统有一次性优化成本 $C_{\mathrm{build}}$，处理 $M$ 次请求，总成本近似为 $C_{\mathrm{build}}+M\mathbb E[C_{\mathrm{run}}]$。优化是否值得，取决于未来调用量以及节省是否稳定。只比较运行成本会忽略构建成本，只比较一次演示账单又会忽略规模效应。[C，§3，PDF pp.4–6]

更重要的是成功交付成本。若某方案平均每次 0.2 个教学成本单位、成功率 0.8，而另一方案每次 0.3、成功率 0.95，不能只凭单次价格选择前者。在每次成本固定、尝试独立、可以可靠识别成功且一直重试的理想假设下，每次成功的期望运行成本分别为 $0.2/0.8=0.25$ 和 $0.3/0.95\approx0.316$；高成功率方案也不一定更便宜。真实系统还要计入验证、人工复查、重试相关性和遗漏后果，并先满足质量约束再比较成本。这里的数字只是算例，不能当作真实模型表现。

延迟也不等于调用次数之和：独立公告可并行读取，依赖前一步结果的补查必须串行；重试会扩大尾部延迟，限流会引入排队。预算应沿关键路径分配，而不是盲目给每个步骤相同超时。

## 10．泛化为什么必须具体到“换了什么”

《AI Agents That Matter》把基准所要求的泛化分为分布内样本、任务、领域等不同层次，并指出测试集应该匹配所声称的泛化范围。若系统只在开发时见过的任务上调提示，测试分数不能证明它能处理新任务。[C，§5，PDF pp.7–9]

内部助手的泛化可以逐层检查：同一公司不同日期；新公司；不同公告类型；不同文档版式；新的用户角色；新的数据源。它们不是同一种迁移。如果提示和规则里写死了公司别名，不能把表现称为跨公司能力；如果只会处理公告正文文本，就不能声称支持扫描 PDF。

训练、优化与最终评测要分开。开发者反复看过的错误样本已经成为开发信息；即使没有更新模型权重，提示、检索规则和人工流程仍可能对这些样本过拟合。保留按时间或公司划分的未见任务，通常比随机混合近重复公告更能暴露问题。[C，§5；具体拆分方式为工程建议]

## 11．怎样定位“Agent 又失败了”

| 现象 | 优先检查 | 可取得的定位证据 | 修正方向 |
|---|---|---|---|
| 没发现重大公告 | 数据覆盖、日期过滤、候选召回 | 抓取清单、查询参数、过滤前后数量 | 修数据或召回，别先换生成模型 |
| 找到原文但数字错误 | 解析、单位、期间与算术 | 原页截图、字段位置、计算输入输出 | 保留表格结构、显式单位、代码计算 |
| 不断重复搜索 | 工具反馈、状态与停止规则 | 连续查询及结果集合变化 | 暴露无进展信号、记录已检索范围 |
| 材料很长但没有判断 | 目标、输出规格和证据选择 | 请求约束、候选事实到段落映射 | 明确决策问题，删除无关上下文 |
| 声称已发送但群里没有 | 工具执行与外部状态 | 请求 ID、服务返回、状态查询 | 用环境确认完成，避免凭文本判断 |
| 新公司表现明显下降 | 评测分布、实体映射与隐含规则 | 按公司/类型分层结果 | 补通用机制，重新划分留出集 |

记录轨迹的目的不是收集越多越好，而是重建“当时看到了什么、为什么允许执行、执行后发生了什么”。应保存模型与提示版本、工具 schema 版本、文档或数据快照、观察摘要与原始证据位置。敏感原文的访问仍受权限和保留策略约束；把全量业务数据复制进日志，不是可观测性的必要条件。[工程建议；A 的 Operation 与 C 的可复现性讨论提供问题背景]

### 11.1 任务成功与安全遵循要分别验证

讲义 pp.64–70 用任务完成与安全遵循的差别、隐私、弹窗攻击、奖励篡改和多 Agent 串谋等例子提醒：完成了表面目标，也可能违背权限或原始目的。对内部助手，“报告按时发出”和“只使用可访问资料、没有把隐私带入报告”是两条检查。外部文本也可能试图改变 Agent 的目标，工具返回应作为数据处理，不能因为出现在检索结果中就获得指令优先级。[L，pp.64–70]

这些页是风险地图，不是一组可统一比较的安全分数。本文没有逐篇复核其外链案例，不复述第 66 页的攻击成功率，也不据此估计本系统的真实被攻击概率。工程上可用权限错误、受控恶意文档和重复执行等测试检查边界，但本文未实际运行这些模型安全实验。

## 12．一个能逐步交付的实现顺序

第一步，把任务输出写成结构契约：每条事件包含公司、时间、事实、来源、影响及不确定性。用人工构造或已核实样例测试契约是否足够表达正常与异常情况。

第二步，建立确定性的资料入口：持仓接口、公告抓取、正文存储与可重复的计算。先不让模型自由调用所有业务接口，先验证输入事实可以稳定取得。

第三步，做固定检索和生成基线。把每个失败归到召回、解析、推理、格式或环境。若主要问题在原文缺失，增加规划没有针对性。

第四步，在确实需要动态补查的地方加入模型选择。动作集合可以先限制为检索、读取、计算、请求澄清和结束。每一步返回结构化观察，并设置预算和无进展停止条件。

第五步，增加持久任务状态与恢复。将已确认的文档 ID、输入版本、完成检查及外部副作用独立保存。恢复时验证环境状态，不能把旧聊天里“准备发送”当作已经发送。

第六步，运行留出集和故障注入：让一个数据源超时、让正文缺页、让工具返回无权限、让同一写入响应丢失。观察系统是否诚实交接、是否重复动作、是否仍保留证据。这里列的是实验设计，本文没有执行这些模型或业务实验。

## 13．自测与参考答案

**题 1：固定检索后调用模型生成答案，算不算 Agent？**  
答案：取决于定义，不能仅靠产品名判断。按本文工作定义，它主要是 workflow；若模型根据观察自主选择后续工具和终止时机，动态控制程度更高。两种都可以是 compound AI system。

**题 2：工具返回 `success=true`，能否证明用户目标完成？**  
答案：只能说明该工具定义的操作成功。还需要验证参数、业务对象、环境结果和用户目标。例如生成了报告文件，不代表报告内容正确或已经发送。

**题 3：把全部历史聊天保存进向量库，是否获得了可靠长期记忆？**  
答案：获得了存储与检索机制，还缺少信息抽取、冲突修订、适用范围、权限和删除策略。能够检索到旧结论，也可能造成使用过时结论。

**题 4：增加反思后成功率上升，能否归因于反思机制？**  
答案：不能直接归因。需控制模型、数据、运行预算和简单重试基线，并在独立任务上重复比较。也要检查反思是否得到新增外部证据。

**题 5：任务中途达到预算上限，应怎样返回？**  
答案：返回已验证结果、未解决事项、预算终止原因和可交接的状态。预算终止应与成功完成分别记录。

**题 6：研究员满意度提高，但事实错误率也提高，该不该上线？**  
答案：先回到产品目标和风险容忍度。满意度不等于事实质量，不能用更受欢迎的文字覆盖不可接受的错误。需要分开评估事实、遗漏、实用性和操作风险。

**题 7：只在熟悉公司的公告上效果好，说明什么？**  
答案：证明该数据分布内的效果，不证明跨公司泛化。检查别名、模板、规则和开发集泄漏，再按目标泛化层次设计未见样本。

**题 8：日志里最关键的三个连接是什么？**  
答案：请求与执行版本的连接、论断与原始证据的连接、动作请求与环境结果的连接。三者帮助分别解释为何运行、依据何物、实际发生何事。
