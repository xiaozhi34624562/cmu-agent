本课解决的问题是：模型知道某件事情应该怎样做，为什么仍然不能直接信任它完成一次查询、计算或写入？答案藏在三处边界里：模型是否选对动作，运行时是否正确执行，执行结果是否真的满足用户要求。工具使用需要把这三处分别设计、记录和评测。

贯穿案例是一位公司的内部助手。用户要求：“查询 A 公司最新季度收入，和上年同期比较；整理两句摘要，准备发给研究组。”这里至少包含资料检索、期间与口径核对、数值计算、文本生成和消息操作。模型可以负责理解与规划，但季度值、增长率和发送结果需要外部证据。下面的架构和例子是教学构造，不代表真实金融分析结论。

## 0. 工具课为什么先收尾 RAG

讲义先把 RAG 失败拆成检索侧、阅读侧和循环侧：没有召回证据、索引过期或权限泄漏；位置偏差、相似干扰和证据冲突；早期错误传播、没有停止条件以及提示注入。[L4，pp.4、13] 这和工具使用其实是同一条工程问题链：检索是一个外部工具，模型拿到返回后仍需判断其相关性、权限、时效与可信度。

第5—7页用长上下文与文档数量的图说明，“检索召回更高”不等于“最终答案更好”。图中的饱和位置依赖当时模型、数据和设置，不能把约10—20份文档当作所有系统的固定上限。第8—10页则提醒引用也是模型生成的：形式完整的出处可能并不支持附近陈述。自学时应把引用拆成存在性、支持关系和覆盖率检查，而不能只数引用个数。[L4，pp.5—12]

这引出本课的主问题：工具提供真实计算或外部信息，但谁来保证取对、用对、停对？后文从接口、训练、协议与评测四层回答。


## 1. 为什么工具接口也是模型能力的一部分

语言模型以 token 为单位预测后续内容。它可以生成“增长率是 18%”这段文本，但文本本身没有执行除法，也没有验证分母是不是上年同季度收入。把计算交给确定性程序，增加的是一条可检查的计算路径；把事实查询交给检索服务，增加的是模型权重以外的信息来源。Toolformer 的出发点就是让外部工具补足算术、事实检索、翻译和时间感知等短板。[R1，§1、§3]

工具不会消除所有错误。计算器可以准确计算错误的两个输入，搜索可以返回真实却过期的资料，数据库可以按照错误口径准确执行 SQL。于是，“工具调用成功”只说明执行器完成了给定操作，“任务成功”还需要证明操作及结果符合业务语义。

对一条要求“工具、参数、执行和结果使用都正确”的特定路径，可以用一条教学分解理解成功条件：

$$
P(S)=P(T)P(A\mid T)P(X\mid T,A)P(U\mid T,A,X).
$$

$T$ 表示选对工具，$A$ 表示在工具正确的前提下参数正确，$X$ 表示执行和返回满足预期，$U$ 表示最终使用结果正确。这里写的是条件概率链，不假设各阶段独立，也不是论文报告的测量公式。它提醒我们：四个环节任一处失败，最终都可能失败。不能用某一阶段的高分替代端到端验证。

## 2. 模型输出调用，应用程序执行调用

函数调用可以理解为一份结构化操作请求。模型生成工具名、参数和调用标识，应用程序解析并验证，获得权限的执行器调用实际服务，再把结果作为观察交回模型。真正的 API Key、数据库连接和文件权限由应用程序管理，不需要让模型拥有。

在贯穿案例中，模型先请求一个读操作：

```json
{
  "name": "get_financial_metric",
  "arguments": {
    "company_id": "company_A",
    "metric": "revenue",
    "period": "2026Q3",
    "reporting_basis": "consolidated"
  }
}
```

这只是教学协议，字段不对应任何供应商 SDK。服务端不能因为 JSON 能解析就直接访问数据：必须验证公司标识是否存在、调用者是否有权限、期间与指标是否受支持。返回中还应保留原始金额、币种、单位、报告期间和来源位置；否则模型看到一个孤立数字，容易把“万元”和“亿元”混在一起。

再把动作分成三层：模型**提出** `send_message`，编排器判断是否达到发送条件，连接器执行并返回服务端消息 ID。只有最后一层的确证才能支持“发送成功”。如果用户只要求准备内容，前两层不应自动扩大为发送授权。这是工程权限设计，不是让模型自行判断权限的提示词技巧。

## 3. 工具描述是一份面向不完美调用者的契约

人类后端开发者读接口文档时会利用代码、类型和项目经验；模型主要依赖当前可见描述。工具名过于相似、参数没有单位、异常只写“failed”，都会把选择和修复变成猜测。

一个有用的契约至少解释：何时调用、输入语义与约束、输出包含什么、哪些错误可恢复、是否有副作用。例子比含糊形容更有帮助。`get_revenue(company, date)` 不如说明 `date` 是报告期末还是公告日，`revenue` 是当季值还是年初至今累计值。若用户要同比，而接口仅返回累计值，工具应清楚表达这一点，模型才不会直接拿两个累计数当当季数比较。

工程上可以把验证分成四级：

| 验证层 | 可以发现的问题 | 仍不能证明的事情 |
|---|---|---|
| 语法 / schema | JSON 错误、必填字段缺失、类型不符 | 选中的指标符合业务问题 |
| 取值 / 权限 | 期间无效、公司不存在、调用者越权 | 资料口径与用户意图完全一致 |
| 执行 / 状态 | 超时、限流、事务失败、数据缺失 | 生成的结论有证据支持 |
| 任务 / 语义 | 期间、币种、引用和最终操作不匹配 | 对任意未来分布都可靠 |

不要把 schema 越写越长当作唯一办法。某些约束更适合在界面和服务端收窄，例如让模型只选择允许的 `metric_id`，而不是编写自由 SQL；让来源服务统一输出标准货币单位，而不是让每次模型调用自行换算。这样既减少动作空间，也让错误定位更直接。

## 4. Toolformer：用“工具结果是否帮助预测”筛选训练数据

Toolformer 关注如何训练模型学会何时调用工具。其方法不是把全部潜在调用都保留，也不是让人工给每个位置标注工具，而是先生成候选，执行它们，再用语言建模损失筛选。[R1，§2，PDF pp.2—4]

设原文本为 $x_1,\ldots,x_n$，候选调用出现在位置 $i$。模型通过少量工具示例生成候选调用 $c_i$，外部 API 返回 $r_i$。论文比较两类条件下预测后续 token 的加权损失：

$$
L_i^+=L_i(e(c_i,r_i)),\qquad
L_i^-=\min\{L_i(\epsilon),L_i(e(c_i,\epsilon))\}.
$$

$e(c,r)$ 表示调用与返回的文本表示，$\epsilon$ 是空序列。$L_i^+$ 使用调用及结果；$L_i^-$ 取“完全不调用”和“只看到调用、没有结果”两种基线中更好的那个。只有当

$$
L_i^- - L_i^+\geq\tau_f
$$

时才保留调用。$\tau_f$ 是过滤阈值；它要求工具返回真正提供额外帮助，而不仅是调用问题本身泄露了待预测答案。

例如原文后半句是“同比增长 20%”。候选计算器调用 `120 / 100 - 1` 的结果是 0.2，可能帮助预测正确数字；查询“这段话是中文吗”即使执行成功，也未必帮助预测后文。损失筛选因此提供一个自动化的“有用性”代理。

随后，留下来的调用及结果插回原文本，用标准语言模型目标微调。推理时模型生成到期待工具结果的位置，应用暂停解码、执行 API、插入返回并继续生成。[R1，§2]

这里有三个容易混淆的边界。第一，这是一个包含数据生成、筛选和**权重更新**的训练过程，不是每次调用工具都会自动训练。第二，训练信号是“更容易预测后续文本”，不是业务收益、事实正确率或操作安全。第三，论文使用的工具输入输出可表示为文本；它不直接解决跨系统权限、付款幂等和多步骤事务恢复。

## 5. 如何阅读 Toolformer 的对照实验

论文的基线包含原 GPT-J、在相同原文本上微调的 GPT-J + CC、工具增强文本上微调的 Toolformer，以及推理时禁用工具的 Toolformer。[R1，§4.1]

这几组对照回答不同问题：与原模型比较，观察整套训练加工具系统的变化；与相同文本的无工具微调比较，减少“只是额外训练了文本”的解释；禁用工具则帮助判断收益有多少依赖推理时真实 API。它们不能被合并成一个“所有任务都优于大模型”的结论。

论文以 CCNet 子集生成工具增强数据，并对不同工具使用特定筛选策略。其工具覆盖问答、Wikipedia 搜索、计算器、翻译和日期；这与企业内成千上万、文档不完整且权限不同的 API 环境仍有差距。[R1，§3—4] 因此，工程迁移更值得学习的是“执行候选并验证贡献”的数据构造思想，而不是照搬论文阈值。

尤其要看评测时的控制条件：该版本在下游评测中限制每个输入最多一次 API 调用，工具训练样本中的调用又是独立采样。这让“先查询日期，再用日期查询事实”这样的依赖链难以表达，原文也在时间任务分析中指出这一限制。[R1，PDF pp.6、8] 因而 Toolformer 的工具学习机制不能直接等同于一个可任意迭代、重规划的 Agent loop。它在开放 QA 上也没有全面超过 GPT-3，说明真实搜索质量和多轮改查能力仍然重要。[R1，PDF p.7，表 5]

若给内部助手做同类数据闭环，可以保存请求、候选工具、参数、真实返回和最终检查结果，比较“有工具结果”和“无工具结果”的性能。但这只是可行的实验设计；本讲没有运行模型训练，也没有证明损失下降能直接预测投研任务收益。

### 5.1 ToolkenGPT 与 ToolLLM：学习对象不同，不只是工具数量不同

讲义第32—35页介绍 ToolkenGPT：给工具增加可学习的 token 表示，模型预测到 toolken 时切换到工具参数生成模式，调用执行后再回到正常生成。它把“选择哪个工具”部分转移到工具表示的学习，而不是每次都把所有调用写成普通文本来生成。[L4，pp.32—35] 第34页图中的工具返回结果标为 `N/A` 并跳过相应结果位置的损失；该图是教学示意，不能把它直接当作完整训练代码，也不能从“只训练工具表示”推导出权限或事实可靠性保证。

讲义第37—38页的 ToolLLM 路线，则把大规模工具说明、指令与轨迹数据结合模型微调，并用工具检索器向当前请求推荐 API。第45页的比较表把四条路线并列：Toolformer用损失筛选构造调用数据；ToolkenGPT学习工具表示；ToolLLM使用调用轨迹与检索；Gorilla结合API文档与调用生成。[L4，pp.37—45] 这张表提供的是学习对象与监督来源的分类，不是统一任务、统一预算下的性能排名；各行工具规模与年份不宜混成同一场实验。

## 6. Gorilla：当工具多到放不进上下文，先检索文档再生成调用

Toolformer 的工具集合较小，而 Gorilla 研究大量、功能重叠、还会变化的 API 文档。其核心思路是把 API 文档放在外部库中，检索候选文档，再让经过训练的模型结合请求和文档生成调用。[R2，§3，PDF pp.3—5]

在数据构造中，研究者收集模型中心的 API 文档，并用自指令方法生成自然语言请求与 API 的配对。检索感知训练在输入中加入参考 API 文档，帮助模型学习“请求中描述目标，文档中提供具体接口细节”的用法。推理时，更新文档库可以向模型提供新的参数或版本信息，避免完全依赖权重里记住的旧接口。

把它迁移到内部系统，接口库不宜只是几段自然语言描述。最好保存工具 ID、版本、支持业务、输入输出 schema、权限、单位、示例、弃用状态和可调用环境。检索出来的候选还要经过确定性的权限和版本过滤；模型只在可用集合中选择。

但检索也会引入新错误：如果取到旧版或相似接口，模型可能非常自信地使用错误文档。Gorilla 的原文也指出，加入检索并非总能提高表现。[R2，§3.2、§4] 因此需要把错误分成“正确工具没召回”“召回了但选错”“选对但参数错”，而不是统一叫工具幻觉。

### 6.1 AST 匹配评测了什么

Gorilla 使用 API 调用的抽象语法树子树匹配来检查调用身份和指定参数，并把不属于 API 数据库的调用定义为一类幻觉；调用存在但选错或参数错误则是另一类错误。[R2，§3.3，PDF pp.5—6]

这比简单比较字符串更合理，因为换行或无关格式不应该改变接口身份。但它不是通用业务语义验证器：未匹配的可选参数、权限、远端数据和外部副作用还需要其他检查。原文聚焦单个 API 调用生成，也明确说实际执行系统不是主要研究重点。

此外，本课所复用的 Gorilla PDF 是 arXiv v1，文内 API 数量在若干位置存在不一致。学习机制时不应把不同位置的清单数字拼成统一总数；若要复现实验，需要回到具体版本的数据代码和划分。本讲不复述这些互不一致的总数，也不把当年的模型对比当作当前选型排名。

**讲义与归档版本的边界**：L4第42页把检索感知训练概括为加入正确和错误检索上下文以增强鲁棒性；本地Gorilla v1的§3.2和§4表2明确描述的是带oracle参考文档的训练，以及不同测试检索器的比较。因此，本讲只据该归档确认“训练时学习使用参考文档、测试检索质量显著影响结果”，不把“混入错误文档的训练配方已由该版本验证”写成确定事实。若复现第42页的更强表述，还需另行核对其具体后续版本和代码。

## 7. MCP：统一连接协议，让调用能力可以被不同应用复用

官网指定的是 MCP 规范的 **2025-06-18** 修订版。其概览使用 JSON-RPC 2.0 描述消息，区分 host、client、server，并定义能力协商、resources、prompts 和 tools 等概念。[R3，Overview、Key Details]

可以把 host 理解为承载助手的应用，client 是应用内连接某服务的连接器，server 暴露上下文或能力。企业文档系统不必分别为每个助手做一套完全不同的“发现工具、说明参数、调用并返回结果”的接口适配。协议降低连接和互操作成本；业务工具仍需实现自己的访问控制、校验和错误语义。

resources、prompts、tools 的作用不同：resource 提供数据或上下文，prompt 提供可复用模板或流程，tool 暴露可执行函数。不要因为都能给模型信息，就把读取资源和触发操作合成一个模糊能力。读取一份公告和发布一条消息的权限与审计要求显然不同。

规范还强调用户控制、数据隐私和工具安全，并指出协议本身不能强制实现这些原则，实施者需要构建适当的授权与保护。[R3，Security and Trust & Safety] 这意味着接上 MCP 不等于工具可信，也不等于模型会选对接口；来自服务端的工具说明、外部文档和返回值仍可能是非可信输入。

**工程建议**：把身份、租户、数据权限和允许的操作绑定在服务端连接上下文，不接受模型通过普通参数自报“我已获授权”。对于写操作，应用程序记录用户授权范围、目标对象、待执行内容和结果，模型只提供计划与候选参数。

### 7.1 从 REST 到 MCP，并不意味着旧接口必须被重做

讲义第47—50页用三个层次解释互操作：HTTP/REST端点提供服务；函数调用schema让模型生成名字与参数；MCP在host与server之间统一发现与调用。它们可以叠加使用，例如MCP server内部仍调用已有REST API。不要把示意表中的“REST缺少机器契约”读成REST不能配OpenAPI，也不要把“每个新API都需重训”当作普遍结论：Gorilla的测试时文档更新就是一个反例。[L4，pp.47—50；R2，§4.2]

`tools/list` 的结果让客户端知道工具名称、说明和输入schema，`tools/call` 使用名称与参数执行，再把content数组交给host。它们分别解决“有什么”与“执行什么”，不自动解决“这次应该调用什么”。第53—54页是课堂简化示例，不能将其中所有字段，例如 `ttlMs`，视为2025-06-18规范的必填字段或通用缓存保证。[L4，pp.53—54；R3]

第55—56页的LMS示例还区分两段认证：agent到MCP server的inbound身份，和MCP server到LMS API的outbound凭据。两段凭据不能互相替代；连接器获准调用server，不代表它可继承server在LMS里的全部管理权限。生产实现仍需按当前用户、租户和操作映射权限。课堂FastMCP代码用于说明包装与认证位置，本讲没有安装或运行相应服务，也不将未验证的SDK示意当作部署配置。[L4，pp.55—56]

## 8. 工具评测必须从一次调用走到一条任务轨迹

一次调用是否选对函数，只覆盖了任务中的一个局部。真实助手会遇到参数补全、多工具依赖、检索不充分、错误恢复和用户补充条件。比较系统时应预先明确评测对象。

| 层级 | 例子 | 合适的检查 |
|---|---|---|
| 工具选择 | 应查财报，却选择新闻搜索 | 候选召回、工具选择正确率 |
| 参数构造 | 2026Q3 当季收入被写成年初至今 | 参数与口径断言 |
| 返回解释 | 单位为千元却按元报告 | 归一化、计算复核和证据绑定 |
| 多步任务 | 比较两期数据后生成摘要 | 最终目标、顺序依赖与状态检查 |
| 有副作用任务 | 准备草稿被误执行为发送 | 授权与副作用审计、终态检查 |

构造任务时应保留“无需调用”“当前没有合适工具”“参数不足需澄清”的例子。如果所有样本都有且只有一个正确工具，系统可以学会每次强行调用，却在现实环境中更不可靠。拒绝、澄清和明确说明缺失证据都是合法结果，但要与真实完成区分。

### 8.1 BFCL、ToolBench、τ-bench各自把哪种错误放进测量范围

BFCL在讲义第59—60页覆盖AST离线匹配、执行和多步状态评估，并区分多个候选函数、可并行调用以及无相关函数的情况。无合适工具时不调用，是能力的一部分，不应为了调用率强行制造动作。[L4，pp.58—60] 此处使用讲义给出的分类；第58页的榜单截图是历史快照，不是本轮获取的实时模型排名。

ToolBench/ToolLLM把评测推进到现实API及多步骤指令，工具可用性和远端变化也会影响结果；讲义第61页标题和正文使用不同的API规模口径，本讲不将它们强行相加或当作同一个版本统计。[L4，pp.61—62] τ-bench则把工具、Agent、用户交互和领域政策放在一起：既要完成数据库终态，也要遵守服务规则，并在需要信息时与用户交互。[L4，pp.63—67] 所以单次调用格式正确、轨迹最终状态正确、交互政策正确，是不同的评估维度。

### 8.2 pass@k和pass^k：一次碰对与重复可靠是两个目标

讲义第64页对同一任务的 $n$ 次尝试中有 $c$ 次成功，给出不放回抽取 $k$ 次的估计：

$$
\widehat{\mathrm{pass@}k}=1-\frac{\binom{n-c}{k}}{\binom nk},\qquad
\widehat{\mathrm{pass}^{k}}=\frac{\binom ck}{\binom nk}.
$$

前者问“$k$次中至少一次成功”，后者问“$k$次全部成功”，最后还需按任务求平均。要求 $1\leq k\leq n$，不足以抽出的组合数按0计；它们不能简单互换。[L4，p.64]

教学例子：$n=10,c=8,k=2$，至少一次成功为 $44/45\approx97.78\%$，两次全成功只有 $28/45\approx62.22\%$。若改成独立同分布、每次成功概率 $p=0.8$ 的新尝试，才有 $1-(1-p)^2=0.96$ 与 $p^2=0.64$；有限样本不放回估计和iid近似的条件不同。这些算术已用Python标准库离线执行[计算脚本](examples/metrics.py)，运行记录见本课 [EXAMPLES.json](EXAMPLES.json)，没有调用模型或复现τ-bench。

对研究助理，“让模型试两次后人工选一次”与“每天无人值守地稳定处理同一类任务”对应不同目标。更高pass@k可能用更多预算搜到一个好结果，但部署需要可靠的结果选择器；如果没有可验证成功的机制，不能自动把多次尝试里的正确答案挑出来。

## 9. 重试、超时与幂等：工具失败不等于重新生成一次就好

只读查询超时通常可以在预算内重试，写操作超时却可能意味着“服务端完成，客户端没收到回执”。这两种情况如果都被模型理解为“失败了，重新执行”，就可能重复发消息或重复创建任务。

教学状态机可以包含 `proposed → validated → authorized → dispatched → confirmed`，以及 `failed`、`outcome_unknown`。`outcome_unknown` 不能直接回到 `dispatched`，应该先查询服务端状态，或者用业务幂等键合并重复请求。这是分布式系统中的执行问题，不能仅靠模型承诺“只执行一次”。

幂等键应由应用根据会话任务、业务对象和操作版本生成。若用户修改了内容，再次发送可能是新操作；因此不能把所有相同文本或所有相同用户的写入粗暴去重。对需要补偿的操作，还要说明撤回、删除或人工处理的可用条件。

幂等键还需要完整的执行契约：在第一次发送前持久化操作 ID 和参数摘要，网络重试与进程恢复复用同一个 ID；服务端拒绝“同键不同参数”，并将去重记录与业务效果原子关联。只有客户端写一条 `sent=true`，无法消除“远端已发送、本地尚未记账就崩溃”的窗口。还需核对服务端去重记录保留多久；过期后重复提交可能再次执行。若远端既不支持幂等，也无法按操作 ID 查询，未知结果应保留为待核实状态，不能声称实现了 exactly-once。[工程推导，承接 L4，p.67 的恢复失败]

错误返回也应让修复有依据：`invalid_period` 应说明支持的期间格式；`permission_denied` 应阻止盲目重试；`rate_limited` 应携带可用的退避提示；`not_found` 应与“空结果”区分。这些是工程设计例子，不是 MCP 要求的统一业务错误码。

## 10. Trace 应该记录到什么程度

能定位根因的 trace 至少要关联请求、模型与提示版本、候选工具集合、选中的工具版本、经过验证的参数、权限判定、执行开始结束、标准化返回、来源位置和终止原因。对于隐私数据，保存受控引用与必要审计信息，而不是把全部正文复制到多个日志平台。

当摘要数字错了，检查顺序应是：原始报告值是否正确；查询参数是否选对期间；工具返回是否带单位；转换和计算是否正确；最后才是模型是否错误转述。只有 token 数和最终错误答案的 trace 很难支持这条诊断链。

工程上还可以记录“调用意图”和“外部事实”的区别：模型说准备查询属于意图，服务端成功返回属于观察，数据库终态属于执行证据。三者用不同事件类型表达，避免失败分析模型把助手的自述当作已经发生的事实。

## 11. 成本与选型：何时值得把能力变成工具

工具成本包括模型生成参数的 token、工具说明的上下文、服务调用延迟、返回的文本量、错误恢复和外部 API 费用。一个工具虽然只需要几毫秒，返回几万字日志仍可能让后续模型调用昂贵且不稳定。

**工程建议**：优先把需要精确计算、受控数据访问、实时状态或可审计写入的动作做成明确工具。对于常见的组合操作，可以让服务返回紧凑、带来源的结构化结果；对探索性任务，则保留灵活的检索与逐步展开能力。是否合并工具取决于它是否经常一起使用、边界是否清楚以及失败能否定位。

工具过细会导致很多轮调用；工具过粗又可能隐藏状态、扩大权限并让错误变得难以修复。可以先建立一次普通请求的调用基线，再用真实失败样本决定是否新增复合工具或引入检索工具库。没有数据支持时，不必一次暴露所有内部接口。

## 12. 自测与答案

1. JSON 合法、工具返回 200，为什么仍可能任务失败？
2. Toolformer 为什么还要比较“有调用但没有结果”的基线？
3. 调用损失下降是否足以说明模型学会了安全地发送消息？
4. Gorilla 在推理时更新文档有什么价值，失败模式是什么？
5. MCP、函数调用和业务权限分别负责什么？
6. 一次发送工具超时，下一步应检查什么？
7. 查询收入的工具应返回哪些字段才能支持同比计算？
8. 如何区分“召回失败”和“模型不会使用工具”？

**答案**：

1. 语法和 HTTP 成功不检查指标、期间、单位、用户意图及最终状态；应增加参数语义和终态检查。
2. 排除调用文本本身就泄露预测信息的情况，要求真实返回带来额外贡献。
3. 不足。该代理目标服务于语言建模，不等价于授权、幂等或业务成功。
4. 提供权重之外的新接口细节；若召回旧版或错误接口，模型会受误导，应分开测文档召回与参数构造。
5. 函数调用表示模型提出的操作请求；MCP 规范应用与服务的互操作；业务权限由实际服务和应用策略执行。
6. 服务端是否已完成、是否存在回执/操作 ID、能否通过幂等键查询或重试，不能假定未收到响应就未执行。
7. 原始值、单位、币种、报告期、当季/累计口径、合并/母公司口径、来源版本和位置；比较前验证同口径。
8. 固定一个包含正确文档的候选集检查生成，再单独评测检索候选；必要时使用 oracle 文档对照，不能只看端到端分数。
