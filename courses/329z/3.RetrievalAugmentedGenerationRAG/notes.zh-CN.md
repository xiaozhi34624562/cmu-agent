## 1．先区分现代工程 RAG 与 2020 年 RAG 模型

今天工程中常说的 RAG，通常指“检索资料后，把资料作为上下文交给生成模型”的系统模式。它可以没有任何梯度训练，也可以接入关键词、向量、关系数据库、文件搜索或混合检索。

Lewis 等人的指定论文则提出了具体概率模型与微调方法：用 DPR 检索 Wikipedia 段落，用 BART 生成输出，把检索到的文档作为潜变量，对不同文档条件下的输出概率进行边缘化，并训练 query encoder 和生成器。论文中的 RAG-Sequence、RAG-Token，不等于今天任意“向量库加 Prompt”的实现。[A，§§1–2，PDF pp.1–4]

两者共享重要思想：参数知识与可检索的外部资料承担不同职责。权重提供通用语言和任务能力；外部库提供可检查、可替换的内容。修改文档库可以更新知识来源，但并不自动让模型正确服从新文档；更新检索索引也不等于重新训练模型。

在企业助手中，用户问“昨天”的公告，答案不应依赖模型是否曾在预训练中见过该公司。系统应能指出资料快照、公告版本和检索范围；若尚未取得正文，就说明缺口，而不是用模型记忆填补。

## 2．把一次回答拆成可诊断的数据流

一个基本 RAG 链路包含离线与在线两部分：

| 阶段 | 输入与产物 | 必须保留的检查点 |
|---|---|---|
| 获取与解析 | PDF、网页、邮件 → 可定位文本/表格 | 原文件、来源、日期、页码、解析版本 |
| 切分与标注 | 文档 → 检索单元 | 文档 ID、段落 ID、实体、期间、权限 |
| 编码与索引 | 检索单元 → 稀疏/稠密/多向量索引 | 模型版本、索引快照、更新状态 |
| 查询与过滤 | 用户问题 → 合法候选范围、检索请求 | 用户身份、时间口径、改写过程 |
| 召回与重排 | 候选 → 相关证据集 | 召回来源、排名、筛除原因 |
| 上下文组装 | 证据集 → 模型输入 | 去重、顺序、token 预算、出处 |
| 生成与核验 | 输入 → 回答和引用 | 论断支持、计算、缺失项、最终状态 |

这个分解是工程解释。它让问题从“RAG 不准”变成可调查的具体问题：正文是否有、证据是否切对、候选是否召回、重排是否删错、模型是否正确使用、引用是否支持论断。

应特别区分三个时点：原始资料何时发布，系统何时取得，索引何时更新。公告发布在昨天，不表示昨晚构建的索引一定已经包含；索引更新时间新，也不表示每个上游源都同步成功。

## 3．解析与 chunking：决定什么有机会成为证据

检索器看不到原始 PDF 的全部视觉语义。若解析把表格列打乱、把页眉接入正文，或遗漏“单位：万元”，后面再强的 embedding 也只能编码错误文本。因此，先检查原文件与解析结果之间的对应，而不是直接调相似度阈值。

一个适合公告资料的检索单元至少保留：

```json
{
  "doc_id":"ann-20261030-A-v1",
  "chunk_id":"ann-20261030-A-v1:p8:table2",
  "company_id":"A",
  "published_at":"2026-10-30",
  "period":"2026Q3",
  "page":8,
  "section":"资本开支计划",
  "unit":"万元",
  "text":"……",
  "source_sha256":"……",
  "acl_group":"research"
}
```

这里只是教学结构，不规定某个数据库 schema。关键是文字与身份、时间、单位和来源不能分离。对表格，可同时保留表题、行列标题和必要脚注；对跨页表格，要避免下一页数据没有列含义。对研究报告，发布日期与覆盖的财务期间也不是同一个字段。

### Chunk 大小的真正取舍

小 chunk 更容易精确匹配，也可能丢掉定义、否定词和表格上下文；大 chunk 保留语义关系，却增加噪声、编码损失和生成输入成本。重叠可以降低边界切断风险，但会产生重复候选和重复证据。没有对所有任务都最优的固定字数。

DPR 原文把文档拆成固定长度段落，并指出理想边界与 retriever、reader 都有关。Lewis RAG 的实验使用 2018 年 12 月 Wikipedia 快照和不重叠的 100-word 片段。这是其历史实验设置，不是中文财报的推荐参数。[B，§2 与脚注 3，PDF p.2；A，§3，PDF p.4]

内部助手可以按标题层级先切分，再对过长段落继续切分；涉及财务表格的证据单元保留完整行及列头。每次改变切分方式，重新评估证据召回、上下文大小与最终事实正确率，而不只看向量索引是否成功写入。

### 3.1 四种补足 chunk 上下文的办法

**Contextual Retrieval** 在索引前，为 chunk 生成简短的文档上下文，例如公司、期间与章节，再与原 chunk 一起编码或建立关键词索引。讲义用“收入环比增长 3%”示范：脱离公司和期间，这句话很难匹配准确问题。补充文字需要来自原文，并保留原始 chunk，不能把模型补出的解释冒充披露事实。该步骤增加离线生成与更新成本。[L，pp.26–29]

**Late chunking** 先用能处理较长输入的 encoder 编码整份文档，再按 chunk 范围聚合 token 向量，让每块表示已经包含更广的上下文。它与前一种方法的差别是上下文进入表示的时间和位置：前者增加文字，后者利用编码时的全局信息。它依赖编码器窗口、输出表示与分块聚合方式，不是普通短文本 embedding 后再简单拼接向量。[L，pp.30–31]

**RAPTOR** 从底层 chunk 开始编码、聚类、生成摘要，再编码摘要并继续向上构建树；查询可以在不同层级取得细节或主题性信息。资本开支具体数值适合回到叶子证据，跨年度项目演变可能受益于高层摘要。摘要会丢细节或带入生成错误，高层节点必须能回溯原文；树结构本身也不保证每个主题都被正确聚类。[L，pp.32–33]

**GraphRAG** 把实体、关系或社区摘要加入检索组织，帮助回答跨对象连接或全局主题问题。讲义展示图与社区结构，不能据此推出它能自动理解企业全部关系。需要额外承担实体消歧、关系抽取、摘要与更新成本；图上的关系仍需来源支持。[L，pp.34–35]

这四种机制可以组合，但应独立比较其收益。讲义 pp.29、31 展示的检索改善来自各自特定实验；本文未取得并逐篇复核这些外链工作的原始实验，因此不把图上的比例推广成企业问答的收益承诺。首要选择依据是问题需要局部事实、文档背景还是跨段关系。

## 4．BM25、稠密检索和混合召回分别解决什么

关键词检索关注词项匹配和统计权重。它对证券代码、产品名、专门术语、条款号和罕见字符串通常有直接价值。用户问“2026 年第三季度某公司可转债转股价调整”，这些精确词可能比宽泛语义相近更重要。

讲义 pp.41–42 用 BM25 解释词频饱和与文档长度归一化。其常见形式为：

$$
\operatorname{BM25}(q,d)=\sum_{t\in q}\operatorname{IDF}(t)\frac{f(t,d)(k_1+1)}{f(t,d)+k_1(1-b+b|d|/\overline{|d|})}.
$$

$f(t,d)$ 是词在文档中出现的次数，$|d|$ 是文档长度，$\overline{|d|}$ 是库中平均长度；$k_1$ 控制词频贡献的饱和速度，$b$ 控制长度归一化。词多出现一次不应一直等量加分，否则很长或重复文本可能占优。讲义使用 $\operatorname{IDF}(t)=\ln[(N-\mathrm{df}(t)+0.5)/(\mathrm{df}(t)+0.5)]$，$N$ 是文档数，$\mathrm{df}$ 是包含该词的文档数；常见实现可能采用加 1 等变体，数值不能跨实现直接比较。常见词在讲义这一 IDF 形式下可能得到负值，不是公式自动证明每个实现都会返回负得分。[L，pp.41–42]

稠密检索将查询和段落编码为向量，以相似度排序。DPR 使用分别编码问题与段落的双编码器：

$$
s(q,p)=E_Q(q)^\top E_P(p).
$$

文档向量可以离线计算，在线只编码查询并搜索索引，因此避免对全库每段都做复杂交叉计算。[B，§3.1，式 1，PDF pp.2–3]

它的价值在于学习“表达不同但语义相关”的匹配，例如“减少扩产预算”与“下调资本开支”。但压缩表示也可能弱化数字、否定、实体细节和长段落中的多个主题。高相似度不是事实相同，也不是文档支持当前结论的概率。

混合召回让关键词与稠密检索共同提供候选。融合可以采用排名而不是直接相加不可比较的分数。例如，教学形式的 reciprocal rank fusion 为：

$$
\operatorname{RRF}(d)=\sum_{r\in\mathcal R}\frac{1}{k_0+\operatorname{rank}_r(d)}.
$$

$\mathcal R$ 是检索列表集合，$k_0$ 是平滑常数，缺席项不贡献分数。这是一个可选工程策略，不是 DPR 或 Lewis RAG 的默认组件。调参应基于本地任务，不能照抄某个 $k_0$ 就认为完成融合。讲义第 49 页给出 $k_0=60$ 的示例；它使融合避免依赖各路原始分数的量纲，并不意味着候选深度、查询分层或融合配置永远无需评测。[L，p.49]

| 资料特性 | 可先建立的基线 | 必须单独检查 |
|---|---|---|
| 证券代码、条款号、专有名 | 关键词 + 精确过滤 | 别名、字符归一化和代码映射 |
| 同义改写、自然语言问题 | 稠密召回 | 领域语义、否定与数值 |
| 混合查询 | 关键词与稠密候选融合 | 两路贡献、候选重复、额外延迟 |
| 需要多个事实连接 | 分解查询、多轮检索 | 中间实体正确性、完整证据集合 |

## 5．DPR 的训练：相似度不是天然懂业务

DPR 从预训练 BERT 初始化两个编码器，再用问题与相关段落对训练检索关系。对一个问题 $q$、正段落 $p^+$ 和负段落集合 $p_j^-$，损失为：

$$
\mathcal L=-\log\frac{\exp s(q,p^+)}{\exp s(q,p^+)+\sum_j\exp s(q,p_j^-)}.
$$

这个目标提高正例相对于负例的分数。它学习的是给定训练分布中的相关性，并没有直接学会“公募公司某项指标的全部财务口径”。训练样例和负例如何定义，决定了什么差异被编码器重视。[B，§3.2，式 2，PDF p.3]

论文使用 in-batch negatives：一个 batch 中其他问题的正段落被用作当前问题的负例，并结合 BM25 找到的难负例。这样能复用计算，但也提醒我们注意假负例：另一个问题的正段落，可能恰好也能回答当前问题。金融资料中，不同报告重复披露同一事实，这类问题尤其常见。[B，§3.2，PDF pp.3–4；金融场景为工程推导]

如果要为内部助手训练检索器，至少区分：与问题完全无关的负例；同公司错期间；同期间错公司；同概念但不同单位；标题相关、正文不支持；旧版与更正版。只用明显无关段落作负例，可能让离线分数好看，却无法学会真实边界。

训练之前先量化收益空间。若正确段落根本不在索引中，训练 embedding 无法解决；若问题主要来自代码和日期过滤，规则修正可能更便宜。只有当语料、标注和评测稳定后，才有条件判断训练是否值得。

## 6．索引近似搜索与生成质量之间隔着一层证据

文档很多时，逐一计算精确向量相似度可能太慢，系统常用 approximate nearest neighbor 索引。HNSW 用多层图支持由粗到细的导航：上层帮助快速接近目标区域，底层精细搜索。它是近似搜索方法，不是提高 embedding 业务理解的训练算法。第 37 页以“约 log N 跳”作直观效率说明，不能把它当成对任意数据、过滤与参数的严格最坏情况保证。第 38 页的分层插入与跨簇连边图强调避免局部陷阱，但实际召回仍依赖图与搜索参数。[L，pp.36–38]

第 36 页还区分 IVF 与 PQ：IVF 把向量空间分区，只搜索部分邻近分区；PQ 将向量表示压缩为短码，降低存储与距离计算代价。两者分别引入搜索范围和表示近似的取舍，可以组合，但不等同于 HNSW 的图导航。选择时应同时看索引体积、构建/更新、过滤能力、查询延迟与召回。[L，p.36]

有两个不同的召回概念：**向量搜索召回**问近似算法是否找回精确向量搜索的近邻；**证据召回**问结果是否包含能回答问题的材料。前者提高，不保证后者提高，因为 embedding 本身可能把错误资料排得很近。

对企业助手，可以先用较小语料上的精确检索作为诊断基线。若精确向量检索也找不到证据，应优先查表示、切分和查询；若精确能找回、ANN 找不回，再查索引配置与过滤执行方式。这能避免一遇到答案错误就盲目调 HNSW 参数。

权限过滤还会改变候选空间。先对全库取很少的近邻、再过滤无权限项，可能导致结果不足；扩大候选又会增加成本。系统应使用支持目标过滤语义的检索路径，并在正文读取时复核授权。索引结构、过滤与删除是否同步，属于正确性问题，不只是性能问题。

## 7．为什么召回之后还需要重排

召回追求从大库中保留可能相关的候选，通常需要便宜和高覆盖；重排在较小候选集上投入更多计算，判断问题与段落是否真正相关。它们优化的阶段和预算不同。

Cross-encoder 将 query 与 passage 放在一起建模，可以通过 token 间交互捕捉细节，但无法像双编码器那样预先把每段压成一个固定向量后独立评分。若有 $K$ 个候选，就需要对这些候选投入联合建模成本。重排也只能在候选中选择；证据没被召回，不能指望重排凭空找回。

### ColBERT 的中间路线

ColBERT 不把整段文本压成单个向量，而是保留 query 和 document 的 token 向量，并在较晚阶段进行交互。其 MaxSim 思想可以写成：

$$
S(q,d)=\sum_{i\in q}\max_{j\in d}\langle \hat q_i,\hat d_j\rangle.
$$

对每个查询 token，在文档 token 中找最匹配的一项，再把匹配分数相加。文档表示可以预先计算，而多个 token 的细粒度匹配保留了比单向量更多的信息。这是 late interaction 的关键：编码阶段尽量可分离，评分阶段再组合。[D，§§3.1–3.3、式 3，PDF pp.4–5；L，pp.51–53]

它仍不是完整的 query-document cross-attention；最大匹配也不直接证明语义蕴含、否定或时间口径成立。ColBERT 原文把 query/document 送入共享 BERT 编码器，但用 [Q]/[D] 标记区分；输出投影并归一化后，点积等价于余弦相似度。其 query augmentation 与文档标点过滤也是具体设计的一部分，不应把简单保存任意 token embedding 就称为完整原版 ColBERT。[D，§3.2，PDF p.4]

多向量表示增加索引体积与检索计算，真正部署还要考虑压缩、候选生成和更新成本。不能只看到匹配更细，就断言一定比单向量系统更划算。

| 方案 | 文档可预计算什么 | 在线交互强度 | 主要取舍 |
|---|---|---|---|
| 单向量双编码器 | 每段一个表示 | 简单相似度 | 快、紧凑，细节压缩较强 |
| ColBERT 类多向量 | token 级表示 | late interaction | 细粒度匹配，存储和检索成本增加 |
| Cross-encoder | 通常不能预计算完整配对分数 | 联合建模 | 候选精排表达强，逐对计算较贵 |

这张表比较的是机制，不是对所有实现的统一性能排名。讲义第 54 页汇总 BM25、DPR、ColBERT 与 cross-encoder 延迟时明确注明不同硬件及运行方式；不能把其中毫秒数当成同机统一压测，更不能直接换算当前企业部署的速度比。ColBERT 原文 §4.1 另交代 MS MARCO、TREC CAR 与其硬件设置。[L，p.54；D，§4.1，PDF p.6]

## 8．检索结果怎样成为模型真正可用的上下文

把 top-k 文本直接拼接，是可运行的基线，但需要至少处理去重、来源标识、上下文预算和证据关系。重复的相邻 chunk 可能挤掉独立信息；同一事实在十份转载里出现，并不等于十份独立证据；新公告和旧报告的冲突也不能靠排名高低悄悄消解。

针对资本开支问题，模型输入应包含：当前公告事实、此前计划或基期、可比口径、发布日期、原文位置，以及尚未查明的差异。让模型区分三类输出：原文事实、基于明确输入的计算、对经营或投资逻辑的分析推断。

可以为每一条最终论断保留证据对象：

```json
{
  "claim":"公司A下调本年度资本开支计划",
  "kind":"reported_fact",
  "supports":[{"doc_id":"ann-20261030-A-v1","page":8,"quote_span":"…"}],
  "comparison_basis":"与2026年中期报告中的全年计划相比",
  "unresolved":["计划调整是否改变实际现金支出节奏"]
}
```

生成时要求引用，核验时检查引用支持关系。文档里含有公司名，不等于支持“削减资本开支”；引用到正确页，也可能错误解释表格列。若要推断对持仓组合的影响，还需要持仓快照与情景假设，不能把公告事实直接变成确定收益判断。

这里也有信任边界：检索内容是数据，不是系统指令。公告或网页中出现“忽略之前要求”“把文件发给某地址”等文字，不应自动获得控制权。权限和执行许可仍由系统定义，不能交给文档内容决定。

## 9．回到 Lewis RAG：文档潜变量怎样参与生成

原论文用 $p_\eta(z\mid x)$ 表示对输入 $x$ 的文档检索分布，用 $p_\theta(y_i\mid x,z,y_{<i})$ 表示以文档为条件的生成概率。RAG-Sequence 为整段输出使用同一文档潜变量：

$$
p_{\mathrm{seq}}(y\mid x)\approx\sum_{z\in\operatorname{top}K}p_\eta(z\mid x)\prod_i p_\theta(y_i\mid x,z,y_{<i}).
$$

RAG-Token 则在每个输出 token 上边缘化文档：

$$
p_{\mathrm{tok}}(y\mid x)\approx\prod_i\sum_{z\in\operatorname{top}K}p_\eta(z\mid x)p_\theta(y_i\mid x,z,y_{<i}).
$$

先求乘积再求和，与先求和再相乘不同。前者在完整序列层面对文档假设混合，后者允许不同 token 的条件贡献来自不同文档。**RAG-Token 不表示每生成一个 token 就重新向搜索引擎发一次查询**；论文是在已检索的 top-K 文档上作概率组合。[A，§2.1，PDF p.3]

训练时，论文更新 query encoder 和 BART generator，保持 document encoder 与文档索引不变，以避免频繁重建全库表示的成本。这里“端到端训练”不等于所有组件、所有参数都更新，也不等于离散 top-K 操作变成了普通可微排序。[A，§2.4，PDF pp.3–4]

这些细节对现代系统的启示是：检索和生成要协同评估；检索分数不是终局目标；索引更新与编码器版本必须一致。如果换了文档 embedding 模型却继续使用旧向量，query 与 document 可能已不在同一表示空间，检索质量会悄悄下降。

## 10．实验能说明什么，不能说明什么

原 RAG 论文的 Wikipedia 知识源、BART/DPR 初始化、任务训练和指标，都与今天直接调用通用对话 API 的企业系统不同。其 NQ 测试表中，DPR 的 EM 为 41.5，RAG-Token 为 44.1，RAG-Sequence 为 44.5。这说明该论文设置下检索与生成结合取得了更高任务分数，不说明任意资料库接入 RAG 都会增加同样的百分点。[A，§3、表 1，PDF pp.4–6]

更不能从这组比较单独推断“收益完全来自生成替代抽取”。系统的初始化、训练和推理方法一起变化，需要对应消融才能作更细归因。论文还分析了生成的事实性、特异性和知识库替换等问题；这些结果应分别回到其任务、样本和评估方式，不能合并成一个通用“幻觉降低率”。

DPR 论文主要研究开放域抽取式 QA 的检索，关注答案段落是否进入 top-k 和下游 reader 的效果。表 2 中 DPR 在五个数据集中的四个优于 BM25，SQuAD 是例外；作者将此与问题编写时可见原段落、词面重合及数据分布偏窄联系起来。讲义第 48 页的“1,000 对即可超过 BM25”具体来自 Natural Questions 开发集上的样本效率实验，编码器已使用预训练 BERT，不能理解为任意领域都只需一千条数据。企业部署仍需以真实语料、查询和成本重新比较。[L，pp.47–48；B，§§5.1–5.2、表 2、图 1，PDF pp.5–6]

## 11．什么时候从单轮 RAG 升级到 Agentic RAG

用户的问题若可以一次检索取得完整证据，单轮链路简单、延迟较低，也更容易回放。多轮 Agentic RAG 的价值在于：读取结果暴露新的问题，系统据此修改查询、查找缺失证据或验证冲突。

对资本开支案例，第一次搜索得到“本年计划调整”；读取正文发现比较口径是“已签约项目”，与上一份报告的“现金支出”不同。这时下一步不应直接相减，而应查定义、读取旧报告脚注，必要时说明不可比。这里的多轮行动由证据缺口驱动，而不是为了显得更智能而固定循环三次。

一个受控循环可以维护：已知事实、需要验证的子问题、已读取文档、已用查询、证据冲突和剩余预算。每轮新增观察后，选择读取、改写查询、分解子问题、计算、结束或交接。无新证据、来源不可得或预算到顶时，返回可定位的缺口。

### Self-RAG 与 CRAG：反馈放在哪里

讲义第 57 页的 Self-RAG 图将“按需检索 → 针对候选证据生成片段 → 评价相关性与支持程度 → 选择较好片段并继续”连接起来。重点不是在报告末尾多加一句“自我反思”，而是让检索与候选选择实际受到反馈影响。评价器仍会出错，需要独立检查它的判断与任务结果是否一致。[L，p.57]

第 58 页的 CRAG 将检索结果评价为较可靠、含糊或不可靠，再选择保留内部资料、补充外部搜索或组合两者。对内部助手，不能机械地把“外部搜索”当作总能解除不确定性：外部源也可能过期、没有权限或与内部口径不同。评价错误会触发错误分支，因此应保存评价依据、路径与最终证据。[L，p.58]

本段按讲义图解释机制和工程含义；没有宣称逐篇复现 Self-RAG/CRAG 论文的训练与实验。下面的 Search-R1 则补充了已归档一手论文，进一步解释模型策略如何通过结果反馈更新。

### Search-R1：优化的是带搜索的行为，而不仅是检索分数

补充一手论文 Search-R1 将搜索引擎放进模型的训练 rollout。模型生成查询，运行框架执行搜索，将检索文本插入上下文，模型继续生成，直到给出答案或动作预算耗尽。这里更新的是选择查询和组织后续生成的模型策略；并不是每轮检索后在线修改索引或 retriever 权重。[E，§§3.1–3.3、算法 1，PDF pp.3–6]

训练轨迹中同时有模型生成 token 和外部检索 token。搜索结果是环境观察，不是模型采样的动作，因此论文把检索 token 从 policy-gradient 损失中屏蔽，KL 计算也作对应屏蔽。模型可以根据检索结果作决策，但不把这段外部文字当成模型自己生成的序列去直接优化。这个区别类似强化学习中“动作由策略产生，观察由环境返回”的边界。[E，§3.1，PDF pp.4–5]

论文的奖励使用最终答案与参考答案的 Exact Match，不另加格式奖励，也没有以一个新的神经奖励模型替代最终规则检查。其训练合并 NQ 和 HotpotQA，检索使用 2018 年 Wikipedia 与 E5，每次返回 3 个段落，并在七个 QA 数据集上评价。把这一方法迁移到晨会材料时，困难在于最终报告没有同样简单的精确匹配答案：需要另行设计事实、证据、遗漏与成本的反馈，不能照搬 EM 就得到可靠训练目标。[E，§3.4、§§4.1–4.3，PDF pp.6–7]

本地 v5 的摘要与 Introduction 对 7B 平均相对改善的概述数字并不一致，本文不引用一个脱离比较基线的统一提升百分比。方法与实验需要按具体表格、模型和设置核查。本文没有训练或复现 Search-R1；它在这里用于解释“提示一个模型去搜”和“通过反馈训练搜索行为”的差别。

Self-RAG 等其他方法也讨论是否检索及如何使用反思信号，但不能因此把不同算法合并为同一种控制器。未实现对应训练和反思机制时，应把自己的系统描述为实际具备的检索循环。

## 12．一套能定位根因的评测设计

讲义 pp.45–46 的指标分别回答不同问题。给定相关证据集合 $R_q$：Hit@k 只检查 top-k 中是否至少有一个相关片段，Failed@k 为其补集；Recall@k 衡量全部已标注相关片段找回多少；MRR@k 关注第一个相关结果的倒数排名，top-k 内没有则为 0；nDCG@k 将相关性按位置折扣并用理想排序归一化。讲义 DCG 使用直接相关性增益，不同工具也可能使用 $2^{\mathrm{rel}}-1$，应固定实现再比较。[L，pp.45–46]

一个教学例子：问题需要两份证据，只召回其中一份且排第一，则 Hit=1、MRR=1，但 Recall 只有 0.5；它仍不足以完成跨期间比较。若相关性标注为空，Recall/nDCG 等如何处理也要预先规定，不能任由评测库隐式决定分母。

只看最终回答分数，会把数据、检索和生成错误混在一起。建议准备带来源标注的任务集，并分层测量：

| 层次 | 问题 | 可用指标或检查 |
|---|---|---|
| 资料覆盖 | 所需文档是否已取得且正确解析 | 文档覆盖、字段/表格抽查 |
| 候选召回 | 需要的证据是否进入候选 | Evidence Recall@k、分类型召回 |
| 排序 | 关键证据是否靠前 | MRR、nDCG，需明确相关性标签 |
| 证据组装 | 输入是否包含完整条件且无冲突混用 | 支持集合覆盖、重复率、token 数 |
| 回答 | 事实、计算和推断是否正确区分 | 事实准确率、引用支持率、缺口披露 |
| 系统 | 是否可稳定且合规地运行 | 延迟、费用、更新滞后、权限测试 |

多跳问题需要检查证据集合，而不只是“至少一段相关”。例如同时需要本期计划和旧计划，检索到其中一份并不足以计算变化。可将任务要求的证据集合记为 $G$，检索集合记为 $R_k$，用 $|G\cap R_k|/|G|$ 衡量集合覆盖，但标注本身也需要审核；不能用答案字符串出现与否替代所有证据判断。

做一个重要的诊断对照：给生成器人工核实的正确证据。如果此时仍答错，优先检查理解、计算、指令以及证据本身是否充分；若正确证据下表现良好，而真实检索下变差，再查解析、召回、重排与组装。这个 oracle-context 对照帮助定位，不代表真实上线会得到完美证据。也不能把差值全部归因于召回：人工证据通常更短、干扰更少。进一步保持上下文长度与顺序，分别补入缺失证据、移除干扰、修正表格解析，才能区分“没找到”与“找到了却没用好”。[工程诊断设计]

## 13．成本与更新：RAG 的账不只在生成 token

总成本包括资料获取、解析、embedding、建索引、存储、更新、在线检索、重排、生成和核验。新文档量大、修订频繁或权限变化多时，离线更新成本可能显著；查询量高时，在线重排与上下文 token 更重要。

改变 embedding 模型通常需要考虑文档重编码和索引重建；改变 chunk 边界会影响文档 ID、引用定位和评测标签；原文更正后，需要让旧版证据可追溯，同时避免新请求无意继续使用失效内容。不要只替换一个向量字段，却忽略其引用和版本关系。

资料库可以维护“原始文档版本 → 解析版本 → chunk 版本 → embedding/index 版本 → 回答使用快照”的链条。它的用途是回答“当时为什么得到这个结论”，不是把所有步骤都变成难以维护的重复副本。高频、低变化资料可评估复用和缓存；动态权限与时效仍要在命中缓存时检查。

对内网有限算力场景，可先用关键词/过滤与通用 embedding 建立基线，再根据任务难度选择重排。多轮检索只在证据缺口明确的任务上启用，并设置预算。模型更换、索引更新和重排配置改变，都应触发相同回归任务，而非只重跑一两个演示问题。

索引升级还需要发布契约：先在新快照中完成解析、编码和检索回归，再把兼容的 query encoder、chunk schema 与索引版本作为一组切换；运行中的请求固定使用同一组版本。保留旧组可以回滚质量退化，但不能回滚已经撤销的权限或必须删除的数据。权限判断应使用当前授权状态，删除应覆盖正文、索引、摘要和缓存；“可复现旧答案”不等于允许继续向用户提供被撤销的内容。这是从讲义陈旧索引与权限泄漏问题推导的部署方案，不是原 RAG 论文提供的现成实现。[L，p.63；工程建议]

## 14．故障诊断与最小修正

| 症状 | 最可能先检查的环节 | 验证方法 | 修正方向 |
|---|---|---|---|
| 库里明明有资料却找不到 | 解析、切分、过滤、索引版本 | 直接按文档 ID 读取，比较精确检索 | 修候选空间，再调表示 |
| 召回很多同公司旧报告 | 时间与版本口径 | 比较发布日期、期间与失效标识 | 明确时点过滤和更正版关系 |
| 找到表格但算错变化 | 单位、列头和基期 | 回看原页并重算 | 结构化表格与确定性计算 |
| 相关段落被重排丢掉 | 重排标签或上下文不足 | 保存重排前后名单 | 加入难例，调整候选/截断 |
| 引用正确文件但不支持论断 | 语义支持关系 | 逐条 claim-evidence 核查 | 限制无据推断，披露缺口 |
| ANN 参数越大，答案仍错 | embedding 或数据问题 | 精确向量检索对照 | 停止只调索引搜索参数 |
| 多轮搜索越查越偏 | 中间实体或假设错误 | 审查每轮子问题和新增证据 | 校验中间状态，加入终止条件 |
| 删除资料后仍能被看到 | 索引、缓存和权限同步 | 按用户身份验证读取路径 | 处理所有派生副本与缓存 |

## 15．自测与答案

**题 1：现代工程 RAG 一定需要联合训练检索器和生成器吗？**  
答案：不需要。通常可以通过外部检索和上下文拼接构建；Lewis 2020 论文提出的是具体可训练概率模型，需要与广义工程模式区分。

**题 2：DPR 的向量相似度高，是否等于证据支持概率高？**  
答案：不等于。它是训练得到的排序分数，仍可能忽略实体、时间、否定或口径差异。

**题 3：把 chunk 缩小一半，一定能提高检索准确率吗？**  
答案：不一定。可能提高局部匹配，也可能切掉定义、单位和上下文；应同时检查证据召回与最终回答。

**题 4：提高 ANN 的近邻召回率，为什么任务证据召回仍可能不变？**  
答案：ANN 只是更接近 embedding 空间的精确近邻；如果表示把错误材料排在前面，精确找到它们也无法改善证据质量。

**题 5：ColBERT 与普通双编码器的关键差异是什么？**  
答案：保留 token 级多向量并进行 late interaction，而不是把整段只压成一个向量。它增加细粒度匹配能力，也带来存储与检索成本。

**题 6：RAG-Token 是否每生成一个 token 就重新搜索？**  
答案：不是。原模型在已检索 top-K 文档上，对每个 token 的条件概率作文档边缘化。

**题 7：原始 RAG 训练为何固定 document encoder？**  
答案：更新文档编码器会要求持续更新大规模文档索引；论文保持其固定，只微调 query encoder 和生成器，并报告该设置能取得较好效果。

**题 8：什么情况下值得启用多轮检索？**  
答案：当读取证据后出现影响下一步查询的缺口、冲突或新实体。若一次检索已取得完整证据，额外轮次可能只增加成本和错误机会。

**题 9：报告引用到了正确页码，能否免除事实复核？**  
答案：不能。还需要检查原文是否支持论断、表格列与单位是否正确、推断是否超出证据。

**题 10：怎样区分检索问题和生成问题？**  
答案：将真实检索上下文与人工核实的正确证据作对照；结合解析、召回、重排和生成的分层记录定位，而非只比较最终文字。
