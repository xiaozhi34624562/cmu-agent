## 0. 课程与阅读材料的关系：不是三个模块，而是一条反馈链

### 0.1 讲义的主线

Lecture 04 第 3 页列出 Agent loop、Tool designs、Context management，并在 Context management 下讨论 Prompt engineering 与 Context engineering。第 7 页强调：模型与循环、工具与护栏、上下文与记忆，共同围绕一个上下文窗口运行，必须一起设计。第 25 页进一步提出：工具设计就是上下文设计。〔[L04，PDF pp. 3–7、25](#ref-l04)〕

可以把全课概括为：

```text
用户目标与约束
    ↓
组装当前上下文
    ↓
模型判断：已经知道什么，还缺什么，下一步做什么？
    ↓
提出工具调用
    ↓
程序检查参数、权限与执行条件
    ↓
工具执行，产生环境反馈
    ↓
保存原始事件，更新工作状态，选择下轮需要的信息
    ↓
继续行动，或提出完成声明并接受验证
```

这里每一个箭头都可能失败。例如，检索到正确文件但读取的是旧版本；参数合法却使用错误业务口径；写入成功但没有完成用户目标；摘要很短却把猜测升级成事实。

因此，本课关注的不是“给模型加多少功能”，而是**信息和状态在这条链上是否正确传递**。

### 0.3 两个贯穿全文的任务

**编码任务，假设案例：**提交订单超时后重试，偶尔出现重复订单。要求定位与修复，不改变公开 API，补充回归测试。

**文档核验任务，假设案例：**检查材料中的业绩表述是否得到指定数据源支持，输出原文位置、核验依据、差异与待补充信息。

前者体现“修改后状态不断变化”；后者体现“原文、数据口径、历史证据必须可追溯”。两者都会用到工具与上下文，但不能机械使用同一种裁剪规则。

## 1. Agent Loop 与 ReAct：把历史整理成下一步可用的状态

### 1.1 最小循环与 Harness 的责任

讲义第 5 页的最小循环包括：调用模型、保存模型响应、执行请求的工具、附加工具返回值、继续调用，直到模型给出最终答案或达到步数上限。第 6 页把工程师的职责标在这个循环上：编写工具定义、组装上下文、校验请求与权限、执行工具，以及必要时处理结果和管理上下文。〔[L04，PDF pp. 5–6](#ref-l04)〕

模型不负责直接执行数据库、操作系统或远程服务中的操作。它输出调用请求，外部程序执行。这一区分也是 R15 对 Agent loop 的解释重点。〔[R15，Agents are a loop／LLM 101](#ref-r15)〕

**工程推导：**即使模型不变，改变工具描述、结果格式、状态组织与停止规则，行为也会改变。原因不是系统神秘地增强了模型，而是模型每一步面对的问题与反馈不同了。

### 1.2 ReAct 的形式化：为什么“推理”也进入动作空间

先把记号接到熟悉的循环：$t$ 是当前步，$o_t$ 是这一步得到的观察（如工具返回值），$a_t$ 是准备采取的动作；$c_t$ 汇集截至当前的交互历史。策略 $\pi$ 表示“给定历史，各种动作被选择的概率”；$\mid$ 读作“在……条件下”，$\sim$ 读作“按这个分布选择”。这与程序根据状态选择分支类似，只是这里由模型给出选择。原论文令上下文为：

$$
c_t=(o_1,a_1,\ldots,o_{t-1},a_{t-1},o_t)
$$

Agent 根据策略选择动作：

$$
a_t\sim\pi(a_t\mid c_t)
$$

困难在于，从原始历史到正确动作之间，常常需要大量整理与判断。因此 ReAct 将动作空间从外部动作集合 $A$ 扩展为：

$$
\hat A=A\cup L
$$

这里 $A$ 是允许的外部动作集合，$L$ 是自然语言空间，$\cup$ 表示合并两类可选动作，$\hat A$ 是扩展后的集合。论文称其中的语言动作是 thought 或 reasoning trace。它不直接改变外部环境，而是提取信息、分解目标、跟踪进度、处理异常，并把这些内容加入上下文，为后续行动提供依据。〔[R01，§2，PDF pp. 3–4](#ref-r01)〕

这就是本课与 ReAct 最深的连接：**推理过程的一部分工作，是把“发生过什么”整理成“接下来怎么做”。**

在编码例子里，“已经定位到重试逻辑，但还没有确认首次请求是否提交成功”比“我需要仔细研究这个问题”更有作用。前者明确了下一项证据缺口，后者只是语气。

### 1.3 原论文实例：Apple Remote 与 Front Row

ReAct 第 2 页 Figure 1 给出一个多跳问题：Apple Remote 最初控制的程序，还可以通过什么设备控制？有效轨迹先查 Apple Remote，得到中间实体 Front Row；搜索 Front Row 没有直接命中时，根据候选项改查软件条目；最后找到键盘功能键这一答案。〔[R01，Figure 1，PDF p. 2](#ref-r01)〕

这个例子不是“多搜索三次”那么简单。它包含实体发现、消歧、失败解释和答案提取。第二次查询在第一次观察之前尚不能准确确定，第三次查询又依赖第二次工具的失败反馈。

因此，Agentic search 与一次性 RAG 的重要差别是：**检索问题本身会根据已获得的证据变化。**

工具的“未命中”消息如果附带相关实体，模型有机会恢复；只有一个 `not found`，则需要它自行猜测失败原因。这说明工具错误设计已经参与了推理过程。

### 1.4 稀疏推理与密集推理：ReAct 不是固定文字仪式

论文在知识问答中使用较密集的推理—行动交替；在 ALFWorld 等较长决策任务中，允许推理只在关键位置出现，用于分解目标、判断子目标完成、选择下一阶段和进行常识判断。〔[R01，§2、§4，PDF pp. 3–4、7–8](#ref-r01)〕

所以，不能把 ReAct 简化成“每次工具调用之前都必须输出一大段思考”。有效性取决于信息处理，而不是某个标签是否出现、文字是否足够长。

**工程推导：**当新观察没有改变决策问题时，不一定需要重新展开全局计划；当观察推翻了关键假设时，必须更新工作状态。可观察的计划、证据缺口和行动理由，可以用于调试；不应把模型输出的解释当成完整、必然忠实的内部计算记录。

### 1.5 原论文结果：增加反馈改变失败类型，并不保证所有任务都更强

先认清表中的比较对象：Standard 直接作答；CoT 先生成中间推理再作答；CoT-SC 对多条推理采样并对答案投票（该实验使用 21 条）；Act 使用外部行动但没有显式推理轨迹；ReAct 交替使用推理与行动。箭头表示满足条件时回退到另一方法，不是每题固定把两套流程全部运行：ReAct 超过规定步数仍未作答时转 CoT-SC，反方向则在 CoT-SC 的答案一致性不足时转 ReAct。以下是 PaLM-540B 在原论文中的部分结果。

| 方法 | HotpotQA，精确匹配率 | FEVER，准确率 |
|---|---:|---:|
| Standard | 28.7 | 57.1 |
| CoT | 29.4 | 56.3 |
| CoT-SC | 33.4 | 60.4 |
| Act | 25.7 | 58.9 |
| ReAct | 27.4 | 60.9 |
| CoT-SC → ReAct | 34.2 | 64.6 |
| ReAct → CoT-SC | 35.1 | 62.0 |

来源：R01，PDF p. 5，Table 1。不同方法还涉及采样与回退策略；不能把表中差异理解为相同成本下的比较。〔[R01，§3.2–3.3，PDF pp. 5–6](#ref-r01)〕

ReAct 比 Act 更强，但在 HotpotQA 上没有超过单独 CoT。论文人工分析了各自的成功与失败样本：ReAct 更依赖真实检索证据，减少了抽样轨迹中的事实幻觉；与此同时，重复行动、推理错误和无信息量搜索结果成为重要失败类型。其中，搜索结果错误占 ReAct 被分析失败样本的 23%，不是全部任务的 23%。〔[R01，Table 2，PDF p. 6](#ref-r01)〕

由此可见，增加工具把一部分“凭记忆编造”的风险转化成了“获取、解释、维护外部信息”的工程问题。**闭环只是允许纠错，工具与上下文决定纠错机会能否被实际利用。**

### 1.6 ReAct 的训练补充：模型能否学会这种交互，也需要单独验证

论文还用 3,000 条最终答案正确的生成轨迹微调较小 PaLM 模型。其特定实验中，微调后的 ReAct 相比仅靠提示示例的版本表现改善，说明“能从少量示例学会整个交互方式”与“通过训练学会交互方式”不是同一要求。〔[R01，§3.2–3.3、Figure 3，PDF pp. 5–7](#ref-r01)〕

这个结果不能推出任意模型都需要同样数量的数据，也不证明只筛选正确最终答案就能保证轨迹过程正确。它的意义是把模型能力与交互设计区分开来。

### 1.7 Weng 的补充：跨尝试的反思，不等于保存全部失败历史

Weng 的综述将规划、记忆、工具使用放在一起，并通过 Reflexion 介绍一种跨尝试循环：执行、评价、反思，再将反思放入后续尝试的工作记忆。文中也讨论通过重复动作和相同观察识别无效轨迹。〔[R05，Agent System Overview／Self-Reflection](#ref-r05)〕

ReAct 关注当前尝试中的反馈驱动行动；Reflexion 补充一次尝试失败后，怎样提炼可用于下一次的经验。讲义最后一页也用不同循环位置区分 ReAct、Reflexion、Plan-and-execute 等组织方式。〔[L04，PDF p. 56](#ref-l04)〕

**工程推导：**保留失败不是为了反复阅读失败故事，而是避免重新付出同一种探索成本。例如，“先前查询命中了另一个同名产品；后续检索必须加产品线与时间约束”是一条可执行经验；十次相同搜索返回值则未必值得常驻。

## 2. Toolformer：工具调用能力怎样通过训练形成

### 2.1 它与 ReAct 研究的不是同一层

ReAct 主要讨论推理与行动的组织。Toolformer 则研究如何通过少量 API 示例与自监督数据构造，使模型学会选择 API、选择时机、填写参数，并利用结果预测后续文本。〔[R14，Abstract、§2，PDF pp. 1–3](#ref-r14)〕

一个系统即使已经有正确的循环，模型仍可能不会调用某种工具；模型即使擅长单次工具调用，也可能不会维护多轮任务进度。这两类问题不能混成一个“Agent 能力”。

### 2.2 数据构造：生成、执行、筛选，再微调

先补训练所需的最小概念。Token 是模型处理文本的基本片段，不必等于一个字或单词。语言建模训练拿已知文本做练习：给定前面的内容，让模型给真实的下一个 Token 分配概率。**预测损失**衡量它预测得有多差，越低越好；单个目标 Token 常用 $-\log p$，其中 $p$ 是模型给正确 Token 的概率，$\log$ 为自然对数。例如概率从 0.1 提高到 0.5，损失从约 2.303 降到 0.693。多个位置的损失加权相加，就能比较哪种输入更帮助预测后文。

Toolformer 从普通语言建模文本出发，先生成潜在调用位置与候选 API 调用，执行这些调用，然后检查返回值是否降低后续 Token 的预测损失。只有带来足够帮助的调用进入增强数据集，供模型训练。这里“微调”指用这些文本继续更新模型参数；仅把工具说明放进某次请求的上下文，不等于做了微调。〔[R14，Figure 2、§2，PDF pp. 2–3](#ref-r14)〕

原论文的 Pittsburgh 示例很直观。后文要写 Steel City，查询“Pittsburgh 的别名”可以帮助预测；查询“Pittsburgh 在哪个国家”也能获得真实信息，但对接下来的文本帮助较小。

**正确的信息，不自动等于当前任务需要的信息。**这与工具返回值应当高信息量、低冗余的工程原则相接。

### 2.3 筛选损失：为什么要有三个对照条件

令 $L_i(z)$ 表示给定辅助前缀 $z$ 后，对位置 $i$ 及之后 Token 的加权预测损失。论文定义：

$$
L_i^+=L_i(e(c_i,r_i))
$$

$$
L_i^-=\min\bigl(L_i(\epsilon),L_i(e(c_i,\epsilon))\bigr)
$$

并保留满足以下条件的调用：

$$
L_i^- - L_i^+ \ge \tau_f
$$

其中，$c_i$ 是调用，$r_i$ 是结果，$e$ 是文本化表示，$\epsilon$ 表示空内容。三个对照分别是：无调用、只有调用没有结果、调用与结果都有。〔[R14，§2 Filtering API Calls，PDF p. 3](#ref-r14)〕

$+$ 与 $-$ 只是两组条件的名字，不表示损失为正或负。$\tau_f$ 是要求的最小改善阈值；$\min$ 取两个基线中损失更低、表现更好的一个。加入“只有调用”的对照，是为了判断真正提供帮助的是否为返回值，而不是调用文字本身。

**手算一次，教学示例。**无调用损失为 2.0，只有调用为 1.8，带返回值为 1.1，阈值为 0.5：基线取 $\min(2.0,1.8)=1.8$，改善 $1.8-1.1=0.7$，保留。如果带返回值的损失为 1.6，改善只有 0.2，就舍弃；不能挑较差基线来放大收益。论文对靠近调用位置的后续 Token 赋更大权重，因此衡量的是局部预测帮助，并非整项任务成功率。这个筛选目标比让模型自评“这个工具很好用”更具体，也更适合自动生成大规模训练数据。

这里还存在一个实现细节：损失筛选时，论文把调用信息作为前缀提供，避免未微调模型因中间插入陌生调用格式而受影响；正式训练数据则将保留的调用插入原文相应位置。理解算法时，不应把这两个阶段混成一次普通聊天调用。〔[R14，PDF pp. 3–4，脚注 3 与 Model Finetuning](#ref-r14)〕

### 2.4 推理时仍需真实外部执行

模型生成到等待工具返回的位置后，解码暂停；外部程序执行 API、插入结果，再继续生成。论文使用问答、Wikipedia 搜索、计算器、翻译与日历五种工具。〔[R14，Inference／Tools，PDF p. 4](#ref-r14)〕

模型学习的是“需要时请求能力并使用结果”，不是把外部服务直接存进参数。更好的工具训练也不会取消 Harness 中的执行、权限与异常处理责任。

### 2.5 三个常被忽略的限制

**解码规则也影响调用倾向。**实验并非只有训练变化。论文将 API 起始标记进入前 $k$ 个候选作为调用触发条件，并采用 $k=10$ 增强调用倾向，同时把每个输入限制为最多一次调用，避免无休止调用。其分析还表明，提高调用倾向会改变调用与不调用样本之间的校准特征。〔[R14，§4.2、§5，PDF pp. 5–6、9](#ref-r14)〕

**单次调用有帮助，不等于解决依赖组合。**先查询日期，再把日期放入另一个工具，是跨工具依赖；论文独立采样调用的训练方式与单次调用约束没有解决这个问题。〔[R14，Temporal Datasets，PDF p. 8](#ref-r14)〕

**语言损失下降，不等于事实或任务目标更正确。**论文数据质量分析中存在语义不相关的检索结果仍降低损失的例子，如 “Fast train success” 对应的搜索调用。它说明筛选目标是一种代理信号，不是业务完成验证。〔[R14，Data Quality／Table 10，PDF pp. 9–10](#ref-r14)〕

### 2.6 对工程的启发：分别评估三层能力

| 层次 | 应检查什么 | 主要依据 |
|---|---|---|
| 模型 | 是否会选工具、构造参数、利用返回值？ | Toolformer |
| 交互过程 | 是否能处理反馈、修正查询、跟踪进度、退出循环？ | ReAct |
| 接口与环境 | 工具是否表达清楚、结果是否有效、错误是否可恢复？ | Lecture 04、工具设计文章 |

**工程推导：**调用次数不是工具价值。价值在于是否获得了必要证据、消除了任务相关的不确定性，或者完成了必要状态变化。该判断不直接等同于 Toolformer 的语言损失目标，需要额外任务评测。

## 3. 检索与读取：把问题变成可定位的证据

### 3.1 五种定位方式：先看线索是什么，再决定用什么工具

讲义第 10–15 页逐页比较 glob／grep、语义检索、外部信号与语言服务器，并在第 11 页额外给出 repo map 这一结构化入口。〔[L04，PDF pp. 10–15](#ref-l04)〕

**为什么同一份材料看起来是“四种”，下表却是五种。** 讲义第 14–15 页的对比表只有四行：glob／grep、Semantic index、Extrinsic signals、Language server。repo map 没有单独成行，它被写在第 11 页“semantic search”这一页里，与 embedding 检索并列——一条 bullet 讲 semantic，一条讲 structural，然后共用第三条成本说明：查询时快，代价在构建与重新同步索引。也就是说，**讲义没有单列 repo map**，且这一页将 semantic 与 structural 并置；将它们理解为共用预建索引成本，是本文的归纳，不能当作讲义明确给出的分类依据；**本表按“定位依据究竟是什么”细分**，所以是五行。下表为帮助选工具而进一步细分，保留这一粒度差异。

| 方式 | 定位依据 | 是否需要预建索引 | 适用线索 | 首要成本 |
|---|---|---|---|---|
| glob／grep | 文件名、路径、字面字符串 | 不需要 | 名称已知或可猜测 | 每一轮搜索都消耗轮次与上下文 |
| 语义检索 | 代码块 embedding 与问题的相似度 | embedding 索引 | 知道功能，不知道命名 | 构建与保持同步 |
| repo map | 文件、类、函数签名的排序摘要 | 结构索引 | 需要先理解代码轮廓 | 排序并裁剪到 token 预算内 |
| 外部信号 | 堆栈、失败测试、Git 历史 | 不需要 | 已有故障线索 | 只在确实存在该信号时可用 |
| LSP | 编译器符号图中的定义、引用、类型 | 语言服务索引 | 需要跟踪真实调用与重构 | 每种语言一个常驻进程，冷启动慢 |

#### 3.1.1 glob／grep：从字面线索开始，代价可预测

机制很直接：glob 匹配路径，grep 匹配内容，两者都是字面或正则匹配，不对代码做任何语义理解。讲义第 10 页用三句话概括它的性质——Agent 反复 `ls`／glob／grep，**没有任何东西需要构建或同步**；它**永远反映 live repo**（工作区当前状态，包括尚未提交的改动）；代价是**烧掉轮次与上下文**，而且字面匹配会漏掉换一种说法的写法。

讲义给的例子值得逐步读：`fix the login timeout` → `grep -rn "timeout" src/`，命中 37 处、分布在 12 个文件 → `glob src/**/auth/*.ts` 把范围收窄到 auth 目录 → 读 `auth/retry.ts`，改掉 `RETRY_MS = 500`。这个链条能成立，靠的是两条线索：报错文本里有 `timeout` 这个字面词，以及目录结构本身携带信息（`auth` 这个名字缩小了范围）。如果报错说的是“偶尔重复扣款”，而代码里写的是 `idempotency_key` 或 `dedupe`，第一步 grep 就会整体落空——这正是“lexical matching misses paraphrase”的具体含义。

两个容易被忽略的边界：

**命中数不等于证据量。** 命中可能落在注释、字符串常量、测试夹具、vendored 依赖和生成文件里。grep 也无法告诉你哪一处是定义、哪一处是调用、哪一处只是名字碰巧相同。

**自适应搜索会增加模型往返与累计输入。** 如果下一条查询依赖上一轮结果，就需要再让模型作决定；继续携带旧输出还会重复消耗输入预算。一个工具调用也可以执行多条已确定的搜索，因此不是每条 grep 都必然对应一次模型调用，成本也不能笼统称为乘性。第 8.4 节会具体算这笔账。R08 在开头举了一个反例：在百万行的 monorepo 上 grep 返回 4,000 条命中，Agent 把窗口烧在无关内容上，真正的原因从头到尾没有进过上下文。〔[R08，What Is Context Engineering?](#ref-r08)〕（这是该文的说明性举例，不是测量值。）

**工程建议：**先用 `-l`、计数或路径限定判断“值不值得展开”，再决定读哪几处。用 grep 缩小范围；命中行可以成为初步证据，但仍需读相邻代码、核对版本和运行路径。

#### 3.1.2 语义检索：解决“知道功能，不知道命名”

Embedding 是模型把文本编码成固定长度的数字数组（向量）；检索器比较问题与代码块的向量距离或相似度，选出候选。可以把它先理解为一种“按内容相似程度定位”的索引，不要求先掌握向量代数。具体机制是：把代码切成块（chunk），用支持代码的 embedding 模型编码后存入向量索引；提问时把问题也编码，取最近的邻居。讲义第 11 页的措辞是 embed code chunks, retrieve by meaning，配图下的一行说明是 same meaning, different words — vectors land close。例子是 `"where do we rate-limit?"` 第一次查询就返回 `throttle.ts`。

它补的是这样一类缺口：命名约定不熟悉、领域词猜不到、代码用了你不认识的说法，或者刚进入一个陌生仓库需要找入口。这些都是字面匹配天然失效的场景。

但它回答的是“哪些片段看起来在讲这件事”，**不是**“哪一处是定义”，也**不是**“谁在调用它”。最近邻表示向量相似，不能保证任务相关：相似度最高的块可能只是注释写得像，或者是一个早已废弃的实现。这一点决定了语义检索的输出必须被当作候选，而不是答案。

成本与边界：

**索引要建、要同步。** R08 把 stale retrieval 列为典型失败模式：上一季度 embedding 的 chunk 已经不对应当前跑在生产的实现，而 Agent 会照着旧 README 里的废弃 API 自信地调用。〔[R08，Stale or Irrelevant Retrieval](#ref-r08)〕

**真正的杠杆在切块与重排，不在数据库。** R08 的说法是，多数团队的瓶颈不是向量库，而是喂给它的 chunking 与 embedding 策略；并且“检索 50 个高召回候选、再重排到精确的 top-5，通常好过把 50 个块全塞进 prompt”。重排这一步是“朴素 RAG 管线开始能用或开始不能用”的分界。

**返回结果要能回答三个问题：**这是哪个版本／哪个提交？还有没有更精确的位置？哪些候选被丢掉了？答不出来，模型就无法判断自己看到的是不是全部。

**设计示例：**检索结果携带 path、chunk 范围与 index revision；重排后同时返回被丢弃候选的数量，让模型知道“此处有 50 个候选，你看到的是 5 个”。

#### 3.1.3 repo map：给仓库一张目录，而不是给它一个搜索引擎

这是最容易看不懂的一项，值得从零讲起。

**它是什么。** repo map 是一份从代码里解析出来的、**按重要性排序的仓库缩略图**。它由文件路径、类、函数与方法签名组成，通常不含函数体。讲义第 11 页给的示例就是三个条目：

```text
aider/coders/base_coder.py:
  class Coder:
    def apply_updates(self)
aider/commands.py: class Commands
```

它回答的问题是“这个仓库里有什么、大致怎么组织”，而不是“这段代码怎么写的”。

**它从哪里来。** 讲义把出处标注为 Aider's repo map。Aider 是一个开源的 AI 结对编程 CLI，它的 repo map 用 tree-sitter 把仓库解析成符号与引用关系，再按引用关系排序，最后把排在前面的部分装进一个受限的 token 预算。〔补充来源：[Aider repo map 官方说明](references/016_Aider_Repository_Map.html)与[2023-10-22 tree-sitter 文章](references/017_Aider_Repository_Map.html)，2026-10-26 保存；讲义只写 file tree plus ranked symbols，未展开解析与图排序实现。这里描述文档版本，未验证当前源码实现。〕

**为什么需要它。** 一个几十万行的仓库，在模型眼里是平的。没有地图时，模型只能靠一轮一轮搜索建立结构感——猜名字、看命中、读文件、修正猜测，每一轮都要付一次调用成本。repo map 把这一串试探换成一次读入：模型先看到 `class Coder` 上有 `apply_updates`，就能直接判断该读哪个文件、该改哪一层。它买的是**方向感**，而方向感在陌生仓库里恰恰是最贵的。

**三种实际用法：**

1. **定位入口。** 不熟的仓库里，用一次结构摘要替代多轮盲搜。
2. **消歧。** 两个文件名相似时，看谁的轮廓里有目标类或方法，而不是把两个都读完。
3. **判断改动应该落在哪里。** 看到模块边界，才知道一次修改“应该”落在哪一层，而不是落在第一个能通过测试的地方。

**它与文件树的区别。** 文件树只给路径和目录组织，告诉模型“有哪些文件”；repo map 在文件树之上再加一层符号，告诉模型“每个文件里有什么”。两者都是结构入口，只是粒度不同。〔[L04，PDF p. 11](#ref-l04)〕

边界有四条，都影响它能不能用：

**地图不是实现。** 看到 `def apply_updates(self)` 只知道这个方法存在，不知道它做什么、在哪里失败、参数有什么隐含约定。地图用来决定读什么，不能代替读。

**排序即偏见。** 既然要裁到 token 预算内，就一定有部分仓库不在地图上。排序错了，或者排序时并不知道当前任务关心什么，答案可能正好落在没有被画出来的那一块。所以 repo map 适合做 Context Admission 的第一步，不应是唯一入口——始终要保留一条超出地图范围的检索路径。

**必须跟着代码更新。** 符号会移动、改名、删除；拿旧地图去读新代码，会读到已经不存在的位置。

**成本位置与语义索引相似。** 查询时通常较便宜，构建与同步需要成本。讲义第 11 页把 semantic 与 structural 放在同一页、共用一条成本说明；把它们归为预建索引的取舍，是本文的解释，不是对教师编排原因的确认。

**工程推导：**repo map 常常被当作“压缩后的上下文”来用——它把整个仓库的信息压成一份可以长期留在窗口里的结构摘要。这与第 12 章的 Admission 与 Offloading 属于同一类动作：先决定什么值得常驻，再决定正文什么时候读进来。

#### 3.1.4 外部信号：从失败出发，而不是从源码出发

机制是：证据不在源码里，而在源码之外——堆栈、失败测试输出、Git 历史（`log`／`blame`／`bisect`）、CI 结果、错误报告。讲义第 12 页称它在调试时是 highest-precision signal：**它已经把位置指出来了**。

例子：checkout 崩溃报告 → 堆栈给出 `cart.ts:88`，共三个具名帧 → 读 `tax.ts:20–60`，问题出在 `applyTax` 的取整 → 改完直接跑 `pytest tests/tax.py` 验证 → 通过，**全程没有做搜索**。例子最后一句 green, no search used 是关键：这条路径不是“搜索更快”，而是根本不需要搜索。

它真正改变的是**方向**。没有信号时是“先找到代码，再看它有没有错”；有信号时是“代码已经被点名，去读它”。这也是讲义在对比表之后专门加一句限制的原因：已有堆栈和失败测试时，可以直接沿信号定位，不必先做一遍全库搜索。

边界同样明确：

**只在有信号时存在。** 一个新增功能的需求没有堆栈，一个“这里为什么这样设计”的问题也不会有。

**信号给位置，不给原因。** 读到那一帧之后，仍然必须判断状态：超时发生在提交前还是提交后？重试复用了同一个请求标识吗？异常处理是否把“结果未知”理解成了“没有提交”？

**信号会过期。** 堆栈里的行号对应的是当时那次构建；代码改动之后第 183 行可能已经是另一句。用行号定位之后，要用当前版本重新确认，而不是直接相信这个数字。这与 3.4 是同一个问题的两面。

**失败测试也可能是环境失败**，不能直接当作产品缺陷的证据。

Git 历史是一类特殊的外部信号：它擅长回答“**为什么**是这样”（某个决定、某次回退、某个兼容性约束），不擅长回答“**现在**是什么样”。用它解释意图，用读代码确认现状。

#### 3.1.5 LSP：让名字变成符号，而不是字符串

**先解释 LSP 是什么。** Language Server Protocol 是一套编辑器与“语言服务器”之间的标准协议（基于 JSON-RPC）。常见部署会为相应语言启动常驻语言服务器，在配置范围内维护语法、类型或符号信息；具体能力由服务器决定，协议本身不保证完整类型分析或所有引用都可解析。讲义第 13 页用三句话概括：查询编译器的索引（定义、引用、符号、类型）；解析 grep 只能猜的 import、重载与重命名；代价是每种语言一个常驻服务器，冷启动慢。

**核心区别只有一句：grep 处理的是文本，LSP 处理的是符号。** 真实代码里，同一个字符串可以指不同东西——一个局部变量 `charge`、另一个类上的方法 `charge`、以别名导入的 `charge`、消息里的 `"charge"` 字面量；同一个东西也可以写成不同形式——别名导入、二次导出、重载、泛型、宏展开。grep 分不出来，只能把 40 处命中一并交给你；语言服务器按符号表解析，能指出哪一处是定义、哪些是真的调用点。

讲义给的例子是一次改名（rename `charge()` to `capture()`），三步：

1. `textDocument/references`——找出真正的引用：42 处调用点，分布在 7 个文件；
2. `textDocument/rename`——连同别名的 import 一起改，而不是只替换字面文本；
3. 类型检查——改完验证，确认没有 unresolved symbol。

第三步值得单独注意：**改完能用同一套索引验证**。纯文本替换做不到这件事——它可能漏掉用别名导入的调用点，也可能误改同名但不相关的标识符，而且这两种错误都可能编译通过、只在运行时才暴露。这就是讲义对比表里 Language server 那一行写 edits must follow references 的原因：**它最大的价值在改，而不只在找。**

常用能力与它们各自的不可替代性：

| 能力 | 回答什么问题 | grep 为什么不够 |
|---|---|---|
| definition | 这个符号定义在哪 | 40 处命中里哪一处才是定义 |
| references | 谁真的在调用它 | 别名、重载、同名标识符分不清 |
| rename | 改这个符号，所有引用一起改 | 文本替换会漏改，也会误改 |
| hover／type | 这个表达式的类型是什么 | 类型信息不存在于文本里 |
| diagnostics | 现在有没有解析／类型错误 | 需要解析器才能判断 |

成本与边界：

**每种语言一个常驻进程。** 多语言仓库要维护多套服务、额外内存与项目配置；monorepo 还需要按构建目标切分工作区。

**冷启动慢。** 第一次查询要等索引建立，这段时间对 Agent 来说就是纯等待，讲义把它明确列为成本。

**覆盖不完整。** 动态语言（Python、JS）中运行时决定的对象关系常使静态解析更困难，不能据语言名称对所有服务器作固定优劣排序；反射、动态派发、元编程、代码生成与宏展开出来的符号可能解析不出来；有些引用只有运行时才知道。生产环境下，效果还要看索引范围、语言覆盖与权限。〔[R08，Context Engineering for AI Coding Agents](#ref-r08)〕

**服务器必须是最新的。** 用 grep 或脚本直接改文件之后，服务可能还没有重新解析；旧索引会报出已经不存在的位置。这与 3.4 的要求一致：把“索引给出的位置”和“当前读到的内容”分开对待。

**工程上通常不要求 Agent 直接讲 LSP**，而是由 Harness 把它封装成工具。用户编辑器里跑着语言服务器，不等于另一个进程里的 Agent 能用上它——这一条在评估“我们的 Agent 有没有代码智能”时经常被忽略。

**它与 repo map 的分工：** repo map 是从上往下看全局轮廓，LSP 是从一个已知符号往外看关系。前者回答“从哪开始”，后者回答“改这里会牵动谁”。

#### 3.1.6 顺序、共同盲点与生产规模的差距

讲义对比表最后一行给出的经验规则是：先 grep，名称线索用尽之后再上索引或 LSP（start with grep; reach for an index or LSP when names run out）。紧接着那句关于堆栈和失败测试的说明，是对它的重要限制——**“从 grep 开始”是默认顺序，不是必须顺序**。

这也说明五种方式补的是不同的信息缺口，而不是同一件事的五种实现：字面匹配补“名字我知道”，语义补“名字我不知道”，结构补“仓库我不熟”，外部信号补“故障已经报出来了”，LSP 补“这个符号和别处是什么关系”。

它们有一个共同盲点：**这些定位结果不能单独构成完整根因或修复证明。堆栈与失败测试已包含运行时观察，但仍需确认具体版本、输入与路径；文本/符号检索本身通常只提供静态线索。** 定位完成之后仍然要读、要跑、要验证——这正是第 3 章后面几节和第 4 章之后要处理的问题。

先把检索指标变成可检查的量。对单个任务，文件召回率是“找到的必要文件数／全部必要文件数”，Precision@5 是“前 5 个结果中的相关文件数／5”；F1 用 $2PR/(P+R)$ 平衡精确率 $P$ 与召回率 $R$。例如修复必须涉及 4 个文件，前 5 个结果命中其中 2 个，则 $P=2/5=0.4$、$R=2/4=0.5$、$F1\approx0.444$。这是教学示例；正式评测还须明确相关文件标注、截断位置与跨任务平均方式，不能拿表中的平均 P、R 直接反算平均 F1。

在生产规模上，这个差别是可以测量的。R08 报告用同一个 Agent 在 370 个企业级任务上比较“本地 grep／file／read”与“接入代码智能 MCP”两种配置：文件召回率从 0.127 升到 0.277，Precision@5 从 0.140 升到 0.478，F1@5 从 0.099 升到 0.262；更值得注意的是有任务从基线超时变成在限额内完成。〔[R08，CodeScaleBench 结果](#ref-r08)〕**边界：**这是 R08 自家基准上的结果，且被比较的不是单一机制——MCP 一侧同时包含关键词检索、语义检索、符号解析、跨仓库导航与提交历史，因此不能把差值单独归因给语义检索或 LSP 中的任何一项。

### 3.2 三个不能互相替代的问题

“哪里实现了限流？”是语义定位问题。“这个 `throttle` 被谁调用？”是符号关系问题。“为什么该请求在这里失败？”是故障路径与状态变化问题。

Sourcegraph 文章补充了生产中的检索视角：当确定结构存在时，定义、引用和依赖查询可以直接返回精确信息，而不仅是若干包含相似字符串的文件；但其效果也受索引、语言覆盖与权限影响。〔[R08，Context Engineering for AI Coding Agents](#ref-r08)〕

**工程推导：**检索器应根据已有线索缩小不确定性，而不是把每个问题都转换成同一个向量 Top-K 查询。关键词、语义、结构与运行证据可以组合，组合顺序由任务决定。

### 3.3 订单案例：合理的定位顺序

如果错误报告已经给出 `order_service.py:183`，先读该位置与调用方；如果明确知道 `submit_order`，先找定义和引用；只有功能描述而不知道命名时，再让语义检索缩小范围。

找到候选文件以后，还需要判断：超时发生在提交前还是提交后？重试是否复用相同请求标识？异常处理是否将“结果未知”错误地理解为“没有提交”？这些都要通过代码、日志或测试证据确认。

这只是调查路径示例，不是对假设故障的预先诊断。

### 3.4 检索发现与当前读取应分开

讲义区分 live repo 与需要重新同步的索引。由此得到一个重要实现要求：**检索用于发现位置，编辑前的当前读取用于建立修改依据。**〔[L04，PDF pp. 10–11](#ref-l04)〕

**设计示例：**检索结果携带路径、索引版本或提交信息；读取结果携带当前文件摘要标识；编辑请求使用当前内容或预期版本作为前置条件。这样可以拒绝针对旧内容的修改，而不是默默猜测。

同理，在文档核验中，检索到的是哪个材料版本、哪个报告期、哪个数据快照，必须明确。引用“相似案例”不能代替当前材料的证据。

### 3.5 Sourcegraph 的四个支柱不是讲义的四个操作

Sourcegraph 用 Instructions、Retrieval、Memory、Tools 组织 Context Engineering；讲义用 Admission、Offloading、Transformation、Compaction 组织上下文管理。前者回答**上下文由哪些部分构成**，后者回答**如何处理这些部分**。〔[R08，The Four Pillars of Context Engineering](#ref-r08)；[L04，PDF pp. 45–49](#ref-l04)〕

例如工具定义既属于 Tools，又可以被 Offloading；历史记忆既属于 Memory，又可能需要 Transformation 或 Compaction。不要把不同作者的四分法强行逐项对应。

## 4. 编辑工具：让修改正确落地，而不只是让模型写出代码

### 4.1 四种格式的取舍

讲义比较整文件重写、统一 diff、精确替换和结构化／AST 编辑。它第 21 页使用的 robustness，重点是修改是否落在预期位置，而不是业务逻辑是否必然正确。〔[L04，PDF pp. 17–21](#ref-l04)〕

| 方式 | 模型输出 | 优点 | 常见失败 |
|---|---|---|---|
| 整文件重写 | 修改后的全部内容 | 没有补丁语法负担 | 输出随文件增长；无关代码可能漂移 |
| Unified diff／patch | 修改块、上下文、补丁信息 | 紧凑、可审查 | 行号或上下文变化可能导致无法应用 |
| Search-and-replace | 精确旧片段与新片段 | 输出与修改量相关 | 锚点不唯一、过期、空白不一致 |
| 结构化／AST | 对符号进行受支持操作 | 可避开部分文本格式错误 | 每种语言需相应能力，操作集合有限 |

R02 的 ACI 讨论解释了为什么这些差异不是纯粹风格：生成 diff 的行数、代码放进 JSON 时的转义，都可能增加模型的格式负担。人类程序可以等价转换的格式，对自回归生成模型未必同样容易。〔[R02，Appendix 2: Prompt engineering your tools](#ref-r02)〕

### 4.2 精确替换的关键是拒绝模糊修改

下面是工程示例，不是某产品的真实接口：

```json
{
  "path": "src/orders/service.py",
  "expected_revision": "workspace-v17",
  "old_text": "原始代码片段",
  "new_text": "替换后的代码片段",
  "expected_matches": 1
}
```

工具需要检查路径边界、当前版本和匹配次数。没有匹配，要求重新读取；出现多处匹配，要求更明确的上下文；版本已变，重新建立修改依据。

**工程推导：**最危险的行为常常不是报错，而是在条件不成立时“替模型猜一个位置”。把隐含假设变成前置条件，比不断在 Prompt 中提醒小心更容易检查。

### 4.3 防错设计：让常见错误无法静默发生

R02 使用 poka-yoke，即防错设计，描述如何改接口减少误用。其例子是 Agent 改变工作目录以后相对路径出错，作者通过要求绝对路径解决了该实验中的混淆。〔[R02，Appendix 2](#ref-r02)〕

可迁移的原则不是“所有系统都应该开放绝对路径”，而是让对象身份与路径语义明确。固定工作区根目录并校验边界，也是同一问题的一种工程设计。

这与后续状态管理相互依赖：如果路径、版本和对象身份没有明确记录，上下文压缩后更容易发生错误对象修改。

### 4.4 三层验证必须分开

**修改层：**是否改了预期文件、位置和范围？

**程序层：**能否解析、通过相关类型检查和测试？

**任务层：**是否解决用户描述的问题，并满足兼容性等约束？

这是本文的工程分层。结构化编辑可以在受支持的操作范围内保证某些语法性质，但不能由此推断业务行为正确。讲义本身在 AST 示例后仍列出 parse 与 type check。〔[L04，PDF p. 20](#ref-l04)〕

对重复订单问题，改完函数参数、通过静态检查，还不能证明“首次提交成功但响应丢失”的场景不会生成第二笔订单。需要覆盖这个语义场景的证据，而不是只确认文件可运行。

### 4.5 多文件预检查不等于原子事务

R13 的个人实践脚本先检查所有旧片段的数量，再逐个写入修改后的文件。这减少了“第一个文件已写入，才发现第二个文件锚点不匹配”的风险。〔[R13，Example 1: In-place multi-file edits](#ref-r13)〕

**实现边界分析：**这不是跨文件事务。实际写入阶段仍可能遇到磁盘错误、进程中断或并发修改。原文偏强的“不会处于半更新树”表达，不能直接变成生产保证。需要更强保证时，还应设计隔离工作区、变更集合检查与恢复机制。

这个例子同时说明：代码运行正确、接口可组合，与系统在所有故障下具备原子性，是不同要求。

## 5. 工具契约：名称、参数、返回值和错误，都是决策界面

### 5.1 普通函数测试与 Agent 工具测试不是一回事

R12 将工具描述为确定性软件与非确定性 Agent 之间的契约。传统调用方已经写好了调用顺序与参数来源；模型则必须从任务、工具说明和历史结果中自行决定如何调用。〔[R12，What is a tool?](#ref-r12)〕

据此可以建立一个工程检查链：

```text
知道工具存在
→ 能从相似工具中选对
→ 能取得并填写正确参数
→ 能正确理解结果
→ 能决定后续动作或停止
```

函数在固定输入下返回正确结果，只验证了其中很小一部分。工具的可用性还依赖描述、命名、输出语义和失败恢复。

### 5.2 少而正交，不等于功能越少越好

讲义第 25 页强调 few, orthogonal tools。问题不只是数量，而是不同工具的职责是否可以明确区分。〔[L04，PDF p. 25](#ref-l04)〕

R12 举例：与其让模型分别读取客户资料、交易、备注再自行拼装，不如在合适场景下提供 `get_customer_context`，一次获取近期相关信息。它把确定性的拼装放回软件里，也减少中间结果占用。〔[R12，Choosing the right tools for agents](#ref-r12)〕

**工程推导：**好的聚合粒度通常是一个稳定、可解释的业务步骤，而不是一个数据库端点，也不是整项任务。

```text
过细：读客户 → 读订单列表 → 逐单读付款 → 逐单读退款 → 自行关联。
适度：读取某笔订单的付款与退款上下文。
过大：自动处理该客户的一切问题。
```

过细让模型承担大量可确定编排；过大则隐藏决策、权限和验证，难以判断错误发生在哪里。应通过真实任务轨迹观察哪个步骤最容易产生无价值轮次，而不是只凭工具列表长度决定。

### 5.3 命名与命名空间：降低选择歧义

R12 建议按服务或资源组织工具，例如 `asana_search`、`jira_search`，或 `asana_projects_search`、`asana_users_search`。作者也指出，前缀与后缀的效果可能随模型变化，应通过评测选择，而不是当作固定法则。〔[R12，Namespacing your tools](#ref-r12)〕

**设计示例：**`search_document`、`search_document_v2`、`smart_search` 同时存在时，模型很难从名称看出边界；`documents_search_text` 与 `documents_read_range` 则分别表达发现候选与读取已知位置。

名称不是越长越好，而是应带上足以区分用途的信息。命名空间同样只是组织方式，不构成权限隔离；谁能查询哪些资源仍由后端授权决定。

### 5.4 参数要消除隐含约定

R12 建议像向新同事说明操作一样写工具定义，明确专业术语、资源关系和输入输出。例如用 `user_id` 替代含义不清的 `user`。〔[R12，Prompt-engineering your tool descriptions](#ref-r12)〕

对于一个新同事也无法凭名字判断的参数，模型没有理由必然知道。例如：时间是业务发生时间还是入库时间？金额是元还是分？对象是产品还是份额类别？路径相对哪个根目录？

**工程推导：**类型校验只确认形状，业务校验确认含义。一个字符串可以符合 Schema，却指向错误客户；日期格式正确，也可能使用错误报告区间。重要口径应该由清楚字段和服务端校验共同表达。

### 5.5 一份工具描述应回答什么

以下是本文提供的描述模板：

```text
工具：search_order_events

用途：
根据已确定的 order_id 查询订单状态变化与请求事件。

何时使用：
需要分析重复请求、状态变化或提交前后的事件顺序。

不要用于：
根据姓名猜测订单；创建订单；执行退款；判断用户是否获准操作。

输入要求：
order_id 必须来自已核验的订单信息。
时间参数注明时区、过滤字段和区间边界。

返回语义：
事件时间、请求标识、状态、证据引用及分页信息。
空结果不自动证明订单不存在。

失败处理：
参数错误时修正；权限不足时停止；结果过大时缩小范围。
```

这不是某个产品的标准 Schema，而是将 R12 的清楚边界与显式契约建议转成可检查的文档。

### 5.6 输出整形：同时保留语义、身份、版本与后续入口

R12 建议返回高信息量、对下游有意义的内容，减少不必要标识与技术字段；又通过 Slack 示例说明，进一步读取线程时需要的 `thread_ts` 等 ID 可以保留在详细返回模式中。文章没有主张所有 ID 都应该删除。〔[R12，Returning meaningful context from your tools](#ref-r12)〕

一个测试结果只有 `success: false`，不足以指导下一步；几万行日志又可能淹没失败重点。工程示例如下：

```json
{
  "status": "failed",
  "workspace_revision": "workspace-v18",
  "failed_tests": [
    {
      "name": "test_retry_after_response_timeout",
      "expected": "one order",
      "actual": "two orders",
      "location": "tests/test_orders.py:82"
    }
  ],
  "log_handle": "artifact:test-run-42",
  "truncated": true
}
```

这让模型知道哪里失败、表现是什么、对应哪个工作区版本，以及如何继续读取。**节省 Token 不是删除到最少，而是保留当前决策与后续操作所必需的信息。**

R12 还指出，JSON、XML、Markdown 等返回结构可能影响表现，不存在对所有模型与任务都最优的一种格式。应按任务评测，而不是只按人类喜好选择。〔[R12，Returning meaningful context／Optimizing tool responses](#ref-r12)〕

### 5.7 结果状态不要把“未知”伪装成“没有”

以下是工程语义区分：

| 返回情况 | 可以说什么 | 不应直接推断什么 |
|---|---|---|
| 查询成功，结果为空 | 在这次查询的范围与权限内没有匹配记录 | 全系统不存在该对象 |
| 结果被截断或分页 | 当前展示的是部分结果 | 已经看完全部结果 |
| 查询失败 | 没有获得可靠查询结果 | 结果为零 |
| 字段为 `null` | 含义取决于契约，可能未知或不适用 | 自动当成零 |
| 测试命令未真正启动 | 测试尚未完成 | 测试通过 |
| 写操作超时 | 调用结果尚未确认 | 操作一定没有生效 |

R15 的队列 Skill 中，`null` 不等于零是明确的业务解释。其他区分是将同一原则应用到工具契约的工程推导。〔[R15，Skills are just instructions，队列示例](#ref-r15)〕

### 5.8 错误返回值应告诉模型怎样恢复

讲义要求 errors that teach；R12 也建议错误和截断提示给出具体可行动的改善方式，而不是只有错误码或冗长堆栈。〔[L04，PDF p. 25](#ref-l04)；[R12，Optimizing tool responses for token efficiency](#ref-r12)〕

可以按恢复动作分类：参数非法，修改参数；锚点过期，重新读文件；范围过大，过滤或分页；权限不足，停止或进入真实授权流程；操作状态未知，先核验再考虑重试。

这些分类不是为了增加新 Agent，而是让同一循环知道下一步该做什么。原样重复一个必然失败的请求不会因为重试次数增加而变得合理。

### 5.9 幂等性不能靠 Prompt 保证

讲义建议尽可能让工具可安全重试。〔[L04，PDF p. 25](#ref-l04)〕

**工程推导：**读操作与有外部副作用的写操作要采用不同恢复策略。写操作发生超时时，调用方只知道自己没有及时得到响应，并不知道后端是否完成。因此需要稳定操作标识、状态查询与重复请求处理机制。

同一个逻辑操作的重试不应每次都创建新的幂等标识；否则后端可能把它们视为不同操作。反过来，也不能让不同内容意外复用一个标识。操作身份、请求内容和结果状态的关系，应在后端明确维护。

这个原则与假设订单故障直接相关，但不构成对该故障根因的预判。

## 6. Bash、程序化处理与长命令：把计算留在环境里

### 6.1 讲义的 Shell 不是一个普通小函数

讲义第 22 页指出 Shell 的四种特点：组合能力、对文件与网络等资源的访问、文件和进程的持久性，以及较大的影响范围。第 23 页要求考虑隔离、失败信号、输出、执行时长和预算。〔[L04，PDF pp. 22–23](#ref-l04)〕

所以，“只给一个 Bash 工具”可能减少模型可见 Schema，却不意味着权限更少、操作空间更小或系统更简单。

**接口选择复杂度与实际执行影响范围，是两种不同的复杂度。**

### 6.2 R13 的三个实践例子，展示的是组合而不是 Bash 语法本身

R13 作者说明这些是个人 Agent 轨迹的简化示例，将“superhuman”限定为迅速合成一次性命令行程序的能力，并明确承认模型仍会犯错。〔[R13，What “superhuman in Bash” means](#ref-r13)〕

**例子一：多文件修改。**Python 先检查旧片段数量，再准备修改内容；写入后运行格式化、静态检查、相关测试和 diff 检查。关键是将编辑前置检查与修改后验证连在一起，不是把若干文件随便重写。

**例子二：偶发回归定位。**独立 worktree 保留当前工作区不动，Git bisect 在多个提交之间搜索，每个候选提交用多个测试种子判定，以减少单次偶发失败的误导。这是作者的具体策略，不保证对所有非确定性测试都充分。

**例子三：压缩日志关联。**Python 分批读取普通或压缩 JSONL，SQLite 完成关联、排序与统计，最终只返回五条聚合记录。大量中间数据从未进入模型上下文。〔[R13，Examples 1–3](#ref-r13)〕

Bash 在这里是路由与组合层；重计算可能由 Python、SQLite、Git、编译器或测试系统完成。

### 6.3 程序化处理与语言摘要，是两种不同路径

```text
语言摘要路径：
大量原始材料进入模型 → 模型理解与压缩 → 少量结论。

程序化处理路径：
原始材料留在环境 → 程序筛选、关联、计算 → 少量结果进入模型。
```

R13 的日志例子体现后一条路径。它与讲义的 Admission 和 Offloading 相连接：不是把长输入压短，而是避免让不必要的原始数据进入模型。〔[R13，Example 3](#ref-r13)；[L04，PDF pp. 46–47](#ref-l04)〕

**工程推导：**精确过滤、聚合、计数和排序通常可以明确交给程序；模型更多负责判断需要哪些字段、解释结果以及决定下一次查询。这样既缩小上下文，也减少模型承担的确定性计算。

但程序化结果仍需要口径说明。R13 日志代码中的延迟统计基于 `status >= 500` 且与错误日志成功关联的请求，而不是全部请求。把结果标成“所有请求的 P95”会改变它的含义。这是代码语义分析，不是额外实验结果。

### 6.4 专用工具与 Shell 的证据为什么看起来相反

讲义第 26 页展示的 GPT-4 设置中，专用 SWE-agent 接口为 18.0%，Shell-only 为 11.0%，并注明 “No on GPT-4”。该页还列出其他接口消融。〔[L04，PDF p. 26 的图](#ref-l04)〕

R13 则报告，在作者比较的另一组编码任务与条件下，以 Shell 为中心的配置完成表现相近或更好。但文章没有提供足够详细的模型、任务与完整量化结果，不能据此作普遍排名。〔[R13，What this means for harness engineering](#ref-r13)〕

两者的模型与任务设置不同，证据形式也不同。**结论应是需要在目标模型、目标任务与目标权限环境里比较，而不是“专用工具已过时”或“Shell 永远不行”。**

### 6.5 小接口把保护责任转移到了 Harness

R13 解释，先前原子工具提供的保护仍然需要存在，只是可以由 Harness 统一承担：控制过量输出、返回退出码和时间信息、限制路径与网络、管理长运行进程。作者还保留媒体查看能力，因为文本路径不会自动使图像像素进入视觉模型。〔[R13，Why atomic tools were right](#ref-r13)〕

这与讲义的执行要求一致。更强的模型可能承担更多命令组合，但不会自动完成授权、安全隔离与失败恢复。

**工程推导：**子 Agent 的独立上下文是信息隔离，不自动等于操作系统安全边界。将探索交给子 Agent 后，仍需明确其可访问目录、网络、凭证与写权限。

### 6.6 Shell 接口背后不一定是真实 Bash 进程

R15 作者介绍，在 Go 应用里实现虚拟文件系统与 Shell 解释能力，一些“二进制命令”实际由 Go 函数提供。模型可以通过熟悉的操作形式使用这些能力。〔[R15，Agents are a loop 后的 Shell 示例](#ref-r15)〕

这说明模型面对的操作语言与底层执行机制可以解耦。它与 Toolformer 相连：模型使用的是可理解的调用契约，而不需要知道服务器内部如何实现。

**边界：**受限解释器可以提供真实实现的能力；不能把“生成一个看起来像成功的返回值”当成真实业务执行。接口兼容与结果真实性是不同问题。

### 6.7 长命令应有生命周期：Duration、后台进程与结果未知

讲义第 23 页把 Duration 一条写作 “long-running and background processes”，与 Isolation、Failure signal、Output、Budgets 并列。这说明在讲义框架里，**执行时长不是性能话题，而是工具契约的一部分**。R13 在“Harness 吸收原子工具原有保护”的清单中也列出 *Asynchronous processes*：让 Agent 启动、检查、停止长命令而不阻塞当前轮次，并把 duration、timeout state 与进程信息归入应返回的诊断内容。〔[L04，PDF p. 23](#ref-l04)；[R13，Why atomic tools were right](#ref-r13)〕

一个测试任务执行十分钟时，只有“同步等待＋超时”通常无法表达全部状态——它只能表达“调用方等到了”或“调用方没等到”，而这两种回答都覆盖不了真实系统里的进程状态。

#### 6.7.1 先分清四种“超时”

| 超时来源 | 由谁设定 | 超时的实际含义 |
|---|---|---|
| 命令自身超时 | 命令参数，如 `timeout 600`、`pytest-timeout`、`curl --max-time` | 程序主动放弃，通常返回它自己的退出码 |
| Harness 等待上限 | 工具层 wall-clock | 调用方不再等待；**命令可能仍在运行** |
| 轮次／预算上限 | Agent 循环 | 本轮不再推进，可能需要交还控制 |
| 人工取消 | 用户 | 目标发生变化，不是失败 |

真正容易出错的是第二行。工具返回 `timeout` 时，系统知道的是“我没有拿到结果”，而不是“这件事没有发生”。这与 5.9 的幂等性是同一条规则在两个维度上的表现：时间维度的超时和网络维度的超时一样，都只产生**结果未知**。

#### 6.7.2 “同步等待＋超时”的四种典型故障

**一、孤儿进程与重复启动。**超时返回后进程仍在后台占用端口、CPU、文件锁或数据库连接。模型把 `timeout` 读成失败，于是启动第二份相同测试。两份任务写同一份产物或竞争同一端口，产生的失败现象与原始任务无关，排查成本更高。

**二、重复副作用。**迁移、批量写、部署、发版类命令被执行两次。15.1 的订单案例属于同一结构：调用方超时后重试，而后端其实已经完成。这里的工程结论不是“不要重试”，而是**超时后先查询状态再决定是否重试**。

**三、完成误判。**日志最后一行看起来像结论，但进程尚未结束：输出缓冲未刷新、子进程仍在运行、被 `&` 放到后台的 daemon 还在继续。没有退出码时，“看到结论”与“任务完成”不是同一件事。测试输出停在 `collected 200 items` 也可能只是还在收集阶段。

**四、阻塞整个循环。**十分钟的同步调用期间，Agent 无法核验中间状态、无法处理其它证据、也无法响应用户。上下文里既没有新增证据，也没有可判断的进度，只有一次漫长的等待。

#### 6.7.3 按执行形态选择处理方式

不是所有命令都要异步化。可以按“时长 × 是否可交互 × 是否有副作用”分成几类：

| 形态 | 典型例子 | 处理方式 |
|---|---|---|
| 秒级，只读或幂等 | `rg`、`git status`、单个测试文件 | 同步阻塞，设置合理上限 |
| 分钟级，有进度输出 | 全量测试、构建、依赖安装 | 同步并限时；接近上限时转入后台 job |
| 长时，非交互 | 训练、大批量数据处理、全量回归 | 异步 job，在轮次之间轮询 |
| 常驻 | dev server、watch、数据库 | 后台运行＋健康检查＋明确的归属与关闭责任 |
| 交互式 | 需要 stdin、TUI、确认提示 | 通常不适合异步 |

最后一行需要单独说明：交互式命令异步化之后，Agent 只是不再阻塞，**并没有获得与它对话的能力**。正确做法一般是先把它改成非交互形式（`-y`、`--no-input`、`CI=1`、显式传参），再考虑是否异步。需要密码或凭据的交互应进入授权流程，而不是靠后台化绕过。

#### 6.7.4 最小工具契约：四个动作

以下为工程设计示例：

```text
start_job(command, cwd, env, budget)   → job_id, pid, log_path, workspace_revision
inspect_job(job_id)                    → 状态、已耗时、退出码、超时状态、输出游标、尾部摘要
read_job_output(job_id, offset, limit) → 指定范围的输出切片
cancel_job(job_id)                     → 发送取消请求并回读最终状态
```

与同步工具相比，这组接口把“等待”从调用语义中拿掉，改为**可查询的状态对象**。模型不再问“它成功了吗”，而是问“它现在是什么状态”。

#### 6.7.5 状态至少要能区分五种

```text
start ──▶ running ──┬─▶ completed    退出码 0
                    ├─▶ failed       退出码非 0
                    ├─▶ cancelled    取消请求已生效并确认结束
                    └─▶ unknown      进程消失、harness 重启、结果无法关联
```

前四种容易想到，**unknown 才是必须显式建模的一类**。它来自 harness 重启、容器被回收、进程被外部杀死、日志与 job 记录对不上等情形。若状态集合里没有 unknown，系统会把它错误地归入 failed，于是触发一次本不该发生的重试。

不确定时，正确的输出是“状态未知＋`job_id`＋如何进一步核验”，而不是猜一个成功或失败。

#### 6.7.6 job 记录里应该能关联到什么

| 字段 | 为什么需要 |
|---|---|
| `job_id` | 跨轮次引用同一份执行；也是防重复启动的键 |
| 完整命令与 `cwd` | 复现与审计；避免把两次不同命令混成同一个 job |
| `workspace_revision` | 结果对哪个代码／数据版本有效 |
| `pid` 与进程组 | 取消时能覆盖子进程，而不只是杀父进程 |
| 启动时间与已耗时 | 判断进度是否异常，而不只是“还在跑” |
| 日志位置与输出游标 | 支持增量读取，避免重复灌入上下文 |
| 退出码、超时状态 | 区分完成、失败与被截断 |
| 取消请求与最终状态 | 区分“已请求取消”和“已确认结束” |
| 关联的任务／步骤标识 | 让证据能回到用户目标，而不是孤立的一次命令 |

**`workspace_revision` 最容易被忽略。**一份全量测试在 v18 上启动，执行期间 Agent 修改了文件得到 v19，只有在不可变快照、隔离 worktree 或执行期间禁止修改的条件下，结果才能归属于 v18。若测试边运行边读取同一可变目录，它可能看到新旧混合内容，启动时记一个 v18 标签不能解决这个问题。必须保存实际输入快照或检测执行期间变更，并重新验证。这与第 4 章的编辑契约、附录 C.3 的验收表属于同一类要求：**结论必须能与它成立时的状态绑定。**

#### 6.7.7 输出按范围读，不要一次性灌回

`inspect_job` 默认返回的应当是**状态和摘要**，不是完整日志。理由与 6.3 的程序化处理路径一致：

- 原始日志留在磁盘，模型按 `offset`／`limit` 取切片；
- harness 可以在返回前做一次聚合，例如只给失败用例名、错误计数和尾部若干行；
- 每次读取从上次的游标继续，而不是从第一行重新开始——否则同一段输出会在上下文里反复出现，既占预算也干扰判断。

否则，同一段日志会被反复送入上下文；累计体积取决于输出速度与轮询方式，不能仅由任务持续时间推算。

#### 6.7.8 取消是请求，不是已经发生的事实

`cancel_job` 的返回值应当是**回读到的最终状态**，而不是“信号已发送”。至少需要考虑：

- 先 `SIGTERM` 给宽限期，再 `SIGKILL`。直接强杀会让带清理钩子的命令（迁移、容器作业、临时文件）留下中间状态；
- 杀进程组而非单个进程，否则子进程成为孤儿并继续持有端口或锁；
- 取消后重新观察一次：进程是否真的结束、退出码是什么、产物处于什么状态；
- 对已经进入提交阶段的操作，正确的下一步往往是**查询现状**，而不是重跑。

#### 6.7.9 Harness 侧还需要并发与去重

异步化之后，“当前正在运行什么”本身成为一个需要被管理的一等状态：

- 维护每工作区（或每资源）的**活动 job 列表**，与附录 C.2 模板中的 `execution.active_jobs` 对应；
- 相同命令已在运行时，`start_job` 应返回既有 `job_id` 或显式报冲突，而不是再起一份；
- 有写副作用的长任务需要独占标记或互斥；
- 并发上限、日志磁盘上限、单任务最长存活时间都需要默认值，否则“后台”会变成无人回收的资源池。

#### 6.7.10 模型侧要被明确告知的两件事

工具契约能表达状态，但模型仍需要被说明如何使用它：

1. **工具描述里给出时长量级指引**，例如“本工具同步等待上限 120 秒；预计更久的命令请使用后台模式”。
2. **超时返回文案必须自解释**：状态为 unknown、给出 `job_id`、说明如何检查、并明确“不要用相同命令重新启动”。

判断进程是否结束，应依据可信的生命周期状态、退出码等字段，不能依据“最后一行日志看起来像结论”。进程结束后，仍要用测试结果或产物检查判断用户任务是否完成；退出码 0 本身不能证明业务目标已达成。这类文案属于 R12 所说的“错误要能教会下一步”，而不是只报告一个错误码。〔[R12，Optimizing tool responses for token efficiency](#ref-r12)〕

#### 6.7.11 边界：不是所有长命令都该异步化

**异步化把复杂度从“等待”转移到了“状态管理”**，只有当任务确实长到值得时才付出这个代价。更优先的通常是把任务本身变短：

- 跑相关测试子集，而不是每次都全量；
- 利用构建与依赖缓存；
- 把可并行的分片拆开；
- 修掉本身有问题的慢测试或轮询等待。

另外两点需要保留：

- **异步不解决授权。**需要凭据或需要人工确认的命令，后台化之后仍然需要真实的授权流程。
- **没有进度输出的长任务，异步化后依然不可观测。**如果命令长时间静默，先让它能报告进度，再考虑是否后台运行。

最后，结果未知必须能被诚实交付。“已提交、结果待核验”作为一个真实状态存在，比编造一个确定结论更接近系统实际能力。

### 6.8 何时重试、何时换方法、何时交还控制

讲义把 Budgets（何时停止重试并交还控制）与 Duration 并列在同一页，两者共同约束长任务：6.7 解决“怎样知道它还在跑”，本节解决“知道之后该做什么”。〔[L04，PDF p. 23](#ref-l04)〕

**工程推导：**重复错误应按类型处理。临时网络错误可能适合有限重试；相同参数校验错误不应原样重试；权限失败不应通过换一个通用工具绕过；长期无进展需要重新检查证据缺口，而不是单纯增加步数。

允许的结束状态不只有成功。环境阻塞、需要用户判断、权限不足、预算耗尽，都可以是诚实且有效的系统输出。重要的是清楚区分它们，并保留恢复所需状态。

## 7. Prompt 与 Workflow：它们也在设计上下文怎样流动

### 7.1 四个问题，分别属于四个层次

讲义第 28 页分别提出：怎样指示模型、让模型看见什么、Agent 怎样运行、什么算成功。它同时提醒，这些名称是帮助识别不同问题的术语，不意味着老师认可所有流行命名。〔[L04，PDF p. 28](#ref-l04)〕

| 层次 | 问题 | 示例 |
|---|---|---|
| Prompt | 如何说明任务与期望行为？ | 明确约束、输出、示例 |
| Context | 当前决策需要哪些信息？ | 检索、历史、状态与证据 |
| Harness | 系统怎样执行与恢复？ | 工具、权限、重试、停止 |
| Goal | 什么结果算完成？ | 验证标准、限制与取舍 |

Prompt 工程没有被上下文工程取代，而是被放进更大的系统。缺少证据时，改措辞不能制造证据；没有执行权限时，加一段角色描述不能创造权限。

### 7.2 八种方法的适用条件与工程边界

讲义第 29–38 页给出以下方法。表中“原文关注”概括讲义，“工程边界”为本文的分析。〔[L04，PDF pp. 29–38](#ref-l04)〕

| 方法 | 原文关注 | 工程边界 |
|---|---|---|
| Zero-shot | 常见任务，规则和格式能直接表达 | 先建立基线，避免一开始堆复杂模板 |
| Few-shot | 隐含规则、特殊格式适合展示 | 选有代表性的不同决策边界，避免重复成功例子 |
| Role／Persona | 受众、语气与判断角度 | 角色不提供事实、专业数据或验证 |
| Chain-of-thought | 多步骤问题，容易跳步 | 关注有效分解，不把输出长度作为质量指标 |
| Tree-of-thought | 多条可行路径，可以评分和剪枝 | 评分器不可靠时，更多分支可能放大误判 |
| Self-consistency | 多次采样并投票 | 一致率不是校准后的正确概率，样本可能共享偏差 |
| Prompt chaining | 可拆阶段，阶段交接可验证 | 上游遗漏限定条件会传播；交接需要证据和结构 |
| Meta prompting | 用模型优化提示词 | 保留独立测试集，防止只修补已见案例 |

讲义第 35 页用五次采样中四次一致说明投票，`4/5=0.8` 是一致率。本文不把它解读成答案有 80% 正确概率。第 39 页提出某些技巧可能已经过时，但未具体指明哪些；不能据此宣布某一种方法普遍失效。〔[L04，PDF pp. 35、39](#ref-l04)〕

### 7.3 指令应具体到可以行动，又不要硬编码全部未来

R07 讨论“合适的抽象高度”：一端是脆弱的超长 if-else，另一端是没有具体行为信息的空泛原则。有效指令应足够明确，同时保留对新情况的判断空间。〔[R07，The anatomy of effective context](#ref-r07)〕

以下是编码案例的工程模板：

```text
目标：定位并修复超时重试产生重复订单的问题。

约束：
保持公开 API 兼容；不得通过删除断言或弱化测试制造通过；
只修改与问题相关的内容。

工作要求：
先寻找可验证的失败证据；区分已验证事实与候选解释；
修改后运行相关回归测试，并检查变更范围。

完成标准：
说明根因、变更、验证结果与仍未验证部分。
缺环境或权限时报告阻塞，不声明修复完成。
```

它没有固定每一次工具调用的顺序，但明确了目标、限制和验证。稳定约束交给指令与代码，不确定探索交给模型，是此处的工程取舍。

### 7.4 明确操作步骤与反对超长 if-else 并非同一要求

R06 建议从已有操作规程、支持脚本与政策文档中整理流程，明确每一步的动作与输出，并处理常见的信息缺失情况。〔[R06，Configuring instructions，PDF p. 11](#ref-r06)〕

R07 反对把复杂业务全部压进一个脆弱的全局 Prompt。两篇文章重点不同，不能假装提供完全一致的提示词策略。

**工程解释：**稳定流程可以明确编写，但应放在合适范围内。全局指令保存长期有效的边界；具体业务方法按需加载；工具契约负责参数与返回语义；必须保证的权限与前置条件由后端执行。这个分层是综合材料的设计建议，不是某一原文的统一架构。

### 7.5 五种工作流模式，其实是五种信息流组织

R02 区分预定义代码路径的 Workflow 与由模型动态决定路径的 Agent，并介绍五种可组合模式。〔[R02，What are agents?／Workflow 各节](#ref-r02)〕

| 模式 | 原文的组织方式 | 本文从上下文角度的解释 |
|---|---|---|
| Chaining | 固定步骤串行，中间可以加入 gate | 一次调用聚焦一个阶段，只传递已验证交接内容 |
| Routing | 分类后进入专门处理流程 | 不让所有输入共享全部指令与工具 |
| Parallelization | 独立分工，或同题多次尝试 | 隔离不同角度，最后聚合 |
| Orchestrator-workers | 模型动态拆分、委派、综合 | 根据当前任务创建局部工作上下文 |
| Evaluator-optimizer | 生成与评价反馈交替 | 把评价结果变成下一轮修改依据 |

原文特别区分固定并行与动态委派：前者的子任务可以预先确定，后者由模型根据任务具体情况决定。

但分阶段不自动提高正确率。如果第一阶段遗漏了证据里的“仅适用于某期间”，第二阶段可能非常稳定地得出错误结论。**工作流边界应交接可核验的信息，不只是上一个模型的结论。**

### 7.6 多次采样与评价器不创造真值

ReAct 论文将内部推理多次采样与外部检索结合，展示了互补价值。〔[R01，Combining Internal and External Knowledge，PDF pp. 5–6](#ref-r01)〕

**工程推导：**多个答案一致，是一致性信息；外部材料支持答案，才是事实依据。评价器若与生成器共享同一个错误前提，可能反复确认错误。高风险结论不能仅靠“另一个 Agent 也同意”验收。

这一点也为 R11 的并行采样讨论建立边界：横向增加尝试可以提高覆盖，但其收益与成本必须在真实任务上衡量。

## 8. 有限上下文：窗口容量、累计成本与有效性不是一回事

### 8.1 模型每一步看到的，是系统构造出来的视图

在 ReAct 的表示上，可加入如下**工程抽象**：

$$
c_t=G(\text{目标},\text{约束},\text{当前状态},\text{历史},\text{检索证据},\text{工具定义};B)
$$

$G$ 是上下文组装逻辑，$B$ 是预算。它不是 ReAct 原论文的新增定理，而是用于明确工程师能够控制的部分。

模型参数相同，$G$ 不同，模型做下一步决策时面对的信息就不同。R07 把 Context Engineering 定义为在推理时持续选择与维护可用信息；R08 则把它落实为每轮运行的组装管线。〔[R07，Context engineering vs. prompt engineering](#ref-r07)；[R08，Context Assembly](#ref-r08)〕

### 8.2 窗口里不只是用户文档

讲义第 44 页的**示意预算**包含系统 Prompt 约 2K、工具定义约 6K、检索内容约 25K、项目环境约 8K，以及持续增长的历史约 80K。这不是建议每个系统采用的配置，而是说明各类内容共同占用容量。〔[L04，PDF p. 44](#ref-l04)〕

优化时不能只盯用户输入。工具定义、旧日志、重复文件、过去计划，都可能占据大量空间。

### 8.3 三种不同限制

**容量限制：**输入和生成需求是否能被模型接口接受？

**资源限制：**整个任务的输入、输出、工具、压缩、延迟与运行时间消耗多少？

**有效性限制：**模型能否在已有内容中找到并正确使用必要信息？

讲义第 42–43 页把 cost、latency、attention 放在一起；R10、R09、R11 则分别提供不同任务中的有效性证据。〔[L04，PDF pp. 42–43](#ref-l04)〕

“支持长窗口”只说明容量的一部分，不能替代对信息利用与长期行为的评测。

### 8.4 历史反复带入为什么会推高累计输入

做一个明确假设下的推导：初始上下文 $P$ 个 Token，每轮增加 $m$ 个 Token，运行 $N$ 轮，每轮都逻辑上携带此前全部内容。因此前三轮输入依次为 $P$、$P+m$、$P+2m$；第 $N$ 轮是 $P+(N-1)m$。把每轮输入相加，固定部分共 $NP$，新增部分是 $m[0+1+\cdots+(N-1)]$，由等差数列求和得到累计输入：

$$
\sum_{t=0}^{N-1}(P+tm)=NP+\frac{mN(N-1)}{2}
$$

例如 $P=1000$、$m=200$、$N=3$，累计输入是 $1000+1200+1400=3600$，而最后一轮窗口只有 1400 个 Token。后半项随轮数二次增长。这是**重复携带历史的累计量**，不是 Transformer 注意力复杂度，也不是所有平台的最终计费公式。

第一轮进入的一万行无关日志，可能在后续许多轮持续带来成本与干扰。因此，入口控制的收益可能大于最后一刻才做一次摘要。

### 8.5 不要用一个复杂度公式解释所有 Context Rot

R07、R08 会用注意力与长序列成本解释为何上下文需要管理。但不能仅凭密集注意力的成对关系数量，数学推出某个模型的答案准确率一定按固定曲线下降。

**概念边界：**计算复杂度、记忆占用、训练分布、位置敏感性、状态冲突和停止策略是不同因素。后面三篇论文研究不同现象，不能全部用“注意力被均分了”代替解释。

同样，缓存优化与上下文质量是两个目标。缓存可能改善重复内容的处理成本，却不会自动删除无关信息或修正事实冲突。本文不涉及任何平台当前的缓存计费与接口保证。

### 8.6 为继续行动留出空间

讲义第 49 页明确要求预留输出空间、保留系统前缀、重新注入关键事实。〔[L04，PDF p. 49](#ref-l04)〕

**工程推导：**预算检查不应只看“现在输入是否小于上限”，还要考虑下一次生成、即将返回的工具结果，以及必要的状态整理。已经完全占满的窗口，可能连继续获取关键证据或生成可靠摘要的余量都没有。

保留多少余量需要按目标模型、任务和结果大小测量；本课程没有给出所有场景都适用的固定百分比。

## 9. Lost in the Middle：证据在窗口里，仍然不一定被正确使用

### 9.1 先区分两类失败

RAG 回答错误，可能是根本没有检索到证据，也可能是证据已经进入窗口，但模型没用对。R10 通过受控实验重点研究第二种问题。〔[R10，§2，PDF pp. 3–5](#ref-r10)〕

这里的问答检索 Recall@K 通常按“前 K 份文档至少包含一份答案证据的问题，占全部问题的比例”计数；它与第 3 章逐任务统计必要文件覆盖率的单位不同，读基准时要先核对分母。两者都只测找回证据。这对工具设计很关键：不能仅用检索 Recall@K 说明 Agent 已经获得可靠回答能力。

### 9.2 多文档问答实验怎样控制变量

论文构造包含 $k$ 份文档的输入，其中一份含有答案，其余是干扰材料。保持问题与正确答案不变，分别改变答案文档的位置，以及加入的干扰文档数量。这样可以研究位置和长度对模型利用信息的影响。〔[R10，§2.1、Figures 2–4，PDF pp. 3–4](#ref-r10)〕

研究使用的是当时的 GPT-3.5-Turbo、Claude-1.3、MPT、LongChat 等模型。论文观察到，多种设置下相关信息位于首尾时表现较好，位于中间时表现较差。第 5 页 Figure 5 展示不同文档数量和位置下的曲线。〔[R10，§2.2–2.3、Figure 5，PDF pp. 4–5](#ref-r10)〕

**边界：**这不是所有模型、所有任务都会严格遵守的 U 形定律，也不表示把全部重要内容移到开头就解决了长上下文问题。

### 9.3 UUID 键值实验：进一步拆掉语义推理

为了区分“理解问题困难”与“简单定位困难”，研究者又构造随机 UUID 键值对，要求返回指定 key 对应的 value。随机字符串尽量减少自然语言语义带来的干扰。〔[R10，§3，PDF pp. 6–7](#ref-r10)〕

结果存在模型差异：部分模型在这种简单匹配任务上接近完美，另一些仍对位置和长度敏感。因此，“能通过找针测试”与“能完成多文档问答”不是同一能力。

**工程推导：**长上下文评测至少应区分精确查找、语义消歧、跨材料推理与动态状态维护。不能用一种测试的高分替代所有场景。

### 9.4 提前放问题为什么不是通用修复

论文测试 query-aware contextualization，把查询放在数据前后，使模型在处理材料时已能看到查询。这个改法对 UUID 键值查找显著有效，但对多文档问答的位置敏感性改善有限。〔[R10，§4.2、Figure 9，PDF pp. 7–8](#ref-r10)〕

这给工程师一个重要提醒：**一个在合成查找任务中有效的 Prompt 改法，不应直接宣称对复杂检索推理同样有效。**

实际需要做的是，按照你的文档、问题、答案和证据类型重新测量。任务不同，信息之间的关系与干扰方式也不同。

### 9.5 模型结构与指令微调的分析也有边界

先用数据流区分结构：编码器—解码器模型先让编码器读取输入，解码器再据此逐步生成输出；仅解码器模型则在同一生成序列中根据前面的 Token 预测下一个。前者的输入编码可以使用双向上下文，后者的因果注意力可读取当前位置及之前的输入、不能读取未来位置；当前位置的表示用于预测下一个 token。这是理解位置实验所需的最小差别，不能据此直接判定哪种架构更强。

论文比较编码器—解码器模型与仅解码器模型，发现部分前者在训练长度范围内对位置较稳健，但超出训练长度后同样可能呈现位置敏感性。论文也观察到，某些基础模型在没有指令微调时已经呈现相似趋势。〔[R10，§4.1、§4.3，PDF pp. 7–9](#ref-r10)〕

这意味着不能把位置偏差完全归因于“指令通常写在开头”，也不能仅凭架构名称判断真实效果。原文给出的是特定模型上的分析，而不是完整的因果解释。

### 9.6 检索召回持续增加，回答表现却先饱和

第 10 页 Figure 11 比较返回文档数量与检索召回、模型表现。作者发现，阅读模型的表现比检索召回更早趋于饱和；从 20 增加到 50 份文档，在其被测模型上带来的增益有限，却增加输入长度。〔[R10，§5、Figure 11，PDF pp. 9–10](#ref-r10)〕

这与 Sourcegraph 的上下文管线互相补充：先广泛获得候选以保证覆盖，再合并、重排、去重并控制进入模型的内容。〔[R08，Context Assembly／Token Budget Management](#ref-r08)〕

**工程推导：**评测应分别回答“证据是否被找到了”与“模型是否使用正确证据”。如果证据已在候选里，继续扩大 Top-K 可能不是最有效的修复；需要检查排序、冗余、结构和证据表达。

### 9.7 对两类任务的迁移

编码任务中，返回 50 个提到同一函数名的文件，可能不如返回定义、真实调用点与失败堆栈；文档核验中，十份相似营销案例也不能替代当前材料的原文与对应数据。

这是从论文与工程文章推导的设计方向，不是论文已在这两个具体任务上验证的结果。其共同原则是：**提高证据可用性，而不只是提高材料数量。**

## 10. Context Pruning：当前局部状态与全局进度必须同时保留

### 10.1 任务：将票据逐项录入真实业务系统

R09 的核心实验是在 Dynamics 365 Finance and Operations 中进行酒店费用明细拆分。Agent 需要创建明细、映射类别、填写金额，并使未分配金额为零；工具返回大量表单状态、字段信息和导航内容。〔[R09，§3.1–3.2，PDF pp. 3–4](#ref-r09)〕

论文第 6 页 Figure 1 的示例总额为 333.05 美元，其中 Hotel Tax 出现两次，金额分别为 6.82 与 10.23 美元。类别名称重复不代表是同一条记录；录入了一个税费条目，也不代表所有税费已处理。〔[R09，Figure 1，PDF p. 6](#ref-r09)〕

**先分清业务目标与评分覆盖。**论文附录 C 的自动评分通过独立回读系统检查金额与条目数；其中 Completely Itemized 的判定是 `remaining_amount == 0.00`。这个指标验证金额已分配完，不单独证明每条类别映射、原始票据对应关系都正确。因此下文“完全完成率”应理解为该金额指标的达标率；用于真实业务验收时，还需另查逐项对应与类别正确性。〔[R09，Appendix C，PDF p. 11](#ref-r09)〕

这里与 Lost in the Middle 的差异是：**信息不只是静态地藏在某个位置，表单状态还在不断变化，旧观察可能已经失效。**

### 10.2 四个配置与真正可比较的部分

| 配置 | 主要差异 | 应怎样理解 |
|---|---|---|
| C1 | GPT-5，无用户模拟模型 | 用于展示无人回答澄清问题时的停滞，不是干净的上下文对照 |
| C2 | 加用户模拟模型，保留全历史 | 上下文策略的基线 |
| C3 | 同样有用户模型，保留最近 5 组工具调用／结果 | 检验近期窗口 |
| C4 | 同样有用户模型，近期窗口＋较早交互摘要 | 检验摘要对全局进度的补充 |

论文明确强调，C2–C4 保持用户模拟模型相同；C1 与其余配置在交互机制上不同，因此不能把 C1 到 C4 的全部提升归因于上下文工程。〔[R09，§3.3，PDF p. 4](#ref-r09)〕

这也是实验设计最重要的一课：**同时换了模型或交互机制，再换上下文策略，不能用最终成绩解释单项贡献。**

### 10.3 主要结果：按任务集总成本理解数字

| 配置 | 完全完成率 | 总 Token／整套 50 任务 | 总耗时／整套 50 任务 |
|---|---:|---:|---:|
| C1 | 8.0% | 约 532,600 | 3.08 小时 |
| C2 | 71.0% | 1,480,996 | 14.56 小时 |
| C3 | 79.0% | 535,274 | 5.39 小时 |
| C4 | 91.6% | 553,374 | 5.79 小时 |

来源：R09，PDF p. 7，Table 2；结果为同一套 50 任务、5 次独立运行的平均。C1 Token 取表中千位精度。以上 Token 不是单次窗口长度，也不是单项任务耗费。〔[R09，Table 2、§4.4–4.5](#ref-r09)〕

在该设置下，裁剪同时减少成本并提高完成率；摘要在较小额外开销下进一步改善完成率。但这不代表任意任务都能得到同等收益。

### 10.4 更有解释力的是失败类型变化

| 失败类型 | C2 全历史 | C3 近期窗口 | C4 近期＋摘要 |
|---|---:|---:|---:|
| 使用过期状态 | 34 | 6 | 4 |
| 类别映射错误 | 8 | 9 | 6 |
| 重复或跳过重复条目 | 12 | 11 | 5 |
| 过早终止 | 9 | 18 | 3 |
| 工具／表单导航错误 | 6 | 5 | 2 |
| 残留金额不匹配 | 4 | 4 | 1 |
| 未完成总数 | 73 | 53 | 21 |

来源：R09，PDF p. 9，Table 5；计数为 5 次运行中失败 task-runs 的汇总。这里按表格记录数字，不把正文中个别倍数措辞当作额外证据。〔[R09，§5、Table 5](#ref-r09)〕

删除旧表单快照后，过期状态错误明显减少；但只保留近期交互时，过早终止从 9 增到 18，因为模型更容易失去整体进度。加入摘要以后，过早终止减少到 3。

因此，摘要的作用不是把旧表单重新原样装回去，而是保留“还剩多少、哪些条目已完成、哪些步骤尚未验证”等全局信息。

论文将二者归纳为两条互补信息通道：**近期工具交互提供当前局部状态，摘要提供全局任务进度。**〔[R09，§6.2–6.3，PDF pp. 9–10](#ref-r09)〕

### 10.5 为什么是最近 5 组，为什么还需要摘要窗口

论文根据任务结构解释 $N=5$：一条明细通常需要两至三次工具操作，近期五组大致覆盖两个局部操作周期。$W=3$ 则用于选取裁剪边界附近的较早内容供摘要使用，不是“每三轮才压缩一次”。〔[R09，§3.3–3.4，PDF pp. 4–5](#ref-r09)〕

**需要保留的实现边界：**正文以 interactions 描述摘要输入，而 Algorithm 1 中的 $E$ 是消息列表，并按最后 $W$ 个元素截取。本文不把这个差异擅自改写成一个已验证的“严格三组完整调用对”实现。逐行复现应进一步对照作者代码；本文的工程方案明确以完整交互单元处理，不声称复现该算法的所有细节。

可迁移的思想不是固定 `N=5, W=3`，而是：**窗口覆盖当前局部操作周期；另外保存不能从局部窗口恢复的全局进度。**

### 10.6 为什么它不是普通 Token 压缩

论文强调以整个工具调用／结果单元保留或剔除，而不在仍需精确读取的表单内容内部随意删除 Token。其原因是字段名、控件名和数字余额可能需要原样使用。〔[R09，§2，PDF pp. 2–3](#ref-r09)〕

**工程推导：**对于代码锚点、金额、日期、引用位置和参数标识，应优先保证精确性；可以摘要探索过程，但不应把必须逐字操作的对象随意压成自然语言。

“在语义层保留完整交互”与“在 Token 层删掉低信息内容”，不是同一算法，也面对不同风险。

### 10.7 扩展实验与外推边界

论文还报告其他费用类别与另一模型家族的结果。其设置下 Travel 和 Meals & Gifts 也观察到近期窗口加摘要的改善；Sonnet 4.5 在无用户模拟模型时没有呈现 GPT-5 同样严重的停滞，进一步说明 C1 的问题具有模型相关性。〔[R09，§4.8–4.9、Table 4，PDF pp. 8–9](#ref-r09)〕

不过，这仍是 ERP 费用类流程，不能直接推广到开放搜索、代码修复或投研。尤其是“只保留最新状态”对当前表单有用，却不能自动用于需要比较历史变化的任务。

### 10.8 数字不能被过度解释

论文报告了多次运行的离散程度与置信区间，但没有把一套固定任务的结果变成所有业务系统的可靠性保证。它也说明，现有研究范围以该类工具交互为主。〔[R09，§4.6、§6.4，PDF pp. 7–10](#ref-r09)〕

**本文的方法论提醒：**输出 Token 数相近，不足以证明模型“推理深度相同”；更高完成率也不证明所有类别映射错误都已解决。应看独立读回的业务状态、具体错误类型和测试条件。

<a id="chapter-11"></a>
## 11. Context Rot：上下文管理会改变停止行为和总探索量

### 11.1 这份 Context Rot 不是 Chroma 那份报告

归档的 R11 是 *Diagnosing and Mitigating Context Rot in Long-horizon Search*，研究多轮搜索任务；讲义第 43 页图中还提到 Chroma Context Rot，它们不是同一来源。本文关于搜索终止行为的数字与定义来自 R11，不能移用为 Chroma 实验结果。〔[L04，PDF p. 43](#ref-l04)；[R11，PDF pp. 1–3](#ref-r11)〕

R11 关注的历史不仅包括外部资料，还包括多轮查询、浏览、失败尝试与模型产生的内容。因此它不只是单次长文档阅读问题。

### 11.2 窗口没满，Agent 已经停止：先分清终止状态

| 类别 | 论文定义的要点 |
|---|---|
| Give up | 明确表示无法解答，并未提供清楚答案 |
| Uncertain answer | 给出明确答案，但结束前的推理内容表示仍有未解决疑点 |
| Confident answer | 给出明确答案，并认为满足用户要求 |
| No answer | 达到上下文或交互预算限制，未给出答案 |

再结合答案正确与否，论文形成 Confident Correct、Uncertain Correct、Confident Incorrect、Uncertain Incorrect、Give Up、No Answer 六种统计结果。过早终止率 PT 定义为 Give Up 与 Uncertain Incorrect 的比例之和，不是所有不确定回答的比例。〔[R11，§3.2、Tables 1–2，PDF pp. 4–6](#ref-r11)〕

这里的 confident 是轨迹表现出的自信，不是经过校准的正确概率。

论文使用模型评审，并通过人工标注检查一致性；实际筛选候选答案时不提供金标准答案，以避免把评测答案泄漏给选择器。〔[R11，§3.2、§4.2，PDF pp. 4、10](#ref-r11)〕

### 11.3 长轨迹是不是仅仅因为问题更难

研究对每个问题采样五条轨迹，按长度排序，然后把每个问题同一排序位置的轨迹组成一组。不同组包含相同问题集合，平均轨迹长度不同，再比较 PT。作者观察到控制问题集合后，PT 仍与上下文长度正相关。〔[R11，§3.3，PDF pp. 6–7，Figure 4](#ref-r11)〕

**方法论边界：**这种方式控制了问题难度构成，但没有随机指定轨迹长度。失败探索也可能同时增加长度与终止倾向。因此，不应把该结果单独写成“任何长上下文都会因长度导致放弃”的完整因果证明。

### 11.4 七种管理策略分别改了什么

论文把干预分为三类、七种：

| 类别 | 变体 | 原文实验中的关键设置 |
|---|---|---|
| Compaction | 按长度摘要 | BrowseComp-Plus 96K，另两个数据集 32K |
| Compaction | 按轮数摘要 | 10 个交互轮次 |
| Compaction | 按语义摘要 | 最近 10 轮中 struggle score 达到 0.5 |
| Trimming | Discard | 达到阈值后只保留最后工具结果，其余旧结果删除 |
| Trimming | Keep Latest | 保留最近 3 个交互轮次的工具结果 |
| Trimming | Keep Latest＋summary | 近期保留与达到长度阈值后的摘要结合 |
| Isolation | FoldAgent | 主 Agent 调用子任务，接收其概括结果 |

实验还使用每种方法最多 100 个交互轮次，并重复运行；具体设置属于论文，不是生产默认值。〔[R11，§4.1，PDF pp. 7–8](#ref-r11)〕

语义触发中的 struggle，指重复失败尝试或缺少进展的轨迹表现，不是关于模型具有真实情绪的主张。

### 11.5 主要结果：压缩可以让系统继续工作，也可能更贵

以下选取 Qwen3.5-397B-A17B 在论文 BrowseComp 设置下的结果。

| 策略 | 准确率 | 平均工具调用数 | PT | No Answer |
|---|---:|---:|---:|---:|
| ReAct | 35.0% | 21.7 | 53.4% | 0.0% |
| Summary，Length | 46.6% | 57.7 | 2.4% | 38.0% |
| Summary，Turn | 46.6% | 53.7 | 1.8% | 38.4% |
| Keep Latest | 43.8% | 40.5 | 33.8% | 4.2% |
| Keep Latest＋summary | 48.2% | 46.8 | 16.2% | 17.6% |
| FoldAgent | 54.0% | 57.4 | 6.4% | 30.4% |

来源：R11，PDF p. 8，Table 3。论文 BrowseComp 使用其选定的 100 题子集，不能把此表称为所有产品在完整公开榜单上的成绩。〔[R11，§3.3、Table 3，PDF pp. 5、8](#ref-r11)〕

结果中的重要现象是：一些原本提前结束的轨迹现在得以继续探索，准确率提高；但总调用增加，另一些轨迹一直工作到预算耗尽。

作者将上下文管理解释为一种 test-time scaling：降低峰值上下文负担，让更多探索实际发生。它不是单纯的输入压缩技术。〔[R11，§4.1 Main Results，PDF p. 8](#ref-r11)〕

### 11.6 为什么与 Pruning 的“更快、更便宜”并不矛盾

R09 的流程结构较明确，旧表单状态多且可能有害，裁剪可以减少无价值处理。R11 的困难之一是尚未找到证据就停止，管理上下文可以使轨迹继续探索。

用如下**工程成本分解**理解：

$$
C_{\text{task}}=\sum_t C_{\text{model},t}+\sum_j C_{\text{tool},j}+C_{\text{management}}+C_{\text{coordination}}
$$

单轮更便宜，不代表总轮数不变；更多摘要与子任务也有成本。因此，真正比较对象是任务成功率、总费用和总延迟，而不是某轮输入长度。

这是一种对两篇材料差异的解释，不是它们使用了相同的成本测量方法。R11 主要用工具次数作为成本代理，R09 还报告 Token 与墙钟时间。

### 11.7 更强的上下文隔离，需要模型会使用它

R11 三个基准的平均准确率中，Qwen 的 FoldAgent 为 64.9%，高于其 ReAct 的 54.4%；GLM-4.7 的 FoldAgent 为 57.5%，未超过其部分被动摘要或裁剪组合。作者据此提出模型相关的策略选择。〔[R11，Table 3 与 §4.1，PDF pp. 8–9](#ref-r11)〕

这不能被理解为对所有任务永久评定某模型更强，而是说明在该实验中，主动决定何时委派、如何描述子任务、如何利用结果，是额外能力要求。

**工程推导：**增加子 Agent，不只是增加计算资源，也增加了新的动作选择与交接负担。架构复杂度本身不是收益。

### 11.8 横向采样与纵向延长：预算还可以换一种用法

论文对每题采样多条完整轨迹，用最少轮数、最短轨迹和多数投票等方式聚合，并在聚合前过滤放弃或存在未解决疑问的轨迹；没有剩余候选时回退原来的选择方式。该过滤在其设置中改善了多种聚合方法。〔[R11，§4.2、Table 5，PDF pp. 9–10](#ref-r11)〕

第 9 页 Figure 5 将工具调用数放在成本横轴，比较并行采样与上下文管理的组合。在过早终止较不严重的任务上，简单 ReAct 加并行尝试可以接近甚至超过一些更复杂策略。〔[R11，Figure 5、Integration and Comparison，PDF pp. 9–10](#ref-r11)〕

它与讲义 Self-consistency、R02 Voting 的连接是：预算可以用于延长一条轨迹，也可以用于增加独立尝试。应比较单位资源带来的真实效果。

**不能直接迁移的部分：**不要把论文筛选规则变成“生产中删除所有不确定回答”。研究、核验等任务可能必须保留证据缺口；自信也不等于正确。应核验证据，而不是鼓励隐藏疑问。

### 11.9 论文自己承认的适用范围

R11 的研究集中在所选开源模型与长程搜索任务，作者明确表示是否完全适用于软件开发等其他长期任务仍不确定。〔[R11，Limitations，PDF p. 10](#ref-r11)〕

因此，这篇论文提供的是失败诊断方法与实验启发，不是所有 Agent 应强制采用某一种压缩器、子 Agent 或并行度的证明。

<a id="chapter-12"></a>
## 12. 四种上下文管理操作：先知道失败在哪里，再选择处理方式

### 12.1 讲义的四分法

讲义依次提出 Admission、Offloading、Transformation、Compaction，并用“从预防、可恢复到有损处理”的方向组织它们。〔[L04，PDF pp. 45–49](#ref-l04)〕

| 操作 | 首要问题 | 常见实现 | 主要风险 |
|---|---|---|---|
| Admission | 什么不该现在进入？ | 定向检索、输出整形、范围控制 | 筛掉关键证据，或让部分结果伪装成全部 |
| Offloading | 什么不必一直常驻？ | 外部文件、稳定句柄、按需工具定义 | 找不回来、权限失效、版本混淆 |
| Transformation | 哪些旧表达应删除或替换？ | 去重、状态替换、观察遮蔽、近期窗口 | 删除长期约束或破坏调用协议 |
| Compaction | 如何用较短表示继续工作？ | 历史摘要、关键事实、持续笔记 | 丢限定条件，把猜测写成事实 |

它们可以组合，但不能只按上下文长度机械触发。先判断信息是当前状态、历史证据还是任务进度，再决定操作。

### 12.2 Admission：最有效的优化可能是让无关材料不进来

讲义第 46 页用原始 DOM 与提取后的价格、标题作教学对比；其数字是幻灯片示意，不是本文项目实测。R12 则给出过滤、分页、范围选择与截断的工具设计方法。〔[L04，PDF p. 46](#ref-l04)；[R12，Optimizing tool responses](#ref-r12)〕

**工程建议：**先按对象与问题缩小范围，再选择必要字段或片段，最后才做长度截断。测试日志应优先提取失败用例、异常堆栈和退出状态，而不是机械截取最前面的若干行。

与此同时保留扩大范围、查看邻近内容与读取原文的方式。入口控制过度，会让模型永远看不到能够推翻当前假设的信息。

一个实用问题是：这段内容进入后会影响哪项决策？暂时不会影响，就考虑保持可检索，而不是常驻。

### 12.3 Offloading：保持可获取，而不是始终在窗口里

讲义第 47 页包括渐进式工具定义、工具搜索、结果外置、任务列表和持久笔记。R07 的 just-in-time retrieval 同样强调先保存轻量引用，需要时再加载。〔[L04，PDF p. 47](#ref-l04)；[R07，Context retrieval and agentic search](#ref-r07)〕

工程示例：

```json
{
  "handle": "artifact:test-run-42",
  "kind": "test_log",
  "workspace_revision": "workspace-v18",
  "summary": "存在失败用例；当前展示并非全部日志",
  "available_views": ["failures", "tail", "range", "full"]
}
```

一个可用外置对象应能定位、读取、辨别版本，访问权限仍有效，模型也知道用什么工具读取。只返回一个无解释的文件名，不足以成为可用记忆。

R07 同时承认运行时探索会增加延迟，因此可以预加载少量稳定信息，再按需扩展。**按需加载是一种取舍，不是所有信息都越晚加载越好。**

### 12.4 Transformation：分清可被替代的状态与不能删除的证据

讲义列出保留对象最新状态、清理旧工具结果与滑动窗口。R09 的实验解释了为什么旧表单快照可能主动误导。〔[L04，PDF p. 48](#ref-l04)；[R09，§6.2](#ref-r09)〕

但以下三类信息不能按同一标准处理：

**状态快照：**当前文件内容、当前表单余额、当前页面布局。新状态可能替代旧状态。

**历史证据：**以前财报、旧版本条款、某次失败测试。只要任务需要比较或溯源，旧并不等于无用。

**任务约束与经验：**不改变公开 API、已经排除的假设、下一步待验证事项。即使很早出现，也可能持续有效。

Weng 对记忆检索讨论相关性、新近程度与重要性。它补充了固定近期窗口的边界：新近程度只是信息价值的一个信号。〔[R05，Generative Agents 的 Memory／Retrieval](#ref-r05)〕

### 12.5 不要把裁剪单位简单定义为“最近几条消息”

下面的代码只是常见反例，不是推荐实现：

```python
messages = messages[-10:]
```

**工程分析：**它可能删除目标，留下没有对应请求的工具结果，或把一次包含多个工具调用的响应拆开。一个协议完整的交互单元，至少应关联发起请求的模型消息与对应结果；异步和并行调用还需要处理未关闭的请求。

R09 的“完整工具调用／结果”思想值得借鉴，但它的伪代码没有替你解决任意平台的批量调用协议。实现时应对照实际协议，而不是机械按消息计数。

任务目标、约束、进度和证据索引最好单独维护，再明确加入活跃上下文，而不是依赖它们碰巧落在近期窗口。

### 12.6 Compaction：压缩的是历史表达，不是事实准确性

R07 建议先保证相关信息召回，再逐步减少冗余。R09 说明摘要需要补充全局进度，而不只是缩短文本。〔[R07，Compaction](#ref-r07)；[R09，§6.3](#ref-r09)〕

普通文章摘要回答“主要讲了什么”；工作摘要回答“还要怎样继续”。以下为工程模板：

```text
目标与约束：必须完成什么，哪些边界不能改变。
已验证事实：事实、来源引用、对应时间或版本。
尚未证实的解释：候选判断及尚缺的证据。
当前状态：已完成、进行中、待执行，以及当前工作区版本。
失败与排除：尝试过什么，为什么无效。
待确认操作：哪些动作仍需用户或外部批准。
下一步：最重要的证据缺口或验证动作。
```

不要将“可能是请求标识变化”压成“根因是请求标识变化”。压缩器没有因为被安排做摘要，就获得确认事实的权限。

**工程推导：**摘要中的关键事实应有证据引用；原始记录单独保存；后续发现冲突时能回到原文。摘要是工作视图，不是取代原始事实的最终数据库。

### 12.7 Compaction 是第一项杠杆还是最后手段

讲义第 49 页称 LLM compaction 为 last resort，R07 则在长期任务中把它称为 first lever。原文用语确实存在差异。〔[L04，PDF p. 49](#ref-l04)；[R07，Context engineering for long-horizon tasks／Compaction](#ref-r07)〕

**本文的工程解释：**新系统应先减少无关信息进入；已有很长会话需要继续时，压缩可能是最直接的连续性机制。这个解释帮助选择实现顺序，但不把两份来源改写成同一优先级。

同样，讲义图的左侧并不意味着所有 Admission 都严格无损：截断可能丢内容，外置也只有在可以准确恢复时才保留信息可用性。应审查具体实现，不根据方法名称保证安全。

### 12.8 用五类失败指导修复，而不是只问“窗口多长”

| 讲义术语 | 含义 | 工程检查方向 |
|---|---|---|
| Poisoning | 幻觉进入窗口，后来被当作事实引用 | 事实与假设分离；来源、版本与证据引用 |
| Distraction | 历史增长，Agent 模仿自己过去的动作 | 重复检测；保留失败原因而不是整段失败噪声 |
| Confusion | 无关工具或文档把任务带偏 | 检索与作用域；工具边界；入口筛选 |
| Clash | 新旧信息矛盾却长期不处理 | 当前状态标识；冲突核验；不要静默覆盖证据 |
| Drift | 原目标被埋没，换成了附近子目标 | 目标与完成标准持续可见；全局进度管理 |

术语来自讲义第 50 页；右列是工程推导。这里 poisoning 特指事实污染，不只指恶意提示注入。〔[L04，PDF p. 50](#ref-l04)〕

编码任务中，Agent 花了很多轮重构重试模块，却从未验证重复订单是否消失，就是 Drift 的例子。流程很忙，不代表目标在推进。

### 12.9 一套简单而完整的处理顺序

以下是本文的实现建议，不是被证明最优的通用算法：

```text
先检查目标、约束和当前状态是否完整；
再筛选与下一步相关的工具定义和证据；
将大型原始材料外置，并保留稳定引用；
去重被替代的状态，按完整交互单元处理历史；
仍超预算时，生成保留关键事实与进度的摘要；
再次检查协议完整性、证据可恢复性与生成余量；
再调用模型。
```

这个顺序的重点是把正确性要求放在“尽量缩短”之前。最终策略要通过第 16 章的受控实验选择。

## 13. Skills、MCP 与子 Agent：分别管理能力、知识和上下文作用域

### 13.1 先把四个概念放回循环

在 R15 讨论的工具接入路径中，MCP 帮助 Harness 发现并调用服务提供的能力；Skill 提供可读取的操作说明；Plugin 负责将相关文件打包分发；Agent loop 则把这些内容与用户任务组织到每次调用中。〔[R15，MCPs are just APIs in tools／Skills are just instructions／Plugins bundle skills](#ref-r15)〕

| 概念 | 在本文范围内的作用 | 不应误解为 |
|---|---|---|
| Tool | 获取信息或执行动作的接口 | 模型必须知道其全部内部实现 |
| MCP | 文章所讨论的标准化工具接入路径 | 接上协议后就自动具备正确业务判断 |
| Skill | 按需加载的操作与领域知识 | 微调、独立权限或必然独立的 Agent |
| Plugin | 打包分发相关能力与文件 | 自动保证内容正确、安全或适配所有环境 |

本文并不以这份解释替代完整 MCP 协议规范。R15 的重点是工具使用心智模型，而不是覆盖协议的全部对象和版本。

### 13.2 队列案例：技术数据正确，仍可能被业务解释用错

R15 的示例系统同时使用 NATS JetStream 与 Google Pub/Sub。Skill 说明每条事件进入其中一个 broker，订阅积压分布在两个系统中，因此只看一边并不完整；某些返回计数为 `null` 代表未知，不是零；清理之前还要判断积压是否正在自然消退。〔[R15，Skills are just instructions，队列 Skill](#ref-r15)〕

这一案例把工具与知识的分工讲得很清楚。工具可以准确返回每个系统的数据，但模型若不知道数据分布和指标口径，就可能得出错误总量或过度操作。

它与 R09 的类别映射错误相接：去掉旧状态可以减少一类错误，却不会自动教会模型业务口径。不同错误需要不同层的信息支持。

### 13.3 Progressive disclosure：知道存在，与实际加载是两件事

R15 描述的加载方式是：名称和简短描述进入索引；任务相关时读取 `SKILL.md`；需要具体细节再读取参考文件。加载包装器还可以记录使用情况、解析路径并返回小型目录索引。〔[R15，Skills are just instructions](#ref-r15)〕

这就是 Offloading 在程序性知识上的应用。它的价值不在 `.md` 扩展名，而在于保持可发现、可访问，避免所有知识永久常驻。

**工程推导：**入口描述负责“何时加载”，正文负责“怎样操作”，参考文件负责“更具体的细节”。三个层次不应各自重复全部内容。Skill 数量很多时，索引本身也会有成本，仍然需要发现和选择机制。

### 13.4 归档的 Agent Patterns 首页支持什么

R04 自述为参考站点而非完整教程，内容按单概念页面组织，强调 Markdown、来源和自包含文档。它与渐进式知识加载相契合。〔[R04，Agent Patterns／For AI agents](#ref-r04)〕

但本地归档是首页及导航，不是它链接的全部正文。本文只依据首页讨论资料组织方式，不把未提供页面中的模式、课程内容或效果当作已读证据。

这是处理任何参考资料时都需要保持的边界：**索引说明某项资料存在，不等于已经读到其中结论。**

### 13.5 “多个 Agent 改成 Skills”与“用子 Agent 隔离”为什么都可能合理

R15 作者报告，将某些专业 Agent 合并成一个 Agent 加按需加载的 Skills，可以减少会话分割造成的信息缺失。讲义和 R07 则强调，子 Agent 可以隔离复杂探索，让主 Agent 接收精简结果而不是几十次原始读取。〔[R15，Skills replace system prompts](#ref-r15)；[L04，PDF p. 24](#ref-l04)；[R07，Sub-agent architectures](#ref-r07)〕

这两种选择分别承担相反成本：单上下文共享信息容易，但噪声会累积；分上下文更专注，但交接可能缺信息。

**工程判断：**只是需要另一套领域知识，先考虑 Skill；需要并行大量探索、不同操作作用域或独立进度，再考虑子任务隔离。不要因为有五种知识就建立五个 Agent，也不要为了坚持单 Agent，把所有原始探索塞进主窗口。

### 13.6 子任务返回应是结果与证据，不只是一个自信结论

以下为工程交接模板：

```json
{
  "task": "检查重试路径是否复用请求标识",
  "status": "needs_more_evidence",
  "findings": [
    {
      "statement": "候选事实或观察",
      "evidence_refs": ["E12"],
      "revision": "workspace-v18"
    }
  ],
  "unresolved": ["尚未检查某个异步调用分支"],
  "recommended_next_step": "读取该分支并运行对应测试"
}
```

这里的字段是示例。重点在于让主 Agent 能检查范围、版本、证据与未解决部分。只返回“全部没问题”，会把探索细节和不确定性同时隐藏。

R11 的模型相关实验还提醒：能否决定何时委派、怎样描述子任务、怎样处理返回结果，需要单独评测。增加子 Agent 是新增策略能力要求，不只是新增算力。〔[R11，§4.1，PDF pp. 8–9](#ref-r11)〕

### 13.7 Manager 与 handoff 不应混同

R06 区分中央管理者把 Agent 当工具调用，与多个 Agent 之间移交执行控制。前者保留统一控制和用户交互，后者涉及执行权转移。〔[R06，Multi-agent systems／Manager pattern，PDF pp. 17–18](#ref-r06)〕

**工程推导：**一个核验任务如果需要统一汇总证据、统一对用户负责，中央协调往往更容易表达责任；但这只是设计选择，不能从拓扑直接推断质量。无论哪种方式，都要明确状态如何交接、谁能修改什么，以及谁确认完成。

### 13.8 Skill 的建议与强制约束，位置不同

R15 作者把部分运行经验从专门 Agent 的系统指令移到 Skill 中，让它们在其 Harness 中作为可权衡的操作指导；但作者也明确表示，必须保证的约束应留在工具层。〔[R15，Skills replace system prompts](#ref-r15)〕

**边界：**Skill 的消息位置与优先级由宿主实现决定，不是 Markdown 文件名天然具有一种全平台固定权限。本文不把作者平台的行为当作所有系统的协议规则。

对强制约束，模型生成 `confirm: true` 不足以证明用户已经授权。授权应来自可信的外部状态，并绑定实际操作内容与范围。模型可以请求审批、解释审批，不应自行创造审批事实。这是本文的工程安全要求。

<a id="chapter-14"></a>
## 14. Harness：维护真实状态，并验证“完成”这个声明

### 14.1 Harness 案例：同样模型、同样 Prompt，失败可以逐层定位

R03 的演示要求 Agent 给 Hacker News 的帖子点赞。最初它到达登录页，没有完成操作，却报告成功。作者保持模型与任务 Prompt 不变，逐步加入预算、上下文处理、验证、重试以及由程序管理的认证。〔[R03，开头与 What changed](#ref-r03)〕

| Harness 改动 | 演示中解决的问题 |
|---|---|
| 预算与上下文限制 | 避免无限运行和窗口溢出 |
| 独立验证与重试 | 识别未成功的事实，并能报告失败 |
| 程序处理认证 | 完成此前被登录阻断的操作 |

这里最重要的不是某个模型“最终也能成功”，而是区分各层责任。上下文处理没有替它登录；验证也没有直接消除认证障碍。验证首先带来的能力是**发现失败而不是虚报成功**。

这是作者演示的结果，不是任意模型和场景的可靠性保证。

### 14.2 三个“成功”不是一回事

**模型说成功：**生成了一段完成声明。

**工具说执行成功：**某个动作达到工具契约定义的后置条件。

**用户目标完成：**整个任务满足目标、约束和验证标准。

在编码中，补丁应用成功、测试命令执行完毕、重复订单问题正确修复，不是同一事件。在文档核验中，报告文件已生成、引用可打开、结论得到充分证据支持，也不是同一要求。

讲义第 5 页的最小循环在 final answer 时返回，是教学上的简化；R09 则通过独立读回保存后的表单状态评分，不依赖 Agent 自述。两者共同提示，生产验收需要额外完成验证。〔[L04，PDF p. 5](#ref-l04)；[R09，§3.5，PDF p. 5](#ref-r09)〕

### 14.3 四类状态，避免全部混在 messages 里

以下为本文的工程架构，不是某一论文提供的成品。

| 保存对象 | 内容 | 用途 |
|---|---|---|
| 完整事件记录 | 请求、调用参数、原始结果、错误、时间与版本 | 审计、排错、回放 |
| 任务状态 | 目标、约束、阶段、已完成与待验证事项、阻塞项 | 维持任务连续性 |
| 证据与产物 | 文件、日志、数据快照、页面图像及稳定引用 | 核验与按需读取 |
| 活跃上下文 | 下一步真正需要的工作视图 | 提供给模型决策 |

完整记录回答“发生过什么”；活跃上下文回答“下一步应知道什么”。不能因为不再发给模型，就把原始事件永久删掉；也不能因为事件必须保存，就让模型每轮读全部历史。

### 14.4 一个职责分明的循环

下面是 **Python 风格伪代码**。类和方法代表职责接口，未提供具体实现，不应当作可直接运行的 SDK。

```python
while run.within_budget():
    context = context_builder.build(
        goal=run.goal,
        constraints=run.constraints,
        task_state=run.task_state,
        closed_tool_turns=run.closed_tool_turns,
        evidence_index=run.evidence_index,
        tool_scope=tool_registry.allowed_scope(run),
        output_reserve=run.output_reserve,
    )

    proposal = model.generate(context)

    if proposal.requests_finish:
        verdict = verifier.check_goal_and_evidence(run, proposal)
        run.record_verification(verdict)

        if verdict.completed:
            return completed_result(run, proposal)
        if verdict.needs_user_or_environment:
            return blocked_result(run, verdict)

        run.add_actionable_feedback(verdict)
        continue

    results = executor.execute_with_guards(
        proposal.tool_calls,
        permissions=run.permissions,
        operation_store=run.operation_store,
        budgets=run.budgets,
    )

    run.record_closed_tool_turn(proposal, results)
    run.update_observed_state(results)
    run.detect_repetitions_and_stalls()

return budget_exhausted_result(run)
```

这段结构要表达的是：模型提出动作，Executor 检查与执行，Context Builder 组织下一轮输入，Verifier 检查完成声明，事件记录保存真实过程。

实际实现还需要处理模型响应同时包含文本与多个调用、异步任务尚未完成、接口返回异常等情况。上下文构建只能在协议允许的位置压缩或重排，不应破坏未完成调用的关联关系。

### 14.5 谁来更新“已完成”状态

**工程推导：**模型可以提出“我认为这个子任务完成了”，但关键状态应由执行结果和验证结果支持。例如只有测试实际运行且结果满足要求时，才将相应验证项标为通过；没有环境时标为阻塞，而不是让摘要自动写成通过。

对于无法完全自动验证的研究结论，可以记录“证据已检查”“数据口径仍待确认”“需要人工判断”等不同层次。不要强行把所有状态压成一个真假位。

这样可以阻止猜测在任务状态与摘要中被反复放大。

### 14.6 认证、授权与护栏不是同一件事

R06 要求将护栏与认证、授权、访问控制等软件安全机制一起使用，并根据工具的读写性质、可逆性、权限和影响评估风险。〔[R06，Guardrails／Tool safeguards，PDF pp. 24–27](#ref-r06)〕

R03 则通过将凭证与稳定认证步骤移到程序中，说明某些确定性工作无需反复交给模型处理。〔[R03，认证改动与 What changed](#ref-r03)〕

**工程推导：**自然语言“不要越权”不是权限系统。公开检索内容、工具输出或 Skill 也不能自行提高执行权限。风险越高，越需要把操作范围、前置条件与审批状态落到程序可检查的对象上。

### 14.7 如何判断 Agent 已经卡住

只看轮数不够。第八轮可能已经原地循环，第四十轮也可能仍在获得重要证据。讲义第 52 页转引的 Harness 改进包含重复与停滞检测，以及卡住后的干预。〔[L04，PDF p. 52](#ref-l04)〕

以下是工程观测信号：相同参数得到相同结果；围绕已否定假设重复探索；连续没有新证据或状态变化；反复出现同一种参数或权限错误；多次声明完成却无法通过同一验证项。

检测后可以重新读取最新状态、收窄问题、切换检索方式、隔离探索或请求用户澄清。并非任何停滞都应该通过增加 Token 解决。

### 14.8 停止状态要支持恢复与诚实交付

建议区分：完成、需要用户输入、需要授权、环境阻塞、预算耗尽、执行失败。最终输出要说明当前产物、已经核验部分、未解决事项与恢复入口。

R11 的过早终止分析不意味着生产系统必须永不停止。高质量停止既包括完成，也包括在真实阻塞下准确交还控制。**减少无意义早停，与诚实表达未完成，并不冲突。**

<a id="chapter-15"></a>
## 15. 两个端到端工程案例：把信息流与动作流同时设计出来

> 本章均为教学性设计示例，不是对真实代码仓库、实际基金材料或现行法规的审核，也没有运行对应业务任务。示例中的“应检查”不代表检查已经发生。

### 15.1 案例一：超时重试导致重复订单

#### 起点：先定义什么算修复

任务需要满足三项要求：重复订单问题得到针对性验证；公开 API 保持兼容；补充能够覆盖故障场景的回归测试。应将这些要求放入任务状态，而不是只在第一条用户消息中出现一次。

初始上下文可以包含任务契约、仓库入口、少量相关工具定义与已有错误信息。不需要一开始读取全部仓库、所有依赖文档与完整生产日志。

这对应讲义的简单起步、R07 的高信息量上下文和 R06 的先建立基线。

#### 定位阶段：让查询随着证据变化

有堆栈时直接沿调用链读取；有函数名时查定义与引用；只知道“重试”功能时，用字面与语义检索寻找候选。每一步记录定位理由与来源版本，真正编辑前读取当前文件。

模型应区分“观察到的调用行为”与“猜测的根因”。例如“发现一个重试分支”并不等于已经证明该分支会造成重复订单。

这对应 ReAct 的观察驱动查询，与 Sourcegraph 的结构检索。

#### 验证阶段：用测试区分候选解释

一个值得检查的场景是首次请求已经提交，但响应在返回前丢失；另一个是首次请求根本没有提交。二者恢复行为不同。

这里的重点是设计能区分假设的测试，而不是要求模型先认定幂等键就是唯一答案。测试返回应说明具体场景、预期、实际、工作区版本与日志入口。

这对应工具输出整形与“真实反馈纠正下一步判断”。

#### 修改阶段：精确前置条件，显式验证状态

编辑工具对路径、版本和匹配次数进行检查。失败则重新读取，不任意应用模糊替换。多文件修改先确认所有变更点，再审查 diff 范围。

修改后区分“补丁已应用”“相关测试已运行”“目标验证已满足”。其中任何一步尚未完成，都不能被摘要简化成“修复完成”。

这对应 ACI 防错、编辑工具选择与 Harness 验收。

#### 历史增长阶段：保留当前实现与全局进度

旧版文件全文和重复日志可以外置或替换；当前实现、最新失败结果、用户约束与尚未验证分支要保持清楚。

摘要应保留已经排除的解释，避免重复探索；原始日志仍可读取，防止摘要误写后没有证据回查。这对应 R09 的局部状态＋全局进度，以及讲义 Transformation／Compaction。

#### 结束阶段：提交证据，不提交自信

最终交付应能说明根因依据、实际变更、执行过的验证、环境限制与未验证部分。若没有条件运行完整测试，应明确这一点，不用流畅表述替代真实验证。

### 15.2 案例二：文档中的业绩表述核验

#### 明确任务边界

任务是检查表述与指定数据源是否一致，输出证据与差异，不是在缺乏法规或数据时直接判定所有合规问题。材料中存在图表、脚注或风险提示时，纯文本可能不足以表达完整语境，必要时应查看对应页面图像。

这呼应讲义的 Browser and visual feedback，以及 R13 关于图像需要通过多模态通道进入模型的说明。页面路径和图像文件名并不意味着视觉内容已经被检查。

#### 按表述建立待核验清单

初始工作状态保留材料版本、待核验表述索引和当前处理的原文片段。按需读取对应规则、案例和数据口径，而不是把全部历史案例与全部工具定义一次性放入窗口。

发现表述与确认表述需要的证据，是两个步骤。相似历史案例可以提示风险，但不能替代当前事实核验。

#### 工具契约首先消除口径歧义

设计时需要明确对象、份额类别、起止日期、计算口径、数据有效时间、单位和来源引用。实际需要哪些字段由业务数据规范决定，不能让模型靠猜测补齐。

以下为示例返回结构：

```json
{
  "claim_id": "C-07",
  "material_revision": "material-v3",
  "status": "needs_clarification",
  "source_fragment": {
    "page": 4,
    "text": "待核验的原始业绩表述"
  },
  "missing_inputs": ["具体区间起止日期", "份额类别"],
  "evidence_refs": [],
  "next_action": "先确认缺失口径，再查询指定数据源"
}
```

这个结构没有编造缺失数据，也没有把“无法计算”写成“不一致”。它体现工具语义与 Skill 业务解释的分工。

#### 每一项保留“原文—口径—数据—结论”关系

处理中的条目保留精确原文与必要邻近内容；已处理条目保存状态、证据引用和待补事项。全局进度应能回答总共有多少表述、哪些仍未核验，而不只是“已经审完大部分”。

数据、表述与规则版本可能分别变化。当前状态的更新不能静默抹去作为比较对象的旧证据。如果任务是比较新旧材料的变化，旧版本必须保留。

这就是 R09 近期窗口思想的迁移边界：财务历史不是“因为旧所以无效”的状态快照。

#### 验证与人工闭环

程序可以检查引用是否可定位、对象与版本是否一致、必要字段是否齐全；专业判断不足或存在争议时，进入人工复核。人工采纳／拒绝可以作为后续案例与评测反馈，但不能不经整理就当作对所有未来任务成立的规则。

这个闭环是本文的工程方案，不是对任何法律要求或真实基金数据的结论。

### 15.3 两个案例的共同结构与不同策略

| 设计对象 | 编码任务 | 文档核验任务 |
|---|---|---|
| 当前局部状态 | 最新代码与测试结果 | 当前表述、口径和核验状态 |
| 长期约束 | 兼容性、变更范围、验证要求 | 数据源、证据标准、版本要求 |
| 外部原始材料 | 完整日志、仓库文件、测试产物 | 原始文档、数据快照、页面图像 |
| 可以替换的旧状态 | 被新修改覆盖的文件快照 | 过期的处理状态或重复读取 |
| 不能随意删的历史 | 已验证失败与被排除解释 | 用于前后比较的真实历史证据 |
| 完成验证 | 变更与测试满足目标 | 证据链闭合或明确标出未验证项 |

可迁移的是设计原则，不是固定窗口大小、工具数量和 Agent 个数。

## 16. 评测、排错与迭代：证明改动有效，而不是证明系统更复杂

### 16.1 从能力基线开始，不要同时改变所有变量

R06 建议先用足够强的模型建立性能基线，再尝试较小模型替换部分环节，观察是否仍满足任务要求。R02 同样建议从尽可能简单的方案开始，只在必要时增加复杂性。〔[R06，Selecting your models，PDF p. 8](#ref-r06)；[R02，When and when not to use agents](#ref-r02)〕

这是避免错误归因的方法，不是要求每个请求永远使用最贵模型。如果同时换模型、加子 Agent、修改工具、增加摘要并改变测试集，就很难知道改善来自哪里。

### 16.2 两层测试：函数契约与 Agent 任务

工具单元测试检查给定参数是否产生正确结果、错误与前置条件是否按约定处理。Agent 任务评测则检查模型能否发现对象、选择工具、取得参数、解释返回值并完成任务。

R12 强调从原型和真实任务入手，运行评测、分析轨迹，再与 Agent 协作改工具；不能只测试已经给出精确标识、几乎没有决策难度的调用。〔[R12，How to write tools／Developing an evaluation](#ref-r12)〕

这也解释了为什么工具本身稳定，Agent 仍可能持续失败：缺陷可能发生在接口选择与语义理解，而不在函数执行内部。

### 16.3 将工具输出与上下文策略做交叉实验

以下为本文的实验设计建议：

| 工具输出 | 全历史 | 近期窗口 | 近期窗口＋摘要 |
|---|---|---|---|
| 原始返回 | 基线 | 单独测试裁剪 | 测试摘要能否补充进度 |
| 整形返回 | 单独测试入口控制 | 检查二者是否互补 | 测试综合策略 |

这个矩阵可以回答：摘要是否只是在补救糟糕输出？输出已经整形后摘要还值不值得？裁剪是否丢掉必要原文？大结果外置是否增加过多读取轮次？

尽量固定模型版本、任务、环境初始状态、工具权限、采样设置和总预算，并进行重复运行。R09 的 C2–C4 对照是控制变量的好例子。

### 16.4 质量、行为、上下文和成本要分别记录

| 维度 | 建议观察项 |
|---|---|
| 最终质量 | 任务完成、约束遵守、证据充分、产物可用 |
| 工具使用 | 选错工具、非法参数、口径错误、无效重复、恢复成功 |
| 信息获取 | 是否召回必要证据，是否遗漏相关对象 |
| 信息利用 | 证据已在上下文却未使用，是否被干扰材料带偏 |
| 状态一致性 | 是否使用过期版本、丢失进度、重复已经完成的动作 |
| 压缩质量 | 是否丢限定条件、制造事实、遗漏未解决事项 |
| 停止行为 | 成功、早停、阻塞、预算耗尽、虚假完成分别占多少 |
| 总资源 | 总输入与输出、工具调用、摘要和协调成本、总延迟 |

R12 建议记录工具次数、时间、Token 与错误，并检查原始轨迹；R10、R09、R11 分别说明信息利用、旧状态和终止分类为何不能只靠总成功率代替。〔[R12，Running the evaluation／Analyzing results](#ref-r12)；[R10，§2–5](#ref-r10)；[R09，§5](#ref-r09)；[R11，§3–4](#ref-r11)〕

### 16.5 三组论文提供三类压力测试

**位置与干扰测试，借鉴 R10。**保持问题和正确证据不变，改变位置；增加词语相似但答案无关的材料；分别观察检索与阅读能力。

**状态更新与压缩恢复测试，借鉴 R09。**同一对象变化多次，检查是否使用最新状态；中途裁剪后，检查是否记得长期约束、进度、重复条目与未完成事项。

**长期探索与停止测试，借鉴 R11。**加入连续无信息搜索、可恢复错误、较长任务与预算限制，观察是否循环、过早结束或在没有证据时声明完成。

这些是测试设计迁移，不是三篇论文已经给出了你的业务评测集。

### 16.6 错误归因要回到第一处失效

**工程排错方法：**先确认完成标准是否正确，再沿轨迹寻找第一处偏离，而不是只看最后回答。

没有找到证据，检查检索；证据已在场却忽略，检查排序与上下文；读到旧对象，检查版本；参数形状合法但口径错误，检查工具与 Skill；动作确实执行却没达到目标，检查契约和验证；摘要后忘掉约束，检查任务状态与压缩。

模型生成的解释可以辅助理解，但不是必然忠实的错误原因。R12 明确提醒需要阅读原始工具调用与返回，不能只相信模型对自己行为的反馈。〔[R12，Analyzing results](#ref-r12)〕

### 16.7 多种有效路径，不要把某条调用轨迹当唯一正确答案

R12 指出，任务可能有多条有效工具路径；评测不能过度规定精确调用顺序，否则会把合理替代策略误判为失败。它也强调保留未参与优化的测试集，检查工具与 Prompt 是否过拟合。〔[R12，Developing an evaluation／Collaborating with agents](#ref-r12)〕

**工程推导：**验收主要根据真实任务结果与必须遵守的约束。对必须先授权、必须核对对象等安全顺序可以硬性要求；对“先关键词还是先语义检索”之类策略选择，应允许多条有效路径。

### 16.8 逐步产品化的顺序

一种合理的实现路线是：先建立单 Agent 与少量清楚工具的可验证基线；再根据真实错误修正返回值和接口；随后增加外置、当前状态、完整交互单元与必要摘要；只有探索噪声或并行需求明确时再引入子 Agent；最后用独立测试集衡量成本与质量变化。

这综合了 R02、R06、R12 的简单起步与评测迭代建议，但不是固定项目排期，也不是所有任务都必须经历的标准流程。

### 16.9 最终比较对象：真实成功任务的成本与可靠性

工具调用更少，可能是接口更高效，也可能是提前放弃；上下文更短，可能更专注，也可能丢掉证据；测试通过率高，可能是修复有效，也可能是测试没有覆盖真实问题。

因此应把任务质量、证据与验证、失败暴露、总成本和延迟放在一起看。不要把任何一个容易展示的指标当成整个系统的目标。

## 17. 全课总结：上下文是工作视图，工具是行动契约

讲义用 “Agent = Model × Harness” 概括模型与外部系统共同决定实际表现。这是工程观点，不是可直接计算的数学定律。〔[L04，PDF pp. 51–53](#ref-l04)〕

ReAct 说明，模型需要把观察整理成可用于后续行动的信息；Toolformer 说明，选择和利用工具是一种需要学习的能力，但局部预测损失不等于完整任务收益。

工具设计与 Bash 案例说明，工程师可以重新划分工作：把确定性查询、检查、关联与计算留在环境中，让模型更多处理目标解释、证据缺口和策略选择。工具返回值又决定下一轮模型看到什么，所以接口与上下文不能分开优化。

Lost in the Middle、Context Pruning、Context Rot 分别揭示：证据即使在窗口里，也可能用不好；旧状态可能主动误导；删除历史会丢进度；上下文管理还会改变探索量与停止行为。它们共同否定了“上下文越多越好”，但没有支持“上下文越少越好”。

Skills 与多 Agent 的材料说明，知识加载、探索隔离和控制权分配是不同选择。增加能力还需要设计发现、交接和评测；文件扩展名、协议名或 Agent 数量本身都不提供可靠性。

Harness 最后把模型声明接回真实环境：参数是否合法，权限是否成立，动作是否完成，证据是否支持结论。**模型说完成，只是需要验证的声明。**

### 可以带进设计评审的三个问题

**第一，此刻有足够且可信的信息做下一步判断吗？**检查目标、约束、当前状态、证据与可获取路径，而不是只看窗口大小。

**第二，下一步动作是否具有清楚、可检查的契约？**检查对象、参数、口径、权限、前置条件、错误与后续反馈，而不是只看工具是否能执行。

**第三，系统凭什么相信任务完成了？**检查真实产物与用户目标是否相符，验证哪些部分仍然不足，而不是只看最后回答是否流畅。

> **Context Engineering 不是管理一段越来越长的聊天记录，而是维护模型每一步的工作视图。Tool Design 不是包装更多函数，而是设计获取证据和改变状态的契约。Harness 将两者组织成一个有边界、可恢复、能验证的闭环。**

### C.1 工具契约评审表

| 检查项 | 评审问题 |
|---|---|
| 用途与边界 | 人类能否根据任务明确判断应使用哪个工具？与相似工具有何区别？ |

| 错误恢复 | 参数错误、权限失败、状态未知和临时错误是否有不同处理？ |
| 重试语义 | 有副作用时如何识别同一次逻辑操作？如何防止重复生效？ |
| 可观测性 | 调用、结果、对象版本、进程状态与证据能否关联？ |

### C.2 长任务状态模板

```yaml
task:
  goal: "用户目标"
  constraints:
    - "必须持续有效的限制"
  completion_criteria:
    - "可以验证的完成条件"

state:
  phase: "investigating"
  working_revision: "workspace-v18"
  completed_items: []
  pending_items:
    - "尚未完成的核验"
  blockers: []

knowledge:
  verified_facts: []
  hypotheses:
    - statement: "候选解释，不得作为事实发布"
      status: "unverified"
  rejected_hypotheses: []
  evidence_refs: []

execution:
  active_jobs: []
  pending_approvals: []
  last_verified_operation: null

continuation:
  next_step: "下一项最重要的验证动作"
  raw_history_ref: "原始事件记录入口"
```

精确字段应根据任务调整。关键是区分事实、假设、操作状态与完成状态，不让它们在自然语言摘要里混为一谈。

### C.3 压缩之后的验收表

| 应保留的内容 | 检查方式 |
|---|---|
| 用户目标与限制 | 与任务契约逐项比对，不能被附近子目标替代 |
| 当前状态与版本 | 与工具观测一致，不混用旧快照 |
| 关键事实与证据 | 引用可读取，摘要没有添加来源中没有的断言 |
| 未解决问题 | 不得把“可能”变“确定”、把“未运行”变“通过” |
| 操作进度 | 能分清已完成、进行中、待验证、待批准 |
| 原始材料入口 | 大文件、日志和历史证据能够恢复 |
| 工具调用关系 | 未完成与已完成调用的协议结构仍然正确 |
| 继续执行余量 | 后续生成和工具结果有空间，不贴着硬上限运行 |

## 附录 D：术语速查

| 术语 | 在本课中的含义 |
|---|---|
| Agent loop | 模型决策、工具执行、反馈回传与继续／停止的循环 |
| Harness | 模型周围的运行层，包括工具、上下文、权限、预算、恢复与验证 |
| Context | 一次模型调用可用的信息集合，不只是用户输入 |
| Active context | 当前这一步使用的工作视图，与完整事件历史不同 |
| Tool schema | 工具名称、描述与参数结构等模型可见契约 |
| ACI | Agent–Computer Interface，面向 Agent 的操作界面 |
| Grounding | 将判断建立在外部资料或环境观测上；仍需检查资料与使用方式 |
| Few-shot | 在输入中提供少量示例，引导任务行为 |
| Self-consistency | 多次采样并聚合，不等于结果概率自动校准 |
| Workflow | 在 R02 中指由预先定义的代码路径组织模型与工具的系统 |
| Admission | 控制哪些信息现在进入上下文 |
| Offloading | 将内容外置，保留引用并按需获取 |
| Transformation | 去重、替换或裁剪已有上下文的组织方式 |
| Compaction | 将历史改写为较短表示以继续工作 |
| Observation masking | 删除或遮蔽部分旧观测，不一定用模型重写 |
| Stale state | 已被较新状态取代，却仍影响决策的旧快照 |
| Progressive disclosure | 先提供索引，任务相关时逐层加载正文与细节 |
| Skill | 可加载的操作或领域知识文件集合；不是模型微调 |
| Sub-agent | 承担局部任务的另一个 Agent 执行上下文；不自动提供安全隔离 |
| Idempotency | 在约定条件下，对同一逻辑操作重复请求不会重复产生预期外副作用 |
| PT | R11 的 premature termination rate，Give Up 与 Uncertain Incorrect 的比例之和 |
| No Answer | R11 中因上下文或轮数等限制未输出答案的状态 |
| Test-time scaling | 用额外推理时资源提高任务表现；R11 用它分析更多有效探索 |
| Verifier | 检查结果是否满足标准的程序或评估过程，不必完全由 LLM 构成 |
| Evidence reference | 能定位原始支持材料的引用，最好同时明确版本和时间 |
| Semantic index | 代码块 embedding 索引；按相似度返回候选，不返回定义与引用 |
| Repo map | 由代码解析出的文件、类与函数签名排序摘要，用于替代多轮盲搜 |
| Extrinsic signal | 源码之外产生的定位证据，如堆栈、失败测试与 Git 历史 |
| Language server（LSP） | 按语言维护符号索引的常驻进程，提供定义、引用、类型与改名 |
| Rename（LSP） | 在服务器支持和正确索引范围内按符号改名；别名、动态引用与生成代码仍需验证 |

这些解释用于本文阅读；不同平台可能采用不同术语边界，不能仅凭名称假定实现相同。
