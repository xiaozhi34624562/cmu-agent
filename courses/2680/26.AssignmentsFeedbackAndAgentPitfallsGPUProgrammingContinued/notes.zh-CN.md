你给 Coding Agent 一个任务：“把模型服务中的这个计算加速，同时保持输出正确。”过了一会儿，它提交代码并报告“测试通过，速度提高三倍”。现在真正困难的工作才开始：测试覆盖了什么？是不是把等待 GPU 的时间漏掉了？快的是一个算子，还是用户看到的整个请求？如果换成非整数倍长度、不同精度或长输入，结论还成立吗？

## 1．先把“更快而且正确”变成可以判断的要求

从一个简单计算开始：

$$y_i=\max(0,\alpha x_i+b),\qquad i=0,\ldots,n-1.$$

这里 $x$ 是长度为 $n$ 的数组，$\alpha$ 和 $b$ 是标量；先缩放，再加偏置，最后把负数变成零。它是一个教学算子，能帮助解释模型中的逐元素计算、融合和内存流量。假设 Java 服务负责接收请求，计算由 Python/CUDA 服务执行。Agent 的工作是优化计算实现，数学目标保持上述定义。

“加速这个函数”还缺少很多决定正确性的条件。输入是不是允许空数组？长度能否不是 256 的整数倍？是否要求保留输入？是否支持非连续数组视图？浮点误差允许多大？返回异步句柄算完成，还是结果已计算出来才算完成？如果这些问题没有答案，Agent 可能写出一种在它自己的理解下正确、在调用方看来错误的程序。[F，pp.5–8；算子及下面契约为教学构造]

可以先把本次允许的范围写成小契约：输入是有限值 FP32 连续数组；支持 $n=0,1,255,256,257$ 及目标业务长度；输出形状不变、输入不得改写；结果与参考实现按事先确定的绝对与相对误差比较；性能对照保持设备、输入和计时边界相同。NaN、无穷大、其他 dtype 和非连续输入若没有实现，就明确拒绝或走参考路径。这样范围是可检验的，不会靠“似乎能跑”猜测。

FP32 表示每个浮点值用 32 位存储；FP16 和 BF16 都用 16 位，但表示范围和有效精度的分配不同。后文的 BF16 权重按每个参数 2 字节估算，只计算权重本身。

为什么浮点要谈误差？实数运算中，先乘后加与融合乘加给出同一个表达式；计算机中前者可能舍入两次，后者通常只舍入一次。更换精度、融合或者改变求和顺序，都可能使末尾几位不同。因此“数学等价”“数值满足用途”“逐位相同”是三个不同要求；先选择实际需要的那个，再设计验证。[G，pp.26、44；CUDA 编程与 Best Practices 的数值精度部分]

最基本的对照形式是：

$$|y_i-\hat y_i|\le \mathrm{atol}+\mathrm{rtol}|\hat y_i|.$$

$\hat y_i$ 是参考结果，`atol` 处理接近零时的绝对误差，`rtol` 随结果大小调整允许偏差。阈值要由精度与业务用途决定，而不是调到候选刚好通过。测试还应确认所有预期用例确实被执行，防止“把测试删掉以后零失败”的空洞成功。[F，pp.32–34；误差检验形式为工程展开]

## 2．Agent 的事件流不是一份按时间排好的故事

F 第 5 页提醒：任务启动顺序与完成顺序不同，后台命令可能来自不同子 Agent。你可以借助 Java 中的异步任务理解：`submit()` 返回只说明提交完成，不代表 `Future` 已经获得结果。Agent 工具调用也至少有“发起请求、开始执行、得到结果、解释结果”几个阶段。

考虑下面的教学事件：

```text
10:00 A 启动参考测试 run-17
10:01 B 修改了待测算子，产生版本 v2
10:02 A 返回“全部通过”
```

仅凭时间线无法断定 v2 通过了测试。A 可能测试了启动时加载的 v1，也可能运行期间读到了部分 v2 文件。要使结果可解释，应记录测试使用的代码提交或内容哈希、输入集、实际命令、退出状态、执行的用例数和完整结果。测试证明的是一个确定版本在确定条件下的行为。[F，pp.5、34、38；版本绑定为教学推导]

一个最小运行记录可以包含：

| 字段 | 回答的问题 |
|---|---|
| `run_id`、父任务与调用标识 | 这是哪次工作，属于谁 |
| 代码版本、输入与配置版本 | 实际测了什么 |
| `queued/running/completed/failed/cancelled` | 执行过程到哪里了 |
| 结果、退出状态、检查项 | 得到了什么可验证证据 |
| 未完成项与失败原因 | 还缺什么，下一步应做什么 |

注意 `completed` 只表示这次过程结束，不能直接代替“目标满足”。例如测试进程完成但 7 个用例失败，或者 profiler 完成但工作负载未启动，都需要单独记录。你平时为后端任务建立状态机的经验，在这里直接有用。

## 3．委派的价值来自分工与信息，不能只数 Agent 个数

同一个小仓库让六个 Agent 反复搜索，可能增加的是阅读重复和协调成本。F 第 7 页给出一组课堂个案：一次多层委派比先前相似任务花了更多时间与费用。这支持“需要检查委派是否有净收益”，不构成“六个 Agent 必然更慢”的普遍实验结论。

对于当前算子任务，可以把职责拆成：A 实现候选；B 审查数学与边界用例；C 在候选冻结后测性能。A 与 B 可以并行，但 C 的输入依赖一个确定的候选版本。如果 C 在 A 不断改文件时运行，测量结果就失去归属。隔离写入目录或工作区，给运行输出独立名称，并在需要时冻结版本，比单纯增加并发数更有价值。[F，pp.7、10、38]

委派还需要控制“知道什么”。审查者应知道要求、参考行为和候选差异，同时有机会独立检查证据。如果只把实现者的成功总结转交给另一个模型，它可能只是重复同一个前提。独立审查不是因为换了一个聊天窗口就自动独立，而是检查对象、证据和判断过程确实允许发现相反结论。[工程推导，依据 F pp.10–12、34]

用户需要看到的进度也应服务于决策：“已经确认误差来自尾部元素，正在改索引检查”比“大量调用日志”更有用。记录当前假设、已验证事实、剩余工作和成本，使人能够及时纠正方向，也使后续会话能接续工作。

## 4．看到一种行为，先找出塑造行为的条件

F pp.13–17 分析了学生作业中 Agent 更偏向 Bash 的现象。讲义把它与当时的系统提示、工具是否暴露、权限模式和功能开关联系起来，并展示相应观察。这里最值得学的是一种解释方法：**运行中的 Agent 行为由模型与外部运行条件共同产生。**

假如系统提示要求通过 Bash 工作，而且专用搜索工具不存在，就不能把“Agent 没用专用搜索工具”解释成模型没有理解要求。相反，如果工具存在、说明清楚、权限允许，却总被选错，才需要继续检查模型、工具描述或上下文竞争。课程列出的具体模型名和开关是当时的分析对象；本文没有核验它们在当前产品中的启用状态，也不把它们当作使用指南。

做工程比较时，至少保存模型版本、系统提示、工具定义与可见集合、权限、运行框架、采样设置，以及任务输入。否则两次“同一个提示”的运行，可能实际处在不同条件下。改变这些条件的一项，是一种干预；观察不同学生自选条件后的差异，则还可能包含能力、任务难度和投入方式等混杂因素。[F，pp.14–17；实验记录建议为工程推导]

## 5．怎样从课堂图表得到合理结论

F pp.18–19 展示对来自 12 名学生的前 18 份提交（top 18 submissions）各评测 10 次的结果，每次在解决任务数与端到端耗时构成的平面上形成一个点。这是经过筛选的提交集合，不是全班随机样本，不能直接推广为全班的表现。先看同一提交的点有多分散，再看不同提交的点群是否分开。前者反映重复运行波动，后者提示版本之间可能存在稳定差异。一次特别好的点不是整个版本的表现，点群分开也需要确认任务与资源条件是否相同。

两个指标通常不能同时压成一个无条件排名。若方案 A 比 B 解决更多任务但更慢，选择取决于时限与目标；若 A 同时解决不少于 B 的任务且耗时不高于 B，至少一项更好，才构成这一指标空间中的支配。**Pareto 前沿**就是没有被其他方案这样同时压过的方案集合。它不替你决定什么代价值得付出。

F pp.21–25 描述了提示数量、活跃时间、工具调用、成本和失败发现者随作业变化。任务本身也发生了变化，因此不能把费用增长直接归因于某一种使用方式。F pp.27–29 中投入时间与成绩的关系同样不能推出“少花时间必然更好”：能力、选题、基础代码和任务策略都可能影响两者。

讲义本身还有一个值得保留的核查点：F p.37 对堆叠改动列出的 A3 比例是 37%，p.46 汇总图列为 78%；单次噪声运行的比例在 p.41 与 p.46 也不同。汇总页注明一组 58 名学生，但不足以解释全部差异。本文不把这些数字混成统一统计或自行猜测原因；保留来源差异，使用它们提出需要验证的问题。这也示范了阅读图表时应检查分母、样本、编码规则和版本，而不只记住醒目的百分比。

## 6．十类失败怎样变成具体的控制动作

下面把 F pp.30–45 的十类问题放回开发过程。它们不是“更仔细一点”的口号，而是要改变输入、执行或判断中的某个环节。

**相信结论但没有证据。** Agent 报告通过时，检查实际命令、用例数量、退出状态和关键输出。若测试命令根本未启动，结果应是验证未完成，不能算通过或功能失败。至少用一个你能判断的小例子手工核对，防止测试和实现共同误解要求。

**失去对改动的理解。** 把大任务切成可审查的增量。例如先保持原实现，只加边界测试；再改变计算布局；最后加性能测量。每步说明改了哪里、依据什么、如何验证。这样错误出现时，回溯空间更小。

**长会话丢失关键约束。** 持久记录目标、决定、代码版本、证据和未解决问题，特别是“为什么没有采用某方案”。摘要是压缩，会丢信息；记录必须允许回到原结果，并在恢复时核查当前代码与记录是否仍一致。换会话本身不会自动修复过期记忆。

**堆叠改动，无法归因。** 一次同时更换模型、提示、重试次数和评分方式，即使成绩提高，也不知道是谁起作用。先固定基线，每轮围绕一个明确假设改变最小因素；存在交互作用时，再安排组合对照。测试集不能反复调到满意后还被称为独立验收集。[教学扩展，依据 F p.37 的受控实验原则]

**并行执行互相污染。** 隔离代码工作区、端口、缓存与输出；测性能时还要控制共享 GPU/CPU 的干扰。不同目录不会隔离同一块 GPU。运行结束也不能直接清理别的任务正在使用的进程或文件。

**破坏性操作丢失成果。** 在高影响操作前保留可恢复版本；把权限与隔离环境作为实际约束。仅在提示里写“不要删除重要文件”，无法代替环境和操作范围控制。保护的对象还包括原始提示、输入快照与运行日志，否则会失去实验可重现性。

**凭据泄露。** 凭据不进入提示、教学示例、提交和共享日志；只让需要的执行环节获得必要权限。环境变量是传递方式，不自动构成保密边界：有读取权限的进程仍可能输出它。讲义的“放在环境变量或忽略的配置里”需要与最小可见范围一起理解。[F p.40；权限解释为工程推导]

**把一次波动当改进。** 同一任务集重复运行，保存逐任务结果和整体分布。先定义可接受差异，再判断收益是否稳定。不能仅挑最快一次，也不能把失败或超时的运行从统计中静默删掉。

**没有提供新证据，只不断要求修复。** 如果相似改动连续失败，下一步应补充可区分假设的观察，例如错误位置、最小失败输入或运行时间分解。把“继续优化”改成“确认时间是否主要花在拷贝而非计算”，会产生更具体的行动。

**把环境问题当作方法问题。** 磁盘满、机器休眠、依赖缺失和测试平台不兼容，会导致任务没有真正执行。先确认环境满足前提，再评价模型或算法；保留环境失败的独立状态，避免把它们算成模型质量变化。

## 7．把这些原则合成一次可解释的迭代

以算子为例，先写下假设：“当前三步逐元素操作分别读写显存，融合可能减少中间数据往返。”这比“改成 CUDA 会更快”更可证伪，因为它指向一个具体资源消耗。

接下来保留参考版本、确定支持的输入集合和误差规则；只做融合这一个改变；先测输出正确性，再用同一组输入重复测量。若提速只在大数组出现，小数组无收益，解释可能是小输入受启动开销主导，而大输入受显存搬运主导。此时结果并不矛盾，而是不同工作区间在响应同一优化。[F p.47 为迭代主线；算子假设与解释为教学推导，后文继续验证其计算依据]

记录的结论应带适用范围，例如“在指定 FP32 连续大数组上，输出满足约定误差；在固定设备与同步计时条件下，重复运行耗时降低”。是否接入服务，还需测端到端表现。单算子占请求时间很小，即使它大幅加速，用户也未必感受到明显变化。

F pp.48–58 展示课堂反馈平台，把使用轨迹、失败和建议连接起来。其主要教学价值是让开发者复盘自己怎样提出任务、检查证据和调整方向。公开入口目前只取得应用外壳，未获取个人报告正文；本文依据讲义中的截图说明用途，没有登录、访问他人报告或推断平台内部评分算法。阅读平台截图时同样要区分“被观察到的行为”“对原因的解释”和“建议尝试的改进”。

接下来进入 GPU 部分：我们已经知道应该怎样验证一个优化，现在要具备解释它为何有效的知识。

## 8．CPU 发出了请求，GPU 未必已经完成计算

G pp.5–6 从执行模型开始。CPU 通常负责控制流程、准备数据和提交任务，GPU 把大量相似计算分给许多线程。`kernel` 就是在 GPU 上执行的函数；一次 launch 会创建一组执行该函数的线程。这里的线程不是一个 Java `Thread` 对象，不适合用“每个元素开一个操作系统线程”的成本模型理解。

假设一次请求依次经历：Java 接口校验、Python 调度、主机到设备拷贝、GPU 计算、设备到主机拷贝、序列化返回。GPU 算子只占其中一段。特别是 CPU 的 launch 调用通常异步返回：它把工作排入执行队列，返回时设备可能还没开始计算。你在调用前后读取主机时钟，可能只测到了排队所需时间。

CUDA 的 **stream** 是提交工作的一条有序队列。同一普通 stream 中的操作通常按顺序执行；不同 stream 提供并发机会，但能否真正同时执行，取决于依赖、设备资源和同步方式。把它类比为后端中的队列有助于理解先后关系，但不能把队列数量直接当作实际并发度。[G pp.5、31–32；CUDA Programming Guide 的 Asynchronous Concurrent Execution]

测单个 kernel，可以使用设备侧事件围住目标区间，并等待结束事件完成再取时间；测真实请求，则用端到端时钟覆盖必要等待。需要先预热，区分首次编译、分配与稳态计算。为了计时而在每个小操作后同步，会破坏本来可以重叠的执行，所以测量方案本身也可能改变系统。[Nsight Systems、CUDA Best Practices；工程展开]

讲义用 PCIe 带宽与 GPU 内部显存带宽的差距提醒你：**数据在哪儿，可能比算得多快更重要。** G p.5 的约 64 GB/s 是特定互连规格的示意，不是所有机器的实测带宽。一个只需极少计算的数组若每次都从主机传进 GPU 再传回，拷贝很可能抵消计算收益。先考虑数据能否留在设备、连续多个计算能否共享它，再考虑更复杂的 kernel。

## 9．从数组索引理解 grid、block、warp 和 SM

一次 launch 的线程集合称为 grid；grid 划分为多个 block；block 被调度到 SM（Streaming Multiprocessor，GPU 的一组执行资源）上。一个 block 内的线程可以协作访问 shared memory，并使用块内同步。普通 block 之间不应假设谁先执行或同时常驻。一个 SM 也不是只能永久对应一个 block：常驻数量受线程、寄存器和共享内存等资源限制。[G pp.6–8；CUDA Programming Guide 的 Programming Model]

先分清三层存储：寄存器主要保存线程正在处理的少量值；shared memory 供同一 block 协作复用；HBM（High Bandwidth Memory）是设备上容量大得多的显存，属于 DRAM。速度、容量和可见范围各不相同，数据经过哪一层会影响成本。Tensor Core 则是擅长矩阵乘加的专用计算单元，不是一个更大的存储区。

在 NVIDIA CUDA 中，线程以 32 个线程一组的 warp 执行。warp 内线程各有自己的索引和数据。如果它们对分支走不同路径，执行会需要掩码或分段处理，不能简单把 32 个线程视为 32 个完全独立的 CPU 核。

对长度为 $n$ 的数组，用每 block 256 个线程，一个线程负责一个元素：

```cpp
// 教学伪代码：未在 CUDA 设备上编译或运行。
i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) {
    y[i] = max(0, alpha * x[i] + b);
}
```

例如第 2 个 block 中编号 1 的线程访问 $2\times256+1=513$ 号元素，编号都从零开始。所需 block 数是 $\lceil n/256\rceil$：当 $n=1,048,576$ 时需要 4096 个 block；当 $n=257$ 时需要两个 block，第二个 block 只有第一个线程对应合法元素。`i<n` 因而是正确性的一部分，不是可有可无的性能细节。

为什么相邻线程最好访问相邻地址？GPU 会把适当对齐、相邻的访问合并成较少的内存事务，称为 **coalescing**。如果一个 warp 的线程各读距离很远的地址，搬进来的数据中可能只有很少一部分有用。这里的核心是“实际搬运了多少字节来满足有效访问”，不只是源代码有多少次 `load`。[G pp.41–42；CUDA Best Practices 的 Coalesced Access]

再看 shared memory。它是 SM 上可由程序显式组织的快速存储，适合一组线程反复使用同一小块数据；它不是 Java 中任意共享对象的别名。shared memory 被划分为 banks，多个线程对同一 bank 中不同地址的某些访问会串行化；但对同一位置的广播等情况另有规则。是否冲突必须结合地址布局、访问宽度与设备规则分析，不能仅凭“使用共享内存”判断更快。

## 10．编程抽象决定你负责哪些选择

G pp.9–15 依次介绍编译、tile 语言和底层指令。tile 是一小块元素或矩阵，tiling 是把大计算切成这些小块来组织；ReLU 就是前面把负数变成零的操作。这些工具并非按“越底层越高级”排序，而是在分配责任。

以 `relu(alpha*x+b)` 为例，写 PyTorch 表达式时，你描述张量操作；编译器可能捕获计算图、融合相邻操作、生成设备代码。PyTorch 2 的论文把 Python 字节码捕获、图处理和后端编译分开描述：Python 中的数据依赖控制流、图中断以及输入假设会影响可编译范围。`torch.compile` 不等于把任意 Python 程序一次变成最佳 GPU 程序。[G p.9；PyTorch 2，§§2–4]

写 Triton 时，你通常描述一块元素如何加载、计算和存储。例如一个 program 处理 1024 个元素，`program_id*1024+arange(0,1024)` 得到一组偏移，再用掩码处理尾部。这里的一个 program 不等于一个标量 CUDA thread；编译器还负责把块级计算映射到线程和指令。TileLang 同样以 tile 为基本表达单位，但给程序员显式安排流水线、内存层级等空间；其论文的性能结果依赖所测算子、形状、硬件和调优设置。[G pp.10–12；Triton Vector Addition；TileLang，§§3–5]

CuTe 用 shape、stride 和 layout 描述逻辑坐标怎样映射到存储位置。例如二维数组的第 $(r,c)$ 个元素，若共有 $N$ 列，在行优先连续布局中偏移为 $rN+c$；转置视图可以改变 stride 而不立即复制所有数据。真正要送给某条矩阵指令时，数据布局还须符合指令要求，必要的重排有成本。CUTLASS 和 ThunderKittens 则提供不同层次的矩阵/数据移动构件。[G pp.13–14；CuTe Layouts、CUTLASS Overview；ThunderKittens，设计章节]

在本课的 NVIDIA 路线中，PTX 是中间的虚拟指令表示，最终还需要产生对应 GPU 的机器指令，通常称为 SASS；因此看到 PTX 不能直接断言最终寄存器数、调度或执行时间。CUDA 编译链、JIT 与缓存状态都会影响首次运行和部署兼容性。[G p.15；NVIDIA CUDA Compiler Driver]

工程上可以逐步增加控制：先用可信库建立基线，再尝试编译器，确有瓶颈且库不能满足时才针对少量算子写 tile kernel；只有需要控制更细的线程、布局或硬件指令时继续下沉。这个顺序是教学建议，目的在于把维护成本花在已确认的瓶颈上。CUDA Tile、Triton、TileLang、CuTe 的 API 并不互换；本文解释其分工，没有运行各自编译器。OpenXLA 官方架构页本轮未取得正文，因此不据此补写 XLA 内部实现细节。

## 11．GPU 利用率 100%，为什么请求仍然很慢

G pp.16–23 的关键是把“忙”拆开。GPU 在采样窗口内一直有 kernel 执行，只说明设备活动持续，不说明所有 SM、Tensor Core 或显存通道都满负荷工作。

| 指标 | 它主要回答什么 | 不能单独证明什么 |
|---|---|---|
| GPU activity/utilization | 采样窗口里设备有多长时间在执行工作 | 峰值算力已经用满 |
| SM active | SM 上有活动 warp 的时间比例 | 活动线程每周期都发出了有效计算 |
| occupancy | 活跃/常驻 warp 相对硬件允许数量的比例，具体以工具定义为准 | occupancy 越高程序必然越快 |
| Tensor Core activity | 对应矩阵执行资源有多忙 | 全请求吞吐或数值质量更好 |
| DRAM throughput | 显存传输达到什么水平 | 传输的每个字节都对结果有贡献 |

这些指标的采样、聚合和计数器定义需要查工具文档。DCGM 的活动度是归一化硬件指标；不能把不同工具中名称相似的指标直接相除得到新结论。较高 occupancy 可以提供更多可调度 warp 来隐藏等待，但也可能来自缩小 tile 或压低寄存器使用，反而增加数据搬运。优化对象仍是正确工作负载的时间和成本。[G pp.21–22；DCGM Profiling、Nsight Compute Profiling Guide]

更直接的判断来自 **算术强度**：完成有效计算所需的 FLOPs 除以对应层级搬运的字节数。

$$I=\frac{F}{D},\qquad P_{\rm attainable}\le\min(P_{\rm peak},B\cdot I).$$

$F$ 是浮点运算量，$D$ 是字节数，$B$ 是该层级带宽，$P$ 是每秒浮点运算数。若一件任务几乎不计算却搬很多数据，提高峰值算力并不能消除带宽瓶颈；若数据复用充分、计算量大，算力才可能成为限制。这个 roofline 式上界是分析工具，尚未计入启动、同步、访存不规则等损失，不能当作实测预测。[G pp.17–19；Databricks MBU 文章；上式为性能模型展开]

**MFU 的分子和分母必须是同一个范围。** 简化稠密模型前向计算常以每 token 约 $2P$ FLOPs 估算，$P$ 为参数数目；注意力随序列长度增加的额外计算等可能需要另计。若 $T$ 是整组 GPU 的 token/s，$G$ 是 GPU 数量，$P_{\rm peak}$ 是单卡相同精度下的峰值：

$$\mathrm{MFU}\approx\frac{2P\,T}{G\,P_{\rm peak}}.$$

G p.17 用 70B 模型、3040 token/s、8 张 H100 和 1979 TFLOP/s 等数值展示约 22%，但“3040 是整组还是每卡”、峰值采用何种精度/稀疏口径并不清楚。如果 **假定** 3040 是整组、1979 是每卡适用峰值，计算应为 $140\times3040/(8\times1979\times1000)\approx2.69\%$；若 3040 是每卡，则约 21.51%。这两种只是澄清单位的条件算例，不能据讲义判断真实实验是哪一种。

PaLM 将模型有效计算与额外重计算区分；Reducing Activation Recomputation 也讨论 activation checkpointing 对训练 FLOPs 和内存的影响。执行了更多重计算会增加硬件工作，不等于每秒处理了更多模型有效 token。训练常用的 FLOP 估算不能不加修改套到仅前向推理。[PaLM，§4 与 MFU 讨论；Reducing Activation Recomputation，§§3–5]

**MBU 也有假设。** 小 batch decode 中，若每一步需要读一次模型权重和已有 KV，可以用其估算字节数除以单步时间，再除以设备带宽。G p.19 的 8B BF16 模型约 16 GB 权重，200 token/s 对应权重流量约 3.2 TB/s；若适用峰值为 4.8 TB/s，比例约 66.7%。这个估算忽略 KV、重复读写和缓存影响，是模型流量代理，不是硬件计数器直接测得的 DRAM 利用率。batch 增大后多个请求共享权重读取，更不能简单对每个 token 重复算整套权重。

## 12．先看整条时间线，再看一个 kernel 为什么慢

G p.20 推荐两种互补视角。Nsight Systems 帮你看 CPU 调度、设备计算、拷贝与同步的时间关系；Nsight Compute 帮你看选定 kernel 的资源和指令行为。前者定位“哪段时间值得解释”，后者分析“那段为何慢”。

假设请求耗时 10 ms，其中准备和传输 7 ms，目标 kernel 2 ms，返回 1 ms。即使 kernel 快一倍，总时间也只降到 9 ms。一般地，某部分占比为 $f$、该部分加速 $s$ 倍，整体上界是：

$$S=\frac{1}{(1-f)+f/s}.$$

这是教学中的 Amdahl 计算，假定其他部分不变，没有引入新开销。它说明为什么不能拿单算子提速百分比代替用户请求提速。[依据 G pp.20、26–35 的性能层次展开]

实际诊断可以沿因果链进行：设备时间线有大空隙，检查主机调度和同步；一直有计算但只用少量 SM，检查任务切分和工作量；SM 活跃而 DRAM 紧张，检查字节流量和访问布局；矩阵单元闲而非矩阵指令繁忙，检查归一化、索引与数据转换；多卡等待明显，则看通信与依赖。

Profiler 自己有成本。Nsight Compute 为采集某些计数器可能 replay kernel 或整个应用；不能把一次 instrumentation 下的耗时直接当生产延迟。先保留无 profiler 的稳态基线，再采样诊断，用修复后的独立计时确认收益。[Nsight Compute Profiling Guide 的 Replay、Overhead；Nsight Systems User Guide]

## 13．融合与 tiling：少搬数据，为什么仍可能变慢

回到三步算子。若分别启动缩放、加偏置、ReLU，每一步都读 $N$ 个元素并写 $N$ 个元素；忽略缓存、标量和额外开销，元素大小为 $s$ 字节，总流量是 $6Ns$。融合后在寄存器里完成三步，只读输入、写最终输出，约为 $2Ns$。**三倍是这个理想模型的流量比，不是已经测出的三倍速度。** 小数组可能主要省启动，大数组可能主要省带宽；缓存、编译器已有融合和硬件限制会改变结果。[G p.26；教学推导]

这是纵向融合：沿生产者到消费者的依赖链合并。横向融合则可能把读同一输入的多个独立操作合在一起。例如 $Q=XW_Q,K=XW_K,V=XW_V$，可拼接权重列做一次较宽矩阵乘，再把结果拆开。代数形状允许这种合并，但实现布局、不同 head 数和后续消费方式决定它是否划算。

Tiling 解决另一种浪费。矩阵乘 $C_{ij}=\sum_k A_{ik}B_{kj}$ 中，一个 $A_{ik}$ 会参与多个列的计算，一个 $B_{kj}$ 会参与多个行的计算。让 block 合作把 A、B 小块搬到 shared memory，再在块内反复使用，可以减少从 HBM 重复读取。tile 过大却会占更多寄存器和共享内存，降低能同时常驻的工作量，甚至导致寄存器 spill 到更慢的存储。[G pp.41–44；CUDA Best Practices、CUTLASS、ThunderKittens]

因此“多融合一点”“tile 越大越好”都缺少资源条件。要看省下的外部搬运，是否被更多寄存器、同步、布局转换和低并行度抵消。编译器的选择也不是免费：大量 autotuning 候选会花编译时间、设备时间和缓存空间；只有未来重复执行足够多次，调优成本才可能摊薄。

## 14．FlashAttention：不保存整张注意力矩阵，怎样仍得到相同数学结果

G pp.27–28 把 FlashAttention 作为融合与硬件协同的代表。先补齐计算对象：$Q$ 是当前查询向量组成的矩阵，$K$ 提供匹配键，$V$ 是被加权汇总的值；每个 query 对各 key 的分数经过 softmax 归一化，再用于加权 V：

$$O=\operatorname{softmax}(QK^\top/\sqrt d+M)V.$$

$d$ 是一个 attention head 内查询/键向量的长度；head 可以理解为一组独立学习的匹配与汇总通道。$M$ 是掩码（不能看到的位置用负无穷屏蔽）。若序列长度为 $L$，直接把所有分数写入 HBM，会形成 $L\times L$ 中间矩阵。FlashAttention 的核心不是删除注意力项，而是分块计算、维护归一化状态，避免把整张中间矩阵反复写回与读出。[FlashAttention，§§2–3；G p.27]

softmax 对一行分数先取指数，再除以该行指数总和，使权重非负且加起来为 1。式子里的转置 $K^\top$ 让每个 query 与各 key 做点积，$\sqrt d$ 缩放分数；这些分数决定各 value 在输出中占多大比重。

对单个 query，先把某块分数记为 $s_j$，维护三个状态：目前最大分数 $m$、指数和 $\ell$、未归一化的加权值 $u$。新一块到来时：

$$m'=\max(m,\max_j s_j),\quad a=e^{m-m'},$$
$$\ell'=a\ell+\sum_j e^{s_j-m'},\qquad u'=au+\sum_j e^{s_j-m'}v_j.$$

结束时输出 $u/\ell$。为什么要乘 $a$？旧状态以旧最大值为基准，新块可能出现更大值；所有旧权重必须换到同一个尺度。减最大值避免指数溢出，并不改变最后归一化比例。空状态可设 $m=-\infty,\ell=0,u=0$，实现时要处理全掩码等特殊情况。

一个可手算例子：分数为 $[0,\ln2,\ln3]$，对应值为 $[10,20,30]$，未归一化权重比是 $1:2:3$，输出 $(10+40+90)/6=23.333\ldots$。把前三项分成不同块，按上式更新仍得到这个值；浮点执行只要求在预先规定的误差内一致。随文 CPU 示例还包含非常大的分数，验证稳定计算和分块合并，而不是测 GPU 性能。

“Exact attention”指保持原始稠密注意力的数学目标，不保证不同实现逐位相同。FlashAttention 也不保证每个 K/V 元素在整个 kernel 中只从 HBM 读取一次：多个 query block、缓存容量和实际布局会影响复用。它减少的是主要中间矩阵物化与相关 IO，而不是让所有内存访问消失。

后续版本沿着新瓶颈继续改动：

- **FA2** 改善工作切分、减少非矩阵计算与 warp 间通信，增加适当并行度；不是仅把 FA1 换个编译器。[FA2，§3]
- **FA3** 针对 Hopper 的异步矩阵计算、TMA 数据移动安排 producer/consumer 和流水重叠；FP8 还要处理布局、分块量化和离群值。其论文 H100 80GB SXM5、特定 head/sequence 设置中的加速与误差结果，应与同配置基线比较；不能当成任意模型端到端收益。[FA3，§§3–4，实际 pp.5–12]
- **FA4** 重新分析 Blackwell 上矩阵单元、共享内存和指数计算的不同增长速度，利用 tensor memory、2-CTA 等特性重排流水。更快的矩阵单元可能让 softmax 或 shared memory 成为新瓶颈；不是每个硬件部件都等比例变快。[FA4，§§2–5]

怎样理解“流水重叠”？设搬入一块数据需要 4 个时间单位、计算需要 6 个。完全串行处理两块需 20；若搬入第二块能与计算第一块同时进行，理想情况下是先搬 4，再计算第一块 6（同时搬第二块 4），最后计算第二块 6，共 16。更多块的稳态节奏趋向两阶段中的较慢者，但开头和结尾仍有空档。producer/consumer 就是让一组 warp 负责供给数据，另一组负责消费；缓冲区、完成通知和等待保证数据未准备好时不被读取。这个算例是教学模型，不是 FA3 的设备计时。

FA3 的 TMA 是用于异步批量数据搬运的硬件机制，计算与搬运可由不同资源推进。FA4 的 tensor memory 是存放矩阵单元中间结果的新存储资源；2-CTA 则让两个协作 block 参与一项更大块的矩阵计算。它们提供新的安排空间，也带来容量、布局和同步条件；了解这些责任后，再深入论文中的指令级实现才有落脚点。

FA4 还用部分指数多项式近似与条件重缩放降低开销，精度论证须结合输入范围、输出 BF16 和最终归一化；这不授权把任意 `exp` 替换为粗略近似。本地 FA4 论文是 2026 年版本，讲义时间线上的年份不能替代论文版本。四篇论文的 GPU、精度、forward/backward、形状与对照不同，本文不把它们的加速比相乘。

## 15．小 batch 的 decode 为什么需要新的并行维度

Prefill 一次处理多个输入 token，有许多 query 行可并行；标准逐 token decode 中每个请求只新增一个 query。即使每个 query 有很长历史，按 query 切分也可能产生不了足够多的独立工作。G p.30 的 Flash-Decoding 把已有 KV 序列分成多个片段，让多个工作单元计算同一个 query 对不同片段的贡献。[Flash-Decoding 官方技术说明]

这里最容易犯的数学错误是“每块自己 softmax，再把输出平均”。各块的总概率质量不一定相同，不能平均。设块 $c$ 保存局部最大值 $m_c$、指数和 $\ell_c$ 和未归一化加权和 $u_c$，取全局 $m=\max_c m_c$，则：

$$O=\frac{\sum_c e^{m_c-m}u_c}{\sum_c e^{m_c-m}\ell_c}.$$

这与上一节是同一个合并原理。新增并行度的代价是临时状态、额外归并及调度。历史很短、batch/head 已提供足够并行时，分得更细反而可能更慢。官方 CodeLlama-34B 长上下文实验中的“最高 8 倍”端到端与“最高 50 倍”attention 微基准是不同指标，不能互换。[官方技术说明 Benchmarks、Component-level micro-benchmarks]

FlashInfer 把这类需求放进服务环境：不同长度、不同 KV 布局、GQA（多个 query head 共享较少的 K/V head）、prefix sharing（复用相同输入前缀的 KV），以及运行时规划和 CUDA Graph 兼容性。它的启发是将逻辑请求形状与具体执行计划分开，用合适粒度调度，同时把计划与执行成本纳入测量。[FlashInfer，§§3–4；G p.30 的工程延伸]

G p.29 的 **persistent kernel** 则改变“谁不断领取任务”：让一批工作单元常驻，持续处理后续 tile。它能减少某些调度开销并支持更灵活的工作分配，但不会自动把不可拆任务平均分开。若有 160 个等长、不可拆 tile，132 个 SM，且每 SM 同时只能跑一个 tile，仍需两轮，第二轮只剩 28 个；理想占用比 $160/(132\times2)\approx60.6\%$。仅把代码改成常驻循环不改变这个算术事实。

GEMM 是通用矩阵乘法；归约就是把多个贡献加成同一个输出，MAC-loop 指沿归约维度反复做乘加的循环。Stream-K 的关键是进一步把 GEMM 的归约工作切成较细的 MAC-loop 区间，再跨 SM 平衡；被拆开的输出 tile 需要合并部分和。它处理的是工作粒度与负载平衡，同时付出同步/归并成本。把“常驻”与“细粒度工作拆分”分开，你才能判断一个方案为什么改善尾部空闲。[Stream-K，§§3–4；对 G p.29 简图的条件补充]

## 16．CUDA Graph、PDL 和 megakernel 分别减少哪种等待

G pp.31–33 的三种方法都与 kernel 边界有关，但它们改变的层次不同。

**CUDA Graph** 预先表达工作节点及依赖，实例化后重复提交，减少主机逐个安排操作的开销。它保留各节点的计算语义，不能自动消除所有设备同步，也不等于把全部算子融合。动态形状、内存地址和图更新策略需要适配；首次捕获/实例化成本要与重复执行收益分开。[G p.31；CUDA Programming Guide 的 CUDA Graphs]

**Programmatic Dependent Launch（PDL）** 允许同一 stream 中的下游 kernel 在上游完成前，提前执行不依赖上游结果的准备部分。例如下游可以先读取自身常量，但使用上游输出前必须确认数据已完成并可见。官方 API 通过 launch 属性、上游触发和下游 `cudaGridDependencySynchronize` 等配合；从 compute capability 9.0 起提供相应重叠能力。并发是机会，不是保证，错误地依赖一定会并发可能死锁。[G p.32；PDL 文档 §§4.5.1–4.5.3]

**Megakernel** 把更多跨算子的任务组织到一个设备 kernel 中。省去粗粒度边界后，原本由这些边界提供的依赖保证也要由更细的调度和同步接替。Hazy 的 Llama-1B 实现让 SM 依据任务队列执行，并用完成信息协调数据依赖；其报告针对 batch 1、指定 Llama-3.2-1B 和 H100/B200 设置。它是特定低延迟场景的设计证据，不表示所有模型、所有 batch 都应融合成一个 kernel。[G p.33；Look Ma, No Bubbles!]

MPK 把这一思路抽象成 SM 级 tGraph：节点是小任务/事件，事件等待其生产者完成，准备好的任务交给 worker。与 Java 任务图相似之处是依赖决定何时可运行；区别在于这里还必须在有限 SM、设备内存可见性、寄存器和共享内存中安排工作。调度器本身会占用 GPU 资源，细任务过多也会增加事件与队列成本。[MPK，§§3–5]

所以选型应从时间线出发：大量主机 launch 间隙，可先试 graph；确有可重叠的上下游准备，可分析 PDL；跨算子细粒度流水收益大、愿意承担编译运行时复杂性时，再研究 megakernel。以上是基于机制的工程建议，不是本机跑出的排名。

## 17．多 GPU 优化：重叠的是资源工作，不是纸面上的两个箭头

G pp.34–35 介绍 FLUX 和 DeepEP。多卡计算通常要交换中间结果。假设先算 8 ms、再通信 4 ms，完全串行需 12 ms；若全部通信都能藏在计算期间，理想下界是 $\max(8,4)=8$ ms。但要达到它，数据必须及时产生、计算与通信不能严重争用同一资源，且重叠的粒度要合适。[教学模型，依据 FLUX 的通信与计算重叠]

张量并行把同一层的矩阵工作分到多卡；collective 是一组设备共同参加的通信，例如 AllGather 汇集各卡片段，ReduceScatter 先对部分结果求和再分片。FLUX 针对其中的 GEMM 与 collective，将通信操作和计算 tile 更紧密地组织，减少只能等待整个算子完成的粗粒度限制。它不是“另开一个 stream 就自动重叠”。切小 tile 可以让数据更早可用，却也可能降低矩阵计算效率或增加同步；因此论文用具体配置评估总耗时，而不只展示通信阶段似乎缩短。[FLUX，设计与实验章节]

MoE（混合专家）让不同输入只激活一部分专家子网络；expert parallel 则把这些专家放到不同设备。DeepEP 面向这类并行：router 把 token 分给专家，dispatch 将输入送到对应设备，combine 再把专家输出按路由权重合并。网络传输、路由不均衡和专家计算共同决定关键路径。讲义的 top-8 是该模型设置，MoE 的专家选择数并非固定为 8。还要留意版本差异：G p.35 的“hook-based transfers 不用 SM”描述历史低延迟路径；本次归档提交的 DeepEP V2.5 README 已统一吞吐/低延迟 EPBuffer 接口，并明确 dispatch/combine 需要 SM、不支持 zero-SM RDMA EP，且已移除旧 V1/NVSHMEM 后端。因此不能照讲义简图推断当前代码不消耗计算资源。当前示例在通信提交后安排独立工作，再在消费结果处等待事件；router 权重由专家计算环节应用，combine 汇总传入结果，不能漏乘或重复乘。本文归档固定提交的 README，解释通信职责，没有运行跨机 RDMA 或测得其吞吐。[DeepEP 固定提交来源见 REFERENCES.json；DeepSeek-V3 §3 的系统背景]

实践中应同时看单次迭代总时长、计算有效进展、通信重叠比例、网络与 HBM 争用、尾部专家的负载。只看某个通信 kernel 提速，可能错过它抢占资源后让计算变慢的代价。Llama 3 与 DeepSeek-V3 的训练系统资料提供了大规模并行的背景，但它们的集群可靠性和训练结果不能直接证明当前服务部署也会受益。

## 18．Agent 生成 kernel：正确性是性能结论的前提

G p.36 把课程前半重新接回 GPU 编程。KernelBench 的任务是从参考 PyTorch 计算生成 GPU 实现，评价不仅看能否生成代码，还要检查输出和相对速度。其 `fast_p` 表示既满足正确性条件、又超过速度阈值的任务比例；分母、硬件、参考实现、计时与支持范围决定这个比例的意义。[KernelBench，任务设置、评估协议与实验章节]

以本课算子为例，Agent 很容易优化到“目标大小很快”，却遗漏尾部、写坏输入、复用旧输出，或者把同步移出计时区间。检查应覆盖不同形状、随机值与边界值，并把正确性失败和计时失败保留为独立结果。一个测试集只能验证其实际覆盖的性质；模型看过公开用例，也可能对其过拟合。

AutoMegaKernel 研究的是带静态检查的生成过程。静态检查可以提前拒绝某些不符合结构、调度和资源约束的方案，让昂贵设备评测集中于更可信候选；但“通过静态检查”不是任意 kernel 数学正确、并发无错且所有硬件都安全的证明。还需要明确检查器覆盖什么、哪些条件在运行时确认，以及最终数值与性能对照。[AutoMegaKernel，方法和验证章节；G p.36 的延伸]

一个可操作的开发顺序是：固定参考与输入契约 → 生成一个小改变 → 编译/结构检查 → 数值与内存行为检查 → 无 profiler 的重复性能测量 → 必要时用 profiler 解释 → 留存版本和失败结果。每轮预算同时包含模型调用、编译、设备运行和人工审查。这个流程是本文的工程建议，未声称已经完成真实 GPU Agent 搜索实验。

## 19．硬件容量、供电与冷却也是系统条件

G pp.38–40 把视角拉到机器与机房。显存容量决定能否放下权重、KV 和工作区；显存带宽影响小 batch decode；设备间互连影响并行；PCIe/网络、CPU、供电、散热和故障恢复影响整机持续工作。型号相同但互连拓扑不同的机器，端到端性能仍可能不同。

要做容量估算，先列出权重、KV、临时工作区、框架缓存和安全余量，按并行切分后计算每卡占用，再考虑峰值而不只是平均值。总成本也包括利用率、失败重试、编译调优以及维护。G p.38 引用的 IntuitionLabs HGX 文章是二手的机房资料，本文只把它作为物理约束清单的线索，不把其中功率或机架配置当作 NVIDIA 官方规格。

Making AI Less “Thirsty” 用模型估算数据中心直接用水及发电相关的间接用水，区分 withdrawal（取水）与 consumption（消耗，未及时回到原水源的部分）。其 GPT-3 训练水量是特定假设下的历史估算，2027 年全球需求数字是预测；不能当成本机测量或固定“每次问答耗水量”。地区、电力结构、季节、冷却方式和利用率都会改变结果。液冷是传热方案，也不能直接推出一定有相同的净耗水量。[该文方法、情景估算与讨论；G p.38]

这部分不要求开发者立刻设计机房，而是建立完整决策意识：算子加速最终应转化为可用吞吐、可接受延迟或更低资源消耗，并在实际部署条件下验证。

## 20．把一节课变成自己能用的判断能力

本课 G pp.41–44 的优化总结可以还原为一条推理链：先确定正确的计算和计时边界；观察关键路径；判断受哪个资源或依赖限制；选择改变数据复用、工作切分、流水或通信的方法；最后验证收益、代价和适用范围。前半 Agent 反馈要求你建立证据，后半 GPU 知识帮助你解释证据。

随文 [CPU 教学示例](examples/gpu_reasoning.py) 可用 `python3 examples/gpu_reasoning.py` 从本课目录运行；[运行记录](examples/EXAMPLE_RUN.json) 保存实际结果。它检查索引覆盖、逐元素参考结果、分块 softmax/归并以及成本模型。**它没有模拟真实 GPU 调度，也没有验证 CUDA 实现或论文性能。** CUDA、Triton、PDL、CUDA Graph、多卡通信与模型测试均未执行。

若有 GPU，后续可以固定设备与软件版本，选择多组数组长度，对“原始三算子、编译器融合、自写融合 kernel”逐个做正确性与稳态计时；再用时间线区分启动、搬运和计算，观察小输入与大输入收益为何不同。随后才扩展到 attention、长上下文和多卡。这是一份未执行的实验设计；不要预填预期加速比作为结果。

### 自测与参考答案

1. **`n=257`、每 block 256 线程，为什么第二个 block 不能无条件写所有元素？** 只有全局索引 256 合法，其余越界；grid 向上取整保证覆盖，掩码保证安全，两者缺一不可。
2. **launch 调用耗时 20 微秒，可以说 kernel 用时 20 微秒吗？** 不可以；可能只测到主机提交。需要设备事件或覆盖必要同步的时间范围，并说明是否包含排队、拷贝和首次编译。
3. **融合把理想字节数从 $6Ns$ 降到 $2Ns$，为什么可能只快 10%？** 原先可能不是带宽主导，其他阶段占比大，已有缓存/编译融合，或新实现增加寄存器压力、同步等。先定位实际关键路径。
4. **GPU 活动度 100%、MFU 很低是否矛盾？** 不矛盾。设备可能一直在搬数据、执行非矩阵指令或只占部分 SM；MFU 还需要同一范围的有效 FLOPs 与精度峰值。
5. **两个 KV 分片的局部 attention 输出为何不能简单平均？** 每片的 softmax 分母和总权重不同；需要按全局统一尺度合并局部指数和与未归一化输出。
6. **persistent kernel 能把 160 个等长不可拆任务在 132 个单任务 SM 上变成一轮吗？** 不能。必须改变工作可拆性、任务粒度或并发假设；Stream-K 的细粒度归约拆分是额外机制。
7. **CUDA Graph、PDL 和 megakernel 是否可以互相替换？** 不可以。它们分别主要影响重复提交、相邻 kernel 的部分重叠和更细的设备任务执行；可组合，但依赖保证、资源与复杂性不同。
8. **计算 8 ms、通信 4 ms，开启重叠后为何仍是 11 ms？** 可能只有部分数据及时可用、通信争用计算资源、细分/同步有成本。8 ms 只是理想完全重叠的下界。
9. **生成 kernel 通过公开用例且最快一次领先，可以直接上线吗？** 不能据此完成验收。还需目标范围的正确性、稳定计时、版本绑定及端到端验证；不能静默排除失败。
10. **反馈图显示投入多的学生分数高，能推出增加 Agent 调用次数就提高分数吗？** 不能。能力、任务难度和投入方式可能混杂；需要受控比较，且课程样本的分母与统计口径要分开。
