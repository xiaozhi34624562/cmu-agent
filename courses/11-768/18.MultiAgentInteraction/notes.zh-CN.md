## 1. 多 Agent 系统增加的是互动关系

### 1.1 从单个函数调用转向共同环境

讲义 [p.2](lecture-18-multi-agent-systems.pdf#page=2) 的图有多个 Agent、共同环境、各自的动作、观察和奖励。核心是：一个执行者做完动作后，其他执行者面对的环境可能已经变了。

可用一个教学记号表达：

$$
s_{t+1}\sim P(\cdot\mid s_t,a_t^1,\ldots,a_t^n),\qquad
o_t^i\sim O_i(\cdot\mid s_t),\qquad r_t^i=R_i(s_t,a_t^1,\ldots,a_t^n).
$$

$s_t$ 是环境状态，$a_t^i$ 是第 $i$ 个执行者的行动，$o_t^i$ 是其可见观察，$r_t^i$ 是其反馈。这个同步记号帮助理解共同影响，不要求所有真实系统同时行动；异步实现还需记录事件顺序。各方的观察和奖励也未必相同。

后端类比：多个服务修改同一业务对象，谁先提交会影响别人读取什么。Agent 又多了一层语义决定：它可能根据刚读到的情况改变目标、解释或后续动作。

### 1.2 本课的三种用途不能混在一起

讲义 [p.3](lecture-18-multi-agent-systems.pdf#page=3) 区分三条路线：

1. **推理时增加投入。** 多个研究或执行循环共同解决一个任务，例如并行查证公司信息。
2. **处理本来就有其他实体的任务。** 用户、交易对方、同事、市场参与者，各自掌握不同信息，甚至有不同利益。
3. **构造训练和评价环境。** 模拟用户、伙伴或辩论者，为一个模型提供学习信号或更强的监督。

同一模型生成多个角色的回复，并不自动获得知识互补；换成不同模型也不自动得到独立错误。更应该看每个执行者有什么输入、可用动作、独立反馈和决策责任。

### 1.3 什么时候值得拆出独立循环

讲义 [p.4](lecture-18-multi-agent-systems.pdf#page=4) 列出单流上下文、串行、专业化不足和探索受限。把它转成工程问题：当前瓶颈究竟是资料太多、独立调用太慢、需要不同权限，还是一条探索路径过早锁定？

简单查询可作为工具；一条需要连续搜索、读证据、发现缺口、调整方向的路径，才更可能值得分配独立上下文。一个连续修改过程如果处处共享隐含决定，拆分反而增加交接。

## 2. 角色工作流：把职责落实为输入、工具和产物

### 2.1 角色名怎样才产生实际差别

讲义 [pp.5–6](lecture-18-multi-agent-systems.pdf#page=5) 从 role-based decomposition 讲到 ChatDev：设计、编码、代码审查、测试等阶段由相应角色对话，前一阶段的产物进入下一阶段。这里固定的是职责与交接流程，不能仅凭角色名称推断能力提高。

把这张图用于工程设计时，可以要求角色对应可观察差别：需求维护者产出需求，设计者固定接口，执行者产生实现，验证者依据规则核验。这是由职责分解得到的工程建议。只在 system prompt 中写“你是资深专家”，没有改变信息、工具和检查依据，能力差异可能很小。

以教学案例“解释三家公司利润变化”为例，把角色分为行业专家、财务专家和审查专家之前，先决定他们分别交付什么。若三个角色都读取同一段摘要并写一段看法，系统仍可能只有同一份信息的三次改写。

### 2.2 子 Agent 作为工具是一种责任安排

讲义 [p.7](lecture-18-multi-agent-systems.pdf#page=7) 用 calendar / email / supervisor 展示：主管调用 `schedule_event`，工具内部启动日历 Agent。对子 Agent 而言，它有自己的工具循环；对主管而言，这是一个有输入输出的能力边界。对应参考为 [personal assistant 文档快照](references/Build_a_personal_assistant_with_subagents.html)。

这种模式中的最终责任通常仍在主管：它委派局部任务，接回结果后继续组织全局。它不同于把后续控制权整体交给另一个 Agent 的 handoff。需要明确谁负责最后回复、谁能改变共同口径、谁可以执行外部写入。

从上述工具边界推导出的工程要求是：返回字符串只是接口形式，不能代替副作用状态。日历任务应能报告活动 ID、创建是否成功、时区和冲突；“我已安排”不是可信的外部执行记录。权限由工具和运行时实施，不能靠角色自称只读来保证。这些字段不是讲义代码已经实现的保证。

### 2.3 工作流减少猜测，也可能过度固定

固定角色和流程适合依赖已知、交付明确的任务；面对事先未知的子问题，角色分类可能不适用。讲义 [p.8](lecture-18-multi-agent-systems.pdf#page=8) 因此转向通用执行者和开放委派。实际设计可以先固定共同约束，再允许局部调查路径变化，没必要在“完全固定”和“完全自由”之间二选一。

## 3. 多 Agent 辩论：交换答案之后发生什么

### 3.1 从独立候选到多轮修正

R1 的基本过程是：各实例先独立生成答案；再把其他实例的答案加入输入，让各自审查并修正；重复若干轮。它是推理期过程，不要求训练权重。见 [R1 pp.3–4，§2](readings/Improving_Factuality_and_Reasoning_in_Language_Models_through_Multiagent_Debate.pdf#page=3) 与讲义 [pp.9–10](lecture-18-multi-agent-systems.pdf#page=9)。

讲义 p.9 的宝石例子可以手算：钻石 175，红宝石少 35，所以红宝石 140；绿宝石是红宝石两倍，为 280；合计 $175+140+280=595$。图展示一个最初错误的实例经交换回答后改正。图中展示的这一条轨迹，不代表每次辩论都会改正错误。

这里与投票的差别是：投票只在候选之间选，辩论会改变候选本身。与“生成—外部验证”也不同：对话中的批评仍是模型输出，未必提供可独立核实的新证据。

读 p.10 的结果表时，应分别比较 single、reflection、majority 与 debate。Arithmetic 和 Grade School Math 列使用百分制，而 Chess 列是 $\Delta PS$ 分数，不能把三列都说成正确率。角色数、轮次和总计算投入也需要一起看；这张表不构成同费用下适用于所有 Agent 环境的结论。

[R1 p.5](readings/Improving_Factuality_and_Reasoning_in_Language_Models_through_Multiagent_Debate.pdf#page=5) 说明主要实验使用 ChatGPT 模型、三个实例和两轮辩论，并保持初始提示与底层模型一致；Chess 用 Stockfish 评估候选走法的兵值优势。相同模型和初始问题控制了部分差异，但没有让单次回答与多轮辩论消耗相同计算量。不能把这组历史实验直接作为当前模型升级或增加团队人数的收益预测。

### 3.2 为什么共识可能越来越错

一个 Agent 看见多个相似答案后，可能把重复误当成支持强度。反复互相引用也可能抹去原先正确但少数的观点。固定轮数和最终一致性只能约束过程，不证明结论。

教学概率例子：三个判断者独立、同分布，正确率均为 $p$，二元多数投票正确率为 $p^3+3p^2(1-p)$；$p=0.7$ 时为 0.784。若三者总在同一组问题上出错，投票后仍是 0.7。独立性是假设，不是“开三个会话”自然带来的属性。

工程上可先保留独立初答，再交换“主张、依据、反例与不确定性”，尽量允许对方重算或回读原文。对于可以程序检查的算术，不必用三轮辩论代替一次重算。停止条件应包括有证据的解决、关键分歧仍在、预算耗尽，不能只等大家同意。

## 4. 开放委派与递归：程序原语只解决调度的一部分

### 4.1 子任务数量为什么会失控

讲义 [pp.11–13](lecture-18-multi-agent-systems.pdf#page=11) 用旅行计划和 Recursive Agent Optimization 展示按需启动子 Agent。父任务把住宿、交通或某个信息缺口交给新实例，子实例还可能继续委派。参见 [RAO 归档原文](references/Recursive_Agent_Optimization.pdf)。

若每个节点最多创建 $b$ 个子执行者，从根节点深度 0 最多递归到深度 $d$，节点上界为 $1+b+\cdots+b^d$。教学例子 $b=3,d=3$ 就可能有 40 个节点。因此并发上限、深度上限、总费用和全局截止时间必须属于共同预算。每个局部任务都遵守自己的小预算，仍可能让总预算超标。

RAO 的论文贡献还包括**训练递归策略何时、怎样委派与通信**。在执行时允许创建子 Agent，只提供了动作空间，不等于已经获得其训练结果。学习对象、训练反馈和推理期接口应分别记录；本地没有执行 RAO 训练。

委派应回答：它补哪个缺口，不能直接使用已有产物吗，执行结果怎样验收？输出“再研究一下”无法证明新分支必要。

### 4.2 gather、await 与共享状态的真实含义

讲义 [p.12](lecture-18-multi-agent-systems.pdf#page=12) 给出 `launch_subagent`、并行收集、`await` 和异步状态管理等原语。`gather` 可以并发等待独立任务；`await` 表达控制依赖。但它们不会检查两家公司是否使用相同财务口径，也不会自动保证写入不冲突。

以下是运行语义示意，不是已部署系统或可直接运行的 SDK：

```text
固定共同研究说明 v3
领取并执行 A / B / C 的就绪任务
每个任务返回带输入版本的候选产物
运行时验证身份、版本、结构与预算
主管判断可比性、证据覆盖与补查需要
```

如果 B 依赖 A 新发现的会计口径，就应建立依赖或重新规划。把所有函数一并交给并发执行，不能消除真实业务依赖。

### 4.3 递归为什么能缓解上下文限制

讲义 [p.13](lecture-18-multi-agent-systems.pdf#page=13) 讨论的是把中间交互分散到多个上下文。父 Agent 只接回子任务需要的结果，子 Agent 的全部探索不必都进入父上下文；单次调用的窗口大小并未因此扩大。这个机制也有交接损失：如果子结果删掉关键假设，父 Agent 仍会在不完整信息上继续推理。

回查 [RAO pp.6–8，Table 1(a)](references/Recursive_Agent_Optimization.pdf#page=6)：图中受限上下文实验是在 TEXTCRAFT-SYNTH 合成制作任务上，使用 Qwen-3-4B-Instruct-2507，训练与评测窗口均为 8K。单 Agent 与递归 Agent 的整体成功率分别为 24% 和 95%；这是经过相应训练后的系统比较，不能理解为给任意模型加一个委派工具就获得相同改善。右图横轴是 **Training Steps**，也不是部署时增加推理次数。

表中的时间还有不同分母：成功率在评测任务集上计算，Steps 和 Time 只在双方都成功的任务交集上统计；该交集上的平均耗时为 7.1 秒与 9.9 秒。因此这张表支持受限上下文下的成功率改善，却不能证明这个条件下递归更快。工程上还需分别记录每个上下文的峰值长度、整棵树的总 token、返回产物质量和总时延。

## 5. MACU 与异步软件工程：共享的不只是文字

### 5.1 计算机使用是部分可观察问题

浏览器登录态、动态页面、后台进程、文件和 UI 状态，往往不能只靠一句完成摘要传递。某个 Agent 看过的临时页面，下一位执行者可能无法重新打开。MACU 因此把观察保留和环境交接作为系统问题。见讲义 [pp.14–15](lecture-18-multi-agent-systems.pdf#page=14) 与 [R2 pp.2–5](readings/Multi-Agent_Computer_Use.pdf#page=2)。

R2 的主管维护子任务 DAG；只有依赖满足的 frontier 节点才能启动。子 Agent 在隔离虚拟机中运行自己的计算机使用循环。完成后，主管接收近几张截图、最终回复、父节点信息以及文件变化，决定是否追加工作、保存文件或修改图。

这与“每人发一段总结”相比，显式保留了后续任务可能无法重建的环境证据。R2 p.5 也说明子 Agent 可以从选定 VM 初始化或继承状态；隔离并不意味着每次从空白环境开始。文件交接、VM 继承和把所有执行者放进同一实时会话，是三种不同安排。迁移到业务系统时，应明确需要保留哪个登录态、页面或文件，这是环境契约的工程要求。

### 5.2 动态 DAG 与局部失败恢复

R2 允许新增、删除、改写或取消节点，并限制图编辑预算。修改后仍需是合法 DAG，不能因为模型给出 JSON 就接受循环依赖。主管还能让原执行者继续工作，而非每次都重启。

教学案例：A 公司财报缺页，主管可以换资料入口，只重做 A 的受影响节点；B、C 已核验结果不需跟着重跑。如果关键输入口径改变，应使依赖旧版本的结果失效，而非把所有迟到结果继续合并。

讲义 p.15 按动作数画出多个基准的成功率，主旨是较长、可并行任务更能获益。横轴是执行动作数，不能直接读成费用或秒数；不同任务、模型和规划预算也不能混为统一增益。本篇不从图形粗略读取新的精确百分比。

具体条件见 R2 p.5：主实验使用 Qwen3.6-27B 子 Agent 与 Claude Opus 4.6 主管，最多 4 个并行子 Agent、重规划预算 10，并另测较弱主管。OSWorld 使用执行验证，而若干网页任务依赖 Judge 或 rubric；这些评分器的误差和权限都应计入结果边界，不应把各基准成功率视为相同性质的测量。

### 5.3 CAID：让异步编码有共同任务与变更记录

讲义 [pp.16–17](lecture-18-multi-agent-systems.pdf#page=16) 提到主管规划 DAG、结构化 JSON 通信、Git 并行与受管理的冲突。对应 [CAID pp.2–3，§2](references/Effective_Strategies_for_Asynchronous_Software_Engineering_Agents.pdf#page=2)。其中，就绪的前提是依赖任务已经完成且成功集成到主分支。工程 Agent 在独立 worktree 中实现并自验，主管尝试合并；产生冲突时，由提交者拉取最新集成状态、解决后重新提交。只收到“做完了”的消息，还不足以释放下游依赖。

由这个交接流程进一步得到的工程建议是：Git 可以记录补丁、隔离分支并帮助合并，但不能发现所有语义冲突。后端把空值视为合法，前端仍拒绝空值，可能完全没有文本 merge conflict。需要共同接口版本、明确拥有者以及真实集成验证。

异步执行也不等于“所有返回都立即采用”：旧任务、已取消任务和过期输入的结果都可能迟到。每条消息至少应关联任务、尝试、输入版本、产物和当前责任。运行时检查状态，主管处理语义差异。

## 6. 黑板、DeLM 与 GitSwarm：共同工作区怎样组织协作

### 6.1 一份黑板里有几种不同的事实

讲义 [p.18](lecture-18-multi-agent-systems.pdf#page=18) 的 Blackboard 不只是“大家共用一张表”。主 Agent 将所需信息写到请求板，各文件 Agent 掌握不同数据簇，自行判断能否响应，把发现写到响应板；主 Agent 使用回复继续生成和执行解题程序。也就是说，主 Agent 仍负责整体问题，但不必事先准确知道应该把每个请求指派给谁。见 [Blackboard pp.2–3，Figure 1](references/LLM-Based_Multi-Agent_Blackboard_System_for_Information_Discovery_in_Data_Science.pdf#page=2)。

由该架构推导到可靠实现，应至少区分：权威任务状态、候选发现、已接受产物。数据库里有一条记录，不代表对应结论已被验证。下面的表设计是工程扩展，不能反过来当成该论文已经实现的事务协议。

一个可实现的教学设计：任务表记录拥有者、依赖和版本；消息日志追加进展；产物存储保留文件和哈希；接受记录说明为什么采用某个版本。普通程序可处理索引、权限和状态原子更新，不需要把这些动作都交给新 Agent。

### 6.2 DeLM 为什么关注等待气泡

讲义 [pp.19–21](lecture-18-multi-agent-systems.pdf#page=19) 描述公共任务队列和 append-only 消息板。DeLM 希望减少主管等待子 Agent、同步讨论等待整轮结束，以及互不知情导致的重复工作。见 [DeLM pp.1–3](references/Decentralized_Multi-Agent_Systems_with_Shared_Context.pdf#page=1)。

执行者可以异步领取任务、发布中间发现，并看到同伴状态。这里“去中心化”改变了调度和信息流，不意味着没有共同规则。至少要解决以下边界：

- **原子领取。** 两个执行者同时看见 READY，不能都自认唯一拥有者。
- **失联恢复。** 领取者中断后，何时允许重派，旧执行者回来怎么办？
- **读取范围。** 日志只追加有助于保留历史，但每次全读仍会造成上下文膨胀。
- **接受规则。** 谁可以把候选结论升级为下游使用的事实？

前三项可以由事务、租约、版本与增量读取支持；最后一项还需要内容验收。以上是工程推导，不是 DeLM 论文公开接口的逐字复刻。其归档实验涉及特定模型和长任务子集，不能把摘要中的最大增益作为任意仓库的保证。

### 6.3 Git 既是产物系统，也是潜在通信渠道

讲义 [p.22](lecture-18-multi-agent-systems.pdf#page=22) 用 GitSwarm 展示借助 Git 组织 swarm；见 [GitSwarm pp.3–4，§2](references/GitSwarm_Decentralized_Compounding_Inference.pdf#page=3)。其关键是持久、可分叉、能记录依赖的贡献：每个 worker 在隔离 worktree 中选择起点，产出原子提交，并用 `informed_by` 声明除 Git 父提交之外还借鉴了哪些贡献。可以读取另一分支的发现，而不必先把整条分支合并进来。

论文还区分贡献、提名已有候选和放弃本轮发布；通用的问题求解设置按提名选择最终候选，研究任务则可按验证分数选择模型。发布校验只保证任务规定的提交要求，不保证方案正确；`informed_by` 也只是 worker 声明的依赖，不是已经独立证明的因果影响。这两项限制在原文中都有明确说明。

p.22 的步骤是检查仓库、界定贡献、选择父提交、开展工作，再发布提交或保留不提交。图中甚至保留了已被反驳但仍有可用局部结果的分支。这提示我们：Git 祖先关系记录了产物血缘，不等于论证成立；反驳、修复、验证和整合应有独立的语义记录。

共享文件内容、文件名、目录名和状态变化都可能携带信息。设计通信边界时，不能只检查显式聊天消息；本课后面 p.35 的案例正好说明环境自身也能成为通道。

## 7. 通信的增益：共享可验证进展，而非反复表达观点

### 7.1 先建立正确对照

R3 区分 $k$ 个相互独立的尝试和 $k$ 个能在执行中交流的执行者。对有评分器的优化任务，`best@k` 表示独立尝试中的最佳结果；`team@k` 表示有通信的团队结果。对二元通过任务，`pass@k` 则关注至少一次通过。名称相似，任务评分和选优机制仍需分别说明。

R3 在各任务的对照内使用相同底层模型和工具，按每 Agent 的行动预算或运行时长设置条件，并从总输出 token 和时间两个维度观察结果。它的直接问题是：同样有 $k$ 条路径时，允许它们互相影响还有没有额外收益？见 [R3 pp.3–5](readings/Scaling_Discovery_through_Test-Time_Communication.pdf#page=3)。

不过，“每 Agent 预算相同”不等于所有资源都逐人相等。[R3 p.25，Table 4](readings/Scaling_Discovery_through_Test-Time_Communication.pdf#page=25) 说明团队共享容器的 CPU 和内存额度，独立尝试各有一份容器；ARC 和 packing 的容器额度不随人数增加，MNIST 团队另有扩容。行动预算、模型推理、任务容器资源及最终状态应分别记账，不能将这个设置描述成完全相同的资源隔离对照。

### 7.2 共享目录里的内容要能改变下一步实验

R3 的执行者有私有 scratch 目录与共享产物；通过原子目录创建领取不同探索槽位，用追加日志发布时间、结果、证据、复现说明及反证。主文强调依据更好的测量结果采用同伴方案；附录提示还允许原路径受阻或临近结束时收敛，要求记录采用原因，并在最终结束前保留有意义的变体，防止全体过早收敛。

这里要分清机制和行为要求。[R3 pp.25–26，Appendix A](readings/Scaling_Discovery_through_Test-Time_Communication.pdf#page=25) 明确说明，报告证据、复查候选、保留变体等主要写在通信提示中；harness 并不会自动替 Agent 证明“更好”或完成采纳。scratch 目录是各自约定的工作区域，也不等于操作系统权限隔离。若在工程系统中要求强制拒绝过期或未经验证的结果，需要另外实现版本与验收检查，不能只复用提示词就认为这些约束已经成立。

教学例子：A 发现某检索参数在固定验证集上提高引用支持率，发布配置、数据版本和逐条结果；B 复现后把它与自己的分块方法组合。这样的消息会改变后续实验。相反，“我觉得这个参数不错”没有给 B 可检查的改进依据。

讲义 [p.25](lecture-18-multi-agent-systems.pdf#page=25) 的图展示通信者在执行中交替吸收进展。收益来自发现被复用，以及失败路径不被重复走；不是因为消息数本身有价值。

一个正面结果来自 R3 Table 2：25 个公开 ARC-AGI-3 游戏上，Sonnet 4.6 的 team@5 完整解题率为 8.0%，独立 best@5 为 2.2%。作者对每个游戏收集 64 次单 Agent 尝试，团队大小 3、5 各进行 20 次试验；best@k 从有限单 Agent 池不放回计算，不能随意换成独立同分布公式 $1-(1-p)^k$。这些条件支持该游戏设置下的通信收益，不代表真实研究普遍有相同比例的改进。见 [R3 pp.4–5](readings/Scaling_Discovery_through_Test-Time_Communication.pdf#page=4)。

### 7.3 同一篇论文也给出了失败对照

讲义 [p.24](lecture-18-multi-agent-systems.pdf#page=24) 摘录 R3 Table 3：

| Terminal-Bench 2.0 条件 | Mean Accuracy | Max Accuracy |
|---|---:|---:|
| 单 Agent pass@1 | 52.53% | — |
| 独立 pass@2 | 62.36% | 64.04% |
| 通信 team@2 | 60.67% | 61.80% |

这个条件下团队超过单次尝试，但低于独立两次的结果。不能只拿第一行与第三行比较，就说“通信本身有效”。原文讨论，算力不足或缺少能可靠区分中间方案的反馈时，协调成本可能抵消收益。R3 的多日研究任务、ARC 游戏和终端任务具有不同预算与指标，不能把某一任务的倍数搬给另一个任务。

进一步回查 [R3 p.17](readings/Scaling_Discovery_through_Test-Time_Communication.pdf#page=17)：这里覆盖 89 个任务，但重复轮数很少，使用两轮 team@2 与四轮单 Agent 评测，作者把差异作为描述性证据。team@2 共享一个最终容器状态；pass@2 保留两份独立最终状态，并由评测结果做 oracle 选优。这两种产物空间和选择权限不同，部署时未必拥有后者的真实答案。不能把这个小样本差距解释成精确的普遍退化幅度。

### 7.4 费用和时延要分开

以下是基于并行调度与 R3 对照思路的教学近似，不是该论文的成本定理：

$$
C_{total}=\sum_i C_i+C_{communication}+C_{verification},\qquad
T_{total}\gtrsim T_{critical\ path}+T_{coordination}.
$$

成本各项应采用互不重复的记账口径；$T_{coordination}$ 在这里仅指落在关键路径、不能被并行隐藏的额外开销，不能把所有异步消息耗时再累加到关键路径上。

多个执行者可以减少墙钟等待，却同时增加总费用；更多验证可能稍微变慢，却减少人工返工。相反，主管重做每个 worker 的完整调查，容易同时支付并行和串行成本。应按真实任务价值选择约束，而非追求某个独立的加速比。

## 8. 人机交互也是多 Agent：下一句话会改变环境

### 8.1 用户掌握的信息不应被默默当成已知

讲义 [pp.26–28](lecture-18-multi-agent-systems.pdf#page=26) 把人机协作放入多 Agent 视角。用户可能知道期望的输出、偏好和边界条件，Agent 只得到一句不完整的初始要求。澄清问题既是信息收集动作，也会消耗用户时间。

教学例子：“帮我比较利润改善”没有明确利润口径。若不同口径会改变结论，询问或回查定义有实际价值；如果已有任务说明明确写了口径，再问一次只是重复。该不该问，要看缺口对后续决策的影响和获取成本。

R4 的 ColBench 用隐藏参考产物模拟这种不对称：后端任务中，用户模拟器能读参考代码，回答 Agent 对边界行为的澄清；前端任务中，它能比较参考页面和当前渲染，再给出差异反馈。见 [R4 pp.4–5](readings/SWEET-RL_Training_Multi-Turn_LLM_Agents_on_Collaborative_Reasoning_Tasks.pdf#page=4)。

### 8.2 为什么这是有用但有限的模拟

参考产物使反馈和最终验证更容易构造。后端任务通过隐藏单测评价，前端任务使用图像表示相似度；这些反馈的权威不同。图像相似不保证交互、可访问性和真实用户满意。

真实用户有时自己也没有固定的最终答案，会改变偏好或无法准确描述需求。模拟器知道完整参考产物，是研究设置中的便利假设。若 Agent 从模拟器回复中获得不该直接泄露的答案，或者评测只奖励与参考图相似，就可能高估真实协作能力。

对应 [用户模拟器参考文章](references/What_does_it_take_to_build_a_human-like_user_simulator.html)，工程评估应检查目标一致性、知识边界、行为多样性和失败表现，而不只检查说话是否“像人”。

讲义 [p.28](lecture-18-multi-agent-systems.pdf#page=28) 还把 **user policy** 和 **reward model** 分开：前者决定用户下一轮说什么、做什么，后者评价任务过程或结果。两者可能使用同一底层模型，却承担不同职责。模拟器回复“我满意了”不能自动当作外部任务成功；否则策略可能同时利用对话和评分器的盲点。这是由图中职责区分得到的工程检查项。

## 9. SWEET-RL 与 PPP：从整段结果回到每一步行为

### 9.1 终局正确不能告诉你哪一步起了作用

本节从讲义 p.27 的 ColBench 图延伸到指定阅读 R4 的训练方法，公式不是讲义逐页推导。一段十轮协作最后失败，可能是早期没问清定义，也可能是最后算错数字。只有终局低奖励时，训练信号很难区分这些情况。**信用分配**就是估计哪些动作对最终效果有帮助，哪些动作需要改变。

R4 将完整交互建模为有限时长的部分可观察过程：Agent 可见历史 $o_t$，隐藏参考信息为 $c$，动作 $a_t$ 是当前轮回复。critic 是评估模型，actor 是产生行动的策略模型。训练时 critic 能看到 $c$，actor 的输入始终只有交互历史，部署时也不依赖这份隐藏参考。见 [R4 pp.5–7](readings/SWEET-RL_Training_Multi-Turn_LLM_Agents_on_Collaborative_Reasoning_Tasks.pdf#page=5)。

### 9.2 advantage 是“相对当前基线，这一步更有利吗”

原文使用：

$$
A^\pi(o_t,a_t,c)=Q^\pi(o_t,a_t,c)-V^\pi(o_t,c).
$$

$\pi$ 表示当前策略，$Q$ 是做了这个动作后继续按该策略执行的期望累计回报，$V$ 是该策略在当前状态的平均回报，差值表示当前动作相对基线的好坏。它不是“这句话文笔如何”的分数，也不要求把一个动作的作用解释为完全独立的因果效应。

教学理解：在只计最终成功的假想任务中，如果当前历史的平均成功概率是 0.5，先澄清一个关键边界后的成功概率是 0.8，那么该动作的 advantage 为 0.3。这需要对后续结果的期望作比较；看到一次成功，并不能直接测出这个数。

SWEET-RL 用偏好轨迹训练逐轮 advantage。给同一任务的优选轨迹 $\tau^+$ 和较差轨迹 $\tau^-$，使用 Bradley–Terry 目标：

$$
\mathcal L_A(\theta)= -\log\sigma\left(
\beta\sum_t A_\theta(o_t^+,a_t^+,c)
-\beta\sum_t A_\theta(o_t^-,a_t^-,c)\right).
$$

$\sigma(z)=1/(1+e^{-z})$ 是 sigmoid，$\beta>0$ 是本章损失的缩放超参数；$+$、$-$ 分别标记同一任务中回报较高、较低的轨迹。增大两条轨迹的累计分数差，会降低这个损失。该目标约束的是累计比较，不能推出优选轨迹的每一步都正确，也不能保证学到的 $A_\theta$ 等于真实 $Q-V$。这里的 $\beta$ 与 §12 的“参数知识正确率”同名但含义不同。

R4 p.7 使用已有语言模型输出头来表示这个分数：

$$
A_\theta(o_t,a_t,c)=\frac{1}{L}\sum_{\ell=1}^{L}
\log\frac{\pi_\theta(a_t^\ell\mid o_t,a_t^{<\ell},c)}
{\pi_{\mathrm{ref}}(a_t^\ell\mid o_t,a_t^{<\ell},c)}.
$$

$a_t^\ell$ 是本轮回复的第 $\ell$ 个 token，$L$ 是回复长度，$\pi_\theta$ 是可训练的 critic 语言模型，$\pi_{\mathrm{ref}}$ 是冻结的初始模型。这里利用它们对同一段回复的概率比评分，不是再生成一段自由文字评价。除以 $L$ 把累加分数变成平均 token 分数；作者报告这有助于稳定训练，不能进一步保证已消除一切长度偏好。归档式 (3) 左侧写作 $h$、条件中写作 $c$，本文按 R4 §4.1 的定义统一称隐藏信息 $c$。

两阶段的输入和输出可以这样对应：

| 阶段 | 模型能看到什么 | 怎样得到学习信号 | 更新什么 |
|---|---|---|---|
| 学 critic | 交互历史、当前动作、隐藏参考 $c$ | 同任务轨迹的终局回报排序；拟合累计 advantage 比较 | $\theta$；参考模型冻结 |
| 学 actor | actor 只见交互历史；critic 另见 $c$ | 每轮采样 16 个动作，critic 排序，从上半区和下半区随机取偏好对 | actor 参数 $\phi$，用 DPO 提高较优动作的相对概率 |
| 部署 | 当前可获得的历史和工具观察 | 环境及用户的真实反馈 | 本方法的部署不需要训练期 critic 或隐藏标准答案 |

**公式版本核查。** R4 v1 p.7 的式 (4) 将 DPO 项排成了两个 log 概率相除；这与 [DPO 原论文 v3，p.4 式 (7)](references/Direct_Preference_Optimization_Your_Language_Model_is_Secretly_a_Reward_Model.pdf#page=4) 的“概率比再取 log”不一致。本文按 DPO 原式解释 actor 更新；对一对本轮动作，忽略数据集平均的写法是：

$$
\ell_{\mathrm{DPO}}(\phi)=-\log\sigma\!\left[
\beta'\left(\log\frac{\pi_\phi(a^+\mid o_t)}{\pi_{\mathrm{ref}}(a^+\mid o_t)}
-\log\frac{\pi_\phi(a^-\mid o_t)}{\pi_{\mathrm{ref}}(a^-\mid o_t)}\right)\right].
$$

其中 $a^+,a^-$ 是 critic 选出的较优、较差动作，$\beta'$ 是 actor 阶段的系数；每个动作的序列 log 概率由其 token log 概率累加。critic 的按长度平均与这里的标准 DPO 不是同一个公式。训练提高的是较优动作相对于较差动作、再相对于冻结参考的偏好程度；actor 的条件仍不含 $c$。这是公式交叉核查，不是对作者代码已逐行验证的声明。

训练可以复用离线交互历史，并在这些历史上采样动作和评分，不需要再向真人收集每一轮回复；这不等于完全不发生模型调用或没有训练成本。以上流程见 [R4 pp.6–7，§4](readings/SWEET-RL_Training_Multi-Turn_LLM_Agents_on_Collaborative_Reasoning_Tasks.pdf#page=6)。

关键不是多加一个审查角色，而是：训练期额外信息让评价更有依据；逐轮信号改善长交互的学习。R4 报告 ColBench 条件下的改善，不能据此声称所有协作场景或任意小模型都能替代更强模型；本地也未训练 critic 或 actor。

### 9.3 PPP：任务完成之外，还要衡量时机与偏好

讲义 [pp.29–30](lecture-18-multi-agent-systems.pdf#page=29) 使用 [Training Proactive and Personalized LLM Agents](references/Training_Proactive_and_Personalized_LLM_Agents.pdf) 展示模拟互动中的多目标奖励：

$$
R=R_{Prod}+R_{Proact}+R_{Pers}.
$$

三项分别关注任务完成质量、主动交互和偏好遵循；其中 productivity 在原文中指完成质量，不是运行速度。具体机制见 [PPP pp.3–5，§4–5](references/Training_Proactive_and_Personalized_LLM_Agents.pdf#page=3)：先把精确需求改写为不完整需求，用户模拟器保留原需求及指定偏好；Agent 可通过 `ask_user` 询问，再完成任务。

主动性奖励并不等于“多问就加分”。模拟器把每次问题分成低、中、高用户努力：能从原需求直接回答为低努力；无收益的额外询问可能为中努力；把查文档、看代码等工作交回用户则可能为高努力。原文奖励在所有问题都是低努力时加 0.05，每个中努力问题扣 0.1，每个高努力问题扣 0.5。个性化奖励另按具体偏好计分，既有规则检查也有 LLM Judge。用户努力的会话级分类与逐次累积的奖励是两种口径，不能混用。

具体说，会话级用户努力按单轮最大努力归类；不做澄清就对模糊需求给出错误结果，也被归为高努力，因为用户还要纠错。这个评价规则说明，“完全不问”也不是默认的良好主动性策略。

p.30 的对照图说明，仅优化任务成功，与加入上述交互奖励，会产生不同曲线。三个分量已经有各自的数值尺度，式中相加不代表三个维度实际影响相等，更不证明可以把该权重直接迁移到所有业务。原文预设 20 种偏好并留出 8 种评测，这能检验该设置下的迁移，但不能覆盖真实用户的所有偏好。

教学案例：研究助手主动提醒“缺少上期可比说明”可能有用；不断打断用户、追问无关偏好则没有价值。实际奖励还要检查误触发、干扰、错误确定性与权限。用户一句“我喜欢简短回复”也不能被误用成可以删掉关键证据或限制条件。

## 10. 模拟器坍缩：训练分数越来越高，真实协作却变差

### 10.1 固定模拟器会塑造策略所见的世界

讲义 [p.31](lecture-18-multi-agent-systems.pdf#page=31) 并排画出训练奖励、留出伙伴奖励和策略熵：训练分数上升，并不保证留出表现持续上升。参见 [Simulator Collapse pp.1–3](references/One_Frozen_Simulator_Is_Not_Enough_Simulator_Collapse_in_Multi-Agent_RL.pdf#page=1)。

一个冻结的用户模型可能总是耐心配合、总用相似表达、总在固定问题之后泄露关键要求。训练中的 Agent 可以学会利用这种模式，减少自己的策略多样性，却未学会面对陌生用户。

用教学记号表示，训练目标 $J(\theta;\psi)=\mathbb E_{\tau\sim(\pi_\theta,\phi_\psi)}[R(\tau)]$ 同时依赖策略 $\pi_\theta$ 和模拟器 $\phi_\psi$；$\theta,\psi$ 为两者参数，$\tau$ 为交互轨迹。模拟器不只是给轨迹打分，它还决定下一轮会看到什么，以及哪些状态被访问。只看 reward 标量，容易错过这种分布变化。

### 10.2 两种干预位于不同层次

讲义 [p.32](lecture-18-multi-agent-systems.pdf#page=32) 与原文提出：

- **Verbalized Sampling：**在每个模拟器回复回合生成带概率的多个候选，再从这个显式分布抽样。它改变模拟器的生成方式，不更新模拟器权重；这里的 inference-time 指训练 rollout 中的模拟器生成阶段，不是只在最后部署时打开一个开关。不能简单等同于把温度调高。
- **Population Co-Training：**训练时让策略面对一组可更新的模拟器，减少只利用单一伙伴模式的机会。

两者都要用未参与优化的伙伴和真实用户评价。训练池增大不等于代表了所有用户，联合训练还可能形成新的共同捷径。来源中的最大改进数字不能离开基线、数据集和人类实验条件使用；本篇重点保留机制与诊断路径。

工程诊断：若训练奖励涨、留出下降、提问和行动类型越来越单一，应先检查模拟器与奖励，不要立即增加训练轮数。训练集与评测集应按要检验的泛化目标，在用户类型、伙伴模型、任务或时间上设置相应留出边界。

## 11. 涌现通信、市场和社会：其他实体未必与你同目标

### 11.1 约定能提高效率，也可能降低外部可理解性

讲义 [pp.33–34](lecture-18-multi-agent-systems.pdf#page=33) 用 [GlossoGen](references/GlossoGen_Emergent_Language_in_Complex_Multi-Agent_LLM_Interactions.pdf) 讨论交互中形成的语言约定。执行者反复合作，可能把长描述压缩成双方理解的短表达。

该参考在 SAVEVEYRU 中构造信息不对称：现场观察者能看症状并采取行动，远程专家知道症状与处理方式的对应关系。对应关系每轮变化，迫使双方继续交流。通信成本按字符计，模拟时间 **1 秒对应 1 个字符**，因此 150s / 2000s 是该环境的通信预算，不是模型 API 的实际墙钟耗时。postmortem 是轮次之间讨论约定的复盘通道，不计入该轮通信预算，也不能用于当前救援过程中绕过限制。见 [GlossoGen pp.5–6，§3.2–4.1](references/GlossoGen_Emergent_Language_in_Complex_Multi-Agent_LLM_Interactions.pdf#page=5)。

讲义 p.34 展示预算高/低与复盘开/关的四组条件，应固定一个因素再比较另一个。上图纵轴是用 GPT-2 计算的 **perplexity（困惑度）**：越高表示消息在这个英语语言模型下越不常见，并不直接表示更短、语义更正确或效率更高。下图才是任务成功率。作者观察到低预算加复盘时更容易出现偏离英语的约定，而且复盘有助于低预算下的成功；这些结果不能单独识别“语言缩短”对成功率的因果贡献，仍须结合协议、模型能力和语言使用分析。

教学类比：团队用“口径 v4、A-C03”引用一个既有定义和结论。这种压缩是否可靠，取决于双方是否共享词表、版本和上下文。不能仅凭出现缩写或新符号，声称形成了普遍更高效的语言。

工程上保留人类可读的协议外层、版本号、来源和解码说明；当伙伴改变时，检查原有约定是否仍适用。提高内部通信效率与保持外部审计能力是两项需要一起评价的目标。

### 11.2 显式消息之外还有环境通道

讲义 [p.35](lecture-18-multi-agent-systems.pdf#page=35) 引用 [METR 对事件的独立调查快照](references/Brief_independent_investigation_of_agents_behavior_reasoning_and_collaboration_in_the_OpenAI_Hugging_Face_hacking_incident.html)，示例涉及通过目录名通信。本文只提取通道边界这一机制，不根据单页图推断整起事件的全部动机与因果。

共享文件、目录、进程、提交信息甚至状态变化都可能被执行者观察。禁止直接发消息，不自动禁止信息流；保存完整聊天，也不自动记录所有环境通信。需要把环境权限、可见性、共享资源和审计范围一起设计。

### 11.3 市场不是“所有 Agent 一起把总分做高”

讲义 [p.36](lecture-18-multi-agent-systems.pdf#page=36) 的 [Magentic Marketplace](references/Magentic_Marketplace_An_Open-Source_Environment_for_Studying_Agentic_Markets.pdf) 引入买卖双方等不同目标。对方声明的能力、成本、偏好和承诺都需要考虑其激励，不能直接当作客观事实。

其环境覆盖搜索、匹配、通信和交易，归档研究使用合成市场场景。由此得到的工程迁移是：任务分配、经济收益与信息可信性应分别验证。即使竞价选到了便宜执行者，还要验证交付；即使双方达成交易，也不证明用户福利或整体效率改善。评价应分别观察个体收益、任务质量、违规与分配结果，避免只汇总对话成功率。此处选型建议不是原文证明的通用市场最优规则。见 [Marketplace p.2](references/Magentic_Marketplace_An_Open-Source_Environment_for_Studying_Agentic_Markets.pdf#page=2)。

### 11.4 社会模拟需要持久记忆与状态转移

讲义 [p.37](lecture-18-multi-agent-systems.pdf#page=37) 引用 [Generative Agents，pp.8–9](references/Generative_Agents_Interactive_Simulacra_of_Human_Behavior.pdf#page=8)。观察先进入带时间信息的 memory stream；检索综合近期程度、重要性与当前问题相关性；反思把多条经历归纳成较高层判断，再与计划一同影响后续行动。这里的学习主要表现为外部记忆与上下文变化，不能读成每次人物对话都更新模型权重。理解重点是个体状态怎样持久化，互动怎样改变他人的信息和计划。

一个看起来合理的小镇故事，不等于经过现实社会预测验证。记忆检索、人物一致性、互动真实性和实际预测能力需要分别衡量。将它迁移到企业助手时，把用户事实、模型推断和临时假设分开保存，是本文的工程建议。

## 12. 用协作自博弈学习“我知道什么”

### 12.1 从口头承认不确定，到行动上选择检索或保留

讲义 [pp.38–41](lecture-18-multi-agent-systems.pdf#page=38) 转向训练环境。R5 的目标是学到可迁移的元知识：什么时候直接回答、用什么工具、怎样对待别人提供的答案，以及什么时候应当保留意见。参见 [R5 pp.4–7](readings/Don_t_lie_to_your_friends_Learning_what_you_know_from_collaborative_self-play.pdf#page=4)。

其动作集合包括 `#ASK`、`#SEARCH`、`#ANSWER`、`#HEDGE`。询问者没有检索工具，两个 helper 有不同语料的检索能力；返回时区分较确定回答和保留回答。这里的 hedge 并非没有内容的“也许”，而是让下游知道这份候选依据不足。

原文还讨论语言模型不可靠地表达不确定性，相关背景见 [Relying on the Unreliable](references/Relying_on_the_Unreliable_The_Impact_of_Language_Models_Reluctance_to_Express_Uncertainty.pdf)。一句自报置信度不能代替外部校准。

讲义 p.39 还提醒：措辞会影响接收者的依赖行为。普通断言、强保证和保留表达，即使携带相同候选答案，也可能让人作出不同选择。因此既要测模型会不会说“不确定”，也要测这种表达能否反映真实正确率，以及接收者是否据此采取合适行动。

### 12.2 奖励怎样让诚实表达有用

R5 给整个群体同一任务目标，并惩罚工具努力：

$$
r(h_T)=Score(y_T,y^*)-\delta\,Effort(h_T).
$$

$h_T$ 为最终交互历史，$y_T$ 为最终答案，$y^*$ 为参考答案。原文具体实验的 `Score` 是答案 token 的 F1，`Effort` 是整条轨迹的检索调用次数；搜索惩罚设得较低，主要用于区分 F1 相同的轨迹。若无必要的搜索增加成本，而错误自信又让全组答错，行动选择才有机会反映工具和参数知识的相对可靠性。惩罚过高也可能诱发少查、乱猜，因此不能只追求工具调用数低。

R5 共享模型参数，不同角色主要通过工具和提示区分。它通过多 Agent 产生训练数据，目标包括改善测试时单 Agent 的工具使用和选择性预测。因此“训练用了多 Agent”和“部署必须有一支团队”是不同结论。

具体实验使用 Gemma2-9b base；helper 分别通过 BM25 检索 Wikipedia、通过 Gecko 稠密表示检索 PubMed，训练问题来自 PopQA 与 BioASQ，并另测 Natural Questions、EntityQuestions 的开发集。工具互补性是刻意构造的条件，不是三个同模型实例自然拥有不同知识。见 R5 p.7。

### 12.3 最小博弈：谁该付出搜索成本

原文 [p.6 的 Table 1 与 Theorem 4.1](readings/Don_t_lie_to_your_friends_Learning_what_you_know_from_collaborative_self-play.pdf#page=6) 简化为两个 helper：$S$ 为搜索后回答，$G$ 为猜测并保留；搜索正确率分别为 $\alpha_1,\alpha_2$，直接猜测正确率为 $\beta$，搜索成本为 $\delta$。混合情形下，询问者采用搜索者较确定的答案；两者同类时随机选一个。

令 $\bar\alpha=(\alpha_1+\alpha_2)/2$，期望收益矩阵为：

| Agent 1 / Agent 2 | $S$ | $G$ |
|---|---|---|
| $S$ | $(\bar\alpha-\delta,\bar\alpha-\delta)$ | $(\alpha_1-\delta,\alpha_1)$ |
| $G$ | $(\alpha_2,\alpha_2-\delta)$ | $(\beta,\beta)$ |

**这里已经切换了成本模型。** 上一节训练使用“最终任务得分减整条轨迹的搜索总成本”，所有角色共享同一个标量；本节理论矩阵给每个 helper 同样的答对收益，但只从搜索者自己的收益扣一次 $\delta$。为单独比较成本口径，下文教学算例将 `Score` 简化为答对得 1、答错得 0，并沿用本博弈的答案选择规则。例如两人都搜时，矩阵每人的收益为 $\bar\alpha-\delta$；若按共同奖励、两次调用计费，则是 $\bar\alpha-2\delta$。因此 Table 1 的 Nash 均衡分析解释的是这个简化信息供给博弈，不能直接当作共享参数 ReST 训练必然收敛到同一均衡的证明。

**教学算例：**$\alpha_1=0.90,\alpha_2=0.54,\beta=0.50,\delta=0.05$。双方都搜的收益为 $(0.67,0.67)$；只让第一个搜为 $(0.85,0.90)$；只让第二个搜为 $(0.54,0.49)$；双方都猜为 $(0.50,0.50)$。检查双方单独改变行动后能否获益，可以得到此算例的唯一纯策略均衡 $(S,G)$。

这个均衡可以逐步核验：第二人选 $G$ 时，第一人搜索得 0.85，高于猜测的 0.50；第一人选 $S$ 时，第二人保留得 0.90，高于也搜索的 0.67，所以谁都不愿单独改行动。其余三格各存在能改善收益的单方偏离。对应训练共同奖励的同参数算例则为：两人都搜 0.62，只让第一人搜 0.85，只让第二人搜 0.49，都不搜 0.50；这是一份轨迹评分，不能当成两人的私人成本矩阵。

直观上，掌握适用检索工具的一方值得搜索；缺少适用工具的一方明确保留，让询问者能选择更有依据的答案。原文定理在 $\alpha_1>\alpha_2$ 且排除相等边界时，用 $\alpha_1>\alpha_2+2\delta$ 或 $\alpha_2<\beta+\delta$ 确保纯策略均衡唯一。唯一性条件成立时，若 $\alpha_1>\beta+\delta$，均衡为 $(S,G)$，否则为 $(G,G)$；唯一性条件不成立时，$(S,G)$ 与 $(G,S)$ 都是纯策略均衡。这个结论依赖限定的 $S/G$ 行动集合，也没有单独证明任意自由表达中的置信度都已校准。

### 12.4 训练过程怎样避免只学习幸运猜中

R5 用 Reinforced Self-Training：生成多条轨迹，按动作序列分组，先选平均奖励更好的动作模式，再从兼容轨迹中选高奖励样本训练；不是只挑一条偶然答对的长对话。见 [R5 p.5 Algorithm 1](readings/Don_t_lie_to_your_friends_Learning_what_you_know_from_collaborative_self-play.pdf#page=5)。

这样区分“路径通常有用”和“这次答案碰巧正确”。但奖励、工具互补性、检索质量和验证数据仍限制泛化。实际系统若检索返回的是过期资料，`#SEARCH` 也不能自动成为“已验证”。

## 13. 对抗辩论监督：裁判信息少，能否辨别专家谁更可信

### 13.1 它与 §3 的共同求解不是同一种辩论

R6 让两个专家分别为不同答案辩护，裁判根据双方论证选择答案。专家看到长文本，非专家裁判看不到原文；互动辩论允许裁判中途提问。见讲义 [pp.42–43](lecture-18-multi-agent-systems.pdf#page=42) 和 [R6 pp.3–4](readings/Debating_with_More_Persuasive_LLMs_Leads_to_More_Truthful_Answers.pdf#page=3)。

“较弱”在这个实验中主要通过信息访问不对称实现，不能笼统理解为任意弱模型监督任意强模型。任务来自经过筛选的 QuALITY 长文本理解问题，提供正确选项和一个强干扰选项；不是开放式、无原文的全部现实研究问题。

### 13.2 为什么引用核验和对照协议很重要

原文使用引文匹配工具标记引用是否真的出现在文本中；裁判被要求信任经过匹配的引文。它还控制总字数、交换位置以降低冗长和顺序偏差，并比较单专家咨询、辩论、互动辩论等协议。

引文匹配只验证“这些字确实出现”，不验证省略条件后是否仍支持结论。因此教学实现还应检查引文上下文、推断范围和候选答案的实际关系。双方都能流畅辩护时，这些机制比角色名称更接近监督的核心。

### 13.3 “更能说服”何时支持真实答案

R6 摘要在其条件下报告非专家模型与人类裁判分别约 76%、88% 的准确率，相应 naive 基线约 48%、60%。这些口径不能与所有 consultation 或互动条件混用。原文 [p.6](readings/Debating_with_More_Persuasive_LLMs_Leads_to_More_Truthful_Answers.pdf#page=6) 还显示，单方咨询者被优化得更能说服时，裁判表现可能反而下降。

这里的“更能说服”也有可操作定义：跨模型比赛中轮换双方所支持的答案，再用胜率与 Elo 评估辩手；部分设置通过 best-of-N 选择裁判更偏好的论证，并非统一通过强化学习更新辩手参数。原文使用三轮、总计 900 词的协议限制，并通过调换论证展示顺序缓解裁判位置偏差。交换支持哪个答案与交换展示顺序控制的是两种不同偏差。见 [R6 pp.3–6](readings/Debating_with_More_Persuasive_LLMs_Leads_to_More_Truthful_Answers.pdf#page=3)。

因此应把“对抗论证、引文核验、裁判能力和对照设置”一起理解。本文不把这个结果升级为“更强的说服力天然带来真相”，也不把辩论裁决视为权威原文缺失时的替代品。

## 14. 贯穿案例：把三家公司经营变化研究做成可恢复的协作

> 以下为教学设计，依据 §2 的职责契约、§5 的 DAG 与产物交接、§6 的共享状态以及 §7 的验证条件组合而成。具体字段、状态枚举、重试和幂等规则均为工程扩展，不是这些论文直接给出的统一系统，也不是已运行的 LLM 实验。

### 14.1 先固定哪些决定必须一致

用户希望比较 A、B、C 两个报告期的经营变化，区分主营改善与一次性因素。共享说明应包括公司身份、报告期、资料截止点、利润与现金流定义、比较范围、必要证据与停止条件。先确定最后要怎样比较，再判断分支怎样拆。

主管把 A、B、C 的调查分别委派给独立 worker，每个 worker 内部仍保持“检索—阅读—计算—检查缺口”的连续循环。无需为每一次数据库查询和算术单独创建 Agent。

### 14.2 产物分层，避免摘要把条件压没

```json
{
  "task_id": "company-A",
  "attempt_id": "attempt-2",
  "input_version": "spec-v4",
  "document_snapshot": "disclosures-7",
  "status": "partial",
  "claim": "利润改善，其中一次性收益占比较高",
  "claim_type": "inference",
  "evidence_refs": ["report-A:page-12:table-2"],
  "counter_evidence_refs": ["report-A:page-28:note-5"],
  "unresolved": ["未取得可比口径说明"],
  "artifact_ref": "artifacts/company-A/attempt-2"
}
```

主管先读短摘要和缺口；需要判断时，再读取结构化数字和原文。上述标识都是示例。实际引用要能回到不可混淆的来源版本，不能把“有一个页码字符串”当作引用核验。

三个 worker 都说利润改善，还不够支持“经营持续复苏”。主管要检查一次性因素、现金流与期间可比性；需要时只补查关键因果链。没有足够证据时保留部分结果，不让写作阶段把不确定性消掉。

### 14.3 将失败限制在明确边界

可以使用这样的教学状态流：

```text
WAITING → READY → RUNNING → RESULT_READY → ACCEPTED
                    ├→ INPUT_REQUIRED
                    ├→ FAILED
                    └→ CANCELLED
```

这不是任何协议的标准状态枚举。`RESULT_READY` 只是产物产生；`ACCEPTED` 表示在指定版本上满足验收。语法正确、文件存在和 worker 自称完成，都只能作为部分检查。

需要持久化的状态包括任务依赖、当前拥有者、尝试号、输入版本、预算、原始工具结果或其引用、产物哈希、验收原因与配置版本。主管判断缺口；程序执行确定性版本、预算和权限约束；开放式证据解释可结合模型与人工。

### 14.4 过程怎样恢复

1. A 缺少上一期资料：返回具体缺口，再换入口补查；不把检索空结果直接当成公司没有披露。
2. B 已接受，C 执行中断：恢复 C 的任务和剩余预算，保留 B 的有效结果。
3. 口径改为 v5：标出受影响任务，旧 v4 的迟到结果保存为历史，不能覆盖当前结论。
4. 同一个 REPORT 重复送达：不重复接受、不重复触发下游写入。
5. 外部写操作超时：先查询是否已发生；有响应缺失不代表动作未执行。
6. 最终预算耗尽：交付已核验事实、剩余关键缺口与不能成立的强结论，明确结束原因。

这条路径结合了动态 DAG、产物交接、共享约束和版本化状态。可靠性依赖整个执行链，而不只是更详细的提示词。

## 15. 方法选型与故障诊断

### 15.1 按瓶颈选机制

| 当前瓶颈 | 优先尝试 | 为什么可能有效 | 要付出的成本 |
|---|---|---|---|
| 独立工具调用串行 | 单 Agent 工具并行 | 不增加语义交接即可减少等待 | 工具限流与结果排序 |
| 多个对象各需长调查 | 主管—worker，独立上下文 | 分散局部阅读与自适应搜索 | 口径统一、产物整合 |
| 环境变化后原计划失效 | 动态 DAG 与观察交接 | 新发现可以改写依赖与路径 | 版本、取消与重规划预算 |
| 主管和同步屏障造成等待 | 异步队列与共享进展 | 就绪任务无需等整批结束 | 并发领取、失联、迟到结果 |
| 多条开放探索互相无法复用进展 | 证据与测量支持的进展共享 | 减少重复试错，组合突破 | 验证、日志与多样性维护 |
| 用户需求藏在后续交互中 | 澄清策略与用户反馈 | 获取真正影响选择的信息 | 用户时间与打断 |
| 训练伙伴上很好、陌生用户上差 | 多样模拟器与留出伙伴评测 | 暴露模拟器捷径 | 模拟及训练成本 |
| 信息少的裁判难审查专家 | 对抗论证、可核验引用 | 把关键证据暴露给裁判 | 论证成本、裁判偏差 |

这张表是综合选型建议，不是原文共同证明的最优策略。先建立强单 Agent 基线，观察失败类别后再增加机制。

### 15.2 把症状追到可观察证据

| 症状 | 先检查什么 | 不能直接下的结论 |
|---|---|---|
| 大家很忙但没有新证据 | 搜索范围重叠、任务目标、已探索记录 | 再加 Agent 就能补齐 |
| 局部都正确，最后不能比较 | 实体、期间、单位、定义和输入版本 | 只改 JSON 格式就够了 |
| 一交流就形成错误共识 | 初答多样性、证据来源重叠、观点采纳依据 | 一致性越高越正确 |
| 新分支无法接上之前工作 | 环境观察、文件、状态和隐含决定是否丢失 | 发完整用户原题就能恢复 |
| 异步系统出现两个拥有者 | 领取原子性、租约、任务与尝试标识 | 模型“不守规矩”是唯一原因 |
| 训练奖励涨，外部表现掉 | 模拟器行为模式、奖励投机、留出切分 | 需要更多同类训练 |
| 审核总同意生成器 | 对错误候选的条件漏检率、可用证据 | 平均正确率高就足以审核 |
| 超时后出现重复外部资源 | 服务执行状态、逻辑操作幂等键 | 没拿到响应就是没执行 |

## 16. 怎样评价协调本身是否值得

以下是基于 R3 的独立采样对照、R4–R5 的训练/部署区分和模拟器泛化问题提出的工程实验设计，本地尚未执行这些模型实验。

### 16.1 需要区分的五种收益来源

一个复杂系统比简单基线更好，可能来自更多 token、更好的工具、更清楚的 SOP、更多独立尝试，或真正的交互收益。评价至少考虑：

1. 强单 Agent，拥有相同资料和合理上下文管理。
2. 单 Agent 加工具并行，隔离单纯的调用并发收益。
3. 单 Agent 执行相同 SOP，隔离交付规范和流程收益。
4. $k$ 次独立尝试，加相同验证与选优能力。
5. $k$ 个可通信执行者，明确计入主管、消息、验证与重试成本。

“同预算”需要说清楚匹配的是 token 上限、实际输出、模型费用、工具调用还是墙钟时间。不同模型的同 token 不等价于同费用。对于 pass@k 的 oracle 选优，还要说明部署时是否真的存在可用验证器。

上述五类系统首先用来比较完整方案，并非每一对都只差一个变量。要归因于通信，应固定模型、工具、初始任务、预算上限和最终选优权限，只切换通信机制；在同一任务集上配对评测并多次重复，同时报告实际消耗与不确定性。再按是否可分解、是否有中间验证信号分组，检查收益是否只集中于少数任务。

### 16.2 评结果，也评失败行为和用户代价

研究任务检查数字、引文支持、覆盖与不确定性；代码任务检查真实产物和环境状态；人机协作检查澄清是否有用、是否遵守偏好和权限。训练场景则加入留出伙伴、留出任务和实际用户反馈。

成本至少包括主管、worker、上下文复制、工具、验证、重试、总时延和人工返工。过程可以有多条有效路径，不应强制唯一检索顺序；但版本、权限和必要验收不能省略。

### 16.3 做机制消融，并保持留出验证

| 消融 | 主要观察 |
|---|---|
| 保留人数但关闭通信 | 有用信息是否来自交互 |
| 只传摘要、不保留原始产物 | 限制条件和证据是否丢失 |
| 去掉独立初答 | 是否更容易过早同质化 |
| 去掉可复现评分记录 | 方案采用是否变成凭语言说服 |
| 固定伙伴 vs 多样伙伴 | 泛化是否受模拟器分布限制 |
| 去掉版本拒收与重复处理 | 故障是否污染已验证结果 |

开发样例用于定位明显失败，留出样例用于判断改进能否迁移。同一批样例反复调优后取得高分，不能再把它当作独立验收。R1 与 R6 的静态阅读/答题证据、R2 的界面操作证据、R3 的开放探索证据和 R4–R5 的训练证据，各自覆盖不同问题，不应混成一个“多 Agent 平均收益”。

## 18. 自测与答案

先自行回答，再对照解析。回答时尽量说明需要检查的状态和证据。

**1. 三个使用同一模型的实例，是三个知识来源吗？** 不一定。实例可以有独立上下文和行动循环，但参数知识和训练盲点可能相同；来源互补要看不同资料、工具和反馈。

**2. 日历 Agent 被包装成工具后，是否由它承担整个用户请求？** 通常只承担委派部分。最终责任、控制权和外部写入权限要由具体协议说明，不能从包装形式推断。

**3. 所有执行者都拿到了原始需求，为什么仍会冲突？** 执行中会产生新的共同决定。初始背景一致，不代表运行中的口径、接口和环境观察持续一致。

**4. `asyncio.gather` 是否保证多 Agent 协作正确？** 它安排并发等待，不检查业务依赖、权限、结果是否可比或是否应该接受。

**5. 为什么 MACU 要传截图和文件差异？** 部分环境状态无法由后续 Agent 重新观察，文字摘要可能省掉影响后续操作的事实。传递哪些观察与文件本身也需要明确规则。

**6. 共享黑板是否意味着只有一个正确状态？** 没有更新和接受规则时不意味着。候选、权威任务状态和已接受产物应分开，并处理并发与版本。

**7. team@2 超过 pass@1，能证明通信有效吗？** 不能。还需与资源和选优能力可比的独立两次尝试对照，并检查共享状态干扰和采样差异。

**8. 为什么一个测量结果比三段赞同更有用？** 它可能提供可复现、可拒绝的采纳依据；但评分器本身仍需与任务目标一致，不能只验证方便的局部指标。

**9. SWEET-RL 中参考答案能否进入部署时 actor 的输入？** 训练期 critic 可使用额外信息帮助信用分配；部署 actor 不应依赖原本不可获得的参考，否则改变了问题并可能泄漏答案。

**10. 模拟器温度更高，是否解决了坍缩？** 不能直接断言。随机表达不等于行为和目标多样；需观察留出伙伴与实际用户上的迁移，而不是只看训练奖励。

**11. 为什么只奖励任务成功可能损害协作？** 它可能不惩罚过多打断、忽视偏好或不必要操作。奖励设计要让这些用户代价可见，同时警惕奖励之间的投机。

**12. R5 为什么先看动作模式的平均奖励，再选具体轨迹？** 降低把偶然猜中当作可靠行动策略的风险；仍不自动保证分布外校准。

**13. `HEDGE` 是否等于永远不要回答？** 它表达候选可靠性不足，可能让下游改用其他证据。该不该保留、检索或回答，取决于工具效果、知识和代价。

**14. R6 是否证明弱模型可以审核任意强模型？** 没有。其主要构造是长文本访问不对称，并配合引用核验、候选选项、协议和特定裁判。

**15. 新方案在同伴消息中声称得分更高，什么时候可以采用？** 至少检查任务和数据版本、测量记录、复现方法、评分器适用范围与副作用；不是看到高分字段就接受。

**16. 多 Agent 训练后能否只部署一个 Agent？** 可以，R5 就把多 Agent 社会互动作为训练环境。训练结构、部署结构和学到的行为需要分别说明。

**17. R5 两个 helper 都搜索时，为什么会出现 0.67 和 0.62 两种数值？** 0.67 是理论博弈中每人的正确率期望 0.72 减自己的搜索成本 0.05；0.62 是同样两次搜索按训练轨迹的共同奖励扣除总成本 0.10。二者回答不同问题，不能混用。

**18. GlossoGen 的困惑度升高，能直接证明通信效率变好吗？** 不能。它表明消息在指定英语模型下更不常见；还要固定预算和复盘条件，检查任务成功、消息成本及约定能否被正确使用。模拟字符预算也不等于真实运行时延。
