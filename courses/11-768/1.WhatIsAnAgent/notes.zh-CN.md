这一讲要建立的能力，是看见一个 Agent 时能够指出：谁做决策、决策依据是什么、动作在哪里实际执行、反馈如何进入下一轮、任务成功由谁判断。能够回答这些问题，才有基础继续学习工具、长上下文、记忆、规划、训练、安全与监控。

**学习起点**：本文面向已经做过 Java 等软件开发、接触过 LLM 应用的读者。可以沿用接口、函数调用、进程状态和测试的经验；概率模型、训练目标和 Agent 专有术语会在用到时解释，不要求预先学过强化学习。

先把 Agent 放回一个熟悉的程序结构里。普通服务常由代码决定下一步调用哪个函数；Agent 系统把其中一部分“下一步做什么”的选择交给模型。模型可能先请求读取文件，看到结果后再请求运行测试，也可能发现缺少信息而继续查询。真正读取文件、启动进程、保存状态的仍是外围程序。这层外围程序称为 **Harness（Agent 运行控制程序）**，作用类似协调模型、工具和任务状态的应用层。这个类比用于理解职责，不意味着任意服务框架天然具备 Agent 能力。

因此，接下来要依次弄清三件事：**模型依据什么选择动作（§2—4），程序怎样把动作变成可观察的执行（§5—6），模型怎样通过训练更善于选择动作（§7—9）**。§10—14 再把这些部件连成可评测、可排错的系统。第一次读到训练公式时，先理解它在比较什么，再看符号；不必为了读懂运行循环，先掌握整套训练算法。

**引用约定**：`[L1，p.14]` 是本地讲义的实际 PDF 页序，从 1 开始；`[T，§2]` 和 `[R，§3]` 分别指 Toolformer 和 ReAct；`[M]` 指本地 README 快照。讲义图页已结合渲染核对。原文机制与结果标明来源；额外公式、案例、设计和排错建议是教学推导。本文没有调用模型、训练模型或复现论文分数。

## 1. 先认识课程问题：高能力与可授权性为什么必须分别测量

讲义用两种材料开场。一种是团队 Agent 构建 C 编译器的案例，另一种是用户要求先审批、Agent 却继续清理邮件的对话截图。[L1，pp.2—3] 两者不是同一个实验的正负样本：编译器案例说明一个有验证环境的复杂工程任务可以取得进展；邮件截图说明系统即使能理解用户语言，也可能没有把授权约束落实到执行控制中。这里提供研究动机，不足以推算任意 Agent 的成功率、事故率或所需预算。

第 4 页把排查结账失败、群发邮件、报税、支付 API 迁移、买票、调整胰岛素剂量放在同一页，让学生讨论 Autonomous、Ask first、Never。图中项目标为 **UNCLASSIFIED**，讲义没有给出统一正确分类。它要训练的是判断维度：动作影响多大、能否撤销、用户授权是否具体、结果能否独立核验、失败会由谁承担。

作为工程练习，可以把“完成任务”分成证据收集、候选产物、外部提交三个阶段。对结账故障，读取日志、构造复现和提出修复通常比直接部署更容易控制；对批量邮件，写好草稿与发送是两类动作。这里不是提供医疗、税务或法律建议，而是分析软件系统怎样表示不同动作的权限与验证条件。

讲义 pp.5—6 的 GUI 与 OpenHands 视频封面说明动作不局限于结构化 API：网页元素、屏幕、终端、代码和浏览器反馈都可以成为交互界面。**视频封面不是完整实验记录**，本文不从静态截图推断视频内每一步是否成功。p.16 的 SWE-bench 轨迹浏览器进一步说明，应把系统当作可查看的动作序列，而不是只看最终回答。

### 1.1 贯穿案例：修复一个配置默认值错误

后文使用同一个小任务：

> 仓库里的 `retry_count` 在 `retries=0` 时错误返回 3。需求是键缺失或值为 `None` 时返回 3，显式 0 要保留。请修复并验证。

错误代码：

```python
def retry_count(config):
    return config.get("retries") or 3
```

这不是课程作业答案，而是教学构造。它足够小，可以区分多种失败：模型没读文件、读对了却误解需求、生成了正确改动但没有写入、测试没有启动、测试通过却声称部署完成。一个 Agent 的工程质量，正体现在能否把这些情况区分开。

## 2. Agent 的最小定义：观察、策略、动作和环境

讲义 p.9 引用 Russell 与 Norvig 的经典定义：Agent 通过传感器感知环境，通过执行器作用于环境。在软件里不必真的有摄像头或机械臂。仓库是环境，文件内容和测试日志是观察，读取文件、编辑文件和运行程序是动作。[L1，p.9]

先用开发中的调试过程理解下面的符号。磁盘上的全部文件、运行中的进程是系统的**真实状态**；某次 `read_file` 返回的几行代码只是一次**观察**；结合任务和已有日志决定“现在运行测试”，就是一次**动作选择**。机器学习里把这种选择规则叫作 **策略（policy）**。它可以是固定规则，也可以由模型实现，不是这里额外藏着一个必须训练的新组件。

把这个过程记成符号，方便后面讲训练和评测时复用：

- $s_t$：时刻 $t$ 的真实环境状态，包括磁盘、进程、远端服务等。
- $o_t$：系统向 Agent 暴露的观察，可能只是 $s_t$ 的一小部分。
- $h_t=(q,o_1,a_1,o_2,\dots,o_t)$：当前可用历史，$q$ 为任务。
- $a_t\sim\pi_\theta(\cdot\mid h_t)$：模型或决策系统选择的动作。
- $s_{t+1}\sim P(\cdot\mid s_t,a_t)$：环境执行后的变化。
- $r_t$ 或 $R(\tau)$：步骤或整条轨迹的评价反馈；$\tau$ 为交互轨迹。

读法是：下标 $t$ 表示第几步；$\theta$ 表示模型已经学到的参数；竖线 $\mid$ 表示“在已知……的条件下”；$a\sim\pi$ 表示按照策略给出的概率选择一个动作。$P$ 则描述环境执行动作后如何变化：同一个网络请求可能成功、超时或遇到已变化的数据，所以不能把环境总当作确定函数。$\tau$ 是从开始到结束的交互记录，而不是另一种模型。

这套符号是本讲的教学形式化，不要求实现一套专门的决策数学求解器。它解释了一个常见错误：`read_file` 返回某个时间点的内容，不证明文件之后没有被其他进程改变。观察不是状态本身；历史也未必包含全部相关事实。

### 2.1 动作可以是读操作，奖励也未必进入模型

搜索和读取文件没有修改业务数据，但它们会改变 Agent 能获得的信息；因此它们也是动作。相反，模型在回答里写“我执行了测试”，如果没有对应运行记录，只是生成文本。

讲义列举通过测试、LLM judge 评分和用户反馈作为 reward 的例子。运行时的一个 ReAct Agent 未必看到数值奖励；训练框架或评测器可以在任务结束后才计算它。必须区分：**环境观察供决策使用，评价反馈供判断或优化使用**。两者有时重合，例如失败测试日志，但不是天然相同。

### 2.2 自主性、复杂性、学习能力是不同轴

一个两步文件查询系统可以是 Agent，即使没有长计划；一个冻结模型加循环控制也可以是 Agent，即使运行后不更新权重。反过来，一个训练时不断学习的分类器不一定会在环境中采取多轮行动。不要把“有记忆”“有子 Agent”“会自我学习”当成所有 Agent 的必要条件。

还要区分目标与动作：用户给出的“修好重试”是目标；模型选择的“读取配置文件”是动作。高层目标不能直接当作可执行契约，Harness 需要把模型提议变成一个明确工具调用。

## 3. 语言模型怎样产生动作：token 层与执行层的连接

讲义 p.10 回顾自回归生成。**token** 是模型处理文本的小单位，可能是字、词的一部分或符号，并不固定等于一个汉字或单词。**自回归**指每生成下一个 token，都把已经生成的内容作为条件继续预测；就像逐步构造一个字符串，但每一步由模型给候选打概率，而不是由固定分支唯一决定。

给定上下文 $c$，模型生成序列的概率为：

$$
p_\theta(y\mid c)=\prod_{i=1}^{|y|}p_\theta(y_i\mid c,y_{<i}).
$$

$y_i$ 是第 $i$ 个输出 token，$y_{<i}$ 是它之前已经生成的 token，$|y|$ 是输出长度，$\prod$ 表示把各步的条件概率相乘。例如一个假设的两 token 输出，第一步选中目标 token 的概率是 0.6，在它之后第二步选中目标 token 的概率是 0.5，这条输出路径的概率就是 $0.6\times0.5=0.3$。这里没有假设两步相互独立：第二个概率已经以第一步输出为条件。理解这一点，就能理解为什么前面插入一条工具结果，会改变后面生成什么。

模型预测的既可以是答案词语，也可以是表示工具名、参数和控制标记的 token。Chain-of-Thought 把中间推理继续放入上下文，因此它会影响后续生成；它本身不会自动查询文件、改变数据库或保证事实正确。[L1，pp.10、13]

### 3.1 工具定义首先是一段有语义的接口说明

讲义 p.11 的 `read_file` 包含名称、描述与 JSON Schema；chat template 将这些内容转换成模型能读取的文本或特殊 token 序列。不同模型的模板、角色标记和调用表示可能不同，逻辑消息结构与最终 token 序列要分开记录。

一个更明确的教学接口如下：

```json
{
  "name": "read_file",
  "description": "Read one UTF-8 file in the task workspace.",
  "parameters": {
    "type": "object",
    "properties": {"path": {"type": "string"}},
    "required": ["path"],
    "additionalProperties": false
  }
}
```

Schema 能约束 `path` 是字符串，却不能单独保证路径存在、位于授权目录、不是指向目录外的符号链接，也不能说明读取结果是否包含敏感数据。接口的类型正确性、运行前条件和权限条件是三项检查。

对读取工具，应说明编码、相对路径基准、最大返回长度和截断方式；对编辑工具，应说明期望旧内容、原子性以及冲突时行为；对运行工具，应说明工作目录、超时、退出码与输出捕获。模型能否正确调用，很大程度上取决于这些契约有没有表达清楚。

### 3.2 工具调用与工具结果必须能对应

讲义 p.12 显示 `tool_calls`、调用 ID 和带 `tool_call_id` 的结果。调用 ID 的作用不是装饰，而是明确“这个结果属于哪一次请求”。例如两个并行 `read_file` 分别读取代码和测试，若结果只按完成顺序拼接，模型可能把测试内容当成代码。

建议每条记录保留：

| 字段 | 含义 | 本例 |
|---|---|---|
| `run_id`、`step_id` | 任务和步骤身份 | 同一修复任务第 2 步 |
| `call_id` | 调用与结果的连接 | `call_read_config_1` |
| `tool`、`arguments` | 请求实际执行什么 | 文件名、编码和范围 |
| `status` | 成功、失败、超时或取消 | `ok`、`timeout` |
| `content` / `artifact_ref` | 观察或大结果索引 | 文件片段、完整日志位置 |
| `started_at`、`duration` | 时序与成本 | 请求时间和执行耗时 |

这是工程建议，不是要求所有供应商 API 使用上述字段名。真正要求是语义可追踪。若调用成功但结果在传输时丢失，状态应为“结果未知”，不能随意归为“未执行”。这一点在有副作用的工具中特别重要。

### 3.3 动作序列经过 Harness 才成为现实

讲义 pp.13—14 的图有两条关键边：模型输出调用后，Harness 解析、校验并执行；工具返回被重新编码为观察 token，进入模型下一次输入。最后的 `send_message` 也是系统中可以表示的动作。

一个正确的事件链是：

```text
模型生成 read_file("config.py")
→ 解析参数并检查契约
→ 实际读取文件
→ 保存带 call_id 的观察
→ 将观察加入下一次模型上下文
→ 模型根据实际内容决定下一步
```

如果执行失败，应该把失败作为结构化观察返回。不要让 Harness 为了“帮助模型”把权限错误改写成一个看似正常的空文件；空文件与读取失败会引导完全不同的修复。

## 4. ReAct：让推理指导行动，让行动修正推理

ReAct 的核心不是必须输出 `Thought:` 这个字符串，而是把可更新的推理状态与环境交互放到同一序列。[R，§2，PDF pp.3—4；L1，p.14]

论文将动作空间从 $\mathcal A$ 扩展为 $\hat{\mathcal A}=\mathcal A\cup\mathcal L$，其中 $\mathcal L$ 是语言“思考”动作。一个语言动作改变后续上下文但不直接改变外部环境；工具动作可能带来新观察。后续决策同时依赖二者。

这里“动作空间”就是允许选择的动作集合，$\cup$ 表示把两类选择合到一起：既可以继续组织推理，也可以请求环境操作。它并不是说一段思考文本会被执行器当成工具调用。

### 4.1 用代码修复任务解释闭环

| 步骤 | 决策或观察 | 这一轮增加什么信息 |
|---|---|---|
| 1 | 先查看函数及现有测试 | 确认真实代码和当前行为 |
| 2 | 观察到 `or 3` 与合法 0 冲突 | 形成可检验的根因假设 |
| 3 | 改为仅在 `None` 时使用 3 | 构造候选修复 |
| 4 | 运行缺失、None、0、2 四类用例 | 检验候选覆盖的语义 |
| 5 | 读取退出码和断言结果 | 判断是否满足规格 |
| 6 | 汇报改动、验证范围和未覆盖项 | 交付证据支持的结果 |

如果第 4 步发现显式 `None` 仍失败，计划就应修订。若模型只重复“现在测试应当通过”，没有吸收观察，那只是文本循环。

### 4.2 论文图 1 真正展示的两种失败

ReAct 的 HotpotQA 示例里，模型需要从 Apple Remote 找到 Front Row，再确定另一种控制设备。无工具推理可能生成貌似连贯但不符合来源的答案；Act-only 可以找到网页却没有把已取到的信息正确整合。ReAct 在搜索 `Front Row` 失败后根据相似实体改搜 `Front Row (software)`，再完成回答。[R，图 1，PDF p.2]

ALFWorld 示例中，Act-only 反复从没有胡椒瓶的位置拿胡椒瓶；ReAct 先定位对象，再跟踪取物与放置子目标。这里图示的价值是**读取反馈并改变行为**，不是说明只要增加一段思考文本就一定成功。

### 4.3 思考频率是设计选择

知识推理实验使用较密集的 thought-action-observation 交替；长行动任务允许在关键节点稀疏地思考，例如目标分解、阶段切换或异常恢复。[R，§2、§4] 工程上可把这一点解释为计算分配问题：工具成功且状态明确时，不必每一步重新写长计划；观察与预期冲突时，值得重新分析。

不要要求产品一定暴露完整内部推理。对用户有用的通常是决策依据、采取的动作、关键证据和不确定性。日志中的简短计划、状态摘要与外部证据也能支持诊断；原论文使用显式 thoughts 的实验结论应保留其设置边界。

### 4.4 可解释轨迹不是正确性证明

一段自然语言理由可能事后合理化错误动作。真正有区分力的检查是：理由引用的观察是否存在、动作是否符合当时证据、反例出现后是否调整、最终结果能否被独立验证。

在本例里，理由“`dict.get` 已处理默认值”听起来合理，但 `config.get("retries",3)` 不会把显式 None 替换为 3。只有对应需求的测试才能发现这点。

## 5. 从最小循环走向可靠控制器

讲义 p.15 展示 Mini-SWE-Agent 的 `run → step → query → execute_actions`。这是一个有意简化的分解：模型调用负责提议，执行层负责动作和观察，消息历史连接各轮。[L1，p.15]

### 5.1 最小循环的隐藏前提

表面上只有 `while True: step()`，但一个完整系统仍需回答：

1. 如何区别最终答案与工具请求？
2. 一次模型响应能否包含多个动作，顺序如何确定？
3. 非法格式、运行错误、超时和预算耗尽是否进入同一种恢复逻辑？
4. 哪些错误可重试，哪些应立即终止？
5. 工具执行之后、消息保存之前进程崩溃，如何恢复？
6. 何时允许宣告任务完成？

这些问题不能全部交给提示“请不要犯错”。最小框架的优点是控制流易理解，并不表示工程责任消失。

### 5.2 一个教学控制器的状态机

```text
READY
→ QUERYING
→ VALIDATING
→ EXECUTING
→ RECORDING_OBSERVATION
→ READY

VALIDATING → FORMAT_ERROR → READY 或 FAILED
EXECUTING → TIMEOUT/TOOL_ERROR → READY 或 FAILED
QUERYING → FINAL_CANDIDATE → VERIFYING → DONE 或 READY
任意可中断阶段 → BUDGET_EXHAUSTED / CANCELLED
```

`FINAL_CANDIDATE` 与 `DONE` 的分离很有用：模型说“完成”是一个候选判断，系统还可以检查必要工件是否存在、测试结果是否来自本次代码、外部动作是否经过授权。验证器的范围必须有限而明确，不能神奇地判定任意开放任务。

预算也不应只限制轮数。一个步骤可以生成很长文本，或调用运行很久的工具。可同时设置最大模型调用数、总输入输出 token、工具时间和总墙钟时间，并在终止记录中指出触发的是哪个限制。

### 5.3 错误分类决定恢复方式

| 类别 | 本例 | 合理的恢复方向 |
|---|---|---|
| 格式错误 | 缺少路径字段 | 返回字段要求，允许有限次重生成 |
| 环境错误 | 测试解释器不存在 | 修复或报告环境，不归因为代码失败 |
| 工具错误 | 路径不存在 | 检查文件定位和工作目录 |
| 任务错误 | 0 仍返回 3 | 依据断言修正实现 |
| 评价错误 | 测试指向旧文件 | 修正验证入口并重新检查 |
| 控制错误 | 已成功仍反复测试 | 检查终止规则和状态同步 |

可重试不是无限重试。若同一个命令、相同输入、相同失败连续出现，没有新增信息，应改变诊断动作或结束并报告。模型可能自己意识到循环，也可能不会；Harness 可以保留重复动作计数，作为诊断或停止条件。

### 5.4 保留动作事实与模型表述的区别

日志中应同时能回答“模型请求了什么”“执行器实际做了什么”“返回了什么”“模型最后怎样描述”。例如模型请求运行 `pytest`，执行器因缺少依赖返回 127，而最终回答说全部测试通过，这是汇报错误；不能因为工具调用字段里有 `pytest` 就记作测试成功。

同理，工具超时不证明没有副作用。对于可能写入的动作，需要根据实际工具契约设计重试：使用幂等键、事务查询或先检查产物状态。这里只给出设计原则，不提供对所有 shell 命令都可靠的通用撤销器。

## 6. Mini-SWE-Agent：为什么简单结构是有价值的研究基线

本地归档 README 自称 v2，并将 v1 放在独立分支。讲义的代码片段用于解释循环，不应假定它逐行等于当前 v2 的实现。[M；L1，p.15] 本地快照没有记录精确 Git commit，因此本文不声称核对过对应版本的所有源码。

归档强调三个设计选择：只使用 bash；历史线性追加；每次动作用独立 `subprocess.run` 执行。它们各自解决不同问题。

### 6.1 Bash-only 的收益与代价

收益是动作空间统一，模型可以组合现成程序，框架无需为每个任务定义专用接口；模型比较时也更容易固定接口。代价是行为范围广、字符串解析脆弱、输出可能很大，而且模型需要理解命令语义。

专用 `read_file` 或 `apply_patch` 可以提供更清楚的参数和错误契约；bash 则更灵活。选型不是“工具越少越先进”，而是当前模型、任务、环境与验证条件的共同结果。归档中关于模型进步后复杂接口收益变小的陈述是作者的设计动机，不能推导为所有专用接口已没有价值。

### 6.2 独立 shell 的状态边界

若每次都启动新进程，前一轮的 `cd`、临时 shell 变量和未持久化进程状态，不会自动成为下一轮环境。磁盘写入可以保留，但 shell 会话状态通常不会。

例如：

```bash
cd /workspace/project
```

下一轮单独执行 `python check.py`，不保证仍在该目录。应在工具层显式传工作目录，或用单次动作里的完整路径。这个例子帮助理解 README 所说的“稳定性”：减少隐含会话状态，有利于重放；它没有消除文件系统、后台进程和外部服务的状态。

### 6.3 线性历史为什么有利于训练与诊断

每一步把模型输出、工具请求与结果追加到同一历史，便于核对模型下一步实际看到什么，也便于将轨迹转换为训练样本。若执行轨迹与输入上下文经过不同的过滤、摘要和裁剪，调试时必须额外记录映射。

线性历史的主要成本是增长。设每轮新生成和观察共 $d$ token，初始提示 $p$ token，若每轮完整重发且不考虑缓存，$T$ 轮累计输入约为：

$$
\sum_{t=1}^{T}[p+(t-1)d]=Tp+\frac{dT(T-1)}2.
$$

例如三轮的输入分别是 $p$、$p+d$、$p+2d$，总和是 $3p+3d$。一般情况下，初始提示出现 $T$ 次；新增历史出现的次数为 $0+1+\cdots+(T-1)$。把这串数正序、倒序相加，每对都是 $T-1$，共有 $T$ 对，再除以 2，就得到 $T(T-1)/2$。所以历史部分随轮数近似平方增长；这是累计重发量，不是最后一轮上下文长度。

这只是教学量级模型，真实系统可能用前缀缓存、不同长度消息或上下文窗口。它解释为什么“每步只多几百 token”仍可能带来明显累计处理负担。摘要能节省输入，也可能丢失边界条件；因此长上下文与记忆是后续独立课程。

### 6.4 README 分数应该怎样使用

归档提到 SWE-bench Verified 超过 74%、DeepSWE 比较和采用机构，但 README 片段没有同时给出完整模型、预算、样本、版本与对照协议。本文把这些内容当作项目自述，不把分数作为简单 Harness 一般优于复杂 Harness 的因果证据，也不把它写成本地复现结果。

可靠比较应固定模型、数据集版本、任务镜像、运行预算、重试和选择规则，再比较框架。若一个系统使用更强模型或更多采样，单看最终成功率无法识别框架贡献。

## 7. Toolformer：工具能力怎样通过训练进入模型

ReAct 主要回答怎样在推理时组织交互；Toolformer 回答怎样生成工具调用训练数据，使模型学会何时调用、调用什么、用什么参数、如何利用结果。[T，§2；L1，p.13] 二者处于不同层次，可以组合，不能简单当成同一个方法的两个名字。

Toolformer 本地 PDF 是 arXiv:2302.04761v1，首页日期 2023-02-09，共 17 页。其基于 GPT-J 的设置与今天任意指令模型或工具协议不同，下面按这个版本解释。

### 7.1 三步数据构建：采样、执行、过滤

给定普通文本 $x=(x_1,\dots,x_n)$，工具调用 $c=(a_c,i_c)$ 包含 API 名与输入，执行结果为 $r$。论文用 $e(c)$ 表示调用文本，$e(c,r)$ 表示带结果的调用文本。

1. **采样**：用少量人工示范构造提示，寻找适合插入 API 的位置，并生成多个候选调用。
2. **执行**：真的执行这些候选，获得结果；此处不是让模型自己编造工具输出。
3. **过滤**：比较提供结果后，原始后续文本是否更容易预测；只保留有足够收益的调用。

这是一种自监督数据选择过程，仍依赖人设计 API、少量示范、数据筛选规则和执行环境。“Teach themselves”不表示没有人类先验，也不表示模型在部署时无限自主学新工具。

### 7.2 损失差过滤到底在比较什么

先不看公式，想象训练文本接下来应出现一个正确答案。不给工具结果时，模型可能只给这个答案 0.1 的概率；给了有用结果后，概率升到 0.8。我们需要一个“预测得越准，数值越小”的分数，才能比较调用是否有帮助。这就是这里的 **损失（loss）**。

负对数把概率变成这种分数：$-\log(0.1)\approx2.303$，$-\log(0.8)\approx0.223$，此处用自然对数。正确后续文本得到更高概率，损失就更小。对多个 token，把各自的分数相加；再给距离调用位置近的 token 更大权重，就得到下式。它衡量的是已知训练文本有多容易预测，并不是工具执行耗时，也不是业务正确率。

论文定义后续 token 的加权负对数似然：

$$
L_i(z)=-\sum_{j=i}^{n}w_{j-i}\log p_M(x_j\mid z,x_{1:j-1}).
$$

其中 $i$ 是候选调用位置，$j$ 逐一遍历它后面的文本位置，$w_{j-i}$ 是该位置的权重，$z$ 是加在前面的辅助内容，$p_M$ 是当前模型给真实下一个 token 的条件概率。$\sum$ 表示逐项加起来。接下来比较三种输入：不给调用、只给调用文字、同时给调用和执行结果。用 $\epsilon$ 表示空内容，定义：

$$
L_i^+=L_i(e(c_i,r_i)),\qquad
L_i^-=\min\{L_i(\epsilon),L_i(e(c_i,\epsilon))\}.
$$

保留条件是 $L_i^- - L_i^+\ge\tau_f$。[T，§2，PDF p.3] 第二项“只有调用、没有结果”很关键：问题文本本身也可能暗示答案；只有结果进一步减少损失，才更接近工具信息有用。

**教学数值例子**：某候选无调用损失 2.4，仅调用文本损失 2.1，完整结果损失 1.2，则收益是 $\min(2.4,2.1)-1.2=0.9$。若阈值为 0.5，保留；另一个调用虽让损失从 2.4 降到 2.0，但仅调用就达到 1.8，实际收益为 -0.2，应丢弃。这个例子只演示筛选公式，没有运行 LM。

论文过滤时把工具内容作为前缀，以避免尚未适应 API 文本的模型被中途插入打断；构造最终微调文本时再将调用插到原位置。过滤过程与最终训练样本布局不可混写。[T，§2，脚注 3，PDF p.3]

### 7.3 为什么降低语言损失不等于真实任务成功

若结果包含与后文偶然相似的词，也可能降低局部损失；如果训练文本本身有错，帮助预测错误文本仍可能通过筛选。论文表 10 给出一个无关搜索结果却降低损失的例子，说明筛选并非无噪声。[T，PDF p.10]

工程上可把这类信号作为候选数据质量指标，再用执行成功、答案正确、时效性和工具成本补充验证。尤其对外部写操作，预测收益不能代替动作授权和业务验证。

### 7.4 五种工具对应五种能力缺口

| 工具 | 主要补什么 | 仍需模型或系统负责什么 |
|---|---|---|
| QA 系统 | 返回简短事实 | 提问是否正确、答案是否适用 |
| Wikipedia Search | 找到证据文本 | 查询改写、取相关信息、处理冲突 |
| Calculator | 精确执行四则运算 | 数学建模、单位、表达式和舍入 |
| Translation | 将其他语言转为英语 | 输入语言、翻译错误和上下文 |
| Calendar | 提供当前日期 | 日期推算、历史事实与时区语义 |

本版本计算器结果保留两位小数；Calendar 不接收参数；翻译器目标语言固定为英语。[T，§3] 这些都是原论文工具契约，不能误当通用工具定义。

### 7.5 训练与推理之间的接力

把几种常见训练方式放在一起，后面的术语就容易定位。**预训练**通常从大量数据学习预测后续 token；**监督微调（SFT）**在已有模型上继续学习精选的输入—输出示范，例如“看到这个任务后应输出这段调用”；**强化学习（RL）**则让策略产生行动或回答，再利用结果评价调整模型，使高回报行为更容易出现。三者都可能改变模型参数；在当前对话里读到错误日志并换一个命令，只改变本次行为，不自动等于训练。这里只建立分工，梯度和具体算法留到训练课程。

微调使用插入调用后的文本和标准语言建模目标。推理时生成到表示等待结果的箭头标记便暂停，执行器调用工具、插入结果，再恢复生成。[T，§2，PDF p.4] 这仍需要 Harness。训练让模型更可能提出有用调用，不能替代执行层。

论文实验还修改解码：当 API 起始 token 进入前 $k$ 个候选就允许开始调用，主要使用 $k=10$，并限制每输入至多一次调用以避免循环。[T，§4.2，PDF pp.5—6] 因此它的结果不是“未经任何控制的普通 greedy decoding”效果，也不证明训练出的策略会自然进行任意长工具链。

greedy decoding（贪心解码）指每一步只选概率最高的 token；这里的控制规则会查看 API 起始 token 是否进入概率排名前 $k$，并不要求它已经排第一。这个区别说明运行时的选择规则也参与塑造结果。

## 8. 两篇论文的证据：能够支持什么，不能支持什么

读表格时先看它在测什么。**accuracy（准确率）**通常是判对的样本比例；**exact match（完全匹配）**要求预测答案按指定规则与标准答案匹配；**success rate（任务成功率）**取决于环境定义的完成条件。**perplexity（困惑度）**则是预测真实文本的平均负对数损失取指数，越低表示这份文本在模型看来越容易预测，不等于任务成功率。相同的百分数形式可能对应不同问题，因此本节把数据集和指标一起读。

### 8.1 Toolformer 的对照如何定位训练和运行收益

论文比较原始 GPT-J、在普通 CCNet 文本上继续训练的 GPT-J+CC、Toolformer，以及关闭工具的 Toolformer。[T，§4.1] 这分别帮助分析继续训练、API 标注训练和实际工具执行的贡献。

以表 4 的 ASDiv 为例，GPT-J 为 7.5，GPT-J+CC 为 9.6，关闭工具的 Toolformer 为 14.8，启用工具为 40.4。这里至少有两种收益：训练数据本身改变了模型，以及推理时计算器提供了外部计算。它们不能全部算作“调用工具的提升”。评测是论文特定零样本提示与较宽松数字提取规则，也不是任意数学能力的通用百分比。[T，PDF p.6]

LAMA 上限制 Wikipedia Search 以避免不公平优势；QA 数据集上禁用 QA 工具，因为底层系统在 Natural Questions 上微调过。[T，§4.2.1、§4.2.3] 这是一个重要实验习惯：可用工具本身可能含有目标任务的答案或训练信息，比较时必须交代。

语言建模表 8 中，关闭工具的 Toolformer 与 GPT-J+CC 在 WikiText、CCNet 的 perplexity 相同到表中精度；不能由此宣称“对任何能力都零损失”。多语种表 6 反而显示部分语言继续训练后退步，Toolformer 并非始终优于原始 GPT-J。[T，PDF pp.7—8]

### 8.2 ReAct 并不是所有表格都获胜

PaLM-540B 的主表中，HotpotQA exact match：CoT 29.4、Act 25.7、ReAct 27.4；FEVER accuracy：CoT 56.3、Act 58.9、ReAct 60.9。[R，表 1，PDF p.5] 结论应写成：相对 Act，推理辅助行动在这些设置下有益；相对 CoT，ReAct 在不同任务呈现不同权衡。

结合 CoT self-consistency 的方法进一步提高结果。这里 self-consistency 指生成多条推理候选，再依据答案一致性等规则选择结果；组合方法还可以在两种求解方式间回退。它增加了采样与控制逻辑，不能把多样本组合分数当作单次 ReAct 的能力，也不能只按每次调用延迟比较。论文图 2 探讨不同采样数，为预算比较提供依据。

在 HotpotQA 的人工分析中，作者分别抽取成功和失败轨迹，每类每方法 50 条，共 200 条。ReAct 失败样本中 search result error 为 23%，reasoning error 为 47%；这些是特定抽样子集中的错误类别占比，不是全部任务的绝对失败率。[R，表 2，PDF p.6]

### 8.3 交互任务中的“best”需要说明选择层次

ALFWorld 表 3 报告 ReAct 平均 57、best of 6 为 71，Act best of 6 为 45，BUTLER best of 8 为 37。这些 best 指不同 prompt 组合或其原基线选择设置，不是“每道题运行六次挑中正确答案”。论文摘要的 34 个百分点来自 71−37，不能省略选择协议。[R，§4、表 3，PDF pp.7—8]

WebShop 表 4 中 ReAct success rate 为 40.0，Act 为 30.1，IL+RL 为 28.7；任务是基于归档商品的研究环境，`buy` 不是真实付款。论文伦理说明也明确其动作空间没有真实购买或编辑 Wikipedia 的危险动作。[R，PDF pp.8、10]

### 8.4 从历史结果迁移到新项目时要重新做什么

这些论文证明机制值得研究，不能直接预测今天某底座在某企业仓库上的效果。至少重新核对：模型与模板、工具契约、任务分布、预算、环境状态、判分器和数据隔离。真正需要复用的是实验逻辑与错误分析方式，而不是把旧分数贴到新系统上。

## 9. 六种 Agent 能力：逐项定位训练与 Harness 的贡献

讲义 pp.17—25 的主线是：同一种外在能力可以通过模型训练与系统工程共同实现。先识别失败位置，再选择改变对象。

### 9.1 准确工具调用

约束解码可以保证输出落在某种语法或 Schema 中，SFT 可以让模型更熟悉工具选择和参数模式。[L1，p.20] 二者都不能自动保证参数语义正确。`read_file(path="tests.py")` 可能格式完美，但用户要的是 `config.py`。

可分别度量：合法格式比例、工具选择正确率、参数正确率、工具执行成功率与最终任务成功率。把它们压成一个“tool accuracy”会隐藏究竟应修格式、描述、模型还是环境。

### 9.2 长上下文连贯性

讲义列出压缩、动态记忆查找、子 Agent 与长上下文训练。[L1，p.21] 在本例里，如果多轮后忘记“None 也要默认”，长窗口只是容纳了要求；不证明它仍被正确使用。

压缩应保留任务约束、已验证事实、未解决问题、关键路径和证据定位。把“曾考虑过方案 A”总结为“已采用方案 A”会改变状态；把失败日志删掉又会让模型重复试错。检验摘要质量，要用依赖早期约束的任务，而不是只检查摘要是否流畅。

### 9.3 可定制性

记忆、Skills 和自定义工具让稳定偏好或领域流程在运行时生效；基于反馈的 RL 可以把部分行为内化进权重。[L1，p.22] 用户说“我的项目要求保留 0”是当前约束；把它永久存成“所有项目都保留全部假值”则是错误泛化。

定制状态应带适用范围、来源和失效条件。只有状态真的在下次调用被加载，才构成实际定制。写入一个从不读取的文件不算获得能力。

### 9.4 复杂任务管理

规划和分解工具使状态显式化，子 Agent 允许并行处理可独立工作，RL 可以训练长时域策略。[L1，p.23] 但有依赖的步骤不能靠并行消除：修复前需确定需求，验收需针对最终代码。

如果多个 Agent 同时写同一函数，合并与冲突成本可能超过收益；若一个负责读现有测试、另一个独立设计边界用例，职责较容易分离。要测完成时间、总成本、冲突次数和最终质量，不能只数并行数量。

### 9.5 环境理解

观察形状与模型训练分布有关，Skills 可以提供领域知识，特定环境 RL 可以学习行动规律。[L1，p.24] CLI、DOM 与截图会暴露不同信息，工具的分页和截断也会改变可见状态。

本例中测试返回“收集到 0 个测试”，退出码与业务含义必须一起理解。若工具把它统一改写成“命令执行成功”，模型就可能误判验收完成。接口设计与环境理解不能完全分开。

### 9.6 安全与可靠性

沙箱、凭据限制、轨迹监控与安全训练共同构成边界。[L1，p.25] 沙箱隔离并不判断用户意图；模型承诺遵守权限也不等于执行器已阻止越权。应把动作分类、授权检查、环境限制和事后审计各自落实。

在本课的修复任务中，Agent 可以获得任务目录的读写与测试权限；部署、付款、邮件发送等不属于该任务动作集。权限按已授权目标配置即可，不必把每次可撤回读操作变成人工审批。

## 10. 系统的五个部分：接口比框架名称更重要

讲义 p.26 的结构图把 Harness、Sandbox、Inference、Training、Monitoring 放在一起，pp.27—31 逐项展开。图不是要求这些组件都运行在同一机器，也不是所有 Agent 都必须在线训练；它是一张责任地图。

| 部分 | 管什么 | 关键输入输出 | 典型故障 |
|---|---|---|---|
| Harness | 上下文、工具、状态、控制流 | 消息→调用→观察→终止 | 历史错配、循环、权限遗漏 |
| Sandbox | 运行环境与资源边界 | 命令、文件、网络→执行结果 | 镜像差异、资源耗尽、隔离失效 |
| Inference | 模型服务、批处理、KV 缓存 | token 请求→生成和计量 | 排队、显存不足、版本不一致 |
| Training | 数据、轨迹采样、参数更新与训练检查点 | 轨迹与奖励→新权重 | 数据错误、不可重放、目标偏移 |
| Monitoring | 轨迹、质量、成本与故障 | 事件→指标和证据查询 | 只有总数，无法定位失败步骤 |

表中的批处理是把多个请求合起来计算；**KV 缓存**保存注意力计算中已处理 token 的中间表示，供后续生成复用，不是外部知识库。训练里的 **rollout** 是让当前策略运行并收集轨迹；**checkpoint（训练检查点）**是保存的模型参数等训练状态，用于恢复或评测，不等于业务任务已经完成。这些术语先用于认清职责，内部机制在后续课程展开。

讲义列举的 OpenHands、Codex、LangChain、Docker、vLLM、SGLang、SkyRL、MLflow 等是实例，不是本课必须采用的依赖清单。软件能力会随版本改变，本文不根据导论截图提供当前产品配置建议。

### 10.1 为什么隔离环境也是实验工具

如果两个方案运行在不同依赖版本或预热状态下，成功率和延迟变化可能来自环境。保存模型标识、工具版本、镜像、任务基线、依赖与随机性配置，能减少混淆。

对代码任务，还要保存最终补丁和被测试的版本。测试执行后又修改了文件，先前的通过记录不能自动代表当前产物通过。环境重置规则也是协议：每题从相同基线开始，还是允许前题留下文件，回答不同问题。

### 10.2 观测应围绕可解释的任务成本

至少记录：任务成功、模型调用数、输入输出 token、工具时间、模型排队时间、总延迟、失败类型。若有多个子 Agent，既记录每分支时间，也记录总资源；最长分支影响墙钟延迟，各分支总和影响成本。

对同一问题，压缩上下文可能减少输入却增加错误重试；更快模型可能每轮便宜却用更多轮。最终要比较每次成功任务的资源与延迟，不能只比较 tokens/s。

## 11. 一套能真正回答问题的 Agent 评测

讲义 p.32 把实现、评测、训练、安全和研究并列为学习目标。建立 Agent 原型之后，应先让实验可以解释，再追求更高分。

### 11.1 明确任务成功契约

本例的成功条件是：函数符合四类规定语义、改动已保存、验证针对最终产物执行、没有在授权范围外操作。若规格还要求类型校验或负数行为，需要在实验开始前补充，不能看到结果后选择有利定义。

自动测试适合可执行性质，人工或模型 rubric 可补报告质量。模型 judge 的偏好并不等于程序正确性；对代码行为，优先用实际断言。若使用 judge，要保留版本、提示、输入和分数来源。

### 11.2 对照实验只改一个有意义的因素

想测试 ReAct 是否有用，可以固定同一模型、工具、任务、总预算，比较：直接回答、仅行动、推理加行动。对工具调用训练，可以按 Toolformer 的思路同时比较训练前、普通继续训练、带工具数据训练、关闭执行。

“同样最大轮数”不一定等预算：每轮输出长度、工具延迟和上下文长度不同。建议同时报告质量和实际资源；若要比较相同成本点，可以从质量—成本曲线选择，而不是只给一个最大预算分数。

### 11.3 多次尝试与单次能力要分开

设单次成功概率为 $p$，独立同分布采样且有完美选择器时，$k$ 次至少一次成功概率为 $1-(1-p)^k$。这是教学概率模型，真实重试相关，选择器也可能犯错。

推导只需要反过来数失败：一次失败概率是 $1-p$，独立尝试 $k$ 次都失败的概率是 $(1-p)^k$，从 1 中减掉它就得到至少成功一次。假设 $p=0.5$、$k=3$，结果是 $1-0.5^3=87.5\%$。如果每次都重复同一个错误，独立性不成立，就不能照这个公式预期收益。

如果能用隐藏答案挑中任意成功候选，测到的是覆盖能力；若系统只能用可见测试自行选择，测到的是可部署选择效果。报告 pass@k 时要说明选择机制、总预算和是否存在真实可用的验证器。

### 11.4 逐题差异比平均数更能定位贡献

基线与新方案逐题配对，分为共同成功、共同失败、新增成功、新增失败。新增失败若集中在长日志或特定文件类型，提示改动可能改变上下文使用或工具语义。

小任务集应报告任务数量、未完成项、重复设置和分组结果。不要把一次演示成功当作稳定能力，也不要把服务超时全部当成模型错误。环境失败可以另列，但必须仍计入用户面对的端到端可靠性。

## 12. 成本推导：为什么更聪明的下一步可能比更快的 token 更值钱

一个串行 Agent 的简化延迟：

$$
T_{\mathrm{task}}=\sum_{i=1}^{N}\left(T_{\mathrm{queue},i}+T_{\mathrm{prefill},i}+T_{\mathrm{decode},i}+T_{\mathrm{tool},i}\right)+T_{\mathrm{control}}.
$$

可以把它当作分段计时表：$N$ 是模型调用轮数；queue 是等待模型服务的时间；**prefill** 是处理本次输入、建立后续生成所需中间状态的阶段；**decode** 是逐步生成后续 token 的阶段；tool 是执行工具的时间；control 是外围程序组织这些步骤的时间。具体实现对首个 token 的计时归属可能不同，统计时只要保持一致。长输入主要增加输入处理负担，长输出会增加逐步生成负担；二者都表现为“慢”，优化位置却不同。

如果存在并行工具或子 Agent，总时间由依赖图关键路径决定，不能直接将所有耗时相加。费用则通常需要累加所有实际消耗，包括被丢弃分支。

**教学例子**：方案 A 每轮 2 个成本单位、需要 8 轮，成功率 0.8；方案 B 每轮 3 个单位、需要 4 轮，成功率 0.9。若每次尝试成本固定且失败不返还费用，每成功任务期望成本近似 $16/0.8=20$ 与 $12/0.9\approx13.33$。B 每轮更贵，但可能总体更优。此处数字是构造，真实任务中成本与成功相关，应直接用总成本除以成功数统计。

工具调用的价值来自新信息、精确计算或环境改变。若模型已经有足够证据，再搜索十次可能增加噪声；若缺少关键事实，减少调用可能只是更快地产生错误答案。选择动作时要问“这次调用能减少哪个不确定性”，而非一味减少步骤。

## 13. 失败诊断：沿信息链定位，不把一切归给模型

| 现象 | 先检查什么 | 有区分力的下一步 |
|---|---|---|
| 模型说读过文件，日志没有结果 | 调用解析与执行链 | 对照 call_id、执行状态、实际输入 |
| JSON 合法但读错目标 | 工具语义和路径基准 | 显示工作目录、文件定位证据 |
| 反复执行相同失败动作 | 是否真的加载新观察 | 比较每轮输入与输出，有限重试 |
| 长任务忘记最初需求 | 裁剪或摘要是否保留约束 | 用早期条件相关用例重放 |
| 测试全绿但用户说错 | 规格和测试覆盖 | 复核真实需求，加入反例 |
| 简单模型更慢 | 轮数、失败重试、队列 | 分解端到端时间与每轮输入 |
| 开发集变好、未见任务退步 | 过拟合或数据泄漏 | 按仓库/模板划分，检查记忆来源 |
| 轨迹看起来正确、分数为零 | 判分入口、标签或状态 | 独立重放产物，区分标签歧义 |

推荐先验证日志与产物一致，再检查工具与环境，然后检查上下文与决策，最后才决定训练。若根因是调用 ID 错配，继续 SFT 往往只会掩盖基础设施问题。

## 14. 可控离线练习：不调用模型也能验证哪些内容

以下练习只验证教学规格，不模拟或声称模型能力。错误版本在显式 0 上不满足要求；正确版本在四个约定输入上满足要求。

```python
cases = [({}, 3), ({"retries": None}, 3),
         ({"retries": 0}, 0), ({"retries": 2}, 2)]

def bad(config):
    return config.get("retries") or 3

def fixed(config):
    value = config.get("retries")
    return 3 if value is None else value

assert [bad(x) == y for x, y in cases] == [True, True, False, True]
assert all(fixed(x) == y for x, y in cases)
```

本地已执行上述断言。它支持“示例修复符合这四个用例”，不支持“Agent 能自动发现修复”或“任何输入都正确”。下一步可加入需求不同的任务：显式 None 应抛错、False 无效、字符串 `"0"` 需解析等，用于检验模型是否错误推广“保留假值”。

另一个离线练习是手工给每条轨迹标记：模型生成、工具执行、环境观察、验证结论、用户汇报。若一句话无法落入清楚类别，例如“运行测试并确认所有部署安全”，就把它拆开，找出每个判断所需的证据。

## 15. 课程组织如何转成自学路线

讲义 pp.7—8 是团队与算力支持，pp.32—38 是学习目标、作业、课表与规则。它们说明课程安排，不是 Agent 技术性能的证据。讲义标注三次作业与项目：A1 Harness，A2 Evaluation，A3 Training；项目整合任务、环境和评测。[L1，pp.33、36]

p.33 的日期是 tentative，p.36 明确以作业说明和 Canvas 为权威；本地笔记不是当前教务通知。p.37 鼓励在许可范围使用 Agent，但 lecture highlights 必须由学生自己写，提交者要对代码、引用和结果负责。本篇为资料库学习讲解，不能替代课程要求学生独立完成的 highlights。

对自学者，一个合理顺序是：先手写能记录和停止的最小循环；再用一组边界明确的任务做失败分析；然后选择一个瓶颈修改工具、上下文或模型；最后在未参与调优的任务上测变化。不要等到接入复杂编排框架之后才决定怎样判成功。
