# 第 19 课 · 人机协作：让 Agent 在合适的时候交出主动权

Valerie Chen 在 2026 年 11 月 10 日讲授这节课。官网名是 *Interaction 2: Human-Agent Interaction*，讲义封面是 *Rethinking Human-AI Collaboration in the Agentic Era*。下文用 PDF 从 1 开始的实际页码。[主讲义](2026-11-10-valerie-chen.pdf) · [指定阅读、参考资料与版本](SOURCES.md)

设想你把一个 Java CSV 导入模块交给 Agent，只说「修复导入崩溃，保持现有 API」。Agent 写完补丁，测试跑绿。它也把空字段悄悄判成坏行。调用方原本用空字段区分「未提供」和「提供了非法值」，所以下游开始丢数据。方法签名没变，你口中的 API 契约却变了。这个问题可以在查到第一条调用链时发现，也可以拖到接手补丁的人读完所有改动才发现。两种方案都能出补丁，交互过程带来的返工和维护成本却完全不同。

本课沿这个问题走三步。先设计主动权怎样交接，再理解怎样从稀疏的真实交互里估计设计效果和学习反馈，最后问代码短期完成后谁能理解、接手和扩展。每个问题有自己的观察量，也有各自的实验。

## 1 · 为什么过程也是交付物

**讲义 p.2–15。** 咖啡店案例中，数据分析 Agent 可以等到最后给用户一篇完整报告，也可以先展示初步统计，在还容易核对时询问样本怎样采集。后者能让用户判断初步结论是否符合业务现场，补充背景后一起决定下一步。对探索性工作而言，用户可能在看见初步结果后才知道真正该问什么。讲义 p.6–11 用两条行动时间线展示变化。传统 AI 可能在人的流程里只承担一次预测，Agent 可以连续执行多步，与人多次交接，所以「在哪一步交接」本身变成了设计选择。[讲义案例](2026-11-10-valerie-chen.pdf#page=2) · [交互时间线](2026-11-10-valerie-chen.pdf#page=6)

**指定阅读补证据。** *Completion ≠ Collaboration* 把交接之间的过程视为一轮。人投入的成本可以是读信息的时间、提供领域知识的次数、理解不透明结果所需的精力。效用可以是成果更接近目标，也可以是这轮让人能作出一个此前做不了的决定。如果人投入更多却一直在重复约束和纠错，合作效用的增量可能很低。论文把每轮效用画成曲线。总体效用按每个任务在观察期内达到的最高值取平均，迭代增益是最高值减首份可用结果的效用，可用性落差比较「连续若干轮未进展就离开」和持续到最终的结果。比如一条教学示意轨迹的首稿得 0.50，连续两轮仍为 0.50，最终才到 0.80。如果忍耐上限是两轮，迭代增益为 0.30，而早退出相比持续到最后低 0.30。即使两套系统最终可能达到相同效用，更早给出增量的系统也更容易让人看到继续投入的价值。它的定量结果来自模拟用户的旅行规划，数轮后出现的平台期受任务、模型和模拟协议限制，不能拿图上的轮数给真实用户规定上限。[阅读 §2–4，PDF 2–11 页](readings/Completion_Collaboration_Scaling_Collaborative_Effort_with_Agents.pdf#page=2)

**CSV 案例的教学展开。** 讲义 p.53 已用 CSV 修复示例说明轨迹，本篇沿用任务，补入假设的 Java 调用方和空字段约束。Agent 先展示最小复现和两条证据：「空字段沿这条调用链应保留 null，已有消费方靠它判断未填写，崩溃发生在格式校验之前」。开发者只需确认一项尚未明确的业务规则，再由 Agent 完成补丁。这次人工投入补上了能改变实现的信息。相比之下，Agent 把几百行 diff 都发来问「可以吗」，用户得先自己找出该审哪一处才有可能回答。判断交接是否有效，可以问：用户给出的那条信息是否改变了计划、测试或最终决策？

## 2 · 交互设计的时机、成本和可纠正性

**讲义 p.16–28。** Mixed initiative 是人和系统可以根据进展轮流发起行动。发起方发现机会或问题，提出一个有效的下一步，另一方可以接受、修改、否决或接管。早期 LookOut 从邮件估计用户是否在安排会议，再根据预期收益、误触发损失和打断成本在等待、提示、生成可修改的草案间选择。即使预测意图错了，用户也有直接控制的入口。若候选动作无法便宜地撤销，同样的模型信心不应获得同样的行动许可。[讲义 p.17–21](2026-11-10-valerie-chen.pdf#page=17) · [Mixed-Initiative Interaction，PDF 1–6 页](references/Mixed-Initiative_Interaction.pdf#page=1) · [Horvitz 的原则与 LookOut，PDF 1–6 页](references/Principles_of_Mixed-Initiative_User_Interfaces.pdf#page=1)

**教学推导。** 假定一个猜错会带来 30 分钟返工的契约决策，当前误判概率为 20%，直接猜的预期返工是 6 分钟。问一个具体问题成本约 2 分钟，且这里假定可以消除歧义，那就值得问。若只是可以马上撤回的一处日志文字，误判成本 1 分钟，乘上 20% 只有 0.2 分钟，Agent 可以先准备方案。这里的概率是教学数字。工程上应根据历史同类问题和权限来判断，也可以先完成复现和查调用方等不依赖该决策的工作。涉及外部副作用的操作仍由明确权限约束。

**讲义结合 CHI 2019 指南。** 原论文归纳了 18 条启发式，覆盖初始、交互中、出错时和长期四类条件，并用多种应用做专家评审与可用性检查。课上把适用的条目映射到多步 Agent 的前、中、后。[讲义 p.24–27](2026-11-10-valerie-chen.pdf#page=24) · [Guidelines for Human-AI Interaction，表 1 与讨论](readings/Guidelines_for_Human-AI_Interaction.pdf#page=3)

| 阶段 | 原则 | CSV 模块中的具体行为 |
|---|---|---|
| 开始前 | G1–G3，能力、能力质量和适时服务 | 说清能读什么、改什么、会跑哪些测试。把「保留已有签名和异常语义」落到可见的约束。约定遇到怎样的分岔会暂停。 |
| 执行中 | G4、G7、G8，展示当前相关状态，易于唤起和撤下建议 | 用简短事件显示已复现崩溃、正在核对调用方。可忽略提示，也可另行取消剩余任务。取消后给出工作区状态和已经结束的工具动作。 |
| 结果出来后 | G9、G11、G16，易于纠错、解释原因、揭示操作后果 | 显示变化、契约依据、测试结果和未验证边界。用户改成「保持整批原子性」时，指出哪些测试和候选实现需要重跑。 |
| 多次互动 | G12–G18，记忆、谨慎适配、收集颗粒化反馈和提供全局控制 | 已确认的仓库约束可以复用。让用户查看、修改或移除长期偏好，说明反馈会影响当前任务还是后续会话。 |

**工程展开。** 把 TaskGoal、ContractEvidence、UserDecision 与 ExecutionState 分开，就像区分请求、配置和工作流实例。用户选择「保留旧异常类型」进入当前任务约束，不能只埋在对话摘要。Agent 进入 WAITING_FOR_DECISION 时保存可恢复检查点，后续恢复前检查任务版本和工作区基线，避免用旧候选覆盖用户的新改动。若已完成的动作需要逆转，应记录补偿能力或给出手动恢复路径。界面上的停止只说明停止信号已发出，工作流要用实际动作状态告诉人什么停下来了。

## 3 · 让 Agent 主动，也让人复核它对意图的判断

**讲义 p.28–35。** 被动系统只回答用户已经提出的问题。主动 Agent 要同时解决「什么时候打断」和「打断时说什么」。上下文包含当前提示、代码和可授权使用的历史。目标是用户要实现的结果，约束是必须遵守的边界，偏好是在多个可行方案中倾向某个选择。对 CSV 任务，「修好崩溃」是目标，「不改变对外契约」是约束，「偏好用 JUnit 参数化测试」是偏好。当前明确要求优先于从历史推断的偏好。[讲义 p.28–35](2026-11-10-valerie-chen.pdf#page=28)

**参考资料 ToM-SWE。** 论文让一个轻量的用户建模伙伴根据历史交流提取并持续修订用户偏好，编码 Agent 可在不确定时检索或征求澄清。实验有两条证据线：带用户模拟器和单测的基准检验完成情况，现场部署观察开发者是否接受建议。现场研究由 17 名开发者使用三周，记录 209 个会话、174 条主动建议。86.2% 是接受或部分接受的合计比例，分母是被建议的交互。它度量的是建议接受情况。有可用的历史时，不够明确的需求可能得到帮助。只有「做个网站」这种极模糊请求时，历史也不一定能补全目标。将偏好按仓库、任务和时间保存，再附来源和确认状态，是对该机制的工程推导。[ToM-SWE §3–6，PDF 3–8 页](references/ToM-SWE_User_Mental_Modeling_for_Software_Engineering_Agents.pdf#page=3)

**讲义 p.36–40 与现场研究。** ProAIDE 在 IDE 中监测工作流时点。模糊 prompt、拒绝编辑和完成提交触发的建议分别对应需求形成、执行和自然收尾。五日研究在 5,732 个交互点记录 229 次主动干预。已展示建议中，提交边界的参与率为 52%，模糊提示为 46%，拒绝编辑为 31%。这里的参与指主动打开建议等行为。调查与日志记录的分母也不同，15 份终期调查与记录到的活跃机器是不同统计口径。三种触发同时有时机和内容差异，结果给了产品设计线索，无法定量分离时机的影响。[开发者现场研究 §3–5、图 4，PDF 4–8 页](references/Developer_Interaction_Patterns_with_Proactive_AI_A_Five-Day_Field_Study.pdf#page=4) · [讲义现场图](2026-11-10-valerie-chen.pdf#page=36)

**工程展开。** 可以优先做三种事件。高代价契约冲突就请求决定，共享工作区变更就暂停重新读取，提交前给总结型评审提示。低代价建议先攒在非打断入口。同一冲突用幂等键合并通知，把 shown、opened、acted、dismissed 分开记录。发布前先让通知策略只记录「原本会出现在哪些位置」，人工看一批样本再启用。做统计时，把各阶段的曝光量和参与率并列，点击总量需要结合触发频率解释。

## 4 · 从一对回答变成一整条交互轨迹

**讲义 p.41–48。** InstructGPT 先用人工示范做监督微调。接着让标注员针对同一个 prompt 比较几个回答，训练一个给候选回答打分的奖励模型。最后用 PPO（通过裁剪等目标设计来抑制策略变化过大的强化学习方法）使模型倾向产生高分输出。本节只需要抓住监督来自一次回答的偏好，更新对象是生成策略。到了多步 Agent，一次修复穿过查文件、执行测试、改代码和等待新约束，同一个最终补丁前可能有很不同的过程。只看最后一条自然语言，无法知道它是否测试、是否扩了修改范围、用户是否被迫反复补充信息。交互轨迹 $X$ 可以包括用户消息、动作、工具观察、状态转移和结果证据，某个工作段可能有评分 $Y$。[讲义 p.44–48](2026-11-10-valerie-chen.pdf#page=44) · [InstructGPT §3.1、3.4，PDF 5–7 页](references/Training_language_models_to_follow_instructions_with_human_feedback.pdf#page=5)

**参考框架 CoALA。** LLM 发起的一次推理，经由决策循环影响系统的工作记忆、长期记忆或外部动作。对一个 Agent 系统，可测试的设计变量可以是基础模型、记忆保留方式、计划策略、工具权限或中途提示。更改 CSV Agent 的计划展示，可以固定其余部分做 A/B。如果实验同时改模型与权限，即使随机对照能识别组合的效果，也无法从这一个比较判断两项各自的影响。[CoALA §4，PDF 8–14 页](references/Cognitive_Architectures_for_Language_Agents.pdf#page=8)

**指定阅读 PULSE §3。** 用户发出一条任务指令并收回一段工作成果，可作为收集评分的工作段。一个会话含多个工作段，论文对有评分的段取平均作为该会话的标签。一段轨迹的用户情绪、用户消息数、漏测、是否跟进提交等线索可转成可比较特征，再用有标签样本拟合预测器 $f(X)$。长轨迹包含大量日志，直接交给一个通用 LLM 打分可能遗漏关键行动。论文以包含 15 项特征的传统预测器和全文 LLM 评审作比较。表 2 所列相关系数，随机森林约 0.29，最强的全文评审约 0.23，对应讲义概括的约 26% 相对增幅。绝对相关性仍不高，而且这是预测评分的指标。特征来自用户反馈、Agent 行为和任务进展，部分由 LLM 提取，须核查定义与抽取误差。例如 git push 可能提示某些任务推进了，也可能只是用户备份。[讲义 p.53–54](2026-11-10-valerie-chen.pdf#page=53) · [PULSE §3.1–3.2、表 2](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=4)

## 5 · 手算 PPI，让预测扩充样本，让真人评分纠偏

**讲义 p.49–52，PULSE §3.3 与 Prediction-Powered Inference §1.1–1.3。** 要比较两个版本，先确定量纲。这里的效应量是平均评分差，单位为「星」。令 $c$ 为版本，$n_c$ 条有真人标签的轨迹是 $(X_i,Y_i)$，$N_c$ 条无标签的轨迹记作 $\widetilde X_j$。预测器可为两类轨迹给分 $f$。PULSE 对每个条件用下面的估计量：

$$
\widehat\mu_c(\lambda_c)=
\frac{1}{n_c}\sum_i Y_i+
\lambda_c\left(
  \frac{1}{N_c}\sum_j f(\widetilde X_j)-
  \frac{1}{n_c}\sum_i f(X_i)\right).
$$

$\lambda_c$ 是预测信息的权重。取 $0$ 只用人工评分，取 $1$ 时可换个顺序看：先用未打分组的预测均值覆盖人群，再加上在有打分组测到的平均残差 $Y-f(X)$。当模型评分普遍偏高，真人评分测出的残差为负，补回去就是下调。版本差是 $\widehat\Delta=\widehat\mu_A-\widehat\mu_B$。[讲义 p.51](2026-11-10-valerie-chen.pdf#page=51) · [PULSE PDF p.5](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=5) · [PPI 原论文，PDF 1–3 页](references/Prediction-Powered_Inference.pdf#page=1)

**教学数据。** A 是展示计划并允许阶段纠正的 CSV Agent，B 是结尾集中汇报的版本。分别用固定的两条人工评分、四条未评分会话演算。所有均值都用样本自己的分母。

| 版本 | 有标签 $Y$ | 同批 $f(X)$ | 无标签 $f(\widetilde X)$ | 真人均值 | 真人校正项 | $\lambda=1$ 估计 |
|---|---|---|---|---:|---:|---:|
| A | 4，5 | 4.4，4.8 | 3.8，4.0，4.2，4.4 | 4.50 | −0.10 | 4.00 |
| B | 3，4 | 3.2，3.8 | 3.1，3.3，3.5，3.7 | 3.50 | 0.00 | 3.40 |

A 的无标签预测均值是 $(3.8+4.0+4.2+4.4)/4=4.10$。有标签的预测均值是 $(4.4+4.8)/2=4.60$，比同一批真人均值 4.50 高 $0.10$，所以从 4.10 减 0.10 得 4.00。B 同批预测和人工均值相同，直接保留无标签预测均值 3.40。只用评分差是 $+1.00$ 星，只用未评分预测差是 $+0.70$ 星，做校正后是 $+0.60$ 星。这里的两条评分足以走完算术，无法拿来下显著性结论。在本课目录执行 `java examples/PpiRatings.java` 可以复核计算。这个固定样本已经用 JDK 21 执行。[CPU 算例记录](examples/ppi-output.txt) · [Java 源码](examples/PpiRatings.java)

**为什么可能更稳？** 先把 $f$ 和 $\lambda$ 视作固定，假设两套样本独立、同版本内来自同一目标总体，则两个预测均值在期望上相同，差的期望为零。用残差形式重写估计量，其方差在这些简化条件下是 $\operatorname{Var}(Y-\lambda f(X))/n+\lambda^2\operatorname{Var}(f(X))/N$。相关性较强时，第一项可能比原 $Y$ 均值的噪声小，大量无标签轨迹可压低第二项。预测器弱或目标变了时，增加预测权重可能拖累效率，应重新估计，必要时回到 $\lambda=0$。将方差对 $\lambda$ 求导并令其为零，可得这个简化模型里的最优权重 $\lambda^*=\operatorname{Cov}(Y,f)/[(1+n/N)\operatorname{Var}(f)]$。直觉是有用的相关信号越强，预测承担的份额可以越大。PULSE 用样本估计协方差和方差，再按成立的抽样和正则条件报告区间。95% 置信区间的频率解释是，若按同样的抽样和计算程序重复很多次，约 95% 的区间会包含真值。[PULSE §3.3](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=5)

**关键假设和调试。** A/B 分配可以随机，但是否主动打分可能依赖任务长度、情绪、用户熟练度和版本。如果缺失恰好集中在 A 的失败短会话，有评分数据估出的纠偏量无法代表短会话。PULSE 原文比较了 15 个观测特征，消息数差异较明显，其余变量的接近也不能证明未观测变量一致。实作先看各臂评分覆盖与任务结构，可随机邀请一小批会话反馈，再验证倾向分层后的代表性。训练预测器与估计残差时使用分离的数据或合适交叉拟合，避免同一条记录既训练又充当独立校准。若同一用户贡献多个会话，在报告区间时考虑按用户分组的相关性。更大的样本与更窄的区间可能同时保留系统性偏差。[PULSE §4、§8、附录 A](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=5)

## 6 · 怎么读 OpenHands 的版本对照

**讲义 p.55–58 与指定阅读。** PULSE 的观察环境是 OpenHands 平台，超过 15,000 用户和 36,000 会话，约 5% 的交互收到评分。论文做了不同模型、计划策略及上下文保留策略的案例。按论文正文的百分数表达，换基础模型的评分差异约为 6–8%，计划策略约为 3%，减少历史上下文的比较未检出显著评分差异。这里保留报告口径，表 5 的小数估计量与区间另读。原文图 4 固定比较用的标签量（每条件 150 个有评分会话），四次实验的区间宽度平均收窄约 39.5%（课件概括为可减少约 40%）。正文百分数与附录表 5 所列估计量呈现方式不同，引用具体区间时按表 5 所列小数和方向复述。例如从不显示计划到显示计划，辅助估计为 $0.031$，95% 区间为 $[0.014,0.049]$，对应仅标签估计的区间 $[-0.003,0.109]$。这来自该组试验里预测辅助的估计精度，不能当作单次任务成功率提高 40%。[讲义 p.55–58](2026-11-10-valerie-chen.pdf#page=55) · [PULSE §5–6、图 4，PDF 6–9 页](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=6) · [附录表 5](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=18)

自动基准的排序也可能与真实用户任务的排序不同。论文在所用模型和七类任务子集比较中看到这种错位。基准仍能验证它覆盖到的行为，线上用户的语言、任务难度和需要接手的时机都可能改变比较结果。对 CSV Agent，先在固定样例上检验异常语义，再看真实等价任务中用户需要补几次语境、每次停顿持续多久、结束后是否复开。若减少历史上下文后的评分差置信区间跨零，只能说当前实验没有排除零差异。要支持节省成本且质量下降可接受，应预先给出可接受降幅，与区间对照。[PULSE §7](readings/How_can_we_assess_human-agent_interactions_Case_studies_in_software_agent_design.pdf#page=8)

## 7 · 从真实轨迹练出 critic，给候选选择更细的监督

**讲义 p.59–63 与依据论文。** PULSE 估计两个版本的人群评分差。Rubric critic 学习一段工作留下了什么结果、过程中有哪些行为。其原始问题是信用分配：最终 PR 合并了，哪一段 Agent 的工作真正保留在最终成果里？论文把 PR、commit、工作片段关联在一起。合并是粗粒度标签，code survival 是某片段新增或修改的行在最终 diff 里保留的比例。比如片段改的 20 行中，最终保留了 15 行，代理标签就是 $15/20=0.75$。合进去不保证正确，重写后的正确思想可能贡献很大却不计为保留行。作者还用 24 项 rubric 标注诸如漏测、误解需求、反复失败和范围蔓延等行为。标注器看轨迹，部分标注可看结束后的用户消息，同时与最终结果标签隔离。若 critic 要在新版本接到用户回复前使用，就要按该时点可取得的输入做训练和评估。[讲义 p.59–63](2026-11-10-valerie-chen.pdf#page=59) · [Rubric critic §2–3，PDF 3–7 页](references/A_Rubric-Supervised_Critic_from_Sparse_Real-World_Outcomes.pdf#page=3)

**两种指标的读法。** p.60 展示的 code-survival AUC 从 0.45 到 0.69，对照的是无真实世界训练数据和加真实数据且做 rubric 监督的 BCE-floor 设置。这里的 BCE-floor 把完全保留标为正例，用二元交叉熵学习结果标签，同时预测 rubric 标签。这个对照同时引入真实数据和 rubric。要拆开两者的贡献，应对照同样用真实数据、仅监督结果的那一行。AUC 衡量在相应二值标签协议下模型把正样本排在负样本前面的能力，量纲和 PR 合并率不同。论文 §5.1 在保留同时存在成功和失败尝试的 SWE-bench Verified 子集上，固定 8 个候选，报告特定 rubric critic 的 Best@8 为 73.8%，只监督结果的对照为 63.6%，随机挑选为 57.9%。该子集专门保留有选择空间的题，报告应始终带上子集边界。论文还用评分筛选真实轨迹供 SFT，和把评分做成 PPO 奖励的流程不同。讲义 p.61 将从交互提取奖励、更新权重作为另一条可能的用途，该页属于课堂举例。[Rubric critic 表 2、§5，PDF 8–12 页](references/A_Rubric-Supervised_Critic_from_Sparse_Real-World_Outcomes.pdf#page=8) · [讲义 p.61](2026-11-10-valerie-chen.pdf#page=61)

**工程展开。** 假设你有三份 CSV 修复候选。先用可执行测试筛掉确定违约的候选，再用 critic 区分是否补了边界测试、是否悄悄改了调用方、是否给出了足够证据。看 top 1 成功率和平均候选数时，固定上游模型和候选池。若早停把置信过高的劣质候选提前接纳，分数更高还是会损害结果。真正接入训练前，应让标签能回溯到准确片段、版本和证据，并保留独立契约评测集以免模型学成「会猜 rubric」。

## 8 · 写出来、看懂、继续改是三种不同任务

**讲义 p.64–68。** *Code with Me or for Me* 比较 20 名平时使用代码助手、熟悉 Python 的学生用 GitHub Copilot 和 OpenHands 做不同开发任务的表现。研究用任务是否正确和人的主动投入时间两个轴描述生产力。讲义图约为 25%（Copilot）与 60%（OpenHands）的任务正确率。论文另报告，仅看成功任务，Copilot 平均用掉人 25.1 分钟，Agent 条件下人主动投入 12.5 分钟，但人机组合的平均完成时间为 27.9 分钟。对需要释放人的时间去做另一件事的团队，这两组时间都值得看。若用户必须一直等结果，体感不一定同步改善。主观体验六个比较项只有两个显著更偏向 Agent。对照改变了整套工具，任务和受试者的使用经验也有边界，研究无法单独识别模型、工具权限或界面的贡献。[讲义 p.66–68](2026-11-10-valerie-chen.pdf#page=66) · [Code with Me or for Me §3–4，PDF 4–11 页](readings/Code_with_Me_or_for_Me_How_Increasing_AI_Automation_Transforms_Developer_Workflows.pdf#page=4)

**讲义 p.69–79。** *(Im)Paired Programming* 纳入分析的 54 位学生分两组，每组 27 人。一组可让 Agent 直接改网页代码，另一组用 chatbot 协助、自己动手。两组先做背景测验，再做初始任务、针对自己代码的理解题，最后都只用 chatbot 完成新增需求。理解题按实际提交内容生成，可询问哪些标识符出现过、哪段是自己写的、改变一段代码会影响什么。AST（抽象语法树）把代码结构变成可查询的节点，辅助生成与当前代码相符的题。难点是两个作品不同，题难度可能跟着变，研究以统一模板、人工审核和题型拆分减少不可比之处。[讲义 p.69–74](2026-11-10-valerie-chen.pdf#page=69) · [(Im)Paired §3、附录 A.9](readings/Im_Paired_Programming_Coding_Agents_Improve_Productivity_but_Harm_Understanding.pdf#page=3)

Agent 组初始任务分数更高，理解测验分数更低。扩展任务在全体样本里的差异不显著，图中 $p=0.45$。筛选初始分大于 0.50 的子组，方向改变但也不显著，$p=0.18$。这种子组还可能受初始表现筛选偏差影响。作者的回归分析提示初始成果质量和理解都与扩展得分正相关。样本和任务限制了结论对专业 Java 团队的外推。讲义柱图的 $p=0.00$ 来自显示精度。讲义建议用更具体的技术描述、主动读代码、保持简洁，这是作者从探索性行为分析得到的线索，代码行数和注释多少需要回到各自的用途判断。[讲义 p.75–79](2026-11-10-valerie-chen.pdf#page=75) · [(Im)Paired §4–5、图 4–7](readings/Im_Paired_Programming_Coding_Agents_Improve_Productivity_but_Harm_Understanding.pdf#page=5)

**参考资料与练习。** 代码理解综述把理解本身和通过任务、得分、时间等得到的测量区分开，且「理解」随任务变化。比如记住 Java 方法叫 parseRow 不足以证明能解释遇到空字段时哪个错误分支会触发。给同一个 CSV 补丁做三类题：找入口，预测输入输出，自己加一类坏行而不破坏旧调用。用统一的测试与等价任务比较完成时间和结果，再单独记录自信或满意度。[代码理解实验综述 §2、§4.7](references/40_Years_of_Designing_Code_Comprehension_Experiments_A_Systematic_Mapping_Study.pdf#page=22)

## 9 · 维护性为何需要后续任务来测

**讲义 p.80 与 CodeThread。** CodeThread 要求第一步（PR1）先解决指定功能问题，比较在人写的 PR1 和 Agent 写的 PR1 上由 Agent 接着完成第二步（PR2）。论文用通过执行测试的前置版本来控制初始功能，再看后续任务解决率。在大多数模型与基准组合上，Agent 在 Agent 补丁上继续工作的解决率更低。表 2 中 GLM 4.7 在 SWE-bench Pro 的差距为 13.1 个百分点。直接数行、判复杂度的解释力有限。输入和错误契约发生漂移，是对部分失败更可追踪的机制，但很多失败没有被归因为这一点。该实验的接手者是 Agent，对人类维护性的判断还要另测。[讲义 p.80](2026-11-10-valerie-chen.pdf#page=80) · [CodeThread §3–5、表 2 与 4，PDF 3–9 页](references/Is_Agent_Code_Less_Maintainable_Than_Human_Code.pdf#page=3)

**教学展开。** 把 CSV 补丁交给下一位工程师或新会话，让他增加可选列校验，同时保持空值和错误行为。运行上一步的兼容测试以及新要求的验收测试，记录重新打开多少文件、误判哪个契约、是否重复修旧问题。比较补丁时先让它们都通过第一步，再观察第二步是否在相同测试下引入冲突。输入约束、错误类型、事务或部分成功行为最好有彼此独立的回归测试和简短说明，避免接手方反复推测当初的隐含决定。

## 10 · 人怎样学会与 Agent 工作

**讲义 p.81–89。** 最后一段把问题从产品使用延伸到培训。Forward-deployed engineer（深入使用者工作现场，帮助明确需求并交付原型的工程角色）的课堂例子从澄清需求、搭原型到解释交付决策，任务完成只是其中一部分。p.84 用需求访谈、原型和展示三个评分维度观察进步，p.85 用个人连线展示不同起点的变化，p.86 把分工变化与审阅、编辑习惯一起看。工作中让 Agent 先产出更多，并不妨碍人增加审阅投入，这两个维度需要分别记录。页上标为拟发布研究，课程索引没有独立正文，因此这里只记录课堂展示提出的研究问题和观察，分组、随机化、统计程序或外部有效性仍需正文支持。班内测到的成果进步，也不能替代迁移到新任务时的测试。[讲义 p.81–89](2026-11-10-valerie-chen.pdf#page=81)

**教学练习。** 让学员先自己写 CSV 模块的公开行为说明，再与 Agent 协作完成补丁，并解释 diff 和测试。隔几天发一个未知变体，只允许聊天提示，不允许直接代改。学员应能描述在哪个阶段交出了主动权、有哪些阶段仍需自己判断，以及如何从测试失败定位到旧契约。若第一阶段更快，第二阶段却需要从头学代码，把这一差异记为学习与交付目标需要不同配置。

## 11 · 把设计变动做成一个能定位问题的实验

**工程建议，实验尚未执行。** 先从一个契约不变的任务族开始。固定 Java 依赖版本、仓库起点、基础模型、token 预算和工具权限，将「关键阶段展示检查点并允许打断」做成一个处理组合。想知道主要收益来自哪个组件，再进一步拆开两个开关。候选用户应覆盖不熟模块和熟悉模块的两类，随机分配或用对等任务交叉试验，避免第二次做同题带来的练习效应。处理组和对照组使用同一验收测试，另用新变体测理解及后续修改。先决定什么效应值得上线，例如每个成功任务的人工处理时间、契约回归数和延迟的容忍范围，再收集数据。触发器每多一次模型判断都要计 token、延迟与监控成本，节省的主动处理时间要与等待和返工分开报。不同用户和任务阶段的平均值可分层汇报，避免高频会话盖住小群体的失败。

| 观测 | 可能原因 | 先回查什么 |
|---|---|---|
| 提示打开率高，但修复后常被重开 | 提示出现在自然边界，内容没有指出真正的行为冲突 | 按 trace 回查哪个问题被提问、用户是否补过正确约束、是否写入任务状态 |
| 测试通过，正常 CSV 的空字段被丢弃 | 测试只覆盖崩溃复现，缺少调用方的兼容行为 | 拿旧版本和补丁跑同一组正常／异常输入，逐项比对返回与报错 |
| 换模型后平均评分升高，单测通过率未变 | 交互体验变化，也可能是评分样本组成变化 | 汇报留评分布和任务难度，核对是否固定实验单位与模型之外的变量 |
| Critic 排序更高，早停实际更差 | 评分校准、候选池或停止阈值不适配 | 固定候选池对比随机、穷举重排和早停，记录通过率、候选数及等待时间 |
| 发版前工作很顺，下一次变更缓慢 | 补丁能过当前测试，契约与维护知识没有留下 | 测独立扩展的通过结果、耗时和行为解释，对同类失败回查 PR1 的协议漂移 |

在 trace 里保留任务和用户的分组 ID、版本、触发点、决定、工具状态和验证摘要。需要留存的原文根据授权加访问控制，敏感代码与自由文本反馈不必进全量分析。把收集用户反馈与可选择退出做成产品行为，再按业务约束决定保留时间。教学验证范围是 §5 的固定样本算术。
