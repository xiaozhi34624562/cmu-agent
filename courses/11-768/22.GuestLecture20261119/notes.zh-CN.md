## 1. 为什么 Agent 跑起来了，我们还不敢交给它？｜[讲义第 1–3 页](2026-11-19-karthik-narasimhan.pdf#page=1)

假设你维护一个 Java 订单服务，给它接上会查单、解释规则和发起取消请求的 LLM Agent。用户问「帮我取消没发货的订单」，Agent 几秒就能答「已取消」。生成动作和答复都快了，真正费时间的是确认取消的是哪张订单、操作是否符合政策、用户是否收到与真实状态一致的结果。如果每次都要人工重做一遍，Agent 省下的操作成本可能转移给了复核人。如果一路放行，错误也能被几秒钟复制很多次。

**讲义的主线。** 第 2 页把逐条人工复核和直接放行两种极端放在一起，第 3 页引出评测阶梯。演示让人明白系统能做什么。讲义的四阶依次用人工标签、环境奖励、开发者测试、用户模拟与终态检查作为判定依据。第 12 页把「下一阶」留白，第 25 页回过头回答怎样让评测真正支持委派。

下面用同一个订单场景串起来。你可以先把它看成一条集成测试，测试夹具固定订单、用户和政策。随后给测试加上交互、失败归因和授权。订单案例的规则为教学设定。取消须验证请求者与订单归属，退款沿原支付路径，涉及例外转人工。线上规则由对应服务的领域契约定义。

## 2. 评测为什么从「看它会做」走到「让环境判」？｜[讲义第 4–12 页](2026-11-19-karthik-narasimhan.pdf#page=4)

### 2.1 演示能发现什么？标注数据增加了什么？

**讲义第 4–7 页。** ELIZA 和 SHRDLU 能展示交互效果。只看演示，很难知道演示者试了多少次、挑过哪些输入、失败是否集中在某类用户。随后 Treebank、MNIST、TREC 等人工整理的资料，把问题转化为在相同输入和标准下比较输出。对你来说，一次演示像在 IDE 里手跑一个预先设置好的测试场景（fixture），数据集像一套可重跑的参数化测试。后者给分数提供了明确的分母。

固定样本也会变得太熟悉。反复根据测试集挑超参数、提示词和工具，会把那个测试集逐渐变成调参依据。即使训练没见过原始样本，系统也可能适应题库的出题套路。反复优化代理指标时，系统可能学会稳定得分，却漏掉指标原本要衡量的目标。这也是讲义引用 Goodhart 定律的用意。讲义借历史基准的饱和引出这个问题。第 7 页用 MNIST 约 18 年、ImageNet 约 6 年、GLUE 约 1 年示意达到人类水平的时间变短。这些是课件历史近似，任务的人类基线不同。Dynabench Fig. 1 也讨论饱和，用各数据集的人类基线归一化。SuperGLUE 属于课件的补充。Dynabench 的补充做法是让人在模型参与的迭代中发现当前失败点，再标注下一轮样本。这样测试随着系统变化，需要纵向比较时，可以冻结一份基线并记录轮次。[Dynabench](references/Dynabench_Rethinking_Benchmarking_in_NLP.pdf)

对应订单场景，先用历史工单给「查询订单」「请求取消」「需澄清」标标签，可以测分类准确率。分类正确的 Agent 仍可能对错订单执行、漏掉归属验证，或者把「退款已申请」说成「退款已完成」。这些错误由一连串动作产生，评测需要推进到环境。

### 2.2 为什么一个 Agent 用例需要初始状态和终态？

**[讲义第 8–9 页](2026-11-19-karthik-narasimhan.pdf#page=8)。** 把一次任务称为一回合（episode）。回合从某个状态开始，Agent 接到用户消息后提出动作，环境执行后给观察结果，Agent 再决定下一步，直到完成、失败或到达预算。环境掌握的状态可能比观察更多。例如一个 GET 响应只给订单摘要，数据库还包括支付记录和已有操作。评测者可以读取或重建这些状态，通过评分器给出一次任务的质量。评分用来评估运行结果，Agent 在执行时未必看到它，也未必用它训练。课件里的文字游戏、TextWorld、Jericho 和小型网页操作环境 MiniWoB 都具备这种动作与反馈的结构。

[讲义第 9 页](2026-11-19-karthik-narasimhan.pdf#page=9)的 WebShop 把网页交互变成可规模重跑的任务。论文 §3 用约 118 万件商品和约 1.2 万条众包购物指令构建环境，Agent 发出搜索、点击、下单等动作，评测用目标商品的隐藏属性、选项、品类和价格约束计算匹配。论文统计平均匹配分与满分率，例如两次购物分别得 1 和 0.5，平均匹配是 75%，满分率是 50%。其他商品只要满足条件也可能得满分。人主要在上游提供目标和标注，后续可自动判分。这种评分能识别选错规格，售后体验之类未建模的质量需要另外观察。[WebShop](readings/WebShop_Towards_Scalable_Real-World_Web_Interaction_with_Grounded_Language_Agents.pdf)

把这个结构放到订单用例，最小测例要有「初始订单和账户、用户任务、工具契约、预期可观察结果」。未发货的 001 与已发货的 001、归属于请求者的 001 与归属尚未核实的 001，应该得到不同结果。记录这些条件后，虽然模型可以用不同的措辞和工具顺序完成任务，评分器仍能判断哪些输出和状态符合要求。

### 2.3 从网页到软件改动，再到有用户的工具调用

**[讲义第 10 页](2026-11-19-karthik-narasimhan.pdf#page=10)与指定阅读。** SWE-bench 把真实 GitHub issue 和指定代码状态交给系统，通过重跑开发者测试评分。用补丁前应失败、补丁后应通过的测试检验目标行为（FAIL_TO_PASS），再用补丁前后都该通过的测试检查回归（PASS_TO_PASS）。它像给 Agent 一套你平时会用的回归测试环境。测试覆盖之外的行为仍需审查。原论文的 2,294 条任务来自 12 个 Python 仓库，表中 Claude 2 配 BM25 检索的早期解决率为 1.96%。讲义用「约 2% 到 90%+」讲快速进展，后者来自 SWE-bench Verified，是另行人工筛选的 500 题。两端的样本、系统和时间都不同。[SWE-bench](readings/SWE-bench_Can_Language_Models_Resolve_Real-World_GitHub_Issues.pdf) · [SWE-bench Verified 发布说明](https://openai.com/index/introducing-swe-bench-verified/)

**[讲义第 11 页](2026-11-19-karthik-narasimhan.pdf#page=11)与指定阅读。** τ-bench 再加入按隐藏任务说明扮演客户的模拟用户。Agent 得到对话、工具说明和业务政策，标准答案只给评测方。工具会改变航空或零售环境的数据库。回合结束后，评测把终态与标准状态比较，对部分任务还检查必须告知用户的信息。论文 §3 明说，即使评分为 1，轨迹仍可能漏掉明确确认。若终态和文字相符却漏了必须的授权步骤，原评分不一定看得出来。这正好接到讲义第 20 页的过程核验。[τ-bench](readings/tau-bench_A_Benchmark_for_Tool-Agent-User_Interaction_in_Real-World_Domains.pdf)

**讲义第 12 页。** 每一阶的支出不同。人工标签要按样本付出，WebShop 需要先构建环境和规则，SWE-bench 复用已有测试，τ-bench 每次还要运行模拟用户模型。自动评分节省逐条判断，出题、维护环境和修复坏测试依然需要人力。可自动化的范围是「我们定义得清楚、环境能观察到」的范围。订单数据库断言属于这类。判断用户是否真正理解一条复杂政策，需要补人工或有独立校准证据的评估。

## 3. 榜单分数可以推到多远？｜[讲义第 13–15 页](2026-11-19-karthik-narasimhan.pdf#page=13)

### 3.1 读榜单之前，先读它实际测了什么

**讲义第 13 页与指定阅读。** 课堂把 Web、桌面、职业工作、软件、研究及通用工具等基准并排。浏览任务可以要求找到一个简短事实，也可以要求在真实网站完成一笔操作。研发基准可以让 Agent 提交一份补丁，也可以要求它在预算内复现一篇论文。即使两个榜单都报「成功率」，被测任务、环境、可用工具、时间预算和评分机制也可能都不同。文末阅读地图逐项给出这些差异。

《Establishing Best Practices for Building Rigorous Agentic Benchmarks》先问评分器能不能把正确判正确、把错误判错误。论文称之为结果效度（outcome validity），例如正确补丁可能被错误断言拒绝，错误补丁可能通过过弱的断言。再看通过任务是否确实需要我们想测的能力，这叫任务效度（task validity）。例如一道题能被背答案的系统通过，就无法检验解决新问题的能力。把结果用于比较系统时，还要看各自有没有见过训练样本、环境是否相同、是否测了同一批任务。作者检查具体基准、复跑并分析误判，并给出构建与审核 checklist。其附录 E.2 报告，他们所查的 τ-bench 任务中，有一部分应拒绝操作且无必需文本输出，空回复和不改变状态即可通过。这说明一套评分器可能把「没有做错写入」与「正确解释并拒绝」看成同一结果。报告里记录基准快照、模型和工具、任务预算、分母、环境失败的判定和复跑规则，才能回溯差异来源。[Agentic Benchmark Checklist](readings/Establishing_Best_Practices_for_Building_Rigorous_Agentic_Benchmarks.pdf)

**工程推导。** 测订单取消时，先拿一批由人工复核的正确轨迹和已知错误轨迹校验评分器。如果评分器要求查订单必须恰好一次，它会错杀解释后再确认的正确回合。如果只看状态，漏验归属的回合也能得分。比较版本时，同时报告包含基础设施故障的全流量口径，及按事先固定规则排除这类故障的诊断口径。保留原始事件和各自分母，便于发现差异出在模型还是环境。

### 3.2 「50% 时间视界」怎么读？

**[讲义第 14 页](2026-11-19-karthik-narasimhan.pdf#page=14)与补充论文。** METR 为软件任务找人类参考完成时间，再测各 Agent 在这些任务上的成功情况。把任务按人类参考耗时放在横轴，通常短任务容易，长任务难。人类基线的参考时间主要用成功样本耗时的几何均值，也含研究人员估计的任务。论文在参考耗时的对数尺度拟合成功概率曲线，把曲线穿过 50% 时对应的人类耗时称为 50% 时间视界。读到「一小时」时，应理解为「在该基准和配置下，人类参考耗时约一小时的任务落在拟合成功率 50% 处」。同等人类耗时的任务仍有明显难度差异。得到各系统的 50% 时间视界后，课件第 14 页把时间按年份放到横轴、时间视界放到纵轴，展示历史趋势。课堂写历史趋势约 4–7 个月翻倍，归档原论文针对其主分析报告约七个月。换任务集、参考人群、通过线或预算都可能改变结果。复查时保留论文原实验的任务组合和版本，新榜单即使沿用相近名字也要另看集合定义。[METR 长软件任务](references/Measuring_AI_Ability_to_Complete_Long_Software_Tasks.pdf)

对订单 Agent 也可以做内部诊断。让熟悉系统的同事完成多类任务，按人类参考耗时看 Agent 在短查询、取消前核实、跨系统异常工单各组上的表现。独立记录 Agent 运行耗时、人工核验耗时和失败后修复耗时。生产体验还取决于这些长尾耗时。

**[讲义第 15 页](2026-11-19-karthik-narasimhan.pdf#page=15)。** 课件的曲线是成本关系示意。改动多时，输出量本身就可能超出复核预算。即使产物很短，细微错误也未必好找，例如回归测试通过了，但只有跨时区订单的截止时间算错。一个查单状态断言几毫秒就能跑完，而审阅范围大的补丁可能比生成更久。只有任务耗时或榜单胜率，还无法回答是否该把它交给模型。下一个维度是「这件事验证起来有多难」。

## 4. 可靠性怎么测？｜[讲义第 16–19 页](2026-11-19-karthik-narasimhan.pdf#page=16)

### 4.1 把可靠性和该不该依赖分开

**[讲义第 16 页](2026-11-19-karthik-narasimhan.pdf#page=16)。** 可靠性问系统在同类任务上能否稳定做对。讨论时要带上任务分布、版本和运行条件，比如「这个模型、这组工具在未发货订单取消上」。「信任」谈人使用系统时知道何时该依赖、何时该接管。前者有统计证据，后者还受错误代价、检查难度和使用者理解的影响。课件用四格表达这组关系。

| | 容易验证 | 难以验证 |
| --- | --- | --- |
| 系统在这类任务上较可靠 | 可在边界内委派，例如读回已取消状态后通知用户 | 缺乏独立检查时容易盲信，应先补证据 |
| 系统在这类任务上不够可靠 | 可限定用途并抽检，关键结果需逐条校验 | 这类任务暂不应交由它执行 |

**指定阅读。** Lee 与 See 在 2004 年的综述把信任视为人在不确定、可能承担损失时对自动化能否帮助达成目标的态度，信任会影响实际依赖。论文用三个维度说明恰当信任，分别是校准（总体信任程度是否贴近真实能力），分辨力（能否随能力高低有所区分），特异性（是否针对某功能或某时段）。论文还区分了三种信任依据，分别是以往和当前表现、系统怎么做、系统为何这么设计。订单 Agent 能稳定查状态，就应在查状态上相应地使用它。退款规则换版后，同一个 Agent 的历史表现需要按任务和版本重新解释。课堂四格是这门课对问题的组织，2004 年综述提供恰当依赖的概念背景。[Trust in Automation](readings/Trust_in_Automation_Designing_for_Appropriate_Reliance.pdf)

### 4.2 一次做对、每次做对、试到做对

**[讲义第 18 页](2026-11-19-karthik-narasimhan.pdf#page=18)，推导依据为 τ-bench §3。** 固定一批任务，对每个任务做多次可比较的运行。对某个任务，$n$ 是已观察到的回合数，$c$ 是成功数，$k$ 是所问的重复次数，需 $1\le k\le n$。$\binom{n}{k}$ 表示从 $n$ 个已观测回合里无放回选出 $k$ 个回合的组合数。可由同一任务的观测样本算出两个量。

$$
\widehat{\mathrm{pass}^{k}}=\frac{\binom{c}{k}}{\binom{n}{k}},
\qquad
\widehat{\mathrm{pass}@k}=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

第一项选出的回合全来自成功样本。第二项先算全部来自失败样本的比例，再用 1 减去它。遇到 $c<k$ 时「从 $c$ 选 $k$」视为 0。基准按任务平均，避免给回合跑得多的题额外权重。$k=1$ 时，两式都等于单题的 $c/n$。在同一任务独立同分布重跑、该任务真实单次成功率为 $q_i$ 的假设下，全成功概率为 $q_i^k$，至少一次成功概率为 $1-(1-q_i)^k$。如果任务难度不同，要逐题算再平均。超时由共享服务引发，或后一次重试继承了前一次状态，就需要记录依赖关系，不能直接按独立回合解释。[τ-bench](readings/tau-bench_A_Benchmark_for_Tool-Agent-User_Interaction_in_Real-World_Domains.pdf)

**教学算例。** 对 5 个任务固定各跑 8 次。下面的样本演绎的是讲义第 18 页的示意比例，计数为本节自设。每列「成功次数」里，一个数字对应一个任务。

| 系统 | 每题 8 次中的成功次数 | pass@1 | pass^8（全成功） | pass@8（至少一次成功） |
| --- | --- | ---: | ---: | ---: |
| A | 8、8、8、0、0 | 60% | 60% | 60% |
| B | 5、5、5、5、4 | 60% | 0% | 100% |

两者均运行 40 次、成功 24 次。A 前三题的 8 次都成功，后两题在这批运行中没有成功候选。B 每题至少成功一次，每题也至少失败一次，所以观测的 pass^8 为 0%。如果固定每道题的真实概率都为 0.6，且 8 次独立，全成功概率才是 $0.6^8\approx 1.68\%$。这个假设算例和上表的观测值各自回答不同的问题。课件同时提醒报告跨采样种子的波动、不同措辞、环境变化、成本和延迟。

例如 B 的第一题，8 次里有 5 次成功。从中抽 2 次，两次都成功的组合是 $\binom{5}{2}=10$ 个，全部组合是 $\binom{8}{2}=28$ 个，所以全成功是 $10/28$。同理选出两次都失败的组合有 $\binom{3}{2}=3$ 个，至少一次成功是 $1-3/28=25/28$。每题各算一次，再平均得到 Java 输出中 B 的 $k=2$。

τ-bench 论文 §5.1 在其零售任务里，GPT-4o 使用 function calling 的 pass^1 为 61.2%，pass^8 低于 25%。这是论文指定系统与任务上的历史结果。上面两行是用来读懂差异的固定数据。[τ-bench](readings/tau-bench_A_Benchmark_for_Tool-Agent-User_Interaction_in_Real-World_Domains.pdf)

候选容易在隔离环境里生成且能用独立测试选择时，pass@k 有助于估计搜索的空间。真实交付还取决于系统选中正确候选的能力。直接让人逐次接受操作时，更关心稳定的重复成功和错误的类型。对于会提交交易的 Java 方法，重试前先读回交易状态，使用幂等键防止重复提交。基准实验则为每个独立回合重置状态，两者目的分别是保护线上副作用和保证测量可解释。

[可运行 Java 算例](examples/TrustEvaluationExample.java)覆盖 $k=1,2,8$ 的组合概率和上表。运行方式为从本课目录执行 `java examples/TrustEvaluationExample.java`。固定数据不调用模型、网络或外部服务。[这次运行输出](examples/RESULTS.txt)

### 4.3 为什么要持续测，还要从大量运行中找失败簇？

**[讲义第 17 页](2026-11-19-karthik-narasimhan.pdf#page=17)。** 评测是部署、保留运行记录、发现失败、写新测试的循环。持续更新的基准（living benchmark）定期加任务，生产监控捕捉流量与历史套件的差异，持续对抗性测试主动找边界失效。SWE-bench-Live、LiveCodeBench 用时间和新题处理公开题老化，某个时点的分数仍依赖当时的快照。如果测试过程中可以检索到题目和答案，发布日期在训练截止之后也不足以排除重叠。[SWE-bench-Live](references/SWE-bench_Goes_Live.pdf) · [LiveCodeBench](references/LiveCodeBench_Holistic_and_Contamination_Free_Evaluation_of_Large_Language_Models_for_Code.pdf)

**[讲义第 19 页](2026-11-19-karthik-narasimhan.pdf#page=19)。** 大规模模拟能多碰到低频错误。课件用软件模糊测试和自动驾驶模拟里程类比，把大量低成本运行交给机器。对于失败簇，课件给出漏查规则、工具入参错误和过早结束三个方向。把失败归入簇是为了发现共同原因，不能从相似文字直接判定根因。

**教学推导与工程做法。** 如果真实失效率为 1%，且每个样本独立、代表那类流量，抽 100 次仍约有 $0.99^{100}\approx36.6\%$ 的概率一次失败都没遇到。若 299 次独立观测均为 0 失败，单侧 95% 二项置信上界 $1-0.05^{1/299}$ 才接近 1%。拿同一条脚本在单一初始状态上机械刷 299 次，不能代表 299 种真实情况。生产分布、模拟覆盖、相关性和标签错误都限制推断。

订单用例可以按状态、权限、用户措辞、并发／超时和版本分层。评测集用三份样本完成不同目标。旧版本固定集用于同比，已发现事故的回归集用于防重犯，独立留出集用于最终评估且不参与调参。上线后记录每类失败的场景分母、故障簇和真实影响。保留能够复放的最小证据，日志对隐私数据脱敏并控制访问。建议把失败重放分为模型、评测器、基础设施、环境、业务规则几层，一条事故可能涉及多层。

## 5. 为什么结果通过，过程仍要拦？｜[讲义第 20 页](2026-11-19-karthik-narasimhan.pdf#page=20)

**[讲义第 20 页读图](2026-11-19-karthik-narasimhan.pdf#page=20)。** 课件把同一次取消订单的过程拆为六步，依次读请求、查订单、跳过身份验证、取消订单、尝试退到新卡、通知用户。图右下只按「订单是否已取消」给结果 Pass。另有两处过程标记：漏身份验证与不安全退款。第 4 步写着评分器不确定、交人复核，这条记录是待核实信号，课件没有把它算成第三处已确认违规。用这张图时，先分清终态评分、轨迹规则和证据不足三个概念。

**工程推导。** Java 服务里可以分别做「任务终态核验」和「有副作用动作的前置条件」：

| 检查 | 独立证据 | 不通过或缺失时 |
| --- | --- | --- |
| 取消写入真的完成了 | 订单服务的终态、操作回执及事务关联 ID | 超时先读回。状态未知时向用户说明尚待确认 |
| 取消前已验证归属 | 受托身份与订单归属的证明、验证事件和动作时间 | 服务端拒绝执行，Agent 请求补充验证 |
| 退款范围、金额与路径符合当前规则 | 交易核对、政策版本、支付侧动作回执 | 规则拒绝或暂停交人工复核 |
| 用户通知符合已知状态 | 发送内容、已确认的终态和异常说明 | 修正通知，记录通知是否实际送达 |

用独立的业务检查器给每项返回「通过／违规／无法验证」。例如模型想走取消工具时，订单服务在动作前强制校验归属。可验证的硬约束交确定性代码。事件表给出的终态和回执来自系统本身，评测器不应只信模型的描述。用户意图是否仍有歧义等语义规则，可由人工或经验证的模型评分器处理。缺证据时报告待人工复核，避免在统计里折算成「通过」。同一条轨迹也可能因日志丢失而无法验证，需定位是缺少检查、检查失败，还是检查过但是缺证据。把副作用风险大的未决样本优先交给人，保留少量低风险随机审计以检查自动评分的盲点。

一个最小的排错过程是先确认规则版本与任务初始状态，再沿运行轨迹（trace，即按时间记录的逐步事件）定位首次与期望分歧的事件，最后确认独立终态。如果是工具签名新旧不一致，固定模型与任务，只替换工具后复跑。如果是模拟用户误解脚本，修环境和标签，重新比较旧模型与新模型。如果模型在明确规则后仍跳过验证，后端拦截先保住状态，随后用失败样本做回归。复测要同时确认正确流量仍能完成，防止通过拒绝一切把风险指标做得好看。

## 6. 可信交付怎样节省复核时间？｜[讲义第 21–23 页](2026-11-19-karthik-narasimhan.pdf#page=21)

**[讲义第 21–22 页](2026-11-19-karthik-narasimhan.pdf#page=21)。** 我们信任同事时有过往表现、职责和审计记录，信任软件时有类型、测试、代码评审和 CI。对 Agent，同样应能指向独立证据。若它只交一份补丁，评审者需要通读或重做。[第 22 页](2026-11-19-karthik-narasimhan.pdf#page=22)给出的做法是随交付说明跑了哪些测试、哪组日志能验证副作用、哪些结论有原文引用、为什么改各块内容。讲义还举 Lean 证明作例子。Lean 会检查写成形式化命题的证明，证据的有效范围取决于命题和使用的假设。测试记录能确认指定环境中被断言覆盖的行为，引用只有在内容支持结论时才有证明力。解释里记录关键动作及依据即可，操作记录和测试输出通常比长篇自述更好查验。

同样地，订单 Agent 的交付面可以把一句「已取消」展开成几个可核验事实。用户界面显示取消成功、退款仍在处理中，并给可查询的业务回执。内部评审能打开服务生成的取消事件、政策版本、授权结果和支付服务回执。关联键把这些证据连到同一次请求。如果读回的证据和输出冲突，例如退款还是待处理，报告以服务状态为准并标注未决。

**[讲义第 23 页](2026-11-19-karthik-narasimhan.pdf#page=23)。** 课件用几行退款补丁示意「系统应该告诉人重点看哪里」。图中特别标出退款补丁中清理资金冻结记录的一行。评审者先确认变更影响哪些记录、它们是否属于当前订单，再找回归测试，分别验证只清理目标订单的记录及写入失败时相关状态一致回滚。评审优先看这种带副作用、测试不足或规则不明的改动。可用校准置信度、未决标记、摘要、按风险排序和抽检来引导注意力。这里的校准可以这样验证：在独立人工标注样本上按评分分组，比较每组实际错误率。如果预测「约 20% 会错」的一组实际错了 45%，这个分数就高估了可靠性。按场景或版本分组也很重要，一组汇总可靠的分数可能掩盖退款分支失真。模型说「我有 98% 把握」属于自报，使用前需要历史校准和版本验证。

**工程推导。** 每个待审项应把风险原因和证据入口一起给人。订单服务例子里，一条无法确认归属的写操作即使预估很少出错，也必须由系统拒绝或暂挂。对低影响、可回滚的状态说明，可按历史错误率和影响分配审计预算。用「该类错误概率 × 可估计损失」辅助排优先级时，还应考虑复核能否拦住错误和消耗的时间。用模型、工具、复跑和人工处理的总成本除以验收通过的交付数，即得每次交付成本。比如 10 个请求的模型与工具成本合计 5 元，人工复核与返工合计 25 元，最终验收通过 8 个，单个可接受交付是 3.75 元。失败的两个请求依然消耗了成本。这是教学数字。上线评估还应看队列积压和用户等待的分位数。

## 7. 怎样用证据逐步扩大自主范围？｜[讲义第 24–25 页](2026-11-19-karthik-narasimhan.pdf#page=24)

**[讲义第 24 页](2026-11-19-karthik-narasimhan.pdf#page=24)。** 自主性是系统在某类任务上凭历史表现赢得的，分为下表五级。

| 讲义级别 | 人与 Agent 如何分工 | 订单服务的教学映射 |
| --- | --- | --- |
| 1 建议 | 人执行 | Agent 提示需要查哪个状态和规则，人操作 |
| 2 起草 | 人批准每一步 | Agent 生成字段和回复，人核对并批准 |
| 3 执行，风险步骤先问 | Agent 做允许的步骤，风险步骤请示 | 自行查询，遇到发货、退款例外或证据矛盾时请示 |
| 4 执行并抽样审计 | Agent 在边界内执行，人抽样复核 | 仅对预先界定的低风险取消流量执行，审计可疑项并做随机抽样 |
| 5 在这一类任务中自主工作 | Agent 自行执行获准的任务类型 | 仅在明确授权的状态查询、模板通知等细分能力内可自主。系统保存证据并持续监控 |

**工程推导。** Java 服务可以按任务类型、版本、动作风险和当前证据做授权，技术上用白名单、状态机和服务端硬校验收口。起步用隔离环境或影子运行（读入真实任务但不提交业务操作），先看错误簇、误接管、人工负载和证据缺失，再逐步放开范围。记录通过条件，例如留出题里没有越权写入，必须验证的动作均可从独立证据回查，人接管队列在可控规模。阈值应由真实任务风险和统计把握决定。若模型、工具、业务政策或流量发生明显变化，可收回相关任务权限，回到草稿或强制审批并复测。「该问人时会问」可以作为独立能力测试，避免把请求帮助当作回合失败一概惩罚。通过率还要纳入接管后真实完成、用户放弃与漏升级情况，否则收紧权限很可能只是把错误藏到队列里。

**[讲义第 25 页](2026-11-19-karthik-narasimhan.pdf#page=25)。** 评测阶梯第五阶指向四个目标。大规模测可靠性，交付附证据，把复核时间花在真正重要的地方，按实绩授予自主范围。订单系统也可依此设计最小可行版本。先让确定性用例回答动作有没有成功，补轨迹规则回答操作是否合规，再通过生产证据和独立留出判断该放多少权限。对一周长的软件任务，要按可验收的中间产物拆证据。短事务能够实现的自动核验比例不能直接外推。

## 9. 自测

1. 两个系统的总体 pass@1 都是 60%。看见一个系统的 pass^8 更高，能得出它适合提供八个候选让测试选吗？应看哪些数字？
2. 订单终态已取消，身份验证事件缺失，退款处理中。结果评分器只看取消，模型答「取消和退款均已完成」。你会怎么记分，线上向用户说什么？
3. 两个版本都测了 500 个请求。第二版拦下了更多需要人工的订单，也少了误操作。你需要哪些证据，才能判断它可以扩大自主范围？
4. 同一类任务 100 次模拟未见事故，能否以单侧 95% 把失效率上界压到 1%？怎样补实验？
5. 模型升级后 METR 50% 时间视界增长了。团队要自动合并跨三个 Java 服务的改动。还缺哪类部署证据？

<details>
<summary>核对答案</summary>

1. pass^8 告诉你重复全成功的情况。对候选搜寻先看 pass@8，再实际测打分器或测试能否选中正确候选，计入预算、失败成本、测试遗漏和环境重置。第 4.2 节例子里 B 的 pass@8 更高，交付稳定性仍需独立验证。
2. 取消终态通过，身份过程记无法验证或按「必须有证明」的契约拒绝放行。若已知确实跳过则记违规。退款完成和通知真实性都未通过，线上说明订单已取消、退款处理中，核实后再确认。风险节点交人工或挂起，保留各自状态。
3. 对比版本用相同留出、任务难度与政策版本。分层看任务成功率、误操作率、误转人工、漏升级、接管后的完成率和审核耗时。查看失败轨迹中的误操作是否真的被拦，回查低风险样本有没有漏报。合格的权限只针对证据覆盖的场景。
4. 在独立且代表性抽样的假设下，0/100 的单侧 95% 上界约为 2.95%。同样条件下累计 299 次零事故，上界才略低于 1%。实际补上权限、状态、措辞、并发与超时等分层，报告每层分母，同时校验模拟与线上差异。
5. 需要这三个服务的目标与回归测试、服务间契约、状态及权限副作用检查，以及补丁和测试的可追溯证据。用隔离环境、固定版本和隐藏留出估计误合并与复核负担，再决定哪些改动可自动合并。METR 的任务设置和模型趋势可作为背景。
