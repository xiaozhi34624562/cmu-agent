## 1. 从策略梯度公式看系统职责

讲义 pp.3—4 将一个简化更新写为轨迹收益减基线，再乘每步对数概率梯度。为说明系统边界，可以写成：

$$
\hat g=\frac1B\sum_{i=1}^{B}\sum_{t\in\mathcal A_i}
\hat A_{i,t}\nabla_\theta\log\pi_\theta(a_{i,t}\mid h_{i,t}),
\qquad\theta\leftarrow\theta+\eta\hat g.
$$

$B$ 是轨迹或问题批次，$h$ 是当时可见历史，$a$ 是模型生成动作 token，$\mathcal A_i$ 是参与策略损失的位置，$\hat A$ 是优势估计，$\eta$ 为学习率。真实 PPO/GRPO 还涉及旧策略、比率、裁剪、KL 和归一化；讲义的式子是系统操作地图，不是完整算法实现。

从这个式子拆出至少六种职责：

| 操作 | 需要什么 | 产生什么 |
|---|---|---|
| `sample` | 当前策略、提示、采样设置 | 生成 token、行为概率、版本 |
| `env.step` | 工具调用和当前环境 | 工具输出、错误、外部状态 |
| `verify` | 最终产物、验证协议 | reward 与可追溯判分证据 |
| `forward` | 原始 token 和掩码 | 可求导 logprob、熵等 |
| `backward/optim_step` | 优势、损失和优化器状态 | 新权重与训练统计 |
| `sync` | 新权重及训练布局 | 推理布局的新策略版本 |

普通 PyTorch 足以表达张量计算，但不自动解决高吞吐自回归生成、跨引擎权重布局、环境并发和轨迹一致性。这就是本讲要用专门 RL 框架而不只写 `optimizer.step()` 的原因。[L12，pp.3—8]

### 1.1 贯穿案例：训练一个测试驱动的代码修复 Agent

设每道题包含一个仓库快照、错误描述和隐藏验收测试。Agent 会读取、编辑、运行公开测试，再提交补丁。每题采样多条轨迹，验证器在干净环境中验收，给成功奖励。下面始终追踪四种状态：

- **策略状态**：哪一版权重实际生成了哪个 token。
- **轨迹状态**：模型看到的精确 token、工具观察及历史变换。
- **环境状态**：仓库、依赖、进程与测试入口。
- **优化状态**：优势计算、损失掩码、梯度、优化器与 checkpoint。

若只保存最终补丁和 reward，无法重算产生该补丁的条件概率；若只保存文本对话，无法保证分词重放；若只保存权重，无法恢复优化器和任务队列。系统设计要把这四种状态关联起来。

## 2. 为什么生成和训练应该使用不同优化路径

讲义 pp.5—7 强调两个工作负载：推理引擎如 vLLM、SGLang 负责 `sample`；训练引擎如 Megatron、FSDP2 负责前反向与更新。引擎名称是例子，关键是计算形状。

### 2.1 训练可并行看见序列，生成必须逐步知道未来

已获得轨迹后，训练采用 teacher forcing：给定完整序列，通过因果 mask 在一个前向过程里得到多个位置的 logprob。它与 prefill 类似，有较大的矩阵运算，也需要保存或重算激活并执行反向。

生成时，下一个 token 依赖前面刚生成的 token。即使多个请求可以批处理，单条序列仍有自回归依赖，常处于反复读取权重和 KV 的 decode 工作负载。训练不能简单复用“无梯度的 KV 缓存”完成全部反向；推理也不必承担保存全部训练激活的成本。

因此“前向都是 `model.forward()`”只是 API 相同，不能说明最优内存布局、并行方式和调度相同。

### 2.2 一步 RL 训练的五阶段

[L12，p.8] 的顺序是：采样并交互 → 验证 → 训练前向重算 logprob → 反向 → 更新和同步。训练端重新前向不是重复劳动失误：推理通常在 no-grad 模式，无法从采样时的浮点 logprob 反传到训练权重。

不过重算必须回答：输入是否完全相同，权重版本是否符合算法假设，采样约束是否改变了行为分布。`logprob` 是一个数值，不附带这些信息时没有完整语义。

### 2.3 工作负载优化的责任表

| 推理侧 | 训练侧 | 跨两侧 |
|---|---|---|
| KV cache、prefix cache | 激活检查点 | 权重同步与重新分片 |
| continuous batching | packing、负载均衡 | token 与模板一致性 |
| speculative decoding | 带梯度前缀共享 | MoE routing replay |
| 高效 decode、并行 | forward/backward、优化器 | 版本、旧策略概率与滞后控制 |

若生成占 80% 时间，单独把训练加速一倍，在理想串行模型下整体只加速 $1/(0.8+0.2/2)\approx1.11$ 倍。这是 Amdahl 式教学推导，说明先测瓶颈再选优化。优化之后瓶颈会移动，GPU 分配也可能需要重调。

## 3. KV Cache：以显存换历史重算

Transformer 在生成新 token 时要用到过去 token 在每层的 key 和 value。KV cache 保存这些张量；新一步只计算新位置的 Q/K/V，并让新 query 读取过去的 K/V。[L12，p.9]

### 3.1 容量公式与讲义数字复核

对标准全层缓存的 decoder，忽略布局和元数据，单序列长度 $S$ 的容量约为：

$$
M_{KV}=2L S H_{KV}d_h b.
$$

$L$ 为层数，$H_{KV}$ 为 KV 头数，$d_h$ 为每头维度，$b$ 为每元素字节数；2 表示 K 和 V。GQA 中 $H_{KV}$ 可以小于 query 头数，不能直接用隐藏维度乘层数代替。

Llama-3-8B 常见结构的教学代入为 $L=32,H_{KV}=8,d_h=128,b=2$，得到每 token $131072$ 字节，即 128 KiB。长度 32768 时为 4 GiB，64 条并发约为 256 GiB。[L12，p.9] 讲义写 KB/GB，按二进制单位算可对应上述 KiB/GiB。这里不含模型权重、碎片、调度结构和其他缓冲，不能把 256 GiB 当整机所需显存。

### 3.2 为什么更多 rollout 会把系统推到容量瓶颈

GRPO 为同一道题采样多条长输出；Agent 多轮还保留工具历史。并发数、上下文长度和每 token KV 大小相乘，可能使可同时运行的序列数量受限。减小 batch、限制长度或量化 KV 都改变系统行为，应同时检查质量、吞吐和数值一致性。

工具执行期间，若请求暂停但 KV 仍驻留，会占据显存而不持续生成。系统可以保留、驱逐或转移这些 KV；每种选择在恢复延迟、重算和容量之间权衡。暂停一个进程不等于释放所有状态。

## 4. Prefix Caching：共享的是同一策略下的精确前缀

讲义 p.10 的图从 system prompt 与 tools 分叉到 Task A/B，再分叉为多个 rollout。同题 group rollout 共享任务提示；同一轨迹下一轮也可能包含上一轮全部历史。SGLang 的 RadixAttention 用前缀树管理这类复用。[R1，§3；L12，p.10]

### 4.1 命中条件比“文本看起来一样”更严格

可复用 KV 至少要求相同模型权重、token ID 序列、位置与注意力语义；多模态输入、adapter、精度和模型配置也可能影响缓存身份。工具定义顺序、空格或模板标记变化都可能使前缀不同。

**教学例子**：题目提示长 8000 token，每题采样 8 条回答。理想情况下，提示 prefill 可以从 8 次减少到 1 次，节省 56000 个重复提示 token 的计算；回答的 decode 仍需分别进行。这个比例不是端到端 8 倍，因为 decode、工具、验证和调度成本没有消失。

### 4.2 权重更新会使旧 KV 失效

KV 是模型参数计算的结果。训练发布新策略后，旧权重生成的 KV 不能无条件供新策略继续使用。若长轨迹中途更新，可能需要丢弃旧 KV、用完整已有 token 在新权重下重建，然后续写；AReaL 的 interruptible rollout 正是这样处理。[R4，§4.1，PDF pp.4—5]

缓存命中率应和权重刷新频率一起测。每个训练步换权重时，静态服务里很高的长期缓存命中率未必保留。多租户或多 LoRA 还必须把适配器身份纳入缓存键。

### 4.3 前缀缓存与训练前缀共享不是同一实现

推理 cache 主要复用数值结果；训练共享还需要保留或重建计算图，并正确汇总所有分支对公共前缀的梯度。把推理 KV 标为 detached 后直接当成训练共享，通常会截断应有梯度。第 7 节会详细区分。

## 5. Continuous Batching：减少长尾等待，不保证每条轨迹更快

静态 batch 的请求 A、C、D 先完成后，空出的槽位仍等待最长的 B；continuous batching 在一个 decode 迭代边界调度，让新请求 E、F 等进入空位。[L12，p.11] 核心单位从“整个请求”变成“生成迭代”。

### 5.1 用一个离线时间表理解利用率

假设四个槽位运行长度 `[2,8,3,1]` 的请求，每 token 时间相同且不考虑 prefill。静态批次占 $4\times8=32$ 个槽位时间，实际有用工作为 14，槽位利用率约 43.75%。连续批处理若队列始终非空，可以更快补入新工作，但已经在运行的 B 不会因此减少自己的 8 个 token。

这个模型没有反映 batch 大小对 token 时间的影响，只用来说明空闲来源。真实 GPU 的吞吐、单请求延迟和显存占用需要实测，不能直接把槽位利用率当 MFU。

### 5.2 长 prefill 与 decode 会相互影响

新请求有长提示时，一次性 prefill 可能占用计算，导致已有 decode 请求的 token 延迟升高。讲义列出 chunked prefill 或 prefill/decode 分离作为处理方向。[L12，p.11] 前者把长提示切成可调度块；后者用不同资源服务不同阶段，也带来 KV 传输和调度成本。

RL 主要关心轨迹和训练供给，但仍要关注长尾：只追求总体 tokens/s，可能使某些极长轨迹长时间滞留，数据版本越来越旧。调度目标应该同时包含吞吐、等待时间和可接受 staleness。

## 6. Speculative Decoding：分布保持依赖完整接受与纠正协议

讲义 p.12 描绘 drafter 一次猜 4 个 token，目标策略并行核验，接受前两个、第三个纠正。它减少串行目标模型步骤，不是让未来 token 摆脱因果依赖。[R2，§2]

### 6.1 为什么不能只“同意就收、不同意就重采样”

设目标分布为 $p$，草稿分布为 $q$，先从 $q$ 采样 $x$，接受概率为：

$$
\alpha(x)=\min\{1,p(x)/q(x)\}.
$$

拒绝时要从残差分布 $p'(x)\propto\max(0,p(x)-q(x))$ 采样。接受路径贡献 $\min(p(x),q(x))$，拒绝后补足剩余质量，才恢复目标分布。若拒绝后随便从 $p$ 重采样，通常不是同一个精确协议。[R2，§2.3、算法 1，PDF p.3]

这里的 $p,q$ 应已包含实际 temperature、top-k 等采样调整；不同实现是否保持目标分布，需要按其协议核实。讲义“exact distribution”是有条件的算法结论，不能泛化到所有标为 speculative 的近似加速。

### 6.2 何时值得做草稿

令平均接受率为 $\bar\alpha$，草稿长度为 $k$，草稿单步成本相对目标为 $c$。在独立接受率和目标并行核验耗时近似固定的简化假设下，论文给出每次核验期望产出：

$$
E[N]=\frac{1-\bar\alpha^{k+1}}{1-\bar\alpha},\qquad
\mathrm{speedup}\approx\frac{E[N]}{1+kc}.
$$

这是论文分析的假设模型，不是硬件无关保证。[R2，§3.1、§3.3] 低接受率浪费草稿和核验计算；高并发时目标模型可能已经充分利用算力，额外核验未必免费。

### 6.3 RL 特有问题：目标策略一直在变

训练过程中 $p$ 每步变化，冻结的 $q$ 可能逐渐不匹配，接受率下降；讲义提出在线 SFT 或蒸馏 drafter 的方向。[L12，p.12] 这增加训练和维护成本，应测净收益。

还要注意 logprob 来源：策略梯度需要实际行为策略的信息，不能把小模型的 $q$ 当成目标策略 $p$ 的概率。精确协议得到目标分布，不表示可以随意省略目标策略的概率记录。

## 7. 训练内存：激活检查点、packing 与带梯度前缀共享

### 7.1 激活检查点节省什么

前向通常保留许多中间张量供反向使用。检查点只保存部分边界，反向到某层时重新计算内部激活，用更多计算换更少峰值内存。[L12，p.13；R3]

讲义以“保存每层输入、重算每层内部”说明机制；并非所有实现都按层切分。经典论文研究不同划分策略，包括在一定假设下 $O(\sqrt n)$ 或更低存储的权衡。[R3，§3—4] 不能把所有 checkpoint 策略概括为同一内存复杂度。

如果原始训练粗略是 1 次 forward 加约 2 次 forward 等价的 backward，再加 1 次 forward 重算，则计算从 3 变 4，约增加 33%。这是讲义的量级解释，实际墙钟、通信重叠和选择性重算可能差异很大。只重算部分昂贵保存的张量可改变权衡。

### 7.2 Packing 为什么需要正确边界

长度不同的轨迹若填充到最长，会产生无效 padding。Packing 把多个样本装入更紧凑批次，减少浪费；但必须让独立样本的注意力、位置和损失边界正确。把样本直接拼接而不隔离，后一个样本可能读到前一个答案，改变训练目标。

日志中至少区分总存储 token、有效上下文 token、损失 token和 padding token。单个“tokens/s”如果计算口径不同，无法比较优化。

### 7.3 训练前缀共享：四个契约缺一不可

若四条轨迹为 $P+r_1,\dots,P+r_4$，公共提示 $P$ 可以只计算一次，但需要：

1. 每个分支能看到公共前缀及自身过去，不能看到兄弟分支。
2. 位置 ID 与各自独立运行时一致。
3. 每条轨迹原本的损失和归一化权重保持不变。
4. 公共前缀接收所有后继分支的梯度贡献。

数学上原目标 $L=\sum_iL(P,r_i)$，共享图应满足：

$$
\nabla_\theta L=\sum_i\nabla_\theta L(P,r_i).
$$

这是精确共享要保持的语义。前缀 token 没有直接预测损失，也可能影响后继 token 的概率，因此它们对梯度并非没有贡献。[L12，pp.14、20]

### 7.4 AReaL-DTA：为什么只装一条根到叶路径

把所有唯一 token 打包成一棵树、用 tree attention mask，可以减少重复，但整棵树的激活仍可能很大。AReaL-DTA 用 DFS，沿当前根到叶路径保留状态；叶子损失回传后释放不再需要的分支；公共节点在所有子树贡献汇总后再完成回传。[R6，§3.1，PDF pp.4—5]

优化版还调整 DFS 顺序，减少太短的前反向片段，并对长后缀分块反向和重算。多 GPU 分配既要均衡工作量，也要避免把共享前缀拆到不同 GPU 后重复算。[R6，§3.2—4] 因而“树 token 最少”与“所有 GPU 同时结束”是相互制约的目标。

### 7.5 讲义加速数字的正确口径

讲义 p.14 引述 ZoRRo 的长提示重复率 80–95%、actor update 最多 6 倍；它是特定长提示配置中的训练阶段指标。本篇没有另行取得该博客完整实验协议，不将它当端到端保证。

AReaL-DTA 本地 v2 在 $\tau^2$-bench 上报告 full-tree 压缩率 9.43，leaf-only 为 5.56，使用 8×H800、16K 训练上下文。[R6，§5.1，PDF p.6] “最多 8.31 倍”是训练吞吐相对 dense 的口径；同文端到端 1.7B/8B 实验为 1.28/2.28 倍，并且重新调优 rollout/training GPU 分配。[R6，§5.2，PDF p.7] 不能把前者写成总 RL 训练 8.31 倍。

## 8. 并行方式：按张量、层、上下文和专家分解不同工作

讲义 p.15 的图展示 EP、TP 和 CP，其中上方两块嵌入媒体在本地 PDF 中是黑色静态区域，本文依据可见结构图解释，不臆造动画。

| 并行方式 | 分什么 | 典型代价与适用问题 |
|---|---|---|
| 数据并行 DP | 不同样本 | 梯度同步；适合扩大吞吐 |
| 参数分片/FSDP | 权重、梯度、优化状态 | all-gather/reduce-scatter；减少单卡常驻状态 |
| 张量并行 TP | 同层矩阵/头 | 层内频繁通信；帮助模型装入多卡 |
| 流水线并行 PP | 不同层 | stage 间传输和气泡；平衡层工作量 |
| 上下文并行 CP | 同序列不同 token | 交换 K/V 或等价中间结果；支持长序列 |
| 专家并行 EP | MoE 专家 | token dispatch/combine，all-to-all 与负载不均 |

训练最优布局不必等于推理最优布局。推理可能想用较少 TP 减少通信、提高每副本 batch；训练需要更多分片容纳优化器。更高并行度也不一定更快：通信、同步与微批大小会改变设备利用率。

**教学预算模型**：若某阶段时间约为计算 $F/P_{eff}$ 加通信 $V/B_{eff}$ 加同步等待，增加 GPU 只改善第一项并不够；网络拓扑会影响后两项。这里 $F$ 是运算量，$V$ 是通信量，$P_{eff}$ 与 $B_{eff}$ 为有效算力和带宽，均应测量而非直接用硬件峰值。

## 9. Weight Sync：发布的必须是完整、可识别的一版策略

讲义 p.16 说 1T 参数若每个参数 2 字节，权重约为 2 TB；把训练权重送到推理引擎还需要布局转换。2 TB 是一份权重的逻辑数据量；实际网络流量取决于广播树、分片、副本数和通信协议，不能简单乘每个 rank 就称总成本。

### 9.1 完整同步、增量同步与原子切换

完整同步简单但数据量大。讲义引用 PULSE，提出低精度权重更新中大量元素存储值可能不变，传差量可减少通信。这里“约 99% 不变”是该引用所述条件，不是所有优化器、模型和训练步的定律；数学梯度很小与 bf16 存储值未变是不同命题。[L12，p.16]

无论全量还是差量，都要明确：基版本、目标版本、张量名称和 shape、dtype、分片映射、校验值与完成确认。差量应用到错误基版本可能生成不可识别权重；某些 rank 已更新、另一些未更新，会形成混合策略。

可靠发布可采用“接收并校验 → 准备 → 所有必要 rank 确认 → 切换可见版本”。这是教学系统协议，不意味着每个框架都必须实现通用分布式事务。关键是不让请求在无记录情况下跨越半更新状态。

### 9.2 训练日志中的版本字段应如何设计

至少保留 `train_step`、`weight_version`、`inference_replica`、`rollout_id`，以及每段或每 token 的行为概率来源。checkpoint 文件名与逻辑版本要关联；服务重启后版本号不能悄悄回到 0 并与旧轨迹混同。

参数一致也不等于概率完全一致。不同 kernel、精度和 MoE 路由可能改变输出；因此要在同步后做固定 token 序列的 train–inference logprob 对照，再判断优化器是否失稳。

## 10. R3：MoE 路由把微小数值差放大成离散变化

讲义 p.17 的三列图比较 rollout、训练重新选路和训练重放选路。MoE router 根据 logits 选 top-k 专家，两个接近的分数可能因浮点误差交换顺序，使前向路径离散改变。[R5，§3—4]

### 10.1 同权重为什么还会有 importance ratio 尖峰

假设 rollout 的行为概率为 0.01，训练重算为 0.03，即使名义权重相同，比率也是 3。优化器会把这个差异当成策略变化，但它可能主要来自计算路径不一致，而不是一次有意更新。

R3 的本地论文以 Qwen3-30B-A3B 和 SGLang/Megatron 对照，报告约 10% router 的专家选择不同、94% token 至少某层不同。[R5，§3.2，PDF p.5] 两个分母不同：router-level 与 token-level，不能混写为“94% 专家错误”。这些数字属于论文具体模型和实现。

### 10.2 重放的是选中的专家 mask，梯度仍来自训练计算

令训练 router logits 为 $s^{train}$，rollout 保存的专家选择 mask 为 $I^{infer}$。R3 使用：

$$
g_i^{replay}=\frac{I_i^{infer}\exp(s_i^{train})}
{\sum_j I_j^{infer}\exp(s_j^{train})},\quad
 y^{replay}=\sum_i g_i^{replay}E_i(x^{train}).
$$

它固定离散选择，让训练端按 rollout 选择走专家；softmax 仍作用于训练 logits，保留对应路径的梯度。[R5，§4.1，PDF p.6] 因此不要把 R3 写成直接复制 rollout 的全部隐藏状态或冻结 router 所有学习。

### 10.3 系统需要额外运输什么

每 token、每 MoE 层的专家索引要与原 token 对齐。公共前缀 cache 不只要缓存 KV，还可能要关联 routing metadata；截断、拼接和序列扩展后仍需一致映射。

R3 减少一种不一致来源，不修复模板变化、错误 mask、staleness 或奖励错误。诊断应分别检查：输入 token 一致、权重一致、路由一致和数值容差。

## 11. Sequence Extension：复杂 Harness 怎样改变训练样本

讲义 pp.19—20 是本课最值得手工推演的内容。Harness A 一直追加历史；Harness B 每两次观察后压缩，把前两轮变成摘要 $S$。

### 11.1 序列扩展性质的准确含义

若第 $k+1$ 次模型输入的 token 序列严格包含此前生成序列作为前缀，就可以把多轮动作放在一个更长的训练序列中，用 loss mask 标出模型生成位置。这要求 token 级前缀相等，不只是消息含义相似。

A 的序列：

```text
T A1 O1 A2 O2 A3 O3 A4 O4
```

其中 $T$ 是任务、$A_i$ 是动作、$O_i$ 是观察。B 在第三轮变为：

```text
T S A3 O3 A4 O4
```

B 的后半段不再包含原 `A1 O1 A2 O2` 前缀，因此不能把全部动作硬拼成一条假想上下文再训练。那会把 $A_3$ 的条件历史改掉。[L12，pp.19—20]

### 11.2 Loss mask 不是 attention mask

讲义 p.20 给任务、观察、摘要直接损失置 0，动作 token 置 1；同一轨迹优势 $\hat A$ 广播到动作位置。这是课堂示意的一种轨迹级信用分配，并不排除其他算法使用逐步优势。

- **Loss mask**：哪些目标 token 参与策略目标。
- **Attention mask**：某 token 能读取哪些前文。
- **Padding mask**：哪些位置是填充而非有效数据。

任务和观察 loss 为 0，仍作为条件影响动作概率，需要前向，也可能通过动作损失获得间接梯度。若把它们从 attention 中全部移除，就改变策略所见状态。

### 11.3 压缩省了生成成本，却可能增加训练重算

在 A 中，多轮可以归为一个序列；B 至少拆成压缩前、压缩后两段样本，任务 $T$ 被重复计算。压缩后上下文更短，运行时可能更便宜或更准确，但训练侧共享减少。答案不能只看训练样本数，而要比较完整序列长度、共享比例、质量和总成本。

原则是“在实际可行时尽量保留精确前缀”，不是禁止所有摘要。超出上下文窗口、长日志噪声或任务状态需要重构时，压缩可能必要；训练框架应正确记录断点，保留真实条件上下文。

## 12. Chat Template 与 TITO：字符串往返不是无损传输

讲义 pp.21—24 提醒：某些模板会删除历史 reasoning，添加空格、特殊标记或不同角色前缀；重新渲染后不再是采样时序列。该讲点名的 Qwen 模板行为按其演示版本理解，不是所有 Qwen 配置永远如此。

### 12.1 需要核对的不是最终看见的文字

若采样 token 为 `[41,52]`，它们 decode 得到 `"ab"`；同一字符串重新 encode 可能得到 `[99]`。模型概率是在 token 事件上定义的，两条 token 序列的似然分解不同，不能用它们相互替换并保持原 logprob。

讲义 p.24 写“Tokenization is one-to-one, de-tokenization is many-to-one”。严格说，普通文本分词不应被笼统称作数学上的一一映射：规范化、特殊 token、byte fallback 和 tokenizer 配置都会影响可逆性。**本课所需的准确结论是：不能假定 `encode(decode(ids)) == ids`。** 必须保存生成时的原始 token ID，而不是依赖字符串重建。

### 12.2 TITO 的数据契约

建议一条可训练记录至少包含：

```json
{
  "trajectory_id": "repair-017-rollout-3",
  "tokenizer_id": "pinned-tokenizer-revision",
  "renderer_id": "agent-template-v1",
  "input_ids": [101, 102, 103],
  "generated_ids": [201, 202],
  "behavior_logprobs": [-0.8, -1.1],
  "loss_mask": [1, 1],
  "policy_version": [17, 17],
  "reward": 1.0,
  "environment_version": "task-image-and-repo-hash"
}
```

这只是字段示意，真实记录要明确各数组对齐到整序列还是生成区间。`generated_ids`、`behavior_logprobs`、`loss_mask` 与版本必须长度一致；分段时保存上下文边界和位置。文本可以另存供人查看，但不作为唯一训练真值。

### 12.3 先做无需训练的 replay 检查

同一固定权重下：采样并保存原 token → 用训练引擎重放 → 对比动作位置 logprob。逐 token 差异的分位数、最大值与特殊 token 分布比单个均值更有用。差异只出现在轮次边界，多半先查模板；只出现在 MoE 则查路由；全体偏移则查采样温度、精度或权重。

这类一致性检查应在长 RL 运行前完成。否则 reward 下降时，系统错误会和算法问题混在一起。

## 13. Async RL：消除等待的同时引入行为分布滞后

同步系统通常先等当前批 rollout 全结束，再更新并同步。长尾轨迹使设备空闲。异步系统分配独立生成和训练资源，让前者持续产出，后者凑够批次就更新。[L12，p.25；R4，§4]

### 13.1 生产者—消费者速度必须匹配

令生成速率为 $\lambda$ 条有效轨迹/秒，训练消耗速率为 $\mu$。若长期 $\lambda>\mu$，队列增长，数据越来越旧；若 $\lambda<\mu$，训练等待。队列容量与 admission control 能限制积压，但需要决定何时暂停生成、丢弃过旧数据或调整 GPU 分配。

讲义举 3:1 推理/训练 GPU 作为 rollout-bound 的可能配置，不是普适默认。轨迹更长、验证更慢、训练前缀共享更好，都可能改变最佳比例。AReaL-DTA 的实验就显示优化训练后可以把更多 GPU 转给 rollout。[R6，表 1]

### 13.2 三种“旧”必须分别记录

1. 轨迹开始时策略已经落后当前 trainer 版本。
2. 一条轨迹很长，完成时 trainer 已又更新多次。
3. 同一轨迹中途刷新权重，前后 token 来自不同版本。

第三种不能用单个 `rollout_version` 完整表示。定义版本滞后 $\delta_t=v_{train}-v_{behavior,t}$，应同时记录时间年龄与版本年龄；一个训练步耗时变化时，两者不等价。

### 13.3 Importance ratio 能表达偏移，但不是任意滞后的万能补救

概念上每 token 可写：

$$
\rho_t=\frac{\pi_{\theta_{train}}(a_t\mid h_t)}
{\pi_{behavior,t}(a_t\mid h_t)}
=\exp(\ell_{train,t}-\ell_{behavior,t}).
$$

概率很小时，log 空间差分更稳定。比率很大意味着少量样本可能主导梯度；裁剪可以限制影响，也会带来偏差。完整异步 PPO 还需区分行为策略、近端策略等角色，不能只加这一个比率就宣称算法正确。[R4，§5]

AReaL 通过 staleness-aware 控制和相应 PPO 变体处理混合版本。论文摘要的最高 2.77 倍是特定数学/代码模型和集群比较，不等于所有 Agent 任务的加速；它主要讨论长推理密集模型，复杂工具环境还需单独验证。

### 13.4 部分轨迹不能悄悄当完整轨迹

中断、超时和取消会改变回报与长度。若任务未结束就以 reward=0 当失败训练，可能惩罚长但有希望的路径；若只留下短成功轨迹，又引入选择偏差。应记录 terminal、truncated、tool_error 等原因，并由算法明确处理，不让基础设施自动猜测。

## 14. In-flight Weight Updates：暂停、刷新、恢复之间的语义

讲义 p.26 展示 SGLang 的暂停生成接口截图，包含 abort、retract、in-place 等模式名。它说明推理引擎为 RL 暴露控制能力；接口细节随版本改变，不能把静态截图当当前使用手册。

工程上要问：暂停后哪些请求排队、哪些已完成 token 保留、KV 是否重建、请求是否重试、模型版本何时切换。AReaL 论文明确在更新时丢弃旧 KV、以新权重重算已有前缀，再继续未完成序列。[R4，§4.1]

在修复 Agent 中，还存在工具调用：推理暂停时外部测试可能仍在运行。权重切换不应重复执行已发出的写操作；模型服务状态与环境状态需要独立 ID。一次推理恢复可以重新计算已有 token，但不应把旧工具请求重新当新动作执行。

## 15. 复杂 Harness：子 Agent、压缩与递归调用要映射为训练图

讲义 p.27 提到 RAO 与 RLM，但本地页中主体图像没有可辨识文字，本文只将其作为复杂 Harness 的方向提示，不臆造论文方法细节。真正需要从系统角度解决的是：一个用户任务可能包含多条模型会话、多个角色、摘要和不同底座。

### 15.1 轨迹树不是天然一条 token 序列

主 Agent 的调用启动子 Agent；子 Agent 看到的是自己的提示与工具结果，主 Agent 可能只看到最后摘要。不能把子 Agent 的全部内部 token 拼入主 Agent 上下文，假装主 Agent 当时看见了这些内容。

训练时应保留每次模型调用的真实条件输入、父子关系、策略身份、动作区间和结果传播。信用分配可以用任务级 reward、角色级 reward 或更细粒度方法，但这是算法选择；日志结构首先要避免虚构条件概率。

### 15.2 摘要由谁生成也影响训练对象

固定程序生成摘要，与可学习模型生成摘要，不是同一策略。若摘要模型属于优化对象，它的输出应具有自己的策略概率与损失范围；若它是外部固定组件，则通常只作为观察。将所有文本统一标 loss=1，会训练模型模仿工具、用户甚至环境返回，偏离目标。

## 16. Harness-Agnostic：代理服务能解耦接口，但不能消除训练协议

讲义 p.29 的 anti-pattern 是为每种 Harness 重写 rollout/environment；中间代理兼容 chat-completions、responses 等推理 API，让现有 Harness 通过更换 endpoint 接入。[L12，p.29]

这一设计的收益是减少应用代码侵入，允许不同 Agent 框架复用训练基础设施。Agent Lightning 是讲义示例，不能从“零代码修改”直接推出“所有训练数据字段自动正确”。

代理需要保留：采样参数、token ID、原始 logprob、模型和 adapter 身份、权重版本、routing metadata、取消与流式状态。若标准接口只返回文字，就需要扩展协议、旁路记录或内部关联，才能支持 TITO 与 R3。

对齐 API 的表面请求格式，与对齐训练语义是两项工作。代理还要知道哪些调用属于同一任务、哪个结果是 reward、哪个调用产生用户可见副作用；这些信息未必能从普通模型请求自动推断。

## 17. 三种系统组织：SPMD、单控制器服务与弹性分层控制

### 17.1 SPMD：所有 rank 运行同一程序

讲义 p.30 的示例 ranks 0–3 训练，4–7 推理；所有 rank 按相同顺序创建通信组，再按角色执行。优点是对通信和时序有直接控制，便于紧耦合调优。代价是角色、依赖和生命周期紧绑，弹性扩缩或异构硬件较不灵活。

“所有 rank 同程序”不表示所有 rank 执行所有 collectives。创建组和参与具体组通信的顺序必须一致，否则可能死锁。教学伪码也省略异常恢复、停止条件和服务就绪检查，不能直接作为生产程序。

### 17.2 Everything-as-a-Service：轻量 CPU 控制器协调专业服务

讲义 pp.31—33 将推理、Agent、Trainer、Reward、Weight Sync 分为服务。各服务独立实现与发布，控制器表达高层训练循环；同协议可换自托管或托管实现。

解耦收益包括不同组件独立升级、算法研究代码更轻、资源比例可变；代价包括网络序列化、版本兼容、部分失败、队列与重试复杂度。服务数量更多不自动更稳定，需要明确协议和可观察的状态转换。

对每个服务至少定义请求 ID、幂等语义、输入输出 schema、错误分类、超时与版本。训练更新不可因重试重复执行；reward 重算需知道环境版本；权重发布需知哪些消费者已确认。

### 17.3 弹性、跨集群和异构硬件

pp.34—36 的图逐步从单 inference service，扩展为 inference controller 管多个副本，再到不同集群和 GPU 类型。p.37 的 AstraFlow 图进一步示意全球区域、多处数据获取、trainer pool 与 weight manager 的协调。

这里的系统机会是把数据采集、训练和服务分布在不同地点或硬件；代价是权重/轨迹传输、跨区延迟、吞吐差异、精度差异和故障域。异构卡的最佳 TP、batch 与 kernel 支持不同，不宜把“卡数相同”当资源相同。

本篇未下载 AstraFlow、PULSE、RAO 等所有讲义链接全文，因此只解释图示和显式讲义主张，未把它们的额外算法或实验数字写作已核验结论。这些限制不会影响本讲的核心一致性链路。

## 18. 多策略、在线 RL 与多租户 LoRA：状态管理进一步分叉

### 18.1 多策略训练

讲义 p.38 指出微服务可支持多种模型同时训练，适用于异构策略的多 Agent 轨迹。对每个动作必须知道谁产生：主 Agent、工具模型还是子 Agent；各自 tokenizer、checkpoint、优化器与奖励归因可能不同。

共同完成一次任务，不表示可以把同一个 loss 直接用于所有模型。需要决定共享奖励、协作或竞争目标、固定对手还是联合更新，并记录 rollout 时其他策略版本。否则训练环境本身在变，而日志没有解释变化来源。

### 18.2 Online RL 不等于每条用户反馈立刻反传

讲义 p.39 提到 AReaL 2.0 和 Cursor 的上线反馈更新案例，是部署后训练方向。线上数据包含选择偏差、延迟反馈、用户偏好变化和任务分布变化。需要先定义允许使用的数据、反馈质量、离线/在线验证和发布条件；“新 checkpoint 每若干小时”属于案例报告，不是本系统承诺。

在代码修复例中，用户采纳补丁可能是弱反馈，不等于所有隐藏行为正确；用户拒绝也可能因为风格而非功能错误。把用户动作直接变 reward 前，应验证它与真实目标的对应关系。

### 18.3 Multi-LoRA 的收益来源

LoRA 在冻结底座上学习低秩增量，例如某矩阵更新 $\Delta W=BA$，其中 $B\in\mathbb R^{d_{out}\times r}$、$A\in\mathbb R^{r\times d_{in}}$，$r$ 通常远小于维度。多个租户可共享底座，分别保存 adapter 与优化器状态。

讲义 p.40 的时间图比较八个串行运行与八个并发运行：聚合吞吐改善，但每个运行可能更慢。Grouped-GEMM/SGMV 类 kernel 使不同 adapter 的小矩阵运算更有效批处理。不能只说“并发更快”而省略单租户延迟和公平性。

p.41 的 Tinker 例子将 training client 与某一训练 run 对应、sampling client 与某一 LoRA checkpoint 对应。设计含义是把可变训练状态和不可混淆的采样版本分开。这里根据讲义解释 API 思想，不提供未核实的当前产品参数。

### 18.4 多租户的一致性清单

共享底座不意味着共享用户状态。adapter ID、版本、tokenizer、optimizer、数据队列与 cache key 都需要正确路由。误用另一个 adapter 的 KV，可能既影响数值正确性，也混淆不同任务的信息边界。验证时为两个 adapter 设计明显不同的固定输入，检查切换、缓存和恢复是否对应正确版本。

## 19. 从空系统到可信实验：一条最小实施顺序

以下是本讲内容导出的工程步骤，不是某个框架的安装教程。

1. 固定模型、tokenizer、renderer、任务镜像与 reward 协议，保存可检索的版本清单。
2. 用固定策略跑单轨迹，记录原 token、工具观察、行为 logprob、mask 与结束原因。
3. 在同权重下跨引擎重放，比较 token 和 logprob；先解决边界差异。
4. 用小批完成一次更新，确认只有预期动作位置参与损失，检查归一化与梯度。
5. 同步新权重，确认所有推理 rank 的逻辑版本；检查旧 KV 处理。
6. 再加入多样本、连续批处理、packing、prefix sharing 等单项优化。
7. 基础同步系统稳定后，再加入异步队列、staleness 上限和混合版本记录。
8. 最后扩大环境并发、多策略和多租户，逐层做故障注入与恢复验证。

每层都要保留一个较慢但语义清楚的参考路径。例如 dense 独立样本训练可用于比较 tree sharing 的 loss 与梯度；同步固定策略可用于隔离异步修正问题。参考路径的意义是提供可解释基线，并非要求永远使用慢实现。

## 20. 指标与故障诊断：把系统错误和学习错误分开

讲义附页 p.43 给出 reward/pass@1、pass@k、entropy、importance ratio、grad norm、staleness、MFU 与阶段时间。指标应联合解释。

| 现象 | 优先假设 | 区分检查 |
|---|---|---|
| 同权重 ratio 已明显偏离 1 | token/模板/精度/路由不一致 | 固定原 token逐项消融 |
| 更新后 ratio 少量极值爆炸 | stale data、对齐错误或数值溢出 | 逐 token定位、分版本和角色分组 |
| reward 上升但未见题下降 | 过拟合、奖励利用或分布偏移 | 隔离评测、检查产物和判分证据 |
| pass@1 上升而 pass@k 下降 | 多样性可能减少 | 固定 k、采样和预算，检查分布 |
| entropy 近零 | 探索减少或 mask 口径错误 | 按模型 token统计，排除工具文本 |
| trainer 等待增加 | 生成/验证供给不足 | 分解 rollout、tool、reward、队列 |
| 队列变长、staleness 增长 | 生产过快或训练变慢 | 比较到达与消耗速率，限流 |
| prefix 命中率突然下降 | 版本切换或模板漂移 | 对比 token前缀和 cache key |
| tree sharing 加速但梯度变了 | mask、位置、分支权重错误 | 对照 dense loss/梯度 |
| GPU 利用率高但学得更慢 | 冗余 token或无效数据增加 | 按墙钟看 held-out质量与有效样本 |

### 20.1 MFU 不等于显存占用或 GPU busy

MFU 通常估计实际模型 FLOPs 相对峰值的比例，口径受是否计重算、稀疏专家与硬件峰值影响。显存使用高可以只是缓存多；GPU busy 高可以是在搬数据。记录定义，避免比较不同仪表盘的同名数字。

### 20.2 先按训练步，再按墙钟看曲线

按步曲线接近、按时间更快，支持系统加速而训练动态大体保留；按步退步、时间看似快，可能是数据旧、样本选择或有效 batch 改变。两种横轴都应报告，并注明 GPU 数、资源类型、生成长度和失败轨迹处理。

对 prefix sharing 等数值等价优化，还可先做确定性小批 loss/梯度比较；对 async 改变，轨迹分布本来就会变化，不能要求逐步完全一致，只能通过匹配协议与重复实验判断质量和稳定性。

## 21. 三个实际执行的离线检查

以下只检查公式与数据契约，已在本地 Python 执行，无 GPU、无模型、无训练。

```python
# 1. KV 容量：教学结构参数
per_token = 2 * 32 * 8 * 128 * 2
assert per_token == 128 * 1024
assert per_token * 32768 == 4 * 1024**3

# 2. 字符串往返可改变 token 分段（构造 tokenizer）
decode = {41: "a", 52: "b", 99: "ab"}
original = [41, 52]
text = "".join(decode[t] for t in original)
encoded = [99] if text == "ab" else []
assert encoded != original

# 3. mask 仅把动作纳入直接策略损失
roles = ["task", "action", "observation", "action"]
mask = [int(role == "action") for role in roles]
assert mask == [0, 1, 0, 1]
assert len(mask) == len(roles)
```

第二项是反例构造，证明“相同文本不足以保证相同 token 序列”在逻辑上可能发生；它没有验证任何指定真实 tokenizer 的具体行为。第三项仅演示角色 mask，不验证 Transformer 反向。要验证真实系统，仍需固定 tokenizer、引擎和样本运行跨引擎概率与梯度对照。

14. 如何区分“系统吞吐改善”与“同预算学得更好”？

### 参考答案

1. 推理通常不保留可反传计算图；训练需对当前训练参数重算可求导概率，并保持原输入与算法版本语义。
2. 不够保证。还需模型权重、碎片、激活、通信和调度缓冲；256 GiB 仅是该教学 KV 项。
3. 不能无条件复用，KV 依赖权重；需要失效、重建或有明确正确性依据的转换。
4. 不自动。它减少空槽并提高吞吐，调度与长 prefill 仍可能增加等待。
5. 接受部分已贡献 $\min(p,q)$ 的概率质量，残差补齐剩余，才能恢复目标分布。
6. 不能。它们作为上下文影响动作概率，仍需条件计算并可能获得间接梯度。
7. 分支注意力隔离、位置 ID、原损失与归一化、公共前缀梯度汇总。
8. 不能。它是特定训练吞吐最大值；v2 端到端实验另有 1.28/2.28 倍及 GPU 重新分配条件。
9. 先查 token、模板、版本、采样设置、数值和 MoE 路由；无更新也不一致时不能首先怪优化步幅。
10. 按真实上下文断点拆样本，保留压缩前后输入、动作 mask与对应优势，不能虚构未曾看到的长前缀。
11. 不够。需分段或逐 token行为版本和概率，配合算法处理混合策略。
12. 不意味着。聚合吞吐和单租户响应时间是不同指标，还需看公平性和尾延迟。
13. 可能缺 token、logprob、路由、版本、任务关联或 reward语义；请求兼容不等于训练协议完整。
14. 同时看每步质量、墙钟质量、资源、有效样本与独立评测；只报 tokens/s无法回答学习效率。
