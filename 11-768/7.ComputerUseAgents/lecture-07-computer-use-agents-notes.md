## 一、总地图：把讲义与论文连成一条问题链

### 1.1 这些论文并不都在研究同一个层次

讨论 CUA 时，一个常见问题是把数据集、评测环境、基础模型、执行框架和多 Agent 系统统称为“Agent 框架”。这样很容易记住很多名字，却不知道它们各自改变了什么。

更有效的分类如下。

| 研究层次 | 对应材料 | 核心问题 |
|---|---|---|
| 决策与交互循环 | WebShop、ReAct | 理解组合需求、探索候选、跟踪进度，怎样决定下一步？ |
| 离线数据与泛化 | Mind2Web | 面对新的任务、网站和领域，能否选对元素与操作？ |
| 功能性端到端评测 | WebArena、OSWorld | 模型自己执行后，环境是否真的达到目标状态？ |
| 视觉理解与精确定位 | VisualWebArena、ScreenSpot-Pro | 看懂目标与准确找到操作位置，分别需要什么能力？ |
| 真实在线环境 | WebVoyager | 页面、内容和外部服务变化后，如何执行与评判？ |
| 模型与示范训练 | OpenCUA、MolmoWeb | 怎样把人的操作、教师轨迹和视觉信息变成有效监督？ |
| 训练任务与环境基础设施 | CUA-Gym、Gym-Anything | 怎样规模化提供可运行、可重置、可验证的任务？ |
| 长任务执行与协调 | MACU、Gym-Anything | 怎样重规划、交接证据、发现遗漏并有效分配计算？ |

这不是严格按发表时间排列的“后一篇取代前一篇”，而是围绕不同瓶颈组织的学习路线。多项工作在时间上重叠，解决的问题也互相独立。[L07，PDF 第17–18、59、75页](#s-l07)

### 1.2 贯穿这些材料的六个问题

可以用下面这条问题链理解整门课：

```text
用户想完成什么？
    ↓
当前界面中，哪些信息与目标有关？
    ↓
下一步应该做什么，具体操作哪个对象？
    ↓
动作是否真正生效，环境发生了什么变化？
    ↓
现在是否满足全部目标，而且没有违反约束？
    ↓
怎样把成功、失败与恢复经验变成下一次的能力？
```

WebShop 主要暴露需求理解与探索问题；Mind2Web 暴露复杂页面中的选择和泛化问题；WebArena 与 OSWorld 强调真实执行结果；OpenCUA 和 MolmoWeb研究如何训练；CUA-Gym 和 Gym-Anything研究如何制造学习所需的世界；MACU研究怎样把复杂工作重新组织起来。

**这些关系比各篇论文的排行榜名次更值得记住。**

### 1.4 一个贯穿全文的任务

OSWorld 提供过这样的任务：根据指定文件夹中的近期交易材料，更新记账表。它不仅包含鼠标操作，还涉及识别文件、读取信息、理解表格、修改数据和验证结果。[OSWorld，Figure 1–2，PDF 第2–4页](#s-os)

在后面的工程章节中，我们将它扩展为一个教学场景：**处理收据、更新账簿、保存新版本，并形成汇总草稿；不能覆盖原件，也不能对外发送。**其中“草稿”和禁止事项属于本文的工程示例，不是原论文同一任务的完整复述。

这个任务能把整门课串起来，因为它同时需要语言理解、视觉定位、跨应用状态管理、数值证据、结果验证与安全边界。

## 二、基本原理：CUA 是部分可观测环境中的闭环决策系统

### 2.1 先区分模型、执行基础设施和环境

Lecture-07 第3页的交互图包含三个部分：模型根据任务与观察提出动作；基础设施验证并执行动作；环境变化后返回新的截图观察。[L07，PDF 第2–8页](#s-l07)

```text
用户任务
   ↓
模型：理解目标、利用历史、提出下一步
   ↓
基础设施：校验动作、执行操作、记录结果
   ↓
环境：网页、桌面应用、文件、窗口与后台状态
   ↓
新的观察与证据
   └────────────→ 回到模型
```

因此，“模型输出了 `click(300, 540)`”只说明它提出了一次操作。它不证明点击已经执行，不证明点中了正确对象，也不证明用户目标已经完成。

这三个层次必须分开，否则调试时会把驱动程序、坐标映射、窗口状态、模型选择和业务判断全部混成一个错误。

### 2.2 状态不等于观察

OSWorld 将任务写成部分可观测马尔可夫决策过程，即 POMDP。这里最值得掌握的不是缩写，而是它背后的区分：[OSWorld，§2.1，PDF 第3页](#s-os)

| 符号 | 含义 | 记账任务中的例子 |
|---|---|---|
| $g$ | 用户目标 | 将本期收据正确写入指定账簿 |
| $s_t$ | 环境真实状态 | 文件内容、当前窗口、未保存修改、后台进程等 |
| $o_t$ | Agent 当前得到的观察 | 一张截图，或截图与可访问性树 |
| $a_t$ | 下一步动作 | 点击、输入、滚动、等待或结束 |
| $h_t$ | 历史 | 已有观察与动作，以及保留的任务信息 |
| $r$ | 评测或训练奖励 | 检查表格内容与任务条件后得到的分数 |

可以用下面的策略表达式概括模型的决策：

$$
a_t \sim \pi_\theta(a_t\mid g,o_0,a_0,\ldots,o_t).
$$

这个式子说明：模型不只需要“看当前屏幕”，还可能需要利用此前发生过什么。

例如，当前截图显示一个表格，但无法单凭这张图知道：刚才输入的内容是否保存到磁盘，另一个窗口的下载是否完成，当前金额是否属于本期，或者用户是否授权覆盖原文件。

**教学推导**：多模态模型可以把截图读得很清楚，却仍然对真实环境状态缺乏足够信息。继续推理不能替代补充观察；“不知道是否保存”通常需要检查保存状态或文件，而不是再写一段更长的解释。

### 2.3 CUA 的动作不只是鼠标点击

OSWorld 的动作包括点击、移动、拖拽、输入、按键、组合键、滚动，以及 `WAIT`、`FAIL`、`DONE`。它使用基于 PyAutoGUI 的表达方式，允许组合低层操作。[OSWorld，§2.4，PDF 第6页](#s-os)

不同动作改变环境的方式不同。点击菜单可能只是改变界面；输入可能改变文档但尚未保存；保存会改变文件；发送或提交则可能改变远端系统。

**工程建议**：动作协议除了描述“做什么”，还应该描述“基于哪次观察”“作用于哪个环境”“可能造成什么副作用”。这些是执行系统需要维护的元数据，不必全部交给模型自由生成。

### 2.4 动作正确、结果正确、过程正确，不是同一件事

Lecture-07 第17页将成功拆为三个层次：Action、Outcome、Process。[L07，PDF 第17、19、25、39页](#s-l07)

以“把一个低于20美元的蓝杯加入购物车，不要购买”为例：

**动作正确**：确实点击了正确杯子的入口。  
**结果正确**：购物车中确实有指定商品，数量和价格符合要求。  
**过程正确**：没有下单，也没有造成其他不允许的修改。

一个系统可能全部点击都符合局部预期，却在最后错误地下单；也可能采用与示范不同的操作路径，但完整满足用户目标。

因此，不能将“动作匹配参考答案”当作全部正确性，也不能将“最终文件存在”当作任务完成。

### 2.5 对 LLM 工程师意味着什么

你熟悉的工具调用中，接口往往已经封装了业务对象与参数。CUA 的不少接口只提供鼠标、键盘与截图，模型需要自己从环境里发现对象、前置条件和操作结果。

**教学解释**：工具调用是在一个已经命名好的操作空间中决策；GUI 操作往往还要先解决“这个空间里有哪些对象、它们在哪里、现在能不能操作”。这不是对所有工具和 GUI 的绝对划分，而是理解两类接口差异的方式。

从这里开始，你应当把 CUA 当作“模型与环境共同组成的执行系统”，而不是给聊天模型额外加一个鼠标工具。

## 三、WebShop 与 ReAct：先学会做决策，再谈精确控制

### 3.1 WebShop 为什么重要：它简化控制，却保留语义决策

WebShop 是包含真实商品信息的模拟购物环境。用户提出颜色、尺寸、用途、价格等组合需求；Agent 需要搜索、阅读商品、比较候选、选择规格，并结束购买流程。[WebShop，§1、§3，PDF 第1–5页](#s-ws)

但是，原论文模型主要使用简化页面表示和语义动作，并不是每一步都从截图预测鼠标坐标：

```text
search[portable folding desk]
choose[某个商品]
choose[khaki]
choose[Buy]
```

环境包含搜索页、结果页、商品页和详情页。人在 HTML 模式中操作，论文模型在 simple mode 中训练和评估。[WebShop，§3.1、Table 1，PDF 第4页](#s-ws)

这一设计把“鼠标点不准”的因素尽量移开，使研究可以聚焦于：用户到底要什么、需要继续搜索吗、候选商品满足全部要求了吗、现在应该购买还是回退。

**工程建议**：开发复杂 Agent 时，可以先通过稳定的语义接口验证任务理解与计划，再把执行环节换成 GUI，分别测量新增错误。否则，语义、视觉、时序与底层控制一起失败，很难定位问题。

### 3.2 WebShop 的奖励不是匹配唯一商品 ID

设用户要求的属性为 $U_{att}$，规格为 $U_{opt}$，价格上限为 $u_{price}$；选中商品对应信息为 $Y_{att}$、$Y_{opt}$、$y_{price}$。论文的奖励是：

$$
r=r_{type}\cdot
\frac{|U_{att}\cap Y_{att}|+|U_{opt}\cap Y_{opt}|+\mathbf 1[y_{price}\leq u_{price}]}
{|U_{att}|+|U_{opt}|+1}.
$$

其中 $r_{type}$ 用于降低“属性相似但商品类型明显不对”的奖励。不同商品只要都满足需求，就可能获得满分。[WebShop，式(1)、评价指标，PDF 第5页](#s-ws)

论文同时报告两种指标：Task Score 是平均奖励乘以100；Success Rate 则只有奖励等于1才计为成功。

这一区分非常接近真实工作中的“局部正确”和“能够交付”。一篇报告中大部分数字正确，不代表它已经满足所有交付要求。

### 3.3 一个值得记住的实验：平均得分上升，完整成功率没有上升

| 方法 | Task Score | Success Rate |
|---|---:|---:|
| 模仿学习 IL | 59.9 | 29.1% |
| IL 后继续强化学习 | 62.4 | 28.7% |

强化学习提高了平均奖励，但严格成功率略降。论文的轨迹分析显示，RL 后的策略更“贪心”，探索商品和重新搜索更少；属性、类型和价格得分上升，但规格选择得分下降。[WebShop，§5.2–5.3、Figure 4、Table 2，PDF 第7–9页](#s-ws)

这不是“RL 不如 SFT”的普遍结论。它说明：**优化什么奖励，可能改变探索与完成方式；平均奖励与完整成功率并不自动一致。**

原论文还将搜索与选择拆开：通过一个能够查看隐藏奖励并穷举候选与规格的 Choice oracle，成功率大幅提高。这有助于定位瓶颈在“怎样选择与探索”，但这个 oracle 拥有普通 Agent 没有的能力，不能把它当成可部署方法。[WebShop，§5.3，PDF 第9页](#s-ws)

### 3.4 WebShop 的模型也不是现代统一大模型策略

其基线用 BART 学习搜索词生成，用 BERT 等组件进行候选动作选择，并结合商品图像特征；在进一步 RL 时，搜索模型的输出被用于构造受限候选空间。[WebShop，§4.2–4.3、Figure 3，PDF 第6–7页](#s-ws)

这有两个阅读意义。第一，不应把这些结果直接当作现代端到端 VLM 的能力。第二，它已经体现了“将生成搜索与选择动作分解处理”的方法思想，后面 MINDACT 的候选检索也有类似的结构化取舍。

### 3.5 ReAct：推理的作用，是重组决策所需的信息

ReAct 把环境动作空间 $A$ 扩展为：

$$
\hat A=A\cup L,
$$

其中 $L$ 是语言空间。环境动作改变外部状态；语言推理不直接改变外部环境，而是更新模型上下文，帮助后续判断。[ReAct，§2，PDF 第3–4页](#s-ra)

在购物中，有用的推理可能是：

> 这个商品满足颜色和价格，但尺寸不符合；不能购买，需要查看其他规格或重新搜索。

这不是把屏幕上的文字重复一遍，而是完成三件事：抽取用户约束、比较当前证据、决定下一步。

ReAct 的思想是双向的：**Reason to act**，用推理指导行动；**Act to reason**，通过行动获取原本缺失的信息。

### 3.6 ReAct 不要求每一步都写长推理

论文对较长的决策任务使用稀疏、灵活的推理，让推理出现在需要分解目标、更新进度、调用常识或处理异常的地方，而不是机械地在每次点击前生成同样长度的说明。[ReAct，§2、§4，PDF 第3–4、7–8页](#s-ra)

这与讲义最后“关键决策时推理，常规操作时减少开销”的方向相连，但不是说所有模型都可以在不训练、不评测的情况下直接删掉推理。

### 3.7 应当怎样解读 ReAct 的实验

在 WebShop 上，论文报告 Act-only 的成功率为30.1%，ReAct 为40.0%；相应得分为62.3和66.6。作者认为，推理帮助模型把嘈杂的商品描述与用户需求、规格选择连接起来。[ReAct，Table 4、§4，PDF 第8页](#s-ra)

更有解释力的比较是 **Act 与 ReAct**。拿 ReAct 与更早的 IL/RL 模型比较，还同时改变了基础模型、预训练能力和参数规模，不能由此推出“Prompt 普遍比训练更好”。

### 3.8 连接下一组论文

WebShop 告诉我们：即使操作接口已经很简单，探索与决策仍然困难。ReAct 告诉我们：通过推理整理约束、进度和异常，可以改善决策。

接下来要问的是：当页面从几个语义按钮变成上千个元素，当前一步错误会改变下一步输入时，这套方法还能否可靠运行？

这正是 Mind2Web、WebArena 与视觉类工作的切入点。

## 四、评测：从预测一步到验证整个工作流

### 4.1 先分清三类正确性、四种评测场景

Lecture-07 一方面区分动作、结果和过程正确性，另一方面区分静态评测、网页端到端评测、桌面/移动端评测，以及长任务评测。[L07，PDF 第17–19、34、38页](#s-l07)

| 场景 | 主要测什么 | 代表材料 | 不能直接说明什么 |
|---|---|---|---|
| 静态 grounding | 固定截图上能否定位目标 | ScreenSpot-Pro | 不能直接说明长任务执行能力 |
| 离线动作预测 | 给定记录状态与历史，下一步是否正确 | Mind2Web | 不能直接说明错误状态中的恢复能力 |
| 自托管网页端到端 | Agent 自己操作后，功能是否实现 | WebArena、VisualWebArena | 不等于覆盖真实网络与登录异常 |
| 真实网页端到端 | 在在线网站上执行并提供证据 | WebVoyager | 难以保证环境不变、结果完全复现 |
| 桌面端到端 | 跨窗口、文件和应用完成任务 | OSWorld | 单一任务集合不代表全部专业软件 |
| 长任务与职业工作流 | 持续完成多个约束与交付物 | Gym-Anything、MACU 中的长任务评测 | 更高部分得分不等于完整交付 |

### 4.2 Mind2Web：真实网站数据，不等于在线执行评测

Mind2Web 收集2,350个任务，覆盖137个网站、31个领域。它保存网页快照和人工操作轨迹，并分别测试跨任务、跨网站、跨领域泛化。[Mind2Web，§2、Table 1，PDF 第3–5页](#s-m2w)

原始评测中，每一步独立计算，并提供真实示范中的历史动作。只有目标元素与操作都正确，这一步才成功；记录中的全部步骤正确，任务才被记为成功。[Mind2Web，§4.2，PDF 第7页](#s-m2w)

这主要回答：

> 在人类正确执行经过的这些状态上，模型能否预测对应动作？

在线执行回答的是：

> 在模型自己操作产生的状态上，它能否继续推进任务？

**教学解释**：离线样本可能直接给出已经打开的日期筛选面板；在线模型的前一步可能根本没有打开面板。后续观察已经变了，错误并不是独立丢掉一分，而是在改写后续输入。

因此，离线数据很适合研究定位、动作语义与跨站泛化，但不能代替实际 rollout。反过来，端到端失败又很难定位原因，所以两种评测需要互补，而不是相互取代。

### 4.3 WebArena：用功能结果允许多条正确路径

WebArena 提供812个任务，核心网站来自四类常见领域，并配有地图、知识资源等辅助站点。自托管设计用于减少内容变化等因素对重复实验的干扰。[WebArena，§1–2，PDF 第2–4页](#s-wa)

论文第3页的 Figure 2 展示了一条跨站任务：寻找匹兹堡艺术博物馆，在地图上整理路线，再把结果写入 GitLab 仓库。

不同 Agent 可以先查不同博物馆、采用不同导航路径，只要最终结果符合要求，就不应因为没有模仿同一条示范而被判错。这正是 functional correctness 的意义。

### 4.4 WebArena 的验证并非全部是完全确定的程序检查

信息查询任务包括 exact match、必须包含的内容，以及 LLM 语义匹配。内容和配置修改任务，则可以通过数据库查询、网站 API 或页面元素定位获取结果，再检查目标条件。[WebArena，§3.2，PDF 第6–7页](#s-wa)

因此，“execution-based evaluation”意味着检查执行产生的效果，但不自动等于“整个评判链条不存在模型误差”。要继续追问：获取了什么状态，检查了哪些字段，哪些条件仍然靠语言模型判断？

### 4.5 无法完成的任务，也需要评测

WebArena 包含缺少信息、权限或网站功能的不可完成任务。一个可靠 Agent 不应该为了返回答案而编造事实，但也不应该因为第一次搜索失败就放弃。[WebArena，§3.2，PDF 第7页](#s-wa)

论文的一个实验很有启发：加入“认为任务不可完成就停止”的提示后，GPT-4 在该设置下将54.9%的可完成任务误判为不可完成。移除这条提示，整体成功率从11.70%提高到14.41%，但不可完成任务的识别表现下降。[WebArena，Table 2、§5.1，PDF 第8页](#s-wa)

**工程建议**：至少区分“暂未找到”“当前路线失败”“权限阻断”“信息不足”“经过必要检查后确认不可行”。它们不能全部压缩成一个 `FAIL`，也不能都转成“继续无限重试”。

### 4.6 评测漏洞为什么会影响训练方向

Lecture-07 第27页展示一个简化的空仓库任务验证器：检查目标 URL 的页面中是否存在仓库名，却没有检查仓库是否为空。[L07，PDF 第27页](#s-l07)

**教学推导**：当这样的验证器被当作 RL 奖励时，策略受到的训练信号是“满足这个检查”，而不是自动满足未被编码的“空仓库”要求。

这不是说该例证明某个 Agent 已经学会投机，而是说明：**验证器遗漏的条件，也会成为训练目标遗漏的条件。**后面 CUA-Gym 的独立奖励编写与反投机检查，正是在处理这种风险。

### 4.7 WebVoyager：真实性上升，复现与判断更困难

WebVoyager 直接访问在线网站，通过 Selenium 执行动作，以带编号的截图、辅助文本和历史为输入。原始系统的交互限制在当前标签页，所选评测站点回避了必须登录或通过 CAPTCHA 才能访问内容的情况。[WebVoyager，§3–4，PDF 第3–5页](#s-wv)

这为“真实在线网页”提供了重要测试，但不能据此认为复杂登录、多账号、多标签和所有真实业务写操作均已被覆盖。

其基准包含643个任务、15个网站。主结果采用人工判断，报告59.1%的任务成功率；自动评判设置与数值应另行标注，不要混用。[WebVoyager，Table 1，PDF 第7页](#s-wv)

### 4.8 评判器质量，本身就是实验对象

WebVoyager 研究 GPT-4V 判断是否完成任务，与人工评价的一致程度。

| 评判器拿到的截图 | 与人工的一致率 | Cohen's κ |
|---|---:|---:|
| 最后一张 | 75.3% | 0.51 |
| 最后两张 | 79.7% | 0.59 |
| 最后三张 | 81.3% | 0.62 |
| 完整轨迹截图 | 85.3% | 0.70 |

来源：[WebVoyager，Table 2，PDF 第7页](#s-wv)。

这说明，完成状态未必能够从最后一张截图充分判断，更多过程证据可以帮助审计。但一致率不是绝对正确率，也不说明所有误判的后果相同。

**工程建议**：单独统计“未完成却判完成”和“已完成却判未完成”。前者造成错误交付；后者造成额外重试和成本。一个总一致率会掩盖这种差别。

### 4.9 OSWorld：把浏览器问题扩展成整个电脑的状态问题

OSWorld 不只增加了软件数量，还增加了窗口、文件、剪贴板、应用配置与跨应用交接。原论文主基准是369个 Ubuntu 任务，另提供43个 Windows 任务。环境支持多个操作系统，不代表同一任务集已在所有系统上进行同口径测量。[OSWorld，§3，PDF 第6页](#s-os)

第4页 Figure 2 展示了完整生命周期：

```text
任务配置
  → 启动与初始化环境
  → 准备文件、窗口和应用状态
  → Agent 实际执行
  → 后处理与获取产物
  → 按任务规则检查文件或应用状态
```

例如，记账任务不应该只看最后一张表格截图，而应读取保存后的工作簿，检查金额、标签、余额，以及原有区域是否保持不变。[OSWorld，Figure 2、Table 1，PDF 第4–5页；L07，PDF 第36页](#s-os)

**工程建议**：评测的可复现单位不是一个 Prompt，而是任务、初始环境、执行接口、验证器及其版本组成的整体。

### 4.10 长任务：部分完成度与完整完成率必须同时报告

Lecture-07 第41页给出一个行程规划示例：8项条件完成7项，平均完成度是0.875，但“全部完成”仍为0。[L07，PDF 第40–41页](#s-l07)

部分分数能区分“完全没做”和“只差一项”，适合分析学习进展；完整完成率反映能否按完整要求交付。两者回答不同问题，不能择其好看的一项报告。

讲义还介绍了 Online-Mind2Web、WindowsAgentArena、Odysseys、OSWorld 2.0，以及移动端相关评测。本文没有获得这些工作的全部对应原论文，因此只保留它们在课程中的定位：在线环境漂移、Windows 环境规模化、长链路约束与更复杂的个人工作状态，不从讲义条目扩写完整技术方案。[L07，PDF 第18–19、32、37、40–45页及附录](#s-l07)

### 4.11 阅读任何分数时，都要附上实验条件

最少需要一起记录：**任务集合和版本、观测接口、动作接口、基础模型与执行框架、步数和成本预算、重复次数，以及验证方式。**

Mind2Web 的独立动作匹配、WebVoyager 的真实网页评判、OSWorld 的执行检查，测量的对象不同。原始 OSWorld 基线的15步限制，与 OpenCUA 后来报告的15/50/100步设置，也不能直接忽略。[Mind2Web，§4.2，PDF 第7页；OSWorld，§4.1，PDF 第10页；OpenCUA，Table 3，PDF 第10页](#s-m2w)

**没有实验条件的百分比，不足以成为工程选型依据。**

## 五、界面建模：DOM、可访问性树、截图与精确定位

### 5.1 同一个界面，可以被表示成不同的信息空间

WebArena 支持 HTML DOM、截图、可访问性树等观测形式。DOM 包含网页结构；可访问性树提供角色、文本、属性等更紧凑的信息；截图保留渲染后的视觉布局。[WebArena，§2.3、Figure 3，PDF 第4页](#s-wa)

| 表示 | 能直接提供什么 | 需要警惕什么 |
|---|---|---|
| HTML / DOM | 元素结构、属性、文本和层次关系 | 大量冗余、动态结构，以及与实际可操作界面之间的差异 |
| 可访问性树 | 角色、可访问名称、状态等语义信息 | 依赖应用提供的结构，不必然完整表达视觉内容 |
| 原始截图 | 布局、颜色、图像、弹窗、窗口位置 | 小字、细小控件、精确坐标与视觉上下文成本 |
| 截图 + SoM | 视觉场景及带编号的可操作候选 | 上游标记质量、遮挡噪声、遗漏元素与编号时效 |
| 混合表示 | 同时利用结构化语义与视觉证据 | 不一致信息、重复输入、更多成本和更复杂的接口 |

表中的风险是结合论文方法与分析得到的工程归纳。它不意味着某一种表示在所有模型上都更好。

**关键选择不是“哪种输入更高级”，而是“这项任务的决定性信息，在哪一种表示里最容易被可靠读取”。**

### 5.2 MINDACT：用候选检索降低复杂页面的决策负担

Mind2Web 的原始页面平均包含约1,135个元素。MINDACT 采用两阶段方案，而不是把所有 HTML 直接交给大模型。[Mind2Web，Table 1、§3，PDF 第5–6页](#s-m2w)

```text
任务描述 + 历史动作
          ↓
小型 cross-encoder 对页面元素打分
          ↓
保留 Top-k 候选及邻近结构
          ↓
大模型选择目标元素
          ↓
生成操作类型和必要输入值
```

第一阶段将任务及历史作为 query，把元素标签、文字、关键属性和父子节点信息作为 candidate representation。第二阶段将元素选择改成多选题，同时生成操作和值。实现中，每组包含五个候选和一个 None 选项，通过多轮选择缩小候选集合。[Mind2Web，Figure 3–5、§3.1–3.2，PDF 第6页](#s-m2w)

对熟悉 RAG 的开发者来说，这可以类比“召回—精排—生成”，但被召回的是可操作对象，而不是知识文档。这个类比帮助理解结构，不意味着两者的评测目标相同。

### 5.3 候选过滤决定了后续模型能看到什么

MINDACT 的候选模型在跨任务、跨网站、跨领域设置中，Recall@50 分别为88.9%、85.3%、85.7%。[Mind2Web，§4.3，PDF 第7页](#s-m2w)

**教学推导**：在“后续模型只能从候选中选择，而且不存在回退接口”的前提下：

$$
P(\text{目标选择正确})\leq P(\text{正确目标进入候选集}).
$$

因此，一次失败至少可能来自三个地方：原始页面预处理就删除了目标；检索没召回目标；目标进入候选后，大模型仍然选错。

只优化最后一步 Prompt，无法修复前两种问题。

**工程建议**：把预处理保留率、候选召回率、候选内选择准确率、操作和值的正确率分别测量。候选为空或低置信时，允许重新检索、扩大范围或切换观察，而不是强迫模型从错误集合中选一个。

### 5.4 VisualWebArena：看懂内容与准确点击，属于两个能力

VisualWebArena 的910个任务全部要求视觉理解，其中25.2%还包含用户输入图片。这不是“只有25.2%的任务需要视觉”。[VisualWebArena，§1，PDF 第1页](#s-vwa)

例如，判断图片中的衣服是什么颜色，属于内容理解；找到对应商品旁边的正确入口，属于界面对象绑定；最终让鼠标点击到该入口，属于低层定位与控制。

这几层可以分别出错：模型可能认对商品却点到旁边；也可能精确点击了一个按钮，却选中了不符合用户要求的商品。

**看图问答强，并不能单独证明 GUI 执行强。**

### 5.5 SoM：把坐标预测转换为带视觉信息的候选选择

VisualWebArena 用 JavaScript 给可交互元素添加边框与唯一编号，模型选择编号，执行层将编号映射到目标。它的 Figure 2 展示了这种视觉—动作绑定。[VisualWebArena，§3.1–3.2、Figure 2，PDF 第3–4页](#s-vwa)

```text
截图：目标商品旁边标记为 31
模型：click [31]
执行层：将当前观察中的 31 映射到对应元素并执行
```

这降低了模型直接预测精确坐标的负担。但必须注意，候选元素由网页结构与 JavaScript 提取提供，并不是基础 VLM 自己从纯像素中检测出了全部控件。

因此，SoM 系统的表现包含模型、元素提取、标记和执行映射共同带来的贡献。

### 5.6 VisualWebArena 的实验支持什么、不支持什么

| 输入与模型组合 | 总体任务成功率 |
|---|---:|
| GPT-4，文本可访问性树 | 7.25% |
| GPT-4，可访问性树 + 图片描述 | 12.75% |
| GPT-4V，截图 + 图片描述 + 可访问性树 | 15.05% |
| GPT-4V，截图 + 图片描述 + SoM | 16.37% |

来源：[VisualWebArena，Table 3，PDF 第8页](#s-vwa)。

这说明在这些设置下，视觉信息与视觉—动作绑定有所帮助。它不证明任何 VLM 加上 SoM 都会提高表现；原论文中其他模型没有一致收益。也不能把后两行叫作“纯像素输入”，因为它们仍包含辅助信息。[VisualWebArena，§6，PDF 第8页](#s-vwa)

**教学解释**：Caption 是一种有损压缩。将图片概括为一句话，可能省下上下文，却遗漏领口、图案、相邻对象等决定任务答案的细节。问题不只是“是否用了视觉”，还包括视觉信息经过哪些压缩之后才到达决策模型。

### 5.7 为什么在桌面软件中，SoM 不一定继续有效

OSWorld 的分析发现，SoM 和可访问性树的效果随模型变化。桌面界面可能包含大量细小元素，例如表格单元格；大量标框会增加噪声。有些操作还需要区域级、坐标级控制，不适合用一个元素框表达。[OSWorld，§4.2，PDF 第11–12页](#s-os)

所以，Web 任务中的有效设计，不能不经测试就迁移到桌面专业软件。界面密度、操作粒度、元素提取质量和模型训练分布都发生了变化。

### 5.8 ScreenSpot-Pro：让精确定位成为独立研究问题

ScreenSpot-Pro 收集1,581个指令—截图样本，覆盖23个应用和3个操作系统。它关注高分辨率专业软件中的细小目标，目标平均面积约占截图的0.07%，而原 ScreenSpot 的相应比例约为2.01%。[ScreenSpot-Pro，§1、§3.4，PDF 第1–2、5页](#s-ssp)

一个模型可能知道“导出入口通常在文件菜单”，却无法直接在高分辨率界面中给出可点击的准确位置。把整张截图缩小之后，关键控件还可能失去足够像素。

这就是为什么“理解任务”与“定位到可操作位置”需要分别测量。

### 5.9 ScreenSeekeR：不是盲目放大，而是利用界面结构进行搜索

ScreenSeekeR 的思路是利用 GUI 的层次结构：窗口、面板、菜单、工具栏之间有组织关系；相邻控件也提供定位线索。[ScreenSpot-Pro，§4.2，PDF 第5–6页](#s-ssp)

```text
理解目标操作
  → 推测目标所在窗口或区域
  → 利用附近控件生成候选区域
  → 扩张、评分、去除重复区域
  → 递归裁剪与搜索
  → 在合适范围内精确定位并检查
```

例如，“删除”可能位于文件管理器顶部工具栏，附近有“新建”“复制”等控件。目标本身不清楚时，所在区域和邻居仍能提供线索。

论文第6页 Figure 4 中，简单定位与 ReGround 被后台的 VS Code 窗口误导；ScreenSeekeR 则先找到前景文件管理器，再搜索顶部操作栏。[ScreenSpot-Pro，Figure 4、§5.3，PDF 第6、8页](#s-ssp)

**教学解释**：放大错误位置，只会更清楚地看到错误对象。区域选择与区域内精度是不同瓶颈。

### 5.10 消融实验：先做简单改进，再判断复杂度是否值得

使用同一个 OS-Atlas-7B grounding 模型：

| 方法 | 定位准确率 |
|---|---:|
| 直接定位 | 18.9% |
| ReGround：围绕初次预测裁剪后重新定位 | 40.2% |
| ScreenSeekeR 移除后续递归搜索 | 41.9% |
| 完整 ScreenSeekeR | 48.1% |

来源：[ScreenSpot-Pro，Table 4，PDF 第8页](#s-ssp)。

简单局部重定位已经提供较大收益；结构化、递归搜索进一步改善。完整方法不需要额外训练，但需要额外规划与模型调用，不能理解为“无成本提升”。不同模型的最佳裁剪范围也不同。[ScreenSpot-Pro，Table 5、§5.3，PDF 第8页](#s-ssp)

**工程建议**：先检查截图缩放、窗口选择与局部重定位，再决定是否引入复杂多模型搜索。使用消融测试衡量增益，不要仅凭方法名字更复杂就采用。

### 5.11 MINDACT 与 ScreenSeekeR 的统一理解

MINDACT 在结构化页面中选择候选元素；ScreenSeekeR 在图像中选择候选区域。两者都在做一件事：**从完整界面中筛出与当前动作有关的信息。**

收益是降低推理和定位负担；风险是把决定性信息提前筛掉。

**工程推论**：感知预处理不是中性的管道，它实际上参与了决策。模型只能在预处理保留下来的世界里行动。

## 六、OpenCUA：从人类操作到可学习的状态、动作与反思

### 6.1 讲义的统一模型图，解决了什么抽象问题

Lecture-07 第47–56页逐步构造目标、截图与动作交错的历史，再将其表示为文本 Token 和视觉表示输入因果 Transformer，由模型生成下一步动作。视觉编码器与投影层将截图转成模型能够处理的表示；具体 Token 数和编码实现随系统变化。[L07，PDF 第47–56页](#s-l07)

这张图帮助我们理解策略接口，但并没有自动回答：历史应该保留多少、截图怎样对齐、错误轨迹怎样使用、动作输出应当多细、训练时需要哪些数据。

OpenCUA 的价值，正在于把这些细节拆开做实验。

### 6.2 OpenCUA 不只是一个模型，而是一套数据与训练方法

OpenCUA 包含人类操作采集工具、AgentNet 数据、轨迹处理与反思合成流程，以及训练后的模型。采集信息包括视频、鼠标键盘事件和可访问性树；执行策略则采用以截图为核心的视觉观察。[OpenCUA，Figure 2、§2，PDF 第2–4页](#s-oc)

阅读数字时还要区分公开数据规模与各模型实际使用的训练轨迹数量。论文给出的公开 AgentNet 任务数为22,625，但不同模型的训练轨迹池并不都等于这个数。[OpenCUA，Table 2及脚注，PDF 第5页](#s-oc)

**公开数据集规模、训练实例数、动作样本数和训练 Token 数，不是同一个计量单位。**

### 6.3 动作离散化：首先定义模型究竟在学习哪种操作

人的操作包含连续鼠标移动、逐字输入、重复滚轮事件和复杂组合键。如果原样输入训练，单个任务可能产生大量低层事件。

OpenCUA 将连续按键合并为文本输入，将修饰键组合抽象成 hotkey，合并同方向滚动，整理拖拽、双击等操作，形成更紧凑的状态—动作轨迹。[OpenCUA，§2.2，PDF 第4页](#s-oc)

这不仅是清洗数据，而是在确定动作粒度。动作太细会增加轨迹长度；动作太粗又可能跨越需要重新观察的状态变化。

**工程建议**：动作协议需要保持一致。例如“输入文本”究竟是追加还是先清空再输入，滚动是全页还是某个面板，必须明确。不同含义被混入同一个动作名，会使训练和执行同时变得不稳定。

### 6.4 状态—动作时间对齐：一个隐蔽的信息泄露来源

若截图取在点击前的瞬间，鼠标可能已经停在目标按钮上。模型可以跟随鼠标位置“猜”目标，而没有真正学习任务与控件之间的关系。

OpenCUA 为点击动作回溯到鼠标预移动阶段之前，寻找合适画面，从而减轻这种未来信息泄露。[OpenCUA，PDF 第5页](#s-oc)

**工程建议**：采集业务轨迹时，要检查输入画面是否已经包含目标动作留下的痕迹。例如，将已填写的输入框当成“填写前观察”，或者把动作后的选中高亮配到动作前标签，都可能让训练得到虚假的高准确率。

### 6.5 为什么不能只保留完美轨迹

Mind2Web 对记录动作进行了清理，去掉多余步骤；OpenCUA 则强调，人类示范中的错误可以提供发现问题与恢复的信息，但需要识别和处理。[Mind2Web，任务验证，PDF 第5页](#s-m2w)；[OpenCUA，§2.2、§3.1，PDF 第4、6页](#s-oc)

OpenCUA 的 Reflector 会对比动作前后的截图，检查动作及说明是否正确、有效或冗余。错误或冗余步骤可以不作为训练目标；正确步骤则保留其带来的状态变化说明，并帮助后续生成反思与计划。[OpenCUA，Figure 5、§3.1，PDF 第6页](#s-oc)

因此，应当区分：

> 把错误动作作为应模仿的答案。  
> 把错误及其后果作为上下文，学习后续识别与恢复。

两者完全不同。**训练恢复能力，不等于训练模型重复错误。**

### 6.6 推理监督要教“状态变化”，而不只是解释动作

有用的反思是：

> 上一步点击后，预期面板没有打开，活动窗口反而变化了；需要重新定位目标窗口。

较弱的事后说明是：

> 我要点击这个按钮，因为需要点击它。

OpenCUA 的反思合成包含状态转移、记忆、计划和纠错。它试图使推理与真实观察、实际动作对齐，而不只是为已有动作配一段合理化文字。[OpenCUA，§3.1、Figure 5–6，PDF 第5–6页](#s-oc)

**教学提醒**：生成出来的推理说明仍然是训练标签，不是人类真实思维过程的直接记录，也不是模型已经正确理解环境的证明。它需要一致性与有效性检查。

### 6.7 L1、L2、L3：当前决策与历史表示要分别设计

| 格式 | 内容 |
|---|---|
| L1 | Action |
| L2 | Thought + Action |
| L3 | Observation + Thought + Action |

OpenCUA 混合这些格式训练。当前推理时采用 L2；历史步骤则倾向于保留更简洁的 L1 动作信息，并结合适量历史截图。[OpenCUA，§3.2–3.3，PDF 第7页](#s-oc)

一个简化的 SFT 目标可以写为：

$$
\mathcal L_{SFT}=-\sum_t\log P_\theta(z_t,a_t\mid g,h_t),
$$

其中 $z_t$ 表示训练样本中的推理说明，$a_t$ 表示动作。这是帮助理解的教学表达，不代表所有模型和训练阶段采用完全相同的损失或格式。

关键不是公式本身，而是条件输入和标签是否因果对齐、与任务相关、可被部署模型实际观察到。

### 6.8 关键消融：不是推理越长、历史越多就越好

论文 Table 6 的几组实验分别显示：

| 被比较的设计 | 结果 | 应当如何理解 |
|---|---|---|
| 只用 L2 训练 / 混合格式训练 | 13.1% / 18.5% | 最佳推理格式不必等于唯一最佳训练格式 |
| 短推理 / 反思增强推理 | 11.5% / 15.3% | 与状态变化和纠错相关的推理有价值 |
| 推理时使用 L1 / L2 / L3 | 16.9% / 18.5% / 17.6% | 更多截图描述并不必然更有效 |

来源：[OpenCUA，§5、Table 6，PDF 第13–14页](#s-oc)。这些是不同消融条件下的比较，不能把每行当作同一模型连续升级的增量。

作者认为，L3 可能描述与当前任务无关的界面元素，反而干扰决策。这与 ReAct 的稀疏推理相呼应：有用的是与决策相关的信息处理，而不是文本长度。

### 6.9 视觉历史与文本历史，需要不同压缩策略

OpenCUA 的一个历史表示消融中，从1张增加到3张截图有明显收益；从3张增加到5张收益较小，却增加了上下文成本。相同3张截图条件下，更长的 L2 历史没有提供相应收益。[OpenCUA，Figure 10、§5，PDF 第13页](#s-oc)

这里最重要的结论是：

**当前步骤为了作决定，可能需要较充分的推理；历史中为了说明发生了什么，可能只需要简洁动作和关键视觉证据。**

不要将“保留最近3张截图”变成通用常数。它是论文在特定模型和数据上的选择。部署自己的任务时，应比较截图数、文本摘要形式、长任务成功率和成本。

### 6.10 混合训练的意义：grounding 是必要条件，但不是完整能力

OpenCUA 使用 GUI grounding、规划轨迹、通用文本与视觉数据等混合训练，并研究不同预算下的阶段式或联合训练方案。论文还观察到，部分模型在单独 grounding 上表现不差，端到端 OSWorld 表现却明显落后。[OpenCUA，§3.3、§4.2，PDF 第7–8、11页](#s-oc)

这说明精准定位和完整任务能力不是同一件事。会点按钮，仍然可能不会制定计划、处理异常、保存结果或决定何时结束。

### 6.11 与前面论文的连接

ReAct 说明推理可以改善单步决策与任务进度管理。OpenCUA 进一步问：如何把这些行为变成可训练的数据格式，并在视觉历史、动作粒度、反思质量和数据混合上实现稳定收益？

**它把“Agent 应该会反思”从一句系统提示，推进成了数据采集、标签构造和模型训练问题。**

## 七、MolmoWeb：怎样构造互补的轨迹、技能与感知数据

### 7.1 为什么只收集完整成功轨迹还不够

完整任务轨迹教模型如何组合步骤，但某种关键控件、少见操作或细小视觉目标，可能在大量任务中只出现少数几次。

MolmoWeb 将训练材料分成任务轨迹、原子技能轨迹和 GUI 感知数据；任务轨迹又包括人类与多种合成来源。[MolmoWeb，Figure 2、§2，PDF 第3–8页](#s-mw)

| 数据类型 | 主要教什么 | 示例 |
|---|---|---|
| 完整任务轨迹 | 组合多个操作以完成目标 | 搜索商品、筛选、比较、返回结果 |
| 原子技能轨迹 | 稳定完成局部操作过程 | 填表、设置筛选、找到并打开元素 |
| Grounding 数据 | 把语言目标映射到位置 | 根据描述预测点击点 |
| 截图问答 | 阅读界面内容与理解功能 | 价格、文本、可用操作、页面用途 |

其中的“原子技能”是训练数据中的短轨迹单元，不应直接等同于运行时加载的 `SKILL.md`。

### 7.2 结构化教师，视觉学生

MolmoWeb 的一个重要设计，是用 AxTree Agent 生成大量合成轨迹。教师观察可访问性树，输出元素 browser ID；采集系统同时记录截图，并把元素 ID 转成像素空间动作。[MolmoWeb，§2.1，PDF 第4页](#s-mw)

```text
教师输入：任务 + 可访问性树 + 历史
教师输出：操作某个元素 ID
             ↓
采集系统记录同一时刻截图，并映射动作位置
             ↓
学生训练：任务 + 截图 + 动作历史 → 像素动作
```

因此，数据生成接口可以比学生部署接口更容易操作。论文中的视觉学生不需要在推理时使用 HTML 或 AxTree。[MolmoWeb，§3.1–3.2，PDF 第7–9页](#s-mw)

**工程推论**：教师所依赖的信息应当尽可能在学生观察中可恢复。如果教师利用了截图中不可见的属性，可能形成“标签正确，但学生输入不足以决定答案”的样本。MolmoWeb 的截图问答数据也过滤了依赖 AxTree 特定标识等非视觉信息的内容。[MolmoWeb，截图问答数据，PDF 第7页](#s-mw)

### 7.3 多角色生成轨迹，不等于部署多 Agent 并行执行

MolmoWeb 还使用 Planner、Operator、Verifier 协作构造轨迹。Planner 制定接下来的子目标，Operator 每步执行操作，Verifier 根据最近截图检查子目标是否完成。达到目标或达到相应尝试条件后，再调用 Planner。[MolmoWeb，Figure 4、§2.1，PDF 第4–5页](#s-mw)

这主要是为了产生更好的训练数据，执行结构以顺序子目标闭环为主。后面 MACU 的重点则是部署时协调多个完整 CUA worker，在依赖图上并行执行和重规划。

**角色名字相似，不代表解决的是同一个问题。**

### 7.4 网站图遍历：先获得可验证轨迹，再生成任务

另一类合成数据从网站导航图出发。系统构造可达链接路径，再使用确定性过程点击与滚动，最后生成与实际走过路径一致的任务描述。[MolmoWeb，Figure 5、节点遍历方法，PDF 第5–6页](#s-mw)

这种方法与“先给任务，再让 Agent 尝试”方向相反：它先得到可靠轨迹，再解释这条轨迹完成了什么。

**教学判断**：它适合提供导航监督，但不能据此认为已经覆盖复杂用户意图。沿一条可达路径走到某页，与在大量候选中根据多项约束选择最合适结果，仍然是不同难度。

### 7.5 人类轨迹可以被分割成可复用的技能监督

MolmoWeb 在人类采集时记录子任务分解，之后将这些片段作为原子技能轨迹。每段从前一子任务完成的真实状态开始，具有自己的子目标。[MolmoWeb，§2.2、Table 1，PDF 第6–7页](#s-mw)

这种方法的价值是：不必为每一种技能从头重新录制完整任务，同时让模型学习在工作进行到一半时继续执行，而不只是从网站首页开始。

不过，数据规模统计也因此需要谨慎。完整轨迹及其抽取片段可能共享操作事件，不能将所有轨迹类别简单相加后称为“互不重复的人类任务数”。论文 Table 2 的类别与单位需要分别阅读。[MolmoWeb，Table 2，PDF 第8页](#s-mw)

### 7.6 人类数据一定优于合成数据吗？

MolmoWeb 在相同任务上分别收集约2,700条人类和合成轨迹进行比较：

| 训练轨迹来源 | DeepShop | WebVoyager | Online-Mind2Web |
|---|---:|---:|---:|
| 人类 | 19.8 | 35.4 | 9.0 |
| 合成 | 24.4 | 53.0 | 16.8 |

来源：[MolmoWeb，Table 6，PDF 第12页](#s-mw)。表中为相应实验中的任务表现，不是来源类别的普遍质量排名。

作者的解释包括：人类在不熟悉网站上有更多绕路；结构化教师的轨迹更直接、更一致。这些是对本实验的解释，不足以推出“人工示范没有价值”。

与 OpenCUA 连起来看，结论更加清楚：**未处理的绕路可能是模仿噪声；经过识别、筛选和反思的错误恢复，则可能成为训练资产。**

### 7.7 一个容易被数据总量掩盖的问题：稀有动作被主流动作淹没

MolmoWeb 观察到，人类轨迹中包含 `scroll_at`，可以滚动某个具体区域；合成数据更多使用全页 `scroll`。混合训练后，模型倾向于输出全页滚动，而不是滚动嵌套元素。[MolmoWeb，§4.4，PDF 第11页](#s-mw)

这很像真实开发中“Agent 一直滚动，但目标列表不动”的失败。问题可能不在于模型没理解滚动，而在于训练分布没有让它稳定区分全页滚动与局部滚动。

**工程建议**：数据混合时不仅检查总量，还要检查操作类型、参数约定、出现频率、前置状态与失败恢复覆盖。大量常见动作的成功样本，不能自动补足少见关键动作。

### 7.8 训练与部署接口应该对齐

MolmoWeb 的策略接收当前截图、任务、近期动作历史，以及页面 URL 和标题等上下文。鼠标坐标采用归一化表示，执行时再还原到视口像素；这属于其具体接口约定。[MolmoWeb，§3、Table 3，PDF 第7–9页](#s-mw)

**工程建议**：不能把一个模型的坐标尺度、输入格式和动作历史长度直接套给另一个模型。训练时使用的动作模板、图片处理与部署转换应当作为模型接入契约进行版本管理。

### 7.9 采样策略也会影响循环行为

论文一个实验中，greedy decoding 得到61.4的 WebVoyager 表现，所测 top-k 为67.4、top-p 为68.5。作者观察到，随机采样有时能摆脱固定位置的重复点击或无效滚动。[MolmoWeb，Table 7、§4.5，PDF 第12页](#s-mw)

这不是让生产系统“遇到错误就随机操作”的理由。实验揭示的是：解码策略会改变轨迹分布与循环行为，应和安全限制、动作校验、恢复机制一起测试，而不是只把温度当作文风参数。

### 7.10 本章最重要的结论

MolmoWeb 将“更多训练数据”拆解为“更合适的数据组合”。完整任务、局部技能、位置监督、界面问答，以及不同来源的行为，承担不同教学职责。

**训练配方不是把数据拼在一起，而是决定模型究竟反复练习哪些观察、决策和操作。**

## 八、CUA-Gym：把可重置环境和验证器变成训练基础设施

### 8.1 从 SFT 到 RL，差的不只是一个优化算法

SFT 可以让模型模仿已有轨迹。但交互式 RL 需要模型自己执行、产生后果，并获得奖励。

CUA-Gym 将基本训练实例写成：

$$
(t,s,r)=\text{任务指令、可复现初始环境、验证奖励函数}.
$$

每个部分都是必须能够真正运行的工程产物。[CUA-Gym，§1–2.1，PDF 第1–3页](#s-cg)

对于桌面任务，这可能意味着准备一台电脑、软件、文件、应用状态，以及能够读取最终产物的验证器。因此，扩大训练规模也在扩大环境与测试工程规模。

### 8.2 为什么不能直接在真实业务里反复探索

Lecture-07 第65页用预订场景说明：重复尝试可能产生真实付费订单、影响真实服务人员；取消也不等于恢复到完全相同的初始世界。[L07，PDF 第65页](#s-l07)

这与普通可重置模拟器不同。撤销本地文件操作，不会自动撤销远端订单或已经发出的通知。

**工程建议**：训练探索放在可重置环境中；生产执行受任务授权与副作用约束。不能为了收集成功轨迹，把真实客户系统当作无限试错场。

### 8.3 Generator、Discriminator、Orchestrator 各自做什么

CUA-Gym 从任务与相关上下文出发，联合构造状态和奖励。[CUA-Gym，Figure 1、§2.1，PDF 第3页](#s-cg)

| 角色 | 主要产物 | 关键边界 |
|---|---|---|
| Generator | `initial_setup.py`、`golden_patch.py` | 构造初始状态与正确完成状态 |
| Discriminator | `reward.py` | 根据任务与结果环境写检查，不读取生成器构造脚本 |
| Orchestrator | 执行结果、反馈与迭代调度 | 管理环境，验证各项一致性条件 |

这里的 Generator—Discriminator 是职责划分，不是说论文在训练一个生成对抗网络。

### 8.4 为什么要隔离环境构造与验证器编写

如果同一个 Agent 同时构造正确状态并编写测试，很容易写成“验证自己做过的事情”，而不是“验证用户要求”。

例如，生成器创建 `done.txt`，验证器只检查文件存在；这可能完全没有检验任务语义。

CUA-Gym 将角色隔离落实到进程与文件视图：Discriminator 无法读取 Generator 的脚本和工作目录，只能根据任务相关信息及状态视图进行判断。[CUA-Gym，附录 A.3.2、访问矩阵，PDF 第16–17页](#s-cg)

**给两个 Agent 不同的角色名称，不等于它们真的独立。独立性还涉及信息和权限。**

### 8.5 五项检查能保证什么

论文的循环验收要求：初始脚本可执行、目标脚本可执行、初始状态奖励为0、目标状态奖励为1，以及奖励代码不包含规定的投机模式。[CUA-Gym，附录 A.3.1–A.3.3，PDF 第16–17页](#s-cg)

其中：

$$
r(s_{init})=0,\qquad r(s_{gold})=1.
$$

**教学推导**：它证明了验证器在这两个端点上的预期行为，不证明所有错误状态都会得0分，也不证明所有合法完成方式都会得1分。

一个只检查少数字段的验证器，仍可能放过其他内容被破坏的错误产物。因此，论文还加入多数评议和教师 rollout 等数据集级过滤，以识别歧义、不可执行或奖励不对齐的实例。[CUA-Gym，过滤流程，PDF 第4页](#s-cg)

**工程建议**：给验证器构造反例测试，如“只完成一半”“文件名正确但内容错误”“目标字段正确但无关数据被破坏”。验证器本身也应该接受测试。

### 8.6 CUA-Gym-Hub：可控制状态，比外观相似更关键

CUA-Gym-Hub 提供94个 mock Web 应用，通过统一状态 API 支持检查、注入和重置。整个 CUA-Gym 环境池还包含16个桌面应用，共110个环境；论文报告32,112个验证过的 RLVR 训练实例。[CUA-Gym，§1、§2.2，PDF 第2、4页](#s-cg)

同一个邮件应用可以注入不同的收件箱、标签和未读状态；代码不变，任务相关世界发生变化。

```text
应用实现：邮件系统
   ├─ 会话 A：空收件箱
   ├─ 会话 B：多个待处理项目通知
   └─ 会话 C：大量积压邮件
```

状态注入将“应用代码”和“训练实例”分开；会话隔离让不同 worker 可以共享应用实现，却不互相污染数据。[CUA-Gym，Figure 3、§2.2，PDF 第4–5页](#s-cg)

需要区分环境构造者、验证器与被训练策略的权限。为了生成和检查任务提供状态 API，不代表部署中的视觉 Agent 应当获得奖励答案或任意后台状态。

### 8.7 实际训练：先 warm-up，再进行有验证奖励的 RL

主实验使用3,578条成功轨迹做 SFT warm-up，再从数据池中取10,858个验证过的实例进行 RLVR，覆盖80多个环境。[CUA-Gym，§3.1，PDF 第5页](#s-cg)

对同一个任务和初始状态，策略生成多条轨迹，分别得到奖励。组内优势可概括为：

$$
\hat A_i=\frac{r_i-\mu_r}{\sigma_r}.
$$

论文采用 GSPO，并使用序列级重要性比率、裁剪与参考策略约束。该比率由新旧策略对序列概率的比值进行长度归一化，而不是简单将每条成功轨迹全部照抄。[CUA-Gym，式(1)–(2)，PDF 第6页](#s-cg)

这组公式的直观意义是：比较同一任务不同尝试的相对表现，在限制更新幅度的情况下改变策略。真正决定反馈是否有用的，仍然是任务可执行性、奖励可信度、初始化能力和样本难度。

### 8.8 长轨迹训练：不能只让模型看到最后几轮

CUA-Gym 的 trajectory slicing 为一条 rollout 构造多个训练样本。保留任务前缀与较早的助手文本，把过时截图折叠为确定性占位符，同时保留近期完整多模态内容。[CUA-Gym，Figure 4，PDF 第5–6页](#s-cg)

这样既能在有限上下文预算下监督后半段动作，又能保留解释这些动作所需的历史；稳定前缀还便于计算策略概率时复用 KV cache。

OpenCUA研究“什么历史表示有利于决策”；CUA-Gym进一步研究“怎样在成本可控的情况下对长历史进行训练”。

**上下文管理不是仅在部署时做一次摘要，它也会影响训练信号。**

### 8.9 模型收益与分领域退化要一起看

| 基座与训练后模型 | OSWorld-Verified | WebArena |
|---|---:|---:|
| Qwen3.5-35B-A3B → CUA-Gym-A3B | 54.5% → 62.1% | 40.8% → 44.5% |
| Qwen3.5-397B-A17B → CUA-Gym-A17B | 62.2% → 72.6% | 54.0% → 56.0% |

来源：[CUA-Gym，Figure 5、主结果，PDF 第6页](#s-cg)。这些是论文给定初始化与评测设置中的结果。

但总体改善不代表每个应用都改善。论文的小模型分领域结果中，Chrome、Thunderbird、VLC 等出现退化。因此，不能用一个总成功率替代目标业务应用的验收。

### 8.10 环境多样性消融，需要读清实验类型

| 实验设置 | 环境数 | 轨迹数 | 对应比较 |
|---|---:|---:|---|
| Narrow | 10 | 3,000 | 与 Mid 比较环境多样性 |
| Mid | 80 | 3,000 | 与 Narrow 保持总量相同 |
| Broad | 80 | 6,000 | 与 Mid 比较数据量 |

这些环境规模实验在 **教师蒸馏的 SFT 设置** 下进行，而不是三组完整 RL 实验。固定数据量增加环境带来较温和的收益，在较广环境池中增加轨迹产生更大的收益。[CUA-Gym，§4.2、Figure 8，PDF 第8–9页](#s-cg)

合适的结论是“环境覆盖与数据量具有互补价值”，不是“论文已经证明在所有 RL 设置中增加环境一定优于增加轨迹”。

### 8.11 RL 还改变了动作粒度

论文观察到，训练后平均每轮工具调用数从约1增加到1.4–1.9，轨迹轮次在相近任务表现下减少约33%–45%。它倾向于合并较确定的短操作序列，而把依赖网络返回或需要观察确认的操作留在批次边界之外。[CUA-Gym，§4.3、Figure 9，PDF 第9页](#s-cg)

作者将其解释为固定步数预算下的效率选择压力。这是对观察结果的解释，不是经过形式证明的机制。

**工程建议**：批处理的单位应当由“中间是否需要新观察”决定，而不只是设定“每次最多执行5个动作”。减少模型轮次与减少环境原子动作，也应分别统计。

### 8.12 必须保留的局限

CUA-Gym 的奖励主要检查终态，不能充分区分正常编辑与破坏后重建到相同终态的过程；信息隔离和静态检查也无法形式化排除所有奖励投机。Mock 没有覆盖完整身份认证、第三方集成、真实网络延迟、限流和罕见服务端故障；较大 RL 实验还存在单随机种子的限制。[CUA-Gym，§6，PDF 第10页](#s-cg)

**可验证训练能够提升能力，但不是生产安全或部署稳健性的完整证明。**

## 九、Gym-Anything：让真实专业软件成为可运行、可审计的环境

### 9.1 它与 CUA-Gym 的侧重点不同

CUA-Gym-Hub 重点是可控制、可重置的 mock 应用；Gym-Anything 重点是把真实软件安装、配置为带领域数据的交互环境，并规模化生成任务。[Gym-Anything，§1–3，PDF 第2–7页](#s-ga)

这不意味着一个只重训练、另一个只重评测。它们都涉及训练和评测，只是处理环境规模化问题的路线不同。

| 维度 | CUA-Gym / CUA-Gym-Hub | Gym-Anything / CUA-World |
|---|---|---|
| 主要环境组织 | 桌面应用加可注入状态的 mock Web 应用 | 真实安装、配置的软件环境 |
| 主要构造对象 | 指令、初始/目标状态、奖励函数 | 软件环境、任务初始状态与检查表 |
| 主要验证路线 | 程序化奖励及一致性过滤 | 特权信息辅助的 checklist VLM 验证 |
| 主要学习展示 | SFT warm-up 后的 RLVR | 成功轨迹蒸馏及测试时审计 |
| 主要局限 | Mock 与真实系统有差距；终态可能漏过程 | 软件构建异质性；VLM 判断与任务配置仍需审计 |

来源：[CUA-Gym，§2–3、§6](#s-cg)；[Gym-Anything，§2–7](#s-ga)。

### 9.2 环境构造被拆为三个可复用阶段

Gym-Anything 的环境定义包含三个脚本阶段和声明式配置：[Gym-Anything，§2.3，PDF 第5–6页](#s-ga)

```text
install：安装软件和依赖
    ↓
configure：准备通用设置与真实数据
    ↓
task setup：设置本任务特有的起始状态
```

同一软件的多个任务可以复用前两个阶段，主要变化在任务初始化。框架处理显示、输入、容器与后端等底层差异。

**工程理解**：环境不再只是一个不可解释的大快照，而是可以检查、版本管理、局部重建和复用的构造过程。需要注意，OSWorld 也包含脚本化初始化与快照结合，并非此前所有工作都只有手工快照。

### 9.3 创建—审计循环：事实来自环境，不来自 Agent 的宣称

创建 Agent 研究软件、寻找数据、编写脚本、运行应用，并提交截图、日志和数据产物。独立审计 Agent 按检查表核验，必要时重新运行环境，再反馈问题。[Gym-Anything，Figure 4、§3，PDF 第6–7页](#s-ga)

一些失败不是程序完全没启动，而是停在安装向导、加载了占位数据、初始界面不正确，或根本没有做验证。

**“环境装好了”是一句声明；运行画面、日志和实际数据才是支持声明的证据。**

这一思路与 CUA-Gym 的验证独立性相通，但两者的访问隔离方式不同。Gym-Anything 的创建和审计角色原则上可以拥有相同工具与文件，差异主要在目标和提示；CUA-Gym 则明确采用进程级信息隔离。不能把二者统称为同一种严格隔离机制。[Gym-Anything，§3，PDF 第7页](#s-ga)；[CUA-Gym，附录 A.3.2，PDF 第16–17页](#s-cg)

### 9.4 环境构造经验也形成记忆

Gym-Anything 将失败原因、修复办法和软件特有注意事项写入共享文件式记忆，区分软件专属说明和可跨软件复用的一般说明，并通过摘要过程控制其增长。[Gym-Anything，§3、Figure 4，PDF 第6–7页](#s-ga)

这里的记忆是环境创建过程的经验，不是用户偏好，也不是当前执行任务的工作状态。三者都叫 memory，但存储对象与更新规则不同。

### 9.5 任务生成：先做少量高质量种子，再扩增

Gym-Anything 使用 propose-and-amplify：先让能够真实运行软件的 Agent提出并执行较少的高质量种子任务，再由较便宜的非 Agent 式 LLM 根据种子扩增，并过滤重复和不匹配实例。[Gym-Anything，§4，PDF 第8页](#s-ga)

扩增后还要启动任务，检查初始状态是否与指令匹配。否则，语言上合理的任务可能引用不存在的文件，或要求当前软件无法完成的操作。

**教学判断**：大量任务文本不等于大量有效训练任务。任务必须与实际可执行世界绑定。

### 9.6 特权信息与 checklist 验证

某些目标值可以从环境初始化数据中确定，例如账户初始余额或已知数据集的正确标注。执行 Agent 不直接拿到答案，验证器可以使用这些特权信息生成更细粒度的检查表。[Gym-Anything，§4.1，PDF 第8–9页](#s-ga)

验证分数可写成：

$$
V(\tau)=\sum_i w_i\cdot VLM(\tau,c_i,I),
$$

其中 $c_i$ 是检查项，$w_i$ 是权重，$I$ 是特权信息，$\tau$ 是轨迹。

此外，完整性检查用于确认是否使用要求的软件、是否通过规定界面完成，以及是否利用环境产物绕过工作。如果完整性检查失败，其他检查项得分再高也会被归零。[Gym-Anything，§4.1，PDF 第9页](#s-ga)

这正对应讲义的“结果与过程都要检查”。

### 9.7 不要把模型写坏的检查脚本，等同于程序化验证的全部能力

Gym-Anything 在60条随机抽取的轨迹上比较检查方式，报告 checklist VLM 的人工一致率为93.3%，直接 VLM 二元判断为81.7%，模型生成的程序验证器为43.3%。作者明确指出，程序方法表现较差的重要原因是生成的脚本无法正确解析产物；人工编写的程序验证器可能提供更强保证。[Gym-Anything，§7.3，PDF 第15页](#s-ga)

因此，正确理解是：该实验中，结构化 checklist 优于所测试的其他实现。它不是“VLM 验证从原理上比程序验证更可靠”的证据。

**工程建议**：精确可计算的内容由经过测试的程序校验，开放式视觉与语义要求由模型辅助判断，关键分歧由人工处理。不同检查方法应服务于不同条件。

### 9.8 范围扩展带来什么实证结果

论文构造的 CUA-World 包含12,103个任务与环境配置，覆盖200种软件，并提供训练、测试与更长任务的划分。其蒸馏实验把2B学生的平均检查表得分从12.7提高到22.5，完整通过率从1.6%提高到4.4%。[Gym-Anything，§5、Table 3，PDF 第9、12页](#s-ga)

这同时说明两件事：环境数据确实能提供学习信号；但显著相对提升之后，绝对完整成功率仍然可能很低。

不要只说“提升近三倍”，却不说明模型仍然很少完整完成任务。

### 9.9 训练过的软件与未见过的软件，收益不同

Gym-Anything 研究增加软件覆盖与任务量，并比较已见软件和未见软件。未见软件也获得收益，但明显弱于已见软件。[Gym-Anything，Figure 7、§7.1，PDF 第12–13页](#s-ga)

这提醒我们：掌握一般 GUI 操作不等于掌握全部专业软件。软件的功能组织、业务概念和操作逻辑仍然会形成迁移障碍。

**工程推论**：做企业 CUA 时，与其泛泛声称“通用电脑操作”，不如明确目标软件集合，并用相应任务与异常分布验证。通用能力是基础，软件特定证据仍不可省略。

<a id="chapter-10"></a>
## 十、长任务与 MACU：怎样使用更多计算，而不是只消耗更多计算

### 10.1 长任务的困难，不只是上下文装不下

长任务还涉及持续维护目标、识别局部错误、保存中间证据、跨应用交接，以及正确判断何时结束。

OpenCUA 发现，许多模型从15步增加到50步有收益，但进一步到100步收益有限；额外预算可能被重复循环、错误恢复失败与不恰当停止消耗。[OpenCUA，Table 3及分析，PDF 第10页](#s-oc)

Gym-Anything 则包含一些本来就需要大量操作的任务，较小预算尚未足以完成必要工作量。[Gym-Anything，§6–7，PDF 第11–14页](#s-ga)

两种现象并不矛盾：**有的任务缺预算，有的任务缺摆脱错误路径的能力。**

### 10.2 三种扩展计算的方式，需要分别理解

| 方式 | 增加了什么 | 主要希望解决什么 |
|---|---|---|
| 单次执行更久 | 更多模型轮次与环境操作 | 必要工作量较大、局部恢复需要更多步骤 |
| 多次独立尝试 | 从初始状态重新探索多条轨迹 | 某次执行早期进入错误分支 |
| 分解与协调 | 子任务、并行执行、重规划与交接 | 一个长任务可以拆成更易管理的工作单元 |

OpenCUA、MolmoWeb、Gym-Anything 和 MACU 分别研究了其中不同组合。不能将它们都简单称为“test-time compute 增加”后忽略结构差异。

### 10.3 增加步数可能只是让 Agent 重复更多次

Gym-Anything 对一类模型的轨迹做自动行为分析，发现失败轨迹中无效重试所占比例更高；重新检查工作是否正确的行为，在成功轨迹中出现得更频繁。[Gym-Anything，Figure 8、§7.3，PDF 第14页](#s-ga)

这里要保留两个限制：这些模式来自特定模型的自动分析；相关性不证明“多检查一次就一定成功”。但它为分析成本提供了重要方向。

**工程建议**：总步数至少拆成有效执行、界面探索、进度验证、无效重试四类。只看到“用了200步”无法判断系统是在做复杂工作，还是卡在同一处。

### 10.4 MolmoWeb：多条短尝试，可能优于一条长尝试

MolmoWeb 比较过独立 rollout 与增加单次步骤预算。论文举例，三次最多30步的尝试及结果选择，表现可以超过一次最多100步的尝试。[MolmoWeb，§4.3，PDF 第10–11页](#s-mw)

直观解释是：单次执行可能在早期被错误路线拖住，重新出发可以探索另一种路径。但这是特定评测与选择方式下的结果，不是所有任务都适合重启。

### 10.5 Pass@k 不等于用户能拿到正确结果

Pass@k 关心多次尝试中是否存在成功。在收集 $m$ 条轨迹、其中 $c$ 条被判成功时，论文使用的估计形式为：

$$
\widehat{\mathrm{pass@}k}=1-\frac{\binom{m-c}{k}}{\binom{m}{k}}.
$$

其成功标签和结果选择使用相应评判机制，因此还会受到 judge 质量影响。[MolmoWeb，§4.3，PDF 第10页](#s-mw)

必须区分三个问题：是否曾经生成正确结果，能否识别哪个结果正确，以及选择过程是否引入额外风险或成本。

一个模型试四次，其中一次正确，但部署系统选错了，用户仍然拿不到正确结果。更不能对发送、付款、提交等不可随意重置的操作直接执行多次，再事后挑选最好的一次。

### 10.6 MACU：从重复尝试转向可修改的任务图

MACU 使用 Manager 将任务分解为 DAG，节点表示子任务，边表示依赖。依赖已满足的节点可以交给 CUA 子 Agent 并行执行；新结果回来后，Manager 可以增加、删除、修改或取消节点。[MACU，§3、Figure 1、Algorithm 1，PDF 第2–5页](#s-mac)

```text
                         ┌→ 网站 A 信息采集 ─┐
用户目标 → Manager 分解 ─┼→ 网站 B 信息采集 ─┼→ 汇总比较 → 生成交付物 → 检查
                         └→ 网站 C 信息采集 ─┘
                                  ↓
                         某分支失败或发现新条件
                                  ↓
                         Manager 修改后续任务图
```

这个示意图是对论文结构的教学表达，不是论文中某个实验的逐节点复刻。

MACU 的子 Agent使用相同 CUA backbone，各自在隔离虚拟机中运行；任务差异来自 Manager 分配的指令和初始化状态，而不一定需要为每个角色训练不同模型。[MACU，§3，PDF 第3–5页](#s-mac)

### 10.7 初始计划是对未知环境的假设

在部分可观测环境中，开始时未必知道某个网站是否有目标信息、文件格式是否符合预期、某个子任务是否可行。MACU 因而把持续重规划作为重要能力，而不只是在开始前写一份计划。[MACU，§1、§3，PDF 第2–4页](#s-mac)

**工程推论**：与其要求初始计划越来越长，不如明确什么证据触发重规划，哪些完成结果需要保留，哪些待执行操作需要取消，以及替代路径如何接入。

### 10.8 重规划消融：收益主要不来自一次性初始计划

论文在36个 OSWorld 任务的子集上，以 Qwen3.5-4B 为 worker、Opus 4.6 为 manager，改变规划预算：

| 规划预算与设置 | 成功率 |
|---|---:|
| $B=0$，不规划 | 25.0% |
| $B=1$，仅初始计划 | 27.8% |
| $B=5$，允许运行时修改 | 47.2% |
| $B=10$，更高修改预算 | 58.3% |

来源：[MACU，Table 2、§4.2，PDF 第7页](#s-mac)。

这是特定子集与模型设置中的消融，不是完整 OSWorld 主结果。它支持的认识是：根据新观察修改计划，比仅在开始时增加一次规划调用，更能解释这组实验中的收益。

### 10.9 多 Agent 提升成功率，不代表一定更快

主实验使用 Qwen3.6-27B 作为 CUA worker。下表摘录 Opus 4.6 Manager 对应的多 Agent设置，与相同 worker 的单 Agent比较：

| 基准 | 单 Agent 成功率 | MACU 成功率 | 单 Agent 中位耗时 | MACU 中位耗时 |
|---|---:|---:|---:|---:|
| OSWorld | 43.8% | 48.5% | 26.6分钟 | 21.4分钟 |
| Online-Mind2Web | 52.2% | 55.6% | 18.5分钟 | 33.6分钟 |
| WebTailBench-v2 | 20.8% | 29.5% | 39.0分钟 | 55.2分钟 |
| Odysseys | 8.5% | 34.0% | 162.4分钟 | 110.3分钟 |

来源：[MACU，Table 1、§4.1，PDF 第6页](#s-mac)。

可分解的长任务更容易从并行和局部重试受益。较强串行依赖的任务，Manager 调用与协调开销可能增加总时间。

论文另一组最大并行数消融，在45个 Odysseys easy 任务上报告从1个到4个并行 worker 的时间缩短，但排除了推理开销。因此，该加速不能直接当作完整线上系统的加速保证。[MACU，Figure 5、§4.2，PDF 第8页](#s-mac)

### 10.10 DAG 不仅是调度结构，也是证据传递结构

MACU 的 Manager读取子 Agent 的近期截图、最终响应和文件系统变化，并决定保存哪些文件、将什么结果交给下游。[MACU，§3，PDF 第3–4页](#s-mac)

原因是，下游未必能够重新观察上游曾经看到的状态。一个浏览器页面可能已关闭，某个动态结果可能已改变，某个文件可能存在多个版本。

**工程建议**：交接单元应当是“结论 + 证据 + 产物 + 未解决问题”，而不是一句“已经完成”。若上游只是尝试下载、没有验证内容，下游不能把它当作已核验文件。

另一个边界是：虚拟机隔离不等于远端业务状态隔离。两个隔离 VM 登录同一个账号，仍可能同时修改同一条记录。真实写操作应另行设计资源锁、版本检查或单一写入者。

### 10.11 同名“多 Agent”，在不同论文里扮演不同角色

| 工作 | 多角色结构的用途 |
|---|---|
| MolmoWeb | 生成更可靠的训练轨迹，主要围绕顺序子目标闭环 |
| CUA-Gym | 分离环境构造与奖励编写，并协调验证 |
| Gym-Anything | 创建环境、审计环境、积累构建经验 |
| MACU | 在部署式执行中分解任务、并行工作、重规划与交接 |

这些方法可以在不同阶段组合，但不应仅因为都使用多个模型调用，就当作同一种架构。

### 10.12 Test-Time Auditing：把“结束”也视为需要验证的决策

Gym-Anything 发现长任务 Agent 经常提前声称完成。其 Test-Time Auditing 在执行模型发出终止信号时，由另一个模型检查完整截图轨迹，指出遗漏，再让执行者继续。[Gym-Anything，§6.2，PDF 第11页](#s-ga)

一个关键设计是：审计者不接收执行模型的 CoT，因为作者发现这些自我叙述会影响审计判断。

这与 OpenCUA 的推理研究形成互补：**推理说明可以帮助执行者作决定，却可能让审计者受到执行者叙述的影响。**同一种信息，对不同角色的价值可能相反。

论文在相同2,000步上限下，把相应模型完整通过率从11.5%提高到14.0%。但审计模型引入了额外计算，不能把“相同步数上限”理解成“总成本完全相同”。[Gym-Anything，Figure 6、§7.2，PDF 第13–14页](#s-ga)

### 10.13 任务时间应拆开分析

Lecture-07 将任务时间近似写成“轮次 × 每轮时间”，并强调更少、更便宜的轮次，以及在关键决策处使用推理。[L07，PDF 第77页](#s-l07)

**工程建议**：进一步将一次执行成本拆成图像处理、上下文处理、推理生成、工具执行、等待、验证、重试和协调。这样才能区分：应该压缩输入、减少推理、批量操作、改进等待，还是减少失败分支。

只优化每次模型调用的延迟，却使错误率上升、重试次数增加，最终每个成功任务的成本可能反而变高。

## 十一、工程落地：把这些论文组合成一个可靠执行系统

> 本章是将前文研究与讨论整理成的工程建议，不是某一篇论文已经实现并完整验证的生产框架。示例中的任务约束和字段是教学设计。

### 11.1 先明确业务结果，再决定哪些步骤使用 GUI

教学任务：读取指定目录的收据，更新本期账簿，保存为新版本，并生成汇总草稿。不得覆盖原始账簿，不得对外发送。

不要直接把这句话交给一个拥有全部桌面权限的 Agent，然后等待它报告完成。先明确哪些内容可以直接确定、哪些需要读取、哪些必须人工确认。

对精确计算与文件内容校验，可以使用获授权的结构化工具；对没有稳定接口的操作，可以使用 GUI。这里追求的是在授权范围内可靠完成工作，而不是刻意让所有环节都模拟鼠标。

但研究基准的接口约定必须遵守。Gym-Anything 的完整性检查会限制通过直接修改底层配置或文件来绕过指定界面。生产混合工具方案不能包装成纯 GUI 基准成绩。[Gym-Anything，§4.1，PDF 第9页](#s-ga)

### 11.2 第一份重要产物：任务契约

建议将任务分成目标条件和不变量。

**目标条件**：本期材料正确识别，交易明细正确写入，金额与余额一致，新版本保存成功，汇总草稿与账簿保持一致。

**不变量**：原文件不被覆盖，无关数据不被改动，未确认材料不被当成确定数据，没有对外发送或提交。

以下是一个简化任务契约，表示设计意图，不是某个现成 SDK 的配置格式：

```json
{
  "task_id": "bookkeeping-demo-001",
  "goal": "根据指定收据更新账簿并生成汇总草稿",
  "inputs": {
    "receipts_directory": "由用户指定的材料目录",
    "workbook": "由用户指定的原始账簿",
    "period": "由用户明确的统计期间"
  },
  "outputs": {
    "workbook": "新的账簿版本",
    "summary": "未发送的汇总草稿"
  },
  "invariants": [
    "原始文件保持不变",
    "无关工作表及原有数据不得被修改",
    "不对外发送",
    "不将未核验值写成已确认事实"
  ],
  "completion_checks": [
    "输入材料处理状态完整",
    "期间与币种口径明确",
    "金额与余额校验通过",
    "新文件能够重新打开",
    "草稿与已核验账簿一致"
  ]
}
```

任务条件应当尽可能转成具体检查，而不是只保存一句“请保证准确”。这分别对应 WebShop 的多条件任务、WebArena 的功能验证，以及讲义的过程正确性。

### 11.3 最小系统可以保持简单，但职责不能混乱

```text
任务契约
   ↓
协调器：预算、当前子目标、状态记录、是否暂停
   ↓
策略模型：基于当前证据提出下一步
   ↓
动作网关：格式、权限、对象、观察时效与风险检查
   ↓
执行环境：浏览器 / 桌面会话 / 获授权工具
   ↓
观察与证据采集：截图、文件、状态、错误
   ↓
验证：前置条件、动作后置条件、最终交付条件
   └────────────────────→ 更新任务状态
```

这些是逻辑职责，不要求每项都对应一个微服务或一个独立 Agent。小团队可以先用单进程协调器、结构化记录和少量适配器实现，再根据真实瓶颈拆分。

### 11.4 观察必须有版本，动作必须知道自己依据哪次观察

一条观察记录建议至少包含：运行和会话标识、观察时间、活动窗口、截图大小、缩放与裁剪信息，以及可获取的结构化页面状态。

例如：

```json
{
  "observation_id": "obs-0042",
  "session_id": "session-A",
  "active_window": "账簿窗口",
  "screenshot": {
    "width": 1920,
    "height": 1080,
    "coordinate_space": "原始截图像素",
    "crop_origin": [0, 0],
    "scale": 1.0
  },
  "captured_at": "采集系统生成的时间戳"
}
```

模型提出的动作应关联 `observation_id`。在执行前，如果窗口、页面或焦点发生了关键变化，应重新观察，而不是继续用旧坐标。

这里要区分两种失败：模型在正确观察上选择错误位置；位置本来正确，但执行时环境已经改变。前者需要改善 grounding，后者首先需要改善运行时状态管理。

### 11.5 坐标转换不能交给自由文本猜测

原始屏幕、浏览器视口、裁剪区域、缩放后的模型输入，以及系统逻辑坐标，可能不是同一坐标空间。

对于一个没有额外变换的裁剪缩放，若模型坐标是 $(x_m,y_m)$，裁剪左上角是 $(x_0,y_0)$，缩放比例是 $k$，则原图坐标可以按下面的教学示意还原：

$$
x_{original}=x_0+x_m/k,\qquad y_{original}=y_0+y_m/k.
$$

实际系统还需按浏览器、设备缩放和模型坐标协议处理其他变换。这个式子不是适用于所有环境的统一实现。

建议由确定性代码维护和测试坐标映射，并检查边界、窗口归属、焦点和目标是否仍然存在。不要让模型一会儿输出0–100，一会儿输出像素坐标，而执行层靠猜测解释。

### 11.6 执行状态至少需要“成功、失败、未知”

点击保存后超时，并不等于保存失败。也可能保存已经完成，只是回执或后续观察丢失。

建议采用下面的状态语义：

| 状态 | 含义 | 后续处理 |
|---|---|---|
| `proposed` | 模型提出操作，尚未执行 | 做权限和前置检查 |
| `executing` | 操作已派发 | 等待并采集结果 |
| `verified_success` | 有证据支持操作或子目标完成 | 更新已确认状态 |
| `verified_failure` | 有证据支持失败 | 选择恢复、替代路线或暂停 |
| `outcome_unknown` | 不能确认是否生效 | 先核查状态，不盲目重复写操作 |
| `blocked` | 权限、资源或必要信息缺失 | 明确原因并请求所需处理 |

读取操作和有副作用的写操作，不应该采用相同的重试策略。特别是发送、付款、提交和覆盖，不能在结果未知时直接重试。

为请求设置唯一 ID 有助于追踪，但在 GUI 或远端系统没有提供相应保证时，不能仅靠一个 ID 宣称实现“严格仅执行一次”。

### 11.7 等待不是随便睡几秒，批处理也不是连续盲点

等待应尽量围绕可观察条件：目标窗口出现、加载状态消失、下载文件稳定、目标字段变化等，并保留超时与未知状态。

批处理则围绕确定性短序列。例如已经确认焦点正确时，清空并输入可以视情况合并；若下一步依赖网络响应或新弹窗，应当停下来重新观察。

这与 CUA-Gym 的动作批处理观察一致，但生产系统仍需单独验证，不能假设模型自然学到的批处理边界总是安全。[CUA-Gym，§4.3，PDF 第9页](#s-cg)

### 11.8 工作记忆必须区分“做过”与“做成了”

不要将“尝试导入收据”压缩成“收据已导入”。一个可用的任务状态可以是：

```text
子任务：读取本期收据
状态：部分完成
已验证：12个文件可读取，其中10个明确属于本期
待确认：2个文件的日期不能可靠识别
证据：每个文件的提取结果与原始位置
下游约束：待确认文件不能计入已核验汇总
```

建议将每条重要结论关联到来源文件、页面或区域、提取版本、统计口径，以及核验状态。

长期任务恢复时，重新加载的是“任务契约 + 已验证状态 + 产物 + 未解决问题”，而不是重放所有操作。读取历史日志也不意味着再次执行日志中的写请求。

### 11.9 数字准确性的关键：从数据产物写作，而不是从会话记忆写作

在记账或报告任务中，将数值整理成独立的结构化事实表。至少保存：数值、单位、期间、对象、来源、计算规则和核验状态。

例如，半年期收益与一年期收益即使数值接近，也应该是两个具有不同期间键的事实，而不是混在一段自然语言摘要中。

写汇总时，先读取这份已经校验的产物，再生成文字。长任务经过上下文压缩后，必要时重新读取源文件或事实表，不依赖模型“记得”某个数字。

这一方案是工程建议。它将前面关于部分可观测性、历史表示和功能验证的讨论，应用到数值与文档任务中，并不是某篇 CUA 论文已经给出的金融报告专用解决方案。

### 11.10 最终验收要检查产物，而不只是检查画面

对于本例，验收至少包含四个方面：输入材料是否全部有处理状态，写入数据是否符合期间与单位，新文件是否真实保存且能够重新打开，汇总草稿是否与账簿一致。

同时检查不变量：原始文件未改变，无关区域未损坏，没有发生外发。

文件哈希适合检查“整个原件是否保持不变”；字段和区域级比较适合检查“只允许变更部分内容”。如果某些软件保存会自动更新元数据，需要事先定义比较范围，不能机械要求所有新产物的字节完全等同于参考文件。

最终回应应该区分：完成并已验证的内容，完成但尚不能充分验证的内容，以及被阻断或留待人工处理的内容。

### 11.11 权限与内容来源必须分开

网页、文档和邮件里的文字是 Agent 处理的数据，不应因为出现在屏幕上就获得修改任务授权的权力。

建议将用户任务授权保存在独立的任务契约中，将外部内容作为带来源的材料传入。高风险动作由动作网关根据策略与实际授权决定是否允许，而不是仅依赖模型输出“低风险”。

这些措施是防御设计，不构成对提示注入或其他风险的完整消除保证。本次材料没有提供针对全部安全攻击的统一已验证方案。

### 11.12 并行读、受控写、证据交接

若任务包含多个独立的信息采集分支，可借鉴 MACU 并行执行。但更新同一工作簿或同一远端记录时，建议采用单一写入者，或使用目标系统提供的版本与并发控制。

交接记录可以包含：子任务 ID、已验证条件、产物位置与版本、证据位置、未解决问题、失败原因和后续限制。下游只使用已经确认的内容，不继承上游没有证据的完成声明。

对小团队，不必从动态多 Agent 开始。先证明单 Agent闭环可靠，再根据实际任务的可并行程度增加 worker。

### 11.13 用户体验也是系统的一部分

Lecture-07 明确提出后台隔离运行、实时进度、纠正、审批和中断；个性化记忆应能够更新，并体现用户控制。[L07，PDF 第78–80页](#s-l07)

建议将停止拆成两层：停止继续生成与停止派发新操作。同时报告已经发生的外部修改；已经发出的动作并不一定能够撤销。

用户的历史偏好可以影响输出格式，但不应自动扩大权限。例如“平时喜欢直接给最终版本”，不等于“本次允许覆盖原件或直接发送”。

<a id="chapter-12"></a>
## 十二、开发与评测闭环：定位失败、选择改进、判断是否需要训练

> 本章给出工程实施与复盘方法。各论文提供相应问题的证据与方法启发，但下面的组合流程不是它们共同发布的一套标准。

### 12.1 不要将所有失败都归结为“模型能力不够”

| 观察到的失败 | 先检查什么 | 对应的研究启发 |
|---|---|---|
| 选错对象、期间或条件 | 任务约束是否完整，决策是否比较全部条件 | WebShop、ReAct |
| 页面上有目标，但模型完全看不到 | 预处理、候选召回是否丢失目标 | Mind2Web |
| 知道需要哪个控件，却点错位置 | 分辨率、区域选择、坐标映射 | ScreenSpot-Pro |
| 页面或窗口变化后仍按旧位置点击 | 观察是否过期，执行前状态是否校验 | OSWorld 的环境状态问题 |
| 反复滚动，但目标区域不动 | 焦点、局部滚动接口和相关训练数据 | MolmoWeb |
| 动作没生效却直接进入下一步 | 是否检查状态变化，历史是否保留失败信息 | OpenCUA |
| 文件存在但内容不正确 | 验证器是否只检查文件名、存在性等代理条件 | WebArena、CUA-Gym |
| 声称完成但漏掉子目标 | 结束判断是否有独立验证 | Gym-Anything |
| 某个分支失败后整个任务停滞 | 是否支持局部恢复、替代路线和重规划 | MACU |
| 并行任务互相覆盖 | VM 之外是否共享远端数据或文件 | 从 MACU 隔离机制推导的工程边界 |

这些对应关系是诊断线索，不表示相关论文已经完全解决该类问题。

### 12.2 给失败增加可复现证据

一次失败记录建议保存：任务契约、初始环境版本、失败前后的观察、动作参数、运行时结果、相关产物与验证输出。

区分三个层次：模型原本打算做什么，执行层实际做了什么，环境最终发生了什么。若这三者缺少任一层，就很容易把因果顺序解释错。

对于复杂问题，可以从失败前的可重置状态重新运行，而不是每次从任务起点开始，节省调试成本。真实远端状态不能随意恢复时，应明确这项限制。

### 12.3 评测集覆盖四类变化

**任务实例变化**：替换日期、文件、商品、对象或输入数据，检查是否只记住演示。

**界面变化**：改变窗口大小、滚动位置、分辨率、弹窗和前景窗口，检查是否依赖固定布局。

**执行异常**：慢响应、下载失败、同名文件、保存回执丢失、部分完成，检查是否能够区分失败与未知。

**权限和可行性边界**：材料缺失、无访问权限、未授权提交、功能不支持，检查是否会编造完成或过早放弃。

Mind2Web 的泛化划分、WebArena 的不可完成任务、OSWorld 的中间初始状态和长任务研究中的恢复问题，为这些测试方向提供了依据。[Mind2Web，§4.1–4.2，PDF 第7页](#s-m2w)；[WebArena，§3.2、§5.1，PDF 第7–8页](#s-wa)；[OSWorld，§2.2.2，PDF 第4页](#s-os)

### 12.4 不只报告一个成功率

| 指标 | 回答的问题 |
|---|---|
| 完整任务成功率 | 全部必需条件是否满足？ |
| 部分完成度 | 未完整完成时，已经取得多少进展？ |
| 错误完成声明率 | 说完成的任务中，有多少其实未完成？ |
| 约束违反率 | 是否发生不允许的修改或外部动作？ |
| 人工接管率与时间 | 用户还需要付出多少工作？ |
| 结果未知率 | 多少操作缺乏足够证据确认结果？ |
| 成功任务的总成本 | 失败、重试、验证和协调计入后，交付一次要多少成本？ |
| 按应用与任务类型分组的结果 | 总体提升是否掩盖局部退化？ |

这些是建议采用的业务指标，不是所有论文都共同使用的统一标准。

一个可解释的成本口径为：

$$
C_{per\ verified\ success}=
\frac{\text{所有尝试的模型、环境、验证、重试与协调成本总和}}
{\text{验证成功的任务数}}.
$$

当没有验证成功的任务时，该比值不应伪装成一个有限的“单位成本”。另外，人工接管成本应单列或明确是否计入。

### 12.5 验证器也要成为被测对象

为每个检查项准备正确样本、错误样本、边界样本，以及不同合法实现。

例如，账簿检查器应识别金额正确但期间错误、内容正确但写入错误工作表、只处理部分收据、原件被覆盖、草稿数字与新表不一致等情况。

再检查误判方向。业务关键数据被错判为正确，通常比排版轻微偏差被错判为失败更严重。重要条件可以独立设置硬门槛，不能让其他条件的高分抵消。

这一实践直接延续了 WebShop 的平均分与成功率区别，以及 CUA-Gym 对验证器语义的重视。

### 12.6 改进应一次改变一个可解释因素

建议按以下顺序定位，而不是一开始同时更换模型、Prompt、浏览器和数据。

| 阶段 | 工作重点 | 要回答的问题 |
|---|---|---|
| 建立基线 | 固定任务、模型、环境与验证器 | 当前失败发生在哪里？ |
| 修复运行时 | 坐标、焦点、等待、观察版本、异常状态 | 不改模型能消除多少错误？ |
| 改善信息供给 | 候选召回、局部图像、任务约束、工作记忆 | 模型是否拿到了足够且相关的信息？ |
| 改善执行组织 | 子目标、验证、恢复、有限重规划 | 错误是否仍然会被无限传播？ |
| 构造针对性数据 | Grounding、技能、完整轨迹、恢复轨迹 | 哪类行为值得训练进模型？ |
| 小范围训练与复测 | 固定对照、分组指标、未见任务 | 收益是否稳定，是否产生退化？ |

这个顺序不是禁止早期训练，而是避免把工程问题错误地交给训练解决。

### 12.7 什么时候值得微调

当一类失败能够稳定复现、观测与执行接口已经明确，而且可以提供可靠训练标签时，微调才更容易形成可解释收益。

例如，大量失败来自某类嵌套表格控件，可以构造定位、局部操作和恢复轨迹；如果失败主要来自过期截图或错误坐标转换，则应先修复基础设施。

训练后不仅测目标技能，还要测原有任务，防止出现类似 MolmoWeb 稀有动作被覆盖，或 CUA-Gym 某些应用退化的现象。[MolmoWeb，§4.4，PDF 第11页](#s-mw)；[CUA-Gym，Figure 5，PDF 第6页](#s-cg)

### 12.8 怎样积累真正有价值的数据资产

不要只存成功截图和最终答案。建议同时保留任务版本、状态—动作对齐信息、操作粒度、失败类型、恢复路径、验证结果和产物。

再将数据按用途整理：定位样本帮助 grounding；短技能轨迹帮助局部操作；完整轨迹帮助任务组织；错误后的有效恢复帮助纠错；验证反例帮助提高评判器质量。

从 OpenCUA、MolmoWeb 到 CUA-Gym，反复出现的主题是：**数据不是越多越好，而是要明确每一类数据在教模型或系统什么。**

<a id="chapter-13"></a>
## 十三、综合洞见：贯穿整门课的几个关键判断

### 13.1 CUA 的能力不只属于模型参数

WebShop 改变动作语义，MINDACT 改变候选范围，SoM 改变目标引用方式，ScreenSeekeR 改变视觉搜索，OpenCUA 改变历史与训练标签，CUA-Gym 改变学习环境，MACU 改变工作组织。

因此，当某个系统表现提高时，需要问：收益来自模型、数据、观察表示、动作接口、环境、验证器，还是计算分配？

**这是跨论文方法的综合判断**：只有分清能力来源，才能判断如何复现效果、迁移到目标业务，以及失败时应该改哪个组件。

### 13.2 预处理其实是决策的一部分

将 HTML 过滤为候选、将图片压成描述、裁剪一个图像区域、删除过期截图，都会决定模型接下来能看到什么。

信息被压掉以后，下游推理无法凭空恢复。更强的模型可能减轻某些问题，但不应成为忽略观察设计的理由。

MINDACT 与 ScreenSeekeR 分别在结构和视觉空间中证明了这种设计的重要性；其共同风险也是上游选择错误。[Mind2Web，§3–4](#s-m2w)；[ScreenSpot-Pro，§4–5](#s-ssp)

### 13.3 不是所有角色都应该拿到全部信息

OpenCUA 区分当前推理与历史表示；MolmoWeb 区分教师观察和学生部署输入；CUA-Gym 隔离构造脚本与奖励编写；Gym-Anything 的测试时审计不接收执行者 CoT。

**综合判断**：信息分配不仅是节省 Token 的技术，还关系到因果对齐、可学习性和评判偏差。对执行者有用的信息，可能影响审计者独立判断；对教师可见的信息，未必对学生可见。

### 13.4 会验证，与验证可靠，是两项不同能力

一个 Agent 可以学会调用验证器，却调用了错误检查；可以反思，却没有真实证据；可以检查文件存在，却没有检查内容。

因此，在架构图中增加 Verifier 节点只是开始。还要检查它读取什么、遗漏什么、与执行者共享什么偏差，以及错误判断会造成什么后果。

WebArena 的检查范围、WebVoyager 的人工一致性实验、CUA-Gym 的独立奖励生成、Gym-Anything 的 checklist 与终止审计，从不同层次展开了这个问题。

### 13.5 长任务能力，本质上是维持可靠状态并调整工作

ReAct 让执行者更新局部计划；OpenCUA 训练状态变化与恢复；Gym-Anything 让遗漏重新被发现；MACU 让任务依赖图随着证据变化。

**综合判断**：更长上下文是资源条件，不是可靠长任务的充分条件。真正的长任务能力，体现为能否知道哪些工作已被验证、哪些信息仍然未知、哪些步骤需要重新观察，以及什么时候应该恢复或暂停。

### 13.6 通用视觉接口与可靠专业操作之间，仍有距离

截图与鼠标键盘提供了广泛适用的接口，但专业软件还要求领域概念、操作知识、真实数据和结果验证。

ScreenSpot-Pro揭示高密度专业界面的定位困难；OSWorld揭示跨应用状态复杂性；Gym-Anything揭示软件覆盖与领域知识的重要性。它们不是同一种失败，不能只靠一个 grounding 分数代表所有能力。[ScreenSpot-Pro，§1、§3](#s-ssp)；[OSWorld，§4–5](#s-os)；[Gym-Anything，§7.1–7.3](#s-ga)

### 13.7 对开发者最有用的最终问题

当你接入一个 CUA 模型或设计一个 Agent 时，先回答下面这些问题：它观察什么，怎样引用操作对象，历史如何保存，动作如何执行与确认，任务怎样判定完成，哪里必须请求授权，以及失败后怎样恢复。

这些问题得到可检查的答案之后，再讨论使用更大的模型、更多 Agent 或更长上下文，才更有工程意义。

> **可靠的 Computer Use Agent，不是永远不点错的模型，而是一个能够持续依据证据更新状态、约束动作、识别错误、恢复进度，并诚实说明交付边界的执行系统。**

## 附录 B：术语速查

| 术语 | 本文中的含义 | 容易混淆的地方 |
|---|---|---|
| CUA | 通过电脑界面观察、决策与执行的 Agent | 不只是截图问答或固定坐标脚本 |
| POMDP | Agent 只能观察真实状态的一部分 | 一张截图不是全部环境状态 |
| Grounding | 将语言目标绑定到界面对象或具体位置 | 知道目标是什么，不等于知道点哪里 |
| DOM | 网页文档的结构化对象表示 | 不等同于渲染后完整视觉内容 |
| AxTree / a11y tree | 可访问性树，包含元素角色、名称与状态等 | 不保证所有应用均完整支持 |
| SoM | Set-of-Marks，用框和编号标记候选对象 | 表现包含上游元素提取与映射贡献 |
| Trajectory / rollout | 一次执行中的观察、动作与结果序列 | 轨迹条数、动作数与任务数不是同一单位 |
| IL / behavior cloning | 用示范学习动作策略 | 依赖示范分布与标签质量 |
| SFT | 对示范或其他标注样本做监督微调 | 不自动具备在线错误恢复能力 |
| RLVR | 利用可验证奖励进行强化学习 | 验证器可靠性仍需单独检查 |
| GSPO | CUA-Gym 使用的序列级策略优化方法 | 算法不替代任务、环境和奖励工程 |
| Task Score | 任务得分，定义依论文而异 | 不一定等于完整成功率 |
| Success / Pass Rate | 满足论文定义的成功条件的比例 | 不同论文的成功条件可能不同 |
| Pass@k | 多次尝试中至少有一次成功的能力指标 | 不等于生产系统能选中正确结果 |
| Verifier / judge | 检查结果或过程的程序、模型或人工 | 添加该角色不等于判断已经可信 |
| Golden state | 用于检查的预期完成状态 | 一个参考状态不代表全部合法完成方式 |
| Information barrier | 对不同角色的可见信息进行限制 | 不只是给两个模型不同的角色名 |
| DAG | 以依赖关系组织子任务的有向无环图 | 动态重规划与一次性静态流程不同 |
| TTA | Gym-Anything 的 Test-Time Auditing | 审计开销仍然需要计入 |
| Working memory | 当前任务的目标、进度、证据与未解决项 | 不等同于用户长期偏好或全部对话历史 |
| Harness | 围绕模型的执行、状态、工具、限制与评测代码 | 论文分数通常是模型和 harness 共同作用 |
| Outcome unknown | 尚不能确认操作是否生效 | 不能当作确定失败后盲目重试 |
