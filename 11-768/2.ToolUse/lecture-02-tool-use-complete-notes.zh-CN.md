# 一、Basic idea：工具是什么，为什么需要工具？

> 对应讲义第 2–5 页。主要参考：[L02](#source-l02)、[P01](#source-p01)。

这节课的问题不是“怎样在 SDK 里多写一个 `tools` 参数”，而是：**一个持续预测下一个 token 的模型，怎样查询外部信息、执行计算，并改变业务系统的状态？**

讲义第 3 页给出的关键分工是：模型提出行动，外部软件决定是否执行，以及如何执行。模型不是执行器；工具调用文本本身也不是执行成功的证明。

## 1.1 工具定义、工具调用、工具实现是三件事

假设存在一个天气工具：

```python
get_weather(city="Pittsburgh")
```

**工具定义**告诉模型：工具叫什么、什么时候使用、需要哪些输入。**工具调用**是模型为本次任务生成的一份操作请求。**工具实现**则是实际连接天气数据源、发送请求、处理响应的程序。

模型写出“我正在调用天气工具”，只发生了文本生成。外部运行时识别出调用，找到实现并执行以后，才发生实际查询。可以把模型的输出理解为一张操作申请单，而不是已经盖章完成的执行回执。

《What Are Tools Anyway?》将工具定义为运行在模型外部的计算机程序的函数接口，由模型生成函数调用及参数。这里的“外部”是相对于模型而言，不一定意味着远程网络服务。本地函数、Python 解释器、数据库查询器，甚至另一个神经网络，都可以通过接口成为工具。[P01，§2.1，p.2](#source-p01)

这也解释了为什么一段提示词通常不是工具：提示词改变模型如何生成，但没有因此建立一个独立执行外部程序的接口。

## 1.2 Extend：突破信息与行动边界

讲义第 4 页首先讨论 Extend：访问模型参数中没有的信息，或者执行单纯文本生成做不到的动作。[L02，p.4](#source-l02)

用户问“公司今天新增了哪些客户”，如果信息不在上下文中，也没有业务系统接口，问题不只是模型推理能力弱，而是缺少必要的信息通道。

用户说“把邮件发给客户”，模型写出邮件正文，也不等于邮件已发送。发送需要能够修改邮件系统状态的能力。

因此，工具可以扩展两种边界：**模型能够知道什么，以及系统能够做什么。** 增加模型参数或让模型思考更久，不能代替对特定私有状态的授权访问。

## 1.3 Facilitate：把确定性操作交给更合适的计算过程

讲义的另一个词是 Facilitate：将某些操作交给更可靠或更高效的外部程序。[L02，p.4](#source-l02)

例如计算 18、23、41、54 的平均值：

```python
sum([18, 23, 41, 54]) / 4
# 34
```

工具的意义不是宣称语言模型永远不能算对，而是没有必要让概率性的语言生成承担全部精确计算责任。

不过，计算器只能准确计算收到的表达式。模型如果把“一年收益”误当“半年收益”，或者把要取平均的列选错，执行再准确，任务也会失败。

**工程推论：应当拆开检查理解、参数构造、执行和解释。**

```text
用户问题理解正确
        ↓
对象、公式、字段与参数构造正确
        ↓
程序执行正确
        ↓
执行结果被正确解释和引用
```

工具主要增强其中的某些环节，不会自动证明整条链路都正确。

## 1.4 感知、计算、行动：根据行为分类，而不是根据工具名字分类

综述将工具功能分成 Perception、Computation 和 Action，并明确指出它们可以重叠。[P01，§2.2，pp.2–3](#source-p01)

| 类别 | 解决的问题 | 例子 |
|---|---|---|
| 感知工具 | 获取环境中的信息 | 搜索网页、读取文件、查询账户状态 |
| 计算工具 | 对信息进行变换或计算 | 计算器、Python、统计分析、翻译模型 |
| 行动工具 | 改变外部环境状态 | 发送邮件、修改记录、创建订单 |

“数据库工具”可能同时属于三类。只读查询主要在获取信息；聚合计算还涉及计算；更新记录则改变状态。

**工程推论：权限和风险分类应落在具体操作上。** 一个允许 `SELECT` 的接口，与能够修改客户信息的接口，不应因为名字都带“数据库”就使用相同授权策略。

综述还从感知环境、作用于环境的经典 Agent 定义出发，讨论了只使用计算工具的模型是否应算作 Agent。这里应把它看成论文采用的概念边界，而不是全行业统一的命名规则。[P01，§2.3，p.3](#source-p01)

## 1.5 工具不是越多越好，调用也不是越频繁越好

讲义第 5 页要求比较工具收益与延迟、费用、失败概率和风险。[L02，p.5](#source-l02)

对于必须访问私有账户状态的任务，工具可能是必要条件。对于“将已给出的三句话润色”，再调一个相近能力的模型，可能只是增加延迟和故障机会。综述关于某些语言任务的讨论也指出，另一个专用神经模型不必然比主模型更有优势；这是条件性的分析，不是“语言任务永远不该使用工具”。[P01，§4.2，p.5](#source-p01)

可以用下面这个**设计思考框架**理解调用决策，它不是论文提出的精确收益估计公式：

$$
\text{调用价值}=\text{信息或行动收益}-\text{时间、费用、失败和风险成本}
$$

真正的工具使用能力包括：知道什么时候需要调用，知道什么时候不该调用，以及知道条件不足时应先询问用户。

## 1.6 是否训练工具能力，要同时看前期投入与长期调用成本

综述专门区分了训练成本和推理成本，并指出只考虑推理时，不同方法的效率比较可能发生变化。[P01，§7，p.11](#source-p01)

工程上可以进一步写成：

$$
C_{\text{total}}=C_{\text{训练与集成}}+N\times C_{\text{单次使用}}
$$

这是成本规划的简化表达。偶尔运行的内部助手，未必值得为某个工具格式做大规模训练；大量重复执行的稳定工作流，则可能值得通过训练减少长提示词、无效调用和重试。

这里还应加入维护成本：工具定义会变化，权限会变化，训练数据里的旧参数也会过时。**训练工具能力不等于把整个业务接口永久写进模型就万事大吉。**

# 二、Examples of tools：从产品能力设计工具接口

> 对应讲义第 6–12 页。主要参考：[L02](#source-l02)、[P01](#source-p01)。

## 2.1 从用户任务出发，而不是从 API 清单出发

第 7 页先问助手需要具备哪些能力，再为不同交互定义窄接口。这暗含的设计顺序是：

```text
用户任务 → 必要能力 → 工具契约 → 实际实现
```

而不是把公司所有接口一次性塞给模型，期待它自行掌握内部对象、状态码和调用顺序。[L02，p.7](#source-l02)

业务 API 往往面向熟悉系统的开发者；Agent 工具还需要帮助模型理解何时使用、参数从哪里来、返回值意味着什么。两者可以复用实现，但未必适合直接一一暴露。

## 2.2 `finish(text)`：结束循环，不等于完成任务

第 8 页的 `finish(text)` 是运行时控制动作，用于返回文本并结束 Agent 循环，不是调用外部程序。[L02，p.8](#source-l02)

**Harness** 可以先理解为包在模型外面的运行程序：组织上下文、调用模型、执行工具、回填结果、处理异常、控制循环。

有的系统显式提供 `finish`；有的系统把“不再产生工具调用的普通回答”视为本轮结束。这是运行时协议选择。

需要始终区分：

```text
模型声明结束 ≠ 用户目标已经实现
```

查询失败以后，模型也可以结束；模型误以为成功时，同样可以结束。因此任务完成需要独立的结果判定。

## 2.3 检索、执行、生成：接口相似，结果形态不同

讲义第 9–11 页分别展示以下能力：[L02，pp.9–11](#source-l02)

| 工具 | 输入 | 外部执行 | 返回对象 |
|---|---|---|---|
| `search_web(query)` | 查询表达式 | 检索信息 | 文本、条目、来源引用 |
| `execute_code(code)` | 程序 | 在隔离环境执行 | 标准输出、错误、文件 |
| `generate_image(query)` | 图像描述 | 图像生成 | 图像或文件引用 |

它们共同形成“请求—执行—观察”，但观察不一定是一大段纯文本。代码工具可以生成表格，图像工具可以返回文件，检索工具可以返回文档定位信息。

**工程推论：完整产物与模型本轮观察应分开设计。** 生成一份大型表格后，模型可能只需要文件标识、表名、行数和校验结果，不必重新读取所有单元格。详细数据应保留在可再次访问的位置，而不是只有一次性上下文。

但压缩观察不能省略关键语义。返回一个数字时，应当考虑同时保留对象、指标、时间、单位及来源；否则，后续生成很容易把数值对应关系弄错。

## 2.4 自定义函数：创建购物车不等于下单付款

第 12 页使用 `create_grocery_cart(items)` 暴露应用能力，返回购物车 C17、3 件商品和 31.42 美元。[L02，p.12](#source-l02)

这个示例包含两个执行边界：用户授权创建购物车，不自动授权支付；模型的计划不能替代实际创建结果。

下面是对课件结果的**教学性结构化改写**：

```json
{
  "status": "created",
  "cart_id": "C17",
  "item_count": 3,
  "currency": "USD",
  "total": "31.42"
}
```

`cart_id` 不是装饰字段。它让下一步操作引用真实存在的对象，而不是重新从自然语言里猜“刚才创建的那个购物车”到底是哪一个。

**好的工具输出既证明当前操作发生了什么，也为下一步提供明确输入。**

## 2.5 工具定义应回答哪些问题？

下面是由讲义接口思想推导的设计检查，不是某个协议强制要求的全部字段。

一个工具至少应说明：它适用于什么任务；每个参数的意义和来源；输出中的关键字段；失败时的反馈。对于有状态操作，还应明确副作用、授权范围，以及是否可安全重复执行。

比较两种描述：

```text
get_data：获取数据。
```

```text
get_product_return：查询指定产品在明确起止日期之间的收益数据。
产品 ID 必须来自产品解析接口或用户提供的有效标识。
返回实际查询区间、数值单位、数据截止时间及结果标识。
本工具只读，不修改产品或账户状态。
```

第二种描述不是单纯“写得更长”，而是在减少模型需要猜测的地方。真正有价值的字段是那些能影响工具选择和参数构造的字段。

## 2.6 工具数量变大后，需要增加候选工具发现阶段

综述 §5.1 区分了少量工具直接放入上下文，以及工具数量增大后先检索相关文档再交给模型的做法。文中的 5–10 个、数百个是当时的示例规模，不是现代系统统一的硬阈值。[P01，§5.1，pp.5–6](#source-p01)

```text
用户任务
    ↓
工具库中的候选召回
    ↓
提供候选工具的完整定义
    ↓
模型选择并构造调用
```

**工程推论：候选召回应考虑前置依赖，而不只是语义相似。** 用户问产品收益，语义最相似的工具是收益查询，但实际执行可能首先需要产品名称解析。遗漏解析工具以后，模型可能为了填满必填字段而猜测 ID。

评测时要把两类问题分开：正确工具没有被召回，是发现阶段的问题；正确工具已经在上下文里，模型仍然选错，才是选择阶段的问题。

权限过滤也不应只做在工具召回阶段。即使模型已经看到工具，执行端仍然应再次检查本次调用是否有权访问具体对象。

### 2.6.1 “做召回”具体怎样操作？

可以把它理解为“先找工具说明书，再让模型读说明书做选择”。下面是一条**工程实现思路**，不是某篇论文规定的唯一流程：

1. **离线建索引**：每个工具保存名称、用途、参数、限制和稳定 ID；将可检索说明编码为向量，也可以建立关键词索引。
2. **在线构造查询**：结合用户需求和当前执行状态，描述现在缺少什么能力。例如“根据产品名称取得产品 ID”。
3. **召回候选**：用关键词、向量或混合检索找出相关工具，可再重排；选多少个取决于召回质量和上下文预算。
4. **提供完整定义**：把候选工具的真实 schema 放进模型上下文。检索摘要不能替代调用所需的参数契约。
5. **按需再次发现**：执行中发现缺少前置能力时，补充检索，而不是强迫模型用现有工具猜着完成。

论文确实给出了更具体的方法。**ToolLLM** 使用训练过的稠密检索器，将任务指令与相关 API 文档匹配，以相关 API 为正例、其他 API 为负例进行对比学习。**CRAFT** 先生成期望工具的名称和说明，再结合原始问题，通过多个检索视角寻找已有工具；“期望工具”只是检索线索，不是已经存在的可调用函数。[R28](#source-r28)

### 2.6.2 召回失败和选择失败怎样分别统计？

**教学数字**：100 道题中，80 道的正确工具真正进入模型上下文，其中 60 道被模型选对：

- 候选命中率：80 / 100 = 80%。
- 候选已命中条件下的选择正确率：60 / 80 = 75%。
- 从发现到选择的整体正确率：60 / 100 = 60%。

这里假设每道题有明确可接受工具。真实评测还应允许等价工具，并检查完成任务所需的前置工具是否齐全。尤其要检查**最终交给模型的候选**：检索曾命中、后来被重排或上下文裁剪去掉，也不能算模型已经看到了正确工具。

## 2.7 一次性脚本与可复用工具之间，还隔着工程化

综述 §5.3 讨论了将经常组合的底层操作抽象成快捷工具，以及让模型创建、验证和复用程序工具。[P01，§5.3，p.7](#source-p01)

但“Agent 写了一段成功运行的代码”不等于“系统已经拥有一个可靠的新工具”。脚本可能包含当前文件路径、固定列名和只适用于本次任务的假设。

**工程建议**：将一次性代码沉淀为工具时，应去除任务硬编码，定义输入输出，补充边界检查和测试，再明确版本、权限与适用范围。这里的目标不是把所有临时脚本都收入工具库，而是保留值得复用、能够验证的抽象。

这也解释了“工具制造”和“Skill”的联系与区别：前者偏向形成可执行能力，后者还可能包含使用流程和判断策略。本文聚焦 lecture-02 的工具接口，不把两者当成同义词。

# 三、Programmatic tool calling：CodeAct 与代码元工具

> 对应讲义第 13–17 页。主要参考：[P01，§5.2](#source-p01)、[P02](#source-p02)。

## 3.1 代码的价值：让一个行动能够表达一段程序

讲义第 14 页把代码称为元工具，因为代码可以组合控制流、库函数和多个操作。[L02，p.14](#source-l02)

原子函数调用表达的是“做这一步”。代码还可以表达“对所有对象重复这一组步骤，保留中间结果，根据条件选择分支，然后汇总”。

以下代码按照 CodeAct 论文图 1 的手机价格比较示例改写；`lookup_rates` 等函数由示例环境提供，**不是可以脱离工具实现直接执行的独立程序**。

```python
countries = ["USA", "Japan", "Germany", "India"]
final_prices = {}

for country in countries:
    exchange_rate, tax_rate = lookup_rates(country)
    local_price = lookup_phone_price("CodeAct1", country)
    converted_price = convert_and_tax(
        local_price, exchange_rate, tax_rate
    )
    shipping_cost = estimate_shipping_cost(country)
    final_prices[country] = estimate_final_price(
        converted_price, shipping_cost
    )

best_country = min(final_prices, key=final_prices.get)
print(best_country, final_prices[best_country])
```

论文强调，代码原生支持变量、循环和函数组合，可以让一组操作在同一个行动内完成。[P02，§1，p.2；图 1](#source-p02)

## 3.2 控制流减少重复决策，数据流减少重复转抄

控制流决定“接下来执行什么”。上面的 `for` 循环不需要模型为每个国家重新发出相同的规划。

数据流决定“前一步结果如何进入后一步”。`local_price` 直接进入 `convert_and_tax`，而不是先转成自然语言，再让模型把数值复制进下一次调用。

**工程推论：代码能够减少不必要的模型往返，以及数据在文本与程序之间反复转换的次数。** 它也使一些错误更容易通过变量名、类型和测试定位。

但它不能保证变量选对。把半年列赋给一年变量，仍然可能是一段完全能运行的错误程序。

## 3.3 一次代码行动，不等于一次底层调用

需要分别统计：模型交互轮数、底层工具调用次数、网络请求次数。

一个循环可能只占一次模型行动，却发起二十次 HTTP 请求。普通 `for` 还可能逐个等待这些请求，并没有自动实现并行。

因此，CodeAct 的收益不能简单描述成“减少 API 调用”。在某些任务中，它主要减少模型往返，将多步组织工作交给程序。底层调用量、并发度和资源消耗仍需要单独度量。

## 3.4 CodeAct 是交互式执行，不只是生成完整脚本

论文把 CodeAct 放在 Agent—User—Environment 的循环中：模型产生代码行动，环境返回执行结果或错误，模型再根据新的观察决定下一步。[P02，§2.1，p.3](#source-p02)

例如：

```text
尝试读取数据并训练模型
    ↓
环境报告：字段里存在 "?"，不能转换为数字
    ↓
模型检查数据并处理缺失值，再次训练
    ↓
环境返回评估值
    ↓
模型根据结果继续分析或结束
```

论文第 6 页展示了使用 Pandas、Scikit-Learn 和 Matplotlib 的多轮交互，也包含多次调试。这说明它研究的是“根据执行反馈修正”，不是“一次生成永远正确”。[P02，图 3，p.6](#source-p02)

这里的运行中修正是改变后续输出，不等于在这几轮对话中对模型权重执行梯度更新。

## 3.5 第一个实验：先拿掉代码的组合优势

为了研究行动格式本身，作者在 API-Bank 的 level-1 任务上要求每次只生成一个原子调用，分别使用 Python 调用、JSON 对象和预定义文本格式，并通过实际执行输出判断正确性。[P02，§2.2，p.4](#source-p02)

这一设计暂时去掉了循环和复杂数据流的优势。对于 `gpt-4-1106-preview`，论文表 2 的结果是：

| 动作格式 | 原子调用执行正确率 |
|---|---:|
| CodeAct | 76.7% |
| JSON | 82.7% |
| 预定义文本 | 73.4% |

来源：[P02，表 2，p.5](#source-p02)。

**这组结果直接反对“Python 格式无条件比 JSON 更好”的理解。** 在这个模型、这类单步任务里，JSON 反而更高。

### 3.5.1 JSON 并不是“不用工具、让模型直接回答”

三种格式都由模型生成调用，再由外部系统解析和执行。下面是同一个日程调用的**改写教学示例**，沿用论文表 A.6 所展示的三种表达方式：[P02，表 A.6](#source-p02)

```text
Python：AddAgenda(content="项目会议", time="2026-10-01 09:00:00")
JSON：{"action":"AddAgenda","content":"项目会议","time":"2026-10-01 09:00:00"}
预定义文本：Action: AddAgenda, content: 项目会议, time: 2026-10-01 09:00:00
```

“预定义文本”指预先约定的模板，框架按模板提取工具名和参数；不是让模型随意写一句“安排好了”。实际字段仍由模型根据任务填写。

Python 也会错，因为解释器只执行程序，不知道用户本来想做什么。例如用户要求计算 `18 × 7`，模型写成 `Calculator("18 + 7")`，语法和执行都可能成功，但调用含义错误。工具选错、日期填错、漏参数和语法错误也都可能导致失败。因此表中的正确率是**不同动作格式下的原子调用执行正确率**，不能据此认定主要错误来自参数解析。

## 3.6 第二个实验：允许控制流和数据流发挥作用

M³ToolEval 包含 82 个手工构造的任务，覆盖网页、金融、行程、科学与信息处理。任务需要多工具、多轮组合，采用简单的零样例提示，最多十轮交互，最终答案使用精确匹配；平均轮数统计所有评测样本。[P02，§2.3，p.4](#source-p02)

同一个模型在表 3 中的结果是：

| 行动格式 | 任务成功率 | 平均交互轮数 |
|---|---:|---:|
| CodeAct | 74.4% | 5.5 |
| JSON | 52.4% | 7.6 |
| 预定义文本 | 53.7% | 7.7 |

来源：[P02，表 3，p.5](#source-p02)。

按表格直接计算，CodeAct 相比 JSON 高 **22.0 个百分点**，平均少 **2.1 轮**；相比文本高 **20.7 个百分点**，平均少 **2.2 轮**。论文邻近正文将 20.7 个百分点与 2.1 轮并列描述，比较口径不完全对应；这里明确采用表格列值，不把两组对照混用。

讲义展示的八个模型子集中，代码行动在八个上取得最高成功率、七个上使用最少轮数；完整十七个模型中，两项计数都是十二个。不能把子集图读成全部模型一致胜出。[L02，p.16](#source-l02)

## 3.7 实验真正证明了什么，又没有证明什么？

论文支持的结论是：**行动表示会影响复杂任务的求解能力，代码的组合能力在该实验设置下可以带来显著收益。**

它没有证明所有模型、所有任务都应替换为任意代码执行。十轮预算也很重要：代码行动一轮可完成多个底层操作，原子格式可能需要多轮。因此这里比较的是行动表示及其在交互预算下的效果，不是严格控制所有底层调用数量后的单变量对比。

另外，JSON 既能用于序列化传输，也能像本实验一样表示原子动作；CodeAct 强调用代码表达行动。外层 JSON 与内层代码可以组合：

```json
{
  "name": "execute_python",
  "arguments": {
    "code": "values = [18, 23, 41, 54]\nprint(sum(values) / len(values))"
  }
}
```

外层用 JSON 携带调用，内层仍然是代码行动。不要把“原子动作与组合程序”的比较，误写成“JSON 文件与 Python 文件”的比较。

### 3.7.1 为什么代码实验更好，工程接口仍大量使用 JSON？

JSON 调用便于按 schema 校验和接入各种语言的业务服务；代码行动则能把循环、筛选、变量传递和多个调用组合起来。前者需要框架组织执行流程，后者需要受控代码运行环境。两者可以搭配，而不是二选一。

**教学例子**：汇总十个部门的支出。如果每次只能提出一个原子调用，可能要多轮往返；代码则可以循环查询并求和，只把总数交回模型。但 JSON 框架也可以提供批量接口或并行调度，所以不能把论文中的简单 JSON 基线等同于所有现代工具系统。进一步地，“某厂商 API 返回 JSON”不能证明模型内部格式也是 JSON，相关边界见 4.5；API 类型比较见 4.20。

## 3.8 CodeActAgent 的训练：不只有 7 千条工具轨迹

论文的训练混合包含以下两部分：[P02，表 4，p.7](#source-p02)

| 数据部分 | 样本数 | 用途 |
|---|---:|---|
| CodeActInstruct | 7,139 | 学习与环境交互、工具使用和错误修正 |
| 通用对话与推理数据 | 69,230 | 保持与用户交流及一般任务能力 |

工具轨迹涉及信息搜索、软件包使用、表格／数据库访问和机器人规划。作者特别保留了先遇到错误、随后根据观察修正的轨迹。[P02，§3.1，pp.6–7](#source-p02)

消融实验表明两类数据都对 Agent 任务有贡献，通用对话数据对维持一般任务表现尤其重要。[P02，§3.2，p.8](#source-p02)

**工程推论：训练恢复能力，需要让数据包含错误、观察和有效修复；只保留一次成功的轨迹，会遗漏如何从失败状态继续工作的监督信号。** 同样，想训练一个既能做事又能沟通的助手，不应只看“调用工具”这一种输出。

## 3.9 代码中的变量存在，不代表模型知道变量内容

论文的 Impact Statement 明确提到，原型仍可能在没有打印检查变量的情况下，想象变量的内容。[P02，p.9](#source-p02)

```text
Python 内有 df
    ≠ 模型知道 df 当前的列、行数和取值

代码运行没有异常
    ≠ 数据口径符合用户要求
```

**工程建议：把计算与检查分开。** 合并表以后检查连接键唯一性、行数变化、关键字段缺失与样本；生成结论之前读取实际计算结果。不要让“已经执行过代码”成为跳过验证的理由。

## 3.10 高表达能力工具，需要更明确的执行限制

窄工具 `get_weather(city)` 的操作范围清晰；`execute_python(code)` 虽然只有一个字符串参数，却可能影响文件、网络、进程和资源使用。讲义因此要求沙箱、资源限制、权限与审计。[L02，p.17](#source-l02)

**工程建议：**把灵活的数据处理放进受限代码环境，把高影响业务写操作留在窄接口后面。不要因为需要做数据分析，就顺便给解释器生产数据库的任意写权限。

遇到必须观察结果才能决定的步骤，应保留交互检查点。巨大的单次脚本可能减少模型轮数，也可能让错误影响范围变大。选择行动粒度时，要同时考虑组合收益与可恢复性。

# 四、Mechanics of providing tools：从消息、模板到执行与反馈

> 对应讲义第 18–25 页。本章将 API、模型模板、框架源码和 Toolformer 放在同一条链路中解释。主要参考：[R01–R03](#references)、[R07–R14](#references)、[P03](#source-p03)。

## 4.1 先看完整链路：不要把所有问题都归给模型

讲义第 19–25 页可以串成下面的过程：[L02，pp.19–25](#source-l02)

```text
用户消息 + 可用工具定义
            ↓
模型适配层：聊天模板、参数编码、tokenization
            ↓
模型生成：普通回答或工具调用序列
            ↓
调用解析：识别名称、参数与调用标识
            ↓
Harness：查找工具、校验输入、检查权限
            ↓
Executor：实际执行外部程序
            ↓
Observation：结果／错误，与调用 ID 对齐
            ↓
回填对话历史，模型继续决策或生成最终回答
```

其中权限检查是对课件分发流程的工程补充。模型原生格式、API 对象、内部调用对象和工具业务结果，是不同边界上的不同表示。

如果用户看到“工具调用失败”，原因可能是模型选错工具，也可能是模板编码不对、解析器不匹配、鉴权失败或上游超时。只有把这些阶段分开，才能定位故障。

## 4.2 工具调用对模型而言，仍然是 token 序列

普通回答是 token 序列，工具调用同样如此。外部协议和运行时赋予其中某些结构“行动请求”的含义。[L02，p.19](#source-l02)

因此，函数调用不是模型在神经网络内部跳转到了 Python 函数。更接近实际的是：模型生成一个程序可以解析的请求，程序再执行对应函数。

这种分离也意味着：**能够生成看起来正确的调用，不等于拥有执行权限；拥有执行权限，也不意味着本次请求一定应该执行。**

## 4.3 `messages` 是应用层对象，不是模型直接读取的列表

开发者通常构造：

```python
messages = [
    {"role": "system", "content": "回答应基于实际查询结果。"},
    {"role": "user", "content": "Pittsburgh 现在天气怎么样？"},
]
```

课件第 20 页说明，这些消息需要经过聊天模板，变成一个模型输入序列。以简化的 Qwen 风格为例：

```text
<|im_start|>system
回答应基于实际查询结果。<|im_end|>
<|im_start|>user
Pittsburgh 现在天气怎么样？<|im_end|>
<|im_start|>assistant
```

这里最后的 assistant 起始标记，是为了提示模型开始一条新的助手消息。这是基于课件格式构造的教学示例，不是所有模型通用的模板。[L02，p.20](#source-l02)

Hugging Face 文档中的 `add_generation_prompt` 用于开始新的助手回复；`continue_final_message` 则用于继续最后一条消息，两者不能同时启用。训练预处理通常使用 `add_generation_prompt=False`。模板已经包含特殊 token 时，另行 tokenize 还要避免重复添加。[R02](#source-r02)

**工程推论：训练格式、推理模板和输出解析器要作为一个整体测试。** 模型续写到错误位置，可能是输入结束边界出了问题，而不一定是模型“不理解工具”。

## 4.4 工具定义怎样进入请求？

第 21 页采用 Chat Completions 风格，将工具声明放在 `tools` 中。下面在课件基础上增加了说明文字，便于理解参数意义：

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市的当前天气；城市存在歧义时应包含国家或地区。",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "明确的城市名称"
        }
      },
      "required": ["city"],
      "additionalProperties": false
    }
  }
}
```

调用形态为：

```python
# 示意：client、model、messages、weather_tool 由应用初始化。
response = client.chat.completions.create(
    model=model,
    messages=messages,
    tools=[weather_tool],
)
```

发送的是工具说明和输入契约，不是业务实现。模型仍然不知道天气服务的连接池或数据库密码，也不需要知道这些实现细节。[L02，p.21](#source-l02)

后面的模型适配层会把工具定义按模型所需形式暴露到输入中。**工具描述是模型用于决策的接口文档，不应仅写成无意义的名字解释。**

## 4.5 API 形式与模型原生调用形式，要分开理解

讲义第 22 页展示 JSON 风格调用，第 23 页进一步比较模型协议。[L02，pp.22–23](#source-l02)

**Qwen2.5 风格的简化调用：**

```text
<tool_call>
{"name":"get_weather","arguments":{"city":"Pittsburgh"}}
</tool_call>
```

**讲义中的 Qwen3.8 格式：**

```text
<tool_call>
<function=get_weather>
<parameter=city>
Pittsburgh
</parameter>
</function>
</tool_call>
```

**讲义中的 Mistral Small 4 格式：**

```text
[TOOL_CALLS] [{"name":"get_weather","arguments":{"city":"Pittsburgh"},"id":"abc123xyz"}]</s>
```

**讲义中的 DeepSeek V3.2 DSML 格式：**

```text
<｜DSML｜function_calls>
<｜DSML｜invoke name="get_weather">
<｜DSML｜parameter name="city" string="true">Pittsburgh</｜DSML｜parameter>
</｜DSML｜invoke>
</｜DSML｜function_calls>
```

它们都可以被适配成相同的逻辑调用，但不能因此使用一个未经测试的通用文本解析器。尤其不能把所有带尖括号的格式都当作标准 XML，或者用一个宽松正则就认定支持所有模型。

“兼容某种 API”首先说明接口层的契约。它并不单独证明聊天模板、原生工具解析、参数类型和并行行为都一致。

## 4.6 模板源码中的关键陷阱：同名 `arguments` 不一定是同一种类型

这正是阅读模板源码相对于只看讲义增加的内容。

| 所在边界 | 所给源码中的相关行为 | 需要注意什么 |
|---|---|---|
| Qwen2.5 模板 | 对 `tool_call.arguments` 使用 `tojson` | 需要避免把已经编码的 JSON 字符串再编码一次 |
| Qwen3.8 模板 | 对 `tool_call.arguments` 按键值项迭代，再序列化值 | 此路径期待可按键值项读取的参数对象 |
| DeepSeek V3.2 编码入口 | 先调用 `json.loads(tool_call["arguments"])` | 这个入口先接收 JSON 字符串，再转对象 |

来源：[R03](#source-r03)、[R08](#source-r08)、[R11](#source-r11)。以上是对应文件中这些路径的行为，不是所有版本、所有 SDK 的统一约定。

例如：

```python
import json

arguments = '{"city": "Pittsburgh"}'
print(json.dumps(arguments))
# 输出的是包含 JSON 文本的字符串，而不是原来的参数对象：
# "{\"city\": \"Pittsburgh\"}"
```

**工程建议：内部统一保留结构化参数对象，让各模型适配器负责边界转换。** 不要让字典和 JSON 字符串在系统里无规则地流动。

下面是只处理表示归一化的教学函数；它不代替 schema、权限或业务检查：

```python
import json
from typing import Any


def normalize_arguments(raw: str | dict[str, Any]) -> dict[str, Any]:
    """把接口传入的 JSON 字符串或参数字典统一为对象。"""
    if isinstance(raw, str):
        try:
            value = json.loads(raw)
        except json.JSONDecodeError as exc:
            raise ValueError("工具参数不是完整的 JSON") from exc
    elif isinstance(raw, dict):
        value = dict(raw)
    else:
        raise TypeError("工具参数必须是 JSON 字符串或字典")

    if not isinstance(value, dict):
        raise ValueError("工具参数顶层必须是对象")
    return value
```

该函数只完成“字符串变对象”。生产边界还要处理输入大小、重复键策略、非标准数值、字段契约及访问控制，不能因为 `json.loads` 成功就执行。

## 4.7 工具结果的 API 角色，也不一定直接变成同名模型角色

Qwen2.5 模板会将连续工具结果包装在带 `<tool_response>` 标记的 user 消息块中。[R03](#source-r03)

这不是在授权外部内容变成用户指令，而是模型输入的序列化约定。需要区分：应用层对消息来源与权限的分类，以及模型训练时采用的 token 表示。

**工程推论：信任边界不能只依赖最终字符串里写着哪个角色名。** 外部检索内容中出现“忽略之前指令”，仍然只是检索内容；是否允许操作应由系统权限决定，而不是由被检索文本决定。

## 4.8 Mistral 的 tokenization guide 还说明了版本差异

该指南比较 V2、V3 与 Tekken，包括调用 ID、工具结果包装方式和空格表示的差异。[R10](#source-r10)

因此，看到 `[TOOL_CALLS]` 只是认出某类控制标记，不等于读懂完整协议。工具定义如何排列、结果是否有列表包装、ID 怎么对应、消息何时终止，都可能影响适配。

Mistral Small 4 模型卡的服务示例还显式设置工具调用解析器；其中的计算器演示使用了 `eval(expression)`。[R09](#source-r09)

**工程建议：模型卡中的最小演示不能直接视为安全生产实现。** 在受信任应用进程中执行模型任意表达式，会扩大操作范围。算术工具应限制可执行运算；需要通用代码时，应使用独立、受限的执行环境。

## 4.9 调用 ID、助手消息和工具结果必须形成可追踪关系

Chat Completions 的函数工具调用中，`function.arguments` 是 JSON 字符串，调用包含 ID；工具结果使用 `tool_call_id` 对应前面的调用。[R01](#source-r01)

例如，以下是教学请求对象：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\":\"Pittsburgh\"}"
      }
    }
  ]
}
```

工具结果再以匹配 ID 回填：

```json
{
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "72°F · sunny"
}
```

这个天气值是讲义中的示例，不是现实天气查询。[L02，p.25](#source-l02)

完整历史要保留“用户问题—助手调用—工具结果—后续回答”的关系。多个调用同时存在时，不能仅凭到达顺序猜它们属于谁。

讲义第 22 页示例把 ID 的附加放在 API 层，第 23 页又展示了包含 ID 的模型原生格式。工程上不应把“所有协议的 ID 都必定由同一层产生”当作事实；应保证结果始终能对应正确调用。

## 4.10 `tool_choice`、流式输出和结束原因是不同控制点

`tool_choice="required"` 要求产生一个或多个工具调用，不保证任务成功；强制指定某个函数，也不等于该函数适合当前任务。[R01](#source-r01)

**工程推论：**在循环每一轮都强制调用，可能导致已经完成查询后还继续发出无意义调用。控制策略应与当前任务阶段一致。

流式函数调用还需分别累积各个调用的参数片段，官方指南使用调用的 `index` 来组织增量。[R07](#source-r07)

对于有副作用的操作，应在完整调用到达、完成解析与授权以后执行，而不是看见工具名称就启动。输出被截断、结束原因不符合预期时，也不能将半截参数自动补成一份“看起来可执行”的请求。

## 4.11 OpenHands：从注册到 Action—Executor—Observation

讲义第 24 页先展示工具注册，再展示调用分发。[L02，p.24](#source-l02)

```text
初始化：工具配置 → resolve_tool → 具体定义 → tools_map[name]

每次调用：解析 → 查找定义 → 构造并验证 Action
                      → Executor 执行 → Observation → 事件回填
```

| 对象 | 主要职责 |
|---|---|
| ToolDefinition | 将名称、说明、输入输出结构和执行器绑定起来 |
| Action | 一次操作的结构化输入 |
| Executor | 执行实际逻辑，必要时管理连接、进程等资源 |
| Observation | 执行结果或环境反馈 |
| 调用／结果事件 | 将一次操作与整个会话历史关联 |

OpenHands 文档使用 Action—Observation 契约，并提供面向模型的 `to_llm_content` 表达。原生工具与 MCP 工具可通过相应路径进入工具系统。[R12](#source-r12)

这使工具业务结果与模型本轮需要阅读的内容有机会分开设计。但不要把架构文档的分层描述误读为所有版本中的执行器都绝对不能接收会话信息：本次读取的源码中，执行路径也可以接收 `conversation`。应区分设计边界与具体版本的函数签名。[R14](#source-r14)

## 4.12 源码补充：验证输入与验证输出是两个方向

本次读取的 `tool.py` 中，`action_from_arguments()` 使用 Action 类型构造、验证输入；执行后，若声明了 observation 类型，会按该类型接收或验证结果，否则走通用 Observation 包装路径。[R14](#source-r14)

因此，更准确的理解是：框架为输入与输出提供契约边界，但检查强度仍取决于你声明的类型、约束和校验逻辑。

**工程推论：**上游接口成功返回，不代表下游拿到的数据符合约定。字段消失、单位变化、对象类型变化，都应作为输出契约问题处理，而不是直接交给模型自行“理解一下”。

类型校验也不等于语义校验。`temperature: float` 无法单独证明温度单位正确；`customer_id: str` 无法证明当前用户有权读取该客户。

## 4.13 工具结果进入上下文以后，仍然可能被误读

假设工具返回：

```json
{
  "metric": "period_return",
  "period": "6M",
  "value": 0.08,
  "unit": "ratio"
}
```

模型却写成“过去一年收益为 8%”。这里调用可能正确、执行成功、数值没有抄错，但周期关联错了。这是教学示例，不是真实产品业绩。

**工程建议：**重要事实应以带上下文的记录保存，而不是只保留一个数字。长任务中可以通过稳定结果标识重新读取事实；撰写后还应检查对象、指标、时间和单位的绑定关系。

外部结果还可能包含不可信的指令性文本。MCP 工具规范要求服务端做访问控制和输出处理，并建议客户端在敏感操作、结果验证方面实施保护。[R23](#source-r23)

所以，工具结果应作为证据和数据进入后续决策，而不应被自动提升为系统指令。

## 4.14 Toolformer：模型怎样学会在适当位置提出调用？

先用一句话把握：**模型自己提议工具调用，系统检查哪些调用有助于续写已有文章，把有帮助的调用变成训练示范。** 它不是在 Transformer 里面装一个能直接访问 API 的执行器。

前面的内容解释了调用如何执行。Toolformer 研究另一个问题：**怎样构造训练数据，让模型学习工具选择、调用位置、参数和结果利用，而不是为每个任务编写大量人工标注？**[P03，§1–2，pp.1–2](#source-p03)

它没有在 Transformer 内部加入一个真正执行 API 的模块，而是在普通文本中插入工具调用及结果，再训练模型生成这类序列。

论文研究五类工具：问答系统、Wikipedia 检索、计算器、翻译系统与日历接口。其中日历接口只是返回当前日期，不是完整的日程管理系统。[P03，§3，p.4](#source-p03)

### 4.14.1 第一步：寻找调用位置并生成候选

原始文本为：

```text
Pittsburgh is also known as the Steel City.
```

模型可以提出两个候选问题：

```text
QA("What other name is Pittsburgh known by?")
QA("Which country is Pittsburgh in?")
```

第一个可能帮助完成“Steel City”，第二个虽然是一个合法问题，却未必有助于当前文本续写。

论文用少量工具示例提示模型，对每个可能位置计算开始调用的概率，筛选位置，再采样候选调用。[P03，§2，p.3；图 2](#source-p03)

这里的位置采样阈值、候选位置数和每个位置的采样数，是数据生成参数，不要与后面推理时调整调用倾向的参数混为一谈。

### 4.14.2 第二步：真实执行候选调用

对每个候选调用执行相应工具，取得文本结果。这里不能让模型自己编一个返回值，再声称已经获得外部反馈。[P03，§2，p.3](#source-p03)

例如第一项返回 `Steel City`，第二项返回 `United States`。下一步才判断它们是否值得进入训练集。

### 4.14.3 第三步：用后续文本预测损失筛选有帮助的结果

设原文是 $x_1,\ldots,x_n$，候选调用位于位置 $i$。论文定义加权的后续预测损失：

$$
L_i(z)=-\sum_{j=i}^{n}w_{j-i}\log p_M(x_j\mid z,x_{1:j-1})
$$

其中 $z$ 表示提供给模型的额外调用信息；$e(c,r)$ 表示调用及结果的序列化形式。比较：

$$
L_i^+=L_i(e(c,r))
$$

$$
L_i^-=\min\bigl(L_i(\varepsilon),L_i(e(c,\varepsilon))\bigr)
$$

仅保留：

$$
L_i^- - L_i^+\geq\tau_f
$$

来源：[P03，§2，p.3](#source-p03)。

直白地说，加入真实结果以后，模型需要比“不调用”以及“只有调用、没有结果”这两种对照中的较好者，预测得更好。

为什么要保留“只有调用、没有结果”的对照？因为问题本身就可能成为提示。这个对照用于判断外部结果是否带来额外信息，而不只是调用文字让模型想起答案。

### 4.14.4 一个实现细节：筛选时前置，训练时插入

论文脚注说明，筛选阶段把候选调用及结果作为前缀，而不是直接插入原文中间。理由是此时模型尚未针对中间插入 API 的格式微调，贸然插入可能破坏原有文本分布，影响损失比较。

随后真正构造微调数据时，才把保留的调用插入相应位置。[P03，p.3 脚注 3、§2 微调部分 pp.3–4](#source-p03)

这说明训练数据管线不只是“插入一个标记”这么简单：生成、筛选与训练阶段可以使用不同表示，但必须理解这种差异的目的。

### 4.14.5 第四步：微调与推理暂停机制

筛选后的调用和结果插入原文，模型使用标准语言建模目标微调。实际生成时，模型产生结果分隔标记后，外部系统暂停生成，执行 API，插入真实结果和结束标记，再继续生成。[P03，§2，p.4](#source-p03)

论文中的 `<API>` 等是说明用记号，实际实现使用已有的括号和箭头 token 序列，避免修改词表。[P03，p.2 脚注 1](#source-p03)

因此，学会输出调用标记与真实执行仍然分离；训练不会消除对运行时的需要。

### 4.14.6 用“18 支铅笔 × 7 盒”走完整个流程

以下为**教学示例**。已有原文是：“每盒有 18 支铅笔，买了 7 盒，一共有 126 支铅笔。”制作数据时已经知道后文是 `126`，可以用它检查候选调用的价值。

```text
候选 A：Calculator("18 * 7") → 实际返回 126
候选 B：Calculator("18 + 7") → 实际返回 25
```

接着测量模型预测原文后续文字的困难程度，也就是损失。假设 A 对应如下结果；这些数值并非实测：

| 提供的信息 | 后文预测损失，越低越好 |
|---|---:|
| 没有调用信息 | 2.0 |
| 只有算式调用，没有结果 | 0.4 |
| 有调用及真实返回值 126 | 0.3 |

外部结果的额外收益只有 `0.4 − 0.3 = 0.1`，不是 `2.0 − 0.3 = 1.7`：算式本身已经帮助模型想起了答案。是否保留，要看 0.1 是否达到筛选门槛；不能只看结果碰巧与答案一致。

筛选通过以后，才构造类似“……一共有 `[Calculator("18 * 7") → 126]` 126 支铅笔”的训练示范。真正使用时，模型提出新算式，外部运行时执行并回填结果，再让模型继续生成。训练中的候选筛选与使用时的真实执行，是两个不同阶段。

## 4.15 Toolformer 的训练信号是局部收益，不是长程任务成功

论文实际采用：

$$
\widetilde w_t=\max(0,1-0.2t),\qquad
w_t=\frac{\widetilde w_t}{\sum_s\widetilde w_s}
$$

距离较远的位置权重降为零，意图是让调用靠近信息马上派上用场的地方。[P03，§4.1，p.5](#source-p03)

所以该信号更接近“工具结果是否让紧接着的文本更容易预测”，不是“这个动作是否让十步以后的业务任务更容易成功”。

例如，一次必要的对象 ID 解析，可能只在后面的查询中体现价值。**工程推论：要训练长程 Agent，不能只照搬局部续写收益就认为已经覆盖任务级信用分配。**

## 4.16 Toolformer 的效果还包含推理策略与调用预算

论文下游实验使用贪心解码，但对调用开始做了修改：只要 `<API>` 进入前十个候选，就允许触发，而不要求它是最可能的 token。同时每个输入最多调用一次，避免陷入持续调用。[P03，§4.2，pp.5–6](#source-p03)

所以应把效果归因拆开：

```text
数据构造 + 微调 + 调用触发策略 + 调用预算
```

不能全部归结为“微调以后模型自然而然就知道何时调用”。论文还观察到提高调用倾向会改变调用覆盖范围和校准行为。[P03，§5，p.9](#source-p03)

## 4.17 区分训练收益与真实工具执行收益

Toolformer 的实验包含原模型、在同一普通语料上继续训练的模型、工具模型但禁用调用，以及允许调用的工具模型。这些对照分别帮助观察继续训练、调用数据和实际执行的作用。[P03，§4.1，p.5](#source-p03)

以论文 ASDiv 结果为例：

| 设置 | 论文报告结果 |
|---|---:|
| GPT-J | 7.5 |
| GPT-J + CC | 9.6 |
| Toolformer，禁用调用 | 14.8 |
| Toolformer，允许调用 | 40.4 |

来源：[P03，表 4，p.6](#source-p03)。这些是历史实验中的百分比结果，不用于预测当前模型表现。

禁用工具后仍有改善，说明训练数据本身可能带来收益；允许真实执行以后进一步改善，才体现执行层的贡献。语言建模能力是否保持，也要相对于匹配的继续训练对照理解，不是宣称所有任务都完全没有变化。

## 4.18 Toolformer 的边界，以及它与 CodeAct、XGrammar 的关系

论文明确指出其训练中缺少链式调用样本，不能充分支持交互式搜索；还存在输入措辞敏感、部分工具样本生成效率低，以及没有考虑工具调用计算成本的问题。[P03，§7，p.11](#source-p03)

以下方法与运行时组件解决不同层面的问题：

| 方法 | 主要问题 |
|---|---|
| Toolformer | 怎样学习何时调用、调用什么，以及利用结果 |
| CodeAct | 怎样表达和组合一个行动 |
| XGrammar | 怎样限制生成结构，并降低约束计算开销 |
| Harness | 怎样真实执行、回填结果和管理运行过程 |

它们不是互相替代的框架名称，而是可以位于同一个系统中的不同层。

## 4.19 延伸：DeepSeek、Kimi、GLM 怎样训练工具使用能力？

**版本范围**：这里阅读的是 DeepSeek-V3.2、Kimi K2 和 GLM-5 技术报告。它们不是相应厂商所有版本的通用配方，也不能把 GLM-5 报告直接当成 GLM-5.3 的完整训练说明。以下重点是已公开的方法，而不是推测未披露的内部流程。

### 4.19.1 Kimi K2：批量制作工具使用示范

Kimi K2 §3.1.1 描述的流程是：收集真实及合成工具说明，组合工具并生成任务及成功标准，再生成多轮交互轨迹，最后按标准筛选成功示范用于监督微调。部分反馈来自维护状态、可模拟失败的工具模拟器；代码等场景补充真实执行沙箱。后训练还包含强化学习。[R29，§3.1.1、§3.2](#source-r29)

这说明“合成数据”不只是在生成问答，也可以在生成“调用—反馈—再调用”的完整示范；同时，模拟器反馈与真实执行反馈要区分，不能把所有样本都说成实际运行了外部 API。

### 4.19.2 DeepSeek-V3.2：生成环境、工具、任务和验证器

DeepSeek-V3.2 先通过提示组合已有推理与工具使用能力，取得冷启动轨迹，再进行强化学习。搜索、代码工程等使用真实工具；通用任务可以自动合成数据库、工具函数、任务和验证程序。参考解法被限制通过工具接口访问数据，任务逐步增加难度。核心设计是**求解有挑战，但完成情况可以验证**。[R30，§3.2.2–3.2.3](#source-r30)

与 Toolformer 的后文损失筛选相比，这里更直接地利用任务环境中的反馈。工具能运行还不够，训练系统还需要能可靠判断结果的验证器。

### 4.19.3 GLM-5：学习长程操作与错误恢复

GLM-5 的监督微调包含工具和 Agent 轨迹，借助执行环境、专家强化学习及筛选提高质量。一个具体细节是：保留轨迹中的错误片段作为上下文，但屏蔽其训练损失，以学习后续纠错而不直接模仿错误。之后在软件工程、终端、搜索等可验证任务上进行 Agent 强化学习；论文介绍了从真实项目问题、容器环境和测试脚本构造训练任务的流程。[R31，§3.1、§3.3、§4.2](#source-r31)

这里“屏蔽错误片段的损失”属于训练目标处理，与 XGrammar 在生成时屏蔽非法候选 token 不同。

### 4.19.4 从一条交互轨迹理解 SFT 和 RL

下面是**自拟教学轨迹**，不是上述论文原始样本：

```text
任务：查询 ORD-17 的物流。
工具说明：get_order(order_id)，get_tracking(tracking_id)。
模型：get_order("ORD-17")
环境：tracking_id = "SF123"
模型：get_tracking("SF123")
环境：正在配送
模型：你的订单正在配送。
```

监督微调（SFT）提供值得模仿的示范，使模型在“已经取得快递单号”的上下文下更倾向于调用物流查询。强化学习（RL）则让模型尝试交互过程，依据奖励更新行为倾向。若模型跳过订单查询、随便编一个单号，即使调用格式正确，也不应获得任务成功奖励。

训练的对象仍然是模型参数，不是把物流 API 装进神经网络。运行时负责执行调用和提供观察。训练系统也不应仅按“调用了多少次工具”奖励，否则可能鼓励无意义调用。

| 比较项 | Toolformer | 上述报告中的任务轨迹训练 |
|---|---|---|
| 主要学习材料 | 普通文本中补入的有用调用 | 任务、工具、环境反馈构成的交互过程 |
| 核心筛选／反馈信号 | 调用结果降低后文预测损失 | 成功标准、验证程序、奖励或轨迹质量 |
| 重点理解 | 怎样自动发现局部有帮助的调用 | 怎样在多步操作中推进任务并纠错 |

现代报告采用合成数据、SFT 或 RL，不等于它们照搬了 Toolformer；没有披露某方法，也不足以断言内部绝未使用过。

## 4.20 延伸：Chat Completions 与 Responses API 的区别

这是**接口协议层**的比较，不是两个模型，也不是 JSON 与 CodeAct 的对立。OpenAI 官方文档建议新项目使用 Responses，同时继续支持 Chat Completions；第三方平台是否支持相同接口，需分别确认。[R32](#source-r32)

| 比较项 | Chat Completions | Responses |
|---|---|---|
| 请求入口 | `/v1/chat/completions` | `/v1/responses` |
| 主要输入 | `messages` 消息列表 | `input` 字符串或输入项 |
| 主要输出组织 | `choices` 下的助手消息 | `output` 中的消息、函数调用等带类型的项 |
| 会话衔接 | 通常由应用组织历史消息 | 可手动组织历史，也可使用响应关联或 Conversations |
| 自定义函数执行 | 应用执行并回填结果 | 同样需要应用执行并回填结果 |

下面仅比较最小调用形状，假设 `client` 已初始化、`MODEL` 在对应端点可用；不是部署示例：

```python
chat = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "解释工具调用"}],
)
print(chat.choices[0].message.content)

response = client.responses.create(
    model=MODEL,
    input="解释工具调用",
)
print(response.output_text)  # SDK 提供的文本聚合属性
```

Responses 的 `output` 不一定只有一段文本；包含函数调用时，应用应按类型处理输出项。使用 `previous_response_id` 衔接也不表示历史上下文无限或免费。平台内置工具可以由平台执行，而自定义业务函数不会因为切换到 Responses 就自动在本地运行。[R32](#source-r32)、[R07](#source-r07)

选择哪套 API，取决于服务支持和应用需求；不能由接口名称推出任务成功率。Chat Completions 可以调用执行代码的工具，Responses 也可以只做一次简单的天气查询。

# 五、Constrained decoding：JSON Schema 与 XGrammar

> 对应讲义第 26–35 页。主要参考：[P04](#source-p04)、[R15](#source-r15)、[R16](#source-r16)。

**先读这一句**：JSON Schema 规定输出应符合什么结构，约束解码在生成过程中排除违规候选，XGrammar 研究如何把这些检查做得足够快。第五章前半讲“怎样约束”，后半讲“怎样高效约束”；它主要不涉及训练模型理解用户意图。

## 5.1 为什么工具调用需要结构约束？

自然语言少一个逗号，人可能仍然读懂；函数参数缺一个右括号，程序可能直接无法解析。讲义第 27 页用缺少 `}` 的调用说明这一问题。[L02，p.27](#source-l02)

但“合法”不止一层：

| 层次 | 需要保证什么 | 示例错误 |
|---|---|---|
| 语法 | JSON 等格式完整有效 | 少一个 `}` |
| 字段结构 | 使用预期字段 | 应该是 `city`，却写成 `location` |
| 类型 | 字段类型符合要求 | `city` 是数字 |
| 值域 | 值在许可范围内 | 只允许 C/F，却传 K |
| 任务语义 | 对象与参数符合用户意图 | 格式完全正确，却查询了另一座城市 |
| 权限与业务条件 | 本次操作被允许 | 客户 ID 合法，但用户无访问权限 |

前四项对应讲义第 28 页的主要结构层次，后两项说明其边界。**结构正确不等于事实正确、工具选择正确、权限正确或任务完成。**[L02，p.28](#source-l02)

## 5.2 JSON Schema 是描述数据契约的语言

讲义给出的 schema 类似：

```json
{
  "type": "object",
  "properties": {
    "city": {"type": "string"},
    "units": {"enum": ["C", "F"]}
  },
  "required": ["city"],
  "additionalProperties": false
}
```

来源：[L02，p.29](#source-l02)。

逐项理解：顶层是对象；`city` 是字符串；`units` 若出现，只能是 C/F；`city` 必须出现；不允许其他字段。

这里有几件容易混淆的事。`properties` 不是必填列表，所以 `units` 可以不出现；`required` 只要求存在，不能单独排除空字符串；`additionalProperties: false` 限制额外字段，不会自动把所有字段设为必填。

因此 `{"city":""}` 可能通过这份 schema，却不适合发送给真实天气查询器。要防止空字符串，还需要相应约束或业务检查。

## 5.3 断言、注解与实现支持，不是一回事

JSON Schema Core 区分断言、注解和子 schema 应用等概念；Validation 定义具体的验证语义。`description`、`default` 等信息不应被理解为自动执行的业务逻辑，声明默认值也不意味着所有校验器都会替你填入。[R15](#source-r15)、[R16](#source-r16)

`format` 还需要特别注意：2020-12 区分 Format-Annotation 与 Format-Assertion，具体是否严格验证取决于词汇表和实现配置。[R16，§7](#source-r16)

```json
{"type": "string", "format": "date"}
```

看到这段 schema，不能未经检查就断定日期格式已经由当前系统强制保证。

**工程上应分别确认三个问题：标准能表达吗？生成服务支持吗？执行端真的验证了吗？** 一份合法的 schema，不等于任意推理服务都完整支持它。

## 5.4 OpenAI strict 模式是特定 API 契约，不等于完整 JSON Schema

官方函数调用指南说明，strict 模式要求对象关闭额外属性，并将声明的属性列为 required；可选性可以用可空类型表示，且支持的 schema 功能存在范围限制。[R07](#source-r07)

下面是本文构造的**可空字段教学示例**，不是对官方示例的逐字复制：

```json
{
  "type": "object",
  "properties": {
    "city": {"type": "string"},
    "units": {
      "type": ["string", "null"],
      "enum": ["C", "F", null]
    }
  },
  "required": ["city", "units"],
  "additionalProperties": false
}
```

这里 `units` 必须存在，但允许为 `null`。同时声明类型和 `enum` 时，值要满足两者；因此示例的 `enum` 也列入 `null`。

应用还要定义 `null` 的业务意义，例如使用明确默认单位或向用户确认，不能让模型和执行器各自理解。

## 5.5 生成后校验与生成时约束，有什么不同？

生成后校验是：

```text
模型生成 → 解析／验证失败 → 返回错误 → 模型重写
```

生成时约束是：

```text
模型给出下一 token 的分数
    ↓
结构引擎屏蔽必然不合法的候选
    ↓
只在允许候选中选择下一个 token
```

XGrammar 研究如何高效完成第二种方式。[P04，§2.1，p.3](#source-p04)

两者不互斥。即使启用约束解码，最终仍应检查完整性、受支持的 schema 约束、业务参数和权限。尤其是输出被 token 上限截断时，合法前缀不一定已经构成完整调用。

## 5.6 为什么需要上下文无关文法和下推自动机？

JSON 可以嵌套对象和数组：

```json
{
  "items": [
    {"name": "milk"},
    {"name": "coffee"}
  ]
}
```

解析器不仅要知道“下一步期待字符串还是分隔符”，还要记得当前数组完成以后返回哪个对象。

上下文无关文法 CFG 用规则和递归组合描述结构；下推自动机 PDA 在局部状态之外加入栈，处理嵌套规则与返回位置。[P04，§2.2，p.3](#source-p04)

可以先用括号栈形成直觉：

```text
进入对象       [object]
进入对象内数组 [object, array]
数组结束       [object]
对象结束       []
```

论文的栈更具体：它保存语法规则展开与返回的位置，而不只是括号类型。栈顶描述当前规则位置，较深的栈元素记录完成当前规则后回到哪里。

讲义所说的任意深度嵌套，是这种模型的表达能力；实际实现仍受内存和资源限制。不能据此推导系统真的拥有无限执行资源。[L02，p.31](#source-l02)

## 5.7 Token 边界，不是语法单元边界

这是理解 XGrammar 的关键。

假设已经生成：

```text
{"city":"Pittsburgh","units":
```

若词表中某个候选 token 解码后是 `"F"}`，它会一次跨越开始字符串、字符 F、结束字符串、结束对象几个语法步骤。该例用于解释边界，不是在断言所有 tokenizer 都存在这个具体 token。

不能只检查首字符合法，就接受整项；也不能要求每个 token 自己就是一个完整 JSON。需要检查的是：**整个候选接到已有前缀后，是否仍能沿语法规则继续形成合法结果。**

XGrammar 使用字节级 PDA，以应对 token 跨越语法边界以及可能只覆盖部分 UTF-8 字节的情况。[L02，p.32](#source-l02)；[P04，§3，p.4](#source-p04)

## 5.8 Token masking 怎样改变下一步概率？

模型为词表中的候选 $v$ 给出 logit $z_v$。语法引擎判断它当前是否允许，记为 $m_v$：

$$
\widetilde z_v=
\begin{cases}
z_v,&m_v=1\\
-\infty,&m_v=0
\end{cases}
$$

再计算：

$$
p(v)=\operatorname{softmax}(\widetilde z)_v
$$

非法候选概率变为零，合法候选之间按原有相对分数重新归一化。结构引擎决定许可集合，模型在许可集合中继续选择。[P04，§2.1、图 2，p.3](#source-p04)

这个机制不知道 Pittsburgh 的真实天气，只知道此处怎样写才符合规定的结构。结构约束不是外部事实验证器。

### 5.8.1 用天气参数理解“禁止选”和“选正确”的区别

**教学示例**：用户要求查询北京天气、使用摄氏度。schema 规定 `city` 为字符串、`units` 只能为 `C` 或 `F`。当生成到 `units` 的值时，规则会排除走向 `K`、数字或其他非法值的候选；实际检查按 token 进行，不一定一步生成完整字段。

但以下对象依然符合这份 schema：

```json
{"city": "上海", "units": "F"}
```

它的城市和单位都不符合用户需求。若要强制只能填写北京，需要应用先确定北京才是正确城市，再把约束缩小；这个语义判断并非通用结构引擎自动完成。

提示词里的“请遵守 JSON 格式”是要求模型尽量遵守；token masking 则将非法候选的概率置零。它保证受支持规则下的生成约束，但长度上限等仍可能截断输出，因此最终要检查是否完整。

## 5.9 最朴素的实现，为什么会变慢？

每生成一个 token，都检查整个词表中的候选；每个候选又可能跨越语法规则、触发入栈和出栈。

词表大、语法复杂、并发生成多时，CPU 上的解释和状态管理可能成为瓶颈。另一方面，完整栈的组合空间不能简单全部预先枚举。[P04，§1，p.1；§2.2，pp.3–4](#source-p04)

XGrammar 的主要思路不是给模型换一组权重，而是拆分“可以预先决定的结构工作”和“必须运行时判断的少量工作”。

## 5.10 优化一：按局部语法位置缓存大多数候选的判断

论文把候选分成两类：[P04，§3.1，p.4](#source-p04)

**上下文无关候选**：仅凭当前局部规则位置就能判断。**上下文相关候选**：需要结束当前规则、回到父规则并查看更深的栈，才能判断剩余内容。

这里的“上下文”是语法解析上下文，不是模型聊天记录。

每个局部位置可以预计算大量接受／拒绝结果，运行时只解释少量依赖完整栈的候选。论文在 Llama-3.1 与 JSON 语法的特定设置中报告，需要这类动态判断的 token 为 128k 词表中的 1,134 个；这不是任意模型或语法上的固定数量。

存在多个仍成立的解析路径时，要取各路径允许候选的**并集**：只要其中一条合法路径能够继续，就不能提前屏蔽该候选。[P04，§3.1，p.4](#source-p04)

## 5.11 优化二：缓存表示也要适应数据分布

缓存并不是对每个状态都机械保存一整张同样大的表。论文将词表分为已知接受、已知拒绝和运行时待判断三部分，并根据分布选择表示：[P04，§3.1，pp.4–5](#source-p04)

| 情况 | 更节省的表示思路 |
|---|---|
| 大部分候选允许 | 主要保存拒绝项与待判断项 |
| 大部分候选拒绝 | 主要保存允许项与待判断项 |
| 两边接近 | 使用位集合等表示 |

论文在特定模型与 JSON 语法设置中报告，缓存内存从 **160 MB 降到 0.46 MB**。这是一种系统优化结果，不是模型显存整体减少到这个数值。

多个解析栈的 mask 合并，也可以利用接受集合与拒绝集合的互补关系，尽量只对小集合运算，而不是每次扫描完整词表。[P04，算法 1，p.5](#source-p04)

**工程启发：缓存性能取决于缓存什么、按什么状态索引，以及怎样存储和合并，而不只是有没有缓存。**

## 5.12 优化三：上下文扩展，提前拒绝更多不可能的候选

有些候选看起来必须返回父规则才能判断，但分析语法后会发现：它无论返回哪个可能位置，剩余部分都不合法。

XGrammar 预先分析当前规则完成后可能接受的后缀，尽早排除这些候选。论文同一设置中，动态依赖候选从 **1,134 个进一步减到 120 个**。[P04，§3.2，pp.5–6](#source-p04)

这不是把全部运行时栈枚举出来，而是利用可静态得到的上下文信息缩小运行时工作量。

## 5.13 优化四：持久化栈支持分支、回滚与共享前缀

如果每尝试一个候选就复制整条解析栈，状态管理会很贵。论文使用持久化执行栈，让不同路径共享相同的底部结构，只保存分支变化；回滚时恢复相应的栈顶指针。[P04，§3.3，pp.6–7](#source-p04)

这里的“持久化”是数据结构中的历史版本保留和结构共享，不是把每一步写入数据库。

它还可以减少候选词公共前缀的重复检查。例如 `read`、`ready`、`reader` 共享前缀；按一定顺序检查并恢复到公共前缀状态，就不必从头重复解析每个字符。

这一思想同样解释了为什么语法状态要与生成分支、回滚操作一起管理：模型输出回滚了，解析器状态却没回滚，会出现两套状态不一致。

## 5.14 优化五：规则内联与节点合并

论文借用编译器优化思想，将一些很小的规则内联进父规则，减少额外跳转；同时合并符合条件的自动机节点，减少无谓分支与并行栈数量。[P04，§3.4，pp.7–8](#source-p04)

内联并不是越多越好，论文也限制内联规模，避免自动机体积膨胀。

**工程启发：有时计算瓶颈来自表示方式，而不是单个函数不够快。** 先减少需要解释的状态和分支，可能比优化一次入栈操作更有效。

## 5.15 优化六：CPU 生成 mask，与 GPU 模型计算重叠

模型计算下一步 logits 和语法引擎生成下一步 mask，都依赖已经生成的 token。论文将两项计算分别放在 GPU 与 CPU 上重叠，在采样前同步；缓存构建也可以与 prefill 重叠。[P04，§3.5，p.8](#source-p04)

用简化模型理解：

$$
T_{\text{串行}}\approx T_{\text{模型}}+T_{\text{mask}}
$$

$$
T_{\text{重叠}}\approx\max(T_{\text{模型}},T_{\text{mask}})+T_{\text{同步}}
$$

这两个式子是对重叠执行的教学解释。所谓接近零额外开销，不是没有做额外工作，而是额外工作在特定负载下可能被模型计算覆盖。若 CPU 饱和、语法复杂或预处理成本很高，仍需实际测量。

## 5.16 消融实验：真正的大幅改善发生在哪里？

论文逐步添加优化，测量的是 **mask 生成的平均每 token 延迟**：[P04，表 3、§4.3，p.10](#source-p04)

| 配置 | 延迟，ms/token |
|---|---:|
| 朴素 PDA | 65.776 |
| 加入节点合并 | 38.280 |
| 加入自适应 token mask 缓存 | 0.154 |
| 再加入规则内联 | 0.035 |
| 再加入上下文扩展 | 0.018 |

这是同一个逐步优化实验，不能把每行理解成互相独立的贡献，也不能把 0.018 ms 当成完整模型的生成速度。

最大的跃迁出现在缓存之后：大量工作从逐 token 解释，变为预先处理、运行时读取。随后结构优化进一步减少剩余计算。

论文还在 MLC-LLM、Llama-3.1 8B 的测试中报告，JSON Schema、batch size 1 的 TPOT 从不启用 XGrammar 的 6.2 ms 变为启用后的 6.3 ms，用来说明该设置下端到端额外开销较小。[P04，表 2，p.10](#source-p04)

## 5.17 “函数调用从 62% 到 100%”，到底是哪一种正确率？

论文表 4 的函数调用项为 62% → 100%，测的是 **生成输出的语法／结构正确性**。论文明确使用 JSON 结构生成任务进行该项测试，不是在声称所有外部业务任务都完成了。[P04，§4.4、表 4，p.10](#source-p04)

因此不能写成“加了 XGrammar，Agent 工具使用成功率达到 100%”。

更准确的工程分工是：结构引擎约束其支持的输出形式；执行端验证参数与权限；业务层检查对象与口径；任务评测确认用户目标。**能确定性验证的部分尽量交给程序，但不要把结构保证夸大成语义保证。**

## 5.18 延伸：现在的模型都在使用 XGrammar 吗？

需要区分**模型权重、推理服务和具体请求配置**。XGrammar 已集成到 vLLM、SGLang、TensorRT-LLM、MLC-LLM 等推理引擎；它在采样前处理候选分数，不要求因此重新训练模型权重。[R33](#source-r33)

同一个开源模型可以部署在不同引擎上；引擎支持 XGrammar，也不表示每个请求都启用了它。厂商 API 提供严格结构化输出，则说明接口提供相应保证，不能单凭这一点确认底层使用 XGrammar 这个库。需要具体实现或官方披露才能确认。

因此，对 OpenAI、Kimi、Qwen、DeepSeek、GLM 等，应分别核查具体版本和服务路径，不能统一写成“都用 Toolformer 和 XGrammar 训练”。前者是工具学习的一种研究方案，后者是生成约束的一种实现；二者处理的问题可以共同存在，具体采用的方法可以不同。

# 六、REST API Calling：从本地函数到网络服务

> 对应讲义第 36–40 页。主要参考：[R17](#source-r17)、[R18](#source-r18)、[R19](#source-r19)。

## 6.1 一个带类型的函数，还不是远程服务

讲义第 37 页给出进程内函数，例如：

```python
from typing import Literal
from pydantic import BaseModel


class Weather(BaseModel):
    summary: str
    temperature: float


def get_weather(city: str, units: Literal["C", "F"] = "F") -> Weather:
    # provider 为应用配置的实际天气提供方，此处是接口示意。
    return provider.lookup(city, units)
```

它说明输入和返回对象，但还没有网络地址、HTTP 方法、请求序列化与远程认证。进程内接口不自动变成网络服务。[L02，p.37](#source-l02)

还要区分类型注解与实际检查：普通 Python 函数不会仅因写了 `Literal["C", "F"]`，就自动拒绝所有非法运行时输入。必须有执行校验的框架、校验器或业务代码。

**工程推论：接口声明、校验器、业务实现应分别明确责任，而不是把“有类型”当成整个系统已经安全。**

## 6.2 FastAPI 增加 HTTP 边界和请求绑定

讲义第 38 页将函数暴露为以下契约：

```text
GET /weather
查询参数：city、units
请求头：X-API-Key
返回：Weather JSON
```

对应的路由示意：

```python
from typing import Annotated, Literal
from fastapi import FastAPI, Security
from fastapi.security import APIKeyHeader

app = FastAPI(title="Weather API")
key_header = APIKeyHeader(name="X-API-Key")


@app.get("/weather", operation_id="get_weather")
def weather(
    city: str,
    key: Annotated[str, Security(key_header)],
    units: Literal["C", "F"] = "F",
) -> Weather:
    verify(key)
    return get_weather(city, units)
```

这是课件调用结构的展示：`Weather`、`get_weather` 和 `verify` 必须由应用实际定义，并不是独立可部署文件。[L02，p.38](#source-l02)

其中提取 API key、在接口文档中声明认证方式，与验证密钥、确定身份和判断访问权限，是不同事情。课件专门保留 `verify(key)`，正好提示你不要遗漏实际验证逻辑。FastAPI 的安全机制可以与 OpenAPI 集成，但具体授权仍需要应用落实。[R19](#source-r19)

## 6.3 JSON Schema 描述值，OpenAPI 描述 HTTP 操作

JSON Schema 可以描述 `city` 是字符串、`units` 只允许 C/F，但不能单独告诉调用者：参数应该放在 URL 路径、query、header，还是 body。

OpenAPI 还描述 HTTP 路径、方法、参数位置、安全方案和响应等。讲义第 39 页强调，两者是嵌套关系而非替代关系。[L02，p.39](#source-l02)

| 问题 | 主要由哪一层描述 |
|---|---|
| 这个值是字符串还是数组？ | JSON Schema |
| 哪些字段必须存在？ | JSON Schema |
| 调用哪个路径与方法？ | OpenAPI |
| 参数放在 query 还是 body？ | OpenAPI |
| 使用什么认证方式？ | OpenAPI 的安全描述，以及实际认证实现 |
| 业务上是否允许这次操作？ | 应用授权与业务校验 |

FastAPI 能生成 `/openapi.json` 及交互式文档，但生成文档不等于执行器，也不会自动实现文档中没有编码的业务约束。[R18](#source-r18)

## 6.4 OpenAPI 转工具，不只是复制一份参数 schema

OpenAPI 中，参数的位置以及序列化方式会影响实际请求；`style`、`explode` 等字段就参与决定数组或对象怎样进入 HTTP 请求。[R17，Parameter Object 及附录 C](#source-r17)

以下是同一教学数据可能对应的两种编码：

```json
{"ids": ["A", "B"]}
```

```text
ids=A&ids=B
```

```text
ids=A,B
```

只知道 `ids` 是字符串数组，不能判断当前服务要求哪一种。

**工程建议：让适配器负责确定性的协议转换。** 模型输出业务参数对象，适配器按固定契约生成 URL、请求头和请求体。没有必要每一轮都要求模型重新拼一个 HTTP 请求，再承担转义和编码错误。

## 6.5 Coding agent 可以直接使用 `curl`，不必先接入 MCP

讲义第 40 页说明，拥有 shell 工具的 coding agent 可以阅读 API 描述，然后执行 `curl`：[L02，p.40](#source-l02)

```bash
# 示例域名，不是真实可查询服务。
curl -sS -G https://weather.example/weather \
  --data-urlencode "city=Pittsburgh" \
  --data-urlencode "units=F" \
  -H "X-API-Key: $WEATHER_API_KEY"
```

其中 shell 展开环境变量，`curl` 构造和发送请求。MCP 不是访问 REST API 的必要前提。

代价同样需要看清：能够执行 shell 的 Agent，可能也能够读取该环境中的密钥。把 key 放进环境变量，可以避免在提示词里直接写明文，但不能自动隔离一个有权读取该环境的程序。

**工程推论：凭证保护取决于权限和部署边界，不取决于它是写在 prompt、配置文件还是环境变量里。** 这自然引出下一章的能力代理和独立认证边界。

# 七、MCP：能力发现、协议适配与凭证边界

> 对应讲义第 41–46 页。主要参考：[R20–R26](#references)。本章先解释讲义结构，再明确所给 2026-07-28 协议参考的版本差异。

## 7.1 Host、Client、Server：模型不是 MCP Client

第 42 页展示一个 AI 应用作为 Host，内部的 Client 分别连接本地或远程 Server。[L02，p.42](#source-l02)

| 角色 | 本课中的含义 |
|---|---|
| Host | 整个 AI 应用，管理模型、上下文、交互和执行策略 |
| Client | Host 内负责 MCP 通信的组件 |
| Server | 通过 MCP 暴露工具、资源等能力的程序 |

通常是 Host 中的软件发现工具、发起 MCP 请求。模型看到 Host 提供的工具定义，然后生成调用意图。

因此至少有两段不同协议：

```text
模型 ⇄ Host：模型工具调用与消息协议
Host ⇄ MCP Server：MCP 协议
```

接入一个 MCP Server，不等于模型内部自动出现 MCP 网络客户端。中间仍需要名称映射、参数转换、策略检查和结果回填。

## 7.2 `tools/list` 是发现能力，`tools/call` 是调用能力

课件将两者列为 MCP 的发现与执行接口：[L02，pp.45–46](#source-l02)

```text
Client 获取工具目录
    ↓
Host 选择需要暴露的工具，转换为模型支持的定义
    ↓
模型提出名称和参数
    ↓
Host 校验并调用 MCP Server
    ↓
工具结果转换为模型的工具结果消息
```

发现和调用是不同阶段。工具目录可以按协议和权限范围缓存，不必每生成一轮都重新拉取；但也不能缓存以后永远忽略权限或版本变化。

**工程推论：目录缓存应包含身份、服务和版本等边界。** 给某个用户发现的工具集合，不能不经检查就当成另一个用户的授权集合。

## 7.3 stdio 与 Streamable HTTP：传输方式不是能力语义

所给传输规范将 stdio 描述为客户端启动子进程后通过标准流传递消息；Streamable HTTP 则通过 MCP 端点的 HTTP 请求与响应承载消息。MCP 使用 JSON-RPC 编码，传输负责如何送达，不定义工具业务含义。[R22](#source-r22)

本地 stdio 不是进程内函数调用。HTTP 也不意味着 MCP 与普通 OpenAPI 描述变成同一件事。

**工程建议：本地工具同样要检查运行权限。** 本地 Server 能读哪些目录、能否发网络请求、是否继承宿主凭证，取决于部署配置，不因“本地”就天然安全。

取消请求也应按实际传输与 SDK 版本处理。更重要的是，取消等待不应被等同为撤销所有已经产生的业务副作用。

## 7.4 FastMCP 怎样把 OpenAPI 映射为 MCP 工具？

OpenAPI 已提供名称或 operationId、描述、输入结构、HTTP 路径与方法，因此可以建立到 MCP 工具的适配。课件第 43 页展示 `FastMCP.from_openapi()`，默认将路由转换为可发现工具。[L02，p.43](#source-l02)

下面保留讲义与所给 FastMCP 文档的 `httpx2` 写法，仅展示调用关系；需要实际 API、依赖版本、认证配置和生命周期管理才能运行：

```python
import httpx2
from fastmcp import FastMCP

# 示例域名；实际项目应检查 HTTP 状态、设置超时并管理客户端生命周期。
spec = httpx2.get("https://weather.example/openapi.json").json()
upstream_client = httpx2.AsyncClient(base_url="https://weather.example")

mcp = FastMCP.from_openapi(
    openapi_spec=spec,
    client=upstream_client,
    name="Weather MCP",
)
```

这里的 HTTP client 用于访问上游 API，不是模型侧的 MCP Client。[R24](#source-r24)

## 7.5 自动转换适合起步，不等于应该把所有路由暴露给模型

FastMCP 文档提供按方法、路径和标签映射或排除路由的机制，也提供兜底排除规则；文档本身提醒复杂 API 更需要经过设计和筛选的工具接口。[R24](#source-r24)

**工程建议：采用显式允许列表，并检查最终导出的工具目录。**

```text
明确允许的业务能力 → 暴露
其余管理、内部或高风险能力 → 默认不暴露
```

这里的关键不只是写一条规则，还要测试配置最终生成了什么。后续自定义映射逻辑、命名处理或配置变更，都可能影响最终暴露面。

一个业务动作若固定需要调用五个底层接口，可以考虑把确定性的组合封装在服务端，让模型调用明确的业务能力。反过来，也不应把一切塞进 `do_everything(task: str)`，否则输入契约和可观察性又消失了。

**合适的工具粒度，是让模型做有价值的决策，把固定的接口胶水工作留给程序。**

## 7.6 MCP 工具的结构化结果，与模型 Structured Outputs 是两个方向

`structuredContent` 是工具服务器返回的结构化数据；`outputSchema` 描述该结果。规范要求声明输出 schema 的服务端返回符合结构的结果，并建议客户端验证。[R23](#source-r23)

它与 XGrammar 限制模型输出不是同一个方向：

```text
模型输出 → 调用输入契约
工具输出 → 工具结果契约
```

应用可以把服务端结果转换成模型需要的观察，同时保留完整数据及引用。没有必要把结构化结果先丢失字段语义地压成一句话，再要求后续模型恢复原结构。

协议成功和业务成功也要区分。MCP 对工具执行错误提供 `isError: true` 的结果表达；HTTP 请求完成，不代表工具业务动作已成功。[R23，错误处理部分](#source-r23)

**工程推论：至少分别记录传输／协议状态与业务执行状态。** 不要让一个模糊的 `success=true` 混合表达“收到了响应”和“已完成退款”。

## 7.7 为什么要分开 MCP 凭证和上游凭证？

课件第 44–45 页的关系是：

```text
Agent Host
    ── MCP_API_KEY ──▶ MCP Server
                           │
                           └── UPSTREAM_API_KEY ──▶ 上游业务 API
```

前者保护 MCP 入口，后者用于访问上游。Server 接收一种凭证、使用另一种凭证调用上游，这提供了能力代理与访问控制的位置，而不是把上游密钥交给模型。[L02，pp.44–45](#source-l02)

但“模型看不到两种密钥”需要实际隔离来成立。如果模型控制的 shell 可以读取 Host 或 Server 的环境，两套密钥仍可能暴露。

**工程建议：**把凭证留在模型不可直接读取的运行边界，按身份和对象实施授权；不要让有效 MCP token 自动拥有上游服务账号的全部权限。

## 7.8 静态 token、JWT 与 OAuth 分别是什么？

先从问题出发：**AI 助手要读取你的日程，服务端凭什么允许它读取？** 客户端需要出示可信凭证；服务端验证后，还要判断这次操作是否被允许。

| 名称 | 回答的问题 | 通俗理解 |
|---|---|---|
| 身份验证 Authentication | 凭证是否可信，代表什么主体？ | 检查工牌 |
| 授权 Authorization | 这个主体能做什么、访问哪些对象？ | 判断工牌能进哪些房间 |
| token | 请求出示什么凭证？ | 一张访问票据 |
| JWT | 凭证中的声明怎样表示？ | 一种带结构的数据格式 |
| OAuth | 应用怎样获得受限的访问授权？ | 发放访问权限的协议流程 |
| Bearer | 请求怎样使用这种持有者凭证？ | 持有效票据访问 |

凭证可能代表用户，也可能代表应用或服务账号；“身份有效”不代表可以操作所有工具和所有对象。

### 7.8.1 静态 token：提前配置好的凭证

最简单的教学方案是管理员生成一个随机字符串，配置到客户端和服务器；服务器根据它查到调用者和权限。客户端每次请求携带同一凭证。“静态”不等于永久有效、不可撤销或权限无限。FastMCP 的静态验证器定位于开发和测试。[R25](#source-r25)

### 7.8.2 JWT：声明、签名与接收方

常见的签名 JWT 表现为 `头部.载荷.签名` 三段。以下为**解码后的载荷教学示例**，不是可用凭证：

```json
{
  "iss": "https://auth.example.com",
  "sub": "user_123",
  "aud": "calendar-mcp",
  "exp": 1800000000,
  "scope": "calendar:read"
}
```

| 字段 | 本例含义 |
|---|---|
| `iss`，issuer | 哪个服务签发 |
| `sub`，subject | 涉及哪个主体 |
| `aud`，audience | 预期由哪个服务接收 |
| `exp` | 到期时间，Unix 时间戳 |
| `scope` | 本例约定的读取日程权限范围 |

非对称签名场景下，签发方用私钥签名，接收服务用可信公钥验证。修改载荷不会自动获得有效的新签名。**普通签名 JWT 的内容可以被解码读取，签名不等于加密**；JWT 也存在加密形式，不能把三段式推广到所有 JWT。[R34](#source-r34)

验证不能停在“能解码”或“签名正确”。例如天气服务和日程服务信任同一个签发方，天气凭证的签名也可能正确；日程服务仍需检查 `aud`，避免接受发给天气服务的凭证。到期时间与可信 issuer 同样需要检查。FastMCP 的 JWT 验证配置也涉及这些检查。[R25](#source-r25)

### 7.8.3 OAuth：应用怎样取得授权？

假设你允许日程助手读取日历，但不想把账号密码交给它。常见授权码流程可简化为：

```text
助手申请读取权限
    ↓
你在日历平台登录并确认授权
    ↓
平台向应用返回授权码
    ↓
应用按协议将授权码换成 access token
    ↓
应用携带 token 访问日历 API
```

用户、客户端应用、授权服务器、资源服务器是不同角色；后两者可以属于同一平台。上图用于建立概念，不是省略 PKCE 等安全机制后的可部署方案。OAuth 不强制 access token 使用 JWT，也不是所有流程都需要用户点击授权；它本身是授权框架，不能直接等同于用户登录协议。[R35](#source-r35)

因此可以组合为：**通过 OAuth 获得授权 → 收到 JWT 格式的 access token → 用 Bearer 方式发送 → 服务端验证并执行授权检查。**

### 7.8.4 回到 FastMCP 客户端代码

前面的概念落到客户端，就是准备好凭证并随请求发送。课件的客户端示例可以写成：

```python
import os
from fastmcp import Client

# 示意：连接地址、凭证与实际服务需由应用配置。
async def query_weather():
    async with Client(
        "https://mcp.example/mcp",
        auth=os.environ["MCP_API_KEY"],
    ) as client:
        return await client.call_tool(
            "get_weather",
            {"city": "Pittsburgh", "units": "F"},
        )
```

所给 Bearer 客户端文档说明，`auth` 直接传 token 字符串时，客户端会添加 Bearer 方案，不要自行再添加一次前缀。[R26](#source-r26)

对应的 HTTP 请求头类似 `Authorization: Bearer <token>`。`MCP_API_KEY` 只是环境变量名，不能由名字判断内容一定是随机 token 还是 JWT；这段代码也没有展示取得 token 的过程。它只展示“拿着已准备好的凭证调用”。Bearer 凭证通常谁持有谁就能使用其权限，应保密并通过 HTTPS 传输。[R35，Bearer 规范](#source-r35)

认证只是执行保护的一部分。参数 schema、身份验证和对象级授权，仍然是三个不同检查。

**教学例子**：调用 `read_calendar(user_id="user_456")` 时，schema 检查 ID 的存在与类型，凭证验证判断调用者是否可信，对象级授权判断此调用者是否可读 `user_456` 的日历。不能仅凭“token 有效”就放行任意 `user_id`。

## 7.9 所给 2026-07-28 协议参考：不能套用旧版握手流程

用户给出的正式发布说明明确：2026-07-28 版改为无状态协议核心，取消旧版 `initialize/initialized` 交换与 `Mcp-Session-Id`，请求携带自身元数据；`server/discover` 为可选发现调用。TypeScript SDK v2 页面声明实现该版协议。[R20](#source-r20)、[R21](#source-r21)

这不是在修改讲义的 Host—Client—Server 结构，而是在补充所用协议版本的通信行为。

无状态协议也不禁止业务状态。发布说明建议需要跨调用状态时，使用显式句柄在操作之间传递。[R20](#source-r20)

工程上要分别锁定：模型版本、MCP 协议版本、SDK 版本与 FastMCP 版本。它们属于不同层；`v2` 这样的 SDK 编号不能替代协议日期。

`draft` 路径还可能继续演进。本文引用其核对时的相关条款，不把它与所有历史教程视为可随意混合的同一个接口版本。

## 7.10 REST / OpenAPI 与 MCP 的关系

讲义第 46 页将它们放在不同契约层上：[L02，p.46](#source-l02)

| 维度 | HTTP API / OpenAPI | MCP |
|---|---|---|
| 基本作用 | 暴露并描述 HTTP 操作 | 标准化 AI Host 发现和调用能力的方式 |
| 发现 | 获取接口描述 | 获取工具目录等 |
| 调用 | 方法、路径、参数及请求体 | `tools/call` 及协议传输 |
| 数据描述 | 参数与响应 schema | 工具输入及可选输出 schema |
| 认证 | 调用者向 API 认证 | 调用者向 MCP 认证，上游认证可独立 |

因此可以是：

```text
Agent → MCP → REST API → 业务系统
```

也可以是：

```text
Agent → 受控函数 → REST API → 业务系统
```

**工程判断：**少量内部能力不一定需要增加 MCP 层；多 Host 复用、统一发现和治理时，这一层更可能有价值。关键不是“是否用了 MCP”，而是它解决了哪个具体集成和控制问题。

# 八、Orchestrating multiple calls：依赖、并发与失败恢复

> 对应讲义第 47–51 页。主要参考：[L02](#source-l02)、[R13](#source-r13)、[R14](#source-r14)、[R27](#source-r27)。

## 8.1 串行调用成本，不只是工具执行时间相加

讲义第 48 页假设三项查询耗时分别为天气 1.2 秒、日历 0.9 秒、航班 1.1 秒，每段模型生成为 0.8 秒。[L02，p.48](#source-l02)

串行链路是：

```text
生成 → 天气 → 生成 → 日历 → 生成 → 航班 → 生成最终回答
```

所以：

$$
T_{\text{serial}}=4\times0.8+1.2+0.9+1.1=6.4\text{ 秒}
$$

这只是课程用的简化模型，不是任何产品的实际延迟统计。

它说明优化 Agent 时，不能只看最慢的 API。重复生成、上下文处理和模型往返，也可能是重要成本。

## 8.2 并行为什么能降到约 2.8 秒？

如果三项操作独立，模型一次提出三个请求，执行器并发运行，结果齐全后再生成回答：

$$
T_{\text{parallel}}=2\times0.8+\max(1.2,0.9,1.1)=2.8\text{ 秒}
$$

来源：[L02，p.49](#source-l02)。

这里必须同时满足两个条件：**模型一次生成多个调用，运行时真的并发执行这些调用。** 一个 `tool_calls` 数组不会自动使你的程序并行；如果执行代码逐个等待，工具部分仍然串行。

同时，减少模型轮数与减少外部请求数仍然不同。这个结论与 CodeAct 中“一个程序行动可以包含多次操作”一致。

## 8.3 先判断输入依赖，再判断共享状态冲突

讲义第 50 页给出的必须串行例子是：[L02，p.50](#source-l02)

```text
查客户 ID → 用 ID 查订单 → 对选定订单退款
```

后一步依赖前一步产生的输入，不能让模型提前猜测。

**工程推论：没有参数依赖，还不意味着安全并行。** 两个操作即使都已经知道账户 ID，也可能同时修改同一余额或记录，发生共享状态冲突。

因此应分别问：本次输入是否已经确定？同时执行是否可能冲突？是否存在不可逆副作用或顺序要求？

一种设计方式是形成依赖图：

```text
解析产品 ID
     ↓
确定时间区间与数据快照
     ├── 查询区间 A ──┐
     └── 查询区间 B ──┤
                      ↓
                 检查并汇总
                      ↓
                 生成最终报告
```

图中同层节点只有在前置条件满足、资源访问兼容时才并行。这里是工程建模方式，不是在声称模型会自动构造完全正确的依赖图。

## 8.4 `asyncio.gather` 只是并发原语，不是完整工具运行时

下面依据讲义第 51 页的骨架，补齐导入和异步函数包装：[L02，p.51](#source-l02)

```python
import asyncio
import json

# 教学骨架：TOOLS 及调用对象由运行时提供；此处假设工具均为异步函数。
async def execute_batch(function_calls):
    async def execute(call):
        args = json.loads(call.arguments)
        value = await TOOLS[call.name](**args)
        return call.call_id, value

    return await asyncio.gather(
        *(execute(call) for call in function_calls),
        return_exceptions=True,
    )
```

Python 文档说明，`gather` 的返回结果按输入 awaitable 的顺序排列，而不是完成顺序；设置 `return_exceptions=True` 会把异常作为结果收集。[R27](#source-r27)

因此需要精确理解“乱序完成”：执行可能先后不一，但上述 `gather` 最终列表仍按输入位置组织。显式 ID 的价值在于跨队列、日志、重试和其他回填路径保持稳定关联，而不只是解决这一种列表顺序。

课件代码只有成功时才返回 `(call_id, value)`。异常对象没有同样的显式结构，虽然可以用输入位置恢复对应，工程上更适合统一成功和失败的结果信封。

## 8.5 成功和失败，都应携带原调用标识

下面是**应用内部设计示例**，不是某个 API 的强制字段格式：

```json
{
  "call_id": "call_123",
  "tool_name": "get_weather",
  "status": "error",
  "data": null,
  "error": {
    "code": "UPSTREAM_TIMEOUT",
    "message": "查询未在期限内返回",
    "retryable": true
  }
}
```

这样，成功、参数校验失败、拒绝执行、上游超时，都能明确对应原调用。错误信息应有足够的可操作性，但不应把密钥、内部堆栈或敏感数据不加处理地交给模型。

一个较完整的执行流程可以表示为以下**伪代码**：

```text
记录调用 ID 和工具版本
检查调用名称是否在许可注册表中
解析参数，并验证输入契约
检查用户、租户、对象与操作权限
判断依赖是否满足，资源是否允许并发
在并发上限、超时和资源预算内执行
验证结果契约，处理敏感字段与大体积输出
生成带原调用 ID 的成功／失败观察
写入事件日志，并按模型协议回填
```

这些环节的先后可以随架构调整，但不应被一个 `gather` 调用掩盖。

## 8.6 OpenHands 源码把“一批动作”作为生命周期管理

“一批动作”就是模型一次提出的操作清单。**提出动作还不代表已经执行**，程序需要整理清单、执行允许的操作、反馈每项结果，最后决定是否结束。

**教学示例**：模型一次提出 `读取 a.txt → 读取 b.txt → finish → 删除 c.txt`，其中 hook 禁止读取 `b.txt`。当前 `_ActionBatch` 的处理规则是：

| 阶段 | 具体行为 | 例子中的结果 |
|---|---|---|
| 截断 | 找到第一个 `finish`，保留它及前面的动作，丢弃后面的动作并记录警告 | 不执行删除 `c.txt` |
| 划分 | 从执行清单中移除已标记阻止的动作 | 不读取 `b.txt` |
| 执行与关联 | 执行允许的动作，把结果与动作 ID 关联 | `a.txt` 的结果不会错配给 `b.txt` |
| 发出反馈 | 按原动作顺序发出结果；阻止项生成带原因的拒绝观察 | 模型明确得知 `b.txt` 未读取 |
| 决定结束 | 没有 `finish` 或它被阻止时不在此结束；否则检查后续改进需求 | 有继续需求且有提示时继续，否则标记 `FINISHED` |

这里拒绝观察的类型叫 `UserRejectObservation`，但本路径的来源标记为 `hook`，不能将它一概理解为用户亲手拒绝。整体顺序是 `prepare → emit → finalize`。[R13，`_ActionBatch`、`_execute_actions`](#source-r13)

`finish` 可以理解为结束申请；标记会话结束不等于证明任务全部成功。模型没有读到 `b.txt`，依然是需要如实报告的未完成部分。按原顺序记录结果，也不等于动作按顺序执行：B 若依赖 A 的输出，仍需显式管理依赖。

执行器另外管理并发上限、资源锁和错误。执行前检测到取消时会跳过并形成错误事件；异步等待被取消时会尝试通知工具中断。资源锁依赖工具正确声明共享资源；中断不保证已发生的副作用回滚。[R36](#source-r36)

以上对应 **2026-09-26 所读 `main`**，不是所有框架唯一正确的方案。批次管理的价值是让执行记录和会话状态一致，而不只是“把多个请求同时发出去”。

## 8.7 超时后为什么不能一律重试？

对于只读查询，重试通常更容易处理。对于创建订单、发送邮件或退款，超时可能意味着：服务端已经完成动作，但响应没有回到客户端。

这时重新执行可能产生第二次副作用。下面是由课件可靠性和副作用要求推导的**工程状态分类**：

| 状态 | 含义 | 典型下一步 |
|---|---|---|
| 已确认成功 | 系统确认动作完成 | 使用实际结果继续 |
| 已确认失败 | 系统确认未完成或拒绝 | 修正输入、权限或终止 |
| 可安全重试的失败 | 满足既定重试条件 | 有界重试 |
| 执行状态未知 | 无法确认是否已经发生副作用 | 查询状态或转人工，不盲目重复 |

工具调用 ID 用于关联请求和结果；**业务幂等键**用于让重复业务请求不重复产生效果。二者不是同一种保证。给调用添加一个 ID，不会自动获得“恰好执行一次”的业务语义。

## 8.8 重试、取消与回滚也要分开

**工程建议：**对只读失败可以设置有限次数的退避重试；对参数错误，应修正参数而不是原样重复；对权限拒绝，不能通过换工具绕过；对有副作用的未知状态，应先确认实际结果。

取消等待只表示客户端不再继续等待，未必能停止远端正在执行的操作。代码沙箱中的文件写入、外部邮件发送、数据库更新也不一定能靠“重新开始一轮”自动回滚。

因此，长任务需要调用预算、截止时间、最大重试次数，以及明确的部分完成状态。**一个能够稳定报告“已完成哪些、哪些失败、哪些状态未知”的 Agent，比一个一直循环直到声称成功的 Agent 更可验证。**

# 九、Evaluating tool use：从函数调用正确到任务真正完成

> 对应讲义第 52–57 页。主要参考：[P01，§6](#source-p01)、[R04](#source-r04)、[R05](#source-r05)、[R06](#source-r06)。

## 9.1 BFCL 为什么不只测“能不能写 JSON”？

**BFCL 全称是 Berkeley Function Calling Leaderboard，伯克利函数调用排行榜。** 广义上是一套评测基准，包括数据集、评分程序与公开排行榜。可以类比为试卷、阅卷系统和成绩榜，不只是一个 JSON 数据文件。[R04](#source-r04)

讲义第 53 页列出单轮、多轮、Agentic 和鲁棒性几类任务，包括多工具、并行、缺少函数、缺少参数、长上下文、搜索、记忆及格式敏感性。[L02，p.53](#source-l02)

它们对应的能力不同：一个模型可能很会填单次参数，却不会根据前一轮的工具结果决定下一步；也可能能完成任务，但对提示格式的变化非常敏感。

尤其要看缺少参数时的行为。用户只说“帮我订明天的机票”，出发地和目的地都不明确，模型不应为了满足 schema 而猜测。**有依据的参数比表面齐全的参数更重要。**

### 9.1.1 单轮：选工具与填参数分别测什么？

下面场景均为**教学例子，非 BFCL 原题**。用户问北京天气，模型输出 `get_weather(city="上海")`，调用可以解析甚至执行成功，但仍然答错。

| 单轮类别 | 设置重点 | 教学例子 |
|---|---|---|
| Simple | 一个工具、一次调用 | 查北京天气 |
| Multiple | 多个候选工具中选一个 | 在天气、地图、汇率工具中选天气 |
| Parallel | 提出多次独立调用 | 分别查北京和上海天气 |
| Parallel Multiple | 多工具选择与多次调用结合 | 查天气，同时换算金额 |

Multiple 强调候选工具多，Parallel 强调输出多次调用。模型提出并行调用清单，执行并发仍由运行时负责。[R37](#source-r37)

### 9.1.2 多步和多轮有什么区别？

```text
用户：查 ORD-17 的物流。
模型：get_order("ORD-17")
工具：返回 tracking_id = "SF123"
模型：get_tracking("SF123")
工具：正在配送
模型：订单正在配送。

用户：那 ORD-18 呢？
模型：开始查询 ORD-18，而不是继续操作 ORD-17。
```

完成同一个请求需要连续操作，是**多步**；用户继续交互、模型需要接续上下文，是**多轮**。上例第二次调用依赖第一次结果，不能预先猜单号、把两次调用当作独立请求并行执行。此类场景检查反馈利用、对象更新与任务推进，而非单次输出的括号是否完整。

### 9.1.3 缺少参数与缺少工具时，不应硬凑调用

假设工具需要 `origin`、`destination`、`date`。用户只说“查明天的机票”，即使当前日期已明确，也不能推出出发地和目的地。

| 信息情况 | 合理行为 |
|---|---|
| 本轮已说明 | 直接使用 |
| 前文已明确且仍适用 | 引用上下文 |
| 可通过允许的工具确定 | 先查询 |
| 必要信息确实缺失、无法可靠确定 | 追问 |

BFCL Missing Parameters 针对必要信息缺失且无法从系统推断的情形，期望澄清。Missing Functions 则检查是否识别当前工具集无法完成请求，后续可补充缺失工具；不是让模型编造不存在的函数。Long Context 检查在大量信息中定位关键内容，不能与“信息根本没提供”混淆。[R38](#source-r38)

**工程归因**：工具没有进入上下文，属于发现或提供阶段；工具已提供却选错，属于选择阶段；没有可用工具仍编造调用，则是面对能力缺口时的错误行为。参见 2.6。

### 9.1.4 搜索、记忆与格式敏感性分别测什么？

搜索不仅要发出一次查询，还可能需要更换检索词、打开页面、多跳取证，最后回答正确；具体评分见 9.3。[R05](#source-r05)

记忆测试使用外部存储工具，检查信息的保存、更新与取回。例如用户先住杭州、后来搬到南京，再询问本地活动时，应使用新信息。这里测的是模型与记忆后端结合的能力，不是仅测模型权重“背了多少知识”。BFCL V4 提供多种记忆后端。[R39](#source-r39)

格式敏感性测试改变工具说明、输出形式、标签、排版及措辞。例如同一个天气工具，分别以 JSON 和 XML 说明，模型是否仍能选对工具并填对参数？公布的 V4 实验在选取的单轮题目上进行，针对提示式非 FC 设置；该项单列，不进入所述 V4 总分。它不是“所有模型均经历同样扰动后的总排名”。[R40](#source-r40)、[R04](#source-r04)、[R05](#source-r05)

### 9.1.5 怎样判分，为什么不是 JSON 解析成功就算对？

| 评测方法 | 检查内容 |
|---|---|
| AST 等调用结构比较 | 提取工具名称及参数，与参考要求比较 |
| 实际执行 | 检查执行结果是否正确 |
| 状态检查 | 例如文件是否建立、数据是否写到正确位置 |
| 必要执行路径检查 | 检查取得答案所需的调用是否发生 |
| 最终答案检查 | 例如搜索题答案是否匹配 |

AST 是 Abstract Syntax Tree（抽象语法树），把调用解析成便于比较的结构；这里的评分不是仅检查语法，还比较工具和参数。多轮评分结合状态与必要执行路径：写操作会改变状态，但只读查询可能不改变任何状态，因此不能只看最终状态。它也不要求每个合理探索动作都与单一参考轨迹逐项相同。[R37](#source-r37)、[R38](#source-r38)

**阅读榜单的顺序**：先确认 BFCL 版本和分项，再看评分设置，最后判断与自己的任务是否相似。能填好一次参数，不代表能处理缺失信息、跨轮依赖或长期记忆；总分不能直接当作内部业务的成功率。

## 9.2 BFCL V4 总分不是纯粹的参数填写能力

所给 V4 方法页面按 Agentic 40%、Multi-Turn 30%、Live 10%、Non-Live 10%、Hallucination Measurement 10% 汇总；Format Sensitivity 单列，不影响该总分。[R05，Scoring Methodology](#source-r05)

| 分项 | 页面给出的权重 |
|---|---:|
| Agentic | 40% |
| Multi-Turn | 30% |
| Live | 10% |
| Non-Live | 10% |
| Hallucination Measurement | 10% |

因此更高总分不直接证明模型在某个内部单步工具上更适合。应查看与你的任务相匹配的分项，并在真实接口契约上重新测试。本文不复述会变化的当前模型排名。

官方演示还区分原始调用与解析后转换成的兼容格式，进一步提醒我们，模型输出和适配器解析不是同一项能力。[R04](#source-r04)

## 9.3 Web Search 评测：不仅要成功，还要知道依赖了什么

该方法页面使用 100 个手工构造的多跳问题，提供搜索与网页获取工具；有摘要和无摘要形成两组条件，并研究网页请求失败。最终对规范化后的 `answer` 字段做精确匹配。[R05，§2、§5、§7](#source-r05)

**工程推论：**搜索摘要可能已经包含答案，所以最终回答正确不一定说明网页读取和证据整合都可靠。移除摘要、制造空结果或改变返回内容，能帮助定位成功依赖了哪一段信息。

这不是为了让评测故意刁难模型，而是区分“真正利用了证据”“依赖捷径”和“偶然答对”。对于内部知识库和财务数据工具，同样需要这种对照思路。

## 9.4 第一层：Selection——选对工具了吗？

讲义第 54 页把选择列为第一层，可以观察 precision 和 recall。[L02，p.54](#source-l02)

该调用时没调用，是漏调用；不该调用时调用，是多余调用或误调用。一个从不使用工具的模型，错误调用次数可能很低，但它不能因此被评为优秀。

如果存在候选工具召回阶段，还应把“正确工具未提供给模型”和“已提供但模型选错”分开。前者不能只通过微调参数生成来修复。

## 9.5 第二层：Arguments——参数的值和含义对了吗？

AST 或 schema 匹配能够检查某些结构，但参数评测还要关心任务语义。[L02，p.54](#source-l02)

例如：

```python
get_return(product_id, start_date, end_date)
```

日期字符串格式正确，仍可能选错截止日；产品 ID 存在，仍可能属于另一份额类别；数值合法，也可能使用了错误单位。

**工程建议：**对对象标识、区间、币种、单位和关键枚举建立可验证的检查。不要把“解析成功率”命名为“业务参数正确率”。

## 9.6 第三层：Trajectory——调用顺序和依赖关系合理吗？

先得到对象 ID，再查询数据，是依赖要求。已经有数据却重复查询，是效率问题。查询失败后直接编造结果，是恢复策略问题。[L02，pp.50、54](#source-l02)

**工程推论：**正确轨迹可能不止一条。两个独立查询先后顺序互换，不应自动判错。比逐字匹配唯一轨迹更有意义的，往往是检查必需步骤、前置条件、禁止动作、调用预算和最终状态。

复杂任务评测还要记录部分完成，不能只保留最终一句“失败”，从而丢失前面哪一步发生了问题。

## 9.7 第四层：Task——用户目标真的完成了吗？

讲义把端到端任务成功单独列为最高一层。[L02，p.54](#source-l02)

用户要求购物车，就检查购物车及商品；要求报告，就检查报告事实、数值与文件；要求退款，就检查实际退款状态。

模型说“已完成”只是一条文本，不是最终状态证明。反过来，所有工具都返回成功，也不保证它们合起来完成的是用户真正要求的任务。

综述同样强调可执行评测的重要性：只匹配调用表达式，有可能遗漏真正执行时的问题。[P01，§6.1–6.2，pp.8–9](#source-p01)

## 9.8 工具本身也要评测，不能把所有波动归因于模型

综述将工具速度、计算开销、失败与风险，以及神经工具自身的不稳定性列为重要评价维度；真实世界数据随时间变化还会影响可复现性。[P01，§6.3，pp.9–10](#source-p01)

**工程建议：**至少维护一组稳定测试夹具，以及一组真实环境测试。前者固定工具响应，帮助定位模型和运行时变化；后者检查认证、超时、限流与真实返回结构。

对于动态信息，可考虑在相同环境时点比较参考执行与模型执行。涉及写操作时，应在隔离环境或可控状态中进行，不能为了评测随意重复真实业务副作用。

## 9.9 质量还包含效率、可靠性与安全

第 55 页明确指出，正确的 Agent 也可能慢到无法使用，或者费用过高。[L02，p.55](#source-l02)

| 维度 | 建议观察的内容 |
|---|---|
| 效率 | 端到端延迟、生成轮数、调用次数、token 与费用 |
| 可靠性 | 超时、限流、重试、部分失败、恢复后成功率 |
| 安全 | 权限、敏感操作、副作用、对抗性外部输出 |

**工程补充：**平均值不够，应结合尾部延迟与超时比例。重试以后成功，也需要把前面的时间、费用和副作用风险计入，而不是只记录最后一次成功。

## 9.10 故障归因：模型、Harness、Provider / Tool

讲义第 56 页将故障分成三层：[L02，p.56](#source-l02)

| 层次 | 典型错误 | 应优先调查什么 |
|---|---|---|
| 模型 | 选错工具、参数错误、忽略结果 | 提示、工具定义、上下文、模型能力 |
| Harness | 解析、校验、认证或 ID 对齐错误 | 模板、适配器、运行时状态与配置 |
| Provider / Tool | 超时、限流、执行异常 | 网络、服务状态、工具实现 |

同样是“没拿到数据”，可能是模型从未提出调用，也可能是请求正确却被限流。把它们都归入“模型不稳定”，会导致一直换模型，却没有修复实际接口问题。

**工程建议：**一条 trace 至少保留模型与工具版本、原始调用、标准化参数、校验与授权结果、执行状态、耗时、重试、回填 ID 和最终任务校验。日志本身也要保护敏感数据。

## 9.11 OpenRouter 图应该怎样引用？

讲义第 57 页是标注为 **2026-08-27** 的 provider tool-call error rates 截图。[L02，p.57](#source-l02)

用户给出的 R06 是 OpenRouter 首页；当前首页不能独立重建该历史图的请求分布、统计口径和当时数值。因此本文只把截图作为讲义中的历史运行指标示例，不据此发布当前供应商排名，也不声称已经通过首页核验同一批历史统计。[R06](#source-r06)

**工程推论：**比较服务路径时，应固定模型、请求集、配置、时间窗口和错误定义。不同任务分布下的错误率，不能直接解释为某个供应商永远更可靠。

### 9.11.1 “错误率”先看分子、分母与统计单位

以下是**自拟数字**：100 次请求中，60 次响应含有工具调用，其中 3 次响应含有格式错误的工具调用。按全部请求计算是 `3 / 100 = 3%`，按返回调用的请求计算是 `3 / 60 = 5%`。两个数字都能算出，但含义不同。这里都按请求计数；若按单个工具调用计数，还需另行统计调用总数，因为一次响应可能包含多个调用。

还需要确认统计单位：一个响应有五个调用，其中一个出错，是算“一次请求失败”，还是“五次调用中失败一次”？没有调用的响应也不能一律算错：信息不足时追问可能正确，明确需要查询却直接编答案才可能失败。

仅凭截图标题不能知道“错误”是否包含格式错误、参数错误、截断、超时、限流、客户端解析失败，或者模型响应之后外部工具的执行失败。**这些是需要核查的可能口径，不是本文声称该历史图实际采用的定义。**

### 9.11.2 为什么不同任务分布不能直接比较？

| 假设服务路径 | 处理的请求 | 错误次数 / 请求数 | 错误率 |
|---|---|---:|---:|
| A | 简单天气查询 | 10 / 1,000 | 1% |
| B | 多轮订单处理、复杂参数 | 50 / 1,000 | 5% |

B 的任务更难，不能由此推断 A 永远更可靠。就像两个人做不同难度的试卷，分数不能直接比较。实际错误率可能同时反映模型能力、服务实现和请求构成。

模型名称、版本、量化或其他部署差异也可能影响表现。无法控制这些差异时，只能比较“这两套服务配置在本测试中的表现”，不能进一步断言差异来自某个内部组件。

### 9.11.3 怎样做有意义的服务比较？

**工程建议**：对同一批请求，在相近时间交错测试两条路径；保持模型版本、工具说明、上下文、输出预算、结构约束、工具选择策略、超时与重试设置一致。报告样本量，并分开记录：

- **请求成功率**：是否正常取得响应。
- **调用结构正确率**：能否解析、是否符合支持的 schema。
- **工具与参数正确率**：是否选对工具、参数是否有依据。
- **任务成功率**：最终目标是否完成。
- **延迟与成本**：包括失败和重试消耗。

`1 / 20` 与 `500 / 10,000` 都是 5%，但统计稳定性不同。当前页面也不能重建历史图当时的流量、时间窗口与筛选条件；截图能证明“讲义展示了这一组数值”，不等于已经复核其全部统计口径。

## 9.12 一组有价值的本地测试情形

下面是从课程各层次推导的**工程测试集设计**，不是 BFCL 的原始测试清单：

| 情形 | 应检查的行为 |
|---|---|
| 不需要外部信息 | 直接回答，不制造无意义调用 |
| 必须访问私有或实时状态 | 实际读取，不凭记忆编造 |
| 缺少参数或对象歧义 | 询问或先解析，不填猜测值 |
| 两个独立只读请求 | 可以并行，且结果正确关联 |
| 后续请求依赖前一步 | 不提前猜 ID 或中间结果 |
| 工具超时、限流、空结果 | 区分原因，有界恢复 |
| 工具返回与模型预期不同 | 根据实际可信结果修正 |
| 写操作响应丢失 | 先确认状态，不盲目重复 |
| 结果中出现指令性文本 | 不把外部内容提升为高权限指令 |
| 输出被截断 | 不执行未完成调用 |

其中一个非常有价值的测试是**替换工具结果**：输入任务保持不变，把工具中的关键值换成另一组合理测试值，观察答案是否相应变化。

例如分别返回半年值 A、一年值 B，再交换数值或返回顺序。检查模型是否根据字段语义引用，而不是按位置或模糊记忆写作。测试数据必须是受控的合成夹具，不用于伪造真实业务证据。

一个 Agent 如果调用了工具，却完全不受结果影响，可能只是生成了形式上的工具轨迹，并没有把观察真正用于决策。

# 十、Takeaways：把所有层次连成一个可验证的 Agent

> 对应讲义第 58–60 页。第 59 页将课程总结为能力、机制、约束、接口和系统五层。[L02，p.59](#source-l02)

## 10.1 各项技术分别负责什么，不负责什么？

| 技术或组件 | 主要解决的问题 | 不能自动保证什么 |
|---|---|---|
| 工具接口 | 将外部能力暴露给模型 | 模型一定选择正确 |
| 工具检索 | 从较大工具库中提供候选 | 前置依赖一定齐全、执行一定获授权 |
| Toolformer | 构造调用学习数据，学习调用与结果利用 | 任意长程工作流、生产可靠性 |
| 轨迹 SFT / RL | 从示范与环境反馈学习工具使用策略 | 所有厂商采用相同训练配方、奖励覆盖所有错误 |
| Chat Completions / Responses | 提交模型输入、接收输出并组织交互 | 自定义业务工具自动执行 |
| JWT / OAuth | 表示可信声明、取得访问授权 | 仅凭有效 token 就允许访问任意对象 |
| CodeAct | 用程序表达组合行动 | 任意代码安全、业务口径正确 |
| Chat template / parser | 消息对象与模型 token 之间转换 | 任务语义、权限、执行成功 |
| JSON Schema / XGrammar | 描述与限制受支持的结构 | 事实、授权与最终任务正确 |
| REST / OpenAPI | 暴露和描述 HTTP 能力 | 模型理解所有业务工作流 |
| MCP | 统一发现、调用及相关能力契约 | 自动完成所有权限治理和规划 |
| Harness | 执行、观察、并发、状态和终止控制 | 单独弥补全部模型能力缺陷 |
| 端到端评测 | 检查整个系统是否达到目标 | 用一个静态分数永久代表线上质量 |

这张表是对前文材料的综合，不是把所有责任强制分配给某个指定框架。一个小系统可以合并模块，但不能因为代码在同一个文件里，就忘记这些不同的保证边界。

## 10.2 用一个数据分析任务串起整节课

以下是**工程教学示例**，不涉及真实基金数据，也不是投资建议。

用户要求：

> 查询某产品最近半年和一年的收益，生成一段说明，并保存报告。

这个任务表面上只是“查两个数字再写一段话”，实际需要多个边界共同正确。

### 第一步：解析对象和问题口径

产品名称可能对应多个对象或份额类别，“最近半年”也需要确定截止日期及区间约定。如果用户没有给出关键条件，应根据明确的产品约定处理，或者先询问，不能默默填入猜测值。

这里对应工具选择、候选工具召回和缺少参数处理。只召回收益查询，却不给产品解析能力，可能逼迫模型猜 ID。

### 第二步：提供工具契约，经过正确的模型适配

应用向模型暴露解析产品、查询指标、生成文件等必要能力。模型适配器使用匹配的模板，将调用转换为内部结构化对象。

同样一个 `arguments`，在 Chat Completions 返回中可能是字符串，在内部应成为对象，到特定编码入口再按其要求转换。这一层错了，后面业务代码根本没有机会正确执行。

### 第三步：校验输入与权限

结构检查确定参数字段与类型；业务检查确定产品标识、日期区间和请求口径；权限检查确定当前用户能访问该对象。

三种检查不能互相替代。Schema 合法不等于产品标识来自有效解析，也不等于用户有权访问。

### 第四步：按依赖组织查询

对象解析和区间确定通常是前置步骤；两个已经明确的只读查询，在数据源和资源条件允许时可以并行。

如果两项指标要求同一数据截止点，应通过明确快照或一致的查询约定保证，而不是假定“几乎同时请求”就自然是相同口径。

### 第五步：返回带语义的数据，而不是两个孤立数字

下面是一组完全合成的结果夹具。日期仅用于演示记录结构，不是在定义真实基金指标的标准计算口径。

```json
{
  "product_id": "DEMO001",
  "data_as_of": "2026-06-30",
  "metrics": [
    {
      "metric_ref": "demo-result-6m",
      "metric_name": "period_return",
      "period": "6M",
      "start_date": "2026-01-01",
      "end_date": "2026-06-30",
      "value": "0.08",
      "unit": "ratio",
      "source_ref": "synthetic-fixture"
    },
    {
      "metric_ref": "demo-result-1y",
      "metric_name": "period_return",
      "period": "1Y",
      "start_date": "2025-07-01",
      "end_date": "2026-06-30",
      "value": "0.12",
      "unit": "ratio",
      "source_ref": "synthetic-fixture"
    }
  ]
}
```

这种结构保留了对象、周期、日期、单位和结果标识。后续写作有明确的事实记录可以引用，也可以在上下文压缩后重新读取。

### 第六步：确定性计算交给程序，关键结果明确展示给模型

需要换算单位、汇总或比较时，让程序计算。计算以后仍应检查使用的字段和口径。不能仅因为 Python 中存在一个变量，就认为模型已经观察过该变量的实际内容。

使用 CodeAct 可以把批量操作组合起来，但仍应保留检查点。结果应与原指标记录绑定，避免模型把转换后的数值丢回一段无结构文字后再猜用途。

### 第七步：生成说明，并验证事实绑定

最终文字应分别对应半年与一年指标。即使所有数字都出现了，只要周期、对象或单位串位，仍然是失败。

可以让生成结果保留事实引用，再通过程序或独立检查环节确认：每个关键数值来自哪个 `metric_ref`，对应哪个区间，输出中的百分比换算是否正确。

这不是让另一个模型凭记忆重新判断，而是利用明确的事实记录核对。

### 第八步：保存文件，并验证交付物

文件写入工具返回成功以后，还要确认实际文件存在、内容包含预期结果，且交付链接对应正确文件。`finish` 只负责结束循环，不能替代这些检查。

如果一个查询失败，应在报告中明确缺失，或暂停任务等待处理；不能用另一个区间的数值代替。任务最终状态可以是完成、部分完成或失败，但不能凭语言风格装成成功。

## 10.3 一个实用的开发优先级

下面是基于课程内容形成的**工程建议**，不是某篇论文的通用最优算法。

先做少量高频工具，明确输入输出、权限和执行结果；然后验证模型模板、参数编码、ID 回填和终止行为；再补充测试集与故障 trace。只有知道错误发生在哪一层以后，才决定改善提示、工具设计、结构解码、模型训练或执行系统。

对于数字与证据密集的任务，优先解决结构化事实记录、确定性计算和结果核对。对于多接口工作流，优先解决依赖、并发、副作用与未知状态。对于工具库规模增长，才进一步引入发现与检索。

不要看到任务失败就立即微调，也不要看到有多个步骤就立即增加多个 Agent。课程真正提供的是拆解责任和定位错误的方法。

## 10.4 对 LLM 开发者最重要的认识

**第一，模型生成的是行动提议，不是执行事实。** 所有“已经完成”的表述，都应追溯到真实结果。

**第二，能力来自多个层共同工作。** 更强模型、正确模板、清晰契约、稳定工具与可靠运行时，解决的是不同类型的问题。

**第三，结构保证越明确，模型越不必承担不必要的形式错误。** 但语义、权限和业务结果仍需独立验证。

**第四，程序化行动的价值在组合，而不只在语法。** 减少模型往返不等于减少外部调用，也不等于自动并行。

**第五，评测必须走到用户目标。** 单步调用正确率、结构正确率和供应商错误率都重要，但它们都不能替代端到端任务成功。

最终应该能够回答：

> 模型根据什么提出这次行动？系统为什么允许执行？实际执行产生了什么？最终回答凭什么声称目标已经完成？

这四个问题把 lecture-02 的所有内容连在了一起，也为后续的上下文管理、记忆、规划与协作课程建立了基础。[L02，pp.59–60](#source-l02)

# 附录 A：关键概念速查

以下是根据正文来源整理的释义，不代替对应章节中的限定条件。

| 概念 | 直白解释 | 容易混淆的对象 |
|---|---|---|
| Tool definition | 给模型看的能力与参数说明 | 不是实际函数实现 |
| Tool call | 一次具体行动请求 | 不是成功回执 |
| Tool implementation | 真正执行操作的程序 | 不由模型生成调用时自动产生 |
| Harness | 管理模型、工具和循环的外部运行程序 | 不等于模型权重 |
| Action | 一次操作的结构化输入 | 不等于已经执行的动作 |
| Observation | 环境返回的结果或错误 | 不应自动成为高权限指令 |
| Chat template | 把消息及工具结构变成模型输入序列 | 不是所有模型共享的字符串模板 |
| Parser | 把模型原生输出解释成调用对象 | 不负责证明业务合理性 |
| CodeAct | 用可执行代码表达环境行动 | 不等于只能使用 Python 格式传输 |
| Toolformer | 从有用调用构造数据并训练模型的方法 | 不等于完整生产 Agent 框架 |
| JSON Schema | 描述和验证 JSON 数据结构的语言 | 不等于所有实现都完整支持 |
| Constrained decoding | 生成时排除违反结构的候选 | 不保证事实和权限正确 |
| CFG | 用递归规则描述结构的文法 | 不能单独完成业务语义验证 |
| PDA | 带栈的解析状态机 | 栈不是聊天历史 |
| Persistent stack | 共享结构并保留历史状态的栈 | 不是数据库持久化 |
| OpenAPI | 描述 HTTP 操作及其参数、响应和安全方案 | 不等于接口实现 |
| MCP | AI Host 与能力服务间的协议 | 不是模型内部的调用格式 |
| JWT | 承载声明的 token 格式，常见形式带签名 | 签名不等于加密 |
| OAuth | 应用获得访问授权的框架 | 不是 token 格式，也不直接等同于登录 |
| Bearer | 持有效凭证即可使用相应权限的方式 | 不等于凭证一定采用 JWT |
| BFCL | Berkeley Function Calling Leaderboard，评测工具调用能力的基准与榜单 | 不只是检查 JSON 语法 |
| Responses API | 用不同类型的项目组织模型输入输出和工具交互 | 不等于另一种模型或完整业务执行器 |
| Call ID | 关联调用与结果的标识 | 不自动提供幂等性 |
| Idempotency key | 用于控制业务重复执行的标识 | 不只是日志追踪 ID |
| Task success | 实际用户目标达成 | 不等于 `finish` 或所有请求均返回 |

<a id="appendix-b"></a>
# 附录 B：常见故障定位

本表为工程检查建议，综合正文机制与失败分类。

| 现象 | 优先检查 | 不应立即下的结论 |
|---|---|---|
| 模型说调用了工具，但系统没有执行 | 是否真正生成原生调用、解析器是否识别 | 模型已经完成调用 |
| API 兼容，但特定模型总是解析失败 | tokenizer、chat template、parser 是否匹配 | 模型不支持任何工具 |
| 参数变成带反斜杠的 JSON 字符串 | 是否重复序列化 `arguments` | 只需再让模型重试 |
| Schema 通过但查错对象 | 对象解析、语义检查与参数来源 | Schema 没有价值 |
| 模型引用了未展示的变量内容 | 是否真实读取／打印结果 | Python 变量存在就足够 |
| 并行请求返回后结果串位 | ID 映射、批次、事件回填 | 多工具必然让模型混乱 |
| 一个请求异常使结果处理困难 | 成功和错误是否统一携带调用标识 | `return_exceptions=True` 已处理所有问题 |
| 超时后重复发送或扣款 | 幂等设计、状态查询与未知执行状态 | 超时一定意味着未执行 |
| 工具响应成功但文章数字错误 | 周期、单位、对象与结果引用绑定 | 只要换更大模型即可 |
| 生成结构偶发截断 | token 上限、结束原因与完成状态 | 开了 strict 就一定有完整对象 |
| MCP token 有效但发生越权 | 对象级授权、上游凭证范围 | 认证成功就拥有全部权限 |
| 指标线上变差但离线不变 | Provider、工具版本、数据和真实故障分布 | 模型能力一定退化 |
| 大工具库经常选错 | 候选召回、描述重叠、前置依赖 | 多放几百个工具必然更强 |
| XGrammar 结构率很高但任务率低 | 语义、工具选择和业务执行 | 约束解码已经解决全部工具问题 |

<a id="appendix-c"></a>
# 附录 C：复习问题

这些问题用于检查是否理解了机制，而不是记住名称。

| 问题 | 回答时应覆盖的关键点 |
|---|---|
| 为什么模型生成工具调用不等于真实执行？ | token、解析、执行器、权限与回执的分离 |
| 同一模型为何原子调用中 JSON 更好，复杂任务中 CodeAct 更好？ | 单步执行指标、控制／数据流与交互预算；表格本身不能确定错误原因 |
| 为什么 Toolformer 要比较“只有调用没有结果”的损失？ | 区分调用文字提示与外部结果的额外价值 |
| Toolformer 的局部损失为什么不足以保证长程工作流成功？ | 代理目标、局部权重、链式数据缺失 |
| API 里的 `arguments` 为什么不能直接传入所有模型模板？ | 字符串与对象边界、重复编码、适配器契约 |
| 一个 token 为什么可能需要访问完整 PDA 栈？ | 跨语法边界、完成子规则、返回父规则 |
| 多个解析路径的合法候选为什么取并集？ | 保留任意一条仍可完成的合法解析路径 |
| XGrammar 的 100% 正确率为什么不是任务成功率？ | 结构指标与业务语义、权限、执行结果的区别 |
| 为什么接入 MCP 不自动解决凭证安全？ | 实际隔离、身份验证、对象授权与上游权限 |
| 为什么调用 ID 不能代替幂等键？ | 结果关联与业务去重是不同保证 |
| 怎样判断 Agent 是否真的使用工具结果？ | 受控结果替换、返回顺序变化与最终事实核对 |
| 工具调用失败时为什么先查 trace，而不是先换模型？ | 选择、编码、解析、授权、执行、回填的故障分层 |

# 附录 E：实验与版本口径说明

## E.1 不同“正确率”不能互换

CodeAct 的 API-Bank 结果是原子调用执行正确率，M³ToolEval 结果是特定预算下的任务成功率；XGrammar 表 4 是结构／语法正确性；BFCL 总分混合多个能力分项；Provider 错误率反映特定请求与服务路径的运行表现。

它们可以共同帮助评估系统，但不是同一个指标，也不能直接横向替换。

## E.2 两个数字来源中的细节

CodeAct 表 3 的列值为 5.5、7.6、7.7 轮。本文分别与 JSON、文本对照计算轮数差，避免将正文中并列出现的改善数字错误地当成同一基线。

XGrammar 的 160 MB → 0.46 MB 是论文缓存内存结果，0.018 ms 是消融实验中的 mask 生成延迟；本文不把它们解释成整个模型内存或完整推理时间。其正文 §3.1–3.2 明确采用“预计算上下文无关候选、运行时检查上下文相关候选”的机制；上传版摘要和结论中的个别相关措辞不一致，本文以这些具体方法段落和算法说明为依据。

## E.3 教学示例不等于实测系统

文中的购物车金额、天气文本属于讲义示例；产品业绩 JSON 是明确构造的合成夹具；伪代码、接口片段和执行流程用于说明工程边界。本文没有声称已经部署真实天气／基金服务，或用这些示例完成新的模型基准测试。

## E.4 可变网页与固定论文版本分开

P01–P04 的解释以上传版本为准；新增 R28–R31 的论文解释以来源索引列出的在线版本为准。源码与文档的 `main`、`latest` 和 `draft` 链接可能变化，文中只对核对时可见的相关内容作说明，不假定所有资料来自同一个软件版本。

需要复现实验或投入生产时，应在自己的项目中记录模型、模板、解析器、依赖包、协议、工具 schema 和测试集的具体版本。这个版本记录本身就是定位工具调用故障的重要证据。
