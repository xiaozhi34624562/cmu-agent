### 1.3 贯穿全文的教学案例

假设一个内部资料下载器出现问题：

> 分页接口返回的数据没有被完整保存，最后一页时有遗漏。请查明原因并修复；保持公开接口和返回格式不变，补充边界测试，提交可审查的修改说明。不要发布或部署。

这是教学示例，不是上传论文中的实验任务，也不预设真实根因。后文为解释机制，会假设某次调查确认了“在累积末页数据之前就判断终止”的错误。

在一个真实仓库中，完成它可能需要理解 issue、找入口、查调用链、准备环境、构造复现、形成假设、修改代码、运行测试、回看结果和交付补丁。模型并不在一开始就知道所有步骤，更不应该把第一种猜测当事实。

**整节课的关键不是如何让模型多写一点，而是怎样组织这个不断获得证据、更新认识、改变环境的过程。**

## 第二章　HumanEval 与 SWE-bench：先定义什么叫“完成任务”

### 2.1 从函数生成到仓库修复，改变的是责任边界

HumanEval 给模型函数签名、说明等信息，让它补出实现，再通过单元测试判断功能是否正确。论文构建了 164 道手写题，强调行为正确性，而不是生成代码与参考代码的文字相似度。[R02，§2.1—2.2，第 2—4 页](#r02)

```text
HumanEval：规格基本已整理好 → 生成函数 → 执行测试
SWE-bench：真实 issue + 仓库快照 → 自行理解与修改 → 在环境中验收
```

SWE-bench 原始版本包含 2,294 个任务，来自 12 个 Python 仓库。任务可能需要协调多个函数、类和文件的修改。[R03，摘要、§2，第 1—3 页](#r03)

真正增加的是三项责任：**建立问题表述、主动获取信息、通过行动修正认识**。例如，最后一页遗漏可能出在分页循环、响应解析、调用方过滤，也可能只是观察数据的方法有误。Agent 必须调查，不能仅凭一个名字像 `pagination.py` 的文件就宣布定位成功。

### 2.2 为什么代码相似度不足以衡量正确性？

两个完全不同的实现可以具有相同功能；两个文字很接近的实现，也可能在边界输入上表现相反。HumanEval 因而选择执行测试，论文还讨论了 BLEU 等文本指标与功能正确性之间的差距。[R02，§2.1、§3.3，第 2、5—6 页](#r02)

这不意味着“测试通过等于数学证明”。有限测试只能覆盖部分行为，但外部执行结果仍然比模型自述“正确”提供了更直接的证据。

**工程推导：**验收应该围绕用户要改变的行为，而不是回答是否流畅、代码是否像参考答案、Agent 是否自信。

### 2.3 pass@k：候选覆盖不等于可交付能力

对一道题生成 $n$ 个样本，其中 $c$ 个通过测试，从中取 $k$ 个，至少有一个正确的估计量为：

$$
\widehat{\mathrm{pass@k}}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}
$$

对各题取平均得到整体指标。原论文用这种无偏估计，并提供数值稳定实现。[R02，§2.1，第 3 页](#r02)

公式表达的是“多个候选中有没有正确答案”，并没有解决“实际把哪个答案交给用户”。原论文的 Codex-S 实验中，100 个样本的理想测试选择覆盖率为 77.5%，用平均 token 对数概率选一个答案则为 44.5%；这是同一研究中候选覆盖与实际排序能力的差距。[R02，第 2 页图 1、§3.3](#r02)

因此：

$$
\text{生成更多候选}\neq\text{知道哪个候选正确}
$$

后续 Agent 通过运行、观察、修改来寻找答案，但仍然需要有效的验证与停止机制。一个 Verifier Agent 的“通过”也不是天然的真值。

### 2.4 SWE-bench 的重要贡献：怎样构建可验证任务

SWE-bench 从大量 PR 中筛选出关联 issue、贡献测试并能成功运行的实例。它在应用实际修复前后运行测试，保留至少有一个 Fail-to-Pass 测试的任务，剔除无法安装或运行的实例。[R03，§2.1，第 2 页](#r03)

Fail-to-Pass 检查目标问题是否修复；已有正常功能的测试用于检查修改是否带来退化。论文允许不同于参考 PR 的正确解，而不是强制生成同一份补丁。[R03，§2.2—2.3，第 3 页](#r03)

对下载器，验收至少要区分：

| 检查层次 | 具体问题 |
|---|---|
| 目标行为 | 原来遗漏的最后一页是否被保存？ |
| 原有行为 | 空结果、单页、多页路径是否仍然正常？ |
| 接口约束 | 函数签名、返回结构与顺序是否保持？ |
| 环境前提 | 测试是否运行在正确代码版本与依赖环境中？ |

后三项中的具体业务约束是案例设定，不是对 SWE-bench 所有任务的额外要求。

### 2.5 静态 RAG 的边界：召回更好，结果仍可能更差

原始 SWE-bench 使用 BM25 找文件后拼接输入、一次生成补丁。第 5 页表 3、表 4 显示：上下文上限从 13k 增大到 50k，平均参考文件召回率从 29.58% 增至 51.06%；Claude 2 的解决率却从 1.96% 降到 1.22%。[R03，第 5 页表 3—4](#r03)

| 上下文上限 | BM25 平均参考文件召回率 | Claude 2 解决率 |
|---|---:|---:|
| 13k | 29.58% | 1.96% |
| 27k | 44.41% | 1.87% |
| 50k | 51.06% | 1.22% |

这支持“输入更多信息不保证更有效利用”，不支持“RAG 无用”或“所有长上下文模型都更差”。

另外，oracle retrieval 只提供参考补丁修改过的文件。论文明确承认：这些文件也可能不包含理解调用关系所需的全部上下文。[R03，§4.1，第 4 页](#r03)

**连接下一章：**当初始检索不足以决定修复，Agent 就需要交互式获取信息。关键不再是一次找齐所有内容，而是每轮根据新证据选择下一步。

## 第三章　SWE-agent：工具接口为什么也是能力的一部分？

### 3.1 ACI 的完整含义

SWE-agent 把模型视为一种具有不同能力与限制的新型计算机使用者，提出 Agent–Computer Interface，即 ACI。它包含动作、说明、反馈以及历史如何组合成模型输入，而不只是函数名和 JSON 参数。[R04，§2，第 2—3 页](#r04)

人在终端里可以扫过大量无关输出；模型要付出上下文与计算成本。人在编辑器里能直接确认文件变化；模型若只得到静默执行，可能把“无输出”误判为失败，或把修改意图当成修改结果。

因此，ACI 的目标是让模型知道：**现在的状态是什么，刚才实际改变了什么，接下来怎样采取有效动作。**

### 3.2 四项设计原则如何落地

论文强调简单动作、紧凑操作、简洁但充分的反馈，以及防止错误传播的检查机制。[R04，§2，第 3 页](#r04)

**搜索先返回摘要，而不是诱导无穷翻页。** 搜索结果过多时要求缩小范围，避免把数千行无关信息灌进上下文。默认搜索最多报告 50 条，超过时提示更具体地查询。这里的 50 是论文配置，不是通用最优值。

**文件查看携带定位信息。** 路径、总行数、当前行号、上下省略行数，让片段可以被放回文件结构中。默认显示 100 行，可跳转或滚动。

**编辑与查看联动。** 修改指定范围后，立即显示真实修改结果，减少额外确认动作。

**语法错误直接反馈并撤回无效编辑。** 模型不必在已经破坏的文件上连续制造更多错误。[R04，§3，第 3—4 页](#r04)

### 3.3 工具返回不能只有 success

对一次修改，下列三种状态完全不同：

```text
参数不合法，执行器没有运行。
执行器运行了，但修改没有应用或被检查撤回。
修改已应用，当前文件如下。
```

“没有命中”和“搜索服务失败”也不能同样返回空列表而不说明原因。

**工程推导：**返回结构应分别描述执行状态、作用对象、版本或时间、主要结果、截断情况，以及必要的纠错信息。不要把业务完成、动作成功与请求合法混成同一个布尔值。

### 3.4 错误反馈的三个组成部分

SWE-agent 附录第 19 页解释：无效编辑反馈应该同时包含**错误类型、尝试修改后的内容、实际保留的原始内容**。[R04，附录 A.1，第 19 页](#r04)

没有错误类型，模型可能误诊；没有尝试内容，容易重复同一个动作；没有原始内容，可能继续根据一份从未保存成功的代码工作。

对下载器，假设 Agent 删除了一个参数，却没有删除函数内部引用。编辑检查失败并回退。下一轮最需要知道的不是“请小心”，而是：

> 删除参数的编辑未被保留；当前文件仍然是原版本；错误来自剩余引用；下面分别是尝试状态与真实状态。

这是防止**模型认识与真实工作区分叉**的设计。

### 3.5 检查机制也会限制合法工作流

附录第 20 页指出：删除参数等重构可能需要先改内部引用，或者同时修改多个相关位置。逐次严格检查会阻止某些暂时不完整、但后续可以补齐的中间状态。[R04，附录 A.1，第 20 页](#r04)

因此，检查机制是在两者间取舍：减少常见错误传播，与允许复杂变更经过过渡状态。

**工程推导：**普通局部编辑适合即时检查；复杂重构可在隔离工作区里完成一组相关变更，再统一检查。批量变更的提交与回退需要另行实现，不能从论文的局部编辑回退推断出多文件事务保证。

### 3.6 消融实验说明了什么？

下表来自论文第 6 页，在其 GPT-4 Turbo 与 SWE-bench Lite 设置下，对比不同 ACI 配置：[R04，第 6 页表 3](#r04)

| 配置 | 解决率 | 相对默认配置的变化 |
|---|---:|---:|
| 默认配置 | 18.0% | — |
| 编辑不带对应 lint 检查 | 15.0% | −3.0 个百分点 |
| 不提供专门编辑动作 | 10.3% | −7.7 个百分点 |
| 逐条翻阅搜索结果 | 12.0% | −6.0 个百分点 |
| 查看整个文件 | 12.7% | −5.3 个百分点 |
| 查看窗口 30 行 | 14.3% | −3.7 个百分点 |
| 保留完整历史 | 15.0% | −3.0 个百分点 |

逐条搜索看起来像人类编辑器，但 Agent 可能一路执行“下一条”，直到看完所有结果，预算已经用光。论文用具体轨迹解释了这种行为。[R04，§5.1，第 6—7 页](#r04)

实验支持“相同模型的表现受到接口显著影响”；不支持把默认窗口、历史长度等参数当成所有模型的永恒最优值。

### 3.7 失败轨迹比平均分更能指导工程修复

论文观察到成功任务往往较早结束，失败任务拖得更久；连续编辑失败后，恢复概率下降。在一组未解决任务的自动分类中，错误实现与过度特殊化实现约占 52.0%，无法从编辑错误恢复约占 23.4%；自动分类与人工验证样本的一致率为 87%。[R04，§5.2，第 8 页](#r04)

这些是特定设置的描述性结果，不能推导出“运行久就是失败”。但它提醒我们：追加预算不一定能纠正错误假设，也可能只是延长循环。

**工程推导：**干预条件应关注新证据、假设变化、真实文件变化和同类错误重复，而不只记录已经调用了多少次模型。

## 第四章　CodeAct：通用行动空间与可靠工具不是二选一

### 4.1 代码为什么可以成为行动语言？

CodeAct 1.0 的资料描述了两类回合：与人交流，或执行 Bash／Python 代码。与此同时，它加入 SWE-agent 风格的打开文件、跳转、搜索和局部编辑工具。[R05，“OpenDevin CodeAct 1.0”](#r05)

这两个方向互相补充：代码让 Agent 能使用已有库、构造复现、处理数据；专门设计的 ACI 则让常见操作更稳定、反馈更明确。

```text
CodeAct：我能够表达哪些行动？
ACI：这些行动是否容易使用，结果是否容易被正确理解？
```

在下载器例子中，用 Python 写复现和断言很自然；修改现有函数则可以用局部编辑接口。没有必要为每种业务都新增 Agent，也没有必要把所有工作压进一个不透明脚本。

### 4.2 显式补丁与隐式补丁

显式补丁生成要求模型直接输出格式严格的 diff；隐式补丁生成让模型修改仓库，再由 `git diff` 得出差异。CodeR 的相关讨论指出，后者能把部分补丁格式与行号处理责任交给已有软件工具。[R07，引言、§4.1，第 1、7—8 页](#r07)

但格式问题减少，不代表修改语义正确。无论怎样得到补丁，仍需在正确仓库版本上执行和验收。

### 4.3 动作粒度的工程取舍

一个动作太细，模型需要为机械步骤反复规划；一个动作太大，发生错误时难以判断哪些步骤完成、哪些需要撤销。

**工程推导：**以“能带来有意义进展、又能说明结果和副作用”为粒度。例如，读取并计算一批只读数据可以合并；下载、修改外部记录、发送消息和部署不宜仅为减少调用次数就绑在一个难以恢复的动作中。

代码生成能力扩大了行动空间，也扩大了错误影响面，所以它需要下一章的状态与执行控制。

### 4.4 固定预算、倒计时与卡住检测

CodeAct 1.0 加入剩余交互次数提醒，鼓励模型在固定交互预算内完成任务。[R05，“OpenDevin CodeAct 1.0”](#r05)

SDK 报告又讨论了相同行动、相同错误和重复查询等卡住模式。[R01，附录 A.11，第 19—20 页](#r01)

两者作用不同：预算提醒让模型知道资源约束，卡住检测观察是否正在无效消耗资源。它们都不能自动保证问题解决。

### 4.5 评测环境也是方法的一部分

CodeAct 1.0 预先准备不同仓库版本及依赖环境，按任务启动测试容器，降低临时安装与环境重置的摩擦。对已公开的同一批 SWE-agent 补丁，它重新评测出 52/300，而原报告为 54/300。[R05，“Containerized SWE-Bench Evaluation”](#r05)

该资料报告 CodeAct 1.0 在 SWE-bench Lite 上为 21.0%；这是当时具体环境中的结果，不是当前领先声明，也不足以单独归因到某一项工具改动。[R05，“How Does OpenDevin CodeAct 1.0 Stack Up?”](#r05)

**连接下一章：**如果环境、状态和执行入口会影响结果，生产框架就不能只提供一个模型循环。它需要把这些条件组织成明确、可保存、可重建的运行过程。

<a id="chapter-05"></a>
## 第五章　OpenHands SDK：让动作、事实与任务状态各归其位

### 5.1 V0 到 V1：重构解决的不是代码目录问题

SDK 报告描述了 V0 的四类压力：执行默认依赖沙箱，后来支持本地时产生重复实现；配置散落在多种入口和覆盖层；应用、研究评测与核心执行耦合；新增行为经常需要修改核心分支。[R01，§3，第 4—5 页](#r01)

例如，Web、CLI、GitHub 集成分别维护自己的 Prompt、环境配置和异常处理，同一任务从不同入口发起就可能行为不同。这里的核心缺陷是执行语义不一致，而不只是“项目大”。

V1 对应提出可选隔离、配置与状态分离、职责分离，以及部署包与类型化组件两层可组合性。[R01，第 2 页、§3](#r01)

**“可选隔离”是部署抽象上的选择，不是生产安全约束可以任意省略。** 本地直接运行与整套执行栈容器化使用相同核心逻辑，减少为不同入口另造执行链路。

### 5.2 四个包和九组核心能力

| 包 | 主要责任 | 为什么单独分开？ |
|---|---|---|
| `openhands.sdk` | Agent、Conversation、LLM、Tool、事件等核心抽象 | 避免应用和环境依赖侵入核心 |
| `openhands.tools` | 具体工具执行器 | 工具实现与慢测试可以独立演进 |
| `openhands.workspace` | 本地、Docker、远程 API 等工作区 | 绑定执行位置和环境资源 |
| `openhands.agent_server` | REST／WebSocket 远程服务 | 统一远程控制和事件传输 |

该划分见报告第 2 页图 1、§4.1。报告的架构章节还分别讨论事件状态、LLM、工具、Agent、上下文窗口、本地 Conversation、凭证、安全确认与部署。[R01，§4，第 5—6 页](#r01)

**ACI 研究一次交互怎样有效；SDK 研究同一种交互怎样在多种入口和环境中可靠复用。**

### 5.3 四个最重要的对象

| 对象 | 你应该把什么放在这里？ | 不应该混入什么？ |
|---|---|---|
| `Agent` | 模型、工具、指令等可复用行为配置 | 某次任务已经进行到哪一步 |
| `Conversation`／`ConversationState` | 任务输入、事件、状态、运行控制 | 另一位用户任务的进展 |
| `Workspace` | 文件、命令执行与环境访问 | 用户界面的展示逻辑 |
| 应用层 | 入口、界面、任务管理和业务流程 | 另一份重复的核心 Agent 循环 |

Agent 配置与可变会话状态的分离，是 SDK 报告的设计原则；表中的“放什么／不放什么”是对其工程责任的解释。[R01，§3.2、§4.2、§4.5](#r01)

讲义第 14—15 页先创建模型和工具，再创建 Conversation，发送任务并执行 `run()`。它表达的是运行关系，不是“一次模型请求等于一次任务”。[R00，第 14—15 页](#r00)

```python
# 讲义中的对象关系示意；变量须由调用方准备。
agent = Agent(llm=llm, tools=tools)
conversation = Conversation(agent=agent, workspace=workspace)
conversation.send_message(task)
conversation.run()
```

`run()` 驱动的是持续的动作—观察过程，直到结束、暂停、等待批准或出错。完整教学调用示例放在附录 A。

### 5.4 Stateless Agent 不等于系统没有记忆

报告把 Agent 与组件视为主要承载不可变、可序列化配置的对象，把可变运行数据集中到 `ConversationState`。[R01，§3.2、§4.2](#r01)

这意味着“不要让状态散落”，而不是把长任务变成无状态请求。它也不意味着文件系统、工具进程、浏览器和外部服务都没有状态。

为理解这点，可使用三个**教学抽象**：

| 记号 | 含义 | 下载器案例 |
|---|---|---|
| $W_t$ | 真实环境状态 | 当前代码、依赖、进程、外部对象 |
| $S_t$ | 执行系统记录的状态 | 运行状态、待处理动作、事件进度 |
| $C_t$ | 本轮模型实际看到的上下文 | 用户约束、代码片段、测试反馈与摘要 |

模型“记得已经修复”属于 $C_t$；文件真的修复属于 $W_t$；系统知道动作已经处理属于 $S_t$。三者不一致时，问题不能仅靠更长 Prompt 解决。

### 5.5 为什么需要事件，而不只是 messages 列表？

聊天消息难以明确区分“准备执行”“已经执行”“用户拒绝”“工具失败”和“历史被压缩”。SDK 使用结构化事件表达这些区别。[R01，§4.2，第 6 页表 1](#r01)

| 事件类别 | 语义 |
|---|---|
| `MessageEvent` | 用户或助手的文字消息 |
| `ActionEvent` | Agent 提出的工具调用 |
| `ObservationEvent` | 工具实际执行结果 |
| `UserRejectObservation` | 用户拒绝该动作 |
| `AgentErrorEvent` | Agent 或执行框架错误 |
| `ConversationStateUpdateEvent` | 内部状态变化 |
| `PauseEvent` | 用户请求暂停 |
| 压缩相关事件 | 记录压缩请求、结果和摘要 |

报告表格和正文对部分压缩事件采用了不同名称；这里保留“压缩相关事件”的功能区分，不据此断言所有类名在实际版本里完全相同。

部分事件可转换为模型消息，部分只供内部控制。**完整运行日志与模型输入不是同一个对象。**

### 5.6 一轮执行究竟发生什么？

下面是根据 SDK 机制整理的**教学时序**，不是源码逐行转录：

```text
读取会话状态与事件
    ↓
按规则构建模型上下文，包括必要的压缩结果
    ↓
模型提出下一条消息或工具动作
    ↓
验证参数并记录动作
    ↓
检查权限／风险／是否需要人类确认
    ├─ 等待确认：保存待处理状态并暂停
    ├─ 被拒绝：记录拒绝，交还模型调整
    └─ 允许执行：调用执行器
                         ↓
                得到实际结果或错误
                         ↓
                记录观察、更新状态
                         ↓
                   下一轮或结束
```

关键是不让“提出动作”和“动作已经发生”混在一起。事件回调把进度输出与运行控制分开，提供安全插入、增量执行和界面更新的位置。[R01，§4.5，第 9 页](#r01)

### 5.7 Action—Execution—Observation：三种不同契约

**Action 是格式契约。** 工具需要哪些输入、字段是什么类型。

**Execution 是执行契约。** 哪个执行器接受动作，在什么资源上真正执行。

**Observation 是结果契约。** 将执行结果或错误转换成模型能够使用的信息。

报告明确采用这一结构，并以 Pydantic 模型验证 Action。[R01，§4.4，第 7—8 页、图 4](#r01)

它与 SWE-agent 的联系非常直接：输入格式正确并不能弥补含糊的反馈；一句“成功”也不能证明业务完成。

$$
\text{格式合法}\neq\text{权限允许}\neq\text{执行成功}\neq\text{任务完成}
$$

这是对责任边界的总结，不是论文提出的形式化定理。

### 5.8 工具注册：跨网络传规格，而不是传运行中的 Python 对象

SDK 把工具描述为注册名称与可序列化参数，再通过注册机制在目标环境中重建具体定义与执行器。它能够结合当前工作区等上下文延迟初始化。[R01，§4.4，第 8 页](#r01)

这让客户端表达“需要哪些能力”，服务端负责绑定“这些能力实际在哪个环境执行”。避免把进程内对象、临时资源和客户端状态直接当成网络协议。

### 5.9 MCP：统一接入，不统一信任

MCP 工具的输入 Schema 被转换为 Action，执行结果表现为 Observation，底层通信由 MCP 客户端处理。于是内建工具与外部工具进入相同执行抽象。[R01，§4.4，第 8 页](#r01)

讲义第 26 页同时提醒服务器访问和信任要求。[R00，第 26 页](#r00)

**工程推导：**一个工具能被发现和调用，不表示它被授权访问全部资料。工具返回的内容也不能仅因来自工具就自动变成高优先级指令。协议层与权限边界必须分开设计。

### 5.10 模型适配、非原生工具调用与多模型路由

SDK 报告包含统一 LLM 接口；对于没有原生工具调用能力的模型，它通过把工具格式写入 Prompt 并解析输出提供适配；`RouterLLM` 则允许同一 Agent 的不同请求使用不同模型。[R01，§4.3，第 7 页](#r01)

不要因此混淆三个维度：

```text
模型数量：底层调用几个模型。
Agent 数量：存在几个独立的任务执行上下文。
并行度：有多少工作同时运行。
```

一个 Agent 可以多模型路由；多个 Agent 也可以全部使用同一个模型。协议兼容也不等于任务能力一致，工具使用质量仍需实际评测。

## 第六章　长任务：上下文、持久化、工作区与恢复语义

### 6.1 日志、模型上下文和真实证据必须分开

SWE-agent 折叠较早观察，不只是省 token，还能避免旧文件内容持续干扰。SDK Condenser 将旧事件替换成摘要，但把压缩结果本身写入日志，原始事件仍被保留。[R04，§3，第 4 页](#r04) [R01，§4.6，第 9 页](#r01)

可以用数据工程类比来理解：事件日志像事实记录；本轮上下文像按任务构建的视图；文件、测试和产物则是当前环境中可检查的对象。这个类比是教学解释，不表示 SDK 与某个数据库具有相同实现。

```text
完整事件日志 ──构建与压缩──> 本轮模型上下文
      │                           │
      └──── 用于追踪和恢复         └──── 用于下一步决策

工作区文件、测试日志、最终产物 ───> 外部核验依据
```

摘要可以帮助找到证据，但不应取代证据。

### 6.2 为什么不处理历史，成本容易快速增长？

假设每步新增约 $b$ 个 token，每轮都重新输入此前全部历史，$T$ 步累计输入量近似为：

$$
C_{\text{input}}\approx\sum_{t=1}^{T}bt=\frac{bT(T+1)}{2}
$$

这是**教学推导**，只说明反复传输历史的输入量趋势，不是模型运算复杂度或真实账单公式。缓存、输出长度和具体计费方式会影响实际成本。

SDK 报告引用了默认摘要器在相关实验中降低成本的结果，但本文不把该结果泛化为任何任务都能固定省一半。[R01，§4.6，第 9 页](#r01)

### 6.3 不同信息具有不同寿命

**工程推导：**约束性信息、任务进展与易变观察，应采用不同维护方式。

| 信息类型 | 例子 | 维护重点 |
|---|---|---|
| 约束 | 不改公开接口、不部署 | 显式保存，防止摘要遗漏 |
| 进展与假设 | 已排除接口漏返回；下一步检查终止条件 | 区分猜测、验证与排除 |
| 具体观察 | 某版本代码片段、上一次网页截图 | 标记对象、时间或版本，处理过期内容 |
| 产物证据 | 测试结果、diff、输出文件 | 保持可追溯，不仅保留口头总结 |

好的摘要不应把“曾经猜测”升级成“已经确认”，也不应把修改前的代码保留为当前事实。

下载器任务可采用如下**摘要模板**：

```text
目标与约束：保持接口，修复末页遗漏，不发布。
已确认事实：每条事实关联文件、测试或事件位置。
当前假设：尚未证实的解释。
已修改内容：对应工作区版本和文件。
验证结果：实际运行的测试、结果和限制。
已排除路径：避免无意义重复。
待办事项：下一步行动及仍缺的证据。
```

### 6.4 讲义的压缩参数只是演示，不是生产答案

讲义第 18 页给出 `LLMSummarizingCondenser(max_size=10, keep_first=2)`，表达保留初始信息与近期工作、压缩较早内容的思路。[R00，第 18 页](#r00)

这些示例用于说明历史规模控制。本文保留其教学用途，但不依据幻灯片中的两个数字推出精确生产阈值或所有版本中的触发逻辑；具体参数语义需要与部署版本核对。

该页最重要的提示是：**压缩可能损失细节，文件与测试仍应作为证据。**

### 6.5 保存 Conversation 不等于保存工作现场

讲义第 17 页明确说 Workspace persistence 是另一个问题。[R00，第 17 页](#r00)

SDK 的 ConversationState 保存可变元数据和追加式事件。启用持久化后，元数据写入状态文件，事件增量存储；恢复时加载状态与事件。[R01，§4.2，第 6—7 页](#r01)

从生产视角，可以进一步分四层：

| 层次 | 要保存或核对的内容 | 恢复聊天历史能否解决？ |
|---|---|---|
| 会话状态 | 暂停位置、待审批动作、运行统计 | 属于会话持久化的主要职责 |
| 事件历史 | 请求、动作、观察、拒绝、压缩 | 需要完整且可关联的记录 |
| 工作区 | 修改后文件、依赖、临时脚本、日志 | 不能，需额外保存或重建 |
| 外部系统 | PR、消息、远程作业等 | 不能，需查询和核对 |

这四层是工程分解，不是宣称 SDK 自动提供了全部恢复保证。

### 6.6 重放不等于重新执行所有动作

SDK 使用 event-sourced state 和 deterministic replay 的表述。应区分：按已记录事件恢复内部状态，与重新向模型提问或重新调用外部服务。[R01，第 2 页、§4.2](#r01)

后者面对的世界可能已经变化。模型调用也可能产生新输出。因此，不能把内部状态重建理解为外部执行天然可重复。

下载器修好后，Agent 创建 PR；PR 已成功，但网络断开，响应没有到达。此时系统不知道结果。直接重试可能重复创建，直接跳过可能漏掉未完成动作。

**工程推导：**为动作维护“尚未执行／已知完成／结果未知”的语义。对支持幂等键的服务使用幂等键；结果未知时先按业务标识查询；无法确认的不可逆动作交给人工处理。事件日志提供判断依据，但不自动让所有外部系统获得恰好执行一次语义。

### 6.7 恢复点应该关联哪些对象？

以下是前述原则的**工程设计建议**，不是 SDK 固定 Schema：

```text
conversation_id
最后确认处理的事件位置
Agent／Prompt／Skill／工具配置版本
workspace_id 或工作区快照
代码基线与当前产物版本
待处理审批
尚未确定结果的外部动作
剩余预算与已用成本
```

目标是恢复之后能回答：记录中的世界和实际工作现场是否一致？不一致时，先对齐，而不是让模型继续建立在错误前提上。

### 6.8 暂停、恢复、撤销与补偿是不同能力

| 能力 | 含义 |
|---|---|
| 暂停 | 不再继续推进后续执行，具体正在运行的动作要看实现 |
| 恢复 | 依据保存状态继续任务 |
| 撤销 | 将某类资源恢复到先前版本 |
| 补偿 | 对不能直接撤销的外部影响执行另一个纠正动作 |

SDK 提供暂停与恢复控制；VS Code 教程又明确指出：停止不撤销已完成动作，恢复检查点不能逆转网络请求、部署或外部服务变更。[R01，§4.7，第 9—10 页](#r01) [R11，“Stop, revise, or undo the work”](#r11)

**工程推导：**面向长命令时，还必须确定子进程是否继续、退出码如何捕获、超时怎样记录以及重启后怎样核对。资料没有给出所有长命令的统一恢复协议，不能从“支持 pause”推导出任意进程都能自动暂停并完整恢复。

<a id="chapter-07"></a>
## 第七章　执行环境与安全：把判断、授权、隔离分开

### 7.1 安全隔离与可复现是两个目标

HumanEval 的函数级评测就需要执行不可信代码。论文使用 gVisor 作为主机保护组件，并使用网络规则限制连接。[R02，§2.3，第 4 页](#r02)

CodeAct 1.0 的容器化评测则强调预置代码版本与依赖、按任务重置环境。[R05，“Containerized SWE-Bench Evaluation”](#r05)

前者回答“代码能影响什么”，后者回答“相同任务的运行条件是否一致”。环境可以隔离良好但依赖漂移，也可以依赖固定但权限过大。

**工程推导：**独立记录安全策略与可复现条件，不能把“使用 Docker”同时当成二者都已解决的证明。

### 7.2 本地与远程的统一接口

正文 §4.10 描述：Conversation 工厂在本地 Workspace 下运行本地循环；在远程 Workspace 下，序列化 Agent 配置并发给 Agent Server，服务端运行本地执行栈，通过 WebSocket 返回事件。[R01，第 10—11 页、图 5—6](#r01)

```text
客户端 RemoteConversation
       │  配置与控制请求
       ▼
Agent Server
       ▼
LocalConversation → Agent + Tools → 工作区
       │
       └──────── 结构化事件返回客户端
```

这对应讲义第 19 页的“Agent Server inside Docker”。[R00，第 19 页](#r00)

**资料差异：**报告附录 A.14 又使用“Agent 在客户端、工具在远程”的描述，与正文图 6 不完全相同。本文按正文与讲义解释远程 Conversation，不把两种叙述合并成同一个已验证拓扑。[R01，附录 A.14，第 20 页](#r01)

### 7.3 接口相同不保证结果相同

同一段 Agent 代码能够切换执行位置，不意味着代码仓库、依赖、文件、网络和凭证已经自动对齐。

报告说明本地 Workspace 是直接操作主机文件和命令的薄封装；给它一个路径，不等于操作系统自动只允许访问该目录。[R01，§4.10，第 11—12 页](#r01)

**工程推导：**远程工作区上线前应验证仓库快照、依赖、必要服务、凭证范围、网络策略和资源限制。这些是运行前提，不应全部靠模型发现并猜测修补。

### 7.4 SecurityAnalyzer 与 ConfirmationPolicy

SDK 用 `SecurityAnalyzer` 给动作评估风险，用 `ConfirmationPolicy` 决定是否需要批准；需要时进入 `WAITING_FOR_CONFIRMATION`，拒绝后可把反馈交还模型寻找替代路径。[R01，§4.9，第 10 页](#r01)

两者分别解决“这个动作看起来危险吗”和“当前策略允许它自动执行吗”。

更完整的责任边界可理解为：

| 层次 | 应回答的问题 |
|---|---|
| 风险判断 | 具体动作是否超出任务、是否有危险副作用？ |
| 授权 | 当前身份能够访问哪个对象、执行哪种操作？ |
| 隔离 | 判断出错后，进程实际能够触及哪些资源？ |
| 人类确认 | 哪些决策必须由人承担授权责任？ |

这个分层是工程解释。**模型认为低风险，不能扩大原本的授权范围。**

### 7.5 SecretRegistry：让凭证在执行时绑定

报告描述的 SecretRegistry 按会话管理凭证，支持执行时注入、输出掩码、序列化脱敏和运行中更新。凭证也可由动态刷新函数等来源提供。[R01，§4.8，第 10 页](#r01)

它能减少把凭证长期放在模型上下文或普通日志中的必要性，但不等于已经证明所有外传通道都被阻断。

**工程推导：**凭证管理要与执行权限、网络约束和资源隔离配合。对普通读取、代码修改、创建外部对象与发布动作分别授权，而不是让一个长期凭证覆盖全部流程。

### 7.6 安全约束应该进入执行控制，而不只是 Prompt

“不要部署”是有用指令，但不是强制保证。正确做法是任务根本不具备不必要的部署能力，或必须经过单独批准。

SDK 的安全插入点提供了实施这类策略的位置；GitHub coding agent 的上传材料也展示了让 Agent 的变更经过分支规则、工作流批准和人工审查的产品设计。[R01，§4.5、§4.9](#r01) [R12，“Integrated, configurable, and secure”](#r12)

**连接下一章：**权限边界也会影响如何划分 Agent。不同权限的执行主体可能值得分开，但不能因为角色名字不同，就认为隔离已经成立。

<a id="chapter-08"></a>
## 第八章　CodeR、MetaGPT 与单 Agent：结构究竟应该放在哪里？

### 8.1 不要把讨论简化成“几个模型一起聊天”

讲义第 22—28 页先展示专门角色，再提出单 Agent 基线、通用工具、Skills 和有明确目的的分工。[R00，第 22—28 页](#r00)

这组资料真正讨论的是：**复杂任务的结构，应该放在角色、任务图、共享产物、工具，还是同一 Agent 的上下文里？**

CodeR 侧重任务执行图；MetaGPT 侧重标准交付物与通信协议；单 Agent 博客质疑不必要的角色隔离。把这三种思想只归为“多 Agent 好还是不好”，会丢掉最重要的设计细节。

### 8.2 CodeR 的五个角色分别承担什么？

| 角色 | 核心责任 | 应产生的结果 |
|---|---|---|
| Manager | 选择计划、解释执行报告、决定提交或调整 | 任务图与整体判断 |
| Reproducer | 从 issue 提取或生成可运行复现 | 复现脚本、实际现象 |
| Fault Localizer | 使用定位工具缩小故障范围 | 可疑代码位置与依据 |
| Editor | 根据上下文实施修改 | 代码变更 |
| Verifier | 运行复现或仓库测试检查 | 实际测试结果与总结 |

职责来自 CodeR §2。其“integration tests”特指仓库已有测试，不等于把 SWE-bench 隐藏验收测试交给 Agent。[R07，§2，第 2—3 页](#r07)

CodeR 还检索相似 issue 与补丁，并要求判断相关性，而不是自动照抄。这里的检索是参考证据，不是对当前任务的真值。[R07，§2，第 2 页](#r07)

### 8.3 Task Graph：软计划与硬控制的区别

CodeR 用 JSON 表示计划，定义 `entry`、角色、`task` 和成功／失败的 `downstream`。节点内部仍可多轮运行，节点之间按图转移。[R07，§3.1，第 4—5 页](#r07)

```text
文字计划：请先复现、再定位、再修改、再验证。
任务图：复现节点完成后，程序根据结果激活指定下游。
```

前者依靠模型持续遵守指令；后者把一部分流程正确性放到程序中。图不会保证每个节点做对，但可以约束节点间的执行顺序与交接。

论文展示四种计划：A 为标准路径，B 直接尝试编辑简单问题，C 加入测试反馈循环，D 使用问题真实测试驱动修复。**实际实验只使用 A 和 B**，不能拿其成绩证明图中所有计划都已验证，也不能认为实验提供了 D 中的真实验收测试。[R07，第 5 页图 3 与正文](#r07)

### 8.4 CodeR 更重要的一步：让测试反馈帮助定位

通常 Agent 只读取测试是否通过和报错文字。CodeR 还利用测试覆盖信息，使用 Spectrum-Based Fault Localization，简称 SBFL，计算语句可疑度。[R07，§3.2，第 5 页](#r07)

直觉是：更常被失败测试覆盖、较少被通过测试覆盖的位置，可能更可疑。它再把这类运行证据与 issue—代码文本相关性结合：

$$
\mathrm{Score}=\lambda\mathrm{Score}_{\mathrm{Ochiai}}+(1-\lambda)\mathrm{Score}_{\mathrm{BM25}}
$$

论文还对文件级 BM25 得分做归一化。[R07，§3.2，第 6 页式 1—2](#r07)

对于下载器，BM25 可能同时找到分页模块、调用方和响应处理器；覆盖信息则告诉你失败复现究竟经过哪些路径。这两类证据分别代表“文字上相关”和“运行上相关”。

这与 SWE-bench 的问题形成直接递进：**不是一味增加检索材料，而是引入不同性质的证据，提高定位质量。**

### 8.5 故障定位有明确前提

SBFL 需要可运行的失败测试；若复现失败或收集不到覆盖，就无法使用该路径。论文的定位分析先保留 140 个成功复现任务，再筛到 104 个具有非空覆盖的任务。[R07，§3.2，第 5—6 页](#r07)

覆盖也不等于因果。一个正常函数可能被所有失败测试经过。它提供排序线索，不替代代码理解与修复验证。

### 8.6 CodeR 消融：收益不能全归因于 Agent 数量

论文在随机选取的 50 个问题上做消融：[R07，第 9 页表 5](#r07)

| 配置 | 解决率 | 解决数 |
|---|---:|---:|
| 完整 CodeR | 22.0% | 11/50 |
| 移除 Multi-Agent 与 Task Graph | 10.0% | 5/50 |
| 移除 Fault Localization | 14.0% | 7/50 |

它支持“这组结构和工具在该设置中有效”，但同时移除多 Agent 与任务图，不能单独识别二者各自贡献。成本与调用次数也发生变化，小样本结果更不应被推广成普遍定律。

CodeR 主结果文本和表格还存在计数差异，见附录 D；本文不自行将这些记录合并成一个统一数值。

### 8.7 MetaGPT：中间产物比角色台词更重要

MetaGPT 使用 Product Manager、Architect、Project Manager、Engineer 和 QA Engineer，按标准操作流程生成需求、设计、任务与代码。[R08，§3.1，第 4—5 页](#r08)

典型链路是：

```text
用户需求 → PRD → 文件／数据结构／接口设计 → 任务分配 → 实现 → 测试
```

这里的主要贡献不是“模拟公司”，而是明确交接物。Architect 不只说“架构已经设计好了”，而是输出下游能够使用的模块结构、接口和交互信息。

**工程推导：**对定位任务，好的交接应该包含文件、函数、复现输入、实际与预期输出、可疑原因与证据；一句“我认为分页函数有问题”不足以支撑下一阶段。

### 8.8 共享消息池与订阅解决什么问题？

MetaGPT 让角色把结构化消息发布到共享池，其他角色按需要读取；订阅机制限制不相关信息进入各自上下文；必要依赖到齐后才触发行动。[R08，§3.2，第 6 页](#r08)

它减少两类问题：反复点对点索取同一份产物，以及所有信息广播给所有角色导致的上下文膨胀。

共享池与订阅是通信组织方式，不意味着输入天然可信、产物必然完整，也不自动解决并发修改一致性。

### 8.9 多角色审查为什么仍然需要实际运行？

MetaGPT 早期实现中的纯文字审查会漏错，因此加入写测试、执行、观察报错并迭代修改的机制，直到通过或达到最多三次重试。[R08，§3.3，第 6 页](#r08)

其消融报告执行反馈使 HumanEval 与 MBPP 的 pass@1 分别提高 4.2 和 5.4 个百分点。[R08，§4.4，第 9 页](#r08)

这再次连接 HumanEval：**内部讨论可以生成候选判断，外部执行提供另一种性质的证据。**

### 8.10 MetaGPT 的结果有哪些适用边界？

MetaGPT 涉及函数级生成，以及从需求开始构建软件，不完全等同于大型现有仓库的 issue 修复。SoftwareDev 包含 70 个任务，比较中选取七个；角色消融使用两个任务。[R08，§4.1、第 7 页；§4.4、第 9 页](#r08)

因此，不能把它的高分与 SWE-bench 分数直接排在同一列，也不能用角色消融证明所有任务都应该增加角色。

还应注意它的部分指标定义：例如 SoftwareDev 的“Productivity”按 token／代码行计，不是长期维护价值；代码更多本身不等于产出更好。[R08，§4.1，第 7 页](#r08)

### 8.11 单 Agent 博客提出的三个反问

《Don't Sleep on Single-agent Systems》指出：预设角色边界可能与问题不匹配；交接摘要可能丢失信息；多个 Prompt 和独立分支增加维护成本。[R06，“Some Issues with Multi-agent Systems”](#r06)

下载器的 Editor 改到一半发现根因在调用方，需要重新定位。如果它被限制得过窄，就要反复交接；若每个角色最后都获得全部工具与全部历史，则最初拆分的价值需要重新解释。

该博客并非否定多 Agent，而是建议先建立强单 Agent 基线，用通用工具与合适指令承担多种活动；权限不同或代表不同主体的情形仍可能需要多 Agent。[R06，“How can we make Excellent Single-agent Systems”“Conclusion”](#r06)

### 8.12 Skills：更多知识不必意味着更多执行主体

讲义将 Skill 定义为给同一个 Agent 的额外指令，早期名字 microagents 容易误导，但这里并不是自动启动另一个 Agent。[R00，第 25 页](#r00)

SDK 的 `AgentContext` 支持常驻与条件激活的 Skill。资料中 `trigger=None` 表示常驻指导，条件激活可根据用户输入中的关键词触发。[R01，§4.5，第 9 页](#r01)

| 机制 | 主要改变什么？ |
|---|---|
| Tool | 能执行什么操作 |
| Skill | 特定场景下应该怎样做 |
| Condenser | 当前任务的历史怎样进入本轮上下文 |
| 子 Agent | 增加独立任务上下文与执行过程 |
| MCP | 外部能力怎样被描述和调用 |
| RouterLLM | 本轮调用哪个基础模型 |

“修改分页逻辑时覆盖空结果、单页、整页与末页”是一条程序性指导，不一定需要“分页专家 Agent”。若该检查是不可省略的发布条件，则应该进一步由程序验收，而不只是放在 Skill 里。

### 8.13 综合设计：流程分阶段，阶段内部保留自主性

**工程推导：**可以同时吸收 CodeR 的任务结构、MetaGPT 的交付规范和单 Agent 的共享上下文优势：

```text
程序确定任务与验收条件
    ↓
一个 Agent 在明确范围内完成复现、定位、编辑、测试
    ↓
程序提取实际产物与证据
    ↓
独立审查或人工复核
    ↓
依据当前版本决定是否交付
```

流程结构与 Agent 数量是可以解耦的。多 Agent 值得引入的常见目的，是独立任务并行、独立审查、权限隔离或明确的成本分工；讲义第 28 页也按这些目的组织分工。[R00，第 28 页](#r00)

### 8.14 并行与独立审查的两个陷阱

SDK 报告中的子 Agent 是独立 Conversation，但继承父任务的模型配置与工作区上下文；报告版本的委派示例是阻塞式并行，父任务等待子任务完成。[R01，§4.5，第 9 页](#r01)

因此，**独立 Conversation 不等于独立文件系统**。多个 Agent 同时修改同一文件仍可能冲突。独立分支、工作目录、合并和复验需要另行设计。

另一方面，审查 Agent 若只阅读前一个 Agent 的总结，可能继承相同错误假设。**工程推导：**独立审查应从原始需求、真实 diff、执行结果和必要的原始文件出发，而不是只检查前一段文字是否自洽。

<a id="chapter-09"></a>
## 第九章　OpenHands-Versa：从代码任务到通用知识工作

### 9.1 泛化瓶颈有时在工具，而不只在模型

Versa 的研究问题是：少量通用工具能否支持多种任务，而不为每个领域设计新的专用 Agent？其三类能力是代码编写与执行、多模态网页浏览，以及搜索和多模态文件访问。[R09，§1，第 1—2 页](#r09)

这不是要求模型把所有知识记在参数中，而是提供完成任务所需的信息与动作通道。

```text
查找资料 → 打开来源 → 读取文件 → 写分析程序 → 执行 → 检查 → 形成报告
```

只会浏览网页的系统可能不能计算；只会写代码的系统可能拿不到文件；一个阶段缺能力，就会阻断整个任务。

### 9.2 改动一：截图与 AXTree 共同构成观察

原 OpenHands 文本浏览使用 accessibility tree，即 AXTree。它表达页面文字与交互结构，却可能遗漏视觉布局。

Versa 在当前视口截图上为可交互元素添加标记与 browsergym ID，同时保留 AXTree；当树太大时可缩到视口范围。[R09，§2.2，第 3 页](#r09)

这把“看到哪个对象”和“用哪个 ID 操作对象”连接起来。它不是仅把截图塞进模型，也不是完全用坐标替代结构化信息。

浏览观察较大且会过期，所以论文保留最近 $k$ 次浏览观察，较早观察以占位消息替代。这个浏览压缩机制与 SDK 的历史摘要相关，但不是同一套算法。[R09，§2.2，第 3 页](#r09)

### 9.3 改动二：搜索 API 与浏览分工

论文通过搜索 API 减少搜索阶段的浏览成本与验证码阻碍。搜索结果帮助选择来源，浏览器负责进一步访问和交互。[R09，§2.2，第 3 页](#r09)

不要扩大为“搜索 API 消除了所有网站限制”。原论文错误分析仍然提到目标页面无法访问的情况。[R09，§5.2，第 8—9 页](#r09)

### 9.4 改动三：统一文件阅读接口

Versa 将多种文件通过转换器整理成 Markdown 表示，使 Agent 不必为每个文件临时编写读取程序。[R09，§2.2，第 3—4 页](#r09)

但统一表示不等于信息完整无损。资料没有证明该能力可以解决所有复杂版面、跨页表格、数值口径与精确坐标追踪问题。

**工程推导：**对研报、财报和营销材料，阅读表示与证据表示应分开：前者帮助模型理解，后者保留原文位置、原页和数据出处。

### 9.5 改动四：周期性计划提示，而不是新增 Planner

Versa 每隔 $\tau$ 步向事件流加入固定提示，要求总结当前进展并规划后续动作。[R09，§2.2，第 4 页](#r09)

它与 CodeR 任务图不同：这里是软提示，帮助模型重新聚焦；任务图则限制程序节点转移。不能因两者都叫“planning”就认为提供相同保证。

### 9.6 相同模型下的对照，比跨系统排行榜更有解释力

论文用相同 Claude 3.7 Sonnet 比较 OpenHands v0.28.1 与 Versa，主结果采用三个基准的测试集。[R09，§3.2—3.3，第 6 页；第 7 页表 2](#r09)

| 系统 | GAIA | SWE-bench Multimodal | The Agent Company 全部完成 | 部分完成得分 |
|---|---:|---:|---:|---:|
| OpenHands v0.28.1 | 37.21% | 31.72% | 26.29% | 36.41% |
| OpenHands-Versa | 51.16% | 31.33% | 30.86% | 40.18% |

这说明在该设置中，信息获取和企业任务能力提升，代码任务基本保持。并不是每项都提升，更不是一个排除模型、工具、预算差异之后的“单 Agent 普遍优于多 Agent”证明。

讲义第 27 页总览图还使用了 Versa 的另一模型配置成绩；分析架构改动时，应回到原论文表 2 的同模型行，而不是混用两种比较。[R00，第 27 页](#r00) [R09，第 7 页表 2](#r09)

### 9.7 工具使用分布提供机制证据

原论文第 8 页图 2 显示，不同任务使用的工具组合不同：GAIA 偏搜索、浏览和独立 Python；The Agent Company 偏内部网页；软件任务偏终端、编辑与文件查看，也用浏览器作视觉验证。[R09，§5.1，第 8 页](#r09)

这支持“统一 Agent 能按任务需求调整行为组合”，而不是简单证明工具越多越好。

### 9.8 搜索服务选择与证据质量的张力

在 GAIA 验证集的搜索 API 对照中，Brave、Exa、Tavily 对应解决率为 56.96%、58.18%、64.24%。这与上面的主结果不是同一数据划分，不能直接相减。[R09，§5.3，第 9 页](#r09)

论文解释，搜索摘要会影响模型选择哪些页面，同时指出依赖不准确摘要可能引入错误。因此，更好的信息入口既能改善任务表现，也需要最终事实复核。

### 9.9 从错误分析提炼边界

Versa 的失败包括错误搜索摘要、网站访问限制、浏览循环、只完成部分要求，以及没有充分运行现有测试就提前结束。[R09，§5.2，第 8—9 页](#r09)

**工程推导：**通用任务应分别检查获取是否充分、处理是否正确、证据是否支持结论，以及所有验收项是否完成。计算成功不能证明数据口径正确；文件能打开不能证明内容解析无误；一条测试通过不能证明整个任务完成。

<a id="chapter-10"></a>
## 第十章　人机协作与界面：Agent 做得更多，人为什么未必更满意？

### 10.1 从任务分数到人的效用

前面的 benchmark 主要问系统是否解决任务；《Code with Me or for Me》还问用户投入多少、如何交互、能否理解结果、是否愿意继续使用。[R10，§3，第 4 页](#r10)

它与讲义第 29—36 页的部署和界面设计直接相关：如果人必须持续盯着输出、手动搬运文件和运行命令，模型即使能生成正确代码，也未必真正减少人的工作。

### 10.2 研究怎样设计？

研究招募 20 位经常使用 Copilot、具有 Python 经验、此前没有 coding agent 使用经验的学生参与者；其中不少具有职业编程经历。每人分别使用 Copilot 和 OpenHands，顺序随机化，每种条件 40 分钟；任务涵盖数据分析、添加功能和修复问题。[R10，§3.1—3.4，第 4—6 页](#r10)

OpenHands 固定使用 Claude Sonnet 3.7；Copilot 条件允许参与者选用可用模型。这是尽量接近使用情境的比较，不是完全控制底层模型的架构消融。研究时间为 2025 年 4—5 月，不应用来描述今天所有同名产品的功能边界。[R10，§3.2—3.4、§5.3](#r10)

### 10.3 “人工投入减半”与“总耗时减半”不同

对正确完成的任务，论文报告：[R10，§4.1，第 8 页图 4](#r10)

| 指标 | 结果 |
|---|---:|
| Copilot 条件下的用户投入 | 平均 25.1 分钟 |
| Agent 条件下的用户投入 | 平均 12.5 分钟 |
| 人与 Agent 完成任务的总耗时 | 平均 27.9 分钟 |

因此，直接参与减少，不等于整项任务更快一倍。释放出的时间能否用于其他工作，取决于真实工作流；研究没有直接测量多人、多任务长期排程的收益。

论文也报告了任务正确率改善，文字使用“35% ± 15% increase”表述，相关检验为 $p=0.02$。这里保留研究的结论方向，不把这一表述改写成所有开发场景统一的相对效率提升。[R10，§4.1，第 8 页](#r10)

### 10.4 投入时间只是研究定义的代理指标

Copilot 条件按任务起止总时间衡量投入；Agent 条件按围绕用户消息的交互时间窗口估计，包含检查输出与提出新要求的时间。[R10，§3.6，第 7 页](#r10)

这不是对全部阅读、等待、认知负担的直接测量，而且时间比较限于正确完成的任务。不能忽略测量方式与样本筛选，把结果简化成普遍生产力结论。

### 10.5 收益来自哪里？不只是更快打字

论文第 10 页图 5 与后续轨迹分析显示，环境准备、创建文件、运行程序、复制错误和调试循环，在 Agent 条件下更多由 AI 完成。[R10，§4.3，第 10—11 页](#r10)

这与 OpenHands 的 Workspace、终端和事件系统连成一条链：**稳定执行基础设施减少了人充当模型与计算机之间搬运工的时间。**

### 10.6 为什么使用意愿仍然有限？

研究的未来使用意愿表中，20% 同意未来更愿意用 OpenHands 而非 Copilot，60% 不同意。[R10，第 11 页表 3](#r10)

访谈指出理解困难、主动行为过多、修改规模超预期、停止时机不佳和等待等问题。论文由此提出三项要求：提高行为透明度、平衡主动性、有效使用人的精力。[R10，§5.1，第 12 页](#r10)

这里不是“Agent 无效”的结论，而是：任务成功、自动化程度、用户信任和使用偏好是不同指标。

### 10.7 透明度不是把所有内部文本倾倒给用户

**工程推导：**用户界面最应该回答的是：现在做什么、实际改了什么、关键依据是什么、哪些检查已运行、为什么停下来、需要我作什么决定。

一千行无法筛选的日志，未必比一份关联真实 diff 与测试结果的进度卡更透明。最终说明应指出不确定性，而不是用一段流畅总结掩盖证据空缺。

### 10.8 执行位置与界面是正交维度

讲义第 30—31 页将本地／云端执行与 IDE／GUI／CLI／集成入口分开。[R00，第 30—31 页](#r00)

| 入口 | 本地执行 | 远程执行 |
|---|---|---|
| IDE | 本地工程文件 | 远程工作区 |
| GUI | 桌面任务工作区 | 浏览器任务工作区 |
| CLI | 本地终端 | 远程会话 |
| 集成 | 本地服务 | 托管任务执行器 |

CLI 不必等于本地，网页也不必等于云端。执行位置决定环境准备与可用性；界面决定人怎样观察、修改和批准。

### 10.9 不同界面承载不同监督任务

IDE 围绕文件、diff、测试进行细粒度协作；任务型 GUI 围绕长任务、并行执行、产物预览与审批；CLI 便于脚本和终端习惯；issue／PR／聊天集成把 Agent 放进原来的工作渠道。[R00，第 32—36 页](#r00)

不要为每种界面复制一套核心执行逻辑。SDK 的共同基础正是为此存在。

### 10.10 VS Code 教程中的双重验证

上传教程先让 Agent 在浏览器中检查用户场景，再要求用户自己测试新增、完成、刷新和删除等行为，并审查 diff。Agent 的验证报告帮助定位问题，但不取代用户审查。[R11，“Review and validate the result”“Verify the result yourself”](#r11)

教程还明确区分停止、修改和恢复检查点，指出外部副作用不在文件恢复的保证范围内。[R11，“Stop, revise, or undo the work”](#r11)

**连接下一章：**人类可理解的产物与明确的批准边界，必须进入自动化流程，而不是只做成 UI 上的提示。

<a id="chapter-11"></a>
## 第十一章　自动化与 Software Factory：自主探索必须连接明确验收

### 11.1 从“一次聊天”转向“一次有边界的运行”

讲义第 39 页的结构是：

```text
Trigger → Context → Run → Artifact → Check
触发       上下文      执行      产物       检查
```

它把 issue、PR 或计划任务转换成限定范围的工作，在隔离环境中运行，产生补丁、报告或评论，再由人或策略检查。[R00，第 39 页](#r00)

自动化入口不应该只有一段 Prompt。没有明确起点、权限、预算和产物，就很难区分“执行完成”和“任务完成”。

### 11.2 外围流程确定，阶段内部允许探索

**工程推导：**把模型擅长的开放探索与程序应该强制的约束分开。

模型可以自主决定先查哪个文件、怎样构造复现、采用哪个修复假设。程序则控制不可越过的权限、预算、批准与验收条件。

```text
明确任务／环境／允许能力
    ↓
Agent 在边界内探索与执行
    ↓
系统检查真实产物，而不是只读取最终回答
    ↓
验收通过，或明确返回未完成／待人工处理
```

这不是所有步骤写死，也不是把所有控制都交给模型。

### 11.3 四篇资料怎样汇合到交付流程？

| 交付问题 | 可借鉴的来源 |
|---|---|
| 起始状态与验收行为是什么？ | SWE-bench 的任务构建 |
| 哪些步骤必须按依赖推进？ | CodeR 的任务图 |
| 下游需要什么中间产物？ | MetaGPT 的结构化交接 |
| 行为怎样运行、记录与恢复？ | OpenHands SDK |
| 用户怎样理解、审查和干预？ | 人机研究、VS Code 与 GitHub 材料 |

**任务完成是这些部分共同满足要求，不是模型最后说了一句“完成”。**

### 11.4 为什么批准必须绑定当前产物？

讲义第 41 页强调：合并检查需要通过检查，并且批准针对当前 commit。[R00，第 41 页](#r00)

版本 A 通过测试后又被修改成 B，不能继续拿 A 的证据证明 B 安全。其逻辑可表示为：

$$
\mathrm{Mergeable}(h)=\mathrm{TestsPassed}(h)\land\mathrm{ReviewApproved}(h)\land\mathrm{PolicyAllowed}(h)
$$

其中 $h$ 是当前提交。这是对讲义的**工程表达**，不是 SDK 内置函数。

同样的思想适用于非代码产物：审核结论针对哪一版文档、事实核验基于哪份数据、内容变化后哪些检查失效，都应该明确。

### 11.5 GitHub coding agent 材料展示的交付形态

上传的发布材料描述了：Agent 为任务准备开发环境、获取仓库、后台工作、持续提交到草稿 PR，提供会话日志，完成后请人审查，审查评论再成为后续修改输入。[R12，“A detailed look”](#r12)

材料还描述只推送到自己创建的分支、网络目的地限制、工作流批准及仓库规则等控制。这是该发布资料的版本描述，不是本文对当前产品所有配置的安全担保。[R12，“Integrated, configurable, and secure”](#r12)

可迁移的思想是：**Agent 应接入已有工程治理，而不是要求团队放弃原有审查去相信一个自动完成按钮。**

### 11.6 产物应该包含什么？

以下是**工程建议**：最终交付既有内容，也有证据身份。

```text
任务标识与原始目标
基线与当前版本
修改文件和实际差异
实际执行的验证命令与结果
已知失败和未验证事项
预算与运行状态
人工审查或批准记录
```

“测试通过”必须能回到某次实际执行。没运行的测试应明确写未运行，不能让摘要器依据计划补造结果。

### 11.7 三层评测：框架没坏、模型会用、任务做对

SDK 报告采用三层测试：[R01，§5.1，第 12 页](#r01)

| 层次 | 验证目标 | 示例 |
|---|---|---|
| 程序化测试 | 核心逻辑和接口契约正确 | 参数校验、拒绝后不执行、状态保存 |
| 真实模型集成测试 | 模型能与工具正确交互 | 搜索、修改、理解错误并纠正 |
| 任务级 benchmark | 最终解决实际任务 | 修复末页遗漏并保持原有功能 |

程序测试可以模拟模型，便于快速稳定检查；真实模型测试覆盖 Prompt、模型与工具组合的行为；benchmark 提供更广的任务能力测量。报告还让示例程序进入测试范围，而不只测试底层函数。

因此，mock 全通过不证明真实模型会用；几个任务成功不证明持久化与审批逻辑可靠。

### 11.8 SDK 的实验应该怎样读？

报告第 13 页表 2 给出特定 SDK 与 benchmark commit 的结果，例如 Claude Sonnet 4.5 在 SWE-bench 项为 72.8%，GAIA 为 67.9%；正文将前者表述为 SWE-bench Verified，并说明 GAIA 使用验证集。[R01，§5.2，第 13 页](#r01)

这些数字主要说明该报告的工程框架能够承载有竞争力的任务表现。它们不是 V0 与 V1 在完全相同条件下的严格单因素消融，也不能与 Versa 的 GAIA 测试集结果直接比较。正文的 72% 与表格 72.8% 差异另见附录 D。

### 11.9 长任务还需要故障注入

以下是**工程推导**，不是报告给定测试清单：

| 注入场景 | 需要核对的性质 |
|---|---|
| 工具实际完成，但响应前断网 | 是否重复产生副作用？ |
| 压缩后重启 | 目标、约束和证据引用是否仍在？ |
| 等待审批时重启 | 是否意外跳过批准？ |
| 会话恢复，但工作区丢失 | 是否先对齐真实状态？ |
| 并行修改后合并 | 测试与批准是否针对合并后的版本？ |
| 预算耗尽 | 是否明确标记未完成，而不是误报成功？ |

这些问题检查的是执行语义，不只是进程能否重新启动。

### 11.10 成本要按“被验收的任务”衡量

**工程推导：**除了任务解决率，还应观察模型与工具成本、总耗时、人工投入、误报完成、恢复失败和权限违规。

一个有用的派生指标是：

$$
\text{每个被验收任务的运行成本}=\frac{\text{全部尝试的运行成本，包括失败尝试}}{\text{最终被验收的任务数}}
$$

这不是论文定义的标准指标，而是帮助避免“每次调用更便宜，但失败与返工更多”的错觉。人工审查成本应另外记录，不应无声排除。

比较多 Agent 与单 Agent 时，控制的是整个系统总预算，而不是让每个子 Agent 都获得相同预算后再把改善全归于协作。

<a id="chapter-12"></a>
## 第十二章　SkillRefiner：把历史轨迹变成下一次更好的工作方法

### 12.1 材料范围与问题定义

本节依据讲义第 42—43 页与上传的 alphaXiv 介绍页面。页面介绍 SkillRefiner 利用初始自然语言 Skill、历史轨迹、结果及可用反馈进行离线改进，优化期间不生成新的任务执行轨迹。[R00，第 42—43 页](#r00) [R13，“Turning traces into reusable instructions”](#r13)

这里的“离线”不是说最终无需评测，而是候选改进的产生不依赖不断重新执行任务。资料没有提供的完整算法参数与源码细节，本文不作推定。

### 12.2 它与 memory、condenser 的区别

| 机制 | 输入 | 主要输出 | 服务范围 |
|---|---|---|---|
| 会话持久化 | 当前任务事件与状态 | 可恢复的运行记录 | 单次任务 |
| Condenser | 较长的当前任务历史 | 下一轮可用的压缩上下文 | 单次任务 |
| 历史案例检索 | 过去任务与问题 | 当前任务的参考案例 | 跨任务参考 |
| SkillRefiner | 多次历史执行及结果 | 修订后的程序性指导 | 跨任务行为改进 |

这是对机制责任的综合区分。SkillRefiner 改变的是“遇到某种情况怎样工作”，不是自动为系统提供新的事实真值，也不是本节中的模型权重训练方法。

### 12.3 五阶段算法的完整逻辑

讲义第 42 页图 1 可以按“证据到指导”理解：[R00，第 42 页](#r00)

```text
初始 Skill + 历史执行轨迹 + 结果／反馈
    ↓
1. 结合反馈的轨迹表示
    ↓
2. 成功与失败分别向量化、聚类
    ↓
3. 从各簇生成候选修改
    ↓
4. 对失败衍生候选做证据检查
    ↓
5. 与初始 Skill 合并，形成修订版本
```

**阶段一：轨迹表示。** 总结任务情境、采取的策略和关键动作，把可用的失败证据纳入分析。重点不是缩短日志而已，而是保留与结果相关的信息。

**阶段二：分别聚类。** 成功与失败被分开处理，寻找重复模式；页面说明单例簇不独立产生修改，避免个例直接变成规则。

**阶段三：候选生成。** 成功簇强化有效做法；失败簇暴露反复出现的问题，模型提出补救假设。

**阶段四：证据门控。** 检查失败衍生的修改是否有历史行为与结果支持。门控不是重新执行任务，也不是自动证明修复有效。

**阶段五：合并。** 将成功建议、通过门控的失败建议与初始 Skill 合并；冲突时限制失败发生的情境，而不是简单无条件禁止某种能力。[R13，“Turning traces into reusable instructions”](#r13)

### 12.4 用下载器例子理解“可执行经验”

假设多个失败任务都只测试了完整页，没有检查最后一个不满页。可能提炼出：

> 修改分页终止条件后，应覆盖空结果、单页、完整页和最后一个不满页，并确认已经从接口返回的数据全部进入最终结果。

这比“以后认真检查”可执行，也比“永远采用某一种循环写法”更能跨任务迁移。这是教学示例，不是 SkillRefiner 实验中报告的具体规则。

### 12.5 失败原因不能从共现直接推出

失败轨迹里经常使用搜索，不代表搜索应该被禁止。真正问题可能是检索太宽、没有回看原文，或者这些任务本来更难。

页面明确说失败修复是模型提出的假设，轨迹不能直接证明其正确；证据门检查的是理由是否受到支持。[R13，“Turning traces into reusable instructions”](#r13)

**工程推导：**候选经验最好分开记录：观察行为、证据、推测原因、建议修改、适用条件和可能副作用。这样人可以拒绝错误归因，而不是只能接受或删除整段新 Skill。

### 12.6 成功与失败信号为什么不同？

成功记录告诉你某种做法在这些条件下有效，但不容易看出哪些步骤是必要的。失败记录可以更直接暴露缺失条件与错误路径，但也更容易被错误归因。

介绍页面的一组消融为 SpreadsheetBench、LLM 初始 Skill、MiniMax-M2.7：[R13，“What the comparisons establish”](#r13)

| 移除组件 | 性能变化 |
|---|---:|
| 失败簇产生的建议 | −8.0 个百分点 |
| 成功簇产生的建议 | 0.0 个百分点 |
| 证据门控 | −5.0 个百分点 |

页面还报告，在八个设置中的七个，移除失败建议比移除成功建议影响更大。它支持有证据约束的失败修正的价值，不支持成功轨迹无用，更不支持每条通过门控的建议都正确。

### 12.8 与 Trace2Skill、GEPA 的关系

按上传页面的介绍，Trace2Skill 从个别历史执行提出修改再整合；SkillRefiner 先聚类再形成每簇建议；GEPA 在相应比较中通过新增执行评估候选，并使用五次候选修订的预算。[R13，“What the comparisons establish”](#r13)

这里是页面对该实验的描述，不是对两个基线全部版本和适用场景的完整综述。

页面的一组优化 token 成本如下：

| 方法 | Refinement tokens |
|---|---:|
| SkillRefiner | 2.78M |
| Trace2Skill | 6.87M |
| GEPA | 117.22M |

**这些只统计优化阶段 token，不含历史轨迹收集成本，也不能直接推出墙钟时间与总计算量按相同比例下降。**[R13，“What the comparisons establish”](#r13)

### 12.9 延迟反馈：为什么 PR 审查是重要案例？

审查建议是否有用，可能要等开发者随后改动代码才显现。页面介绍的 PR Review 用后续开发者处理的问题作延迟监督，并由 LLM judge 匹配建议，计算 F1。[R13，“History as feedback”](#r13)

它是审查效用的代理指标，不是完美的真实缺陷标签。GEPA 在该设置中未被应用，是因为缺少即时重放与自动反馈，而不是证明在线方法普遍不适合审查任务。

### 12.10 从离线提炼到上线，中间仍然需要验证

**工程推导：**合理发布链路是：

```text
历史轨迹 → 候选 Skill → 独立任务评测 → 重要变更人工审查
→ 小范围使用 → 监测失败与回滚
```

不要让模型每天总结日志后直接覆盖线上 Skill。保留旧版本、修改理由、支持案例、适用条件和评测结果，才能判断收益从哪里来，退化从哪里来。

单例簇被过滤也不意味着罕见高风险事件不值得处理。严重越权或数据泄漏类错误应有独立治理渠道，不能仅凭“没有形成重复模式”而忽略。这是风险处理建议，不是聚类算法的实验结论。

### 12.11 对材料审核与投研流程的迁移边界

迁移到相关业务时，采纳／拒绝可以成为学习信号，但拒绝可能因为重复、优先级、表达方式或范围，采纳也不天然证明事实正确。

**工程推导：**回流记录应尽量包含反馈理由、原文证据、最终处理与版本。Skill 可以改进“何时查原文、何时执行数据核验、怎样输出修改建议”等工作方法，不能未经核实地把用户偏好升级成事实，也不能把一个历史案例自动升级成法规依据。

<a id="chapter-13"></a>
## 第十三章　综合案例：把论文机制放进同一个可交付系统

> 本章是前述资料的工程综合，不是 OpenHands 官方架构图，也不是一项已经执行过的实验。

### 13.1 任务契约：先说清改变什么、保持什么

对于“内部资料下载器遗漏末页”，首先固定仓库起点，说明现象、接口约束、允许资源、预算与禁止动作，并定义可验证的交付条件。

这一步吸收 SWE-bench 的核心思想：任务不只是问题文本，还包含起点与验收方式。[R03，§2](#r03)

不要提前在任务描述中断言根因，否则会把原本需要调查的问题变成被 Prompt 诱导的结论。

### 13.2 建立单 Agent 基线

给一个 Agent 提供搜索、文件查看、编辑、执行和任务进度记录能力，先看它能否完成复现—定位—修改—验证。

这是讲义的单 Agent 基线方向；任务追踪器用于显式记录计划，但计划条目本身不是强制状态机。[R00，第 14、23 页](#r00)

### 13.3 让工具返回真实、可定位的观察

搜索命中需要文件与位置；编辑结果需要当前片段与检查结果；执行测试需要命令、退出状态和必要日志。对输出截断，应明确指出，而不是让模型以为已经看到全部结果。

这里继承 SWE-agent 的 ACI 原则，避免模型把无输出、执行失败和没有匹配混淆。[R04，§2—3、附录 A.1](#r04)

### 13.4 在适用时引入不同性质的定位证据

文本搜索不足时，使用复现、栈信息、测试覆盖等进一步缩小范围。CodeR 的启示不是必须有一个名为 Fault Localizer 的角色，而是已有软件工程工具能提供模型自身没有的运行信号。[R07，§3.2](#r07)

复现没有成功、覆盖为空时，应明确记录局限，不生成一份假装依据充分的定位报告。

### 13.5 让状态更新跟着实际结果走

提出编辑动作后，先检查与执行，再把 Observation 写入事件历史。修改失败或被拒绝，就返回真实状态。恢复时核对工作区与事件进度，不让模型直接从旧摘要继续。

SDK 的事件、ConversationState 与 Workspace 提供这些责任的承载位置，但外部未知结果的核对协议仍需按业务实现。[R01，§4.2、§4.5、§4.10](#r01)

### 13.6 长任务期间维护约束、进展和证据路径

压缩较早观察时，保留目标、接口约束、已经验证和已经排除的结论，以及测试／文件证据的定位。周期性进度检查可以借鉴 Versa 的规划提示，但关键验收步骤由外围流程检查。[R01，§4.6](#r01) [R09，§2.2](#r09)

### 13.7 交付要来自工作区，而不是来自自述

系统提取真实 diff、测试记录和产物版本，让 Agent 解释这些材料，而不是只让 Agent 写“我做了什么”。必要时增加独立审查阶段，重新从任务与差异出发检查。

此处结合了 MetaGPT 的交接物、单 Agent 的连续上下文，以及讲义 Software Factory 的独立验证思想。[R08，§3.2](#r08) [R00，第 41 页](#r00)

### 13.8 人类反馈与经验改进

人审查当前产物，提出采纳、拒绝或修改意见；这些反馈关联具体任务与证据。重复失败模式可进入离线 Skill 改进，再以独立任务评测决定是否发布。

这时，执行日志不再只是事故排查材料，也可以成为程序性知识的来源，但不能跳过证据检查与版本管理。[R13，“Turning traces into reusable instructions”“History as feedback”](#r13)

### 13.9 整个系统的责任分工

| 环节 | 模型承担 | 程序／环境／人工承担 |
|---|---|---|
| 理解任务 | 提取目标、发现歧义 | 固定范围与验收身份 |
| 调查 | 选择查询、提出假设 | 提供真实文件和执行证据 |
| 修改 | 提出代码变更 | 应用修改、检查与返回实际状态 |
| 长任务 | 根据观察调整行动 | 状态持久化、预算、恢复与权限 |
| 协作 | 阶段内自主求解 | 依赖、交付物与隔离边界 |
| 完成判断 | 解释结果与不确定性 | 当前版本验收与批准 |
| 学习改进 | 提出候选指导 | 证据、独立评测、版本与回滚 |

关键不是让模型包办一切，而是让它与程序、工具和人的能力互补。

## 第十四章　工程诊断：失败应该在哪一层修？

### 14.1 不要把所有缺陷都解释为模型不够聪明

以下诊断表是本课的**工程综合**，不是唯一处理路径：

| 观察到的失败 | 首先检查 | 不宜立刻采用的反应 |
|---|---|---|
| 找不到代码或事实 | 搜索接口、范围与证据来源 | 无差别增加上下文 |
| 工具参数反复错误 | Schema、说明与错误反馈 | 只追加“仔细思考” |
| 认为编辑成功但文件没变 | 执行结果与状态确认 | 再增加一个总结 Agent |
| 长任务忘记约束 | 约束保存与上下文维护 | 把全部历史永久保留 |
| 反复尝试同一失败动作 | 新证据、假设与卡住检测 | 只扩充预算 |
| 重启后任务与文件不一致 | 会话与工作区恢复 | 直接继续模型循环 |
| 并行任务互相覆盖 | 工作区与合并边界 | 把冲突全交给聊天解决 |
| 提前宣布完成 | 验收覆盖与停止机制 | 只要求提高自信度 |
| 同类流程遗漏反复出现 | Skill、明确流程或程序检查 | 立即进行微调 |
| 越权或信息泄漏风险 | 授权、隔离与网络边界 | 只依赖安全 Prompt |

### 14.2 五组最重要的“不等于”

**更多上下文，不等于更多可用信息。** SWE-bench 的检索实验与 SWE-agent 的窗口消融共同说明，要看信息是否能被有效使用。[R03，第 5 页](#r03) [R04，第 6 页](#r04)

**更多 Agent，不等于更好的结构。** 结构可以放在任务图、交付物、工具和 Skills 中；角色边界本身也可能造成信息损失。[R07，§3.1](#r07) [R08，§3.2](#r08) [R06](#r06)

**日志完整，不等于世界可以回滚。** 会话、工作区与外部副作用是不同层次。[R00，第 17 页](#r00) [R11，“Stop, revise, or undo the work”](#r11)

**自动化更多，不等于人的总成本更低。** 理解、等待、审查和承担结果也需要成本。[R10，§4—5](#r10)

**从失败提炼出建议，不等于建议已被证明有效。** 历史证据支持归因假设，最终仍需要独立评测与上线控制。[R13](#r13)

### 14.3 本课的最终认识

HumanEval 与 SWE-bench 把交付锚定到外部行为；SWE-agent 与 CodeAct 改善模型的行动与观察；CodeR、MetaGPT 和单 Agent 路线探索任务结构的位置；OpenHands SDK 管理运行事实与生命周期；人机研究检验真实使用价值；Software Factory 与 SkillRefiner 则把一次执行连接到反复交付和持续改进。

**成熟的 Agent 系统应该能够说明：为什么继续、为什么停下、实际改变了什么、依据什么判断完成，以及失败后如何回到一个可信的状态。**

作为开发工程师，最值得训练的判断是：什么时候让模型探索，什么时候让程序强制，什么时候必须回到外部证据重新确认。

### A.1 最小调用骨架

下面根据讲义第 14—15 页的对象关系整理。它不是官方完整生产示例，也没有在真实模型服务中执行验证。部署时需核对使用版本的导入路径、工具注册和参数，准备相应依赖、模型凭证与隔离的练习工作区。[R00，第 14—15 页](#r00)

```python
import os
from pathlib import Path

from openhands.sdk import Agent, Conversation, LLM, Tool
from openhands.tools.file_editor import FileEditorTool
from openhands.tools.task_tracker import TaskTrackerTool
from openhands.tools.terminal import TerminalTool


def required_env(name: str) -> str:
    value = os.environ.get(name, "").strip()
    if not value:
        raise RuntimeError(f"缺少环境变量：{name}")
    return value


def main() -> None:
    workspace = Path(required_env("DEMO_REPO")).resolve(strict=True)
    if not workspace.is_dir():
        raise ValueError("DEMO_REPO 必须是一个练习仓库目录")

    llm = LLM(
        model=required_env("LLM_MODEL"),
        api_key=required_env("LLM_API_KEY"),
    )
    agent = Agent(
        llm=llm,
        tools=[
            Tool(name=TerminalTool.name),
            Tool(name=FileEditorTool.name),
            Tool(name=TaskTrackerTool.name),
        ],
    )
    conversation = Conversation(agent=agent, workspace=str(workspace))
    conversation.send_message(
        "调查资料下载器遗漏最后一页的问题。"
        "先复现和确认原因，再做最小修改；保持公开接口与返回格式。"
        "运行相关已有测试并补充边界测试。"
        "最后报告实际改动、真实测试结果和未验证事项。不要发布或部署。"
    )
    conversation.run()


if __name__ == "__main__":
    main()
```

**边界提醒：**这里传入目录属于本地执行示意，不是操作系统级沙箱；Prompt 中“不要发布”不是权限控制。示例没有包含完整的远程部署、强制授权、故障恢复和独立验收。

### A.4 可复用的任务输入模板

```text
任务目标：
说明需要改变的行为，以及当前可观察到的问题。

任务起点：
仓库／文件／数据版本，以及准备好的运行环境。

允许范围：

交付要求：
真实修改产物、版本、执行记录、结果和剩余风险。

停止条件：
超预算、环境无法恢复、需要扩大权限或无法获得必要信息时，
停止并明确说明，不把未完成包装为完成。
```

这是工程任务契约模板，不是要求所有任务机械执行同样的步骤。

```text
任务：
产物版本：
原始问题是否被复现：
已确认原因及其依据：
实际修改：
```

## 附录 B　把课程变成实验：一个可控的验证计划

> 本附录为工程练习设计；没有声称这些实验已经运行，也不规定某个样本量足以建立普遍结论。

### B.1 先固定一个能重复运行的基线

选择能够准备初始状态和验收条件的一组仓库问题。固定模型、工具版本、任务预算、工作区和结果判定方式，保留全部尝试，包括失败。

先完成单 Agent 基线，而不是同时引入多模型路由、多 Agent、动态 Skill 更新和复杂自动发布。否则难以判断哪项改动带来收益。

### B.2 一次改变一个主要因素

| 实验 | 对照 | 主要观察 |
|---|---|---|
| ACI | 普通终端输出 vs 结构化、限长且带恢复信息的输出 | 无效动作、错误恢复、任务成功 |
| 上下文 | 完整历史 vs 压缩／过滤后的历史 | 成本、约束遗漏、过时信息使用 |
| Skill | 无领域指导 vs 明确程序性指导 | 固定步骤遗漏与边界覆盖 |
| 流程结构 | 自由推进 vs 明确验收节点 | 提前结束、漏检、错误交接 |
| 独立审查 | 无审查 vs 从需求与 diff 重新检查 | 漏检减少是否抵消额外成本 |
| 历史改进 | 初始 Skill vs 历史提炼后 Skill | 未参与优化任务上的真实收益 |
| 恢复 | 正常运行 vs 故障注入 | 是否保持授权、状态和外部副作用语义 |

比较单／多 Agent 时，需要同时看等总预算条件；增加 Agent 后带来的额外采样和执行次数应单独说明。

### B.3 记录不止一个分数

建议保留任务成败、模型与工具消耗、总运行时间、人工参与、修改规模、误报完成、权限违规、恢复失败与失败原因。

关键问题是：成功率提高是否靠显著增加审查投入？成本下降是否以更多失败为代价？恢复机制是否会重复执行外部动作？

小样本结果先用于发现问题。基线与候选尽量在同一组任务上比较，并检查逐任务变化，不能只比较两个总体平均数就宣布因果关系。

### B.4 从日志到改进的闭环

```text
任务执行 → 分类失败 → 查看关键证据 → 提出单项改动
→ 固定条件对照 → 检查退化与成本 → 决定保留或回滚
```

论文、工具、Prompt 和 Skill 都是候选改进来源。诊断出问题位于工具反馈时，不必急着训练模型；问题是流程漏项时，也不必先增加角色。

## 附录 C　概念速查

| 概念 | 本文中的含义 | 最容易混淆的对象 |
|---|---|---|
| Agent | 在任务中持续观察、决策和行动的执行主体 | 单次模型调用 |
| Agent 配置 | 模型、工具、指令等可复用规格 | 某次任务的可变进展 |
| Conversation | 一次任务交互及运行控制的载体 | 完整工作区备份 |
| Event Log | 动作、观察与内部控制的记录 | 每轮原样提交给模型的 messages |
| ACI | 面向模型设计的动作、说明、反馈与上下文接口 | 普通人类终端界面 |
| Action | 待执行的结构化动作 | 已发生的事实 |
| Observation | 执行或交互得到的结果 | 模型对结果的猜测 |
| Workspace | 文件与执行环境 | 自动提供全能隔离的目录参数 |
| Condenser | 处理当前长历史的上下文压缩机制 | 跨任务经验学习 |
| Skill | 可复用的程序性指导 | 必须独立启动的子 Agent |
| Task Graph | 节点、依赖与转移控制 | 一段未被程序执行的文字计划 |
| MCP | 外部工具描述与调用的连接机制 | 信任或授权保证 |
| Sub-agent | 独立 Conversation 下的委派任务 | 天然独立文件系统 |
| RouterLLM | 按请求选择基础模型的适配层 | 必须采用多个 Agent |
| Fail-to-Pass | 修复前失败、修复后应通过的检查 | 已有正常行为的回归检查 |
| pass@k | 多个候选中存在通过样本的覆盖指标 | 系统一定选中并交付正确候选 |
| Artifact | 可检查的补丁、文件、报告等交付物 | 仅有文字“我完成了” |
| Replay | 按记录重建或分析执行过程，需说明范围 | 无条件重新产生全部外部副作用 |
| Skill refinement | 从经验修改程序性指导 | 自动证明新规则正确 |

该表是术语归纳；各项定义、细节和边界以相应章节引用的材料为准。

## 附录 D　证据边界与资料内部差异

### D.1 不把历史特性比较当成当前事实

SDK 报告第 14 页的框架功能表明确标注截至 2025 年 10 月 29 日；人机研究测量的是 2025 年 4—5 月的使用条件。本文没有把这些横向比较转换成当前产品功能判断。[R01，第 14 页表 3](#r01) [R10，§3.4、§5.3](#r10)

### D.2 远程执行拓扑的差异

SDK 正文 §4.10 和第 11 页图 6 描述服务器重建 Agent 并运行完整循环；附录 A.14 又表述 Agent 在本地、工具在远程。本文保留差异，并明确采用正文与讲义所示架构解释远程 Conversation，不把二者静默揉合。[R01，第 10—11、20 页](#r01)

### D.3 API 示例不是完整版本契约

报告不同示例中的 `get_default_agent` 导入位置并不完全一致；正文以 `pause()` 与再次 `run()` 说明恢复，附录又出现 `resume()` 表述。本文不据此保证任意版本支持所有写法。最小代码用于理解对象关系，实际运行需核对选定版本。[R01，第 3、9—11、18 页](#r01)

### D.4 CodeR 主结果的计数差异

上传的 CodeR 在贡献部分把 28.33% 写为 85/300；结果正文又出现“84 of 300”；第 9 页表 4 区分 reported 28.33%（85）与 ours 27.33%（82）。本笔记没有把这些不同记录合并成一个无条件结论，主要用明确条件的消融讨论机制。[R07，第 2、8—9 页](#r07)

### D.5 SDK 主结果的文字与表格差异

SDK 第 13 页表 2 的 Claude Sonnet 4.5 SWE-bench 项为 72.8%，正文写 72%；表头采用 SWE-Bench，正文描述为 SWE-bench Verified。本文列数字时使用表格，数据划分依据正文说明，并保留这个差异。[R01，第 13 页](#r01)

### D.6 人机研究的统计表述

研究 §3.6 设定显著性阈值 $\alpha=0.05$；第 9 页有关 C6 输出理解的段落使用“significantly”，同时给出 $p=0.07$。本文保留其偏好比例与定性反馈，不把这项结果转述为满足该阈值的显著差异。[R10，第 7、9 页](#r10)

同样，“35% ± 15% increase”的文字表述不能在没有额外定义的情况下随意改写为“速度提升 35%”或普遍适用的生产力指标。[R10，第 8 页](#r10)

### D.7 不跨数据划分比较

SWE-bench 原始版、Lite、Verified、Multimodal 不是同一评测；Versa 主结果的 GAIA 测试集与其搜索 API 实验的验证集不同；SDK 报告的 GAIA 结果又是验证集。不同数字不能简单连成统一时间趋势或直接相减。[R03](#r03) [R04，§4](#r04) [R09，§3.3、§5.3](#r09) [R01，§5.2](#r01)

### D.8 SkillRefiner 的材料级别与因果边界

本文的五阶段机制、部分消融与 token 成本来自上传的介绍页面；结果表来自讲义第 43 页。未提供完整论文 PDF、聚类参数或完整 Prompt，不把页面摘要扩展成精确复现说明。[R13](#r13) [R00，第 42—43 页](#r00)

证据门控支持失败修正的合理性，不等于逐条因果验证；优化阶段不生成新 rollout，不等于部署前无需评测；refinement tokens 也不等于包含历史数据收集的全部成本。

### D.9 正文中的工程扩展

幂等核对、外部副作用补偿、工作区版本联动、独立审查输入、故障注入、实验计划与交付模板，是基于资料机制提出的工程推导。本笔记明确标出这些内容，不声称所有机制已经存在于 OpenHands SDK，或已被引用论文实验证明。
