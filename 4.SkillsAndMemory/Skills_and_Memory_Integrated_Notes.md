# Skills 与 Memory：从有限上下文到可验证的经验复用

## lecture-04、readings 与 references 的综合学习笔记

**面向读者：** LLM 开发工程师。
**课程主线：** Representation（表示）→ Induction（提炼）→ Lifecycle（生命周期）。
**核心问题：** Agent 怎样把一次任务中的信息、方法与教训，转化成后续任务可以可靠使用的能力？

> 一个 Agent 做完任务，并不等于它学会了这个任务的方法；保存了方法，也不等于这个方法值得复用。真正需要建立的是：**经历有据可查，经验能够提炼，技能可以验证，更新接受后续任务的检验。**

# 1. 课程与材料的问题地图：沿着能力形成链组织研究

## 1.1 从一个重复结构开始

讲义第 2 页并列了两个任务：把 Sony 耳机加入收藏夹，以及查询无线键盘的价格范围。最终目标不同，但它们共享“进入商店、找到搜索框、输入查询、提交搜索”的过程。课程要讨论的是：这段共同结构是否值得保存，应该保存成什么，以及下一次怎样正确使用。〔[L04](#src-l04)，p.2〕

这可以展开为一条连续的问题链：

```text
专家已经知道怎么做
    → 怎样把方法交给 Agent？                         OpenHands
    → 怎样证明这些方法确实有帮助？                   SkillsBench

Agent 已经经历过一些事情
    → 信息不在当前上下文时，怎样保存、取回并继续？    MemGPT
    → 怎样从经历中提炼可复用的子流程？               AWM
    → 怎样把子流程变成可调用、可验证的程序？         ASI
    → 怎样从成功与失败中学习可迁移的判断策略？       ReasoningBank

系统会持续运行
    → 怎样迁移到不同环境并练出新技能？               PolySkill、SkillWeaver、Voyager
    → 怎样选择、更新、修复、淘汰这些内容？           TroVE、ASSAY 与技能生命周期
    → 怎样用后续结果训练保存和使用策略？             SAGE、AgeMem
```

| 材料 | 在讲义中的位置 | 主要贡献 | 不能把它误认为 |
|---|---|---|---|
| OpenHands 文章 | pp.8–15 | 技能编写、部署、记录、评估和改进的实际工作流 | 仅仅一种 Markdown 目录格式 |
| SkillsBench | pp.12–13 | 对技能增强效果进行配对测量，分析收益与失败 | 随便安装技能就能得到固定增益的保证 |
| MemGPT | p.17 | 分层存储、上下文调度、记忆函数与控制流 | 在模型里真正增加了无限同时可见的上下文 |
| AWM | pp.22–28 | 从具体经历中提炼抽象子流程，作为记忆指导行动 | 默认就是全局向量库加 top-k 检索 |
| ASI | pp.29–36 | 诱导、执行验证和使用程序技能，扩展动作空间 | 只要把文字改成 Python 就会更可靠 |
| ReasoningBank | pp.38–41，并补充 MaTTS | 从成败经历提炼判断策略，研究记忆与探索的相互促进 | 已解决所有冲突、遗忘、权限和长期维护问题的完整平台 |

上述位置与研究分工来自讲义和各论文的方法描述；“不能误认为”是本文为避免概念混用而给出的综合理解。〔[L04](#src-l04)，pp.8–15、17、22–43；[MG](#src-mg)，§2；[AWM](#src-awm)，§2；[ASI](#src-asi)，§2；[RB](#src-rb)，§3、附录 E〕

这六份 readings 构成正文的主要展开顺序。references 则围绕尚未解决的问题接入：Mem0 补事实更新；Reflexion、ExpeL、Synapse、Agent S、ICAL 区分反馈与经历的加工方式；Voyager、SkillWeaver 和 PolySkill 补主动练习与迁移；DreamCoder、Stitch、LAPS、LILO 解释程序库抽象；TroVE、ASSAY、SAGE、AgeMem 展开维护与学习目标；HermesAgent 提供技能发现和加载的代码实例。这里按问题关联材料，不表示它们构成单一技术演进顺序。各项机制在对应章节直接引用原文。

## 1.2 Agent 的变化可以发生在三个位置

讲义第 3 页区分三种更新路径。把经历留在上下文中，保真度较高，但会变长、变贵，也不自动决定哪些内容重要。把经历转成外部制品，便于检查、编辑、检索与迁移，但需要提炼、选择和维护。更新模型权重可以改变内部行为，但更新更重、变化不透明，也与具体模型绑定。〔[L04](#src-l04)，p.3〕

可以用一个工作场景理解：上下文是正在使用的工作台；原始记录和持久资料是档案；技能是操作规程与工具；模型权重是已经内化的能力。这是教学类比，不是严格的计算机架构对应关系。

**本课主要研究第二条路径：不一定修改模型参数，也能改变整个系统的行为。**

三条路径也可以组合。SAGE、AgeMem 在训练阶段更新模型参数，学习怎样生成、保存或使用外部记忆；部署时再利用该策略管理不断变化的外部内容。DreamCoder 也同时学习程序库与神经搜索模型。因此，本文会区分“本次经验是否通过外部制品积累”和“产生这些行为的模型是否经过训练”，不把全部参考研究归为免训练方法。〔[SAGE](#src-sage)，§3；[AgeMem](#src-agemem)，§3；[DC](#src-dc)，pp.4–6〕

为了统一理解，下面给出一个教学表达，而非某篇论文的原始公式：

$$
a_t \sim \pi_\theta(a\mid q,C_t,A_t)
$$

其中，$q$ 是任务，$C_t$ 是当前上下文，$A_t$ 是可调用的动作集合，$\theta$ 是模型权重。外部记忆 $M_t$ 需要经过选择与组装，才能进入当前上下文：

$$
C_t=\operatorname{Assemble}(q,\text{当前状态},\operatorname{Select}(M_t))
$$

完成任务后产生经历 $e_t$，系统再决定怎样更新：

$$
(M_{t+1},A_{t+1})=\operatorname{Update}(M_t,A_t,e_t,\text{反馈})
$$

用这个表达看，MemGPT 主要调度当前工作集；AWM 主要改变工作流记忆；ASI 还改变可执行动作集合；ReasoningBank 主要改变供模型决策时使用的策略记忆。ASI 原文明确定义了不修改语言模型参数、通过更新记忆或动作空间实现适应的方式。〔[ASI](#src-asi)，§2.1–2.3，pp.2–4〕

**因此，权重不变不代表系统没有学习；但文件越来越多，也不代表系统已经学到有效能力。**

## 1.3 Memory 与 Skill 不是互斥概念

按讲义第 5 页的用法，Memory 强调来源：信息来自 Agent 自己过去的交互；Skill 强调用途：它是关于如何行动的可复用知识，可以是文字、代码或两者组合。人类写的发布清单是 Skill，不一定是 Agent 自己的 Memory；Agent 从成功搜索中提炼出的流程，既是 Memory，也是 Skill。〔[L04](#src-l04)，pp.4–6〕

以下分类帮助区分后文讨论的对象，不应看成所有论文统一采用的标准本体：

| 对象 | 回答的问题 | 示例 | 核心风险 |
|---|---|---|---|
| Episode，经历 | 上次具体发生了什么？ | 当时的查询、观察、动作、结果 | 长、嘈杂，夹杂实例细节 |
| Fact，事实 | 关于对象或环境，知道什么？ | 价格只在商品详情页显示 | 过时、来源不明、范围混淆 |
| Lesson，经验教训 | 遇到什么情况，应调整什么判断？ | 结果过多时先检查筛选条件 | 错误归因、过度泛化 |
| Text Skill，文本技能 | 这类任务通常怎样完成？ | 搜索、核对、汇总的操作流程 | 套用不适合的路径 |
| Code Skill，代码技能 | 哪些过程可以直接调用执行？ | `search_product(query)` | 环境变化、接口不兼容、错误副作用 |
| Task State，任务状态 | 本次做到哪里，接下来做什么？ | 已完成章节、待确认问题、产物位置 | 恢复时遗漏或重复执行 |

前五类来自讲义的对象讨论与后续材料；任务状态是本文工程部分单独管理的一类对象。〔[L04](#src-l04)，pp.4–5、38、44；[RB](#src-rb)，§3.2〕

不要只问“用哪一个 Memory 框架”。应先问：**我需要恢复事实、恢复进度，还是复用方法？** 这三种需求的存储、检索、验证和失效规则都不同。

## 1.4 学习本课时始终分开三个维度

**保存什么**是内容问题：经历、事实、流程、策略、程序。

**怎样保存**是组织问题：文件、关系数据库、向量索引、分层存储。

**怎样使用**是执行问题：供模型阅读，还是成为真正能够调用的动作。

这三个维度不能互相替代。代码放在提示词里供阅读，与同样代码被注册为可执行函数，运行意义不同；向量数据库能存工作流，但向量检索本身并不会自动保证工作流适用。

# 2. 人工技能与运行框架：把专家方法交付给 Agent

## 2.1 OpenHands 的起点：重复说明与执行偏差

OpenHands 文章从添加测试、代码审查、升级依赖等重复工作出发。组织往往已经有固定流程，但每次都重新告诉 Agent，既浪费精力，也容易漏掉细节。它把 Skill 描述为提示、脚本和资源组成的可复用工作包。〔[OH](#src-oh)，When to Create Skills、What is a Skill?〕

例如，Python 审查不只是“检查代码有没有问题”，还包括项目使用哪些格式与检查工具、哪些接口要求类型标注、如何补测试、如何形成最终结论。**技能的目标是交付一种工作方法，而不是保存一次回答。**

文章特别建议：在刚完成一个值得重复的流程后提炼技能，再运行多次测试。此时具体步骤、异常处理和有效结果仍在上下文中，比完全凭空编写更有依据。〔[OH](#src-oh)，Creating a New Skill〕

这已经与 AWM、ASI 连接起来：三者都关注从工作过程沉淀方法，只是自动化程度、表示方式与验证机制不同。

## 2.2 一个 Skill 包的三个层次

讲义展示的典型结构是：

```text
python-review/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

重点不在目录名称，而在内容何时进入模型上下文：

| 层级 | 加载时机 | 解决的问题 |
|---|---|---|
| 元数据：名称与描述 | 构建技能索引时 | 当前任务是否需要这个技能？ |
| 正文：流程与要求 | 确定使用该技能时 | 应该怎样执行这类任务？ |
| 附属资源 | 某一步实际需要时 | 具体计算、规则核查或产物生成怎样完成？ |

讲义把它称为 Progressive Disclosure，渐进式披露。附属脚本可以直接运行，进入上下文的只是输出，不必把脚本全部源码读给模型。〔[L04](#src-l04)，pp.9–11；[OH](#src-oh)，What is a Skill?〕

```text
用户提出审查请求
→ 模型先看到技能名称与描述
→ 读取匹配技能的正文
→ 按正文调用检查脚本
→ 根据脚本结果判断问题
→ 遇到特殊规范时，再读取相应参考资料
```

**综合理解：** 元数据是选择接口，正文是执行指导，资源是具体工作手段。某一层失败，可能表现为完全不同的故障，不能笼统归因为“模型没有遵守 Skill”。

讲义和 OpenHands 示例中出现 `triggers` 字段。本文保留这一来源事实，但不据此认定所有运行框架都支持相同字段与触发逻辑；上传材料不足以建立跨框架的一致实现保证。

## 2.3 发现、读取、使用、正确完成，是四件事

一个技能已经安装，未必会被发现；被发现，未必被读取；被读取，未必被真正使用；被使用，仍可能导致错误。

SkillsBench 明确定义 Harness 为连接模型与环境的执行层：它提供工具、管理文件与工作区、执行脚本、返回观察，并处理技能发现与加载。Skill 本身既不是模型权重，也不自动等于可执行工具。〔[SB](#src-sb)，§2，p.2〕

例如，提示词里出现 `validate_report(report)`，并不说明环境真的提供了该函数。模型看到函数名却无法调用，是接口设计问题，不只是语言理解问题。ASI 的消融中确实观察到，模型会尝试调用仅作为参考文本提供的程序。〔[ASI](#src-asi)，§3.3，p.6〕

**工程建议：** 日志中至少区分候选技能、已加载技能、实际执行资源、执行结果和最终任务结果。仅记录“本次触发了 Skill”不足以定位失败。

## 2.4 Skill、工具、检索与 Prompt 的关系

SkillsBench 表 1 使用作者的分类口径，对 Prompts、RAG、Tools、Skills 的特征作了比较。它强调 Skills 同时具备模块化程序性指导与可执行资源。这个表适合说明论文的定位，不应被扩展为“任何检索系统都不能检索程序性知识”。〔[SB](#src-sb)，§2、表 1，pp.2–3〕

从本文的工程功能视角看：Prompt 是表达指令与上下文的方式；工具执行一个动作；检索把需要的内容找出来；Skill 组织完成一类任务的方法，可能使用多个工具，也可能通过检索被找到。它们可以组合，不是四种互斥的产品。

因此，比“Skill 会不会取代 RAG”更好的问题是：**什么信息应该常驻，什么方法应该按需加载，什么步骤应该直接执行？**

## 2.5 HermesAgent：从渐进式披露到实际加载链路

仓库中的 HermesAgent 快照给出了一个具体实现。`prompt_builder.py` 的 `build_skills_system_prompt` 及相关函数扫描技能来源、处理可见性和名称优先级，再由 `_render_skills_index` 组织名称与描述；`skills_tool.py` 的 `skills_list` 返回轻量索引，`skill_view` 返回技能正文、可用状态与附属文件索引，需要附件时再传入 `file_path`。因此，“索引—正文—资源”有明确的加载接口，并非只靠文件目录约定。〔[H-PB](#src-hpb)，`build_skills_system_prompt`、`_render_skills_index`；[H-ST](#src-hst)，`skills_list`、`skill_view`〕

```text
框架汇集技能并建立索引
→ 模型根据名称、描述与当前任务判断相关性
→ skill_view(name) 加载正文与附件索引
→ skill_view(name, file_path=...) 读取所需附件
→ 模型按指导选择工具执行
```

这条链路仍有两类边界。首先，名称冲突、平台限制、禁用状态以及依赖就绪情况，会影响技能是否可见、能否读取或是否具备运行条件；读到了正文不等于所需程序已经能运行。其次，索引中的“必须加载”等文字是给模型的行为要求，不等于运行时已经证明技能被正确使用。〔[H-PB](#src-hpb)，`_skill_should_show`、`_render_skills_index`；[H-ST](#src-hst)，`_locate_skill`、`_skill_readiness`、`skill_view`〕

一个值得保留的实现细节是：`_skill_view_with_bump` 在未命中重复读取缓存、且读取成功时，会尝试同时更新 view 与 use 统计。这个 use 表示加载行为，不能直接当作“脚本已执行”或“任务因技能而成功”。§14.5 会将它与论文中的使用率一起讨论。另一个边界是，这两份快照不足以解释整个 HermesAgent：虽然提示文本提到 `skill_manage`，其完整写入实现不在这两个文件中，本文不据此推断创建、修改和删除的全部规则。〔[H-ST](#src-hst)，`_skill_view_with_bump`；[H-PB](#src-hpb)，`_render_skills_index`〕

# 3. SkillsBench：怎样证明一个技能值得交付？

## 3.1 一次成功不能证明技能有效

加入技能后做对了，可能是模型本来就会做，也可能是技能直接暴露了答案。不同任务之间比较，也会混入任务难度差异。

SkillsBench 因此采用配对设计：同一任务、模型、运行框架与环境，比较没有任务技能包与提供人工整理技能包的结果。任务提供固定数据和环境，参考解与验证器隐藏，指令不直接告诉 Agent 应使用哪个技能。〔[SB](#src-sb)，§3–4，pp.3–5〕

按照论文 §4 的主要指标定义，先对一个任务的多次通过／失败结果取平均，再对任务取平均。可用下式说明其任务宏平均思想：

$$
\operatorname{TaskMacroPass}
=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{R}\sum_{r=1}^{R} y_{i,r}
$$

其中 $y_{i,r}$ 是第 $i$ 个任务第 $r$ 次运行的通过／失败结果。本文对主结果沿用 §4 的定义；论文图 3 另有测试项通过比例的示意，二者不在这里混成同一口径。〔[SB](#src-sb)，图 3、§4，pp.4–5〕

## 3.2 主结果：有效，但增益依赖具体系统

上传版本覆盖 87 个任务、8 个领域、18 种模型—运行框架组合。平均通过率从 **33.9% 提高到 50.5%**，提升 **16.6 个百分点**；各组合增幅为 **4.1–25.7 个百分点**。这不是“相对提高 16.6%”，更不是任何生产任务的固定收益。〔[SB](#src-sb)，§4–5、表 2，pp.5–6〕

论文还给出 normalized gain，表示在原有失败空间中弥补了多少：

$$
g=\frac{p_{\text{skill}}-p_{\text{base}}}{1-p_{\text{base}}}
$$

其均值行先对各配置计算，再做宏平均，因此不应直接用汇总后的 33.9% 与 50.5% 重新计算并指责均值不一致。〔[SB](#src-sb)，§4、表 2，pp.5–6〕

更重要的结论是：**技能效果是“内容、模型、运行框架、任务”共同决定的经验属性。** 同一模型在不同 Harness 中的发现、提示与执行过程不同，最终收益也会不同；调用率高也不保证完成率高。〔[SB](#src-sb)，§5.1.1，pp.6–7〕

## 3.3 读主结果时必须带上三个边界

**技能已经过筛选。** 附录 A.4 说明基准优先使用高质量技能，作者也承认这比真实技能生态更乐观；真实使用还存在低质量内容与不完美任务匹配。〔[SB](#src-sb)，附录 A.4，p.15〕

**任务也经过筛选。** 文中说明，条件之间没有可测区分的任务可能被排除为低信号任务。本文据此认为，平均提升更适合解释为“所选专业任务上的技能增强收益”，不适合直接推广成任意任务分布的平均收益。后半句是对实验选择机制的解读。〔[SB](#src-sb)，§3，p.4；附录 B.10，p.18〕

**具体因果贡献尚未完全分离。** 更多上下文、步骤说明、实例和可执行资源可能共同起作用。作者明确提出需要长度匹配的普通文档、无关文本等对照，进一步分离各组件的贡献。〔[SB](#src-sb)，§6.1，p.8〕

## 3.4 高价值技能补的是操作细节，不是百科全书

附录 F.4 对高收益任务的轨迹审查归纳出五类内容：带校准默认值的脚本；明确的数据源与解析细节；精确的文件格式约束；算法需要保持的条件；有助于首次扫描匹配的技能描述。〔[SB](#src-sb)，§6、附录 F.4，pp.8、28–29〕

**综合理解：** Skill 应优先补齐“模型不能可靠地从任务本身推断出来”的东西。

“认真分析数据”没有指定行动。“比较两个值之前，核对对象、期间、单位与版本；不能确认时返回待核实状态”，则会改变执行过程。这个数据分析例子是本文的教学迁移，不是基准中的原始技能。

同样，“使用某种算法”往往不如“使用经过测试的实现、明确输入约束、检查一个关键不变量、对异常输出执行回退”有操作价值。

## 3.5 为什么技能有时会伤害表现？

论文中有 13 个任务加技能后结果变差。轨迹审查归纳三种机制：要求过重的流程，挤掉足以完成任务的简单方案；通用流程压制模型更强的直接策略；把模型引向它无法调试的框架或格式。〔[SB](#src-sb)，§5.1.3、附录 F.3，pp.7、28〕

这些技能未必在理论上错误，可能只是对当前任务、预算和执行者不合适。因此，好的技能必须回答“什么时候不用我”。

论文提出一种复杂度契约建议，包含预计工具与 token 成本、适用边界和轻量回退路径。**这是文中的改进提议，不是本文宣称已经普遍实现的格式标准。**〔[SB](#src-sb)，§6，p.8〕

## 3.6 数量与长度：相关性不能被误读为通用最优值

附录 F 的任务分组结果是：

| 每个任务所配技能数 | 任务数 | 无技能通过率 | 有技能通过率 | 提升 |
|---|---:|---:|---:|---:|
| 1 | 23 | 32.2% | 50.2% | 18.0 个百分点 |
| 2–3 | 43 | 34.4% | 53.4% | 19.0 个百分点 |
| ≥4 | 21 | 34.8% | 44.9% | 10.1 个百分点 |

〔[SB](#src-sb)，附录 F.1、表 8，p.28〕

不同长度的文档组也表现出聚焦内容更有收益的趋势。但这些组对应不同任务，不是把完全相同的任务随机分配不同技能数量后得到的通用因果规律。因此不能直接得出“任何任务最多三个技能”或“删掉一半文字一定更好”。〔[SB](#src-sb)，附录 F.1–F.2，p.28〕

**工程建议：** 控制的是当前任务实际加载的无效内容与冲突，而不是机械追求某个文件数。小而明确的任务可能需要一个技能；复杂任务可能需要多个互补技能，关键在于是否各有明确职责。

《Not All Skills Help》的 ASSAY 框架进一步把问题从“加载多少”推进到“具体加载谁”：某个技能对一类任务有帮助，对另一类任务有害，总体均值可能相互抵消。§10.6 会展开按任务整理和屏蔽技能的机制，§14.2 则说明如何通过随机对照估计单个技能的贡献。它与此处按任务分组观察技能数量的结果，证据类型不同。〔[ASSAY](#src-assay)，§2，pp.3–5〕

## 3.7 自生成技能退步，究竟说明什么？

自生成条件先让 Creator 在没有人工整理技能的情况下，借助 skill-creator 编写技能包，再由 Solver 求解。三个专用框架配置中的自生成结果都低于无技能基线。〔[SB](#src-sb)，附录 D.6，pp.21–23〕

但轨迹审查发现，问题并非只有“内容写得差”：生成的技能可能未被发现；编写技能挤占求解过程；被使用的技能固化了错误假设；部分看似成功的案例实际上把具体任务答案线索带进了技能包。不同配置还有会话、文件系统状态、覆盖率或推理设置差异。〔[SB](#src-sb)，附录 D.6–D.6.1，pp.22–23〕

因此，这个实验更适合被理解为对“一次性自写技能替代人工技能”的诊断，不能直接否定 AWM、ASI 那种从真实执行反馈中逐步提炼、验证、复用的方法。

**从描述中写“应该怎么做”，与从实际执行中发现“什么做法值得复用”，不是同一种学习过程。**

# 4. 从 MemGPT 到经验记忆：调度上下文、维护事实与加工经历

## 4.1 有数据库，为什么仍然会忘？

即使所有历史都在数据库里，当前模型仍然需要知道自己缺少什么、发出合适查询、读取结果，并在必要时继续查询。数据库保存了信息，不代表信息已经进入当前决策。

MemGPT 借用操作系统的分层内存与换页思想：模型上下文相当于有限工作集，外部存储保存暂时不在工作集中的信息，需要时再调入。它扩展的是可访问的信息范围，不是一次推理中同时可见的信息数量。〔[MG](#src-mg)，§1–2，pp.1–2〕

因此，“无限上下文”的说法应按论文的 virtual context management 理解：**用访问与调度机制提供更大的有效信息空间，而不是消除模型上下文上限。**

## 4.2 架构中的不同组件，职责不能混在一起

MemGPT 的主上下文包含三部分：只读的系统说明、可以通过函数修改的 Working Context，以及保存近期消息和工具结果的 FIFO 队列。队列头部还保留被移出消息的递归摘要。〔[MG](#src-mg)，§2.1，p.2〕

外部存储包含 Recall Storage 与 Archival Storage。Recall 保存历史消息，队列管理器负责写入输入与输出；Archival 可以保存通过函数读写的较长文本对象。信息必须显式进入主上下文，才能用于当前推理。〔[MG](#src-mg)，§2–2.3，pp.2–3〕

| 组件 | 主要内容 | 谁负责改变它 | 对开发者的意义 |
|---|---|---|---|
| 系统说明 | 角色、记忆层级与函数使用说明 | 在该架构中是静态只读内容 | 不与日常记忆编辑混用 |
| Working Context | 当前持续需要的关键信息 | 模型通过记忆函数修改 | 保留正在使用的核心信息 |
| FIFO 队列 | 近期消息、工具调用与结果、历史摘要 | 队列管理器 | 保留近期交互细节并控制容量 |
| Recall Storage | 原始交互历史 | 队列管理器写入，函数检索 | 历史被移出上下文后仍能重新访问 |
| Archival Storage | 其他持久文本对象 | 记忆函数读写 | 长期资料不必常驻上下文 |

表中前三列概括论文架构，最后一列是工程解读。〔[MG](#src-mg)，图 3、§2，pp.2–4〕

## 4.3 容量警告与换出：不是先丢掉，再想办法

队列管理器在上下文接近上限时发送 Memory Pressure 警告，给模型机会把关键信息写入 Working Context 或 Archival Storage。需要释放空间时，系统移出部分旧消息并更新摘要；旧消息虽然不再直接可见，但仍保存在 Recall Storage 中。〔[MG](#src-mg)，§2.2，p.3〕

论文给出的 70% 警告、100% 刷新、移出一部分消息等数值是描述机制的示例，不应直接被解释为所有模型和工作负载的部署最佳参数。

**工程建议：** 将“保存可恢复状态”设计为压缩前的显式步骤，而不是等模型已经失去关键约束后，再要求它凭摘要恢复。精确事实、任务进度和解释性摘要应分开处理。

## 4.4 心跳机制：记忆管理同时也是控制流管理

MemGPT 中，用户消息、系统提醒、容量事件等可以触发模型推理。函数调用的特殊参数 `request_heartbeat` 允许工具执行后立即再次调用模型；否则系统可以让出控制权，等待下一个外部事件。〔[MG](#src-mg)，图 3、§2.4，pp.3–4〕

这使一个请求可以完整执行：

```text
接到问题
→ 查询历史
→ 读取第一页
→ 发现需要更多内容
→ 读取下一页或改写查询
→ 找到相关信息
→ 整合并回答
```

如果没有继续执行的控制机制，Agent 可能完成一次查询就停止，等待用户反复说“继续”。因此，MemGPT 与“回答前固定检索一次”的差别，不只是存储层级多，而是**检索可以成为推理过程中的连续动作**。

## 4.5 DMR 实验：保留可访问的原始历史，比只依赖摘要更有优势

Deep Memory Retrieval 要求回答前几次对话中的具体信息。论文表 2 中，GPT-4 基线为 32.1%，加入 MemGPT 后为 92.5%。但这个结果必须连同实验条件一起读：基线看到有损历史摘要，而 MemGPT 可以通过分页搜索访问完整历史。评价还使用了参考答案、ROUGE-L 与模型评估。〔[MG](#src-mg)，§3.1.1、表 2，p.5〕

它直接支持的认识是：**对精确信息，保留重新读取原始记录的能力，优于只依赖被压缩的描述。** 它不单独证明任意数据库架构或任意当前模型都会获得相同幅度的提升。

## 4.6 多文档与嵌套查询：记忆系统需要会继续查、也会正确停止

在文档问答中，固定检索—阅读方式将一批文档交给模型；MemGPT 则允许模型主动查询归档并翻阅分页结果。论文将检索排序质量与模型是否愿意继续翻页都视为影响效果的因素。〔[MG](#src-mg)，§3.2.1，pp.6–7〕

嵌套键值任务进一步测试多跳能力：

```text
K1 的值是 K2
K2 的值是 K3
K3 的值是最终值
```

输入 K1 后，拿到 K2 不能立刻回答。系统必须继续确认该值是否仍然是一个键。这里测试的是连续查询、维护中间结果和判断停止条件，而不只是一次检索命中。不同底层模型仍可能因为查询次数不足而失败。〔[MG](#src-mg)，§3.2.2，pp.7–8〕

操作系统类比也有边界：传统程序访问地址时可以明确触发缺页，但 Agent 不一定知道自己遗漏了什么。论文观察到，MemGPT 有时会过早停止分页检索，较弱的函数调用能力也会拖累表现。〔[MG](#src-mg)，§3.2.1–3.2.2，pp.7–8〕

**外部空间大，不等于信息一定能被有效访问；能访问，也不等于访问策略一定正确。**

## 4.7 摘要应该导航，不应该替代精确事实

下面是对上述机制的工程迁移。

一条原始数值可能同时包含对象、份额类别、统计期间、单位、口径、数据版本和来源位置。多轮摘要后，可能只剩“这个产品近期收益约为 X”。数字还在，但它的身份丢了。

因此，应让摘要回答“正在做什么、去哪里找”，让结构化事实记录回答“这个数究竟属于哪个对象、哪个期间、哪个版本”。压缩以后，Agent 根据事实标识重新加载当前章节需要的数据，而不是凭摘要中的数字继续写。

这并不是 MemGPT 已经实现了完整的财务事实核对系统，而是从“可重新访问原始记录”的架构中得到的设计建议。

## 4.8 Mem0：事实进入记忆前，要先提取再比较

MemGPT 重点回答“当前上下文放什么、怎样访问外部内容”；Mem0 则提供了一条维护持久事实的具体流程。新消息对到达后，提取器结合对话摘要与近期消息，从这次交互中形成候选事实；摘要由独立模块异步更新。随后，对每条候选检索相似旧记忆，再让模型通过工具调用选择 ADD、UPDATE、DELETE 或 NOOP。它不是只把每轮对话直接做 embedding 后追加到库里。〔[Mem0](#src-mem0)，§2.1，pp.3–5〕

```text
新交互 + 对话摘要 + 近期消息
→ 提取候选事实
→ 检索相关旧记忆
→ 比较新旧内容
→ 新增、更新、删除或保持不变
```

四种操作来自讲义 p.18 与论文方法：没有等价信息时可以新增，有补充或变化时可以更新，遇到否定旧记忆的信息时可以删除，重复或不需改变记忆时选择 NOOP。具体决策仍由模型解释新旧陈述；操作名称本身不能保证对象对齐、时间判断和冲突归因都正确。§10.3 将进一步讨论这些工程条件。〔[L04](#src-l04)，p.18；[Mem0](#src-mem0)，§2.1〕

图记忆版本 Mem0ᵍ 进一步把内容表示为带类型的实体与关系三元组。检索既可以从查询中的实体出发访问相邻关系，也可以对关系三元组做语义匹配。原文还描述了将过时关系标记为无效而非物理删除，以保留时间推理所需的信息；不要把这与基础版本的 DELETE 操作混为一谈。〔[Mem0](#src-mem0)，§2.2，pp.5–6〕

**综合理解：** 对话摘要提供背景，候选事实提供可维护对象，关系表示提供对象之间的连接。它们与保留原始历史可以共存，但本身都可能损失信息。论文在 LOCOMO 多轮对话问答上评测，并排除了 adversarial 类别，不能据此宣称已经验证了完整的不可回答问题识别、任意事实冲突处理或程序技能维护。〔[Mem0](#src-mem0)，§3.1–3.2，pp.6–7〕

## 4.9 Reflexion：反馈如何改变下一次尝试？

讲义 p.19 的 Reflexion 案例展示同一问题上的尝试、评估、反思与重试。论文将其分为 Actor、Evaluator、Self-Reflection 三个职责：Actor 行动，Evaluator 判断结果，Self-Reflection 把轨迹和反馈转成可指导下一次尝试的文字，保存在记忆缓冲区。反馈可以来自外部环境、规则、测试或模型判断，不必全部由另一个语言模型生成。〔[L04](#src-l04)，p.19；[REF](#src-ref)，§3，pp.3–5〕

例如，“运行失败”只是一个结果；“读取容器内容前没有确认目标物体已放入，下一次先检查该状态”才会改变行动。这个教学例子说明反思承担了把稀疏信号加工为具体修改建议的职责，但解释仍可能归因错误。

论文所说的 verbal reinforcement learning 通过反思文本影响后续行为，不是对语言模型权重做梯度更新。本节强调同任务多次尝试的机制；后面的 ExpeL、AWM 和 ReasoningBank 则进一步讨论怎样将经验用于别的任务。比较结果时，必须区分允许重试后的成绩与未见任务上的单次表现。〔[REF](#src-ref)，§3–4〕

## 4.10 检索经历之前，经历往往已经被加工

讲义 p.20 把多项研究放在“相似轨迹作为示范”的共同视角下。回到原论文，它们保存的对象、加工方式和使用层级并不相同：

| 方法 | 保存前做了什么 | 取回的内容用在哪里 | 需要保留的区别 |
|---|---|---|---|
| Synapse | 过滤无关状态，把任务、观察与动作组织成完整示范轨迹 | 按任务元数据检索示例，辅助当前行动生成 | 轨迹示范不等于原始 HTML 全量回放 |
| Agent S | 分别总结全任务与子任务经历 | 全任务 Narrative Memory 辅助规划；子任务 Episodic Memory 辅助执行 | 两层的粒度、检索键与成败筛选条件不同 |
| ICAL | 修正不完美动作，增加语言注释，再通过执行与人类反馈完善 | 形成后续任务可检索的高质量示范；本地版本也研究微调 | 注释包含状态、子目标与因果解释，不能仅视为删减轨迹 |
| ExpeL | 收集成败经历，并额外提炼和修订跨任务 insights | 成功轨迹作示例，insights 作为规则性指导 | 同时复用具体经验和抽象原则 |

〔[SYN](#src-syn)，§3，pp.4–6；[AGS](#src-ags)，§3.1–3.2，pp.4–6；[ICAL](#src-ical)，§3，pp.3–6；[EXP](#src-exp)，§4，pp.3–5〕

Synapse 的状态抽象服务于一个具体目标：让有限上下文能容纳更有用的轨迹。其 trajectory-as-exemplar 格式还允许模型生成一组连续动作，直到需要新观察再继续。因此，示范记忆也可能改变行动生成的时间粒度，不能把全部效率收益都归于“已经注册好的宏函数”。〔[SYN](#src-syn)，§3.2–3.3，pp.4–5〕

Agent S 的 Narrative Memory 包含对成功和失败的抽象任务总结，而 Episodic Memory 保留被 Worker 标为成功的子任务总结及较具体的行动指导。它说明，“失败要不要保存”不能脱离保存层级讨论。论文中这些成功信号涉及自评，不能与最终基准的独立验收混用。〔[AGS](#src-ags)，§3.1，pp.4–5〕

ExpeL 则把跨任务学习显式分成两条：一条检索训练期的成功轨迹；另一条对比同任务的成功／失败轨迹，或从多项成功任务中找共同做法，提炼 insights。这里的“训练期”指在训练任务上收集与整理经验，不更新语言模型参数。规则可以被 ADD、EDIT、UPVOTE、DOWNVOTE；新规则的计数从 2 开始，赞同或编辑增加计数，反对减少计数，降到 0 时删除。测试时拼接完整规则列表，并检索相关成功示例。这里的计数反映模型在经验整理中的支持程度，不是通过随机对照测得的任务收益。〔[EXP](#src-exp)，§4.1–4.3，p.4〕

这些方法使问题从“保留多少历史”转向“把历史加工成什么”。下一章聚焦其中一类对象：**可参数化、可反复使用的子任务工作流。**

# 5. AWM：从具体经历到可复用工作流

## 5.1 用“评论检索”贯穿提炼过程

讲义中的任务是统计包含 “satisfied” 的评论数量。原始过程包括进入 Marketing、打开 All Reviews、输入关键词、搜索并报告数量。〔[L04](#src-l04)，p.26〕

如果保存整段经历，保存的是某次关键词和某次答案。AWM 希望保留的是可变参数之外的共同结构：

```text
实例：检索 satisfied，得到本次结果。

工作流：
目标：搜索包含 {term} 的评论。
前提：能够进入评论列表。
过程：定位搜索入口 → 输入 {term} → 提交 → 读取当前结果。
```

上面的“前提”是本文为说明适用条件而显式补出的教学组织；AWM 原始工作流由目标描述与包含环境描述、说明和动作的步骤组成。〔[AWM](#src-awm)，§2.2，p.3〕

## 5.2 抽象需要同时解决变量、边界和环境信息

**变量：** 将商品名、关键词等实例值替换成描述性参数。

**边界：** 提炼反复出现的子任务，而不是整段业务目标。例如“搜索商品”可以服务收藏、比较或购买；“搜索并收藏某商品”复用范围更窄。

**环境信息：** 保留为什么某个动作在当前状态下成立。只有“点击、输入、点击”的动作形状，无法区分大量完全不同的任务。

前两点是 AWM 提炼提示的明确要求；工作流中的环境状态描述则为动作提供上下文。〔[AWM](#src-awm)，§2.2–2.3、附录 A.1，pp.3、14〕

这不是单纯压缩字数，而是在寻找未来任务也会出现的结构。

ICAL 提供了另一种补充：示范可能来自不完美的人类操作或较弱策略，提炼时不仅删除绕路，还增加任务与因果关系、状态变化、子目标和相关状态信息等注释，再执行修改后的轨迹并用人类反馈修订。用一个教学例子说明：“碗已经清洁”描述状态，“由于已经清洁，无需再洗”表达行动依据，二者不等价。**综合理解：抽象既可以减少实例细节，也可以补足原始动作序列没有说明的适用条件。** 这些补充解释需要执行或反馈支持，不能只因语言流畅就当作已验证因果关系。〔[ICAL](#src-ical)，§3.2–3.3，pp.4–6〕

## 5.3 原始 AWM 怎样使用工作流？

AWM 主要把工作流加入模型可见的辅助记忆。模型仍然需要结合当前观察逐步生成动作。即使工作流中的动作长得像程序，也不意味着整个流程已经注册为一次可执行调用。〔[AWM](#src-awm)，§2.3，pp.3–4〕

原文离线设定按网站汇集训练经历并提炼工作流，然后把工作流加入测试时记忆；实验按网站组织，以保持较小且相关的工作流集合。**这不是已经验证了“全局十万技能向量库，每步 top-k 选择”的架构。**〔[AWM](#src-awm)，§2.3、§3，p.4〕

将 AWM 扩展为检索式技能服务是可能的工程方向，但其路由质量、候选数量和冲突控制需要另外评测。

## 5.4 离线与在线：学习信号来自哪里？

离线方式从已有的较高质量经历中提炼，后续使用相对固定的工作流。在线方式从顺序到达的任务中积累：先执行，模型评估器判断是否成功，被判断为成功的经历再转成工作流，用于下一项任务。〔[AWM](#src-awm)，§2.3，p.4〕

```text
离线：已有经历 → 提炼工作流 → 固定记忆 → 后续任务
在线：当前任务 → 执行经历 → 成功判断 → 新工作流 → 下一任务
```

这与 Reflexion 的同任务重试不同。AWM 关注的是：前面的经历是否能帮助后面的任务。

在线方式还会从目标环境获得经验，因此“允许在新网站中继续积累”的跨环境适应，与“把冻结的旧技能直接迁移过去”不是同一难度。论文在分析中明确讨论了目标任务分布与离线示例不匹配的问题。〔[AWM](#src-awm)，§3.2.2，pp.7–8〕

## 5.5 跨任务积累：从找地点到查邮编

讲义第 28 页和 AWM 图 6 展示了一个具体过程：先学会按名称找地点，再将这段流程作为后续查询邮编的前半部分，继续增加步骤，形成更复杂的工作流。〔[L04](#src-l04)，p.28；[AWM](#src-awm)，§3.1.3、图 6，p.6〕

这体现的是结构复用，而不只是相似问句匹配。论文还构造跨模板子集，每个模板只选一个任务，用于检查收益是否仅来自同一模板内替换实例值。〔[AWM](#src-awm)，§3.1.3，pp.5–6〕

不过，某个示例里形成了复合流程，不代表系统已经解决任意技能组合、依赖冲突或无限复杂度增长的问题。

## 5.6 三个比摘要更有价值的消融

### 规则式提炼并不总是弱于语言模型提炼

在 WebArena 上，规则式与语言模型式提炼的成功率分别为 35.6% 和 35.5%，步数分别为 6.3 与 5.9。作者认为模型提炼的子流程更细，减少了不必要步骤，但该实验并不支持“必须用复杂 LLM 提炼器才有效”。〔[AWM](#src-awm)，§4.1、表 5，p.8〕

**工程建议：** 先建立去重、过滤明显无效动作和复用成功经历的简单基线，再判断进一步提炼的收益。

### 供模型阅读的代码，与供模型阅读的自然语言，都可能有效

AWM 将工作流中的动作代码改写为自然语言，两种形式总体差异不大。这里比较的是记忆表达形式，不是“文本指导”和“真实可执行程序”之间的全部差异。〔[AWM](#src-awm)，§4.2、表 7，p.9〕

这一区别是读懂 ASI 的前提。

### 更多环境细节，可能带来更多噪声

论文尝试同时提供自然语言状态描述与过滤后的 HTML，结果没有优于单独使用描述。作者把可能原因归结为上下文增加以及 HTML 过滤错误引入不相关或矛盾信息。〔[AWM](#src-awm)，§4.3、表 8，p.9〕

**综合理解：** 好的记忆不是完整复刻历史页面，而是保留对未来决策有用的信息，同时避免过时元素编号与偶然布局干扰。

## 5.7 “步骤成功”与“任务成功”不能互换

Mind2Web 的评价分为元素选择、动作匹配、单步成功，以及所有步骤均正确的整任务成功。AWM 在 GPT-4 跨任务实验中，单步成功率从 36.2% 提升到 45.1%，但整任务成功率是从 2.0% 到 4.8%。〔[AWM](#src-awm)，§3.2、表 3，pp.6–7〕

因此，不能把“45.1%”写成整任务成功率。长任务里，单步改进有价值，但从每步更可靠到完整任务可靠，中间仍然有距离。

论文也观察到，工作流可能引导模型执行不适合当前状态的动作，说明“知道何时偏离工作流”仍然是难点。〔[AWM](#src-awm)，§3.2.1，p.7〕

## 5.8 离线经验加在线经验，为什么没有简单相加？

附录 C 以离线工作流初始化，再加入在线工作流，结果没有呈现简单叠加收益。作者认为两类工作流并非完全兼容，旧工作流还可能影响新流程的生成和使用。〔[AWM](#src-awm)，附录 C、表 11，p.16〕

把它与 SkillsBench 的负面案例联系起来，得到同一条认识：**经验不仅提供帮助，也会形成行为惯性。**

所以记忆系统既要会调用，也要会判断“不应让这段旧经验影响当前任务”。

# 6. 程序技能：从 ASI 的验证到迁移与主动练习

## 6.1 AWM 已尝试宏动作，ASI 的重点在于更完整的验证链路

AWM 第 5 节已经探索将工作流包装成高层动作。但固定序列会遇到中间状态问题：输入城市后出现机场候选，下一步应该选择什么，必须看见弹窗才知道。若宏动作不读取中间观察，就可能盲目执行。〔[AWM](#src-awm)，§5、图 7，pp.9–10〕

因此，不应把研究史简单写成“AWM 从未执行工作流，ASI 第一次想到函数”。准确的区别是：AWM 主方法以记忆指导为主；ASI 将程序诱导、测试轨迹、执行检查和动作空间更新作为核心设计。〔[ASI](#src-asi)，§2，pp.2–4〕

## 6.2 从评论搜索经历生成两个技能

ASI 可以把“进入评论页”和“输入关键词搜索”提炼为不同函数：

```python
# 论文例子的简化表示：具体函数需要运行环境提供底层动作。
open_marketing_reviews()
search_reviews(search_box_id, search_button_id, term)
```

“satisfied”变成参数，最终答案不应写死在函数里。部分导航函数仍可能有站点特定常量，论文明确允许按网站诱导某些上下文相关技能，因此不能宣称所有生成程序已经完全环境无关。〔[ASI](#src-asi)，§2.3、图 2，pp.3–4〕

在诱导前，ASI 会清理明显执行错误的动作，并将冗长说明压缩为短行动描述。论文报告，这部分文字由平均每步 87.9 tokens 降到 13.4 tokens。它让提炼更集中于行动与状态变化，但没有免除保留原始执行证据的必要。〔[ASI](#src-asi)，§2.3，p.3〕

## 6.3 最重要的测试设计：让成功真的依赖新技能

**第一种假象：任务通过，但没有使用新技能。** 如果只允许 Agent 自由重做，它可能绕开新技能，仍用旧动作完成任务。ASI 因此把原始轨迹重写为包含新技能调用的执行前缀。〔[ASI](#src-asi)，§2.3，p.4〕

**第二种假象：新技能无效，旧答案却让测试通过。** 原始轨迹最后可能是 `send_msg_to_user("2")`。若原样保留，前面的新技能即使失效，最后仍会输出正确答案。ASI 会删除最后一次技能调用之后的尾部原始动作，让 Agent 根据新执行结果重新完成剩余任务。〔[ASI](#src-asi)，§2.3，p.4〕

```text
原轨迹
    点击 → 点击 → 填词 → 搜索 → 直接回答旧结果

重写轨迹
    新导航技能 → 新搜索技能 → 直接回答旧结果

真正用于验证的前缀
    新导航技能 → 新搜索技能
                         ↓
                 根据本次观察继续完成
```

随后检查三个条件：模型评估器判断任务完成；实际调用了新技能；技能调用造成了环境变化。满足条件后，只将测试中被调用的技能加入库。〔[ASI](#src-asi)，§2.3，p.4〕

**工程启发：验证一个组件，不能允许旧答案或旁路逻辑替它制造成功。** 测试计算技能时，不只看最终文本是否含目标数字，还应检查数字是否依赖本次输入与本次计算。

## 6.4 “执行过”不等于“得到正确性证明”

ASI 的在线学习过程没有真实奖励标签，使用模型评估器判断成败；最终 WebArena 评价则使用环境中的程序化评估。两种验证发生在不同层次。〔[ASI](#src-asi)，§2.2–2.3、§3.1，pp.3–5〕

执行后环境有变化，只能排除部分无效技能；环境是否发生了正确变化、是否覆盖全部要求，仍需要更具体的验收。原任务重放通过，也不能保证程序对新参数和新环境都正确。

因此，建议分开“原经历成功”“提炼程序有效”“未来复用有效”三个判断，不能用同一个通过标记概括。

## 6.5 消融：验证与执行方式是两条贡献路径

购物网站的表 3 报告：

| 提炼与使用方式 | 成功率 |
|---|---:|
| 未验证文本，放入记忆 | 32.6% |
| 已验证程序，放入记忆供阅读 | 36.4% |
| 验证后转成文本，放入记忆 | 39.0% |
| 已验证程序，作为可调用动作 | 40.1% |

〔[ASI](#src-asi)，§3.3、表 3，p.6〕

这个结果不能只总结为“代码比文字好”。它支持更细的认识：经过验证的提炼内容，即使以文本提供也有价值；程序表示必须与执行接口匹配；直接调用程序还可能提供额外收益。

同时，该消融的一些对照同时改变了验证与表示，不是每一行都只改变一个变量，不能把全部差值当作纯粹的单因素因果效应。

**来源差异：** 同页正文把 32.6% 到 36.4% 的变化写成 4.2 个百分点，但表值直接相减为 3.8。本文保留表格原值，不复述不一致的差值；其定性结论不依赖于选择哪一处差值。

## 6.6 高层技能压缩的是模型决策链

同一 Claude-3.5-Sonnet 实验配置中，表 1 的 Vanilla、AWM、ASI 成功率分别为 32.7%、36.3%、40.4%，平均步数分别为 5.6、5.9、5.0。这里应看同配置的比较，而不是与其他论文不同模型的绝对分数排队。〔[ASI](#src-asi)，§3.1–3.2、表 1，p.5〕

进一步的扩展浏览任务使用检查点完成比例。讲义汇总为无记忆 41.3%、文本技能 59.5%、代码技能 80.2%；平均 Agent 步数为 24.5、20.6、15.0。**80.2% 是检查点完成指标，不是 80.2% 的任务全部成功。**〔[L04](#src-l04)，p.33；[ASI](#src-asi)，§4、表 4，p.7〕

一个技能调用可能在内部执行多个浏览器动作。因此，Agent 决策次数减少，不代表底层动作按同样比例减少，也不自动等于端到端成本下降。还必须计入诱导、测试、异常恢复和执行等待。

## 6.7 代码是否一定更僵硬？关键在状态访问与适用范围

程序可以包含条件和循环，ASI 附录给出了相关例子。问题不在代码只能顺序执行，而在生成程序是否能看到需要的状态、处理新分支，并在前提不成立时退出。〔[ASI](#src-asi)，附录 B.2，pp.16–17〕

跨网站案例中，搜索函数可以迁移，但旧排序函数使用下拉框，新网站却打开侧边栏，语义相似不代表操作兼容。〔[ASI](#src-asi)，§5、图 4，p.8〕

附录 C.3 进一步指出，跨网站测试中 ASI 相比 AWM 的成功率优势没有达到其采用的显著性标准，效率优势则达到了；对应 p 值分别为 0.1673 和 0.0378。这比主文表注的宽泛概括更有条件限制。〔[ASI](#src-asi)，附录 C.3、表 18，p.18〕

**综合判断：** 稳定、重复、可验证的子过程更适合固化；需要不断解释新观察、选择例外路径的部分，应保留必要的模型判断。不能从重复任务上的优势推出代码技能普遍优于文本技能。

## 6.8 PolySkill：把稳定接口与网站实现分开

§6.7 的跨网站排序失败，暴露了一个表示问题：任务语义相似，并不意味着按钮、页面结构与操作方式相同。讲义 p.35 引入 PolySkill，用软件工程中的多态思想，把技能的抽象目的与网站实现分开。〔[L04](#src-l04)，p.35；[POLY](#src-poly)，§3.2–3.3，pp.4–6〕

例如，购物网站可以共享 `search_product(query)` 和 `add_to_cart(item_id, quantity)` 等接口，但每个网站有自己的实现；“搜索后加入购物车”的组合流程调用这些接口，无需为每个网站重新写一份组合逻辑。以下是对论文表 1 的概念性归纳，不是可直接运行的浏览器代码：

```text
购物领域接口：搜索商品、加入购物车、结账
    ├─ 网站 A：具体搜索框、按钮和跳转方式
    └─ 网站 B：另一套页面与操作实现

组合技能：调用搜索接口 → 调用加入购物车接口
    → 在不同网站绑定相应实现
```

PolySkill 在诱导时先建立或沿用领域抽象类，再注册方法签名并形成网站实现；技能准入承接 ASI 的执行验证思路。已有的抽象接口还可以成为新网站上的探索目标：Agent 知道需要学会哪些操作，而不必每次从零决定要探索什么。〔[POLY](#src-poly)，§3.3，pp.5–6〕

这里迁移的是接口、组合结构以及对探索方向的约束。新网站仍需要找到可行实现并验证，不能把它描述为“旧代码不经修改就能在所有网站运行”。领域划分与接口语义也可能不一致，例如不同网站对商品标识或结账阶段的定义不同；后者是工程上应额外验证的契约问题，不是多态语法自动解决的问题。

这也回应了“代码技能是否一定僵硬”：需要固定的可以是组合结构，允许变化的可以是底层实现。维护时应明确失效发生在哪一层，再决定替换实现还是修改接口与所有依赖它的组合技能。

## 6.9 不是每次任务都要产生新技能

ASI 附录报告，少量任务产生了通过准入的技能，而这些技能在更多后续任务中被复用：按附录口径，成功诱导涉及约 7.6% 的任务，至少复用一次技能的任务约为 42.5%。不同网站差异明显。〔[ASI](#src-asi)，附录 B.1、表 8，p.16〕

这提示一种更合理的目标：**少量可靠技能被反复使用，而不是每次运行都必须新增一个文件。**

论文诱导提示中的函数长度、动作集合以及不包含 `try-except` 等限制，是特定实验的生成约束，不应直接转化为生产系统的普遍编码规范。〔[ASI](#src-asi)，附录 A，p.15〕

## 6.10 Voyager 与 SkillWeaver：从等待经历到主动练习

ASI 从已完成任务中提炼技能。另一个问题是：如果现有经历不足以形成有用技能，Agent 能否主动选择练习目标？Voyager 和 SkillWeaver 都让技能库影响后续探索，但作用环境和实现不同。

Voyager 的三个核心组件是自动课程、可执行技能库和迭代反馈。自动课程结合当前物品、环境与已完成／失败任务选择下一个目标；生成程序时检索已有技能，使复杂技能能够调用简单技能。执行后分别利用环境反馈、代码解释器错误和模型自验证继续修订，任务被判定完成后才把程序存入技能库。〔[VOY](#src-voy)，§2，pp.3–6〕

这里需要分开三种信息：“缺少材料”说明环境前提，“函数名不存在”说明执行错误，“目标仍未完成”说明任务验收。它们可能导致不同修复，不能全部压成一句“请再试一次”。模型自验证仍会出错；论文在 Minecraft 中的开放探索与新世界迁移，也不等于任意生产环境中的安全自主探索。

SkillWeaver 则面向网站，按以下三阶段形成 API：

| 阶段 | 具体工作 | 与仅保存成功轨迹的区别 |
|---|---|---|
| Skill Proposal | 根据网页观察和已有技能提出短程、可复用的程序性、导航或信息获取任务 | 主动补充练习目标，并从简单技能逐渐走向组合 |
| Skill Synthesis | 实际练习，利用奖励模型判断结果，再把成功过程合成为函数 | 从运行经历形成实现；静态检查发现常见生成问题时重新生成 |
| Skill Honing | 对函数执行测试；需要参数时由模型构造参数，并根据反馈调试 | 合成完成后继续验证和修复，而非生成即入库 |

〔[SW](#src-sw)，§2.1–2.3，pp.3–5〕

论文中的 API 指包含 Playwright 操作的 Python 函数，不等于发现了网站官方 REST 接口。其文档还记录前置状态和使用经历；讲义 p.31 展示“参数定义后没有被使用”的检查，正说明语法可运行与功能完整之间仍有距离。〔[SW](#src-sw)，§2.2、附录 A.6；[L04](#src-l04)，p.31〕

SkillWeaver 还研究了把较强 Agent 生成的 API 交给较弱 Agent 使用。因此，技能可以成为不同模型之间共享的外部制品；这不等于把强模型的全部推理能力迁移过去，也不保证网站专用实现能跨网站复用。论文真实网站实验因成本和可访问性筛选到四个网站、57 个任务，引用收益时应保留这一范围。〔[SW](#src-sw)，§3.2、§4〕

**综合理解：** 自动课程决定“收集哪些经历”，提炼决定“从经历中保留什么”，测试决定“当前候选是否可用”，后续复用才检验“练这个技能是否值得”。主动练习由此接入学习链路，但其额外环境交互、模型调用和测试成本必须计入评测。

<a id="chapter-07"></a>
# 7. ReasoningBank：从成功与失败中学习判断策略

## 7.1 有些经验不是流程，而是“什么时候应该改变做法”

AWM 擅长提炼常见子过程，ASI 将可验证部分程序化。但某些经验更像判断原则。

例如，查第一次购买日期，只看 Recent Orders 可能不够。值得复用的不是某个历史按钮编号，而是“查询最早记录前，确认访问的是完整历史”。ReasoningBank 用这类例子说明它要保存的是可迁移的决策启发。〔[RB](#src-rb)，图 1、§1，p.2；附录 C.5，p.28〕

| 表示 | 最擅长保留什么 | 使用时还需要什么 |
|---|---|---|
| 原始经历 | 具体证据与上下文 | 识别哪些细节可迁移 |
| 工作流 | 子目标与常见操作 | 结合当前环境调整 |
| 程序技能 | 可直接执行的实现 | 确认接口与条件匹配 |
| 策略记忆 | 条件性判断与防错启发 | 重新取证，确认当下适用 |

这个表是对几种表示的综合比较，不是严格互斥分类。实际文本工作流也可能包含策略，程序也可以实现条件判断。

## 7.2 从“失败动作”到“失败教训”

讲义案例中，Agent 搜索蓝牙耳机，结果多达 5,578 条，每页 12 条；不断翻页后耗尽步骤，未完成用户要求。提炼出的策略是改进搜索表达、使用筛选以及调整每页显示数量。〔[L04](#src-l04)，p.38；[RB](#src-rb)，附录 E 前的案例图 17，p.30〕

同一经历可以被加工成完全不同的内容：

```text
记录：我一直翻页，最后失败。
空泛总结：以后要提高效率。
可行动经验：结果集过大且包含无关对象时，先检查查询与筛选条件。
```

第三种内容才明确改变未来决策，但也不能过度泛化为“永远不要翻页”。如果用户要求覆盖全部有效结果，分页仍然可能是必要步骤。

**工程建议：** 失败经验应包含适用条件和边界，不能只留下一个绝对化口号。

## 7.3 为什么加入失败，对不同记忆方式影响不同？

在 WebArena-Shopping、Gemini-2.5-flash 的实验中：

| 方法 | 只用成功经历 | 加入失败经历 |
|---|---:|---:|
| Synapse | 40.6% | 41.7% |
| AWM | 44.4% | 42.2% |
| ReasoningBank | 46.5% | 49.7% |

〔[RB](#src-rb)，§5、图 7，pp.10–11〕

这说明失败不是一种直接追加就有用的材料。把失败动作当示范，可能引入负面引导；将失败条件提炼成防范策略，则可能有帮助。

这也不是“AWM 在理论上永远不能使用失败”。它说明的是该实验中几种记忆设计和处理方式的差异。

§4.10 的 ExpeL 已经从成败对比中提炼跨任务 insights；Agent S 也在全任务层保存失败总结。因此，ReasoningBank 的定位不应写成“首次发现失败能转成经验”。更有意义的比较是：ExpeL 主要先整理训练经历与规则，再用于未见任务；ReasoningBank 在顺序任务流中从成败持续提炼策略，并进一步研究记忆与测试时多次探索的结合。上表的 Synapse 数值来自 ReasoningBank 论文中的比较配置，不是 Synapse 原论文在自身基准上的结果。〔[EXP](#src-exp)，§4；[AGS](#src-ags)，§3.1；[RB](#src-rb)，§3、§5〕

## 7.4 ReasoningBank 实际保存什么？

原始记忆条目有三个核心字段：`title`、`description`、`content`。普通提炼最多从一次经历中产生三个条目，强调简短、不重复，尽量去掉具体网站、查询和字符串，保留可迁移内容。〔[RB](#src-rb)，§3.2、附录 A.1，pp.5、21〕

```text
Title：查历史信息时确认数据覆盖范围
Description：最早、全部等要求不能只依赖近期视图。
Content：先确认当前页面覆盖范围，再使用完整历史、筛选或分页验证。
```

以上是按论文结构编写的教学示例，不是原始记忆逐字摘录。

抽象不能没有边界：去掉特定网站名有助于迁移，但若同时丢失限制条件，也会让经验变成宽泛建议。本文工程方案因此会额外保存适用范围、来源和验证状态；这些不是论文的原始三个字段。

## 7.5 检索粒度与保存方式，比名字听起来简单

论文实现主要对过去任务查询计算向量相似度，找到最相近的经历，再取出该经历对应的记忆条目。默认 $k=1$ 指一个经历，不一定是一个条目。〔[RB](#src-rb)，附录 A.2，p.22〕

存储使用 JSON，保留任务查询、原始轨迹和条目；embedding 另外保存。所谓 consolidation，在实现中主要是直接追加新条目，没有额外剪枝、合并和遗忘算法。〔[RB](#src-rb)，附录 A.2，p.23〕

因此，不能因为论文使用“记忆整合”一词，就自动推断它已经处理复杂的冲突、版本与生命周期。

它与 MemGPT 是互补关系：前者强调经验内容，后者强调信息分层访问与控制流。ReasoningBank 自身在局限性与未来方向中也作了这种区分。〔[RB](#src-rb)，附录 D–E，pp.29–30〕

## 7.6 判断器的噪声会进入未来行为

ReasoningBank 使用模型作为成功／失败判断器。论文在一个购物实验中测得其准确率为 72.7%，再通过随机翻转真实标签模拟不同质量的判断器，观察到一定范围内仍有收益。〔[RB](#src-rb)，§5、图 8，p.11〕

需要区别两类错误：随机把部分标签判错，与持续把同一类缺陷判为成功。后者可能反复污染某一类经验，例如把“写得完整”当作“证据完整”。这一点是对系统风险的工程分析，不是随机噪声实验已经覆盖的结论。

同一个模型承担执行、判断和提炼时，三个环节可能共享错误假设。因此，高风险技能不应只凭“模型认为自己做对了”正式发布。论文也将更强验证器、人工反馈和集成判断列为后续方向。〔[RB](#src-rb)，附录 E，p.30〕

## 7.7 失败归因是一项需要证据的诊断

任务失败可能源于策略、工具、权限、环境、数据或评估器本身。把所有失败都总结成“这种方法不好”，会产生错误的限制。

**工程建议：** 保存“发生了什么”“哪些证据支持解释”“解释尚有什么不确定性”“如何验证修改”，而不是只保存一段流畅的反思。成功经验也一样：任务成功不代表每个中间步骤都必要，更不代表那些步骤都是成功原因。

这正是下一章引入多条轨迹对比的动机之一：利用不同路径之间的差异，获得比单次自我叙述更丰富的信号。

# 8. 从 MaTTS 到 SAGE：把探索计算与后续复用连接起来

## 8.1 多试几次有两种不同目标

普通多次尝试主要关注：本次能否从多个候选中得到一个正确结果。MaTTS 还关注：多次尝试之间的差异，能否改善记忆内容，进而帮助后续任务。

ReasoningBank 比较了三种方式：每条轨迹独立产生记忆的简单扩展；并行生成多条轨迹后对比提炼；在一条轨迹初次完成后继续检查和修正，利用中间纠错信息提炼。〔[RB](#src-rb)，§3.3、图 3，pp.5–6〕

```text
简单追加：轨迹 A → 记忆 A
          轨迹 B → 记忆 B
          轨迹 C → 记忆 C

并行 MaTTS：轨迹 A、B、C
             → 对比成功与失败路径
             → 提炼少量共同或互补的策略

顺序 MaTTS：初次轨迹
             → 检查与修正
             → 再次检查
             → 利用最终结果和中间修正提炼策略
```

并行提炼提示要求从全部候选中形成有限数量的条目，而非每条轨迹机械追加同样多的总结。〔[RB](#src-rb)，附录 A.3，pp.23–24〕

## 8.2 对比信号为什么有价值？

假设同一任务的一条路径不断翻页，另一条路径先筛选后验证完整性。两条路径的区别，可能比任何一条路径单独生成的“成功经验”更能突出关键策略。

但这里依然不是严格的因果识别。成功路径可能有偶然因素，几条路径也可能共享错误假设。**综合理解：对比提高了诊断的信息量，不自动提供因果证明。**

ExpeL 的成败轨迹对比与此有共同动机，但实验协议不同：ExpeL 在经验收集阶段借助重试构造成败对，MaTTS 则在测试时扩展中组织并行候选或顺序修正，并把新增经验反馈到记忆。不能把二者都概括成“多采样几次”，从而忽略经验在哪个阶段形成、之后由哪些任务使用。〔[EXP](#src-exp)，§4.1–4.2；[RB](#src-rb)，§3.3〕

对于有外部副作用的任务，并行尝试还不能直接在同一生产环境中重复执行。下面的工程部分把额外探索限定在适合重复、隔离或重放的环境，而不把论文中的多轨迹试验直接迁移为生产多次提交。

## 8.3 Pass@1、Pass@k 与 Best-of-N，不能混用

ReasoningBank 在 WebArena-Shopping、Gemini-2.5-flash 的相关设定中报告：

| 结果口径 | 数值 | 实际在测什么 |
|---|---:|---|
| ReasoningBank，不额外扩展 | 49.7% | 原始经验学习设定下的结果 |
| 并行扩展系数为 5，随机单条轨迹的 Pass@1 | 53.0% | 扩展与记忆积累条件下，单条轨迹的平均质量 |
| 同一扩展条件下 Best-of-5 | 55.1% | 从五个候选中经选择器选出一个结果的质量 |

〔[RB](#src-rb)，§4.3–4.4、图 4–5，pp.8–10〕

附录说明，Best-of-N 使用语言模型比较候选轨迹，不是直接用真实标签挑答案。论文还给出 Pass@k 分析，它反映候选集合中至少存在成功结果的能力，与实际选择器能否选中不是同一件事。〔[RB](#src-rb)，附录 A.3、C.3，pp.24、27〕

因此，不能把多次尝试后的最佳结果分数，当成同成本单次能力；也不能把随机单条改善完全归因于某一个独立组件，因为其记忆本身是在扩展流程中持续形成的。

## 8.4 步数更少，不保证总 token 更少

ReasoningBank 的成本表是很好的提醒：

| 方法 | 行动生成 | 判断器 | 记忆提炼 | 总 token |
|---|---:|---:|---:|---:|
| 无记忆 | 50,847.4 | — | — | 50,847.4 |
| ReasoningBank | 49,306.1 | 2,186.3 | 1,562.1 | 53,054.5 |

〔[RB](#src-rb)，附录 C.2、表 5，p.27〕

行动生成部分减少，但加上学习链路，总 token 增加约 4.3%。这可以与质量改善同时成立，不是逻辑矛盾。它也不直接等于费用增加相同比例，因为不同类型请求、缓存和执行延迟可能有不同成本；论文这张表测量的是 token 消耗。

**工程建议：** 评价一个技能或记忆机制，应使用完整生命周期成本，至少包括生成、提炼、验证、检索、执行和维护。只计算最后回答阶段，会漏掉经验形成的代价。

## 8.5 保存价值是延迟出现的

讲义第 43 页提出：任务 1 成功，只说明任务完成，不能说明保存其中一段代码是否值得。只有任务 2 的成功复用，才提供保存价值的信号。讲义以 SAGE 和 AgeMem 说明把后续任务纳入学习过程的方向。〔[L04](#src-l04)，p.43〕

可以用一个教学账本理解：

$$
\text{技能净价值}
=\text{未来质量与效率收益}
-\text{创建、验证、使用与维护成本}
-\text{误用损失}
$$

这不是论文中的统一训练目标，而是架构决策的表达。一个只会被使用一次的复杂技能，可能不值得保存；一个被长期稳定复用的小检查，可能有更高价值。

**真正的学习目标不应是“生成更多技能”，而应是“生成未来值得使用的技能”。**

## 8.6 SAGE：把后续复用放进训练样例和奖励

MaTTS 通过额外推理与交互改善外部记忆；SAGE 则训练模型，使它更善于生成和使用可执行技能。其 Skill Augmented GRPO for self-Evolution 在一个 sequential rollout 中串联相关任务：先执行任务 1，将期间形成的技能保留到共享库，再执行任务 2，让后续复用结果成为训练信号。论文主要使用两任务链，以控制训练成本。〔[SAGE](#src-sage)，§3.2，pp.4–5〕

这里的 GRPO（组相对策略优化）通过组内采样结果的相对奖励更新模型参数；SAGE 的关键改动是让任务采样与奖励反映跨任务技能复用。本文着重解释这两点，优化算法的完整推导可结合强化学习课程阅读。〔[SAGE](#src-sage)，§3.2.1–3.2.4〕

与任务结束后另请一个模型总结不同，SAGE 的 Agent 可以在求解过程中定义函数、调用函数、修复失败实现并保存可执行函数，也允许在无需技能时直接调用 API。技能生成和任务执行因此进入同一类可训练轨迹。能执行而无错误是其中的保存条件，不应被理解为已经证明跨任务正确；后续任务奖励进一步约束这种保存行为。〔[SAGE](#src-sage)，§3.1，pp.3–4〕

设两任务的结果奖励为 $r_1,r_2\in[0,1]$，$u=1$ 表示任务 2 使用了任务 1 生成的技能。论文的技能奖励为：

$$
R_1=r_1+\mathbf{1}[r_1=1]\mathbf{1}[r_2=1]u,
\qquad
R_2=r_2+\mathbf{1}[r_2=1]u.
$$

第一项奖励本任务结果，附加项鼓励后续成功复用；只有记录了技能被调用，还不够获得“成功复用”的奖励。原文还对不生成代码便结束的响应设置惩罚。以上是论文的奖励设计，不是本文 §8.5 的净价值账本，也不表示它已单独识别出每个技能对成功的因果贡献。〔[SAGE](#src-sage)，§3.2.3，p.5〕

在 Qwen2.5-32B、AppWorld Test Normal 的奖励消融中：

| 奖励设计 | Scenario Goal Completion（SGC） | 平均交互步数 | 平均生成 tokens |
|---|---:|---:|---:|
| 仅任务结果 | 55.4% | 13.1 | 1,469 |
| 任务链全部成功的附加奖励 | 56.6% | 15.7 | 1,361 |
| 成功技能复用的附加奖励 | 60.7% | 12.1 | 1,475 |

〔[SAGE](#src-sage)，§4.4、表 5，p.9；[L04](#src-l04)，p.43〕

SGC 要求一个场景中的三个相关测试任务全部成功，不能与单任务完成率 TGC 混用，也不能把训练中的“两任务链”误写成评测指标的分母。这里成功复用奖励对应更高 SGC 和更少步数，但生成 tokens 并非最低，再次说明效率需要分项衡量。〔[SAGE](#src-sage)，pp.3、9〕

主结果使用专家轨迹 SFT 初始化；训练任务配对和评测技能检索也会影响结果。论文另外测试了用相似度构造任务链，以及用查询或技能 embedding 检索，而不是默认任意部署环境都能提供场景标签。因此应把收益归于所测训练与执行配置，不能全部归于“加了一个技能库”。〔[SAGE](#src-sage)，§4.4，表 3–7，pp.8–9〕

到这里，学习目标已经从“做好本次任务”扩展为“形成后续能使用的能力”。第 11 章将用 AgeMem 进一步讨论：同样的延迟反馈思想，怎样用于保存、检索、压缩和删除等记忆决策。

# 9. 把看似矛盾的结论放在一起，避免错误选型

## 9.1 自生成技能退步，与自动诱导技能有效，并不矛盾

SkillsBench 的自生成条件偏向“根据当前任务和环境编写一个包，再交给求解者”；AWM 从被判断为成功的执行经历提炼；ASI 增加了程序重放与准入检查；ReasoningBank 还使用失败轨迹及对比信号。四者的输入、反馈与使用路径不同。〔[SB](#src-sb)，附录 D.6；[AWM](#src-awm)，§2.3；[ASI](#src-asi)，§2.3；[RB](#src-rb)，§3〕

所以需要比较的是经验依据、验证质量、技能发现与后续复用，而不是只比较“是否由模型生成”。

## 9.2 文本与代码的比较，要先问是否真的执行

AWM 的文本／代码对照主要是记忆表达；ASI 的核心比较还涉及是否注册为动作。不能因为 AWM 发现两种表达都有效，就否定可执行程序的价值；也不能因为 ASI 表现更好，就认为把所有参考资料改成代码文本都会提高效果。〔[AWM](#src-awm)，§4.2；[ASI](#src-asi)，§3.3〕

## 9.3 “文本技能不提高效率”是讲义概括，不是可直接照搬的绝对结论

讲义第 36 页使用了这句话，但 AWM 的实验报告了减少绕路与步数。二者在字面上存在张力。本文采用的**机制性解释**是：文本技能不直接把多个底层操作变成一次可调用动作，却可能通过减少无效探索改善整体效率。这个解释是本文的综合分析，不声称已经确认讲义作者原本的具体意图。〔[L04](#src-l04)，p.36；[AWM](#src-awm)，§3.1.1，p.5〕

## 9.4 记忆不是越多越好，技能也不是越专用越好

SkillsBench 的内容负担、AWM 的旧新流程干扰，以及 ReasoningBank 的过量检索结果，都说明经验具有负面作用的可能性。〔[SB](#src-sb)，附录 F；[AWM](#src-awm)，附录 C；[RB](#src-rb)，附录 C.1〕

ASSAY 又指出，负面作用未必是技能整体质量差，也可能是任务条件改变。PolySkill 则提供了另一种处理专用性的方式：保留可复用接口，把网站特有的操作放到具体实现中。前者关注“这项任务是否应该受到该技能影响”，后者关注“相同功能如何绑定不同实现”，不能用同一个相关性分数代替这两类判断。〔[ASSAY](#src-assay)，§2；[POLY](#src-poly)，§3〕

另一端，过度抽象也会失去指导性。“认真验证”适用范围很广，但可执行信息很少。**综合理解：好的表示要去掉实例偶然性，同时保留使方法成立的条件。**

## 9.5 “不微调”不等于“没有成本”，也不等于“替代训练”

MemGPT、AWM、ASI、ReasoningBank 等方法主要通过外部制品改变当前系统行为，但仍需要推理、执行、存储与维护，也依赖底层模型的工具调用和理解能力。MemGPT 的模型差异，以及 SkillsBench 的模型—框架差异都表明，外部增强不自动抹平基础能力差距。〔[MG](#src-mg)，§3.2；[SB](#src-sb)，§5〕

SAGE 和 AgeMem 则直接训练使用技能或管理记忆的策略。ICAL 的本地版本同时研究检索增强与微调，DreamCoder 也训练神经搜索模型。这说明参数学习和外部知识积累可以互相支持；“技能在所有场景下优于 SFT”或“外部记忆可以替代训练”都不是本组材料建立的结论。〔[SAGE](#src-sage)，§3–4；[AgeMem](#src-agemem)，§3；[ICAL](#src-ical)，§4；[DC](#src-dc)，pp.4–6〕

## 9.6 不同论文的绝对分数不能直接形成排行榜

ASI 主实验使用 Claude-3.5-Sonnet 与其配置的 WebArena；ReasoningBank 使用其他模型，并因网站问题排除 Maps。不同论文的任务集、模型、动作接口和实验协议不一致。〔[ASI](#src-asi)，§3.1；[RB](#src-rb)，§4.1、表 1〕

因此，比较方法应优先看同论文内的匹配基线、消融和机制，而不是把来自不同条件的 40.4%、48.8% 等数字直接排序。

# 10. 生命周期：提炼、使用与维护是三条相互连接的循环

讲义第 25 页给出全课最有工程价值的结构：

```text
学习：episode → judge → induce → admit → memory
使用：memory → select/retrieve → act → outcomes
维护：outcomes → add → repair → retire → memory
```

〔[L04](#src-l04)，p.25〕

下面将它展开为可操作的设计。§10.5–10.6 用 TroVE 与 ASSAY 具体说明整理机制，其余位置也会标出论文或代码依据；没有来源标记的设计流程和治理要求属于工程建议，不代表某一论文已经验证了完整生命周期。

## 10.1 学习链路：记录发生过，不等于认可值得复用

原始轨迹可以进入受权限与保留策略约束的记录系统。但把其中内容提升为经验或技能，应是另外一条受控链路。

```text
原始记录
→ 识别值得分析的经历
→ 判断结果及反馈可靠性
→ 选择表示：事实、经验、工作流或程序
→ 形成候选
→ 验证适用范围与反例
→ 批准发布
```

建议设置明确状态，例如：

```text
candidate ─验证通过→ verified → active → deprecated
          └验证失败→ rejected
```

具体名称不重要，重要的是区分“已生成”“已验证”“当前允许使用”。生成一个格式正确的文件，不应自动等于对其内容的认可。

失败原因不明时，可以保存原始证据和待验证解释，而不是立即生成强制行为规则。

## 10.2 使用链路：相似度之后还需要适用性判断

ReasoningBank 的一个实验中，检索 0、1、2、3、4 个经历时，成功率分别为 39.0%、49.7%、46.0%、45.5%、44.4%。这说明该设定下，额外经历可能引入噪声或冲突；并不能推出所有检索系统都应设 top-k=1。〔[RB](#src-rb)，附录 C.1、图 13，p.26〕

生产系统可以把选择分为几个层次：先根据权限、项目、环境版本与有效时间排除不可用内容，再召回相关候选，最后判断前提、冲突、冗余与当前预算。

```text
当前任务 + 当前状态
→ 权限与范围过滤
→ 相关性召回
→ 适用条件核对
→ 冲突与冗余检查
→ 选择少量必要内容
→ 加载或执行
```

例如，旧版本接口的成功流程与新任务高度相似，但接口签名已经变化；过去某团队采用的规范，也不必适用于当前项目。相似度不能替代版本与权限检查。

检索键也应匹配决策层级。Agent S 用全任务经验辅助 Manager 规划，用任务、子任务与上下文检索 Worker 经验；ReasoningBank 则按过去任务查询找经历及其策略条目。这些实现提醒我们先确认“当前是在选总体方案，还是执行一个子步骤”，再决定检索粒度。它们没有建立某一种检索键适合所有系统的结论。〔[AGS](#src-ags)，§3.1，pp.4–5；[RB](#src-rb)，附录 A.2〕

**选择“不使用任何经验”也应是合法结果。** 一个系统如果强制每次从库中选内容，会把不相关经验带入原本可以直接解决的问题。

## 10.3 冲突处理先确认对象，再确认是否真的矛盾

讲义与 Mem0 的 ADD、UPDATE、DELETE、NOOP 给出了基本操作类别。Mem0 先召回相似旧记忆，再决定怎样更新；工程上在执行 UPDATE 或 DELETE 前，还应确认两条信息是不是同一个对象、同一范围、同一时间和同一版本。语义相似是比较入口，不能单独证明二者互相矛盾。〔[L04](#src-l04)，p.18；[Mem0](#src-mem0)，§2.1，pp.3–5〕

“接口 V1 返回比例小数”与“接口 V2 返回百分数”可以同时成立，不应粗暴覆盖。“某项目禁止某依赖”与“另一个项目允许使用”也未必冲突。

对于历史记录，退出当前活跃检索视图与删除审计记录是不同操作。保留多久、谁有删除权限，应由系统治理要求决定，而不是临时交给模型猜测。

## 10.4 维护链路：技能会过时，也会互相依赖

维护至少要处理内容错误、环境漂移、重复技能、冲突指导和依赖变化。

底层函数改变了输入或语义，调用它的组合技能也应重新验证。仅修改一个 `SKILL.md` 而不记录版本，会使历史结果难以解释：同一任务昨天和今天用了什么方法，无法再复现。

建议一次运行固定技能版本与记忆快照，记录候选、已选条目、执行资源和评估结果。发生回退时，不仅回退模型，还应能回退技能与提示配置。

参考研究提供了几种不同粒度的维护方式：ExpeL 修订与淘汰文本 insights；SkillWeaver 测试并调试候选 API；PolySkill 分开接口与网站实现；LILO 重新压缩程序集合并重建库，以替换早期不佳抽象。它们分别处理规则、单个实现、实现组织和整个库的结构，不能把“支持更新”理解为已经覆盖所有粒度。〔[EXP](#src-exp)，§4.2；[SW](#src-sw)，§2.3；[POLY](#src-poly)，§3；[LILO](#src-lilo)，§3，pp.4–6〕

## 10.5 TroVE：在复用、新建与只用基础函数之间选择

讲义 p.42 引用了 TroVE 的低频淘汰规则，但原方法还包括工具的使用、生成与选择。它按顺序处理可用程序求解的任务，对每个任务分别在三种模式下采样候选：IMPORT 使用已有函数，CREATE 新建函数并求解，SKIP 只用基础函数。每种模式生成 $K$ 个响应，共得到 $3K$ 个候选，而不是只让模型先选一种模式。〔[TRO](#src-tro)，§3.1，pp.3–4〕

系统先执行候选并排除不能成功执行的程序，再按输出一致性保留多数答案对应的解；仍有多个候选时，优先选择操作数较少的解，最后采用选中响应的解并将其中函数纳入库。这里的“可验证”不能读成形式化正确性：执行不报错排除了一类错误，多数候选仍可能共享错误假设。〔[TRO](#src-tro)，§3.2，p.4〕

工具库会周期性淘汰使用次数低于 $\frac{1}{2}\log_{10}(n)$ 的函数，其中 $n$ 是已经处理的样例数。论文还重新生成依赖被删函数的旧解，使用 IMPORT 与 SKIP 模式，使这些解仍能由现有库表达。这比只保留一个删除公式更能体现维护问题：**改变工具库，还要处理原来依赖它的产物。**〔[TRO](#src-tro)，§3.3、脚注 3，p.4；[L04](#src-l04)，p.42〕

这种频次规则是特定实验的启发式策略。生产系统里的低频异常恢复流程可能很重要，高频技能也可能持续造成错误；应同时考虑近期有效性、错误影响、替代方案和依赖关系。还应计入 TroVE 的多候选生成与执行成本，不能只把最终解更短解释为全过程更便宜。

## 10.6 ASSAY：同一技能为什么需要按任务判断价值？

《Not All Skills Help》提出 ASSAY，将“从经验生成技能”和“用实验决定哪些技能有帮助”分开。关键问题是技能作用的异质性：一个检查规则可能帮助复杂任务，却使简单任务增加无关步骤；正负作用在全局均值中抵消后，单一总分会掩盖问题。论文通过开发集上的随机技能屏蔽估计这种差异，具体测量方式见 §14.2。〔[ASSAY](#src-assay)，§2.1，pp.3–4〕

例如，论文中一条核对联系人规则在共享费用核对任务中有帮助，却会在无关的单应用任务中引入额外核查。这不是说明身份核对普遍无用，而是说明该指令的触发范围需要与任务相符。〔[ASSAY](#src-assay)，§3.4，p.8〕

其整理过程有两个层次：

| 层次 | 方法 | 作用 |
|---|---|---|
| 离线整理技能库 | 先拆分作用差异大的规则，为变体写明条件；再淘汰低信号规则；最后合并近似重复项 | 改善库中技能的边界与冗余；拆分须通过开发集验收，不通过则保留原规则 |
| 针对当前任务选择 | 找到相似开发任务，对已测贡献加权，预测各技能的作用并屏蔽可能有害者 | 同一技能可在任务 A 保留、任务 B 不加载；受保护技能豁免，筛选后保留的技能过少时回退到完整库 |

〔[ASSAY](#src-assay)，§2.2–2.3，pp.4–5〕

这里仍然使用语义相似度，但相似度用于寻找可参考的**开发任务及其实验结果**，不是直接把语义最像的技能当成最有帮助的技能。也不能把所有负面贡献都解释为技能内容错误：其价值依赖当前模型、共同出现的其他技能、任务预算和任务分布。

论文在 GPT-5.1／AppWorld Test Normal 的顺序消融中，将人工操作模板、离线整理和按任务屏蔽分别加入，按任务屏蔽带来其中最大的单步增量。这支持在该配置中重视路由，但完整系统还包含受保护模板、上游经验整理和回退策略，不能把主结果全部归因于一种屏蔽算法。§14.2 会进一步限定有限开发集估计的含义。〔[ASSAY](#src-assay)，§3.3、附录 H，pp.8、17〕

**综合理解：** 淘汰回答“这条内容是否还应留在库里”，路由回答“本任务是否应该看到它”。对某类任务有害，并不必然意味着应该从所有任务中删除。

## 10.7 人类参与的价值在不同环节不同

讲义第 45 页区分了人工与 Agent 更适合承担的职责：方法已经明确、正确性具有规范性或风险很高、罕见例外需要责任判断时，人类投入有价值；方法需要探索、结果可执行且测试便宜、路由重复且有反馈时，Agent 的自动化更有价值。〔[L04](#src-l04)，p.45〕

这不等于“每次记忆写入都必须人工审批”，也不等于“自动系统可以自我批准全部规则”。应根据错误影响与验证能力安排准入强度。

ICAL 提供了一个具体例子：人类在修改后的轨迹执行失败时给出自然语言反馈，模型据此同时修改动作和解释，再继续验证。此时人的贡献是补充模型从现有观察中没有可靠识别的环境约束，而不仅是对一份总结点击“通过”。这类人力与环境交互成本也属于经验形成成本。〔[ICAL](#src-ical)，§3.3，pp.5–6〕

<a id="chapter-11"></a>
# 11. 学术联系：为什么表示选择会改变学习与泛化？

## 11.1 技能提炼与程序库学习有共同结构

讲义第 23 页将技能诱导连接到 Voyager、DreamCoder、Stitch、LAPS 和 LILO。共同问题是：能否将过去解题过程中的结构变成后续求解的构件？但这些工作的学习对象和机制有明显区别。Voyager 的主动课程与程序技能库已在 §6.10 展开，另外四项工作更直接研究程序语言、抽象和搜索。〔[L04](#src-l04)，p.23〕

| 方法 | 怎样形成可复用结构 | 同时改变了什么 | 对本课的启发 |
|---|---|---|---|
| DreamCoder | Wake 阶段求解任务，Abstraction 阶段从解中提炼程序库 | Dreaming 阶段使用生成和回放的任务训练神经搜索模型 | 既学习“有哪些构件”，也学习“怎样找到它们的组合” |
| Stitch | 以程序语料约束自顶向下的候选搜索，寻找有压缩收益的函数抽象 | 重写原程序集合，使其调用新抽象 | 提炼可以由明确的符号搜索完成，不必完全依赖语言模型总结 |
| LAPS | 在 DreamCoder 式学习中加入自然语言描述的联合建模 | 语言同时引导库抽象和搜索策略 | 当前语料最容易压缩的结构，未必最适合未来泛化 |
| LILO | 生成程序，再由 Stitch 压缩，最后给抽象命名和写文档 | LLM 搜索与枚举搜索协作，并迭代重建可解释程序库 | 新函数除了可执行，还要能被后续求解者理解 |

〔[DC](#src-dc)，pp.4–6；[STI](#src-sti)，§1–2，pp.1–3；[LAPS](#src-laps)，§4–5，pp.3–6；[LILO](#src-lilo)，§3，pp.4–6〕

可以用一个教学表达理解抽象的目标：

$$
\text{总描述成本}
=\text{技能库的描述长度}
+\text{使用技能库后各任务的描述长度}
$$

每个任务保存一个专用技能，库会很大而复用很弱；把所有技能简化成“认真完成任务”，库很小却没有实际指导。好的抽象在中间：去掉偶然信息，保留重复结构与必要条件。

这个表达与程序库学习的描述长度视角相联系；LILO §3 的压缩式将新抽象的长度与重写后程序集合的长度共同计算。但上式仍是教学表达，不是 AWM 或 ASI 实际优化的统一目标函数。代码变短、搜索更容易、模型更会使用新函数，是需要分别测量的三种结果。〔[LILO](#src-lilo)，§2–3，pp.3–5〕

LAPS 用多边形说明压缩与泛化的张力：当前任务可能偏好保留某个固定边长，而“多边形”这一语言概念提示把边数与边长都参数化。语言在这里提供抽象偏好，不只是完成后给函数加标签。论文还评测了测试时没有语言提示的情况，以检查已经学到的库与搜索能力是否仍有帮助。〔[LAPS](#src-laps)，§4.3–5、§6〕

LILO 的 AutoDoc 则解决另一问题：Stitch 找到的匿名函数虽然可执行，名称如 `fn_42` 却不能清楚表达用途。LILO 用函数使用示例生成名称与 docstring，让后续 LLM 更容易解释和调用；论文通过移除 AutoDoc 的消融检验其作用。高效压缩还使它能够每轮从基础库重新推导整个库，以放弃早期不佳抽象。这里的“维护”不仅是给旧文件追加新函数。〔[LILO](#src-lilo)，§3–4.1，pp.4–7〕

这些结果来自特定的领域专用语言（DSL）与程序合成任务。把它们迁移到浏览器技能时，需要另行处理交互状态、环境副作用和执行失败；不能直接将程序语料压缩率当作 Agent 成功率。同时，DreamCoder、LAPS 及 LILO 中的神经搜索学习与外部程序库更新应分开记录，不能因它们都产出函数库就称为纯粹的免训练方法。

## 11.2 表示越具体，执行约束越强；表示越抽象，解释负担越大

原始轨迹保留细节，但迁移时需要过滤；文本技能可解释、可调整，但每次仍需要模型组织行动；代码技能减少重复决策，却需要输入契约和环境兼容；策略记忆可跨不同操作迁移，但可能过于抽象。〔[L04](#src-l04)，pp.29、36、44；[RB](#src-rb)，§3.2〕

因此，表示选择不是“选一个最先进格式”，而是在决定：**哪些判断继续交给模型，哪些判断固定到制品中。**

这是讲义第 36 页问题的直接延伸。把某段过程程序化，本质上是在提前承诺一部分行为；承诺越强，越需要清楚的适用与退出条件。

## 11.3 AgeMem：把长期记忆与短期上下文作为联合策略训练

行动策略决定下一步做什么；记忆策略决定保存什么、找什么、信任什么以及丢弃什么。

MemGPT 让检索和写入成为动作；AWM、ASI、ReasoningBank 将经历转成可复用内容；SAGE 训练可执行技能的生成与复用。AgeMem 则将长期记忆（LTM）与短期上下文（STM）的管理共同纳入 Agent 策略，补充的是另一层控制问题。〔[MG](#src-mg)，§2；[SAGE](#src-sage)，§3；[AgeMem](#src-agemem)，§3〕

论文提供六类记忆工具：

| 作用对象 | 工具 | 操作的含义 |
|---|---|---|
| 长期记忆 | ADD、UPDATE、DELETE | 新增、修改或移除持久条目 |
| 当前上下文 | RETRIEVE | 将长期记忆中的相关内容取入当前上下文 |
| 当前上下文 | SUMMARY、FILTER | 压缩历史片段，或过滤无关内容 |

〔[AgeMem](#src-agemem)，§3.2、表 1，pp.4–5〕

RETRIEVE 会访问 LTM，但论文按其作用把它归入 STM 操作：它改变的是当前可见工作集。这样读可以避免把“长期库保存了什么”与“当前上下文已加载什么”混在一起。

为了让模型学到早期保存行为的后续价值，训练中的每条完整轨迹被分为三个阶段：

```text
阶段 1：接触上下文信息，选择写入长期记忆
        ↓ 保留长期记忆，重置短期上下文
阶段 2：加入与目标无关的干扰消息，练习过滤与压缩
        ↓
阶段 3：给出正式任务，协调检索、上下文管理与求解
        ↓
根据整条轨迹的表现训练各阶段的决策
```

阶段 1 到阶段 2 的上下文重置有明确作用：防止模型绕过长期记忆，直接依靠残留上下文完成后续任务。它建立了对保存和取回的需求，但仍需检查记忆内容与评价数据之间的隔离。〔[AgeMem](#src-agemem)，§3.1、§3.3，pp.4–5〕

论文的 step-wise GRPO 将完整轨迹的终局奖励做组内归一化，再把该轨迹的优势值广播给各步骤，训练记忆动作和求解动作。**“逐步优化”在这里不表示每次写入或删除都获得独立、精确的因果贡献分数。** 总奖励也不只有任务成败，还包含上下文效率、信息保留、长期记忆质量等项，以及超出上下文或交互限制的惩罚。〔[AgeMem](#src-agemem)，§3.4–3.5，pp.5–6〕

| 比较点 | SAGE | AgeMem |
|---|---|---|
| 主要学习对象 | 可执行技能的生成和后续使用 | 长期记忆与短期上下文的联合管理 |
| 延迟反馈结构 | 主要训练配置为两个相关任务共享技能库 | 信息积累、干扰、后续求解组成完整轨迹 |
| 关键监督 | 任务结果与成功技能复用奖励 | 任务、上下文管理、记忆质量等组合奖励 |
| 与外部积累的关系 | 训练策略，再通过运行中的技能库积累方法 | 训练策略，再在任务中选择存储、检索与整理操作 |

两项研究都包含参数训练，不能作为“无需训练也能得到同等记忆管理能力”的证据。AgeMem 在 HotpotQA 训练集上进行 RL，再在五类基准上评测；各基准使用的完成率、进度率或模型评分也不相同，不能把跨基准均值当作统一意义的任务成功概率。〔[AgeMem](#src-agemem)，§4.1，pp.6–8；[SAGE](#src-sage)，§3–4〕

**综合理解：** 一个系统可以行动很聪明，但记忆策略很差。例如每次都能把任务做对，却只保存实例答案；或者每次都生成长总结，却不会选择何时重新取证。

## 11.4 经验不是权威，解释不是观察

AWM 与 ReasoningBank 都使用模型产生的中间说明辅助提炼，ReasoningBank 还明确提到以模型过程文本近似部分冗长观察的做法。它有助于控制信息量，但来源层次不能因此消失。〔[AWM](#src-awm)，§2.2；[RB](#src-rb)，§3.1，p.4，脚注 1〕

工程中应区分实际工具观察、模型对观察的解释、模型的结果判断，以及进一步提炼出的经验。后面三者可能层层继承前面的误解。

因此，原始证据应能回溯，经验应带验证状态，而不是被检索出来就具有与当前事实或正式规则相同的权威。

# 12. 生产系统的最小设计：先分清对象，再选择数据库或框架

> 本章是综合材料后的工程方案，不是任何单篇论文已经完整实现的产品架构。以下结构、字段和流程均为教学设计，需要结合实际运行框架实现与验证。

## 12.1 五类对象可以由简单存储实现

| 对象 | 保存内容 | 主要使用方式 | 典型更新条件 |
|---|---|---|---|
| 原始经历 | 任务、观察、动作、结果、反馈、环境版本 | 精确回读、审计、重新提炼 | 新运行或新反馈到达 |
| 任务状态 | 当前目标、已完成步骤、待办、未确认问题、产物位置 | 长任务恢复 | 完成一个阶段或发生中断 |
| 事实与证据 | 数值或陈述、对象、范围、来源、有效时间、版本 | 写作与判断前取证 | 来源更新、口径变化、发现冲突 |
| 候选经验 | 工作流、失败教训、程序草案 | 离线评审与测试 | 提炼、修订、验证 |
| 已发布技能 | 固定版本的方法、程序、模板、契约 | 发现、加载与执行 | 测试通过后发布或退役 |

这不要求五套数据库。可以先使用已有数据库与文件存储，关键是逻辑类型和生命周期不同，不能全塞进一个没有范围字段的“记忆文本”。

“某指标值是 X”“读取指标前核对单位”“第三章已经完成”，分别是事实、工作方法和任务状态，不应共享同一条覆盖逻辑。

## 12.2 一个候选经验对象的教学示例

```json
{
  "id": "lesson-review-001",
  "kind": "lesson",
  "title": "提出缺失结论前检查相关处理位置",
  "scope": {
    "task_family": "code-review",
    "project": "example-project",
    "environment_version": "snapshot-001"
  },
  "applicability": "准备声称某函数缺少异常处理时",
  "guidance": "检查调用方和统一异常处理入口，再判断是否仍有未覆盖路径",
  "exceptions": ["未获得必要文件时，不输出已完成全量检查的结论"],
  "evidence_refs": ["episode-001", "human-feedback-001"],
  "validation": {
    "status": "candidate",
    "result": "not_yet_evaluated"
  },
  "owner": "review-maintainer",
  "version": 1
}
```

这个结构刻意不把来源、适用条件和验证状态藏在一大段自然语言里。`candidate` 也明确表示尚不能被当成已验证的强制规则。

对于多租户或有访问限制的环境，权限标识应由可信运行时写入并验证，不能只相信模型生成的 `scope` 字段。

## 12.3 已发布 Skill 的契约

一个正式技能至少应回答：什么时候适用，需要哪些输入，执行时观察什么，怎样验收，什么时候退出，失败后怎样恢复。

下面是一个数据分析技能正文的教学模板。它保留前文讨论的事实核对与长任务恢复要求，不假设已经实现了专有工具接口：

````markdown
---
name: evidence-backed-analysis
description: 基于给定表格或文档撰写含数值的分析，
  适用于需要跨章节保持指标、期间、单位与来源一致的任务。
---

# 基于证据的数据分析

## 适用范围
用户提供了分析材料，需要输出可追溯的数值分析或报告。

## 执行流程
1. 明确对象、指标定义、统计期间、单位和数据版本。
2. 为需要引用的事实建立记录，保留可重新读取的原始位置。
3. 可计算内容使用程序计算，记录计算输入、逻辑和结果。
4. 每个章节加载该章节需要的事实，不凭模糊聊天记忆补数字。
5. 输出前核对正文与事实记录的绑定关系。

## 验收要求
重要数值能定位到事实记录；事实记录能定位到来源与口径。
没有将不同对象、期间或版本的同名指标混用。
尚未核实的问题已明确保留，不伪装成确定结果。

## 退出与异常
来源缺失、权限不足、口径冲突未解决时，停止给出确定性数值结论。
数据版本变化后，重新检查依赖该数据的计算与结论。

## 长任务恢复
先读取任务状态和产物索引，再加载当前步骤依赖的事实。
摘要用于导航，不作为精确数值的唯一依据。

## 权限边界
本技能不授予新权限，不替代人工批准，也不自行提交外部业务操作。
````

这里的模板只是表达契约。真正运行时仍需要文件访问、事实记录、程序执行和输出验证等能力。一个 Markdown 文件不能单独保证这些要求被满足。

## 12.4 一次任务的运行顺序

```text
接收任务
→ 读取当前任务状态与必要约束
→ 选择适用的已发布技能版本
→ 加载相关经验，检查范围与冲突
→ 重新取得任务所需的当前证据
→ 执行并记录观察、动作与产物
→ 检查任务是否真的完成
→ 更新任务状态
→ 将值得学习的经历送入候选提炼链路
```

主执行与候选学习可以分开安排。是否异步执行取决于基础设施，但不应为了即时新增技能而明显挤占本次任务的完成预算。这是对 SkillsBench Creator／Solver 干扰现象的工程回应。〔[SB](#src-sb)，附录 D.6.1，p.23〕

## 12.5 发布、权限与副作用属于运行时责任

经验可能包含错误指令，候选脚本可能存在危险行为。建议把候选运行放在受限环境，正式版本经批准发布；工具权限、网络范围和敏感写入确认由运行时控制。

外部文档或历史轨迹中出现“以后跳过校验”，不能因为被检索出来就升级为系统规则。它首先是待解释的来源内容，而不是自动具有执行权威。

对于会写数据库、发消息或提交变更的技能，应记录是否尚未执行、部分完成或已完成。失败后重试应基于执行状态恢复，而非默认整段重跑。程序封装了更多动作后，这个问题只会更重要。

# 13. 两个完整工程案例：把记忆、技能与验证接入工作链路

## 13.1 案例一：代码审查 Agent 怎样从人工纠正中积累能力？

### 先看 OpenHands 的实际闭环

OpenHands 文章不仅介绍编写技能，还记录每次审查，在 PR 合并后读取人类回复和最终代码差异，统计哪些可执行建议被采用，并分析多余建议和遗漏。随后把当前技能与多次运行的分析交给模型，寻找重复问题，再修改技能并继续观察。〔[OH](#src-oh)，Monitoring and Improving Skills〕

文章展示的两种问题很有代表性：建议忽略仓库已有习惯；发现严重缺陷却仍给通过结论。前者需要补上下文一致性检查，后者需要修改发现与最终结论的对应条件。文中的约 15%、约 10% 是其分析示例中的频率表述，不应被当作所有代码审查系统的普遍统计。〔[OH](#src-oh)，Aggregating Feedback for Skill Improvement〕

这说明更新技能应针对具体失败模式，而不是不断追加“请认真检查”。

### 再构造一个贯穿全课的教学案例

假设 Agent 提出“这个函数缺少异常处理”，人工指出调用方的统一入口已经处理，因此拒绝该建议。

**第一步，保留经历。** 保存本次检查的文件、调用链证据、Agent 的建议、人工纠正和代码版本。只保存“建议被拒绝”不足以支持学习。

**第二步，形成条件性经验。** 使用 ReasoningBank 式提炼：准备声称异常处理缺失时，先检查调用方与统一处理入口；未取得必要文件时不能宣称已经确认缺失。它暂时是候选，不是全项目强制规则。

**第三步，识别重复结构。** 如果这类判断反复出现，可以用 AWM 式流程表示：定位异常来源、查调用路径、查统一入口、判断仍未覆盖的路径、形成证据和建议。

**第四步，程序化稳定部分。** 仓库搜索、收集引用、运行测试等可形成辅助程序；是否处理充分仍可能需要模型解释。采用 ASI 的验证思想，测试应确保新检查确实读取了相关位置，不能只看最终文本出现“已检查调用方”。

**第五步，更新技能并做配对评测。** 用包含“其他层已经处理”和“确实未处理”的任务分别测试，防止新规则造成反向错误。按 SkillsBench 的思路比较修改前后，而不是只展示一个纠正后的成功例子。

**第六步，支持长任务恢复。** 检查过程跨越多个文件或上下文压缩时，用 MemGPT 式工作集思想保留当前状态，同时能重新读取原始代码与工具结果，而不是把旧摘要当成代码事实。

上述六步是本文的组合方案。各材料分别提供了其中的方法，但没有哪篇论文直接验证了这整套代码审查系统。

### 人工采纳与正确性，必须分开统计

OpenHands 把建议是否被人类采用作为反馈信号，有实际价值，但不等于独立正确性证明。正确建议可能因时间、范围或其他约束未被采纳；错误建议也可能被接受。

**工程建议：** 同时记录建议是否正确、是否重要、是否采纳以及是否有关键遗漏。只优化采纳率，可能让系统倾向于提出容易接受的小建议，而回避复杂但必要的问题。

## 13.2 案例二：长篇数据报告，怎样避免后半段把数字与期间混在一起？

### 问题不是只有“记忆容量不够”

假设同一个产品同时有近六个月和近一年收益，Agent 前半段能区分，后半段经历多次摘要后，把数字与期间错配。即使数值本身还留在摘要中，它与对象、份额、期间、单位、口径和版本的绑定已经减弱。

这个场景是工程教学案例，不是论文中的实验结果。解决方案也不应只是在 Prompt 里重复“不要算错”。

### 分别管理事实、进度、方法与教训

| 对象 | 在报告任务中保存什么 |
|---|---|
| 事实记录 | 原始值及对象、期间、单位、口径、版本、来源位置 |
| 任务状态 | 哪些章节完成，使用哪些事实，哪些问题尚未核实 |
| Skill | 怎样读取、计算、引用、核对与恢复任务 |
| 经验记忆 | 曾经因何种条件发生期间混用，应增加哪种检查 |

例如，下表数值全部是假设值，只用于演示标识绑定：

| fact_id | 对象 | 指标 | 期间 | 展示值 |
|---|---|---|---|---:|
| fact-001 | 示例产品 A／同一份额 | 区间收益 | 近六个月 | 8.00% |
| fact-002 | 示例产品 A／同一份额 | 区间收益 | 近一年 | 12.00% |

正文不能只引用“8%”，而应在生成与核对过程中关联 `fact-001`。即使文章最终不展示内部标识，系统也应保留这条关联。

完整事实键不应只有指标名，可以由以下维度共同组成：

```text
对象 + 类别/份额 + 指标定义 + 起止期间 + 单位 + 数据版本
```

来源还应保留原文件、工作表／段落／单元格等位置。对于计算结果，另存输入事实、计算逻辑和结果，而不是只记录最终数值。

### 完整执行链路

```text
确认任务口径
→ 读取并规范化原始数据
→ 建立事实记录与来源绑定
→ 用程序完成需要的计算
→ 按章节加载相关事实
→ 生成章节并保存引用关联
→ 保存进度与未确认问题
→ 压缩或中断后，从状态和事实记录恢复
→ 输出前核对数值、期间、单位与来源
```

MemGPT 的启发是“摘要之外保留可重新取回的原始信息”；AWM 的启发是把重复核对过程抽成方法；ASI 的启发是把可验证计算与一致性检查交给程序；ReasoningBank 的启发是保存“什么条件下容易错配”的教训；SkillsBench 的启发是用无技能、人工技能、诱导技能等配对条件验证效果。〔[MG](#src-mg)，§2–3；[AWM](#src-awm)，§2；[ASI](#src-asi)，§2.3；[RB](#src-rb)，§3；[SB](#src-sb)，§4〕

### 什么时候必须重新取证？

**工程建议：** 当前结论没有对应事实、存在同名指标的多个候选、数据版本变化、来源位置失效或恢复状态不足时，重新读取来源；不能把模型对旧内容的自信当成证据。

检索到一条历史数值，与验证当前报告应使用该数值，是不同动作。记忆可以帮助定位来源，却不能替代当前任务所需的数据有效性检查。

### 验证不能只看“报告读起来顺不顺”

测试集应该包含同名不同期间、不同单位、不同份额、来源更新、上下文压缩后恢复，以及缺少数据等情况。验证应检查具体绑定关系，不能只用另一个模型打一个总体写作分数。

这类事实保真能力，既是记忆问题，也是数据建模、工具设计和执行约束问题。扩大上下文可能有帮助，但不替代这些机制。

## 13.3 对审核类 Agent 的补充边界

前述方法也可迁移到材料审核，但要分清历史经验与正式依据。

历史案例可以提示“这类表达容易漏掉某项检查”，却不能因为某次建议被采纳，就自动形成普遍有效的新规则。经验更新可以改善检索、检查顺序与例外提示；正式判断依据的变更则应有明确来源、版本和责任流程。

这是工程治理建议，不是本文对具体法规的解释。它与讲义关于规范性、高风险判断需要明确人类责任的分工一致。〔[L04](#src-l04)，p.45〕

<a id="chapter-14"></a>
# 14. 评测与实施路线：证明能力增长，而不是文件增长

## 14.1 三层正确性必须分别建立证据

| 层次 | 核心问题 | 典型错误 |
|---|---|---|
| 经历层 | 原任务真的成功了吗？失败解释可靠吗？ | 模型自评正确，但实际遗漏要求 |
| 技能层 | 提炼后的流程或程序真的有效吗？ | 原任务成功，提炼程序却写死参数或漏了步骤 |
| 复用层 | 对未参与提炼的后续任务有净帮助吗？ | 原任务重放通过，新环境却被错误套用 |

AWM、ReasoningBank 的判断器主要服务经历筛选或经验提炼；ASI 加入技能执行检查；SkillsBench 的配对设计与讲义的延迟复用价值，则提醒我们继续验证后续效果。〔[AWM](#src-awm)，§2.3；[ASI](#src-asi)，§2.3；[RB](#src-rb)，§3.2；[SB](#src-sb)，§4；[L04](#src-l04)，p.43〕

这三层不是一个测试通过标记能够替代的。

## 14.2 用对照组分离内容质量与路由质量

下面是一组工程评测设计，不是要求所有项目同时实施全部实验：

| 对照组 | 主要回答的问题 |
|---|---|
| 无任务技能与经验增强 | 原始系统能做到什么程度？ |
| 人工指定适用技能 | 技能内容本身能否帮助当前模型？ |
| 系统自动选择技能 | 发现、路由和加载损失了多少效果？ |
| 原始经历作为参考 | 直接复用轨迹的价值与噪声是什么？ |
| 自动提炼的文本流程 | 抽象是否比原始经历更有效？ |
| 验证后的程序技能 | 程序化与验证能提供多少额外价值？ |
| 长度相近的普通参考资料 | 增益是否只是来自额外上下文？ |

尽可能固定模型版本、工具、数据、任务预算、容器和提示配置。内容与执行接口一起变化时，应明确承认不能把全部差异归因于单一因素。这遵循 SkillsBench 的配对思路，也回应其关于更强对照的局限性说明。〔[SB](#src-sb)，§4、§6.1〕

### 从整个技能包的收益，进一步测量单项贡献

ASSAY 对开发集重复运行随机技能子集，让每个技能以固定概率独立被包含，然后比较某技能“出现”与“不出现”时任务的平均结果。对技能 $s_j$ 和开发任务 $d_i$，其估计量可以写为：

$$
C_{j,i}=\operatorname{mean}(y_i\mid s_j\text{ 被包含})
       -\operatorname{mean}(y_i\mid s_j\text{ 未被包含}).
$$

原论文用此构建“技能 × 开发任务”的贡献矩阵，再驱动 §10.6 的离线整理和按任务屏蔽。其随机化解释是：在给定模型、任务与其他技能随机共现的分布下，估计包含该技能的平均边际作用。这比“模型说这条技能有帮助”多了一层实验依据，但没有消除有限样本误差，也没有为所有技能组合提供独立正确性保证。〔[ASSAY](#src-assay)，§2.1，pp.3–4〕

论文使用 15 个开发任务、12 个随机掩码，即每个模型 180 次 Agent rollout，并按模型重新计算归因。成本之外还要注意两层外推：对新任务的贡献是由相似开发任务预测的；拆分后的新文本也不能仅凭旧条目的分数就视为已被独立验证。开发集验收与回退机制限制了部分风险，不证明未见任务上的性能必然不下降。〔[ASSAY](#src-assay)，§2–3.1，pp.3–7；末两句为对估计与验证范围的分析〕

**工程建议：** 同时报告分任务类型的正负效果、开发集覆盖与测量预算；做受保护模板、整理、屏蔽等组件消融。若始终只看总分，就可能删除对少数重要任务有用的技能，或保留总体均值接近零但局部有害的规则。

## 14.3 冻结评测与持续学习评测，回答不同问题

**冻结记忆评测：** 先固定技能库与记忆快照，再在未参与提炼的任务上测试。它测已经积累的内容能否泛化。

**持续学习评测：** 任务按顺序到达，只允许使用此前经历，再观察累计或分阶段表现。它测更新机制是否帮助后续任务。讲义与 AWM、ReasoningBank 都明确采用了顺序到达的设定。〔[L04](#src-l04)，p.24；[AWM](#src-awm)，§2.3；[RB](#src-rb)，§3.1〕

工程上还应改变任务顺序重复试验，检查早期错误经验是否长期影响后续结果。任务模板、实体与环境的切分方式也应记录；只替换一个商品名，不能代表已经通过跨流程泛化。

允许主动探索的网站评测还应单列探索预算；PolySkill 在新网站学习实现，与冻结旧技能直接迁移并非同一协议。对于 SAGE，则应记录如何配对训练任务、如何检索测试技能，以及是否使用了场景标签。训练策略改进、适配过程收益和冻结制品泛化，回答的是不同问题。〔[SW](#src-sw)，§2–3；[POLY](#src-poly)，§3.3–3.4；[SAGE](#src-sage)，§4.4，pp.8–9〕

## 14.4 测试“不该使用”的能力

负面迁移测试应包含：语义相似但接口版本不同；目标相似但需要的覆盖范围不同；正常流程遇到例外；历史经验与当前权威依据冲突；现有技能成本明显超出任务预算。

一个技能除了在适用任务上有效，还应能在不适用任务上被忽略或退出。SkillsBench 的负面案例与 ASI 的排序迁移失败，都说明这种测试不可省略。〔[SB](#src-sb)，附录 F.3；[ASI](#src-asi)，§5〕

## 14.5 不只看一个总分

**任务质量：** 完成率、关键要求覆盖、数值与证据一致性、严重错误、未完成任务是否被正确识别。

**使用质量：** 应用是否恰当、是否实际调用资源、是否存在绕过技能的假通过、是否因为旧经验造成负面迁移。

**整体成本：** 模型决策次数、底层动作、token、执行时延、人工复审、经验提炼与验证的代价。

**长期状态：** 技能过时率、版本回退、重复或冲突项、错误经验扩散，以及在记忆库增长后的表现变化。

这些是工程指标建议。AWM 的覆盖率、功能重叠与使用率，ASI 的诱导与复用统计，ReasoningBank 的总成本分解，分别提供了部分对应观察。〔[AWM](#src-awm)，附录 A.3；[ASI](#src-asi)，附录 B.1；[RB](#src-rb)，附录 C.2〕

**调用率高只能证明技能被访问或使用，不能证明它对任务有帮助。**〔[SB](#src-sb)，§5.1.1，pp.6–7〕

而“使用”的记录也要查实现。HermesAgent 本地快照会将未被重复读取缓存拦截的成功 `skill_view` 计入 use，TroVE 按函数使用频次整理库，SAGE 另行统计使用技能后的任务成功率，ASSAY 则实验估计按任务的边际贡献。这些量依次涉及加载、调用、条件成功与对照收益，不能作为同一指标汇总。〔[H-ST](#src-hst)，`_skill_view_with_bump`；[TRO](#src-tro)，§3.3；[SAGE](#src-sage)，§4.3；[ASSAY](#src-assay)，§2.1〕

## 14.6 防止“自进化评测”变成答案泄漏

用于提炼的实例答案、评估脚本、目标文件中的直接解答，不应混进通用技能。技能可以说明算法和检查方法，但不能直接记住测试实例的正确输出。

Creator 与 Solver 的隔离不只涉及聊天上下文，也涉及文件系统与环境状态。SkillsBench 的自生成审查发现，状态残留可以让看似复用的成功实际来自泄漏。〔[SB](#src-sb)，附录 D.6.1、M.7，pp.23、38〕

ASI 删除旧答案尾部的测试设计，也是在防止同类虚假成功。二者从不同位置提醒：**验证过程必须检查结果的来源，而不只是检查结果文本。**〔[ASI](#src-asi)，§2.3，p.4〕

AgeMem 在早期信息积累后重置短期上下文，是另一种让后续成功依赖所测记忆路径的设计；ASSAY 将归因开发集与测试集分开，避免按测试表现直接筛技能。工程上应进一步记录信息何时可见、何时允许写入、哪些标签只供评估器使用，不能把“用了持久记忆”自动视为没有泄漏。〔[AgeMem](#src-agemem)，§3.1–3.3；[ASSAY](#src-assay)，§2、§3.1〕

## 14.7 适合小团队的实施顺序

| 阶段 | 先建立什么 | 进入下一阶段前要回答什么 |
|---|---|---|
| 人工技能基线 | 一个高频、边界清楚的技能，固定测试集 | 比原系统有帮助吗？在哪些任务上退步？ |
| 状态与证据 | 可恢复任务状态、可回读事实、运行日志 | 中断后是否仍能继续且不混用来源？ |
| 离线经验提炼 | 从真实轨迹产生候选经验或程序 | 候选是否经过验证，是否存在实例泄漏？ |
| 受控发布与维护 | 版本、负责人、灰度、回退、依赖检查 | 更新能否解释、复现和撤销？ |
| 有限在线适应 | 对可验证、低副作用任务自动更新部分记忆 | 长期收益是否稳定，错误能否及时阻断？ |

这是一条工程路线，不是论文承诺的实施周期。它的重点是先学会区分有效更新与无效更新，再扩大自动化范围，而不是一开始就建设庞大的自动技能生成平台。

# 15. 全课总结：Agent 的能力积累是一条证据链

把讲义、readings 与 references 合在一起，可以得到三个层次的认识。

**第一层，信息必须可管理。** MemGPT 让有限上下文成为可调度的工作集，Mem0 展示事实提取与更新。原始记录、抽象事实与当前工作集职责不同；有效存储仍依赖正确检索、冲突处理、继续执行与停止。

**第二层，经历必须被恰当地加工。** 从 Reflexion 的反思、ExpeL 的示例与 insights，到 AWM 的工作流、ASI 的程序和 ReasoningBank 的策略，经验加工有不同粒度。Voyager 与 SkillWeaver 还主动选择练习；程序库学习解释共享结构如何形成，PolySkill 则分开接口与环境实现。不同表示保留不同信息，不存在脱离任务与环境的唯一最优表示。

**第三层，更新必须接受后续检验。** SkillsBench 提供配对测量思想，ASI 检查新技能执行，OpenHands 用运行与人工反馈定位失败；TroVE 整理工具库，ASSAY 区分全局保留与按任务使用；SAGE 和 AgeMem 进一步训练技能复用与记忆管理策略。保存价值需要由未来使用结果支持，训练策略也不能免除制品本身的验证。

这三层对应 lecture-04 的主线：表示、提炼、生命周期。references 提供了各环节的不同实现与实验边界，具体依据见上述章节，不应把这些研究拼成一个已经整体完成验证的系统。〔[L04](#src-l04)，pp.2、25、43–45〕

对于 LLM 开发工程师，最重要的不是“会装技能、会接向量库”，而是能够回答：什么应该原样保留，什么值得抽象；什么可以交给程序，什么需要实时判断；哪些经验已被验证，哪些仍是待检验的解释。

> **任务完成产生经历；经历经过提炼形成候选；候选经过验证成为可用方法；方法在后续任务中的表现，决定它是否值得继续存在。**

建立这条链路，才是在积累能力，而不是积累文件。

## B.2 自生成技能的负面案例也要保留作者限定

SkillsBench 附录 D.6.1 的轨迹审查选取了条件差异明显的案例，不是对所有任务的随机代表性样本。作者还提示部分验证器后来有改动、部分创建过程或工具输出不在公开轨迹中。因此，本文只用它说明可能的失败机制，不把个别案例频率或因果解释推广到所有自生成系统。〔[SB](#src-sb)，附录 D.6.1，p.23〕

尤其是单位解释案例，原文提及后续验证器接受了另一种解释；它不能在忽略该说明的情况下，被包装成没有任何歧义的“模型必然算错”的证据。

## B.3 常见过度推断

“研究中检索一个经历最优”不等于所有 RAG 的 top-k 必须为 1；“1–3 个技能组收益较大”不等于系统总共只能安装三个技能；“程序经过执行验证”不等于形式化证明；“随机判断噪声下有收益”不等于系统性判断偏差无害。

“在线跨环境适应有效”不等于冻结技能零样本迁移同样有效；“任务被人类采纳”不等于结果正确；“底层权重没有修改”不等于没有学习成本；“记忆条目描述在变得高级”也不等于实现已经具备复杂的条目更新与合并算法。

“函数接口相同”不等于不同网站实现具有相同前提；“程序输出多数一致”不等于答案正确；“随机屏蔽估计的平均贡献”不等于任意技能组合中的固定贡献；“逐步 GRPO 更新”不等于每个记忆动作都获得独立贡献标签；“读取被计为 use”不等于资源已执行。对应机制分别见 PolySkill、TroVE、ASSAY、AgeMem 和 HermesAgent 小节。

这些限制分别来自正文讨论的实验条件与本文的推论边界，不应在对外介绍时被省略。

| AutoDoc | LILO 为新抽象生成可理解名称与文档的步骤 |
| Causal Masking | ASSAY 根据随机屏蔽得到的开发任务贡献，预测并屏蔽当前任务中可能有害的技能 |
| Sequential Rollout | SAGE 让相关任务顺序执行并共享技能库的训练采样方式 |
| LTM / STM | AgeMem 中的持久长期记忆／当前输入上下文，二者由同一策略协调 |
| TGC / SGC（SAGE） | 单任务目标完成／场景目标完成；后者要求同场景三个测试任务全部成功 |
