## 一、贯穿全课的问题：为什么各自正确，合起来却失败？

### 1.1 同样是 Flappy Bird，两份材料为什么给出不同启示？

MetaGPT 第 2 页 Figure 1 用开发 Flappy Bird 展示团队式软件工作流：从需求文档、系统设计、任务分配，推进到实现和验收。图中最重要的不是出现五个角色，而是每个阶段都有面向后续工作的交付物。[^mg-sop]

Cognition 也使用 Flappy Bird，但描述的是一种失败拆分：一个 Agent 做背景、管道和碰撞区域，另一个 Agent 做可移动的小鸟，最后再合并。它们可能误解整体产品，也可能在理解同一初始任务后，仍各自选择了不兼容的视觉风格和行为。[^co-principles]

两者并不是在相同模型、相同任务集、相同预算下进行的对照实验，因此不能用它们判断哪篇“证伪”了哪篇。

**综合解读：MetaGPT 关注如何在执行前减少不确定性；Cognition 追问执行中不断产生的新决定如何持续保持一致。**

例如，在“背景”和“小鸟”分工之前，可能需要确定坐标系统、速度单位、碰撞接口和美术风格。这些是两个子任务共同依赖的决定。如果它们没有被明确表达，局部成果即使各自可运行，也可能无法组成一个一致的游戏。

因此，这节课的核心不是“怎样同时运行几个 LLM”，而是：

> **怎样让分散的执行始终服务于同一个目标、同一组约束，以及一套可验证的完成标准？**

### 1.2 讲义中的“局部完成，整体失败”

讲义第 25 页给出一个极简反例：三个章节分别完成，但整份报告自相矛盾。这个例子说明，检查各个子任务的完成状态，不能替代检查整体结果。[^lec-failures]

假设三个研究 Agent 分别得到：公司收入增长、公司利润下降、公司现金流改善。这些事实可以同时成立。真正的整体任务可能是解释变化原因与持续性，而不是把三个句子按顺序拼接。

**worker 的责任是局部交付，协调机制的责任是让局部交付在整体目标下成立。** 主管、共享工作区、任务依赖、验证器和人工节点，都可以承担这项责任的一部分；不一定要由一个“超级主管 LLM”包办。

### 1.3 学习这组材料时，反复追问四件事

对每一种机制，都应问：它解决了什么具体失败？依赖什么条件？实验改变了哪些变量？增加的质量或效率是否覆盖额外成本？

这四个问题会帮助我们区分：反馈回路的收益、流程规范的收益、独立上下文的收益、更多计算的收益，以及真正来自多智能体协调的收益。

## 二、基本模型：Agent、协调、通信与三张图

### 2.1 Agent 数量，不等于模型数量，也不等于模型调用次数

Scaling 论文将 Agent 系统写为：

$$
\mathcal{S}=(A,E,C,\Omega)
$$

其中 $A$ 是 Agent 集合，$E$ 是环境，$C$ 是通信拓扑，$\Omega$ 是协调策略。每个 Agent 有推理机制、动作空间、内部记忆和从观察历史选择下一步行动的决策函数。[^sc-definition]

通俗地说，Agent 是“模型能力、当前上下文、可用动作、反馈循环”的组合。同一个基础模型可以驱动多个具有独立上下文和任务的 Agent；一个 Agent 多次调用模型或工具，则不必构成多智能体。

但这不是所有论文唯一采用的定义。AutoGen 的 `ConversableAgent` 可以由 LLM、工具、人类或它们的组合驱动。其典型双 Agent 系统可能是“一个生成代码的 LLM + 一个工具／人类代理”，并非两个独立推理的 LLM。[^ag-definition]

所以，比较论文前先统一分析口径：**有几个独立决策循环，各自掌握什么信息，谁可以改变任务方向？** 不能只数对象实例或角色名字。

### 2.2 Coordination 与 Communication 的区别

Scaling 论文区分：**communication** 是信息传递；**coordination** 是对活动的战略组织，例如拆分任务、监控进展、安排下一步。集中式系统中两者较容易区分，去中心化讨论中两者可能同时发生。[^sc-definition]

“给另一个 Agent 发了一条消息”只说明建立了通信。只有当这条消息推动任务分配、约束同步、反馈处理或结果整合时，它才在协调中发挥作用。

同理，消息能送达、JSON 能解析，只能说明通信链路和格式没有出错，不代表消息中的事实正确，也不代表接收者采取了正确行动。

### 2.3 讲义为什么要求分别画三张图？

讲义第 7 页区分控制图、任务图和通信图。[^lec-graphs]

| 图 | 回答的问题 | 一个研究任务中的例子 |
|---|---|---|
| Control graph | 谁决定分工、重规划、交接和结束？ | 主管批准追加研究；人工决定是否发布 |
| Task graph | 工作如何分解，哪些任务依赖哪些输入？ | 三家公司可分别研究，比较分析依赖必要结果 |
| Communication graph | 哪些信息可以在谁之间流动？ | worker 回报摘要，完整证据进入共享产物存储 |

一个系统可以同时拥有星形控制结构、DAG 式任务依赖和共享文件式通信。这并不矛盾，因为三张图回答不同问题。

**综合解读：不要用一张“组织架构图”掩盖依赖、权限和信息流。** “主管—研究员—审核员”三个方框，尚未说明何时能开始、产物放在哪里、谁能覆盖结果、出现缺口怎样返回。

### 2.4 四个拆分理由，以及四种伴随成本

讲义第 6 页给出 specialization、isolation、parallelism、context management。[^lec-why]

| 理由 | 希望得到的收益 | 同时引入的问题 |
|---|---|---|
| 专业化 | 不同目标、模型、工具形成分工 | 路由错误；角色名不等于真实专业能力 |
| 隔离 | 不同执行者拥有不同权限 | 交接与授权需要被执行系统约束 |
| 并行 | 独立工作同时推进 | 同步、慢分支、资源竞争和合并 |
| 上下文管理 | 每个执行者专注相关信息 | 局部背景不足、摘要损失、过期认知 |

**综合解读：拆分不是免费扩容，而是在“局部专注”与“全局一致”之间交换。** 这个交换是否值得，需要后续实验确认。

### 2.5 委派与交接不是一回事

讲义在控制图中提到 handoff，又在消息语义中列出 DELEGATE 和 HANDOFF。[^lec-graphs][^lec-message]

为了实现时避免责任模糊，可以采用以下解释：委派是“替我完成一部分，结果回来，我继续负责”；交接是“后续处理权转交给你”。这是工程语义设计，不是材料中完整规定的状态机。

如果运行时没有区分两者，可能出现两个执行者都认为自己负责最后答复，或者都认为最后一步由别人完成。

## 三、八种架构：复杂度被放在了哪里？

讲义第 8—18 页给出八类架构。下面保留其名称和主要权衡，同时用参考资料解释机制。架构类别是设计视角，不应被理解为现实系统只能选择其中一个。[^lec-architecture]

| 架构 | 核心机制 | 适合的任务特征 | 主要代价 |
|---|---|---|---|
| Supervisor–worker | 主管规划、委派、整合 | 子任务可分离 | 主管吞吐和上下文瓶颈 |
| Hierarchical | 主管管理子主管，递归分解 | 本身具有层次结构 | 多层边界的上下文损失与错误放大 |
| Pipeline / DAG | 固定阶段与类型化交付契约 | 已知阶段、明确依赖 | 上游错误传播；纯前向流程难反馈 |
| Blackboard | 通过共享状态和产物协作 | 围绕共同工作区推进 | 过期状态、并发与版本冲突 |
| Committee / debate | 提议、讨论，再由裁决或投票合并 | 判断存在分歧 | 共同盲点、群体附和、讨论成本 |
| Market / auction | 根据能力、成本、时延投标 | 异构执行资源 | 自报能力不可信、分配规则复杂 |
| Swarm | 无固定主管，直接协商 | 局部协作与协商 | 冲突解决、终止和全互联通信成本 |
| Dynamic topology | 运行中新增、移除或重连 Agent | 事前结构未知 | 执行形态变化，故障难复现 |

### 3.1 Supervisor–worker：主管最重要的工作是整体验收

讲义指出，主管会重新阅读每个结果，因而上下文增长最快。Anthropic Research 采用此类结构，但主 Agent 不只是收集答案，还会判断是否需要更多研究。[^lec-architecture][^an-architecture]

主管应关注跨分支问题：对象和时间范围是否相同，输出是否可比，证据缺口是否影响最终回答。它不必重复每个 worker 的全部检索，否则很容易既支付并行工作成本，又支付一次完整串行复查成本。

**工程推演：将 worker 的交付分为短摘要、结构化记录和完整产物，主管按需下钻。** 这借鉴 Anthropic 的产物引用，但不保证自动解决所有上下文瓶颈。

### 3.2 Hierarchical：层级是递归管理，不是免费提升管理能力

层级结构适合本身可以分层的问题，例如功能负责人之下分别有后端和前端，再各自分配局部工作。讲义强调，关键难点是在哪一层分解，以及多少上下文穿过每个边界。[^lec-architecture]

**综合解读：每增加一个转述层，既可能减少上层需要处理的细节，也可能隐藏下层知道的重要条件。** 层级太浅时主管过载，层级太深时理解失真和责任追踪困难。

不要只按团队人数决定层级。更重要的是是否存在稳定的子问题边界和清楚的交付标准。

### 3.3 Pipeline / DAG：一条反馈边有时胜过一个新 Agent

讲义中的纯前向例子是发票处理：OCR、提取字段、匹配采购单、批准、入账。后面阶段如果发现输入质量不足，却没有返回路径，就无法要求上游补充资料。讲义以“one retry edge beats one more agent”强调这一点。[^lec-architecture]

AutoGen 的交互式检索正好提供实例：证据不足触发 `UPDATE CONTEXT`，而不是直接终止。真正增加的是反馈能力，不是角色数量。后文第 5 章展开其消融数据。[^ag-rag]

**概念说明：**这里的批评针对讲义展示的纯前向执行方式，不是说所有工作流系统都不能重试。严格的 DAG 不包含环；重试可以由运行时控制，返工也可以通过生成新任务实例表达。

### 3.4 Blackboard：共享存储不等于共享理解

讲义中的黑板可以是数据库、向量库、文件系统、Git 仓库或任务图。它使工作区可持久化、可检查，但引入一致性、并发、来源、版本和清理问题。[^lec-architecture]

MetaGPT 的消息池提供了一个具体实现思路：结构化发布、按角色订阅、依赖齐全后执行。需要注意，采用共享消息池并不意味着其整个工作流没有组织规则；MetaGPT 仍使用 SOP。[^mg-communication]

**工程推演：区分“权威任务状态”和“候选研究材料”。** 任务归属、已接受版本和完成状态需要明确更新规则；草稿、候选解释和搜索结果则可以保留多个版本。把两者都混在一个向量库里，不会自动获得一致性。

### 3.5 Committee / debate：增加的是判断机会，不保证增加独立信息

讲义认为此类机制可以用于判断密集任务，同时明确提醒“agreement without independence”。相同模型和相同上下文可能产生相同盲点。[^lec-architecture]

AutoGen 的 Safeguard、MetaGPT 的执行反馈和棋盘规则检查，展示了不同性质的验证。它们不能统称为“多模型投票”。是否要讨论、交叉检查或直接调用规则验证，要看错误类型。

关于独立投票与条件漏检率，第 9 章给出教学公式。

### 3.6 Market / auction：分配资源和共同推理不是同一种难题

讲义描述按能力、成本和时延投标。例如在时延约束下选择最低可行成本的计算节点，难点在于投标可能夸大能力。图中仍有清算分配的 auctioneer，因此“没有中心规划者”不等于“没有分配规则”。[^lec-architecture]

MetaGPT 附录讨论多 Agent 经济与服务购买，这是展望和初步平台设想，不应与主文软件开发实验的证据强度混同。[^mg-outlook]

**综合解读：**任务竞价解决“谁来做”的资源选择问题，未必解决“彼此结论如何一致”的语义问题。两种机制可以组合，但不能互相替代。

### 3.7 Swarm：没有固定主管，不代表没有协议和约束

讲义要求发现、寻址、同步、终止与信任协议，并对全互联通信标注 $O(n^2)$。这个量级描述的是讲义的 all-to-all 拓扑，不能推广成所有多智能体通信都必然平方增长。[^lec-architecture]

星形、树形和稀疏依赖图会有不同通信结构。去掉中心节点，可能移除一个瓶颈，却把责任分配和冲突裁决转移到对等协商中。

### 3.8 Dynamic topology：动态能力需要动态任务记录

动态拓扑允许任务升级时再加入专门执行者，避免简单任务承担完整团队的成本。讲义指出每次运行形态不同，故障也更难复现。[^lec-architecture]

Anthropic 的主 Agent 根据研究缺口追加分支，是相关实践。其早期系统也曾对简单查询创建 50 个子 Agent，说明“能够创建”必须与“应该创建”分开。[^an-delegation]

### 3.9 真实系统是组合，不是选一个框架标签

讲义第 17 页将主管、规划者、动态任务 DAG、编码／研究／测试分支、共享 Git 和 Reviewer 放在一起，并允许重新规划。[^lec-architecture]

因此，一个合理的设计描述可以是：**集中管理目标、按依赖并行执行、以产物交接、在必要位置设置核验和返工。** 这比单说“我们用了层级多 Agent”更能解释系统如何工作。

## 四、任务分解：先设计边界与合并，再分配角色

### 4.1 六种分解维度

讲义第 20 页列出数据、专业能力、阶段、假设、工具和权限域六种方式，也允许组合，例如先按 PR 文件分片，再按安全和性能角度检查。[^lec-decomposition]

| 维度 | 具体含义 | 教学例子 |
|---|---|---|
| Data | 处理不同对象或记录 | 分别调查不同公司或不同文档 |
| Expertise | 从不同专业角度处理同一对象 | 正确性、安全、性能审查 |
| Stage | 按过程环节分工 | 需求、设计、实现、测试 |
| Hypothesis | 调查不同候选解释 | 利润变化来自价格、销量还是成本 |
| Tool | 按数据入口或执行能力分工 | 搜索、数据库、代码执行 |
| Authority | 按管理域与权限分工 | 读取、修改、批准、发布 |

但某个步骤“可以命名”，不等于值得成为独立 Agent。一个简单数据库查询可能更适合作为工具；一个会根据证据多轮调整查询与核验方式的研究过程，才可能需要独立行动循环。

### 4.2 拆分边界必须考虑共享假设

按文件、公司或章节分工，只描述表面边界。真正的依赖可能隐藏在共同指标、接口约定、时间范围和未说出的假设中。

**工程判断：如果 A 在执行中新获得信息，B 是否经常需要推翻已完成的工作？** 若答案经常是“是”，两者就不适合不受管理地独立决策。可以仍然并行，但应明确共同决策点与变更通知。

这连接了讲义的 hidden dependency、MetaGPT 的系统设计，以及 Cognition 的隐含决策警告；它是综合判断，不是原文给出的量化判定公式。[^lec-failures][^mg-sop][^co-principles]

### 4.3 子任务是一份交付契约，不是一句话

讲义第 21 页的八个要素是：目标，输入与相关上下文，范围与排除项，工具与权限，输出结构，完成测试，预算与截止时间，依赖。[^lec-decomposition]

下面是教学契约，不是某个框架 API，预算数字也不是通用建议值：

```yaml
task_id: research-company-A
objective: 解释公司 A 在指定两个报告期内的经营变化
inputs:
  global_spec_ref: specs/comparison/v3
  company_id: A
  document_snapshot: snapshot-7
scope:
  include: [收入, 营业成本, 利润变化原因, 原文证据]
  exclude: [股价预测, 投资评级]
tools: [search_documents, read_document, calculate]
permissions:
  read: [documents/A/]
  write: [artifacts/research-company-A/]
output_schema: CompanyAnalysis/v1
acceptance:
  - 每个数字包含报告期、计量单位、计算口径和原文定位
  - 区分原文事实与分析推断
  - 缺失信息必须显式说明，不得猜测
budget:
  max_tool_calls: 12
  max_runtime_seconds: 180
dependencies: [global-spec-v3-confirmed]
```

目标说明“要做什么”；范围、权限和依赖说明“在哪些条件下做”；输出与验收说明“做到什么才算完成”。三者缺一不可。

Anthropic 早期的“研究半导体短缺”任务产生年份错位和重复搜索，正说明短指令没有建立这种责任边界。[^an-delegation]

### 4.4 先定义合并规则，才能判断拆分是否成立

如果三家公司分别使用年度、季度和滚动数据，即使局部分析很深入，也未必能直接比较。相同 JSON 结构同样无法修复不同统计口径。

**工程推演：先固定实体标识、时间范围、数据截止点、单位和指标定义，再分配局部工作。** 允许局部执行者提出口径变更，但不能让它们静默修改共同定义。

这对应讲义的 unmergeable outputs 和 lost global context。这里“无法合并”不仅包括格式冲突，也包括语义不兼容；后者是对讲义例子的工程扩展。[^lec-failures]

### 4.5 粒度：什么时候并行真的更快？

讲义给出近似时间分解：

$$
T_{\text{multi}}\approx T_{\text{planning}}+T_{\text{critical path}}+T_{\text{communication}}+T_{\text{merge}}
$$

并行节省的串行时间，必须超过规划、通信与整合成本。[^lec-granularity]

**教学例子：**四个独立任务各需 60 秒，串行 240 秒；并行执行 60 秒，加上 45 秒协调和合并，共 105 秒，有收益。若每个任务只需 2 秒，串行仅 8 秒，同样开销下并行反而约 47 秒。

关键路径是依赖链中决定总完成时间的路径，不总是某一个最慢函数。Agent 并行也不能消除必须等待前置观察的步骤。

### 4.6 静态、动态、递归和机会式分配

静态拆分在执行前确定；动态拆分响应新发现；递归拆分允许 worker 继续委派；机会式分配让空闲执行者领取新就绪任务。讲义明确要求创建数量、预算、深度和终止条件。[^lec-dynamic]

**工程推演：模型提出追加工作，运行时审批资源。** 它可以说“还缺一份原始资料”，但是否启动新分支，要检查重复任务、并发、总预算和剩余时间。

达成目标与预算耗尽是两个不同终止原因。系统应当如实保留这种区别，不能因为停止了就宣称完成。

### 4.7 六类失败直接变成测试分类

| 讲义中的失败 | 典型表现 | 工程防范方向 |
|---|---|---|
| Overlap | 多个 Agent 做相同搜索或分析 | 显式范围、任务去重、已探索记录 |
| Gap | 所有子任务合起来仍遗漏需求 | 需求覆盖表、必需证据清单 |
| Hidden dependency | 执行中才发现依赖其他结果 | 依赖显式化，必要时重规划 |
| Unmergeable outputs | 结构、单位或口径不兼容 | 统一契约、接收时检查 |
| Lost global context | 局部合理，整体自相矛盾 | 共同约束、跨结果核验 |
| Straggler | 慢分支阻塞整体 | 截止时间、必需／可选结果策略 |

左列来自讲义，右列是工程推演。慢分支可能正在处理最重要的缺口，因此不能为了降低时延无条件丢弃。[^lec-failures]

## 五、AutoGen：把交互和反馈变成程序

### 5.1 论文真正提出的两个核心抽象

AutoGen 第 2 节的重点是 **Conversable Agents** 和 **Conversation Programming**。前者提供可接收、处理和回复消息的执行单元；后者用这些单元之间的交互来表达计算与控制。[^ag-definition][^ag-programming]

这不是只给同一个模型贴上“产品经理”“工程师”等标签。一个 Agent 的能力、内部上下文、工具执行和人工介入方式，都可以分别配置。

其典型接口包括 `send`、`receive` 和 `generate_reply`。接到消息后，回复过程可以调用 LLM、执行工具、请求人类输入，也可以先和另一个 Agent 交互再回来答复。这些是论文版本中的抽象，不是当前 SDK 的调用教程。

### 5.2 Computation 与 Control Flow

**Computation** 指收到消息之后做什么，例如推理、检索或运行 Python。**Control Flow** 指这些计算何时发生、先后顺序是什么、满足什么条件才继续或终止。AutoGen 把二者组织在对话机制中。[^ag-programming]

```text
用户提出任务
    ↓
Assistant 生成代码
    ↓
Executor 运行代码
    ├── 失败：返回错误信息 → Assistant 修改 → 再执行
    └── 成功：返回运行结果 → Assistant 解释 → 结束
```

这段文字流程是对论文交互模式的简化。真正的收益在于反馈能够改变后续行动，不需要人类每次复制日志、重新提问。

一个回复循环如果只不断确认“收到”“继续”，仍然没有完成有用协调。可编程接口只是基础，任务进展还需要恰当的反馈、执行和终止逻辑。

### 5.3 自然语言控制和程序控制是混合的

论文区分三种方式：自然语言指导模型失败后修正、完成后输出终止信号；程序规定最大回复次数、人工输入方式和工具执行；模型通过函数调用在两者之间转移控制。[^ag-programming]

这与讲义“自然语言承载内容、结构化协议承载协调”的要求可以连接起来：模型判断可能需要继续研究，程序判断是否还有资源、依赖是否就绪、操作是否获得权限。[^lec-message]

**工程推演：`TERMINATE` 只能作为结束声明，不应直接等同于业务验收。** 如果必需文件没有生成、证据尚未齐全，就应保留未完成状态。模型结束生成与系统接受结果是两个边界。

### 5.4 六个应用展示的不是同一种收益

| AutoGen 应用 | 关键机制 | 学习时应辨别的收益来源 |
|---|---|---|
| A1 Math Problem Solving | 助手、工具和可选人类交互 | 工具执行、反馈与人工参与 |
| A2 Retrieval-augmented Chat | 证据不足触发再次检索 | 反馈边与检索策略 |
| A3 ALFWorld | 在重复失败时提供 grounding 信息 | 特定错误模式的修正 |
| A4 OptiGuide | Commander、Writer、Safeguard | 职责分离、执行闭环、减少人工搬运 |
| A5 Dynamic Group Chat | Manager 动态选择发言者并广播 | 调度与参与时机 |
| A6 Conversational Chess | 棋盘代理依据规则检查动作 | 外部约束与执行前验证 |

这六个应用来自论文第 3 节。不能把所有表现改善都统一归因于“有更多独立推理 Agent”。[^ag-applications]

### 5.5 交互式 RAG：反馈回路比 Agent 数量更容易解释

A2 在检索上下文不含答案时，让 Assistant 返回 `UPDATE CONTEXT`，从而触发额外检索。其消融条件改为直接回答不知道，而不是继续更新上下文。[^ag-rag]

| Natural Questions 指标 | 无交互式检索 | 有交互式检索 | 绝对变化 |
|---|---:|---:|---:|
| F1 | 22.79 | 25.88 | +3.09 |
| Recall | 62.59 | 66.65 | +4.06 |

数值来自 Figure 4b，按图中的百分制显示。这里没有通过增加角色数量构造对照，因而更直接支持“证据不足时继续检索有帮助”。[^ag-rag]

**与其他材料的连接：**讲义中的“回退边”给出设计原则；AutoGen 给出可实现机制与消融；Anthropic 则把局部动态检索扩展成多个并行研究循环。它们形成的是一条机制演进线，而不是三个相互独立的产品介绍。

### 5.6 Dynamic Group Chat：多 Agent 不自动等于并行

GroupChatManager 重复三步：选择一个发言者，要求其回应，把消息广播给其他参与者。因此，这种群聊可以是“动态选择下一位执行者”的串行过程。[^ag-group]

论文用 12 个手工构造任务进行小规模实验，GPT-4 条件下结果为：

| 方案 | 完成任务数 | 平均 LLM 调用次数 | 终止失败数 |
|---|---:|---:|---:|
| 双 Agent | 9 / 12 | 6.8 | 3 |
| 群聊，角色式发言选择 | 11 / 12 | 4.5 | 0 |
| 同样群聊成员，任务式发言选择提示 | 8 / 12 | 4.0 | 0 |

数据来自附录 D 的 Table 5–6。相同成员改变发言选择，就产生不同结果，说明参与时机与调度策略是独立的设计变量；但 12 个任务不能支持广泛性能保证。[^ag-group]

### 5.7 OptiGuide：主管管理交互，Writer 同时写代码和解释结果

OptiGuide 中，用户提出一个“改变约束会怎样”的问题。Commander 把任务交给 Writer，Writer 产生代码；Safeguard 检查代码；通过后 Commander 执行；Writer 解释执行日志；最后 Commander 返回答案。检查失败或执行异常会反馈给 Writer。[^ag-optiguide]

这里有两个容易忽略的细节。

**第一，Commander 管理用户交互相关记忆。** 这不是“所有角色都平等保存全部上下文”，而是让用户意图有明确的维护位置。

**第二，论文将 Coder 和 Interpreter 合并为 Writer。** 同一个执行者写代码并理解执行输出，复用相关上下文。多智能体框架本身也可以通过合并角色减少交接，而非只会拆分。[^ag-optiguide]

论文报告核心工作流代码从超过 430 行减至约 100 行；人工时间比较的一个实验是单名熟悉 Python 和 Gurobi 的专家处理 10 个问题，两种系统均答对 8 个，AutoGen 方案减少了当时手工转移和执行代码的负担。另一个涉及 2,000 个问题、五类应用的分析统计用户输入次数。它们分别是实现简化和人工交互指标，不是今天各产品能力的比较，也不能单独证明模型推理更强。[^ag-optiguide]

### 5.8 从 AutoGen 应该带走什么？

**综合解读：**把 Agent 看作可组合的交互单元；把反馈边当作第一等结构；让职责与权限可以分离；把调度策略、终止条件和人工介入明确表达。

但“对话可编程”仍然没有回答交付物是否完整、任务是否可合并、重要条件是否在交接时丢失。这是 MetaGPT 与 Cognition 接下来补充的问题。

## 六、MetaGPT：从聊天协作走向交付物协作

### 6.1 SOP 不是装饰，而是中间结果的生产规范

MetaGPT 主张把标准操作流程编码进提示序列，以缓解简单串联 LLM 引发的逻辑不一致和级联幻觉。角色不仅有名字，还有目标、约束、上下文和工具配置。[^mg-sop]

| 角色 | 主要输入 | 主要交付物 | 为下游减少的不确定性 |
|---|---|---|---|
| Product Manager | 用户要求 | PRD、User Stories、Requirement Pool | 到底要做什么 |
| Architect | PRD | File Lists、Data Structures、Interface Definitions | 各部分怎样连接 |
| Project Manager | 需求与设计 | 任务分配 | 谁实现哪些内容 |
| Engineer | 任务及系统设计 | 代码与修复 | 如何具体实现 |
| QA Engineer | 需求和实现 | 测试用例、质量检查 | 实现是否满足要求 |

上述流程和术语来自第 3.1 节与 Figure 1–3。其主文流程强调按 SOP 顺序推进，不应被描绘为所有角色自由并行讨论。[^mg-sop]

**综合解读：SOP 把一部分原本需要临时协商的内容，提前变成公共约定。** 下游不必反复猜测需求和接口。角色带来的价值，常常通过这些中间约束体现，而不是通过职位名称本身体现。

### 6.2 Figure 2 的左右两半，分别解决不同问题

左半图是通信协议：共享消息池，结构化发布，按角色订阅。右半图是工程师内部的迭代编程：编写代码，运行，检查错误，结合需求、设计和历史结果调试。[^mg-communication][^mg-feedback]

这两部分形成两种闭环：**跨角色交付闭环**与**局部执行反馈闭环**。只有通信而没有运行检查，仍可能传递错误代码；只有局部测试而没有共同设计，不同模块又可能无法组合。

### 6.3 文档协作与自由对话的区别

MetaGPT 让 Agent 通过文档、图表和接口规范交付关键内容，而不是依赖没有约束的多轮闲聊。论文以传话游戏说明自然语言在多层转述中的失真风险。[^mg-communication]

它并不是禁止自然语言。PRD 和设计说明仍可能包含大量自然语言。重点在于**交付物有确定的结构、职责和用途**，下游知道哪些内容是自己需要依赖的。

例如，工程师需要系统接口定义，而不是通过阅读十轮产品讨论去猜最终版本。这个机制可与讲义的 typed contract、artifact passing 和 blackboard 联系起来。

### 6.4 发布—订阅表达的是“信息依赖”

消息池使 Agent 能直接取得所需交付物，订阅机制避免无差别接收全部信息；论文说明，只有获得全部前置依赖后才激活动作。[^mg-communication]

和 AutoGen 群聊对照：广播倾向于保持共同对话背景，但可能增加无关上下文；订阅减少输入，却需要正确描述谁依赖什么。

**综合解读：广播的主要风险是过载，订阅的主要风险是漏掉真实依赖。** 没有一种通道能替代依赖设计。

### 6.5 可执行反馈，而不仅是“另一个 LLM 觉得没问题”

MetaGPT 早期审查仍会遗漏错误，所以加入执行反馈：工程师生成代码后编写、运行测试，根据结果继续调试，直到通过或达到最多三次重试。[^mg-feedback]

| 代码生成指标 | 无执行反馈 | 有执行反馈 | 提升 |
|---|---:|---:|---:|
| HumanEval Pass@1 | 81.7% | 85.9% | +4.2 个百分点 |
| MBPP Pass@1 | 82.3% | 87.7% | +5.4 个百分点 |

这些是 Figure 4 与第 4.4 节的实验结果，不是所有代码任务的可靠性保证。[^mg-experiments]

在 SoftwareDev 中，代价与收益更接近工程上的实际取舍：

| 指标 | ChatDev | MetaGPT 无反馈 | MetaGPT 有反馈 |
|---|---:|---:|---:|
| Executability，1–4 分 | 2.25 | 3.67 | 3.75 |
| Running time，秒 | 762 | 503 | 541 |
| Token usage | 19,292 | 24,613 | 31,255 |
| Total code lines | 77.5 | 194.6 | 251.4 |
| Human revision cost | 2.5 | 2.25 | 0.83 |

数据按 Table 1 的列分别列出。原文正文叙述中提到 503 秒，而表中它对应无反馈条件，有反馈条件是 541 秒；这里显式保留这种条件区分，不把 503 秒笼统当成所有 MetaGPT 配置的耗时。[^mg-experiments]

Human revision cost 是作者定义的人工修改次数指标，不是工时。代码行数也不等于业务价值。更稳妥的解读是：在这些任务上，额外执行与修复成本换来了更少人工返工。

### 6.6 角色消融：支持“补齐流程有帮助”，不等于支持“人越多越好”

Table 3 中，只有 Engineer 的配置可执行性评分为 1.0，人工修改次数为 10；加入 Product、Architect、Project 后的四 Agent 配置分别为 4.0 和 2.5。[^mg-roles]

但正文说明这组角色消融只用了两个任务。增加角色的同时，交付阶段、费用、输出量也改变了。因此，它不能排除“一个执行相同 SOP、拥有相近预算的单 Agent”获得类似收益。

另外，SoftwareDev 总集包含 70 个任务，主比较选取七个代表任务；附录还提供其他实验。不能把某张表的结果表述为对所有 70 个任务、所有模型和生产仓库都成立。[^mg-experiments][^mg-roles]

### 6.7 回到 Flappy Bird：SOP 能缓解冲突，但不能穷尽隐含决定

MetaGPT 的需求和系统设计阶段，可以承载视觉风格、接口、坐标等跨子任务约束。这是根据其结构作出的工程推论，并非材料直接证明它解决了 Cognition 描述的所有失败。

设计文档仍可能遗漏条件；执行中也会出现事前未知的新信息。因此：

> **SOP 可以减少隐含决策，不能保证所有决策都已经显式化。**

这正是下一章需要进一步处理的问题。

## 七、上下文与共同决策：连接 Cognition、MetaGPT 和 Anthropic

### 7.1 Cognition 的两个原则要分别理解

Cognition 在 2025-06-12 的文章中提出：共享相关上下文与完整执行轨迹，而不只是孤立消息；行动包含隐含决策，冲突的决策会造成坏结果。[^co-principles]

第一个原则针对**已有信息在交接中丢失**。第二个针对**并行执行中新产生的信息和决定彼此不可见**。

初始任务传错了，可以通过补充背景改善；执行中新作出的决定互相冲突，则需要持续同步或明确共同决策权。把用户原始问题复制给全部 worker，不能单独解决第二类问题。

### 7.2 隐含决策比“谁改了哪个文件”更难追踪

**教学例子：**两个开发分支都读过接口设计。后端在执行中发现某字段必须允许空值，于是更改处理；前端仍按不可为空校验。两者都读过初始上下文，却不再基于相同条件工作。

类似问题也会出现在研究报告中：一个分支决定使用累计期间数据，另一个沿用单季度；一个将企业披露当成事实，另一个要求外部验证。冲突未必表现为相同文件被覆盖，而可能表现为最终结论无法比较。

**综合解读：协调需要管理共享假设的变化，不只是消息和文件的流动。**

### 7.3 为什么 Cognition 更偏好连续执行链？

文章认为，最简单的方式是保持单线程线性 Agent，让每一步看到此前相关决定；对于很长任务，再通过压缩保留关键细节、事件和决策。作者同时强调做好这种压缩很难，并提到在其场景中考虑或使用专门的小模型。[^co-context]

这是一篇带有明确工程立场的文章，不是严格对照实验。其关于 Claude Code 子 Agent 和 Edit Apply Models 的描述限定于文章所述时期，不能照搬成当前产品规则。

Edit Apply Models 案例很有启发性：大模型用文字描述修改，小模型再实际改文件，轻微歧义就可能造成错误。作者讨论把修改决策和应用合并的好处。[^co-applications]

与 AutoGen 将 Coder、Interpreter 合并为 Writer 的设计相连接，可以得到一个工程启发：**强共享上下文的连续过程可以合并；需要独立视角、独立权限或独立资料范围的工作再拆分。** 这不是一条已被普遍验证的定律。

### 7.4 Anthropic 为什么反而强调独立上下文？

Anthropic 的研究型任务常常有多个可独立调查方向。每个子 Agent 在自己的上下文中迭代搜索，再提炼重要内容给主 Agent，可以处理超过单个上下文能够直接容纳的信息。[^an-benefits]

在这种场景中，worker 的主要贡献是新增证据和调查覆盖，而不一定是同时修改一个强耦合的共同系统。文章也承认，要求共享大量上下文、存在许多相互依赖的任务，不容易从这种设计获益。

因此，不能把 Anthropic 与 Cognition 的文章硬解释为同一主张。它们对上下文完整性与并行探索的重视程度不同，任务和系统也不同。

### 7.5 条件性的综合：探索可以分散，共同决定需要维护

下面是综合两篇文章与 MetaGPT 机制后的设计判断：

| 工作性质 | 可以考虑的安排 | 需要付出的代价 |
|---|---|---|
| 只读、对象可分片的调查 | 独立上下文、并行探索 | 统一对象、时间范围与输出口径 |
| 连续修改同一系统 | 明确共同设计与整合入口 | 决策同步、版本检查、冲突处理 |
| 需要不同检查依据的验证 | 职责隔离、外部证据 | 验证开销、误拒与漏检 |
| 局部过程共享大量细节 | 放在同一行动循环内 | 单点上下文与时延压力 |

这些是条件性建议，不是原文共同证明的统一最优架构。

### 7.6 “保存完整轨迹”与“每次输入完整轨迹”不同

令 worker 的完整历史为 $h_i$，交给主管的摘要为 $m_i=f(h_i)$。这个记号只是教学表达：摘要通常选择性保留信息，主管无法从被删除的信息中自动恢复关键条件。

如果每个接收者都读全部原始历史，可能造成上下文过载；如果只读很短摘要，又可能失去证据与限制条件。MetaGPT 的订阅和 Anthropic 的产物引用，分别提供了限制无关输入和保留原始交付物的思路。[^mg-communication][^an-artifacts]

**工程推演：将保留策略与输入策略分开。** 必要轨迹和原始产物持久化；当前上下文按任务构造；共同约束主动传递；具体证据按引用下钻。这里的轨迹指系统可取得的输入、输出、工具调用和决策摘要，并不假定能够取得模型不可见的内部推理。

### 7.7 摘要最危险的损失，可能是条件而不是数字

**教学例子：**原文说“订单恢复主要来自一次性补库存，持续性仍待观察”；worker 写成“订单恢复”；主管再写成“行业需求持续复苏”。没有任何数字抄错，结论却逐步越界。

因此，交付中应保留：哪些是事实，哪些是推断，推断成立的条件，什么反例尚未排除，以及哪些更强结论没有证据支持。

建议采用三层交付：简短摘要用于导航；结构化记录保存事实、口径、条件与缺口；原始产物保存可复核内容。这一分层是工程推演，不是三篇材料统一规定的格式。

### 7.8 结构正确与事实正确是两道门

JSON 解析成功说明语法可处理；Schema 检查通过说明字段和类型符合约定。它们都不能保证引用真的支持结论。

相反，一个事实正确的结果也可能因为缺少单位、版本或时间范围而无法安全合并。协调系统需要同时检查**可消费性**和**内容有效性**，不能用其中一个替代另一个。

## 八、Anthropic Research：动态研究、预算和两层并行

### 8.1 两个层次的反馈循环

文章的完整研究流程是：LeadResearcher 分析用户问题、形成策略并保存计划；创建子 Agent 并行调查；每个子 Agent 根据工具结果继续评估与调整；主管综合后决定是否补查；足够后进入报告与引用定位流程。[^an-architecture]

```text
用户问题
   ↓
LeadResearcher：理解目标、规划、保存计划
   ↓
创建多个有明确范围的研究分支
   ↓
每个分支：搜索 → 读证据 → 识别缺口 → 调整搜索
   ↓
返回发现与交付物
   ↓
主管：检查覆盖、分歧和剩余问题
   ├── 需要补查：创建或调整任务 → 继续研究
   └── 达到条件：形成报告 → CitationAgent 定位引用
```

**局部自主性**决定怎样调查一个问题；**全局自主性**决定整个任务还缺什么、资源投向哪里。这比一次性分成三份再拼接答案更复杂。

### 8.2 八条提示工程原则在协调系统中的位置

| 原文原则 | 对应问题 | 具体启示 |
|---|---|---|
| Think like your agents | 为什么提示与实际行为不同 | 用实际提示和工具观察执行轨迹 |
| Teach the orchestrator how to delegate | 任务重叠、遗漏和误解 | 给出目标、格式、来源、工具、范围 |
| Scale effort to query complexity | 简单问题过度投入 | 用启发式分配分支数和调用预算 |
| Tool design and selection are critical | 用错入口和能力 | 工具职责明确，数据源与任务匹配 |
| Let agents improve themselves | 工具说明和提示缺陷 | 通过受控测试与反馈提出改进 |
| Start wide, then narrow down | 过早锁定错误线索 | 先了解候选信息，再缩小查询 |
| Guide the thinking process | 工具结果没有改变策略 | 引导检查结果质量、缺口与下一步 |
| Parallel tool calling transforms speed and performance | 不必要的串行等待 | 区分 Agent 并行和工具并行 |

这是对文章八条原则的中文整理，并非八个独立 Agent 的建议。[^an-delegation][^an-tools]

### 8.3 委派质量：边界必须覆盖时间与来源

文章描述，早期“研究半导体短缺”的简短指令导致不同年份混淆，多个 worker 还进行了重复调查。改进不是简单让指令更长，而是让局部工作承担清晰的整体责任。[^an-delegation]

主管需要明确每个分支为何存在：补充哪个对象、哪个维度、哪种候选解释，还是验证某个关键判断。没有这个目的，即使每个 worker 都认真检索，也可能只是昂贵的重复劳动。

### 8.4 资源启发式是经验，不是统一最佳 Agent 数量

原文的经验规则包括：简单事实查询用一个 Agent、3–10 次工具调用；直接比较可能需要 2–4 个子 Agent、每个 10–15 次调用；复杂研究可能使用超过 10 个分工明确的子 Agent。原文也描述过简单问题创建 50 个子 Agent、持续寻找不存在来源等失败。[^an-delegation]

这些数字属于当时系统的经验。不能把它们当成所有模型、任务和预算下的最优参数，也不能据此推导“复杂研究至少十个 Agent”。

**教学预算例子：**总预算 24,000 token，预留 4,000 给规划、通信和整合，剩余 20,000。四个 worker 平均各 5,000，八个平均各 2,500。在固定预算下，增加 Agent 主要是重新切分能力，而不是凭空扩大能力。

这个预算等式只是解释资源取舍，不是 Anthropic 原文的实际配额。

### 8.5 Agent 并行与工具并行分别解决什么？

文章引入两层并行：主管同时启动约 3–5 个子 Agent，子 Agent 内部再并行调用多个工具，报告复杂查询研究时间最多减少约 90%。[^an-parallel]

如果问题慢在独立工具调用串行，可能只需要同一个 Agent 发起并行工具调用；如果问题包含多条各自需要持续自适应的调查路径，才可能从多个 Agent 循环中获得额外收益。

因此，评测多智能体时应该包含“单 Agent + 工具并行”这个对照，避免把全部加速归因于分散决策。

### 8.6 五个常被混用的数字

| 原文数字 | 实际衡量什么 | 不应怎样理解 |
|---|---|---|
| +90.2% | 特定主／子模型组合相对单模型在内部研究评测上的提升 | 不是准确率 90.2%，不是普遍增加 90.2 个百分点 |
| 最多约 −90% | 两层并行后的复杂查询时间缩短 | 不是所有请求的平均加速 |
| 约 4× | 单 Agent 相对聊天的 token 使用 | 不是多 Agent 相对单 Agent |
| 约 15× | 多 Agent 相对聊天的 token 使用 | 不是多 Agent 一定比单 Agent 贵十五倍 |
| 约 80%／95% | token 使用量／再加工具调用和模型选择，对分析中表现方差的解释比例 | 不是增加预算必然导致相同幅度质量提升 |

质量对比使用 Opus 4 主管与 Sonnet 4 子 Agent，对照单 Opus 4，属于文章内部研究评测。方差解释是统计关联，不等于因果保证。[^an-benefits][^an-parallel]

### 8.7 工具描述是协调入口的一部分

文章提醒，在只有内部系统才存在的信息上使用网页搜索，路径一开始就错了。工具名称相近、说明模糊，也会让 Agent 选择错误能力。它们通过工具测试 Agent 反复使用并改写说明，报告某项改进使后续完成时间下降约 40%。[^an-tools]

这说明系统改进对象可以是能力接口，而不只是模型提示和角色数量。但该数字对应文章中的具体改进，不能作为“自动改写工具说明普遍提速 40%”的承诺。

### 8.8 长任务记忆与外部产物

文章建议阶段性总结并将关键内容存到外部记忆；接近上下文限制时可以借助新的上下文和明确交接继续工作。对于代码、报告和图表等产物，可以直接写入文件或外部系统，让主管接收轻量引用，减少传话失真和重复 token。[^an-artifacts]

保存计划防止全局意图丢失；保存产物防止交付内容在转述中丢失。两者解决不同问题，不能只保留其中之一。

### 8.9 产品收益背后的生产条件

原文还强调小样本尽早评测、LLM Judge 与人工测试结合、失败恢复、定期 checkpoint、生产追踪和不中断旧任务的部署。它描述的主管按批等待子 Agent，异步执行则被视为有潜在收益、但增加状态一致性和错误传播复杂度的方向。[^an-eval][^an-production]

这些细节使文章不是一个简单的“主管—worker”架构示意，而是一份关于如何持续调试和运营研究系统的经验记录。第 11 章把它们与讲义的分布式系统问题合并讨论。

## 九、验证与整合：共识不等于证据，完成声明不等于验收

### 9.1 不同验证机制的权威来自哪里？

把 AutoGen 的几个应用与 MetaGPT 放在一起，会发现“审核 Agent”这个词过于粗糙。它们提供的检查依据并不相同。

| 机制 | 检查或反馈依据 | 能帮助发现什么 | 仍然存在的边界 |
|---|---|---|---|
| Grounding Agent | 模型提供的常识与前置条件 | 卡在重复错误行动模式 | 常识反馈本身可能有误 |
| Safeguard | 模型对候选代码的安全判断 | 实验范围内的不安全代码 | 不是完整安全保证 |
| Chess Board | 明确游戏规则和棋盘状态 | 非法动作 | 只覆盖形式化规则范围 |
| Executable Feedback | 代码执行和测试结果 | 运行失败、测试不通过 | 测试不覆盖的错误仍可遗漏 |
| CitationAgent | 文档和报告中的引用位置 | 引用定位与归属 | 有引用不自动等于推断成立 |

前四项来自 AutoGen 和 MetaGPT，最后一项来自 Anthropic 的研究流程。表中“边界”是对这些机制作用范围的解释，不把某个检查器视为绝对正确。[^ag-grounding][^ag-optiguide][^ag-chess][^mg-feedback][^an-architecture]

### 9.2 Grounding Agent：在正确时机提供纠错信息

AutoGen 的 ALFWorld 系统最初由提出计划的助手和执行环境动作的执行器组成。有时它们反复违反基本条件，例如未拿取物体就尝试检查。新增 Grounding Agent 在重复错误的早期征兆出现时，提供“先找到并拿取物体”等提示。[^ag-grounding]

在 134 个未见任务的实验中，两 Agent 平均成功率约 54%，三 Agent 约 69%，即增加约 15 个百分点。Figure 4c 还展示 Best-of-3 数字，但它与单次平均表现不是同一个口径。[^ag-grounding]

这个结果支持的是**针对已观察到的失败模式，适时引入额外纠错信息可以有帮助**，不是让三个 Agent 投票批准原来的计划。

### 9.3 棋盘检查：约束应在执行边界实施

AutoGen Conversational Chess 使用棋盘代理依据规则检查动作，不合法则要求重新提交。去掉这个代理，只靠提示双方保证动作合法时，论文观察到非法动作导致游戏受损。[^ag-chess]

**工程解读：可以程序化检查的前置条件，应落实在执行边界。** “你是只读 Agent”不是权限控制；“请遵循规则”不是规则验证。模型承诺与实际能力限制属于不同防线。

### 9.4 Safeguard：职责隔离有证据，但证据有边界

OptiGuide 的 Writer 写代码、Safeguard 检查、Commander 执行。论文在 100 个包含等量安全／不安全任务的实验中比较单 Agent 与分离设计；Figure 4d 中 GPT-4 的不安全代码识别 F1 从 88% 提升到 96%。[^ag-optiguide]

这是 8 个百分点变化。它说明该实验中的独立检查职责有帮助，不意味着上线后没有越权、数据泄露或其他未覆盖风险。运行时权限、工具范围和必要的人类授权仍需独立设计。

### 9.5 为什么三个 Agent 一致，也可能没有更可信？

下面是**数学教学例子**，不是某篇材料的实验模型。

若三个判断者对二元问题的正确率都为 $p$，且错误相互独立，多数投票正确率为：

$$
P_{\text{vote}}=p^3+3p^2(1-p)
$$

当 $p=0.7$，结果为 $0.784$。但如果三者总在同一批题目上犯完全相同的错误，多数投票正确率仍为 $0.7$。

这个例子解释讲义“相同模型、相同上下文、相同盲点”的警告。它不是说任何同模型实例的错误都完全相关，也不是说换一个模型就自动独立。[^lec-architecture]

**工程推演：关注检查依据是否不同，而不只关注角色名字是否不同。** 一个分支核查原始材料，一个重新计算数字，一个查找反例，可能比三个分支复述同一结论更有用；是否有效仍应消融验证。

### 9.6 生成器与审核器的正确率不能直接相乘

对于“错误候选被审核通过”这一条路径，概率分解为：

$$
P(\text{错误被放行})
=P(\text{候选错误})\cdot P(\text{审核通过}\mid\text{候选错误})
$$

这是概率规则的教学应用。关键是后面的条件概率：**第一个 Agent 已经出错时，第二个是否能识别这些特定错误？** 两个模型各自平均正确率较高，并不能说明这个条件漏检率一定低。

公式也没有覆盖审核者错误修改正确答案、最终整合阶段新引入错误等路径。因此，它只能说明一个局部风险，不能被当作整个系统的端到端可靠性公式。

### 9.7 整合不是摘要拼接，而是兼容性与证据检查

根据材料中的交付契约、反馈回路和上下文问题，可以设计下面的**工程整合流程**：

```text
对齐对象与时间范围
        ↓
检查结构、单位、定义和输入版本
        ↓
核查数字、来源与结论支持关系
        ↓
识别事实分歧、口径分歧与推断分歧
        ↓
只对受影响问题补查或返工
        ↓
生成统一表达，并保留未解决的不确定性
```

例如两个 worker 分别说盈利改善和盈利恶化，先检查它们是否使用净利润与经营现金流、年度与季度等不同口径。并不应首先让 Judge 随机或凭语言说服力选择一方。

**协调的目标不是快速消除不同意见，而是弄清哪些分歧可以被证据解决，哪些应作为不确定性保留。**

### 9.8 三种状态不能合并

模型已经生成文本、任务已经产生候选产物、系统已经接受产物，是三个不同状态。

对研究任务，接受条件可以包含结构检查、数值重算、原文定位检查、语义核验和必要人工复核。并非所有验收都能变成确定性代码，但能够确定性检查的部分不应让模型凭感觉决定。

这也是从“能够演示”走向“可恢复、可评估”的重要边界。

## 十、Scaling 论文：多智能体收益的条件、指标与实验边界

### 10.1 为什么需要这篇论文？

AutoGen、MetaGPT 和 Anthropic 展示了有价值的机制，但这些实验不都在隔离同一个变量。增加角色，可能同时增加流程、工具使用、测试和计算预算。更复杂的系统表现更好，不意味着协调结构本身是唯一原因。

Scaling 论文明确批评两类混杂：不同系统使用不同提示、工具或预算；只看最终正确率，不分析协调开销、信息流和错误传播。它试图通过受控配置研究条件性的架构收益。[^sc-introduction]

### 10.2 Agentic 任务与静态答题的差别

论文关注持续多步环境交互、部分可观察条件下的信息收集，以及根据反馈调整策略。它将这些任务与单次、无环境反馈的静态题目区分。[^sc-definition]

这里应保留原文边界：HumanEval 等静态题目上的提升，并不能自动证明长时仓库修改、网页操作或连续规划中的协调同样有效。给静态题目加入测试和反馈，可以形成一个更丰富的求解过程，但这不等于原始基准已经覆盖生产环境的全部动态特征。

### 10.3 实验设计：260 种配置，不是 260 个业务任务

上传 v3 研究六个基准、五类架构和三个模型家族。260 指模型—基准—架构等组合形成的配置，不是评测任务数量。[^sc-introduction]

| 基准 | 本次实验的主要任务性质 | 原文披露的实例数或子集 |
|---|---|---:|
| BrowseComp-Plus | 浏览与信息查找 | 100 |
| Finance Agent | 金融分析与多源资料研究 | 50 |
| PlanCraft | 交互式制作与顺序约束规划 | 100 |
| Workbench | 工作场景工具任务 | 100 |
| SWE-bench Verified | 仓库软件问题解决 | 20 个实例子集 |
| Terminal-Bench | 终端环境任务 | 20 个实例子集 |

实例数来自论文 Data Availability。不同基准的样本量和评分方法不同，不能把配置平均理解成大样本生产成功率。[^sc-limitations]

论文描述通过匹配最大总迭代等方式分配计算预算，并在相关分析中声明匹配总 reasoning-token 预算和工具访问。以下结果按论文原文条件报告；这些措辞不应被替换成“所有实际账单、输出 token 和用户等待时间都完全相等”。[^sc-method]

### 10.4 五类架构的操作定义，比名称更重要

| 架构 | 论文中的主要机制 | 解释结果时要注意 |
|---|---|---|
| SAS | 单一推理与行动循环 | 仍可使用工具和自我反思 |
| Independent | 独立探索后用 `synthesis_only` 汇集 | 不做交叉验证、多数投票或分析性比较 |
| Centralized | 主管组织和检查子 Agent 结果 | 同时改变控制和核验方式 |
| Decentralized | 同伴通信与若干讨论轮次 | 通信和协调交织 |
| Hybrid | 主管层次控制加有限同伴通信 | 两种机制的组合也有额外开销 |

这些定义来自第 3.1 节。尤其不能将 Independent 的结果扩展为“所有独立尝试加验证器的系统都会失败”。[^sc-architectures]

### 10.5 主要结果：收益高度依赖任务

| 基准与架构 | SAS 平均成功率 | 对应 MAS 成功率 | 相对变化 |
|---|---:|---:|---:|
| Finance Agent，Centralized | 34.9% | 63.1% | +80.8% |
| Finance Agent，Decentralized | 34.9% | 60.9% | +74.5% |
| BrowseComp-Plus，Decentralized | 31.8% | 34.7% | +9.2% |
| Workbench，Decentralized | 62.9% | 66.4% | +5.6% |
| PlanCraft，Centralized | 56.8% | 28.2% | −50.3% |
| PlanCraft，Independent | 56.8% | 17.0% | −70.0% |
| SWE-bench Verified，Hybrid | 52.2% | 51.1% | −2.1% |
| Terminal-Bench，Independent | 34.4% | 35.0% | +1.7% |

这是从原文第 4.2 节选取的代表结果，而不是所有架构的完整排名。小差异尤其需要结合置信区间和样本量理解。[^sc-results]

Finance Agent 的 34.9% 到 63.1%，绝对变化为 28.2 个百分点，相对变化约为：

$$
\frac{63.1-34.9}{34.9}\times100\%\approx80.8\%
$$

不要把“提升 80.8%”读成“增加 80.8 个百分点”。

### 10.6 轨迹分析：复杂任务不一定可分解

论文举例：某些 PlanCraft 任务只需要查配方、移动材料、制作。如果人为拆成配方研究员、库存检查员和制作执行者，就为很短的顺序任务制造了大量交接。[^sc-results]

Finance Agent 则可以让分支调查新闻、申报文件和经营影响，再综合不同信息流。论文认为这种自然分解与架构更匹配。

**综合解读：任务难度与任务可分解性是两个维度。** 一个任务可能非常难，但必须在一条连续状态链上推进；另一个任务单个部分不难，却因资料范围大而适合分片。

因此，不应通过“复杂”二字直接选择多 Agent。

### 10.7 要读交互项，而不只看 Agent 数量

原文回归模型包含模型能力、Agent 数量、工具数、单 Agent 基线，以及协调开销、效率、消息密度、冗余和错误传播等指标。它通过交互项表示某种影响依赖其他条件。[^sc-regression]

例如：

$$
P_{\mathrm{SA}}\times\log(1+n)
$$

表达增加 Agent 的影响可能随单 Agent 基线改变；另一个 $E_c\times T_{\mathrm{tools}}$ 表达效率与工具环境的关系。这里使用 $T_{\mathrm{tools}}$ 以避免和论文其他部分表示轮数的 $T$ 混淆。

这不是让读者直接把业务参数塞进几个系数，就能获得可靠预测。原文变量有变换和标准化，完整方程还有其他项；脱离这些处理使用原始数值相乘，会改变模型含义。

**学术上的核心认识：架构收益是一种条件关系，而不是“Agent 数量的单调函数”。**

### 10.8 指标必须逐一定义

| 指标 | 原文含义 | 不应混同的量 |
|---|---|---|
| Task success / accuracy | 基准定义下的成功或正确率 | 用户实际业务收益 |
| Turns | 推理—响应轮次 | 秒数、token、美元 |
| Coordination overhead | 相对 SAS 的轮数／工作开销指标，按原文定义使用 | 直接账单倍数 |
| Message density | 每推理轮次的 Agent 间消息数 | 每条消息的信息价值 |
| Redundancy | 原文以输出 embedding 相似度等指标衡量 | 对同一业务步骤重复执行的精确比例 |
| Coordination efficiency | 成功率除以相对轮数 | 端到端业务 ROI |
| Task-level error amplification | MAS 与 SAS 任务失败率比值 | 轨迹级错误放大 |
| Trace-level error amplification | 根据执行轨迹 token 分析估计的协调失败相关工作放大 | 最终错误概率倍数 |

原文不同段落对开销和冗余的解释侧重点并不完全相同。本稿保留其明确定义，不将相似度、重复任务比例、轮次和 token 互换；它们不能被视为同一单位。[^sc-metrics]

协调效率的定义为：

$$
E_c=\frac{S}{T_{\mathrm{turns}}/T_{\mathrm{SAS}}}
$$

其中 $S$ 是成功率，$T_{\mathrm{turns}}/T_{\mathrm{SAS}}$ 是相对轮数。这是一种归一化效率指标，不是每美元收益。[^sc-metrics]

### 10.9 17.2 倍与 4.4 倍为什么不是失败概率？

论文定义：

$$
E=1-P,\qquad A_e^{\mathrm{task}}=\frac{E_{\mathrm{MAS}}}{E_{\mathrm{SAS}}}
$$

另有从轨迹 token 分析估计的 $A_e^{\mathrm{trace}}$。表中的 17.2 和 4.4 对应后者。[^sc-errors]

按 Table 5 的平均成功率，Independent 为 0.370，SAS 为 0.466，则任务级失败率比值为：

$$
\frac{1-0.370}{1-0.466}=\frac{0.630}{0.534}\approx1.18
$$

这个计算只是为了分清口径，不是在重新估计原文的轨迹指标。

论文中带验证的结构更能限制某些错误传播，不代表“有主管就安全”。主管也可能误判，且不同任务的最终表现仍然不同。

### 10.10 约 45% 的基线阈值：经验模式，不是开关

原文报告单 Agent 较高基线下出现协调边际收益递减，并讨论约 45% 的阈值。这个值与所测试的模型、任务、预算、提示和拟合过程相关。[^sc-regression][^sc-limitations]

不能制定“业务准确率超过 45% 就禁止多 Agent”的规则。论文自身也有高基线条件下小幅收益的代表结果，说明不能抹去架构与任务差异。

更可迁移的工程问题是：**剩余错误是否能通过并行信息、职责分离或额外验证减少，还是主要来自所有 Agent 都有的模型能力限制？** 这是综合解读，仍需本地实验。

### 10.11 87%、R² 与统计修正分别意味着什么？

论文报告在留出配置中选择最优架构的准确率为 87%。它不等于对任意新业务有 87% 的成功把握。六基准交叉验证 $R^2$ 为 0.373，换用任务相关的 Agentic Capability Index 后为 0.413。[^sc-regression][^sc-limitations]

作者进行数据集聚类的稳健误差分析和多重比较校正后，将若干结果称为方向性模式，强调能力饱和是更稳健的发现。不同修正处理不同统计问题，不能只挑未经修正的显著系数进行推广。

这些结果说明架构、能力与任务特征之间存在可分析关系，也说明预测仍有大量未解释变化。它是一项有边界的经验研究，不是普遍适用的协调物理定律。

### 10.12 限制决定你能怎样迁移它

作者披露：只覆盖六个基准；两个代码／终端基准各用 20 个实例；没有为每个模型家族专门优化提示；异构组合探索有限；大规模团队探索也有限；跨领域绝对表现预测仍困难。[^sc-limitations]

其异构模型初步实验没有显示混合模型自动突破所述能力饱和现象，因此“多个不同模型必然互补”也没有从本材料获得普遍支持。

**最终方法论：把任务分解、通信结构和验证方式当作可测量设计变量；用受控实验检查收益来源，而不是先相信某种架构，再寻找成功例子。**

## 十一、生产运行时：让灵活策略在明确约束内执行

本章将讲义的分布式系统问题与 Anthropic 的生产经验连接。任务表、版本字段和状态机是**工程推演**，不是原文公开的完整实现，也不代表必须采用某个数据库或 Agent 框架。

### 11.1 分开模型策略与执行约束

讲义指出网络延迟、丢包、乱序、重复、时钟差异、并发、部分失败、复制状态一致性和可观测性问题；多 Agent 还增加不可预先确定的调度、资源和记忆需求。[^lec-runtime]

我会将职责安排为：模型提出任务计划、解释证据、建议补查；程序验证依赖、权限、预算和结构，并保存状态；语义验收可以组合模型与人类。

例如主管建议创建五个任务，运行时检查其是否重复、是否超过并发和预算；worker 声称完成，系统检查候选产物是否存在及是否通过验收。

这不是让程序替模型解决所有开放问题，而是让确定性约束不依赖模型记忆和承诺。

### 11.2 状态机要区分“有结果”和“接受结果”

一个教学用的内部状态流可以是：

```text
WAITING_DEPENDENCIES → READY → RUNNING → RESULT_READY → ACCEPTED
                                  ├── INPUT_REQUIRED
                                  ├── RETRYABLE_FAILURE
                                  ├── FAILED
                                  └── CANCELED
```

`RESULT_READY` 表示产生了候选产物，`ACCEPTED` 表示通过当前验收。输入不足、预算耗尽、执行失败和用户取消，应有可区分的原因。

这是自定义运行时示例，不是 A2A 标准状态枚举。任务进入候选结果状态后，验收失败可以创建修复任务或重新尝试，但应保留前一次结果与原因。

### 11.3 最小任务记录应该能够回答什么？

| 记录内容 | 要解决的问题 |
|---|---|
| task_id、parent_task_id | 当前工作属于哪个目标和分解路径 |
| owner、attempt_id | 当前由谁执行，这是哪次尝试 |
| input_versions、dependency_versions | 结果依赖什么版本的输入 |
| status、reason | 是完成、等待、失败还是取消 |
| budget_used、budget_remaining | 消耗多少，是否还能继续 |
| artifact_refs | 完整交付物在哪里 |
| acceptance_record | 为什么被接受或拒绝 |
| configuration_version | 使用哪版提示、工具结构和执行逻辑 |

字段本身不是保证。必须进一步规定谁有权更新、何时可以改变状态，以及重试和并发更新怎样检查版本。

这对应讲义的 provenance、versioning、checkpoint 与 lost ownership 问题。[^lec-runtime]

### 11.4 重试、重规划和从头开始必须分开

重试是再次执行相同操作；重规划是改变路径、工具或范围；从头开始是丢弃已有进展重新做整个任务。

Anthropic 强调长任务失败后重启成本很高，因此采用恢复执行、重试和定期 checkpoint，同时允许模型知道工具失败并调整策略。[^an-production]

**工程推演：错误分类应决定后续动作。** 网络暂时不可用可能适合重试；权限不足需要授权或换路径；数据不存在应返回明确缺口；口径冲突需要重新确认；证据不足通常需要补查，而不只是生成同一句话三次。

### 11.5 超时后，最危险的是“不知道动作是否已经发生”

讲义以购买 GPU 实例后超时说明：没有收到响应，不能推断对方没有执行。它讨论幂等、至少一次／至多一次、补偿和回滚。[^lec-runtime]

工程上要区分**逻辑操作**与**执行尝试**。同一次购买的再次尝试应复用逻辑幂等标识；同一任务里的两次不同购买不能因共用 `task_id` 被错误去重。

这是对讲义“任务幂等键”的实现细化，不是原文额外规定。外部效果是否幂等仍需要服务端支持、查询核对或补偿机制。本地状态里写“只执行一次”，并不自动带来外部 exactly-once。

**读失败通常可以重试；有外部副作用的写失败，先处理执行状态不明。** 不可逆操作尤其需要明确权限和人工节点。

### 11.6 版本比到达时间更能说明结果是否适用

**教学例子：**全局口径由 v3 更新到 v4，一个旧 worker 刚刚返回 v3 的结果。它到达得晚，不代表它适用于最新任务。

接收端应检查任务版本、输入版本和依赖版本；必要时把结果保留为历史产物，但拒绝将其并入当前结论。

类似地，取消后迟到的输出、重新派发后旧执行者的输出，都不能无条件覆盖当前状态。这是对讲义 stale information 的具体实现回应。[^lec-runtime]

### 11.7 同步屏障与异步执行的取舍

Anthropic 文章描述主管按批等待子 Agent 完成。这种方式简单，但可能被一个慢分支阻塞；改为异步可以提高并行性，也增加结果协调、状态一致性和错误传播难度。[^an-production]

不能把异步理解成只更换一个并发函数。异步运行时需要回答：哪些结果必须等，哪些允许部分完成；主管变更计划时旧任务怎么办；超时分支是否继续消耗预算；取消失败后怎样限制迟到副作用。

对小团队或初版系统，简单同步方案可能更容易验证。这里不是推荐固定架构，而是提醒应把运行时复杂度计入收益比较。

### 11.8 Checkpoint 不只是保存对话

为了恢复，系统需要知道哪些操作已成功、哪些结果已接受、哪些输入已经变化、剩余预算多少。仅保存一段聊天再让模型自行恢复这些状态，可能再次引入歧义。

**工程推演：同时保存任务状态、配置版本、关键共同决定和产物引用。** 原始工具结果可按权限和保留策略持久化，模型工作上下文则可以重新构造。

Anthropic 的阶段记忆与产物机制给出设计方向，但文章未公开完整持久化模式；上述字段划分属于实现建议。[^an-artifacts][^an-production]

### 11.9 部署版本也是长任务状态的一部分

Anthropic 使用 rainbow deployments，让旧版本运行中的任务继续完成，新流量逐步转入新版本。[^an-production]

**工程解读：提示词、工具结构与产物协议不能在运行中随意替换。** 某个任务已经基于旧格式形成结果，下游突然换新格式可能破坏交接。可以绑定运行配置版本；需要升级时，将迁移作为显式、可检查的操作，而非静默替换。

### 11.10 可观测性要沿任务与产物追踪

原文强调，只有看到生产执行轨迹，才能分清是查询不当、来源选择差、工具失败还是其他原因。[^an-production]

建议追踪任务父子关系、工具输入输出的适当记录、预算、产物、验收原因和配置版本。重点不是保存海量文字，而是能回答：资料没有找到，还是找到了却没传给下游？数字算错，还是口径错位？结果过期，还是模型判断错误？

敏感原文、用户数据和权限信息必须按访问范围与脱敏策略处理。可观测不等于所有人都能读取全部内容。

### 11.11 不要让运行时本身也全变成 Agent

任务持久化、状态更新、预算计数、文件保存、结构校验和权限检查，可以由普通程序承担。只有确实需要开放式语义判断和自适应探索的部分，才需要模型参与。

**综合解读：多智能体系统的可靠性，往往依赖一些刻意不做成 Agent 的组件。** 这不是对某种框架的否定，而是避免把可确定处理的问题也转化为不确定对话。

## 十二、A2A 与 MCP：连接协议和协调策略的边界

本章按上传讲义解释抽象，不声称覆盖当前协议的全部能力。具体字段、状态、扩展和兼容行为应按项目采用的规范版本核验。

### 12.1 A2A：围绕一个有生命周期的工作对象交互

讲义第 37—41 页描述：发现能力，发送消息并创建任务，接收进度，返回产物。Agent Card 表达身份、技能、接口、流式能力与认证要求。[^lec-a2a]

这里需要辨别“对方宣称会什么”与“对方经过评测能可靠完成什么”。Agent Card 的能力描述不是性能保证；身份和授权也不会自动解决任务质量问题。

### 12.2 Message、Task 和 Artifact

| 抽象 | 讲义中的含义 | 教学例子 |
|---|---|---|
| Message | 调用方与 Agent 的一次交互 | 提交研究要求、补充时间范围 |
| Task | 有 ID 与生命周期的工作单位 | 一次公司比较研究 |
| Artifact | 任务产生的交付物 | 报告、结构化结果、数据文件 |

一条后续消息可以继续同一个任务，而不是每次补充都创建完全无关的新工作。[^lec-a2a]

### 12.3 任务不是只能“成功／失败”

讲义展示 Submitted、Working、Input required、Auth required、Completed、Failed、Rejected、Canceled。需要输入或认证时可以暂停，满足条件后继续。[^lec-a2a]

缺少用户输入不是普通网络异常；等待授权也不应被标为完成。通过轮询、流式更新或推送可以跟踪任务，但它们只是不同状态交付方式。

讲义明确强调：**A2A 标准化通信，不标准化 orchestration；委派、拆分和停止仍由 harness 负责。**

### 12.4 MCP 与 A2A 的讲义对照

| 维度 | MCP | A2A |
|---|---|---|
| 主要抽象 | capability / tool | agent / task |
| 关系 | Agent 到能力服务 | Agent 到 Agent |
| 发现内容 | tools、resources、prompts | Agent 能力 |
| 讲义的工作单位示意 | 一次工具调用 | 有生命周期的任务 |
| 组合方式 | 为 Agent 提供能力 | 远程 Agent 内部还可以使用多个 MCP 服务 |

该表忠于讲义的对比框架。讲义用“一次工具调用”与“长任务”帮助理解主要边界，**不能把这张教学表当成所有版本中同步／异步能力的完整规范**。这里保留其抽象意义，不引入材料外的最新协议说明。[^lec-mcp]

“运行一次查询”更接近能力调用；“调查一个问题，必要时自己查询、计算和补查，再交付结果”更接近任务委派。这是用于理解的例子，并非禁止某种协议承载某类行为。

### 12.5 协议不会替你决定这些问题

即使服务发现、认证、任务提交和进度通知都接通了，仍需要回答：谁负责共同口径，何时追加任务，如何判断引用支持结论，谁有权接受或拒绝产物，预算耗尽怎样结束。

**连接可用只是协调的前提之一，不是协调正确的证明。**

<a id="ch13"></a>
## 十三、端到端工程推演：三家公司经营变化研究

> 本章是把前述机制应用到一个假设研究任务的设计练习，不是金融事实分析、投资建议，也不是论文已经评测过的系统。公司、任务 ID、路径和预算均为示例。

### 13.1 用户问题与完成标准

假设任务是：比较三家公司在指定两个报告期内的经营变化，区分有证据支持的持续改善与一次性因素，给出原文依据，并明确哪些判断仍不确定。

首先形成共享任务说明，而不是直接创建三个“行业专家”。说明至少包括对象、时间范围、资料截止点、指标口径、必答问题和验收条件。

这一步借鉴 MetaGPT 的需求与设计阶段，也回应 Cognition 的共同决策问题。没有它，三个 worker 可能各自认真研究股价、利润和现金流，却没有回答同一个问题。

### 13.2 最小组件，不必全部做成 Agent

| 组件 | 职责 | 是否必须使用 LLM |
|---|---|---|
| 协调者 | 理解目标、形成计划、判断缺口、综合结论 | 开放式语义判断适合使用 |
| 研究 worker | 围绕一个明确范围循环检索、读取、计算和核验 | 可使用 Agent 循环 |
| 任务与产物存储 | 保存版本、状态、预算、证据与交付物 | 普通程序和存储即可 |
| 验收入口 | 检查结构、数字、引用支持、整体一致性 | 程序、模型与人工组合 |

初版不必另外设置十几个 Planner、Critic、Reflector 和 Formatter。增加一个执行者前，先明确它处理哪类已观察到的失败，以及为什么现有流程不能更简单地修复。

### 13.3 三张图分别设计

**控制图：**协调者维护目标和分工，运行时审批资源和权限，验收入口决定候选产物是否可用，必要时由人工处理关键不确定性。

**任务图：**共享口径确认后，三家公司可以分别调查；比较分析依赖必需结果；补查仅重做受影响的子问题。

**通信图：**worker 返回短摘要和状态，完整结构化记录与原始产物写入共享存储；共同口径的变更通知所有受影响任务，不把全部搜索日志广播给所有人。

这对应讲义第 17 页的混合结构，但具体安排属于本章推演。

### 13.4 不按每次工具调用拆 Agent

一个公司 worker 内部可以连续完成搜索、读取、计算和证据核验。简单查询不必交给独立“数据库 Agent”，再把结果转回独立“计算 Agent”。

这借鉴 Anthropic 的局部研究循环，也呼应 AutoGen 合并 Writer 职责的做法：共享上下文很强的局部过程可以放在同一个循环里。

三家公司是否应该对应三个并行 worker，仍需用强单 Agent 基线比较。对象数量不是自动创建相同数量 Agent 的理由。

### 13.5 交付记录：保留条件、证据与未解决问题

可以采用以下教学格式：

```json
{
  "task_id": "company-A-analysis",
  "task_version": 3,
  "input_versions": {
    "global_spec": "v3",
    "document_set": "snapshot-7"
  },
  "status": "partial",
  "findings": [
    {
      "claim_id": "A-C01",
      "claim": "报告期利润改善，但持续性仍缺少充分证据",
      "claim_type": "inference",
      "basis": "指定报告期与统一指标口径",
      "evidence_refs": ["report-A:page-12:paragraph-3"],
      "counter_evidence_refs": ["report-A:page-28:note-5"],
      "unresolved": ["尚未取得可比口径说明"]
    }
  ],
  "artifact_ref": "artifacts/company-A/v2"
}
```

其中的结论只是格式示例，不代表真实公司情况。`partial` 防止“已经生成文字”被误当成“已经完整完成”。`input_versions` 使接收者知道它依据哪组资料；反向证据和未解决问题防止摘要逐层变得过度确定。

这分别借鉴 MetaGPT 的结构化交付、Anthropic 的产物引用、Cognition 对相关决定与条件的保留，以及讲义中的来源与版本问题。

### 13.6 消息外层表达控制，内层表达业务

以下消息示例和候选产物分开存储：

```json
{
  "message_id": "msg-381",
  "task_id": "company-A-analysis",
  "task_version": 3,
  "type": "REPORT",
  "from": "researcher-A",
  "to": "coordinator",
  "payload": {
    "status": "partial",
    "artifact_ref": "artifacts/company-A/v2",
    "missing": ["上一报告期的可比口径说明"],
    "requires_response": true
  }
}
```

运行时依据类型和字段路由，不需要先调用模型解释“这是报告还是取消请求”。业务含义仍需要内容验收；结构化不是事实保证。

### 13.7 从输入到交付的完整过程

```text
接收用户问题
    ↓
形成并确认共享任务说明
    ↓
规划候选任务 → 检查依赖、重叠、预算与权限
    ↓
执行就绪任务，每个 worker 保持局部查证循环
    ↓
保存候选产物 → 发出结构化 REPORT
    ↓
接收端检查版本、结构、数字与证据
    ↓
协调者检查跨公司可比性与需求覆盖
    ├── 存在关键缺口：只补查受影响问题
    ├── 预算耗尽：如实交付部分结果与缺口
    └── 满足标准：形成最终报告和来源定位
```

“口径确认”“结构校验”“数值重算”“版本检查”不必都调用 LLM。对开放式因果解释，可以使用模型帮助分析，但仍保留事实与推断的区分。

### 13.8 主管的主要职责是跨边界问题

主管不应简单再做三遍全部研究。它重点判断三家公司是否使用相同期间，数字是否可比，某个局部缺口是否破坏整体比较，以及是否需要探索另一种解释。

例如公司 A 缺少可比口径，通常先补查 A 的相关资料，不必把 B、C 所有任务重跑。这是 AutoGen 的反馈边、MetaGPT 的依赖契约和 Anthropic 的动态追加研究在同一系统中的组合。

### 13.9 结果写作发生在检查之后，但检查也可能触发再研究

先核对数字、原文位置和证据支持，再统一表达；发现问题时保留反馈路径，不把“进入写作阶段”当作不能返回的单向门。

引用定位也需要区分两件事：有没有一处可引用来源，来源是否支持当前结论。CitationAgent 的定位思路可以借鉴，但不应被当成推断正确性的自动保证。

### 13.10 为这个系统设计故障注入

| 注入场景 | 期望系统行为 | 对应材料问题 |
|---|---|---|
| 两个 worker 收到重叠范围 | 识别重复或避免重复执行 | Overlap |
| 删除一个必需报告期的资料 | 返回缺口，不编造 | Gap、证据不足 |
| 一个计算依赖未就绪口径 | 等待或重新规划 | Hidden dependency |
| 一个结果使用错误单位 | 接收时拒绝合并 | Unmergeable outputs |
| 三份局部结论互相冲突 | 检查口径与证据，不机械拼接 | Lost global context |
| 关键 worker 超时 | 区分必需与可选结果 | Straggler |
| 口径变更后旧结果迟到 | 保留历史但拒绝作为当前结果 | Stale information |
| 同一 REPORT 被重复投递 | 不重复接受、不重复触发下游副作用 | 消息重复、幂等 |
| 进程在产物保存后中断 | 能识别已有产物并继续验收 | Checkpoint、恢复 |

左中两列是教学测试设计，不是论文实验结果。它们衡量的不是“从不失败”，而是能否识别失败、限制影响、正确恢复或如实停止。

## 十四、评估与消融：怎样证明协调本身值得付费？

### 14.1 先建立强基线，而不是方便获胜的弱对照

下面是根据材料推演的实验矩阵：

| 条件 | 要回答的问题 |
|---|---|
| 强单 Agent，工具和上下文管理充分 | 不拆分到底能做到多好 |
| 单 Agent，独立工具调用可并行 | 时延收益是否来自工具并行 |
| 单 Agent 执行同样 SOP，给予相近预算 | 收益是否来自流程和交付标准 |
| 多次独立尝试，使用统一验证机制 | 收益是否来自额外采样和选优 |
| 主管—worker，统一约束和证据交付 | 独立上下文与协调是否额外有用 |

不要把简单单 Agent 与精心调优的多 Agent 直接比较，再把所有差异归因于“多智能体”。Scaling 对提示、工具和预算混杂的批评，正适用于这种实验。[^sc-introduction]

### 14.2 两类预算比较都重要，但回答不同问题

**相近资源下比较**用来检验效率和架构影响。要明确匹配的是总 token 上限、实际消耗、工具次数、模型成本还是迭代数，不能只写“公平预算”。

**真实产品约束下比较**用来判断业务价值，例如在固定截止时间和费用上限内，哪种方案达到更好的证据覆盖或减少更多人工返工。

两者都有效，但不能将增加大量成本换来的质量提升，表述为同预算下协调更高效；也不能因为同预算提升小，就否定更高价值任务愿意支付额外成本。

### 14.3 同时评结果、成本、过程约束与恢复

| 评估面 | 具体问题 |
|---|---|
| 事实与计算 | 数字、转换、计算结果是否准确 |
| 证据支持 | 引用是否对应原文，原文是否支持结论 |
| 覆盖程度 | 所有对象、期间和必答维度是否处理 |
| 整体一致性 | 分支是否遵守相同口径和共同约束 |
| 资源成本 | 主管、worker、通信和重试分别消耗多少 |
| 时延 | 总等待多久，瓶颈和关键路径在哪里 |
| 人工成本 | 修改、核验和恢复需要多少人工参与 |
| 故障行为 | 中断、重复、旧版本、缺证时能否正确处理 |

这些维度对应各材料关注的不同收益，不应压成一个不透明的总分。原文中不同指标也有不同含义，例如 MetaGPT 的人工修改次数不等于工时，Scaling 的轮数不等于美元。

### 14.4 不规定唯一轨迹，但必须保留过程约束

Anthropic 强调，同一任务可能有多条有效完成路径，不能仅检查是否走了预设步骤。它们评估事实、引用、完整性、来源质量和工具效率；对持续修改状态的任务，还讨论最终状态与关键检查点。[^an-eval][^an-appendix]

**工程推演：区分策略自由与不可违反的约束。** 搜索顺序可以变化，但不能使用无权限数据；分支数量可以变化，但不能漏掉必要验收；找到的来源可以不同，但不能把没有证据的结论说成确定事实。

只评最终文字可能遗漏过程中的危险副作用；强制唯一正确轨迹又会误惩罚其他有效解法。两者都应避免。

### 14.5 LLM Judge 和人工评估是互补，不是替代

Anthropic 使用按 rubric 评分的 LLM Judge，并在其测试中发现一次统一评分调用比拆分多个 Judge 更一致、更贴近人类判断。这是其经验，不是“Judge 越少越好”的普遍规律。[^an-eval]

人工测试还发现系统偏好排名靠前的 SEO 内容，而忽略权威但不靠前的来源。这个问题并不是看输出流畅度就能发现。

因此，Judge 需要人类校准和具体参考证据；不能让它仅凭文字自信判断事实正确。对重要失败类别保留人工复核，尤其关注自动评分可能忽视的来源偏差、遗漏与不当确定性。

### 14.6 从小样本开始，但不要拿小样本证明小差异

Anthropic 从约 20 个代表真实使用的查询开始快速迭代。它强调早期变化大时，小样本也能发现明显问题。[^an-eval]

这不意味着 20 个样例足以确认两个系统之间很小的胜率差。开发调试集与最终验证集应承担不同责任；同一任务多次运行的随机差异也需要记录。

**工程建议：先把失败类型观察清楚，再扩大样本检验稳定性。** 不能因为早期五个例子全成功，就宣布架构已经可靠。

### 14.7 做机制消融，而不只做“Agent 数量消融”

| 变化 | 主要观察的机制 |
|---|---|
| 去掉再次检索反馈 | 证据不足是否被过早转化为终止 |
| 去掉共享口径 | 跨分支可比性是否下降 |
| 去掉结构化交付 | 是否增加遗漏与整合错误 |
| 去掉产物引用，只传摘要 | 条件、数字和证据是否在传话中损失 |
| 去掉执行反馈 | 人工返工和不可执行结果是否增加 |
| 改变发言选择或调度策略 | 同一组 Agent 的质量和成本怎样变化 |
| 取消资源限制 | 是否发生过度搜索和递归委派 |

AutoGen 的 RAG 与群聊实验、MetaGPT 的执行反馈消融，为这些研究方式提供了具体例子。把可观察变化和机制关联起来，比单纯把 Agent 数量从二改成四更有解释力。[^ag-rag][^ag-group][^mg-experiments]

<a id="ch15"></a>
## 十五、持续改进：学习协作，不等于无限增加 Agent

### 15.1 材料中已经出现的三种改进对象

MetaGPT 附录 A.1 描述将项目交接反馈总结到长期记忆，在新项目开始前修改角色约束提示。作者同时指出，这种初步机制修改的是角色约束，还没有修改结构化通信接口。[^mg-outlook]

Anthropic 的工具测试 Agent 根据实际使用反馈改进工具说明。Cognition 则讨论为历史压缩保留关键决定投入专门设计，甚至考虑或使用小模型微调。[^an-tools][^co-context]

这些工作说明，可优化的不只有模型权重，还包括角色约束、委派提示、工具描述、压缩策略、交付契约和工作流。但材料没有证明它们能够自动形成普遍可靠的“自进化团队”。

### 15.2 主文机制、附录探索和未来设想要分开

MetaGPT 的 SOP、消息池和执行反馈是主文机制；角色约束自改进和多 Agent 经济属于附录讨论与探索。Scaling 的潜在激活共享、稀疏通信和协调器蒸馏属于作者列举的未来方向，不是本文已验证的部署方案。[^mg-outlook][^sc-limitations]

因此，不能把这些方向拼接成“论文已经提供从规则优化到自组织经济的完整系统”。每个部分都有自己的证据范围。

### 15.3 一条更可控的改进流程

以下是工程推演：将失败轨迹整理成可复现测试，判断失败来自分解、工具、交接、验证或运行时；提出单一或少量修改；在留出任务上重新评估质量、成本与新失败；通过后发布新配置版本，并保留回滚路径。

这与运行时版本绑定相连接：不要让任务执行到一半，所有 Agent 的提示、Schema 和权限同时被自动重写。一次修改改善局部，也可能破坏下游的接口假设。

**持续改进的单位应是可检验的机制变化，不只是“模型认为新提示更好”。**

## 十六、最终形成的工程判断

### 16.1 五份阅读不是五个架构广告，而是五种观察角度

| 材料 | 最值得保留的认识 | 要警惕的误读 |
|---|---|---|
| AutoGen | 交互、反馈和调度可以程序化；角色可以拆，也可以合并 | 框架里的多个对象就是多个独立大脑 |
| MetaGPT | SOP 与中间交付标准减少下游猜测，执行反馈减少返工 | 更多职位本身就是质量来源 |
| Cognition | 交接会丢背景，行动会生成新的隐含决定 | 单线程永远最优，或多 Agent 永远无效 |
| Anthropic | 可分解研究能通过独立上下文和动态委派扩展投入 | 更多搜索和 token 必然产生更多有用信息 |
| Scaling | 架构要与任务和预算匹配，收益必须拆开验证 | 经验阈值和某个榜单结果是普遍规律 |

上表是全文的综合解读。它们之间存在真实侧重点差异；本笔记没有把它们强行消除为同一套主张。

### 16.2 从讲义最后四条原则出发

讲义最后要求先问多 Agent 是否必要，让拓扑反映任务依赖，识别信息丢失点，并明确失败隔离边界。[^lec-principles]

现在可以把每条原则展开成实际问题：

**是否必要？** 当前瓶颈是独立信息范围、连续上下文、验证能力，还是简单的工具串行？哪一种能通过更少复杂度改善？

**拓扑是否匹配？** 哪些任务真的独立，哪些共同依赖一个决定？哪些交接应该保持串行，哪些可以通过产物并行？

**信息在哪里丢失？** 摘要是否删除了限制条件、排除项和反向证据？下游是否能够查回原始产物？

**失败在哪里被限制？** 候选结果何时被接受？旧版本、重复消息、权限失败和未知副作用如何处理？部分失败是否会被错误包装成整体成功？

### 16.3 一套设计顺序

**工程综合：**先确定目标与验收，再分析依赖与共同决定；先选择可以独立交付的工作单元，再决定是否需要独立 Agent；先定义信息与产物契约，再设计通信；建立强基线和受控实验，最后再扩大并行与动态能力。

这不是唯一工作方法，但能避免最常见的倒置：先创建十个角色，再尝试解释它们为什么存在。

### 16.4 本课最重要的结论

> **多智能体协调不是“怎样把更多模型连起来”，而是“怎样把任务中的不确定性、信息、决策权和验证责任分配到合适的位置”。**

探索可以分散，共同约束需要维护；结果可以并行产生，接受结果需要标准；策略可以自适应，权限、预算、版本和终止条件必须可控。

能解释每个拆分边界为何存在、每次交接可能丢失什么、每个结果如何被验证，以及额外成本换来了什么，才算真正掌握 multi-agent coordination。

<a id="appendix-d"></a>
## 附录 D：常见误解与自测

### D.1 常见误解

| 误解 | 更准确的理解 |
|---|---|
| 多 Agent 就是几个模型同时运行 | 核心是多个执行／决策单元的组织，模型可相同，也可能串行 |
| 两个 AutoGen Agent 就是两个推理模型 | 一个对象可能只是工具或人类代理 |
| 有消息队列就有协调 | 队列不决定依赖、权限、验收和结束 |
| 角色越细，专业化越强 | 强共享上下文的角色可能应该合并 |
| 复杂任务一定要多 Agent | 难度与可分解性不同 |
| 有主管就解决一致性和安全 | 主管自身也可能误判或过载 |
| 共享数据库意味着认知一致 | 读写版本、接受规则和共同口径仍需维护 |
| JSON 正确就可以安全合并 | 结构正确不代表事实正确和语义可比 |
| 多数 Agent 同意就更可信 | 错误可能高度相关，共识不等于独立证据 |
| 验证只能再调用一个模型 | 规则、运行、计算、原文与人工都可提供检查依据 |
| 超时说明动作未执行 | 可能是执行完成但响应丢失 |
| 保存对话就能恢复任务 | 还需操作状态、版本、预算和产物信息 |
| 所有多 Agent 通信都是平方复杂度 | 全互联是特定拓扑；树形、星形和稀疏图不同 |
| 45% 是普遍架构选择阈值 | 是特定研究条件下的经验结果 |
| 17.2× 是最终失败率增加 | 它是轨迹级指标，与任务级失败率不同 |
| 自改提示就等于学会协作 | 必须用独立评测检验是否改进且没有破坏其他约束 |

### D.2 自测与回答要点

**问题 1：一个系统有四个角色，能否直接判断它比单 Agent 更复杂或更强？** 不能。先看有几个独立推理循环、谁负责工具执行、控制与通信如何安排，再比较任务和预算。

**问题 2：一个研究流程总在证据不足时结束，第一步应加 Reviewer 吗？** 未必。先检查能否明确表达证据不足，并增加返回检索或补查的反馈路径。AG 的交互式 RAG 是直接例子。

**问题 3：所有 worker 都拿到了初始用户问题，为什么还会冲突？** 因为行动中新产生的共同决定未必同步；初始上下文共享不能解决所有运行中依赖。

**问题 4：把完整历史发给所有 Agent 是否是最佳方案？** 材料不支持统一答案。它可能保留更多相关背景，也会增加无关上下文与通信成本。应区分保留完整产物和每次输入全部产物。

**问题 5：为什么要用“单 Agent 执行相同 SOP”做对照？** 因为 MG 中增加角色同时增加了中间交付和流程。这个对照有助于区分流程价值与多个独立上下文的价值。

**问题 6：关键分支超时，其他分支都完成了，最终应怎样报告？** 依据预先定义的验收和部分结果策略。关键证据不足时如实说明，不能以停止运行替代完成任务。

**问题 7：SC 的 Finance Agent 结果能否证明所有投研任务都该集中协调？** 不能。必须检查本任务是否具有类似的信息分解、工具、预算与验收特征，并做本地比较。

**问题 8：一个升级在开发样例上提升成功率，能否立即改掉所有运行中的 Agent？** 不宜据此直接推断安全。需要留出评测、配置版本与运行兼容检查，长任务还涉及旧产物与新协议的交接。
