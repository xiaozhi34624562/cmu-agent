### 1.2 全文使用同一个教学案例

设想一个现有 RAG 服务需要完成如下任务：

> 审查并修复身份认证、文档级权限过滤、缓存隔离和可追溯引用，证明修改没有破坏原有功能。

后文会反复用这个案例说明交接、并行、竞争假设、验证、集成和评测。这里的代码路径、问题和产物均为**教学示例**，不是对真实仓库的审计发现。

这个任务看似可以分成“认证 Agent、检索 Agent、缓存 Agent、引用 Agent”。但在分工之前必须先明确：认证通过是否意味着有权访问所有文档？权限在哪一层执行？缓存命中后是否重新校验？引用指向哪个版本？这些前提不一致，多个局部合理的答案仍然可能拼不出正确系统。

**因此，先让工作能够被可靠委托，再讨论增加执行者。**

## 2. 概念基础：Agent、Skill、Workflow 与 Multi-agent

### 2.1 Agent 不是一段“你是某某专家”的提示词

讲义先回顾 Agent loop、上下文作为工作记忆、跨会话记忆，以及工具扩展。后面又强调，子 Agent 拥有自己的上下文、工具和权限。[L，PDF 第 3、31 页](#source-l)

为了便于工程分析，可以采用如下工作定义：

> **Agent 是一个带有目标、局部状态和受限行动能力的执行单元，能够根据观察结果决定后续动作。**

例如：

```text
收到任务
→ 查找相关代码
→ 发现信息不足，继续读取调用方
→ 提出候选修改
→ 执行获准的测试
→ 根据失败反馈调整
→ 交付候选产物与验证证据
```

一次模型调用可能是这个过程的一部分，但不等于整个 Agent。连续调用三次模型，也不能仅凭调用次数就证明系统发生了有意义的多 Agent 协作。

### 2.2 同一个模型，也可以形成不同的执行单元

下面是**分析抽象，不是讲义公式**：

$$
a_{i,t}\sim\pi_{\theta_i}(\cdot\mid g_i,c_{i,t},\mathcal T_i)
$$

其中，`g_i` 是第 i 个 Agent 的目标，`c_i,t` 是当前上下文，`T_i` 是可用工具，`θ_i` 表示模型参数。动作可以是读取资料、调用工具、提交候选结果或停止。

即使多个执行者共享相同模型参数，只要目标、输入、工具与验收边界不同，它们就可能形成有用分工。反之，只更换“专家”的称谓，却使用相同输入、相同方法和相同验收，并不必然增加有效信息。

**真正的专业化，是让执行者关注不同的问题和证据，而不是只给它不同职位名称。**

### 2.3 几个常被混淆的机制

| 机制 | 主要职责 | 不应误解为 |
|---|---|---|
| Agent | 执行任务，维护局部上下文，根据反馈继续行动 | 一段角色提示词 |
| Skill | 提供可复用的程序性指导、脚本和参考资料 | 新模型，或者天然独立的进程 |
| Hook | 在指定生命周期事件发生时执行逻辑 | 对模型遵循所有指令的保证 |
| MCP | 将外部能力暴露为可调用工具 | 自动决定何时应该调用工具的规划器 |
| Plugin | 打包、分发和安装能力 | 一定包含复杂编排的框架 |
| Workflow | 组织执行步骤、分支、等待和中间结果 | 所有步骤都必须由 Agent 完成 |
| Harness | 承载循环、工具执行、状态、权限与运行控制的外围系统 | 仅仅是一段 system prompt |

前五项的区分来自讲义的 Superpowers 与 Caveman 架构；Workflow 的控制职责由 R3 展开。Harness 在本文中是对外围运行系统的统一称呼。[L，PDF 第 8—14、19—25 页](#source-l)；[R3，工作流与其他机制的比较](#source-r3)

### 2.4 多 Agent、并行和长任务不是同一件事

子 Agent 可以串行执行，但仍能隔离高噪声上下文或使用不同工具权限。多个 Agent 也可以并行做完全不同的用户任务，而没有共同协作。一个长任务还可能只由一个 Agent 推进。

讲义将扩展分为三个方向：并行扩大工作宽度，子 Agent 扩展委托的宽度与深度，长任务扩展持续时间；Teams 和 Workflows 可以组合这些方向。[L，PDF 第 27 页](#source-l)

**在选架构前，先回答自己要改善的是等待时间、信息隔离、独立探索，还是长期持续推进。**

## 3. Superpowers：把愿望变成可以委托的工作

### 3.1 同样的模型和工具，为什么会有不同结果？

讲义第 6 页比较了两种方式：普通流程收到需求后直接写代码、再迭代修正；Superpowers 先澄清问题、批准设计、写计划，再测试驱动实现、审查验证与集成。讲义明确指出，模型和工具可以相同，差异在工作指令与程序。[L，PDF 第 6 页](#source-l)

```text
需求 → 澄清 → 设计确认 → 具体计划
     → 隔离实现 → 测试与审查 → 集成
```

在 RAG 案例里，“增加权限控制”必须先转成不变量，例如：没有文档访问权限的用户，不得从正文、检索片段、缓存或引用接口获得该文档内容。否则，一个 Agent 可能只增加登录校验，另一个却以为已经完成文档授权。

这里的工程推导是：**流程设计首先减少目标歧义；只有被澄清的目标，才适合继续分解。**

### 3.2 九个 Skill 怎样连成完整工作过程

| Skill | 讲义中的职责 | 对多 Agent 的意义 |
|---|---|---|
| `using-superpowers` | 发现并调用适用 Skill | 保证工作方法有统一入口 |
| `brainstorming` | 把请求转成经批准的设计 | 形成共同前提 |
| `writing-plans` | 把设计分成具体任务 | 产生可委托单元 |
| `using-git-worktrees` | 创建独立工作区 | 降低直接写入干扰 |
| `test-driven-development` | 先失败测试，再实现，再重构 | 为局部工作提供反馈 |
| `systematic-debugging` | 先定位根因，再提出修复 | 减少盲目试改 |
| `requesting-code-review` | 对照计划审查实现 | 检查目标偏移 |
| `verification-before-completion` | 报告成功前提供证据 | 为完成状态设要求 |
| `finishing-a-development-branch` | 合并、PR、保留或清理 | 把局部产物带回主流程 |

九个名称与职责来自讲义第 7 页；第三列是与多 Agent 设计的连接性解释。[L，PDF 第 7 页](#source-l)

重要的不是每个项目都照搬九个 Skill，而是区分“形成目标、执行工作、证明完成、集成产物”这些不同责任。把所有责任都浓缩成一句“请高质量完成”，会让许多判断留在隐含状态。

### 3.3 Skill 是程序性上下文，Plugin 是分发容器

讲义展示的结构中，Plugin 元数据负责打包，`skills/` 保存工作程序，`hooks/` 保存会话启动逻辑，`tests/` 检查行为。Skill 的 frontmatter 提供名字、描述等元数据，正文定义入口条件、必做步骤、禁止行为、批准节点、验证条件和下一阶段。[L，PDF 第 8—10、14 页](#source-l)

```text
Plugin
├── 元数据：怎样安装与识别
├── Skills：怎样完成这类工作
├── Hooks：在什么事件下注入指导或执行检查
└── Tests：怎样知道预期行为发生了
```

**工程推导：**工作规范应当能够单独更新和测试，而不是只能作为某个长提示词的一部分存在。

### 3.4 为什么 Skill 可用，不代表一定使用？

讲义指出，安装 Skill 只让它可用，不保证模型主动检查。Superpowers 因此利用 `SessionStart` Hook，在启动、清理或压缩后的相关事件中注入引导内容。简化脚本会读取 bootstrap Skill，编码为 JSON，并通过 `additionalContext` 交给运行时加入上下文。[L，PDF 第 11—13 页](#source-l)

但是：

```text
Hook 确实执行
≠ Skill 一定成功加载
≠ 模型一定遵循全部步骤
≠ 最终产物已经满足要求
```

这是从机制推导出的边界。指令约束应与实际产物检查配合；后文的 `TaskCompleted` Hook 和编译器 CI，会进一步把验证要求放到状态转换中。

### 3.5 与 R1、R5 的连接：方法怎样传递，为什么值得固化？

R1 允许在子 Agent 的 `skills` 字段中预加载完整 Skill 内容。因此，同一份方法可以由不同执行实例使用。它也说明，预加载列表不是访问白名单：具备 `Skill` 工具的执行者还可能发现其他 Skill；缺失或被策略禁用的条目会被跳过并记录警告。[R1，Preload skills into subagents](#source-r1)

R5 把从临时描述任务转向可复用流程的变化，称为 **Systematization of Agentic Work**。没有这层系统化，用户每次都要重新提供背景和程序性指导，能够交出去的工作范围就会受限。[R5，§5.3，PDF 第 19—22 页](#source-r5)

由此形成完整关系：**Superpowers 编码工作方法，Subagents 将方法交给独立执行者，Systematization 让这种委托能够反复发生。**

## 4. Caveman：先管理信息流，再扩大执行规模

### 4.1 上下文为何会被无效信息占满？

讲义列出的典型内容包括日志、diff、文件、搜索结果和工具输出。第 16 页以数百行测试输出为例，说明模型往往只需要先知道失败摘要和定位入口；等到上下文很长再压缩，又可能丢掉关键细节。[L，PDF 第 16 页](#source-l)

Caveman 分别处理两个方向：输入侧由本地代理与压缩引擎改变模型读取的内容；输出侧由 response Skill 改变模型表达方式。讲义报告输出 token 减少约 65%，但同时提醒 Skill 自身增加输入，因此不能把该比例等同于整个会话的成本节省。[L，PDF 第 17 页](#source-l)

这里保留的是**讲义所报告的结果**，不是本文重复测试所得。

### 4.2 六类组件分别做什么？

| 组件 | 讲义中的职责 |
|---|---|
| Skill | 定义压缩表达风格和聚焦任务的程序 |
| Command | 由用户显式选择模式或操作 |
| Hook | 初始化模式、检测用户改变、在压缩后恢复相关指导 |
| 本地代理 | 位于 Agent 与模型提供方之间，处理即将发送的输入 |
| 压缩引擎 | 针对日志、代码、diff、JSON 等保留不同结构 |
| MCP 工具 | 显式压缩、取回原文、查询统计、执行编码转换 |

讲义的具体调用链是：保存模式、注入提醒、Agent 执行工具、代理压缩高噪声结果、模型读取较短输入、生成诊断、需要时取回原文。[L，PDF 第 18—25 页](#source-l)

**不要把 MCP 工具调用和透明代理拦截混为一谈。**前者在被调用时执行，后者改变模型请求通道上的内容。讲义还指出，现成 Hook 不等于可以透明重写所有模型请求；自建 Harness 则可以在自己的消息组装阶段实现相应控制。[L，PDF 第 24 页](#source-l)

### 4.3 “保留可检索原文”与“无损摘要”不是一回事

讲义中的压缩工具返回压缩文本及 recovery handle，取回工具能够读取原始内容。不能据此说摘要本身可以无损还原原文；正确理解是，原文另有存储，没有因摘要而被删除。[L，PDF 第 23 页](#source-l)

教学示例：

```json
{
  "summary": "3 项测试失败，首个失败为请求超时",
  "first_failure": "tests/test_client.py::test_retry",
  "error": "TimeoutError",
  "artifact_ref": "artifacts/test-run-042.log",
  "tested_revision": "example-revision"
}
```

模型先读摘要，再按需要打开完整日志。路径、错误类型、否定词、数字和单位不应在压缩时丢失。对于真实的不确定性，也不应该为了简短而删除“尚未验证”等说明；这是对讲义压缩规则的工程使用边界，而不是把风格优化当作事实保证。

### 4.4 与 Subagent、编译器实验的统一关系

Caveman 管理的是**一条工具结果如何进入上下文**；子 Agent 管理的是**一段探索过程属于谁的上下文**；编译器实验中的日志与进度文件管理的是**长项目怎样在新会话中重新获得必要状态**。

三者都体现：当前上下文负责决策，外部存储负责完整细节和长期产物。不能让每个 Agent 都背着整个项目的全部历史，也不能只传一句没有证据入口的摘要。[L，PDF 第 16、31、48—49 页](#source-l)；[R4，Put yourself in Claude’s shoes](#source-r4)

## 5. 三条扩展轴：并行、委托与持续时间

### 5.1 先区分各自购买了什么能力

| 扩展方式 | 主要收益 | 新增代价 |
|---|---|---|
| 手动并行 | 同时推进独立任务，降低墙钟时间 | 人负责计划、信息转交和合并 |
| 子 Agent | 分配有边界的任务，隔离中间上下文 | 交接损耗、重复收集背景 |
| Agent Teams | 共享任务状态，交换中间发现 | 通信、协调和冲突管理 |
| Dynamic Workflow | 用脚本管理规模化调度和结果 | 恢复语义、错误处理、脚本维护 |
| 长任务机制 | 在更长时间里持续推进 | 进展判断、预算、终止与恢复 |

前三条扩展轴和四种多 Agent 方式来自讲义；这里把主要代价并列，便于选择。[L，PDF 第 27、46 页](#source-l)

### 5.2 Git worktree 解决了什么，没有解决什么？

讲义展示：不同会话在各自工作目录和分支上工作，共享同一仓库历史。示例命令为：

```bash
claude -w feature-retrieval
claude -w fix-citations
```

这两条命令用于说明讲义快照中的工作区用法，不是本文已经执行的操作。[L，PDF 第 28—29 页](#source-l)

**工程边界：**工作目录隔离不等于完整安全沙箱。不同会话仍可能使用相同数据库、凭证、端口和远程 API。甚至不同文件之间也可能存在接口冲突。工作树减少直接写入干扰，并不免除集成验证。

### 5.3 为什么手动并行很快把人变成瓶颈？

讲义第 30 页明确列出：计划仍在人脑中；信息需要人搬运；分支合并由人处理；执行过程没有被写下来，难以重复。[L，PDF 第 30 页](#source-l)

因此，从三个会话扩展到二十个会话，不只是购买更多执行能力，也同时扩大人的协调负担。

这正是 Teams 和 Workflows 存在的理由：把原来隐含在人脑中的任务状态与控制流显式化。但显式化并不意味着所有协调都应由另一个 LLM 完成；任务登记、依赖检查和预算控制可以由代码承担。

### 5.4 并行生产与并行探索

**并行生产**让不同执行者完成不同的必要工作，例如修复独立测试。**并行探索**让不同执行者调查不同解释或候选方案，再通过证据选择和合并。

编译器早期阶段主要体现前者；R2 的竞争假设调查主要体现后者。[R4，Make parallelism easy](#source-r4)；[R2，Investigate with competing hypotheses](#source-r2)

这个分析区分会影响评测：生产型并行主要看合格交付吞吐量与集成成本；探索型并行主要看新增有效证据、发现覆盖与验证后的判断改善。不能把所有收益都称作“提速”。

<a id="s06"></a>
## 6. Subagents：把上下文边界、交接接口和生命周期设计清楚

### 6.1 子 Agent 更像一次有状态的任务调用

典型过程是：主 Agent 明确子任务，提供必要输入；子 Agent 在局部上下文中探索和行动；它返回结果与证据；主 Agent 再决定如何继续。讲义强调，日志、搜索结果和文件转储可以留在子 Agent 中，而不是全部污染主对话。[L，PDF 第 31、35、37 页](#source-l)

这并不要求所有子 Agent 都并行。即使串行，一个大范围检索子 Agent 也可能因为隔离高噪声过程而有价值。

但主 Agent 不接收全部过程，不等于可以只接收无法检查的结论。**交接需要保留下一步决策所需的前提、证据和限制。**

### 6.2 普通子 Agent 启动时知道什么？

R1 的 *What loads at startup* 是理解机制的关键：非 conversation-fork 子 Agent 不自动继承主会话历史，不自动知道已经读取的文件，也不自动继承此前调用过的 Skill。主 Agent 编写委托消息，子 Agent 从相应启动上下文工作。[R1，What loads at startup](#source-r1)

| 启动内容 | 原文机制 | 应用时要注意什么 |
|---|---|---|
| 系统提示 | 子 Agent 自己的提示及运行时补充的环境信息 | 主 Agent 提示中的隐含规则未必在场 |
| 任务消息 | 主 Agent 组织的 delegation prompt | 当前目标与关键约束必须在这里明确 |
| 项目指令 | 按规则加载相应 `CLAUDE.md` 等文件 | Explore、Plan 和特殊配置存在例外 |
| Git 状态 | 启动时的仓库或工作树快照 | 它不是持续同步的全局认知 |
| 预加载 Skill | `skills` 指定的完整内容 | 必须确认有效加载，不要只检查配置存在 |
| 成员名单 | 满足工具与命名条件时注入的名单快照 | 名单存在不等于已知道成员的最新发现 |

R1 还说明：主会话的 output style 和 auto memory 不会自动成为普通子 Agent 的相应状态；子 Agent 的窗口大小由自己的模型决定。[R1，Manage subagent context](#source-r1)

**最典型的交接错误，是主 Agent 知道“全局中间件负责认证”，却没有传给真正执行路由审查的子 Agent。后者因此把缺少局部认证调用误判成问题。**这首先是信息接口错误，不必全部归因于模型能力。

### 6.3 委托消息要像一张可独立执行的工单

下面是教学用的任务结构，不是 Claude Code 内置 schema：

```json
{
  "task_id": "audit-retrieval-authz",
  "goal": "检查检索结果是否受文档访问权限约束",
  "baseline_revision": "example-revision",
  "scope": ["src/retrieval/", "src/cache/"],
  "shared_facts": [
    "身份认证由全局中间件负责",
    "认证通过不代表有权访问全部文档"
  ],
  "constraints": [
    "仅审查，不修改代码",
    "同时追踪缓存命中和未命中路径"
  ],
  "acceptance": "每项发现提供位置、触发条件、证据和未验证项",
  "on_missing_context": "返回具体缺失信息，不推测补全"
}
```

一个良好的交接必须让执行者独立回答：目标是什么，输入与基线是什么，边界在哪里，用什么证据说明完成，缺少信息时怎样退出。

相应地，一个结果不应只有“权限不足，建议加强”。它应说明：哪个版本、哪个路径、什么输入条件、观察到了什么行为、依据在哪里，以及实际验证到哪一步。

### 6.4 配置一个边界明确的只读审查子 Agent

讲义使用 Markdown 正文加 YAML frontmatter 定义子 Agent；项目级定义位于 `.claude/agents/`，用户级定义位于 `~/.claude/agents/`。R1 进一步展开了工具、模型、turn 上限、Skill、MCP 和记忆等字段。[L，PDF 第 33 页](#source-l)；[R1，Write subagent files、Supported frontmatter fields](#source-r1)

下面是可改用的配置示例。文件名为 `.claude/agents/evidence-reviewer.md`；示例未接入实际仓库验证：

```markdown
---
name: evidence-reviewer
description: 对指定代码范围进行只读审查，返回带位置与证据的问题。
tools: Read, Glob, Grep
model: inherit
maxTurns: 12
---

根据委托消息中的目标、版本、公共前提和文件范围审查代码。

每项发现必须包含问题描述、触发条件、文件路径、行号、
支持结论的证据、修改建议和未验证项。

不要修改代码。不要声称运行了没有实际执行的测试。
阅读已有测试结果时，核对结果对应的代码版本。
无法判断时返回缺失信息；没有发现不等于证明系统安全。
```

这里没有 Bash，因此它不能自己运行测试；没有 `Agent`，因此不能通过该工具继续分派；没有启用持久记忆，因此不额外引入记忆写入能力。`maxTurns: 12` 是示例限制，不是通用最优值，也不是系统总成本上限。

### 6.5 预加载 Skill，不等于限制可访问的 Skill

R1 明确区分了预加载与访问：`skills` 中指定的内容会在启动时注入，但未预加载的 Skill 仍可能被执行者通过 `Skill` 工具发现。要限制调用能力，应检查实际工具集合，而不是误用预加载列表作为白名单。[R1，Preload skills into subagents](#source-r1)

还要区分两个看起来都带“fork”的机制：**conversation fork** 继承主对话历史；Skill 中的 `context: fork` 是将该 Skill 放入指定 Agent 的执行上下文，R1 明确说明它不是继承主对话历史的同一种机制。[R1，Fork the current conversation；Preload skills into subagents](#source-r1)

### 6.6 新建、恢复、conversation fork、持久记忆

| 机制 | 保留的主要信息 | 用途 | 不能保证什么 |
|---|---|---|---|
| 新建 | 新组织的任务输入与启动信息 | 新的有边界任务 | 不会自动接续同名 Agent 的旧工作 |
| 恢复实例 | 该实例的既有对话、工具结果等历史 | 继续同一次调查 | 历史中的环境假设仍需检查 |
| Conversation fork | 分叉时主对话已有的背景 | 高度依赖当前讨论的旁支任务 | 不是主、子会话实时共享一个上下文 |
| 持久记忆 | 跨会话保留的知识文件 | 项目约定、模式、经验 | 不是模型参数训练，也不是事实自动更新 |

R1 说明每次新调用创建新实例，恢复则接续已有历史。该快照中的 Explore 和 Plan 是一次性调用，不提供普通的可恢复实例 ID。达到 `maxTurns` 的结果可以被标记为 partial；partial 应被理解为“工作尚可能未完成”，不能直接变成完成证据。[R1，Resume subagents](#source-r1)

Conversation fork 放弃普通子 Agent 的输入隔离，让它继承主会话背景，但自己的后续中间工作仍可留在旁支里，最终结果再返回。[R1，Fork the current conversation](#source-r1)

### 6.7 持久记忆的范围与隐含权限变化

R1 的 `memory` 有 user、project、local 三种范围。user 跨项目；project 可随项目版本管理分享；local 是项目本地但通常不提交版本库。运行时向 Agent 提供记忆目录读写指导，并注入 `MEMORY.md` 的有限前缀内容。[R1，Enable persistent memory](#source-r1)

有一个重要细节：启用记忆会自动启用 Read、Write、Edit 工具。即使你的目的是“让审查 Agent 记住经验”，也需要重新核对有效工具集与目录权限，不能仅凭最初的只读提示就断言它没有写入能力。

**工程推导：**应区分经验证事实、工作假设、历史经验与过期结论，并记录来源、适用版本和更新时间。比如“这个路由无需局部认证”若来自旧版本，就不应永远被当作当前事实。

### 6.8 前台、后台与完成通知

R1 区分前台执行和后台执行：前台阻塞主对话，后台可与主会话并行；需要权限时，会通过相应机制把请求交给用户。具体选择还受 fork mode、交互模式、Agent SDK 和 teammate 运行方式影响。[R1，Run subagents in foreground or background](#source-r1)

因此，不能把“子 Agent 默认总在前台”或“后台不需要权限”当作普遍规则。更关键的是：主 Agent 必须等到真实完成通知或明确状态，才能汇报子任务结果。运行中、结束返回、验证通过，属于不同状态。

### 6.9 嵌套深度与并发度是两个独立控制量

讲义展示主 Agent、实现/调试/审查子 Agent、再到测试/验证子 Agent 的层次结构。它使用五层上限作为当时的产品说明，并把两到三层作为经验性建议。[L，PDF 第 34—35 页](#source-l)

R1 快照则说明默认允许主对话下三层，并通过 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 配置；文档保留了早期五层默认行为的版本说明。两者不应被静默合并为一个无版本结论。[R1，Let subagents spawn their own subagents](#source-r1)

并发限制另由机制控制，普通子 Agent、Workflow 和 Teams 也可能使用不同限制；R1 还列出了恢复、fork 等路径对并发计数的例外。因此，产品某一个并发参数不能自动被当作整套系统的全局预算。[R1，Concurrent subagent limit](#source-r1)

### 6.10 什么时候留在主会话更好？

讲义建议：频繁往返、多个阶段共享大量背景、小范围修改和低延迟要求，通常更适合主上下文；高噪声输出、工具权限限制、独立可交付工作和并行任务，更适合子 Agent。[L，PDF 第 37 页](#source-l)

这不是对任务“高级程度”的评判，而是对交接成本的判断。一个只需修改两行代码的任务，重新给子 Agent 解释背景可能比直接完成更贵。

<a id="s07"></a>
## 7. Agent Teams：管理的不只是聊天，而是依赖、消息和状态

### 7.1 四个组成部分

R2 将 Agent Team 拆成 lead、teammates、shared task list、mailbox。成员各自有上下文，项目背景可以按规则加载，但不继承 lead 的完整对话历史；任务专属信息仍需通过启动提示提供。[L，PDF 第 38—42 页](#source-l)；[R2，Architecture；Give teammates enough context](#source-r2)

| 组件 | 职责 |
|---|---|
| Lead | 创建成员、协调任务、汇总结果 |
| Teammates | 在自己的上下文中推进工作 |
| Task list | 保存任务、归属、依赖与状态 |
| Mailbox | 传递普通信息与结构化协议消息 |

所以，Team 并不只是给多个模型建立群聊。它需要一套可观察、可推进的执行协议。

### 7.2 共享任务列表如何运行？

R2 中的原生任务状态是 pending、in progress、completed。有未完成依赖的任务不能被领取；lead 可以指派，成员也可以自行领取；任务认领用文件锁处理同时竞争；完成任务会解除下游依赖。[R2，Assign and claim tasks；Architecture](#source-r2)

在教学案例里，可以先确认公共权限接口，再允许检索过滤、缓存隔离和独立测试并行推进，最后进行集成验收。

但“执行者已返回”不应自动解释为“该任务满足业务验收”。原生三态只是产品的状态模型；生产系统是否另需 submitted、verified、integrated 等业务状态，是后续工程设计问题。

### 7.3 任务锁与语义冲突

任务锁解决的是“同一任务是否被同时领取”。它不能阻止两个不同任务修改相互依赖的接口，也不保证独立分支合并后语义一致。

例如，一个 Agent 将 `doc_id` 改成 `document_id`，另一个按旧字段实现引用校验。它们没有抢同一任务，也未必改同一文件，但系统仍然失败。

**工程推导：**任务依赖、公共契约和文件所有权应同时被明确。公共接口先确认；跨模块契约变更集中处理；最终集成版本重新验证。R2 的避免文件冲突建议只是其中一部分。[R2，Avoid file conflicts](#source-r2)

### 7.4 什么才算“消息发送成功”？

R2 的邮箱是本地 JSON 文件。运行时只有在成功写入接收者邮箱后，才报告发送成功；磁盘或权限导致写入失败时，发送者收到错误。读取时也会验证消息格式，避免异常条目阻塞有效消息。[R2，Architecture](#source-r2)

从可靠性角度，还必须理解以下差异：

```text
已生成待发送内容
→ 已写入邮箱
→ 已被读取
→ 已被处理
→ 已形成产物
→ 产物已通过验证
```

这些不是同一个完成事件。R2 提供了其中部分运行语义；后续的处理确认与业务验证，是系统设计仍需考虑的事情。

“接口已经更新”的消息成功发出，不代表另一个成员已经修改并验证调用方。最终应以产物版本和检查记录作为依据，而不是依据聊天中的“收到”。

### 7.5 横向通信应当带来新增信息

判断 Team 是否值得使用，可以问：**别人的中间发现，会不会改变我下一步应该做什么？**这是本文的选择启发，不是产品定理。

如果每个人只需要完成一项独立审查，最后返回问题列表，普通子 Agent 通常已经能够表达这种组织方式。如果缓存调查发现了可复现的跨用户异常，检索与引用调查必须据此改变方向，直接交换证据才有具体价值。

一条有用的消息是：

> 已排除缓存未命中路径。切换用户后，相同查询命中旧访问范围对应的结果。证据在测试产物 X；请检查命中后是否重验授权。当前尚未证明引用路径是否同样受影响。

一条价值较弱的消息是：“我觉得是缓存，你怎么看？”前者传递证据和范围，后者可能只增加没有新观察的讨论。

### 7.6 竞争假设调查：并行探索的具体模式

R2 提议让多个成员分别调查不同假设，并主动挑战彼此，而不是找到一个看似合理解释就结束。这是文档中的实践方法；该部分没有给出受控实验中的准确率增幅。[R2，Investigate with competing hypotheses](#source-r2)

在案例中，三种可区分的假设可以是：授权过滤缺失、缓存键缺少访问范围、引用接口绕过授权。每个假设应给出可反驳预测。例如，如果异常来自共享查询缓存，清空缓存后的第一次请求应不同于跨用户重复请求。

**工程建议：**先独立调查，再交换证据，最后用实验或原始产物处理分歧。目标不是投票一致，而是让判断接受外部约束。

### 7.7 团队规模与任务粒度

R2 建议先从少量成员开始，并指出过多成员增加通信、协调和冲突。它把三到五名成员、每个成员多个任务作为实践起点，而不是所有问题的最佳配置。[R2，Choose an appropriate team size；Size tasks appropriately](#source-r2)

任务过小，启动与交接成本会超过执行收益；任务过大，执行者可能长时间偏离目标。更合适的是能产生明确交付物的单元，并让任务队列足够丰富，以便成员卡住时重新分配。

**任务数可以大于执行者数。优化目标是任务队列的可信推进，不是给每项任务配置一个永久 Agent。**

### 7.8 “完成”需要质量关卡

R2 提供 `TeammateIdle`、`TaskCreated`、`TaskCompleted` 等 Hook。特定退出码可以阻止成员转为空闲，或阻止任务创建、完成，并返回反馈。[R2，Enforce quality gates with hooks](#source-r2)

与 Superpowers 对照，Skill 负责表达“完成前要验证”，Hook 则可以让程序在完成节点检查产物和证据。

自建系统可以采用这样的流程：

```text
Agent 提交候选结果
→ 检查产物是否存在
→ 检查是否绑定当前版本
→ 执行相应验证器
→ 通过后再解除下游业务依赖
```

这里是工程方案，不应误写成 R2 已有的完整业务验收实现。

### 7.9 计划批准、权限批准与人工批准不能互相代替

本地 R2 快照有一个容易忽略的说明：成员在 plan mode 形成计划后发送批准请求，运行时在 lead 会话中收到后即批准，**并非 lead 已审查计划内容**。随后动作仍走相应权限流程。[R2，Have teammates plan before implementing](#source-r2)

因此，“发生了 plan approval”不等于“主 Agent 审查通过”，更不等于“用户已同意”。它也不等于 Superpowers 中等待用户确认设计的节点。

R2 另明确指出，成员消息来自另一个 Agent，不来自用户；成员不能代表用户批准权限，也不能通过转交任务绕过已拒绝动作。[R2，Permissions](#source-r2)

**评价一个批准机制，要检查它实际验证了什么、批准者是谁、批准对象是什么，而不是只看名称。**

### 7.10 同一份 Agent 定义，在 Team 中未必按相同方式生效

R2 支持复用子 Agent 定义作为 teammate，但该快照说明：工具、模型、正文等字段在不同运行模式下有不同处理；`skills` 预加载字段不会按普通子 Agent 的方式应用给 teammate，而是从项目与用户设置加载 Skill。[R2，Use subagent definitions for teammates](#source-r2)

这意味着不能把一个验证过的子 Agent 配置移到 Team 后，就假定行为完全一致。有效提示、工具、Skill 和权限需要在实际启动模式下重新检查。

同样，讲义把普通子 Agent 的典型通信画成“结果返回调用者”，但 R1 快照还存在具备 `SendMessage` 的普通子 Agent。两者应理解为典型组织方式与具体产品能力的不同层次，而不是永远成立的通信禁令。[L，PDF 第 40—42 页](#source-l)；[R1，Resume subagents；What loads at startup](#source-r1)

<a id="s08"></a>
## 8. Dynamic Workflows：把调度计划从对话移到代码

### 8.1 真正的变化是“谁持有计划”

讲义第 43 页介绍由 JavaScript 在后台编排大量子 Agent。R3 进一步区分：在主 Agent 编排中，模型逐轮决定下一步；在工作流中，脚本持有循环、分支与中间结果，模型负责具体工作节点。[L，PDF 第 43、46 页](#source-l)；[R3，工作流与 Subagents、Skills、Teams 的比较](#source-r3)

审查几百个文件时，主 Agent 不应只靠聊天历史记住哪些已分配、哪些失败、哪些需要复查。工作流可以明确维护这些集合。

**程序保证按控制结构推进，不代表每项模型判断一定正确。**控制流的确定性和结果的语义可靠性必须分开。

### 8.2 动态生成计划，与可重放执行并不矛盾

模型可以根据任务生成不同脚本；脚本一旦进入执行，运行时则需要追踪调用序列、已完成结果和恢复位置。R3 禁止脚本直接调用 `Date.now()`、`Math.random()` 或无参数 `new Date()`，要求需要的时间通过 `args` 输入，以减少重启时控制流的无意变化。[R3，Edit a saved script](#source-r3)

这不是把 Agent 输出变成确定函数，而是避免调度层另外引入难追踪的随机变化。

对于带时间条件的任务，固定输入时间还不够：原始资料本身是否发生变化也需要处理。**“固定 as-of 参数”不等于自动获得历史数据快照**，后者属于数据系统的责任。这是工程推导。

### 8.3 运行时提供哪些基本能力？

R3 中，`agent()` 发起一个子 Agent；`pipeline()` 为列表中的条目运行相应任务；`parallel()` 同时运行一组任务并等待；`phase()` 和 `log()` 提供进度组织；指定 `schema` 可以约束结构化输出。[R3，What the saved script looks like；Edit a saved script](#source-r3)

典型审查结构：

```text
确定检查清单
→ 对各工作单元并行初查
→ 收集候选发现
→ 对发现逐项验证
→ 去重与排序
→ 生成报告，并保留覆盖缺口
```

R3 给出了逐文件审查、并行迁移、反复修复直到检查通过、多来源研究等模式。它们是执行形状，不是对最优任务粒度的证明。跨文件授权链不能只看局部文件就下结论。[R3，Example workflow prompts](#source-r3)

### 8.4 一个保留失败项的示例

下面按 R3 的运行时形式改写，放在 `.claude/workflows/` 的脚本中。它依赖该产品运行时，不是可直接用普通 Node.js 执行的完整程序；目录必须替换为实际项目目录，工具权限另行配置。本文没有实际发起这些 Agent。

```javascript
export const meta = {
  name: "audit-modules",
  description: "按模块审查，并保留未完成项"
};

const modules = [
  "src/retrieval/",
  "src/cache/",
  "src/citations/"
];

const results = await pipeline(modules, modulePath =>
  agent(
    `只读审查 ${modulePath} 的权限与引用问题。
     不只看局部文件；追踪相关中间件和调用方。
     返回位置、触发条件、证据及未验证项。`,
    { label: modulePath }
  )
);

return modules.map((modulePath, index) => ({
  module: modulePath,
  execution_status: results[index] === null
    ? "incomplete"
    : "returned",
  verification_status: "not_independently_verified",
  result: results[index]
}));
```

示例把“收到返回”与“独立验证”分开。提示中的“只读”不代替运行时权限。固定列表也只说明检查这三个模块；如果要求“全仓覆盖”，必须另行验证枚举清单完整，而不是让生成摘要的人猜测。

### 8.5 `null` 不能从审查报告中消失

R3 说明，取消或某些不可恢复错误可能令 `agent()` 返回 `null`，`pipeline()` 保留对应位置。原文的小型示例使用 `.filter(Boolean)` 丢弃空项。[R3，What the saved script looks like](#source-r3)

这个展示技巧不应不加区分地用于完整性敏感任务：十项检查只有八项返回，不能写成“十项全部审查完成”。

R3 对内置研究工作流给出另一条值得借鉴的处理原则：验证者因为限流或 API 故障无法核查主张时，标为 unverified，而不是 refuted。[R3，Run a bundled workflow：Read the report](#source-r3)

因此建议分别记录：

| 维度 | 问题 | 示例状态 |
|---|---|---|
| 执行状态 | 任务有没有正常运行并返回？ | returned、failed、cancelled、partial |
| 验证结论 | 证据支持什么判断？ | supported、refuted、unverified |
| 覆盖状态 | 请求范围是否全部被处理？ | complete、incomplete、unknown |

这张表是本文的设计建议，不是产品统一枚举。**基础设施失败不构成事实被反驳的证据；没有发现也不等于证明不存在。**

### 8.6 Schema 合法，只保证形式上的某些条件

R3 说明，运行时可以在执行前发现部分 schema 矛盾，并对输出做结构验证和有限重试。[R3，What the saved script looks like](#source-r3)

但是，JSON 满足 schema，不代表路径真实、引用有效、测试实际执行，更不代表结论正确。结构化输出应当作为后续校验的输入，而不是作为最终验收。

### 8.7 暂停后恢复：不一定只重跑失败分支

R3 给出的具体例子是：若调用启动顺序为 A、B、C、D，B 失败，重新执行会复用 A，重跑 B、C、D，即使 C、D 已经完成。改变调用顺序也可能使第一个不匹配位置及后续工作重跑。[R3，Resume after a pause](#source-r3)

```text
原始启动：A → B → C → D
结果：    成功  失败  成功  成功
恢复：    复用  重跑  重跑  重跑
```

这是文档描述的序列相关复用规则，不应泛化为“任何已完成 DAG 节点都会精确保留”。它会影响成本、延迟以及重复副作用。

### 8.8 卡住重启，与恢复旧实例完全不同

R3 说明，卡住后的新尝试从相同提示重新开始，但不携带旧尝试的 transcript；已经修改的文件继续保留，已经消耗的 token 继续计入总量。[R3，When an agent stalls and restarts](#source-r3)

与 R1 的恢复实例对照：

| 操作 | 对话历史 | 外部世界 |
|---|---|---|
| 恢复已有子 Agent | 接续已有历史 | 需要检查环境是否已经变化 |
| 重启卡住的 Workflow Agent | 不带旧尝试 transcript | 旧修改可能仍然存在 |
| 回滚外部状态 | 不是上述操作的同义词 | 必须另行实现或执行 |

**重试没有撤销旧世界。**新 Agent 可能不知道旧尝试做过什么，却正在操作一个已经被部分修改的环境。

工程上应在重试入口检查产物、操作记录与当前版本；对于外部写入，设计幂等标识、去重或明确补偿；不要把 resumable 当作 exactly-once 或事务回滚。

### 8.9 并发、规模建议、缓存和总预算

R3 的 small、medium、large 是编写工作流时的规模建议，不是硬上限。运行时另有并发、单次列表和总 Agent 数限制。[R3，Set a size guideline；How a workflow runs](#source-r3)

该快照提及：默认并发最多 16，CPU 可用量较少时还会降低；单次 `parallel()` 或 `pipeline()` 最多 4,096 项；一次运行最多 1,000 个 Agent。相关默认值和可配置范围具有版本条件，不能据此推断所有版本或其他框架。[R3，运行限制表](#source-r3)

此外，相同模型、工具、schema 和系统提示前缀等条件下，多个执行者可以利用提示缓存。运行时可能短暂错开启动，让后续请求读到第一个请求建立的缓存。[R3，Prompt caching in a fan-out](#source-r3)

缓存优化的是重复处理前缀的计算，不是共享调查发现。并发上限约束同时运行数，不是整个任务的花费。总预算还需要累计后代任务、结构重试、工具调用和恢复成本。

### 8.10 产品工作流的能力边界

R3 快照说明：脚本本身不直接访问文件系统和 shell，不加载模块，相关操作由 Agent 执行；运行中的任意人工签字不是其通用能力，需要将需要签字的阶段拆成独立工作流。权限提示与用量等待属于不同的暂停机制。[R3，How a workflow runs：Constraints](#source-r3)

所以，原型可借助产品工作流，生产系统是否还需要持久任务库、业务审批服务和独立执行平台，要根据需求决定，不能仅凭“支持 Workflow”就认定已经具备完整业务流程引擎。

## 9. 长任务：持续执行不等于持续进展

### 9.1 `/goal` 与 `/loop` 的差异

讲义中，`/goal` 接收可以验证的终态，例如 lint 零错误，由评估器重复检查，满足条件或达到尝试上限后结束；`/loop` 按时间重复提示，由时间触发，而不是由成功条件触发。[L，PDF 第 44—46 页](#source-l)

| 机制 | 回答的问题 | 讲义中的结束方式 |
|---|---|---|
| `/goal` | 什么条件成立才算完成？ | 目标满足或尝试上限耗尽 |
| `/loop` | 多久再执行一次？ | 用户停止 |

这些是讲义快照中的行为说明，不是本文推荐在所有系统上照搬的命令接口。

### 9.2 长任务必须有合法的未完成出口

“不断继续直到做好”并不足以设计控制器。执行者可能重复运行相同测试、重试已失败的方法，或修好 A 又破坏 B。

**工程建议：**控制器至少区分目标满足、预算耗尽、无进展、执行失败、等待人工决策。R3 的示例也会在连续若干轮没有进展时停止，而不只提供无限重试。[R3，Keep fixing until a check passes](#source-r3)

合法出口并不降低能力；它让系统在缺少证据时能够诚实终止，而不是用一句“已完成”填补状态空白。

### 9.3 终态要绑定验收条件和产物版本

“输出完成”不是验收；“测试通过”也需要说明测试范围和对应版本。测试是否被删除、是否只覆盖样例、是否在合并后的版本上执行，都会改变“通过”的意义。

一个更可靠的终态表达是：

> 在固定的验收要求下，对明确版本的产物，获得足够的外部检查证据，并对剩余限制做显式说明。

这是对讲义“可验证终态”原则的工程化展开，而不是形式化正确性证明。[L，PDF 第 44、58—59 页](#source-l)

### 9.4 长任务的连续性应该由外部状态承载

同一个 Agent 永远不结束，不是完成长任务的唯一方式。编译器实验通过新会话不断读取代码、进度和测试产物持续推进；子 Agent 的恢复记录、持久记忆和 Workflow 执行日志又提供了不同层次的连续性。[R1，Resume subagents；Enable persistent memory](#source-r1)；[R3，Resume after a pause](#source-r3)；[R4，Enabling long-running Claudes](#source-r4)

**要保存的不只是“上次说了什么”，还包括“上次实际改变了什么、哪些结论已验证、下一次应该从哪个状态继续”。**

## 10. 深入案例：16 个 Agent 构建 C 编译器

### 10.1 先准确理解实验目标和结果

R4 由 Nicholas Carlini 撰写，目标是探索模型能够勉强达到的复杂工程能力，而不是宣布一种已被证明普遍可靠的生产方法。文章报告：16 个并行 Agent，约两周、近 2,000 个 Claude Code 会话，消耗约 20 亿输入 token、1.4 亿输出 token，API 成本略低于 2 万美元，得到约十万行 Rust 实现的 C 编译器。[R4，开头；Stress testing the limits of agent teams；Evaluation](#source-r4)

报告的产物能够构建 Linux 6.9、QEMU、FFmpeg、SQLite、Postgres、Redis 等项目，在多数所用编译器测试集上达到约 99% 通过率，也能编译运行 Doom。但“能构建 Linux”的说明必须与后文的 x86 16 位依赖等限制一起读。[R4，Evaluation](#source-r4)

| 维度 | 报告中的结果 | 不应直接推出 |
|---|---|---|
| 执行规模 | 16 个并行执行者、近 2,000 会话 | 获得 16 倍提速 |
| 代码产物 | 约十万行 Rust 代码 | 十万行都具有专家级质量 |
| 测试表现 | 多数所用测试集约 99% 通过 | 任意 C 程序都正确 |
| 实际项目 | 构建多个真实项目 | 可无条件替代成熟编译器 |
| API 成本 | 略低于 2 万美元 | 已统计全部人工和基础设施成本 |

右列是对证据范围的分析，而不是否定实验的工程价值。

### 10.2 为什么它不等于 R2 的产品 Team 架构？

文章中的基础设施非常朴素：每个 Agent 有独立容器和 Git checkout，共享上游裸仓库；通过 `current_tasks/` 中的文件认领任务；工作后拉取上游、合并、推送并释放任务；新的会话继续推进。[R4，Running Claude in parallel](#source-r4)

作者明确说明，该研究原型没有编排 Agent，也没有额外实现成员通信方式。执行者会从当前仓库状态中选择下一项明显任务，在卡住时保存失败方法和待办。[R4，Running Claude in parallel](#source-r4)

```text
读取代码、README、进度和失败日志
→ 认领任务
→ 在本地工作区实现与测试
→ 拉取他人修改，处理合并
→ 推送并释放任务
→ 新会话继续
```

因此，这里的协作主要由共享产物和状态承担，而不是由一个“总经理 Agent”持续指挥。**多 Agent 不必表现为多模型聊天；共享环境与产物也能承载协作。**

### 10.3 人的工作没有消失，而是转向设计环境

文章说，作者主要投入在测试、环境和反馈设计，让执行者能够在没有逐步指导时知道怎样取得进展。测试集、构建脚本、验证器、失败模式补充测试，以及后期更严格的 CI，都是这一工作的组成部分。[R4，Lessons from programming with Claude agent teams](#source-r4)

这里的“多数时候离开运行现场”不能被解释为“人没有提供架构、验证和环境设计”。真正发生的是，人从逐行实现转向建立一个可以持续观察与约束进展的系统。

这与 R5 的委托、监督和集成框架一致，但编译器案例本身没有对这种工作转移的全部人工时间做完整量化。[R5，§6](#source-r5)

### 10.4 早期为什么容易并行？

当有很多相互独立的失败测试时，不同 Agent 可以分别处理不同问题。测试接近通过以后，又可以分别推进不同的小型开源项目编译。[R4，Make parallelism easy](#source-r4)

这时环境提供了三个条件：问题可区分，进展可局部观察，修复可局部验证。因此，多个执行者有不同的有效工作可以做。

**并行收益来自可独立推进的问题数量，不来自项目名字听上去足够大。**

### 10.5 为什么编译 Linux 时 16 个 Agent 一起卡住？

文章描述，内核构建是一个大规模整体任务。所有 Agent 都撞上同一个错误，分别修复它，再覆盖彼此的修改；此时多开执行者没有帮助。[R4，Make parallelism easy](#source-r4)

问题不只是“没有分好任务”。更深一层，是环境只暴露一个整体失败，难以告诉每个执行者自己的子范围是否正确。

```text
一个整体失败
→ 所有人选择同一阻断问题
→ 重复劳动和修改冲突
→ 更多执行者不再带来更多有效进展
```

这也是任务锁的边界：即使解决了某些重复认领，也不能自动创造可独立验证的工作。

### 10.6 GCC oracle 怎样重新创造并行性？

作者把 GCC 作为已知可用的对照编译器，让大多数文件由 GCC 编译，只让一个子集由新编译器编译，再观察组合是否工作。失败时继续用 GCC 替换部分子集，缩小问题范围。这样不同 Agent 才能定位和修复不同文件所暴露的缺陷。[R4，Make parallelism easy](#source-r4)

教学化地表示：

```text
全部使用新编译器 → 整体失败，不知道从哪里开始

A、B 使用新编译器，其余使用 GCC → 失败
只有 A 使用新编译器 → 通过
只有 B 使用新编译器 → 失败

得到一个优先调查 B 的可复现问题
```

这个例子说明故障定位方式，并不证明有限测试通过的代码已经形式化正确。GCC 在这里是执行时的参照，不是给 LLM 进行参数训练，也不是“模型通过调用 GCC 学会了编译器实现”。

更重要的是，作者还需要 delta debugging 来处理交互缺陷：A 单独替换正常，B 单独替换正常，A、B 同时替换却失败。[R4，Make parallelism easy](#source-r4)

**局部测试与集成测试必须并存。**把大问题拆开以后，仍要识别子任务之间的组合效应。

### 10.7 本案例最重要的推导：验证器决定任务的可分解性

验证器通常被看作最后给答案打分的组件。这个实验显示，它还可能改变工作本身：从一个无法定位的整体故障，转成多个能够分别调查的可复现故障。

所以，有时提高 Multi-agent 能力的最佳行动不是增加规划者，而是改造环境，让系统看得到不同部分的独立进展。

迁移到 RAG 工程，若只有一个最终答案分数，下降后所有 Agent 都可能盲目改提示词。如果评测能够分别暴露实体识别、检索命中、证据保留、引用定位和回答支持关系的问题，才能更有针对性地生成修复任务。这是本文的工程迁移，不是 R4 已经实验验证的 RAG 结论。

### 10.8 测试反馈必须写给执行者使用

文章建议只向终端输出少量关键信息，把完整日志放到文件；错误格式便于自动搜索；汇总统计预先计算；README 与进度文件经常更新，帮助新会话定位。[R4，Put yourself in Claude’s shoes](#source-r4)

这与 Caveman 和 Subagents 形成同一条原则：**压缩当前决策需要读取的内容，但保留原始证据与恢复入口。**

测试框架还需要避免让 Agent 花大量时间重复运行全套测试。文章提供 `--fast` 抽样模式，在单个 Agent 内保持样本稳定，在不同 VM 之间使用不同样本。[R4，Put yourself in Claude’s shoes](#source-r4)

稳定样本便于判断修改前后的变化，不同样本有助于扩大探索范围。但“有助于扩大”不等于已证明全覆盖；最终验收仍需适当的全面检查。

### 10.9 为什么后期要增加严格 CI？

文章报告，新增功能与修复开始频繁破坏已有功能，因此作者增加持续集成和更严格约束。[R4，Write extremely high-quality tests](#source-r4)

把三份材料放在一起：Superpowers 指导完成前验证，Teams Hook 可以拦住未满足条件的完成状态，CI 检查合并后的系统是否回归。它们分别约束执行者行为、任务放行和集成产物，不能互相代替。

### 10.10 真正的专业化来自不同优化目标

文章给专门 Agent 分配去重、编译器自身性能、生成代码效率、Rust 结构质量和文档任务。[R4，Multiple agent roles](#source-r4)

“编译器运行得快”和“编译出的程序运行得快”是两个不同目标，可能依赖不同测试和取舍。这种专业化具有清晰的输入与验收边界，不只是换称谓。

### 10.11 限制与 clean-room 的准确解释

文章说明实现过程中没有互联网访问、编译器自身依赖 Rust 标准库；这描述的是开发环境与实现依赖，不能据此证明模型训练中从未见过相关代码，也不能抹去构建演示中使用外部工具的事实。[R4，Evaluation](#source-r4)

报告的限制包括：x86 16 位启动阶段仍调用 GCC；汇编器和链接器的自动化尚不成熟，演示使用现有工具；并非所有项目都能构建；生成代码效率低于 GCC；Rust 实现不等于专家质量。文章还记录某些 16 位输出超过 Linux 允许的大小约束，反映“能生成指令”与“满足实际系统要求”不是一回事。[R4，Evaluation](#source-r4)

**正确结论是复杂工程能力得到显著展示，同时也暴露模型、任务结构和验证体系的边界，而不是多 Agent 已经自动消除了软件工程约束。**

### 10.12 案例与前面课程内容的逐项对应

| 编译器设计 | 对应课程问题 |
|---|---|
| 不同容器与 checkout | 执行和产物隔离 |
| Git 任务标记 | 工作认领与状态协调 |

## 11. Programming / Software 3.0：把不确定的判断放进可依赖的系统

### 11.1 两个“3.0”不能混为一谈

讲义第 52 页的 **Programming 3.0** 是作者自己的命名：从硬件指令、编程语言，发展到由人表达目标、Agent 生成程序。第 53 页介绍的 **Software 3.0** 则采用 Karpathy 的划分：源代码、神经网络权重、LLM 提示与上下文分别成为不同形式的“程序”。[L，PDF 第 52—53 页](#source-l)

| 划分 | 核心内容 |
|---|---|
| 作者的 Programming 3.0 | 人表达目标，Agent 参与产生程序 |
| Karpathy 的 Software 1.0 | 人编写源代码 |
| Karpathy 的 Software 2.0 | 通过数据与优化获得神经网络权重 |
| Karpathy 的 Software 3.0 | 语言与上下文驱动 LLM 行动 |

本文根据讲义解释这些概念，没有把 SOURCES 中仅列出的外部文章或视频当作已经完整阅读的材料。

### 11.2 不确定性不是从 LLM 才开始

讲义指出，传统软件也受到硬件、并发、网络和依赖版本影响。Agent 系统新增的难点，是在生成和执行过程中与环境交互，同时受到语言歧义、检索漂移、上下文截断、模型生成变化和工具失败的影响。[L，PDF 第 55—57 页](#source-l)

| 层次 | 可能的不确定性 | 工程上应定位什么 |
|---|---|---|
| 用户意图 | 目标与限制歧义 | 需求与验收是否明确 |
| 检索和上下文 | 数据更新、索引变化、遗漏 | 原始来源、版本、检索范围 |
| 模型生成 | 采样与运行差异 | 模型、提示、输入和有效配置 |
| 工具循环 | 失败、环境变化、部分写入 | 调用记录与外部状态 |
| 生成后的程序 | 在适当条件下通常较确定 | 是否还调用模型、工具或共享状态 |

因此，不能把所有失败都用“模型随机性”解释。主 Agent 未传约束、测试读取了旧版本、外部写入超时但实际已成功，都是不同层次的问题。

### 11.3 讲义的三组实践原则

讲义第 58 页把实践分成 DEFINE、CONTROL、VERIFY & GOVERN。[L，PDF 第 58 页](#source-l)

**DEFINE：明确目标与假设。**先确认歧义，描述需求、不变量、约束和验收，而不只是追求一段听起来强大的提示词。

**CONTROL：分离提议与执行。**模型可以提出计划和候选修改，系统在提交前检查；上下文、来源与过期信息由明确机制管理。

**VERIFY & GOVERN：缩短验证循环，并测量更深一层。**频繁、低成本的检查比只在最后做一次大审查更有机会尽早发现问题；同时使用多种指标和能解释其行为的测试负载。

这些原则在前述材料中都有具体实现：工作方法由 Skill 表达，任务与消息由运行时管理，工作流持有控制结构，编译器测试把进展变成可观察信号。

### 11.4 模型与程序应如何分工？

下面是工程推导：模型处理需要理解、探索和判断的工作，如形成假设、追踪调用链、解释失败；代码处理可以明确检查的控制要求，如任务唯一归属、预算、依赖、结果完整性和验证记录。

“每项请求都必须有一个最终状态”没有必要依赖模型记忆；“这段实现是否违反授权不变量”则可能需要模型配合工具调查。

这不是说程序天然没有错误，而是把约束放在更容易测试与审计的位置。

讲义第 59 页的总结是：**不要期待 Agent 完全确定，要让外围系统值得依赖；自主程度应与风险相匹配。**[L，PDF 第 59 页](#source-l)

## 12. 实证阅读：The Shift to Agentic AI 到底支持什么结论？

### 12.1 研究对象不是多 Agent 架构竞赛

R5 比较个人用户、组织用户与 OpenAI 内部员工，观察 Codex 采用、委托任务、并发、执行时长和流程复用。它是使用数据的观察性研究，不是为某一 Team 架构做随机对照实验。[R5，摘要、§1、§3—5](#source-r5)

论文自己的界定也不是绝对二分：ChatGPT 有工具与 Agent 能力，Codex 有些交互也是纯对话；是否调用工具只是 agentic 程度的不完美代理指标。[R5，PDF 第 2 页脚注 1](#source-r5)

因此，“使用 Codex”不能直接等于“运行多 Agent 协作”，“多线程并发”也不能直接等于“Agent 彼此交换信息”。

### 12.2 四条主要观察如何与课程连接？

论文的总体框架可以概括为：采用快速但不均匀；委托以产出具体工作为导向；软件生产是主要领域但不局限于写代码；深度使用者更倾向于长任务、并发和可复用流程。[R5，§1，PDF 第 2—4 页](#source-r5)

与课程对应，Superpowers 和 Skill 让工作有程序；Subagents 和 Teams 让工作能够分配；Workflow 让重复分配与执行系统化；长任务机制扩大一次委托的范围。

这种联系解释了为什么更深的使用方式不只是“聊天更多”，而是人开始承担计划、监督、审查和集成的职责。[R5，§6](#source-r5)

### 12.3 采用率、token 总占比与人均占比必须分开

R5 第 7 页图 1 区分活跃用户中是否用过 Codex，以及 Codex 占两类产品输出 token 的比例。正文报告，相关窗口里个人活跃用户的采用率低于 1%，组织用户约 17.3%；但 token 占比分别更高。内部员工的采用与使用强度显著不同。[R5，§3，PDF 第 6—7 页、图 1](#source-r5)

论文还给出一个很能说明统计口径的例子：外部组织中的工程师，平均每人由 Codex 生成的 token 份额约 26.8%；但把该类用户的 token 全部汇总，Codex 占比约 88.3%。高强度用户对汇总量的贡献更大，因此两者不同。[R5，PDF 第 8—10 页](#source-r5)

这不是数字矛盾，而是加权口径不同。评估自己的系统时，也应区分“有多少人受益”“平均一人怎样变化”和“总输出怎样变化”。

### 12.4 并发指标测量的是观测周内峰值

R5 第 17 页图 9 使用不同线程中超过 30 秒的执行重叠，统计用户一周内的峰值并发。正文报告，组织用户约 67.4%、个人用户约 63.9% 在该期没有并发；内部样本只有约 10.7% 始终只使用一个执行流，约 28.6% 在某一时刻达到五个或更多并发 Agent。[R5，§5.1，PDF 第 17—18 页](#source-r5)

它支持“部分用户开始管理多条并行工作”，但不证明持续整周保持高并发，不证明这些 Agent 相互通信，也不证明五个一定优于两个。

**人的工作组合并行，与单个任务内部的多 Agent 协作，是不同的分析单位。**

### 12.5 为什么一天可以有 71 个 Agent-hours？

论文报告，2026 年 6 月 11 日内部员工中位数的 Codex 累计运行时间约 2.5 小时；高强度分位用户的日累计时间可到约 71 小时，因为并发执行时间相加。统计还有响应间隔处理、起始日期归属，以及非交互批处理排除等规则。[R5，§5.2，PDF 第 18—19 页](#source-r5)

这个指标描述执行强度，不能直接解释为节省相同小时数的熟练人工劳动。真正的节省还取决于交付质量、监督、返工和对照工作方式。

### 12.6 “请求越来越复杂”怎样被估计？

论文用一个模型分析请求，估计熟练人类在没有 AI 时完成实质任务所需的主动工作时间。复杂度分析采用允许相关数据用于模型训练的个人用户中的 0.1% 随机样本。[R5，§4.2，PDF 第 12—14 页](#source-r5)

正文报告，至少提交过一项估计需要一小时任务的用户占比，从 2025 年 12 月的 35.4% 升至 2026 年 5 月的 70.2%；八小时阈值相应从 2.1% 升至 25.6%。这是用户在指定窗口中是否达到阈值，不是所有请求都达到了该复杂度，也不是成功完成比例。[R5，§4.2、图 6](#source-r5)

按这两个正文端点直接相除，八小时阈值约为 12.2 倍；摘要使用的是不同概括口径的“接近十倍”。引用时应明确时间窗和指标，而不是把各种宣传性近似表达混成一个精确数字。图 6 还注明部分月份数据不完整。[R5，摘要；图 6 图注](#source-r5)

### 12.7 附录 F：自动复杂度估计器怎样验证？

附录 F 说明使用 `gpt-5-mini` 估计主动工作分钟数，排除等待、审批、构建与 AI 运行时间等；没有实质请求时返回零。随后在 1,000 道随机 Codeforces 问题上，把估计值与最快五位人类的平均解题时间、题目难度分数比较。[R5，附录 F，PDF 第 49—50 页](#source-r5)

第 50 页图 A9 报告两种相关系数约为 0.65 和 0.69。作者也指出，对照组偏向竞赛程序员，估计时间通常比这些最快解题者更长。[R5，图 A9 与附录 F](#source-r5)

这支持估计器在一定程度上区分相对难易。**工程分析：**相关性不等于绝对时间校准正确；竞赛题上的验证也不直接证明大型工程或知识工作上的时间估计准确，更不能用来证明 Agent 真正完成了相应劳动。

这里对 Agent Eval 最有价值的启示，是评分器也要说明输入、口径、验证范围和局限，而不是因为它使用另一个模型就默认可信。

### 12.8 工作系统化为何重要？

论文第 5.3 节把从临时委托转向可复用流程基础设施的变化称为系统化。Skill 可以承载程序性上下文，Plugin 可以把 Skill、工具和相关集成打包分发。[R5，§5.3，PDF 第 19—22 页](#source-r5)

图 11 与正文报告，在截至 2026 年 6 月 11 日的七天窗口中，至少使用过一个 Skill 的活跃用户占比：个人约 25.7%，组织约 30.4%，内部约 96.2%；不同 Skill 来源允许同一用户重复出现在多个分类中。[R5，图 11、PDF 第 20—21 页](#source-r5)

这些观察不能单独证明 Skill 的因果生产力收益。但它们支持作者的解释：深度使用不仅依赖通用模型能力，还依赖把本地规范、重复流程和组织背景附着到执行过程上。

### 12.9 组织条件为什么影响同一种技术的使用？

论文明确说明，OpenAI 内部有较高熟悉度、组织支持、培训和知识共享，使用的边际成本条件也不同，因此不能代表一般组织。相关系统访问、权限、人员能力、管理预期和复核流程，都会影响采用。[R5，§1—2，PDF 第 2、5—6 页](#source-r5)

论文借用电气化的历史类比：仅更换动力来源、维持原布局，不等于重新组织生产过程。对 Agent 也是如此，仅把原流程的某一步换成模型，未必产生系统级收益；任务衔接和人机责任仍需重新设计。[R5，§5，PDF 第 15—17 页](#source-r5)

这是论文的解释框架，不是本文额外验证过的历史或因果研究。

### 12.10 九月材料：图表标题不能代替指标定义

讲义第 64—67 页展示九月内部使用报告的图表，应逐一按实际指标阅读：[L，PDF 第 64—67 页](#source-l)

| 讲义位置 | 图表实际表达 | 不能直接推出 |
|---|---|---|
| 第 64 页 | Agent workdays 与研究者 workdays 的比值，图中约 3.14 | 科研成果提高相同比例 |
| 第 65 页 | 每位活跃贡献者的代码改动行数，相对基准归一化 | 功能交付周期、代码质量、商业价值都提高近八倍 |
| 第 66 页 | 按任务复杂度区分零干预成功、需干预成功、失败、工具错误与无明确目标 | 大任务已经可以普遍无人监督完成 |
| 第 67 页 | 研究者使用量按 API 价格计量的变化 | 这些金额是组织实际现金支出或收益 |

第 66 页还需要核对分母：讲义图例保留工具错误与无明确目标类别；R6 网页 §3 的成功率图注明排除结果不确定的分类。图表口径不同，不能直接拼接成同一条成功率趋势。

尤其是第 65 页，标题写“Shipping Almost 8x Faster”，纵轴却是代码改动行数。本文保留原图的表达，同时明确其测量边界，不将标题直接升级为交付效率结论。

课程列出的九月在线报告还强调：研究过程有多个瓶颈，人仍负责设定方向与判断结果；代码和实验活动增加不等于整体科研速度同比增加，算力供给增长也影响实验数。该网页的正文已在线核对；它不构成上述活动指标的因果生产力验证。[R6，§1—2](#source-r6)

### 12.11 委托阶梯不是架构排行榜

讲义第 68 页把使用方式分为 Chatbot、Assistant、Agent、Multi-agent worker、Systematized workflows。这是从问答到交付、再到重复委托的工作组织阶梯，不应理解为“任何任务都必须升到最后一级”。[L，PDF 第 68 页](#source-l)

查一个简单事实可以继续用单轮问答；一个小修改可以留在主 Agent；成熟、重复、可检查的流程才适合进一步系统化。选择应由任务结构决定。

## 13. 学术抽象：并行上限、信息结构与错误相关性

> 本章用分析模型解释前述机制。这些公式是帮助解释机制的简化推导，不是 lecture-03 或五份附件报告的实测模型，不应作为未经验证的生产性能预测器。

### 13.1 三种关系，不能只画成一张“Agent 连线图”

**任务依赖图**表示先后关系：公共接口未确认，调用方实现就不能可靠开始。它决定潜在并行度。

**通信关系图**表示谁需要知道谁的发现：独立审查可以只返回主 Agent，竞争假设调查可能需要定向交换证据。它决定信息传输路径和成本。

**产物与状态依赖图**表示谁读写相同文件、数据库记录或接口：两个任务名不同，仍可能修改共同契约。它决定冲突与重新验证范围。

R2 的任务列表主要显式表达第一类；mailbox 表达第二类；编译器实验的 Git、checkout 和 CI 处理第三类的一部分。三类关系有关联，但不是同一结构。[R2，Architecture](#source-r2)；[R4，Running Claude in parallel](#source-r4)

由此得到一个设计问题：一个任务能否分派，不只看它是否可以用自然语言描述，还看它是否拥有足够清晰的输入、产物边界和验收方式。

### 13.2 为什么八个 Agent 未必有八倍提速？

假设总工作中可并行比例为 p，剩余部分必须串行；可并行部分能理想平均分配。再把额外协调开销记为 `T_coord(n)`：

$$
T_n=T_1\left((1-p)+\frac{p}{n}\right)+T_{\mathrm{coord}}(n)
$$

例如 p=0.8、n=8，暂不计算协调成本：

$$
\mathrm{Speedup}=\frac{1}{0.2+0.8/8}\approx3.33
$$

即使无限增加执行者，串行部分仍把理想上限限制在五倍。实际还存在启动、等待、工具限流、验证与集成开销。

这里采用的是简化并行分析，不是说所有 LLM 任务都有固定的 p。编译器实验恰好说明，p 会随着任务和验证环境改变：多个独立失败时并行空间大，所有人撞同一阻断错误时并行空间缩小，引入 GCC 定位后又被重新扩大。[R4，Make parallelism easy](#source-r4)

**先寻找关键路径和集成瓶颈，再决定是否增加并发。**

### 13.3 任务粒度决定哪里在浪费

可以把总成本写成一个记账框架：

$$
C_{\mathrm{total}}=C_{\mathrm{work}}+C_{\mathrm{context}}+
C_{\mathrm{coord}}+C_{\mathrm{verify}}+C_{\mathrm{rework}}
$$

分别表示有效执行、上下文准备、协调、验证和返工。切得过小，准备与交接占比上升；切得过大，串行路径和错误扩散范围增加。

这个公式的作用是提示测量，不是给出固定最优粒度。若主要成本来自重复读取背景，就改善公共背景供给；若来自公共接口冲突，就调整任务边界；若来自后期返工，就把验证前移。

### 13.4 主上下文更短，不意味着系统总消耗更少

假设十次调查各产生两万 token 中间材料，每次只返回五百 token 摘要。主 Agent 收到的摘要总量约五千 token，但子 Agent 产生和处理原始材料的成本仍然存在，公共背景也可能被重复读取。

这些是假设数字，仅用于区分指标。实际应分别测量主窗口占用、总输入输出、重复检索、墙钟延迟与质量，不能以其中一个替代全部。

Caveman 的压缩、子 Agent 的隔离和 Workflow 的脚本状态，各自优化不同位置的信息成本；提示缓存又只是计算复用层面的优化。[L，PDF 第 16—17、31 页](#source-l)；[R3，Prompt caching in a fan-out](#source-r3)

### 13.5 多个 Agent 的一致意见，为什么可能仍然很弱？

如果多个执行者共享相同错误前提或同一份不完整材料，它们的错误可能高度相关。给它们不同名字，不会自动产生独立证据。

用一个严格限制适用范围的统计类比：若 n 个估计量方差同为 `σ²`，两两相关系数都为 `ρ`，则其平均值的方差为：

$$
\operatorname{Var}(\bar X)=\frac{\sigma^2}{n}\left[1+(n-1)\rho\right]
$$

相对于独立估计量，可定义等效样本数：

$$
n_{\mathrm{eff}}=\frac{n}{1+(n-1)\rho}
$$

在 n=5、ρ=0.8 的假设下，等效样本数约为 1.19。这不是 LLM 多数投票准确率公式，也不能据此计算某次审查的置信度；它只说明相关性可能吞掉重复判断的收益。

因此，可靠性导向的并行更应当增加不同来源、可区分假设、反例或执行验证，而不只是重复采样相同输入。R2 的竞争假设和 R4 的外部参照分别体现了两个可操作方向。[R2，Investigate with competing hypotheses](#source-r2)；[R4，Make parallelism easy](#source-r4)

### 13.6 独立验证者的价值取决于它是否真的能发现错误

令 F 表示候选结果错误，A 表示验证器接受它，则：

$$
P(F\cap A)=P(F)P(A\mid F)
$$

这是条件概率恒等式，不需要假定生成器和验证器独立。它提醒我们：只增加一个“验证 Agent”，不保证 `P(A|F)` 足够低；若验证器只阅读生成者的自述，不回到代码、数据或测试，它可能延续相同错误。

因此，应问验证者能接触什么证据、能实施什么检查，以及在哪些失败类型上被测试过，而不是只问角色是否存在。

### 13.7 什么时候值得再启动一个 Agent？

可以将决策表述为一个待评估的边际问题：新增执行者带来的覆盖、延迟改善或有效反例，是否超过其上下文、协调、验证与返工成本？

材料不提供适用于所有业务的统一阈值。这个阈值应该通过任务分层实验获得：独立批量工作、强依赖修改、根因调查、跨来源研究分别测量。

**最小有效协作结构**比最大的团队更值得追求：足够获得需要的信息和吞吐量，同时避免没有新增信息的组织层级。

## 14. 工程综合：一个可靠 Multi-agent 系统需要哪些边界？

> 本章是由课程机制推导的设计方案，不是 Claude Code 或编译器原型的内部实现说明。对小团队而言，可以从清晰的数据结构、一个任务状态存储和一个产物目录开始，不必为了“多 Agent”先引入庞大平台。

### 14.1 将工作上下文、权威状态与证据分开

| 存储或执行位置 | 应保存什么 | 不应被当成什么 |
|---|---|---|
| 主 Agent 上下文 | 当前目标、关键取舍、必要摘要 | 全部原始日志仓库 |
| Worker 上下文 | 当前子任务的背景和探索过程 | 系统权威状态 |
| 任务状态存储 | 任务、依赖、负责人、尝试次数、状态 | 模型随意描述的“进度” |
| 证据与产物存储 | 原文、diff、测试日志、版本与定位 | 没有来源的结论堆积 |
| 经整理的记忆 | 可复用规范、经验及适用条件 | 永不过期的事实真相 |

R1 的上下文与 transcript、R2 的本地任务列表、R3 的执行记录、R4 的 Git 与日志，分别展示了这种分离的必要性。[R1，Manage subagent context](#source-r1)；[R2，Architecture](#source-r2)；[R3，How a workflow runs](#source-r3)；[R4](#source-r4)

### 14.2 完成状态分两层：执行结束与业务验收

自建系统可以采用如下业务状态机：

```text
pending → running → submitted → verified → integrated
                    ↓            ↓
                 rework        rejected

其他合法状态：blocked / failed / cancelled / partial
```

这不是产品内置状态清单。它表达：Agent 返回候选产物只到 submitted，经过检查才到 verified，合入目标版本后才到 integrated。

如果“完成”只来自一句自然语言，下游很难区分产物缺失、验证未运行和真正完成。权威状态应由被允许的系统动作更新。

### 14.3 用版本绑定每个结论和验证结果

一份“测试通过”至少要说明：测试命令、测试条件、产物版本、结果位置和执行时间。数据类任务还应绑定数据快照或 as-of 语义。

A 对版本 v1 的审查通过后，B 修改了公共接口，不能直接把 A 的通过记录用于 v2。跨 Agent 协作中，过期的正确结论也会造成错误。

因此，集成不是机械拼接各方摘要，而是判断哪些结论在当前版本下仍然有效，并触发必要复查。

### 14.4 重试、租约与过期执行者

设 Worker A 超时，任务重新交给 B。A 随后恢复并提交旧结果。若系统只看任务 ID，不看当前尝试编号，就可能被过期结果覆盖。

一种工程方法是为任务尝试分配递增编号，仅接受当前有效尝试；任务领取具有租约与心跳；候选提交校验 task_id、attempt_id 和基线版本。

但是，这种检查只在相应提交点生效。若 A 已经向外部系统发起不可逆动作，事后拒绝它的结果并不会撤销动作。还要让外部接口支持幂等标识，或把写入集中到受控的提交阶段。

**防止过期结果覆盖、避免重复副作用、回滚既有修改，是三个不同问题。**R3 的恢复限制正说明不能把它们统称为“自动重试已经解决”。[R3，Resume after a pause；When an agent stalls and restarts](#source-r3)

### 14.5 权限应在有效工具与执行环境中体现

“只读审查”不应只是一句提示。应核对实际工具、可访问目录、数据库账户、网络与外部写权限。R1 的 memory 和 R2 的 teammate 定义复用，都说明有效能力可能不同于表面配置。[R1，Enable persistent memory](#source-r1)；[R2，Use subagent definitions for teammates](#source-r2)

不同工作树不是独立权限域；容器存在也不自动证明凭证和网络隔离配置正确。真正应检查的是具体资源边界。

Agent 之间的消息按协作数据处理，不能被升级为用户授权。需要批准的动作应绑定批准主体、对象、范围与版本。

### 14.6 总预算必须覆盖所有后代工作

每个 Agent 允许十二轮，不等于系统只执行十二轮；允许递归分派时，节点数还会增加。总预算应累计模型调用、工具成本、schema 重试、失败恢复以及验证成本。

至少区分四种限制：递归深度、同时运行数、累计调用数、累计花费或时长。R1 和 R3 使用不同的限制机制，说明不能以一个局部产品参数代替全系统控制。[R1，Concurrent subagent limit](#source-r1)；[R3，运行限制与规模建议](#source-r3)

### 14.7 可观测性要能解释“为什么接受这个结果”

建议记录：任务和父任务、执行尝试、模型与提示版本、Skill 和工具的有效配置、输入/产物版本、调用结果、时长与用量、证据引用、验证器版本、接受或拒绝原因、人工决定。

重点是外部可检查事件，不需要把模型自由形式的内部解释当作事实日志。

一次失败应能还原：谁根据哪份前提做了什么，改变了哪个产物，什么检查没有拦住问题。这样下一次改进才能落到任务、上下文、协调、工具或验证中的具体层次。

### 14.8 故障恢复前先观察当前世界

恢复入口应重新读取任务状态、候选产物与外部动作记录，而不是只恢复旧提示。尤其在 R3 的重启路径中，旧 transcript 不在，但旧文件修改仍可能在。[R3，When an agent stalls and restarts](#source-r3)

一个合适的恢复动作可能是继续既有补丁、验证已有产物、回滚到基线、重新分派，或等待人工判断。没有一种“永远从原提示重来”的策略适合所有副作用。

## 15. 端到端教学案例：审查、修复并验证一套 RAG 服务

> 本章将前文机制放进同一个示意流程。所有任务、路径与问题都用于教学；没有执行真实仓库修改，也没有报告实测效果。

### 15.1 先定义终态，不急着定义角色

目标是：用户只能获得其有权访问的文档内容；缓存不能跨越授权边界；引用能回到实际使用的文档版本和片段；已有功能不因修改退化。

需要先确认身份从哪里来、访问权限由哪个系统定义、授权对象粒度、缓存键规则、文档版本语义，以及何种情形允许返回“不足以回答”。这是 Superpowers 的需求与设计阶段。

验收不能只有“增加一个权限函数”。它必须覆盖授权结果如何贯穿检索、缓存和引用路径。

### 15.2 固定共享契约与可用工具

把公共约定写成版本化文件，例如用户身份只能来自服务端认证结果，检索候选包含稳定文档标识与版本，引用定位依赖实际检索证据。

不同执行者读取相同契约；必要条款还应写入委托消息，以防特定启动模式没有加载预期项目背景。只读调查和修改执行使用不同工具权限。

### 15.3 按依赖分任务，而不是照组织职位分任务

| 任务 | 必要前提 | 交付物 |
|---|---|---|
| T0：梳理公共权限与引用契约 | 需求已澄清 | 经确认的规范与验收清单 |
| T1：审查检索授权路径 | T0 | 带证据的候选问题 |
| T2：审查缓存隔离路径 | T0 | 命中/未命中行为与候选问题 |
| T3：审查引用访问路径 | T0 | 来源定位与授权缺陷候选 |
| T4：验证候选发现 | 对应调查已返回 | supported/refuted/unverified 记录 |
| T5：生成修复 | 经验证且获准的发现 | 独立工作区中的补丁 |
| T6：集成与回归 | 对应补丁已通过检查 | 最终版本与验收证据 |

T1—T3 可以并行，但它们都依赖 T0。跨路径发现可以产生新的验证任务，而不是强迫每个 Agent 都在最初范围内独自给出全局结论。

### 15.4 一次交接应该长什么样？

例如给缓存调查者的任务：

> 以提交版本 X 和权限规范 V 为基线，只读检查查询缓存。全局中间件负责身份认证，但文档授权仍需追踪。请比较缓存命中和未命中两条路径，关注不同用户、不同访问范围、文档权限变化后的行为。每项发现返回代码位置、触发条件和证据。没有测试环境时明确列出未验证项，不修改源代码，也不要自行调整业务权限规范。

它显式传递前提、范围、输出和禁止行为，避免“你检查缓存安全”这种过宽委托。

### 15.5 何时启动横向协调？

如果 T2 发现某种异常只在缓存命中发生，而 T1 已确认未命中路径正常，可以将两份证据合成一个定向验证任务。

无需让所有执行者持续广播全部日志。只交换足以改变其他人下一步行为的信息：已验证的事实、被排除的假设、阻断依赖和明确请求。

这种选择同时利用 Subagents 的上下文隔离与 Teams 的协作思路，而不是把两者当作非此即彼的产品阵营。

### 15.6 验证者应回到原始产物

验证 Agent 不能只阅读初查者的摘要并判断“有道理”。它应核对相关代码、公共规范、调用链与可用测试，必要时构造反例。

如果测试环境失败，执行状态写 failed 或 partial，事实判断写 unverified；不能自动写“问题被反驳”。

如果初查依赖了错误前提，验证应指出具体前提和来源，便于修订任务模板，而不是仅给一个低分。

### 15.7 修改阶段降低写入冲突

经验证、需要修复的问题进入独立工作区。公共返回结构由明确负责人修改，其他执行者遵循同一版本契约。跨模块修改完成后，再集成到目标分支运行回归。

单个补丁测试通过，不代表全部补丁合并后通过；一次旧版本审查也不自动对新版本有效。

可采用“并行调查、受控修改、集中集成”的初始结构，再根据实际评测逐渐扩大自动化边界。

### 15.8 反例测试要针对真实要求

可考虑的教学测试包括：无文档权限用户不能通过检索和引用获得内容；同一查询切换用户后不错误复用旧访问范围；权限变化后缓存按设计失效或重验；引用指向真实使用的版本；证据不足时不伪造来源；最后集成版本仍通过既有功能检查。

这里不是宣称这些测试已经充分证明安全，而是展示验收应围绕业务不变量，而不是只检查代码能否运行。

### 15.9 最终交付应包含结果与边界

最终报告至少说明：检查范围、基线与最终版本、实际完成项、已验证发现、已拒绝发现、未完成项、修复摘要、测试产物和仍需人工决定的问题。

报告生成者不能因为部分失败项没有进入摘要，就声称全范围完成。权威任务清单应参与最终一致性检查。

### 15.10 开发时多 Agent，不等于产品运行时多 Agent

可以用多个 Coding Agent 协同开发这个服务，但上线后的普通问答完全可能只是明确的身份校验、受权限约束的检索、回答生成和引用校验。

只有运行时任务本身需要独立探索、不同假设、跨来源核验或动态补充证据，才有理由继续设计多个自主执行者。

**用 Multi-agent 开发系统，与开发一个运行时 Multi-agent 系统，是两项不同的架构决策。**

## 16. 评测：如何证明多 Agent 的收益来自正确的地方？

> 本章是工程评测建议。它延续讲义“测量更深一层”的要求以及 R5 对测量口径的提醒，不报告本文未执行的实验结果。[L，PDF 第 58 页](#source-l)；[R5，附录 F](#source-r5)

### 16.1 建立能够解释收益来源的基线

| 方案 | 用来回答的问题 |
|---|---|
| 强单 Agent | 一个组织良好的执行者能做到什么？ |
| 单 Agent＋相同 Skill | 收益是否主要来自程序与提示改善？ |
| 相同工作拆分、串行子 Agent | 上下文隔离本身是否有价值？ |
| 主 Agent＋并行子 Agent | 并行是否进一步改善延迟和覆盖？ |
| Team | 横向交换发现是否值得新增成本？ |
| 脚本 Workflow＋独立验证 | 覆盖追踪、恢复与验证是否改善可信交付？ |

不必一次实现所有方案，但至少应避免给多 Agent 方案更好的规范、更强工具和更多预算，却把所有改善都归因于“Agent 数量”。

### 16.2 保持比较条件可解释

固定任务集、代码或数据快照、工具权限、验收条件；记录模型、提示、Skill 和运行模式。重复执行，报告分布，而不是每个方案只演示一次。

分别在固定成本预算下比较质量，以及在相近质量要求下比较成本与延迟。相同 token、相同金额和相同时间预算不是同一实验条件，应明确选用哪一种。

人工监督也应记录，否则一个方案暗中依赖大量人工救场，仍可能在表面成功率上领先。

### 16.3 评测对象是验证合格的交付，而不是活动量

主要指标可以包括独立验收成功率、发现的精确率与召回率、引用有效性、范围覆盖、总成本、墙钟延迟、人工复核与返工时间，以及有写操作时的回归和重复副作用。

token 越多、Agent-hours 越长、代码改动越大，都不能单独解释为效果更好。R5 和讲义图表中的测量边界已经说明这一点。[R5，§5](#source-r5)；[L，PDF 第 64—67 页](#source-l)

### 16.4 将覆盖分成“执行过”和“验证过”

一个教学式指标定义：

$$
\mathrm{ExecutionCoverage}=\frac{\text{完成规定执行步骤的任务数}}{\text{要求处理的任务数}}
$$

$$
\mathrm{VerifiedCoverage}=\frac{\text{具备规定验证证据的任务数}}{\text{要求处理的任务数}}
$$

这些只是建议口径。必须先定义任务单位和验证要求，并约定分母为零或范围未知时如何处理。它们不等于事实完整性：即使所有文件都检查过，也可能漏掉跨文件问题。

### 16.5 验证器本身也要评测

给验证器提供已知正确、已知错误、证据不足、版本错配、引用失效等样例。测量它是否把未知当错误、是否被生成者的自信措辞影响、是否遗漏关键反例。

R5 附录 F 的方法提示我们：自动评估器也需要外部校验，并报告它在哪些范围内有证据支持。其 Codeforces 相关性结果不能直接替你验证业务评分器。[R5，附录 F](#source-r5)

### 16.6 做消融，而不只是比较最终总分

有解释力的消融包括：去掉横向消息，保持其他条件；去掉独立验证；改变子任务粒度；共享或不共享公共背景；统一模型；保持总预算改变并发；改变恢复策略。

若去掉聊天后质量不变而成本下降，就说明通信可能没有新增信息。若加入验证后误报下降但延迟过高，应继续优化验证成本，而不是立即再加一层管理 Agent。

### 16.7 必须覆盖的故障注入场景

| 注入场景 | 应观察什么 |
|---|---|
| 子任务限流或取消 | 失败项是否仍出现在覆盖清单中 |
| 部分写入后进程退出 | 重试是否识别已有修改 |
| Worker 超时后又恢复 | 过期结果是否被拒绝 |
| 消息写入失败 | 是否错误报告已发送 |
| 基线被其他任务更新 | 旧验证是否被错误复用 |
| Skill 缺失或配置未生效 | 是否能发现有效上下文不符合预期 |
| 验证器无法访问工具 | 是否标记 unverified 而非 refuted |
| 任务清单为空或枚举不完整 | 是否错误报告全范围无问题 |
| 总预算耗尽 | 是否能够停止后代任务并说明未完成范围 |

这些是从 R1—R4 的具体机制推导的测试设计，不代表材料已经穷举所有故障。

### 16.8 将失败归因到可以修复的层次

交接遗漏应改任务输入；重复领取应改协调；过期结果覆盖应改状态协议；问题证据不足应改调查方法；测试通过但业务错误应改验证器；局部正确但合并失败应改接口与集成。

“模型幻觉”可能描述了现象，却往往不足以指导修复。应保留导致错误的输入、动作、版本和验证记录，才能形成可复用回归集。

<a id="s17"></a>
## 17. 选择方法、课程回顾与复习路径

### 17.1 用最小有效结构解决任务

| 任务特征 | 优先考虑 | 首先检查的风险 |
|---|---|---|
| 小改动、频繁往返、共享大量背景 | 主 Agent | 不必要的交接 |
| 重复执行某种程序 | Skill | 可用但未实际加载或执行 |
| 独立、结果明确、高噪声调查 | Subagent | 关键前提未传递 |
| 中间发现会改变其他成员行动 | Team 或明确的消息协作 | 无效讨论、状态与产物冲突 |
| 大规模、重复、需要追踪覆盖和恢复 | 脚本 Workflow | 静默漏项、重放和副作用 |
| 长时间推进可验证目标 | 上述结构加长任务控制 | 无进展、预算与错误终态 |

这张表综合讲义与 R1—R4 的判断边界，不是要求所有任务依次升级到最复杂形态。[L，PDF 第 37、38、46 页](#source-l)；[R1](#source-r1)；[R2](#source-r2)；[R3](#source-r3)

### 17.2 讲义末尾“Beyond Claude Code”应该怎样读？

可选页列出不同 Coding Agent，并提出五个比较维度：开放性、供应商绑定、隔离与权限方式、本地与云执行、功能完整与最小内核。[L，PDF 第 71—72 页](#source-l)

这些维度可以保留为选型问题，但不能把课堂快照中的产品分类直接当作当前产品事实。例如，“权限提示”与“操作系统沙箱”并非逻辑上互斥，具体产品可能同时有多种机制。本文不在没有逐项验证的情况下扩展成最新产品比较或采购建议。

### 17.3 本课的八个核心判断

**第一，先形成可以委托的工作。**目标、输入、边界和验收比角色名称更重要。

**第二，上下文隔离与信息交接是一对取舍。**更干净的窗口可能伴随更高的前提遗漏风险。

**第三，任务状态、消息状态和产物状态必须分开。**“返回了”“发出去了”“通过了”不是同一个事件。

**第四，工作流负责控制结构，Agent 负责局部判断。**规模化不能只靠一个模型记住全部进度。

**第五，恢复不等于回滚。**重新执行前必须面对已经变化的外部世界。

**第六，验证器能改变任务本身。**好的验证不只是打分，还能创造可独立推进的问题。

**第七，活动量不等于价值。**并发、token、运行时长和改动行数都需要与合格交付区分。

**第八，自主程度应与风险和可验证程度匹配。**不能让外围系统只是不断相信模型说自己已经完成。

### 17.4 建议的实践顺序

先让一个 Agent 按明确方法稳定完成一项工作；再定义交接和证据结构；接着在只读、独立任务上试有限并行；只有需要交换中间发现时才引入协作；最后把稳定流程固化为脚本，并加入故障测试、预算与人工边界。

这样的顺序不是保守地拒绝多 Agent，而是让每次增加复杂度都有可以测量的原因。

### 17.5 总结整条课程链

```text
Superpowers：把目标整理成可执行方法
        ↓
Caveman：让决策上下文保留高价值信息
        ↓
Subagents：让独立执行者获得任务与必要背景
        ↓
Agent Teams：显式管理成员、依赖和信息交换
        ↓
Dynamic Workflows：用代码持有规模化调度与结果
        ↓
长任务 + 编译器案例：用外部状态与验证持续推进
        ↓
Software 3.0：把不确定判断放进可依赖系统
        ↓
Codex 研究：人类工作转向委托、监督、复核与系统化
```

这条链并不是产品演进的严格历史顺序，而是本文沿讲义组织的学习顺序。

**最终要设计的不是一个热闹的 Agent 团队，而是一套能把工作交出去、把证据拿回来、在失败后恢复，并对交付负责的系统。**

| 全部文件均被枚举 | 容易理解为语义全覆盖 | 跨文件调用链和组合问题仍需检查 |
| “8 倍提速” | 容易理解为交付时间缩短八倍 | 讲义第 65 页图表衡量代码改动行数，不直接衡量交付周期 |
| 71 Agent-hours | 容易理解为省下 71 小时人工 | R5 是并发累加运行指标，人工节省需要独立测量 |
| 复杂度达到八小时 | 容易理解为成功完成八小时劳动 | R5 是请求复杂度估计，不是实际完成率 |
| 权限提示与沙箱 | 容易视为二选一的产品类别 | 这是不同控制层，具体配置可以并存；讲义可选表不等于当前全量产品核查 |

来源定位分别见 [L](#source-l)、[R1](#source-r1)、[R2](#source-r2)、[R3](#source-r3)、[R4](#source-r4)、[R5](#source-r5)。

## 附录 C. 工程工作单与复习练习

> 以下模板属于本文的工程整理，字段可以按业务简化，不是某个框架要求的固定格式。

### C.1 启动新 Agent 前的工作单

| 问题 | 需要填写的答案 |
|---|---|
| 为什么不用主 Agent 直接完成？ | 独立探索、隔离上下文、权限边界或并行收益 |
| 它真正需要知道什么？ | 目标、约束、版本、公共前提与原始资料入口 |
| 哪些内容只按需读取？ | 大文件、完整日志、历史尝试与辅助资料 |
| 能做什么，不能做什么？ | 有效工具、目录、外部资源、写入与授权范围 |
| 产物是什么？ | 补丁、证据列表、复现测试或结构化分析 |
| 谁验证，怎样验证？ | 验证器、验收标准、对应版本与证据存储 |
| 何时停止或升级？ | 完成、预算、无进展、信息不足或人工决定 |
| 重试会改变什么？ | 已有产物、幂等标识、过期尝试和副作用 |

### C.3 一次恢复前的检查记录

恢复时检查：当前任务的有效尝试编号；最新基线与候选产物；旧尝试是否仍然运行；哪些外部动作可能已发生；哪些证据仍适用于当前版本；下一步是继续、验证、撤销、重新分派，还是转人工。

不要只保存“请继续”的提示。恢复的对象是工作状态，不只是对话文本。

### C.4 八个复习问题与答案要点

| 问题 | 答案要点 |
|---|---|
| 相同模型的多个实例为什么仍可能有用？ | 目标、上下文、工具与验收边界不同；不必修改模型参数 |
| 子 Agent 最常见的信息误解是什么？ | 默认以为它继承了主会话已经知道的前提 |
| 为什么 Team 任务锁不足以避免集成错误？ | 任务归属一致不代表公共接口或产物语义一致 |
| 怎样识别无效协作？ | 消息很多，但没有新增证据，也不改变后续行动 |
| Workflow 比主 Agent 编排多解决了什么？ | 将控制结构与中间状态显式化，但未自动解决语义正确性 |
| 为什么重试可能比首次执行复杂？ | 新尝试的历史与外部世界可能不一致，旧副作用仍存在 |
| 编译器案例最重要的工程突破是什么？ | 改造验证环境，使整体失败能被局部定位与并行处理 |
| 判断 Multi-agent 是否值得采用看什么？ | 相同条件下的合格交付、成本、延迟、人工负担和故障表现 |

### C.5 一个小规模实验的记录模板

选择若干可公开或脱敏的真实任务，固定版本；分别运行强单 Agent、带相同 Skill 的单 Agent，以及有限并行子 Agent。记录任务类别、预算、执行条件、结果、验证证据、人工干预、失败层次和重试成本。

至少包含一个强依赖任务、一个独立批量任务和一个根因不明确的调查任务。不要在没有重复实验时，从一次成功演示推出整体优越性。

<a id="appendix-d"></a>
## 附录 D. 延伸阅读：失败分类与架构扩展

这两项不是课程上传的五份辅助材料。为补充失败诊断与扩展规律，同时避免把外部研究混入讲义，本附录单独列出。这里仅概括本次核对到的论文 v3 摘要结论，不冒充对全文所有实验的重新分析。

### D.1 MAST：把失败拆成可诊断问题

*Why Do Multi-Agent LLM Systems Fail?* 提出 MAST 失败分类与带标注的执行轨迹数据。摘要将 14 种失败模式归入系统设计问题、Agent 间不一致、任务验证三个大类，并讨论自动标注与人工标注的一致性。[E1，v3 摘要](#source-e1)

它对本课的补充，是提醒我们把失败定位到规格、交接、协调和验证等不同层次，而不是笼统归因于模型。正文第 16 章的故障归因表是本文工程整理，不是对 MAST 全部 14 类的逐项翻译。

### D.2 Scaling Agent Systems：协作收益依赖任务与架构匹配

*Towards a Science of Scaling Agent Systems* 在标准化工具、提示与计算条件下比较单 Agent 及多种多 Agent 架构。v3 摘要报告，可分解任务与强顺序依赖任务上的协作效果明显不同，单 Agent 能力、工具负担、协调与验证方式都会影响收益。[E2，v3 摘要](#source-e2)

它支持“先判断任务结构，再决定协作结构”的研究方向，但不提供可以直接用于所有业务或 Claude Code 配置的普遍增益。本文不把其具体基准结果当作本案例的性能预测。

---

**全文最后的判断标准：不是系统用了多少 Agent，而是它能否在明确成本、权限和验证条件下，持续交付可追溯、可恢复、可接受的工作。**
