### 1.2 真正需要讲透的是几组表面矛盾

**“交付前验证”与“反复验证会浪费”。** 讲义希望减少返工；Anthropic 反对机械验证仪式；PTE 展示了先完整推导、再调用工具重放结果的开销。共同的问题是：验证是否有明确对象、独立检查能力和停止标准，而不是要不要一律验证。[L，p. 9](#src-l) [A，Instructions](#src-a) [T，§6.2、附录 D.1](#src-t)

**“逐步骤切模型”与“尽量保持缓存”。** 路由可以降低单价，但模型或部分设置变化会影响前缀复用。选择更便宜模型之前，必须知道当前缓存、剩余步骤和切换成本。[L，p. 22](#src-l) [A，Prompt cache](#src-a)

**“减少 token”与“后面的步骤仍然更贵”。** 生成 token 变少，不代表已有上下文变短。PTE 论文把这种“输出前重后轻、计算成本后期上升”的差异作为重要分析对象。[T，图 5、图 8，pp. 7、14](#src-t)

**“压缩历史”与“丢失信息后重新工作”。** 一次摘要可以降低输入负担，也可能让 Agent 重读文件、重新搜索、重建缓存。净收益必须扣除这些反向成本。[L，p. 25](#src-l)

这些连接会贯穿全文。它们共同说明：优化变量并不独立，不能把几个局部节约比例直接相乘，宣称获得同样幅度的整体收益。

### 1.3 用“任务轨迹”作为贯穿全文的单位

以下是一个说明性任务：

> 比较一家公司两期财报，解释利润变化，并给出原文证据与页码。

一次用户请求可能触发定位文档、读取页面、抽取数字、计算、查补证据、分析、验证和最终交付。一段错误规划或一份超大工具返回，可能影响后面所有步骤。

因此，本文讨论的不是孤立的 `model.generate()`，而是从接收任务到成功、失败或明确转交的完整轨迹。后面的财务例子只用于说明软件流程与证据管理，不构成财务判断或投资建议。

## 2. 先定义“做对”，再讨论便宜：目标函数与成功成本

### 2.1 优化对象是完整配置，不只是模型

**解释性建模。** 把一个 Agent 配置记为：

$$
\pi=(\text{模型策略、effort、提示词、工具、上下文、调度、验证、停止规则})
$$

再评价三个维度：

$$
(Q(\pi),\ C(\pi),\ T(\pi))
$$

其中，质量 $Q$ 需要与业务验收条件对应，成本 $C$ 需要说明统计口径，时间 $T$ 需要说明是单次模型延迟、任务延迟还是整批完成时间。

一个工程目标可以写为：

$$
\min_{\pi}\mathbb{E}[C(\pi)]
\quad\text{s.t.}\quad
Q(\pi)\ge Q_{\min},\qquad
\Pr(T(\pi)\le D)\ge0.95
$$

其含义是：在质量与完成时限满足要求的配置中，寻找成本更低的方案。并不是默许减少证据、跳过测试或放弃困难任务来压低账单。

### 2.2 单次调用便宜，不等于交付便宜

**教学算例。** 对同一批十个任务：

| 配置 | 全部花费 | 成功任务数 | 每个成功任务分摊成本 |
|---|---:|---:|---:|
| A：便宜模型，失败较多 | 1 美元 | 2 | 0.50 美元 |
| B：较贵模型，成功较多 | 2 美元 | 8 | 0.25 美元 |

建议在业务仪表盘使用：

$$
C_{\mathrm{success}}=
\frac{\text{全部任务总成本，包括失败与返工}}
{\text{成功完成的任务数}}
$$

分子不能只算成功任务的调用。没有成功任务时，这个比值应标记为不可用或无穷，而不是显示为零。

但是，单独优化该比值仍然不够。系统可以通过只处理容易任务让数字变好，因此还必须同时报告覆盖率、任务解决数和成功率。Assignment 3 同时考察解决数、单位成功成本和单位成功时间，体现的就是多维约束。[H，pp. 6–7](#src-h)

### 2.3 先消除被全面超过的配置，再讨论权衡

**教学算例。**

| 配置 | 成功率 | 平均任务成本 | 平均完成时间 |
|---|---:|---:|---:|
| A | 80% | 0.20 美元 | 60 秒 |
| B | 85% | 0.12 美元 | 40 秒 |
| C | 92% | 0.30 美元 | 80 秒 |

B 在三个维度都优于 A，A 是被支配的配置。B 与 C 才构成真实的质量、费用、时间取舍。

**帕累托前沿（Pareto frontier）**就是不能在不牺牲其他指标的情况下被另一配置改进的候选集合。其工程价值是：别在明显低效的配置上讨论“质量与价格不可兼得”。先修复无效工作，系统可能同时更便宜、更好。

Anthropic 的提示词迁移实验提供了这种可能性：文章报告换模型带来约 18% 的成本下降，进一步清理反模式又下降约 9%，准确率上升约两个百分点。该实验人为植入了反模式，不能据此承诺任意生产提示词都有相同收益。[A，Instructions，图 3 对应正文](#src-a)

### 2.4 质量、延迟、吞吐量要分开

质量是有没有完成正确的任务；延迟是一个任务从开始到交付多久；吞吐量是单位时间能完成多少任务。并行启动更多工作可能缩短某个任务的等待，却占用更多资源，使其他任务排队。

**工程建议。** 至少同时看成功率、平均与 p95 成本、平均与 p95 完成时间、超时率，以及目标负载下的吞吐量。只看均值容易漏掉极少数失控轨迹。

### 2.5 生产总成本超出讲义的计费边界

讲义明确主要讨论 LLM 成本；生产中可扩展为：

$$
C_{\mathrm{total}}=
C_{\mathrm{LLM}}+C_{\mathrm{tools}}+C_{\mathrm{infra}}
+C_{\mathrm{human}}+C_{\mathrm{rework}}
$$

这是工程扩展，不是讲义原始公式。一个方案即使把 API 费用减半，如果人工审核时间翻倍、错误恢复增加，整体仍可能更贵。[L，p. 5](#src-l)

## 3. 建立成本账：Session、Turn、Step 与历史重放

### 3.1 讲义的乘法公式是一张诊断地图

讲义区分 session、用户 turn，以及一个 turn 内的多次模型和工具 step，并给出：

$$
\begin{aligned}
C\approx{}&\text{Users}
\times\frac{\text{Sessions}}{\text{User}}
\times\frac{\text{Turns}}{\text{Session}}\\
&\times\frac{\text{Steps}}{\text{Turn}}
\times\frac{\text{Tokens}}{\text{Step}}
\times\frac{\text{Price}}{\text{Token}}
\end{aligned}
$$

前两项是采用率与使用深度，通常希望增加；后面几项才是本节优化轨迹和单价的对象。[L，pp. 6–7](#src-l)

这不是严格要求所有平均值彼此独立的统计恒等式。做真实核算时，应逐调用求和；做诊断时，这个分解帮助回答：是任务变多、任务变难、调用变多、上下文变大，还是价格变了？

### 3.2 真正做账，要区分互斥计费桶

**工程建模。** 对第 $j$ 次调用定义普通输入 $U_j$、缓存写入 $W_j$、缓存读取 $R_j$、计费输出 $O_j$：

$$
C_{\mathrm{LLM}}=
\sum_{j=1}^{K}
\frac{p_{u,j}U_j+p_{w,j}W_j+p_{r,j}R_j+p_{o,j}O_j}{10^6}
$$

价格单位为美元/百万 token。输出应采用供应商实际计费口径，包括适用的推理 token；不能默认可见回答长度就是全部输出成本。

四个 token 桶必须互斥。不同供应商的 `input_tokens`、缓存字段和总 token 字段可能采用不同口径，因此适配层需要记录原始 usage，再转换为内部统一格式，不能无条件“总输入加缓存输入”。本文不将某个供应商的字段约定当作跨平台标准。

还应保存请求时的模型版本、价格版本、批处理方式和计费倍率，避免过几个月用新价格解释旧账单。

### 3.3 课堂数据提示：尾部轨迹与重复读取值得优先排查

| 讲义观察 | 数据 | 正确解释 |

### 3.4 平方增长从哪里来？

**解释性推导。** 初始上下文为 $H_0$，每次调用新增 $d$ 个 token，不压缩、不删除：

$$
I_k=H_0+(k-1)d
$$

$$
\sum_{k=1}^{K}I_k=KH_0+\frac{dK(K-1)}{2}
$$

例如初始 20K、每步增加 4K，10 次调用累计输入 380K，20 次则为 1,160K。调用数翻倍，累计输入超过三倍。

这展开了讲义 p. 9 关于历史反复读取的论述。但必须保留条件：缓存、压缩、裁剪、前缀改变和模型切换都会改变实际费用及计算；该式不是“每一步一定完整重算”的证明。[L，p. 9](#src-l)

### 3.5 一段无用工具结果，有“未来持有成本”

**解释性推导。** 若一份日志有 49K 无用 token，它们继续留在上下文中，将在后续调用反复被消费：

$$
\Delta C\approx
\Delta N_{\mathrm{tokens}}
\times N_{\mathrm{future\ calls}}
\times p_{\mathrm{effective\ input}}
$$

因此，越早进入轨迹的冗余，通常越值得优先处理。讲义 p. 16 的上下文裁剪与 PTE 论文的 first-step effect，在这里连接起来：早期冗余不仅影响当时输出，还可能增加后续 prefill 和 decode 的负担。[L，p. 16](#src-l) [T，§6.2、图 5、图 8](#src-t)

## 4. 深入 PTE：token 数不是计算成本的充分代理

### 4.1 论文解决的具体问题

《Beyond Accuracy: Unveiling Inefficiency Patterns in Tool-Integrated Reasoning》将 TIR 定义为模型推理与外部工具交替执行的场景。它关注两种机制：工具执行造成请求间停顿，KV cache 可能失效或不可复用；未经筛选的工具返回拉长上下文，使之后的生成访问更大的历史状态。[T，摘要、§3.1](#src-t)

它不只是说“多调用工具贵”，而是在问：**为什么相同数量的生成 token，放在不同上下文中，计算负担不同？**

### 4.2 Prefill 与 Decode 的不对称

论文使用的主要近似是：prefill 并行处理输入，主要受计算吞吐约束；decode 顺序生成 token，权重与 KV 读取使内存带宽成为重要瓶颈，尤其是长上下文的 KV 访问随历史长度增长。[T，§3.1，p. 3](#src-t)

这是该论文的建模假设，不是所有模型、批大小、硬件和 serving 配置下都严格成立的二分法。

可以将 prompt caching 类比为“复用读完相同材料后的中间状态”。但即使该状态已经存在，之后生成仍需使用历史状态，因此“复用 prefill”不等于“长上下文后续免费”。

### 4.3 PTE 公式逐项解释

论文提出 Prefill Token Equivalents：把不同计算阶段折算到“处理一个输入 token”的等价尺度：

$$
\mathrm{PTE}=
\sum_{i=1}^{K}
\left(D_{\mathrm{prefill},i}+\gamma L_{\mathrm{seq},i}D_{\mathrm{decode},i}\right)
$$

| 符号 | 论文含义 |
|---|---|
| $D_{\mathrm{prefill},i}$ | 第 $i$ 步截至当前的上下文 token 数，对应论文完整上下文 prefill 的近似 |
| $D_{\mathrm{decode},i}$ | 该步生成 token 数 |
| $L_{\mathrm{seq},i}$ | 该步开始生成之前的累计上下文长度 |
| $\gamma$ | 模型—硬件组合中，内存受限开销相对于 prefill 的折算系数 |

最关键的是乘积 $L_{\mathrm{seq},i}D_{\mathrm{decode},i}$：输出量相同，历史更长，生成负担也可能更大。[T，§3.2，p. 4](#src-t)

### 4.4 一个反直觉算例：说得更少，却计算更多

**教学算例。** 设 $\gamma=0.002$，并沿用论文的完整上下文 prefill 假设：

| 阶段 | 上下文长度 | 新生成 token | PTE 计算 | PTE |
|---|---:|---:|---|---:|
| 第一步 | 2,000 | 1,000 | $2000+0.002\times2000\times1000$ | 6,000 |
| 中间一步 | 10,000 | 600 | $10000+0.002\times10000\times600$ | 22,000 |
| 后面一步 | 40,000 | 200 | $40000+0.002\times40000\times200$ | 56,000 |

第三步输出只有第一步五分之一，但该近似指标明显更大。不能据此说真实任务延迟必然严格按这些比例变化；它说明的是“只看输出 token 会遗漏什么”。

论文图 8 呈现生成长度的 first-step effect，图 5 则呈现累计上下文下后续 PTE 上升，两张图需要对照阅读。[T，pp. 7、14](#src-t)

### 4.5 $\gamma$ 如何从硬件量推导？

论文近似一个 prefill token 的计算量为：

$$
C_{\mathrm{prefill}}\approx2N_{\mathrm{params}}
$$

其中 $N_{\mathrm{params}}$ 为活跃参数数目。对于简化的 FP16 KV 表示，读取一个历史位置的 KV 访问量写作：

$$
S_{\mathrm{KV}}=4n_{\mathrm{layers}}d_{\mathrm{model}}\quad\text{Bytes}
$$

然后以论文所称的 Hardware Operational Intensity：

$$
\mathrm{HOI}=\frac{\text{Peak FLOPs/s}}{\text{Peak Bytes/s}}
$$

将带宽开销换算成等价计算量，得到：

$$
\gamma=
\frac{2n_{\mathrm{layers}}d_{\mathrm{model}}\mathrm{HOI}}
{N_{\mathrm{params}}}
$$

GQA 按 KV/Query head 比例调整；MLA 使用压缩维度替代相应表示维度。这些是论文建模中的修正，不是本文重新测出的硬件结果。[T，§3.3、附录 A](#src-t)

**低 $\gamma$ 不等于绝对速度快。** 它描述相对于该模型 prefill 单位的上下文扩张代价。大模型的一个 prefill token 本身可能更贵，因此不能直接用不同模型的 $\gamma$ 给 tokens/s 排名。论文附录 A.4 也明确作此区分。[T，pp. 12–13](#src-t)

若为了理解量纲，将 PTE 乘回某模型的 prefill 单位时间，可写出粗略推导：

$$
\widehat T_{\mathrm{model}}\approx
\frac{2N_{\mathrm{params}}}{F_{\mathrm{effective}}}\mathrm{PTE}
$$

这仅帮助理解换算关系，不是完整 serving 延迟公式，更不是线上容量规划的替代品。

### 4.6 实验支持到什么程度？

论文的延迟验证使用 DeepSeek-V3.2、8×H200、vLLM TP=8、256 并行请求，并记录纯模型生成延迟，明确排除了工具执行和网络传输时间。文中报告 PTE 与这类延迟具有较高相关性。[T，§4.1、附录 B.3](#src-t)

跨硬件部分是对 $\gamma$ 的敏感性分析：在已有 WebInstruct-Verified 轨迹上，使用不同硬件参数重新计算 PTE 并比较排名，不是把全部模型在每种设备上完整重跑。[T，§4.2、附录 A.3](#src-t)

论文也承认，PTE 不覆盖 API 等真实系统开销，$\gamma$ 简化了硬件优化与运行时动态，跨领域泛化仍需更多验证。[T，§9](#src-t)

### 4.7 三个不能混为一谈的指标

| 指标 | 衡量什么 | 不能代替什么 |
|---|---|---|
| API 美元账单 | 供应商按 usage 与价格计算的费用 | 不是物理计算量 |
| PTE / 模型性能剖析 | 模型轨迹中的近似计算负担 | 不是工具与网络在内的端到端延迟 |
| 任务 wall-clock | 从任务开始到交付的真实等待 | 不自动解释是哪一层造成慢 |

特别注意：原始 PTE 把该步完整上下文计入 prefill，重点分析 cache 不可复用场景。若系统具有稳定前缀复用，不能将完整输入都当成每轮实际重算量。可以另外记录真正的新计算部分，但那是对原指标的工程扩展，应另行标注并验证。

### 4.8 高 PTE 是诊断线索，不是失败判决器

论文观察到高 PTE 与错误轨迹共同出现，并明确说这是相关性。附录控制难度后报告的相关系数约为 $-0.040$，即使统计上显著，效应量也很小，不能据此建立“贵了就一定快失败”的判断。[T，§7、附录 F.3](#src-t)

工程上应把它与重复错误、无新增证据、状态停滞等信号结合，而不是只因任务已经昂贵就宣布停止或成功。

## 5. 低效轨迹、提示词与验证：减少无用功，而不是减少必要工作

### 5.1 四种低效模式应当如何读？

PTE 论文将观察到的问题组织为四类。分类是诊断起点，不是可以不加判断地部署的禁止规则。[T，图 2、§6.2、附录 D–E](#src-t)

| 模式 | 典型行为 | 可能的工程问题 | 不应作出的过度结论 |
|---|---|---|---|
| Confirmatory Tool Usage | 已经长篇得到答案，再调用工具重放同一计算 | 内部推导与工具功能重叠 | 不能据此说所有事后验证都浪费 |
| Tool-Mixing | 搜索得到文字后，再用 Python 打印同一段文字 | 工具切换没有新增证据或状态变化 | 不能据此禁止检索与计算组合 |
| Lack of Tool Priors | 不理解执行环境，例如 Python 执行后没有输出 | 工具契约、示例和模型训练分布不匹配 | 不能仅凭失败轨迹确定训练数据究竟缺了什么 |
| Tool Format Collapse | 幻觉工具名、参数类型或调用格式，反复解析失败 | 模型、chat template、解析器与 schema 不兼容 | 不代表问题语义本身一定太难 |

论文在各模式最明显的特定模型—任务组合中报告：确认式使用的 PTE 倍率为 1.77×，工具混用为 2.42×，工具先验不足为 2.15×；格式崩溃没有给出相同意义的倍率。这些是组间描述，不是任何任务上增加或删除一次调用的因果效果。[T，表 7，p. 17](#src-t)

### 5.2 为什么“交付前验证”与“不要验证仪式”并不矛盾？

讲义希望通过运行测试和检查输出减少用户返工。Anthropic 则警告“重复核验两次”“务必极其彻底”等笼统指令可能被模型机械执行，造成额外推理、重复查订单或过多知识库搜索。[L，p. 9](#src-l) [A，Instructions](#src-a)

关键是：**验证能发现哪一种错误？**

| 验证动作 | 可以检查什么 | 通常检查不了什么 |
|---|---|---|
| 把模型的结论再打印一次 | 是否执行了打印 | 结论真假、计算正确性 |
| 用 Python 计算同一个公式 | 算术和程序执行问题 | 原公式是否正确建模 |
| 用独立枚举验证推导 | 部分公式或推导错误 | 枚举程序与需求同时理解错误 |
| 运行回归测试 | 测试覆盖到的执行错误 | 没被测试覆盖的行为 |
| 以原文核对数字、日期和单位 | 引用与口径一致性 | 所有未被提出的业务问题 |

因此，“验证是否改变了最终答案”不是判断价值的充分条件。一个真正有检错能力的验证，即使最终确认答案正确，也可能值得执行。

**工程建议。** 把验证写成四部分：对象、独立检查方法、通过条件、失败动作。例如，“逐个核对引用是否指向实际页面；核对所引数字及单位；不匹配则重取证据”，比“全面再想一遍”明确得多。

### 5.3 论文的确认式算例还揭示了什么？

附录 D.1 的概率题中，模型已经详细计算并得到正确结果，随后用 Python 再计算同一组组合数。论文将其视为增加上下文与 PTE、但没有新增信息的轨迹。[T，图 12，p. 19](#src-t)

**方法学分析。** 该案例足以展示“重复内部计算再交给工具”的行为，但不能仅因最终答案原本正确就证明这类验证在总体上没有收益。更有说服力的生产实验应比较：直接工具求解、先推理再同式校验、独立方法验证三种流程，在正确性、成本和延迟上的差异。

这不是替论文改结论，而是区分其定性案例支持到哪里，以及迁移时还需要测什么。

### 5.4 Tool-Mixing 应按信息增益判断

论文附录 D.2 展示先网页检索，再调用 Python 整理打印已有文字答案的例子。这次计算没有新增外部证据，也没有必要的数值运算。[T，图 13，p. 20](#src-t)

但是，“检索财报 → 抽取数据 → Python 计算 → 对照披露 → 解释差异”是合理组合。因此，论文附录用“多于一种工具类型”作检测启发式时，只能帮助找候选异常，不能直接作为生产中的低效判决。

**工程建议。** 给每次调用关联一个目的，例如 `fill_evidence_gap`、`execute_calculation`、`run_regression_test`、`read_changed_file`。这些标签不能自行证明有效，但便于事后检查：该调用到底补了哪个证据缺口，或推进了哪个状态？

### 5.5 工具先验与格式错误，应先修适配层

论文中“忘记 print()”的案例说明：模型可能以为执行环境会自动返回末尾表达式，而真实工具只返回 stdout。另一个案例中，模型反复使用原先习惯的 `search`，但系统暴露的是 `google_search_tool`，随后又退回不兼容调用格式。[T，图 14–15，pp. 21–22](#src-t)

**工程建议。** 更换模型时，先做一组很小的工具契约测试：工具名、必填参数、字符串与数组、空结果、结构化错误、执行返回方式、失败后的纠正。不要先跑几十分钟的复杂任务，再把协议不兼容误判为推理能力不足。

对错误返回也应区分：可以有限重试的临时失败、必须改参数的调用错误、应当终止的权限错误，以及“动作是否已经生效未知”的超时。特别是有副作用的操作，不应把超时直接等同于未执行而重复提交。

### 5.6 Anthropic 的六类提示词反模式

文章列出验证仪式、过度强调彻底性、固定 scratchpad/步骤模板、陈旧 few-shot、相互矛盾的规则和过时配置。它的迁移实验从干净提示词出发，每次植入一种反模式，形成六个旧提示词，再比较换模型与清理反模式的效果。[A，Instructions](#src-a)

材料报告的收益来自不同原因：有的配置让请求直接被拒绝；有的矛盾规则导致本应执行的动作被搁置；有的手工 scratchpad 干扰了实际工具调用。并非所有失败都是“模型不够聪明”。

这里应同时守住两条边界：不必要的行为仪式可以删，但任务约束、必要证据、权限和安全流程不能因模型升级而删除；严格结构化输出有助于接口，但讲义 p. 20 也提醒，过强格式约束可能影响推理，不能把所有内部处理都压成过窄模板。[L，pp. 18–20](#src-l)

### 5.7 同一提示词公平比较，和最佳部署配置比较，是两种实验

PTE 论文使用相同 system prompt 与工具定义比较模型，这有助于控制实验条件。但其 WebInstruct 示例 prompt 本身要求用工具验证计算、交叉检查信息并持续探索。[T，§5.2、图 9](#src-t)

**方法学分析。** 因而，当研究额外调用来自哪里时，还需要区分模型倾向、提示要求和接口适配。可以补充提示策略消融，但不能将这一分析写成论文已经完成的实验。

实际选型最好同时保留两类结果：“统一接口和统一提示的可迁移性”，以及“每个模型经过合理适配后的最佳业务表现”。否则可能把适配问题当成模型能力差异，进一步误导 Router。

## 6. 减少模型步骤：哪些决策根本不该反复问模型？

### 6.1 从减少用户返工开始，而不是强行禁止澄清

讲义建议前置规划、结构化分解、定义完成检查，以及交付前自检，以减少“没计划、过早停止、没有检查”导致的用户返工。[L，p. 9](#src-l)

例如，“修复日期解析错误”可以先明确为：复现指定失败输入、修复目标格式、增加回归测试、运行相关测试、说明尚未验证范围。这个完成契约的作用是约束执行，不是让 Agent 多写一份冗长计划。

**工程边界。** 减少不必要的 check-in，不等于跳过关键澄清或授权。一个及时的必要问题可能避免整条错误轨迹；对外部有影响的操作，也不能为了自治率放弃人类控制。

### 6.2 批量化、并行化、程序化不是同一件事

| 方法 | 做了什么 | 适用条件 |
|---|---|---|
| 批量化 | 一次决策发出多个已知请求 | 已经知道要执行哪些调用 |
| 并行化 | 多个操作同时进行 | 没有阻止并行的数据或状态依赖 |
| 程序化 | 用代码接管确定性控制流 | 即使步骤有依赖，下一步也能由规则确定 |

讲义 p. 11 将“每读一个文件就调用一次模型”改成“一次读取多个独立文件”。节约来自减少模型往返，也来自减少历史重复读取。[L，p. 11](#src-l)

但 SQL 提交与取结果有依赖，不能简单并行；仍然可以把提交、轮询、取结果写成程序循环，不必每次轮询都让模型参与。

### 6.3 Uber 案例：省下的是确定性协调

Uber 文章将 SQL 的提交、状态轮询和取结果放入程序，只把结果摘要交回模型。在同一会话的对照中，`SELECT 1` 的 token 从 903 降到 402，`GROUP BY LIMIT 20` 从 1,600 降到 457。它还按会话间隔区分主会话与短任务子 Agent 的缓存 TTL。这些是该工作负载的测量，不是通用节约比例。[U，Code-Mode、Prompt Caching Strategy](#src-u)

**由此推导。** 程序循环不仅减少调用数，也避免中间轮询消息进入上下文，因而可能同时影响讲义乘法公式中的 steps、tokens/step，以及 PTE 中的累计长度。不是数据库查询本身变快，而是模型不再为已确定的流程反复作决定。

### 6.4 前置加载与按需检索怎样配合？

讲义同时建议提前读取必要文件，以及按需检索、保持上下文精简。这两者并不矛盾。[L，pp. 11、16](#src-l)

合理策略是：已经确定相关的内容，一批读取；尚不知道是否相关的内容，先定位再读取。两个极端都容易低效：一次只读一点形成大量串行探索；第一次就塞入整个仓库，导致后续每次调用都背着无关内容。

### 6.5 复用经验，也要计算维护成本

讲义 p. 12 将复用分为可执行 Skill、经验洞见、计划模板和长期记忆，并提示：任务重复时复用才有收益，记忆维护和过期条目会抵消节约。[L，p. 12](#src-l)

**解释性推导。**

$$
\text{复用净收益}
\approx
N_{\mathrm{reuse}}\times\text{单次节约}
-\text{构建成本}-\text{维护成本}-\text{过期导致的返工}
$$

工程上，一个短脚本若真正稳定替代重复工作，通常比每次检索长篇“经验总结”更容易评价。但这需要任务验证，不能把任何历史轨迹直接固化为正确 Skill。

### 6.6 最便宜的 LLM 调用，有时是不调用 LLM

讲义 p. 27 建议：固定输入用解析器，重复动作写脚本，窄标签任务考虑小分类器，固定工作流用程序控制，只在需要推理的步骤调用 LLM。[L，p. 27](#src-l)

讲义中“规则解析每次调用不花钱”的措辞，放在其 LLM 计费边界内理解：它不再产生相同的生成式模型费用，并不意味着没有 CPU、存储、开发和维护成本。

## 7. 上下文管理：压缩的是叙述，保存的是工作状态

### 7.1 三类信息应采用不同生命周期

**工程建议，基于讲义上下文方法展开。**

| 信息类别 | 例子 | 适合的处理方式 |
|---|---|---|
| 稳定规则 | 工具协议、任务约束、输出要求 | 稳定前缀、版本化 |
| 当前工作状态 | 已确认事实、假设、证据缺口、下一步 | 精简、结构化、可恢复 |
| 原始材料 | 全量日志、网页、PDF、查询大结果 | 外部保存，按定位重新读取 |

讲义列出的裁剪旧结果、压缩观察、外置大输出、选择性检索和子 Agent 隔离，分别对应这些生命周期。[L，p. 16](#src-l)

### 7.2 好的状态摘要不是聊天摘要

以下是**说明性结构**，不是论文规定的 schema：

```json
{
  "task_id": "task-demo-001",
  "goal": "比较两期财报并解释利润变化",
  "acceptance": ["主要判断有原文定位", "数字单位与期间一致"],
  "document_versions": ["report-current-v1", "report-prior-v1"],
  "verified_facts": [
    {"fact_id": "fact-17", "evidence_id": "ev-42", "page": 8}
  ],
  "open_questions": ["利润口径是否包含非经常性项目"],
  "rejected_paths": [
    {"path": "直接使用新闻摘要中的数字", "reason": "缺少原始口径"}
  ],
  "artifacts": ["artifact://report-current-v1/table-3"],
  "next_action": "核对利润口径与附注"
}
```

这里保存的是未来继续工作的必要状态。尤其要保留已排除路线及原因，否则压缩后 Agent 可能重新走一遍失败路径。

### 7.3 什么应该先从工具返回中删除？

优先裁掉明确无关的重复文本、完整堆栈中不相关的帧、已经被处理的旧日志，以及不用于当前任务的字段。保留错误类型、必要上下文、原始结果位置和截断标志。

但“过滤”不是不受约束的模型摘要。若过滤器删除了否定句、单位、日期、例外条件或跨页表格表头，就可能改变材料含义。工程上应对工具摘要与原文一致性单独测试。

### 7.4 什么时候压缩才回本？

讲义提醒压缩可能导致重读与缓存重写。[L，p. 25](#src-l)

**解释性推导。**

$$
\begin{aligned}
\text{压缩净收益}={}&\text{未来减少的输入与模型计算成本}\\
&-\text{生成摘要成本}-\text{缓存重建成本}\\
&-\text{重新获取信息成本}-\text{信息丢失造成的期望返工}
\end{aligned}
$$

即将完成的任务通常不容易摊回一次昂贵压缩；剩余几十步时，收益可能更大。因此不能仅按固定步数触发，也不能只等窗口快满才考虑。阈值应由真实轨迹、剩余工作量和重建率校准。

### 7.5 子 Agent 的成本价值，可能主要来自探索隔离

一个子 Agent 完整探索一家公司，另一个探索另一家公司，主 Agent 只接收结论、证据和冲突，可以避免两条完整轨迹长期一起进入主上下文。[L，p. 16](#src-l)

但子 Agent 会复制公共指令、材料，且需要汇总；讲义 p. 25 明确列出这项反向成本。[L，p. 25](#src-l)

**解释性推导。**

$$
\text{子 Agent 净收益}
=\text{主上下文减少的重复成本}
-\text{子 Agent 额外执行、重复输入与合并成本}
$$

因此，“多 Agent 一定贵”和“多 Agent 一定省”都没有依据。要比较完整任务总成本，而不是仅比较主 Agent 的上下文长度。

### 7.6 对证据密集型任务，压缩必须保持证据身份

**工程建议。** 投研、文档审核等场景应优先保存文档版本、日期、主体、单位、比较口径、页码与原文定位、冲突状态。可以省略探索过程的长篇叙述，但不能把“特定期间、特定份额、特定口径的数据”压成“相关业绩数据”。

节约几十个 token，却失去最关键的证据口径，是典型的局部节约、整体返工。

## 8. 缓存经济学：复用计算与减少上下文必须同时做

### 8.1 Prompt cache 缓存的不是最终答案

Anthropic 文章解释，prompt cache 复用相同输入前缀对应的内部状态，依赖模型、前缀一致性和有效期等条件；它不是简单返回上一次回答。[A，Prompt cache](#src-a)

与之不同，工具结果缓存复用查询或计算结果，答案缓存复用最终业务响应。三者有不同的失效条件。比如工具缓存应匹配参数、版本及权限范围，不能把某次读到的数据无限当成当前事实。

### 8.2 缓存命中和上下文精简不是互相替代

讲义观察到大量缓存读取；PTE 重点研究 cache 不可复用场景。它们描述的是不同负载与条件，而不是一个普遍系统同时具备的互斥事实。[L，p. 15](#src-l) [T，§3.1–3.2](#src-t)

即使大部分前缀命中，留下的冗余仍然可能收费并影响后续生成。因此应分别优化：**少携带不必要的信息；少重复加工相同的信息。**

### 8.3 稳定前缀是一种请求布局策略

文章指出动态时间戳、随机 ID、工具定义重排、修改系统前缀、模型切换和部分推理设置变化，都可能影响前缀复用。[A，Prompt cache](#src-a)

```text
更有利于复用的布局：
稳定工具定义 → 稳定系统规则 → 稳定背景 → 已有历史 → 本轮新增内容

容易产生额外失效的布局：
每次变化的时间戳/ID → 动态重排工具 → 不断重写规则 → 其余历史
```

**工程建议。** 请求构造尽量确定性序列化，记录工具和规则版本；对缓存失效不仅统计命中率，还定位相邻请求第一个不同的前缀位置。授权策略更新必须真正生效，不能为了缓存而延迟必要的安全规则变化。

### 8.4 一段前缀使用几次，缓存才回本？

**解释性推导。** 设该前缀普通读取一次价格为 $P$，写入倍率为 $w$，读取倍率为 $r$，总共使用 $n$ 次，且只有一次写入：

$$
C_{\mathrm{plain}}=nP
$$

$$
C_{\mathrm{cache}}=[w+(n-1)r]P
$$

因此：

$$
n>\frac{w-r}{1-r}
$$

以材料的示例倍率 $w=1.25,r=0.1$ 计算，总共使用两次就可能回本；$w=2,r=0.1$ 则通常要三次。前提是确实复用成功，不能忽略过期后再次写入。[A，Prompt cache](#src-a) [L，p. 21](#src-l)

### 8.5 TTL 的选择要看请求间隔

**教学算例，沿用上述材料倍率，不是当前所有模型报价。** 某前缀使用五次，五次均在一小时内。

若请求间隔约八分钟，五分钟缓存每次都需重写：

$$
C_{5m}=5\times1.25P=6.25P
$$

一小时缓存写一次、读四次：

$$
C_{1h}=2P+4\times0.1P=2.4P
$$

此时长 TTL 约节约 61.6%。

若间隔只有十秒，两种缓存都能复用：

$$
C_{5m}=1.25P+4\times0.1P=1.65P
$$

$$
C_{1h}=2.4P
$$

此时长 TTL 反而贵约 45.5%。因此不能统一设成最长 TTL。人类交互停顿、工具执行时间与子任务生命周期，都应进入选择条件。

### 8.6 文章中的进阶缓存手段，应保留版本边界

附件文章还介绍了延迟加载不常用工具、把部分系统更新作为中途消息追加、自动移动 cache breakpoint、预热缓存，以及在压缩边界切换模型或 effort。[A，Prompt cache / How to fix it](#src-a)

其中 `defer_loading`、`max_tokens: 0` 预热和中途系统消息是文中对应平台的具体特性，不是所有 API 都支持的抽象协议。接入时必须核对目标模型和接口契约，不能把示例字段无条件复制到别的平台。

预热也不是免费：若会话之后没有真正使用，预热成本就浪费。可以用“后续复用概率 × 可避免的重建与等待价值”对照预热费用，并考虑资源竞争。讲义 Pi 案例将缓存保温与价格判断联系起来，也是这个方向。[L，p. 50](#src-l)

### 8.7 模型、effort、工具发现与缓存相互耦合

文章既提醒修改 effort 可能破坏前缀，也给出了特定模型的例外。因此正确结论是“影响取决于模型与修改方式”，而不是“一定破坏”或“一定不破坏”。[A，Prompt cache](#src-a)

同理，按需发现工具本意是缩短输入，但若每次发现都重写最前面的工具集合，也可能降低复用。需要评估净效果，而不是分别追求最少 schema 和最高命中率。

文章建议将模型/effort 的切换尽可能安排到 compaction 本来就会重建会话缓存的时点。这是上下文模块与路由模块需要联合决策的直接例子。[A，Prompt cache](#src-a)

### 8.8 两种 batching 不要混淆

讲义 p. 11 的 batch 是一次模型决策发出多个已知工具调用，主要减少往返；p. 21 的 Batch 则是平台异步批处理计费方式，面向可等待的评测、回填和批量工作。[L，pp. 11、21](#src-l)

讲义列出输出 5×、输入 1×、Batch 输入 0.5×、缓存读取 0.1×、Batch 加缓存 0.05×的示例关系。它说明可能的经济结构，不代表所有模型都使用同一倍率，也不代表所有批处理负载都必然命中缓存。延迟敏感任务不能只为折扣牺牲交付时限。

## 9. 输出与 Effort：少说和少想，是两种控制

### 9.1 先删除中间冗余，而不是削弱最终交付

讲义给出简洁指令、长度限制、只返回必要 JSON 字段等方法。[L，pp. 18–19](#src-l)

工程上优先删除：每次工具调用前重新复述任务、反复宣告下一步、编辑少量内容却输出全文件，以及已经在状态中记录的长篇解释。最终交付仍应包含用户需要的结论、证据、限制和必要说明。

“工具循环中的通信尽量精简”与“最终讲解完整易懂”不是矛盾。不要为了少输出，让用户再来一轮追问遗漏信息。

### 9.2 `max_tokens` 是保险丝，不是智能预算分配器

硬上限可以限制极端输出，却可能截断代码、JSON 或答案。讲义特别提醒推理也可能消耗输出上限。[L，p. 18](#src-l)

因此应分开配置：交付格式和篇幅控制可见输出；effort 或推理预算控制为解决问题投入多少计算；整个任务预算再约束多次调用、工具和重试。

结构合法也不等于语义正确，schema 检查不能代替事实与执行验证。

### 9.3 同样的额外推理，在不同任务上回报不同

PTE 论文提供了同系列 Instruct 与 Thinking 模型的对照：

| 任务与配置 | 准确率 | 平均 PTE |
|---|---:|---:|
| AIME25：Qwen3-235B-Instruct | 63.3% | 19,956 |
| AIME25：Qwen3-235B-Thinking | 80.0% | 35,829 |
| SimpleQA：Qwen3-235B-A22B-Instruct | 85.1% | 3,184 |
| SimpleQA：Qwen3-235B-A22B-Thinking | 81.7% | 9,306 |

AIME25 上提高约 16.7 个百分点，PTE 约为 1.80 倍；SimpleQA 上准确率下降约 3.4 个百分点，表格 PTE 比例约为 2.92。[T，表 5–6，pp. 16–17](#src-t)

**原文差异。** 论文正文将 SimpleQA 的倍率写为 4.2×，而上述表值相除为约 2.92×。本文保留两者，不猜测造成差异的原因，也不把它们合成一个确定实验结果。[T，p. 6、p. 17](#src-t)

### 9.4 用 effort 曲线理解边际收益

Anthropic 文章报告，在 FrontierCode Diamond 的最难 50 题上，Fable 5 的 low effort 为 11.5%、约 5.35 美元/任务，max 为 30.9%、约 19 美元/任务。得分差约 19.4 个百分点，成本约 3.55 倍。[A，Effort，图 4 对应正文](#src-a)

另一个 HLE 无工具示例中，从低到高有明显收益，但最后提高到 max 的一步只增加约半个百分点，成本增加约 46%；文章认为该得分差在运行波动范围内。[A，Effort](#src-a)

**解释性推导。**

$$
\text{边际计算收益}=\frac{\Delta Q}{\Delta C}
$$

曲线陡峭时，额外计算可能有价值；曲线平坦时，再加 effort 需要更强理由。这里的比值仍需结合风险与时限，不是任何任务都应追求最高平均比值。

### 9.5 平坦曲线是排查线索，不是病因诊断

提高 effort 后质量不变，可能是检索没找到关键证据、工具格式失败、任务定义不清、验收器有盲区，或模型已经达到该配置下的能力上限。材料支持用 effort sweep 理解任务形状，但不能单凭曲线确定是哪一个瓶颈。[A，Effort / Understand your task shape](#src-a)

反方向也要防范：低 effort 的少工具调用，可能只是过早接受第一条搜索结果。更少步骤不一定更高效，有时只是少完成了必要工作。[A，Effort](#src-a)

### 9.6 应比较“模型 × effort × 提示词”

文章建议测试更强模型的低 effort，而不是假设高单价模型一定更贵。其 CursorBench 例子同时涉及执行工作量减少与缓存读取价格差异，所以应将行为收益和供应商价格变化分开。[A，Effort，图 5 对应正文](#src-a)

一种实验矩阵可以是：

| 候选 | low | medium | high |
|---|---|---|---|
| 强模型，已清理提示词 | 测 Q/C/T | 测 Q/C/T | 测 Q/C/T |
| 中模型，已适配工具 | 测 Q/C/T | 测 Q/C/T | 测 Q/C/T |
| 便宜模型，明确任务契约 | 测 Q/C/T | 测 Q/C/T | 测 Q/C/T |

表格是实验建议，不是已完成的测量。不同阶段可以选择不同配置，但切换成本必须进入总账。

### 9.7 提示词与模型联合优化的案例

文章的 hillclimb 案例从旧模型高 effort 出发，先试较强模型低 effort 并清理提示词，训练集 accuracy 达到 98.9%，约 2.6 美分/工单；换到更便宜模型低 effort 后，成本约 1 美分、accuracy 降到 88.9%；分析训练失败后补充路由规则与退款上限交叉引用，accuracy 又达到 98.9%。[A，Effort，图 6 对应正文](#src-a)

它说明“便宜模型失败”不一定全是能力不足，也可能缺失任务规则。但保留测试集的统计口径必须明确：正文报告 14 张保留工单上 90.5% 对 78.6%，仅凭这些数字不能推断每张工单只计一个二元分数，更不能等同于长任务的全流程可靠完成。见附录 C。

### 9.8 自动优化工具的思想，比命令名称更重要

| 文中命令 | 核心流程 | 不能替代的工作 |
|---|---|---|
| `/claude-api prompt-audit` | 检查 prompts、Skills、工具说明中的反模式 | 不能擅自删除业务和安全约束 |
| `/claude-api cost-optimize` | 从 usage、账单或代码估算定位成本，再测试缓存、裁剪、批处理等 | 没有真实评测不能证明质量不变 |
| `/claude-api hillclimb` | 用训练失败样本引导配置修改，最后保留集评估 | 不能将测试集反复当调参材料 |

这些名称和行为来自附件文章，不是本文对当前安装环境的功能保证。[A，Automating cost reduction、Getting started](#src-a)

## 10. RouteLLM：从偏好数据学习如何分配强模型调用

### 10.1 这篇论文在讲义中处于什么位置？

讲义区分生成前选择、失败升级和逐步骤重选。RouteLLM 主要研究第一种：先看问题，再决定由强模型或弱模型生成回答；它不是先让两个生成模型都回答再挑选，也不是一个已经解决长轨迹联合调度的算法。[L，pp. 22、24](#src-l) [R，§2–3](#src-r)

论文首发编号为 arXiv:2406.18665，上传版本为 v4，首页标注 ICLR 2025。讲义将其记为 RouteLLM（2024），是在使用首发年份，不应据此判断材料互相矛盾。[R，p. 1](#src-r)

### 10.2 Router 预测的是相对优势，不是绝对难度

令 $q$ 为问题，$M_s$ 为强模型，$M_w$ 为弱模型。RouteLLM 学习：

$$
P_\theta(M_s\succ M_w\mid q)
$$

即强模型回答优于弱模型的概率，而不是“这道题很难的概率”。[R，§3.1](#src-r)

一个难题如果两个模型都不会，升级未必有大收益；一个短问题如果恰好处于弱模型短板，强模型可能很值得用。Router 要捕捉的是问题与能力差异的关系。

同时，**比较偏好不等于绝对正确性**：A 比 B 好，并不保证 A 达到业务验收标准。对事实、代码和审核任务，工程迁移时应把测试、标准答案、证据完整性等纳入标签设计，而不是只学习“哪个回答更像专家”。

### 10.3 概率怎样变成实际选择？

论文使用成本阈值 $\alpha$：

$$
R^\alpha(q)=
\begin{cases}
M_w,&P_\theta(M_s\succ M_w\mid q)<\alpha\\
M_s,&P_\theta(M_s\succ M_w\mid q)\ge\alpha
\end{cases}
$$

$\alpha$ 越高，对调用强模型的要求越严格，强模型使用比例越低。[R，§3.1，公式 2](#src-r)

这个阈值不天然等于 0.5。它控制质量—成本位置，应通过验证集扫描。在业务里还要看真实费用，而不是只看强模型调用比例，因为不同请求长度、模型输出长度和缓存状态可能不同。

### 10.4 训练数据：历史上什么问题谁更好？

原始 Chatbot Arena 数据包含约 80K 次匿名对战：用户提问，两个模型回答，用户选胜者或平局。经过留出验证集和过滤等处理，实验部分报告约 65K 条、64 个模型之间的比较；这两个数量描述不同处理阶段，不应混用。[R，§4.1、§5](#src-r)

原始任意模型对的比较很稀疏，平均不足全部标签的 0.1%。作者将模型按排行榜分数聚为十个 tier，降低稀疏性，取最高两个 tier 表示强模型类，第三个 tier 表示弱模型类。训练时保留问题和胜负标签，不把候选回答作为线上路由必须依赖的输入。[R，p. 5](#src-r)

**训练时可以花钱生成两个模型的答案；线上生成前路由时不需要先获得这两个答案。** 这是它区别于 ensemble 的关键。

### 10.5 两种增强数据为什么重要？

有标准答案时，可以让两个模型回答，然后比较与标准答案的匹配来构建胜负；论文使用 MMLU 验证集约 1,500 条。开放问答没有标准答案时，可以用评审模型生成偏好；论文利用 Nectar 已有 GPT-4 回答、补充 Mixtral 回答并进行比较，形成约 120K 条增强标签。[R，§4.1.1](#src-r)

工程上，增强数据的价值不是“增加数量”本身，而是补齐当前请求分布中缺失的能力对比。若真实业务主要是中文表格、复杂工具或长文档，通用英文聊天偏好未必足以指导路由。

### 10.6 四种 Router 的算法与工程代价

#### Similarity-weighted ranking：相似问题上的对战更有参考价值

对新问题计算与历史问题的相似度，给相近问题的偏好更大权重，再通过 Bradley–Terry 型比较模型估计胜率。论文这一路线主要在推理时求解，而不是先训练一个固定神经分类器。[R，§4.2，p. 5](#src-r)

直观上，遇到复杂表格问题，更重视历史表格问题上的胜负，而不是将所有闲聊对战等权平均。代价在于在线相似性计算和求解，不能默认最轻。

#### Matrix factorization：学习问题特征与模型能力的匹配

论文学习一个隐藏评分函数：

$$
\delta(M,q)=w_2^\top\left[v_M\odot(W_1^\top v_q+b)\right]
$$

再定义：

$$
P_\theta(M\succ M'\mid q)=\sigma\big(\delta(M,q)-\delta(M',q)\big)
$$

$v_q$ 是问题表示，$v_M$ 是模型表示，投影层将维度对齐，逐元素乘积刻画匹配，最后映射成相对分数。它借鉴推荐系统中的低秩结构学习，并不要求 Router 每次生成一篇选择理由。[R，§4.2，p. 6](#src-r)

可以理解为：推荐系统学习“用户喜欢哪些物品”，这里学习“模型在哪些问题上更有优势”。

#### BERT classifier：直接把问题分类为相对胜率

论文用 BERT 的 CLS 表示接分类头，并全参数微调。表达能力更强，但标签稀疏时未必比轻量方法泛化更好。[R，§4.2](#src-r)

#### Causal LLM classifier：通过标签 token 预测胜负

论文用 Llama 3 8B，将比较标签加入词表，以标签类别上的概率完成预测。这不是让 8B 模型生成长篇“该选谁”的分析，而是用生成式模型做标签分类。[R，§4.2](#src-r)

| 方法 | 主要机制 | 需要关注的成本或风险 |
|---|---|---|
| SW ranking | 相似问题加权后在线比较求解 | 在线开销与数据规模 |
| Matrix factorization | 问题表示与模型表示匹配 | 表示质量、训练分布与轻量预测误差 |
| BERT | 问题编码加分类头 | 数据量、长度截断与领域迁移 |
| Causal LLM | 用生成模型预测比较标签 | 部署规模、训练与推理费用 |

### 10.7 PGR：收回了多少性能差距？

论文定义：

$$
\mathrm{PGR}=
\frac{Q_{\mathrm{router}}-Q_{\mathrm{weak}}}
{Q_{\mathrm{strong}}-Q_{\mathrm{weak}}}
$$

**教学算例。** 弱模型 70%，强模型 90%，Router 86%：

$$
\mathrm{PGR}=\frac{86-70}{90-70}=80\%
$$

含义是收回强弱模型差距的 80%，不是准确率为 80%，也不是达到强模型准确率的 80%。[R，§3.2，公式 6](#src-r)

工程解释还应注意分母：若强弱模型差距很小，PGR 会对测量噪声敏感。质量差距和置信区间应一起看，不能只看归一化指标。

### 10.8 CPT 与 APGR：为什么要评价整条曲线？

**CPT(x%)** 是达到 PGR 为 x% 所需的最小强模型调用比例。它回答“为目标质量要买多少强模型能力”。

**APGR** 是扫描强模型调用比例时 PGR 曲线的面积。它回答“不同预算要求下，Router 整体表现怎样”。论文以十个离散调用比例近似这一指标。[R，§3.2](#src-r)

随机选择强模型的比例若为 $c$，在简化的平均质量模型中，期望收回的差距也是 $c$，所以随机曲线面积约为 0.5。优秀 Router 希望在相同预算下高于随机曲线。

图 1 应这样读：横轴是昂贵模型调用比例，不直接是美元；纵轴是质量或归一化质量恢复；同样横轴位置上曲线更高，才是更有效地分配调用。[R，图 1，p. 2](#src-r)

### 10.9 核心实验：数据增强比“哪一种 Router 永远最好”更重要

MT Bench，强模型为 GPT-4-1106-preview，弱模型为 Mixtral 8x7B：

| 训练数据 | 方法 | CPT(50%) | CPT(80%) | APGR |
|---|---|---:|---:|---:|
| — | 随机路由 | 49.03% | 78.08% | 0.500 |
| Arena | BERT | 78.09% | 87.64% | 0.391 |
| Arena | Causal LLM | 28.82% | 77.53% | 0.573 |
| Arena | Matrix factorization | 25.32% | 74.26% | 0.580 |
| Arena | SW ranking | 37.85% | 58.99% | 0.610 |
| Arena + judge | BERT | 19.58% | 34.02% | 0.751 |
| Arena + judge | Causal LLM | 31.50% | 48.75% | 0.679 |
| Arena + judge | Matrix factorization | 13.40% | 31.31% | 0.802 |
| Arena + judge | SW ranking | 23.21% | 36.04% | 0.759 |

来源为论文表 1。BERT 在仅 Arena 设置下弱于随机，而增强后明显改善；增强后的 Matrix factorization 在该表中最好。[R，表 1，p. 7](#src-r)

不能把“CPT(80%)=31.31%”解读成“只花 31.31% 的真实账单”；它是强模型调用份额，弱模型、Router、长度和缓存仍有费用。

### 10.10 领域分布改变后，结果也会改变

MMLU 上仅用 Arena 训练的结果接近随机，加入约 1,500 条相关标注后改善。GSM8K 上也存在类似现象，而且增强后最好的是 Causal LLM，而不是 MT Bench 中最好的 Matrix factorization。[R，表 2–3、§5.1](#src-r)

论文还计算 benchmark 与训练数据的相似度：MT Bench 从约 0.6078 到 0.6525，MMLU 从约 0.4823 到 0.5678，GSM8K 从约 0.4926 到 0.5335；这些变化与相应 Router 表现改善相关。[R，表 5、附录 C](#src-r)

相似度衡量的是评估问题在训练问题中的表示覆盖，不是保证泛化的证明。少量高度相关样本可能比大量无关对战更有价值，这也是领域路由应先收集自身任务数据的原因。

### 10.11 换模型不重训：论文证明的是有限范围内的迁移

作者将输出模型对替换为 Claude 3 Opus/Sonnet、Llama 3.1 70B/8B，在 MT Bench 复用同一组 Router，得到优于随机的结果。[R，§5.2、表 4](#src-r)

它表明有些“什么时候值得用更强模型”的问题特征可以迁移；不意味着可以对任意新模型、任意协议和任意任务直接保证路由准确。

PTE 论文进一步提醒，工具能力会随任务和工具类型变化。因此生产标签最好记录“模型 + prompt + 工具协议 + 任务环境”的版本，而不只有模型名。[T，§6.1–6.2](#src-t)

### 10.12 路由开销与低流量经济性

| 方法 | 论文每百万请求开销 | 论文吞吐量 |
|---|---:|---:|
| SW ranking | 39.26 美元 | 2.9 requests/s |
| Matrix factorization | 3.32 美元 | 155.16 requests/s |
| BERT | 3.19 美元 | 69.62 requests/s |
| Causal LLM | 5.23 美元 | 42.46 requests/s |

这些数字来自当时特定 VM、GPU/CPU、嵌入与负载设置，不是今天任意部署的单位价格。论文以吞吐和每小时机器费换算单位成本，低流量下空闲资源的摊销可能不同。[R，§5.5、表 7](#src-r)

**工程建议。** 小团队先用清晰任务分类、固定阶段模型与离线配置搜索建立基线；确认确有足够调用量和稳定能力差异后，再部署学习式 Router。不要为节约很少的 API 费用，先承担更大的常驻服务成本。

### 10.13 不能直接搬用论文里的“节约 3.66 倍”

论文的经济分析使用短提示、单轮请求假设，平均输入约 95 token、输出约 264 token；这与几十轮、上百 K 上下文的 Agent 不同。[R，附录 D](#src-r)

另外，表 6 的标题与正文比较基线存在容易误读的地方：正文说按优秀 Router 相对随机 Router 的强模型调用比例计算，表标题却写相对 GPT-4。以表 1 的 $49.03/13.40\approx3.66$ 能对应其倍率。本文不将这个数字改写成“相对所有问题都调用强模型的通用账单节约”。原材料边界详见附录 C。[R，§5.4、表 6](#src-r)

## 11. 从单轮 Router 到长任务：模型、缓存、验证与预算联合决策

### 11.1 当前步骤的便宜，可能是后续轨迹的昂贵

讲义 p. 22 直指难点：一次便宜规划错误可以浪费后面很多动作。[L，p. 22](#src-l)

**教学算例。** 弱模型当前调用 0.01 美元、错误概率 30%；强模型 0.05 美元、错误概率 5%。每次错误平均造成后续 0.50 美元返工：

$$
C_w=0.01+0.30\times0.50=0.16
$$

$$
C_s=0.05+0.05\times0.50=0.075
$$

强模型单次贵五倍，考虑返工后反而更便宜。这不证明规划总要用最高档模型，而说明应按错误传播范围和恢复成本评价。

### 11.2 路由需要知道哪些状态？

以下是**对讲义与阅读的工程扩展，不是 RouteLLM 原算法**：

| 状态 | 决策价值 |
|---|---|
| 任务阶段与当前子目标 | 规划、抽取、编辑、汇总的错误后果不同 |
| 证据缺口与不确定性类型 | 决定该增加推理还是先获取材料 |
| 工具结果与验证结果 | 决定是否可以接受便宜模型或需要升级 |
| 剩余预算、剩余时间 | 决定还能负担多少探索与恢复 |
| 当前缓存模型、前缀、年龄 | 决定切换后的真实成本 |
| 最近几步的进展 | 区分有效探索和重复绕圈 |
| 动作权限与副作用 | 决定哪些动作可以自动执行或重试 |

可用一个解释性目标表达联合决策：

$$
a_t^*=\arg\max_a
\left[
\mathbb{E}(\Delta Q_{\mathrm{final}}\mid s_t,a)
-\lambda\Delta C_{\mathrm{total}}
-\mu\Delta T_{\mathrm{critical}}
\right]
$$

这里质量收益、费用和关键路径时间通过权重转换到可比较尺度。该式是帮助设计策略的抽象，不是已经训练好的预测器；用规则和离线统计实现一个可测量基线，往往比立即训练复杂控制模型更实际。

### 11.3 热缓存强模型，可能比冷缓存弱模型便宜

**教学算例。** 假设强模型输入 1 美元/百万 token、输出 5 美元；弱模型输入 0.2 美元、输出 1 美元；缓存读倍率 0.1、写倍率 1.25。当前有 100K 前缀，只生成 200 token，忽略其他开销。

继续使用强模型热缓存：

$$
C_{s,\mathrm{warm}}=0.1\times0.1+0.0002\times5=0.011
$$

切换到弱模型并首次写缓存：

$$
C_{w,\mathrm{cold}}=0.1\times0.2\times1.25+0.0002\times1=0.0252
$$

弱模型这一轮更贵；后续弱模型热缓存每轮约 0.0022 美元。假设后续前缀与输出长度不变且都命中，弱模型累计 $n$ 轮为：

$$
0.0252+(n-1)\times0.0022
$$

强模型为 $0.011n$，从总共约三轮起，切换才开始有账面优势。真实系统还要加上模型能力差异、上下文增长和重新传递状态的成本。

这展开了 Anthropic 的缓存切换建议：切换判断不应只看目标模型单价，应看从当前状态完成剩余任务的总成本。[A，Prompt cache](#src-a)

### 11.4 失败再升级，依赖检查器的检错能力

令弱模型错误率为 $e$，检查器检出错误的比例为 $s$，把正确结果误判为失败的比例为 $f$。在一个简化 cascade 中：

$$
P_{\mathrm{upgrade}}=es+(1-e)f
$$

$$
\mathbb{E}[C]=C_w+C_{\mathrm{check}}
+P_{\mathrm{upgrade}}(C_s+C_{\mathrm{switch}})
$$

但未被发现的错误为：

$$
P_{\mathrm{silent\ error}}=e(1-s)
$$

若 $e=10\%$、$s=80\%$，即使所有升级后的答案都正确，仍有 2% 的请求可能带着未发现错误直接交付。这些公式是工程分析，不是 RouteLLM 的实验结果。

讲义列出 learned scorer、自验证和执行反馈三类检查方式，不能将它们当成相同可靠性的免费模块。[L，p. 22](#src-l)

### 11.5 不同阶段应按可验证性，而不只按表面难度分配能力

格式转换有严格 schema，适合先尝试低成本配置；关键规划出错可能污染后面很多步，需要重视上游质量；数字计算可交给程序，但输入口径仍需核验；最终语义解释可能需要更强推理，但没有原始证据时单纯提高 effort 无法补齐事实。

这些是工程建议，不是“某种业务永远使用某档模型”的固定映射。应在实际工具环境中测试每个阶段，并记录失败是能力、信息、协议还是执行原因。

### 11.6 阶段边界比每步随意切换更容易管理

为减少缓存抖动与状态迁移，可先采用较粗粒度策略：任务开始选默认配置；独立子任务单独选配置；验证失败时升级；需要 compaction 时再评估切换；达到停止条件后输出可恢复摘要。[L，pp. 22、25–26](#src-l) [A，Prompt cache](#src-a)

这是一个低复杂度基线。它不一定全局最优，但通常比“每轮只看单价换模型”更容易测量和解释。

## 12. 性能优化：关键路径、工具等待与并行调度

### 12.1 成本看全部工作，完成时间看关键路径

讲义第 29 页用规划、两个并行 worker 和合并展示：红色关键路径决定交付时刻。最快分支继续变快，未必改变最终时间。[L，p. 29](#src-l)

**教学算例。** 规划 2 秒，三个独立任务分别 6、10、4 秒，合并 3 秒：

$$
T_{\mathrm{serial}}=2+6+10+4+3=25\mathrm{s}
$$

$$
T_{\mathrm{parallel}}=2+\max(6,10,4)+3=15\mathrm{s}
$$

将 6 秒分支减到 3 秒，整体仍为 15 秒。只有缩短 10 秒关键分支、规划或合并，才会改变这一理想时间线。

实际还要加入网络、队列、共享资源竞争和合并依赖。先记录这些边，再做性能判断。

### 12.2 模型加速很大，不代表任务加速很大

假设任务 100 秒，其中模型 20 秒、工具与等待 80 秒。模型速度翻倍，总时间变为 90 秒，只得到约 1.11 倍整体加速。

这说明讲义 p. 32 的建议很重要：先测工具时间，再决定是否调模型；构建、测试、页面加载可能超过模型调用本身。[L，p. 32](#src-l)

PTE 帮助解释模型部分，但不能告诉你某个数据库为什么排队十分钟。需要让计算账与端到端 trace 互相补充。

### 12.3 编排层的四个常用方向

讲义列出异步执行、持久会话、流式流水线和服务就近部署。[L，p. 31](#src-l)

| 方向 | 可以减少什么 | 工程边界 |
|---|---|---|
| 异步执行 | 等一个工具时的空闲 | 只能提前执行不依赖该结果的必要工作 |
| 持久会话 | shell、浏览器、连接反复初始化 | 要控制状态污染、故障恢复与隔离 |
| 流式流水线 | 模型响应结束后的额外等待 | 参数完整、可解析、获授权后才执行，不对残缺参数产生副作用 |
| 服务就近部署 | 网络往返与传输 | 需保留权限、数据边界和服务可维护性 |

工具自身还可采用缓存、合适计算资源、更好的接口和超时控制。但工具结果复用要绑定版本、参数及权限上下文，不能用不适用的旧结果换速度。[L，p. 32](#src-l)

### 12.4 并行并不总是增加总成本

将三个已确定的文件读取并发执行，可能保持同样工作量并减少模型轮次。让三个 Agent 分别完整解决同一问题再投票，则明显增加探索工作。

因此应区分“同样的工作并发执行”和“增加分支的并行探索”。讲义同时讨论并行工具与并行子 Agent，并要求独立任务才能直接并行，共享状态需要合并。[L，p. 33](#src-l)

**工程建议。** 为 CPU、数据库连接、浏览器、模型 API 分别设并发上限；让调度器知道资源类型。五个任务同时跑重测试，可能争用同一台机器，不能期待都维持单独运行时的速度。

### 12.5 更便宜与更快，不是普遍等价

讲义 p. 30 使用“前面的成本技术也能降延迟”的概括性表述，但 p. 28–29 同时写明更快不总更便宜、小模型可能多走步骤。[L，pp. 28–30](#src-l)

按整套材料解释，应该保留条件：减少冗余经常同时省钱和提速；异步 Batch 可能更便宜但等待更久；cascade 可能节约强模型费用却增加一次串行请求；更多并行探索可能缩短交付时间但增加总计算。不能把单页概括扩展成无条件定律。

### 12.6 工具加速还可能间接改善缓存

**跨材料推导。** 如果工具等待从超过 TTL 缩短到 TTL 内，除了少等工具，还可能避免下一步重建前缀。这是工具延迟与缓存成本之间的间接联系，不是只在工具账上节约几秒。[L，p. 32](#src-l) [A，Prompt cache](#src-a)

反过来，单纯把模型变快却仍让父 Agent 长时间阻塞在子任务上，可能无法解决缓存过期问题。

## 13. 投机执行：提前做可能需要的事，用浪费风险换等待时间

### 13.1 投机动作不同于普通工具调用

讲义描述三个步骤：预测主模型下一步动作；在主模型思考时提前执行；主模型决定后对比。猜中就复用结果，猜错则丢弃。[L，p. 34](#src-l)

它不是为了新增更多候选答案，而是为了将可能必需的工具等待移出后续关键路径。也不同于 token 级 speculative decoding：这里提前执行的是动作或工具请求，而非仅预测下一个 token。

### 13.2 讲义提供了两条分类轴

| 分类轴 | 讲义中的类别 |
|---|---|
| 预测范围 | 工具意图、工具与参数、下一动作、多个分支、整段轨迹 |
| 预测来源 | 小模型预测、同一模型早期分叉自预测、历史轨迹预测 |
| 保留条件 | 始终验证后保留，或跳过部分检查的有损策略 |

讲义对应列出 SPORK、PASTE、Speculative Actions、B-PASTE、Speculative Macro Commit 等阅读方向。本文只保留讲义赋予它们的分类和示例，不声称已阅读全文或复现这些论文。[L，pp. 35–36](#src-l)

### 13.3 PASTE 与 SPORK 的例子应该怎样理解？

按讲义描述，PASTE 从历史轨迹发现 `search → visit → extract` 的模式，等 search 返回 URL 就提前 visit。SPORK 在同一模型的早期推理分支中预测稍后会发出的工具调用，提前准备结果。[L，p. 37](#src-l)

```text
没有投机：主模型决定调用 → 工具执行 → 模型继续
有投机：  主模型仍在思考 ─────────→ 对比最终动作 → 复用或丢弃
                       ↘ 预测并提前执行工具 ↗
```

### 13.4 什么时候值得投机？

**解释性推导。** 若把时间价值折算成成本，可比较：

$$
P_{\mathrm{hit}}\times V_{\mathrm{saved\ critical\ time}}
>
C_{\mathrm{prediction}}+C_{\mathrm{wasted\ execution}}
+C_{\mathrm{contention}}+C_{\mathrm{recovery}}
$$

高命中率、工具等待较长、额外资源有余量时更容易有收益。若提前执行的工作挤占正在关键路径上的任务，预测命中也可能不值得。

这是讲义留下的开放调度问题的具体化思路，不是材料给出的成熟最优算法。[L，p. 34](#src-l)

### 13.5 “动作一样”不足以证明结果可复用

**工程建议。** 先限定只读、低成本、可隔离、绑定相同数据版本的动作。工具名和参数相同，但执行时文件或数据库已变化，结果仍可能不等价。取消请求也不一定能取消远端已开始的执行。

发邮件、提交交易、修改生产数据等动作，不适合仅凭猜测提前执行。讲义提到“能撤销”有利于投机，但生产设计还应检查权限、状态版本、幂等与外部可见副作用。

## 14. Harness 架构：成本策略为什么必须落实到运行系统？

### 14.1 三种架构的区别是责任归属，不是 Agent 数量

| 维度 | Monolithic harness | Modular harness | Agent microkernel |
|---|---|---|---|
| 基本思想 | 一个运行时拥有全部组件 | 一个 controller 通过接口调用组件 | 小核心协调状态、调度与安全，能力由服务提供 |
| 组件替换 | 较难、耦合高 | 比较容易 | 协议匹配时较容易 |
| 通信成本 | 低 | 低到中 | 可能较高 |
| 生命周期 | 集中 | 仍由 controller 控制 | 能力服务可独立管理 |
| 隔离 | 需要额外实现 | 接口化不自动隔离 | 架构强调隔离，但仍需实际强制执行 |
| 适用取舍 | 单体 Agent、快速调试 | 可扩展框架与小团队工程 | 共享基础设施、独立扩缩容与多 Agent 服务 |

这是讲义 pp. 40–45 的框架。执行一个 Python 片段时，微内核示例由独立执行服务管理沙箱分配和生命周期；模块化示例只是将具体实现放在 provider 接口后面。[L，pp. 40–45](#src-l)

### 14.2 模块化不等于微服务，也不等于安全

所有 provider 可以仍在一个进程里，共享故障域；单体也可以认真实现沙箱，并非天然不能隔离。讲义比较的是责任与部署倾向，不能把架构标签当成安全证明。[L，pp. 42–45](#src-l)

**工程建议。** 小团队先做模块化单体：一个主循环，明确模型、上下文、工具执行、验证、预算和日志接口；等共享沙箱池、隔离与独立扩缩容需求真实出现，再决定拆服务。不要为了形式上的“微内核”制造更多网络等待和故障路径。

### 14.3 模块之间需要共享决策信息

Router 知道想换模型，ContextBuilder 知道即将压缩，Scheduler 知道工具预计运行多久，BudgetManager 知道剩余额度。这些信息若互相隔离，可能导致：

```text
为了便宜而切模型
→ 冷缓存重建
→ 启动很长工具
→ 等待后缓存过期
→ 预算只在事后发现超支
```

**工程建议。** 清晰模块边界不意味着独立贪心优化。控制器需要共享任务阶段、预算、缓存状态和待执行依赖，并记录每次策略变化的原因。

### 14.4 八种 Harness：读成设计快照，而不是产品排行榜

下表只转述讲义中的版本描述，不是当前源码审计；“特色”也不意味着只有该项目具备。

| 讲义案例 | 讲义强调的机制 | 成本与性能上的解释性启示 |
|---|---|---|
| Claude Code | policy layer 与 typed hooks | 运行前后统一检查，减少不受控行为；不能只靠提示词约束预算和权限 |
| Codex CLI | 沙箱优先；patch envelope 受语法约束 | 减少非法编辑与失控执行，降低恢复成本 |
| DeepSeek Harness | loop 也是插件；请求是日志快照；compare-and-swap 编辑 | 可替换组件，避免依据过期文件继续写入 |
| OpenCode | 共享 session server；受大小限制的模糊编辑；文件快照 | 会话与客户端分离，恢复文件状态而不只恢复聊天 |
| Pi | 小核心；缓存保温先判断预期节约 | 少量核心功能与经济性门槛，避免优化本身成为浪费 |
| oh-my-pi | hashline 编辑；持久 shell；原生开发工具 | 减少重复旧文本和初始化，提升执行接口效率 |
| OpenClaw | 会话队列；压缩前写记忆；不可信文本隔离机制 | 保存状态后再压缩，避免同会话并发破坏上下文 |
| Hermes Agent | 后台检查并更新记忆/Skills；较早压缩；执行前写调用记录 | 更好追踪恢复和经验，但需承担维护与压缩成本 |

[L，pp. 46–53](#src-l)

### 14.5 几个机制不能过度解读

Compare-and-swap 在文件变化后拒绝旧编辑，可能增加一次重读，但避免将错误修改继续传播。拒绝并不自动算低效，应比较后续返工。

执行前日志提供恢复依据，却不自动实现 exactly-once。外部动作成功后、结果落库前崩溃，仍会产生不确定状态；需要幂等键、状态查询或补偿流程。

压缩前写记忆能减少丢失，却增加一次保存成本；Skill 自动更新也可能引入陈旧或错误规则。这些收益需要通过回归评测，而不是由“自学习”“可恢复”的命名保证。

以上是工程分析。讲义所列具体 API 数量、工具数、压缩阈值等只能作为当时案例，不能作为长期选型参数。[L，pp. 48、50、52–53](#src-l)

### 14.6 一套适合起步的责任划分

**工程建议。**

| 组件 | 负责什么 | 至少要暴露什么 |
|---|---|---|
| TaskState | 任务、证据、待解决问题、版本 | 当前进展与验收状态 |
| ContextBuilder | 请求构造、裁剪、压缩 | 长度、前缀版本、重建原因 |
| ModelPolicy | 模型与 effort 选择 | 选择原因、预计成本、升级条件 |
| ToolExecutor | 参数校验、权限、执行与恢复 | 工具状态、副作用、错误类型 |
| Verifier | 执行与事实检查 | 检查范围、结果、未覆盖项 |
| BudgetManager | 预留、结算、并发额度 | 已花费、已预留、剩余预算 |
| TraceStore | 原始 usage、依赖、状态事件 | 可重放的版本化轨迹 |

这不是要求构建七个网络服务。它们可以是一个进程中的模块，关键是可测试、可观测、责任明确。

## 15. 预算、停止与可观测性：把控制从提示词移到 Harness

### 15.1 预算是执行约束，不是模型记住的愿望

讲义 p. 26 示例包含美元、模型调用数、工具时间和每步重试上限，并强调根据成功轨迹分布选择阈值。示例中的 10 美元、80 次调用、15 分钟、两次重试不是普适默认值。[L，p. 26](#src-l)

只写“请节约成本”，无法保证多个并行 worker 不超支。预算应由共享账本约束，并在调用前预留、调用后按实际 usage 结算。

### 15.2 并行预算要扣除已经承诺的开销

**工程建议。**

$$
B_{\mathrm{available}}
=B_{\mathrm{total}}-C_{\mathrm{settled}}-C_{\mathrm{reserved}}
$$

一个 worker 准备发出请求时，先原子预留其预算，再发送。响应到达后按真实费用结算，释放未用部分。若请求超时但服务端是否计费未知，应标记待核对，而不是立即认定免费并释放全部额度。

还要分别限制总时长、并行槽位、单工具超时和重试次数。美元限额无法单独阻止一个便宜但永不结束的工具。

### 15.3 什么时候停止？

材料提出验证通过、没有新增通过测试、相同错误重复、达到上限等停止信号，并建议留下摘要而不是放任失控。[L，p. 26](#src-l)

**工程建议。** 对知识任务，可记录未解决问题是否减少、关键证据是否补齐、矛盾是否解决；对代码任务，可记录测试状态、错误类别与文件状态变化。不要把暂时没有输出的长测试误判成没有进展。

停止状态至少区分：完成、证据不足、预算耗尽、超时、权限阻断、不可恢复错误、等待人工。未完成时不能把“停止”包装成“任务成功”。

### 15.4 重试的单位应是错误类型

临时网络错误可以有限退避；参数错误先修正参数；同一 schema 错误重复出现应检查适配而不是反复提高 effort；权限错误应按授权流程处理；有副作用的超时先确认执行状态。

这是将工具效率论文的格式崩溃与讲义的有限重试结合的工程策略，不是所有工具统一重试两次。[T，§6.2](#src-t) [L，p. 26](#src-l)

### 15.5 最小执行循环：说明职责，而不是伪装成可部署框架

以下为**架构伪代码**，真实实现还需供应商适配、并发控制、存储与安全策略：

```text
读取任务与最近有效检查点
循环：
    检查任务验收状态、预算、期限和重复错误
    若达到停止条件：持久化状态，交付结果或未完成摘要
    构造必要上下文，记录前缀、长度与版本
    根据阶段、验证反馈、缓存状态选择模型与 effort
    原子预留本次最大允许费用
    发出模型请求，保存原始 usage，结算实际费用
    若有工具调用：
        校验 schema、权限、状态版本与副作用风险
        执行前持久化必要调用标识
        并发执行相互独立、预算允许的动作
        对错误分类，保存结果与状态变化
        只把必要观察放回模型上下文
    运行对应验证，更新证据与进度
```

循环的重点是：模型不拥有最终预算权限；工具输出不自动成为可信指令；检查器只对实际检查过的范围负责；日志不是事后装饰。

### 15.6 一条 trace 应能回答“为什么贵”

| 记录层次 | 关键字段 | 用途 |
|---|---|---|
| 任务与版本 | task_id、trace_id、parent_span、模型/提示词/工具/数据版本 | 保证可比较与可重放 |
| 计费 | 原始 usage、四类 token、价格版本、实际费用 | 防止重复计费和口径混用 |
| 时间与依赖 | 起止时间、排队、模型、工具、重试、依赖边 | 找到关键路径与等待来源 |
| 上下文 | 长度、前缀版本、cache read/write、压缩原因、重读次数 | 区分膨胀与缓存失效 |
| 执行与结果 | 错误类别、测试结果、证据变化、停止原因 | 判断少花钱是否只是少完成任务 |

这展开了讲义“记录每次调用、token、工具与等待”的优化闭环。[L，p. 38](#src-l)

### 15.7 不要只记录成本下降，还要记录反向成本

压缩后文件重读率，路由后的升级率与静默错误率，子 Agent 的重复输入量，投机请求丢弃率，取消后的远端计费，以及重复执行造成的恢复次数，都是净收益的一部分。

讲义 p. 25 将其统一为：

$$
\text{Net saving}=\text{Gross saving}-\text{Counter-cost}
$$

这应当是仪表盘的设计原则，而不只是一句课程总结。[L，p. 25](#src-l)

## 16. 如何证明优化有效：从单项消融到联合配置搜索

### 16.1 先建立可重放基线，再选择技术

讲义 p. 38 的闭环是：运行并记录、找成本与延迟来源、改一件事、同任务重评估。它要求同时看成功、支出和 p95 延迟，而不是只看 token 减少。[L，p. 38](#src-l)

**工程建议。** 首先做一个功能简单、验证明确、日志完整的基线。它不必一开始最便宜，但必须知道哪里失败、哪里等待、费用如何计算。没有这个基线，复杂 Router、自动压缩或多 Agent 往往会一起改变太多变量。

### 16.2 不同任务的主要节约来源不同

Anthropic `cost-optimize` 的四个案例说明：先定位主要开销，再选策略。[A，Automating cost reduction](#src-a)

| 工作负载 | 材料中的主要调整 | 报告成本变化 | 材料支持的质量描述 |
|---|---|---:|---|
| LegalBench | 缓存、低 effort、Batch | 约降低 67% | accuracy 变化不到一个百分点；thinking token 降约 84% |
| tau2-bench retail | 识别约 93% 可缓存前缀 | 约降低 73% | pass rate 不变 |
| OfficeQA Pro | Batch、将过大文档裁到相关内容 | 约降低 72% | 得分无显著变化 |
| SWE-bench Verified | 已有缓存基础上改 medium effort、减少冗余输出 | 约降低 24% | 正文报告成本变化，不能自行补出未提供的精确质量差 |

这些是特定基线、任务和配置下的报告结果。它们不能直接变成其他业务的收益承诺，也不能证明其中每个单独调整都贡献了相同效果。

### 16.3 实验前至少冻结四组条件

| 条件 | 应固定或记录的内容 | 避免的误判 |
|---|---|---|
| 任务与环境 | 相同任务、代码起点、工具版本、数据快照 | 任务变简单被当成策略改进 |
| 配置版本 | 模型、prompt、effort、schema、上下文策略 | 无法定位到底改了什么 |
| 缓存条件 | 冷启动、热缓存或真实调用间隔回放 | 测试缓存状态不公平 |
| 评价口径 | 成功标准、超时、取消、失败成本 | 省钱只是少完成工作 |

实时网页和外部数据可能变化。对可重复实验可使用固定快照或可控回放；线上效果则单独观察，不能把两种测试混作同一证据。

### 16.4 分开统计价格收益与行为收益

**解释性推导。** 令 $\tau$ 为执行轨迹，$p$ 为价格表。要测系统行为是否更高效，可用同一参考价格重算：

$$
C_{\mathrm{old,ref}}=C(\tau_{\mathrm{old}},p_{\mathrm{ref}})
$$

$$
C_{\mathrm{new,ref}}=C(\tau_{\mathrm{new}},p_{\mathrm{ref}})
$$

真实账单则按各自实际价格另算。这样可以区分“供应商降价”和“Agent 少走了弯路”。Anthropic 的强模型低 effort 比较同时涉及模型行为和读取价格差异，这正是需要拆开的两种来源。[A，Effort](#src-a)

类似地，缓存读取 token 占比不等于节约比例。可以另定义相对“同一条轨迹不使用缓存”的估算差值，但应标注这是反事实估算，不是现实中真的跑过的另一条轨迹。

### 16.5 先单项消融，再检查关键交互

一开始一次改一个变量，便于归因；确认哪些变量有效后，再测试交互。例如：

| 联合变化 | 为什么不能只看单项效果 |
|---|---|
| 路由 × 缓存 | 单价下降可能被冷缓存重建抵消 |
| 压缩 × 检索 | 摘要短了，但文件重读可能增多 |
| effort × 提示词 | 旧提示词仪式可能放大高 effort 开销 |
| 并行 × 资源限制 | 单任务并行加速可能造成全局排队 |
| 子 Agent × 上下文隔离 | 主上下文缩短，但重复输入与汇总增加 |
| cascade × 验证器 | 看似省钱可能增加未发现错误 |

单项实验用于理解原因，联合实验用于选择真实部署配置。两者不是对立方法。

### 16.6 优化顺序会改变 Router 的标签

如果先用不合理的旧提示词测试弱模型，Router 会学到“很多问题必须升级”。之后修复提示词和工具协议，弱模型已能处理更多任务，但旧 Router 仍可能过度调用强模型。

这连接 Anthropic 的提示词迁移与 RouteLLM 的数据分布依赖。[A，Instructions](#src-a) [R，§6](#src-r)

**工程建议的顺序：** 修协议和确定性流程 → 建立上下文与缓存基线 → 扫描模型与 effort → 校准或训练路由 → 调整并行与投机 → 重新验证整体质量与成本。具体瓶颈不同，顺序可以调整，但路由标签必须随实际配置版本更新。

### 16.7 训练、验证、测试应承担不同角色

RouteLLM 留出验证数据用于模型选择，并进行训练—评估问题的相似性污染检查；Anthropic 的 hillclimb 用训练失败指导修改，再看保留测试集。[R，§5、附录 B](#src-r) [A，Getting started](#src-a)

**工程建议。** 按任务家族、文档来源或时间切分，避免同一问题轻微改写后落入两边。测试集不能被不断读取、修补后仍叫“未见测试”。新的最终配置需要真正没参与调参的数据来评价。

### 16.8 随机性和统计单位不能忽略

同一任务多次运行可能有不同轨迹，因此一次跑出的 10% 成本变化不一定稳定。应做配对任务比较，必要时多次重复，报告分布、失败类型和不确定性，而不是只给一个平均数。

论文也提醒，同一轨迹内部的步骤存在序列依赖，逐步 p 值仅作描述，不能当独立样本的正式检验。[T，p. 5 注释](#src-t)

**工程建议。** 以完整任务或轨迹作为统计单位；使用 bootstrap 等方法时也按任务重采样，而不是将一条轨迹的一百步当成一百个独立任务。任务集很小，尤其是只含 26 题时，p95 等尾部指标应结合单条轨迹查看，避免过度解释少数观测。

### 16.9 一个结果报告至少应该长什么样？

| 维度 | 建议内容 |
|---|---|
| 基线与候选 | 完整配置版本、任务与数据快照 |
| 质量 | 成功数、成功率、分任务类型质量、静默错误 |
| 费用 | 总费用、全部成本/成功数、平均与尾部、冷/热缓存区分 |
| 时间 | 平均与 p95 任务时间、超时率、关键路径分解 |
| 行为 | 模型调用、工具调用、重复错误、证据重取、升级与压缩 |
| 反向成本 | Router、摘要、验证、投机丢弃、人工与恢复开销 |
| 不确定性 | 重复运行次数、样本量、置信区间或波动范围 |
| 决策 | 为什么保留或拒绝该候选，尚未验证什么 |

这张表是工程模板，不是附件报告的原始统一格式。

## 17. Assignment 3：把课程转成受预算约束的 Harness 实验

### 17.1 先看清环境，而不是立即实现复杂 Agent

作业名称为 **MadsOpt: Harness Competition**。框架有 26 个任务，图示分为 Agent、Task 和 Grading 三类容器；Agent 与任务分离，通过 HTTP 请求访问任务环境。Dispatcher 传入任务，Agent 产生 patch，再由评估流程返回结果。最多五个任务并行。[H，pp. 1–3](#src-h)

限制如下：

| 项目 | 作业材料规定 |
|---|---|
| 模型档位 | Expert、Standard、Starter |
| 单次 `evaluate()` | 最长 35 分钟 |
| 整体时间 | 4 小时 |
| 每日预算 | 30 美元 |
| 每次 run | 10 美元 |
| 最大并行任务 | 5 |
| 网络范围 | 离线评估，仅允许课程指定 API 域名 |

[H，pp. 2–4](#src-h)

**10 美元是整次 run，不是每个任务。35 分钟是每次 evaluate()，不是材料规定的每任务固定时长。** 这与主讲义 p. 26 的示例预算必须区分。

### 17.2 评分不是只追求便宜

提交按解决任务数、每个成功任务成本、每个成功任务时间评价，使用 Skyline 三指标比较；至少解决七个任务，另有解决十六个任务的 baseline。材料说明满足 baseline 时评分为 $\max(81-r,50)$，否则为 $81-r$，并给出排名示例 `1,1,1,4,...`。[H，pp. 6–7](#src-h)

幻灯片没有给出全部评分脚本细节，所以不能自行规定 Skyline 的全部实现、单位成本的具体分母或超时处理方式。实际复现应以课程脚本为准。

材料还说明一次只能有一个排队提交，取消的提交也计入并消耗每日预算。排行榜占 80，writeup 与 video 各占 10。[H，pp. 6–7](#src-h)

### 17.3 哪些内容允许修改？

作业将 Agent 逻辑和 sandbox 请求放在 `src`，提交的是 `src.zip`；`dispatcher` 与 `evaluation_scripts` 用于任务调度和评分，要求本地测试时不要修改。初始化与打包脚本还用于生成会话日志。[H，p. 5](#src-h)

优化对象是 Agent，不是评分器。不能用改测试或隐藏评测结果的方法制造成功。主讲义也明确要求不要篡改会话日志。[L，p. 3](#src-l)

### 17.4 五轮实验，比一开始做所有技术更可控

| 轮次 | 实现重点 | 主要判断 |
|---|---|---|
| 基线 | 单控制循环、工具契约、可用 patch、验证与完整 trace | 能否稳定跑通，主要失败是什么 |
| 步骤优化 | 批量读取、程序控制确定性工作、错误分类 | 是否减少无用模型往返 |
| 上下文优化 | 限定返回、保存原始材料位置、必要摘要 | 重读和重建是否抵消节约 |
| 配置实验 | 三档模型、可用参数、任务阶段 | 哪些场景真实需要升级 |
| 联合调度 | 共享预算、阶段路由、有限并行 | 成功数、总成本、整批完成时间是否一起改善 |

这是应用本节思想的实验建议，不是已经跑过的获奖方案。作业 API 的三档真实模型身份、价格、缓存和 effort 支持并未在这份幻灯片中完整披露，不能把 Claude 平台特性直接假设成课程接口能力。

### 17.5 全局预算不应机械平均

10 美元除以 26 个任务约为每个 0.38 美元，但平均分配未必最优。有的任务只差一次有效验证就能完成；有的陷入协议错误，再加推理预算没有意义。

**工程推导。** 可按“额外预算带来的预期成功概率增量 / 额外预算”安排下一次投入，同时满足最低覆盖和任务成功要求。初期用任务状态、错误类别、历史统计作规则估计即可，不必一开始训练复杂调度器。

最后还应预留保存 patch、持久化状态、生成未完成说明的时间和预算，避免所有资源用在探索，产物尚未保存就被强制停止。

### 17.6 一套适合 writeup 的结构

写清任务环境与未改动的评分部分，描述基线，按单项与联合变化报告质量/成本/时间，列出失败案例和反向成本，最后解释为何选择最终配置。不能只展示最成功一次运行，也不能将取消运行的费用从比较中抹掉。

主讲义 p. 38 的图底部提到了 Assignment 4；本章将其测量闭环应用到 Assignment 3，是教学迁移，不改写幻灯片原文。

## 18. 投研与审核 Agent：用证据工作流贯通全部机制

本章为**工程设计示例**。它将材料的方法迁移到知识工作，不是对法规条文、财务数据或真实系统效果作判断；没有模拟成已经上线的生产收益。

### 18.1 示例一：两期财报比较

任务是：比较一家公司两期财报，解释利润变化，并给出原文证据与页码。

一个低效轨迹可能是：模型先长篇列出可能原因；逐份检索并读取完整报告；每得到一个数字都调用模型重新判断；手工算完再让 Python 重算；所有过程留在上下文；中途频繁切模型；压缩丢失单位和期间；最后不得不重新读取报告。

这不是单独一个模型的问题，而是 first-step effect、工具负载、确认式重复、缓存失效和状态丢失叠加。

### 18.2 更合理的阶段划分

| 阶段 | 工作分配 | 必须保留的状态 | 验收信号 |
|---|---|---|---|
| 任务确定 | 明确公司、两期范围、比较口径与输出 | 任务契约 | 核心歧义已解决 |
| 文档定位 | 检索或索引定位原始报告 | 文档 ID、版本、日期、页码范围 | 两期材料及必要附注齐全 |
| 数字获取 | 抽取相关表格和段落 | 原始数字、单位、证据位置 | 关键字段与口径核验通过 |
| 确定性计算 | 程序计算增减、比例和对应检查 | 输入、公式、结果 | 数值检查通过 |
| 解释判断 | 模型分析变化原因与证据支持程度 | 事实、假设、冲突、未知项 | 主要判断与证据一一对应 |
| 最终验证 | 检查引用、数字一致性、遗漏与不确定性 | 完成状态及未解决问题 | 达到验收标准或明确转交 |

这些阶段不必各自成为独立 Agent。默认一个主控制器，只有探索隔离或独立并发确有价值时才开子任务。

### 18.3 每份材料如何影响这个设计？

**讲义的作用：** 批量读取必要片段、让确定性计算离开模型循环、控制上下文驻留、记录关键路径。

**PTE 的作用：** 早期不要生成大量没有证据的长推导；工具返回只提供相关内容；避免“先手算再打印确认”替代真正独立校验。

**Anthropic 文章的作用：** 稳定规则与工具前缀，按阶段校准 effort；将验证写成明确对象与条件；不要为少量短输出贸然放弃热缓存。

**RouteLLM 的作用：** 基于这类真实任务的成功差异决定何时升级，不按“抽取一定简单、分析一定复杂”机械分档。复杂表格抽取可能比某些文字解释更难。

**Assignment 的启示：** 一批公司研究共享预算，多个任务不能各自无限重试；最终应按完成任务和证据质量计效果，而不只看调用次数。

上述是跨材料综合后的工程解释，不是这些来源共同报告过的一个实验。

### 18.4 证据状态应支持追溯与重新获取

一个适合这类任务的记录可以是：

```json
{
  "claim_id": "claim-demo-01",
  "claim_type": "profit_change_explanation",
  "status": "needs_review",
  "evidence": [
    {
      "document_id": "report-current-v1",
      "page": 18,
      "locator": "table-2-row-5",
      "period": "period-current",
      "unit": "原表单位",
      "source_version": "v1"
    }
  ],
  "calculation_id": "calc-demo-03",
  "unresolved": ["两期资料对该指标的定义是否完全一致"],
  "next_action": "核对历史附注中的定义"
}
```

这是说明性数据结构，里面没有真实公司结论。它让压缩、重新检索与人工审核共享同一证据身份，而不是仅交换一段不可追溯的总结。

### 18.5 示例二：营销材料预审核

可把流程分为文档预处理、候选风险识别、规则与事实证据获取、复杂语义判断、输出检查及人工复核。

| 层次 | 适合的设计 | 必须避免的省钱方式 |
|---|---|---|
| 预处理 | 解析、版本、页面定位与确定性格式处理 | 用不可靠摘要替代原始证据 |
| 候选识别 | 轻量模型或规则先定位需判断内容 | 未验证的低召回筛选成为高风险问题唯一入口 |
| 证据获取 | 独立查询可并行，返回相关条款或事实定位 | 为缓存命中长期复用过期材料 |
| 语义判断 | 将片段、相关规则、事实交给合适模型 | 没证据时只提高 effort |
| 输出检查 | 程序检查引用存在性、字段和数值一致性 | 把 schema 合法当成语义合规 |
| 人工复核 | 接受、拒绝与原因回流 | 把采纳率直接当成正确率 |

这里不提供具体法规结论，也不假设 AI 取代必要人工审核。例子只说明：把模型能力集中在不确定性较高的位置，并让证据与执行流程可验证。

### 18.6 业务指标要覆盖被模型费用遮住的部分

研究任务可以评价关键结论证据覆盖、口径一致性、人工修订时间与交付完成率；审核任务可以评价已知问题检出、误报、证据准确性和人工复审耗时。指标定义需要真实标注和验收规则。

采纳不等于没有漏检，拒绝也不一定代表事实错误，可能只是措辞或适用场景不同。因此用户反馈适合形成训练与诊断材料，但不能单独承担质量真值。

把总成本中的人工与返工部分记录下来，才有机会判断“减少 API 费用”是否真的提高业务效率。

## 19. 总结：一张可以用于排查系统的诊断地图

### 19.1 不要先选技术，先识别机制

| 观测到的症状 | 优先怀疑什么 | 可先做的实验 | 必须同时监控什么 |
|---|---|---|---|
| 每次调用便宜，任务总账昂贵 | 步骤多、失败重试、用户返工 | 明确完成条件，分类重复错误 | 成功率、静默错误、任务覆盖 |
| 输出变短，但后期步骤仍慢 | 上下文累计、cache 不可复用、长 KV 访问 | 裁剪无关早期内容，对照模型时间 | 重读率、证据丢失与质量 |
| 缓存读很多，账单仍高 | 缓存内大量无关历史、重复调用 | 减少驻留内容与模型往返 | 缓存重建和后续恢复成本 |
| 换便宜模型后整体变贵 | 冷缓存、更多步骤、错误传播 | 比较完整剩余轨迹，不只单价 | 升级次数、下游返工 |
| 高 effort 没有质量提升 | 信息、工具或任务契约瓶颈 | effort sweep 加失败分类 | 是否过早停止、证据覆盖 |
| 模型总在调用工具确认 | 无停止条件的验证仪式 | 改成明确检错目标 | 真正错误检出能力 |
| 开并行后所有任务变慢 | CPU、工具或 API 竞争 | 按资源类型限制并发 | 整批吞吐、p95、总成本 |
| 压缩后重复找资料 | 丢了状态、证据身份或排除路线 | 保存结构化状态后再压缩 | 重新获取成本与错误 |
| 成本漂亮但人工更累 | 验证不足、交付不完整、误报 | 加入人工和返工指标 | 全链路成功成本 |

这些是工程诊断假设，而不是看到症状就能确定病因。每个假设都需要在同样任务上验证。

### 19.2 四条最值得带走的综合结论

**第一，优化单位是轨迹，不是一次调用。** 早期错误和冗余有后续成本；便宜模型、压缩和子 Agent 都必须计算反向成本。

**第二，证据、计算和等待是三种不同资源。** 更多思考不能自动补足缺失证据；更少 token 不一定代表更少计算；模型更快也不一定缩短关键路径。

**第三，模型选择是系统配置选择。** 模型、prompt、effort、工具协议、缓存和验证共同决定结果。Router 不能脱离这些条件独立宣称省钱。

**第四，可靠性与经济性经常同向。** 明确完成标准、可恢复状态、适配正确的工具和有效验证，可以减少最昂贵的返工。但验证本身也要具体、有限、可测。

最终排查顺序可以概括为：

```text
任务是否明确、验收是否可信？
→ 哪些步骤没有推进任务？
→ 哪些历史负担被重复消费？
→ 当前不确定性需要证据、代码还是更强推理？
→ 工作是否位于关键路径？
→ 优化后的净收益是否在同任务上成立？
```

> **一个优秀的 Agent 不是尽量少调用模型，而是在预算和时限内，用可追溯的证据、适量的推理与有效的验证完成任务。**

## 附录 B：术语与公式索引

### B.1 术语速查

| 术语 | 在本文中的含义 |
|---|---|
| Session | 一段会话，可能包含多个用户 turn |
| Turn | 一次用户输入及 Agent 为其完成的回应过程 |
| Step | 轨迹中的一个模型或工具阶段；具体统计需注明是否仅计模型调用 |
| Trajectory | 从任务开始到结束、失败或转交的完整执行过程 |
| Prefill | 处理已有输入并构建对应模型状态 |
| Decode | 在已有状态上逐个生成 token |
| KV cache | 用于复用历史表示的键值状态 |
| Prompt cache | 对相同输入前缀状态的复用机制，不等于答案缓存 |
| TTL | 缓存有效期；具体起算、刷新与失效规则由平台决定 |
| Compaction | 将历史转换为更紧凑工作状态，可能有信息与缓存重建成本 |
| Effort | 材料中控制推理投入的配置维度，不等于最终回答长度 |
| PTE | Prefill Token Equivalents，论文提出的计算成本近似指标 |
| HOI | PTE 论文采用的峰值计算吞吐/峰值内存带宽比例 |
| PGR | 相对于强弱模型质量差距，Router 收回的比例 |
| CPT | 达到某个 PGR 所需的最小强模型调用比例 |
| APGR | 扫描强模型调用预算时，PGR 曲线面积 |
| Router | 选择由哪个模型处理请求或步骤的策略 |
| Cascade | 先尝试一个模型，按检查结果升级或继续 |
| Ensemble | 多个模型或分支生成后再选择、比较或合并 |
| Critical path | 决定最终完成时间的依赖路径 |
| Speculative action | 主路径决定之前预测并提前执行的候选动作 |
| Counter-cost | 优化引入的反向费用、等待、恢复或质量代价 |
| Harness | 包围模型的任务执行、上下文、工具、权限、状态与观测运行系统 |
| Pareto frontier | 在目标指标上未被其他配置全面超过的候选集合 |

### B.3 一个可单独复算的成本函数

以下为**本文工程示例**，只计算已经规范化为互斥桶的 usage，不调用任何供应商 API，也不实现预算预留或完整 Agent。价格由调用方提供，不能用它猜测未知账单。

```python
from dataclasses import dataclass
from decimal import Decimal


@dataclass(frozen=True)
class Usage:
    uncached_input: int
    cache_write: int
    cache_read: int
    billed_output: int


@dataclass(frozen=True)
class Prices:
    # 单位均为美元/百万 token；用 Decimal("...") 构造。
    uncached_input: Decimal
    cache_write: Decimal
    cache_read: Decimal
    billed_output: Decimal


def llm_cost(usage: Usage, prices: Prices) -> Decimal:
    """只对规范化后的互斥计费桶求和，不重复加入总输入字段。"""
    names = (
        "uncached_input", "cache_write", "cache_read", "billed_output"
    )
    total = Decimal("0")
    for name in names:
        tokens = getattr(usage, name)
        price = getattr(prices, name)
        if type(tokens) is not int or tokens < 0:
            raise ValueError(f"{name}: token 数必须是非负整数")
        if not isinstance(price, Decimal):
            raise TypeError(f"{name}: 价格必须使用 Decimal")
        if not price.is_finite() or price < 0:
            raise ValueError(f"{name}: 价格必须有限且非负")
        total += Decimal(tokens) * price
    return total / Decimal("1000000")


# 对应 11.3 的教学价格，不是真实供应商报价。
strong = Prices(
    Decimal("1"), Decimal("1.25"), Decimal("0.1"), Decimal("5")
)
weak = Prices(
    Decimal("0.2"), Decimal("0.25"), Decimal("0.02"), Decimal("1")
)
assert llm_cost(Usage(0, 0, 100_000, 200), strong) == Decimal("0.011")
assert llm_cost(Usage(0, 100_000, 0, 200), weak) == Decimal("0.0252")
```

供应商折扣、阶梯价格、Batch、不同 TTL 写入价、失败请求收费、工具费用等，应先按实际规则转换成对应 usage/price 或独立账项，不能从这段简化代码中推断。
