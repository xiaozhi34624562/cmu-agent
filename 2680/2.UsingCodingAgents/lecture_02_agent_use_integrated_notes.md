# Lecture 02｜Agent Use：从模型调用到可验证的工作系统

> 核心问题：当模型已经具有较强的推理和编程能力时，我们应当怎样组织任务、上下文、记忆、工具、过程知识、权限和反馈，才能把模型能力转化成稳定的工作能力？

**面向读者：**具有 Java／Python 或其他软件开发经验的 LLM 开发工程师。

## 1. 课程地图：九份参考资料分别补上了什么

### 1.1 讲义提供结构，参考资料提供机制、证据和边界

讲义回答“一个无状态模型怎样成为 Agent”，主要展开 Memory、Tools、Skills、Hooks 与 Plugins。它的关键执行边界是：**模型提出下一步，Harness 执行下一步，执行结果再进入上下文。**[L02，p.4、p.6—14](#ref-l02)

九份材料并不处在同一个证据层级：产品文档说明特定实现；工程文章报告组织或个人实践；实验论文在指定任务与配置上比较效果。不能把三者都当成普适定理。

| R02 | Agentic Engineering Patterns | 工程师责任、测试先行、实际运行、证据式讲解、经验资产积累 | 上传的是目录；章节正文单独列为延伸阅读 |

### 1.2 三组张力，是理解这节课的钥匙

**第一组：需要更多专业知识，还是应该减少指令？**

R03、R05 强调补充组织知识与过程知识。R08 发现，一些看起来正确的通用指令未必产生预期收益。它们研究的不是完全相同的问题：补充模型不知道的事实，与反复要求它“认真、清晰、完整”，不能混为一谈。[R03](#ref-r03)；[R05，Skills are just instructions](#ref-r05)；[R08，§5—7](#ref-r08)

**第二组：代码执行能节省开销，为什么 MCP／CLI 的成本比较仍不稳定？**

R04 解释可减少浪费的机制；R09 测量具体系统，发现协议名称不足以解释结果。工具目录如何加载、结果返回多少内容、模型走多少轮、是否重复调用，都属于实际系统行为。[R04](#ref-r04)；[R09，§4、§8](#ref-r09)

**第三组：一个 Agent 加多个 Skills，还是多个 Agent？**

R05 关心知识与上下文不必要地被分散；R07 关心规划、执行和审查的责任分工。知识模块、工作阶段、上下文隔离和权限隔离是不同维度，不能仅凭 Agent 数量判断架构好坏。[R05，Skills replace system prompts](#ref-r05)；[R07](#ref-r07)

本文的总原则是：**把每一种问题交给真正能解决它的那一层，而不是给所有问题都增加一段提示词。**这是综合解释，不是某篇论文的原句。

## 2. Agent Loop：从一次回答到一个可验证的交互循环

> 讲义主线：p.6—14。参考资料：R05 的消息线程解释，R01 的验证循环，R02 的工程责任，R09 的真实状态验收。

### 2.1 一条用户消息，为什么会触发很多次模型调用

讲义第 6 页明确指出：一次用户请求通常展开为多次模型推理与工具执行，而不是一次 API 请求、一次回答。第 10 页以测试失败修复说明了 `pytest → 读取文件 → 搜索 → 编辑 → pytest` 的交替过程。[L02，p.6、p.10](#ref-l02)
<!-- 原始文件证据：fileciteturn14file0L74-L89 fileciteturn14file0L155-L169 -->

以“修复过期会话仍被接受的问题”为教学例子：

```text
用户目标
  ↓
Harness 组织上下文
  ↓
模型提出：运行相关测试
  ↓
Harness 检查权限、执行测试，返回失败信息
  ↓
模型提出：读取会话校验代码及调用方
  ↓
Harness 返回代码片段
  ↓
模型提出：修改边界判断
  ↓
Harness 执行获准的修改
  ↓
模型提出：重新运行测试
  ↓
根据新结果继续修复，或者提交完成说明
```

循环的价值在于：**每次行动都能根据新观察修正，而不是把起初猜测的计划一直执行到底。**

### 2.2 模型提出动作，Harness 执行动作

模型输出 `Bash("pytest")`，并不等于测试已经运行。查找实现、校验输入、授权、启动进程和收集结果，发生在运行时。R05 用天气查询展示了相同机制：工具结果被追加到消息线程，再次提供给模型。[L02，p.9](#ref-l02)；[R05，LLM 101](#ref-r05)
<!-- 原始文件证据：fileciteturn14file0L135-L150 fileciteturn14file5L298-L338 -->

| 问题 | 主要责任层 |
|---|---|
| 下一步应该调查什么？ | 模型的决策 |
| 本轮看见什么信息？ | Harness 的上下文组织 |
| 参数是否合法？ | 工具契约与校验 |
| 动作有没有权限？ | 授权与策略执行 |
| 外部世界实际发生了什么？ | 工具与环境 |
| 是否完成用户目标？ | 验证机制，必要时包括人 |

这张表是对讲义执行边界的综合整理。它提醒我们：同一模型进入不同运行环境后，实际面对的任务信息、行动空间与反馈可能不同。

### 2.3 停止调用工具，不等于任务成功

R05 用“模型不再要求调用工具”解释一个最小循环的停止方式。这个解释有助于理解机制，但它不是生产系统的完整验收条件。[R05，Agents are a loop](#ref-r05)

R09 因而在 Agent 结束后检查仓库，而不是接受“已完成”的文字：分支存在吗？补丁真的进入文件了吗？PR 存在吗？文件数报告正确吗？每轮前恢复初始仓库状态，避免上一轮的残留被算作本轮成果。[R09，§2.1—2.2，p.4](#ref-r09)
<!-- 原始文件证据：fileciteturn14file9L171-L191 -->

**工程推导：**将结束状态明确区分为“已验证完成”“等待审批”“环境阻塞”“部分完成”“验证未通过”“预算耗尽”。不要只用一个 `done=true` 混合这些情况。

### 2.4 内层循环与外层循环

内层循环是模型与工具的交互。人管理的外层循环是：

```text
定义问题 → 明确范围和验收 → 执行 → 检查证据
       → 纠偏或接受 → 保存可复用经验
```

R02 的 *What is agentic engineering?* 强调，工程师仍需选择问题、配置工具、明确需求并验证结果；它把“辅助开发软件”与放弃检查代码的工作方式区分开来。[R02a](#ref-r02a)
<!-- 延伸阅读证据：citeturn901974view0 -->

因此，Agent Use 不是单纯写出更长的 Prompt，而是管理一个能获得信息、采取行动、接受检验并积累经验的工作过程。

### 2.5 一个学术抽象：模型只能依据被提供的信息行动

**教学抽象，非原论文定理：**

$$
c_t=\operatorname{BuildContext}(g,h_t,m_t,\mathcal{T}_t)
$$

$$
a_t\sim\pi_\theta(\cdot\mid c_t)
$$

其中，$g$ 是目标，$h_t$ 是运行历史，$m_t$ 是本轮加载的记忆，$\mathcal{T}_t$ 是当前暴露的工具，$c_t$ 是模型可见的信息，$a_t$ 是提出的动作。

这个抽象的用途不是炫耀公式，而是定位错误：没有读到的文件、丢失的异常字段、过期的任务摘要，都可能使模型基于不完整或错误信息行动。提高 Agent 能力，既包括改进决策，也包括改善它观察世界的方式。

## 3. Context 与 Memory：决定模型在什么时候知道什么

> 讲义主线：p.7—8、p.12、p.16—26。参考资料：R01 的会话管理，R03／R05 的分层加载，R08 对规则数量与内容的实证限制。

### 3.1 用户输入之前，上下文已经不是空的

讲义第 7 页列出系统指令、项目环境、持久化记忆、工具定义、Skills／MCP 发现信息和用户消息。页面所示“10+k Token”描述的是讲义展示的环境，不是所有 Agent 的统一启动成本。[L02，p.7](#ref-l02)

因此，看到相同的用户问题与相同的模型名称，不代表两次调用拥有相同输入。项目指令、工具目录和历史轨迹都可能改变决策条件。

### 3.2 仓库在磁盘上，进入模型的是需要的片段

讲义第 8 页的关键关系是：文件系统保存完整仓库，搜索和读取工具选择相关片段，只有这些片段进入本轮上下文。[L02，p.8](#ref-l02)

```text
目录与索引 → 搜索命中 → 相关文件 → 具体实现
                         → 必要调用方与测试
```

**综合解释：**上下文管理不是“读得越少越好”，而是在足以支持当前判断的前提下减少无关内容。只读一个函数而漏掉调用约定，是信息不足；读遍大量无关文件，是信息过载。

**工程边界：**没有整体发送仓库，不等于读取出的片段不会被发送给模型服务。数据保护应围绕实际进入请求的内容设计。

### 3.3 为什么早期的大日志会持续增加负担

**假设性成本模型：**初始上下文长 $B$，每轮平均新增历史 $\Delta$，调用 $N$ 轮，不做压缩，则累计逻辑输入量约为：

$$
\sum_{t=1}^{N}[B+(t-1)\Delta]
=NB+\frac{\Delta N(N-1)}{2}
$$

如果某一轮带入大量无用日志，这段历史可能被后续多轮反复携带。这里算的是逻辑输入量，不是实际账单或计算量；缓存、服务端状态和压缩都会影响成本。讲义第 12 页提醒，重复上下文及缓存读取也需要纳入成本考虑。[L02，p.12](#ref-l02)

**工程推导：**优先检查冗余工具输出、重复发现、失败重试与不必要轮次，而不只是缩短最后的回答。

### 3.4 “无状态”不等于整个系统不能保存状态

R05 说明，连续工作的状态由消息线程和外围系统承载，而不是一次任务结束后自动写进模型参数。[R05，LLM 101](#ref-r05)

需要区分四件事：模型参数中的一般能力、当前上下文中的信息、外部持久化的记忆，以及用于加速重复处理的缓存。讲义用文件记忆解释本课中的实现，不是在断言所有记忆系统只能使用文件。[L02，p.15—16](#ref-l02)

### 3.5 先按信息性质分类，再决定文件放哪里

**工程分类：**

| 信息 | 例子 | 合适的承载位置 |
|---|---|---|
| 广泛适用的稳定约定 | 测试入口、生成目录、模块边界 | 项目指令、范围规则 |
| 特定任务的过程知识 | 发布准备、队列排障 | Skill |
| 当前任务状态 | 已排除原因、待运行测试 | 任务记录、交接摘要 |
| 大体量事实与证据 | 日志、财报原文、完整查询结果 | 外部文件／数据系统，按需获取 |
| 时效性信息 | 临时降级、当天系统异常 | 带时间与适用范围的记录 |

这比先问“放 CLAUDE.md 还是 SKILL.md”更容易得到稳定答案。

### 3.6 CLAUDE.md 与 Auto Memory 的职责

讲义区分了人工维护的 `CLAUDE.md` 与 Claude 编写的 Auto Memory：前者用于标准、规则、架构与工作约定；后者用于偏好、纠正、项目经验和参考信息。[L02，p.18—19、p.23](#ref-l02)
<!-- 原始文件证据：fileciteturn14file0L323-L337 fileciteturn14file0L409-L422 -->

讲义快照还列出组织、用户、项目和本地指令的不同作用域。项目规则可以共享，本地偏好则不一定应该进入团队版本库。不要把加载顺序等同于“后写的文字可以覆盖组织权限”：文字说明和执行权限仍是不同层。[L02，p.20](#ref-l02)

适合常驻指令的内容是模型无法便宜推断的项目事实，例如运行测试的命令、生成文件的位置和真实的变更边界。不适合反复常驻的是通用语言教程、完整变更日志、秘密信息，以及格式化工具已经落实的长篇风格要求。[L02，p.21](#ref-l02)

### 3.7 拆成多个文件，不一定节省上下文

讲义第 22 页给出 `.claude/rules/`，并说明带 `paths` 条件的规则按相关文件加载；没有 `paths` 的规则仍可能在每次会话加载。[L02，p.22](#ref-l02)

所以，把两千行拆成十份两百行，如果十份都常驻，只改善了文件组织，没有降低总信息量。

Auto Memory 的 `MEMORY.md` 则承担索引功能，主题文件按需读取。讲义中的“前 200 行／25KB”是该快照描述的自动记忆索引加载限制；`CLAUDE.md` 的“两百行以内”是编写建议，两者不能混成同一种限制。[L02，p.21、p.23—24](#ref-l02)

### 3.8 Compaction：把经历压缩成可继续工作的状态

讲义第 12 页示意：上下文不断增长，随后总结旧轨迹、重新注入重要指令与记忆，再继续调用。它并未给出“摘要永远完整保留关键内容”的保证。[L02，p.12](#ref-l02)

**工程推导：**好的交接摘要应分开目标、事实、假设、已执行动作、验证状态和下一步。例如：

```text
目标：修复过期会话仍被接受的问题。
事实：异常集中在有效性边界判断；不是请求解析失败。
当前改动：session.py 一处判断；尚未合并。
已验证：目标回归测试通过，证据对应当前工作区快照。
未验证：相关集成测试；时区转换调用路径。
约束：不弱化断言，不进行无关重构。
下一步：运行相关集成测试；必要时读取调用方。
```

R01 建议避免混杂无关任务的长会话，并在反复走错后，把已经学到的事实变成更清晰的起始说明。其重点不是机械地“失败两次就清空”，而是避免把全部错误路线继续当作执行上下文。[R01，Manage your session；Avoid common failure patterns](#ref-r01)
<!-- 原始文件证据：fileciteturn12file4L57-L57 -->

摘要不是实时数据库。代码再次修改后，“测试已通过”可能过期；恢复任务时，关键环境事实需要重新确认。

### 3.9 记忆维护的重点是有效性，而不仅是容量

讲义特别强调过期记忆会误导 Agent，应该像代码一样审查和清理。[L02，p.26](#ref-l02)

**工程推导：**稳定约定可以长期保存；临时状态应有更新时间与适用范围；单次成功经验要经过反例检查后再升级为长期规则。一次通过重启解决的问题，不能直接变成以后所有故障都先重启的规定。

本章与 Skills 的连接是：**记忆决定经验怎样延续，Skill 决定过程知识怎样在相关任务中重新进入工作上下文。**

<a id="ch04"></a>
## 4. Tools：调用正确、业务正确与任务正确

> 讲义主线：p.28。参考资料：R05 的队列案例与虚拟 Shell，R09 的独立验收。

### 4.1 六类基础工具，已经可以形成复杂工作链

讲义列出 Read、Search、Fetch、Edit／Write、Shell、Delegate。它们分别承担观察、定位信息、读取外部内容、修改状态、运行程序和委派子任务。[L02，p.28](#ref-l02)

使用者看到的是模型自己选择工具；开发者必须负责这些工具怎样描述、怎样限定作用范围，以及怎样表达结果。

### 4.2 三种正确性不能混在一起

**综合解释：**

| 层次 | 检查问题 | 错误例子 |
|---|---|---|
| 调用正确 | 工具存在，参数有效，调用可执行吗？ | 字段名或类型错误 |
| 业务正确 | 数据和动作符合真实语义吗？ | 把未知数量当成零 |
| 任务正确 | 最终状态实现了用户目标吗？ | 清空队列消除了积压，但丢掉了待处理消息 |

Schema 校验主要作用于第一层；领域知识与过程判断支撑第二层；外部验收支撑第三层。工具返回 `success`，不能自动证明三层都正确。

### 4.3 R05 的队列案例：接口接通之后，还缺什么

incident.io 的示例说明：事件通过负载均衡进入 Google Pub/Sub 或 NATS JetStream 中的一个 Broker，订阅积压可能分布在两侧；任一侧都不代表完整状态。`null` 数量表示无法获知，不是零。执行清理前，应观察最老未确认消息年龄是否下降，因为积压可能正在自然消退。[R05，Skills are just instructions](#ref-r05)
<!-- 原始文件证据：fileciteturn14file5L568-L590 -->

由此，合理操作首先应辨认对象、获取两侧观察、补充未知信息、检查趋势，再判断是否需要干预，而不是看到积压就调用清理。

这个案例补上了讲义中“工具让 Agent 能行动”之后的第二句话：**能行动，不等于懂得什么时候应该行动。**

### 4.4 工具结果应该保留未知、失败与部分成功

**教学示例：**

```json
{
  "status": "partial",
  "data": {"backlog_count": null},
  "warnings": ["管理接口未提供数量，需要查询监控指标"],
  "source": "queue-admin",
  "observed_at": "2026-01-01T00:00:00Z"
}
```

这里的时间仅作结构示例。重点是不要把“没有”“未知”“失败”“部分成功”折叠成相同返回。

对写工具，还应考虑怎样表达已经发生的副作用。请求超时不是“没有执行”的证据；是否安全重试需要由工具与业务系统的语义决定。这是工程推导，而不是队列文章已经给出的完整事务方案。

### 4.5 通用接口可以有受控实现

R05 描述了在 Go 应用里实现虚拟文件系统和 Shell 风格的解释层，所谓“二进制”实际对应 Go 函数。模型面对的是熟悉的交互模式，不一定是一个无限制的宿主机 Bash。[R05，Agents are a loop](#ref-r05)
<!-- 原始文件证据：fileciteturn14file5L445-L466 -->

可迁移的思想是：为模型提供易用接口，同时明确其真实能力边界。它不是伪造执行结果；工具返回必须对应真实的、定义清楚的操作语义。

## 5. Skills：把工具能力组织成专业工作方法

> 讲义主线：p.30—35。参考资料：R03 的组成与三层加载，R05 的业务实现，R02 的工作示例积累，R08 的配置实验。

### 5.1 四个扩展机制，先各归其位

| 机制 | 回答的问题 | 发布任务中的例子 |
|---|---|---|
| Skill | 应该怎样完成这项任务？ | 检查版本、准备变更与回滚方案 |
| MCP | 可以连接哪些外部数据和动作？ | 查询 Issue，创建 Release |
| Hook | 某个生命周期事件发生时自动做什么？ | 执行前检查，修改后格式化 |
| Plugin | 怎样把整套能力交付给别人？ | 打包 Skill、Hook 与 MCP 配置 |

这是讲义第 30—32 页的分类。分类是责任边界，不表示四者只能独立使用。[L02，p.30—32](#ref-l02)
<!-- 原始文件证据：fileciteturn14file0L537-L550 fileciteturn14file0L576-L586 -->

### 5.2 Skill 不只是长提示词，而是一组过程资产

R03 把 Skill 解释为包含指令、脚本与资源的目录，以可组合的方式注入专业知识，类似新员工的入职资料。R05 用 API 文档类比：只有接口参考，使用者仍要自己摸索；指南和教程解释了怎样组合接口完成工作。[R03，The anatomy of a skill](#ref-r03)；[R05，Skills are just instructions](#ref-r05)

```text
.claude/skills/queue-diagnosis/
├── SKILL.md
├── references/
│   ├── broker-semantics.md
│   └── common-failure-modes.md
└── scripts/
    └── summarize_queue_status.py
```

以上是教学结构。正文负责判断与导航；参考文件保存详细语义；脚本完成确定步骤。没有脚本的 Skill 仍然可以是 Skill；有脚本也不意味着脚本已经正确或安全。

### 5.3 Progressive disclosure：目录、流程、细节

R03 的 PDF 案例展示三层：先加载 `name` 和 `description`，相关时读取 `SKILL.md`，需要表单处理时再读取 `forms.md` 等支持文件。其预写 Python 脚本可以执行表单字段提取，而不必把脚本和整份 PDF 先装进模型上下文。[R03，The anatomy of a skill；Skills and code execution](#ref-r03)
<!-- 原始文件证据：fileciteturn14file3L1-L1 -->

```text
知道有哪些能力
      ↓
识别本次属于哪类工作
      ↓
加载这类工作的主要流程
      ↓
按当前分支读取细节或执行脚本
```

**综合解释：**分层加载不只是节省 Token，也是在分阶段缩小模型当前需要解决的问题。

### 5.4 按需加载的收益与边界

**假设例子：**50 个 Skills，每个描述 100 Token，正文 3,000 Token，一次只使用一个。全量加载为 155,000 Token；只加载描述与一个正文为 8,000 Token。这是说明机制的算例，不是实测收益。

**工程推导：**技能很多时，发现信息仍有成本；内容加载后是否保留、重复加载是否去重、升级后会话是否仍携带旧版正文，都由运行时管理。“按需加载”不自动等于“按需卸载”或“无限上下文”。

讲义区分用户显式调用与模型自行选择，并建议对有副作用的工作流通常要求显式调用。但显式选择某个 Skill，不等于给其全部潜在副作用发放无限授权。[L02，p.35](#ref-l02)

### 5.5 一个 Skill 的五类核心内容

以下是对 R03、R05 的工程整理：

| 内容 | 需要回答的问题 |
|---|---|
| 适用条件 | 哪些任务该用？哪些近似任务不该用？ |
| 业务语义 | 哪些概念、字段和关系不能靠常识猜？ |
| 决策条件 | 何时调查、等待、执行、升级或停止？ |
| 确定性操作 | 哪些步骤直接使用已测试脚本？ |
| 完成证据 | 怎样证明结果满足目标？ |

队列 Skill 中“双 Broker”“null 不是零”“先看积压趋势”是业务语义与决策依据，不是泛泛要求“认真排障”。

### 5.6 Skill 加载器为什么值得被显式记录

R05 说明，读取文件本身就可以加载 Skill。但 incident.io 使用专门工具按名称定位、记录已加载技能，并返回正文和小型目录索引，减少额外发现工作。[R05，Skills are just instructions](#ref-r05)
<!-- 原始文件证据：fileciteturn14file5L661-L684 -->

**工程推导：**这样可以分开诊断：没有发现、发现但没加载、加载但没读必要分支、流程理解错误、工具执行失败、技能本身错误。没有这些分层证据，团队容易把所有问题都归为“不遵循提示词”。

### 5.7 路由评测和执行评测必须分开

R03 建议从代表性任务中的真实缺口开始建设技能，并观察名称、描述与运行轨迹。[R03，Developing and evaluating skills](#ref-r03)

**工程方案：**路由测试覆盖应触发、不应触发与容易混淆的任务；执行测试则在已加载正确 Skill 的条件下，检查语义理解、工具动作和验收结果。改正文不能直接修复发现失败，改描述也不能修复错误口径。

### 5.8 确定步骤写成代码，选择与例外留给判断

R03 用排序与表单提取说明代码执行的价值，R04 则进一步将已验证的工具组合保存为可复用脚本。[R03，Skills and code execution](#ref-r03)；[R04，State persistence and skills](#ref-r04)

**综合解释：**判断应该采用哪一种方法，可以需要模型；已经确定的过滤、计算、排序、格式转换与字段校验，通常可以由代码完成。但“确定性执行”不代表“程序无错误”，依然需要输入校验、测试和版本管理。

### 5.9 Skill 的知识从哪里来

R02 的 *Hoard things you know how to do* 鼓励保存带可运行证据的工作示例。作者通过组合 PDF 页面渲染与浏览器 OCR 两段已有代码构建工具，强调已经跑通的例子可以成为新任务的输入。[R02c](#ref-r02c)
<!-- 延伸阅读证据：citeturn901974view2 -->

与 R03、R04 结合，可以形成如下资产积累路径：

```text
真实任务 → 工作示例和证据 → 可复用条件
        → 受测脚本 → 使用脚本的 Skill → 回归评测
```

这是工程综合，不表示一次成功轨迹应立即成为全局规范。经验需要先说明适用范围与失败边界。

## 6. 论文精读：Guardrails Beat Guidance

> 对应讲义：常驻指令、记忆和 Skills，尤其 p.21、p.26、p.33—35。重点不是“怎样写一句好提示”，而是“怎样验证持久化配置是否真的改变了任务表现”。

### 6.1 先明确研究对象：不是 Hook，也不是完整 Skill 运行时

R08 的标题包含 Rules、Skills 与 Persistent Configuration，但其实际操作是在运行前替换 `CLAUDE.md`，保持 Agent、模型、提示模板和工具不变，主要改变自然语言规则。[R08，§5，p.4](#ref-r08)

**因此，论文中的 Guardrails 主要指“不要做某事”的文字约束，而不是一个关于沙箱、Hook 或服务端授权的安全实验。**它也没有全面测试动态 Skill 检索、脚本执行与技能包发布。
<!-- 原始文件证据：fileciteturn14file8L245-L250 -->

### 6.2 语料规模、运行次数和任务数是不同概念

论文收集 679 份规则文件，清洗后得到 25,532 条规则，并按六类归类。其中项目专属规则约占 64.9%，但实际实验重点是其余五种可迁移类别，排除了项目专属规则。[R08，§3、§5，p.3—4](#ref-r08)

| 项目 | 论文描述 |
|---|---|
| Agent／模型 | Claude Code + Claude Opus 4.6 |
| 基准 | SWE-bench Verified 的 Python 修复任务 |
| 主要实验任务数 | 实验 1—3 使用 58 个有区分度任务 |
| 细粒度任务数 | 实验 4 使用 35 个任务 |
| 运行总量 | 包括 1,500 次筛选运行和多组实验，超过 5,000 次 |
| 主要变化 | 注入规则的来源、数量、类型、单条与组合 |

这些都是该论文的实验设定，不是当前模型能力排名。五千多次运行不等于五千多个独立任务。[R08，§5，p.4](#ref-r08)
<!-- 原始文件证据：fileciteturn14file8L236-L293 -->

### 6.3 PBRS 是产生假设的类比，不是对 Prompt 的理论证明

作者借用 potential-based reward shaping 的术语，讨论辅助信号是在帮助任务，还是把行动引向别处。由此提出三项可检验预期：与状态相关的规则可能更有帮助；持续偏置可能在规则增加时累积；不同引导可能近似相加。[R08，§4，p.4](#ref-r08)

论文明确承认，这是一种 **generative metaphor**，不是证明自然语言指令等价于某种强化学习奖励。本文不将它改写成“状态相关的 Prompt 一定保持最优策略”。[R08，§1—2、§4](#ref-r08)

### 6.4 实验一：规则来源——内容的优势没有直觉中清晰

第 11 页表 2 给出如下结果：

| 条件 | 通过率 | 帮助的任务 | 损害的任务 |
|---|---:|---:|---:|
| 无规则 | 50.0% | — | — |
| 随机规则 | 63.8% | 12 | 4 |
| 人工精选 | 63.8% | 14 | 6 |
| 热门规则 | 60.3% | 18 | 12 |
| 不匹配领域 | 58.6% | 15 | 10 |
| 匹配领域 | 56.9% | 11 | 7 |
| 打乱顺序 | 56.9% | 13 | 9 |
| 原生格式 | 56.9% | 15 | 11 |

“帮助／损害”表示相对于对应无规则运行的成功／失败翻转。这是同一批任务上的配对结果。[R08，附录 B，表 2，p.11](#ref-r08)
<!-- 原始文件证据：fileciteturn16file0L16-L31 -->

两个细节比标题更重要。第一，随机与精选的总体分数相同，但影响的任务组合不同。第二，单个条件与基线的 McNemar 检验没有达到常见的显著性阈值。作者对整体方向另做了符号检验，并提出 **context priming** 假设：结构化规则的存在本身，可能影响模型的工作方式。[R08，§6.1，p.5](#ref-r08)

不能由此推出“随机内容与专家知识已经被证明等价”。没有发现显著差异，不等于完成等效性证明；作者提出的机制解释，也不是直接观察到的模型内部因果过程。

### 6.5 实验二：规则数量——没有观察到预期的累积退化

作者比较 0、1、3、5、10、20、50 条规则，并进行不同采样条件的运行。通过率大体处于 59%—67% 区间；50 条为 66.7%，该实验的无规则基线为 60.3%。[R08，§6.2，图 3a，p.5—6](#ref-r08)

注意，**这里的 60.3% 与实验一的 50.0% 属于不同实验的运行口径，不能混为同一次基线，也不能直接解释成加规则前后的十个百分点变化。**论文在局限中讨论了基线与运行随机性。[R08，§7，p.9](#ref-r08)

结论是：在该实验范围内，作者没有观察到预测中的数量转折。它不证明无限增加规则没有成本，也不证明所有模型在所有长上下文上都不会退化。

### 6.6 实验三：规则类型——方向性结果，不是确定排名

第 11 页表 3 报告：工具／过程 63.8%，混合 62.1%，安全类 60.3%，代码风格 56.9%，架构类 53.4%。作者强调，这个排序仅提供方向性支持，没有达到充分的统计确认。[R08，§6.3；附录 C，表 3](#ref-r08)

直观解释是：与具体状态绑定的建议，例如遇到测试失败时调查根因，可能比始终要求使用某种抽象结构更贴近任务。但这是对实验的解释，不是所有架构指导都有害。

### 6.7 实验四 A：单条消融测的是组合中的边际作用

令 $R$ 为完整规则集，可以把消融效果写为：

$$
\Delta_i=Q(R)-Q(R\setminus\{r_i\})
$$

这是对论文附录定义的教学表达。正数表示移除该规则后表现更差，即它在当前组合中有益；负数表示移除后更好。它不等于“这条规则单独加入任意系统时的固定收益”。

| 规则简述 | 消融边际效果 | 表 4 中的 p 值 |
|---|---:|---:|
| 不进行无关重构 | +20.0 个百分点 | .016 |
| 不安装不必要的新依赖 | +8.6 个百分点 | .508 |
| 不修改无关文件 | +5.7 个百分点 | .688 |
| 保持兼容 | −8.6 个百分点 | .508 |
| 处理相关边界情况 | −11.4 个百分点 | .289 |
| 读取测试文件 | −14.3 个百分点 | .227 |
| 遵循已有代码风格 | −14.3 个百分点 | .180 |

来源为第 11 页表 4。作者按绝对变化超过 5 个百分点分类，得到 3 条 shaping、4 条 distorting、11 条 inert；这是一项分类阈值，不是显著性阈值。[R08，§6.4；附录 D，表 4](#ref-r08)
<!-- 原始文件证据：fileciteturn16file0L54-L76 -->

论文同时说明：最显著的单条比较也无法通过严格的多重比较校正，且正负极性模式对阈值有敏感性。[R08，§6.4，p.6](#ref-r08)

### 6.8 实验四 B／C：单条规则的表面伤害，不会简单相加

作者对 17 个基线曾可靠解决的任务测试单条规则，观察到一些任务翻转为失败；但基线重测本身也不是 100% 稳定，因此不能把每一次翻转都认定为该规则造成。[R08，§6.4，p.6](#ref-r08)

组合实验更有启发性。表 5 中一个例子是：

| 无规则 | 仅 A | 仅 B | A + B |
|---:|---:|---:|---:|
| 68.6% | 71.4% | 74.3% | 65.7% |

A、B 单独出现时点估计都有改善，合并后反而降低。另一组中，某条规则的负面变化被另一条补偿。论文在五组配对中观察到三组近似相加、两组明显非线性。[R08，附录 E，表 5，p.12](#ref-r08)
<!-- 原始文件证据：fileciteturn16file0L89-L99 -->

**工程推导：**不要只靠逐条挑选看似有益的指令构建最终配置。最终规则组合、模型、任务分布与工具环境仍然需要一起评测。

### 6.9 为什么不应把“读取测试文件有负向效果”解读为“不需要测试”

这里比较的是“是否额外添加一条文字指令”，不是“测试机制存在与否”。一个已有测试倾向的 Agent，可能不需要额外重复提醒；但没有测试与外部验收，仍然缺少可靠反馈。

因此，R01／R02 倡导测试与 R08 的某个消融结果，不能被当成直接互相否定。它们操纵的变量不同。[R01，Give Claude a way to verify its work](#ref-r01)；[R02d](#ref-r02d)；[R08，§5—6](#ref-r08)

### 6.10 与 R03、R05 的真正连接

| 想增加的内容 | 它主要改变什么 | 应怎样验证 |
|---|---|---|
| “null 表示未知，不是零” | 提供缺失的业务事实 | 语义判断是否正确 |
| “仔细思考，写优雅代码” | 改变一般行为倾向 | 是否改善真实任务，而不只是回答风格 |
| “必须获得授权才能发布” | 表达组织约束 | 除理解外，还需验证执行层不能绕过 |

R08 排除了大量项目专属规则，所以不能拿它否定内部业务知识的价值。R03、R05 也不能证明所有长技能说明都值得加载。

**综合结论：优先增加模型缺失的事实和判断条件；对通用行为要求做消融；不可妥协的限制落实到运行时。**

### 6.11 与“精简上下文”之间的边界

R08 没观察到 0—50 条规则之间的明显退化，不能说明额外 Token 没成本。R01 建议精简，也不意味着所有较长规则都必须删除。正确目标是减少无价值负担，保留完成工作确实需要的信息，而不是机械地越短越好。

## 7. MCP 与代码执行：分开连接、发现和执行组织

> 讲义主线：p.36—37、p.45—51。参考资料：R04 的代码执行机制、R05 的接口解释、R09 的对照实验。

### 7.1 MCP 连接能力，不替 Agent 决定业务动作

讲义中的 MCP 调用链是：模型识别动作，Client 发起调用，Server 处理请求，外部系统执行，结构化结果返回，模型继续判断。协议传递调用，Agent 决定是否提出调用。[L02，p.37](#ref-l02)

Host 是用户使用的应用；Client 在 Host 中与 Server 交互；Server 暴露外部系统能力。这三个组件不是三个分别思考的 Agent。[L02，p.45—46](#ref-l02)

MCP 的目标之一是减少不同客户端与服务之间重复的定制集成。它不自动包含公司的业务工作方法；R05 正是因此在接口之上增加队列 Skill。[L02，p.45](#ref-l02)；[R05，MCPs are just APIs in tools](#ref-r05)

### 7.2 Tools、Resources、Prompts 的分工

| 原语 | 提供什么 | 讲义例子 |
|---|---|---|
| Tools | 可调用的动作 | 创建 Issue、查询相关错误 |
| Resources | 可读取的数据 | Issue 内容、数据库 Schema |
| Prompts | 服务暴露的可复用提示模板 | 按组织流程分析 Issue |

一个 Prompt 返回说明，不会因为名为 Prompt 就自动执行外部操作。Resources 提供信息，也不等于授权修改。讲义第 47—48 页将三者放在同一个 Issue 分析任务中说明协作。[L02，p.47—48](#ref-l02)
<!-- 原始文件证据：fileciteturn16file3L559-L591 -->

### 7.3 “MCP 还是 CLI”混合了三个问题

**综合分类：**

| 维度 | 选择内容 |
|---|---|
| 连接方式 | MCP、普通 API、CLI 等 |
| 能力发现 | 全量暴露、搜索工具、读取帮助、读取接口文件 |
| 执行组织 | 每一步经模型决策，或用程序组合多步操作 |

MCP 可以按需发现；CLI 可以产生海量输出；代码执行内部仍可调用 MCP。R04 与 R09 合读的第一收益，就是不再把协议、目录加载和控制流当成一个变量。[R04](#ref-r04)；[R09，§4.3](#ref-r09)

### 7.4 R04 的例子：为什么不应让模型搬运整份会议记录

任务是从 Google Drive 读取会议记录，再附到 Salesforce。直接调用中，完整文本先作为工具结果进入上下文，之后又由模型生成到下一次写操作的参数里。[R04，Intermediate tool results consume additional tokens](#ref-r04)
<!-- 原始文件证据：fileciteturn14file4L12-L21 -->

```text
直接逐步调用：
服务 A → 完整文本进入模型 → 模型重新生成完整文本 → 服务 B

代码执行：
模型给出操作程序 → 程序从 A 获取对象 → 程序把对象交给 B
               → 模型只接收必要结果与异常
```

**教学伪代码，不对应某个可直接运行的 SDK：**

```python
transcript = source.read_document(document_id)
result = destination.attach_document(record_id, transcript)
return {
    "destination_id": result.id,
    "status": result.status,
    "warnings": result.warnings,
}
```

这个变化把不需要语义判断的数据传递，从自然语言生成通道移到程序数据通道。

### 7.5 三种节省来自不同位置

**按需加载定义。**模型先探索可用服务和工具，只读取相关接口文件；也可以通过工具搜索分层获得名称、描述或完整 Schema。

**在执行侧处理结果。**过滤、聚合和转换在程序中完成，不把所有原始数据反复交给模型。

**用程序组织控制流。**循环、条件分支和等待可以在执行环境完成，避免每一个简单判断都触发一次模型推理。

这三类是 R04 的核心工程机制。[R04，Progressive disclosure；Context efficient tool results；More powerful and context-efficient control flow](#ref-r04)
<!-- 原始文件证据：fileciteturn5file0L10-L10 fileciteturn5file7L80-L92 -->

### 7.6 150,000 到 2,000 Token 应怎样解释

R04 报告了一个将相关上下文开销从约 150,000 Token 降至 2,000 Token、减少约 98.7% 的示例。它用于展示工具按需加载与代码组织的优化空间，不能作为任意 MCP 系统端到端成本都降低 98.7% 的保证。[R04，Code execution with MCP improves context efficiency](#ref-r04)

R09 随后说明，即使都使用 MCP，具体目录提供方式也可以不同。因此，正确问题是“我们的请求实际带了什么、发生了多少轮”，不是“协议名称是什么”。

### 7.7 数据不进入模型，不等于系统已经安全

R04 讨论中间数据留在执行环境中，并用占位符等方式减少敏感信息进入上下文；同时指出代码执行需要沙箱、资源限制和监控。[R04，Privacy-preserving operations；Summary](#ref-r04)

**工程推导：**数据不进入模型只减少一类暴露路径。程序仍可能把数据发送到错误对象，或者在一次 `run_code` 内产生多次远程写入。授权和审计需要覆盖真正访问资源的接口，而不仅是外层代码执行工具。

### 7.8 程序化数据处理仍要保留决策所需证据

**工程推导：**对于批量数据，优先返回统计量、异常片段、代表性样本和原始数据定位。不能为了缩短输出而把支持判断的证据全部聚合掉。模型负责判断，不意味着它只需要一句“处理成功”。

这与 R02 的代码讲解模式相连：原始代码和日志由工具直接读取，解释由模型完成。精确证据与解释最好走不同的生产路径。[R02g](#ref-r02g)

### 7.9 MCP Gateway：统一治理，也集中信任

讲义选读把 Gateway 描述为 Host 与多个 MCP Server 之间的控制层，承担目录聚合、路由、身份代理、策略、审计、限流与扩展。适合多个用户、Agent、服务和凭证需要一致治理的场景。[L02，p.50—51](#ref-l02)

讲义同时提醒：凭证过宽、最终用户身份丢失、名称冲突、日志泄密和单点故障都是风险。Gateway 不是“接上以后自动安全”，而是需要被认真设计的新信任边界。[L02，p.51](#ref-l02)
<!-- 原始文件证据：fileciteturn16file3L616-L655 -->

**版本附记。**讲义第 52 页将无状态核心、路由请求头和扩展机制归于其所述的 2026-07-28 修订。本文仅保留这一快照的课程内容，不据此宣称所有在用 Server 都实现该版本。协议层的无状态设计，也不意味着 Agent 无须保存任务状态。[L02，p.52](#ref-l02)

## 8. 论文精读：The Scaffolding Matters More Than the Interface

> 对应讲义：Harness、上下文成本、MCP。主要作用是训练对系统实验的归因能力，而不是直接给产品排一个通用榜单。

### 8.1 研究问题与任务范围

R09 研究七种 Scaffolding、五种模型以及 MCP／CLI 访问方式。固定任务是：找到指定 Issue、创建分支、应用给定补丁、提交、创建 PR、报告某个目录中的文件数。[R09，§2.1—2.4](#ref-r09)

**补丁已经给定。**所以它不是让 Agent 从零解决复杂软件问题，也不能直接推广为长期软件开发能力排名。

验收独立检查四项持久状态，且每次重置仓库。这个设计首先解决了“模型说完成”与“确实完成”的区别。[R09，§2.2](#ref-r09)

### 8.2 实验隔离：配置了某接口，不代表实际使用它

CLI 组没有 MCP Server；MCP 组由 Server 持有凭证，同时清除 Shell 路径的相应凭证，尽量阻止 Agent 通过另一条可用路径完成远程操作。[R09，§2.4](#ref-r09)

为什么需要这么做？前置的公开仓库实验中，部分 Agent 只走 Shell，部分混用接口，也有直接访问 Web API 的行为。增加提示并没有可靠消除这些现象。[R09，§7](#ref-r09)

**方法论：测量实际调用，而不是仅记录给它开放了什么。**

### 8.3 计量口径：输入、缓存、工具调用和子 Agent 都要算

论文通过统一代理记录请求，包括输入 Token、缓存量、工具调用和每次请求的 Schema 数。这样可以避免子 Agent 的消耗被遗漏。[R09，§2.5](#ref-r09)

美元数是依据统一价格表计算的建模成本，不是实际账单；本地模型也用假设价格估算。不同 Scaffolding 没有完整覆盖全部模型，横向行统计存在模型组合差异。[R09，§2.5，p.6](#ref-r09)
<!-- 原始文件证据：fileciteturn14file9L234-L270 -->

因此，不能把论文表格中的单个美元数直接当作自己的生产成本。

### 8.4 固定接口下，Scaffolding 的差异仍然存在

论文只比较没有连接 MCP 的 CLI 运行时，第 12 页表 2 报告的中位输入 Token 如下：

| Scaffolding | CLI 完成运行的中位输入 Token |
|---|---:|
| pi | 14,660 |
| Tau | 16,459 |
| Codex | 82,378 |
| Hermes | 83,954 |
| opencode | 137,800 |
| qwen-code | 297,649 |
| Claude Code | 410,797 |

这些是各行成功样本的描述统计，不能忽略模型组合和样本数量不同。它们支持“外围软件的选择可能很重要”，但不能把所有差异归因于是否支持 MCP，也不能当成当前版本产品性能结论。[R09，§3.2，表 2，p.12](#ref-r09)
<!-- 原始文件证据：fileciteturn14file9L548-L577 -->

论文还给出一个小模型在不同配置下完成同一任务时，输入消耗相差约 139 倍的极端例子。它说明单一任务上同一模型的实际开销可被外围软件显著改变，不说明模型能力在所有场景都不再重要。[R09，§3、§6](#ref-r09)

### 8.5 同一 Scaffolding 内，MCP 并没有一个稳定成本倍数

第 13 页图 3 与表 3 的组间中位比值方向不同：有的 MCP 组更高，有的更低。严格限制到同一模型、同一 Scaffolding、两侧都完成的 13 对观察后，比值范围为 0.43—29.06，中位数 0.93。作者报告该比较不能支持稳定方向的结论。[R09，§4.1，p.13](#ref-r09)
<!-- 原始文件证据：fileciteturn16file1L139-L161 -->

**不能推出：**MCP 天生昂贵、CLI 一定更优，或两者已被证明等价。这里是数据分散、样本有限、运行波动下的归因限制。

### 8.6 按需工具目录：有合理机制，但观察仍有混杂

第 14 页图 4 与第 15 页表 5 报告：按需目录组的中位输入约 70,836，全量目录组约 216,986。两组都连接相同 Server、暴露相同操作。[R09，§4.3](#ref-r09)

但只有一个 Scaffolding 采用按需方式，因而目录提供方式与该系统的其他差异混在一起。作者明确说，这是一种值得继续检验的机制，不能把约 3.1 倍差异全部因果归于按需加载。[R09，§4.3，p.15](#ref-r09)
<!-- 原始文件证据：fileciteturn16file1L218-L254 -->

这正是它与 R04 的关系：R04 提供可行的优化机制，R09 限定单个比较能够证明到哪里。

### 8.7 失败支出占比不是失败率

第 16 页表 6：

| 组别 | 运行数 | 失败数 | 失败运行消耗的 Token 占比 | 失败运行的建模支出占比 |
|---|---:|---:|---:|---:|
| CLI | 19 | 3 | 7.3% | 2.2% |
| MCP | 19 | 3 | 9.8% | 12.9% |

两组都失败三次。12.9% 与 2.2% 反映这些失败落在哪些成本更高的配置上，不是失败概率。[R09，§4.4，p.16](#ref-r09)
<!-- 原始文件证据：fileciteturn16file1L266-L288 -->

作者的重复实验也报告两种接口各完成 25／29 次。论文后面还有按模型规模分组的分析，属于另一种范围的观察，不能替换全组口径。[R09，§8.1](#ref-r09)

### 8.8 环境错误不能偷偷算成被比较机制的缺陷

论文发现过验收条件不可满足的问题，也发现某配置把凭证变量名当作真实凭证传入，导致所有 API 调用被拒绝。修正环境后重新运行，结果明显变化。[R09，§2.6](#ref-r09)

这带来两种不同的评测目的：**研究某项机制时，应将实验装置错误与机制本身分开；衡量生产系统可靠性时，配置与凭证故障仍然属于用户真实体验的一部分。**后半句是工程分析，不是把论文的研究口径直接照搬到生产报表。

### 8.9 重复运行的波动与外推限制

论文重复本地模型配置时，完成运行的 Token 最大／最小比值在不同配置间的典型量级约 1.51，最宽约 5.41。作者据此认为，许多小于约两倍的差异在其数据中不足以稳定分辨。[R09，§8.1，p.20](#ref-r09)

这不是通用的“差两倍才显著”统计法则。论文的限制还包括单任务、托管模型主要单次运行、模型覆盖不均、目录方式仅有一个按需实现，以及只观察成功样本成本时的选择影响。[R09，§8](#ref-r09)

### 8.10 对实际工程最有价值的结论

**综合解释：**开放探索可以需要通用 Harness 的广度；边界清晰、重复发生的任务，可以逐渐沉淀成更贴合任务的流程、脚本和工具集合。R09 的讨论支持检验这一方向，但不保证所有任务都从极简系统受益。[R09，§9.2](#ref-r09)

“精简”应删掉任务用不到的常驻负担，而不是删掉授权、验证、恢复与观察。

## 9. Hooks 与权限：把建议和执行边界分开

> 讲义主线：p.11、p.38、p.49—51。参考资料：R06 的真实故障语义，R05 的工具前置条件，R09 的接口绕行观察。

### 9.1 让模型少提危险动作，与不让危险动作执行，是两种控制

**教学分解：**对一个需要模型提出的危险动作，可将其落地事件理解为“模型提出”与“执行层放行”共同成立。Prompt 和 Skill 主要影响前者；授权、工具前置条件和资源侧策略影响后者。

这不是量化风险保证，只是解释分工：**建议改变被选择的倾向，执行约束限制实际可发生的行为。**

讲义第 11 页把权限层放在意图与执行之间，正是在强调这个边界。[L02，p.11](#ref-l02)

### 9.2 Hook 的触发是程序化的，检查内容不一定确定

Skill 需要被加载并由模型使用；Hook 则在运行时的匹配事件发生时触发。讲义列出会话开始、用户输入、工具调用前、调用后和停止前，同时标明模型内部推理不是一个 Hook 事件。[L02，p.38](#ref-l02)
<!-- 原始文件证据：fileciteturn14file0L698-L717 -->

如果 Hook 执行纯代码条件检查，其判断可以有确定语义；如果它调用模型或子 Agent 做判断，触发虽然自动，结论仍可能有不确定性。不能把“Hook 自动执行”替换成“Hook 一定正确”。

### 9.3 位置决定能力

| 事件位置 | 可以承担的工作 | 不能误以为已经保证的事情 |
|---|---|---|
| 调用前 | 校验目标、参数、前置条件，拒绝动作 | 覆盖未经过该事件的替代访问路径 |
| 调用后 | 记录实际结果、格式化、反馈问题 | 撤销已经发生的远程副作用 |
| 停止前 | 检查验收是否充分，要求继续工作 | 保证任务最终成功或永不结束 |
| 会话开始 | 加载必要信息、初始化记录 | 自动恢复全部外部系统状态 |

R06 的 `PostToolUse` 说明特别重要：其阻止／反馈字段用于向后续模型提供反馈，不能把已经完成的操作变成没有执行。[R06，PostToolUse decision control](#ref-r06)
<!-- 原始文件证据：fileciteturn13file4L30-L33 -->

### 9.4 退出码和故障语义，必须看具体协议

按上传的 R06 快照，不能仅凭普通程序的 `exit 1` 就认为动作被拒绝。对于相应可阻止事件，需要使用该事件规定的阻止方式；有效 JSON、退出码和事件类型共同决定处理结果。文档对 `exit 2`、输出格式、超时与非阻塞错误分别作出说明。[R06，Hook input and output；Exit code output](#ref-r06)

快照还介绍适用命令／HTTP Hook 的 `onFailure: "block"`，并注明版本要求。没有按预期启动、超时或返回无效结果的检查器，可能无法承担原以为的阻止职责。[R06，Block the action when a hook fails](#ref-r06)
<!-- 原始文件证据：fileciteturn7file7L122-L122 fileciteturn15file8L370-L382 -->

本文保留的是快照中的实现细节，不提供脱离部署版本的通用配置承诺。

### 9.5 两类 Hook 测试缺一不可

**工程建议：**

| 测试类别 | 要测试的内容 |
|---|---|
| 业务逻辑 | 应允许是否允许，应阻止是否阻止，错误信息是否可处理 |
| 故障语义 | 脚本不存在、依赖缺失、超时、输出损坏、服务不可达时怎样处理 |

此外，异步检查不应被当作已经完成的行动前审批。若动作执行后检查才返回，得到的是事后检测，不是事前阻止。

### 9.6 Stop Hook 不是无限成功循环

R06 提到 `stop_hook_active` 等状态和续跑限制，目的是避免不断阻止一个无法满足的结束条件。模型被中断、API 失败、环境不能恢复等情况，也不等于正常停止事件的同一种处理。[R06，Stop；Stop input](#ref-r06)
<!-- 原始文件证据：fileciteturn15file4L231-L231 -->

**工程推导：**停止检查应区分可继续修复、需要人工、环境阻塞与预算耗尽。不能把外部服务宕机变成“再想一遍直到成功”。外部验收状态必须独立于一次对话是否被结束。

### 9.7 布尔确认字段不等于可信的人类审批

R05 的队列接口要求预览或明确确认，缺少两者的调用被拒绝。作者强调不可谈判的限制应位于工具层。[R05，队列 Skill；Skills replace system prompts](#ref-r05)

**工程分析：**仅有 `confirm: true`，只能证明调用者给出了这个字段，不能证明真实用户批准过该动作。重要审批应由可信系统产生并核验，绑定用户、对象、动作参数和适用时限；不能由模型同时生成操作与批准凭据。

### 9.8 一条路径的 Hook，不等于资源被全面保护

R09 的绕行观察说明：Agent 可能通过 Shell、API 或其他通道访问同一个外部服务。[R09，§7](#ref-r09)

因此，重要限制应尽可能落实到实际资源边界，例如最小权限凭证、服务端授权、网络策略和受保护的发布入口。讲义第 49 页也明确要求读写分离、最小权限、写操作审批，以及不把工具输出当成可信指令。[L02，p.49](#ref-l02)
<!-- 原始文件证据：fileciteturn16file3L597-L613 -->

**综合认识：**Skill 描述正确工作方法，Hook 把检查接到生命周期，权限和资源侧策略界定实际能力。三者协作，但不互相替代。

## 10. Agent Use 的日常方法：规格、测试、证据、纠偏与交付

> 主要串联 R01 的使用工作流、R02 的工程模式、R07 的角色分工和 R09 的验收原则。这一章回答工程师每天具体应该怎样组织一次任务。

### 10.1 从“帮我做”转为“目标、范围、证据、权限”

R01 强调给 Agent 一个能运行的检查，而不是让“看起来完成”成为唯一信号。它推荐先探索，再计划与实施，并用证据展示结果。[R01，Give Claude a way to verify its work；Explore first, then plan, then code](#ref-r01)
<!-- 原始文件证据：fileciteturn13file0L5-L8 fileciteturn1file8L261-L261 -->

**工程化任务契约：**

| 内容 | 需要说清楚什么 |
|---|---|
| 目标 | 最终希望系统产生什么可观察行为 |
| 现象或输入 | 已知错误、相关文件、示例数据 |
| 范围 | 优先修改什么，明确不做什么 |
| 验收 | 使用什么命令、样例或实际入口检查 |
| 授权 | 哪些本地动作可以自行执行，哪些外部副作用需确认 |
| 交付 | 输出代码差异、证据、剩余风险和未验证项 |

这些字段不是为了把任务写长，而是避免 Agent 在实现之前先替你猜测业务需求。

### 10.2 复杂任务先形成可独立理解的规格

R01 建议让 Agent 先追问实现、界面、边界情况和权衡，再形成 `SPEC.md`。规范应该能独立理解，包含涉及文件与接口、范围外事项和端到端验证；随后可以用干净会话执行。[R01，Let Claude interview you](#ref-r01)
<!-- 原始文件证据：fileciteturn12file5L67-L74 -->

**综合解释：**这一步既是在澄清需求，也是在把讨论历史压缩成实施契约。例如“增加导出”可能隐藏数据范围、权限、数据量、失败行为与异步执行方式。没有澄清时，生成代码其实是在同时生成需求。

### 10.3 什么时候需要计划，什么时候不需要复杂计划

**工程判断：**未知信息多、跨模块影响大、存在不可逆副作用时，计划更有价值；问题局部、修改范围清楚、验证迅速时，可以直接小步修改并测试。计划的产物应是必要步骤、依赖与验收，而不是一份脱离代码的长报告。

R07 的 DAG 规划适合表达某些任务依赖，但它是作者的工作流，不是每个简单修复都必须使用的流程。[R07](#ref-r07)

### 10.4 把三个测试模式连成一个闭环

**先运行已有测试。**R02 的 *First run the tests* 用实际运行让 Agent 找到测试入口、理解当前基线，也让测试成为后续工作的一部分。[R02e](#ref-r02e)
<!-- 延伸阅读证据：citeturn209059view0 -->

**先红后绿。**R02 的 *Red/green TDD* 强调先看到针对目标行为的失败，再修改实现，最后确认通过，避免新增一个原本就通过、根本未检测到问题的测试。[R02d](#ref-r02d)
<!-- 延伸阅读证据：citeturn901974view3 -->

**实际运行入口。**R02 的 *Agentic manual testing* 指出，测试通过仍可能漏掉服务启动、接口行为和界面问题。Agent 可以实际调用程序、启动开发服务或操作浏览器；发现的新问题再加入回归测试。[R02f](#ref-r02f)
<!-- 延伸阅读证据：citeturn209059view1 -->

```text
环境基线 → 目标问题复现 → 回归测试因目标问题失败
        → 最小必要修改 → 相关测试通过 → 实际入口验证
```

**工程检查：**导入失败不是业务复现；没有运行不是通过；测试跳过不等于覆盖；代码修改后的验收需要对应新的代码快照。

### 10.5 让精确证据由工具生成，让模型解释证据

R02 的 *Linear walkthroughs* 用工具直接抽取源码片段，再由模型组织解释，避免手工重新生成代码片段造成错误。其示例还记录执行命令与输出，使文档能反映实际观察。[R02g](#ref-r02g)
<!-- 延伸阅读证据：citeturn209059view2 -->

与 R04 的会议记录例子合读，可以得到一条很实用的分工：**需要原样保留的内容由工具读取和传递；需要理解与表达的部分交给模型。**代码、原文引用、查询结果和日志都适用这个思路，但解释仍需接受核查。

### 10.6 独立审查不等于强制挑错

R01 建议在新上下文中审查代码差异与验收条件，而不是让实施者继续沿用原先的解释。它也提醒，要求 Reviewer 一定找问题，可能诱发无关发现与过度工程。[R01，Add an adversarial review step](#ref-r01)
<!-- 原始文件证据：fileciteturn12file1L20-L20 -->

**工程建议：**审查应允许“未发现阻塞性问题”，重点检查需求遗漏、错误行为、真实风险和无关修改，不强制数量，也不把个人风格偏好自动升级为缺陷。

### 10.7 及时纠偏，而不是在失败轨迹上无限追加说明

R01 提供中断、回退、清理上下文与恢复会话的使用方式。它的重点是短反馈循环和避免无关历史持续堆积。[R01，Manage your session](#ref-r01)

**快照中的常用入口：**`/clear` 用于清理当前上下文，`/compact` 用于压缩，`/rewind` 用于打开回退选择；讲义另列 `/memory`、`/context`、`/init`、`/doctor` 帮助检查记忆与项目指令。具体能力以部署版本为准。[R01](#ref-r01)；[L02，p.25](#ref-l02)

注意，R01 明确限制检查点的覆盖范围：特定文件编辑工具之外的 Bash 或外部进程改动不一定被捕获，检查点不是 Git 的替代品。[R01，Rewind with checkpoints](#ref-r01)
<!-- 原始文件证据：fileciteturn13file1L13-L14 -->

### 10.8 交付代码，不是交付待审查的生成量

R02 的 *Writing code is cheap now* 区分“代码生成更便宜”与“可信软件交付仍有成本”：正确问题、验证、异常处理、可维护性和适度文档依然重要。[R02b](#ref-r02b)
<!-- 延伸阅读证据：citeturn901974view1 -->

其反模式章节提醒，不要把自己没有检查的大量生成代码转交同事，让审查者承担实际验证；变更应可审查，说明也应经过确认，并附验证证据。[R02i](#ref-r02i)
<!-- 延伸阅读证据：citeturn209059view4 -->

**综合解释：**Agent 提高产出速度后，工程师的责任更集中在范围控制、证据和可信交付，而不是行数。

### 10.9 无人值守不应等同于取消权限

R01 讨论非交互运行、结构化输出和批量任务，也建议先在少量样本上调整流程，再扩大范围，并限制任务需要的工具。[R01，Automate and scale](#ref-r01)
<!-- 原始文件证据：fileciteturn12file6L86-L86 -->

**工程推导：**无人值守场景要提前定义不满足授权条件时的行为，例如拒绝并记录、暂停等待或返回明确阻塞状态，而不是为了避免弹窗给出无限权限。

## 11. Subagents、Plugins 与 Harness：隔离什么，复用什么

> 讲义主线：p.28、p.39—41。参考资料：R05 的单 Agent 多 Skills，R07 的工作角色，R02 的子 Agent，R01 的审查。

### 11.1 R05 为什么把多个专业 Agent 合并

R05 描述了把调度、遥测等专业 Agent 的知识转成 Skills，由一个 Agent 按需加载。作者强调减少上下文割裂，并避免把可调整的操作建议全部放进过于刚性的系统提示。[R05，Skills replace system prompts](#ref-r05)

一个例子是长时间范围遥测查询。原来要求拆分查询的系统级建议，在用户知道整段查询可安全执行时仍可能僵硬地阻止它；迁移到 Skill 后，作者的实现更容易结合用户当前任务权衡这类建议。[R05，同上](#ref-r05)
<!-- 原始文件证据：fileciteturn16file2L352-L366 fileciteturn16file2L428-L465 -->

这是一项实现经验，不是“所有 Skill 在所有产品中都低于用户要求”的协议保证。不可协商的限制仍应由执行层落实。

### 11.2 R07 为什么又把工作分成多个角色

R07 的工作流为：

```text
Explore → Planner → Worker → Critic → Promoter
```

探索形成依赖计划，执行者逐项完成，审查者检查与简化，必要时退回执行，最后处理交付沟通。作者还借鉴 prewalk，将较强模型用于计划与首个任务，模式建立后交接后续工作。[R07，The cost advantage](#ref-r07)
<!-- 原始文件证据：fileciteturn14file7L62-L66 -->

作者报告过较强模型使用量下降，但没有提供可作为普适选型依据的控制实验。可借鉴的是分工方法，而不是把个人收益比例当成保证。

### 11.3 两者不应按 Agent 数量机械比较

R05 在问“业务知识是否需要分散在多个上下文”。R07 在问“不同工作目标怎样安排”。这不是完全相同的轴。

**工程判断：**

| 主要需要 | 优先考虑 |
|---|---|
| 不同领域知识，但共享完整任务语境 | 单 Agent 按需加载 Skills |
| 大量独立探索会污染主上下文 | 独立上下文的子任务 |
| 多项互不依赖的工作 | 在明确资源边界下并行 |
| 对结果重新判断 | 新上下文的 Reviewer |
| 不同文件写入权或资源权限 | 真正的工作区与授权隔离 |
| 流程已经完全确定 | 普通代码，不必增加 Agent |

### 11.4 Subagent 的核心价值之一，是保护主上下文

R02 的 Subagents 章节用探索仓库和返回摘要解释子 Agent，强调把 Token 密集型工作放到独立上下文，再将必要结果交回。作者同时提醒不要过度拆分出大量专业角色。[R02h](#ref-r02h)
<!-- 延伸阅读证据：citeturn209059view3 -->

**工程补充：**独立上下文不自动意味着独立文件系统、网络凭证或数据库状态。上下文隔离、执行环境隔离和权限隔离必须分别设计。并行任务也应明确文件归属、共享资源和结果合并方式。

### 11.5 Plugin 让工作方法成为可安装资产

讲义将 Plugin 定义为包含 Skills、Hooks、Agents、MCP 配置等的安装单元，提供版本、命名空间和团队复用。[L02，p.39](#ref-l02)

R05 的 data brain 案例具体说明了它的价值：数据模型文档与使用方法以 Skills／参考资料组织，内部 MCP 提供查询能力；加载 Plugin 与连接后，这组能力被用于其他 Agent 入口。[R05，Plugins bundle skills](#ref-r05)
<!-- 原始文件证据：fileciteturn16file2L323-L345 -->

**工程推导：**Plugin 应像软件发布管理版本、依赖、测试和回滚。它可能同时改变指令、外部访问和可执行代码，不能因为包含 Markdown 就把它当成没有副作用的说明文件。

### 11.6 R07 的深层价值：拥有可迁移的工作资产

R07 描述多个交互入口共享指令、Skills、脚本和工作目录。产品能力还通过可脚本化入口接入 Harness，重复工作不必每次重新生成实现。[R07，A product harness connection；Breaking down the harness](#ref-r07)
<!-- 原始文件证据：fileciteturn14file7L58-L79 -->

与 R02 收藏可运行示例、R03 封装 Skills、R04 保存脚本联系起来，资产积累可以理解为：

```text
一次会话的成果
  ↓
带证据的工作示例
  ↓
脚本、参考知识、任务 Skill
  ↓
可安装的能力包
  ↓
不同 Agent 入口上的回归验证
```

格式可以迁移，不代表行为自动等价。模型、工具契约、路径、依赖和权限不同，仍然需要验证。

## 12. 生产工程与评测：怎样知道系统真的改进了

> 本章主要是把前文工程推导集中整理，不声称以下状态机或目录是 Claude Code 的内部源码实现。来源基础是 L02 的执行循环、R01／R03 的验证要求、R08／R09 的实验方法。

### 12.1 除了消息历史，还要有任务状态

聊天历史告诉系统“曾经说过什么”，但不一定能直接回答“现在有哪些副作用已经发生，哪些验收仍然有效”。

**建议的逻辑状态：**

```text
已接收 → 探索 → 计划 → 执行 → 验证 → 已验证完成
                      ↘ 等待审批
                      ↘ 环境阻塞
                      ↘ 部分完成
                      ↘ 验证失败
                      ↘ 预算耗尽
```

状态可以采用很简单的存储方式。重要的不是使用复杂框架，而是能够明确区分成功、停滞与需要干预。

### 12.2 一个有边界的运行循环应表达什么

**教学伪代码，不是可直接部署的 Agent 实现：**

```text
while task.has_budget:
    context = build_context(goal, task_state, memory, observations)
    proposal = model(context, visible_tools)

    if proposal requests action:
        validate tool name and arguments
        inspect authorization and preconditions

        if needs human approval:
            persist WAITING_APPROVAL
            return
        if denied:
            append an explicit denial observation
            continue

        execute within the configured environment
        persist actual outcome and known side effects
        append a bounded, semantically clear observation
        continue

    verdict = verify(task_goal, current_artifacts, actual_environment)
    if verdict is verified_success:
        persist VERIFIED_COMPLETE with evidence references
        return
    if verdict needs external intervention:
        persist BLOCKED or PARTIAL
        return

    append concrete verification gaps

persist BUDGET_EXHAUSTED without claiming success
```

这个循环补充的不是“更多智能”，而是不会被模型一句“完成了”代替的状态与验收规则。

### 12.3 验证证据应绑定当前产物

**工程建议：**测试记录关联代码快照与工作区差异；文档证据关联材料版本；事实核验关联数据来源、观察时间和口径。修改产物后，先前证据应重新判断是否仍适用。

一个无版本的 `tests_passed=true` 很容易被误用。恢复运行时也不能仅凭摘要认定外部状态没有变化。

### 12.4 最小可观测性要服务于归因

| 信息 | 为什么要记录 |
|---|---|
| 任务、输入与产物版本 | 能复现当时到底处理了什么 |
| 模型、指令、Skill 和工具版本 | 区分升级引发的变化 |
| Skill 发现与加载 | 区分路由失败和正文失败 |
| 实际工具调用及权限结果 | 检查绕行与错误动作 |
| 工具耗时、失败类型与重试 | 区分模型问题和环境问题 |
| 上下文、输入输出和缓存量 | 解释成本与轮次增长 |
| 子 Agent 的消耗与结果 | 避免将成本隐藏在委派中 |
| 最终验收与未完成项 | 防止自我报告取代真实状态 |

R09 使用统一计量路径纳入子 Agent 请求，说明了最后几项为何不能只在主会话上统计。[R09，§2.5](#ref-r09)

日志本身也可能包含敏感数据。记录足够的定位与摘要，不意味着无条件保存全部正文、凭证和原始返回。

### 12.5 从基线开始做递进实验

R03 建议先观察能力缺口，再增加 Skills。R08 提醒组合效应与波动；R09 提醒控制变量和实际调用验证。[R03，Developing and evaluating skills](#ref-r03)；[R08，§5—7](#ref-r08)；[R09，§2、§8](#ref-r09)

**建议的实验阶梯：**

| 配置 | 新增机制 | 主要验证问题 |
|---|---|---|
| A | 模型、必要工具、最小指令 | 原始失败发生在哪里 |
| B | 项目事实和任务边界 | 是否减少误解与无关修改 |
| C | 按需 Skill | 是否选对技能并正确完成专业流程 |
| D | 受测脚本 | 是否减少确定性错误和无效轮次 |
| E | 执行检查与独立验收 | 是否减少违规动作、虚假完成和漏检 |

该阶梯不是唯一实验设计，也不是所有机制只能逐项叠加。关键是固定任务输入、环境、模型与验收口径，重复运行，并记录新增机制的收益与代价。

### 12.6 不要只看总分

R08 中随机规则与精选规则总分相同，但帮助和损害的任务组合不同。[R08，表 2](#ref-r08)

**工程推导：**评测至少分层看任务类型、错误严重程度、事实缺失场景、权限请求和工具故障。一个修改可能提升多数简单任务，却破坏少数高风险任务；总平均会掩盖这种变化。

### 12.7 成本与质量一起看，但保留原始口径

R09 把完成运行成本和失败消耗分开报告。[R09，§2.8、§4.4](#ref-r09)

**建议增加的业务指标，非论文原定义：**

$$
\text{单位已验收任务成本}
=\frac{\text{全部运行的总成本，包括失败与重试}}{\text{通过验收的任务数}}
$$

分母为零时报告“没有成功任务／该指标不可计算”，不要伪造一个有限均值。还应同时报告成功率、延迟分布和严重错误，不能用一个比值替代全部质量评价。

### 12.8 失败诊断矩阵

| 现象 | 优先调查 | 不应立即采用的反应 |
|---|---|---|
| 总在错误文件上猜测 | 搜索、索引、上下文是否缺失 | 只要求多思考 |
| 找到数据但误解含义 | 工具语义、Skill 的领域知识 | 只增加返回长度 |
| 正确工具频繁失败 | 环境、依赖、授权与参数契约 | 一律归因模型不行 |
| 重复相同行动 | 历史状态、进展判断、重试策略 | 无限续跑 |
| 说完成但产物不对 | 外部验收和证据绑定 | 强化“必须成功”的措辞 |
| 做了不该做的变更 | 权限与替代路径 | 只补一句禁止 |
| Skill 看似无效 | 是否发现、加载、走对分支 | 立刻重写全部正文 |
| Reviewer 总要求更多修改 | 审查目标是否强制挑错 | 逐条照单全收 |

这是前面多份材料形成的工程排障地图，而不是某篇论文的正式失败分类。

### 12.9 恢复设计要围绕副作用，而不是只围绕消息

R01 的检查点限制意味着回退对话与回退环境不同。[R01，Rewind with checkpoints](#ref-r01)

**工程推导：**本地文件可以用版本控制或快照处理；远程写入应重新查询结果；是否能补偿、是否可重试，需要各工具契约明确。不能把“恢复了对话”“恢复了代码”“撤销了全部外部动作”视为同一件事。

### 12.10 让经验晋级为资产，而不是让技能库无限增长

```text
一次反馈 → 候选经验 → 检查适用条件与反例
       → 回归评测 → 更新案例、Skill 或脚本
       → 版本化发布 → 继续观察
```

这是综合 R02、R03、R04 与 R08 得出的工程闭环。一次成功不应直接成为全局规则，一次失败也不应立即否定一个机制；如果没有新增价值，应删除或不晋级。

## 13. 应用推演：投研与基金营销材料预审核 Agent

> 本章是把前文方法迁移到你的工作方向的设计推演。它不是上述论文在金融任务上的实验结论，不提供具体法规解释，也不声称某项架构已经达到金融生产所需的准确率。

### 13.1 从真实工作目标开始

假设任务是：上传材料后识别需要修改的内容，给出依据、原文位置和可执行建议，最后由人采纳或拒绝。

“输出一份专业报告”不足以成为验收目标。我会把成功分为三层：

| 层次 | 验收关注 |
|---|---|
| 内容 | 建议针对什么陈述，哪些内容仍无法判断 |
| 证据 | 原文、位置、规则、事实核验是否可以对应起来 |
| 工作流 | 人工决定是否被正确保存，是否避免越权自动发布 |

这是将 R01 的可验证目标和 R09 的真实状态验收迁移到业务场景。

### 13.2 规则库、案例库与 Skill，不是同一个东西

**规则库**保存规范正文、适用条件、例外和版本。

**案例库**保存历史材料、建议、人工决定及其情境。

**Skill**保存如何识别场景、检索候选规则、检查例外、组织核验和生成建议的过程。

**工具**提供文档读取、位置定位、事实查询、计算和结果保存。

**运行时策略**决定可以修改什么、何时需要批准以及能否对外发布。

把每一条规则都变成一个 Agent 或 Skill，未必会增加判断能力，反而可能引入大量路由与维护负担。这里的划分是责任划分，具体数量应由任务评测决定。

### 13.3 信息分配与加载

| 信息 | 建议位置 |
|---|---|
| 不编造依据、证据不足要标注等共通要求 | 简洁的项目指令，同时配合检查 |
| 场景识别与规则适用判断流程 | 核心审核 Skill |
| 数值核验流程与口径说明 | 专门的事实核验 Skill |
| 具体规则正文和历史案例 | 可检索知识与数据系统 |
| 文档页码、坐标、原始片段 | 文档证据层 |
| 当前审核进度、缺失数据、待处理建议 | 当前任务状态 |
| 采纳／拒绝与备注 | 人工决策记录 |

这个设计沿用 R05 的思想：接口返回一个数字，不等于模型自然理解它的业务语义。来源、期间、类别、时间和口径必须能明确表达。

### 13.4 建议的处理链

```text
读取结构化文档及位置索引
  ↓
识别待核查陈述
  ↓
检索候选规则与相似案例
  ↓
判断适用性、例外与证据缺口
  ↓
必要时调用事实核验工具或确定性计算
  ↓
保留原始片段、位置、来源与计算记录
  ↓
生成可执行修改建议
  ↓
独立检查证据完整性与输出结构
  ↓
人工采纳／拒绝
  ↓
保存本次结果与反馈，不自动把反馈升级为全局规则
```

识别、适用性和措辞建议需要判断；原文传递、数字计算和结构校验尽量由可测试程序完成。这是 R04 与 R02 证据生成原则的应用。

### 13.5 最重要的状态区分：未知不是正确

```text
没有发现问题
    ≠ 没有检索到适用规则
    ≠ 证据不足
    ≠ 文档解析失败
    ≠ 事实工具不可用
    ≠ 已经核验无误
```

这是从 R05 的 `null ≠ 0` 迁移出的原则。系统必须能表达“未核验”“部分核验”“无法判断”，而不是把工具失败和检索缺失默认为没有风险。

### 13.6 一个建议记录的教学结构

```json
{
  "finding_id": "example-finding-001",
  "document_version": "example-v1",
  "claim_text": "待核查的原始陈述",
  "location": {"page": 3, "evidence_id": "example-evidence-003"},
  "candidate_rule_ids": ["example-rule-01"],
  "assessment": "needs_review",
  "reason": "为什么可能适用，以及尚未确认的条件",
  "suggestion": "明确可执行的修改建议",
  "fact_check_status": "not_verified",
  "missing_evidence": ["需要补充的数据或上下文"],
  "human_decision": "pending",
  "human_note": null
}
```

这是示例 Schema，不是实际业务规则、法律结论或已验证实现。规则编号与证据编号均为示意。

### 13.7 人工采纳不是无需解释的真理标签

用户可能采纳的是更好的措辞，而不是确认所有依据；拒绝也可能来自业务时机、风格或建议不可执行，而不是规则本身不适用。

**建议做法：**先保存情境化反馈，区分事实更正、规则适用性、更改措辞和流程偏好，再通过回归任务与反例检验，决定是否更新案例、Skill 或脚本。

R08 的组合实验尤其提醒：经验越积越多，系统不一定单调变好。最终配置仍需复验。

### 13.8 以小团队的最小闭环起步

优先建立清晰的主流程、少量必要的专业 Skills、可重复脚本、可信证据、执行授权和真实任务评测。只有出现明确的上下文、并行或权限需求时，再增加子 Agent。

这个方向借鉴 R05 的单 Agent 多 Skills 与 R09 对固定任务开销的讨论，但不把“简单”当成删除验证和安全控制的理由。

## 14. 统一认识：材料中的张力、边界与设计选择

### 14.1 不强行把不同材料写成同一个结论

| 表面冲突 | 来源各自在说什么 | 可以保留的认识 |
|---|---|---|
| R03／R05 要增加 Skills，R08 警惕指令 | 前者补充组织与过程知识，后者重点测试常驻通用规则 | 缺失知识与冗余指导需要分别评估 |
| R01 建议精简，R08 测试 50 条未退化 | 使用经验与特定范围实验不同 | 没测到质量下降，不代表无 Token 成本；也不应机械剪短 |
| R04 展示大幅节省，R09 的 MCP／CLI 比值不稳定 | 优化机制与具体系统组合的测量不同 | 检查目录、数据流、控制流和实际轨迹，而不是协议标签 |
| 讲义展示延迟加载，R09 某些配置全量携带目录 | 快照、实现和实验配置不同 | 材料不足以确定差异来源，不自行归因某次升级 |
| R05 合并 Agent，R07 分工 | 知识组织与工作角色不是同一维度 | 按上下文、任务依赖与权限需求决定隔离 |
| Hook 被称为执行约束，R06 有故障与超时 | 正常检查能力与实际失败处理不同 | 验证正常逻辑，也验证故障路径；资源边界仍需保护 |
| 测试相关指令可能无增益，但 R01／R02 强调测试 | 额外文字的边际作用与验证机制本身不同 | 不把 Prompt 消融误读成无需测试 |

### 14.2 不能从这些材料推出什么

不能推出模型能力已经不重要；不能推出 MCP 天生比 CLI 昂贵；不能推出负向措辞总是优于正向表达；不能推出技能越多越好；不能推出同一套 Skill 在所有模型上行为一致；不能推出独立 Reviewer 必然正确；也不能推出金融应用已得到这些软件任务实验的验证。

这些限制不是否定材料的价值，而是把可用证据放在其真实适用范围内。

### 14.3 一套实用的选择顺序

**工程综合：**先问是否缺信息，再问是否缺工作知识；先确认工具和环境，再评价模型决策；先给出验收，再要求自主完成；先限制副作用，再放大无人值守规模；先积累可运行资产，再扩展角色与能力目录。

归结起来：

> 让模型处理需要判断的部分，让程序处理已经确定的执行，让外部状态提供证据，让权限限制副作用，让评测决定哪些经验值得永久保留。

Agent Use 的成熟度，不是取决于你能同时启动多少 Agent，而是取决于你是否知道哪些事情已经被可靠完成、哪些只是模型的推测，以及哪些动作即使模型提出了也不应被执行。

## 附录 B：任务、项目指令、Skill、交接与评测模板

**模板性质：**以下内容是前述工程推导的可编辑起点，不是官方配置全集，也没有在你的项目中执行测试。示例路径、命令、编号和验收项需要按项目事实替换；文字约束不能替代真实权限。

### B.1 一份任务规格模板

```markdown
# 任务：修复过期会话仍被接受的问题

## 目标
会话过期后不再被视为有效；不改变与该问题无关的行为。

## 已知现象
记录当前错误表现、复现输入及相关测试。
明确这些是已经验证的事实，还是尚待确认的报告。

## 调查
先定位入口、会话有效性判断、调用方和相关测试。
说明直接原因；证据不足时继续调查，不先假定根因。

## 变更范围
优先修改会话校验相关模块。
不进行无关重构，不通过删除测试或弱化断言掩盖问题。
需要扩大范围时说明原因。

## 验收
- 环境能够运行相关测试。
- 回归测试在修复前因目标问题失败，而不是导入或环境错误。
- 修复后目标测试及相关回归测试通过。
- 对真实入口进行适当验证。
- 展示实际命令、退出状态、代码差异和未验证项。

## 授权
允许在指定本地工作区修改和测试。
推送、创建发布或修改远程状态必须按已配置的审批流程进行。

## 交付
问题原因、修改范围、验证证据、剩余风险与最终状态。
```

### B.2 一份简洁的 CLAUDE.md 模板

```markdown
# 项目工作约定

## 项目事实
- 所有业务时间比较使用 UTC；接口展示时间另行处理。
- generated/ 为生成目录，不直接修改。
- 修改前检查相关模块的调用约定与测试入口。

## 运行与验证
- 单元测试入口：填写本项目真实命令。
- 集成测试依赖：填写所需测试服务及启动方式。
- 不把测试环境缺失报告为测试通过。

## 变更边界
- 不修改与当前任务无关的模块。
- 不通过删除测试、弱化断言或隐藏错误掩盖实现问题。
- 新增依赖、修改构建配置时说明必要性。

## 外部动作
- 本地工作权限与远程发布权限分开。
- 未经授权不推送、不发布、不修改生产数据。
- 这些说明不代替运行时和服务端权限设置。
```

## 附录 C：常见误解与复习题

### C.1 十个需要主动避免的误解

| 误解 | 应保留的区别 |
|---|---|
| Agent 就是一个更长的回答 | 它包含多次推理、执行与环境反馈 |
| 模型请求工具说明动作已经执行 | 请求、授权、执行和结果是不同阶段 |
| 记忆意味着运行中更新模型参数 | 本课的记忆主要是外部信息重新进入上下文 |
| Skills 就是把提示词写长 | 名称发现、流程、参考知识与脚本承担不同责任 |
| MCP 自带业务理解 | 协议连接与业务方法不同 |
| 代码执行必然更安全 | 中间数据暴露减少，不代表副作用与网络访问已受控 |
| Hook 总能保证正确 | 事件覆盖、检查逻辑、故障语义与绕行路径都需要验证 |
| 新上下文就是新沙箱 | 上下文、环境与权限隔离不同 |
| 测试通过就证明所有需求满足 | 覆盖范围、当前版本与真实入口仍需检查 |
| 一次人工采纳就能生成新规则 | 反馈需要结合情境、反例和回归结果解释 |

这些区别对应正文各章，不额外引入新的事实结论。

### C.2 复习题与参考答案

**问题 1：Agent 生成了正确格式的工具参数，为什么任务仍可能失败？**

参考答案：格式只覆盖调用正确性。它可能误解业务语义、调用错误对象、缺少授权，或者即使工具成功也没有实现用户目标。参见第 4 章。

**问题 2：把一个两千行指令文件拆成十份两百行文件，为什么不一定节省上下文？**

参考答案：若十份都常驻，总输入没有减少。需要考察实际加载策略和作用域。参见第 3 章。

**问题 3：R08 中随机与精选规则的通过率都为 63.8%，可以证明具体知识无用吗？**

参考答案：不能。任务翻转组合不同，统计能力有限，实验主要排除了项目专属规则，也没有全面测试动态 Skill 包。参见第 6 章。

**问题 4：R09 的 12.9% 和 2.2% 是什么？**

参考答案：失败运行的建模支出占比，不是失败率。对应原始两组都是 19 次运行中失败 3 次。参见第 8 章。

**问题 5：一个发布工具有 PreToolUse 检查，能否认定所有发布路径都已受控？**

参考答案：不能。还要检查 CLI、直接 API、其他凭证和代码执行内部的替代路径，以及资源侧权限。参见第 9 章。

**问题 6：什么时候用 Skill，什么时候用 Subagent？**

参考答案：仅知识不同且需要共享完整语境时，优先考虑 Skill；需要独立上下文、并行任务或不同授权边界时，再考虑适当隔离。不同授权边界必须真实配置。参见第 11 章。

**问题 7：为什么“先红后绿”的红必须由目标错误触发？**

参考答案：环境不可用、导入失败只能说明测试没能正确运行，不能证明回归测试捕获了目标行为。参见第 10 章。

**问题 8：审核系统没有找到问题，应怎样区分“没有问题”和“没有完成判断”？**

参考答案：单独表达检索缺失、证据不足、解析错误和核验失败，不把未知状态默认为正确。参见第 13 章。

### C.3 讲义第 42 页分类练习

| 要求 | 讲义中的分类 | 需要理解的理由 |
|---|---|---|
| 应用公司的 API 约定 | Skill | 提供工作知识与方法 |
| 从 Jira 读取 Issue | MCP | 提供外部访问能力 |
| 每次编辑后运行格式化 | Hook | 生命周期事件自动处理 |
| 指导多步部署 | Skill | 提供过程知识 |
| 完成后发送通知 | Hook + MCP | 触发时机与外部发送能力分别负责 |
| 阻止生产写入 | Hook 或 Policy | 是执行限制，不只是语言建议 |
| 在多个仓库共享整套配置 | Plugin | 打包与分发 |

这是讲义练习的答案；实际工程还需要结合第 9 章的失败与绕行边界理解“阻止”的有效范围。[L02，p.42](#ref-l02)

## 文档收束

这份讲义的重点不是记住每个名词，而是学会定位问题：信息不足要改善观察，业务知识缺失要补过程与语义，确定步骤要交给受测程序，重要副作用要经过可信授权，完成状态要有外部证据，经验是否值得长期保留要由评测决定。

**模型能力、工作环境、过程资产、执行边界与验证机制共同决定 Agent 的实际表现。**理解它们之间的分工，才能把一次惊艳的演示，逐步变成可维护、可解释、可复用的工作系统。
