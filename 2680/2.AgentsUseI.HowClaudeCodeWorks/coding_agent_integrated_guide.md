# Coding Agent：从运行机制到可靠工程系统

*讲义与参考资料融合精讲*

**适用读者：** 已有 Java / Python 或其他软件开发经验，希望深入理解 Coding Agent 的 LLM 开发工程师。  
**整理日期：** 2026-10-13。  
**内容基础：** 本次对话中的两轮讲解、实际上传的主讲义、001—009 参考材料，以及前文已经使用的 Simon Willison 补充章节。  
**核心问题：** 怎样把一个会生成代码、也会犯错的模型，组织成能够理解项目、执行修改、利用反馈、控制风险并积累工程经验的系统？

> Coding Agent 的价值，不是让模型替你生成尽可能多的代码，而是让它以可控制、可验证、可复用的方式，减少软件开发中的不确定性。

## 1. 全局框架：这些材料究竟怎样串起来

### 1.1 讲义给结构，参考资料解释设计取舍

讲义第 4 页的顺序是：How Claude Code works → 从无状态 LLM 到 Agent → Memory → Tools、Skills、Hooks、Plugins。这是一条从模型调用走向完整应用的结构线。[S0，第 4 页](#src-s0)

但知道系统“有这些模块”，还不足以设计好系统。参考资料的作用，是回答每一层的设计为什么有效、什么时候失效，以及怎样测量它。

| 主线问题 | 联读材料 | 真正需要回答的工程问题 |
|---|---|---|
| 模型怎样变成 Agent | S0、S5、S1、W1 | 有了循环，为什么还不能保证完成任务？ |
| 应该给模型什么上下文 | S0、S1、S3 | 哪些信息常驻，哪些按需读取，哪些不必进入模型？ |
| 永久规则是否有价值 | S0、S8 | 新增指令是在补足知识，还是引入竞争目标？ |
| Skills 与工具怎样协作 | S3、S5 | 接口知识、业务语义和执行代码分别放在哪里？ |
| 为什么又慢又贵 | S4、S9 | 协议、工具目录、数据搬运和运行轨迹分别贡献多少成本？ |
| 如何限制副作用 | S0、S6、S5 | 文本要求、执行前拦截与执行后检查各自能保证什么？ |
| 是否需要更多 Agent | S1、S5、S7 | 新上下文获得什么，又丢掉什么？ |
| 怎样形成长期能力 | S3、S4、S7、W9 | 经验应该变成测试、脚本、Skill，还是不应该保存？ |

这里最重要的不是把九份材料各讲一遍，而是让它们参与同一个问题的推导。

### 1.2 用一个统一的工作过程理解系统

下面是根据材料整理的系统视图，不是某个产品的源码架构图：

```text
用户目标与验收条件
        ↓
组织本轮上下文：任务、代码、工具结果、项目事实、相关 Skill
        ↓
模型提出下一步动作
        ↓
权限与执行前检查
        ↓
工具执行：读取、搜索、编辑、运行、访问服务、委派
        ↓
取得实际结果：输出、状态、错误、产物位置
        ↓
验证并更新任务状态
        ├── 尚未满足：继续调查、修改或请求决策
        ├── 受阻 / 超预算：保留现场，明确停止原因
        └── 满足验收：交付代码与证据
                              ↓
                  复盘并更新可复用工程资产
```

前半段对应讲义的运行循环；验证与交付结合 S1、S9 和 Simon 的实践；复盘与资产化结合 S3、S4、S7。**后两层是综合组织，不是声称讲义已经实现了全部机制。**

### 1.3 “系统能力”与“模型能力”必须分开

模型的代码知识、推理和工具选择能力当然重要。但最终行为还受以下条件影响：它是否看到相关事实；工具是否提供充分结果；环境是否允许正确操作；完成是否有外部标准。

同一个模型，在两个不同环境中可能表现很不一样。一个环境有可靠测试、简明项目说明、可检索日志；另一个只有一段含糊需求和一个返回“失败”的工具。不能把这种差异全部归因于模型。[S0，第 6—12 页](#src-s0) [S9，§1.1、§2.5](#src-s9)

**本课程的工程视角：先找出失败发生在哪一层，再决定改模型、上下文、工具、权限还是验证器。**

## 2. Agentic loop：让错误能够被现实纠正

### 2.1 一次用户请求为什么对应很多次模型调用

讲义第 6 页明确写出：一次用户提示可能展开成多次模型调用与工具执行。第 9 页进一步区分：模型提出动作，harness 解析请求、检查权限、执行，再把结果放回上下文。[S0，第 6、9—10 页](#src-s0)

Lawrence Jones 用消息线程解释同一过程：模型输出工具名与参数，外围程序查找实现并调用，然后追加工具结果，再次调用模型。界面上的“正在处理”隐藏的是这个循环。[S5，《LLM 101》《Agents are a loop》](#src-s5)

例如，一次“修复失败测试”的请求可能展开为：

```text
运行测试 → 读取错误 → 搜索函数 → 读取实现及调用方
→ 编辑代码 → 再运行测试 → 检查差异 → 交付说明
```

这里模型没有直接进入机器。它提出请求，真正启动进程、修改文件和访问服务的是运行系统。

### 2.2 Coding Agent 与普通代码生成的差别是反馈

只让模型生成代码，得到的是一个候选实现。让它运行候选、读取错误、再修改，才建立了与外部环境的反馈关系。

Simon 将“能够编写并执行代码”视为 Coding Agent 的关键能力：执行使它能够迭代到有实际运行证据的软件，而不仅仅输出看起来合理的程序。[W1](#src-w1)

假设模型认为一个修改没有破坏调用方，编译器却报告接口不兼容。这个结果不是“模型换种措辞再想一次”，而是进入系统的**新事实**。它可能否定先前的方案。

**综合理解：生成能力给出候选，反馈能力淘汰错误候选。** Coding Agent 是否可靠，很大程度上取决于错误是否能够及时变成清晰的反馈。

### 2.3 循环并不自动意味着接近正确答案

下面也是一个循环：

```text
误解需求 → 写错误实现 → 按错误理解写测试 → 测试通过 → 宣布完成
```

所有调用都正常，任务仍然可能没有完成。原因是实现与验证共同依赖了错误的需求理解。

S1 因而把“提供可运行的验证方式”放在突出位置；S9 则通过仓库状态检查任务，而不是相信 Agent 的完成总结。这两份材料补上了讲义中循环之外的关键问题：**我们究竟用什么判断成功？** [S1，《Give Claude a way to verify its work》](#src-s1) [S9，§2.2](#src-s9)

| 状态 | 实际含义 |
|---|---|
| 模型结束回答 | 当前不再提出新的工具动作 |
| 运行过程结束 | 本次执行退出，可能完成、受阻、超时或失败 |
| 任务通过验收 | 外部检查确认交付物满足约定条件 |

这三个状态不能混用。正常退出不等于业务完成；有一份流畅的完成说明，也不等于目标已经实现。

S9 的重复实验中，有一次运行虽然创建了 PR、报告文件数量并正常退出，却没有完成全部分支和补丁条件。只有验收器读取真实状态，才能发现问题。[S9，§8.1，第 21 页](#src-s9)

### 2.4 一个教学抽象：模型只根据当前可见信息行动

以下公式用于解释机制，不是讲义原公式，也不是 Claude Code 源码。

设：

- `s_t` 是真实环境状态，例如工作树、进程和远端业务记录。
- `h_t` 是已经发生的交互历史。
- `m_t` 是可以加载的外部记忆。
- `c_t` 是本轮实际提供给模型的上下文。
- `a_t` 是模型提出的动作。

$$
c_t = G_H(\text{任务}, h_t, m_t, \text{环境观测}, \text{工具}, \text{预算})
$$

$$
a_t \sim \pi_\theta(\cdot \mid c_t)
$$

`G_H` 表示 harness 的上下文组织方式。即使模型参数不变，只要上下文选择和工具反馈改变，行为轨迹就可能改变。

这个抽象带来三个认识。

**模型看不到完整环境。** 它看到文件片段、工具输出和已有记录，因此“继续读一个关键文件”有时是必要的信息获取，而不是没有进展。

**观测不一定唯一确定真实状态。** 写入请求超时，可能是没有写入，也可能是写入成功但响应丢失。运行系统应当帮助 Agent 表达这种不确定性，而不是把所有异常都压成一个“失败”。

**改善系统不一定需要修改模型权重。** 更好的项目导航、错误信息、受控工具和验证器，都可能减少错误路径。它们改善的是决策条件与执行环境。

### 2.5 从这个抽象得到故障定位方法

以下是工程诊断框架，不是论文提出的正式分类法：

| 失败层 | 可观察现象 | 优先排查 |
|---|---|---|
| 信息缺失 | 没读到关键调用方或业务约定 | 检索范围、导航与按需知识 |
| 理解错误 | 已看到事实却错误解释 | 任务歧义、提示冲突、模型能力 |
| 执行错误 | 参数或环境不符合工具契约 | schema、错误分类、环境准备 |
| 状态不清 | 超时后不知道动作是否发生 | 操作状态查询、幂等与恢复 |
| 验证错误 | 测试全绿但需求没满足 | 验收条件、测试覆盖、独立检查 |
| 终止错误 | 重复尝试、不停扩展任务 | 预算、停止条件与任务边界 |

换模型可能解决其中一些问题，但不是每一类问题的直接修复方式。

## 3. 上下文：Agent 真正使用的工作台

### 3.1 用户提示只是上下文的一部分

讲义第 7 页列出启动时可能已经加载的系统指令、项目环境、持久记忆、核心工具以及 Skills/MCP 索引。用户消息并不是模型收到的全部内容。[S0，第 7 页](#src-s0)

因此，“相同用户提示、相同模型”并不代表相同实验条件。两个环境可能在项目规则、工具定义、自动记忆和历史内容上已经不同。

**工程推论：排查行为变化时，应该检查模型实际收到什么，而不是只比较用户输入的一句话。**

### 3.2 仓库在磁盘上，不等于整个仓库进入上下文

讲义第 8 页说明，代码仓库保留在磁盘上，Agent 使用搜索与读取按需取得片段。[S0，第 8 页](#src-s0)

一个合理的缺陷调查路径可以是：

```text
问题描述 / 错误堆栈
→ 路由或函数入口
→ 关键业务逻辑
→ 数据读写与事务边界
→ 调用方和相关测试
→ 根据新发现继续扩大范围
```

这是一种按问题依赖展开的调查，而不是按目录把仓库全部读一遍。

但不要把“不一次性发送整个仓库”理解成“代码绝不离开本机”。按照材料中的机制，实际加入模型请求的片段仍然可能传给模型服务。读取范围、敏感内容与模型服务边界需要另外设计。

### 3.3 上下文管理不是一味求短

S1 列出几种常见失败：无关任务塞进同一会话、重复纠正使失败路径累积、项目指令过度规定，以及没有范围的无限探索。它也承认，深入同一复杂问题时，保留历史可能有价值。[S1，《Avoid common failure patterns》《Develop your intuition》](#src-s1)

因此，更好的选择标准是：

> 这段内容能否支持当前或接下来的关键决策？它是否仍然有效？

完整项目历史不必然比两条当前模块约定更有效；但为了节省上下文而删掉“为什么方案 A 已被排除”，也可能让 Agent 重走错误路径。

**目标是保留决策价值，而不是机械缩短 token 数。**

### 3.4 渐进式加载连接了代码、记忆和 Skills

主讲义中的仓库按需读取、记忆索引，以及 S3 的 Skill 三级结构，共享同一个模式：

```text
先给导航信息 → 找到相关主题 → 再读具体内容 → 必要时读取附录
```

外部文件可以很多，模型本轮不需要同时看到所有文件。适当的目录、路径、描述和返回位置，是上下文工程的一部分。[S0，第 8、24 页](#src-s0) [S3，《The anatomy of a skill》](#src-s3)

但索引不是免费的。如果安装大量 Skill，每项描述都常驻，索引本身也会增长。渐进式加载降低了正文同时加载的负担，不保证任何规模都没有成本。

### 3.5 为什么长任务的累计输入可以很大

下面是教学算例，不是某产品账单。

假设初始上下文为 `B` 个 token，每轮新增 `d` 个 token，运行 `N` 轮。暂不考虑压缩，并按每轮逻辑请求都包含已有历史计算：

$$
T_{\mathrm{input}} = NB + d\frac{N(N-1)}{2}
$$

若 `B = 8,000`、`d = 2,000`、`N = 20`，最后一轮上下文为 46,000 token，但累计逻辑输入是 540,000 token。

这说明，早期加入的一段冗余内容可能在后续多轮反复出现。它的成本不只发生在第一次读取。

实际费用还受缓存、服务计费方式和上下文组织影响。S9 明确区分输入量、缓存量与估算费用，不能直接把累计 token 当成实际支出。[S9，§2.5、§4.2](#src-s9)

### 3.6 缓存与上下文选择解决不同问题

| 优化方式 | 解决的问题 | 不能自动解决的问题 |
|---|---|---|
| 前缀缓存 | 重复内容的计算或计费负担 | 内容是否相关、是否过期、是否造成干扰 |
| 按需加载 | 本轮不必携带全部知识和工具定义 | 加载路由是否准确 |
| 结果筛选 | 中间数据太大 | 筛选是否保留了关键异常 |
| 轨迹压缩 | 历史持续增长 | 摘要是否忠实、是否丢掉决策依据 |

这张表是对 S0、S3、S4、S9 的综合理解。一个巨大但命中缓存的工具目录，仍然巨大；一次没有缓存的新检索，也可能因为提供了关键事实而减少后续多轮错误。

### 3.7 压缩应该留下“事实、排除过程和未完成项”

讲义第 12 页描述对旧轨迹进行总结，再重新注入项目指令和记忆。第 17 页则指出，压缩时决策与假设可能丢失。[S0，第 12、17 页](#src-s0)

下面是一个教学交接模板：

```text
目标与范围：当前任务要改变什么，不能改变什么。
已确认事实：事实、来源位置、必要的版本信息。
已排除方案：哪个候选因为哪项证据被否定。
当前变更：修改了哪些文件，仍未完成哪些修改。
验证记录：实际运行了什么，对应哪个工作树状态。
未解决问题：缺少什么信息，哪些假设尚未确认。
下一步：最有信息价值的一个动作是什么。
```

“已经研究很多文件，正在修复”只是对话摘要；“先查再写无法通过并发测试，下一步检查写入边界”才保留了决策价值。

恢复时还要重新读取必要环境状态。笔记记录上次观察，不保证工作树、进程或远端资源现在仍然相同。

## 4. 记忆与项目规则：管理长期影响

### 4.1 “模型无状态”与“应用有记忆”不矛盾

讲义第 15—19 页把状态、模型与工具分开，并区分当前上下文和跨会话持久记忆。S5 也用消息线程解释状态是怎样被重新提供给模型的。[S0，第 15—19 页](#src-s0) [S5，《LLM 101》](#src-s5)

更准确的理解是：模型不会因为刚做过一个项目，就自动把最新项目知识永久写进参数；应用可以保存会话、文件、进度和经验，在后续重新加载。

| 机制 | 改变了什么 | 例子 |
|---|---|---|
| 当前上下文 | 本轮可见信息 | 刚读过的代码与错误信息 |
| 持久记忆 | 后续可重新加载的信息 | 项目约定、经验、决策说明 |
| 模型训练 | 参数中的能力与行为倾向 | 本讲未展开的训练过程 |

保存经验是更新外部知识，不等于发生了 SFT 或强化学习。

### 4.2 四类内容应该分开存放

以下是根据讲义与 S3、S5 整理的工程分类：

| 内容类型 | 例子 | 合理承载方式 |
|---|---|---|
| 项目事实 | 生成文件的源定义在另一个目录 | 项目说明或路径相关规则 |
| 程序性知识 | 排查积压要同时检查两个 broker | 按需加载的 Skill |
| 任务状态 | 已排除方案 A，方案 B 尚未验证 | 进度文件、交接记录 |
| 强制边界 | 未批准不得发布 | 指令说明意图，权限层执行 |

临时任务进度不应自动进入永久规范；安全边界也不应只靠一段操作指南。

### 4.3 `CLAUDE.md` 应该包含什么

讲义第 21 页建议提供测试、构建与检查命令，以及模型不容易推断的布局、所有权和容易踩坑的事实；不建议写语言常识、已有格式化工具负责的风格、长篇历史或秘密信息。[S0，第 21 页](#src-s0)

一个简短的教学示例如下，路径与命令需替换成项目实际值：

```markdown
# 项目导航
采纳建议的业务逻辑位于 src/reviews/。
相关测试位于 tests/reviews/。

# 验证入口
使用 python -m pytest tests/reviews -q 运行相关测试。

# 当前项目边界
不要直接编辑生成文件；修改对应源定义。
不要为使测试通过而跳过测试或削弱需求断言。
涉及数据结构变更时，先说明兼容性与迁移影响。

# 业务语义
“未查询到状态”与“状态为未采纳”不是一回事。
```

衡量一句话是否值得常驻，可以问：**它能否改变一次真实、重要的工程决策？** “你是一位资深工程师”不如“这个目录是生成结果”直接影响文件选择。

### 4.4 加载范围与加载优先次序，不是权限系统

讲义展示组织、用户、项目和本地说明文件，并说明从较宽范围到较近范围读取。它也介绍 `.claude/rules/` 中按主题拆分，并通过 `paths` 让规则只在相关文件工作中加载；没有范围限制的文件则会常规加载。[S0，第 20—22 页](#src-s0)

两个工程边界需要明确。

**拆文件不等于按需加载。** 把一个长文件拆成十个始终加载的小文件，逻辑内容没有变少。

**后读取不等于获得底层授权。** 文本加载次序影响模型判断，不能覆盖服务端权限或沙箱策略。

### 4.5 Auto memory 应该是可审查的经验

上传讲义将自动记忆分为用户信息、反馈、项目决策与外部引用；使用 `MEMORY.md` 作为索引，主题文件按需读取。它还列出 `/memory`、`/context`、`/init`、`/doctor` 等检查入口。这些具体行为按材料快照理解，不视为所有版本的保证。[S0，第 23—25 页](#src-s0)

讲义第 26 页的关键提醒是：过期记忆可能比没有记忆更坏，因为它会主动误导；记忆应像代码一样被检查、清理和管理。[S0，第 26 页](#src-s0)

例如，一次修复后写入“重复请求都加唯一索引”，就把具体方案过度泛化了。更好的经验应该保留适用条件：业务唯一性如何定义、哪些环境验证过、什么情况下不适用。

**工程建议：** 对会长期影响行为的记忆，保留来源、适用范围、验证依据与失效条件。自动生成可以是候选入口，不应自动成为永久真理。

### 4.6 这一层为什么需要论文来约束直觉

前面看起来都合理，但“内容合理”不保证“加载后整体任务表现更好”。持久指令会改变整个运行轨迹，可能帮助，也可能干扰。

这正是下一章 S8 的意义：把规则从文字建议，变成可测量的系统干预。

## 5. 论文精读：Guardrails Beat Guidance

### 5.1 研究问题与实际干预

论文研究的是：持久加载的自然语言规则，怎样影响 Coding Agent 的多步行为与任务通过率。它通过替换工作目录的 `CLAUDE.md`，改变规则内容，尽量固定 Agent、模型、提示模板和工具。[S8，§1、§5，第 1—4 页](#src-s8)

其设置不能省略：

| 项目 | 上传论文中的设置 |
|---|---|
| Agent | Claude Code |
| 基础模型 | Claude Opus 4.6，经 AWS Bedrock 调用 |
| 任务 | SWE-bench Verified 的 Python 问题修复 |
| 规则语料 | 679 个文件、25,532 条清理后的规则 |
| 主要任务子集 | 实验 1—3 使用 58 个有区分度的任务 |
| 细粒度实验 | 实验 4 使用 35 个任务；其中 4b 分析 17 个基线已解决任务 |
| 运行数量 | 四组实验 3,544 次，加上 1,500 次筛选运行，总计超过 5,000 次 |

“超过 5,000 次运行”不是“5,000 个独立工程任务”。有区分度的任务又经过基线筛选，因此不能将结果不加说明地推广到所有任务。[S8，§5，第 4 页](#src-s8)

### 5.2 最重要的适用范围：项目特定规则被排除

语料中项目特定规则占 64.9%，是最大类别；但主要实验集中在五类可跨项目迁移的规则，排除了项目特定类别。[S8，图 2、§3、§5，第 3—4 页](#src-s8)

这意味着论文主要在问：

> 给一个已经有编程能力的 Agent 加上通用行为、流程、风格或约束，会怎样改变表现？

它没有直接证明“模型不知道的项目事实没有用”，也没有完整测量 Skill 的触发、附件导航、脚本质量和权限治理。

因此，S8 与 S3 并不是互相否定：S3 提供组织程序性知识的机制；S8 检验某种持久自然语言干预的效果。它们有交集，但不是同一个实验对象。

### 5.3 四组实验构成了一条完整论证

| 实验 | 改变的变量 | 检验的问题 |
|---|---|---|
| 1：规则来源 | 人工整理、随机抽取、热门、领域匹配、打乱顺序等 | 是内容品质重要，还是规则存在本身重要？ |
| 2：规则数量 | 0、1、3、5、10、20、50 条 | 规则越多，是否出现持续退化？ |
| 3：规则类型 | 工具流程、混合、安全、风格、架构 | 哪类规则更可能帮助模型？ |
| 4：单条与组合 | 完整集合中移除一条、单条加入、两条组合 | 规则效果是否稳定，能否相加？ |

来源：S8，§6，第 5—7 页。

### 5.4 实验一：随机规则与人工规则同为 63.8%，应该怎样解释

论文第 11 页表 2 给出以下结果。这里的“随机”是抽取真实社区规则，不是随机字符。

| 条件 | 通过率 | 相对无规则基线的配对检验 p 值 |
|---|---:|---:|
| 无规则 | 50.0% | — |
| 随机社区规则 | 63.8% | 0.077 |
| 人工整理规则 | 63.8% | 0.115 |
| 热门规则 | 60.3% | 0.361 |
| 不匹配领域规则 | 58.6% | 0.424 |
| 匹配领域规则 | 56.9% | 0.481 |
| 打乱顺序的规则 | 56.9% | 0.523 |
| 仅原生格式规则 | 56.9% | 0.556 |

来源：[S8，§6.1、表 2，第 5、11 页](#src-s8)。

论文发现各规则条件的方向都好于该次无规则基线，但单个条件与基线的 McNemar 比较，没有达到通常使用的 `p < 0.05` 门槛。作者另用七个提升方向的符号检验支持总体趋势，并将结论强度限定为有限但一致的证据。

作者提出 **context priming** 解释：有组织、与任务大体相关的说明，可能使模型进入更谨慎的工作模式，具体内容的额外贡献没有预想中强。但论文没有通过单独实验完全隔离这个机制。[S8，§6.1、§7—8](#src-s8)

应当保留三个区别：

**相近分数不等于证明两种方法等价。** 样本与统计能力有限，可能识别不出较小差异。

**没有显著差异不等于内容没有作用。** 它只说明这组实验不足以建立稳定的差异结论。

**通用规则贡献有限，不等于项目事实可以随便写。** 项目特定知识并非这里主要测试的对象。

所以，“随便加规则就能稳定提升 13.8 个百分点”不是合理结论。

### 5.5 实验二：50 条规则没有明显退化，如何理解

数量实验使用不同抽样种子，测试从 0 到 50 条规则。通过率位于约 59%—67% 区间；50 条的均值为 66.7%，该实验零规则基线为 60.3%。论文没有观察到预期的明显数量退化。[S8，§6.2、图 3，第 5—6 页](#src-s8)

这里的 **60.3%** 与实验一的 **50.0%** 来自不同实验统计设置。不能把两个基线混用，拼接成一个更大的提升幅度。作者在局限性中讨论了基线方差和重复运行的影响。[S8，§7，第 9 页](#src-s8)

这与 S1 的“清理过长项目指令”存在张力，但不必强行判定谁对谁错。

S8 观察的是特定模型、特定任务、有限数量规则下的通过率；S1 还讨论长会话、无关信息和失败轨迹累积。**未观察到正确率下降，也不等于没有输入成本、维护成本或路由成本。**

合理的工程处理是分别测量正确率、成本与错误类型，而不是把“越少越好”或“50 条以内随便加”当作定律。

### 5.6 实验三：规则类型的排序是方向证据，不是确定结论

| 规则类型 | 通过率 |
|---|---:|
| 工具 / 流程 | 63.8% |
| 混合类型 | 62.1% |
| 安全约束 | 60.3% |
| 代码风格 | 56.9% |
| 架构指导 | 53.4% |

来源：[S8，§6.3、表 3，第 5、11 页](#src-s8)。

工具 / 流程规则在方向上更好，最高与最低相差 10.4 个百分点。但论文同时报告，类型间差异没有达到足够的统计显著性。因此，不能说某类规则已经被证明一定优于另一类。

一个可用于理解的例子是：“测试失败时先调查根因”与“总是使用某种架构模式”不同。前者在具体状态下提供行动指导，后者可能在不需要时增加目标。但这是作者的解释方向，不是对每条规则都成立的因果结论。

### 5.7 实验四：为什么负向约束看起来更好

从完整 18 条规则集合出发，逐条移除规则。按作者设定的 `|Δ| > 5pp` 分类，3 条有益规则都是负向约束，4 条有害规则都是正向指令，11 条被归为影响不明显。[S8，§6.4、表 4](#src-s8)

| 规则的简化含义 | 在完整集合中的条件性贡献 | p 值 |
|---|---:|---:|
| 不重构无关代码 | +20.0 个百分点 | 0.016 |
| 不添加不必要的新依赖 | +8.6 个百分点 | 0.508 |
| 不修改无关文件 | +5.7 个百分点 | 0.688 |
| 保持兼容性 | −8.6 个百分点 | 0.508 |
| 处理相关边界情况 | −11.4 个百分点 | 0.289 |
| 阅读相关测试 | −14.3 个百分点 | 0.227 |
| 遵循代码风格 | −14.3 个百分点 | 0.180 |

**表中正值**表示移除它会使结果变差；**负值**表示移除它后结果反而更好。这不是某条规则在所有上下文里的固有价值。[S8，表 4，第 11 页](#src-s8)

作者解释：基础模型已经知道许多编程方法，泛化正向指令可能引入与当前任务竞争的活动；负向约束则限制不必要的偏离。例如，仅修复空值处理时，“全面改善质量和统一风格”可能使任务扩大，而“不修改无关模块”维持了范围。[S8，第 6—8 页](#src-s8)

但要注意证据边界。

**第一，最强的一条也不能通过严格的多重比较校正。** 同时测试很多规则，不能只挑出一个小 p 值而忽略比较次数。

**第二，分类阈值会影响极性结论。** 论文改变阈值后，信号变弱；无阈值的连续效应检验没有给出强证据。

**第三，规则内容与肯定 / 否定形式并未完全分离。** 实验不是将相同语义分别改写为肯定句和否定句，再做充分的配对测试。[S8，第 6 页及第 9 页](#src-s8)

因此，真正值得学习的是**减少无关目标扩张，并测试指令效果**，不是迷信“不要”两个字。

### 5.8 “阅读测试有价值”与“加一句阅读测试没有提升”不矛盾

这是联读 S1、W2、W3 与 S8 时最容易混淆的地方。

“读测试有助于理解代码”描述的是一种行为价值；“永久增加一句阅读测试的指令，是否提高最终通过率”描述的是一次系统干预效果。

新增指令可能改变探索顺序、阅读范围和停止条件。模型本来就会读测试时，这句话可能没有增益；在某个任务里，它也可能引起过度探索。

**工程推论：不能因为一条测试相关指令没有显著帮助，就取消验证环节；也不能因为测试很重要，就认为任何形式的测试指令都应该永久加入。**

### 5.9 单条效果不能直接相加：这是最值得记住的结果

论文第 12 页表 5 给出了五组两条规则的组合结果：

| 组合 | 无规则 | 仅 A | 仅 B | A+B | 按加法预期 | 偏差 |
|---|---:|---:|---:|---:|---:|---:|
| Pair 0 | 68.6% | 71.4% | 74.3% | 65.7% | 77.1% | 11.4pp |
| Pair 1 | 71.4% | 54.3% | 65.7% | 71.4% | 48.6% | 22.9pp |
| Pair 2 | 71.4% | 65.7% | 68.6% | 68.6% | 62.9% | 5.7pp |
| Pair 3 | 74.3% | 62.9% | 68.6% | 54.3% | 57.1% | 2.9pp |
| Pair 4 | 74.3% | 80.0% | 60.0% | 62.9% | 65.7% | 2.9pp |

来源：[S8，表 5，第 12 页](#src-s8)。各行是不同配对条件，不能当作同一次基线下的独立提升。

Pair 0 中，A、B 单独都更好，组合后却更差。Pair 1 中，A 单独很差，组合后却恢复到该行基线。作者将这类现象解释为干扰与补偿。

因此，这种策略不可靠：逐条挑出看似有益的规则，再假定所有规则组合后一定更好。规则共同进入上下文，会一起改变任务理解、注意分配与执行轨迹。

此外，4b 对基线已解决任务的分析，也受到运行随机性影响：基线复测可靠性为 88.2%，所以某次由通过变失败不能全部归因于新增规则。[S8，§6.4，第 6 页](#src-s8)

**工程结论：最终必须评测实际部署的规则组合，而不只评测单条规则。**

### 5.10 PBRS 在论文中是解释视角，不是理论保证

论文借用强化学习中的 potential-based reward shaping，提出三个预期：状态相关规则可能更好；偏置可能随数量累积；规则效果可能近似相加。实验只对第一项提供方向支持，后两项没有普遍成立。作者明确将 PBRS 作为生成假说的类比，而非正式理论。[S8，§4、§7](#src-s8)

本文不把“条件式自然语言规则”说成满足某个强化学习定理，也不把加载 Skill 说成奖励塑形训练。材料并未提供这种对应关系的严格证明。

### 5.11 对实际规则库的使用方法

以下是从论文得到的工程建议，而不是论文证明的最佳流程：

先区分项目事实与泛化行为要求；针对已经观察到的失败，提出少量规则候选；比较有无规则及最终组合；记录通过率、轨迹和成本；在不同任务上复测，再决定保留、修改或退休。

这篇论文最有价值的改变，是把问题从“这句话听起来是否专业”，转成：

> 它在什么任务上改变了什么行为？这种改变是否减少了真实失败？

## 6. 工具设计：模型与现实的接触面

### 6.1 六类核心工具

讲义第 28 页列出 Read、Search、Fetch、Edit/Write、Shell、Delegate。前三类主要提供信息；编辑与运行会改变环境；委派把部分工作交给另一个上下文。[S0，第 28 页](#src-s0)

表面上工具可以很朴素，但接口细节决定模型能否获得清楚反馈。S5 的解释也强调，Shell、文件编辑和搜索等普通工具足以支撑大量复杂行为。[S5，《Agents are a loop》](#src-s5)

### 6.2 工具不仅决定能做什么，也决定能知道什么

以下是接口设计推论。

只返回 `{"success": false}`，会把很多不同情形混在一起：参数不合法、权限拒绝、进程失败、测试失败、网络超时、外部动作状态未知。

一个面向 Agent 的结果可以表达得更清楚。下面是**教学 schema**，不是 Claude Code 原生返回格式：

```json
{
  "status": "failed",
  "exit_code": 1,
  "summary": "并发回归测试未通过",
  "workspace_snapshot": "本次验证对应的工作树标识",
  "artifact_ref": "完整测试日志的位置",
  "truncated": true
}
```

大结果保存在可追溯位置，返回关键结论及定位信息；需要时再读取原始内容。不能为了压缩而把决定下一步所必需的错误细节删掉。

### 6.3 错误分类应该对应不同后续动作

| 工具结果 | 环境是否改变 | 合理的后续处理方向 |
|---|---|---|
| 参数校验未通过 | 通常尚未执行 | 修正参数 |
| 权限拒绝 | 被拒动作未执行 | 停止或请求适当授权 |
| 测试已执行但失败 | 可能产生测试环境变更 | 读取失败条件，判断根因 |
| 长命令仍在运行 | 进程状态持续变化 | 查询已有任务，不要盲目重启 |
| 外部写入超时 | 可能已经产生副作用 | 先核对状态或按幂等契约恢复 |

这不是任何具体工具的统一规范，而是自建工具需要考虑的语义区别。

### 6.4 编辑应检测旧状态是否失效

模型读取文件后生成补丁，但用户、格式化器或其他 Agent 可能已经改过文件。无条件覆盖会把旧判断作用于新状态。

**工程建议：** 编辑工具使用旧内容匹配、文件版本或工作树快照做前置校验；不匹配时返回冲突，让 Agent 重新读取。补丁表达的是“基于某份状态的修改”，不是任意覆盖当前文件的授权。

这与测试结果绑定代码版本是同一个原则：**观察、修改与验证都要知道自己对应哪个状态。**

### 6.5 长命令应有独立生命周期

构建或测试尚未结束时，Agent 需要任务标识、状态查询、增量输出和必要的取消能力。恢复会话时，也要区分进程仍在运行、已经退出和状态未知。

这是本文工程推论，不是讲义展示的完整进程管理实现。其目的很直接：不要把“尚未拿到结果”误当成“从未执行”，从而重复启动昂贵或有副作用的操作。

### 6.6 一个 Shell schema 不等于一个狭窄能力

S5 描述了用 Go 实现虚拟文件系统和 Shell 解释器的实践：工具可以提供模型熟悉的命令语义，而不必直接运行真实 Bash。[S5，《Agents are a loop》](#src-s5)

但接口简单不代表权限小。讲义指出，没有沙箱限制时，Shell 可能触及整台机器。[S0，第 28 页](#src-s0)

**工程推论：** 给 Agent 一个“只读角色名”，却允许其通过 Shell 写文件、读取凭据和访问网络，并不构成只读系统。能力边界应由真实执行环境和服务权限落实。

## 7. Skills：按需加载的程序性知识

### 7.1 先看真实业务案例：工具接通不代表知识接通

Lawrence 的队列系统在两个 broker 之间分配事件：Google Pub/Sub 与 NATS JetStream。其 Skill 说明，每条消息只进入一个 broker，因此一个订阅的积压要结合两边看。某个计数为 `null` 表示该来源无法提供数量，不表示零；必要时应从遥测获取计数。执行清理前还应查看警告和积压是否已经在消退。[S5，《Skills are just instructions》，队列 Skill 示例](#src-s5)

工具 schema 可以告诉模型某个操作的参数，却未必解释：两个来源如何组合、未知值意味着什么、什么情况下应该等待而不是清理。

这就是 **接口知识与业务知识的差距**。

S5 用 API 参考与使用指南的区别来解释：知道 endpoint 怎样调用，不等于知道多个 endpoint 应该怎样配合。[S5，《Skills are just instructions》](#src-s5)

### 7.2 Skill 的结构为什么采用三级加载

S3 定义的 Skill 是包含说明、脚本和资源的目录。最小入口为带 `name`、`description` 的 `SKILL.md`。名称与描述先进入上下文，相关时读取正文，再根据需要读取参考文件。[S3，《The anatomy of a skill》](#src-s3)

| 层级 | 主要作用 | 模型获得什么 |
|---|---|---|
| 名称与描述 | 发现、路由 | 这项能力是什么，什么时候适用 |
| `SKILL.md` 正文 | 主流程 | 怎样处理任务，有哪些判断分支 |
| 参考文件与脚本 | 细节、执行 | 特定情形的知识和可运行实现 |

S3 的 PDF 表单例子，把一般 PDF 指导与表单操作细节分离。它强调的是“按需获得细节”，不是“一个 Markdown 文件能代替任何工程实现”。

原文说可以在 Skill 中打包大量外部内容，不等于模型同时理解全部内容。扩展的是可用资源，不是模型本轮上下文的无限容量。

### 7.3 description 是路由接口，不只是简介

比较两个教学描述：

> 帮助编写高质量代码。

> 排查请求重试和并发调用导致的重复业务效果；检查操作标识、状态变化、写入边界与回归验证。

第一句适用于几乎所有任务，难以与其他 Skill 区分；第二句给出了触发范围。

讲义强调清晰且互相区分的描述有助于减少错误选择，S3 要求观察真实轨迹，尤其关注名称与描述。[S0，第 34—35 页](#src-s0) [S3，《Developing and evaluating skills》](#src-s3)

Skill 的正文再好，如果需要时没有加载，也不能发挥作用。

### 7.4 一个教学目录与正文示例

下面是基于队列例子组织的教学目录，并非原作者仓库的完整结构：

```text
queue/
├── SKILL.md
├── references/
│   ├── broker-semantics.md
│   ├── interpreting-metrics.md
│   └── purge-procedure.md
└── scripts/
    └── summarize_snapshot.py
```

查询状态时，不必自动加载所有清理流程。正文可以这样表达：

```markdown
---
name: inspect-queue-backlog
description: 解释多 broker 的订阅积压、计数缺失和事件处理延迟。
---

# 目标
定位积压在哪些来源出现，并区分零、未知与已确认积压。

# 调查
读取订阅与 broker 明细。
依据 references/broker-semantics.md 解释各字段。
若某来源不能提供计数，保留未知状态，不自行补零。
需要趋势判断时，读取相关遥测说明。

# 输出
分别说明已确认事实、未知信息和下一项必要检查。

# 边界
本技能用于调查；清理操作需要独立流程与真实授权。
```

这是程序性指导，不是严格执行的工作流引擎。是否调用工具、如何解释步骤，仍会经过模型判断。

### 7.5 什么时候读脚本，什么时候运行脚本

S3 的例子中，PDF Skill 携带提取表单字段的 Python 脚本。Agent 可以运行脚本，不必先把整段脚本及整个 PDF 都读进上下文。原文将排序等操作列为更适合传统代码处理的例子。[S3，《Skills and code execution》](#src-s3)

据此可以分工：模型选择和解释；脚本执行已经确定的计算；权限层限制副作用。

例如，解释未知计数为什么不能补零属于业务知识；按照确定规则检查字段、生成汇总表可以交给脚本。**脚本执行可重复，不等于脚本逻辑自动正确。** 它仍然需要测试、依赖管理和版本控制。

S3 还建议明确告诉 Agent，某个脚本是应直接执行，还是只作为参考阅读，避免不必要的上下文加载。

### 7.6 加载 Skill 为什么值得封装成工具

S5 说明，直接读取 `SKILL.md` 已经可以使内容进入上下文；封装一个 Skill 工具，则便于按名称解析路径、记录使用、返回正文和小型目录索引，省去额外目录搜索。[S5，Skill 加载实现，第 661—684 行附近](#src-s5)

这说明有价值的 harness 扩展不一定很复杂。一次小的返回设计，就可能减少后续无效动作，也让技能使用可以被观察。

### 7.7 模型触发与用户触发不能代替授权

讲义区分模型按描述触发与用户显式调用，并建议有副作用的工作流通常采用显式调用。[S0，第 35 页](#src-s0)

但“显式调用了发布 Skill”仍然不等于所有发布动作都被批准。Skill 启动、工具允许执行、服务端批准具体动作，是不同边界。第 10 章进一步展开。

### 7.8 怎样评测 Skill

根据 S3 的“先观察能力缺口，再增量构建”建议，本文将评测拆成三个问题：

**该加载时是否加载？** 看触发与路由。

**加载后是否正确使用？** 看分支、引用、脚本与工具调用。

**最后是否改善任务？** 看验收结果、成本和人工介入。

只统计调用次数不够。高调用率可能意味着有价值，也可能意味着描述过宽，给很多无关任务增加了流程。[S3，《Developing and evaluating skills》](#src-s3)

此外，S3 提醒 Skills 可以携带恶意指令、依赖和外部访问，应审查来源、脚本及引用资源。把操作指南视为软件供应的一部分，比把它当成无害文字更稳妥。[S3，《Security considerations when using Skills》](#src-s3)

### 7.9 与规则论文的连接

S8 没有否定内部业务语义的价值；它提醒的是，**合理内容一旦作为上下文干预进入系统，最终效果仍要测量**。

好的技能库不应该以“文件越来越多”为成功标准，而应该证明：关键事实更容易在需要时出现，已经验证的操作更容易复用，原有失败减少，而无关负担可控。

## 8. MCP 与代码执行：连接、发现、组合是三件事

### 8.1 MCP 连接能力，不自动提供业务判断

讲义第 36—37 页将 MCP 放在外部能力层：Agent 判断需要什么操作，client 发起调用，server 连接相应系统，结果返回模型。协议传递调用，是否调用以及怎样解释结果仍由 Agent 决定。[S0，第 36—37 页](#src-s0)

S5 的队列案例因此需要 Skill：工具提供订阅状态与清理入口，Skill 解释多个 broker、未知计数和处理顺序。**连接成功不代表理解正确，返回成功也不代表业务判断成立。**

讲义附录还介绍 Tools、Resources、Prompts 三种基本元素，不能把 MCP 简化成“只能注册几个函数”。这一部分放在附录 A，便于与主线分开阅读。[S0，第 45—48 页](#src-s0)

### 8.2 先拆开三个独立设计问题

| 问题 | 常见选择 |
|---|---|
| 外部系统怎样连接 | MCP、直接 API、CLI |
| 操作知识怎样进入模型 | 全量 schema、按需搜索、目录索引、帮助文档 |
| 多个操作怎样组合 | 每一步由模型选择，或在执行环境中用代码组合 |

这是对 S4、S5、S9 的综合组织，而不是三份材料中的统一原始分类。

**使用 MCP，不意味着必须每轮携带全部 schema。**

**通过代码调用工具，不意味着放弃 MCP。**

**CLI 也不是完全没有工具定义，它通常经由 Shell 工具提供给模型。**

S9 前几页描述两种知识放置方式：大量操作被显式列在请求中，或者主要给出 Shell，让模型利用已有命令行知识。S5 也提到工具搜索可以让 schema 延迟进入上下文。[S9，§1.1—1.2](#src-s9) [S5，《MCPs are just APIs in tools》](#src-s5)

不要把一种具体 harness 的工具暴露策略，当作协议的不可改变属性。

### 8.3 S4 指出的两个成本来源

**工具定义的负担。** 接入很多服务后，模型可能在处理任务前就看到大量当前用不到的说明。

**中间结果的负担。** 长文本或大型数据集被返回给模型，模型再把它们写进下一次工具参数，形成不必要的重复输入与输出。[S4，《Excessive token consumption from tools makes agents less efficient》](#src-s4)

原文使用从 Google Drive 获取会议记录、再写入 Salesforce 的例子。朴素方式让整段文本先进入模型上下文，再由模型在后续参数里重新写出。

对数据工程师而言，这可以理解为：本来可以在执行环境中传递的变量，被变成了语言模型的输入输出。模型开始兼任数据搬运通道。

### 8.4 Code execution with MCP 的核心变化

原文提出，让模型编写代码，在执行环境中发现并调用工具、筛选结果、组合操作，仅把必要内容返回给模型。[S4，《Code execution with MCP》及后续小节](#src-s4)

下面是**数据流示意**，不是可直接运行的真实 API：

```javascript
const transcript = await drive.getDocument(documentId);
await crm.attachNotes(recordId, transcript.body);

return {
  documentId,
  recordId,
  attached: true
};
```

关键不是使用 JavaScript，而是 `transcript.body` 在执行环境中传递，不必由模型重新生成。

另一个典型过程是：

```text
模型选择筛选规则
→ 执行环境取得大量数据
→ 在代码中筛选、聚合和保存
→ 返回数量、异常样本、警告和完整结果位置
→ 模型解释必要信息
```

这里必须保留可追溯的完整结果。省上下文不应变成只留下无法核对的摘要。

### 8.5 工具发现也可以下沉到文件和搜索

S4 展示把工具定义映射为文件，由 Agent 查看相关目录或搜索工具，再加载具体定义，而不是一次性看到全部操作。其一个示例将 token 使用量从 150,000 降到 2,000，约减少 98.7%。[S4，《Progressive disclosure》](#src-s4)

这个数字是原文示例中设计变化的结果，不是 MCP 的普遍收益承诺，也不能套到任何现成产品上。

这种设计与 S3 的 Skill 加载完全呼应：**先提供可发现性，再按需提供细节。** 区别在于一个主要加载操作接口知识，一个主要加载任务流程知识。

### 8.6 控制流下沉：不需要每个 if 都问模型

原文还讨论，把已经明确的条件分支、轮询与数据处理放进代码，减少模型在机械步骤之间反复往返。[S4，《More powerful and context-efficient control flow》相关段落](#src-s4)

综合理解是：模型参与需要语义判断的节点，普通代码处理已经确定的步骤。

但不能把所有任务一次性编成很长的脚本。若后续动作需要理解刚返回的新事实，仍然需要把合适观测交回模型。代码执行的作用是减少不必要的模型回合，不是取消必要的反馈。

### 8.7 数据不经过模型，不等于数据自动安全

S4 指出，中间结果可以留在执行环境；更敏感的值还可以替换成占位标识，避免进入模型上下文。[S4，《Privacy-preserving operations》](#src-s4)

据此需要区分三个边界：

**模型可见范围。** 什么内容进入模型请求。

**执行环境可访问范围。** 脚本能读什么文件、调用什么服务、发往什么网络地址。

**日志可见范围。** 原始结果是否已经进入终端输出、遥测或第三方记录。

后两点是工程推论。仅保证模型不看见秘密，不保证执行环境不能外传，也不保证日志没有记录。

### 8.8 合并工具调用后，授权粒度不能消失

一段脚本可能内部执行多个外部写操作。如果系统只批准“执行这段代码”，却不约束脚本内部实际访问的资源，权限就可能过于粗糙。

**工程建议：** 有副作用的操作仍由服务端、受控代理或能力层检查授权。不要因为它隐藏在代码执行内，就让其绕开原来逐动作的权限要求。

这不是反对代码执行，而是说明优化上下文时必须同时重新检查执行与审计边界。

### 8.9 从一次执行到可复用能力

S4 不只讲省 token，还展示将工作状态保存到文件，以及把已经有效的代码保存为可复用函数。[S4，《State persistence and skills》](#src-s4)

这与 S3、S7 可以连成一条完整路径：

```text
模型探索并形成可运行实现
→ 验证实现
→ 固化成脚本或函数
→ 用 Skill 解释适用条件与调用方式
→ 用 Plugin 或仓库分发
→ 后续任务按需复用
```

**代码执行让一次任务更高效，Skill 让已有实现下次被正确找到，Plugin 让团队共享同一套设置。**

## 9. 论文精读：The Scaffolding Matters More Than the Interface

### 9.1 先看任务，不要先看排名

论文想比较 MCP 与 CLI 的工具使用成本，固定了一个软件操作任务：定位 issue、创建分支、应用已经提供的补丁、提交、创建 PR、报告目录文件数。[S9，§2.1，第 4 页](#src-s9)

“补丁已经提供”非常重要。它测试多步骤软件操作，不是让 Agent 独立诊断复杂缺陷并发明修复方案。因此，不应把结果直接解释为所有编码任务上的总体能力排名。

验收器通过 GitHub API 检查四项条件：分支、补丁后的文件内容、PR 和文件数。每次运行前重置仓库，避免继承前一轮结果。[S9，§2.2](#src-s9)

**它最值得复用的方法，是验收真实产物，而不是相信 Agent 的自述。**

### 9.2 实验到底比较了什么

| 维度 | 上传论文中的设计 |
|---|---|
| Scaffolding | Claude Code、Codex、qwen-code、Hermes、opencode、pi、Tau |
| 模型 | 五个模型，覆盖并非完整的笛卡尔积 |
| 工具接口 | 支持 MCP 的框架分别运行 MCP 与 CLI 条件 |
| 控制参照 | pi、Tau 在测试版本中不带 MCP client，只运行 CLI 条件 |
| 操作隔离 | MCP 条件下隔离 Shell 侧凭据，减少静默走另一条路径 |
| 记录 | 输入、缓存、实际工具调用、每次请求的 schema 数量 |
| 完成检查 | 独立读取仓库状态 |

来源：[S9，§2.3—2.5，第 5—6 页](#src-s9)。

论文的主矩阵为 54 个配置单元，其中 46 次实际执行、40 次完成；不能把不可运行的配置单元当作成功或零成本。后续还对本地模型配置进行了重复实验。[S9，第 10 页、§2.9、附录 A](#src-s9)

统一代理计量的一个目的，是把子 Agent 请求也纳入成本。否则，一个大量委派的系统可能看起来很便宜，只因为账漏记了。[S9，§2.5](#src-s9)

### 9.3 数字口径：token 不是账单

论文的美元金额是按统一价格表推算的**模型化费用**，不是每次运行的实际账单。本地模型也按租用等价能力的假设计价；缓存折扣另作敏感性分析。[S9，§2.5](#src-s9)

同时，大部分框架比较表只对**完成的运行**计算成本，完成率与失败支出分别报告。某个没有成功运行的条件，不应被理解成没有花钱。

因此必须分别看：输入量、模型价格、缓存、完成率和失败支出，而不是把某一列当作系统的完整价值。

### 9.4 跨框架输入量差异很大，但不是纯粹因果排名

论文第 10 页表 1 的核心结果如下。表中输入与输出都是完成运行的中位数，完成次数属于主矩阵。

| Scaffolding | 完成 / 实际运行 | 输入 token 中位数 | 输出 token 中位数 |
|---|---:|---:|---:|
| pi | 4 / 4 | 14,660 | 824 |
| Tau | 4 / 4 | 16,459 | 1,064 |
| Hermes | 7 / 8 | 75,352 | 991 |
| Codex | 6 / 8 | 92,639 | 1,226 |
| opencode | 7 / 8 | 131,649 | 1,186 |
| Claude Code | 5 / 6 | 260,170 | 1,197 |
| qwen-code | 7 / 8 | 288,808 | 1,367 |

来源：[S9，表 1、图 2，第 10 页](#src-s9)。

输入跨度接近 20 倍，而输出跨度约 1.7 倍。对该任务，差异主要体现在系统为完成工作携带和反复读取多少上下文，而不只是最终生成多少文本。[S9，§3.1](#src-s9)

但各行覆盖的模型组合不同，成本统计又以成功为条件。即便比较 token 而非美元，也不能完全排除模型、接口、成功子集等差异。因此，表格是测试配置的观察，不是一个不加条件的通用产品排行榜。

### 9.5 不连接 MCP 时，框架差异依然存在

论文还只比较 CLI 条件：所有运行都没有连接 MCP server，输入中位数仍从约 1.5 万到约 41.1 万不等。[S9，§3.2、表 2，第 12 页](#src-s9)

这说明，不能把所有输入负担都归因于“附加了 MCP”。系统提示、内置工具、额外上下文、轮数和失败后的行为，也需要考虑。

但作者同样承认：无 MCP client 的框架与其他框架在很多方面不同，不能把它们的优势全部归因于“没有 MCP 支持”这个单一特征。[S9，§3.2、§8](#src-s9)

**工程推论：轻量方案可能适合边界清楚的任务，但“越轻越好”不是这个实验建立的通用定律。**

### 9.6 MCP 与 CLI 的严格配对结果是不确定

对于同一框架、同一模型、两种条件都成功的 13 组配对，MCP 输入量除以 CLI 输入量的比值范围为 **0.43—29.06**，中位数为 **0.93**。作者将接口成本比较的结论明确写为 **inconclusive**。[S9，§4.1，第 13 页](#src-s9)

这不能解释成“MCP 没有影响”，也不能解释成“MCP 稳定更贵”。更可能需要进一步研究模型、任务和框架之间的交互，但该数据不足以给出统一方向。

还要区分两种数字：第 13 页表 3 是框架内部两个成功子集的中位数比值，子集中的模型可能不同；13 组严格配对才更接近同模型比较。不能静默混用这两种统计。

### 9.7 按需工具发现：机制值得测，但收益尚未被完全隔离

论文第 14—15 页比较了两种目录交付方式。一个框架通过少量入口按需发现工具；其他测试配置每轮携带完整目录。两组完成运行的输入中位数分别为 70,836 与 216,986，约相差 3.1 倍。[S9，§4.3、图 4、表 5](#src-s9)

但按需加载只出现在一个框架中。加载方式与该框架的其他设计混在一起，所以不能把全部差异都归因于“按需加载”。论文明确将它作为值得验证的候选机制。

这与 S4 的证据关系是：S4 提供机制和工程示例；S9 观察到相容现象，同时提醒因果识别不足。**对工程师而言，这是做消融实验的理由，不是照抄固定倍数的理由。**

### 9.8 讲义与论文描述的加载方式不同，不能自行填补原因

讲义第 7 页描述 Skill/MCP 条目按需加载；S9 则记录部分测试配置每轮发送完整工具目录。[S0，第 7 页](#src-s0) [S9，§4.3](#src-s9)

两份材料描述的行为确实不同。仅凭这些材料，不能确定差异全部来自版本、配置还是测量路径。

正确的保留方式是分别注明来源与测试设置，不自行替作者解释成同一种实现。

**工程建议：在自己的系统中检查实际发给模型的请求，尤其是工具定义与被注入内容，不要只根据产品名称推断行为。**

### 9.9 失败支出占比不是失败率

论文第 16 页表 6 报告：

| 条件 | 运行次数 | 失败次数 | 失败输入占比 | 失败估算费用占比 |
|---|---:|---:|---:|---:|
| CLI | 19 | 3 | 7.3% | 2.2% |
| MCP | 19 | 3 | 9.8% | 12.9% |
| 无 MCP client 的参照组 | 8 | 0 | 0.0% | 0.0% |

来源：[S9，§4.4、表 6，第 16 页](#src-s9)。

两组都是 3 次失败。费用占比不同，部分原因是失败发生在价格和消耗不同的配置上。不能说“MCP 失败率是 CLI 的近六倍”。

对实践更重要的提示是：失败不一定廉价结束。一个 Agent 可能反复尝试、消耗大量上下文，最终仍然没有交付。因此，成本分析必须包含失败轨迹。

论文后续重复实验中，CLI 与 MCP 各为 25/29 完成；无 MCP client 的组是 11/12，因此“从不失败”也只能描述主矩阵，不能覆盖全部数据。[S9，§8.1，第 20—21 页](#src-s9)

### 9.10 一个小模型的 139 倍差异，说明什么、不说明什么

论文报告，同一个 27B 模型在某轻量配置下用 17,416 输入 token 完成任务；另一配置使用 2,418,828 token、108 次工具调用才完成，约相差 139 倍。[S9，§3、第 11 页，§6](#src-s9)

它说明这个任务存在巨大的运行轨迹差异，小模型并非在所有配置中都做不到。

但它不说明模型永远不是瓶颈，也不说明任意复杂编码任务都能用同样的小模型完成。任务规模、补丁已经给定和框架设置都限制了外推范围。

### 9.11 记录实际行为，而不是期待行为

早期实验中，部分 Agent 虽然接了 MCP，却通过 Shell 或直接 HTTP 完成操作。添加“使用某接口”的提示没有充分改变这一现象；隔离替代路径的凭据，才让比较条件更接近设计目标。[S9，§7，第 19 页](#src-s9)

因此，评测中“配置了工具 A”和“实际通过工具 A 完成”必须分开记录。

这也与权限设计直接相连：要求模型走某个受控路径，不代表其他路径已经不存在。只要替代凭据与能力还在，文字要求就不是完整的边界。

### 9.12 验收器和实验装置也会犯错

论文披露了两次修正：一个验收条件依赖会在重置后变化的 issue 编号，导致原条件无法满足；另一个配置没有正确展开凭据，使服务认证失败。修正配置后，相应完成情况与失败费用占比发生变化。[S9，§2.6，第 6—7 页](#src-s9)

这意味着，一个看似可信的 Agent 分数可能测量的是实验装置错误。

但还要区分研究与生产：为了测接口效果，可以修复并重跑装置故障；生产系统的凭据故障和环境故障仍然损害用户体验，不能在业务成功率中静默删除。后者是本文的评测设计建议。

### 9.13 这篇论文最终怎样帮助工程决策

对于工具集合明确、重复执行、任务边界固定的工作，可以考虑更小的运行程序，甚至直接采用确定性脚本。对于开放式探索，通用 harness 的广度可能有价值。论文讨论了这个分工，但没有建立对所有任务的框架选择规则。[S9，§9.2](#src-s9)

真正要复用的是测量方法：固定任务与环境、记录真实请求和调用、核对产物、区分成功与失败支出、重复运行，并披露实验局限。

## 10. Hooks、权限与沙箱：把建议变成执行约束

### 10.1 自然语言 guardrail 与运行时控制不是一回事

S8 中的 guardrails 主要指负向文本约束；S6 中的 Hook 是生命周期事件上的处理逻辑。两者不能用同一个词掩盖保证强度的差别。

**文本规则影响模型提出什么。**

**执行层检查决定动作能否发生。**

“不要发布”是一条建议或指令；没有批准时服务端拒绝发布，是实际控制。[S8，实验设计](#src-s8) [S6，《PreToolUse decision control》](#src-s6)

### 10.2 Hook 可以在哪些边界工作

讲义第 38 页展示会话开始、用户输入、工具调用前、工具结果后和停止前等事件，并明确标出模型推理本身不是 Hook 事件。[S0，第 38 页](#src-s0)

因此，Hook 适合接入上下文准备、参数检查、自动格式化、测试、日志和终止检查，但不能被解释成能够读取并修正模型内部每一步想法的装置。

自动触发也不等于判断确定。命令处理器可以执行固定检查；如果处理器调用另一个模型做风险判断，触发时机由程序控制，判断仍然来自模型。

### 10.3 PreToolUse：动作发生前进行检查

上传的 S6 使用 `hookSpecificOutput` 返回执行前决定，并给出 `allow`、`deny`、`ask`、`defer` 等结果；具体选项和行为按该快照理解。[S6，《PreToolUse decision control》](#src-s6)

下面是拒绝结果的格式示例，不是一套完整安全实现：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "当前任务只允许读取，不允许修改该资源"
  }
}
```

关键在于：此时动作尚未发生，可以阻止实际执行。

原文还允许在执行前修改输入。由此得到的工程要求是，授权应针对最终执行的参数，而不是只批准一份随后又被改写的旧参数。

### 10.4 PostToolUse：事后反馈不等于撤销

S6 的执行后 Hook 可以补充反馈，或替换模型收到的工具输出。但工具已经运行，文件写入、命令执行或网络请求已经发生。名为 `block` 的事后字段，也不意味着自动撤回原操作。[S6，《PostToolUse decision control》](#src-s6)

必须区分：

| 机制 | 时机 | 能做什么 |
|---|---|---|
| 阻止 | 动作之前 | 不让副作用发生 |
| 发现 | 动作之后 | 告知异常或不合规结果 |
| 补偿 | 发现之后 | 用明确的新动作修复或抵消影响 |

补偿是否可行取决于外部系统，不能由会话回退自动保证。

### 10.5 Hook 自己坏了，策略是否还生效

上传的参考说明，命令 Hook 输出纯文本或无输出并以状态码 1 退出，可能只是非阻断错误；路径错误、不可执行和部分超时也可能不阻止原动作。不能把一般 Unix 的“非零失败”直接理解成“安全检查失败所以拒绝”。[S6，《Other exit codes》《Timeouts》](#src-s6)

该快照介绍了适用 `command`、`http` Hook 的 `onFailure: "block"`，并标明版本要求为 Claude Code v2.1.295 或以后。它不是所有事件、所有处理器或异步 Hook 的通用选项。[S6，《Block the action when a hook fails》](#src-s6)

**工程建议：** 策略测试除允许、拒绝外，还应包括脚本不存在、异常退出、超时、输出格式错误、事件未匹配。对必须执行的边界，检查失败时如何处理，应是显式设计。

一个“失败时打印警告”的程序，不等于一个“失败时拒绝动作”的门禁。

### 10.6 异步 Hook 不能承担同步门禁

原文明确说，异步 Hook 无法通过决定字段阻止已经发生的动作。因此，发布后的异步测试不是发布前审批；异步日志也不能替代执行前授权。[S6，《Run hooks in the background》](#src-s6)

另一方面，不必把所有检查都塞进同步路径。格式检查、测试和通知的时机应根据目标区分：什么必须先通过，什么可以稍后记录。这是工程取舍，不是“一律同步”或“一律异步”。

### 10.7 工具返回内容与日志是两个数据边界

S6 特别提醒，`updatedToolOutput` 只改变模型看到的内容；遥测和工具事件可能在 Hook 前就记录了原始输出。替换结构不符合要求时，原输出也可能仍被使用。[S6，《PostToolUse decision control》](#src-s6)

因此，“执行后把输出脱敏”并不证明敏感信息从未进入日志。

这与 S4 的隐私优化必须一起看：数据是否进入模型、是否留在执行环境、是否进入审计和遥测，需要分别验证。安全设计应覆盖完整数据流，而不是只看模型回复。

### 10.8 只读角色、最小权限与沙箱

讲义附录要求限制凭据范围、分开读写、对变更保留审批，并把工具返回内容视为不可信数据，而不是新的指令。[S0，第 49 页](#src-s0)

据此可以建立分层设计：文本说明边界，工具层检查请求，执行环境与服务权限限制实际影响。

如果一个只读工具被限制，但 Shell 仍持有写凭据，系统整体就不是只读。对任意命令的字符串黑名单也不足以定义完整权限。本文不提供这样的黑名单作为安全保证。

### 10.9 `confirm: true` 不证明人类批准

S5 中清理工具要求预览或显式确认参数，这说明一部分约束下沉到了工具层。但模型能够填写布尔值时，布尔值只能证明请求包含该字段，不能独立证明人类批准了本次动作。[S5，队列 Skill 示例](#src-s5)

**工程建议：** 真正需要人工批准的操作，应由可信服务验证批准记录，将其绑定到身份、目标资源、动作参数与有效范围。不要让模型同时提出动作并为自己生成授权证明。

### 10.10 “允许停止”与“已成功”应当分开

Stop 检查可以发现未完成项，但系统不能无限要求“继续直到成功”。缺少权限、环境异常或预算耗尽时，也要能够保留现场并终止。

下面是自建系统可以采用的状态语义，不是 Claude Code 官方枚举：

```text
VERIFIED          已通过约定验收
PARTIAL           有产物，但仍有未通过或未执行的检查
BLOCKED           缺少必要信息、权限或人工决策
BUDGET_EXHAUSTED  达到运行预算，保留现场
FAILED            明确失败，并记录原因
```

上传文档提供 `stop_hook_active` 等状态辅助避免停止检查的重复循环；具体处理应按事件契约设计。[S6，Stop / SubagentStop 相关章节](#src-s6)

### 10.11 验证必须对应实际代码状态

这是从外部验收原则得到的工程要求：记录测试结果时，应同时记录代码快照。测试通过后又改代码，旧结果不能证明新状态。

同样，会话检查点不等于所有副作用的回滚。S1 明确提醒，检查点只覆盖特定文件编辑工具产生的变更，不覆盖 Bash 或外部进程的全部改变，也不能替代 Git。[S1，检查点说明](#src-s1)

**恢复对话、恢复文件、恢复进程、恢复远端业务状态，是不同的恢复问题。**

## 11. 多 Agent 与 Plugin：什么时候拆，什么时候合

### 11.1 Skill 不等于子 Agent

Skill 主要让当前上下文获得另一套知识和流程；子 Agent 则形成另一个工作上下文。S1 建议把大量探索放进子 Agent，以减少主上下文噪声；S5 却描述把某些专业 Agent 合并成一个 Agent 加多个 Skills。[S1，子 Agent 与上下文管理章节](#src-s1) [S5，《Skills replace system prompts》](#src-s5)

这两种方法不是必然冲突，它们分别处理不同的信息组织问题。

### 11.2 Scott 的拆分：按阶段目标分工

S7 描述的实践为：

```text
Exploration → Plan / DAG → Worker → Critic → Promoter
                               ↑         │
                               └─修改反馈─┘
```

探索后形成显式任务依赖图，worker 逐节点实现，critic 检查与简化，必要时退回修改，promoter 负责把成果正确传达出去。[S7，《The cost advantage》](#src-s7)

作者还尝试用更强模型探索、规划和建立第一个实现模式，之后切换其他模型处理重复工作。这是个人工程经验，不是受控实验证明的最优路由。

有价值的思想是：不同阶段优化的目标不完全相同。实现者关注满足要求，审查者关注缺口和不必要复杂度，交付说明关注别人能否理解和接手。

### 11.3 Lawrence 的合并：专业知识不必等于独立 Agent

S5 描述把调度、遥测等 Agent 合并为一个 Agent 加多个 Skills。分离后的 Agent 只看得到传给自己的片段，可能缺少完整任务信息；各自系统提示中的建议又可能过于僵硬。[S5，《Skills replace system prompts》](#src-s5)

原文的例子是：长时间范围查询通常应该拆分，但把这一建议放在高优先级提示里，可能让系统在用户明确知道某个查询可安全执行时仍坚持拆分。改为按需指导之后，可以更灵活地处理具体情况。

这不意味着所有限制都应降级为指导。作者同时强调不可协商的要求应留在工具层。它区分的是**一般操作建议**与**必须执行的约束**。

### 11.4 一个可复用的拆分判断

以下是本文的工程判断表：

| 情况 | 优先考虑 | 原因 |
|---|---|---|
| 只是需要另一套领域知识，且必须共享当前任务细节 | 同一 Agent 加 Skill | 减少交接信息损失 |
| 调查需要大量独立资料，主流程只需结论和证据 | 子 Agent | 隔离探索上下文 |
| 需要以不同目标检查已有成果 | 新上下文 reviewer | 把验收标准与实现叙述分开 |
| 步骤已经确定、重复且可测试 | 脚本或普通工作流 | 不必每次增加一次模型决策 |
| 多项可独立实现且可安全合并 | 隔离工作区的并行任务 | 在处理共享资源后再利用并行性 |

真正问题是“是否需要独立上下文”，不是“能否给它起一个岗位名称”。

### 11.5 子 Agent 节省主上下文，不保证节省总成本

每个子 Agent 都需要启动上下文、读取信息和模型调用。主对话变短，不意味着系统总输入变少。S9 的统一代理计量正是为了避免漏掉委派成本。[S9，§2.5](#src-s9)

交接也应带事实、位置、未解决项，而不只返回“已找到原因”。如果原始证据丢失，主 Agent 很难判断结论是否适用。

### 11.6 reviewer 也可能把任务扩大

S1 提醒，要求 reviewer 找问题，它往往就会给出一些问题；追逐所有建议会形成过度工程化。[S1，《Add an adversarial review step》](#src-s1)

这与 S8 的“提示本身就是干预”直接相连。不要要求“至少找出五个问题”，而应要求指出影响正确性或明确需求的缺口，并提供位置、触发条件与影响；没有实质问题时允许没有发现。

新上下文能提供另一条审查路径，但仍是模型判断，不能代替测试和实际系统状态。

### 11.7 并行工作树不是完整隔离

S1 讨论并行会话与分散任务。对于实现层，本文建议使用独立工作树、明确文件责任与合并检查。[S1，并行会话相关章节](#src-s1)

但工作树只处理部分文件状态。测试数据库、端口、外部服务、缓存和凭据可能仍然共享。若多个 Agent 同时修改同一外部环境，文件不冲突也不代表行为不冲突。

这是工程推论，不能把“每个 Agent 一个目录”当作充分的生产隔离方案。

### 11.8 Plugin 把一套工作方式变成团队资产

讲义第 39—41 页把 Plugin 定位为可安装的打包层，包含 Skills、Hooks、Agent 配置及 MCP 配置，并提供版本、命名空间和团队共享。[S0，第 39—41 页](#src-s0)

S7 则展示了跨工具复用 Skills、`AGENTS.md` 和脚本的个人实践。对工程师而言，关键不是某个界面，而是已经验证的工作方式能否离开聊天记录，进入可维护的项目资产。[S7，《There are new truths》《Breaking down the harness》](#src-s7)

打包不会自动证明安全或有效。版本化可以帮助复现和回退，但仍要评测整套安装后的实际行为。

## 12. 完整开发案例：队列未知计数被当成零

> 本章是根据 S5 队列语义改编的教学案例，不是原作者报告的真实缺陷。流程用于串联前面的机制，不声称已在某个实际仓库运行。

### 12.1 任务应该如何提出

任务：队列状态页面把某个 broker 的未知计数显示为零，进而错误显示“没有积压”。要求修复、补充测试、准备交付说明，但不执行生产清理或发布。

这里同时有四种信息：需要改变的行为、内部业务语义、禁止的副作用，以及验收方式。只说“把页面做得更健壮”，会把大量决策留给模型猜测。

S5 提供的真实语义是，`null` 计数不能直接解释成零，多 broker 的结果需要结合上下文理解。下面把它转成一份教学验收表。[S5，队列 Skill 示例](#src-s5)

假设两个计数已经被标准化为**同一订阅、同一快照口径，且对应不重叠消息集合**：

| 来源 A | 来源 B | 应有解释 |
|---:|---:|---|
| 0 | 0 | 已知没有积压 |
| 0 | 未知 | 无法确认没有积压 |
| 5 | 未知 | 已知存在积压，总量未知 |
| 5 | 3 | 已知总量为 8 |

这些假设不能在真实项目中省略。若两个来源时间点、范围或是否重复计数不明确，应先确认，而不是直接套用加法。

### 12.2 探索应围绕缺陷路径

先取得项目导航与测试入口，再沿数据流调查：

```text
broker 数据
→ 标准化快照
→ 汇总函数
→ API 响应
→ 页面渲染
```

可能找到这样的错误代码：

```python
# 教学反例：将未知与零合并，不能据此判断“没有积压”。
total = (broker_a_count or 0) + (broker_b_count or 0)
no_backlog = total == 0
```

Agent 不必先读取整个仓库，但必须确认错误出现在哪一层。若后端响应已经丢失未知状态，只改页面文字不能完整修复；若后端正确而前端默认补零，只改汇总函数也不够。

这一步使用讲义的按需读取与工具反馈，不是无限探索。

### 12.3 先建立现状基线

Simon 的《First run the tests》建议在已有项目中先运行测试，借此发现测试入口、了解项目已有行为并建立后续验证方式。[W2](#src-w2)

本案例中，先记录现有相关测试能否运行，以及哪些失败在修改前已经存在。环境依赖未就绪、测试本身失败和新增补丁造成的回归，需要分开。

“先运行测试”不是要求任何项目都先跑最昂贵的全量测试；具体选择相关检查还是全量检查，是本文建议按任务规模与环境成本决定的工程取舍。

### 12.4 Red / green 的关键是证明测试看见了问题

Simon 的 Red/green TDD 要求先写测试并确认失败，再修改实现使其通过。省掉确认失败，可能得到一个旧实现本来就能通过的测试。[W3](#src-w3)

在本案例中，红灯应当来自“未知值被误认为零”的行为，而不是依赖没装好或测试语法错误。绿灯则证明候选修改通过了相同检查。

**工程推论：红灯验证测试能看见目标缺陷，绿灯验证候选修复通过该检查；两者仍不等于全部业务需求已被证明。**

### 12.5 计划的作用是消除关键不确定性

S1 推荐先探索、再计划、再实现，但也指出计划会增加开销。任务小、方案清楚时可以直接做；跨文件、代码不熟悉或方案不确定时，计划更有价值。[S1，《Explore first, then plan, then code》](#src-s1)

本案例的计划应说明：未知状态怎样表示、哪些层要保留它、如何避免破坏既有接口、怎样验证。

没有必要生成空泛的“分析—开发—测试—上线”清单。计划应当包含实际依赖与决策，不是给简单工作增加仪式。

### 12.6 小步实现，及时获得外部反馈

先修改已经定位的行为，再运行目标测试。失败后区分实现错误、需求理解错误和环境问题，而不是立即扩大重构或添加更多 Agent。

例如，候选修复可能使汇总函数正确返回未知，但 API schema 不允许未知字段。这个失败反馈说明下一步需要检查接口契约，不是“模型还不够努力”。

文件编辑应针对已读取状态；发生并行变化时先重新读取。验证结果则应绑定修改后的工作树快照。

### 12.7 自动测试之外，运行真实应用路径

Simon 的《Agentic manual testing》指出，测试通过仍可能遗漏启动错误、页面元素或真实交互。可以让 Agent 实际运行应用、调用接口、观察浏览器，再把发现的问题补进永久测试。[W4](#src-w4)

本案例至少应确认：后端返回的未知状态没有在序列化时丢失，页面不会把它再渲染成零，已确认正值但另一边未知时也不会显示“没有积压”。

这里的作用分工是：单元测试验证局部规则，实际运行验证这些规则是否被正确连接到用户界面。

### 12.8 reviewer 检查需求，不是欣赏实现

给新上下文 reviewer 提供验收表、diff 和必要代码位置，要求核对：未知状态是否保留，是否仍有补零路径，是否修改无关模块，是否添加未经要求的清理动作。

不要先给出一长段“为什么实现已经正确”的说明，也不要要求一定找到若干问题。审查意见应该包含位置、触发条件和实际影响。[S1，独立审查及过度工程化警告](#src-s1)

如果 reviewer 建议引入一个泛化框架，仍要判断这是否为当前验收所必需。另一位 Agent 的建议不是自动扩大范围的理由。

### 12.9 门禁依据代码状态与验证证据

讲义的发布例子把 Skill、MCP、Hook、Plugin 放进同一流程：操作指南、外部动作、检查与分发各有位置。[S0，第 32 页](#src-s0)

本案例只允许准备材料，不能因为本地测试通过就发布生产。准备发布与执行发布是不同动作，需要不同授权。

自建验证记录至少应包括代码快照、实际执行的检查、结果、日志位置及未执行项。这是工程建议，不是原生产品 schema。

### 12.10 交付的是修改与证据

一个合格的交付说明可以是：

```text
行为变化：未知计数不再转换为零；总量未知时不会报告“没有积压”。
修改范围：列出实际修改文件和原因。
验证：逐项列出实际运行的命令、结果及对应代码状态。
运行检查：接口与页面分别检查了什么。
未完成项：明确未执行的集成、部署或生产验证。
权限边界：未执行清理，未发布生产。
```

这里是交付模板，不是本次已执行结果。不要用模板中的“已通过”替代真实运行。

S9 的外部状态验收、S7 的 promoter 阶段，以及 Simon 对 PR 说明也需人工审查的提醒，在这一步汇合：**任务结束时应让别人能够核对和接手，而不是只留下模型的自信总结。** [S9，§2.2](#src-s9) [S7](#src-s7) [W6](#src-w6)

## 13. 第二个案例：重试、重复审计与状态恢复

> 本章保留第一轮讲解中的“采纳建议”接口案例。它是教学场景，不是对某个真实业务系统或数据库产品的实现断言。

### 13.1 问题：客户端超时后重试，出现重复审计记录

任务要求修复重复处理，同时保留权限校验，不顺带重构其他模块。

模型可能先提出：查询是否已经采纳，若已采纳就直接返回。

这个想法能处理某些顺序重试，却未必解决并发竞争。两个请求可能发生这样的时序：

```text
请求 A：查询，尚未处理
请求 B：查询，尚未处理
请求 A：写入业务效果与审计记录
请求 B：再次写入业务效果与审计记录
```

这是一种逻辑上可能的教学时序，是否真实发生需要检查具体实现、事务与数据约束。关键是：不能只因为顺序测试通过，就声称并发安全。

### 13.2 先确认“同一次操作”是什么意思

修复之前，Agent 应确认业务标识：哪些请求属于同一次操作，哪些属于合法的新操作；同一标识携带不同参数如何处理；用户或资源是否参与作用域。

否则，简单去重可能把合法操作合并，或者把不同用户的请求错误关联。

这里的教训是：**幂等机制不能替代业务语义定义。** 模型可以提出候选，但不应该擅自决定未给出的产品契约。

### 13.3 超时是观测，不一定是业务失败

写入超时至少可能表示：没有执行；执行中；执行完成但响应丢失。

如果工具只返回“失败”，Agent 可能盲目重试；如果返回“状态未知，需要查询操作结果”，后续轨迹就可能不同。

这连接到第 2 章的部分观测和第 6 章的工具契约：真实世界状态与一次工具输出不是同一个东西。

### 13.4 应当验证哪些路径

下面是工程验收设计示例，具体预期必须由项目确认：

| 路径 | 需要检查的问题 |
|---|---|
| 顺序重试 | 同一次请求是否重复产生业务效果 |
| 并发相同请求 | 两个请求同时进入是否绕过检查 |
| 写入完成、响应丢失 | 客户端重试是否重复写入 |
| 相同标识、不同参数 | 是否明确拒绝或按既定契约处理 |
| 不同用户 / 资源 | 去重范围是否正确隔离 |
| 未授权请求 | 原有权限检查是否仍然生效 |
| 业务写入与审计 | 两者是否可能产生不一致的部分完成 |

请求标识、唯一性约束、事务边界或操作状态表，都是可调查的机制方向；不能在没有实现信息时断言其中某一种一定正确。

### 13.5 为什么这个案例也是 harness 设计课

Coding Agent 自己也会面临类似问题：创建 PR 的请求超时，是否已经创建；写文件之后会话断开，文件是否已变；长测试进程没有响应，是否仍在运行。

因此，恢复机制需要回答实际状态，而不只是重新加载对话。

**工程建议：** 保存动作标识和产物位置；能查询状态时先查询；具有副作用的恢复按操作契约处理；避免把所有异常都转换成无条件重试。

这与前文“验证绑定状态”“停止不等于成功”“会话检查点不等于外部回滚”是同一个系统问题。

### 13.6 两个案例的共同原理

队列案例中，未知计数不能自动变成零；重试案例中，未知执行状态不能自动变成未执行。

**共同错误是把不确定性压成一个方便处理、却未经证实的确定值。**

好的 Agent 系统既要帮助模型减少不确定性，也要在尚未消除时允许它被准确表达，而不是强迫模型或工具生成一个看似完整的答案。

## 14. 评测与可观测性：怎样知道系统真的变好了

### 14.1 评测单位应该是完整任务

S8 评测规则干预后的任务通过率；S9 评测多步操作留下的实际产物。两者共同说明，不能只看最终回答是否流畅、某一次工具参数是否正确。[S8，§5—6](#src-s8) [S9，§2](#src-s9)

下面是面向自建系统的工程建议：固定一批有验收条件的任务，保存代码起点、依赖环境、允许动作、权限和检查方式。将用于调试配置的任务与最终评估任务区分开，避免只在熟悉样本上反复优化。

### 14.2 比较配置时，先明确改变了哪个变量

| 对照 | 要检验的问题 | 需要尽量固定 |
|---|---|---|
| 无规则 vs 简短项目事实 | 补充知识是否减少探索与错误 | 模型、任务、工具、环境 |
| 基线规则 vs 新规则组合 | 干预是否改善总体轨迹 | 模型、验收与运行预算 |
| 全量工具说明 vs 按需发现 | 索引策略是否值得 | 同一工具集合与权限 |
| 每步模型调用 vs 代码组合 | 控制流下沉是否省成本 | 相同任务语义与结果核验 |
| 单 Agent vs 新上下文审查 | 额外检查是否减少漏项 | 验收标准与完成判定 |

这张表是实验设计建议，不表示这些对照已经全部在参考论文中完成。

尤其不要同时改模型、提示、工具目录与任务集，再把收益全部归因于其中一个组件。

### 14.3 重复运行和配对比较为何重要

S8 讨论基线波动、筛选任务与多重比较；S9 的重复实验观察到，同一配置的 token 消耗也有明显变化。一次运行不足以稳定判断效果。[S8，第 6、9 页](#src-s8) [S9，§8.1](#src-s9)

工程上应保留相同任务在不同配置下的配对结果，并按需要重复运行。重复次数取决于预算、任务差异和希望识别的效应大小，不应把某个固定次数当作普遍答案。

还要区分统计结论：没有识别到差异，不等于证明等价；某一条规则表现很好，也不等于对整套规则都具有相同贡献。

### 14.4 除结果外，还需要记录哪些上下文

自建评测记录建议包含：模型与 harness 版本、提示和 Skill 版本、记忆快照、仓库起点、权限配置、实际发出的工具定义、真实调用、错误类别、工作树变化、产物和验收结果。

这些是外部可观察记录。评测不需要把模型不可见的内部推理当作可靠日志，也不应把一段自述的思考过程当成执行证据。

若完整请求涉及敏感代码或数据，记录策略本身也需要授权、最小化和访问控制。不要为了“可观测性”无条件保存全部敏感上下文。

### 14.5 三类特别容易被最终回答评分掩盖的失败

**重复循环。** 相同错误发生后，仍然重复相同调用或相同修改，没有获得新信息。

**虚假完成。** 最终总结声称完成，实际文件、PR 或测试状态不满足条件。

**越界解决。** 通过跳过测试、削弱断言、修改无关模块或改变需求，得到一个表面成功。

这是本文的工程诊断分类。S8 的指令干扰与 S9 的外部验收实例说明，仅看最终自然语言输出容易漏掉关键问题。

### 14.6 成本至少应看三种口径

S9 将成功运行成本、完成率与失败支出分开报告。这种拆分适合解释实验，但业务系统还可以补充整体投入产出指标。[S9，§2.8、§4.4](#src-s9)

以下是本文建议的指标，不是论文原始定义：

$$
\text{每个有效完成的模型与工具成本} =
\frac{\text{所有尝试的模型和工具总成本}}{\text{通过真实验收的任务数}}
$$

再把人工与返工纳入业务视角：

$$
\text{每个有效交付的总成本} =
\frac{\text{模型成本}+\text{工具成本}+\text{人工审查成本}+\text{返工成本}}{\text{通过真实验收的任务数}}
$$

分母为零时应报告“无有效完成”及已消耗成本，不生成一个误导性的正常平均值。

这类汇总需要统一任务定义与预算，也应报告各任务类型结果，避免用大量简单任务掩盖复杂任务失败。

### 14.7 不要只追求 token 更少

还应观察延迟、人工介入、回归、未授权动作和交付可维护性。一个配置虽然省输入，却让工程师花更多时间调查错误，未必是进步。

同样，更多模型回合也未必浪费。一次额外检查可能避免昂贵回归。关键是多出的步骤是否增加了决策信息或验证强度，而不是单纯减少回合数。

这是从两篇论文与 S1、W5 综合得到的工程判断。

### 14.8 区分模型问题、实验装置问题与生产可用性问题

研究接口效果时，错误凭据可能是需要修复重跑的实验装置故障；面向用户的生产成功率则应记录这次任务确实受阻。

建议同时维护：能力评测结果、基础设施故障、端到端用户任务结果。不要静默删除环境失败，也不要把所有环境失败都算作模型推理能力不足。

这个区分可以防止两种错误决策：为了修配置错误而换模型；或者为了让分数好看而忽略真实运行故障。

## 15. 人的角色与经验复用：从一次成功到长期能力

### 15.1 代码生成变便宜，好软件仍然有成本

Simon 在《Writing code is cheap now》中区分产出代码与产出好代码：后者还要解决正确问题、获得运行证据、处理错误、保持简单、具备回归测试并满足相应质量要求。[W5](#src-w5)

这与 S9 的成本分析构成互补。模型输入费用是一部分，需求判断、检查和维护也是真实工作。

因此，工程师的作用不是把所有键盘输入交给 Agent 后退出，而是选择任务、明确边界、评估取舍，并为交付质量负责。

### 15.2 不能把未经审查的成本转移给同事

Simon 的反模式文章提醒，未经本人检查就把大量 Agent 代码和自动生成的 PR 描述交给同事，是把真正工作转移给别人。代码、说明和运行证据都需要审查。[W6](#src-w6)

它与 S7 的 promoter 阶段相连：交付沟通不只是包装，而是让他人理解变更目标、影响范围、验证方式和剩余风险。

**工程推论：衡量 Agent 生产力时，也要看它是否降低团队协作成本，而不只是增加提交行数。**

### 15.3 核心代码失去理解，会形成认知债务

Simon 将失去对 Agent 代码的理解称为 cognitive debt：核心系统变成黑箱后，人就难以继续判断设计和故障，长期会拖慢进展。[W8](#src-w8)

你不必逐字阅读所有机械生成内容，但应理解关键状态、边界和失败模式。队列案例中需要知道未知状态怎样传递；重试案例中需要知道同一次操作怎样定义，以及响应丢失时怎样恢复。

这与 Agent memory 是两件互补的事情：Agent 需要保留决策信息，人也需要保留系统理解。

### 15.4 用讲解帮助理解，但仍然锚定真实代码

Simon 的 linear walkthrough 方法让 Agent 按结构解释代码，并使用真实提取的代码片段，而不是手动重写片段。Showboat 可以记录命令和执行输出，降低说明与实际代码不一致的风险。[W7](#src-w7)

对复杂算法，还可以要求交互式解释。W8 的例子用逐步可见的动画帮助理解布局算法；重点在于让人能够观察规则怎样作用，不只是阅读专业术语。

这些解释不是正确性证明，但有助于发现人是否真的理解交付物，以及说明是否与实现相符。

### 15.5 积累运行过的实现，而不是只积累提示词

W9 主张收集带证据的工作示例：知道某事理论上可行，与手中有一个运行过的实现不同；多个已有实现还可以成为 Agent 组合新功能的输入。[W9](#src-w9)

S7 的实践也包括让模型帮助写出脚本，再通过可编程接口驱动自己的应用；S4 则展示保存成功函数和状态；S3 负责将这些实现包装为可发现、可复用的能力。[S7，《A product harness connection》](#src-s7) [S4，持久化与 Skills 部分](#src-s4) [S3](#src-s3)

这里值得积累的资产包括：回归测试、可运行脚本、带适用条件的项目事实、操作指南、真实示例与交付模板。

### 15.6 一个任务后的经验应该存到哪里

下面是工程决策表：

| 新发现 | 优先保存为 |
|---|---|
| 明确的产品行为缺陷 | 回归测试 |
| 可重复的确定性处理 | 脚本或函数 |
| 模型不易推断的项目事实 | 项目说明或范围相关规则 |
| 多步骤、带条件的领域流程 | Skill |
| 当前任务尚未完成的状态 | 交接记录 |
| 必须被执行的安全边界 | 权限、服务端校验或受控策略 |
| 一次偶然成功、未验证的猜测 | 待验证笔记，而非永久规范 |

不要把每次复盘都变成“再追加十条系统提示”。S8 已经说明规则存在组合效应；更多永久内容可能带来新的干扰。

### 15.7 第二个闭环：系统改进也需要验证

```text
任务完成
→ 区分错误类型与真正有用的经验
→ 提出测试、脚本、规则或 Skill 变更
→ 在独立任务上验证
→ 版本化发布
→ 观察回归
→ 必要时撤回
```

这个闭环是对材料的工程综合，不是模型参数自动学习。它使系统能够积累外部能力，同时保留回滚与审查。

S8 的讨论还提醒，技能库增长可能造成检索和路由退化；它引用了相关研究，但这不是该文四组实验直接完成的技能库实验。[S8，§7，第 8 页](#src-s8)

因此，经验治理不仅包括新增，也包括修订、限制适用范围与退休。

### 15.8 对 LLM 开发工程师的能力转变

从“让模型回答得更好”转向“设计让模型能发现和纠正错误的环境”；从“写出越来越多提示词”转向“明确知识、执行与控制边界”；从“看一次演示很成功”转向“用任务集和轨迹证明系统改变”。

最终值得培养的能力，是判断：哪一部分需要模型推理，哪一部分应该成为普通代码，哪一部分必须由授权与验证系统承担。

## 16. 总复盘：设计判断、误区与实践模板

### 16.1 把全部材料放回同一个工作过程

| 阶段 | 主要材料 | 关键产物或约束 |
|---|---|---|
| 明确任务 | S1、W1、W5 | 目标、范围、验收条件 |
| 组织信息 | S0、S1、S3、S5 | 本轮必要上下文 |
| 获取与执行 | S0、S4、S5 | 清楚的工具结果与可追溯产物 |
| 限制动作 | S0、S6 | 真实权限与执行前检查 |
| 迭代修复 | S1、W2、W3、W4 | 基线、红绿验证、实际运行反馈 |
| 审查与协作 | S1、S5、S7 | 必要的信息隔离与检查标准 |
| 验收交付 | S9、S7、W6 | 产物状态与验证证据 |
| 积累能力 | S3、S4、S7、S8、W9 | 经过评测的测试、脚本、规则与 Skills |

这个表是资料间的连接图，不表示每份材料都对整条流程做过实验验证。

### 16.2 十个容易混淆的判断

| 容易混淆的说法 | 应当保留的区别 |
|---|---|
| 会写代码就是可靠 Coding Agent | 还需要执行、反馈、边界与验收 |
| Agent 停止就是完成 | 模型停止、运行结束与任务通过是三件事 |
| 仓库没整体上传，所以代码不会离开本机 | 按需读取的片段仍可能进入模型请求 |
| 外部记忆就是模型训练 | 保存文件与更新模型参数不同 |
| 规则越多越好，或越少越好 | 规则内容、任务、组合与成本都需要测量 |
| 负向句式已经被证明普遍最好 | 论文有样本、阈值、内容混淆和统计限制 |
| MCP 天生要求完整目录常驻 | 连接协议与工具暴露策略不同 |
| 代码执行自动保证安全 | 仍需治理数据、网络、凭据、日志与副作用 |
| 新增 reviewer 就获得独立真相 | 新上下文仍然是模型判断，不能替代证据 |
| 子 Agent 多一定更便宜、更强 | 信息隔离、交接损失与总成本要一起衡量 |

### 16.3 开始一个任务的契约模板

以下模板为本文工程建议，不是原文逐字提示词。不要把占位内容当作实际项目事实。

```text
任务目标：
需要改变的具体行为，以及不需要改变的内容。

已知资料：
相关文件、报错、接口说明、业务语义与已有复现信息。

需要确认：
哪些定义、接口口径或业务行为尚不清楚。

执行边界：
允许修改的范围；禁止的外部动作；需要人工批准的决策。

验收：
能够证明原问题存在与修复有效的检查；必要的兼容性检查。

工作方式：
先建立必要基线；存在关键不确定性时先调查或提问。
不要为了完成而削弱测试、改变需求或扩大无关范围。

交付：
实际改动、验证命令与结果、对应代码状态、未验证项和剩余风险。
```

模板的价值在于分清目标、信息缺口、权限与验收，而不是指挥每一次搜索。

### 16.4 新上下文 reviewer 模板

```text
请检查当前 diff 是否满足给定验收条件。

只报告影响正确性、明确需求或已声明边界的问题。
每条问题给出文件位置、触发条件、影响和验证方式。
没有实质问题时可以明确说明没有发现。
不要为了凑数量提出抽象层、风格偏好或不可能场景。

实现说明仅作参考；以实际代码、测试和需求为依据。
```

这个模板对应 S1 对独立审查和过度工程化的提醒，也吸收 S8 对指令干预的谨慎态度。

### 16.5 长任务交接模板

```text
当前目标 / 范围：
环境和代码状态：
已确认事实及来源：
已排除方案及原因：
当前已改动内容：
实际验证记录：
仍在运行的任务及标识：
状态未知的外部动作：
未解决问题：
下一步：
```

恢复后先核对会变化的状态，不把交接文件当作实时事实。

### 16.6 交付审查的最低问题

交付前应能回答：现在的代码是什么状态；原问题由什么测试或运行检查复现；修复后相同检查结果如何；有没有未执行项；有没有修改无关范围；有没有未授权副作用；别人能否凭现有记录核对结论。

这不是要求为每个小改动生成巨型报告，而是避免用流畅文字替代关键证据。

### 16.7 最终认识

讲义解释如何让模型持续工作；S1 与 Simon 的模式解释如何组织软件开发反馈；S3—S5 解释知识和工具怎样按需组合；S6 解释实际控制点；S7 解释如何沉淀与复用工作方式；S8、S9 则提醒这些设计必须接受实验检验。

**Coding Agent 工程的核心，是把“它应该会做”改造成：它看得到必要事实，做得到正确动作，被限制在适当范围内，并且做完之后能够拿出证据。**

## 附录 A：讲义中的 MCP 架构与 Gateway

本附录保留讲义第 45—52 页的可选内容。它是材料快照说明，不是对所有现有 MCP server、client 或协议版本的兼容性认证。

### A.1 Host、Client、Server 的角色

讲义将用户面对的应用称为 Host，例如 Claude Code；Host 内的 MCP client 与外部 MCP server 交互；server 暴露业务系统能力。外部系统可以是代码托管、数据库、消息服务或本地服务。[S0，第 45—46 页](#src-s0)

这个划分解决的是连接与职责，不自动决定模型能看到多少工具定义，也不自动定义业务权限。正文第 8 章的三轴区分仍然适用。

### A.2 三类基本元素

| 元素 | 讲义中的含义 | 示例用途 |
|---|---|---|
| Tools | 可调用操作 | 获取诊断信息、创建 issue |
| Resources | 可读取数据 | issue 内容、数据库 schema |
| Prompts | 服务端提供的可复用提示模板 | 组织的 issue 分诊流程 |

讲义用 issue 分诊展示三者配合：Prompt 提供流程，Resource 提供事件内容，Tool 取得当前诊断信息。[S0，第 47—48 页](#src-s0)

这与 Skill 有部分功能邻近，但不能因此把两者视为同一个部署机制。本文只保留讲义对三类元素的介绍，不扩展未展示的协议实现细节。

### A.3 为什么需要 Gateway

讲义将 Gateway 描述为 client 与多个 server 之间的控制层，从 client 看可以像另一个 MCP server，统一处理认证、策略、日志、路由和限流。[S0，第 50 页](#src-s0)

| 作用 | 讲义中的解释 |
|---|---|
| 聚合 | 统一命名空间与能力目录 |
| 路由 | 将请求送往负责的 server |
| 执行策略 | 决定谁能连接、哪些工具可见、哪些需要审批 |
| 身份代理 | 客户端认证，后端凭据由受控层持有 |
| 观测 | 记录身份、工具、决策、延迟、结果与成本 |
| 扩展性 | 负载均衡、重试、熔断、目录缓存与配额 |

来源：[S0，第 51 页](#src-s0)。

当用户、Agent、server、凭据和治理要求较多时，统一层可能有价值。但讲义也指出，它会集中信任：过宽凭据、丢失最终用户身份、名称冲突、日志泄密和单点故障都是需要处理的问题。

**工程推论：Gateway 不是自动安全的黑盒。** 权限范围与最终用户身份能否沿请求传递，仍然决定系统的实际边界。

### A.4 讲义提及的 2026-07-28 协议快照

第 52 页按该版规范描述无状态核心、用于路由的 `Mcp-Method` 头、可缓存的列表，以及将长任务和 MCP Apps 作为扩展的组织方式。[S0，第 52 页](#src-s0)

本文保留这段版本化描述，不由此声称所有安装中的工具都已经实现相同能力。

另一个需要独立理解的工程边界是：协议请求无状态，不代表业务状态不存在，更不代表业务动作天然可安全重试。创建 PR、写入记录和发送消息的副作用，仍然需要按各自业务契约处理。这是正文第 13 章的推论，不是协议快照直接保证的性质。

## 附录 B：术语表

下表整理本文使用方式。部分定义是教学概括，不用于替代各产品或协议的完整术语规范。

| 术语 | 本文中的含义 | 容易混淆的边界 |
|---|---|---|
| Coding Agent | 使用模型与工具循环开展软件工作的系统 | 不等于单次代码生成 |
| Harness / Scaffolding | 组织上下文、驱动模型、执行工具、管理状态与边界的外围系统 | 不是另一个基础模型 |
| Agentic loop | 模型提出动作、执行工具、返回结果、继续决策的循环 | 循环运行不保证任务正确 |
| Context | 本轮实际进入模型的信息 | 不等于外部保存的全部文件 |
| Working memory | 当前上下文中的工作信息 | 不能代替持久状态 |
| Persistent memory | 可在后续运行重新读取的外部知识 | 不等于模型权重更新 |
| Compaction | 对旧轨迹压缩并保留必要信息 | 摘要可能丢失事实与决策依据 |
| Progressive disclosure | 先提供索引，再按需提供细节 | 不保证索引或路由没有成本 |
| Tool schema | 操作名称、说明和参数结构 | 不一定包含完整业务语义 |
| Skill | 按需加载的知识、流程、脚本与资源集合 | 不是底层权限系统 |
| MCP | 连接外部能力的协议 | 不等于全量工具定义必须常驻 |
| Code execution with MCP | 用执行环境中的代码发现、调用与组合 MCP 工具 | 仍需控制内部副作用 |
| Hook | 生命周期事件上的处理入口 | 自动触发不等于判断必然正确 |
| Guardrail | 本文会区分文本约束与运行时控制 | 两者保证强度不同 |
| Sandbox | 限制执行能力与影响范围的环境边界 | 一个角色名称或目录不是完整沙箱 |
| Subagent | 独立上下文中的委派工作单元 | 主上下文变短不等于总成本变小 |
| Plugin | 打包和分发扩展的单元 | 可安装不等于安全有效 |
| Artifact | 可保留、检查的文件或执行产物 | 模型口头声明不是实际产物 |
| Acceptance / Verifier | 对交付结果执行约定检查 | 验收器本身也需要测试 |
| Red / green TDD | 先确认目标测试失败，再使它通过 | 红灯必须对应目标问题 |
| Ablation | 移除组件观察结果变化 | 得到的是当前条件下的贡献 |
| Context priming | S8 对规则存在效应提出的解释 | 不是完全隔离并证明的因果机制 |
| PBRS | S8 借用的奖励塑形解释视角 | 不证明自然语言规则满足 RL 定理 |
| Cognitive debt | 人失去对 Agent 代码关键机制的理解 | 更多代码不等于更强系统掌控力 |
