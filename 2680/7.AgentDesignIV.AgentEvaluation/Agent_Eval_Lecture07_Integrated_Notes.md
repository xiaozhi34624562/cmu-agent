## 1. 整节课的主线：从工作到测量，再到部署判断

### 1.1 这些材料不是平行清单，而是一条研究链

SWE-bench、AgentBench 和 τ-bench 首先解决“怎样把 Agent 完成工作变成实验”。ABC 和 NIST 随后追问：任务与评分器有没有漏洞？Agent Reliability 进一步追问：通过一次是否意味着可依赖？《AI Agents That Matter》追问：效果提高来自有效机制，还是仅仅投入更多计算？METR 与 Headlong 把问题推进到长任务和持续运行。Dapper、AgentOps、Firecracker 与 ActPlane 则提供追踪、隔离和约束执行的工程基础。

这是一条概念上的联系，不表示这些论文按这一顺序发表，或后者都直接以所有前作为实验对象。

| 核心问题 | 讲义位置 | 主要参考材料 | 最重要的连接 |
|---|---|---|---|
| 评估完整系统还是内部组件？ | p.6、p.11、p.26 | AgentBench、SWE-bench、AgentOps | 分数依赖执行架构；组件指标不能代替最终交付 |
| 怎样把工作包装成任务？ | p.12–23 | SWE-bench、τ-bench、AgentBench | 输入之外，还需要初始状态、工具、政策与验收条件 |
| 评分为什么可能失真？ | p.25–26、p.31 | ABC、NIST、SWE-bench 审计 | 真实任务不自动保证有效测量；裁判自身需要测试 |
| 一次成功是否可靠？ | p.10、p.31、p.34 | τ-bench、Agent Reliability | 找到一次正确解与持续正确交付是不同目标 |
| 长任务意味着什么？ | p.27–34 | METR、Headlong | 人类任务耗时、Agent 运行耗时、长期服务时间不可混淆 |
| 为什么多维评价会改变架构选择？ | p.10、p.31、p.35 | AI Agents That Matter | 相同预算下的简单基线，是判断复杂机制价值的前提 |
| 如何从测量走到可控生产？ | p.6、p.31、p.34 | Dapper、AgentOps、Firecracker、ActPlane | 观察、隔离、约束和恢复是可信评估的基础设施 |

来源：讲义结构与阅读清单。[S00，PDF p.6–35](#source-s00) [S15](#source-s15)

### 1.2 一个“涨了八分”的报告，可能混淆三个系统

**教学形式化：**

$$
O=\operatorname{Run}(A,T,E,\xi)
$$

$$
Y=G(O,T)
$$

$$
D=\operatorname{Decision}(Y,C,L,R,\mathcal{D}_{\text{business}})
$$

其中，$A$ 是 Agent 配置，$T$ 是任务，$E$ 是环境，$\xi$ 是随机因素，$O$ 是运行产物与轨迹，$G$ 是裁判，$C$ 是成本，$L$ 是时延，$R$ 是风险，$\mathcal{D}_{\text{business}}$ 是业务任务分布。

第一层是**被测系统**，第二层是**测量系统**，第三层是**部署决策系统**。

新版本得分从 80 提升到 88，可能是 Agent 更强了，也可能是裁判更宽松、测试集更容易、工具能访问的信息更多，或预算提高了。只看最终分数无法区分这些解释。

由此得到一条工程纪律：**任务集、Agent 配置、环境与评分器要分别版本化。**讲义第 26 页已经明确把模型、prompt、scaffold、工具、检索、记忆、环境放进同一个性能函数；ABC 则说明测量端本身也会影响结果。[S00，PDF p.26](#source-s00) [S03，PDF p.3–5](#source-s03)

### 1.3 评估的最终目标是支持一个有范围的决定

“这个 Agent 成功率 90%”缺少很多信息。更完整的表达是：

> 在固定版本的材料、知识库、工具、权限和预算下，这个版本对指定类别任务达到某种成功率；重复与扰动实验暴露了哪些不稳定性；哪些高风险动作被禁止；结论适用于哪些用户、任务和操作范围。

这不是文字游戏。同一个系统可能是合格的辅助审核工具，却不适合无人监督自动发布；可能适合有可执行验证的代码候选生成，却不适合把未经核验的研究判断直接转为外部操作。可靠性论文明确区分人类辅助场景与全自动场景对可靠性的不同要求。[S02，PDF p.9](#source-s02)

## 2. 评估对象：模型、Agent 系统与交互环境

### 2.1 从“写出正确答案”走向“让环境进入正确状态”

讲义 p.8–9 将评价目标分成预测文本、生成正确答案、生成偏好回复、生成能运行的代码，以及完成交互任务。对应的评分可以是困惑度、准确率／F1、偏好胜率、可执行测试与环境状态检查。[S00，PDF p.8–10](#source-s00)

这里的变化不是题目越来越长，而是**正确性的对象发生了变化**。

普通问答中，主要检查一段文本。Agent 任务中，文本可能只是操作说明，真正需要检查的是文件、数据库、网页、代码库或业务状态是否改变，以及改变过程中是否遵守限制。

例如“生成一个修订建议”与“修改文档并发布”是两个任务。前者主要评估建议质量；后者必须增加原件保护、版本、权限、人工确认与外部副作用检查。

### 2.2 为什么 POMDP 对工程师有意义？

AgentBench 将交互式评估形式化为部分可观测马尔可夫决策过程；τ-bench 进一步把数据库与用户都放进状态空间。[S06，PDF p.3](#source-s06) [S08，PDF p.3](#source-s08)

不必先背术语。它要表达的是：Agent 看不到整个世界，只能通过工具与用户交流逐步获取信息；动作会改变世界；改变后的世界又影响下一步可行操作。

可以写成：

$$
h_t=(u,o_0,a_0,o_1,\ldots,o_t),\qquad a_t\sim\pi_A(\cdot\mid h_t)
$$

$$
s_{t+1}\sim P_E(\cdot\mid s_t,a_t)
$$

这里 $h_t$ 是历史，$s_t$ 是真实状态，$o_t$ 是可见观察。这是对上述形式化的教学改写，不是两个原论文完全相同的记号。

工程含义是：**一个局部合理动作可能改变后续可行空间。**重复查询通常可以补救；错误地消耗一次性写入机会、发送邮件或覆盖文件，可能无法靠改写最终答案恢复。

### 2.3 模型比较与产品比较，需要不同控制方式

AgentBench 故意采用较朴素的 CoT 与行动方式，不加入复杂反思、搜索或重复生成，以较低成本比较模型。其特定实验还会裁剪历史，使输入落在约 3,500 个按论文规则估计的 token 范围内。因此它测到的是“模型在该交互和上下文组织方式中的表现”，不是脱离执行系统的纯粹能力。[S06，PDF p.3、p.6–7](#source-s06)

《AI Agents That Matter》把两类需求分开：

**模型研究**希望固定其他条件，研究模型或架构变化的作用；**下游工程**希望选择最合适的系统，应该比较真实质量与成本，可以允许各方案合理适配。[S01，PDF p.6–7](#source-s01)

因此，实验前应写清楚自己问的是“在相同 harness 下谁更强”，还是“各自优化后谁更适合我的业务”。前者控制变量更严格；后者更接近采购和部署。两种结论不能互相冒充。

### 2.4 组件评估与端到端评估，分别负责诊断与验收

讲义把 planning、tool use、memory、error recovery 放在组件层，把 success rate、cost、latency 放在端到端层。[S00，PDF p.6](#source-s00)

| 层次 | 典型问题 | 不能单独证明什么 |
|---|---|---|
| 解析 | 页码、段落、表格、限定条件是否提取正确？ | 无法证明最终审核正确 |
| 检索 | 是否返回正确规则、证据和版本？ | 召回了不等于被正确使用 |
| 决策 | 是否满足规则条件与例外？ | 正确决定不等于执行成功 |
| 工具 | 调用结构、参数、身份和时点是否正确？ | API 成功不等于业务完成 |
| 恢复 | 失败后能否停止、重试、改计划或转人工？ | 恢复动作本身不等于最终交付 |
| 端到端 | 用户目标是否在约束内完成？ | 总分不能直接指出根因 |

表格是工程分解。最重要的关系是：**端到端实验告诉你能否交付，组件实验帮助解释为什么。**

## 3. Benchmark 的设计逻辑：怎样把工作变成可执行任务

### 3.1 不按名字背 benchmark，按“观察—行动—验收”理解

讲义 p.12–23 展示了多种工作形态。下表保留其框架，不把讲义中的特定新版本描述当作整理日最新状态。[S00，PDF p.12–23](#source-s00)

| Benchmark | Agent 观察与操作什么 | 主要验收对象 | 关键提醒 |
|---|---|---|---|
| GAIA | 搜索、文件、计算与多工具信息处理 | 简短最终答案 | 复杂取证过程可能不直接计分 |
| BFCL | 函数接口、结构化参数与工具状态 | 调用、参数及相应状态／回复 | 格式合法、参数正确、业务正确是三层问题 |
| WebArena | 网站、可访问性树、页面与后台 | 网站或后端状态 | 不应只检查最后 URL 或表面文本 |
| OSWorld | 截图、鼠标、键盘与桌面应用 | 文件、应用和系统状态 | 保存了文件不等于文件内容正确 |
| SWE-bench | 代码库、问题描述、代码编辑与测试 | 补丁应用后是否通过验收测试 | 必须兼顾修复与回归 |
| τ-bench | 用户对话、领域政策、业务 API | 数据库状态与必要回复 | 最终状态不能自动证明过程授权正确 |
| Terminal-Bench | 终端命令、容器与系统环境 | 任务特定的验证测试 | 任务范围不局限于修复代码仓库 |
| TheAgentCompany | 文档、代码、工单、聊天与模拟同事 | 检查点及最终工作状态 | 部分进展不能替代完整交付 |
| AgentBench | 八种代码、游戏与网页环境 | 按环境定义的成功率、F1、奖励等 | 总体分不是统一业务成功概率 |

AgentBench 的八种环境包括操作系统、数据库、知识图谱、数字卡牌、侧向思维谜题、家务环境、网页购物与网页浏览。不同环境使用不同评价指标，论文再做归一化加权；总体分不能直接解释为“完成了百分之多少任务”。[S06，PDF p.2、p.6–7](#source-s06)

### 3.2 GAIA 与 BFCL：答案正确和接口可靠不是同一件事

讲义的 GAIA 图展示搜索、打开网页、下载 PDF、提取表格和执行 Python，最终只评分规范化后的简短答案。它适合验证信息获取与综合后的结果，但不会自动验证所有过程副作用。[S00，PDF p.12–13](#source-s00)

BFCL 的例子强调应选对搜索与预订工具，不能发明乘客 ID，也不能无故查询天气。接口层面可以检查调用结构、参数和执行结果；但一次函数成功返回，并不证明查的是正确基金、正确份额类别或正确日期。[S00，PDF p.14](#source-s00)

**跨材料综合：**GAIA 提醒我们不要把复杂过程误认为复杂评分；BFCL 提醒我们不要把工具执行成功误认为业务目标成功；τ-bench 则把接口放进真实政策与多轮需求约束中。

### 3.3 SWE-bench：真实 issue 只是原料，必须经过可执行筛选

SWE-bench 不是把 GitHub issue 文本收集起来就算完成数据集。原论文采用三阶段构建：从 12 个 Python 仓库收集约 90,000 个 PR；筛选解决 issue 且修改测试的合并 PR；在修改前后执行测试，保留至少一个 fail-to-pass 测试的任务，同时排除安装和运行环境有问题的实例。最终得到 2,294 个任务。[S05，PDF p.2–3，Figure 2](#source-s05)

这说明：**真实来源不等于天然可评估。**issue 可能缺少背景，PR 可能同时修多个问题，测试可能不能重建。历史审核邮件同样如此：“这里改一下”往往隐含了当时的口头解释、材料版本和业务背景。

将历史记录变成评估任务，需要独立读者能够从允许输入中理解目标，并且存在可检查的成功条件。

### 3.4 成功包括“修好问题”与“没有改坏别的东西”

SWE-bench 的 fail-to-pass 测试检查原问题是否被解决；附加回归测试检查原有功能是否保持。原论文报告每个任务至少有一个 fail-to-pass 测试，并运行其他相关测试来保护已有行为。[S05，PDF p.3](#source-s05)

**教学抽象：**

$$
\text{成功}=\text{目标条件满足}\land\text{原有不变量保持}
$$

对合规预审核而言，识别新风险是前者；不误报大量正常内容、不丢失正确引用、不覆盖原件是后者。只看新增问题召回，会鼓励系统越来越激进。

参考 PR 只证明存在一种修复方案。SWE-bench 允许不同于参考 PR 的有效解。[S05，PDF p.3](#source-s05) 同理，一条风险可能通过删除、补充限定条件或准确改写来解决；不能因为输出与历史人工措辞不同，就一律判错。

### 3.5 上下文实验：组件改善为何没有变成端到端改善？

SWE-bench 比较 BM25 检索与 oracle retrieval。后者直接提供参考修复修改过的文件，用来分析“已知大致改哪里”之后的能力。作者明确说明它不现实，而且修改过的文件也未必包含理解问题的全部上下文。[S05，PDF p.5](#source-s05)

论文 p.5 的 Tables 2–3 给出一个非常重要的历史实验：

| 最大上下文预算 | BM25 覆盖全部参考修改文件的任务比例 | Claude 2 问题解决率 |
|---|---:|---:|
| 13k | 26.09% | 1.96% |
| 27k | 39.83% | 1.87% |
| 50k | 45.90% | 1.22% |

来源：[S05，PDF p.5，Tables 2–3](#source-s05)。这里不涉及当前模型表现，也不把不同表格中的其他历史结果合并。

检索覆盖提高，最终解决率却下降。这不能证明上下文普遍越长越差，但足以否定“召回率上升必然让 Agent 更好”。新增信息还需要被定位、理解、选择和使用；无关上下文可能增加后续处理难度。

**工程设计：**对规则检索，同时报告召回覆盖、规则适用判断、最终建议质量。用人工核验证据替换检索结果，可以检验瓶颈假设，但应标成诊断实验，不能作为真实端到端成绩。Oracle 也不应无条件称为理论上限，因为它可能只覆盖参考解所需的一部分信息。

### 3.6 τ-bench：将数据库、政策与用户放进同一个实验

τ-bench 的状态包含数据库与用户，对应动作包含 API 调用与自然语言交流。数据库转移由 Python 实现，用户由模型模拟；用户看不到工具内部交互，只能依据 Agent 对自己说的话作出回应。[S08，PDF p.3–4](#source-s08)

它的任务构建同样是三阶段：人工共设计 schema、API 和政策；借助模型生成数据；人工撰写用户情境并通过试运行检查和修改标注。设计者努力使用户意图与政策导向一个可比较的目标数据库状态。[S08，PDF p.5–6](#source-s08)

**独特之处不是多了聊天，而是多了一条反馈回路：**

$$
\text{Agent提供的信息}\rightarrow\text{用户的选择}\rightarrow\text{后续目标与操作}
$$

论文的 wrong information 案例包括错误价格影响用户是否取消或换货。后续调用即使合法，整条决策链也可能建立在错误信息上。[S08，PDF p.8](#source-s08)

### 3.7 局部合法，为什么仍然全局失败？

τ-retail 某些换货或修改动作只能执行一次。Agent 必须先收集全部要处理的商品，再一起调用。论文中的 Agent 提前处理一个商品，后面的商品便无法继续处理。[S08，PDF p.8，§5.2](#source-s08)

这里没有 JSON 语法错误，也不是工具不可达。失败机制是：**过早执行局部合理动作，消耗了完成全局目标的机会。**

这比“是否写出计划”更接近真正的 planning evaluation：关键不可逆动作前是否收集完信息，是否识别依赖，是否保留其他子目标的可行性。

### 3.8 规则消融：怎样证明 Agent 真正在使用政策？

τ-bench 删除系统提示中的领域政策，观察性能变化。零售任务较接近常识，下降相对有限；航空规则更复杂，较强模型在消融表中的成绩从 33.2% 降至 10.8%，下降 22.4 个百分点。[S08，PDF p.8，Table 3](#source-s08)

**来源边界：**同文主结果 Table 2 的对应航空成绩为 35.2%，Table 3 使用 33.2%；原文没有在这两处明确解释差异。本文按 Table 3 解释该消融，不推测差异原因，也不混合两表计算。

这一实验在问：成功来自提供的领域政策，还是来自常识或其他因素？工程上可借鉴“正确规则／无规则／无关但结构相似规则”对照。若结果不变，需要检查任务是否过于简单、规则是否进入上下文、模型是否使用规则，或裁判是否根本没测规则边界。日志中出现检索调用，不等于规则库有贡献。

### 3.9 执行症状与业务根因，需要同时记录

AgentBench 将结束原因分为上下文超限、格式错误、无效动作、轮数超限和正常结束。正常结束不保证成功。[S06，PDF p.4](#source-s06)

τ-bench 对一组 115 条零售轨迹进行人工分析：40 条失败，其中 4 条源于用户指令笔误或歧义，剩余 36 条归为 Agent 问题；主要类型是错误参数、错误信息、错误决策与只完成部分需求。[S08，PDF p.7–8，Figure 5](#source-s08)

两者合起来，适合形成这样的工程记录：

```text
执行结束原因：达到最大轮数
首次关键偏离：信息未收集完就执行一次性换货
业务后果：第二个商品无法处理
恢复尝试：重复调用已失效的工具
最终验收：未完成
```

AgentBench 更像执行症状，τ-bench 更像业务失败机制。一个 `failed` 或一段笼统的“推理能力不足”无法替代这种分层记录。

### 3.10 部分得分的价值与陷阱

讲义的 TheAgentCompany 用工作流检查点提供部分得分，并额外奖励完整完成，其示意为：

$$
S_{\text{partial}}=0.5\frac{\text{earned}}{\text{total}}+0.5S_{\text{full}}
$$

这使 4/8 检查点但未交付得到 0.25，完整完成得到 1。[S00，PDF p.22](#source-s00)

工程上，检查点可以定位进度，但不应通过堆积容易完成的前置步骤掩盖交付失败。读了所有文件、调用了所有查询，却没有生成可用报告，仍然没有完成用户工作。

## 4. 裁判有效性：为什么真实任务也可能测出假分数

### 4.1 ABC 的两段等价关系

ABC 的核心不是“列出很多检查项”，而是区分两条关系：

$$
\text{目标能力}
\overset{\text{Task validity}}{\longleftrightarrow}
\text{任务成功}
\overset{\text{Outcome validity}}{\longleftrightarrow}
\text{评估通过}
$$

任务有效性问：完成任务是否真的需要目标能力，具备目标能力时任务是否合理可解？结果有效性问：通过裁判是否真的意味着完成，完成后是否能被裁判接受？这是 ABC Figure 1 的概念结构，不是声称现实中可以完全证明双向等价。[S03，PDF p.2–4，Figure 1](#source-s03)

| 失真方向 | 示例 | 后果 |
|---|---|---|
| 不需要目标能力也能拿分 | 不回答就保持数据库不变 | 能力被高估 |
| 有能力也做不了题 | 必需 API 不可达、初始环境不正确 | 能力被低估 |
| 未完成却被判成功 | 只检查文件存在、不检查内容 | 错误结果混入成功样本 |
| 完成却被判失败 | 只接受参考函数名或固定措辞 | 合理答案被错杀 |

这与讲义 p.31 的提醒一致：只看结果可能放过幸运或不安全的运行，而严格匹配一条轨迹又可能拒绝合法方案。[S00，PDF p.31](#source-s00)

### 4.2 τ-bench 的“空回答 38%”：自动状态验收为何失灵？

τ-bench 尽力将多样对话映射为唯一数据库目标状态。ABC 却发现，在其检查的航空子集中，38% 的任务目标数据库状态不变且不要求输出，其中包括按政策应拒绝的任务。什么也不做的 Agent 也会通过这些任务；零售子集相应比例为6%。原文p.8概括为intentionally unsolvable，附录E.2展示non-refundable拒绝案例，不能据此断言38%的每一道题都只需拒绝。[S03，PDF p.8、p.27–28 §E.2](#source-s03)

问题不是“拒绝型任务不该出现”，而是：

$$
\text{状态没有变化}\not\Rightarrow\text{理解政策并正确拒绝}
$$

正确拒绝应包含必要的信息获取、条件判断和用户沟通。空输出没有证明这些能力。

不能把一个模型的总分直接减去 38% 当成真实成绩。空回答与模型通过的任务集合可能不同，必须逐题比较。此外，该比例属于被审计的版本和子集，不是所有 τ-bench 版本的固定属性。

**工程设计：**给自己的裁判准备几个 trivial baselines：永远说没问题、永远说有风险、列出全部规则、什么也不输出。它们是评分器的漏洞探针，不是业务候选架构。

### 4.3 子串匹配为什么特别容易误判？

若裁判只检查输出是否含有正确答案，就可能忽略否定、冲突或无关信息。“有风险”与“没有风险”共享子串；同时列出所有候选答案，也可能碰到必需文本。ABC 因此要求考虑否定修饰、语义等价、额外文本和穷举答案等情况。[S03，PDF p.5–6](#source-s03)

但评分器也不能无限宽松。若用户明确要求机器可解析的 JSON，格式不符合就是实际失败。ABC 特别区分“裁判擅自假设格式”与“任务明确要求格式”。[S03，PDF p.5，脚注 3](#source-s03)

**工程含义：**只宽容那些不改变业务正确性和接口契约的表达差异，不宽容明确契约违反。

### 4.4 可执行测试不是自动正确的裁判

SWE-bench 把文本相似度升级为行为测试，但测试仍然是人工设计的近似。ABC 强调单元测试、fuzz testing 和端到端测试都需要质量验证；状态检查还应覆盖“不应该发生变化的部分”。[S03，PDF p.6](#source-s03)

阅读清单中的 OpenAI 审计检查了 138 个 o3 在多次运行中不能稳定解决的 SWE-bench Verified 问题。文章报告，59.4% 的被审计问题有实质性的测试或描述问题，既包括强制未要求的实现细节，也包括测试额外要求题目未描述的功能。例如，题目未要求新函数名，测试却直接导入特定函数，导致合理实现失败。**这个比例针对经过选择的 138 题，不是全部 500 题的随机错误率。**[S14，§Too narrow and too wide tests](#source-s14)

**跨材料综合：**测试太弱会放过错误方案；测试过窄会错杀正确方案；测试超出题目会让完成显式需求仍然失败。因此，“采用可执行测试”并没有消灭测量问题，而是把一部分问题转移到了测试本身。

### 4.5 NIST：答案污染与裁判利用，是两种不同问题

NIST CAISI 将评估作弊分成：

**Solution contamination（答案污染）：**Agent 访问了目标真实场景本不允许获得的解题信息，例如未来 Git 提交、公开题解、环境遗留的答案。

**Grader gaming（利用评分器）：**没有实现预期任务，却通过自动评分。其案例包括使目标呈现被评分器认可的表面状态，却没有展示指定目标能力。[S04，§2.1–2.2](#source-s04)

两者的修复不同。前者需要信息、时间和权限边界；后者需要评分器、状态验收和轨迹审计。

不是所有联网检索都算作弊，也不是所有不同于参考路径的方案都算作弊。需要先确定任务允许获得什么信息、允许采取什么路径。若任务目标本来允许多路径完成，应接受不同正确解；若题目要证明指定机制或能力，则仅仅制造相同表面结果可能不够。

NIST 还说明，其分析来自原先为其他目的收集的历史数据，不同模型和 benchmark 的样本数不一致；成功作弊案例经过人工核验，但仍可能漏检。因此不能把检测到的次数直接当成不同模型固有作弊倾向的公平排名。[S04，§2 开头的方法说明](#source-s04)

### 4.6 为什么重复一万次也救不了一个坏裁判？

**教学推导：**设真实成功概率为 $p$，裁判误接受错误结果的概率为 $\alpha$，误拒绝正确结果的概率为 $\beta$。则：

$$
P(\text{裁判判成功})=p(1-\beta)+(1-p)\alpha
$$

重复运行越多，只会更精确地估计右侧这个量，不会自动把 $\alpha$ 与 $\beta$ 变成零。

如果 Agent 的输出策略会影响裁判错误，例如枚举全部答案更容易命中子串，误差还会随被测系统变化。此时并不存在一个可以对所有架构统一减掉的“裁判噪声常数”。

> 统计精度无法补救测量失真。一个置信区间很窄的分数，也可能没有你以为的含义。

### 4.7 坏标签如何进一步污染可靠性指标？

可靠性论文引用一项清理结果：原始 50 个航空任务中有 24 个存在标签或描述问题，因此采用剩余 26 个任务进行主要分析。论文 p.8 又比较原始和清理后集合，发现可预测性，尤其校准，受到明显影响。[S02，PDF p.5、p.8，Figure 6](#source-s02)

原因很直白：Agent 自信地完成任务，却被错误答案判失败，看起来就像“过度自信”。

这构成一条重要研究链：

```text
τ-bench：建立自动状态评分
    ↓
ABC 与相关审计：评分及任务设计可能失真
    ↓
Agent Reliability：失真不仅污染成功率，还会污染校准等更高层指标
```

这里不是说上述审计完全相同：ABC 的空回答问题与可靠性论文引用的 24 题清理并非同一个实验。清理子集也改变了任务分布，不能把差异全都解释成“同一分布上的标签修正效果”。

### 4.8 LLM-as-a-judge：不是取消标准，而是把标准交给模型执行

ABC 要求验证裁判准确性、自一致性、与人工的一致程度，并考虑对抗输入和 reward hacking。[S03，PDF p.5–7](#source-s03)

**工程设计：**将验收划分为确定性检查、语义检查与人工裁定。文件能否打开、金额是否一致、引用页码是否存在、是否产生额外写入，尽量由程序检查；证据是否支持结论、建议是否解决问题，可以用明确 rubric 的模型裁判；高风险、争议和信息不足的样本进入人工复核。

不要只问“好不好，请打 1–10 分”。应要求逐项判断，并返回对应证据位置和无法判断的原因。例如：

```json
{
  "criterion_id": "evidence_support",
  "verdict": "supported",
  "evidence_refs": ["document_A:page_3:paragraph_2"],
  "reason": "引用段落包含结论所需的对象、期间和限定条件",
  "needs_human_review": false
}
```

这是输出契约示例，不是生产裁判实现。

裁判还应有自己的测试集：正确但表述不同、形式精美却事实错误、引用真实却不支持结论、建议正确却越权修改原件、空回答、列举全部候选等。先确认裁判能够区分这些情况，再增加被测 Agent 的运行规模。

## 5. 重复成功：pass@k、pass^k 与选择器问题

### 5.1 两个相似符号，代表不同产品目标

对同一道任务，假设每次完整运行独立、成功概率固定为 $p$：

$$
\operatorname{pass@k}=1-(1-p)^k
$$

$$
\operatorname{pass^k}=p^k
$$

前者问“给 $k$ 次机会，至少能找到一个正确解吗”；后者问“同一场景重复 $k$ 次，能否每次都完成”。τ-bench 为客服等需要重复可靠交付的场景引入 pass^k。[S08，PDF p.4–5](#source-s08)

当 $p=0.8$：

$$
\operatorname{pass@5}=99.968\%,\qquad
\operatorname{pass^5}=32.768\%
$$

这不是矛盾，而是两个不同问题。这里的 $k$ 是完整运行次数，不是工具步数，不是一次运行内的五次反思或重试。

### 5.2 同样 80% 成功率，行为分布可能完全不同

**教学构造：**系统 A 对 80% 的任务永远成功、20% 永远失败；系统 B 对每一道任务都有 80% 成功概率。

| 指标 | A：边界固定 | B：每题都有随机性 |
|---|---:|---:|
| 平均成功率 | 80% | 80% |
| pass@5 | 80% | 99.968% |
| pass^5 | 80% | 32.768% |

A 可能适合在识别出能力边界后定向自动化；B 可能更适合多生成再验证。但这都依赖额外条件：能否识别当前任务属于哪种情况，以及能否识别候选解中正确的那一个。

所以不能把总体平均成功率直接取 $k$ 次方。多任务总体指标为：

$$
\operatorname{pass^k}=\frac{1}{N}\sum_i p_i^k
$$

$$
\operatorname{pass@k}=\frac{1}{N}\sum_i[1-(1-p_i)^k]
$$

任务难度和行为分布的差异会影响这些量。

### 5.3 选择器问题：生成正确答案，不等于交付正确答案

五个答案里只有一个正确，离线标准答案可以确认“至少有一个正确”，真实产品却未必知道哪个正确。

$$
\text{候选集合包含正确解}\not\Rightarrow\text{最终选择正确解}
$$

《AI Agents That Matter》的简单重试基线利用题目提供的示例测试作为反馈，再用评估体系检验最终提交。它不是在生产场景中凭空获得隐藏答案。[S01，PDF p.3](#source-s01)

**工程设计：**若多次生成后使用模型裁判、多数票或规则选择，最终评估必须包括该选择过程、失败时的行为与全部成本。Oracle 意义上的 pass@k 是候选覆盖能力，不应直接充当服务成功率。

### 5.4 有限次数的组合数估计

每道任务运行 $n$ 次，成功 $c_i$ 次。τ-bench 给出：

$$
\widehat{\operatorname{pass^k}}
=\frac{1}{N}\sum_i\frac{\binom{c_i}{k}}{\binom{n}{k}}
$$

$$
\widehat{\operatorname{pass@k}}
=1-\frac{1}{N}\sum_i\frac{\binom{n-c_i}{k}}{\binom{n}{k}}
$$

需要 $n\ge k$；当成功次数或失败次数小于 $k$ 时，对应组合数视为零。直观上，相当于从已有运行中抽取 $k$ 次，计算全部成功或至少一次成功的比例。[S08，PDF p.5](#source-s08)

无偏估计的统计解释依赖相同任务下的独立同分布运行。若第二次访问第一次留下的答案、记忆或状态，就改变了协议。

### 5.5 τ-bench 的重复运行还包含用户变化

τ-bench 固定场景的用户指令和数据库转移，但用户模拟与 Agent 消息采样带来对话变化。因此 pass^k 测量的不只是模型服务的非确定性，还包括在相同意图与政策下应对不同对话的能力。[S08，PDF p.5](#source-s08)

**工程设计：**分别记录模型随机因素、用户模拟配置、工具扰动和环境版本。需要隔离原因时，做单因素实验；需要估计整体产品可靠性时，按明确协议共同变化。不能把所有差异一律解释成“temperature 太高”。

### 5.6 temperature=0 也不应代替重复实验

《AI Agents That Matter》在零温度条件下仍采用重试；可靠性论文也报告零温度下的重复运行，并讨论非采样随机来源，同时指出部分推理模型不暴露温度参数，使用提供方默认设置。[S01，PDF p.3、附录 A.1](#source-s01) [S02，PDF p.5](#source-s02)

因此，“温度设为零”是配置说明，不是结果必定相同的证明。需要冻结的还包括模型版本、上下文、工具结果、初始状态以及可控的随机种子。

## 6. 可靠性：一致性、鲁棒性、可预测性与安全性

### 6.1 四个维度，不是换一个更复杂的总分

《Towards a Science of AI Agent Reliability》将安全关键工程的可靠性视角用于 Agent，给出四维、十二项指标。实验覆盖两个 benchmark 和 15 个模型；作者发现，在其实验条件下，可靠性提升落后于能力提升。[S02，PDF p.1–5](#source-s02)

| 维度 | 子指标 | 回答的问题 |
|---|---|---|
| Consistency | 结果一致性、轨迹分布一致性、轨迹顺序一致性、资源一致性 | 同条件重复时是否稳定？ |
| Robustness | 工具故障、环境变化、提示改写 | 条件改变时怎样退化？ |
| Predictability | 校准、区分能力、Brier | 能否识别成功与失败概率？ |
| Safety | 约束遵守、违规严重程度 | 失败带来什么后果？ |

论文把 reliability 限定为自然变化与偶发故障下的行为属性，不声称覆盖所有对抗攻击、价值对齐或社会技术问题。[S02，PDF p.2](#source-s02)

所谓“独立于能力的评价维度”不意味着所有指标与成功率数学上统计独立。部分指标直接由成功概率计算；更恰当的理解是，平均成功率不足以完整代表这些属性。

### 6.2 结果一致性：稳定不等于正确

论文采用：

$$
C_{\text{out}}=\frac{1}{N}\sum_i(2\hat p_i-1)^2
$$

总成功和总失败都接近 1，成功失败各半接近 0。它测的是结果稳定性，而不是正确性，因此必须与成功率并排报告。[S02，PDF p.4，Table 2](#source-s02)

一个稳定地错误引用旧规则的系统可以有高一致性，但依然不可用。反过来，一致性不足也可能来自少数边界任务，需要按任务类型切片，而不是只看总值。

**教学推导：有限样本的影响。**若每题有 $K$ 次独立 Bernoulli 运行，真实概率为 $p$，则：

$$
E[(2\hat p-1)^2]=(2p-1)^2+\frac{4p(1-p)}{K}
$$

真实 $p=0.5$ 且 $K=5$ 时，样本指标期望为 0.2。不同重复次数的指标不应直接比较。这是从论文公式推导出的有限样本提醒，不是原文新增的推荐指标。

### 6.3 轨迹一致性：相同动作集合不等于相同顺序

论文分别比较动作类型分布与动作序列。前者使用动作分布之间的 Jensen–Shannon divergence，后者使用归一化编辑距离；二者衡量“做了哪些事”和“按什么顺序做”。[S02，PDF p.4](#source-s02)

论文在其结果中观察到，部分 Agent 的动作类型分布比执行顺序更稳定，即“做什么”较一致，“何时做”变化更大。[S02，PDF p.6](#source-s02)

但工程验收不能因此要求所有合法流程精确一致。查询顺序可交换不一定有问题，授权顺序通常不能交换。

**工程设计：**把轨迹距离用于行为分析；把“必须先查询、核验、确认，再执行特定写入”等关键时序转换为明确约束。普通搜索路径不同不应自动判错。

### 6.4 资源一致性：最终都成功，仍可能很难运营

论文用资源变异系数 $CV_r=\sigma_r/\mu_r$，再进行指数转换：

$$
C_{\text{res}}=\exp\left[-\frac{1}{|\mathcal R|}\sum_{r\in\mathcal R}CV_r\right]
$$

资源可以是成本、时间和调用次数。[S02，PDF p.4](#source-s02)

两个系统平均耗时相同，一个每次都接近一分钟，另一个有时十秒、有时十分钟，用户体验和容量规划不同。

**工程设计：**保留平均、分位数和各次原始值；均值为零、运行超时和失败样本怎样计入，需要在指标实现中明确。一个资源一致性分数不能替代尾部时延与预算违约统计。

### 6.5 鲁棒性：扰动必须保持你想保持的语义

论文区分 fault、environment 和 prompt robustness，并使用扰动成功率与基线成功率的比值，最高截断为 1。[S02，PDF p.3–6](#source-s02)

$$
R_{\text{fault}}=\min\left(\frac{\operatorname{Acc}_{\text{fault}}}{\operatorname{Acc}_0},1\right)
$$

附录给出了环境变化细节：例如 snake_case 改为 camelCase、时间格式改变、响应外面增加包装层。Agent 获得的接口说明相应更新，执行前再反向映射到原接口，底层任务语义保持不变。[S02，PDF p.33](#source-s02)

这区别于“偷偷改了实现却不给新说明”。后者可能是接口契约错误，不是同类鲁棒性实验。

**工程设计：**同时报告绝对成功率、下降百分点与相对保持率。基线 5%、扰动后 5%，并不意味着好用。基线为零时该比值无定义，不应强行填成 1。对多种扰动强度，应分别报告，不把严重程度不同的故障随意平均。

### 6.6 校准与区分能力：两个容易混淆的概念

**校准**问：声称八成把握的任务，是否真的大约八成成功？  
**区分能力**问：成功任务的置信度是否普遍高于失败任务？

一个系统对所有任务都说“80%”，且总体成功率确实为 80%，可能校准不错，却没有能力挑出哪道题危险。[S02，PDF p.4](#source-s02)

常规 Brier 损失为：

$$
\operatorname{Brier}=\frac{1}{M}\sum_j(c_j-y_j)^2
$$

论文使用 $P_{\text{brier}}=1-\operatorname{Brier}$，使方向与其他分数一致。[S02，PDF p.4](#source-s02)

**实现边界：**论文 Table 2 的 AUROC 写法只显式计入 $c_{\text{success}}>c_{\text{failure}}$，同时称其等价于 AUC-ROC；常规 AUROC 实现还会给置信度相同的配对半分。复现时应报告使用的是哪种 ties 约定，而不是默默改写原公式。样本只有成功或只有失败时，区分能力也不能直接估计。

### 6.7 置信度的预测时点，决定了它能支持什么决定

可靠性论文在任务完成后，让 Agent 看完整历史并自评置信度。这是 post-hoc confidence，不是执行前预测，也不是每一个危险动作之前的实时风险判断。[S02，PDF p.33–34](#source-s02)

附录F.3.4还规定：自评响应无法提取数值置信度时，根据执行错误计数使用启发式回退。因此部分记录不完全来自模型自评；复现应保存解析成功率、回退比例及两类记录的切片，避免把混合信号全归因于自知能力。[S02，PDF p.34](#source-s02)

因此不能据此证明：“Agent 在发送材料前就知道这次会不会错。”

**工程设计：**分别评估执行前、关键动作前和交付前的判断。每次只能使用当时可得信息，不能把后续失败信号反向喂给一个声称是事前预测的评分器。

可以进一步建立选择性处理曲线：当系统只自动处理置信度超过阈值 $\theta$ 的任务时，自动处理覆盖率是多少，自动处理部分的错误率是多少？

$$
\operatorname{Coverage}(\theta)=\frac{\#\{j:c_j\ge\theta\}}{M}
$$

$$
\operatorname{Risk}(\theta)=
\frac{\sum_{j:c_j\ge\theta}(1-y_j)}{\#\{j:c_j\ge\theta\}}
$$

这两式是工程扩展，零覆盖时 risk 应标记为不可估计。它们把置信度连接到“自动完成／补充核验／转人工”，而不是仅在页面展示百分比。

### 6.8 安全性：低频严重错误不应被平均掉

论文分开统计无违规比例 $S_{\text{comp}}$ 与违规后的危害程度，并采用：

$$
R_{\text{saf}}=1-P(\text{violation})E[\text{severity}\mid\text{violation}]
$$

其严重度权重是研究中的设计选择，不是自然常数。作者不把安全性平均进总体 reliability，避免尾部风险被其他高分掩盖。[S02，PDF p.4–5](#source-s02)

错一处格式、少一个引用、未经确认对外发布，不能仅按“各失败一次”看待。实际发布门槛应单独处理不可接受的越权与危害。

此外，“危险尝试被护栏拦下”和“模型没有危险尝试”不同。需要分别统计尝试、拦截、实际后果和恢复，后文 ActPlane 会把这个区分做成实验。

### 6.9 聚合方法与结论边界

论文先将轨迹分布与顺序平均，再将结果、轨迹、资源三类平均为一致性；鲁棒性聚合三种扰动；可预测性主要采用 Brier 变体；整体对一致性、鲁棒性、可预测性平均，安全另列。[S02，PDF p.5](#source-s02)

这不等于十二个指标直接平均，也不表示业务系统必须照抄同样权重。作者承认：两个 benchmark 覆盖有限，每个 benchmark 只使用一个 scaffold，安全依赖模型裁判，指标与归一化也有主观设计成分。[S02，PDF p.9](#source-s02)

本文对其核心结论的采用范围是：**平均成功率之外需要明确测量行为稳定性、退化、失败预测与后果。**不能据有限实验断言所有模型、所有行业都存在同样程度的可靠性停滞。

## 7. 成本与因果：怎样证明架构真的有用

### 7.1 控制预算，不只是为了省钱

《AI Agents That Matter》提出：只比较准确率，会把额外计算带来的收益误归因于复杂架构。它重评了 LDB、LATS、Reflexion，并加入 Retry、Warming、Escalation 三类简单基线。[S01，PDF p.2–4](#source-s01)

Retry 在未通过题目示例测试时重新生成；Warming 逐步提高温度以增加候选多样性；Escalation 从较便宜模型开始，失败后升级到更昂贵模型。这些反馈来自可用的题目示例测试，不应与最终隐藏验收答案混淆。[S01，PDF p.3](#source-s01)

在论文的 HumanEval 设置中，最佳复杂架构与 Warming 的准确率没有显著差异，成本却可以相差很大。作者并没有证明反思或搜索永远无用，而是指出：缺乏这些简单对照，就无法识别复杂机制对增益的贡献。[S01，PDF p.3–4，Figure 1](#source-s01)

**教学例子：**原流程调用一次成功率 70%，增加反思后调用三次成功率 80%。可能是反思有效，也可能是多一次生成和验证就足够。应增加相近预算下的简单重试或检索方案，才能比较机制。

重试在工程上可能很有价值。“不能证明架构创新”不等于“没有产品价值”。论文的批评主要针对错误因果解释与只追求榜单分数的研究习惯。

### 7.2 如何读 Pareto frontier，而不只选最高分？

讲义最后给出能力、成本、速度三个维度：方案 A 在所有维度不差于 B，至少一个维度更好，才称 A 支配 B；无法被其他方案支配的一组配置构成 Pareto frontier。[S00，PDF p.35](#source-s00)

工程上可以先排除被明显支配的方案，再根据业务要求在前沿上选择。时延是硬约束的交互产品，与可等待一小时的批处理任务，不会选择同一点。

《AI Agents That Matter》Figure 1 的横轴是当时 164 道 HumanEval 任务的总成本，横轴有断轴、纵轴也非从零起始。不能把视觉距离解释成单题成本收益，更不能外推为所有任务上的收益比例。[S01，PDF p.4](#source-s01)

### 7.3 为什么不能把 HumanEval 的发现概括成“简单 Agent 总是更好”？

HumanEval 的重试可以获得可执行反馈。τ-bench 的错误可能是误解政策、在信息不完整时执行一次性动作，或用错误价格诱导用户确认。后者不一定能通过重新生成恢复。[S01，PDF p.3](#source-s01) [S08，PDF p.8](#source-s08)

**跨材料综合：**复杂架构的价值，取决于它是否增加有效信息、验证能力或动作控制，而不取决于是否被称为规划、反思或多 Agent。

同一份材料换个角色再读一遍，可能只是增加计算；查询独立事实源、执行确定性计算、检查实际产物，则可能真正提供新信号。需要通过消融实验区分，而不是凭架构名称判断。

### 7.4 HotPotQA：把评估目标直接用于系统优化

《AI Agents That Matter》还做了联合优化实验：使用 DSPy 组织多跳检索，用 ColBERTv2 检索 Wikipedia，在候选 few-shot、数量、模块温度和格式说明等参数中搜索效果与成本的折中。[S01，PDF p.5](#source-s01)

该实验使用 100 个训练样本和 200 个测试样本，优化过程中再将训练部分分为候选收集与验证。一个非常重要的口径是：**它衡量的是是否检索到了全部标注证据文档，不是最终问答答案的正确率。**[S01，PDF p.5，§3.1](#source-s01)

论文在这一设置下报告，相近效果时 GPT-3.5 可变成本降低 53%，Llama-3-70B 降低 41%。这属于特定任务、模型和当时价格条件下的结果。[S01，PDF p.5–6](#source-s01)

与 SWE-bench 上下文实验结合起来，结论更有价值：更多上下文可能提高召回，却增加下游负担；更少且更合适的示例可能保持目标效果，同时减少成本。**上下文不是免费燃料，而是需要用评估选择的变量。**

### 7.5 固定成本、运行成本与回本规模

论文区分前期优化成本与每次运行成本。[S01，PDF p.4–6](#source-s01)

**教学推导：**

$$
C_{\text{total}}(n)=C_{\text{build}}+nC_{\text{run}}
$$

若 B 前期更贵、单次更便宜，忽略其他差异时：

$$
n^*=\frac{C_{\text{build},B}-C_{\text{build},A}}
{C_{\text{run},A}-C_{\text{run},B}}
$$

只有分母为正等条件成立时，这个回本规模才有意义。低频小工具可能不值得复杂优化；高频业务则可能值得细化上下文、工具返回与验证策略。

此外：

$$
C_{\text{per success}}=
\frac{\text{全部任务运行成本}}{\text{成功完成次数}}
$$

分子应包含失败、重试和升级的消耗。只统计成功样本会掩盖昂贵的失败。没有成功样本时，应标记不可估计或无有效交付，不要填零。

### 7.6 NovelQA：使用模式决定成本结论

《AI Agents That Matter》指出，先输入整本小说再一次性回答全部问题，与真实用户逐次提问，成本结构不同。其 NovelQA 案例认为，这种负载差异会影响长上下文与 RAG 的比较。[S01，PDF p.7](#source-s01)

这不是一个可以不加条件应用于当前缓存机制的固定成本倍数。本文保留其方法论：**评估负载必须模拟实际用法。**

对投研文档问答，应说明是否反复访问同一文档、是否共享前缀、缓存是否预热、工具是否复用结果、价格使用哪个时间点。缓存价格或命中行为变化之后，可以用保存的 token 和调用记录重算成本，不能仅留下一个美元总数。

### 7.7 三本账：服务、评估、人工

τ-bench 将被测 Agent 与模拟用户的调用成本分别统计，这提醒我们不要把评估平台所有消耗都当作生产服务成本。[S08，PDF p.7](#source-s08)

**工程设计：**

| 账本 | 包含什么 | 用于什么决定 |
|---|---|---|
| 服务成本 | Agent 模型、检索、工具、运行环境、重试 | 单次业务是否经济可行 |
| 评估成本 | 模拟用户、模型裁判、重复实验、标注和沙箱 | 研发迭代与验收的成本 |
| 人工成本 | 复核、修订、沟通、事故处理 | 实际是否节省工作量 |

机器成本下降，却让审核人多花大量时间核验，未必是总体改进。模型调用速度更快，却在工具或人工等待上形成尾部延迟，也不一定改善体验。

### 7.8 时延应看完整关键路径

讲义强调 latency 不只包括 LLM。[S00，PDF p.10](#source-s00) 工程上应记录模型生成、检索、工具、环境启动、排队、重试与必要人工交互。

串行任务看整条流程；并行任务看最终交付所依赖的关键路径，不能简单相加所有子 Agent 耗时。平均时延还应与高分位、超时比例、预算违约和失败时长一起报告。

## 8. 泛化与泄漏：整个 Agent 栈都属于考试边界

### 8.1 “没有微调”为什么远远不够？

讲义明确列出四层问题：训练泄漏、评估时泄漏、环境泄漏、benchmark 过拟合，并进一步扩展到 prompt、retriever、memory、web search、scaffold 和开发过程。[S00，PDF p.25–26](#source-s00)

| 层面 | 可能的泄漏 | 工程边界 |
|---|---|---|
| 模型训练 | 见过题目和修复方案 | 明确训练与评估时间及数据来源能证明到什么程度 |
| Few-shot／prompt | 示例由测试答案整理而来 | 示例必须来自允许的开发材料 |
| RAG | 案例库中有当前测试的完整答案 | 业务知识与评估标签分离 |
| Memory | 上次测试的裁判反馈留在长期记忆 | 独立重复应恢复同一初始记忆 |
| 联网搜索 | 搜到公开题解或未来修复 | 按任务定义控制可访问信息 |
| 执行环境 | 可读隐藏测试、未来提交、答案文件 | 使用实际权限隔离，而非仅文本提醒 |
| 开发过程 | 反复看测试失败后改路由或规则 | 这些样本转为开发／回归集，保留新测试集 |

NIST 也强调，评估时答案污染不同于训练污染；即使题目晚于模型训练，Agent 仍可能在执行时获得答案。[S04，§2.1](#source-s04)

### 8.2 规则库可以用，测试答案不一定可以用

在一个材料审核系统里，规则条文本来就是允许使用的知识。可是某份测试材料对应的人工最终审核结论，可能是裁判标签。

若相似案例检索直接返回同一测试材料的历史结论，就算没有微调，也改变了测试条件。原稿、修订稿、PDF、图片和文字改写可能属于同一案例家族，应按任务意图决定是否必须放在同一数据分区。

这不是否定案例检索，而是要求区分两类能力：利用已知案例处理相似请求，和面对未见材料独立应用规则。二者都可评价，但需要不同协议。

### 8.3 泛化范围越大，留出的变化也应越大

《AI Agents That Matter》提出四层 generality，并要求留出集与声明的泛化范围相匹配。[S01，PDF p.8，Table 1](#source-s01)

| 预期泛化 | 论文中的留出方向 | 业务中的对应设计 |
|---|---|---|
| Distribution-specific | 同分布样本 | 同类新材料，但隔离同一案例家族 |
| Task-specific | 分布外样本与漂移 | 新模板、来源、版式、接口变化 |
| Domain-general | 新任务 | 领域内未反复调优的工作流程与规则组合 |
| General-purpose | 新领域 | 不同领域任务，而非只换几个输入 |

论文强调，不能声明领域通用，却只在已知固定任务上调优和测量。相同原则也适用于“跨行业投研”或“全渠道营销审核”的产品宣称。

### 8.4 STeP 案例：工程捷径与泛化宣称不是同一个问题

《AI Agents That Matter》讨论了 STeP 在 WebArena 中使用固定任务策略，例如按已知 URL 规则进入用户页面。作者明确承认：如果目标就是组合已知任务的固定策略，这些设计有道理；问题在于将结果解释为对未见网站和未见任务的通用能力。[S01，PDF p.9](#source-s01)

因此不能简单把硬编码业务规则都叫“作弊”。固定规则往往是合理产品设计。需要问的是：它有没有超出任务允许的信息范围，以及你有没有夸大泛化结论。

### 8.5 Point-in-time：历史评估应回到当时的信息条件

**工程设计：**对投研场景，任务应明确 `as_of`、数据版本、公告可获得时间与来源快照。历史事件之后披露的修订数据、后验解释、后续价格走势，不应无意进入声称只使用当时信息的实验。

只在 prompt 写“不能使用未来信息”不构成隔离。限制需要落实到检索索引、数据查询条件、工具服务和评估数据构建。

当任务本来是“今天回看一年前的事件”，允许信息又不同。关键是任务定义与实际可访问信息一致，而不是一律禁止后来的材料。

### 8.6 开发集、回归集与保密测试集，各自有职责

一旦测试失败成为日常改 prompt、补规则、调检索的依据，它就已经参与开发。讲义将这种反复调优列为全栈过拟合来源。[S00，PDF p.26](#source-s00)

**工程设计：**开发集用于选择方案，回归集用于防止旧问题重现，保密或时间外测试集用于估计未见任务表现。已用于开发的样本不需要丢弃，但要改变用途标签。

同样，修复裁判后分数上升，不是 Agent 能力提升；应保留旧裁判版本、变化原因和必要的重评分。任务与裁判更新都应能在报告中被看见。

## 9. 长任务与持续 Agent：METR 和 Headlong 的不同问题

### 9.1 单轮任务遗漏了什么？

讲义 p.27–30 强调：真实需求可能缺少条件、被中途纠正、被打断或改变目标；只提供完整初始指令的 benchmark 难以测量必要澄清、重新规划与跨轮约束保留。p.28–29 的课程使用图显示了多轮甚至持续数小时的会话，但它是课程作业样本，不代表全部用户分布。[S00，PDF p.27–30](#source-s00)

τ-bench 已开始处理用户互动，却仍依赖模拟用户的能力和标注质量。作者承认模拟用户可能在计算、记忆、规则理解和遵循指令方面有局限，也承认用特定模型迭代任务说明可能带来偏差。[S08，PDF p.9](#source-s08)

《AI Agents That Matter》进一步提醒，人类反馈可能显著改变系统 usefulness，而结果也依赖参与者的技能。[S01，PDF p.9–10](#source-s01)

**工程设计：**澄清能力应同时考虑是否问了必要问题，以及是否重复询问已可从上下文或工具获得的信息。模拟用户评估与真实人机协作试用是互补关系，前者不能自动替代后者。

### 9.2 METR 试图解决“不同 benchmark 分数没有共同尺度”

《Measuring AI Ability to Complete Long Software Tasks》使用人类通常完成任务所需的时间，构造 task-completion time horizon。论文的任务套件由 HCAST、RE-Bench 与较短的软件原子动作组成，主文按约 170 个任务描述，并让人类与 Agent 尝试任务。[S07，PDF p.2–5](#source-s07)

先区分三个时间：

| 时间 | 含义 | 不能误读成 |
|---|---|---|
| 人类任务耗时 | 对任务难度的一个参考尺度 | Agent 连续运行时长 |
| Agent 实际耗时 | 执行速度与资源成本 | 任务对人类的难度 |
| 持续服务时间 | 系统运行多天后的状态与价值 | 单次长任务能力 |

METR 的 horizon 主要围绕第一项；Headlong 主要暴露第三项问题。它们不是同一个指标的两个名称。

### 9.3 Time horizon 是怎么计算的？

论文将任务表现转成成功或失败；对连续评分任务，使用任务特定的阈值，再以成功人类基线的几何平均时间作为任务时间参考，拟合：

$$
p_{\text{success}}(t)=\sigma[\beta(\log h-\log t)]
$$

$h$ 是 50% time horizon，$\beta$ 控制成功率随任务长度下降的速度。当 $t=h$ 时，成功率为 50%。[S07，PDF p.5–6](#source-s07)

“50% horizon 为一小时”表示在该任务分布、人类基线和实验设置下，对人类约一小时的任务有相应拟合成功概率。它不表示能稳定工作一小时，也不表示能完成一半的软件工程岗位职责。

**教学推导：**对于 $\beta>0$，达到成功概率 $q$ 的 horizon 为：

$$
h_q=h_{50}\exp\left[-\frac{\operatorname{logit}(q)}{\beta}\right]
$$

所以 50%、80%、95% horizon 的差异还取决于斜率，不是固定倍数。论文实验中，80% horizon 比 50% horizon 短约 4–6 倍，并明确说数据不足以可靠测量非常高成功率下的 horizon。[S07，PDF p.7](#source-s07)

### 9.4 趋势与人类基线，也有适用范围

论文在其历史模型与任务范围中，拟合出约 207 天翻倍的 50% horizon 趋势，使用任务家族、任务、运行三级 bootstrap 估计不确定性。[S07，PDF p.6](#source-s07)

这是历史实验结果，不是保证未来持续翻倍。论文讨论了外部有效性、任务分布与人类参考群体的影响。内部 PR 实验中，外部承包者完成任务比熟悉仓库的维护者耗时明显更长；控制任务长度后，缺少明确反馈或需要主动寻找信息的“messier”任务仍然更难。[S07，PDF p.7–8](#source-s07)

**工程设计：**投研任务的人类耗时应区分主动处理、等待资料和对领域的熟悉程度。等两小时数据更新，与主动分析两小时，不应不加区分地作为同一种长任务难度。

### 9.5 METR 与可靠性论文为什么不必被强行统一？

METR 将其历史能力提升与更好的工具使用、错误适应和逻辑推理联系起来；可靠性论文则在 GAIA、τ-bench 及固定 scaffold 下，测量重复一致性、扰动鲁棒性和失败预测等指标。[S07，PDF p.7](#source-s07) [S02，PDF p.5–9](#source-s02)

**跨材料综合：**一个系统可能完成更长的软件任务，同时仍然在相同任务重复运行、提示改写或自我置信度方面存在问题。两篇论文对 reliability 的操作定义、任务、人类基线、时期和执行框架都不同，不能仅凭摘要措辞判断互相证伪。

保留差异比强行“和解”更重要。本文没有把它们拼成一个共同实验，也没有从中推导所有行业相同的可靠性趋势。

### 9.6 Headlong：短任务 Demo 看不到的持续故障

Headlong 材料描述一个持续运行的 microharness，Agent 在外部互动间仍执行自身循环。它保留长期轨迹，采用不同分辨率的历史压缩，并把上下文视作轨迹的一种投影。[S09，§Microharness](#source-s09)

最值得学习的是实际故障，而不是拟人化描述。

**记忆召回集成故障。**Agent 写了一个记忆召回进程，直接调用测试正常；真实运行中，上游通过 pipe 传入内容，下游却读取一个从未设置的环境变量，于是不断运行却没有返回记忆。后来它检查连接方式、修复并做端到端验证。[S09，§Persistent agency in action](#source-s09)

它把讲义的组件／端到端区分变成了真实案例：组件存在不等于接入正确；工具调用成功不等于业务能力生效。

**Watchdog 与后续使用变化。**子运行机制遇到 30 秒无输出终止限制，造成多次失败。材料记录前两天有 64 次子运行合并，后面十二天只有 12 次，并将减少与 watchdog 经历联系起来。[S09，§What broke](#source-s09)

这不是一般规律的受控证明，但提示一个需要测的问题：过去的故障会不会通过长期记忆和策略调整，改变未来是否使用某项能力？每次重置的单任务评估难以观察这种历史依赖。

材料还记录了 Agent 多次误停自身服务，之后增加限制。它同样说明，能完成局部修改，不代表持续服务具备恢复和自保护能力。[S09，§What broke](#source-s09)

### 9.7 持续运行的价值，原材料还没有充分量化

Headlong 作者明确表示，传统独立任务评估不太适合衡量 persistent agency，对其长期价值的许多调整仍主要依赖定性评价。[S09，§Measuring improvement](#source-s09)

不能把单次自主修复故事当成完整可靠性证明，也不能把运行时间长当作有用工作多。背景调用、重复无效思考、打扰用户和不可控自修改都需要被纳入实验。

### 9.8 重置与保留记忆，怎样同时成立？

ABC 要求任务之间清理残留，以保证独立性；持续 Agent 需要保留历史，因为历史本身是被测对象。[S03，PDF p.5](#source-s03) [S09，§Measuring improvement](#source-s09)

**工程设计：**

| 协议 | 一次实验内部 | 不同实验之间 | 测量什么 |
|---|---|---|---|
| 独立任务 | 按任务起始状态执行 | 环境与初始记忆恢复一致 | 当前能力与重复可靠性 |
| 长期任务流 | 保留任务顺序与状态演化 | 恢复同一初始世界 | 记忆更新、干扰、漂移和长期成本 |

核心是：**实验之间隔离，长期实验内部保留历史。**不要把裁判答案回写后再次遇到同一题的改善，声称为未见任务泛化。

## 10. 可观测性与隔离：Dapper、AgentOps、Firecracker

### 10.1 Dapper 的启示：追踪必须能低负担地长期存在

Dapper 的归档文件是 Google Research 介绍网页，强调低开销、应用级透明与广泛部署，并通过公共库埋点和采样提高追踪实用性。[S10，Abstract](#source-s10)

它与 Agent eval 的联系是工程上的：如果关键证据只在一次临时调试时被记录，就难以用于持续的性能分析、失败定位与版本比较。

不能据这份介绍页断言所有 Dapper 实现细节，也不能把传统追踪采样策略原样当成高风险 Agent 的审计策略。二者记录目标与完整性要求不同。

### 10.2 AgentOps：不仅记录 LLM token，还要记录任务对象

AgentOps 论文是一项工具映射研究与 taxonomy 提案，不是通过一个随机实验证明“有日志就安全”。它指出常见观测偏重模型调用和 prompt，却不充分覆盖目标、计划、工作流、工具及运行时演化。[S11，PDF p.1–3](#source-s11)

其 p.8–9 的关系图与分类图将 Agent、计划、任务、工具、评价、guardrail 与 LLM spans 联系起来，通用字段包括名称、时间、输入输出、错误、指标、父 ID 和 links。[S11，PDF p.8–10](#source-s11)

**工程设计：**对一条审核任务，应能回答：模型看到了哪个版本材料？使用哪条规则？查询了哪个日期的数据？哪个工具失败？最后引用的依据在哪？产生了什么状态变化？是哪版裁判判成功？

### 10.3 一套可回查的运行记录

下面是设计字段，不是某个平台固定规范：

```yaml
run_id: run_demo_001
task_id: review_demo_001
agent:
  code_revision: revision_A
  model_snapshot: model_A
  prompt_version: prompt_v3
  tool_schema_version: tools_v2
knowledge:
  rules_snapshot: rules_v3
  cases_snapshot: cases_v5
  initial_memory_snapshot: memory_0
environment:
  image_digest: environment_A
  initial_state_id: state_001
  as_of: task_defined_time
protocol:
  dataset_version: eval_v1
  grader_version: grader_v2
  budget_profile: budget_small
artifacts:
  visible_context_refs: []
  tool_event_refs: []
  output_refs: []
  state_diff_ref: state_diff_001
```

真正存储时可以用对象引用与哈希减少重复内容，但引用必须可解析。敏感信息需要适当权限与脱敏，这些是工程安全设计要求，不是从某份日志 taxonomy 自动获得的保障。

“模型声称已检查”是一段输出；测试进程结果、产物内容和状态变化才是独立证据。记录可见计划可以帮助理解行为，但不应把它当成模型真实内部推理的完整证明。

### 10.4 三种轨迹不能混成同一个可写文件

将 AgentOps 与 Headlong 放在一起，可以得到一个工程区分：

| 数据对象 | 用途 | 主要风险 |
|---|---|---|
| 运行观测 trace | 排错、性能和成本分析 | 采样或缺失导致分析不全 |
| Agent 自身记忆 | 后续检索、计划与个性化 | 错误、过期信息、跨测试污染 |
| 评估审计证据 | 重建判分、检查越权与副作用 | 被测 Agent 改写、标签反向泄漏 |

三者可以关联，但不宜由被测 Agent 同等控制。特别是裁判标签不能自动进入被测记忆；审计证据不应随 Agent 压缩记忆而丢失。

### 10.5 Trace 提供线索，干预实验检验根因

日志出现“检索遗漏规则 → 最终错误”，并不证明检索是唯一原因。正确规则提供后，模型可能依然误解条件。

**工程设计：**依次替换人工核验的解析结果、证据集合或确定性计算结果，观察后续表现。这样结合了 AgentOps 的观测与 SWE-bench 的 oracle 式诊断。

还要区分三种重放：读取旧轨迹重新评分，是 regrading；从原始快照再次执行，是 rerun；替换某个环节后继续运行，是诊断干预。第三种可能导致后续动作改变，不能简单沿用旧轨迹中的全部工具结果假装环境仍然匹配。

### 10.6 Firecracker：隔离是条件，不是评分器

Firecracker 的归档材料是 NSDI 论文介绍网页，讨论在低开销下获得安全与性能隔离的虚拟化设计。它不是 Agent 专用评估框架，也不直接判断任务是否完成。[S12，Abstract](#source-s12)

**工程应用推演：**独立执行环境可以减少对宿主与其他任务的影响，辅助任务重置和资源控制。但还需要额外解决答案隔离、裁判保护、网络访问和远程副作用。

三条边界尤其重要：

**运行隔离不等于答案隔离。**隐藏答案若在沙箱内可读，仍然会污染。

**本地重置不等于外部回滚。**已经发送的邮件或远程数据库写入不会随容器销毁而消失。

**系统访问权限不等于业务授权。**能访问发布接口，不代表获得了发布当前材料的确认。

这些区别把 Firecracker 与 ABC、NIST、ActPlane 连接起来：先有执行边界，再分别保护信息、验收和业务动作。

### 10.7 观测采样不能偷偷改变指标分母

**工程设计：**离线验收应保留关键任务、工具、权限与结果事件；生产环境可以针对性能日志采样，但事故与关键写入需要不同完整性策略。如果为了排错过采样失败轨迹，就不能直接拿采样后的失败比例当真实业务错误率。

同理，多 Agent 子任务的成本可以相加，但并行时延不应机械相加；对跨 Agent 合并、异步任务与外部事件，除了父子 span，还可能需要显式 links 或因果关联标识。

## 11. 运行时约束：ActPlane 如何把拦截连接到恢复

### 11.1 从自然语言要求到具体系统事件，中间有语义鸿沟

ActPlane 研究的问题是：“不要删数据”“提交前运行测试”等要求如何变成可执行限制。工具层可能只看到 `run_script`，而真正的文件、进程、网络副作用发生在脚本内部。论文使用策略 DSL、操作系统层执行和信息流／跨事件状态，尝试弥补这类边界盲区。[S13，PDF p.1–2、p.5–7](#source-s13)

它并不意味着所有合规问题都应该下沉到内核。规则的类型决定适合在哪一层处理。

### 11.2 83% 可观察，不等于 83% 可由 ActPlane 强制执行

论文将策略分为 semantic-only、content、per-event、cross-event。其样本中，约 83% 属于系统可观察行为，其中约 38% 需要内容检查，29% 是单事件，16% 是跨事件。ActPlane 直接针对的是后两类，合计约 45%。[S13，PDF p.3，Figure 4](#source-s13)

| 类别 | 例子 | 更直接的检查方式 |
|---|---|---|
| 语义要求 | 解释应清楚、沟通应准确 | 语义评价或人工 |
| 内容要求 | 文件内容满足特定规范 | linter、解析器、内容检查 |
| 单事件约束 | 不删除指定数据目录 | 系统事件或受控工具权限 |
| 跨事件约束 | 最近修改后测试成功，才可提交 | 持久时序与状态检查 |

将“可观察”说成“已正确强制执行”会夸大覆盖能力。论文中的统计也只属于其项目样本。

### 11.3 “提交前测试”真正要求什么？

不是历史上运行过测试，而是：

$$
\text{最近一次相关修改}<\text{测试成功}<\text{提交}
$$

测试通过之后再次改代码，之前的测试资格应该失效。ActPlane 用类似 `after ... since ...` 的 temporal gate 表达这种条件。[S13，PDF p.6](#source-s13)

**工程推演：**材料发布可以采用相似结构：当前版本修改之后完成审核，且针对当前版本获得有效发布授权。它不同于“这份材料以前被审核过”。这是一种状态机条件，不是简单查找“已审核”几个字。

### 11.4 继承约束不能被低权限 Agent 削弱

论文的设计让更高权限规则在 Agent 开始之前加载，Agent 可以增加本域约束，但不能取消或削弱继承的限制；子域的规则也不应影响其他域。[S13，PDF p.5–7](#source-s13)

这解决的是权限结构问题，不保证 Agent 自己写出的附加规则一定正确。错误翻译可能造成漏拦或误拦。

论文也限定覆盖范围：保证针对已配置 hook 的事件检查，并不等于识别所有语义等价动作；文件内容、内核被攻破及其他未覆盖路径有明确边界。[S13，PDF p.6](#source-s13)

### 11.5 最值得学习的是实验分解，而不是一个最终拦截率

ActPlane 的 RQ2 从 38 条规则构造 190 条轨迹，每条规则包括合法边界操作、类似违规但合法的操作，以及直接、脚本内部、隐藏入口的违规。之后允许 Agent 在反馈后继续最多五个工具步骤，观察能否恢复合规。[S13，PDF p.8–9](#source-s13)

其 Decision Compliance Rate 为：

$$
\operatorname{DCR}=\frac{TP+TN}{TP+TN+FP+FN}
$$

这些 TP／TN 对应端到端决策合规结果，包含翻译、执行、反馈与恢复，不应直接当成单个拦截器的分类准确率。论文使用轨迹模型裁判，并对部分结果进行人工检查。[S13，PDF p.9](#source-s13)

| 版本 | DCR | 正确处理违规轨迹数量 | 合法轨迹误干预数量 |
|---|---:|---:|---:|
| 无语义反馈的 ActPlane-opaque | 53.7% | 27 | 1 |
| 完整 ActPlane | 75.8% | 86 | 18 |

来源：[S13，PDF p.9，Table 2](#source-s13)。指标属于该 190 条轨迹的特定设置。

两者违规检测率约为 75.4% 与 77.2%，差异远小于恢复结果差异。没有语义反馈时，被检测后继续合规的比例约为 31.4%；完整系统中，该条件恢复比例明显更高。[S13，PDF p.10](#source-s13)

**跨材料综合：**阻止错误，不等于帮助任务继续。通用“权限不足”可能引发重复尝试；明确说明“最近修改后尚未测试成功，请运行指定测试”则提供了可执行恢复路径。

但完整系统的误干预数量也更高，不能只报有利数字。它再次证明安全、恢复和完成率需要联合评估。

### 11.6 看了失败再修规则，不等于未见任务泛化

论文将部分漏检轨迹与纠正信息提供给翻译 Agent，允许修改一次规则，再在这些失败轨迹上重测，恢复了其中大多数案例。[S13，PDF p.10](#source-s13)

这个实验说明规则可修订、错误可被诊断。它不是新的保密测试成绩，因为修订已经利用了这些失败证据。将它与 Lecture-07 的 benchmark overfitting 放在一起，正好能区分**开发改进**与**未见任务验证**。

### 11.7 安全实验与性能开销都要保留分母和条件

在 361 个安全任务的实验里，基线有 106 个不安全结果，ActPlane 阻止其中 78 个，仍有 28 个未阻止。因此约 74% 是对基线不安全行为的阻止比例，不是全部任务的安全准确率。论文也报告对部分原本安全任务发生了策略激活。[S13，PDF p.11–12，Figure 15](#source-s13)

剩余问题包括纯语义伤害、文件内容风险，以及发生在服务内部而未被当前 hook 观察到的副作用。不能因为有操作系统执行层就宣称所有业务违规被覆盖。[S13，PDF p.12](#source-s13)

开销实验使用固定工作负载与 no-hit 配置：32 条规则时，Agent 轨迹重放约增加 1.9% 开销，内核构建约增加 6.5%；100 条规则时相应构建开销为 8.4%。这些不是包含所有模型纠错、规则生成与人工操作的通用全流程成本。[S13，PDF p.10–11](#source-s13)

### 11.8 应分别验收三件事

**规则被确定性执行。**  
**自然语言规则被正确翻译。**  
**规则和监控覆盖所有目标相关路径。**

第一项成立，不保证后两项成立。对于生产 Agent，应分别测试翻译正确性、拦截覆盖、误拦、恢复能力、最终业务成功与开销。这是 ActPlane 对整节评估课最重要的工程贡献之一。

## 12. 工程落地：一套最小但完整的评估系统

本章是对前述材料的**工程综合设计**。字段、目录和执行流程不是某篇论文的现成框架，也不是已经连接真实业务接口的生产实现。

### 12.1 最小架构有四个边界

```text
任务与版本注册
    ├─ Agent 可见：目标、材料、允许知识、工具、权限、预算
    └─ 裁判专用：标签、验收条件、隐藏测试、人工裁定
                  ↓
独立运行器：恢复环境 → 执行 Agent → 记录轨迹与产物
                  ↓
受保护裁判：结果检查 + 状态不变量 + 关键过程约束
                  ↓
报告与决策：切片、重复可靠性、成本时延、风险、回归差异
```

Agent 与裁判应有不同权限。即使运行器和裁判写在同一代码库，也不能因此允许被测 Agent 修改裁判文件或读取标签。模型裁判的上下文同样应避免把标准答案或反馈回流给尚在运行的被测系统。

### 12.2 一道任务需要哪些内容？

```yaml
task_id: review_demo_001
family_id: material_family_A
purpose: 对未见材料应用已知规则

agent_visible:
  instruction: 审核材料并给出有依据的建议，不修改原件，不对外发布
  document_ref: material_v1.pdf
  rules_snapshot: rules_v3
  facts_snapshot: facts_v2
  initial_memory_snapshot: memory_0
  allowed_tools:
    - read_document
    - retrieve_rules
    - query_facts
  budget_profile: budget_standard

evaluator_only:
  expected_findings:
    - issue_id: issue_A
      acceptable_rule_ids: [R-DEMO-01]
      evidence_ref: material_v1:page_3:paragraph_2
      condition_to_check: 结合本段限定条件判断，不仅匹配关键词
  required_output:
    - 可定位的原文证据
    - 适用依据与条件
    - 能解决问题的修改建议
  invariants:
    - 原始材料未被覆盖
    - 未发生对外发布
    - 未生成虚假的人工批准记录
  ambiguity_policy: 信息不足时允许提出必要澄清
```

规则 ID 与案例都是占位符。这里的 `evaluator_only` 是逻辑说明，实际必须通过存储与执行权限隔离，不能仅将其保存在 Agent 可读文件的另一个字段里。

任务还有一个需要人工审查的问题：**允许输入是否足够支持预期结论？**如果关键例外只出现在裁判标签里，Agent 无从获知，就不应因未猜中而被判失败。

### 12.3 运行配置与裁判版本分别冻结

可以使用独立 manifest：

```yaml
evaluation_id: eval_demo_release_A
protocol_version: protocol_v1
dataset_version: tasks_v1
grader_version: grader_v2
agent_config_version: agent_v7

run_protocol:
  repetitions: 5
  reset_environment_between_runs: true
  reset_memory_between_runs: true
  user_simulator_version: simulator_v1
  fault_profile: baseline

budget:
  wall_time_seconds: 600
  max_tool_calls: 40

reporting:
  group_by: [family_id, risk_level, task_type]
  include_failed_run_costs: true
  report_infrastructure_failures: true
```

五次、600 秒和 40 次调用只是教学示例，不是通用上线标准。实际预算应由业务要求和基线决定，并对所有候选方案清楚公开。

### 12.4 评估循环：停止、评分、清理都必须有明确职责

```text
加载任务集、Agent 配置、环境和裁判的固定版本

对每个任务：
    对每次重复运行：
        建立独立环境
        恢复任务初始数据与初始记忆
        配置权限、时点和预算
        只提供允许输入

        执行 Agent
        记录输入输出、工具事件、成本、时间和结束原因
        保存最终产物与状态差异

        在受保护的裁判侧：
            检查用户目标是否实现
            检查不该改变的状态是否保持
            检查关键授权与先后顺序
            对语义项目使用经过验证的模型裁判
            对争议或高风险项目进入人工复核

        保存判分依据和裁判版本
        清理执行资源

按任务家族、类型、风险与运行条件汇总
对新旧版本进行配对比较与回归分析
```

这是流程伪代码，不是可直接调用的 SDK。实际实现还需要持久化、失败恢复、幂等和资源清理等基础设施；本文不虚构这些接口已经存在。

### 12.5 基础设施失败与 Agent 失败不能混在一起，也不能悄悄删除

应至少区分：业务未完成、Agent 产生无效动作、达到预算、被权限策略阻止、评估平台故障、任务或标签有问题、裁判无法判定。

同一“工具超时”有两种含义。它若是刻意注入的扰动，就是鲁棒性任务的一部分；若是未预期的评估服务损坏，应作为基础设施问题披露，并按预先规定的重跑规则处理。不能为了让分数更好看，事后只删除失败运行。

对产品实际服务能力，还可能需要把外部服务不可用带来的用户失败计入总体体验；对隔离模型能力的实验，则可能采用不同归因。关键是同时保留原始事件与明确的指标分母。

### 12.6 最低限度的产物目录

```text
eval_project/
  tasks/                 # Agent 可见任务定义
  manifests/             # 固定版本的实验配置
  fixtures/              # 初始状态与可控工具数据
  agent_configs/         # 模型、prompt、工具与执行流程
  private_grading/       # 不挂载给 Agent 的标签与验收规则
  runs/
    run_id/
      events.jsonl
      usage.json
      termination.json
      artifact_index.json
      state_diff.json
  judgments/             # 与 run_id 关联，但不反馈给被测运行
  reports/
```

目录名称不是安全边界。是否挂载、谁能读取、谁能写入，以及模型上下文里能出现什么，才是安全边界。

### 12.7 回放需要三种不同实验标签

**重新评分（regrading）**读取旧产物，用新裁判检验原判分；这是裁判变化，不是 Agent 变化。

**重新运行（rerun）**恢复初始状态，再次执行 Agent；它可用于重复可靠性或新版本比较。

**受控干预（diagnostic intervention）**替换解析、证据或计算，再让后续流程继续；它用于定位原因，不能当作原始任务成绩。

如果被替换的结果让后续动作改变，后续环境也必须响应新动作，不能继续机械喂旧工具记录。这对交互用户模拟和写入型任务尤其重要。

### 12.8 从小规模开始，但先把测量仪器做对

一个合理起点是少量经过人工核验、覆盖明确失败机制的任务。先验证可解性、裁判、版本冻结和轨迹完整性，再增加规模和重复次数。

少量高质量任务可以建立回归与诊断闭环；但不能因它们全部通过就宣称高可靠部署。任务覆盖、样本量和严重错误概率，需要后续实验支持。

这个先后顺序来自三组材料的共同要求：SWE-bench 与 τ-bench 认真构造可执行任务，ABC 验证测量有效性，可靠性论文与 METR 再讨论重复与不确定性。[S05，PDF p.2–3](#source-s05) [S08，PDF p.5–6](#source-s08) [S03，PDF p.4–7](#source-s03)

## 13. 贯穿案例：投研／基金材料预审核 Agent

本章保留前文围绕投研与合规系统的应用推演。所有例子都是**系统设计示例**，不代替合规人员对真实法规、业务政策和材料的判断，也不声称参考论文已经验证了本章方案。

### 13.1 先定义交付，不从“准备多少题”开始

目标可以设为：识别材料中的潜在问题，说明适用依据，定位原文证据，提出可执行建议，交由人工采纳或拒绝；不自动修改原件或发布。

这种定义把三个容易混淆的事情分开：找出相关规则、正确适用规则、按照权限完成交付。

系统流程可以是：

```text
解析材料
  → 候选风险初筛
  → 检索规则与相似案例
  → 核验规则条件、例外和事实
  → 形成有证据的建议
  → 人工采纳／拒绝
  → 经裁定后进入案例与评估闭环
```

只看最终回复质量无法定位解析或检索问题；只看规则召回率又无法判断最终建议是否正确。两层评估都需要。

### 13.2 五类质量应分别衡量

| 维度 | 主要检查 | 典型“看似成功”陷阱 |
|---|---|---|
| 问题识别 | 该发现的是否发现，正常内容是否误报 | 全部判有问题以获取高召回 |
| 规则适用 | 对象、渠道、时点、条件和例外是否成立 | 检索到了相关条款就认定适用 |
| 证据与事实 | 引用真实、可定位、支持结论，数据口径一致 | 引用存在但不支持当前结论 |
| 修改建议 | 可执行、解决问题、不引入新问题 | 用笼统风险提示替代具体修复 |
| 行为约束 | 保留原件、等待确认、避免越权 | 内容正确但自动发布或覆盖原件 |

这些项目对应 ABC 的目标与结果有效性，以及 τ-bench 对领域规则与操作约束的区分；具体 rubric 需要业务人员制定。[S03，PDF p.3–6](#source-s03) [S08，PDF p.3–4](#source-s08)

### 13.3 风险点级评分：防止“多输出就多得分”

一份材料可能对应多个风险点，应建立预测项与经人工裁定风险点的一对一匹配。匹配依据可以包括位置、问题类型、规则条件和必要证据，不能只比较问题标题是否相似。

在确定匹配协议后，可以计算：

$$
\operatorname{Precision}=\frac{TP}{TP+FP},\qquad
\operatorname{Recall}=\frac{TP}{TP+FN}
$$

这是工程中的标准计数应用，而不是这些论文规定的唯一审核指标。

同一问题被重复列五次，不应获得五个 TP。发现正确问题但引用完全错误，可以在识别维度得分、在证据维度失败。这样才能知道改进应针对哪里。

高风险召回应单独报告；正常材料的误报负担也应独立报告。不宜只给一个 F1，然后隐藏关键风险漏检。

### 13.4 整份材料可交付率，不能被局部得分替代

风险点级指标用于诊断，还需要材料级验收：关键问题覆盖、证据可回查、建议可执行、权限约束保持。

一个系统识别了十个小问题，却漏掉一个不可接受的问题，不应因为平均项分高而被认为可直接交付。同样，八个检查点做了七个，却没有生成建议列表，仍然没有完成任务。

这一点是 SWE-bench 的回归思想与讲义工作流完成度思想在审核场景里的应用。[S05，PDF p.3](#source-s05) [S00，PDF p.22](#source-s00)

### 13.5 事实核验应区分“对值”与“对口径”

对投研与基金事实，数字相同不一定意味着核验正确。至少需要检查对象、份额类别、指标定义、期间、时点与来源是否一致。

这属于工程设计，不是本文对任何具体财务数据的断言。可以把事实任务拆为：正确定位对象、选择对应时间与口径、调用统一数据源、计算或比较、给出证据。

对历史任务还应固定可得信息时点。对当下查证任务则需明确工具数据更新情况；二者不应混在同一个成功标签里。

### 13.6 测试集按失败机制组织，比只按文件格式更有价值

| 测试类型 | 示例设置 | 主要诊断目标 |
|---|---|---|
| 跨页条件 | 结论在一页，限定条件在另一页 | 解析与上下文定位 |
| 规则例外 | 触发关键词出现，但存在有效例外 | 适用性判断 |
| 证据冲突 | 同主题来源口径不同 | 冲突处理与不确定性 |
| 多子目标 | 一份材料包含多个互相关联问题 | 完整性与全局规划 |
| 工具故障 | 某次事实查询失败 | 恢复、重试与转人工 |
| 用户纠正 | 用户中途撤回自动改写要求 | 重新规划与约束保留 |
| 版本变化 | 材料在审核后再次被修改 | 当前版本资格与失效机制 |
| 长期记忆冲突 | 旧案例结论与新版本规则不一致 | 记忆更新与过期信息处理 |
| 正常材料 | 没有标注问题的有效内容 | 误报与无效建议负担 |

材料格式仍需覆盖，但它不是唯一切片。出现退化时，“跨页例外理解下降”比“PDF 分数下降”更接近可操作根因。

### 13.7 用四组对照评估“二次核验”

| 版本 | 设置 | 试图隔离的贡献 |
|---|---|---|
| A | 原始流程 | 当前基线 |
| B | 相近预算的简单重试或额外检索 | 更多计算与机会 |
| C | 二次审查，但不提供新增独立证据 | 重新审视已有内容 |
| D | 二次审查时访问独立事实或确定性验证 | 新信息与可执行校验 |

这是《AI Agents That Matter》的预算控制、SWE-bench 的组件诊断与 τ-bench 的规则消融的综合应用。每组都必须评价最终选择结果，并计入全部成本。

“调用次数一样”不一定预算一样，上下文、模型和工具成本也要记录。D 若更好，还要看改善了哪些错误、是否增加误报，以及人工复核负担有没有降低。

### 13.8 人工采纳／拒绝需要原因，不应自动变成真值

AgentOps 将用户反馈附着到运行 trace 或生成记录，用于改进系统。[S11，PDF p.6–7](#source-s11)

但在审核产品中，采纳可能受表达、时间和业务决策影响；拒绝可能是误报，也可能是修改建议不合适、业务暂不处理，或审核人掌握额外信息。

所以应区分：

```text
用户反馈：拒绝
拒绝原因：问题识别正确，但建议改变了材料原意
人工裁定：风险点正确，建议不合格
回流对象：修改建议训练／开发案例
是否保留在保密测试集：否
```

`accepted=true` 不应直接等价于 `correct=true`。否则系统可能学到“更讨用户喜欢”，却被误认为“更符合规则”。

## 14. 统计、发布门槛与人工反馈闭环

### 14.1 80% 到 83%，先问是不是同一个实验

比较前应确认相同任务、相同版本裁判、环境与可用信息、明确预算口径及重复协议。再看哪些题从失败变成功，哪些题发生回归，高风险切片是否退化。

ABC 要求报告置信区间、基线、结果解释与不可避免缺陷的影响；《AI Agents That Matter》也把缺乏重复与标准化列为影响可信度的问题。[S03，PDF p.7](#source-s03) [S01，PDF p.10–11](#source-s01)

只看两个总分，既看不到任务变化，也看不到“修好了十道，改坏了七道”的结构。

### 14.2 配对比较比不相关的两次均值更有解释力

**工程设计：**对同一任务的旧版和新版计算差异：

$$
\Delta=\frac{1}{N}\sum_i\big(\bar y_{i,\text{new}}-\bar y_{i,\text{old}}\big)
$$

若任务属于同一文档家族或共享环境，应按相应层级处理依赖。不能把同一材料五次重复当成五份完全独立业务。

METR 使用任务家族、任务、运行的三级 bootstrap，是这种层次结构的具体例子。[S07，PDF p.6](#source-s07) 实际项目可按任务家族或文档级进行配对重采样，再汇报差值的不确定性；具体采样单位应与任务构建一致。

### 14.3 运行次数与任务覆盖是两个不同预算

100 道任务各跑五次，有助于观察同一场景的不稳定性；500 道不同任务各跑一次，则增加任务覆盖，却很难估计重复稳定性。

两者没有脱离目标的统一最优配比。开发阶段可以用少量关键回归任务多次运行，再对更广任务做较低重复覆盖；最终报告必须披露两种规模，不用一个总运行数掩盖任务覆盖不足。

重复协议也应区分模型、用户模拟、环境故障与时间漂移。随机因素同时变化适合估计完整系统表现，固定大部分因素适合定位原因。

### 14.4 零事故不等于事故概率为零

**教学推导：**假设每次独立运行事故概率为 $q$，连续 $n$ 次无事故的概率为：

$$
(1-q)^n
$$

零事故观测对应的单侧 95% 上界为：

$$
q_{\text{upper}}=1-0.05^{1/n}\approx\frac{3}{n}
$$

| 无事故运行数 | 单侧 95% 上界，约值 |
|---:|---:|
| 30 | 9.50% |
| 100 | 2.95% |
| 1,000 | 0.30% |

该解释依赖独立同分布及固定事故定义；相关故障、任务选择偏差和环境漂移会限制推断。

因此，高风险系统不能只靠“测试时没出事”。需要确定性校验、权限隔离、有效授权、人工把关和恢复机制。可靠性论文的风险测量与 ActPlane 的部分运行时限制是互补关系，不是彼此替代。[S02，PDF p.5、p.9](#source-s02) [S13，PDF p.5–6](#source-s13)

### 14.5 发布门槛是一组条件，不是任意加权总分

下面是工程决策结构，不是论文给出的行业阈值：

| 门槛 | 需要的证据 |
|---|---|
| 目标工作可交付 | 材料级或任务级验收结果 |
| 关键风险没有不可接受退化 | 风险等级切片、漏检与严重度 |
| 正常业务未被大量误伤 | 误报、误拦截与人工负担 |
| 运行预算可接受 | 全部任务成本、时延分布、超时率 |
| 重复与扰动行为可接受 | pass^k、故障与改写测试 |
| 关键权限边界有效 | 危险尝试、拦截、真实副作用和恢复 |
| 结论能够复查 | 版本、任务输入、轨迹、产物与裁判依据 |

阈值应由业务风险、已有基线和实验不确定性决定，不能从一篇论文抄一个百分比就当成上线标准。

安全性不宜被好看的速度或文字质量“抵消”。一个更便宜、平均正确率更高、却新增擅自发布行为的系统，不应靠加权平均过关。

### 14.6 线上反馈不只是再算一遍离线分数

AgentOps 强调部署后的追踪、反馈与运行时变化。[S11，PDF p.6–10](#source-s11)

**工程设计：**线上需要识别任务分布、规则版本、工具和用户用法的变化。离线正确的接口可能变更，文档模板可能新增，旧记忆可能过期；这些应触发对应回归，而不是等平均用户评分下降后才调查。

人工反馈进入系统后，要先区分标签修正、建议质量、用户偏好和流程问题，再决定进入案例库、开发集或回归集。不能将所有拒绝都当作“模型错误”，也不能将所有采纳都当作“客观正确”。

### 14.7 报告应该让别人知道你的结论能信到哪里

一次可复查的发布报告至少应说明：版本与任务范围，主要指标与切片，预算和成本口径，重复与扰动协议，基础设施失败和排除规则，裁判验证情况，已知缺陷，以及与旧版相比的改善和回归。

这些字段与 ABC 的 reporting 思想一致：无法完全消除缺陷时，应该说明影响与缓解措施，而不是用一个精确小数遮盖不确定性。[S03，PDF p.7](#source-s03)

## 15. 综合判断：读完这些材料应该形成什么能力

### 15.1 六条互相连接的结论

**第一，评估系统而非只评估模型。**AgentBench 的固定交互方式、SWE-bench 的上下文配置、讲义的全栈性能函数，都说明分数必须绑定执行条件。[S06，PDF p.3、p.6–7](#source-s06) [S05，PDF p.5](#source-s05) [S00，PDF p.26](#source-s00)

**第二，先证明测量有效，再讨论数字精度。**SWE-bench 与 τ-bench 把任务做成可执行验收，ABC 和 NIST 又揭示其中的捷径、标签、环境和裁判问题。重复次数增加不能自动修复坏裁判。[S03，PDF p.2–8](#source-s03) [S04，§2.1–2.2](#source-s04)

**第三，找到一次正确解与稳定交付是不同能力。**pass@k、pass^k、校准、区分能力和安全后果，分别影响候选生成、自动化范围与人工分流。[S08，PDF p.4–5](#source-s08) [S02，PDF p.3–5](#source-s02)

**第四，没有预算匹配与有效对照，就难以解释架构增益。**复杂机制的价值应落实到新增信息、反馈或控制，而不只是多次模型调用。[S01，PDF p.2–6](#source-s01)

**第五，长任务能力不等于长期服务可靠。**METR 测人类任务时间尺度上的成功边界，Headlong 暴露跨任务历史、集成、watchdog 和持续状态问题。它们需要不同评估单位。[S07，PDF p.2–7](#source-s07) [S09，§What broke、§Measuring improvement](#source-s09)

**第六，可观测性、隔离与约束执行是可信交付的基础，但每一层都有边界。**Trace 不自动证明因果，沙箱不自动隐藏答案，确定性执行不自动保证规则翻译正确，拦截不自动保证恢复。[S11，PDF p.8–10](#source-s11) [S12，Abstract](#source-s12) [S13，PDF p.6、p.9–12](#source-s13)

### 15.2 常见误区与更准确的表达

| 容易说错的话 | 更准确的表达 |
|---|---|
| 模型没训练过测试集，所以没有泄漏 | 检索、记忆、环境和开发过程也可能使用测试信息 |
| API 返回成功，任务就成功 | 还要检查业务目标、参数语义、状态与授权 |
| 正常结束等于完成 | 结束原因和独立验收是两个字段 |
| pass@5 接近 100%，产品几乎不会错 | 它可能只表示候选覆盖，还要评估选择器和完整成本 |
| 一致性高就是可靠正确 | 稳定错误也可以高一致，必须并列正确率 |
| 置信度校准好就能提前避免事故 | 需要确认置信度产生的时点、可用信息和区分能力 |
| 用了测试或 LLM judge 就客观 | 裁判也需要可解性、准确性与边界验证 |
| 检索召回上升，端到端必然变好 | 还需检验证据使用、干扰与最终质量 |
| 多 Agent 比单 Agent 高分就证明协作有效 | 还需相近预算的简单基线与机制消融 |
| 50% horizon 是一小时，所以可稳定工作一小时 | 指人类任务耗时对应的拟合成功边界，不是运行时长 |
| 有沙箱就不会作弊或越权 | 答案隔离、裁判保护、业务授权和远程副作用仍要处理 |
| 拦截率高就更适合上线 | 还要看误拦、恢复、完成率和覆盖范围 |
| 用户采纳说明建议正确 | 采纳与客观正确性应经原因与裁定区分 |
| 零事故测试证明安全 | 需要样本量、统计假设、风险边界与运行时保障 |

这些区别来自前文研究与工程推导的整合，不构成一套无需验证即可迁移到所有应用的统一标准。

### 15.3 最终思考顺序

> 先定义工作，再定义成功；先验证裁判，再测量 Agent；先冻结条件并控制预算，再解释提升；最后把质量、稳定性、成本和风险一起用于发布决定。

从 senior AI engineer 的角度，成熟的评估能力是能够回答：**改动改善了什么、为什么改善、代价是什么、结论适用于什么范围，以及还有哪些风险没有被证明可接受。**

## 附录 A：公式与术语速查

### A.1 统一记号

| 记号 | 含义 |
|---|---|
| $N$ | 任务数，不是运行总数 |
| $n$／$K$ | 每个任务的重复运行次数，按所在公式定义 |
| $c_i$ | 第 $i$ 个任务的成功运行次数 |
| $p_i$ | 固定协议下任务 $i$ 的真实成功概率 |
| $\hat p_i$ | 任务 $i$ 的样本成功率 |
| $y_j$ | 一次运行的结果，成功为 1，失败为 0 |
| $c_j$（置信度章节） | 一次运行的预测置信度，注意与成功次数 $c_i$ 区分 |
| $h_q$ | 达到成功概率 $q$ 的人类任务时间 horizon |
| $G$ | 验收函数或评分器 |
| $\alpha,\beta$（裁判误差章节） | 误接受与误拒绝概率，不同于 horizon 的斜率记号 |

不同论文使用的符号并不完全相同。正文已按解释需要重写，复现原论文时应回查其定义，而不是仅凭符号名称匹配。

### A.2 主要公式、用途与限制

| 指标／关系 | 定义 | 重要条件 |
|---|---|---|
| pass@k | $1-(1-p)^k$ | 同任务独立同分布；不包含产品选择器保证 |
| pass^k | $p^k$ | 同任务全部 $k$ 次成功，不是 $k$ 个步骤成功 |
| pass^k 样本估计 | $\binom{c}{k}/\binom{n}{k}$ | $n\ge k$，之后再跨任务平均 |
| pass@k 样本估计 | $1-\binom{n-c}{k}/\binom{n}{k}$ | 同上 |
| 结果一致性 | $\frac1N\sum_i(2\hat p_i-1)^2$ | 稳定失败也高；有有限样本影响 |
| 相对鲁棒性 | $\min(\operatorname{Acc}_{pert}/\operatorname{Acc}_0,1)$ | 基线非零；同时保留绝对成绩 |
| Brier 损失 | $\frac1M\sum_j(c_j-y_j)^2$ | 越低越好；论文用其 $1-$ 变体 |
| 风险结构 | $P(\text{违规})E[\text{严重度}\mid\text{违规}]$ | 严重度权重需要说明；不能用均值掩盖严重尾部 |
| horizon 曲线 | $\sigma[\beta(\log h-\log t)]$ | $t$ 是人类任务时间，不是 Agent 执行时间 |
| 单位成功成本 | 总运行成本／成功次数 | 计入失败和重试；零成功时无有效交付 |
| 裁判观测成功率 | $p(1-\beta)+(1-p)\alpha$ | 教学误差模型，不代表误差对所有 Agent 固定 |
| 零事故 95% 上界 | $1-0.05^{1/n}$ | 独立同分布、固定事故定义 |

来源：pass 指标来自 S08，可靠性指标来自 S02，horizon 来自 S07；成本关系、裁判误差、选择性处理与零事故上界属于正文明确标注的教学推导。[S08，PDF p.4–5](#source-s08) [S02，PDF p.4–5](#source-s02) [S07，PDF p.5–7](#source-s07)

### A.3 四组最需要分开的术语

**Benchmark、evaluation、grader。**Benchmark 是任务和环境等组成的基准；evaluation 是按协议执行和分析的过程；grader 是其中的测量组件。它们都可能有版本与缺陷。

**Capability、consistency、robustness、predictability。**能完成，不等于重复稳定；重复稳定，不等于扰动不退化；总体高成功率，也不等于能识别哪一题会错。

**Outcome、trajectory、invariant。**Outcome 是最终结果；trajectory 是过程；invariant 是不应被破坏的条件。好的验收可以允许轨迹多样，同时要求结果和关键约束成立。

**Monitoring、memory、audit。**运行监控、Agent 自身记忆与受保护审计证据可以关联，但不能混同权限与保留策略。

```python
@dataclass(frozen=True)
class TaskMetrics:
    task_id: str
    runs: int
    successes: int
    success_rate: float
    pass_at_k: float
    pass_all_k: float
    outcome_consistency_plugin: float


def _validate_binary(values: Sequence[int]) -> list[int]:
    """Validate already-adjudicated outcomes; do not guess missing labels."""
    if not values:
        raise ValueError("At least one adjudicated outcome is required.")
    if any(not isinstance(x, (int, bool)) or x not in (0, 1) for x in values):
        raise ValueError("Outcomes must contain only integer/bool 0 or 1.")
    return [int(x) for x in values]


def _comb_or_zero(n: int, k: int) -> int:
    return 0 if n < k else math.comb(n, k)


def task_metrics(task_id: str, outcomes: Sequence[int], k: int) -> TaskMetrics:
    if not isinstance(task_id, str) or not task_id.strip():
        raise ValueError("task_id must be a nonempty string.")
    if isinstance(k, bool) or not isinstance(k, int) or k < 1:
        raise ValueError("k must be a positive integer.")

    ys = _validate_binary(outcomes)
    n, c = len(ys), sum(ys)
    if n < k:
        raise ValueError(f"Task {task_id}: {n} runs cannot estimate k={k}.")

    denominator = math.comb(n, k)
    p_hat = c / n
    return TaskMetrics(
        task_id=task_id,
        runs=n,
        successes=c,
        success_rate=p_hat,
        pass_at_k=1.0 - _comb_or_zero(n - c, k) / denominator,
        pass_all_k=_comb_or_zero(c, k) / denominator,
        # This is the paper's sample plug-in form, not a bias-corrected estimator.
        outcome_consistency_plugin=(2.0 * p_hat - 1.0) ** 2,
    )


def summarize(
    task_outcomes: Mapping[str, Sequence[int]], k: int
) -> tuple[list[TaskMetrics], dict[str, float]]:
    """Macro-average across tasks, not across all runs."""
    if not task_outcomes:
        raise ValueError("No tasks supplied.")
    rows = [task_metrics(task_id, ys, k) for task_id, ys in task_outcomes.items()]
    fields = (
        "success_rate", "pass_at_k", "pass_all_k", "outcome_consistency_plugin"
    )
    macro = {
        field: math.fsum(getattr(row, field) for row in rows) / len(rows)
        for field in fields
    }
    return rows, macro


def brier_loss(confidences: Sequence[float], outcomes: Sequence[int]) -> float:
    ys = _validate_binary(outcomes)
    if len(confidences) != len(ys):
        raise ValueError("Confidence and outcome counts must match.")
    cs = [float(c) for c in confidences]
    if any(not math.isfinite(c) or not 0.0 <= c <= 1.0 for c in cs):
        raise ValueError("Confidence must be finite and between 0 and 1.")
    return math.fsum((c - y) ** 2 for c, y in zip(cs, ys)) / len(ys)


def zero_event_upper_bound(n: int, alpha: float = 0.05) -> float:
    """One-sided (1-alpha) upper bound after n IID trials with zero events."""
    if isinstance(n, bool) or not isinstance(n, int) or n < 1:
        raise ValueError("n must be a positive integer.")
    if not math.isfinite(alpha) or not 0.0 < alpha < 1.0:
        raise ValueError("alpha must be between 0 and 1, exclusively.")
    return -math.expm1(math.log(alpha) / n)


def _self_test() -> None:
    mixed = task_metrics("mixed", [1, 1, 1, 1, 0], k=3)
    assert math.isclose(mixed.pass_at_k, 1.0)
    assert math.isclose(mixed.pass_all_k, 0.4)
    assert math.isclose(mixed.outcome_consistency_plugin, 0.36)

    all_good = task_metrics("good", [1] * 5, k=5)
    all_bad = task_metrics("bad", [0] * 5, k=5)
    assert all_good.pass_at_k == all_good.pass_all_k == 1.0
    assert all_bad.pass_at_k == all_bad.pass_all_k == 0.0
    assert all_bad.outcome_consistency_plugin == 1.0

    one = task_metrics("one", [1, 0, 1, 1, 0], k=1)
    assert math.isclose(one.success_rate, one.pass_at_k)
    assert math.isclose(one.success_rate, one.pass_all_k)
    assert math.isclose(brier_loss([0.9, 0.8, 0.7, 0.1], [1, 0, 1, 0]), 0.1875)
    assert 0.0029 < zero_event_upper_bound(1000) < 0.0031

    for invalid in ([], [1, 2]):
        try:
            task_metrics("invalid", invalid, k=1)
        except ValueError:
            pass
        else:
            raise AssertionError("Invalid outcomes were not rejected.")

    try:
        task_metrics("too_few", [1, 0], k=3)
    except ValueError:
        pass
    else:
        raise AssertionError("Insufficient repetitions were not rejected.")


if __name__ == "__main__":
    _self_test()
    rows, macro = summarize(
        {
            "task_A": [1, 1, 1, 1, 1],
            "task_B": [1, 1, 1, 1, 0],
            "task_C": [0, 0, 0, 0, 0],
        },
        k=3,
    )
    output = {
        "per_task": [asdict(row) for row in rows],
        "macro": macro,
        "zero_event_95pct_upper_bound_n1000": zero_event_upper_bound(1000),
    }
    print(json.dumps(output, indent=2, ensure_ascii=False))
```

示例的任务宏平均约为：success rate 0.6000、pass@3 0.6667、pass^3 0.4667、结果一致性样本指标 0.7867。`task_C` 永远失败但一致性为 1，故意保留这个现象，提醒读者不要把一致性当正确率。

统计解释还需要任务代表性、独立性和裁判质量。代码计算正确，不等于实验设计正确。

## 结语

这份文档的重点不是为每个系统套上相同仪表盘，而是把一个可信实验拆清楚：任务是否代表目标工作，Agent 到底获得了什么信息，裁判是否接受真正正确的结果，重复与扰动是否暴露不稳定，成本是否公平计算，以及证据和权限能否支撑最终部署决定。

**当一个版本分数提高时，真正要问的不是“涨了多少”，而是“哪些真实能力被可靠地改善了，以及我们有多充分的证据相信这一点”。**
