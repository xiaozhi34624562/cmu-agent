## 阅读入口：从应用开发走到 AI 系统

本文以 LLM Developer、具备 Java 等编程经验的读者为起点。你熟悉的接口、调用链、缓存、并发与失败恢复仍然适用；新增的是模型每一步计算、生成历史和 GPU 资源之间的约束。无需先掌握 Transformer 数学或硬件体系结构。

先建立一个最小模型：文本经过 **tokenizer（分词器）**成为 token 编号序列，token 可能是字、词或词片段。模型的**权重**是训练得到、推理时用于计算的参数；本课主要讨论使用已有权重生成结果，而不是怎样训练它们。模型对下一个 token 给出一组未归一化分数，称为 **logits**；选择最大分数叫 argmax，按分数转换的概率抽取叫采样。选出的 token 加回历史，再预测下一个。**上下文**是本次调用实际提供的信息，不等于磁盘上所有文件；**Harness**是你在模型外编写的控制程序，负责组织信息、调用工具和维护运行状态。

沿这条链阅读：第 1—3 节建立目标和分层，第 4—8 节解释一次生成为何消耗时间与资源，第 9—17 节把多次调用连成任务，第 18—21 节检验优化是否真正有效。第一次读第 6.4 节的并行缩写，只需知道“拆到多张卡会增加通信”；第 8.1 节的指数模型是可选数量校核，不是后文必备数学。读完应能拿出一次服务调用记录，分清慢在哪里、改动影响哪一层，以及用什么任务指标验收。

## 1. 课程不是模型排行榜：从研究问题到可工作的系统

讲义 pp.3—4 介绍讲师与 MaDSys 的研究方向：测量、设计和运行真实系统，围绕性能、效率、可靠性、可持续性寻找问题。四项目标经常相互制约，而不是同时随着一个指标上涨。

- **性能**关心给定任务多久完成、单位时间处理多少工作。
- **效率**关心完成这些工作消耗多少资源，包含空闲、重复计算和无效产出。
- **可靠性**关心故障下是否仍能满足约定，以及能否恢复。
- **可持续性**关心能耗与资源生命周期；本课导论提出动机，不给出某个产品的碳排承诺。

一个模型在离线题集上回答正确，只说明它在某种输入与生成协议下有能力。产品还要接收并发请求、排队、调用工具、保存状态、处理失败和交付结果。[L1，pp.28—29] 系统会决定用户能否以可接受的时间与成本使用这份能力。

### 1.1 贯穿例子：代码修复服务

假设我们部署一个处理 Python 小仓库的 Agent 服务。每个任务要求修复一个 bug，提交补丁并运行测试。一次典型交互为：

```text
用户提交需求
→ 模型决定读哪些文件
→ 文件工具返回代码和测试
→ 模型提出修改
→ 编辑工具保存补丁
→ 测试进程返回日志
→ 模型判断是否继续
→ 独立验收并交付结果
```

这个服务涉及 CPU 分词与进程、GPU 推理、磁盘文件、网络请求和测试容器。即便每次模型推理都加速 30%，端到端也未必快 30%；如果更激进的模型压缩导致更多修复轮次，任务可能反而更慢。

后文用构造数字做推导，不假装这些数字来自课程实验。重点是学会如何建立测量与归因，而不是提前猜某种架构最优。

## 3. AI Systems：能力模型之外的状态、调度与故障

讲义 p.28 区分“使用什么模型解决问题”和“怎样在规模上训练、服务模型”。它把 scheduling/orchestration、state、communication、caching、fault tolerance、security、observability 一并列入系统问题。

### 3.1 三层对象不要混在一起

1. **模型层**：权重、tokenizer、生成分布与上下文能力。
2. **请求服务层**：队列、batch、KV、路由、并行和资源。
3. **Agent 任务层**：目标、工具、状态、分支、完成与验证。

一次优化可以跨层产生影响：模型量化可能提高每步速度，却改变工具调用准确率；前缀缓存可能降低请求 prefill 成本，但前提是 Harness 保留稳定前缀；多分支搜索可能提高成功率，却改变服务负载和队列延迟。

因此每个改动应说明改变哪个对象、预计通过什么链路影响最终结果，以及需要固定哪些变量才能判断贡献。

### 3.2 “近似计算可接受”的前提是任务容差

模型输出本来具有随机性，并不代表任何系统误差都可以忽略。文本措辞微变可能无关紧要；工具名、JSON 参数、金额或代码语义改变可能决定任务成败。优化应验证最终性质，而不是只看浮点差很小。

更严格地说，应事先确定一个可接受关系：输出是否同义、测试是否通过、分类是否一致、端到端成功率变化是否在允许范围内。没有给定任务和容差，不能从“近似”一词推出“质量保持”。[L1，p.31 的工程展开]

## 4. 计算为何异构：Prefill 与 Decode 的瓶颈不同

讲义 p.30 指出 CPU负责 tokenization、kernel launch、数据移动和工具调用，GPU擅长矩阵乘法；同一部署中，prefill、decode 和工具等待可能依次成为瓶颈。

先把硬件词与开发经验对齐：**GPU 显存**是 GPU 运算时存放权重和中间数据的内存；**容量**回答装得下多少，**带宽**回答每秒能搬多少字节，**算力**回答每秒能做多少运算。像服务既可能受 CPU 处理能力限制，也可能在等数据库传输，GPU 忙不等于所有资源都有效利用。**batch**把多条请求合在一次计算中，**kernel**是执行某个计算步骤的 GPU 程序；这里的 kernel 不是操作系统内核。

### 4.1 Prefill：一次处理已知前缀

先看两种输入：提示“请解释这个函数”已经全部给定；回答的第 20 个 token 却要等第 19 个选出后才能继续。这形成 prefill 与 decode 的区别。

已有 $S$ 个提示 token，Transformer（一类通过注意力等计算结合不同位置的信息的模型）可以并行计算多个位置。矩阵运算的工作量随 batch、长度和架构变化；在常见足够大矩阵下，可能更受算力约束。它影响 time to first token，但不能把 TTFT全部归给prefill：排队、tokenization、检索和网络也可能占大头。

### 4.2 Decode：每条序列逐 token 推进

新 token 依赖前面刚生成的 token，单序列有串行依赖。KV cache避免每步重算全部历史，但每步仍要读取权重与历史K/V。小 batch的decode常受显存带宽约束；更大 batch、不同架构和并行方式会改变瓶颈。

因此讲义“prefill compute-bound、decode memory-bandwidth-bound”应当读成重要的常见工作区间，不是所有模型、序列、batch和GPU都满足的定律。短prefill、小矩阵也可能未充分利用算力；大batch decode也可能受计算或KV容量限制。

### 4.3 Roofline式的判断方法

**教学模型**：设一次运算需要 $F$ 次浮点操作、从主要内存搬运 $D$ 字节，有效算力 $P$、有效带宽 $B$，理想下界为：

$$
T\gtrsim\max(F/P,D/B),\qquad I=F/D.
$$

$I$ 是算术强度（arithmetic intensity），单位为操作数/字节。$F/P$ 是计算这些操作至少需要的秒数，$D/B$ 是搬运这些数据至少需要的秒数；即使二者理想重叠，也不能快过较慢的一项，所以取最大值。例如构造一个步骤，计算需要 2 毫秒、搬运需要 10 毫秒，理想下界就是 10 毫秒；只把算力加倍，搬运这一关仍在。只有算术强度与硬件算力/带宽比例结合，才能判断偏向哪一边；实际还要加kernel启动、同步和排队。图形界面里的“GPU 90%”不能替代这个分析。

**例子**：若某decode阶段搬运权重占主要时间，提高计算峰值但带宽不变，未必同比加速。若batching让一次权重读取服务更多序列，资源效率可能提高；但等batch的排队延迟也可能增加。这连接到后面“吞吐与任务延迟不总同向”。

### 4.4 输出长度使服务时间不可预知

传统请求的成本有时能根据输入大致估计；LLM输出可能提前停止，也可能产生长推理。Agent还会根据中途观察决定是否再调用模型。到达时往往不知道完整服务时间。

调度需面对短请求被长请求阻塞、长上下文占KV、工具返回后突发恢复等问题。最大输出token是上限，不是实际长度；用所有请求的同一上限估算平均时长会失真。[L1，pp.30、39]

## 5. 数值不确定性：可重复运行不是只有随机种子

讲义 p.31 列出浮点加法不满足结合律，运行时、软件和硬件会影响归约与舍入；微小logit变化可能改变下一token，再使后续轨迹分叉。

### 5.1 一个实际执行的非结合例子

在本地Python双精度中：

```python
a, b, c = 1e16, -1e16, 1.0
left = (a + b) + c
right = a + (b + c)
assert left == 1.0
assert right == 0.0
```

这不是算术规则失效，而是有限精度下每步舍入。在GPU归约里，操作顺序、融合乘加与不同kernel也可能改变舍入路径。NVIDIA的[浮点白皮书](https://docs.nvidia.com/cuda/floating-point/index.html) §2—3解释了此类现象；[本地快照](references/nvidia-floating-point.html)保留查阅版本。

### 5.2 讲义“相等不传递”需要限定

该页页脚写 `a == b, b == c does not imply a == c`。对于普通有限浮点值的精确相等比较，这个说法不能直接成立；数值上更常见的是**近似相等关系不传递**。

令“接近”定义为 $|x-y|\le0.1$，取 $a=0,b=0.09,c=0.18$，则 $a$接近$b$、$b$接近$c$，但$a$不接近$c$。这说明容差判定不应被当作可任意链式合并的等价关系。NaN等特殊值还有额外比较语义，也不能用来为上述一般表述作无条件证明。

[Python浮点教程](https://docs.python.org/3/tutorial/floatingpoint.html)解释表示误差和近似比较；[本地快照](references/python-floatingpoint.html)用于保留来源。这里纠正的是讲义措辞边界，不是在声称所有数值差都会影响模型质量。

### 5.3 细微数值差怎样进入Agent路径

假设两个候选token logits非常接近，微小变化可以切换argmax。若token是普通词，后果可能很小；若是 `read_file` 与 `edit_file`、分支标签或JSON闭括号，可能改变工具执行与后续状态。即使greedy decoding，也不保证跨硬件、batch或kernel得到逐token一致输出。

可分三种重现目标：

| 目标 | 要求 | 适用场景 |
|---|---|---|
| 位级重现 | 张量/输出完全相同 | 数值回归、底层排错 |
| 轨迹重现 | 同动作与观察顺序 | 特定失败回放 |
| 统计重现 | 同协议下质量和成本分布接近 | 模型/系统效果比较 |

固定seed有帮助，但要同时保存模型、tokenizer、采样、软件、硬件、并行、batching与环境。论文或项目应明确要求哪种，而非把所有“不完全一样”都当成无效实验。

## 6. 内存、存储和通信：状态才是规模化的核心约束

讲义 p.32 列出权重、KV、prefix cache、各种并行通信与RDMA。它们不是同一种数据，生命周期也不同。

先理解 KV 的用途：在注意力计算中，当前位置形成 query（查询向量），用历史位置的 key（键向量）判断相关程度，再组合相应 value（值向量）。向量就是一组数值。对常见因果生成模型，已处理历史的 K/V 可以保留，下一步直接读取，避免重复计算；这就是 KV cache。它缓存的是**模型计算的中间结果**，不是业务查询的答案。一个注意力“头”是这样的一组计算通道，头维度是每个向量包含的数值个数；多层模型每层都需要相应状态。

### 6.1 四类状态分别在哪

| 状态 | 产生与复用 | 典型管理问题 |
|---|---|---|
| 模型权重 | 多请求共享，模型更新时变化 | 是否装得下、分片与版本 |
| KV cache | 每条生成历史的中间状态 | 长度增长、容量、释放与恢复 |
| Prefix cache | 相同模型下共同前缀KV | 命中、失效、驱逐与路由 |
| Agent持久状态 | 文件、消息、记忆、工具结果 | 恢复、一致性、权限和版本 |

KV cache不是长期记忆数据库；聊天历史存在磁盘，也不表示相应KV仍在GPU上；摘要相同语义，不表示可直接复用旧前缀KV。这些边界决定优化是否正确。

### 6.2 容量公式帮助检查数量级

标准decoder的KV估算为：

$$
M_{KV}=2L S H_{KV}d_h b N.
$$

$L$层，$S$每序列token数，$H_{KV}$为KV头数，$d_h$头维度，$b$每元素字节数，$N$并发序列数。此式忽略碎片、元数据和共享，仅作教学估算；MLA、滑窗、量化和混合架构需要调整。

公式中的 2 来自 K、V 两份数据；先算一层一个 token 的头数×头维度×字节数，再乘层数、历史长度和并发序列数。若教学代入每token为128KiB、每序列32K（此处取32,768个token）、并发64，则每序列占4GiB，再乘64，得到仅KV约256GiB。KiB、GiB分别按 $2^{10}$、$2^{30}$ 字节计。讲义说“10s–100s KB/token”是在提醒数量级，不能把它当所有模型固定常数。[L1，p.32]

### 6.3 前缀复用为什么与Agent特别相关

系统提示、工具定义、任务背景和前几轮历史经常重复。若保留相同token前缀，可以少做prefill；如果每轮改写系统提示、重排工具或把时间戳放在前面，可能破坏复用。

不过不能为命中率牺牲语义：已经过时的工具结果不能因为“缓存便宜”就继续当当前事实；不同模型权重或adapter的KV不能混用。前缀缓存的工程契约是同计算条件下的共享，并不理解业务新鲜度。

### 6.4 多GPU的通信不能只看卡数

TP在层内拆张量，需要频繁通信；PP按层分段，有流水气泡；EP搬运token到专家，可能受all-to-all与负载影响；CP拆长上下文，也要交换中间状态。DP复制或分片模型处理不同数据，目标又不同。

NVLink、Ethernet/InfiniBand与RDMA影响有效带宽、延迟、拓扑和CPU开销。讲义的名字用于构建地图，导论不要求实现这些协议。后续优化应测模型实际使用的通信量，而不是只用网卡标称带宽估算。

## 7. 模型与工作负载一起演化：为什么优化不能固定一种请求

讲义 p.33 把MHA、GQA、MLA、稀疏或线性attention与聊天、推理、RAG、Agent并列。模型架构改变每token状态与计算；应用模式改变长度、依赖和复用。

### 7.1 同一tokens/s在不同任务中含义不同

- 交互聊天可能更关注首token与响应流畅。
- 长推理关注完成时间、答案质量和输出长度。
- RAG可能有长输入、检索延迟与证据处理。
- Agent有多轮、工具等待、不断增长历史与分支。

因此评测集应包含真实的长度与到达分布，而不是只跑固定长度生成。只针对短prompt、长output调出来的系统，未必适合长工具历史与短动作输出。

### 7.2 Agent—Serving协同设计的三个方向

1. **上层让下层更容易优化**：稳定前缀、清楚任务边界、显式优先级或取消信号。
2. **下层向上层暴露有用信息**：预计排队、缓存状态、资源可用性，让策略选择考虑等待。
3. **联合选择**：模型路由、摘要时机和并行分支一起影响质量与资源，需在任务层约束下比较。

这些是从讲义系统栈推导的研究方向。不能仅因为某特性有利于缓存，就要求所有Agent采用相同消息布局；还要看模型理解、工具协议和安全边界。

## 8. 可靠性与能耗：大规模系统的故障不再稀有

讲义 p.34 写9% AFR、50,000小时MTBF，以及16K GPU集群约每3小时一个故障。这一页需要核对数量级，不能把不同统计直接串成一个精确计算。

### 8.1 从单设备MTBF推集群故障间隔的条件

MTBF 是平均故障间隔，AFR 是年故障率；必须先查其统计定义，二者不能只凭名称互换。直觉上，一台设备故障少，不代表同时使用一万台时也很少遇到故障，因为可能出问题的对象变多。下面先算事件数量，再核查年度概率。

若各设备独立、同分布且近似恒定故障率，单设备MTBF为$m$小时，$N$台至少一台故障的事件率近似$N/m$，平均事件间隔$m/N$。

代入50,000/16,000=3.125小时，与讲义“约3小时”一致。这个推导不包括相关故障、电源、网络和机架事件；“出现一次设备故障”也不等于整个服务停机。

下面一项可作为进阶校核：恒定故障率的指数模型中，平均间隔为 $m$ 小时，连续 $t$ 小时无故障的概率是 $e^{-t/m}$，因此一年至少一次的概率是 $1-e^{-8760/m}$。若AFR=9%被理解为同一设备一年内至少故障一次的概率，反解这个式子给 $m=-8760/\log(1-0.09)\approx92900$小时，并非50,000小时。后者对应约16.1%年故障概率。因此不能认定三项数据来自同一测量口径；本文保留讲义数字，明确它们只能分别作规模化动机，不合并为统一实测结论。

### 8.2 任务恢复比请求重试更复杂

代码修复Agent运行30分钟后服务断开：模型请求可以重发，但文件可能已改、测试已启动、外部写入也可能完成。恢复要区分“生成未完成”“工具结果未知”“动作已执行但回执丢失”。

对纯读请求可以更容易重试；有副作用动作应有幂等键、状态查询或业务补偿。保存一段对话不等于完成checkpoint，第19节会拆解所需状态。

### 8.3 能耗应以成功任务归一化

讲义列CPU、GPU和服务器功率数量级，说明供电、散热与波动也是系统约束。这些数字按本地讲义理解，不是当前设备采购规格。

定义成功任务能耗：

$$
E_{success}=\frac{\int P_{system}(t)\,dt}{N_{success}}.
$$

$P_{system}(t)$ 是时刻 $t$ 的系统功率；积分符号表示把每个小时间段的“功率×时间”累计，得到能量。恒定200W运行10秒就是2000J，再除以成功任务数。分子要说明是GPU、整机还是含网络与冷却；分母必须说明成功定义。更低功率运行更久，可能总能耗更高；更高功率但减少无效重试，可能更节能。导论给出测量问题，不从峰值W直接推产品碳排。

## 9. Agent的定义：计划—行动—观察—调整—交付

讲义 pp.35—37 转到Agent：模型围绕目标推理，使用工具，多步执行，并根据新信息更新计划。图中LLM与memory向环境发action，接收observation。[L1，p.36]

### 9.1 用符号区分状态和观察

令真实环境状态为$s_t$，观察为$o_t$，可用历史为$h_t$，动作$a_t\sim\pi(\cdot\mid h_t)$，环境执行后生成新状态及观察。这里 $t$ 表示步骤编号，$\pi$ 是给定历史后选择动作的分布，竖线表示“给定”，$\sim$ 表示据此产生动作；它只是把“根据已看到的信息决定下一步”写成符号，不要求此时学习强化学习。模型通常只看到部分状态，不能把屏幕或一段日志当作整个世界。

对代码服务：环境状态含磁盘与测试进程；观察可能只返回日志末尾100行；动作可以是读取、编辑或测试。若失败信息在截断前半段丢失，模型可能误以为没有错误。工具返回策略直接影响可决策信息。

### 9.2 记忆解决的是持久状态，不是无限正确性

讲义 p.37 指出LLM在持久记忆、上下文理解、幻觉、不确定性和安全方面的弱点。Agent可用工具和状态机制补足部分缺口，但也增加新的错误边界。

把用户偏好写到数据库，只有在相关任务被正确检索和使用时才有作用；错误记忆可能让未来任务更差。工具取得新信息，也需要判断来源与时效。系统围绕模型建立支持，不会自动把弱点全部消除。

### 9.3 附录中“Agent会学习”不是必要条件

讲义 pp.49—50 用Agent、assistant、bot对照自主性、复杂度与learning，是可选阅读的概括。工程上不能把“必须持续学习”当Agent定义：冻结模型在观察—动作循环中也能完成任务；有学习能力的模型也可能只做一次分类。

同样，assistant可以调用工具，bot也可执行多步流程。类别边界取决于产品和研究语境。最可靠的描述是列明自主决策范围、动作集、反馈、状态与更新机制，而不是单靠标签推断架构。

## 10. “新型计算机”的类比：哪里有用，哪里会误导

讲义 p.38 对照CPU↔LLM、RAM↔context、peripherals↔tools、OS↔Harness、application↔Agent。它帮助系统工程师把已有知识迁移过来：调度、缓存、故障恢复与接口都仍重要。

### 10.1 上下文不是普通随机访问内存

RAM有明确地址与读写语义；context通过token影响概率分布，信息即使在窗口里，也未必被模型稳定使用。摘要、检索与长上下文训练改变的是可访问与利用信息的方式。把上下文当“多装一些就一定记得”，会低估选择与干扰问题。

### 10.2 模型不是确定性指令CPU

传统指令集通常有明确操作语义；自然语言提示是概率性控制，可能歧义、冲突或被外部文本干扰。工具调用形成较明确执行边界，但语义与授权仍需程序校验。

Harness可以像OS管理资源与执行，但它不能仅凭自然语言最终答案判定任意任务完成。验证器、工具契约和环境边界都是独立组件。类比应帮助提出问题，不能替代具体故障模型。

## 11. 从一次请求到依赖图：Agent关键路径怎样形成

讲义 p.39 对比传统 `request → inference → response` 与 `infer → tool → infer → tool → retrieval → infer`。后一种工作负载的关键路径跨GPU、CPU、存储、网络和外部服务。

### 11.1 串行任务的时间分解

对于无并行的$K$步任务，教学模型为：

$$
T_{task}=\sum_{i=1}^{K}(Q_i+P_i+D_i+U_i)+T_{control},
$$

$Q$排队，$P$prefill，$D$decode，$U$工具/环境时间。必须定义时间边界，例如网络往返归入工具还是服务，不能重复计算。

构造一次任务：4次推理每次2秒，2次测试每次10秒，其余2秒，总计30秒。把推理加速一倍，变为26秒，整体约1.15倍；把一次无必要测试省掉，则可能降至20秒。后者前提是仍满足验证契约，不能为了速度删掉必要测试。

### 11.2 并行任务应看最长依赖路径

若读取代码和读取独立文档可以并行，它们的等待近似取最大而非求和；写补丁依赖代码读取，验收依赖最终补丁，这些边不能省。

可把任务表示为有向无环依赖图（DAG）$G=(V,E)$：$V$ 是步骤集合，$E$ 是必须遵循的先后依赖，沿依赖不能绕回原步骤。节点是模型/工具/控制步骤，边是数据或控制依赖。忽略资源竞争时下界为最长路径；实际还受GPU队列、并行槽位和网络限制。即使两个节点无逻辑依赖，也不保证资源允许同时执行。

### 11.3 子Agent什么时候有价值

把两项可独立调查交给子Agent，可能缩短关键路径；协调、上下文分发、结果整合和重复探索却增加总成本。如果任务本来只有一条严格依赖链，拆分未必加速。

可先估计可并行工作、交接信息量、输出契约、冲突风险与验证成本，再测端到端。子Agent数不是成果指标；应比较相同目标和资源约束下的质量与延迟。

## 12. Agentic Systems Stack：优化要能沿栈追溯

讲义 p.40 的栈从用户应用、Harness、model、serving、runtime/kernel到hardware；右侧是外部工具和系统。共同设计意味着：上层目标与下层资源之间要有明确接口。

| 层 | 控制对象 | 影响任务的途径 |
|---|---|---|
| 应用 | 用户目标、验收与优先级 | 决定何谓有用结果 |
| Harness | 计划、上下文、记忆、工具与子Agent | 决定模型调用次数、输入与依赖 |
| Model | 权重、采样、能力 | 决定决策与生成质量 |
| Serving | batching、scheduling、routing、caching | 决定排队、处理速度与状态复用 |
| Runtime/Kernels | CUDA、Triton、collectives | 决定算子与通信效率、数值路径 |
| Hardware | GPU/CPU/内存/网络/存储 | 决定容量、带宽、功率和故障域 |
| Tools/Environment | 文件、网页、API、人类反馈 | 决定外部信息、执行与副作用 |

一次任务失败，先定位链路。模型没有见到日志不是推理能力低；工具命令正确但目录错是执行上下文问题；API队列慢不应通过修改答案提示来解决。跨层优化需要跨层证据。

## 13. 指标体系：为什么最大化吞吐不是最终目标

讲义 p.41 给出本课最重要的约束优化形式：最大化task success，subject to latency、cost、resources、reliability、security。TTFT、TPOT、工具延迟和GPU利用率是有用中间指标，但不足以替代任务指标。

### 13.1 成功定义、分母和失败成本

设任务$i$的成功指示为$s_i\in\{0,1\}$，总成本$c_i$，端到端时间$t_i$。最基本的统计为：

$$
\mathrm{SuccessRate}=\frac{\sum_i s_i}{N},\quad
C_{success}=\frac{\sum_i c_i}{\sum_i s_i}.
$$

后者把失败尝试成本纳入，是用户真实承担的一部分。只统计成功轨迹均值 $\sum_{i:s_i=1}c_i/\sum_i s_i$ 会漏掉失败消耗，特别容易奖励“失败得很多但成功时便宜”的方案。

延迟也应报告未完成/超时比例和上限，不要只看成功任务的中位数。任务难度分布不同的两个服务不能直接用整体成功率比较，应在共同题集上配对。

### 13.2 一个实际执行的成本反例

假设A尝试100题，每题花1单位，成功60题；B每题花1.3单位，成功90题：

```python
a_cost_per_success = 100 / 60
b_cost_per_success = 130 / 90
assert b_cost_per_success < a_cost_per_success
```

B单次更贵，但每成功任务成本约1.44，低于A约1.67。数字为教学构造，说明分母的重要性；不表示更大模型总能获得这一改善。

### 13.3 延迟、费用与资源约束应明确到统计口径

p95延迟是按耗时排序后第95百分位的位置，帮助观察较慢的一端；均值下降不代表这一端也改善。可以写：在某任务族成功率至少$x$、p95端到端延迟不超过$T$、平均每成功任务费用不超过$C$时最大化吞吐；也可在固定资源下最大化成功任务/小时。$x,T,C$需来自产品需求，不在导论中替任何业务凭空决定。

不同约束会选出不同系统。交互排错希望首轮快速反馈；批量修复可能更重视总完成量；高错误成本任务可能接受更长验证。先定义约束，才知道“优化”是向哪里移动。

### 13.4 Pareto前沿比单一分数更诚实

若一个方案更准确但更贵，另一个更快但成功率低，通常没有无条件赢家。绘制质量—费用、质量—延迟关系，找不被另一方案同时支配的候选。只有某方案在所有关心指标都不差且至少一项更好，才更容易称为明确改进。

如果必须合成分数，权重与尺度应事先定义，并报告原始指标。否则调权就能把任意方案包装成赢家。

## 14. Batching、缓存与路由的局部最优陷阱

### 14.1 Batching提高吞吐，为什么可能拖慢Agent

把更多请求凑成batch，一次权重读取服务更多序列，效率可能提高；但排队凑batch会增加等待。Agent下一步依赖当前结果，小延迟在多轮串行链上累积。

**教学例子**：单任务10次模型调用，每次因凑batch多等0.3秒，任务多等3秒。若每次decode节省0.1秒，总共仅省1秒，端到端仍慢2秒。实际服务可能continuous batching而非固定等待，本例只说明需测关键路径上的净变化。

### 14.2 缓存命中与负载均衡可能冲突

请求回到同一副本更可能命中前缀；但该副本队列可能很长。路由到空闲副本可减少排队，却需要重算前缀。比较：

$$
T_{sticky}=Q_{hot}+T_{suffix},\qquad
T_{move}=Q_{cold}+T_{state}+T_{suffix}.
$$

其中$T_{state}$是冷副本取得可用前缀状态的成本：完全重算时取$T_{prefix}$，可行的状态转移方案则计传输和必要转换，混合方案按实际执行计量，避免把互斥路径重复相加。决策需要估计排队、前缀成本和传输，不能只最大化cache hit rate。

### 14.3 什么时候调用更大模型

大模型可在困难决策、长上下文或失败恢复中提高成功机会，也可能只是更贵更慢。应根据任务特征、置信代理、工具错误或阶段状态做路由，并用共同题集验证。

一个清楚实验是：全小、全大、按难度路由三组，固定总预算与任务；报告路由错误、升级比例、新增成功和新增失败。若只在已经失败的任务上追加大模型，最终分数包含重试收益，应报告首试和累计预算。

## 15. 讲义的十种工作负载特征，怎样变成可研究的问题

[L1，p.42] 的映射可以用于项目选题，但每一项都要缩成具体测量。

| 特征 → 系统问题 | 可操作研究问题 | 需要的证据 |
|---|---|---|
| 长轨迹 → 状态与上下文 | 摘要是否减少费用且保留约束？ | 长任务成功、摘要错误与token |
| 重复前缀 → caching | 稳定模板能提高多少实际复用？ | 命中token、prefill时间、质量 |
| 工具依赖 → scheduling | 优先恢复即将结束任务是否有益？ | DAG、剩余步骤、完成时间分布 |
| 工具时延变化 → async | 哪些工具能安全并行？ | 依赖、总成本、错误与尾延迟 |
| 多Agent → orchestration | 分工如何减少重复探索？ | 交接契约、冲突与成功 |
| 巨大context → memory/retrieval | 选取证据还是全量输入更合适？ | 证据覆盖、输入token与答案 |
| 分支推理 → speculation | 提前分支是否值得被丢弃工作？ | 选择器、接受率与总资源 |
| 不同模型 → routing | 哪些步骤值得升级模型？ | 升级比例、漏升/误升与收益 |
| 外部副作用 → isolation | 重试是否可能重复执行？ | 幂等与未知结果恢复 |
| 长运行任务 → checkpoint | 保存哪些状态才能恢复？ | 故障注入、恢复时间、重复动作 |

这张表是讲义地图的工程展开，不是十个已经证明有效的方法。好的研究问题应允许负结果：例如提高缓存命中却因队列拥塞拖慢任务，就是有价值的系统观察。

## 16. 可观测性：分布式trace必须能还原嵌套轨迹

讲义 p.43 的图从Session到Turn、Agent step、Model request、Tool call/result，再到Subagent。对Agent，一个平面日志列表常不足以解释父子关系和因果依赖。

### 16.1 最小事件模型

可以给每个事件保存：

```json
{
  "session_id": "s17",
  "turn_id": "t2",
  "span_id": "tool9",
  "parent_span_id": "agent4",
  "kind": "tool_result",
  "call_id": "call_read_3",
  "status": "ok",
  "duration_ms": 14,
  "artifact_ref": "saved-output-location"
}
```

真实字段名可不同，但要能关联一次调用与结果、父Agent与子Agent、模型请求与对应版本。日志只写“执行完成”无法说明哪个动作完成；只写最终费用无法定位哪一轮失控。

### 16.2 时钟、跨度与成本不要直接相加

并发span重叠，耗时求和可能超过端到端时间；跨机器时钟可能偏移。总延迟用明确起止时刻，关键路径用依赖与持续时间分析；CPU/GPU时间、墙钟时间和计费token分别统计。

子Agent成本应计入父任务，但展示时避免再次加总造成重复计费。聚合树最好区分exclusive与inclusive成本。教学记录中如果只给总额，应注明没有足够粒度分析组件。

### 16.3 工具成功、运行结束、任务成功是三个状态

读取文件成功只表示取得内容；Agent循环结束只表示不再行动；任务成功还需满足验收。UI若把三个状态都画成同一个绿色勾，会诱导用户和评测器误判。

在代码服务里：模型可能正常退出但没有补丁；测试命令执行了却收集零用例；补丁通过公开样例却未通过独立验收。事件模型应保留退出原因、验证结果与最终产物版本。

## 17. 作业1作为可观测性练习：先重放事件，再花钱跑Agent

本课SOURCES列作业1作为参考。它要求为已有Claude Code做UI，不要求此时重写Agent循环，后者是作业2。[作业1本地全文](../site/assignments/assignment1.html) 本节解释设计含义，不代写课程要求学生独立完成的观察报告。

### 17.1 七项特征对应七个系统契约

作业要求提交prompt、实时显示轨迹、显示工具结果、工具/运行两层状态、续接session、显示成本/时间/turn数，以及子Agent树和outline。它们共同验证：前端知道正在发生什么、知道结果属于哪个动作、知道运行何时结束。

对JSONL事件流，需要处理分块读取：网络chunk不一定刚好是一行JSON，半行要缓冲，完整行解析后再渲染。前端断开、后台进程失败或最终result未到，都不应让页面永远显示running。可用明确错误事件、进程退出与超时机制区分。

这些是软件工程建议，不是声明课程事件格式永不变化。具体命令、认证和标记按已归档作业版本理解，不把它升级为当前产品操作指南。

### 17.2 重放与真实运行分别能验证什么

作业建议保存完整`events.jsonl`，重放开发UI，最后再跑真实任务。重放可以检查顺序、嵌套、折叠、错误展示与计数；它不能单独验证实时到达和真实session resume。

这提供普适实验方法：能离线重放的部分，用固定证据加快迭代；依赖实际环境的契约，再做小规模端到端验证。这样既减少成本，又不会把模拟通过冒充线上成功。

### 17.3 可视化不是隐藏原始证据

长工具输出可以折叠和裁剪以保持可读性，但完整日志应可定位，截断要明示。若前端只显示最后几行“Done”，看不到中间失败，用户会获得误导。树形展示也要保留原事件ID，避免重新排序后丢失因果关系。

## 18. 怎样评测一个系统优化：给贡献寻找反事实

### 18.1 先定义一个足够窄的假设

例如：

> 在同一模型、任务集、工具与预算下，稳定系统提示和工具顺序可以增加可复用前缀，减少prefill时间，同时不降低任务成功。

它包含改变对象、预期机制和质量约束。相比“让Agent更快”，这样的假设能被证伪：命中率没变、prefill不是瓶颈或成功率下降，都可能否定它。

### 18.2 固定什么，记录什么

应固定或明确报告模型revision、tokenizer/模板、采样、输入任务、工作目录/镜像、可用工具、终止和重试规则、服务硬件与并发。缓存实验要区分冷启动、预热与混合状态；路由实验要记录真实到达顺序和负载。

如果上层提示也变、下层量化也变、GPU也换，很难知道收益来自哪里。可以先比较完整系统总收益，再用消融定位，而不是把总收益都归给最有新意的组件。

### 18.3 同题配对与独立任务

对每题记录新旧成功、成本、延迟与失败原因。把结果分为共同成功、共同失败、新增成功、新增失败，比只报平均提升更容易发现退化。

开发集用于选择方案，反复看过后已经参与调优。最终保留按仓库、模板或时间隔离的任务，以检验泛化。只把相同问题换变量名随机拆分，可能高估系统在真实新任务中的收益。

### 18.4 工具不稳定也是系统结果的一部分

远端API故障可以单独归因，帮助解释模型能力；但用户最终面对的是整个服务。应同时报告“环境正常条件下质量”和“包含环境失败的端到端成功”，并说明排除标准。

同理，超时任务不能悄悄从延迟分母删除；人工中断也要记录原因。衡量可靠性不是把失败项筛掉后报告漂亮均值。

## 19. 故障恢复与副作用：30分钟Agent应该保存什么

讲义 p.44 提问如何恢复一个长运行Agent。一个checkpoint应保存到足以判定下一步，而不只是重开模型请求。

| 状态 | 为什么需要 | 缺失时可能发生什么 |
|---|---|---|
| 用户目标与约束 | 决定任务语义 | 恢复后完成了错误目标 |
| 消息/摘要与证据索引 | 保留已知信息 | 重复探索或丢失边界条件 |
| 代码与文件版本 | 确认实际产物 | 旧测试对应新代码 |
| 工具调用ID及状态 | 确认执行事实 | 重复写入或误判未执行 |
| 模型/工具/环境版本 | 恢复相同协议 | 观察与行为发生变化 |
| 预算与完成条件 | 保持控制边界 | 重启后预算无限延长 |
| 任务依赖和子Agent状态 | 恢复并发关系 | 孤立分支继续消耗资源 |

恢复测试可以在“动作发出前”“动作执行后、结果记录前”“验证完成后、最终回复前”等边界注入中断，观察是否重复动作或丢结果。没有真实执行这些测试之前，只能称为恢复设计，不能称为故障保证。

## 20. 选型与成本：从任务结构决定工程投入

### 20.1 先选择需要掌控的层

如果主要问题是工具结果太长，先检查Harness信息设计；如果模型一直排队，查serving负载；如果prefill耗时高且重复前缀多，研究cache；如果模型根本不会正确选择工具，单纯优化kernel只能更快地产生错误。

服务资源有限时，固定硬件与请求速率做小规模测量，再决定是否需要自托管、缓存、路由或更复杂并行。导论不提供“所有团队都应自建服务”的结论。

### 20.2 一次性开发成本也要摊销

若优化开发与验证成本为$C_{build}$，每任务节省$\Delta c$，预计未来处理$N$任务，简化回本条件为：

$$
N\Delta c>C_{build},
$$

同时要求质量与约束满足。真实系统还需考虑维护、升级、故障和分布变化。一项复杂优化在高频稳定工作负载上值得做，在低频且快速变化场景里未必划算。

### 20.3 成本与延迟的独立账本

并行四个分支可能缩短等待，却仍消耗四份资源。缓存转移可能减少GPU重算，却增加网络费用和工程复杂度。若只看账单，遗漏了人类审阅与失败补救；若只看墙钟，又遗漏总资源。按项目目标明确计量边界，不需要把所有不可得项虚构成精确金额。

## 21. 离线练习、故障诊断与自测

### 21.1 已执行的检查

本地Python已验证：浮点非结合示例结果为1.0与0.0；近似相等例子不传递；50,000/16,000=3.125小时；9%年故障概率在指数模型下不对应50,000小时；每成功任务成本反例中B更低。它们检验教学算式，不包含真实硬件、故障数据或模型评测。

### 21.2 诊断表

| 现象 | 优先检查 | 下一步测量 |
|---|---|---|
| tokens/s上升、任务更慢 | 等batch、轮数或工具等待 | 逐任务关键路径 |
| 平均延迟下降、投诉增加 | 尾延迟、超时与难题分布 | p95/p99及失败比例 |
| cache hit高、GPU仍慢 | 命中token长度、decode、路由队列 | prefill/decode分解 |
| GPU利用率低、任务慢 | CPU工具或网络阻塞 | 嵌套trace与等待状态 |
| 换GPU后结果不同 | 精度、kernel、batch与采样 | 固定token/logit对照 |
| 便宜模型费用更高 | 轮数与失败重试 | 总成本/成功任务 |
| 重启后重复编辑或发送 | 已执行动作没有提交记录 | call ID与幂等恢复 |
| UI显示成功但产物失败 | 工具/运行/任务状态混同 | 独立验收与最终版本 |

### 21.5 迁移练习：从一次调用链选择优化

一个代码助手每项任务有 4 次串行模型调用和 2 次串行测试。每次模型调用包含排队 1 秒、prefill 0.5 秒、decode 1.5 秒；每次测试 4 秒。方案 A 将 decode 时间减半；方案 B 通过调度将排队减半。两方案成功率和其他时间假设不变。请先算总时间，再判断哪个改善更大；如果 A 的工具调用成功率下降，原比较还成立吗？

**答案与推理：**原时间是 $4\times(1+0.5+1.5)+2\times4=20$ 秒。A 节省 $4\times0.75=3$ 秒，变为17秒；B 节省 $4\times0.5=2$ 秒，变为18秒。在给定假设下 A 更快；如果 A 降低成功率，不能只用17秒宣称更优，需补失败、重试、每成功成本与质量约束。这个例子要求沿调用链归因，不代表真实模型实验。
