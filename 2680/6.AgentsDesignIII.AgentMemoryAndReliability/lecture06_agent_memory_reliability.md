## 导读：这节课究竟要解决什么？

Memory 与 Reliability 不是两个互不相干的功能模块。

**Memory 决定 Agent 下一步能看到什么，以及它把哪些历史信息当作当前状态。Reliability 则决定，当这些信息、判断或动作出错时，系统能否发现偏差、阻止传播、恢复执行，并正确判断任务是否完成。**

一条错误如果只出现在某次输出里，影响可能局限于一次回答；如果被写入长期记忆、被其他 Agent 共享，又被当作成功经验反复检索，它就可能成为持续产生错误的源头。这是把讲义的记忆生命周期与 AgentDebug 的错误传播分析连接起来得到的系统视角。[L06，pp. 6–18](#source-l06)；[R3，§2.1，p. 3](#source-r3)

整份文档围绕一个问题展开：

> **怎样让 Agent 在有限上下文中持续维护有证据支持的任务状态，并在出错后停止相信错误状态、回到正确轨道？**

## 1. 先用一条失败轨迹，把所有材料连接起来

### 1.1 一个看起来顺利、实际已经失败的任务

假设你要实现一个基金材料预审核 Agent。用户提出：

> 检查材料中基金甲 A 类份额的业绩表述，确认数据和比较口径，并给出有证据的修改建议。

系统执行了以下过程：

```text
读取材料
→ 找到“收益率 12%”的数据
→ 摘要时没有保留表头中的“C 类份额”
→ 写入记忆：“基金甲收益率为 12%”
→ 主 Agent 将这条记忆用于 A 类份额的判断
→ 审核 Agent 发现文字前后一致，认为没有问题
→ 系统宣布任务完成
→ 将本次输出作为“成功案例”写入经验库
```

这里可能没有任何 API 报错，JSON 也完全合法。问题不是计算机没执行，而是系统持续执行了建立在错误前提上的动作。

每份材料恰好解释其中一个环节：

| 材料 | 在这条轨迹中负责回答的问题 | 尚未自动解决的问题 |
|---|---|---|
| Lecture 06 | 什么值得记？怎样表达、存储、读取、更新和遗忘？故障属于哪个系统层？ | 需要具体机制和实验来解释设计取舍 |
| RAG | 外部资料怎样被检索并参与生成？检索器怎样学习什么更有用？ | 资料是否适用于当前实体、时间与任务；持续写入和恢复 |
| MemGPT | 历史太多时，怎样主动搜索、翻页、搬运和编辑有限上下文？ | 摘要是否正确、何时停止读取、记忆如何治理 |
| AgentDebug | 最早的一条错误记忆如何引起后续级联错误？从哪里修复？ | 诊断本身可能错误；现实环境未必能任意重放 |
| MAST | 为什么第二个 Agent 没纠正第一个？交接与验证出了什么问题？ | 一个角色名称或通信协议不能保证完成可靠交接 |
| Overthinking | 为什么模型继续分析，却不回到原始表头和实际数据确认？ | 多推理或多采样后，仍需要有效观测与选择器 |
| Beyond the Leaderboard | “格式正确”“审稿通过”“声明完成”究竟测到了什么？ | 需要针对业务构建正确的验收和评估流程 |

这张表是教学归纳，不表示这些论文共同提出了同一个统一架构。它们的研究对象、实验条件和分类体系都需要分别理解。

### 1.2 参数、上下文、外部记忆、执行状态的区别

讲义区分了临时的上下文窗口与跨交互持久存在的 Memory Store；RAG 区分参数化记忆和非参数化记忆；MemGPT 则说明，外部信息必须显式进入当前上下文，才能被当次模型推理使用。[L06，p. 5](#source-l06)；[R1，§2.2–2.3，p. 3](#source-r1)；[R2，§2，pp. 2–3](#source-r2)

可以用工程师工作的场景来理解：

| 概念 | 类比 | 在 Agent 中的含义 |
|---|---|---|
| 模型参数 | 工程师已经学会的知识和技能 | 语言理解、推理方法、训练中吸收的事实 |
| 当前上下文 | 现在摊在桌面上的材料 | 当前任务、最近消息、工具结果、被选中的记忆 |
| 外部记忆 | 档案柜和项目资料库 | 历史交互、事实、案例、长期文档 |
| 执行状态 | 项目进度表和操作流水 | 哪些步骤真正完成、哪些失败、下一步从哪里继续 |

最后一行是本文的工程区分：它可以持久化，也可以被放入模型上下文，但不应仅依赖模型自由概括。

例如，“第 1–8 页已检查；第 9 页数据核验超时；尚未生成最终建议”是执行状态。把它概括成“已审核大部分内容，整体问题不大”，就丢失了恢复任务需要的信息。

**资料存在档案柜里，不等于模型此刻看得到；模型此刻看得到，不等于下次还能准确恢复。保存聊天记录，也不等于保存了可恢复的任务状态。**

### 1.3 一个贯穿全文的教学模型

用 $o_t$ 表示本轮实际观测，$M_t$ 表示持久化记忆，$S_t$ 表示执行状态，$C_t$ 表示送给模型的上下文。可以写成：

$$
C_t=\operatorname{Assemble}(\text{任务合同},o_t,S_t,\operatorname{Retrieve}(M_t))
$$

$$
a_t\sim\pi_\theta(\cdot\mid C_t)
$$

$$
(M_{t+1},S_{t+1})=\operatorname{Update}(M_t,S_t,a_t,o_{t+1})
$$

这是教学抽象，不是某篇论文原样给出的形式化模型。它强调了三个不同责任：组织上下文、决定动作、更新状态。

失败不一定出在 $\pi_\theta$。如果上下文组装丢了限定条件，或者 Update 把超时误记为空结果，更强的推理模型也可能在错误前提上继续运行。

因此，本课的分析单位不只是一次模型调用，而是**证据、状态、动作与反馈之间的转换**。

## 2. RAG：让模型访问外部知识，但不要把“答对”误认为“证据充分”

> **与讲义的关系**：展开讲义中的非参数化存储、检索与知识使用问题。  
> **核心参考**：[R1，§2–4](#source-r1)。

### 2.1 原始 RAG 解决的是什么问题？

RAG 论文关注知识密集型任务：模型参数中虽然存有知识，但不容易精确更新和追溯来源。它把 DPR 检索器与 BART 生成模型组合起来，用 Wikipedia 文本索引作为外部非参数化记忆。[R1，pp. 1–3](#source-r1)

基本过程是：

```text
问题 x
→ 查询编码器 q(x)
→ 检索候选文本 z
→ BART 结合问题与候选文本生成答案 y
```

但原始 RAG 不只是“查几段文本，然后拼进 Prompt”。它把检索到的文档作为隐变量，通过最终答案的概率把检索器和生成器连接起来。

这里的“文档”可以是文本片段，不必是整份 PDF。论文把 Wikipedia 划分成不重叠的 100 词片段，得到约 2,100 万条检索单元；训练检索数量取 5 或 10，再在验证集上选择测试时的数量。[R1，§3，p. 4](#source-r1)

这些是论文的实验配置，不是金融文档切分的推荐常数。表格、脚注与限定条件是否应该一起保留，要由实际任务决定。

### 2.2 为什么把检索文档当成隐变量？

训练样本通常给出问题 $x$ 和答案 $y$，但未必告诉系统：“这个答案应该由文档 A 而不是文档 B 支持。”

于是令 $z$ 表示潜在的支持文档。检索器提供 $P_\eta(z\mid x)$，生成器提供 $P_\theta(y\mid x,z)$。两者结合后，对可能的文档求和。

#### RAG-Sequence：同一文档支持一个完整生成分支

$$
P(y\mid x)\approx\sum_{z\in\operatorname{TopK}(x)}P_\eta(z\mid x)\prod_iP_\theta(y_i\mid x,z,y_{<i})
$$

直观解释是：分别考虑“根据文档 A 生成整段答案”“根据文档 B 生成整段答案”的可能性，再按检索概率组合。

**这不是只检索一篇文档，而是每个候选生成分支内部采用同一篇文档。**[R1，§2.1，p. 3](#source-r1)

#### RAG-Token：答案不同部分可依赖不同候选文档

$$
P(y\mid x)\approx\prod_i\sum_{z\in\operatorname{TopK}(x)}P_\eta(z\mid x)P_\theta(y_i\mid x,z,y_{<i})
$$

它在每个输出位置上，对不同候选文档的贡献进行边缘化。例如，答案前半部分更多依赖文档 A，后半部分更多依赖文档 B。

**这不意味着每生成一个 token 都重新去数据库搜索一次。**论文先取得 Top-K 候选，再组合这些候选所对应的下一个 token 分布。[R1，§2.1，p. 3](#source-r1)

两种公式中，求和与连乘的位置不同，代表的是文档选择粒度不同，不只是实现上的记号差异。

### 2.3 检索器如何从答案监督中学到“什么更有用”？

论文联合训练查询编码器和 BART，固定文档编码器及索引。固定索引避免文档向量持续变化时反复重建整个检索库。[R1，§2.4，pp. 3–4](#source-r1)

下面从 RAG-Sequence 目标做一个教学推导。对一次训练样本，在固定候选集合中记：

$$
p_z=P_\eta(z\mid x),\qquad g_z=P_\theta(y\mid x,z)
$$

损失为：

$$
\mathcal L=-\log\sum_zp_zg_z
$$

定义：

$$
r_z=\frac{p_zg_z}{\sum_jp_jg_j}
$$

$r_z$ 可以理解为：已知正确答案以后，文档 $z$ 对生成这个答案应该承担多大“责任”。

如果检索概率由候选分数 $s_z$ 的 softmax 得到，则在固定候选集合的简化条件下：

$$
\frac{\partial\mathcal L}{\partial s_z}=p_z-r_z
$$

一组教学数字：

| 文档 | 原检索概率 $p_z$ | 生成正确答案的概率 $g_z$ | 后验责任 $r_z$ |
|---|---:|---:|---:|
| A | 0.8 | 0.1 | 约 0.308 |
| B | 0.2 | 0.9 | 约 0.692 |

文档 A 很像问题，但对生成正确答案帮助较小；文档 B 被低估，却更有用。梯度下降会降低 A 的相对分数、提高 B 的相对分数。

这条推导不能理解为对离散 Top-K 选择直接求导。它解释的是候选集合固定时，检索分数如何受到答案监督影响。

**工程启发：检索要优化的不只是“看起来相似”，而是“帮助当前任务正确完成”。**

还要保留一个训练边界：RAG 的联合微调没有使用直接的支持文档标签，但它初始化使用的 DPR 已接受过 Natural Questions 和 TriviaQA 的检索监督。因此，不能把整套方法描述为从未使用过检索监督。[R1，§2.2、§4.1，pp. 3、5](#source-r1)

### 2.4 RAG 与讲义的检索信号怎样连接？

讲义第 11 页列出五个信号：Semantic match、Scope、Importance、Validity、Provenance。[L06，p. 11](#source-l06)

| 信号 | 需要回答的问题 | 基金审核中的示例 |
|---|---|---|
| 语义匹配 | 内容是否与当前查询有关？ | 是否讨论业绩比较 |
| 作用范围 | 是否属于同一用户、项目、实体或任务？ | 是否同一基金、同一份额 |
| 重要性 | 漏掉或错误引入的代价是什么？ | 是否包含决定结论的例外条件 |
| 有效性 | 对本任务、在这个时间是否成立？ | 数据期间和适用版本是否一致 |
| 来源 | 信息来自哪里，有什么证据？ | 原始表头、数据接口、来源版本 |

RAG 解释了“相关信息如何影响生成”。讲义进一步要求“这些信息是否有资格用于当前任务”。

工程上可以分成两步：先判断能不能用，再判断值不值得读。权限、实体身份和硬性时间条件应作为准入或明确的使用约束，不能仅作为可被高相似度抵消的软分数。

### 2.5 实验一：为什么 BM25 在某些任务上仍然有价值？

论文的检索消融中，学习式密集检索在开放域问答上有优势；但 FEVER 事实验证任务上，替换成 BM25 的版本表现更好。作者推测 FEVER 更依赖实体和词项重合。[R1，§4.5，pp. 7–8，表 6](#source-r1)

这并不证明某种金融检索方案最优，但提醒我们区分查询性质：基金代码、条款编号、份额类别和报告期可能更需要精确匹配；案例措辞、风险表达和类似失败经历则可能受益于语义匹配。

不要把“密集向量”当成所有检索任务的统一答案，也不要未经评测就把原始 RAG 的实验结论推广到自己的语料。

### 2.6 实验二：换索引，可以更新模型能访问的知识

论文使用 2016 年和 2018 年的 Wikipedia 索引，对 82 位在此期间发生变化的世界领导人构造模板问题。与目标年份匹配时准确率分别约 70% 和 68%；2018 索引回答 2016 年目标、2016 索引回答 2018 年目标时则分别为 12% 和 4%。[R1，§4.5，pp. 7–8](#source-r1)

这个实验支持：**非参数化记忆可以独立于生成模型参数更新，并影响回答。**

但“能更新外部知识”不等于“能正确回答任意历史时点问题”。后者还需要保存版本、明确查询时间，并区分信息有效时间和系统获知时间，第 4 章继续展开。

### 2.7 实验三：答案正确，不代表当前文档已经提供充分证据

RAG 报告，在 NQ 中，即便检索文档没有包含正确答案，模型仍有 11.8% 的情况生成正确答案。第 7 页图 2 及相关分析也展示了参数化知识与检索信息配合：外部片段引导模型生成书名开头，模型可能用参数中的知识补全后续内容。[R1，§4.1、§4.3，pp. 6–7](#source-r1)

这里的“文档没有包含答案”不必然等于文档毫无支持作用；文档可能包含间接线索。不能把 11.8% 全部归为无证据猜对。

但这个实验足以提醒工程系统：

> **模型的生成结果可能同时来自检索内容、参数化知识和推断。仅凭答案正确，不能证明每项结论都由当前证据完整支持。**

在开放域问答中，这种知识互补可能是优点；在要求严格依据的审核任务中，必须另行检查“这条证据是否支持这项具体结论”。

### 2.8 RAG 留下了什么问题？

RAG 主要回答外部知识如何参与生成。它没有自动回答：该读取几次、如何根据已取得的信息改写下一次查询、哪些新信息值得写入长期记忆、怎样管理上下文容量、何时停止，以及错误记忆如何撤回。

**因此，RAG 是记忆系统的重要读取机制，但不是完整的 Agent Memory 生命周期。下一层问题不是换一个向量数据库，而是谁来决定“现在该看什么”。**

## 3. MemGPT：把记忆调度变成可执行的控制流

> **与讲义的关系**：展开模型控制型记忆、存储层级、上下文组织与运行时责任。  
> **核心参考**：[R2，§2–3](#source-r2)。

### 3.1 从一次检索到主动的信息获取

RAG 更像有人把资料找好放在桌面上。MemGPT 更进一步：Agent 可以自己决定何时查档案、把什么保留在桌面、把什么移出去，以及查完一页后是否继续。

例如：

```text
搜索上次讨论
→ 确认项目名称
→ 查询项目迁移记录
→ 找到服务引擎变更时间
→ 回看迁移之前的决策依据
→ 汇总答案
```

每一步的新信息会改变下一步查询。此时，检索不再是问题前的一次预处理，而是任务执行的一部分。[R2，§2.3–2.4，pp. 3–4](#source-r2)

### 3.2 按第 3 页架构图理解五类状态

MemGPT 区分当前上下文与外部存储。当前上下文包含三个区域，外部存储包含两个重要部分。[R2，图 3、§2.1–2.3，pp. 2–3](#source-r2)

| 区域 | 主要内容 | 读写责任 |
|---|---|---|
| System Instructions | 记忆层级、函数使用与控制流规则 | 只读、静态 |
| Working Context | 需要持续关注的关键事实、偏好、核心信息 | 固定容量，通过函数修改 |
| FIFO Queue | 最近消息、系统提示、工具调用与结果、递归摘要 | Queue Manager 管理 |
| Recall Storage | 历史消息记录 | Queue Manager 写入，模型通过函数读取 |
| Archival Storage | 可保存较长文本的外部档案 | 模型通过函数读写 |

```text
当前有限上下文：System Instructions（只读）
                Working Context（函数可修改）
                FIFO Queue（Queue Manager 写入）
                          ↓ 模型输出函数调用
                    Function Executor
                    ├── 读写 Archival Storage
                    ├── 修改 Working Context
                    └── 查询 Recall Storage，结果经队列进入上下文

Queue Manager：维护 FIFO、写入 Recall Storage、处理消息淘汰与递归摘要
Recall Storage：保存消息历史；不由模型直接改写历史
```

这是便于阅读的文字化示意，不是对论文所有组件连线的逐像素复刻。原始图 3 还区分输出缓冲区，并标注了各层具体读写权限。

最关键的责任边界是：**模型提出读写请求；运行时负责解析、参数校验、存储执行、容量控制和结果回传。**“模型自主管理记忆”不意味着存储系统失去程序化边界。

### 3.3 上下文快满时，先交接关键状态，再淘汰旧消息

Queue Manager 在上下文接近阈值时插入 memory pressure 提示，给模型机会把重要信息迁移到 Working Context 或 Archival Storage。达到清理阈值后，系统淘汰一部分消息并更新递归摘要。论文实现仍将移出的原始消息保存在 Recall Storage，之后可以再次检索。[R2，§2.2，p. 3](#source-r2)

论文中的 70% 警告阈值、100% 清理阈值、淘汰约 50% 等是举例，不是经过证明的最优参数。实际工程还需要给输出和工具返回预留空间。

最值得迁移的，不一定是最长的段落，而是影响后续动作的事实和约束：

> 当前目标是 A 类；已取到的是 C 类；目标份额核验尚未完成；不能把这条观测当作目标数据。

如果压缩后只留下“业绩数据已处理”，上下文整理就改变了任务状态。这直接对应 AgentErrorTaxonomy 的 Over-simplification / Incomplete Summary。[R3，附录 A.2，pp. 13–14](#source-r3)

**MemGPT 提供状态搬运机制；AgentDebug 的分类告诉我们，搬运时丢掉哪些信息会导致错误传播。**

### 3.4 Heartbeat 与 yield：继续读取也是一个架构问题

MemGPT 允许函数调用请求工具完成后的下一次模型推理；论文使用 `request_heartbeat=true` 表示这种继续请求。不请求继续时，系统让出控制权，等待用户消息、系统事件或定时事件等新的触发。[R2，图 3、§2.4，pp. 3–4](#source-r2)

这支持如下过程：

```text
查第一页
→ 看结果
→ 证据不足，继续查询
→ 取得新信息
→ 判断足够，回答并让出控制权
```

这里的研究贡献不只是一个搜索 API，而是把**检索、上下文编辑、响应和停止**放进可调度的控制流。

同时，新能力也带来新故障：模型可能不继续找，也可能反复找同样内容。读取策略本身必须评估，不能只评估向量索引的召回率。

### 3.5 为什么“虚拟上下文”不是无限注意力？

MemGPT 使用操作系统虚拟内存作为设计类比，但模型在一次推理中仍只看到当前装载的内容。外部资料再多，也不会自动同时进入注意力计算。

语义检索还可能漏召回；摘要可能丢信息；模型可能过早停止；函数调用也可能错误。因此，按语义找资料不具有精确地址读取内存页的同等保证。

论文在多跳检索实验中也观察到：某些底座模型没有执行足够多次查询，导致性能下降。[R2，§3.2.2，pp. 7–8](#source-r2)

**正确理解是：有限上下文通过多轮调度访问更大的外部空间，而不是底座模型获得了无限且无损的上下文。**

### 3.6 实验一：深层历史回忆 DMR

论文基于 Multi-Session Chat 的五次历史会话构建第六次会话的深层记忆检索问题，问题与参考答案由另一个 LLM 生成，准确率由 LLM Judge 对照参考答案判断，另报 ROUGE-L recall；它不是人工真实用户长期使用的成功率。论文比较固定上下文基线与 MemGPT。[R2，§3.1.1，p. 5，表 2](#source-r2)

| 模型 | 固定上下文基线准确率 | 加入 MemGPT |
|---|---:|---:|
| GPT-3.5 Turbo | 38.7% | 66.9% |
| GPT-4 | 32.1% | 92.5% |
| GPT-4 Turbo | 35.3% | 93.4% |

理解这个提升必须同时看输入条件：基线看到前面会话的有损摘要；MemGPT 可以通过分页搜索访问完整历史。§3 明确本实验端点为 `gpt-3.5-turbo-1106`、`gpt-4-0613` 与 `gpt-4-1106-preview`，对应约 16K、8K、128K 的底座窗口；这些是 2024 年归档版本的配置，不代表当前同名产品。

因此，实验支持“保留原始历史并按需访问，能够显著缓解只依赖摘要的损失”。它没有证明相同架构在任意模型、任意任务和相同总预算下都具有同样幅度的优势。

### 3.7 实验二：对话开场与主动利用记忆

MemGPT 还研究 Conversation Opener：下一次会话的开场是否能利用以前的用户信息。论文用与 persona 标签和人工开场的相似度指标评价，指出 Working Context 中的信息有助于主动生成个性化开场。[R2，§3.1.2，pp. 5–6，表 3](#source-r2)

这是“主动利用记忆”而非“用户明确问起后回忆”的另一种能力。但相似度分数较高，不能直接等同于用户真实体验、业务质量或隐私适当性更好。投研系统需要的是任务相关的信息，不是每轮都展示对用户的了解。

### 3.8 实验三：文档问答与分页

第 6 页图 5 在从 NaturalQuestions-Open 抽取的 50 个问题上，使用 LLM Judge 评估文档问答；二者采用同一种 `text-embedding-ada-002` 向量检索，MemGPT 使用 PostgreSQL／pgvector，并能继续查询和分页。固定上下文基线为了容纳更多文档，需要截短文档；当压缩增强，关键内容被截掉的风险上升。MemGPT 可以分页读取，不必把全部文档一次塞入上下文。[R2，§3.2.1，pp. 6–7，图 5–6](#source-r2)

这里要分清三个量：外部库容量、单次装载量、整项任务累计读取量。它们不是同一个“上下文长度”。

论文也明确承认：即使理论上可以不断翻页，MemGPT 仍有时会提前停止。这个发现把存储容量问题进一步转化为“信息获取策略是否可靠”。

### 3.9 实验四：嵌套键值检索

论文构建多跳键值查询：

```text
A → B
B → C
查询 C，判断它是否仍是一个键
最后返回终点值
```

基础模型可能能完成一次键值查询，却在多次关联时失败。MemGPT 通过显式查询改善这一能力，但不同底座模型仍有差异；某些版本会因为没有执行足够查询而下降。[R2，§3.2.2，pp. 7–8，图 7–8](#source-r2)

这把三个问题分开了：库中有没有信息、工具能不能访问、Agent 会不会正确组合访问结果。

它也预示了后面 Beyond the Leaderboard 的主题：**子技能分别能做，不代表组合起来就稳定完成。**

### 3.10 从 MemGPT 回到完整记忆设计

MemGPT 补上了主动读写和上下文调度，但早期实现并不等于完整的时间治理、跨用户隔离、衍生记忆删除、证据核验和生产恢复机制。

下一章回到讲义的生命周期：谁可以把什么内容写成长期事实，何时应该更新或遗忘，以及怎样避免原始记录在压缩和归纳中改变含义。

## 4. 记忆生命周期：从原始事件到可复用经验

> **讲义主线**：Write / Skip → Encode / Organize → Store → Retrieve → Reflect / Generalize → Keep / Update / Delete，并讨论所有权。[L06，pp. 6–17](#source-l06)  
> **串联关系**：RAG 负责知识读取，MemGPT 负责主动调度；本章处理两者都不能自动替代的语义治理。

### 4.1 写入：事件记录与活跃记忆承担不同责任

讲义指出，写入每次交互会提高召回，也会提高噪声。写入决策可以来自明确的用户要求、确定性规则、小分类器或周期性 LLM 审查。[L06，p. 7](#source-l06)

这里最重要的区分是：

**事件记录保存“发生过什么”；活跃记忆保存“未来决策值得复用什么”。**

例如，“这次汇报先不讨论估值”可以属于本次任务约束，却不能直接变成“用户不关心估值”。“接口在 14:03 超时”是一条观测，也不能直接变成“这个接口永久不可用”。

一个工程写入流程可以是：

```text
原始事件
→ 提取候选记忆
→ 判断是否值得长期保留
→ 核对来源、范围与限定条件
→ 检查重复与冲突
→ 标注事实／推断／待验证
→ 提交到相应记忆层
```

保留事件同样需要权限和保留期限，不意味着永久保存所有内容。区别在于，原始记录承担追溯责任，活跃记忆承担决策支持责任。

### 4.2 编码：压缩不能改变条件、否定和不确定性

讲义用“从 vLLM 迁到 SGLang”比较四种表示方式。[L06，p. 8](#source-l06)

| 表示方式 | 保存示例 | 优势 | 主要风险 |
|---|---|---|---|
| Raw events / episodes | “我们把服务从 vLLM 迁到了 SGLang。” | 保真度高、可回溯过程 | 冗余、检索和阅读成本较高 |
| Unstructured summaries | “项目使用 SGLang 服务模型。” | 紧凑、易读 | 可能丢失迁移时间和原因 |
| Structured state | `{"serving_engine":"SGLang"}` | 易查询和校验 | 字段设计决定能够保留什么 |
| Knowledge graph | `Project → USES → SGLang` | 易表达实体关系 | 仍然需要时间、来源和冲突处理 |

这些方式不必四选一。原始记录保留证据，结构化记录表达事实，工作摘要辅助理解，索引帮助查找，可以配合使用。

压缩的目标应当是保留决定后续行动的语义，而不只是缩短文字。

> 原文：“在当前披露口径下，这个比较暂时不能使用。”  
> 错误摘要：“这个比较不能使用。”

错误摘要没有凭空创造主题，但它删掉了条件和时间限定，扩大了判断范围。AgentDebug 将这类错误列在 Memory 模块中，而不是只归为语言生成质量差。[R3，附录 A.2，p. 14](#source-r3)

对工作摘要，除了“已经知道什么”，还应保留“仍不知道什么”“哪些检查没有完成”“哪些假设已经排除”。这些是本文对执行状态的工程要求，不是要求模型保存全部中间思考过程。

### 4.3 存储：不要让相似度承担精确状态管理

讲义列出文件、键值或关系数据库、向量存储、图数据库。[L06，p. 9](#source-l06)

| 存储方式 | 讲义强调的用途 | 适合承载的信息示例 |
|---|---|---|
| 普通文件 | 容易检查、比较差异和搜索 | 项目说明、任务笔记、可审核的文本经验 |
| 键值／关系数据库 | 精确查询、过滤、事务 | 实体身份、版本、时间、任务状态 |
| 向量存储 | 精确或近似相似度搜索 | 相似历史案例、相关语义片段 |
| 图数据库 | 关系查询、多跳遍历 | 项目、人物、事件之间的关联 |

这是能力划分，不是要求同时部署四类数据库。一个小团队可以先用关系数据库保存状态和元数据，用文件保存原始资料，再根据实测需求增加检索索引。

在业务查询中，“这条记忆属于哪个用户”“基金代码是什么”“当时哪一版有效”通常需要精确条件；“有没有类似的经历”才主要依赖语义相似度。

**向量索引适合发现候选，不应该成为事实有效性、权限与执行进度的唯一真相来源。**这是从讲义用途划分得到的工程结论。

### 4.4 读取：自动、运行时控制、模型控制可以混合

讲义比较了三类策略。[L06，p. 10](#source-l06)

| 策略 | 方式 | 好处 | 风险 |
|---|---|---|---|
| Automatic | 每轮搜索、调用模型、写入 | 简单且可预测 | 延迟增加，可能引入无关上下文 |
| Runtime-controlled | 规则或分类器决定何时读写 | 选择性强、便于控制 | 需要设计判定逻辑 |
| Model-controlled | 模型调用搜索、添加、更新、遗忘工具 | 按需、灵活 | 可能漏读漏写，或反复调用 |

MemGPT 展示了模型控制型读取与运行时管理的结合：模型决定信息需求，Queue Manager 和 Function Executor 管理容量与执行。

对于审核 Agent，一个可行的分工是：当前材料版本、产品身份、份额、任务不变量由运行时保持；是否搜索某个相似案例由模型按需决定；最终读写权限和状态转换由程序执行。

这里的“关键约束固定在窗口外”，不能理解为模型能直接看到窗口外数据。它指约束保存在不受聊天裁剪影响的状态中，并在必要时重新注入上下文或由程序直接执行检查。

### 4.5 检索：先准入，再排序，再按任务组织

讲义强调相似性不是唯一信号。可以把它落实为以下工程流程：[L06，p. 11](#source-l06)

```text
识别用户、项目、实体与任务
→ 权限和作用范围过滤
→ 按任务要求选择有效时间与版本
→ 精确查询、关键词和语义检索
→ 检查来源与冲突
→ 排序、去重、选择上下文内容
→ 保留来源指针与未解决冲突
```

“去年使用 vLLM”和“现在使用 SGLang”可能都是真实历史。检索出两条并不一定错，错的是不区分时间就把旧事实覆盖当前状态。

同样，查询历史任务时，最新事实不必然是最适用事实。使用哪一版取决于问题要求，而不是总是取更新时间最大的一条。

### 4.6 归纳：推断必须保留为推断

讲义把“用户多次询问 vLLM、SGLang、TRT-LLM 和调度”归纳为“可能经常关注 LLM 推理系统”，明确标为 Hypothesis，置信度为中等。[L06，p. 12](#source-l06)

可以据此区分三种工程状态：

| 状态 | 含义 | 不能被误解成什么 |
|---|---|---|
| Observed | 用户、文档或工具实际提供了这项内容 | 来源内容必然客观正确 |
| Inferred | 系统根据已有信息得到推断 | 已经由外部证据确认 |
| Verified | 经过指定检查、在相应范围和版本下通过 | 永久、无条件、绝对正确 |

这是一种工程建模方案，不是论文统一规定的枚举。实际系统可以把“来源类型”和“验证状态”拆成两个独立字段，避免将它们当作单一等级。

尤其要警惕反思回流：AgentDebug 的根因判断首先是一个诊断假设。只有回查证据、验证修复结果之后，才适合晋升为可复用经验。否则，错误执行可能经过错误反思，变成更持久的错误记忆。

### 4.7 经验应当包含适用条件、动作和验证方法

“下次更认真”“注意风险提示”很难直接指导下一次执行。更有用的经验形式是：

```text
适用条件：任务涉及同一产品的不同份额或口径
观察到的问题：名称相同导致错误匹配，摘要丢失份额字段
动作：按产品代码、份额、期间与口径联合核对
验证：所有目标字段一致后，才能标记核验通过
例外与限制：这条经验不解释所有业绩差异
来源：已人工复核的具体案例与修复记录
```

这是对前面讨论的经验记忆设计，不是论文里已有的金融规则。

人工采纳一条修改建议，证明的是“这次反馈被采纳”，不自动证明“原措辞在全部场景中都不合规”。案例回流和规则升级应该分开。

### 4.8 时间：有效时间与系统获知时间不能混淆

讲义要求 valid time 和 provenance：哪条事实在哪个时间成立，以及来自哪个 episode。[L06，p. 14](#source-l06)

工程上，还可以增加 recorded time，即系统何时得到这条信息。

例如，系统 6 月 3 日收到通知：“项目从 6 月 1 日起切换服务引擎。”那么有效时间从 6 月 1 日开始，系统获知时间却是 6 月 3 日。

这能回答两个不同问题：

> 6 月 2 日实际使用什么？  
> 截至 6 月 2 日，我们的系统知道什么？

该区分是对讲义时间管理的工程扩展，尤其适用于历史复盘。它不应被自动解释为所有数据源已经提供相应的时间元数据。

示例记录：

```json
{
  "id": "mem-018",
  "scope": {
    "tenant_id": "team-demo",
    "project_id": "project-p"
  },
  "claim": "项目 P 使用 SGLang 提供模型服务",
  "source_kind": "user_statement",
  "verification_status": "source_confirmed",
  "valid_from": "2026-06-01",
  "valid_to": null,
  "recorded_at": "2026-06-03T09:00:00+08:00",
  "source_event_id": "event-28",
  "status": "active",
  "supersedes": "mem-011",
  "version": 3
}
```

这条示例中的确认只针对来源陈述，并不宣称已检查实际运行环境。

### 4.9 冲突：不要把所有差异都当作“更新覆盖”

一条新记录与旧记录不同，至少可能有几种情况：同一事实真实发生变更；不同实体被错误合并；不同时间或口径下两条都成立；来源互相矛盾；旧记录本来就是错误推断。

因此，不应统一采取“新内容覆盖旧内容”。可以保留 supersedes、conflicts_with、来源和适用范围，让系统知道这是版本替换还是尚待解决的冲突。

同一份原始证据被多次摘要和引用，也不应被误认为多个独立来源。否则，记忆库中的重复记录会制造虚假的证据强度。这是本文对来源治理的工程要求。

### 4.10 遗忘：停止使用与彻底删除是两种操作

讲义列出标记无效、永久删除、TTL 到期、分层淘汰等方式。[L06，p. 13](#source-l06)

**停止作为当前事实使用**，可以通过失效或降级处理。**不再保留该信息**，则需要处理原文、结构化记录、摘要、索引、缓存和衍生经验。

```text
原始事件
→ 提取事实
→ 工作摘要
→ 检索索引
→ 缓存
→ 从该事实归纳出的经验
```

只删向量，而后台又从原文重建索引，不等于完成删除；只改一条核心记忆，而其他摘要仍保留旧值，也可能让过期信息再次进入上下文。

这并非 MemGPT 早期的历史保留机制已经解决的问题。记忆系统进入真实业务后，需要单独设计删除语义、依赖追踪和防止重新生成的控制。

### 4.11 所有权：Agent 自己维护，还是独立记忆层？

讲义比较 Harness 内的文件、任务笔记与独立记忆 API。文件方便检查和 diff；独立服务便于跨 Agent、跨会话共享，但引入共享更新问题。[L06，pp. 15、21](#source-l06)

第 16 页用 Mem0、Graphiti、supermemory 分别示例事实型、时态知识图谱型，以及画像／记忆／文档整合型设计。这是讲义中的定位，不是本文核验过的当前产品能力比较。[L06，p. 16](#source-l06)

真正需要决定的是：谁可以写入、谁可以晋升事实、如何处理并发修改、旧摘要会不会覆盖新记录、删除是否传播到所有读取入口。

单 Agent 的错误可能是“我记错了”；共享记忆的错误可能变成“所有 Agent 都读取同一个错误前提”。这自然连接到第 9 章的 MAST。

<a id="chapter-5"></a>
## 5. Memory 也会制造故障：八类失败与持久化污染

> **核心依据**：[L06，p. 18](#source-l06)。  
> **连接论文**：AgentDebug 的记忆错误与错误传播、MAST 的交接问题、Beyond the Leaderboard 的安全失败。

### 5.1 八类失败要区分，修复方法不能混用

| 讲义中的失败模式 | 含义 | 贯穿案例中的表现 | 工程排查方向 |
|---|---|---|---|
| Retrieval miss | 有用记忆存在，但没找到 | 原表头有份额信息，却没检索到 | 查询、索引、范围、分页和召回 |
| Context pollution | 无关内容进入上下文 | 大量旧案例挤占当前证据 | 准入、排序、去重、预算 |
| Memory hallucination | 推断或虚构内容被保存为事实 | 将 C 类记成 A 类 | 原始证据、来源类型、写入校验 |
| Staleness | 旧信息覆盖新信息 | 使用旧版本材料或过期数据 | 有效时间、版本与失效传播 |
| Isolation failure | 记忆越过用户或范围边界 | 读取其他用户或项目的私有案例 | 权限与租户隔离 |
| Overgeneralization | 一次事件变成长期规则 | 一次采纳变成永久审核规则 | 适用条件、例外、晋升审批 |
| Persistent prompt injection | 不可信内容以后以指令身份出现 | 文档指令被总结成操作要求 | 信任边界、来源标记、权限执行 |
| Unbounded growth | 长期积累导致成本和质量下降 | 重复摘要与重复案例越来越多 | 生命周期、合并、分层和淘汰 |

前两类尤其容易误修：找不到资料时可能需要改善召回；无关资料太多时盲目扩大 Top-K，可能让问题更严重。

### 5.2 为什么错误写入比一次错误回答更危险？

一次错误回答未必会再次进入后续任务。但被标注为“已确认”的错误记忆，会改变以后上下文的默认前提。

```text
错误提取
→ 写成确定事实
→ 自动检索进入下一任务
→ 新结论引用旧错误
→ 新结论又成为额外记忆
```

这条循环是根据讲义故障模式与 AgentDebug 的传播机制做出的工程推演。它说明，优化记忆不能只看检索 recall，还要看写入 precision、失效处理和错误重新引入率。

### 5.3 持久化提示注入：保存过，不代表可信度提升

讲义明确把 persistent prompt injection 列为记忆风险：不可信内容以后作为指令返回。[L06，p. 18](#source-l06)

例如：

```text
外部材料中包含诱导性操作要求
→ 摘要没有保留“这是文档内容”的来源边界
→ 被保存成“项目规范”
→ 下一次任务自动加载
→ Agent 按它决定工具动作
```

这里的关键不是文本有没有被保存，而是它的身份是否从“待处理数据”被错误提升成“系统必须遵守的指令”。

工程上应保留来源与信任属性，将外部材料作为数据处理。权限检查和高风险动作授权应由运行时执行，不能依赖同一份可能被污染的记忆决定。

### 5.4 安全暂停不是业务成功，强能力也不是安全保证

Beyond the Leaderboard 区分能力错误与安全错误：一个调用可以格式正确、执行成功，但仍可能因不当假设或恶意内容而造成不适当的行为。[R5，§4.5，pp. 8–9](#source-r5)

因此，至少要分开回答：动作是否能执行、是否满足任务、是否获得授权、是否允许承担这种后果。

本文没有新增具体安全法规判断。对示例系统而言，材料审核与最终发布是不同权限，是否允许发布需要由业务授权明确决定。

<a id="chapter-6"></a>
## 6. Reliability：长任务需要的不只是单步正确率

> **讲义主线**：为什么错误累积 → 故障来自哪一层 → 面向失败设计。[L06，pp. 22–30](#source-l06)

### 6.1 正确理解 $0.95^{50}$

讲义假设每一步独立地以 95% 概率成功，并且任务要求每一步都成功，则：

$$
P(\text{全程无错})=0.95^T
$$

| 步数 $T$ | 全程无错概率 |
|---|---:|
| 1 | 95.0% |
| 5 | 77.4% |
| 10 | 59.9% |
| 20 | 35.8% |
| 50 | 7.7% |

这些是按讲义假设计算的示意值，不是某个 Agent 的实测结果。[L06，p. 22](#source-l06)

**全程没有错误不等于最终完成。**先传错参数、再修正参数，也可能完成任务。

真实步骤还可能相关。更一般地：

$$
P(E_1,\ldots,E_T)=\prod_{t=1}^{T}P(E_t\mid E_1,\ldots,E_{t-1})
$$

不能只根据“错误存在相关性”，就推断整体概率一定高于或低于 $0.95^T$。要看条件概率、恢复路径以及什么错误会阻止最终完成。

AgentDebug 研究的是另一层机制：早期错误改变后续状态，使后面的判断系统性偏离。这不是每一步额外掷一次独立骰子，而是前面的失败改变了接下来的路径。[R3，§5.2，pp. 8–9](#source-r3)

### 6.2 一个说明恢复价值的简化模型

设直接成功概率为 $p$；失败后被检测到的概率为 $d$；检测到后成功修复的概率为 $r$。忽略误报、恢复代价、新错误和预算限制，则：

$$
p_{\text{有效}}=p+(1-p)dr
$$

取教学数值 $p=0.95$、$d=0.9$、$r=0.9$：

$$
p_{\text{有效}}=0.9905
$$

再假设各步骤经过恢复后的结果独立，则 50 步约为：

$$
0.9905^{50}\approx62.0\%
$$

这不是论文实测提升，也不是生产预测模型。它只是解释：除了提高原始正确率，错误检测与恢复也是能够改变总体结果的变量。

真实系统中的检测器会误报、恢复会消耗预算，也可能执行错误补偿。因此，恢复策略必须和执行策略一样被评估。

### 6.3 五层故障：先找责任层，再决定修什么

讲义区分 User / task spec、Agent harness、LLM、Tool layer、Environment。[L06，p. 24](#source-l06)

下面保留讲义的主要故障与修复方向。它们是设计诊断表，不应被解释为每一项都有统一、已证明的最佳实现。

#### 第一层：Task specification

| 失败 | 讲义中的例子 | 修复方向 |
|---|---|---|
| 目标模糊 | “修复登录错误”，却修了三个问题中的另一个 | 指明症状、文件和复现方法 |
| 代理目标错误 | “让测试通过”，结果删除失败测试 | 规定不允许的修改，审查 diff |
| 隐含约束 | “加速搜索”，却破坏公共 API | 明确不能改变的条件 |
| 没有完成定义 | “清理解析器”，持续重构不停止 | 退出测试与停止规则 |
| 目标冲突 | 同时要求最小修改与全部边界覆盖，模型默默舍弃一项 | 明确优先级 |

来源：[L06，p. 25](#source-l06)。

这层问题不是提示词文风，而是任务合同。任务本身没有规定什么叫正确完成，模型可能优化一个错误的代理目标。

#### 第二层：Agent harness

| 失败 | 表现 | 修复方向 |
|---|---|---|
| 上下文截断 | 丢掉“保持 API 不变”的约束 | 将关键规则持久化，必要时重新注入或程序化执行 |
| 过期记忆 | 依据旧笔记编辑已移动的文件 | 时间标注与使用前复查 |
| 状态损坏 | 保留半完成编辑，后续依赖破损状态 | 检查点与失败步骤恢复 |
| 控制循环失控 | 没有步数或费用上限，长时间无进展 | 限制步数、费用与时间 |
| 阻塞 fan-out | 等待所有子 Agent，一个慢任务阻塞整体 | 超时与显式部分结果 |

来源：[L06，p. 26](#source-l06)。

“使用部分结果”不等于“假装全部完成”。必要子任务缺失时，应明确阻塞或限制结论范围，而不是把缺失内容当作已验证。

#### 第三层：Model

| 失败 | 表现 | 修复方向 |
|---|---|---|
| 幻觉 | 调用不存在的函数 | 对照实际文档与工具注册信息 |
| 不遵守约束 | 为了速度修改禁止改变的签名 | 重新表达约束并检查实际变更 |
| 推理错误 | 将超时解释为网络故障，实际是死锁 | 在修复前测试假设 |
| 推理与动作不一致 | 说只改一个文件，实际重写多个文件 | 对照计划检查动作 |
| 未验证就声明成功 | 没跑测试就说测试通过 | 要求真实测试输出 |
| 长任务退化 | 忘记自己已修复，再次撤销修改 | 重读状态、切分短任务 |

来源：[L06，p. 27](#source-l06)。

#### 第四层：Tool

| 失败 | 表现 | 修复方向 |
|---|---|---|
| 输出截断 | 只返回前 100 行，真正错误在后面 | 错误优先展示、支持分页 |
| 静默失败 | 失败却返回空结果，模型认为没有匹配项 | 区分 empty 与 failed |
| schema 模糊 | 时间没有时区 | 明确类型和语义 |
| 调用不稳定 | 第一次超时就判断服务不可用 | 对允许重试的暂时故障使用退避 |
| 错误信息误导 | 拼写问题却提示权限不足 | 返回精确且可操作的错误 |

来源：[L06，p. 28](#source-l06)。

#### 第五层：Environment

| 失败 | 表现 | 修复方向 |
|---|---|---|
| 过期状态 | 用昨天的缓存构建测试今天的代码 | 清理缓存、核对实际产物 |
| 版本不一致 | 开发与运行时依赖不同 | 固定版本与环境 |
| 随机失败 | 同一任务因环境随机条件失败 | 重跑诊断，隔离不稳定测试 |
| 页面布局改变 | 使用旧页面理解进行点击 | 操作前重新读取页面 |
| 限流 | 长任务中途遇到 429 | 节流、检查点与可恢复执行 |

来源：[L06，p. 29](#source-l06)。

### 6.4 为什么分类的目的不是“甩锅”，而是减少无效优化？

工具把超时包装成空数组，换大模型不一定解决，因为观测已经失真。

原始信息存在，但摘要丢失了产品份额，提高向量召回也不一定解决，因为有用字段在写入时就被删掉了。

两个 Agent 都看到了信息，却没有传递未完成事项，增加 Agent 数量可能增加交接点，而不是修复交接。

**先判断信息在哪个转换环节变错，再决定改善模型、提示、状态、工具还是环境。**下一章用 AgentDebug 把这个原则变成轨迹级诊断。

<a id="chapter-7"></a>
## 7. AgentDebug：定位关键错误，而不只是重写最后一个答案

> **与讲义的关系**：把“错误来自哪里”推进到“错误如何在轨迹中传播、应该从哪里恢复”。  
> **核心参考**：[R3，§2–5、附录 A.2、A.5](#source-r3)。

### 7.1 局部可执行，不代表全局正确

贯穿案例中的工具参数可以完全合法：基金代码存在、份额字段合法、查询日期合法。问题是这些参数来自错误的任务状态。

这与“工具缺少参数”不同。缺少参数可能立即暴露错误；语义状态错误却可能让每次调用都顺利执行，最终得到一个完全错误的结论。

AgentDebug 关注的就是这种依赖链：Memory 出错，Reflection 错误判断进度，Planning 在错误前提上制定计划，Action 按计划执行。最后的动作可能只是上游错误的表现。[R3，§2.1、§3.1，pp. 3、5](#source-r3)

### 7.2 研究对象与数据：诊断标签也有不确定性

论文先分析了来自 ALFWorld、WebShop、GAIA 的 500 多条失败轨迹，提出 AgentErrorTaxonomy。随后构建 AgentErrorBench，包含 200 条代表性轨迹：100 条 ALFWorld、50 条 WebShop、50 条 GAIA，由 10 位有相关研究经验的标注者参与标注。[R3，§2.1–2.2，pp. 3–4](#source-r3)

标注不只是给最终答案打分，还包括步骤错误、模块、关键根因和可操作反馈。论文报告跨模块 Cohen’s $\kappa=0.55$。

这个数值提醒我们：复杂轨迹的根因并不总能被一致地判断。不能因为论文给了一个“标准标签”，就把诊断任务想象成完全确定、不存在标注分歧的问题。

也不能直接把它与 MAST 的 $\kappa=0.88$ 比成“哪种方法更好”：两者的分类任务、标注程序和样本范围不同。

### 7.3 AgentErrorTaxonomy：五个模块、不同错误机制

论文把四个运行功能模块与系统错误放在同一分类表中。[R3，附录 A.2，pp. 13–14](#source-r3)

| 模块 | 原文错误类型 | 中文解释 |
|---|---|---|
| Memory | Over-simplification / Incomplete Summary | 摘要过于粗糙，遗漏关键限定 |
| Memory | Hallucination (False Memory) | 回忆了没有发生过的事实或状态 |
| Memory | Retrieval Failure | 有相关信息，但需要时未检索到 |
| Reflection | Progress Misassessment | 错判进度或是否完成 |
| Reflection | Outcome Misinterpretation | 误读刚发生的动作结果与反馈 |
| Reflection | Causal Misattribution | 知道失败，却解释错原因 |
| Reflection | Hallucination | 反思了没有发生的事件或结果 |
| Planning | Constraint Ignorance | 规划时忽视时间、预算等约束 |
| Planning | Impossible Action | 当前前置条件下不可能执行的计划 |
| Planning | Inefficient Planning | 计划冗长、不合理，浪费步数 |
| Action | Planning–Action Disconnect | 实际动作与计划意图不一致 |
| Action | Format Error | 生成语法无效的动作 |
| Action | Parameter Error | 参数不合理或格式不正确 |
| System | Step Limit Exhaustion | 因步数上限耗尽而失败 |
| System | Tool Execution Error | 外部工具或 API 出错 |
| System | LLM Limit | API、模型超时或 token 限制 |
| System | Environment Error | 环境、模拟器或网络异常 |

讲义的五层是系统责任划分；这里的五模块是决策过程划分。MAST 则关注多 Agent 的组织和交接。不要把它们硬合成一个互斥的“大分类表”。

同一事件可以同时标注责任层和功能表现：例如，Harness 截断引起 Memory 丢失，随后导致 Planning 忽略约束。

### 7.4 第一阶段：逐步骤、逐模块检查

AgentDebug 先为轨迹中的各步骤和模块识别细粒度错误。附录第 19 页的 Detector Prompt 明确要求依照错误定义判断、提供证据，并分别考虑各模块当时应使用的输入。[R3，附录 A.5，p. 19](#source-r3)

这解决一个重要问题：不能只因为最终失败，就把前面的每次探索都判为错误。

例如，第一次搜索没有找到数据，可能是合理探索；把“没找到”误写成“不存在”，才可能是状态错误。一个合理动作碰到环境故障，也不能自动归咎于模型推理。

工程中应依据实际可记录的内容诊断：任务输入、工具参数、观测、状态修改、可见计划和产物。不要假定总能取得模型完整内部推理，也不要把可见解释文本当作内部机制的完整记录。

### 7.5 第二阶段：从局部错误中定位关键错误

局部检测问：“这一模块是否违反定义？”全局诊断问：“哪项错误改变了后面整个任务的前提？”

在基金例子里，最早的关键错误可能是第 3 步丢失份额字段，而不是第 15 步写出错误结论。第 15 步文字不严谨可以修饰，但没有修复原始份额错误，其他结论仍然不可信。

附录第 20 页的 AgentDebug Prompt 要求从整条轨迹反向定位根因，输出关键步骤、模块、错误类型、证据、纠正建议及级联影响。[R3，附录 A.5，p. 20](#source-r3)

“最早出现的小错”和“最早关键错误”不是同一概念。有些小错误已经自行恢复，有些探索错误不影响最终任务，有些失败存在多个独立根因。

### 7.6 第三阶段：针对性反馈与重新展开

论文的思路是从定位出的关键位置重新执行后续轨迹，而不是每次从头重跑。反馈如果无效，就在预算内进一步调整。[R3，§3.2、Algorithm 1，pp. 5–6](#source-r3)

弱反馈：

> 请仔细检查，避免混淆。

更可操作的反馈：

> 第 3 步把 C 类数据压缩为基金级事实，丢失了份额属性。原始表头说明这是 C 类，任务目标却是 A 类。使该中间事实失效，重新取得 A 类数据，并重新执行依赖该事实的比较与结论检查。

后一种反馈同时说明错误位置、依据、应撤回的状态和下一步行动。

这也连接回记忆治理：诊断结果首先是待验证的判断，不能仅因它由“调试 Agent”产生，就直接升级为永久经验。

### 7.7 必须区分“诊断提出根因”与“通过干预证明根因”

归档版本存在一处重要差异：Algorithm 1 明确写着由 LLM 定位关键错误，不做 rollout/counterfactuals；第 3.2 节却描述逐步替换动作、通过反事实测试寻找关键错误。附录提示词则主要要求基于全局轨迹作出判断。[R3，p. 5 Algorithm 1；p. 6 §3.2；p. 20](#source-r3)

本文不替作者确定哪一种才是所有实验的真实实现。

工程上可以采取更清晰的分层：模型提出根因假设；可隔离的环境帮助验证；确认修复有效后，才提交状态更正和经验晋升。无法重放时，保留诊断不确定性。

修正某个错误后任务仍失败，也不一定说明这个错误毫无作用：可能还存在另一个独立阻塞点。单一根因叙事有时会过度简化真实系统。

### 7.8 错误定位实验：提升明显，但诊断远非完美

表 1 使用 GPT-4.1 作为诊断模型、temperature=0，报告三个环境的宏平均值；这不是将 200 条轨迹按样本量加权后的准确率，低温度也不构成服务端绝对可重复的保证。[R3，pp. 6–7，表 1](#source-r3)

| 方法 | Step：步骤正确 | Step + Module | All：步骤、模块、类型都正确 |
|---|---:|---:|---:|
| Direct Prompting | 28.0% | 10.0% | 0.3% |
| Brute Force | 12.0% | 4.3% | 0.0% |
| Binary Search | 18.7% | 8.0% | 0.3% |
| AgentDebug | 45.0% | 31.3% | 24.3% |

28.0% 到 45.0% 是增加 17 个百分点，相对增加约 60.7%。0.3% 到 24.3% 是增加 24 个百分点。这些不能混写为同一口径的“提升 17%／24%”。

更重要的是，它们是**错误定位成绩，不是业务任务完成率**。即便方案优于基线，45% 的步骤定位准确率仍意味着诊断器可能找错位置。

### 7.9 下游恢复实验：不能只比较首次尝试与多次尝试

论文 §4.2 声明最多 $N=5$ 次重新展开，并说明基线按总 token 使用量匹配；图 7(a) 的横轴另按五次 attempt 展示、首点是初次成绩，因此不能脱离图文口径自行推断“初次加五次”中每个报告值的位置。第 7 页图 5 展示 ALFWorld 上不同底座模型的结果。[R3，§4.2，pp. 7–8，图 5、7(a)](#source-r3)

| 底座模型 | 首次尝试 | Self-Refine | AgentDebug |
|---|---:|---:|---:|
| GPT-4o-mini | 21% | 41% | 55% |
| Qwen3-8B | 48% | 74% | 74% |
| Qwen3-Next-80B | 60% | 78% | 84% |

这些是该实验的成功率，不是当前模型的通用能力排名。Qwen3-8B 上，AgentDebug 与 Self-Refine 持平，并非严格胜过全部基线。

从首次尝试到多次恢复的提升，同时包含了更多执行机会；与预算匹配的基线比较，才更有助于判断针对性恢复机制的价值。论文给出了预算匹配说明，但不能因此推断所有工程部署的实际费用也完全相等。

### 7.10 消融：加入 Memory 不等于解决全部可靠性问题

第 8 页图 7(c) 报告一组零样本 rollout 策略比较：[R3，§5.1，p. 8](#source-r3)

| Rollout 策略 | 成功率 |
|---|---:|
| Act Only | 0.10 |
| ReAct | 0.26 |
| Reflection | 0.32 |
| Memory + ReAct | 0.34 |
| Modular | 0.38 |

它说明在该设置下，不同组织方式影响结果，单独加入记忆不是终点。但这不是证明每个任务都应拆成四次模型调用；分类中的功能模块也不必对应独立服务。

附录中的 Vanilla Debugger 也要求定位最早错误，因此不能把全部收益简单归因于“第一次想到根因分析”。更具体的差异来自错误定义、细粒度分析、全局组织、反馈和重新执行的组合。[R3，附录 A.5，pp. 19–21](#source-r3)

### 7.11 面向生产：诊断、恢复、经验学习是三条不同链路

诊断器回答“哪里可能错”；恢复器决定“允许如何修”；经验层判断“什么值得留给未来”。不要让一个自由生成的诊断文本同时取得三种权力。

论文没有训练一个专门的金融调试模型，也未验证本文的基金场景。它明确把更长任务、多模态和金融等高风险领域列为后续扩展方向。[R3，附录 A.1，p. 12](#source-r3)

因此，适合借鉴的是有证据的轨迹分析、局部恢复和预算约束，而不是让调试器拥有无限重试、任意回滚外部世界的权限。

<a id="chapter-8"></a>
## 8. Overthinking：推理应该帮助获取反馈，而不是替代反馈

> **与讲义的关系**：对应模型推理错误、未验证成功、控制循环和证据要求。  
> **核心参考**：[R6，§3–6](#source-r6)。

### 8.1 核心定义：不是 token 多，而是与环境脱节

论文把 Overthinking 定义为过度依赖内部推理，同时没有寻求或整合必要的外部反馈。[R6，§3.1，p. 3](#source-r6)

例如，发现 A 类与 C 类数据可能混淆后，模型开始长篇分析费用、期间、分红、更新节奏等可能原因，但不读取原始表头，也不查询目标份额。

问题不是文字长，而是不断围绕未知前提推演，却没有取得能改变判断的观测。

好的长推理可以帮助设计有效检查；坏的短推理也可能直接忽视反馈。不能用 token 数单独判定是否 Overthinking。

### 8.2 三种表现，对应三类闭环断点

| 原文术语 | 含义 | 工程中的可观察表现 |
|---|---|---|
| Analysis Paralysis | 大量规划，缺少实际进展 | 反复细化计划，却不读取必要文件、不运行检查 |
| Rogue Actions | 相互依赖的动作越过环境反馈 | 假定前一步成功，直接串起下一串修改 |
| Premature Disengagement | 根据内部预测过早退出 | 没完成必要验证就放弃或结束 |

来源：[R6，§3.2，p. 4，图 4](#source-r6)。

Rogue Actions 不等于所有并行调用都有问题。几个相互独立的只读查询可以并行；依赖前一步成功的后续修改，应在相应状态得到确认后执行。

Premature Disengagement 也不是要求 Agent 永远不能停止。证据不足、没有授权或预算耗尽时，可以明确暂停。论文批评的是不恰当地用内部预测替代可取得的环境验证。

### 8.3 MemGPT 与 Overthinking 的关系：有更多工具，不代表会取得更多有效信息

MemGPT 提供搜索、翻页、修改工作信息和继续推理等能力。使用得当时，它们帮助 Agent 缓解信息不足；使用不当时，也可能形成：

```text
没有读到关键证据
→ 反复总结已有内容
→ 把总结重新存入记忆
→ 检索到自己刚写的总结
→ 基于总结继续推理
```

这是一条工程上需要监测的循环，而不是 MemGPT 论文报告的固定故障模式。它综合了上下文调度与 Overthinking 的反馈问题。

因此，不能只记录“调用了几次工具”，还应看调用是否带来新证据、确认了哪些状态，或者是否重复已排除的路径。

### 8.4 论文如何测量 Overthinking？

作者根据三类可观察行为构建 0–10 分量表，使用 Claude Sonnet 3.5、temperature=0 给轨迹评分和依据。提示词刻意避免直接使用 “overthinking” 一词，以降低评估器套用自己定义的风险；评分时不提供最终任务成功标签，避免“失败所以过度思考”的循环判断。[R6，§3.3–4.1，pp. 4–6](#source-r6)

对 o1 系列，轨迹没有提供内部 reasoning tokens，作者因此强调可观察行为。人工校验由 4 位专家对 20 条随机轨迹进行评分。[R6，p. 4](#source-r6)

这一方法值得借鉴：不要只要求 Judge 判断“是否可靠”“是否认真”。更可测量的描述是：未运行验收却声明通过；工具返回失败却报告空结果；在没有新信息时重复相同动作。

但人工校验规模有限，跨模型相关性也不等于任何场景下的严格因果证明。

### 8.5 实验设置与推理预算：不支持“一律减少思考”

论文在 OpenHands 的 CodeAct 单 Agent 脚手架中使用 SWE-bench Verified，比较 19 个模型的轨迹。归档版本对总轨迹数存在 4,018 与 3,908 两种记载，详见附录 B。[R6，pp. 1–2、6](#source-r6)

第 7 页表 4 的均值为：

| 配置 | Overthinking 分数 |
|---|---:|
| o1 Low | 2.774 ± 3.081 |
| o1 High | 2.426 ± 2.880 |

方向上，高 reasoning effort 的平均分更低。正文“低预算高 35%”与这两个表中均值不对应，不能直接照搬该百分比。[R6，§5.4，p. 7](#source-r6)

**推理数量与反馈使用质量是不同变量。**工程决策应该先问：不确定性来自没有数据，还是已有数据之间的推理不足？

不知道字段含义，优先查 schema；已有完整信息但约束复杂，增加推理可能更有意义。高风险的外部动作则不能为了“试一下取得反馈”而绕过授权。

### 8.6 多候选与选择器：存在正确答案，不等于选中正确答案

论文区分 Pass@K 与 Lowest Overthinking@K。前者问 K 个候选中是否至少一个成功，后者只选择 Overthinking 分数最低的候选，再看它是否成功。[R6，图 3、§5.6，pp. 2、8](#source-r6)

| 候选数 K | Pass@K | 最低 Overthinking 分数候选的成功率 |
|---|---:|---:|
| 2 | 32.0% | 27.3% |
| 3 | 38.0% | 30.3% |
| 4 | 39.0% | 29.3% |

候选集中存在成功解的概率上升，最终选出的解却不一定更好。

对只负责选择、不额外改写或修复候选的选择器，可以写出：

$$
P(\text{选中正确})=P(\text{存在正确候选})\,P(\text{选对}\mid\text{存在正确候选})
$$

这与 Beyond the Leaderboard 的 verification gap 相连接：更多生成预算不一定能改善识别正确候选的能力。[R5，§4.2，p. 6](#source-r5)

### 8.7 成本实验：要保留比较基线

论文报告如下实验配置：[R6，§5.6，p. 8](#source-r6)

| 配置 | 解决率 | 论文报告的配置成本 |
|---|---:|---:|
| 低推理预算，单次尝试 | 21.0% | 400 美元 |
| 高推理预算，单次尝试 | 29.1% | 1,400 美元 |
| 两个低预算候选，按 Overthinking 分数选择 | 27.3% | 800 美元 |
| 三个低预算候选，按 Overthinking 分数选择 | 30.3% | 1,200 美元 |

这些不是当前价格，也不是每个用户任务的单次收费。

两候选方案相对低预算单次尝试，解决率相对提高 30%；相对高预算单次尝试，成本降低约 43%，但解决率为 27.3% 对 29.1%，并未更高。

因此，“性能提高 30% 且成本降低 43%”涉及不同参照配置，不能让读者误以为它相对同一基线同时实现了这两个改善。真实工程比较还需要统一计入选择器、验证器、工具和重试成本。

### 8.8 原生函数调用的结果：接口设计可能影响反馈使用

论文比较高推理预算 o1 有无原生函数调用：问题解决率从 29.1% 到 47.7%，平均 Overthinking 分数从约 2.43 降到 1.05。作者也指出，在另一项多轮函数调用比较中，提升更小，不能仅用函数调用能力解释全部变化。[R6，§6.1，p. 8](#source-r6)

可以借鉴的方向是：动作格式、工具接口与反馈回传会影响 Agent 行为。但不能据此推出所有模型启用原生函数调用都会得到相同收益，更不能把语法约束当作语义正确性的保证。

### 8.9 工程判断：把预算投到当前瓶颈

预算至少有三个用途：生成更多候选、取得更好的外部观测、提高验证与选择能力。

当缺少关键证据时，继续生成可能扩大猜测；当候选很多但无法判断对错时，更多候选可能只扩大选择难度；当动作语义错误时，减短推理也不一定修复状态。

本节结论不是“少想多做”，而是：**让推理服务于证据获取、约束分析和结果验证，并用真实反馈更新状态。**

## 9. MAST：多 Agent 可靠性取决于交接、职责与验证

> **与讲义的关系**：连接共享记忆、所有权、fan-out、任务规格与完成判断。  
> **核心参考**：[R4，§3–5、附录 H](#source-r4)。

### 9.1 先看 Phone Agent 的真实失败例子

MAST 第 6 页图 3 描述：上级 Agent 提供邮箱形式的用户名；Phone Agent 读取 API 文档后，本应知道 `username` 实际要求手机号；它仍使用邮箱登录。失败后，只向上级报告凭据错误，没有传递“用户名必须是手机号”的信息。[R4，图 3，p. 6](#source-r4)

这里不是数据库中没有信息。接口说明已经被读取，失败反馈也已返回，但关键信息没有完成交接。

**系统中某个 Agent 知道，不等于整体系统知道；消息发送成功，也不等于决策所需信息完整传递。**

这个例子串起前面的论文：RAG 改善检索未必有用，因为资料已经找到；MemGPT 增加上下文未必有用，因为不是只有容量问题；AgentDebug 应把“凭据错误”的表面现象追到“接口要求没有被使用和传递”。

### 9.2 MAST 的方法：先建立可复用的错误语言

论文从约 150 条轨迹的专家分析出发，通过 Grounded Theory 归纳错误模式，再迭代定义和标注，形成 14 类模式。随后使用经过人工校准的 LLM 标注流程扩展到 1,642 条轨迹，覆盖 7 类 MAS 框架配置。[R4，§3，pp. 4–6](#source-r4)

因此，不能把 1,642 条都描述为人工完整逐条标注。论文区分人工参与的数据与 LLM 标注扩展数据。

人工定义校准报告 $\kappa=0.88$；带 few-shot 的 LLM 标注器与人工结果比较报告准确率 0.94、F1 0.80、$\kappa=0.77$。没有 few-shot 的对应值为准确率 0.89、F1 0.64、$\kappa=0.58$。[R4，§3.3，p. 6，表 2](#source-r4)

工程价值在于：用清晰定义分析失败分布，而不只看一个总成功率。但分类一致性不等于已经严格证明了全部因果关系。

### 9.3 完整保留三类、十四种失败模式

| 大类 | 编号 | 原文名称 | 含义 |
|---|---|---|---|
| System Design Issues | 1.1 | Disobey Task Specification | 不遵守任务要求 |
| System Design Issues | 1.2 | Disobey Role Specification | 不遵守角色职责 |
| System Design Issues | 1.3 | Step Repetition | 重复执行步骤 |
| System Design Issues | 1.4 | Loss of Conversation History | 丢失对话历史 |
| System Design Issues | 1.5 | Unaware of Termination Conditions | 不清楚终止条件 |
| Inter-Agent Misalignment | 2.1 | Conversation Reset | 交互过程中不恰当地重置对话 |
| Inter-Agent Misalignment | 2.2 | Fail to Ask for Clarification | 应澄清时未澄清 |
| Inter-Agent Misalignment | 2.3 | Task Derailment | 偏离任务 |
| Inter-Agent Misalignment | 2.4 | Information Withholding | 未传递关键的信息 |
| Inter-Agent Misalignment | 2.5 | Ignored Other Agent’s Input | 忽略其他 Agent 输入 |
| Inter-Agent Misalignment | 2.6 | Reasoning–Action Mismatch | 推理与实际动作不一致 |
| Task Verification | 3.1 | Premature Termination | 提前终止任务 |
| Task Verification | 3.2 | No or Incomplete Verification | 未验证或验证不完整 |
| Task Verification | 3.3 | Incorrect Verification | 验证方法或判断错误 |

来源：[R4，图 1、§4，pp. 2、7–8](#source-r4)。

Information Withholding 是行为标签，不能仅凭这个词就推断 Agent 具有故意隐瞒的动机。

“下游没用到某信息”也可能有不同根因：上游没传、下游忽视、上下文被截断、旧状态覆盖。表面相似，修复位置不同。

### 9.4 失败比例：分母不同，不要混用

论文图 1 针对 1,642 条轨迹报告的三类分布为约 44.2%、32.3%、23.5%；图 4 针对每个系统前 30 条、共 210 条轨迹的分布为约 41.8%、36.9%、21.3%。[R4，图 1、图 4，pp. 2、8](#source-r4)

这些是论文各图报告的错误分布，不应直接改写成“44.2% 的所有业务任务因为设计问题失败”。分类标签、采样范围和任务条件都影响解释。

图 4 还明确说明，不同 MAS 配置的任务与基准可能不同，主要展示系统特征，不用于公平的跨系统性能排行。

### 9.5 可靠交接不能只有最终结论

贯穿案例中，下面的交接很危险：

> 收益率 12%，已核验。

一个更可操作的交接是：

```text
任务目标：基金甲 A 类
实际发现：基金甲 C 类，收益率 12%
核验状态：目标份额尚未核验
证据位置：原始表格引用
未完成事项：获取 A 类记录
使用限制：不得据此完成 A 类业绩比较
```

这是本文的工程交接契约。关键不仅是“发现了什么”，还包括“没确认什么”和“下游不能做什么”。

这与记忆摘要的要求完全一致：交接是跨 Agent 的状态压缩，摘要是跨时间的状态压缩，两者都可能丢掉影响决策的限定条件。

MAST 作者认为，标准化通信格式仍不足以覆盖全部协作问题，还需要改善消息内容和 Agent 对其他成员信息需求的理解。[R4，§4，p. 8](#source-r4)

### 9.6 共享错误不是多重独立验证

如果数据 Agent、分析 Agent 和审稿 Agent 都只读取同一条错误摘要，它们可以相互赞同，却没有增加独立证据。

审核 Agent 若只看初稿，通常只能检查文字一致性；要检查任务是否完成，还需要任务要求、原始证据和未完成检查项。

角色 Prompt、信息可见范围、工具权限和终止权应当匹配。写着“你是审稿员”，不代表它真的具备审稿所需的证据和执行权限。

### 9.7 形式验证、事实验证、任务验证要分开

MAST 的国际象棋案例中，程序通过编译等浅层检查，却没有验证真实游戏规则，产物仍然不可用。[R4，§4，p. 8](#source-r4)

可以区分三个层次：

| 层次 | 例子 | 无法自动保证的内容 |
|---|---|---|
| 形式正确 | JSON 能解析、代码能编译 | 数据和业务语义正确 |
| 局部事实正确 | 某个数字来自真实数据 | 实体、期间和比较口径符合任务 |
| 任务正确 | 所有必要要求在当前版本上满足 | 外部发布等动作已经获得授权 |

这又回到 RAG 的边界：生成正确文本，不等于每一项任务证据都已满足。

### 9.8 干预实验：针对故障改结构，而不是崇拜某种拓扑

论文附录 H 的表 5 为：[R4，pp. 26–27](#source-r4)

| 配置 | AG2 GSM-Plus / GPT-4 | AG2 GSM-Plus / GPT-4o | ChatDev ProgramDev-v0 | ChatDev HumanEval |
|---|---:|---:|---:|---:|
| Baseline | 84.75 ± 1.94 | 84.25 ± 1.86 | 25.0 | 89.6 |
| Improved prompt | 89.75 ± 1.44 | 89.00 ± 1.38 | 34.4 | 90.3 |
| New topology | 85.50 ± 1.18 | 88.83 ± 1.51 | 40.6 | 91.5 |

数值为论文报告的准确率百分数。AG2 使用随机抽取的 200 道 GSM-Plus 题，并做六次重复；ChatDev 的 ProgramDev-v0 是自建的 32 道程序生成任务，和文中另一套 ProgramDev 并非同一集合。表中的小数和误差不能脱离这些样本规模理解。不能跨不同列直接比较系统强弱。

ChatDev 的结构调整将一次性流程改为可循环审核，并由指定角色确认审核条件后终止，同时保留迭代上限。在 ProgramDev-v0 上，25.0% 到 40.6% 是增加 15.6 个百分点。改进 Prompt 的 34.4% 对基线是增加 9.4 个百分点。

但在 AG2 的 GPT-4 配置里，新拓扑没有取得同样提升；论文报告该比较的 $p=0.4$，未显示统计显著，而改进 Prompt 的结果更好。

**因此，不存在从这组实验直接推出的“循环图永远优于 DAG”或“再加一个验证 Agent 就必然可靠”。应根据失败分布选择干预，再测量目标错误是否减少。**

<a id="chapter-10"></a>
## 10. Beyond the Leaderboard：连“成功是怎样测出来的”也要检查

> **与讲义的关系**：将故障分析扩展到跨任务组合能力、安全和测量有效性。  
> **核心参考**：[R5，§3–9](#source-r5)。

### 10.1 这是一份文献综合，不是一个新 Agent 算法

该文说明自己是一项 narrative synthesis，而非按预注册协议开展的正式系统综述。作者综合了 27 篇基准、分类和审计论文，覆盖 19 个不同基准或评估框架，归纳六类失败。[R5，§3，pp. 3–5](#source-r5)

它的重要作用是建立问题地图，而不是提供一个已经由作者统一复现的横向排行榜。作者明确表示，汇总数字来自各底层研究，没有独立复现全部实验。[R5，§9，p. 14](#source-r5)

本文因此主要使用它的分类、论证和评估提醒，不把其中的模型排名、年份趋势或安全比例当作对当前系统的新测量。

### 10.2 六类失败与前面材料怎样对应？

| 综述类别 | 核心问题 | 与本课其他材料的连接 |
|---|---|---|
| Tool Invocation and Parameter-Level Failures | 调错工具、参数、格式，或误解输出 | 讲义工具层；AgentDebug Action 与 System |
| Planning and Constraint-Satisfaction Failures | 子目标各自合理，整体约束却不能同时满足 | 讲义任务合同；AgentDebug Planning |
| Long-Horizon Degradation and Context Management | 长任务中失去目标、状态、有效上下文 | 记忆生命周期、MemGPT、错误传播 |
| Multi-Agent Coordination Failures | 角色、信息、假设和交接不一致 | MAST |
| Safety and Security Failures | 动作可执行，却不安全或没有适当授权 | 讲义隔离与持久化注入风险 |
| Measurement Validity Problems | 分数未必测量真实能力和任务完成 | 验收定义、评测污染、预算口径 |

来源：[R5，§4，pp. 5–9](#source-r5)。

这六类不替代讲义的五层，也不替代 AgentErrorTaxonomy 或 MAST。不同分类回答不同层次的问题，应保留原始框架的用途。

### 10.3 子技能不能自动组合：为什么这是跨论文的共同问题？

RAG 能检索出有帮助的片段，不保证其适用性。MemGPT 能查询键值，不保证执行足够多次关联。工具能正确执行一个动作，不保证状态前提正确。审稿 Agent 能判断文本自洽，不保证全部任务约束已满足。

综述将这种差异概括为子技能能力与组合任务成功之间的缺口。[R5，§4.2、§7.2，pp. 6、12](#source-r5)

所以，不能用“函数调用准确率很高”代替多轮业务成功率，也不能用“记忆问答分数提高”代替长任务可靠性。

### 10.4 更多上下文、更多 Agent、更多计算的收益为什么不稳定？

综述把额外脚手架的收益描述为 uneven，而不是一致正向或一致负向。[R5，§7.4，p. 12](#source-r5)

前面的原始研究提供了具体例子：

RAG 中增加检索文档，对 RAG-Sequence 与 RAG-Token 的影响不同。[R1，§4.5，p. 8](#source-r1)

MemGPT 增加了可访问的外部历史，但仍依赖模型执行正确的读取与停止策略。[R2，§3.2，pp. 6–8](#source-r2)

MAST 的新拓扑在不同系统配置上的收益不同。[R4，附录 H，pp. 26–27](#source-r4)

Overthinking 中，候选集的 Pass@K 上升，实际选择结果未必上升。[R6，图 3，p. 2](#source-r6)

这些结果没有互相推翻，而是共同说明：**额外资源要作用在真实瓶颈上。缺证据、缺状态管理、缺恢复、缺选择器，不是同一种问题。**

### 10.5 测量本身也可能出错

综述讨论测试集污染、解答泄漏、测试不充分与成本不透明等问题。[R5，§4.6、§8.1，pp. 9、13](#source-r5)

对业务系统，类似问题包括：把历史验收答案提前放进记忆库；只检查 JSON 完整却不检查证据；只展示一次成功；不同版本给予不同预算；只统计自动完成的简单任务，忽略被排除的复杂样本。

这些例子是本文的工程对应，不是综述直接评测过的基金案例。

### 10.6 能力、安全、稳定性与可预测性应分别观察

系统能正确调用工具，不代表能抵抗不可信内容；可以安全暂停，不代表已经完成任务；平均完成率较高，也不代表相同条件下每次都稳定。[R5，§7.5、§8.3，pp. 12–13](#source-r5)

因此，评价结果至少应把任务完成、误完成、风险事件、人工介入和成本分开。不能把所有指标压成一个数字之后，就失去系统为什么失败的解释能力。

### 10.7 本章的收束：成功必须回到任务合同

RAG 问答准确率、MemGPT 历史回忆、AgentDebug 根因定位、MAST 任务干预、Overthinking 行为评分，分别测量不同东西。

构建系统时，可以借用这些局部评估，但最后仍要回答：**在规定范围、版本、权限和预算下，用户要求的任务究竟有没有完成？**

下面两章将这个问题落实为状态、证据、交接和恢复的数据结构。

<a id="chapter-11"></a>
## 11. 工程整合：一个有证据、有状态、可恢复的 Agent

> **本章属于工程推演。**它整合前面的机制与失败分析，不宣称原论文已经验证了这个金融应用，也不要求采用特定产品或框架。

### 11.1 先确定四种逻辑记录，不急于拆成四个服务

| 记录 | 回答的问题 | 内容 |
|---|---|---|
| Evidence / 原始证据 | 实际看到了什么？ | 原材料、片段、表格、工具响应、时间和来源版本 |
| Fact Memory / 事实记忆 | 当前可以基于什么信息判断？ | 实体、属性、值、范围、有效期、验证状态、来源 |
| Execution State / 执行状态 | 系统确实运行到哪里？ | 子任务、检查点、预算、阻塞、待完成动作 |
| Experience Memory / 经验记忆 | 哪些经过验证的经验可复用？ | 失败原因、修复动作、适用条件、例外与回归结果 |

它们可以共用关系数据库和文件存储。拆分的是责任和语义，不一定是部署单元。

最需要防止的转换错误是：计划被当成完成；猜测被当成观测；工具执行成功被当成业务核验成功；一次采纳被当成普遍规则。

### 11.2 开始执行前，写出任务合同

讲义要求在任务开始时定义 done 和不变量。[L06，pp. 25、30](#source-l06)

对贯穿案例，任务合同可以规定：材料版本、目标基金与份额、数据期间、需要核验的项目、允许的数据来源、输出要求，以及最终如何判定完成。

例如：

> 本任务只生成预审核建议，不执行对外发布。每条确定性建议必须带原文位置与相应依据；涉及业绩事实的判断必须核对目标实体、份额、期间和口径。未核验项必须保留为未核验，不能包装成通过。任务是否完成，按照这份合同中列出的必要检查项判断。

这是一份工程验收约定，不是法律条文。真实法规和审核规则应由实际业务规则库与业务人员确认。

“只生成建议的任务已完成”和“材料获准发布”是不同状态。不要把发布授权强行算作所有预审核任务的完成条件，也不能用预审核完成自动推出发布授权。

### 11.3 每一步都区分观察、验证与提交

一个可恢复的主循环可以是：

```text
读取任务合同与执行检查点
→ 根据权限、时间和范围读取相关记忆
→ 组织本轮上下文
→ 提出下一步动作
→ 校验权限、参数和前置条件
→ 执行工具
→ 记录原始响应和实际状态
→ 验证这一步产生的结论
→ 提交已确认的状态变化
→ 更新检查点
→ 满足任务验收后结束，否则继续或明确阻塞
```

失败的原始结果也要记录，因为它是诊断依据。但失败后生成的猜测，不应自动进入已确认事实。

例如，接口超时后可以记录“本次调用超时”；不能提交“该基金没有业绩记录”，因为后者不是前者的逻辑结论。

### 11.4 让错误停在“事实晋升”之前

工具返回 C 类数据时，可以保存这条观测，但在目标 A 类任务中应阻止“业绩核验通过”的状态转换。

```text
取得记录
→ 产品身份检查
→ 份额检查
→ 期间检查
→ 口径检查
→ 计算与结论核验
```

找到一个真实数字，仅代表完成了取数过程中的一部分，不代表所有前提成立。

程序能够精确检查的字段，不必让模型每次自由判断。模型仍可解释语义和发现异常，但不应取代确定性的身份、版本和状态校验。

### 11.5 工具需要表达五种不同结果

讲义特别强调区分 empty 与 failed。[L06，p. 28](#source-l06)

本示例可进一步设计：

| 状态 | 语义 | 后续处理 |
|---|---|---|
| OK | 调用完成，返回了约定范围内的数据 | 检查数据是否适用于任务 |
| EMPTY | 调用完成，在明确范围内无匹配项 | 记录查询范围，不扩大成全局不存在 |
| PARTIAL | 只完成一部分范围或分页 | 继续读取，或限制可作出的结论 |
| ERROR | 明确失败，并有错误原因 | 判断是否允许重试或需改变策略 |
| UNKNOWN | 外部动作是否完成尚不明确 | 先查状态，不盲目重复有副作用动作 |

PARTIAL 和 UNKNOWN 是本文为工程场景提出的额外区分，不是讲义原有枚举。

EMPTY 也需要知道查询了什么、权限能看什么、是否读完全部分页。缺少这些前提时，“没有查到”不能等同于“客观不存在”。

### 11.6 验证必须绑定版本，不能只保存一个“通过”标签

昨天的材料通过，不代表今天修改后的材料也通过。类似地，更换了数据快照、规则版本或模型生成的产物，之前的验证可能已不再适用。

因此，验证记录应绑定它实际检查的对象：材料版本、数据版本、规则版本、产物版本和具体检查项。

```text
原始事实 F1 被确认不适用于当前任务
→ 依赖 F1 的比较 C1 失效
→ 依赖 C1 的建议 S1 需要重算
→ 对 S1 的审核记录也失效
→ 最终任务状态重新变为待处理
```

这比把记忆中的某个字符改掉更重要。修改上游事实不会自动修复所有已生成下游结果。

对依赖关系不清楚的任务，保守地重新验证更大范围可能更合适；不能假装依赖图天然完整。

### 11.7 检查点要保存能恢复的状态，不只是对话

一个可用的检查点至少应让系统知道：当前任务版本、已确认事实、已完成与未完成步骤、产物位置与版本、外部动作状态、剩余预算，以及待处理的阻塞。

恢复时还要重新确认环境是否变化。保存模型上下文不能保证外部文件、数据库、网页或服务状态没有改变。

这将 MemGPT 的上下文管理和讲义的 checkpoint 区分开：前者主要管理模型本次可见信息；后者需要支撑整个任务状态的恢复。

### 11.8 内部回滚不等于撤销外部世界

读取文档通常可以重新读取；本地草稿可以通过版本恢复；已经发送的消息、已发布的内容或已修改的外部数据，不会因恢复聊天记录自动撤销。

生产恢复应该分别考虑：内部状态恢复、外部动作状态查询、幂等重试、补偿动作和人工介入。

最典型的风险是发布请求超时：它可能没有成功，也可能已经成功只是响应丢失。此时应该先查外部状态，而不是直接再次发布。

幂等标识需要由执行系统和外部服务共同支持。仅在 Prompt 中要求“不要重复”，并不能建立这样的保证。本文不宣称任何给定工具天然具备幂等能力。

### 11.9 什么时候重试，什么时候诊断，什么时候停？

| 场景 | 优先动作 | 不应做的事情 |
|---|---|---|
| 无副作用的暂时网络故障 | 在预算内退避重试 | 一次超时就形成永久经验 |
| 字段或口径不匹配 | 回查证据、修正查询或状态 | 用更流畅的文字掩盖不匹配 |
| 多次相同动作无新结果 | 检查原因、改变策略或诊断 | 无限循环调用 |
| 外部动作状态未知 | 查询状态或转人工 | 盲目重复有副作用动作 |
| 缺少必要授权 | 明确暂停 | 为了测试环境而越权执行 |
| 无法满足验收且预算耗尽 | 保存检查点，报告未完成部分 | 伪造完成状态 |

这是根据讲义的预算、工具错误和恢复原则提出的处理表，不是经实验得出的统一阈值策略。

### 11.10 人工反馈闭环：先作为案例，再考虑晋升为规则

采纳／拒绝反馈应和原建议、材料版本、人工修改、反馈理由一并记录。

第一层用途是相似案例检索：让未来任务看到原情境。

第二层用途才是通用经验或规则晋升：确认适用条件、例外、支持案例和回归测试后，决定是否扩大使用范围。

这条链路避免“上次被采纳的答案，下次继续照搬”。系统积累的是可验证的处理方法，而不是一串脱离上下文的结论。

## 12. 数据结构与执行流程示例

> **本章全部是教学接口与数据示例。**字段名不对应某个已部署产品的真实 SDK，也不代表完整生产实现。示例中的实体、数值和标识均为虚构。

### 12.1 任务合同：明确实体、范围与完成条件

```json
{
  "task_id": "review-001",
  "task_version": 1,
  "objective": "生成基金业绩表述的预审核建议",
  "document": {
    "id": "material-demo",
    "version": "doc-v3"
  },
  "target": {
    "fund_id": "fund-demo",
    "share_class": "A",
    "period_start": "2026-01-01",
    "period_end": "2026-06-30",
    "return_basis": "example-basis-v1"
  },
  "required_checks": [
    "entity_match",
    "share_class_match",
    "period_match",
    "return_basis_match",
    "evidence_support"
  ],
  "constraints": {
    "publish_allowed": false,
    "unverified_claims_must_be_labeled": true
  },
  "acceptance": {
    "all_required_checks_resolved": true,
    "every_determinate_finding_has_evidence": true
  }
}
```

实际业务里的 `resolved` 需要明确含义：一个问题可以被确认通过、确认存在风险，或被判定无法完成核验。后者是否允许结束“建议生成任务”，由任务合同规定；不能把它误记成核验通过。

### 12.2 工具结果：保留范围、版本和部分成功

```json
{
  "call_id": "call-017",
  "status": "OK",

    "fund_id": "fund-demo",

```

### 12.8 主循环伪代码：模型决定建议动作，程序保护边界

以下是控制流伪代码，不是可以直接运行的 SDK：

```text
加载任务合同、权限、预算与检查点

循环直到预算耗尽：
    核对任务和外部状态是否仍匹配检查点
    读取有权限、在本任务范围内有效的记忆
    组装任务要求、当前状态、观测与必要证据
    请求模型提出下一步动作

    如果模型请求结束：
        运行任务验收
        如果合同要求已满足：
            保存最终产物和验证记录
            结束
        否则：
            将未满足项返回模型或进入阻塞状态
            继续

    校验动作的权限、类型、参数与前置条件
    对有副作用动作记录执行意图与幂等信息
    执行动作并记录原始结果

    如果状态是 UNKNOWN：
        查询外部执行状态；无法确认时转人工
    否则如果发生可重试的暂时故障：
        在预算内按策略重试
    否则如果发现语义或状态冲突：
        产生诊断假设
        校验恢复范围和权限
        使受影响结果失效，并从合适检查点继续
    否则：
        验证结果
        提交已确认状态，并保存检查点

若无法完成：
    保存检查点、阻塞原因和未完成项
    明确返回未完成或部分完成，而不是伪造成功
```

该流程综合讲义的预算、证据、工具失败表达和恢复思想；RAG 提供检索机制，MemGPT 提供调度启发，AgentDebug 提供诊断组织方式，MAST 提供交接和终止检查，Overthinking 提醒系统回到真实反馈，Beyond the Leaderboard 则约束最终验收。

## 13. 评估：既测“记得住”，也测“会不会记错、用错和误报完成”

> **材料依据**：讲义的记忆评估、MAST 的故障分布分析、AgentDebug 的定位与恢复指标、Overthinking 的行为评估，以及综述的测量有效性提醒。  
> **本章中的业务测试设计和公式口径属于工程提议，不是已经执行过的实验。**

### 13.1 讲义已有的四个评估层面

| 层面 | 讲义列出的指标 |
|---|---|
| Retrieval | Precision、Recall |
| Writes and update | Precision、Recall、Stale-memory rate |
| Governance | Deletion compliance、Scope isolation |
| System | Latency、Token overhead、Store growth |

来源：[L06，p. 19](#source-l06)。

讲义第 20 页还列出 LoCoMo、LongMemEval、BEAM 等记忆评估，主要覆盖历史回忆、时间推理、更新、偏好和拒答。这些是讲义对相关基准的概述，不是本文新增的基准复现，也不能用它们直接替代工具执行与恢复测试。[L06，p. 20](#source-l06)

### 13.2 业务系统应同时观察哪些指标？

| 维度 | 建议观察的内容 | 为什么不能省略 |
|---|---|---|
| 写入质量 | 事实与来源一致率、错误归纳率、重复率 | 写错后可能长期复用 |
| 读取质量 | 必要信息召回、无关信息引入、范围和时态错误 | 相似资料不一定适用 |
| 证据质量 | 具体结论是否得到具体证据支持 | 答案正确与依据充分不同 |
| 状态质量 | 完成、未完成、失败、未知是否区分正确 | 状态误判会改变后续路径 |
| 诊断质量 | 步骤、模块、错误类型定位；根因假设的验证结果 | 调试器本身可能犯错 |
| 恢复能力 | 检测后恢复成功率、恢复成本、恢复副作用 | 发现错误不等于能修复 |
| 完成判断 | 误完成率、验收覆盖率 | 声称完成可能掩盖漏检 |
| 安全与治理 | 越权、泄漏、删除、注入持久化 | 能力提升不自动等于安全 |
| 系统代价 | 总延迟、工具次数、模型费用、人工复核 | 局部成绩不能脱离预算 |

### 13.3 三个值得单独保留的工程指标

**误完成率**关注所有宣布完成的运行中，实际未满足验收的比例：

$$
\operatorname{FalseCompletionRate}=\frac{\#\text{宣布完成但验收未满足}}{\#\text{宣布完成}}
$$

当没有任何运行宣布完成时，应标记为无可用分母，而不是机械记成 0%。它也必须与任务完成率一起报告，防止“永远不宣布完成”获得虚假的好成绩。

**检测后恢复率**关注已经发现且允许恢复的失败中，有多少在预算内恢复并最终通过相关验收：

$$
\operatorname{RecoveryRate}=\frac{\#\text{检测后成功恢复且通过验收}}{\#\text{检测到且允许恢复的失败}}
$$

这不能替代整体检测率。只检测最简单的错误，即使恢复率高，也可能留下大量未发现的问题。

**记忆引入回退**关注不需要历史信息的任务，在加入记忆后是否变差。应比较同一任务集在有无记忆下的完成、错误、延迟与成本，不能只在需要记忆的样本上报告收益。

### 13.4 测试集需要包含什么情境？

| 情境 | 期望行为 |
|---|---|
| 关键信息出现在很早的交互中 | 找到原始信息，不能只凭模糊摘要猜测 |
| 新事实修正旧事实 | 当前任务使用适用版本，保留必要历史 |
| 查询过去某天的状态 | 区分有效时间与系统当时已知信息 |
| 相似基金或不同份额 | 精确匹配实体与份额，不被相似名称误导 |
| 用户或项目边界不同 | 无权限记忆不进入可用上下文 |
| 一次性的任务偏好 | 不自动变成永久偏好 |
| 人工采纳一个特殊案例 | 保留情境，不直接晋升普遍规则 |
| 要求删除一条信息 | 原始数据、摘要、索引、缓存和衍生记录一致处理 |
| 当前任务不需要记忆 | 不无谓检索或引入旧偏好 |
| 工具返回 EMPTY | 只对明确查询范围作不存在判断 |
| 工具返回 PARTIAL | 不把部分数据当作全部数据 |
| 有副作用动作超时 | 先查状态，不盲目重复执行 |
| 运行在中途被打断 | 从可核对的检查点恢复 |
| 旧事实被更正 | 依赖它的结论与验证同步失效 |
| 外部文档包含诱导指令 | 保持数据身份，不升级为高权限指令 |
| 某个子 Agent 未返回 | 显示缺失或阻塞，不假装完成 |

这些测试不一定需要复杂仿真。优先从明确可判定的任务、数据快照和故障注入开始，更容易知道改善发生在哪里。

### 13.5 四个版本的消融：知道收益来自哪里

| 版本 | 配置 | 主要检验问题 |
|---|---|---|
| A | 无长期记忆，但保留当前任务状态 | 基础流程是否已经稳定？ |
| B | 所有历史直接进入检索 | 粗放引入记忆的净收益与干扰是什么？ |
| C | 选择性写入、来源、范围、时态与冲突控制 | 记忆治理是否改善了 B 的故障？ |
| D | 在 C 上加入版本化验证、检查点与针对性恢复 | 检测恢复机制是否带来额外收益？ |

固定任务集、模型版本和可比预算，记录每次实际消耗，重复运行而不是只展示一次演示。

C 优于 B，才支持记忆治理的贡献；D 优于 C，才支持恢复机制的贡献。即使 D 更好，也要检查它是否只用了更多工具调用或更高总成本。

### 13.6 更有诊断性的四组干预实验

#### A. 直接提供正确记忆

在离线诊断实验中，用人工确认的正确实体、份额、期间和状态替换原记忆。若结果明显改善，瓶颈可能在写入、检索或选择；若仍失败，应继续看推理、工具、动作与验收。

这里的人工答案只用于诊断，不允许混进正式测试运行的可检索记忆，避免形成评测泄漏。

#### B. 原始数据相同，只改变摘要

比较“业绩数据已获取”与“已取得 C 类；目标是 A 类；目标核验未完成”。观察后续行为，而不只给摘要流畅度打分。

这个实验直接测试压缩是否保留了决定动作的信息。

#### C. 模型和角色不变，只改变交接

分别使用自由文本结论与带版本、证据、未完成项的结构化交接。观察是否减少错误实体使用、忽视阻塞和提前终止。

这更接近 MAST 的针对性结构干预，而不是增加角色数量。

#### D. 从同一检查点注入可恢复错误

注入超时、份额不匹配、旧版本事实、分页不完整等故障。分别测检测、诊断、恢复和误完成。

恢复实验必须在允许重放的隔离环境中进行；有真实外部副作用时，应使用受控替代工具或明确的状态模拟，而不是对真实发布动作反复试错。

### 13.7 评测必须防止记忆泄漏

记忆系统尤其容易让先前任务的验收答案进入后面的可用上下文。需要明确哪些信息允许跨会话积累，哪些是独立测试任务。

独立样本应使用相应干净的状态；真正的长会话测试则要保留受控历史，但不能把未来事件或标准答案提前暴露。

任务、材料或同一案例的近似版本，也不应随意分散到“训练经验库”和“测试集”两侧。本文把这些作为工程评测约束，不声称给定基准已经全部采用这种划分。

### 13.8 Judge 的设计要基于可观察证据

借鉴 AgentDebug 和 Overthinking，评估提示应包含清楚定义、任务条件、实际观测和必要证据，而不是只要求“评价质量”。

对根因定位，可以记录模型判断与人工复核分歧。对是否完成，应优先执行可程序化的验收，再由人工或 Judge 处理不能直接形式化的语义部分。

不能假定同一个模型看一遍自己的输出，就提供了独立验证；也不能将低温度配置直接当作结果绝对可重复的保证。

### 13.9 报告结果时，保留分母、版本和预算

每个结果至少交代任务范围、运行配置、尝试次数、计算和工具预算、记忆初始状态、验收方式，以及哪些任务被排除。

分开报告：任务完成、部分完成、安全暂停、误完成、工具／环境失败、人工介入和成本。安全暂停可能是正确控制行为，但不是已经完成原任务。

这一做法与综述建议的任务级、约束级、成本感知和污染检查相呼应。[R5，§8.1，p. 13](#source-r5)

## 14. 整体认识：让记忆成为可靠性的基础，而不是错误放大器

### 14.1 七份材料组成的完整问题链

**RAG**说明知识可以从参数之外取得，检索与生成可以联合优化；但答案与证据之间仍需要检查。

**MemGPT**说明有限上下文可以通过分层存储和主动调度访问更长历史；但调度、摘要和停止也可能失败。

**讲义的记忆生命周期**要求继续追问：什么值得写、怎样表达、由谁拥有、何时有效、如何更新和遗忘。

**AgentDebug**把错误看成有依赖关系的传播过程，强调定位关键前提与针对性恢复，而不只修饰最终答案。

**Overthinking**要求推理回到环境反馈，提醒我们不要用更多内部模拟替代获取缺失证据。

**MAST**说明协作增加了信息交接、角色权限和验收组织问题；多个 Agent 共享一个错误前提，不等于多重独立检查。

**Beyond the Leaderboard**最后追问：任务是否真的完成，是否只是通过了不充分的测量，或者消耗了更多预算。

### 14.2 三个最重要的状态边界

**第一，信息进入长期记忆的边界。**原始观测、来源陈述、模型推断、验证结果和通用经验不应被混成同一种“事实”。

**第二，状态允许下一步动作的边界。**取得一个结果不代表完成目标核验；参数合法不代表实体正确；工具成功不代表任务正确。

**第三，系统宣布完成的边界。**完成必须对应当前版本的任务合同与验收，不能由模型一句“已经完成”决定。

这三个边界清楚，记忆才不容易把猜测固定下来，恢复也才知道应该撤回哪些依赖结果。

### 14.3 对常见架构问题的回答

**是不是有 RAG 就有 Memory？**

RAG 是重要读取机制，但完整 Memory 还包含选择性写入、组织、时间、范围、更新、遗忘和所有权。

**是不是长上下文足够大，就不需要记忆调度？**

外部资料总量、单次可见内容和执行状态是不同问题。MemGPT 的启发是管理这些关系，而不是只扩大一个窗口数值。

**是不是给一个反思 Agent 就能修复错误？**

反思也可能误读结果或错误归因。诊断要有证据，恢复要有权限和状态管理，经验晋升要有验证。

**是不是多 Agent 更可靠？**

要看任务分解是否合理、交接是否完整、证据是否独立、验收是否充分。MAST 的实验不支持统一答案。

**是不是推理越少越好？**

不是。Overthinking 关注反馈使用，不只是推理长度。应判断缺的是观测、推理、验证还是恢复。

**“从失败中学习”是不是已经做了 SFT？**

不能混为一谈。RAG 论文确实包含检索器与生成器的联合微调；MemGPT 和 AgentDebug 的这里所述机制主要通过外部记忆、控制流、反馈和后续执行影响行为。AgentDebug 的归档版本说明采用已有模型与提示方法，并未因此证明底座权重已经更新。[R1，§2.4](#source-r1)；[R3，附录 A.1](#source-r3)

### 14.4 面向工程实践的最后一句话

> **不要只设计 Agent 怎样生成下一步，还要设计它依据什么状态生成下一步、这个状态有什么证据，以及状态被证明错误后，系统怎样停止继续相信它。**

可靠性不是要求 Agent 永远不犯错，而是让它不轻易把猜测固化成事实、不把未完成包装成完成、不让一次错误通过记忆和协作无限传播。

### 14.5 自测与回答要点

**问题 1：RAG-Token 的每个输出位置能混合不同文档，为什么还可能漏掉证据？** 候选集合由检索阶段先取得；候选之外的关键文档没有自动参与求和。混合生成分布不能修复检索范围、实体或时间准入错误。

**问题 2：两个候选的检索概率为 0.8、0.2，正确答案生成概率为 0.1、0.9，哪个应被上调？** 责任权重为 $0.08/0.26\approx0.308$ 和 $0.18/0.26\approx0.692$。在固定候选的简化 softmax 推导中，梯度为 $p-r$，所以第二个的分数应上调；这不表示对离散 Top-K 直接求导。

**问题 3：Memory Store 中有正确记录，但 Agent 没用到，是否只需扩大窗口？** 先分清检索未命中、权限／时间过滤、未触发读取、分页提前停止和摘要丢失。扩大窗口不能保证这些控制与语义问题消失。

**问题 4：诊断器认定第 3 步是根因，是否可以直接撤回所有外部操作？** 不可以。先保留诊断假设和证据，检查恢复权限与外部状态。内部依赖可以失效；外部副作用需要状态查询、幂等处理或允许的补偿，无法确认时明确阻塞。

**问题 5：Pass@4 比 Pass@3 高，最低 Overthinking 选择成绩却下降，是否矛盾？** 不矛盾。前者只要求候选中存在成功解，后者还要求代理评分正确挑选。更多候选同时增加选择任务，不能用 oracle 的存在率当实际交付率。

**问题 6：任务收到 C 类数据、目标是 A 类，工具状态该记 ERROR 吗？** 工具可如实记录 OK 和 C 类观测；任务的份额检查记 FAILED、目标核验记 BLOCKED，并继续获取目标数据。混合工具执行与业务验收状态，会掩盖真正的修复位置。

**问题 7：删除了一条向量记录，是否完成遗忘？** 需检查原始事件、摘要、结构化事实、缓存及衍生经验是否仍可重新引入它；停止作为当前事实使用与按要求彻底删除是不同语义。

## 附录 B：实验口径与归档版本中的差异

本附录用于保留材料的边界，不对未检查的代码实现或其他版本作判断。出现不一致时，正文明确说明采用哪个表、图或段落，不静默替作者统一。

### B.1 常见误读对照

| 容易产生的误读 | 应保留的准确解释 |

| RAG-Sequence 只检索一篇文档 | 它检索多个候选，对每个候选支持的完整生成分支求和 |

### B.2 AgentDebug：方法描述并不完全一致

第 5 页 Algorithm 1 写明 Stage 2 使用 LLM 定位，且标注不做 rollout/counterfactuals。第 6 页 §3.2 则描述逐步替换动作进行反事实测试。第 20 页附录提示要求全局分析轨迹，输出关键根因与建议。[R3，pp. 5–6、20](#source-r3)

**处理方式**：不声称全部实验都实现了逐点反事实测试。正文将 LLM 诊断与实际干预验证分开。

### B.3 AgentDebug：摘要性数字与具体表格存在差异

第 7 页表 1 平均 Step 为 45.0%，All 为 24.3%；第 8 页 Findings 框出现 50.0% 与 42.5%。第 6 页一些文字对 GAIA 的比较也与表中基线不完全对应。[R3，pp. 6–8](#source-r3)

**处理方式**：正文引用错误定位实验时明确采用表 1，不把其他数值合成同一个结论。原文“提升 17%／24%”需要区分百分点与相对提升。

论文还在正文强调记忆与反思的传播重要性，但某些分布图中 Planning 的计数很高。传播影响与标签出现次数不是同一指标，不应把它们混写成“记忆错误在所有统计中最多”。

### B.4 MAST：样本范围、干预配置与百分比

图 1 的 1,642 条轨迹与图 4 的 210 条子集使用不同分布比例，不能混用。表 5 中 ProgramDev-v0 从 25.0 到 40.6 是增加 15.6 个百分点。[R4，pp. 2、8、27](#source-r4)

AG2 的某个新拓扑比较未显示统计显著，与 ChatDev 的改善不矛盾；它说明收益依赖系统、底座和任务。原文的组织解释与经验结果有价值，但不是某种拓扑的普遍最优性证明。

### B.5 Overthinking：轨迹数量存在两个记载

摘要和第 2 页写 4,018 条轨迹，第 6 页 Results 写 3,908 条。[R6，pp. 1–2、6](#source-r6)

**处理方式**：不替作者选择一个所谓真实总数。正文说明研究分析约四千条轨迹并保留差异；需要精确复现时，应另核对具体数据和代码，而本文没有声称完成了这一步。

### B.6 Overthinking：正文比例与表格均值不一致

第 7 页表 4 中，o1 Low 为 2.774，o1 High 为 2.426，和正文“高 35%”不对应。表 2 的推理／非推理模型均值为 3.505 与 2.228，也不支持第 2 页“近三倍”的直接均值比较。[R6，pp. 2、7](#source-r6)

**处理方式**：保留方向性观察和具体均值，不照搬不对应的比例，不猜测它是否来自其他未说明的分组。

### B.7 Overthinking：性能与成本改善的参照项不同

两候选方案的 27.3% 对 21.0% 是相对提高 30%；800 美元对 1,400 美元是成本降低约 43%。前者参照低预算单次尝试，后者参照高预算单次尝试。[R6，pp. 2–3、8](#source-r6)

**处理方式**：正文列出全部参照配置。实际生产成本评估还要记录选择器与验证器等开销，不能把历史配置成本当成当前单次任务价格。

### B.8 综述：汇总结果不等于统一条件下复现

Beyond the Leaderboard 明确说明自己是 narrative synthesis，没有独立复现所有底层实验，部分数据来自不同版本、不同任务设置与不同测量方式。[R5，§3、§9，pp. 3、14](#source-r5)

**处理方式**：主要用于提供分类和论证地图。对当前真实系统的收益、安全或成本，不直接套用它汇总的比例。

### B.9 哪些内容属于本文件的教学推导？

第 1 章的状态模型，第 2 章的候选责任与梯度推导，第 6 章的简化检测恢复概率，以及第 8 章的候选选择概率分解，均是教学解释。

其中概率和梯度的假设已经在相应位置说明；它们不是论文实验增益，也不是保证某个业务系统成功率的预测公式。

第 11–13 章的数据结构、任务合同、依赖失效、幂等恢复与业务评测，是工程整合建议。文中没有声称它们已经部署、跑过测试或获得了量化收益。

## 附录 C：关键术语表

| 术语 | 本文中的含义 | 使用时的边界 |
|---|---|---|
| Context window | 本次模型调用可以访问的输入工作空间 | 不等于全部持久化历史 |
| Parametric memory | 存在于模型参数中的知识 | 不等于可查询的项目状态表 |
| Non-parametric memory | 模型参数之外、可检索的知识或记录 | 存在于库中不等于已被读取 |
| Working Context | MemGPT 中固定容量、可通过函数修改的核心信息区 | 不是无限工作内存 |
| Recall Storage | MemGPT 的历史消息存储 | 读取仍需要函数与上下文装载 |
| Archival Storage | MemGPT 的外部长期文本存储 | 不能自动保证事实正确与时态有效 |
| Memory pressure | 上下文容量接近阈值时的提示 | 具体阈值属于实现配置 |
| Heartbeat | MemGPT 中工具完成后请求继续推理的控制信号 | 不表示新的用户授权 |
| Provenance | 信息来源及其证据链 | 一个来源的多个摘要不是独立证据 |
| Valid time | 事实在哪段时间适用 | 不等于系统何时获知 |
| Recorded time | 系统记录或获知信息的时间 | 本文的工程扩展字段 |
| Consolidation | 合并重复信息、处理冲突和归纳经验 | 不能把假设自动晋升为事实 |
| Staleness | 过期信息被当成当前有效信息使用 | 旧信息可能仍适用于历史查询 |
| Task contract | 任务范围、约束、权限与验收的明确表达 | 本文工程术语，不是法律合同判断 |
| Error propagation | 错误经由状态和决策依赖继续扩散 | 不等于各步骤独立随机出错 |
| Critical error | 对最终失败有关键影响的错误位置或原因 | 不一定是最早的小错，也不一定只有一个 |
| Re-rollout | 从特定状态重新展开后续执行 | 不自动恢复外部世界 |
| Checkpoint | 用于恢复的执行状态快照或记录 | 仅保存聊天文本可能不足 |
| Verification gap | 能生成候选，却不能可靠识别哪个完成任务 | 增加候选数不一定缩小它 |
| Pass@K | K 个候选中至少存在一个成功解的比例或相应估计 | 不是实际选择器交付正确答案的比例 |
| Overthinking | 内部推理过度替代必要的环境交互 | 不能仅用 token 数定义 |
| Inter-Agent Misalignment | Agent 之间信息、假设或行动衔接失败 | 不必解释为具有主观欺骗意图 |
| False completion | 未满足验收却宣布完成 | 应与完成率和暂停率联合报告 |
| Idempotency | 重复同一业务操作不重复产生不期望的效果 | 需要执行系统支持，不是 Prompt 保证 |
| Compensation | 对已发生的外部副作用采取允许的补偿动作 | 不一定能完全恢复原世界状态 |
